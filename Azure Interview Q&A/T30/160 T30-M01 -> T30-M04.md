# **T30-M01. What is an error budget?**

**Answer:**

An error budget is the **amount of unreliability a service is allowed to have while still meeting its SLO**.

If my availability SLO is **99.9%**, then the service is allowed to be unavailable or unsuccessful for the remaining **0.1%** of the measurement window.

So:

```text
Error Budget
=
100% - SLO
```

For a 30-day period:

```text
30 days
= 43,200 minutes

SLO = 99.9%

Allowed unreliability
= 0.1%

Error budget
≈ 43.2 minutes
```

The value of an error budget is not just the calculation. It gives engineering teams a practical way to balance **reliability against change velocity**. If the service is comfortably within its budget, the team can generally continue shipping changes. If the budget is being consumed rapidly, reliability work becomes more important. If it is exhausted, the team may temporarily reduce risky changes and focus on restoring reliability.

---

## **How it relates to SLI and SLO**

The sequence is:

```text
SLI
→ what we actually measure

SLO
→ target for that SLI

Error Budget
→ how much failure is acceptable
   before violating the SLO
```

Example:

```text
SLI:
99.93% successful requests

SLO:
99.90%

Error budget:
0.10%

Current remaining margin:
0.03%
```

The team is still meeting the SLO, but it has consumed much of the allowed unreliability.

---

## **Request-based error budget**

For an API, error budgets are often easier to reason about using requests rather than minutes.

Suppose:

```text
Monthly valid requests
= 10,000,000

SLO
= 99.9% success
```

Allowed failures:

```text
10,000,000 × 0.001
= 10,000 failed requests
```

So the error budget is:

```text
10,000 allowable failed requests
```

If 8,000 have already failed:

```text
80% of budget consumed
```

even if the calendar month is only half finished.

---

## **Time-based vs request-based**

Two common approaches are:

### Time-based

```text
Service available
-----------------
total measured time
```

Useful when availability is naturally measured as uptime.

### Request-based

```text
good requests
-------------
valid requests
```

Often better for APIs because users experience **requests**, not infrastructure uptime.

For example:

```text
API process is technically running
but returns 500 for every request
```

Time-based host uptime could look excellent.

Request success SLI would correctly show the service as broken.

---

## **Why error budgets are useful**

Without an error budget, operations and development often argue like this:

```text
Operations:
"We need maximum reliability."

Developers:
"We need to ship quickly."
```

Error budgets turn that conflict into measurable policy.

```text
Reliability comfortably above SLO
        ↓
budget available
        ↓
continue normal release velocity

Reliability degrading
        ↓
budget burning quickly
        ↓
increase caution / reliability work

Budget exhausted
        ↓
reduce risky change
        ↓
focus on restoring reliability
```

This creates a shared engineering language.

---

## **Example in Azure**

Suppose an API runs on:

```text
Azure Front Door
      ↓
Application Gateway
      ↓
AKS
      ↓
Azure SQL
```

SLO:

```text
99.95% of valid API requests
must succeed
over rolling 30 days
```

Telemetry from:

```text
Application Insights
Azure Monitor
Prometheus
```

can be used to calculate the SLI.

If the error budget burns quickly after an AKS deployment:

```text
new release
   ↓
5xx increases
   ↓
error-budget burn increases
```

that is a strong signal that the release is harming reliability.

The response might be:

```text
Stop rollout
↓
rollback or fix forward
↓
stabilize service
↓
resume normal delivery
```

---

## **Burn rate is more useful than waiting for exhaustion**

Suppose the service has a monthly error budget of:

```text
43 minutes
```

and consumes:

```text
20 minutes
```

in the first hour.

Waiting until all 43 minutes are consumed is a poor operational strategy.

Instead, teams often monitor **error-budget burn rate**:

```text
How fast are we consuming
the allowed unreliability?
```

High burn rate:

```text
short severe outage
```

Low burn rate:

```text
small persistent degradation
```

Both can matter.

---

## **Error budget does not mean planned downtime allowance**

A dangerous interpretation is:

> “We still have 20 minutes of error budget, so we are allowed to cause a 20-minute outage.”

No.

The budget is a **reliability-management mechanism**, not permission to waste customer availability.

The goal is still to operate reliably.

The budget helps answer:

```text
How much operational risk
can the team reasonably take?
```

---

## **Error budget and deployments**

A sensible policy might be:

```text
Budget > 75% remaining
→ normal deployment cadence

Budget between 25–75%
→ investigate trend / increase caution

Budget nearly exhausted
→ restrict risky releases

Budget exhausted
→ reliability work takes priority
```

These thresholds are organizational choices, not universal SRE laws.

---

## **What can consume the budget?**

Potentially:

```text
Application failures
Bad deployments
Dependency failures
Infrastructure failures
Networking failures
Database outages
Capacity exhaustion
```

But whether every failure counts depends on the exact SLI definition.

For example, you must decide whether:

```text
HTTP 400 from invalid user input
```

counts against the SLO.

Usually you want the SLI to measure **service-caused failures**, not invalid client behavior.

---

### **Interview answer condensed**

> “An error budget is the amount of unreliability a service can tolerate while still meeting its SLO. If the SLO is 99.9%, the error budget is the remaining 0.1%. For an API that could mean a certain number of failed requests, or for time-based availability it could mean roughly 43 minutes in a 30-day month. The useful part is operational: if the budget is healthy, teams can continue normal delivery; if it burns quickly or is exhausted, reliability work and safer change management take priority.”

**Memory line:**
**SLO defines how reliable we want to be; error budget defines how much failure we can tolerate before missing that target.**

**Interview trap:**
An error budget is **not permission to deliberately consume downtime** just because some budget remains.

**Keywords:**
Error budget, SLO, SLI, reliability, allowable failure, burn rate, change velocity, failed requests.

**Likely follow-ups:**

* How would you calculate an error budget for a 99.99% SLO?
* What is error-budget burn rate?
* What should happen when the budget is exhausted?
* Would client-generated 4xx errors count against an API error budget?

# **T30-M02. What is the difference between availability and reliability?**

**Answer:**

Availability is about **whether the service is accessible and usable when users need it**, while reliability is the broader ability of the system to **perform correctly and consistently over time, including during failures and recovery**.

So availability is one part of reliability.

A service can be highly available but still unreliable. For example, an API may respond 100% of the time but frequently return incorrect data, time out, or fail transactions. It is technically reachable, but users cannot depend on it.

```text
Reliability
├── Availability
├── Correctness
├── Resilience
├── Recoverability
└── Consistency
```

---

## **Availability asks: “Is it up?”**

Typical availability SLI:

```text
successful requests
-------------------
valid requests
```

or:

```text
available time
--------------
total measured time
```

Example:

```text
Service reachable
99.95% of month
```

That is an availability measurement.

---

## **Reliability asks a broader question**

Reliability asks:

> Can users depend on the system to behave correctly over time, including under failures, load, maintenance, and recovery?

That can include:

```text
Availability
Correctness
Durability
Failure tolerance
Recovery
Dependency resilience
Operational stability
```

---

## **Example 1 — Available but unreliable**

Suppose:

```text
API endpoint responds:
HTTP 200
```

for every request.

But 15% of responses contain stale or incorrect data.

Then:

```text
Reachability:
Excellent

Correctness:
Poor
```

So the system might look available but still be unreliable.

---

## **Example 2 — Fast recovery improves reliability**

Suppose two systems each experience a VM failure.

### System A

```text
VM fails
 ↓
manual ticket
 ↓
engineer responds
 ↓
2 hours later service restored
```

### System B

```text
VM fails
 ↓
health probe detects failure
 ↓
traffic moves to healthy replica
 ↓
service continues
```

System B is more reliable because failure has much less user impact.

---

# **Availability is usually a measurable outcome**

Example:

```text
Requests:
1,000,000

Successful:
999,500
```

Availability:

```text
99.95%
```

Reliability may include additional SLIs such as:

```text
99.95% successful
99% < 500 ms
99.999% durable writes
```

A workload can therefore have multiple reliability objectives.

---

# **Azure example**

Consider:

```text
Azure Front Door
      ↓
AKS
      ↓
Azure SQL
```

Availability controls might include:

```text
multiple Pods
multiple nodes
Availability Zones
health probes
load balancing
```

Reliability also considers:

```text
retry behavior
database failover
backup/restore
deployment safety
dependency timeouts
data correctness
disaster recovery
```

So simply adding:

```text
three replicas
```

does not make the entire workload reliable.

---

# **Availability vs durability**

Another useful distinction.

Availability:

```text
Can I access the data now?
```

Durability:

```text
Will the data remain intact
after failures?
```

A Storage Account could temporarily be unavailable but still preserve every byte of data.

Conversely, a badly designed application could be constantly reachable but corrupt data.

So durability also contributes to overall reliability.

---

# **High availability isn't automatically high reliability**

Suppose an application runs across:

```text
Zone 1
Zone 2
Zone 3
```

but every replica depends on:

```text
one misconfigured database
```

Then:

```text
zone redundancy
+
single shared failure
=
still unreliable
```

This is why architecture reviews have to follow the dependency chain end-to-end.

---

# **Reliability also includes recovery**

Suppose the whole Azure region is lost.

A highly available single-region workload may not survive that failure.

Reliability planning asks:

```text
Can we recover?
How long?
How much data can we lose?
```

That brings in:

```text
RTO
RPO
Backups
Geo-replication
DR runbooks
```

Availability alone doesn't fully answer those questions.

---

## **Practical interview example**

If an interviewer asks:

> “Our API has 99.99% uptime. Is it reliable?”

I would say:

> “Not enough information.”

I would also want to know:

```text
Does it return correct responses?
What is latency?
How often do transactions fail?
Can it tolerate dependency failures?
Can it recover from data loss?
How are deployments handled?
```

Only then can I assess reliability properly.

---

### **Interview answer condensed**

> “Availability tells me whether a service is reachable and usable when needed, usually measured as successful requests or uptime. Reliability is broader: it includes availability, but also correctness, resilience, recoverability, and consistent behavior under failure. A system can therefore be highly available but unreliable—for example if it responds to every request but returns incorrect data or repeatedly loses transactions. In Azure I would evaluate availability through redundancy and health probes, but reliability also requires resilient dependencies, safe deployments, backup, disaster recovery, and correct application behavior.”

**Memory line:**
**Availability is ‘is it up?’; reliability is ‘can users depend on it to work correctly over time?’**

**Interview trap:**
High availability does **not automatically mean high reliability**.

**Keywords:**
Availability, reliability, correctness, resilience, recoverability, redundancy, durability, RTO, RPO.

**Likely follow-ups:**

* Can a system be available but not reliable?
* Is durability the same as availability?
* How would Availability Zones improve availability but still leave reliability gaps?
* What metrics would you use to measure reliability beyond uptime?

# **T30-M03. What is observability?**

**Answer:**

Observability is the ability to **understand the internal state and behavior of a system from the telemetry it produces**, so that when something goes wrong I can investigate *why*, not just know that something is broken.

Monitoring typically tells me:

```text
CPU is high
API is returning 5xx
latency increased
```

Observability should help me answer:

```text
Which service is causing it?
Which dependency is slow?
Which requests are affected?
Did a deployment trigger it?
Which region or version is impacted?
```

The main telemetry signals are usually **logs, metrics, and traces**, combined with useful context such as resource metadata, deployment version, region, pod, node, correlation ID, or request ID.

```text
Application / Infrastructure
        ↓
 ┌──────┼───────┐
 ↓      ↓       ↓
Logs  Metrics  Traces
 └──────┼───────┘
        ↓
Azure Monitor / observability platform
        ↓
Dashboards
Alerts
Queries
Correlations
        ↓
Understand system behavior
```

---

## **Monitoring vs observability**

These concepts overlap, but there is a useful distinction.

### Monitoring

Usually answers predefined questions:

```text
Is CPU > 80%?
Is the endpoint down?
Are there 5xx errors?
```

### Observability

Helps investigate questions you may **not have predicted in advance**:

```text
Why are only users in one region slow?
Why did latency increase only for one API version?
Which downstream service caused this trace to stall?
```

So:

```text
Monitoring
→ known failure signals

Observability
→ ability to explore system behavior
```

Monitoring is part of observability.

---

# **The three common telemetry signals**

```text
Logs
→ discrete events with detail

Metrics
→ numerical measurements over time

Traces
→ request journey across components
```

These work best together.

---

# **Example incident**

Users report:

> Checkout is slow.

### Metrics show

```text
checkout p95 latency
300 ms → 3.5 sec
```

This confirms:

```text
performance degraded
```

but doesn't tell me why.

### Trace shows

```text
Frontend: 50 ms
Checkout API: 80 ms
Payment API: 3,100 ms
Database: 40 ms
```

Now I know:

```text
Payment service
```

is where most time is spent.

### Payment logs show

```text
Timeout calling external provider
```

Now I have:

```text
Metric
→ tells me something is wrong

Trace
→ isolates the slow dependency

Log
→ gives detailed failure evidence
```

That is observability in practice.

---

# **Azure observability example**

A common Azure path might be:

```text
AKS / App Service / Functions
        ↓
Application telemetry
        ↓
Azure Monitor
        ↓
Application Insights
        ↓
Log Analytics
        ↓
Dashboards / alerts / queries
```

For Kubernetes, additional systems could include:

```text
Managed Prometheus
Azure Managed Grafana
Container Insights
OpenTelemetry
```

depending on the architecture.

The important point is not which dashboard product is used.

The important question is:

> Can I correlate symptoms across layers quickly enough to find the failure?

---

# **Context makes telemetry useful**

A log such as:

```text
"Request failed"
```

is weak.

A better log includes:

```text
timestamp
service
environment
request ID
trace ID
deployment version
status code
dependency
duration
```

Then I can correlate it with other telemetry.

For example:

```text
traceId = abc123
```

appears in:

```text
frontend log
API log
payment-service log
distributed trace
```

Now troubleshooting becomes much faster.

---

# **Cardinality matters**

Observability can become expensive and difficult if you attach uncontrolled dimensions.

For metrics, something like:

```text
user_id
request_id
```

as a metric label can create extremely high cardinality.

Example:

```text
10 million users
×
100 endpoints
```

can explode the number of metric time series.

Better:

```text
service
region
status class
endpoint category
deployment version
```

where appropriate.

High-cardinality detail often belongs in logs or traces rather than every metric label.

---

# **Observability must be designed, not added after the outage**

Bad approach:

```text
Production outage
       ↓
"No logs"
       ↓
"Let's add telemetry now"
```

Better:

```text
Architecture
      ↓
Define SLIs
      ↓
Instrument application
      ↓
Collect telemetry
      ↓
Dashboards + alerts
      ↓
Production
```

Instrumentation should be part of the design.

---

# **OpenTelemetry**

OpenTelemetry is especially useful in distributed systems because it provides vendor-neutral APIs/SDKs and conventions for producing telemetry.

Conceptually:

```text
Application
   ↓
OpenTelemetry instrumentation
   ↓
logs / metrics / traces
   ↓
collector/backend
```

Then the telemetry can be exported to an appropriate observability platform.

This reduces tight coupling between application instrumentation and one backend.

---

# **Observability and alerting**

Observability doesn't mean:

```text
collect everything
+
alert on everything
```

Good alerts should focus on user-impacting or actionable conditions.

For example:

```text
5xx rate > SLO threshold
```

is usually more useful than:

```text
CPU briefly hit 81%
```

unless the CPU condition is directly actionable.

---

# **Troubleshooting flow**

Suppose:

```text
API latency increased
```

A sensible observability workflow is:

```text
1. Metrics
   ↓
Confirm scope and timing

2. Traces
   ↓
Identify slow service/dependency

3. Logs
   ↓
Inspect detailed cause

4. Infrastructure telemetry
   ↓
CPU / memory / network / DB

5. Deployment/change history
   ↓
Correlate with release/config change
```

This is much stronger than randomly opening logs from every service.

---

# **Observability vs telemetry**

Telemetry is the raw data.

```text
Logs
Metrics
Traces
```

Observability is the **capability created by meaningful telemetry plus correlation, querying, and operational context**.

So:

```text
Huge log volume
≠
good observability
```

You can collect terabytes and still be unable to answer basic questions.

---

### **Interview answer condensed**

> “Observability is the ability to infer what is happening inside a system from the telemetry it emits. Monitoring can tell me that latency or error rate is bad; observability should let me investigate why—for example which service, dependency, region, or deployment is responsible. I normally build that around logs, metrics, and distributed traces, with consistent metadata and correlation IDs. In Azure that can involve Azure Monitor, Application Insights, Log Analytics, Managed Prometheus, Grafana, and OpenTelemetry. Good observability is about being able to troubleshoot unknown failure modes, not simply collecting more data.”

**Memory line:**
**Monitoring tells me something is wrong; observability helps me explain why.**

**Interview trap:**
Collecting a huge volume of logs does **not automatically mean the system is observable**.

**Keywords:**
Observability, monitoring, telemetry, logs, metrics, traces, Application Insights, Azure Monitor, OpenTelemetry, correlation ID.

**Likely follow-ups:**

* What's the difference between monitoring and observability?
* Why are distributed traces useful in microservices?
* What is metric cardinality and why does it matter?
* How would you investigate an API latency spike using observability data?

# **T30-M04. What are logs, metrics, and traces?**

**Answer:**

Logs, metrics, and traces are the three main telemetry signals used in observability, and each answers a different kind of question.

**Logs** are detailed event records, such as an exception or authentication failure.

**Metrics** are numerical values measured over time, such as CPU usage, request rate, error percentage, or latency.

**Traces** show how a single request travels through multiple components and where time or failures occur.

I normally use them together:

```text
Metric
→ tells me there is a problem

Trace
→ tells me where it happened

Log
→ tells me detailed context about why
```

---

# **1. Logs**

Logs are discrete event records.

Example:

```text
2026-09-06T10:20:31Z
service=payment-api
level=ERROR
trace_id=abc123
dependency=stripe
error="request timed out"
duration_ms=5000
```

Logs are very good for:

```text
Exceptions
Authentication failures
Deployment messages
Audit details
Application events
Detailed debugging context
```

---

## **Structured logs are better than free-form logs**

Weak:

```text
"Payment failed again"
```

Better:

```json
{
  "service": "payment-api",
  "environment": "prod",
  "traceId": "abc123",
  "statusCode": 504,
  "dependency": "payment-provider",
  "durationMs": 5000
}
```

Structured logs can be filtered and aggregated much more easily.

For example:

```text
Show all:
statusCode = 504
AND
service = payment-api
AND
deploymentVersion = v2.7.1
```

---

# **2. Metrics**

Metrics are numeric measurements over time.

Examples:

```text
CPU = 72%
memory = 4.3 GB
requests/sec = 1,200
error rate = 2.1%
p95 latency = 850 ms
queue depth = 17,000
```

Metrics are ideal for:

* dashboards,
* trends,
* alerts,
* capacity analysis,
* SLI calculations.

They are much cheaper and faster to aggregate than reading millions of individual logs.

---

## **Types of useful metrics**

Common conceptual types include:

### Counter

Only increases over time.

```text
total HTTP requests
```

### Gauge

Can increase or decrease.

```text
CPU
queue depth
active connections
```

### Histogram/distribution

Used for values such as:

```text
request latency
payload size
```

which lets you calculate percentiles such as:

```text
p50
p95
p99
```

---

# **3. Traces**

A distributed trace follows a request through a distributed system.

Example:

```text
User request
     ↓
Frontend
50 ms
     ↓
Checkout API
100 ms
     ↓
Inventory API
40 ms
     ↓
Payment API
2,900 ms
     ↓
External Payment Provider
2,700 ms
```

Now instead of simply knowing:

```text
overall request = 3 seconds
```

I can see:

```text
payment-provider dependency
consumed most of the time
```

---

## **Trace and span**

A trace represents:

```text
entire request journey
```

A span represents:

```text
one operation within that journey
```

For example:

```text
Trace abc123
│
├── Span: frontend
├── Span: checkout-api
├── Span: inventory-api
└── Span: payment-api
      └── Span: external-payment-call
```

Each span can contain:

* start/end time,
* service,
* operation name,
* status,
* attributes,
* parent/child relationship.

---

# **How they complement each other**

Suppose users say:

> “Checkout is failing.”

### Metric

```text
checkout error rate
0.2% → 8%
```

This confirms scope and timing.

### Trace

```text
failed requests
      ↓
payment-api
      ↓
external-provider call
      ↓
timeout
```

This localizes the problem.

### Log

```text
trace_id=abc123
provider=payments-x
timeout=5s
retry_count=3
```

This gives deeper detail.

Together:

```text
Metrics
→ WHAT / HOW MUCH

Traces
→ WHERE

Logs
→ WHY / DETAIL
```

That mental model is extremely useful in interviews.

### Metrics

```text

```

# **Infrastructure logs vs application logs**

Don't mix these carelessly.

### Control-plane log

Example:

```text
Azure Activity Log:
Who deleted the VM?
```

### Resource/service log

Example:

```text
Key Vault access audit
```

### Application log

Example:

```text
Order creation failed
```

They answer different questions.

---

# **Metrics are not enough for debugging**

Suppose metric shows:

```text
5xx = 8%
```

It tells me a failure exists.

But it doesn't necessarily tell me:

```text
which customer?
which request?
which exception?
which dependency?
```

Logs/traces provide that context.

---

# **Logs are not ideal for everything either**

Suppose I have:

```text
500 million request logs
```

and want:

```text
p95 API latency over 24 hours
```

Calculating that repeatedly from raw logs can be expensive and inefficient.

A metric or histogram is usually a better source for dashboards and alerts.

---

# **Tracing has cost too**

Tracing every single request in a massive system can generate significant telemetry volume.

Therefore production systems may use:

```text
sampling
```

Examples:

```text
100% of errors
+
small percentage of successful requests
```

or adaptive strategies depending on the observability backend.

You need enough traces for diagnosis without unlimited cost.

---

# **Correlation is key**

The three signals become much more useful if they share context.

For example:

```text
trace_id = abc123
service = checkout
version = 2.4.8
region = centralindia
```

Then:

```text
Metric alert
      ↓
trace
      ↓
matching logs
```

can all be tied together.

---

# **Example production investigation**

Symptom:

```text
API p99 latency increased
```

I would use:

```text
1. Metrics
   ↓
Which endpoint?
Which region?
When did it start?

2. Traces
   ↓
Which service/span contributes delay?

3. Logs
   ↓
What error or dependency behavior occurred?

4. Deployment metadata
   ↓
Did a new version deploy at the same time?
```

That is a practical observability workflow.

---

# **Data-retention and cost**

Telemetry has financial and compliance implications.

Logs can become expensive because of:

```text
ingestion
storage
retention
query volume
```

Metrics are generally compact.

Traces can become large at scale.

So I design retention by value:

```text
Hot operational logs
→ shorter retention

Audit/security logs
→ retention based on compliance

High-volume debug telemetry
→ sampled or reduced
```

rather than retaining everything indefinitely.

---

### **Interview answer condensed**

> “Logs, metrics, and traces are complementary observability signals. Logs are detailed event records such as exceptions or audit events. Metrics are numerical time-series values such as CPU, request rate, error percentage, or p95 latency and are ideal for dashboards and alerts. Traces follow a single request across distributed services and show where time or failures occurred. In an incident I often use metrics to identify what changed, traces to isolate where the problem is, and logs to inspect the detailed cause. Correlation IDs and consistent metadata let those signals work together.”

**Memory line:**
**Metrics show what changed, traces show where it happened, and logs provide the detailed context behind it.**

**Interview trap:**
Logs, metrics, and traces are **not interchangeable**—each is optimized for a different type of operational question.
