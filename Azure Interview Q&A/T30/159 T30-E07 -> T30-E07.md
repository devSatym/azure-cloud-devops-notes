# **T30-E07. What is security?**

**Answer:**

In the Azure Well-Architected Framework, security means **protecting the workload's confidentiality, integrity, and availability by controlling identities, access, network exposure, data protection, and threat detection throughout the system lifecycle**.

In practice, I would use controls such as Microsoft Entra ID, Managed Identities, least-privilege Azure RBAC, Key Vault, encryption, NSGs, Private Endpoints where appropriate, Defender for Cloud, logging, and continuous security monitoring.

The important point is that security is **layered**. I don't rely on a single control such as a firewall.

```text
Identity
   ↓
Authentication
   ↓
Authorization
   ↓
Network controls
   ↓
Secrets / data protection
   ↓
Logging & detection
```

---

## **Core security goals**

A useful model is the CIA triad:

```text
Confidentiality
→ only authorized users/services can access data

Integrity
→ data/configuration cannot be changed improperly

Availability
→ systems remain available to legitimate users
```

For example:

```text
Key Vault + RBAC
→ Confidentiality

Signed artifacts + controlled CI/CD
→ Integrity

Multi-zone deployment + DDoS protection
→ Availability
```

Security therefore isn't only about preventing data theft.

---

## **Identity comes first**

For Azure workloads I would normally prefer:

```text
Managed Identity / Workload Identity
```

over:

```text
stored usernames/passwords
long-lived client secrets
```

Example:

```text
AKS workload
     ↓
Workload Identity
     ↓
Microsoft Entra ID
     ↓
Key Vault
```

No secret needs to be embedded in the application for Azure authentication.

---

## **Authentication vs authorization**

Very important:

```text
Authentication
→ Who are you?

Authorization
→ What are you allowed to do?
```

A workload may successfully authenticate using Managed Identity but still receive:

```text
403 Forbidden
```

because the identity lacks the correct Azure RBAC or data-plane role.

So:

```text
Valid identity
≠
permission to every Azure resource
```

---

## **Network security**

Security also considers exposure.

For sensitive PaaS services I may prefer:

```text
Application
    ↓
Private DNS
    ↓
Private Endpoint
    ↓
Key Vault / Storage / SQL
```

rather than exposing the service publicly.

But:

```text
Private Endpoint
without correct Private DNS
```

can still result in connectivity failures.

---

## **Secrets and data**

Secrets should normally live in:

```text
Azure Key Vault
```

rather than:

```text
source code
pipeline YAML
Docker image
plain parameter file
```

For data, I consider:

* encryption at rest,
* encryption in transit,
* key ownership requirements,
* access controls,
* backup protection.

---

## **Detection matters too**

Preventive security alone isn't enough.

I also need:

```text
Azure Monitor
Activity Logs
Defender for Cloud
Microsoft Sentinel where applicable
application/security logs
```

because eventually I need to answer:

> Who changed this resource?

or:

> Was this identity used suspiciously?

---

## **Security is a shared responsibility**

Azure secures the underlying cloud platform, but the customer is still responsible for many things such as:

* identities,
* RBAC,
* application vulnerabilities,
* network configuration,
* secrets,
* data,
* workload configuration.

The exact responsibility split depends on whether the service is IaaS, PaaS, or SaaS.

---

**Memory line:**
**Security is layered protection of identity, access, network exposure, secrets, data, and detection—not just a firewall.**

**Interview trap:**
Successful authentication does **not** mean successful authorization, and private networking does **not** replace identity controls.

**Keywords:**
Security, confidentiality, integrity, availability, Microsoft Entra ID, Managed Identity, Azure RBAC, Key Vault, Private Endpoint, Defender for Cloud.

# **T30-E08. What is an SLA?**

**Answer:**

An SLA, or **Service Level Agreement**, is a formal commitment from a service provider about the level of service they expect to provide, usually expressed as an availability percentage such as **99.9% or 99.99%** over a defined measurement period.

In Azure, Microsoft publishes SLAs for eligible services and configurations. If the service fails to meet the SLA conditions, the customer may be eligible for a service credit according to the specific SLA terms.

The important distinction is that an Azure service SLA is **not the same as the SLA of my complete application**.

```text
Azure component SLA
        ↓
contributes to
        ↓
Application architecture
        ↓
Application availability
```

---

## **Example**

Suppose a service has:

```text
99.9% monthly availability
```

A common approximation for maximum monthly unavailability over a 30-day month is:

```text
30 days
= 43,200 minutes

0.1% × 43,200
≈ 43.2 minutes
```

So roughly:

```text
99.9%
→ about 43 minutes/month
```

By comparison:

```text
99.99%
→ about 4.3 minutes/month
```

This is a useful interview approximation, but the actual SLA calculation and exclusions depend on the provider's contract.

---

## **SLA isn't an outage guarantee**

A common misconception:

```text
99.99% SLA
=
Azure guarantees the service can never exceed ~4 minutes of outage
```

Not exactly.

An SLA is a **contractual service commitment** with specific measurement rules and exclusions.

If it isn't met, the usual contractual remedy is:

```text
service credit
```

not:

```text
Azure somehow prevents the outage from happening
```

---

## **Application SLA can be lower than component SLA**

Suppose an application requires two dependent services:

```text
App
├── Service A: 99.9%
└── Service B: 99.9%
```

If both are required for every request, overall theoretical availability is approximately:

```text
0.999 × 0.999
= 0.998001
≈ 99.8001%
```

So combining dependencies can reduce end-to-end availability.

This becomes especially important in architecture interviews.

---

## **Architecture can also improve availability**

Suppose two independent instances are arranged redundantly:

```text
Instance A
     \
      → Load balancing / failover
     /
Instance B
```

Then application availability may be higher than a single instance's availability, depending on:

* independence of failures,
* failover design,
* shared dependencies.

So you should never calculate application availability by simply reading one Azure product's SLA.

---

## **SLA vs SLO**

```text
SLA
→ contractual commitment

SLO
→ internal reliability target
```

For example:

```text
Customer SLA = 99.9%

Internal SLO = 99.95%
```

The internal target is often stricter so the team has safety margin before violating the customer commitment.

---

**Memory line:**
**An SLA is the formal service commitment; it is not automatically the same as your application's real end-to-end availability.**

**Interview trap:**
Two dependencies each having a 99.9% SLA does **not mean the whole application also has a 99.9% SLA**.

**Keywords:**
SLA, Service Level Agreement, availability, service credit, downtime, dependency, contractual commitment.

# **T30-E09. What is an SLI?**

**Answer:**

An SLI, or **Service Level Indicator**, is the actual measurable signal used to determine how well a service is behaving from the user's perspective.

Examples include:

```text
request success rate
availability
latency
throughput
correctness
```

For an API, a useful SLI might be:

> **Percentage of valid requests that return successfully within 500 ms.**

So:

```text
SLI
= what I measure
```

while:

```text
SLO
= the target I set for that measurement
```

---

## **Example: availability SLI**

Suppose during one month:

```text
Valid requests = 1,000,000
Successful requests = 999,500
```

Then:

```text
SLI
= successful / valid requests

= 999,500 / 1,000,000
= 99.95%
```

That **99.95%** is the observed SLI value.

---

## **Example: latency SLI**

Suppose we define:

> Requests completed in less than 300 ms.

Then:

```text
950,000 requests < 300 ms
out of
1,000,000 valid requests
```

SLI:

```text
95%
```

That number can then be compared with an SLO.

---

## **SLIs should represent user experience**

Weak SLI:

```text
VM CPU < 70%
```

Why weak?

Because a user doesn't care directly whether CPU is 40% or 80%.

They care:

```text
Did my request succeed?
Was it fast enough?
```

CPU is useful as an operational metric, but not necessarily the best service-level indicator.

Better:

```text
99.9% of checkout requests succeed
```

or:

```text
95% of requests complete within 300 ms
```

---

## **Example with Azure**

For an application monitored with Application Insights / Azure Monitor:

```text
Application requests
      ↓
Request telemetry
      ↓
Calculate:
├── success rate
└── latency
```

Then those measurements become the basis for SLI reporting.

---

## **Good SLI characteristics**

A good SLI should be:

* measurable,
* meaningful to users,
* consistently defined,
* based on reliable telemetry.

For example, define exactly:

```text
What counts as a valid request?
Which status codes count as success?
Are client errors included?
Which percentile or threshold?
What measurement window?
```

Otherwise teams can calculate different “availability” values from the same service.

---

## **SLI vs metric**

Every SLI is derived from measurement, but not every metric is a useful SLI.

For example:

```text
pod memory usage
```

is an operational metric.

```text
percentage of requests successfully completed
```

is much closer to a service-level indicator.

---

**Memory line:**
**An SLI is the number I actually measure to represent service reliability or user experience.**

**Interview trap:**
A raw infrastructure metric such as CPU utilization is **not automatically an SLI**; good SLIs usually reflect something users actually experience.

**Keywords:**
SLI, Service Level Indicator, availability, latency, success rate, user experience, telemetry, measurement.

# **T30-E10. What is an SLO?**

**Answer:**

An SLO, or **Service Level Objective**, is the target value a team sets for an SLI over a defined time window.

For example, if my SLI is:

> Percentage of successful API requests,

my SLO might be:

> **99.9% of valid requests should succeed over a rolling 30-day period.**

So:

```text
SLI
→ what we measure

SLO
→ what level we aim to achieve
```

SLOs are fundamental in SRE because they translate a vague requirement like “the API should be highly available” into something measurable and actionable.

---

## **Example**

SLI:

```text
successful requests
-------------------
valid requests
```

SLO:

```text
>= 99.9%
over 30 days
```

Observed this month:

```text
99.96%
```

Therefore:

```text
SLI result = 99.96%

SLO target = 99.9%

Status = meeting objective
```

---

## **An SLO must include a time window**

This is important.

Saying:

```text
"Our availability target is 99.9%"
```

is incomplete.

Better:

```text
"99.9% availability
over a rolling 30-day window"
```

because reliability calculations need a measurement period.

---

## **SLO vs SLA**

```text
SLO
→ engineering/internal target

SLA
→ external/contractual commitment
```

For example:

```text
Customer SLA
= 99.9%

Internal SLO
= 99.95%
```

Why make the SLO stricter?

Because if the team targets exactly the SLA boundary:

```text
99.900%
```

even a small reliability regression can breach the contractual commitment.

The extra margin creates operational safety.

---

## **SLO drives reliability decisions**

Suppose:

```text
Internal portal
SLO = 99.5%
```

A single-region deployment might be acceptable.

But:

```text
Payment API
SLO = 99.99%
```

may require stronger:

* zone redundancy,
* database HA,
* failover,
* resilient dependencies,
* deployment controls.

Therefore:

```text
Architecture
should follow reliability requirements
```

not:

```text
add multi-region because it sounds impressive
```

---

## **SLO and error budget**

If:

```text
SLO = 99.9%
```

then the allowed unreliability is:

```text
100% - 99.9%
= 0.1%
```

That:

```text
0.1%
```

becomes the basis of the **error budget**.

Conceptually:

```text
SLI
→ actual reliability

SLO
→ target reliability

1 - SLO
→ allowable unreliability / error budget
```

The next question in the bank builds directly on this concept.

---

## **Example API SLO**

A meaningful SLO could be:

```text
Availability:
99.95% of valid API requests succeed
over rolling 30 days

Latency:
99% of successful API requests
complete within 500 ms
over rolling 30 days
```

This is much stronger than:

```text
"The API should be fast and reliable."
```

because it is measurable.

---

## **Don't blindly choose 100%**

A 100% SLO sounds attractive, but it can create unreasonable engineering cost and discourage normal change.

If the business genuinely requires extremely high availability, design for it.

But don't select:

```text
100%
```

without considering:

* architecture,
* dependency SLAs,
* maintenance,
* cost,
* complexity.

SRE uses SLOs partly to define the **appropriate reliability level**, not infinite reliability.

---

**Memory line:**
**SLI is the measured number; SLO is the reliability target we promise ourselves to meet over a defined period.**

**Interview trap:**
An SLO should not be chosen arbitrarily or automatically set to 100%; it should reflect user expectations and business value.

**Keywords:**
SLO, Service Level Objective, SLI, SLA, target, measurement window, reliability, error budget.
