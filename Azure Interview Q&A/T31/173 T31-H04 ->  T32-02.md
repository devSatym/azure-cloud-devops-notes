# **T31-H04. What would your rollback strategy be if a production migration failed?**

**Answer:**

My rollback strategy would be **designed and tested before the migration starts**, not invented after the cutover fails.

I would define explicit rollback triggers such as critical business transactions failing, unacceptable error rate or latency, data-integrity problems, authentication failures, or the new Azure environment not meeting agreed SLOs.

For a stateless workload, rollback may be relatively straightforward: keep the original environment healthy, preserve its configuration, and redirect traffic back through DNS, Front Door, or the load-balancing layer.

For a stateful workload, rollback is much harder because once users write new data to Azure, simply sending traffic back to the old database can lose or split those transactions. Therefore, before cutover I would design the **data failback strategy**—for example continuous reverse replication where supported, a controlled write freeze, or reconciliation of the new transactions before reactivating the source.

My rule would be:

```text
Failed cutover
     ↓
Stop further change
     ↓
Protect data
     ↓
Decide within predefined rollback window
     ↓
Restore source as authoritative
     ↓
Redirect traffic
     ↓
Validate
     ↓
Investigate afterward
```

Microsoft's current Cloud Adoption Framework recommends keeping the source environment available as a fallback throughout the stabilization period so traffic and previous configurations can be restored if critical issues appear. ([Microsoft Learn][1])

---

## **1. Define rollback criteria before migration**

I don't want this discussion during an outage:

> “Should we keep debugging for another hour or roll back?”

Before migration I'd define something like:

```text
ROLL BACK if any of these occur:

Critical checkout flow fails
OR
5xx > 5% for 5 minutes
OR
p95 latency > 2 seconds for 10 minutes
OR
data reconciliation fails
OR
authentication unavailable
OR
critical dependency unreachable
```

And equally importantly:

```text
Who can declare rollback?
```

For example:

```text
Incident commander
+
Application owner
```

with one person having clear final authority if required.

---

# **2. Establish a rollback window**

Rollback becomes more complicated as time passes.

Immediately after cutover:

```text
Few/no new writes
→ rollback relatively easy
```

Several hours later:

```text
Thousands of new writes
→ rollback much harder
```

Therefore I define a period such as:

```text
First 15–30 minutes:
fast rollback decision window
```

followed by:

```text
stabilization period:
heightened monitoring
```

The exact duration depends on the workload.

---

# **3. Preserve the source environment**

I would not:

```text
Cut over to Azure
       ↓
Delete VMware environment
```

on migration day.

Instead:

```text
Source environment
├── powered/ready as required
├── configuration preserved
├── credentials available
├── network path intact
└── rollback documented
```

Microsoft specifically recommends retaining the source as a fallback while the Azure workload stabilizes. ([Microsoft Learn][1])

# **4. Stateless rollback is comparatively simple**

Suppose:

```text
Internet
   ↓
DNS / Front Door
   ↓
Azure application
```

and the application has no state local to Azure.

If Azure deployment fails:

```text
Traffic
   ↓
switch back
   ↓
on-prem application
```

Potential mechanisms:

```text
Front Door backend priority/weight
Load balancer configuration
DNS change
```

Then validate:

```text
health endpoint
login
critical business transactions
latency
errors
```

Still, DNS caching can delay rollback if DNS is the switching mechanism.

---

# **5. Stateful rollback is the difficult part**

Consider:

```text
Source DB
   ↓ replication
Azure DB
```

At T0:

```text
Azure becomes writer
```

Then users create:

```text
Order 1001
Order 1002
Payment 1003
```

If at T+20 minutes I simply switch traffic to the old source:

```text
Old DB
doesn't contain those transactions
```

Now I have:

```text
data loss
```

or inconsistent business state.

So rollback planning must answer:

> **How does data created after cutover return to the original source?**

---

# **6. Prevent split brain**

One of the most dangerous migration failures is:

```text
Source accepting writes
+
Target accepting writes
```

at the same time.

Then:

```text
Customer A writes source
Customer B writes Azure
```

and neither database has the complete truth.

I therefore establish an explicit writer transition:

```text
Source writable
      ↓
Quiesce writes
      ↓
Final synchronization
      ↓
Source read-only/off
      ↓
Target becomes writer
```

If rollback occurs:

```text
Target writes stopped
      ↓
data reconciled/reverse-synced
      ↓
Source becomes authoritative
```

Never casually operate two independent writable copies of a transactional database.

---

# **7. Decide rollback strategy per data technology**

Possible options include:

### **Option A — Reverse replication**

Where platform/application technology supports it:

```text
Source → Azure
before cutover

Azure → Source
after cutover
```

Then failback can synchronize newer Azure writes.

This is ideal where supported and tested.

---

### **Option B — Short rollback window**

For some systems:

```text
Cut over
      ↓
very short validation window
      ↓
do not allow significant writes
until acceptance tests pass
```

For example:

```text
read-only validation
```

before enabling full write traffic.

This reduces reconciliation complexity.

---

### **Option C — Transaction reconciliation**

For systems where reverse replication isn't practical:

```text
Azure transactions since cutover
      ↓
export / replay / reconcile
      ↓
old source updated
```

This can be complicated and application-specific.

It must be designed before the migration.

# **8. Preserve immutable deployment/configuration artifacts**

Rollback needs a known-good target.

I would keep:

```text
Terraform/Bicep version
Application image/package
Database migration scripts
Configuration
DNS records
Firewall configuration
Connection settings
```

versioned.

For example:

```text
release-v42
→ Azure migration version

release-v41
→ known-good original
```

Not:

```text
"Does anyone remember what config
production had yesterday?"
```

# **9. Database schema changes require special care**

Suppose migration includes:

```sql
ALTER TABLE Orders DROP COLUMN LegacyStatus;
```

and the old application expects that field.

Rolling the application back may fail even if infrastructure is restored.

I therefore prefer **backward-compatible schema migrations** around high-risk cutovers.

Pattern:

```text
Expand
 ↓
deploy compatible schema additions
 ↓
old + new app both work
 ↓
cut over
 ↓
stabilize
 ↓
Contract/remove legacy schema later
```

This is the **expand-and-contract** pattern.


# **11. DNS deserves extra planning**

If current DNS is:

```text
app.contoso.com
→ On-prem public IP
```

and migration changes it to Azure:

```text
app.contoso.com
→ Azure endpoint
```

I would reduce TTL well before cutover.

Example:

```text
72 hours before:
TTL 3600 → 60
```

Then rollback:

```text
DNS → original endpoint
```

can propagate more quickly.

But I still assume:

```text
not every resolver/client obeys TTL perfectly
```

so both environments may receive traffic temporarily.

That means the rollback architecture should tolerate a transition period.

# **12. Roll back the application before doing deep RCA**

Suppose at cutover:

```text
5xx = 40%
```

and the rollback threshold is:

```text
5%
```

I should not spend an hour investigating:

```text
NSGs?
DNS?
SQL?
Connection pools?
```

while customers are failing.

Operational sequence:

```text
Protect customers
      ↓
rollback
      ↓
restore service
      ↓
perform RCA
```

Restoration comes before perfect understanding.

# **13. But don't blindly rollback if rollback is more dangerous**

Suppose Azure is healthy but data has already diverged substantially.

Returning to source could cause:

```text
financial transaction loss
```

In that case the safer path may be:

```text
remain on target
+
fix forward
```

So rollback decisions must compare:

```text
Risk of staying
vs
Risk of rollback
```

especially for stateful systems.

# **14. A practical rollback architecture**

```text
                    Clients
                       │
                       ▼
                Front Door / DNS
                 /             \
                /               \
     Source environment       Azure target
         (fallback)              │
              │                  │
              └──── Data sync ───┘
```

Before cutover:

```text
Traffic → Source
Data → replicated to Azure
```

After cutover:

```text
Traffic → Azure
Source preserved
```

If acceptance fails early:

```text
Stop Azure writes
      ↓
reconcile required changes
      ↓
Traffic → Source
```

# **15. Example rollback runbook**

Assume migration from on-prem app + SQL to Azure.

### **Pre-cutover**

```text
✓ Source backup verified
✓ Azure replication healthy
✓ Rollback DNS value documented
✓ Old connection strings preserved
✓ Application release artifact preserved
✓ DB failback strategy verified
```

### **Cutover**

```text
1. Stop source writes
2. Final synchronization
3. Azure DB becomes authoritative
4. Switch Front Door/DNS
5. Validate
```

### **Failure**

Suppose:

```text
Checkout payment fails
```

Then:

```text
1. Declare rollback
2. Stop new Azure writes
3. Drain Azure traffic
4. Reconcile transactions written after T0
5. Confirm source DB consistency
6. Restore source write capability
7. Switch traffic back
8. Execute critical smoke tests
9. Monitor
10. Freeze migration attempt
```

# **16. Validate rollback itself**

The runbook isn't proven until tested.

Before production I'd perform:

```text
Migration rehearsal
      ↓
simulate failure
      ↓
execute rollback
```

and measure:

```text
Rollback RTO
Data loss / RPO
DNS convergence
Application health
```

If business says:

```text
Migration rollback must restore service
within 15 minutes
```

and rehearsal takes:

```text
47 minutes
```

the plan isn't ready.

# **17. Post-rollback state**

After successfully rolling back:

```text
Source = production again
Azure = isolated
```

I would:

```text
preserve Azure evidence
stop automated writes
collect logs
compare configuration
perform postmortem
fix cause
rehearse again
```

Not immediately attempt a second production cutover because:

> “Maybe it works now.”

## **Interview answer condensed**

> “My rollback strategy would be designed and rehearsed before cutover with explicit health thresholds and one clear go/no-go owner. I would preserve the source environment and its configuration throughout stabilization. For stateless workloads, rollback may simply mean restoring the old backend and redirecting traffic. For stateful workloads, data is the key issue: once Azure accepts writes, I can't safely point users back to an older database without reverse synchronization or reconciliation. I would therefore quiesce writes during authority changes, prevent split brain, preserve backward-compatible schemas where possible, and define how post-cutover transactions get back to the source. If acceptance criteria fail inside the rollback window, I'd restore service first and investigate root cause afterward.”

**Memory line:**
**Traffic rollback is easy; data rollback is what makes production migration rollback hard.**

**Interview trap:**
Keeping the old VM powered on is **not a complete rollback strategy** if the Azure target has already accepted newer state.

**Keywords:**
Rollback, failback, source of truth, split brain, reverse replication, reconciliation, DNS TTL, expand-and-contract, rollback threshold.

**Likely follow-ups:**

* How would you roll back after 10,000 new transactions were written in Azure?
* What is split brain during migration?
* Why use backward-compatible database migrations?
* When would you choose fix-forward instead of rollback?
* How would you prove your rollback plan actually works?

# **T31-H05. How would you modernize a VM-based application into Azure PaaS or container services?**

**Answer:**

I would modernize it **incrementally**, starting with an assessment of what the VM actually provides—application runtime, web server, scheduled jobs, local files, session state, databases, credentials, networking, and operational dependencies.

Then I would choose the **simplest managed target that satisfies the workload**, rather than automatically selecting Kubernetes.

For a standard web application I would first evaluate **Azure App Service**. For containerized applications or APIs that need container semantics and event-driven scaling but not Kubernetes control, I'd evaluate **Azure Container Apps**. I would choose **AKS** when the organization genuinely needs Kubernetes features such as complex orchestration, custom controllers/operators, advanced networking, or a standardized Kubernetes platform.

I would externalize local state, move data toward managed services where appropriate, replace stored credentials with Managed Identity or Workload Identity, implement observability, build CI/CD, test the modernized workload in parallel, then gradually shift production traffic rather than perform a risky big-bang rewrite.

Microsoft's current guidance supports migrating ASP.NET and Java applications to AKS through Azure Migrate and also supports containerizing ASP.NET applications for Azure App Service. ([Microsoft Learn][2])

---

## **1. First understand what's inside the VM**

A VM may look like:

```text
VM01
├── IIS / Nginx
├── Application
├── Local sessions
├── Local uploads
├── Cron / scheduled task
├── Secrets in config
├── Log files
└── DB connection
```

Before choosing a target I ask:

```text
What is the actual workload?
```

Because:

```text
VM
```

is only the current hosting model.

---

# **2. Decompose responsibilities**

Map each VM responsibility to a potential managed capability.

Example:

| VM responsibility    | Possible Azure target                            |
| -------------------- | ------------------------------------------------ |
| Web/API runtime      | App Service / Container Apps / AKS               |
| SQL Server           | Azure SQL Database / Managed Instance            |
| File uploads         | Blob Storage                                     |
| Secrets              | Key Vault                                        |
| Sessions/cache       | Azure Managed Redis / suitable external cache    |
| Scheduled processing | Functions / Container Apps jobs / worker service |
| Messaging            | Service Bus                                      |
| Logs/traces          | Application Insights / Azure Monitor             |

The objective is:

```text
VM as one big operational unit
        ↓
Managed capabilities
with clearer responsibility boundaries
```

Suppose:

```text

   ↓
IIS
   ↓
ASP.NET application
```

```text
     ↓

```

# **4. Containerize only when containerization gives value**

Possible current architecture:

```text
VM
 ↓
Java application
```

Container target:

```text
Docker image
     ↓
ACR
     ↓
Container Apps / AKS
```

Containerization gives:

```text

```

But containerizing an application does **not automatically modernize its internals**.

A container can still contain:

```text

```

So:

```text

```

is often a **replatforming step**, not complete modernization.

# **5. Choose Container Apps when Kubernetes control isn't needed**

A common mistake is:

```text

```

Not necessarily.

Azure Container Apps is attractive for:

```text

```

Conceptually:

```text

 ↓

 ↓

 ↓

```

This keeps operational complexity lower than managing a full Kubernetes platform.

> “I would modernize a VM application incrementally. # **T32-01. Design Azure infrastructure for a three-tier web application.**

**Answer:**

For a production three-tier application, I would separate the architecture into **presentation, application, and data tiers**, give each tier only the connectivity it requires, use managed Azure services where they reduce operational burden, and remove direct public exposure from the backend and database.

A common Azure design would be:

```text
Internet
   ↓
Azure Front Door (optional global edge)
   ↓
Application Gateway + WAF
   ↓
Frontend / Web tier
   ↓
Private application/API tier
   ↓
Private database tier
```

For PaaS, I might use App Service for the web/API tiers and Azure SQL Database for data. For a container platform, the application tier could be AKS or Container Apps.

I would use Microsoft Entra ID and Managed Identity for authentication, Key Vault for any remaining secrets/certificates, Private Endpoints for sensitive PaaS resources, Private DNS for name resolution, Azure Monitor/Application Insights for observability, Availability Zones or zone-redundant service options for production reliability, and Terraform/Bicep for repeatable provisioning.

The central design principle is:

> **Only the entry point should be publicly reachable; internal tiers communicate privately and each tier gets least-privilege network and identity access.**

Microsoft's current web-app reference architecture shows this pattern with Application Gateway/WAF in front of App Service, private endpoints for PaaS services, VNet Integration for outbound web-app traffic, Private DNS, Azure SQL, Key Vault, and Storage. ([Microsoft Learn][5])

# **1. Presentation tier**

The presentation tier serves:

```text
HTML
CSS
JavaScript
user-facing HTTP requests
```

Possible services:

```text
App Service
AKS
Container Apps
```

For a normal business application, I'd usually start by considering **App Service**, because I don't want Kubernetes complexity without a reason.

---

# **2. Application tier**

The backend provides:

```text
business logic
API
validation
orchestration
```

It should normally not be directly exposed to arbitrary internet traffic.

Flow:

```text
Frontend
   ↓
HTTPS
   ↓
Private backend/API
```

Possible hosting:

```text
App Service
Container Apps
AKS
```

depending on workload requirements.

# **3. Data tier**

Typical services:

```text
Azure SQL Database
Azure Database for PostgreSQL
Cosmos DB
Blob Storage
```

depending on the application's data model.

For relational data:

```text
API
 ↓
Azure SQL
```

I would generally:

```text
disable public network access
+
use Private Endpoint
+
use Private DNS
```

where the architecture requires private access.

---

# **4. Public ingress**

For regional Layer-7 ingress:

```text
Internet
   ↓
Application Gateway WAF
```

Application Gateway provides:

```text
TLS termination
host/path routing
health probes
WAF
```

and can route to private-address/FQDN backends. ([Microsoft Learn][6])

WAF helps protect against common web attack patterns such as:

```text

malicious request patterns
```

# **5. Front Door when global edge capability is needed**

For a globally distributed application:

```text

      ↓

      ↓
Regional application
```

Front Door can provide:

```text
global HTTP routing
edge acceleration
WAF
TLS
regional failover
```

Then Application Gateway can still provide regional ingress/security where that layered model is justified.

For a simple single-region application:

```text
Front Door
```

may not be necessary.

Then apply:


according to expected flows.

# **8. Identity flow**

Don't rely only on network trust.

Example:

```text

     ↓
Managed Identity
     ↓
Microsoft Entra ID
     ↓
Azure SQL / Key Vault / Storage
```

Authentication:

```text
Who is the workload?
```

Authorization:

```text
What is it allowed to access?
```

using appropriate data-plane permissions/RBAC.

So even from a valid subnet:

```text
No correct identity/permission
→ access denied
```

Defense in depth.

# **9. Secret management**

with:

```text
 ↓
Azure SQL
```

## **Interview answer condensed**

> “For a production three-tier application I'd separate presentation, application, and data tiers and expose only the ingress layer publicly. A typical design would use Application Gateway with WAF in front of App Service, Container Apps, or AKS for the web tier, a privately reachable API tier, and Azure SQL or another managed database through Private Endpoint. I'd use VNet segmentation, Private DNS, Managed Identity rather than stored credentials, Key Vault where secrets remain, and Azure Monitor/Application Insights for end-to-end observability. I'd run multiple instances or zone-redundant configurations where the SLO requires them, use autoscaling, and provision everything through Terraform or Bicep with CI/CD. Front Door can be added if global routing, edge performance, or regional failover is required.”

**Memory line:**
**Public entry point, private application path, private data tier, identity at every hop.**

**Interview trap:**
Putting the database on a private endpoint does **not** secure the whole application if the backend itself remains directly publicly reachable or uses excessive permissions.

**Keywords:**
Three-tier, Application Gateway, WAF, App Service, AKS, Container Apps, Azure SQL, Private Endpoint, Private DNS, Managed Identity, Key Vault.

* How would you make this multi-region?
* When would you choose AKS instead of App Service?

# **T32-02. How would you deploy a public frontend, private backend, and private database?**

**Answer:**

I would create **one intentional public ingress path** and make both the backend and database privately addressable.

For example, I could expose the frontend through Azure Application Gateway with WAF or Azure Front Door, host the frontend in App Service, and make the backend App Service reachable only through a Private Endpoint. The frontend or regional gateway would resolve that backend through Private DNS.

The backend would use **VNet Integration for outbound traffic** and reach Azure SQL through the database's Private Endpoint. Public network access would be disabled on the backend and database. For authentication, the backend would use Managed Identity with the minimum required database or Azure permissions.

The flow would look like:

```text
Internet
   ↓
Application Gateway + WAF
   ↓
Public frontend
   ↓ private connection
Private backend
   ↓ private connection
Private database
```

Microsoft's current web-app architecture reference uses this same model: Application Gateway/WAF at the edge, App Service with private connectivity, Private Endpoints for PaaS services such as Azure SQL and Key Vault, VNet Integration for App Service outbound connectivity, and Private DNS zones. ([Microsoft Learn][5])

# **1. Public frontend**

The frontend is intentionally internet-accessible.

Possible entry:

```text
Internet
 ↓
Application Gateway WAF
```

or:

```text
Internet
 ↓
Azure Front Door
```

depending on regional/global requirements.

Application Gateway supports a public frontend IP and routes requests to backend pools using Layer-7 routing and health probes. ([Microsoft Learn][7])

# **2. Why put WAF at ingress?**

Because the public attack surface is:

```text
HTTP/HTTPS
```

WAF can apply managed/custom rules for common web threats and request filtering.

Conceptually:

```text
Malicious request
      ↓
WAF
      X
blocked

Valid request
      ↓
application
```

The Azure Architecture Center's current Gatekeeper pattern similarly uses Application Gateway WAF as an outer gatekeeper before private application services. ([Microsoft Learn][8])

# **3. Private backend**

Suppose backend is:

```text
api.contoso.internal
```

hosted on App Service.

Create:

```text
Private Endpoint
      ↓
backend App Service
```

Then disable public network access.

Now:

```text
Internet
   X
Backend
```

while:

```text
VNet/private path
    ↓
Backend
```

works.

Microsoft states that App Service private endpoints can eliminate public exposure when public network access is disabled. ([Microsoft Learn][3])

---

# **4. Private Endpoint means inbound connectivity**

This is a key interview distinction.

For backend App Service:

```text
Private Endpoint
```

means:

> Clients can reach the App Service privately.

It does **not** mean:

> App Service can automatically reach every private resource.

For outbound:

```text
App Service
      ↓
VNet Integration
      ↓
VNet resources/private endpoints
```

Microsoft explicitly says private endpoints handle incoming traffic, while VNet Integration is used to inject App Service outbound traffic into the VNet. ([Microsoft Learn][3])

---

# **5. Private database**

For Azure SQL:

```text
Azure SQL
   ↓
Private Endpoint
   ↓
IP from VNet
```

Then:

```text
Public network access = Disabled
```

Traffic:

```text
Backend
  ↓
VNet Integration
  ↓
Private Endpoint IP
  ↓
Azure SQL
```

Now the database doesn't require public internet exposure.

---

# **6. Private DNS is mandatory to get right**

Backend calls:

```text
mydb.database.windows.net
```

Public DNS normally resolves toward the public service.

With Private Link, DNS should ultimately resolve to:

```text
private endpoint IP
```

through the appropriate Private DNS zone.

Likewise, an App Service private endpoint normally involves the `privatelink.azurewebsites.net` DNS path. Microsoft's reference on private App Service connectivity describes DNS resolving the app's normal hostname through a `privatelink` CNAME to an A record containing the private endpoint address. ([Microsoft Learn][9])

So troubleshooting:

```text
Backend can't reach SQL
```

starts with:

```text
1. DNS resolves private IP?
2. Route/path exists?
3. NSGs/firewall?
4. SQL endpoint reachable?
5. Identity/auth?
```

# **7. Frontend-to-backend flow**

There are several valid architectures.

### **Pattern A — Frontend directly calls private backend server-side**

If frontend is server-rendered / backend-for-frontend:

```text
Browser
  ↓
Public frontend
  ↓
server-side HTTPS
  ↓
Private backend
```

This works because the frontend service participates in the private network path.

---

### **Important browser nuance**

If JavaScript running in the user's browser tries to call:

```text
https://private-backend...
```

directly, the user's internet browser cannot normally reach a private VNet endpoint.

So for a SPA:

```text
Browser
```

usually needs a public-facing gateway/API ingress:

```text
Browser
 ↓
Application Gateway / APIM / Front Door
 ↓
Private backend
```

rather than exposing the backend endpoint directly.

This distinction is very important.

```text
 ↓

 ↓

 ↓

```

API Management can provide:

```text

quotas

versioning
```

while Application Gateway/WAF handles the web ingress/security layer.

The current Azure Gatekeeper pattern describes Application Gateway WAF forwarding approved traffic toward API Management and private App Service backends. ([Microsoft Learn][8])

# **18. Troubleshooting example**

Symptom:

> Frontend works, but API calls fail.

Dependency-first flow:

```text
1. Is backend App Service healthy?
2. Does frontend resolve backend FQDN to private IP?
3. Is frontend using a valid VNet Integration path?
4. Do routes/NSGs permit traffic?
5. Is backend public access correctly disabled but PE approved?
6. Does TLS hostname/certificate validate?
7. Does application authentication succeed?
8. What do App Insights/backend logs show?
```

If DNS resolves public:

```text
private DNS linkage/configuration
```

is a prime suspect.

# **19. Database troubleshooting**

Symptom:

```text
Backend → SQL timeout
```

Order:

```text
1. Resolve SQL hostname
```

Expected:

```text
private IP
```

If public IP:

```text
fix Private DNS
```

Then:

```text
2. Test TCP 1433/path as appropriate
3. Check NSGs/routes/firewall
4. Check private endpoint status
5. Check SQL health
6. Check Entra token/identity
7. Check database authorization
```

This separates:

```text
network failure
```

from:

```text
authentication/authorization failure
```

## **Interview answer condensed**

> “I would expose only an approved ingress layer publicly. A typical design is Application Gateway with WAF in front of the frontend, while the backend App Service has a Private Endpoint and public network access disabled. For App Service, I would use VNet Integration for outbound traffic so the backend can reach Azure SQL through the SQL Private Endpoint. Private DNS must resolve both backend and SQL hostnames to their private addresses. The backend would authenticate to SQL using Managed Identity where supported rather than a stored password. For browser-based SPAs, I wouldn't expect the browser itself to reach a private API; I would expose the API through the approved gateway while keeping the actual backend private. I'd verify the design by proving direct internet access to backend and database fails while the intended private paths succeed.”

**Memory line:**
**Public ingress, private services, private data—and remember: Private Endpoint is inbound, VNet Integration is outbound for App Service.**

**Interview trap:**
A private backend cannot be called directly by ordinary browser JavaScript over the public internet; the browser needs a reachable gateway/API entry point.
