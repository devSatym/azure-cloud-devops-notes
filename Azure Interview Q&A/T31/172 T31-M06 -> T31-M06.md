# **T31-M06. How can databases be migrated to Azure?**

**Answer:**

I would migrate a database to Azure in four broad stages: **assess the source, choose the correct Azure database target, choose an offline or online migration method based on downtime requirements, and validate data and application behavior before cutover**.

For SQL Server, the target might be **SQL Server on Azure VM, Azure SQL Managed Instance, or Azure SQL Database** depending on compatibility and how much modernization I want. Azure Migrate can help assess the SQL estate, while **Azure Database Migration Service, or DMS**, supports database migration scenarios including online migrations designed to minimize downtime.

For a critical database, I would normally seed the target while production continues, continuously replicate changes, monitor replication lag, briefly stop or restrict writes during final synchronization, cut the application connection over to Azure, validate data and transactions, and keep a rollback path until the migration is proven stable. ([Microsoft Learn][1])

```text
Source Database
      ↓
Discovery / Assessment
      ↓
Choose Azure target
      ↓
Compatibility remediation
      ↓
Initial data copy
      ↓
Continuous replication
      ↓
Final synchronization
      ↓
Application cutover
      ↓
Validation
      ↓
Decommission source later
```

## **1. First choose the right Azure target**

For SQL Server, I would normally evaluate three main targets.

```text
SQL Server on-prem
        ↓
 ┌──────┼─────────────────┐
 ↓      ↓                 ↓
SQL VM  SQL Managed       Azure SQL
        Instance          Database
```

### **SQL Server on Azure VM**

Best fit when I need:

* high SQL Server compatibility,
* OS-level control,
* instance-level features,
* minimal application changes.

This is closer to **rehosting**.

### **Azure SQL Managed Instance**

Useful when I want:

* a managed PaaS service,
* high SQL Server instance compatibility,
* less OS/patch/HA administration.

This is typically a **replatforming** choice.

### **Azure SQL Database**

More cloud-native PaaS.

Azure handles much of:

* patching,
* built-in availability,
* infrastructure management,
* scaling capabilities.

But I need to validate whether the application relies on SQL Server instance-level capabilities that don't map directly to SQL Database. Microsoft currently recommends Azure SQL Database where its PaaS model and feature set meet workload requirements. ([Microsoft Learn][2])

Azure Migrate can discover and assess SQL workloads and provide Azure SQL target, sizing, and cost recommendations. ([Microsoft Learn][3])

## **3. Offline vs online migration**

This is one of the most important decisions.

### **Offline migration**

Conceptually:

```text
Stop application writes
       ↓
Backup/export source
       ↓
Move/restore into Azure
       ↓
Validate
       ↓
Point application to Azure
```

Advantages:

* simpler,
* easier consistency model.

Disadvantage:

* longer downtime.

This may be perfectly acceptable if:

```text
maintenance window = 6 hours
```

and the database can be migrated within that window.

---

### **Online migration**

For a business-critical system:

```text
Source stays active
      ↓
Initial synchronization
      ↓
Changes continuously replicated
      ↓
Replication lag approaches zero
      ↓
Short write freeze
      ↓
Final sync
      ↓
Switch application
```

Azure Database Migration Service supports online migrations for supported targets specifically to reduce downtime. ([Microsoft Learn][4])

## **6. Cutover sequence**

For a low-downtime production migration:

```text
1. Initial replication complete
2. Replication healthy
3. Target performance validated
4. Application target connectivity tested
5. Lower DNS TTL beforehand if DNS switch is used
6. Announce maintenance/cutover
7. Stop or restrict source writes
8. Wait for replication lag = 0
9. Verify final synchronization
10. Change connection/routing
11. Start application against Azure target
12. Run smoke/business tests
13. Monitor errors and performance
14. Keep source protected for rollback
```

Microsoft's current Cloud Adoption Framework recommends continuous database replication for near-zero-downtime migrations, monitoring replication lag, and completing final synchronization before traffic cutover. ([Microsoft Learn][5])

### **Interview answer condensed**

> “I would first assess the database and choose the appropriate Azure target—for SQL Server that could be SQL Server on Azure VM, SQL Managed Instance, or Azure SQL Database depending on compatibility and modernization goals. Then I'd choose offline or online migration based on downtime tolerance. For a critical database I'd use continuous replication, validate that replication lag reaches zero, briefly freeze writes for final synchronization, switch the application to the Azure target, and validate both data integrity and real business transactions. # **T31-H01. How would you migrate a critical application with minimal downtime?**

**Answer:**

For a critical application, I would design the migration so that **most data and infrastructure preparation happens while production is still running**, leaving only a very small final synchronization and traffic-switch window.

I would first assess the complete application dependency graph and define measurable **RTO, RPO, maximum cutover downtime, rollback criteria, and success criteria**. Then I would build the Azure target through IaC, establish networking, identity, monitoring and security, replicate servers/data continuously, and perform an isolated test migration.

For final cutover, I would reduce DNS TTL beforehand if DNS is involved, freeze risky changes, verify replication is healthy and lag is near zero, put the source in read-only or stop writes briefly where required, perform final synchronization, redirect traffic, and run automated functional, data-integrity, and performance checks.

I would keep the source environment intact until the new environment has passed the stabilization period. If predefined health thresholds fail, I would stop the cutover and execute the rollback plan rather than troubleshooting indefinitely while customers are impacted. Microsoft's current Cloud Adoption Framework follows this same near-zero-downtime pattern: continuous data replication, final synchronization, traffic switch, validation, and retaining a fallback option during stabilization. ([Microsoft Learn][5])

---

## **1. Define the objective before designing the migration**

“Minimal downtime” is too vague.

I would turn it into:

```text
Maximum user-visible downtime = 5 minutes
RPO = 0–1 minute
RTO = 15 minutes
```

Then define:

```text
Cutover success:
error rate < 1%
p95 <= source baseline + agreed tolerance
critical transactions pass
data reconciliation passes
```

And rollback:

```text
Rollback if:
critical transaction fails
or
5xx > threshold
or
data integrity fails
or
latency exceeds threshold for N minutes
```

This removes debate during the migration.

Example:

```text

  ↓
```

# **7. Avoid connecting the test environment to production blindly**

Suppose the migrated test server starts a scheduled task:

```text

```

or connects to the production message queue.

You could accidentally run production work twice.

Therefore test migration should normally use:

```text

```

where appropriate.

Before cutover capture:

```text

```

Example:

```text

```

```text

```

# **9. Prepare DNS/traffic switching**

If DNS participates in cutover, lower TTL **before** the migration.

For example:

```text
Several days before:
TTL 3600 sec
    ↓
TTL 60 sec
```

Then caches have time to age out before cutover.

But DNS isn't instantaneous even with a low TTL because:

* client caching exists,
* resolver behavior varies,
* existing connections may stay alive.

If possible, a global/load-balancer traffic switch can give more deterministic control.

# **10. Freeze unrelated change**

Before the migration:

```text

```

Don't simultaneously allow:

```text

firewall redesign
database schema migration
identity refactor

```

If something breaks, you want a small hypothesis space.

# **12. Source write control is critical**

Suppose:

```text
Source DB
and
Azure DB
```

both accept independent writes after cutover.

Now you have:

```text

```

Rollback becomes extremely difficult.

During the authority switch:

```text
Source = read-only / writes stopped
       ↓
final sync
       ↓
Target becomes authoritative writer
```

There should be a clear **single source of truth**.

```text

≠

```

For complex stateful apps I still coordinate the application/database properly.

# **16. Maintain fallback**

Do not do:

```text
Cutover successful for 10 min
      ↓
delete on-prem source
```

Keep it available according to an agreed stabilization period and rollback design.

Microsoft migration guidance explicitly recommends maintaining a fallback option after cutover until the Azure workload is proven stable. ([Microsoft Learn][5])

# **17. But rollback becomes harder after writes begin**

This is crucial.

Suppose users have written:

```text
10,000 new orders
```

to the Azure database.

Simply switching DNS back to the old source gives:

```text
10,000 missing orders
```

Therefore rollback for stateful systems needs:

```text
reverse synchronization
or
controlled data reconciliation
```

or a design where the source/target replication model supports failback.

Rollback isn't just DNS.

# **18. Stabilization**

For the first period after cutover:

```text
heightened monitoring
on-call engineers ready
migration team available
user feedback tracked
```

Microsoft recommends post-cutover functional/data validation and close monitoring during stabilization rather than declaring success immediately after traffic moves. ([Microsoft Learn][5])

### **Interview answer condensed**

> “For a critical low-downtime migration, I would do almost all preparation while production remains live. I'd define the RTO, RPO, downtime budget and rollback thresholds, map dependencies, build and secure the Azure target through IaC, establish hybrid connectivity, and continuously replicate servers and data. I'd run an isolated Azure Migrate test migration and validate functionality and performance against a source baseline. During final cutover I'd freeze unrelated changes, briefly quiesce writes if required, ensure replication lag is zero or within RPO, perform final synchronization, switch traffic, and immediately validate critical business transactions and telemetry. I would keep the original environment as a fallback until the Azure workload has completed its stabilization period.”

**Memory line:**
**Minimal downtime comes from doing the big copy while production is live and leaving only the final delta and traffic switch for cutover.**

**Interview trap:**
A rollback for a stateful application is **not simply switching DNS back** once users have written new data to Azure.

**Keywords:**
Continuous replication, Azure Migrate, test migration, final sync, cutover, replication lag, RTO, RPO, DNS TTL, rollback, stabilization.

# **T31-H02. How would you migrate hundreds of interdependent VMs to Azure?**

**Answer:**

I would treat hundreds of interdependent VMs as a **migration program organized into application dependency groups and controlled waves**, not as hundreds of individual VM migrations.

First I would use Azure Migrate discovery and dependency analysis plus CMDB/application-owner input to build an accurate inventory and map which servers communicate. I would group tightly coupled web, application, database, identity, and middleware components into migration units.

Then I would rank those applications by criticality and complexity and build waves—starting with low-risk pilot workloads, followed by progressively more important workloads. Shared foundations such as landing-zone subscriptions, identity, ExpressRoute/VPN, DNS, monitoring, backup, and security would be established first.

For every wave I would use a repeatable runbook: assess, replicate, test migrate, validate, cut over, monitor, and retain rollback capability. I would automate repetitive configuration through IaC and pipelines but keep business go/no-go decisions explicit.

Microsoft's current migration-wave guidance recommends dividing large migrations into manageable waves and specifically grouping dependent systems together, rather than trying to move the full estate simultaneously. ([Microsoft Learn][8])

```text
10.20.0.0/16
```

and an on-prem site already uses:

```text
10.20.0.0/16
```

hybrid routing becomes painful.

I'd integrate with enterprise IPAM and allocate landing-zone ranges before waves begin.

---

# **14. Cut over by application group**

For one wave:

```text
Pre-check
      ↓
Source healthy
      ↓
Replication healthy
      ↓
Freeze writes if required
      ↓
Final sync
      ↓
Migrate VMs/data
      ↓
Update DNS/LB
      ↓
Validate application
      ↓
Business owner approval
```

Not:

```text
VM migrated successfully
→ next VM
```

The unit of success is the **application**, not the Azure Migrate job.

---

# **15. Have wave-level rollback criteria**

For every wave define:

```text
If:
authentication broken
database reconciliation fails
latency > threshold
critical function fails
```

then:

```text
rollback wave
```

rather than debating during the outage.

# **16. Monitor migration program metrics**

At scale I want:

```text
Discovered VMs
Assessed VMs
Ready VMs
Replicating
Tested
Migrated
Validated
Failed
Rolled back
```

plus:

```text
Application count
Migration wave progress
Blockers
Performance coverage
Dependency completeness
```

This makes program risk visible.

---

# **17. Handle exceptions separately**

Some servers will be:

```text
Unsupported OS
Huge database
Special hardware
Licensing restriction
Unsupported appliance
```

Don't let 5 exceptional machines derail the other 495.

Put them into:

```text
exception workstream
```

with a separate treatment:

```text
retain
replace
upgrade
rearchitect
```

---

# **18. Post-wave learning**

After each wave:

```text
What failed?
What took longer?
Which runbook step was unclear?
Which firewall rules were missing?
Did sizing match reality?
```

Then improve the next wave.

That's the major advantage of wave-based migration.

---

### **Interview answer condensed**

> “For hundreds of interdependent VMs, I would migrate applications in controlled waves rather than treat each VM independently. I'd use Azure Migrate discovery and dependency analysis, supplement it with CMDB and application-owner knowledge, and group tightly coupled web, app, database and middleware servers into migration units. I'd establish the landing-zone network, DNS, identity, security, backup and monitoring first, then start with a low-risk pilot. For each wave I'd replicate ahead of time, perform isolated test migrations, validate dependencies and performance, execute an application-level cutover with explicit rollback criteria, and monitor closely. I'd automate repeatable Azure configuration through Terraform or Bicep and feed lessons from each wave into the next one.”

**Memory line:**
**At scale, migrate dependency groups in waves—not hundreds of VM objects independently.**

**Interview trap:**
A migration dashboard showing 500 successfully migrated VMs does **not mean 500 applications are working correctly**.

**Keywords:**
Migration waves, Azure Migrate, dependency analysis, application groups, pilot, replication, test migration, hybrid connectivity, IaC, cutover.

**Likely follow-ups:**

* How would you choose the size of each migration wave?
* What would you do with a shared database used by ten applications?
* How would you operate hybrid connectivity during a six-month migration?
* How would you detect undocumented dependencies?
* What would you automate versus leave as a manual go/no-go decision?

# **T31-H03. How would you validate that a migrated application performs correctly before cutover?**

**Answer:**

I would validate the migrated application against **predefined functional, performance, dependency, security, data-integrity, and operational acceptance criteria**, ideally using an isolated Azure test migration before production cutover.

Before migration I would capture a source baseline—for example p95/p99 latency, throughput, error rate, database latency, batch duration, resource utilization, and critical business transaction success.

Then I would create the test workload in Azure, run end-to-end business transactions, load tests at representative and peak traffic, verify data integrity, identity, DNS, private connectivity, external dependencies, monitoring, backup and failover behavior, and compare the target against the baseline and SLO.

I would only approve cutover when objective criteria pass. “The VM boots and the homepage opens” is not enough.

Azure Migrate explicitly recommends test migrations before actual migration so teams can perform application testing and resolve issues while source workloads remain operational. ([Microsoft Learn][6])

---

## **Validation model**

```text
Source Production
      ↓
Baseline
      ↓
Replication
      ↓
Azure Test Migration
      ↓
 ┌────┼────┬────┬───────┐
 ↓    ↓    ↓    ↓       ↓
Func Perf Data Security Operations
 └────┼────┴────┴───────┘
      ↓
Acceptance criteria
      ↓
PASS?
 /       \
Yes       No
 ↓         ↓
Cutover   Fix + retest
```

---

# **1. Define acceptance criteria before testing**

Bad:

> “We'll test it and see whether it looks good.”

Better:

```text
Availability:
100% of critical smoke tests succeed

Checkout:
p95 < 500 ms

Error rate:
< 0.5%

DB:
no reconciliation mismatch

Authentication:
all expected user roles work

Security:
no unexpected public exposure
```

Then:

```text
PASS / FAIL
```

is objective.

---

# **2. Capture source performance baseline**

Before migration:

```text
Requests/sec
p50
p95
p99
5xx rate
DB query latency
CPU
memory
disk latency
IOPS
network throughput
batch duration
queue depth
```

Example:

```text
On-prem checkout
p50 = 120 ms
p95 = 390 ms
p99 = 800 ms
```

Without this I can't answer:

> Did Azure make it slower?

---

# **3. Use an isolated Azure Migrate test migration**

For supported VM migrations:

```text
Source VM
      ↓
Azure Migrate replication
      ↓
Test migration
      ↓
non-production Azure VNet
```

The source remains operational and replication continues while the test VM is used for validation. ([Microsoft Learn][6])

This lets me test safely before the actual cutover.

---

# **4. Validate infrastructure first**

Dependency order:

```text
VM/compute
  ↓
Network
  ↓
DNS
  ↓
Application
  ↓
Dependencies
```

Check:

```text
VM boots?
Correct NIC/subnet?
NSG correct?
Routes correct?
DNS resolving?
Time synchronization okay?
Disk mounted?
```

If infrastructure is wrong, application testing is premature.

---

# **5. Validate identity**

Test actual authentication paths:

```text
Users
 ↓
Microsoft Entra / AD
 ↓
Application
```

and:

```text
Application
 ↓
Managed Identity / service account
 ↓
Database / Key Vault / Storage
```

Test:

```text
valid user
invalid user
admin
read-only user
application identity
```

Don't just test with:

```text
global administrator account
```

because that can hide RBAC problems.

---

# **6. Validate DNS specifically**

For each critical endpoint:

```text
nslookup / Resolve-DnsName
```

I want:

```text
expected hostname
→ expected Azure/private IP
```

If using Private Endpoint:

```text
FQDN
 ↓
Private DNS
 ↓
private IP
```

not public IP.

A test environment can have perfect routing but still fail because DNS points somewhere else.

---

# **7. Validate every critical dependency**

Create a checklist from dependency mapping:

```text
Application
├── SQL
├── Redis
├── Service Bus
├── Key Vault
├── file share
├── Entra/AD
└── third-party API
```

For each:

```text
DNS?
TCP connectivity?
TLS?
Authentication?
Authorization?
Latency?
```

This catches “application starts but transaction fails” problems.

---

# **8. Run real functional tests**

Not just:

```text
GET /
→ 200
```

Test:

```text
Login
Search
Create order
Update order
Payment
Generate report
Upload file
Send message
Read/write DB
Logout
```

Whatever represents the business.

Microsoft migration guidance recommends validating critical workload functionality, including authentication and core transactions, before declaring migration success. ([Microsoft Learn][5])

---

# **9. Validate data integrity**

Check:

```text
Schema
Row counts
Critical records
Checksums/hashes
Relationships
Stored procedures
Permissions
```

For example:

```text
Source:
Order 991829 = Paid, ₹2,500

Target:
Order 991829 = Paid, ₹2,500
```

For larger reconciliation:

```text
checksums
aggregate totals
business totals
```

Microsoft specifically recommends checksums/hash-based validation for stronger confidence than simple record counts alone. ([Microsoft Learn][5])

# **10. Load-test the Azure target**

Functional success with one tester proves almost nothing about production capacity.

Simulate:

```text
Normal traffic
      ↓
Expected peak
      ↓
burst
      ↓
stress where appropriate
```

Monitor:

```text
p95/p99 latency
throughput
5xx
CPU/memory
disk
database
connection pools
queue depth
```

For modernization workloads, Microsoft guidance recommends realistic load testing and comparison to source performance baselines before production deployment. ([Microsoft Learn][11])

---

# **11. Compare like-for-like**

Suppose source p95:

```text
400 ms
```

Azure p95:

```text
450 ms
```

Maybe acceptable.

But if Azure:

```text
1.8 sec
```

I investigate before cutover.

Dependency flow:

```text
Request
 ↓
Trace
 ↓
Which span increased?
```

Maybe:

```text
Application: unchanged
Database call:
10 ms → 400 ms
```

Then the issue is likely data/network/database architecture rather than VM CPU.

---

# **12. Test at expected concurrency**

An application might pass:

```text
1 user
```

but fail:

```text
2,000 concurrent sessions
```

because of:

```text
connection pool
thread pool
session state
SNAT
database connections
```

So test realistic concurrency, not only request volume.

---

# **13. Validate availability design**

If the target claims to be highly available, test some failures.

For example:

```text
Stop one application instance
      ↓
Do users continue?
```

For AKS:

```text
Delete Pod
      ↓
Service still available?
```

For VM/load-balancer architecture:

```text
Remove backend
      ↓
Health probe detects it?
Traffic shifts?
```

A design diagram isn't proof.

---

# **14. Validate monitoring before production**

I need telemetry before cutover, not after the first outage.

Validate:

```text
Azure Monitor metrics
Application Insights
Log Analytics
alerts
dashboards
Activity Logs
dependency traces
```

Trigger a safe test failure:

```text

```

and confirm:

```text
Telemetry appears?
Alert fires?
Correct team gets notified?
```

# **15. Validate backup/recovery**

Ask:

```text
Is backup configured?
Did it succeed?
Can we restore?
```

A green backup policy assignment isn't enough.

For critical systems:

```text
restore test
```

provides stronger evidence.

Check:

```text
Public exposure
NSGs
Firewall
Private Endpoints

```

If the target architecture says:

```text

```

# **17. Run UAT**

Automated tests can prove technical behavior.

Business users may catch:

```text
report formatting
workflow behavior
business rules
integration quirks
```

that infrastructure engineers don't know.

For critical apps:

```text
Application owner
+
business owner
```

should approve critical workflows before cutover.

---

# **18. Compare operational characteristics**

Migration success includes operations:

```text
Can support team access logs?
Can we restart?
Can we scale?
Can we patch?
Can we restore?
Are alerts routed?
Is documentation updated?
```

A technically functional app that nobody can operate isn't production-ready.

---

# **19. Re-test near cutover**

A test run two months earlier may no longer represent current production.

Before final cutover confirm:

```text
Application version unchanged or accounted for
Schema updated?
Dependencies changed?
Firewall changed?
Data volume increased?
```

Otherwise the successful test may be stale.

# **20. Define a go/no-go gate**

Example:

```text
Functional tests       PASS
Data reconciliation    PASS
p95 latency            PASS
Peak load              PASS
Authentication         PASS
Dependency tests       PASS
Security               PASS
Monitoring             PASS
Backup                  PASS
Business UAT            PASS
```

Only then:

```text
GO
```

If a critical criterion is red:

```text
NO-GO
```

Not:

> “We're already here, so let's try production.”

# **21. Validate again after real cutover**

Test migration cannot reproduce every production condition.

After cutover:

```text
Real traffic
      ↓
Azure target
```

immediately compare:

```text
SLI
error rate
p95/p99
DB latency
business throughput
```

Microsoft recommends comprehensive post-cutover validation and close monitoring rather than assuming pre-cutover testing guarantees production success. ([Microsoft Learn][5])

### **Interview answer condensed**

> “Before cutover I'd establish objective acceptance criteria and capture a source baseline for latency, throughput, error rate, database performance and critical business transactions. I'd then use Azure Migrate test migration in an isolated VNet so the production source stays operational. I'd validate in dependency order: infrastructure, DNS and networking, identity, application startup, database and external dependencies, then real end-to-end business workflows. I'd reconcile data using counts and checksums where appropriate, run representative and peak load tests, validate monitoring, backup and security, and obtain application-owner UAT. Cutover only gets a go decision if those criteria pass; the VM booting and a homepage returning HTTP 200 are nowhere near enough.”

**Memory line:**
**Validate the user journey and business outcome against a baseline—not merely whether the migrated VM turns green.**

**Interview trap:**
A successful **Azure Migrate test-migration job proves infrastructure migration worked; it does not prove application functionality, performance, or data correctness.**

**Keywords:**
Test migration, baseline, UAT, functional testing, load testing, p95/p99, data integrity, dependency validation, go/no-go, Azure Monitor.
