# **T31-E03. What is lift-and-shift?**

**Answer:**

Lift-and-shift is a migration approach where I **move an existing workload to Azure with little or no change to its application code or architecture**.

For example, if an application currently runs on VMware with Windows Server, IIS, and SQL Server, I might move those workloads to Azure VMs while keeping essentially the same architecture.

The main advantage is **speed and lower migration risk**, because I don't redesign the application during the move. The trade-off is that I may carry existing technical debt and VM-management overhead into Azure, so I might modernize the workload later.

Microsoft's current migration guidance describes **rehost** as the lift-and-shift strategy: move a workload to Azure infrastructure without code changes, changing primarily *where* it runs rather than *how* it runs. ([Microsoft Learn][1])

```text
Before

On-premises
│
├── Windows VM
│    └── IIS Application
│
└── SQL Server VM


Lift-and-shift
        ↓

Azure
│
├── Azure VM
│    └── IIS Application
│
└── Azure VM
     └── SQL Server
```

---

## **What normally changes?**

Even in a lift-and-shift migration, **nothing changes** is too strong.

The application code may remain largely unchanged, but I still need to deal with:

```text
Azure networking
DNS
IP addresses
Azure RBAC
VM sizing
Storage
NSGs
Monitoring
Backup
Identity
Connectivity to remaining on-prem dependencies
```

So:

```text
No major application redesign
≠
no migration work
```

---

## **Why would I choose it?**

Lift-and-shift is attractive when:

```text
Migration deadline is tight
Application is stable
Code is difficult to modify
Modernization risk is high
Datacenter exit is urgent
Modernization will happen later
```

Example:

> The company must leave a datacenter within six months, but rewriting 80 legacy applications would take several years.

A sensible strategy might be:

```text
Phase 1
Rehost to Azure

Phase 2
Stabilize

Phase 3
Modernize selected workloads
```

---

## **Main disadvantage**

If the source architecture is:

```text
15 oversized VMs
+
manual patching
+
poor scaling
```

and I simply move it to Azure:

```text
15 oversized Azure VMs
+
manual patching
+
poor scaling
```

I have changed the hosting location but not necessarily improved the architecture.

This is sometimes described informally as:

> **moving the technical debt with the workload.**

---

## **Example**

Before:

```text
VMware
 ↓
Windows Server
 ↓
IIS
 ↓
.NET application
```

After:

```text
Azure VM
 ↓
Windows Server
 ↓
IIS
 ↓
same .NET application
```

That's a classic lift-and-shift.

If instead I move the application to:

```text
Azure App Service
```

with some platform adaptation, I'm moving toward **replatforming**, not pure lift-and-shift.

---

**Memory line:**
**Lift-and-shift means change the hosting location with minimal change to the workload itself.**

**Interview trap:**
Lift-and-shift does **not mean literally zero changes**—networking, identity, sizing, monitoring, backup, and dependencies still have to be redesigned or validated for Azure.

**Keywords:**
Lift-and-shift, rehost, Azure VM, minimal change, migration, technical debt, IaaS.

# **T31-E04. What is rehosting?**

**Answer:**

Rehosting means **moving an existing workload to Azure infrastructure with minimal or no application-code changes**. It is essentially the formal migration-strategy name for what is commonly called **lift-and-shift**.

For example, I might migrate a VMware VM running an IIS application into an Azure VM while keeping the operating system and application architecture largely the same.

Rehosting is useful when migration speed and low transformation risk are more important than immediate cloud-native modernization. Microsoft currently defines rehosting as moving the workload to Azure infrastructure without code changes. ([Microsoft Learn][1])

```text
Rehost

On-prem VM
     ↓
Azure VM

Application architecture
≈ largely unchanged
```

---

## **Rehost = lift-and-shift**

For interview purposes:

```text
Lift-and-shift
      =
Rehosting
```

Don't treat them as two unrelated migration strategies.

**Lift-and-shift** is the common phrase.

**Rehost** is the migration-strategy term.

---

## **What stays similar?**

Usually:

```text
Application code
Operating system
Runtime
Application topology
```

remain largely intact.

For example:

```text
On-prem:
Windows Server 2022
IIS
.NET Framework app

Azure:
Azure VM
Windows Server
IIS
same application
```

---

## **What still needs Azure design?**

Even with rehosting I need to validate:

```text
VNet/subnet
NSGs
DNS
Azure connectivity
VM SKU
disk performance
availability
backup
Azure Monitor
security
dependencies
```

If the original VM had:

```text
8 vCPU
32 GB RAM
```

I shouldn't automatically choose an Azure VM with exactly the same capacity.

Performance data may show that the old server was heavily overprovisioned.

Right-sizing can reduce cost even without modifying the application.

---

## **Rehost vs replatform**

This distinction matters:

```text
Rehost
→ VM → Azure VM
→ minimal architectural change

Replatform
→ VM-hosted component → Azure PaaS
→ limited changes
```

Example:

```text
SQL Server VM
→ SQL Server on Azure VM
```

is generally rehosting.

Whereas:

```text
SQL Server
→ Azure SQL Managed Instance
```

is a replatforming-style move because responsibility shifts toward a managed platform service.

Microsoft's current migration guidance characterizes replatforming as making limited changes to gain Azure PaaS benefits without performing a full rewrite. ([Microsoft Learn][1])

---

**Memory line:**
**Rehosting is the formal name for lift-and-shift: move the workload with minimal application change.**

**Interview trap:**
Don't say **rehost and lift-and-shift are different strategies**—in normal cloud-migration terminology, lift-and-shift refers to rehosting.

**Keywords:**
Rehost, lift-and-shift, IaaS, Azure VM, minimal changes, migration.

# **T31-E05. What is refactoring?**

**Answer:**

Refactoring means **modifying an application's code to improve its maintainability, performance, scalability, reliability, or suitability for cloud environments while generally preserving its intended external behavior**.

Compared with rehosting, refactoring involves meaningful code changes.

For example, I might modify an application to use Managed Identity instead of stored credentials, add OpenTelemetry instrumentation, improve statelessness so it can scale horizontally, or change blocking code so the application works better on Azure.

Microsoft's current modernization guidance describes refactoring as modifying application code to improve characteristics such as maintainability, performance, and alignment with cloud design practices. ([Microsoft Learn][2])

```text
Rehost
→ mostly move

Refactor
→ change code
   to improve how the workload behaves
```

---

## **Example**

Suppose the existing application stores session state:

```text
Web server local memory
```

That makes horizontal scaling difficult because:

```text
Request 1 → Server A
session stored on A

Request 2 → Server B
session missing
```

During refactoring I might externalize session state:

```text
        Load Balancer
           /      \
          ↓        ↓
       App 1     App 2
          \        /
           \      /
       Shared state/cache
```

Now the application can scale horizontally more effectively.

---

## **Other refactoring examples**

I might change:

```text
hardcoded password
      ↓
Managed Identity

local filesystem dependency
      ↓
Azure Storage

synchronous processing
      ↓
asynchronous messaging

poor telemetry
      ↓
OpenTelemetry instrumentation

single-instance assumptions
      ↓
stateless scalable design
```

These involve application changes, not merely moving the VM.

---

## **Refactor vs replatform**

A useful distinction:

### Replatform

```text
limited changes
+
move to managed platform
```

Example:

```text
SQL Server
→ Azure SQL Managed Instance
```

### Refactor

```text
modify application code
```

Example:

```text
change application authentication
connection handling
state management
telemetry
resilience logic
```

Sometimes a migration contains **both**.

For example:

```text
Replatform database
+
Refactor application connection/authentication logic
```

Migration strategies don't always exist in perfect isolation.

---

## **Refactor vs rearchitect**

Refactoring generally improves the existing code/design without necessarily replacing the fundamental architecture.

Rearchitecting is broader:

```text
Monolith
     ↓
major architectural redesign
     ↓
event-driven services / microservices
```

Microsoft's current guidance distinguishes refactoring from rearchitecting: refactoring focuses on code-level improvement, while rearchitecting changes the broader architecture to enable capabilities such as greater scalability or cloud-native design. ([Microsoft Learn][2])

---

**Memory line:**
**Rehost changes where the application runs; refactor changes its code so it runs better.**

**Interview trap:**
Refactoring is **not automatically the same as rewriting the entire application or converting a monolith into microservices**; that may move into rearchitecting or rebuilding.

**Keywords:**
Refactor, modernization, code changes, scalability, maintainability, Managed Identity, statelessness, cloud optimization.

# **T31-M01. What are common cloud-migration strategies?**

**Answer:**

I would choose the migration strategy **per workload**, based on business value, technical condition, migration deadline, risk, cost, and how much architectural change is justified.

Microsoft's current Cloud Adoption Framework describes an **8-R migration strategy model**:

**Retire, Retain, Rehost, Replatform, Refactor, Rearchitect, Rebuild, and Replace.** ([Microsoft Learn][3])

The most common migration path is often somewhere on this spectrum:

```text
Least change                            Most change
    │                                      │
    ▼                                      ▼

Retain → Rehost → Replatform → Refactor → Rearchitect → Rebuild
             \
              Replace / Retire
```

I wouldn't automatically modernize everything. For example, a stable legacy application under a datacenter-exit deadline may be rehosted first, while a strategically important application with scalability problems may justify replatforming, refactoring, or rearchitecting.

---

# **1. Retire**

Meaning:

> **The workload is no longer needed, so don't migrate it.**

Example:

```text
Legacy reporting server
       ↓
No users for 18 months
       ↓
Retire
```

This sounds obvious, but migration projects often discover:

```text
unknown VMs
duplicate applications
abandoned test servers
unused databases
```

Moving them to Azure would simply turn:

```text
on-prem waste
```

into:

```text
Azure monthly cost
```

So discovery should happen before migration.

---

# **2. Retain**

Meaning:

> **Keep the workload where it currently runs for now.**

Reasons might include:

```text
hardware dependency
latency requirement
regulatory restriction
unsupported technology
migration cost too high
application nearing retirement
```

Example:

```text
Factory control application
      ↓
requires local hardware
      ↓
retain on-premises
```

Retain doesn't necessarily mean:

```text
forget about it forever
```

It can mean:

```text
not migrating in this wave
```

For retained servers, Azure Arc may provide Azure-based governance and operations without moving the machine into Azure. Current Azure Migrate assessment guidance explicitly identifies Retain as a valid strategy and recommends Arc as an option for managing retained servers. ([Microsoft Learn][4])

---

# **3. Rehost**

Also:

```text
lift-and-shift
```

Meaning:

> Move the workload largely as-is to Azure infrastructure.

Example:

```text
VMware VM
     ↓
Azure VM
```

Good when:

```text
migration deadline is short
code changes are risky
application is stable
datacenter exit is urgent
```

Advantages:

```text
fast
lower application-change risk
```

Disadvantages:

```text
technical debt retained
VM operations retained
cloud optimization limited
```

Microsoft explicitly characterizes rehost as moving the workload to Azure infrastructure without code changes. ([Microsoft Learn][1])

---

# **4. Replatform**

Sometimes described as:

> **lift, adjust, and shift.**

Meaning:

> Make relatively small changes so the workload can consume managed Azure services.

Example:

```text
SQL Server VM
      ↓
Azure SQL Managed Instance
```

or potentially:

```text
VM-hosted application
      ↓
Azure App Service
```

where compatibility permits.

Why?

You can reduce:

```text
OS patching
infrastructure management
backup administration
HA administration
```

without rewriting the entire application.

Microsoft's current guidance defines replatforming as moving components toward Azure PaaS with limited changes to reduce operational overhead and gain platform capabilities. ([Microsoft Learn][1])

---

# **5. Refactor**

Meaning:

> Change the application code so it works better in the cloud.

Examples:

```text
stored credentials
→ Managed Identity

local session state
→ externalized state

poor telemetry
→ OpenTelemetry

synchronous blocking workflow
→ async processing
```

This requires more:

```text
engineering
testing
application knowledge
```

than rehosting or replatforming.

But it can improve:

* scalability,
* reliability,
* maintainability,
* performance,
* operational maturity.

---

# **6. Rearchitect**

Meaning:

> Make significant architectural changes because the existing architecture prevents the workload from meeting its goals.

For example:

```text
Large tightly coupled monolith
           ↓
Architectural redesign
           ↓
API/services
+
asynchronous messaging
+
independent scaling
```

Important:

```text
Rearchitect
≠
"always convert to microservices"
```

A modular monolith may be the correct target.

The point is to redesign architectural boundaries where justified.

Microsoft's current modernization guidance describes rearchitecting as redesigning workload architecture to improve characteristics such as scalability, agility, or cloud-native capability. ([Microsoft Learn][2])

---

# **7. Rebuild**

Meaning:

> Create the application again using a new cloud-oriented implementation rather than incrementally modifying the old application.

Imagine:

```text
20-year-old application
+
unsupported framework
+
large technical debt
+
business still needs functionality
```

Trying to refactor it may be harder than:

```text
requirements
      ↓
new implementation
      ↓
cloud-native architecture
```

Rebuild usually involves the greatest:

* engineering effort,
* migration duration,
* application risk,

but may remove significant legacy constraints.

---

# **8. Replace**

Meaning:

> Replace the custom/existing application with another product, often SaaS.

For example:

```text
Custom legacy CRM
       ↓
SaaS CRM
```

instead of migrating and maintaining:

```text
20 VMs
database
application code
patching
backup
```

Sometimes the best cloud migration is:

> **Don't migrate the application at all—replace the business capability.**

---

# **Current terminology nuance**

This is useful because Microsoft documentation can show different-sized “R” models depending on context.

The current **Cloud Adoption Framework planning guidance uses the broader 8 Rs**:

```text
Retire
Retain
Rehost
Replatform
Refactor
Rearchitect
Rebuild
Replace
```

([Microsoft Learn][3])

But current **Azure Migrate application assessments expose a 5-R recommendation set**:

```text
Refactor
Replatform
Rehost
Retain
Retire
```

([Microsoft Learn][4])

And some application-modernization guidance uses a **6-R model**.

So if an interviewer says:

> “What are the 6 Rs?”

I would use their terminology rather than arguing about the number.

The core thing is understanding the strategies and trade-offs.

---

# **How I would choose between them**

I would evaluate:

```text
Business value
     ↓
Application health
     ↓
Migration deadline
     ↓
Technical debt
     ↓
Cloud benefit
     ↓
Dependencies
     ↓
Compliance
     ↓
Engineering capacity
     ↓
Cost / risk
```

Then choose treatment per workload.

---

# **Example portfolio**

Suppose an organization discovers 100 applications.

A reasonable portfolio could look like:

```text
15 → Retire
10 → Retain
40 → Rehost
15 → Replatform
8  → Refactor
5  → Rearchitect
2  → Rebuild
5  → Replace
```

The goal is **not**:

```text
100 apps
→ all microservices
```

The goal is:

```text
appropriate treatment
for each workload
```

---

# **Migration strategy can be phased**

An important production pattern:

```text
Rehost now
      ↓
stabilize in Azure
      ↓
replatform later
      ↓
refactor selectively
```

For example:

```text
Phase 1:
VMware → Azure VM

Phase 2:
SQL VM → Azure SQL Managed Instance

Phase 3:
application uses Managed Identity
and improved observability
```

This may reduce migration risk compared with trying to change infrastructure, database, networking, and application code simultaneously.

---

# **Why not modernize everything during migration?**

Because changing:

```text
hosting
networking
database
identity
application architecture
deployment model
```

all at once increases:

```text
test surface
risk
rollback complexity
project duration
```

Sometimes separating:

```text
Migration
from
Modernization
```

is strategically safer.

But if the current application cannot operate effectively in Azure without redesign, then modernization during migration may be necessary.

---

# **Decision example**

Suppose I have a .NET application on Windows VMs.

### Case 1

```text
Datacenter closes in 3 months
Application stable
Minimal engineering capacity
```

I'd strongly consider:

```text
Rehost
```

---

### Case 2

```text
Application compatible with App Service
Team wants less OS management
Small configuration changes acceptable
```

I'd evaluate:

```text
Replatform
```

---

### Case 3

```text
Application stores local state
can't horizontally scale
stored credentials everywhere
```

I'd consider:

```text
Refactor
```

---

### Case 4

```text
Architecture cannot meet scale requirements
components tightly coupled
deployments require full-system outage
```

Potentially:

```text
Rearchitect
```

---

### Case 5

```text
Legacy HR application
standard SaaS product now satisfies requirement
```

Potentially:

```text
Replace
```

---

# **Azure Migrate's role**

Azure Migrate can help provide evidence for treatment decisions through:

```text
Discovery
     ↓
Inventory
     ↓
Performance data
     ↓
Dependency information
     ↓
Readiness / sizing / cost
     ↓
Migration recommendation
```

Current Azure Migrate application assessment can recommend among its supported 5-R assessment strategies and show information such as cost, code-change implications, environment, and recommendation reasoning. ([Microsoft Learn][4])

But I would still combine tool output with business requirements.

A tool may know:

```text
CPU
RAM
dependencies
compatibility
```

but not necessarily:

```text
"This application will be retired next quarter."
```

That's why migration strategy is both a technical and business decision.

---

### **Interview answer condensed**

> “I choose migration strategy per workload rather than applying one method to the whole estate. Microsoft's current Cloud Adoption Framework uses an 8-R model: Retire, Retain, Rehost, Replatform, Refactor, Rearchitect, Rebuild, and Replace. Rehost is lift-and-shift with minimal code change; replatform introduces managed Azure services with limited changes; refactor changes code; rearchitect changes the larger architecture; rebuild creates a new implementation; replace moves the capability to another product such as SaaS; retain keeps it where it is; and retire removes it. I base the decision on business value, migration deadline, dependencies, technical debt, risk, cloud benefit, and engineering capacity. Often I rehost first under a tight deadline and modernize selectively afterward.”

**Memory line:**
**Don't ask “How do we migrate everything?”—ask “What is the right treatment for each workload?”**

**Interview trap:**
There is **not one universally used number of “Rs” across every Microsoft tool and guide**; current CAF uses 8 Rs, while some Azure Migrate and modernization experiences use narrower subsets.

**Keywords:**
8 Rs, Retire, Retain, Rehost, Replatform, Refactor, Rearchitect, Rebuild, Replace, Azure Migrate, modernization.

**Likely follow-ups:**

* What's the difference between rehost and replatform?
* When would you rehost first and modernize later?
* What's the difference between refactoring and rearchitecting?
* How would Azure Migrate help decide the migration strategy?
