# **T31-M02. How would you assess an on-premises workload before moving it to Azure?**

**Answer:**

Before moving an on-premises workload to Azure, I would assess it in a structured order: **business requirements, application inventory, dependencies, performance, compatibility, target Azure architecture, security/networking, availability requirements, and cost**.

I would normally use **Azure Migrate Discovery and Assessment** to discover servers and collect configuration and performance data. Then I would identify which servers actually belong to the application, map their dependencies, evaluate Azure readiness, generate right-sized target recommendations, and estimate cost.

I would not migrate a server just because Azure Migrate says the VM itself is compatible. I also need to know whether the application depends on DNS, Active Directory, databases, file shares, hardcoded IP addresses, licenses, external systems, or low-latency on-prem connectivity.

My overall flow would be:

```text
Discover
   ↓
Inventory
   ↓
Dependency mapping
   ↓
Performance baseline
   ↓
Compatibility/readiness
   ↓
Choose migration strategy
   ↓
Target Azure architecture
   ↓
Cost + security + DR review
   ↓
Migration-wave planning
   ↓
Test
```

Azure Migrate currently supports discovery followed by either **as-is** or **performance-based** assessment and can provide Azure readiness, sizing, and cost recommendations. ([Microsoft Learn][1])

---

## **1. Understand the business requirement first**

Before collecting CPU statistics, I need to know:

```text
Why are we migrating?
```

Possible reasons:

```text
Datacenter exit
Hardware refresh avoidance
Cost reduction
Higher availability
Global expansion
Security/compliance
Modernization
```

Then I establish:

```text
Application owner
Business criticality
Maintenance windows
Expected migration deadline
Downtime tolerance
RTO
RPO
Compliance requirements
```

These strongly affect the migration strategy.

For example:

```text
RTO = 8 hours
RPO = 4 hours
```

allows much more flexibility than:

```text
RTO = 5 minutes
RPO ≈ 0
```

---

# **2. Build a complete inventory**

I would discover:

```text
Servers
├── OS/version
├── CPU
├── RAM
├── disks
├── NICs
├── IP addresses
├── installed software
└── uptime

Databases
Applications
Load balancers
File shares
DNS dependencies
Certificates
Service accounts
Scheduled jobs
```

The biggest migration mistake is often:

> “We knew about the main VM, but not the five things it depended on.”

---

# **3. Use Azure Migrate discovery**

For supported environments, an Azure Migrate appliance can discover infrastructure and gather information used for assessment.

Conceptually:

```text
VMware / Hyper-V / physical servers
            ↓
     Azure Migrate appliance
            ↓
       Azure Migrate
            ↓
 Inventory + performance
```

Azure Migrate can also work from imported server information in supported assessment scenarios, but live discovery gives richer data for planning. ([Microsoft Learn][1])

---

# **4. Map application dependencies**

This is one of the most important steps.

Suppose I discover:

```text
web01
app01
sql01
file01
```

I need to know:

```text
web01
  ↓
app01
  ↓
sql01
  ↓
file01
```

and perhaps:

```text
app01
   ↓
LDAP / Active Directory
   ↓
on-prem DNS
```

Azure Migrate dependency analysis can identify network dependencies and help group interdependent servers into applications, specifically to avoid leaving a required system behind during migration. ([Microsoft Learn][2])

---

# **5. Establish a performance baseline**

I wouldn't size Azure only from the current physical/virtual configuration.

Suppose:

```text
On-prem VM
16 vCPU
64 GB RAM
```

but actual usage is:

```text
CPU p95 = 18%
Memory p95 = 30%
```

Copying it directly to a similarly sized Azure VM can waste money.

I would capture representative:

```text
CPU
Memory
Disk IOPS
Disk throughput
Network throughput
Latency
Peak periods
Seasonality
```

Azure Migrate performance-based assessment uses CPU and memory utilization for compute sizing and disk IOPS/throughput for storage recommendations. ([Microsoft Learn][3])

---

# **6. Make sure performance history is representative**

This matters a lot.

Suppose the assessment collects only:

```text
Sunday night
```

when the ERP workload is almost idle.

It may recommend a VM that is too small for:

```text
Monday 10 AM
month-end payroll
Black Friday
quarter-end processing
```

So I need:

```text
Representative performance window
+
sensible percentile
+
capacity headroom
```

Azure Migrate supports percentile-based performance sizing and a **comfort factor** to provide headroom above measured utilization. ([Microsoft Learn][4])

---

# **7. Assess compatibility/readiness**

I would check:

```text
Supported OS?
Supported architecture?
Boot/disk configuration?
Required drivers?
Legacy software?
Licensing?
Database compatibility?
Application runtime?
```

Then Azure target compatibility:

```text
Azure VM?
App Service?
AKS?
Azure SQL?
SQL Managed Instance?
Other PaaS?
```

This is also where the migration strategy starts becoming clear.

---

# **8. Decide the migration strategy**

For each component:

```text
Retire?
Retain?
Rehost?
Replatform?
Refactor?
Rearchitect?
Rebuild?
Replace?
```

For example:

```text
Legacy web VM
→ Rehost

SQL Server
→ Replatform to SQL Managed Instance

Unused reporting server
→ Retire
```

The application does not have to use one strategy for every component.

Azure Migrate's cross-workload assessment can evaluate an application's constituent workloads together rather than assessing every server in isolation. ([Microsoft Learn][5])

---

# **9. Assess networking**

I would document:

```text
Source subnets
IP ranges
DNS
Internet ingress
Internet egress
Firewall rules
Proxies
Load balancers
On-prem routes
Bandwidth requirements
Latency-sensitive dependencies
```

Then design:

```text
Azure VNet
      ↓
Hub / Virtual WAN if applicable
      ↓
VPN / ExpressRoute
      ↓
remaining on-prem dependencies
```

A migration can be technically successful yet unusable because network latency doubles or DNS no longer resolves a legacy dependency.

---

# **10. Look for hardcoded dependencies**

Examples:

```text
10.1.2.15
```

inside application configuration.

Or:

```text
\\fileserver01\share
```

Or:

```text
sql-old01.corp.local
```

Before moving anything I want to know whether these are:

```text
DNS-based
IP-based
certificate-bound
latency-sensitive
```

Hardcoded IPs make migration much more fragile.

---

# **11. Assess identity**

Ask:

```text
Does the app use AD authentication?
Service accounts?
Kerberos?
NTLM?
Local accounts?
LDAP?
Certificates?
Database credentials?
```

Then determine Azure target authentication.

Potential modernization:

```text
stored service account password
        ↓
Managed Identity
```

But if this is a pure rehost, I may initially preserve existing domain integration and modernize later.

---

# **12. Assess security and compliance**

I would understand:

```text
Data classification
Encryption requirements
Regulatory location requirements
Public-access restrictions
Privileged access model
Logging/audit retention
Key ownership
```

These can determine whether the target needs:

```text
Private Endpoints
Azure Firewall
Key Vault
Defender for Cloud
specific Azure regions
```

before the migration even begins.

---

# **13. Assess availability and DR requirements**

Current on-prem architecture:

```text
one VM
one database
nightly backup
```

doesn't automatically mean Azure should reproduce it exactly.

I ask:

```text
Required SLO?
RTO?
RPO?
Zone failure requirement?
Region failure requirement?
```

Migration is a chance to fix obvious reliability risks even if we're not doing a full modernization.

---

# **14. Evaluate target cost**

Azure Migrate assessments can estimate Azure cost after target sizing and selected pricing assumptions. ([Microsoft Learn][6])

But I would include more than VM price:

```text
Compute
Disks
Backup
Azure Monitor
Networking
Data transfer
Defender
Load balancers
Licensing
DR
```

Otherwise the business case is incomplete.

---

# **15. Check performance-data quality**

Azure Migrate exposes **performance coverage** for performance-based assessments.

If:

```text
CPU data present
Memory data missing
Disk data incomplete
```

the sizing recommendation may be unreliable.

Microsoft explicitly warns that missing CPU, RAM, disk IOPS/throughput, or network performance data can reduce recommendation reliability. ([Microsoft Learn][7])

I wouldn't blindly accept:

```text
Recommended: D2as_v5
```

without checking why it was recommended.

---

# **16. Group into migration waves**

After understanding dependencies:

```text
Wave 1
→ low-risk standalone apps

Wave 2
→ medium-complexity apps

Wave 3
→ critical multi-tier app
```

Within one application:

```text
DB
App
Web
```

may need to migrate together or in a tightly controlled sequence.

This reduces cross-site latency and broken dependency risk.

---

# **17. Establish baseline measurements before migration**

Before cutover, record:

```text
p95 latency
requests/sec
batch duration
database query latency
CPU
memory
error rate
business transaction success
```

Then after migration:

```text
Before
vs
After
```

Without a baseline, users can say:

> “Azure feels slower.”

and I have no objective comparison.

---

My final assessment would contain something like:


Now the migration team has an engineering plan rather than a server spreadsheet.

---

### **Interview answer condensed**

> “I would assess the workload from both business and technical perspectives. First I'd capture criticality, SLO, RTO, RPO, downtime tolerance, compliance, and ownership. Then I'd use Azure Migrate to discover the infrastructure, collect representative CPU, memory, disk and network performance data, evaluate Azure readiness and right-sizing, and map dependencies between servers. I'd also inspect networking, DNS, identity, hardcoded IPs, databases, licensing, security and remaining on-prem dependencies. From that I would choose a strategy such as rehost or replatform, design the Azure target, estimate total cost, group dependent systems into migration waves, and establish pre-migration performance baselines so we can validate the result after migration.”

**Memory line:**
**Assess the application and its dependencies—not just the VM you can see.**

**Interview trap:**
An Azure Migrate VM showing **Ready for Azure** does not prove the entire application will work after migration.

**Keywords:**
Azure Migrate, discovery, assessment, readiness, performance baseline, dependency mapping, RTO, RPO, right-sizing, migration waves.

**Likely follow-ups:**

* How long would you collect performance data?
* What if Azure Migrate recommends a much smaller VM than the existing server?
* How would you find dependencies that aren't documented?
* What baseline would you capture before migration?

# **T31-M03. How do dependencies affect migration planning?**

**Answer:**

Dependencies determine **which workloads must move together, in what order, and what connectivity must remain during the migration**.

An application is rarely just one server. A web server might depend on an application server, SQL database, Active Directory, DNS, file share, message broker, and third-party service. If I migrate only the web server while leaving a latency-sensitive database on-premises, the application may technically start in Azure but perform terribly or fail entirely.

So before defining migration waves, I map dependencies and classify them as **critical, optional, synchronous, asynchronous, latency-sensitive, identity-related, or external**.

Azure Migrate's dependency analysis is designed specifically to identify network dependencies between discovered servers, group related servers into applications, and find systems that should migrate together. ([Microsoft Learn][2])

---

## **Simple example**

Suppose:

```text
Users
  ↓
Web01
  ↓
App01
  ↓
SQL01
```

If I migrate only:

```text
Web01 → Azure
```

but leave:

```text
App01 + SQL01 → on-prem
```

then every user request becomes:

```text
Azure
  ↓
VPN / ExpressRoute
  ↓
On-prem App
  ↓
On-prem SQL
```

Latency and connectivity dependency increase dramatically.

---

# **1. Dependencies determine migration groups**

Suppose Azure Migrate discovers:

```text
web01 ↔ app01
app01 ↔ sql01
app01 ↔ redis01
```

Those probably belong to the same application.

Instead of:

```text
Wave 1 → web01
Wave 4 → app01
Wave 7 → sql01
```

I might plan:

```text
Migration group A
├── web01
├── app01
├── sql01
└── redis01
```

or a coordinated staged sequence.

This is one of the explicit purposes of Azure Migrate dependency mapping. ([Microsoft Learn][2])

---

# **2. Dependencies determine migration order**

A typical three-tier application might be migrated in dependency-aware sequence:

```text
Target network ready
        ↓
Identity/DNS ready
        ↓
Database replicated
        ↓
Application tier migrated
        ↓
Web tier migrated
        ↓
Traffic cutover
```

Why not start with the frontend?

Because:

```text
Frontend
```

may be useless if:

```text
backend/database connectivity
```

isn't ready.

---

# **3. Synchronous dependencies are particularly sensitive**

Suppose every request makes five synchronous database/API calls.

On-prem latency:

```text
1 ms each
```

After moving the app to Azure but leaving the dependency on-prem:

```text
30 ms each
```

Five sequential calls may add roughly:

```text
5 × 30 ms
= 150 ms
```

just from network delay.

And real applications may make hundreds of calls.

This is why an app can be:

```text
CPU healthy
memory healthy
Azure VM healthy
```

but still become slow after migration.

---

# **4. Database dependencies are usually critical**

Suppose:

```text
App → SQL Server
```

If the application moves first and SQL remains on-premises:

```text
App in Azure
      ↓
ExpressRoute/VPN
      ↓
SQL on-prem
```

I need to evaluate:

```text
Latency
Bandwidth
Network reliability
Firewall
DNS
Authentication
Transaction volume
```

For a chatty application, that may be unacceptable.

I might therefore migrate:

```text
App + DB
```

within the same wave.

---

# **5. Identity is also a dependency**

Applications may depend on:

```text
Active Directory
LDAP
Kerberos
NTLM
service accounts
certificate authorities
```

Example:

```text
Azure VM
   ↓
domain authentication
   ↓
on-prem domain controller
```

If connectivity to the domain controller fails:

```text
application authentication
```

may fail even though the Azure VM itself is healthy.

So identity must be mapped just like databases.

---

# **6. DNS is a dependency**

An application might call:

```text
sql01.corp.local
```

If Azure doesn't have a resolution path for:

```text
corp.local
```

then:

```text
routing may be perfect
firewall may be open
SQL may be healthy
```

but the app still fails with:

```text
name resolution error
```

So hybrid DNS must often exist before workload cutover.

---

# **7. File shares can be hidden dependencies**

Legacy apps often contain:

```text
\\fileserver01\reports
```

or:

```text
NFS mount
```

that nobody documented.

After migration:

```text
Azure VM
      ↓
file share on-prem
```

may introduce:

* latency,
* SMB/NFS firewall requirements,
* availability dependency,
* bandwidth load.

Dependency discovery plus application-owner interviews are both important because not every logical dependency is obvious from infrastructure inventory.

---

# **8. External dependencies matter**

Example:

```text
Payment API
Shipping provider
SAP
Partner SFTP
Mainframe
```

Some cannot move to Azure at all.

Then migration architecture becomes:

```text
Azure workload
      ↓
secure network/API path
      ↓
external system
```

For each external dependency I want:

```text
Endpoint
Protocol
Port
DNS
Latency
Authentication
SLA
Owner
```

---

# **9. Dependencies influence network design**

Suppose application must continue reaching:

```text
on-prem SAP
```

Then before migration I need:

```text
Azure VNet
   ↓
Hub
   ↓
ExpressRoute / VPN
   ↓
SAP
```

Migration cannot begin with:

> “We'll figure connectivity out after the VM is in Azure.”

The dependency tells me what networking must exist first.

---

# **10. Dependencies affect rollback**

Suppose during migration:

```text
DB becomes writable in Azure
```

and users start creating new records.

If I need to roll the application back on-premises:

```text
Where is the latest data?
```

becomes critical.

Dependencies therefore affect not only:

```text
migration order
```

but:

```text
rollback design
```

especially when stateful systems are involved.

---

# **11. Data dependencies need cutover ownership**

Consider:

```text
Old DB
      ↔
New DB
```

At cutover I need a clear point where:

```text
old DB stops accepting writes
      ↓
final sync
      ↓
new DB becomes authoritative
```

Otherwise:

```text
split writes
```

can create inconsistent data.

This is much more dangerous than moving a stateless web server.

---

# **12. Optional dependencies can migrate separately**

Suppose:

```text
Product API
├── SQL
├── Inventory
└── Recommendation
```

Recommendation is optional.

If the application gracefully degrades:

```text
Recommendation unavailable
→ hide recommendations
```

then I may be able to migrate recommendation independently.

Not every dependency requires the same migration-wave coupling.

---

# **13. Use dependency analysis for migration waves**

A simple planning structure:

```text
Wave 1
Low dependency
├── standalone Dev servers
└── simple web apps

Wave 2
Moderate dependency
├── web + app + DB
└── internal systems

Wave 3
High dependency
├── ERP
├── AD integrations
├── file systems
└── external systems
```

This lets the migration team learn on low-risk workloads first.

---

# **14. Current Azure Migrate behavior**

Azure Migrate dependency analysis can identify dependencies across discovered environments including VMware, Hyper-V, physical servers, and supported servers hosted in other public clouds. Its documentation specifically highlights:

* reviewing network dependencies,
* grouping interdependent servers,
* identifying systems that should migrate together,
* avoiding surprise outages from leaving dependencies behind. ([Microsoft Learn][2])

That's exactly how I would use it operationally.

---

# **15. But don't rely on network dependency mapping alone**

Suppose the application communicates with an external service:

```text
only once at midnight
```

and you collect a short observation window.

You might miss it.

Or the dependency is:

```text
manual file import
scheduled task
certificate authority
business process
```

and doesn't show clearly as constant network traffic.

So I combine:

```text
Automated dependency mapping
+
Configuration review
+
Application-owner interviews
+
CMDB/docs
+
Firewall/log data
```

for important workloads.

---

### **Interview answer condensed**

> “Dependencies determine which systems should migrate together, the migration order, and what hybrid connectivity must exist during the transition. I would use Azure Migrate dependency analysis plus application-owner validation to map web, application, database, identity, DNS, file-share and external-service dependencies. Then I'd group tightly coupled or latency-sensitive components into the same migration wave. I'd pay particular attention to stateful dependencies because database cutover and rollback require a clear source of truth. I also wouldn't rely only on network mapping, because infrequent scheduled or business-process dependencies can be missed.”

**Memory line:**
**Migration waves should follow dependency boundaries, not just server lists.**

**Interview trap:**
A migrated VM can be perfectly healthy while the **application is broken because one dependency was left behind**.

**Keywords:**
Dependency mapping, Azure Migrate, migration groups, migration waves, hybrid connectivity, DNS, identity, database, latency, source of truth.

**Likely follow-ups:**

* How would you identify dependencies that Azure Migrate didn't discover?
* Why are chatty applications difficult to split across Azure and on-prem?
* How do stateful dependencies affect rollback?
* Would every dependency need to migrate in the same wave?

# **T31-M04. How would you choose an Azure VM size for an existing on-premises server?**

**Answer:**

I would **not map the on-premises server specification directly to the same number of Azure vCPUs and RAM** unless I had no reliable performance data.

I would collect representative performance data for CPU, memory, disk IOPS, disk throughput, and network usage, then use a **performance-based Azure Migrate assessment** to identify suitable Azure VM sizes. I would also account for workload characteristics such as CPU-to-memory ratio, accelerated networking requirements, local/temp disk needs, premium-storage support, generation, architecture, availability-zone support, and regional SKU availability.

Then I would add reasonable headroom, verify the price, test the workload under representative load, and monitor after migration so I can right-size again.

Azure Migrate currently supports both **as-is on-premises sizing** and **performance-based sizing**. Performance-based sizing uses measured utilization and is especially useful where on-prem servers are overallocated. ([Microsoft Learn][3])

---

## **1. Start with workload behavior, not VM names**

Suppose the source server is:

```text
16 vCPU
64 GB RAM
```

That only tells me:

```text
allocated capacity
```

not:

```text
required capacity
```

If historical usage is:

```text
CPU p95 = 20%
Memory p95 = 35%
```

then matching 16 vCPUs in Azure may be wasteful.

---

# **2. Capture representative performance data**

I want:

```text
CPU utilization
Memory utilization
Disk IOPS
Disk throughput
Disk capacity
Network throughput
```

over a meaningful workload period.

Azure Migrate's current performance-based assessment uses CPU and memory utilization for compute recommendations and IOPS/throughput for disk recommendations. ([Microsoft Learn][3])

---

# **3. Prefer percentile data over a simple average**

Suppose CPU usage is:

```text
Average = 20%
```

but:

```text
Every weekday 10 AM
CPU = 85%
```

If I size from the average:

```text
VM too small
```

may result.

Azure Migrate performance assessments can use a selected utilization percentile over a selected performance-history period.

For example:

```text
95th percentile
```

means it sizes around the utilization level exceeded by only the top roughly 5% of samples.

Azure Migrate also allows using higher percentiles such as 99th when peak behavior is more important. ([Microsoft Learn][4])

---

# **4. Add headroom with a comfort factor**

Suppose:

```text
16 allocated cores

p95 actual CPU
= 20%
```

Equivalent measured demand:

```text
16 × 0.20
≈ 3.2 cores
```

I probably don't choose exactly 4 cores with zero margin.

Azure Migrate can apply a **comfort factor** above measured usage.

Conceptually:

```text
Measured demand
      ×
Comfort factor
      ↓
Target requirement
```

Microsoft's documentation currently gives the example of using a comfort factor to account for short performance histories, seasonal growth, and unexpected load. ([Microsoft Learn][4])

---

# **5. CPU and RAM are only the beginning**

Suppose Azure Migrate suggests a VM with:

```text
4 vCPU
16 GB RAM
```

but the application requires:

```text
10,000 disk IOPS
```

Not every 4-vCPU Azure VM can support the required storage performance.

I also check:

```text
Maximum disk IOPS
Maximum disk throughput
NIC/network bandwidth
Premium SSD support
Ultra Disk support if needed
Accelerated Networking
Temp disk characteristics
```

The VM has to satisfy **all bottlenecks**, not only CPU.

---

# **6. Choose the right VM family**

A rough mental model:

```text
D-series
→ general purpose

E-series
→ memory optimized

F-series
→ compute optimized
```

plus other specialized families depending on requirements.

Example:

```text
Database:
CPU = moderate
Memory = very high
```

I'd probably investigate a memory-optimized family rather than blindly selecting a general-purpose VM with enough RAM.

---

# **7. Check architecture and OS compatibility**

I also validate:

```text
x64 or Arm?
Generation 1/2 requirements?
UEFI?
OS supported?
Drivers?
Kernel?
Licensing?
```

The cheapest theoretical VM is useless if the workload can't boot or software licensing forbids the configuration.

---

# **8. Check regional availability**

Suppose assessment recommends:

```text
SKU X
```

but the target region doesn't offer it or subscription quota is insufficient.

Before finalizing:

```bash
az vm list-skus \
  --location centralindia \
  --resource-type virtualMachines \
  --output table
```

This helps confirm available VM SKUs.

I would also check:

```text
subscription quota
zone availability
capacity constraints
```

because a supported SKU does not guarantee capacity at every moment.

---

# **9. Availability Zones can affect SKU choice**

Suppose production requires:

```text
Zone 1 + Zone 2 + Zone 3
```

Then the chosen VM SKU must be available in the required zones for that region.

I wouldn't discover during deployment that:

```text
SKU supported in region
but not desired zone
```

or quota is missing.

---

# **10. Disk sizing must use performance, not only capacity**

On-prem disk:

```text
2 TB
```

does not tell me whether I need:

```text
Standard SSD
Premium SSD
Ultra Disk
```

I need:

```text
Consumed capacity
IOPS
Throughput
Latency
```

Azure Migrate considers disk IOPS and throughput during performance-based storage recommendations. ([Microsoft Learn][3])

---

# **11. Network throughput can constrain the VM**

Imagine a server uses:

```text
5 Gbps
```

during peak processing.

A low-cost VM with enough CPU and RAM but inadequate networking could become:

```text
network bottleneck
```

after migration.

So target sizing is multidimensional:

```text
CPU
RAM
Disk
Network
```

not:

```text
CPU + RAM only
```

---

# **12. Performance coverage matters**

Suppose Azure Migrate shows:

```text
CPU data = good
RAM data = good
Disk IOPS = missing
Network = incomplete
```

Then the recommendation has lower confidence.

Microsoft explicitly exposes performance-coverage information to help assess how reliable performance-based recommendations are. ([Microsoft Learn][7])

I would investigate missing data before accepting the target size for a critical workload.

---

# **13. Example**

Source server:

```text
16 vCPU
64 GB RAM
2 TB disk
```

Observed:

```text
CPU p95 = 22%
RAM p95 = 40%
Disk max = 3,000 IOPS
Throughput = 120 MB/s
Network peak = 600 Mbps
```

Instead of:

```text
Azure:
16 vCPU
64 GB
```

Azure Migrate may indicate that a smaller target could satisfy actual utilization.

I would then:

```text
Check suggested SKU
      ↓
Check disk/network limits
      ↓
Apply capacity headroom
      ↓
Check region/zone availability
      ↓
Estimate cost
      ↓
Test workload
```

---

# **14. Include future growth**

Historical data tells me:

```text
what happened
```

not necessarily:

```text
what will happen next year
```

If business predicts:

```text
50% transaction growth
```

I need that in the sizing decision.

Options:

```text
larger initial VM
```

or:

```text
architecture capable of scaling
```

depending on workload.

---

# **15. Test migration before production cutover**

I would run:

```text
Azure Migrate test migration
or equivalent isolated test
```

then execute:

```text
synthetic load
business transactions
database operations
batch jobs
```

and compare with the baseline.

Target:

```text
p95 latency <= agreed requirement
IOPS within limits
CPU headroom acceptable
memory healthy
no throttling
```

The assessment is the starting recommendation.

Production validation is the proof.

---

# **16. Right-size again after migration**

Cloud gives us the advantage that we can observe real Azure behavior.

After:

```text
2–4 weeks representative production usage
```

I would review:

```text
CPU
memory
disk
network
application latency
cost
```

and resize if necessary.

Initial sizing should not be treated as permanent.

---

# **17. As-is sizing has a valid use**

Performance data isn't always trustworthy or available.

Examples:

```text
new workload
monitoring unavailable
server runs rare monthly batch
assessment window too short
```

Then I may initially use:

```text
as-is sizing
```

plus conservative headroom.

Azure Migrate explicitly supports as-is sizing where recommendations are based on allocated on-prem configuration rather than performance history. ([Microsoft Learn][3])

---

### **Interview answer condensed**

> “I would avoid one-to-one sizing from the current on-prem specification because those servers are often overprovisioned. I'd collect representative CPU, memory, disk IOPS/throughput, and network data and use an Azure Migrate performance-based assessment, including a sensible percentile and comfort factor for headroom. Then I'd validate that the recommended SKU also satisfies disk and network limits, OS and architecture compatibility, zone/region availability, and subscription quota. I'd load-test the migrated workload against the pre-migration baseline and right-size again after observing real Azure production usage.”

**Memory line:**
**Size for measured workload demand plus justified headroom—not for the sticker on the old physical server.**

**Interview trap:**
A VM with enough **CPU and RAM can still be undersized because of disk IOPS, throughput, or network limits**.

**Keywords:**
Azure Migrate, performance-based sizing, as-is sizing, percentile, comfort factor, IOPS, throughput, VM family, right-sizing.

**Likely follow-ups:**

* Why would you use the 95th percentile instead of average CPU?
* What is Azure Migrate's comfort factor?
* What would you do if performance coverage is low?
* Why might the recommended VM still perform poorly after migration?

# **T31-M05. When should an application be rehosted versus modernized?**

**Answer:**

I would **rehost** when the primary goal is to move the workload quickly with minimal application change—for example because of a datacenter-exit deadline, limited engineering capacity, high application-change risk, or because the application is stable and does not justify immediate redesign.

I would **modernize** when the current architecture is creating meaningful problems such as high operational overhead, poor scalability, reliability limitations, unsupported technology, slow deployment cycles, or high infrastructure cost, and the business value justifies changing the application or platform.

A common practical strategy is:

```text
Rehost first
      ↓
meet migration deadline
      ↓
stabilize in Azure
      ↓
modernize selectively
```

rather than combining infrastructure migration and major application redesign into one high-risk cutover.

Microsoft's current modernization guidance distinguishes **replatforming, refactoring, and rearchitecting** as progressively more significant modernization strategies. Replatforming targets PaaS with minimal code change; refactoring modifies code; rearchitecting makes larger architecture changes. ([Microsoft Learn][8])

---

# **Start from business constraints**

I ask:

```text
What is the deadline?
What business problem are we solving?
How much downtime is acceptable?
How much application change is acceptable?
How much engineering capacity exists?
When is the workload being retired?
```

The answers often decide whether modernization makes sense.

---

# **Choose rehost when speed matters**

Example:

```text
Datacenter contract ends
in 4 months
```

but the organization has:

```text
70 applications
```

Rewriting everything first would likely miss the deadline.

So:

```text
VMware
   ↓
Azure VMs
```

may be the appropriate first step.

---

# **Choose rehost when application change is too risky**

Suppose:

```text
15-year-old vendor application
```

with:

```text
little documentation
no source code
vendor support constraints
```

Trying to containerize or refactor it could create massive risk.

If it's compatible with Azure VMs:

```text
Rehost
```

is much more sensible.

---

# **Choose rehost when workload has a short remaining lifetime**

Suppose the application will be retired in:

```text
18 months
```

Would I spend:

```text
6 months
```

rewriting it into microservices?

Probably not.

A small rehost may be financially and operationally more rational.

---

# **But rehost can preserve operational overhead**

Example:

```text
On-prem:
Windows VM
IIS
SQL Server VM
manual patching
manual backup
```

Rehost:

```text
Azure VMs
Windows
IIS
SQL Server
```

I still own much of:

```text
OS patching
VM monitoring
capacity
HA
backup configuration
```

So rehosting doesn't automatically give the full operational benefits of cloud-native services.

---

# **Modernize when PaaS removes meaningful toil**

Suppose application is compatible with:

```text
Azure App Service
```

Instead of:

```text
Azure VM
├── Windows patching
├── IIS configuration
├── VM backup
└── server lifecycle
```

I may replatform:

```text
App Service
```

and shift more infrastructure responsibility to Azure.

Microsoft's current guidance specifically positions **replatforming** as a way to reduce operational overhead or improve reliability using PaaS with limited code changes. ([Microsoft Learn][8])

---

# **Modernize when scalability is constrained**

Suppose:

```text
Application stores session locally
```

and only runs safely on:

```text
one server
```

Traffic growth requires:

```text
horizontal scaling
```

Then simple rehosting might just move:

```text
single-server bottleneck
```

into Azure.

I might refactor:

```text
local session
      ↓
shared state/cache
```

and make the application stateless enough to scale.

---

# **Modernize when architecture harms reliability**

Example:

```text
Web
 ↓
synchronous monolith
 ↓
long-running batch
 ↓
single database
```

One batch job blocks customer requests.

Potential modernization:

```text
Web/API
   ↓
Service Bus
   ↓
Worker
```

Now background work is decoupled.

That may provide more business value than simply moving the same VM.

---

# **Modernize when technology is unsupported**

Suppose:

```text
Unsupported OS
Unsupported .NET version
End-of-life database
```

Rehosting may technically move it but leave:

```text
security risk
support risk
```

unchanged.

A modernization project may be necessary before or during migration.

---

# **Modernize when development velocity is the real problem**

Suppose the infrastructure works, but:

```text
deployment takes 4 hours
requires downtime
one release per quarter
```

The application architecture may be limiting business agility.

Refactoring/rearchitecting might enable:

```text
CI/CD
safe deployment
independent components
better testing
```

which may justify the investment.

---

# **Evaluate cost carefully**

People often say:

> “PaaS is always cheaper.”

Not necessarily.

I would compare:

```text
VM infrastructure cost
+
patching
+
operations
+
backup
+
HA
+
engineering effort
```

against:

```text
PaaS consumption
+
migration engineering
+
possible architectural changes
```

Modernization may cost more initially but reduce lifecycle cost.

---

# **Rehost-first can reduce migration risk**

Suppose I simultaneously change:

```text
on-prem → Azure
Windows VM → Linux container
SQL Server → PostgreSQL
service account → Managed Identity
monolith → microservices
```

If production breaks:

```text
Which change caused it?
```

Rollback is very complex.

A phased strategy:

```text
Phase 1
Rehost

Phase 2
Stabilize

Phase 3
Replatform DB

Phase 4
Refactor identity/observability

Phase 5
Rearchitect only where justified
```

may be safer.

---

# **But don't blindly rehost everything**

There is a danger in saying:

> “We'll modernize later.”

and then never doing it.

Five years later:

```text
same legacy VMs
+
higher Azure bill
+
same manual operations
```

So if using rehost-first, I would identify:

```text
modernization candidates
owner
business case
target state
timeline
```

during migration planning.

# **Useful decision matrix**

| Condition                    |         Rehost |         Modernize |
| ---------------------------- | -------------: | ----------------: |
| Datacenter exit urgently     |   ✅ Strong fit |       Maybe later |
| No source code               |              ✅ |         Difficult |
| Workload retiring soon       |              ✅ |  Usually poor ROI |
| Stable low-change legacy app |              ✅ | Maybe unnecessary |
| High VM operational toil     |       Possible |                 ✅ |
| Scaling problems             |           Weak |                 ✅ |
| Unsupported runtime          | Temporary only |                 ✅ |
| Need cloud-native resilience |        Limited |                 ✅ |
| Frequent business change     |           Weak |                 ✅ |
| Large technical debt         |     Moves debt |    ✅ if justified |

# **Modernization itself has levels**

Modernization does not automatically mean:

```text
microservices
```

It may be:

### Replatform

```text
VM app
→ App Service
```

Minimal application change.

### Refactor

```text
stored secret
→ Managed Identity
```

or:

```text
local state
→ external state
```

### Rearchitect

```text
tightly coupled monolith
→ substantially redesigned architecture
```

Microsoft's current modernization guidance uses these as distinct modernization approaches rather than treating modernization as one single action. ([Microsoft Learn][8])

---

# **Example 1 — Rehost**

Application:

```text
.NET Framework
Windows Server
IIS
Vendor-supported
Retires in 2 years
Datacenter closes in 3 months
```

Decision:

```text
Rehost
→ Azure VM
```

Why:

```text
Deadline
+
limited remaining lifespan
+
high rewrite risk
```

---

# **Example 2 — Replatform**

Application:

```text
.NET 8 web API
stateless
supported on App Service
```

Decision:

```text
App Service
```

because we can reduce VM management with limited application change.

---

# **Example 3 — Refactor**

Application:

```text
local session state
hardcoded secrets
no telemetry
```

Modernize:

```text
external session/cache
Managed Identity
OpenTelemetry/Application Insights
```

This improves cloud suitability without necessarily rewriting the entire architecture.

---

# **Example 4 — Rearchitect**

Application:

```text
one monolith
takes 2 hours to deploy
single component failure
takes whole service down
independent scaling impossible
```

If business value justifies it, I might redesign the architecture.

But I would not say:

```text
microservices automatically
```

without proving that the additional complexity is worth it.

---

# **Decision sequence**

My actual process:

```text
1. Business value
       ↓
2. Migration deadline
       ↓
3. Remaining application lifetime
       ↓
4. Current operational pain
       ↓
5. Scalability/reliability limitations
       ↓
6. Technical debt/supportability
       ↓
7. Engineering capacity
       ↓
8. Modernization ROI
       ↓
9. Choose:
   Rehost
   Replatform
   Refactor
   Rearchitect
```

---

### **Interview answer condensed**

> “I would rehost when the priority is speed and low application-change risk—for example a datacenter exit, a stable legacy workload, limited engineering capacity, or an application nearing retirement. I'd modernize when the existing design is causing real business or operational problems such as poor scalability, unsupported technology, high VM-management toil, reliability issues, or slow release cycles. Modernization doesn't have to mean a full rewrite; I might replatform to App Service or SQL Managed Instance, refactor specific cloud-unfriendly code, or rearchitect only where the value justifies the complexity. Under a tight deadline, a common approach is to rehost first, stabilize, and modernize selected workloads afterward.”

**Memory line:**
**Rehost when moving quickly matters most; modernize when changing the workload creates enough long-term value to justify the risk and effort.**

**Interview trap:**
Do not assume every Azure migration should become **microservices or Kubernetes**—modernization must have a business and technical reason.

**Keywords:**
Rehost, modernization, replatform, refactor, rearchitect, technical debt, operational toil, scalability, migration risk, ROI.

**Likely follow-ups:**

* Would you modernize during migration or after migration?
* When is App Service a better target than Azure VMs?
* What risks come from a rehost-first strategy?
* How would you justify modernization cost to the business?
