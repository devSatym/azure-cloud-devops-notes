### **T16-H01. Why might a VM resolve an Azure PaaS service to its public address despite a private endpoint existing?**

**Answer:**
If a VM resolves an Azure PaaS service to a **public IP even though a Private Endpoint exists**, I would treat it primarily as a **DNS-path problem**. A Private Endpoint does not force every client to use it. The VM must resolve the service's normal FQDN through the correct **Private DNS zone** so it gets the Private Endpoint's IP.

Microsoft's current troubleshooting guidance says the most common causes are a missing VNet link, a missing/stale A record, or custom DNS that isn't forwarding Private Link queries correctly. ([Microsoft Learn][1])

### **Diagnostic order**

```text
VM
 ↓
service.azure-domain
 ↓
DNS query
 ↓
Public IP returned
 ↓
Why wasn't Private DNS used?
```

#### **1. Prove the DNS result**

From the VM:

```bash
nslookup mystorage.blob.core.windows.net
```

or:

```bash
dig mystorage.blob.core.windows.net
```

If the result is:

```text
20.x.x.x
```

instead of:

```text
10.x.x.x
```

I know the Private Endpoint isn't being selected through DNS.

---

#### **2. Verify the correct Private DNS zone**

For example:

```text
Blob Storage
→ privatelink.blob.core.windows.net

Azure SQL
→ privatelink.database.windows.net

Key Vault
→ privatelink.vaultcore.azure.net
```

I check:

```text
Private DNS zone exists?
       ↓
Correct A record exists?
       ↓
A record points to Private Endpoint IP?
```

Example:

```text
mystorage
→ 10.20.5.7
```

If the record is absent or stale:

```text
Private Endpoint exists ✓
DNS mapping ✗
```

and the public result can be returned instead. ([Microsoft Learn][1])

---

#### **3. Verify the VM's VNet is linked to the zone**

This is one of the most common failures.

```text
Private DNS Zone
       │
       X  missing link
       │
Application VNet
       ↓
VM
```

The correct design might be:

```text
privatelink.blob.core.windows.net
            │
         VNet Link
            ↓
        prod-vnet
            ↓
             VM
```

Microsoft's latest Private Endpoint troubleshooting guidance identifies a missing zone-to-querying-VNet link as the **most common** reason the FQDN resolves publicly. ([Microsoft Learn][1])

---

#### **4. Check which DNS server the VM actually uses**

On Linux:

```bash
cat /etc/resolv.conf
```

or:

```bash
resolvectl status
```

Maybe the architecture uses:

```text
VM
 ↓
Corporate DNS
10.0.0.10
```

instead of Azure-provided DNS.

Then:

```text
Private DNS Zone correctly linked ✓

but

Corporate DNS
 ↓
Public resolver
 ↓
Public PaaS IP
```

The VNet link alone doesn't fix that custom-DNS path.

---

#### **5. Check conditional forwarding**

For custom DNS, the query needs to reach Azure's private DNS resolution path.

A production pattern is:

```text
VM
 ↓
Corporate DNS
 ↓
conditional forwarder
 ↓
Azure DNS Private Resolver
 ↓
Private DNS Zone
 ↓
10.20.5.7
```

Microsoft specifically lists incorrect or missing conditional forwarding as a common reason Private Endpoint names resolve publicly. ([Microsoft Learn][2])

---

#### **6. Don't point on-premises DNS directly at `168.63.129.16`**

This is a good interview detail.

Azure's virtual DNS address:

```text
168.63.129.16
```

is reachable **inside Azure VNets**, not directly from an on-premises network.

For on-premises clients, use:

```text
On-prem DNS
     ↓
conditional forwarder
     ↓
DNS Private Resolver inbound endpoint
     ↓
Azure Private DNS
```

Microsoft's current hybrid DNS troubleshooting guidance explicitly warns that `168.63.129.16` isn't reachable across VPN or ExpressRoute from on-premises. ([Microsoft Learn][3])

---

#### **7. Compare against a known-good machine**

If:

```text
VM A → private IP
VM B → public IP
```

I compare:

```text
DNS server configuration
VNet
Private DNS zone links
custom DNS settings
DNS cache
```

rather than changing the Private Endpoint itself.

---

#### **8. Flush stale cache after a DNS change**

If the DNS architecture was recently corrected, stale records may remain cached.

Depending on OS:

```bash
sudo resolvectl flush-caches
```

Then retest.

---

### **Strong interview answer**

> “If a VM resolves a PaaS service publicly despite a Private Endpoint existing, I start with DNS. I verify the normal service FQDN using `nslookup` and confirm whether it resolves to the Private Endpoint IP. If it doesn't, I inspect the service-specific `privatelink` Private DNS zone, its A record, and especially whether that zone is linked to the querying VNet. If the VNet uses custom DNS, I verify conditional forwarding toward Azure DNS Private Resolver. I wouldn't change NSGs yet because if DNS returns the public address, the packet isn't even trying to reach the Private Endpoint.”

**Memory line:**
**Private Endpoint exists + FQDN resolves publicly = investigate DNS path before network policy.**

**Interview trap:**
Do not assume **creating the Private Endpoint automatically changes DNS for every VNet**.

**Keywords:**
Private DNS, VNet link, `privatelink.*`, A record, custom DNS, DNS Private Resolver

**Likely follow-ups:**

* What if the FQDN resolves privately but TCP still fails?
* Why does the application use the normal service hostname?
* Can peered VNets automatically use another VNet's Private DNS zone?
* Why can't on-prem DNS query `168.63.129.16` directly?

### **T16-H02. How would on-premises clients resolve Azure private endpoints?**

**Answer:**
I would use **conditional DNS forwarding from the on-premises DNS servers to an Azure DNS Private Resolver inbound endpoint**. The Azure Private DNS zones containing the Private Endpoint records are linked to a VNet where the resolver can resolve them. On-premises clients continue querying their normal corporate DNS server; they don't need Azure-specific DNS settings individually.

Microsoft recommends Azure DNS Private Resolver for this hybrid pattern. ([Microsoft Learn][2])

### **Architecture**

```text
On-prem application
       ↓
On-prem DNS server
       ↓
Conditional forwarder
       ↓
VPN / ExpressRoute
       ↓
DNS Private Resolver
Inbound Endpoint
10.10.0.4
       ↓
Azure Private DNS
       ↓
Private Endpoint
10.20.5.7
```

---

### **1. Start with network connectivity**

Before DNS, the on-prem network needs connectivity into Azure:

```text
On-prem
   ↓
Site-to-Site VPN
or
ExpressRoute
   ↓
Azure Hub VNet
```

This provides reachability toward:

```text
DNS resolver
+
Private Endpoint IP
```

DNS resolution alone doesn't create the network path.

---

### **2. Deploy Azure DNS Private Resolver**

Usually in the connectivity/hub VNet:

```text
Hub VNet
│
├── DNS Private Resolver
│     ├── Inbound endpoint
│     └── Outbound endpoint (if needed)
│
└── Private DNS zones
```

The **inbound endpoint** gets private IPs that external DNS infrastructure can query.

Microsoft defines the inbound endpoint as the target for DNS queries originating outside that VNet, including from on-premises environments. ([Microsoft Learn][2])

---

### **3. Link Azure Private DNS zones**

Example:

```text
privatelink.database.windows.net
              │
           VNet Link
              ↓
           Hub VNet
```

The zone contains:

```text
sql-prod
→ 10.20.5.10
```

which represents:

```text
SQL Private Endpoint
```

---

### **4. Configure an on-prem conditional forwarder**

For example:

```text
On-prem DNS
```

receives:

```text
sql-prod.database.windows.net
```

and forwards the relevant Azure private namespace toward:

```text
Azure DNS Private Resolver
Inbound IP
10.10.0.4
```

Microsoft's hybrid DNS guidance recommends conditional forwarding from on-premises DNS to the resolver's inbound endpoint for Azure Private DNS resolution. ([Microsoft Learn][4])

---

### **5. Query flow**

The user/application does nothing special:

```text
Application
 ↓
sql-prod.database.windows.net
 ↓
Corporate DNS
 ↓
conditional forwarding
 ↓
Azure DNS Private Resolver
 ↓
Private DNS Zone
 ↓
10.20.5.10
```

The returned answer reaches the application:

```text
sql-prod.database.windows.net
→ 10.20.5.10
```

Then SQL traffic flows:

```text
On-prem application
       ↓
VPN / ExpressRoute
       ↓
10.20.5.10
       ↓
Private Endpoint
       ↓
Azure SQL
```

---

### **6. Don't point on-prem DNS at Azure virtual DNS directly**

Wrong:

```text
On-prem DNS
     ↓
168.63.129.16
```

Microsoft's latest troubleshooting documentation explicitly says `168.63.129.16` is an **Azure-internal address** and isn't directly reachable across VPN or ExpressRoute. ([Microsoft Learn][3])

Correct:

```text
On-prem DNS
     ↓
Private Resolver inbound endpoint
     ↓
Azure DNS
```

---

### **7. Bidirectional DNS if Azure also needs on-prem names**

Maybe:

```text
Azure VM
 ↓
db.corp.internal
```

must resolve on-premises resources.

Then I also configure:

```text
DNS Private Resolver
Outbound Endpoint
       ↓
Forwarding Ruleset
       ↓
On-prem DNS
```

So:

```text
On-prem → Azure private names
= inbound endpoint

Azure → on-prem private names
= outbound endpoint + ruleset
```

Microsoft's current architecture guidance describes precisely this bidirectional model. ([Microsoft Learn][2])

---

### **8. Troubleshooting order**

From on-prem:

```bash
nslookup sql-prod.database.windows.net
```

Then:

```text
1. Does corporate DNS receive query?

2. Conditional forwarder configured?

3. Can DNS server reach resolver IP TCP/UDP 53?

4. Resolver healthy?

5. Private DNS zone linked?

6. A record exists?

7. Private IP returned?

8. Can client route to that private IP?
```

Don't confuse:

```text
DNS succeeds
```

with:

```text
Private Endpoint reachable
```

Both layers must work.

---

### **Strong interview answer**

> “For on-premises Private Endpoint resolution, I would keep clients using the existing corporate DNS servers and configure those DNS servers with conditional forwarders toward an Azure DNS Private Resolver inbound endpoint in the hub VNet. The relevant `privatelink` Private DNS zones are linked into Azure so the resolver can return the Private Endpoint IP. The on-prem network must also have VPN or ExpressRoute connectivity to the resolver and Private Endpoint. For reverse resolution of on-prem names from Azure, I add a resolver outbound endpoint and forwarding ruleset.”

**Memory line:**
**On-prem DNS → conditional forwarder → Private Resolver inbound endpoint → Azure Private DNS → Private Endpoint IP.**

**Interview trap:**
Do not point on-prem DNS directly at `168.63.129.16`.

**Keywords:**
DNS Private Resolver, inbound endpoint, conditional forwarder, VPN, ExpressRoute, Private DNS

**Likely follow-ups:**

* What is the outbound endpoint used for?
* Does DNS Private Resolver replace VPN/ExpressRoute?
* Why can't on-prem query Azure DNS directly?
* How would you make DNS resolution redundant?

### **T16-H03. How would you provide private access to Azure PaaS services from multiple spoke networks?**

**Answer:**
I would design Private Link as a **shared platform capability** across the hub-and-spoke topology. PaaS resources would use **Private Endpoints**, their `privatelink.*` DNS zones would be centrally governed, and every spoke that needs a service would have both a **DNS resolution path** and a **network path** to the appropriate Private Endpoint.

I would deliberately separate:

```text
DNS architecture
from
network-routing architecture
```

because having one without the other doesn't provide working private connectivity.

Microsoft's Azure Architecture Center specifically documents Private Link designs for hub-and-spoke networks. ([Microsoft Learn][5])

### **High-level architecture**

```text
                    Shared Hub
        ┌───────────────────────────────┐
        │ DNS Private Resolver          │
        │ Private DNS Zones             │
        │ Firewall / connectivity       │
        └──────────────┬────────────────┘
                       │
              ┌────────┼────────┐
              ↓        ↓        ↓
           Spoke A   Spoke B   Spoke C
              \        |        /
               \       |       /
                  Private
                 Endpoints
                     ↓
             SQL / Storage /
             Key Vault / ACR
```

---

### **1. Decide where Private Endpoints live**

There are two broad approaches.

#### **A. Centralized Private Endpoints**

```text
Hub / shared-services VNet
      ↓
Private Endpoints
```

Advantages:

```text
central governance
simpler discovery
shared DNS model
security-team ownership
```

But consider:

```text
cross-spoke traffic
routing design
blast radius
ownership
```

---

#### **B. Private Endpoint in application spokes**

```text
Spoke A
→ SQL PE A

Spoke B
→ SQL PE B
```

Advantages:

```text
application isolation
local ownership
simple local routing
```

Tradeoff:

```text
more endpoints
more IP consumption
more management/cost
```

The right choice depends on ownership, isolation, routing, and scale rather than a universal rule. Azure's architecture guidance explicitly presents multiple Private Link deployment patterns for hub-and-spoke environments. ([Microsoft Learn][5])

---

### **2. Centralize DNS zones**

I would usually govern zones such as:

```text
privatelink.database.windows.net
privatelink.blob.core.windows.net
privatelink.vaultcore.azure.net
privatelink.azurecr.io
```

centrally rather than letting every application team create competing copies.

Why?

Because duplicate independently managed zones can create:

```text
inconsistent records
broken name resolution
operational confusion
```

---

### **3. Give every spoke a DNS path**

For a smaller design:

```text
Private DNS Zone
 ├── link → Spoke A
 ├── link → Spoke B
 └── link → Spoke C
```

Then workloads using Azure DNS can resolve the records directly.

For larger enterprise environments, I would prefer:

```text
Shared Private DNS
       ↓
DNS Private Resolver
       ↓
forwarding architecture
       ↓
all spokes
```

Microsoft recommends centralized resolution with Azure DNS Private Resolver for multi-VNet environments. ([Microsoft Learn][2])

---

### **4. Provide the network path**

If the Private Endpoint is centralized:

```text
Spoke A
   ↓
VNet peering
   ↓
Hub/shared VNet
   ↓
PE 10.10.5.4
```

I verify:

```text
peering
UDRs
Azure Firewall
NSGs
address spaces
return path
```

Remember:

```text
DNS:
service → 10.10.5.4 ✓

but

route to 10.10.5.4 ✗
```

still means failure.

---

### **5. Avoid overlapping VNet CIDRs**

Suppose:

```text
Spoke A = 10.10.0.0/16
Spoke B = 10.10.0.0/16
```

centralized routing to Private Endpoints becomes problematic.

A large hub-spoke platform therefore needs planned, non-overlapping address space.

---

### **6. Central firewall inspection where required**

Architecture:

```text
Spoke
  ↓
UDR
  ↓
Azure Firewall/NVA
  ↓
Private Endpoint
```

may be used where routing/network policies and Private Endpoint network-policy configuration support the intended inspection model.

I verify both:

```text
forward path
return path
```

to avoid asymmetric routing.

---

### **7. Restrict PaaS public access**

After every required spoke has:

```text
DNS ✓
routing ✓
Private Endpoint ✓
identity ✓
```

I would normally configure:

```text
Public network access
→ Disabled
```

for private-only production resources where supported.

Final design:

```text
Spoke workloads
     ↓
private IPs
     ↓
Private Link

Internet
     X
PaaS public access
```

---

### **8. Identity stays separate**

Every spoke reaching the same Key Vault Private Endpoint doesn't mean every workload can read every secret.

Example:

```text
Spoke A Workload Identity
→ Key Vault Secrets User

Spoke B Workload Identity
→ no role
```

Then:

```text
Both can establish network path

Only Spoke A
→ authorized
```

So architecture needs:

```text
Private networking
+
Entra identity
+
least-privilege RBAC
```

---

### **9. Monitor centrally**

I would monitor:

```text
Private Endpoint state
DNS resolution
resolver availability
Firewall deny logs
connectivity tests
PaaS availability
```

For critical services, Connection Monitor or synthetic tests from representative spokes can detect:

```text
DNS works but endpoint unreachable
```

before applications report outages.

---

### **Strong interview answer**

> “For multiple spokes I would make Private Link a shared platform capability. PaaS services get Private Endpoints, and I centrally govern the service-specific Private DNS zones. For a small number of spokes I can link those zones directly to each spoke; at enterprise scale I prefer Azure DNS Private Resolver and centralized forwarding. I separately make sure every spoke has routing and security access to the Private Endpoint IP through peering or the hub. Once all private paths are validated, I disable PaaS public access where appropriate. Identity remains separate, so each workload still gets least-privilege RBAC.”

**Memory line:**
**Multi-spoke PaaS access needs two things everywhere: private DNS resolution + network reachability to the Private Endpoint.**

**Interview trap:**
Do not centralize DNS but forget routing—or centralize Private Endpoints but assume peering automatically shares DNS.

**Keywords:**
Hub-and-spoke, Private Link, Private Endpoint, Private DNS, DNS Private Resolver, centralized networking

**Likely follow-ups:**

* Central Private Endpoints vs per-spoke Private Endpoints?
* Should every spoke link to every Private DNS zone?
* How would you inspect traffic through Azure Firewall?
* How would on-premises clients join this design?

### **T16-H04. How would you design centralized private DNS in hub-and-spoke architecture?**

**Answer:**
I would place **Azure DNS Private Resolver in the hub/connectivity VNet**, centrally manage the Azure Private DNS zones there, and provide resolution to spokes through either **direct zone links** or **DNS forwarding rulesets**, depending on scale and governance requirements. If on-premises DNS is involved, its conditional forwarders point to the resolver's **inbound endpoint**. Azure workloads that need on-premises names use the resolver's **outbound endpoint and forwarding rulesets**.

Microsoft's current networking guidance recommends this centralized resolver model for hub-and-spoke and hybrid environments. ([Microsoft Learn][2])

### **Architecture**

```text
                       On-premises
                           │
                    Corporate DNS
                           │
                 conditional forward
                           ↓
                ┌──────────────────┐
                │     HUB VNet     │
                │                  │
                │ DNS Private      │
                │ Resolver         │
                │                  │
                │ Inbound Endpoint │
                │ Outbound Endpoint│
                │                  │
                │ Private DNS Zones│
                └────────┬─────────┘
                         │
                DNS forwarding rules
            ┌────────────┼────────────┐
            ↓            ↓            ↓
         Spoke A       Spoke B      Spoke C
            │            │            │
            ↓            ↓            ↓
      Private Endpoints / internal resources
```

---

### **1. Centralize Private DNS zones**

For example:

```text
Connectivity subscription
└── Private DNS resource group
    ├── privatelink.database.windows.net
    ├── privatelink.blob.core.windows.net
    ├── privatelink.vaultcore.azure.net
    └── privatelink.azurecr.io
```

This creates one authoritative platform-managed location instead of:

```text
Team A SQL zone
Team B SQL zone
Team C SQL zone
```

which becomes difficult to govern.

---

### **2. Deploy DNS Private Resolver in the hub**

I use dedicated subnets:

```text
Hub VNet
│
├── resolver-inbound-subnet
└── resolver-outbound-subnet
```

Microsoft requires separate delegated subnets for inbound and outbound resolver endpoints. ([Microsoft Learn][2])

Conceptually:

```text
Inbound Endpoint
→ DNS queries coming INTO Azure resolution

Outbound Endpoint
→ Azure forwarding queries OUT to
  on-prem/other DNS systems
```

---

### **3. Resolve Azure Private Endpoints from spokes**

There are two useful patterns.

#### **Pattern A — direct zone links**

```text
Private DNS Zone
 ├── Spoke A link
 ├── Spoke B link
 └── Spoke C link
```

Simple and perfectly reasonable for smaller environments.

---

#### **Pattern B — centralized forwarding**

For a larger design:

```text
Spoke A ─┐
Spoke B ─┼→ DNS forwarding architecture → hub resolver
Spoke C ─┘
```

with shared rules.

Microsoft notes that VNets linked to DNS forwarding rulesets can use those rules **without needing VNet peering purely for DNS resolution**. ([Microsoft Learn][6])

This is a useful distinction:

```text
DNS ruleset relationship
≠
network peering relationship
```

although the workload still needs actual network connectivity to the final private resource.

---

### **4. Resolve Azure private names from on-premises**

On-prem corporate DNS:

```text
database.windows.net
or appropriate Azure private namespace
       ↓
conditional forwarder
       ↓
Private Resolver inbound IP
```

Then:

```text
Inbound Endpoint
      ↓
Azure DNS
      ↓
Private DNS Zone
      ↓
SQL Private Endpoint IP
```

Microsoft's Cloud Adoption Framework specifically recommends on-prem conditional forwarding toward a DNS Private Resolver inbound endpoint. ([Microsoft Learn][4])

---

### **5. Resolve on-premises names from Azure**

Suppose a workload in Spoke A requests:

```text
db.corp.contoso.com
```

Flow:

```text
Spoke
 ↓
Azure DNS
 ↓
DNS forwarding ruleset
 ↓
Resolver outbound endpoint
 ↓
On-prem DNS
 ↓
10.x corporate address
```

So the architecture becomes bidirectional:

```text
On-prem → Azure
= inbound endpoint

Azure → on-prem
= outbound endpoint
```

---

### **6. Add redundancy**

DNS is production-critical infrastructure.

For important hybrid environments I consider:

```text
multiple resolver endpoints
regional resiliency
redundant VPN/ExpressRoute paths
multiple on-prem DNS servers
multiple conditional-forwarder targets
```

Microsoft publishes a reference design using resolvers across regions so on-premises DNS can fall back if one path or resolver becomes unavailable. ([Microsoft Learn][7])

---

### **7. Govern it centrally**

I would restrict who can modify:

```text
Private DNS zones
VNet links
resolver
forwarding rules
Private Endpoint DNS records
```

to the platform/network team or an automated IaC pipeline.

Application teams request:

```text
new Private Endpoint
```

and automation handles:

```text
PE
+
zone association
+
record
+
validation
```

This avoids configuration drift.

---

### **8. Use Infrastructure as Code**

For example:

```text
Terraform
   ↓
Hub DNS architecture
   ├── Private Resolver
   ├── endpoints
   ├── rulesets
   ├── Private DNS zones
   └── VNet/ruleset links
```

rather than manually configuring dozens of zones in the portal.

---

### **9. Monitor DNS itself**

I would monitor:

```text
Resolver availability
DNS failures/NXDOMAIN trends
private endpoint health
network reachability to resolver
TCP/UDP 53
```

During an incident I separate:

```text
Can I reach the DNS server?
        ↓
Can DNS resolve the name?
        ↓
Can I reach the returned IP?
```

That's the fastest diagnostic hierarchy.

```text
                    On-prem DNS
                         │

                         ↓
                 HUB CONNECTIVITY
        ┌────────────────────────────────┐
        │ Azure DNS Private Resolver     │
        │                                │
        │ inbound        outbound        │
        │    │               │           │
        │ Private DNS    forwarding      │
        │ zones          rulesets        │
        └──────────────┬─────────────────┘
                       │

        ↓              ↓              ↓
```

> **In an interview, I would say:**
> “I centralize private DNS in the hub/connectivity layer. The platform team owns the `privatelink.*` Private DNS zones and an Azure DNS Private Resolver. Its inbound endpoint allows on-premises DNS servers to forward Azure-private queries into Azure. Its outbound endpoint and forwarding rulesets allow Azure workloads to resolve on-premises namespaces. Spokes either link directly to the appropriate zones in smaller environments or use centrally managed forwarding rulesets at scale. I deploy the whole DNS layer with IaC and add redundant resolver/connectivity paths because DNS becomes a critical shared service.”

**Memory line:**
**Central DNS hub = Private DNS zones + Private Resolver + inbound for on-prem → Azure + outbound for Azure → on-prem.**

**Interview trap:**
Do not make a single hand-built DNS VM in the hub your only resolver for the entire enterprise when Azure DNS Private Resolver can provide a managed architecture.

Azure DNS Private Resolver, hub-and-spoke, inbound endpoint, outbound endpoint, forwarding ruleset, conditional forwarding
