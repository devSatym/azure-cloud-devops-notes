### **T18-E04. What are Azure tags?**

**Answer:**
Azure tags are **key-value metadata** attached to Azure resources, resource groups, and subscriptions to help organize, search, report, automate, and allocate costs.

Example:

```text
Environment = Production
Owner       = Platform-Team
CostCenter  = CC-1042
Application = Payments
```

So instead of relying only on names such as:

```text
vm-prod-payments-01
```

I can query resources based on structured metadata:

```text
Environment = Production
AND
Application = Payments
```

Microsoft defines Azure tags as metadata key-value pairs used to identify resources based on organizational information. ([Microsoft Learn][1])

---

### **Common uses**

Tags are especially useful for:

```text
Cost allocation
Resource ownership
Environment classification
Application mapping
Automation
Operational reporting
Governance
```

For example:

```text
Subscription
│
├── VM
│   ├── Environment = Prod
│   ├── Owner = SRE
│   └── CostCenter = 2001
│
└── Storage
    ├── Environment = Prod
    ├── Owner = Data
    └── CostCenter = 2001
```

Then Azure Cost Management can group costs using tags. ([Microsoft Learn][1])

---

### **Where can tags be applied?**

Azure supports tags on:

```text
Subscriptions
Resource Groups
Resources
```

But not directly on:

```text
Management Groups
```

according to current Azure Resource Manager guidance. ([Microsoft Learn][1])

---

### **Important: tags are NOT automatically inherited**

This is a common interview trap.

Suppose:

```text
Resource Group
Environment = Production
```

and inside it:

```text
VM01
```

The VM does **not automatically receive**:

```text
Environment = Production
```

Azure Resource Manager tags don't inherit from subscription/resource-group scope to resources by default. ([Microsoft Learn][1])

If I want inheritance, I can use:

```text
Azure Policy
    ↓
Modify effect
    ↓
inherit tag from resource group/subscription
```

Microsoft provides built-in policies for this pattern and supports remediation of existing resources. ([Microsoft Learn][2])

---

### **Example governance strategy**

I might standardize:

```text
Environment
Application
Owner
CostCenter
DataClassification
```

Then use Azure Policy to:

```text
Require CostCenter
Require Environment
Inherit Owner from Resource Group
Add/modify missing tags
```

This turns tags from:

```text
optional labels
```

into:

```text
governed metadata
```

---

### **Tags are not security controls**

I wouldn't use:

```text
SecurityLevel = Restricted
```

and assume the resource becomes protected.

Tags can drive automation and policy, but:

```text
Tag
≠ firewall
≠ RBAC
≠ encryption
```

They are metadata.

> **In an interview, I would say:**
> “Azure tags are key-value metadata that I use to organize and classify subscriptions, resource groups, and resources. Common examples are Environment, Owner, Application, and CostCenter, and they're especially useful for cost allocation and governance. Tags don't automatically inherit from a resource group or subscription to child resources, so at enterprise scale I use Azure Policy with the Modify effect to enforce or inherit required tags.”

**Memory line:**
**Tags = key-value metadata for ownership, environment, cost, and governance.**

**Interview trap:**
Tags on a Resource Group do **not automatically become tags on its resources**.

**Keywords:**
Tags, key-value metadata, CostCenter, Azure Policy, Modify, cost allocation

**Likely follow-ups:**

* Do tags automatically inherit?
* How would you enforce mandatory tags?
* Can management groups have tags?
* How do tags help with FinOps?

## **T18-M01. What is the difference between Azure Policy and Azure RBAC?**

**Answer:**
The cleanest distinction is:

```text
Azure RBAC
→ WHO can perform an action?

Azure Policy
→ WHAT resource configuration is allowed or required?
```

They solve different governance problems and are commonly used together.

---

### **Example**

Suppose a developer has:

```text
Role:
Contributor
```

RBAC might authorize:

```text
Create virtual machine ✓
```

But an Azure Policy says:

```text
Allowed locations:
Central India
West Europe
```

The developer tries:

```text
Create VM in East US
```

Flow:

```text
Developer
   ↓
Authentication ✓
   ↓
RBAC authorization ✓
"You are allowed to create VMs"
   ↓
Azure Policy evaluation
   ↓
Location = East US
   ↓
DENY
```

So:

```text
RBAC permitted the operation
but
Policy rejected the configuration
```

---

### **Azure RBAC**

RBAC is an **authorization system**.

A role assignment combines:

```text
Security principal
+
Role definition
+
Scope
```

Example:

```text
Managed Identity
      +
Storage Blob Data Reader
      +
Storage Account
```

Meaning:

> This identity may read blob data on this Storage Account.

---

### **Azure Policy**

Policy is primarily a **governance/compliance system**.

Example requirements:

```text
No public IPs in production
Only approved regions
Require tags
Require diagnostic settings
Approved VM SKUs only
```

A Policy definition contains a condition and an effect, such as:

```text
IF
public IP resource is being created

THEN
Deny
```

Microsoft describes policy definitions as defining resource compliance conditions and the effect applied when those conditions are met. ([Microsoft Learn][3])

---

### **Side-by-side**

| Question                 | Azure RBAC                       | Azure Policy                       |
| ------------------------ | -------------------------------- | ---------------------------------- |
| Main purpose             | Authorization                    | Governance/compliance              |
| Answers                  | Who can do what?                 | What is allowed/required?          |
| Example                  | Developer can create VM          | VM must be in approved region      |
| Common objects           | Role definition, role assignment | Definition, initiative, assignment |
| Can block deployment?    | If user lacks permission         | Yes, e.g. `Deny`                   |
| Can audit configuration? | Not its primary purpose          | Yes                                |

---

### **They complement each other**

A production governance model might be:

```text
RBAC
Developer
→ Contributor on dev subscription

Policy
Dev Subscription
→ only approved regions
→ mandatory tags
→ approved VM SKUs
```

So the developer has freedom:

```text
within guardrails
```

rather than:

```text
unrestricted Contributor access
```

> **In an interview, I would say:**
> “Azure RBAC controls authorization—who can perform which operations at a particular scope. Azure Policy governs the resulting resource configuration and compliance. For example, Contributor may give me permission to create a VM, but a Policy with the Deny effect can still block that VM if it's being created in an unapproved region. In enterprise Azure environments I use them together: RBAC provides least-privilege access and Policy provides guardrails.”

**Memory line:**
**RBAC = who can do it; Policy = whether that configuration is allowed.**

**Interview trap:**
Do not say Azure Policy replaces RBAC. They address **different layers of governance**.

**Keywords:**
Azure RBAC, Azure Policy, authorization, governance, compliance, guardrails, Deny

**Likely follow-ups:**

* Can Contributor bypass Azure Policy?
* Policy `Deny` vs RBAC permission?
* What is a Policy assignment?
* Where can RBAC and Policy be scoped?

## **T18-M02. What is a policy definition?**

**Answer:**
An Azure Policy definition is the **reusable rule that describes the condition Azure should evaluate and the effect Azure should take when that condition is met**.

Conceptually:

```text
IF
resource violates requirement

THEN
apply policy effect
```

Microsoft defines a Policy definition as describing **resource compliance conditions and the effect to take when those conditions are satisfied**. ([Microsoft Learn][3])

---

### **Simple example**

Requirement:

> Only deploy resources into Central India or West Europe.

Conceptually:

```text
IF
location NOT IN
[
  Central India,
  West Europe
]

THEN
Deny
```

That logic is the:

```text
Policy Definition
```

---

### **Basic structure**

A simplified definition might look like:

```json
{
  "if": {
    "field": "location",
    "notIn": "[parameters('allowedLocations')]"
  },
  "then": {
    "effect": "deny"
  }
}
```

Important components include:

```text
Policy rule
├── IF condition
└── THEN effect

Parameters
Mode
Metadata
Version
```

---

### **Parameters make definitions reusable**

Instead of creating:

```text
Policy 1
→ Central India

Policy 2
→ West Europe

Policy 3
→ East US
```

I can define:

```text
Parameter:
allowedLocations
```

Then different assignments provide different values.

Example:

```text
Production assignment
allowedLocations =
Central India, West Europe

Development assignment
allowedLocations =
Central India, East US
```

Same policy definition:

```text
different parameter values
```

This reduces duplication.

---

### **Built-in vs custom definitions**

Azure provides:

```text
Built-in policy definitions
```

for many common requirements.

For organization-specific controls I can create:

```text
Custom policy definitions
```

Example:

```text
Only approved internal VM SKUs
```

or:

```text
Require a specific company CostCenter tag format
```

---

### **Definition vs assignment**

This distinction is extremely important:

```text
Policy Definition
→ WHAT is the rule?

Policy Assignment
→ WHERE should the rule apply?
```

Example:

```text
Definition:
Only approved locations

Assignment:
Apply it to Production Management Group
```

Diagram:

```text
Policy Definition
"Allowed locations"
       ↓
Policy Assignment
       ↓
Production MG
       ↓
Subscriptions
       ↓
Resources
```

---

### **Where custom definitions live**

Custom policy definitions are created at a:

```text
Management Group
or
Subscription
```

and that location determines where beneath the hierarchy they can later be assigned. ([Microsoft Learn][4])

For enterprise use:

```text
Management Group definition
```

is generally more reusable across multiple child subscriptions than defining the same custom policy separately in each subscription.

---

> **In an interview, I would say:**
> “A Policy definition contains the reusable compliance rule Azure evaluates. It normally contains an `if` condition and a `then` effect, with optional parameters so the same definition can be reused with different values. For example, I can define an Allowed Locations policy with an `allowedLocations` parameter. The definition itself specifies what the rule means; a Policy assignment later determines where that rule is enforced.”

**Memory line:**
**Definition = what rule; assignment = where rule applies.**

**Interview trap:**
Creating a Policy definition alone does **not automatically enforce it anywhere**. It must be assigned.

**Keywords:**
Policy definition, condition, effect, parameter, built-in policy, custom policy

**Likely follow-ups:**

* Policy definition vs assignment?
* What does the `if` block do?
* Why use parameters?
* Built-in vs custom policies?

## **T18-M03. What is a policy initiative?**

**Answer:**
An Azure Policy initiative—also called a **policy set definition**—is a **collection of related Policy definitions grouped together so they can be managed and assigned as one unit toward a common governance objective**. ([Microsoft Learn][5])

Instead of assigning:

```text
Policy A
Policy B
Policy C
Policy D
Policy E
```

individually, I create:

```text
Initiative
├── Policy A
├── Policy B
├── Policy C
├── Policy D
└── Policy E
```

and assign the initiative once.

---

### **Example: Production security baseline**

Suppose production requires:

```text
1. Deny public IP addresses
2. Require HTTPS
3. Require diagnostic settings
4. Require encryption
5. Require Environment tag
6. Restrict locations
```

Instead of managing six unrelated assignments:

```text
Production Security Baseline Initiative
│
├── Deny public IP
├── Require HTTPS
├── Deploy diagnostics
├── Require encryption
├── Require tags
└── Restrict locations
```

Then:

```text
Initiative
    ↓
Assignment
    ↓
Production Management Group
    ↓
all production subscriptions
```

---

### **Why initiatives matter**

Without initiatives:

```text
100 subscriptions
×
20 policies
=
huge assignment-management problem
```

With:

```text
Security Baseline Initiative
```

I can treat the policies as one governance package.

Microsoft specifically says initiatives simplify assignment and management because related definitions are handled as a single item. ([Microsoft Learn][5])

---

### **Initiatives can have parameters**

Suppose multiple policies need:

```text
Allowed locations
```

The initiative can expose:

```text
initiative parameter:
allowedLocations
```

and pass that value into its included Policy definitions. ([Microsoft Learn][5])

Example:

```text
Production Baseline
allowedLocations =
Central India
West Europe
```

Those values can feed several policies in the initiative.

---

### **Policy vs initiative**

```text
Policy
→ one governance rule

Initiative
→ collection of related governance rules
```

Example:

```text
Policy:
Require encryption

Initiative:
Production Security Baseline
├── Require encryption
├── Deny public IP
├── Deploy monitoring
└── Restrict locations
```

---

### **Initiative vs assignment**

Again:

```text
Initiative
→ WHICH policies belong together?

Assignment
→ WHERE should they apply?
```

So:

```text
Initiative Definition
Production Baseline
       ↓
Assignment
       ↓
Production Management Group
```

---

### **Compliance reporting**

Initiatives also give a useful compliance view around a common goal.

Instead of only asking:

```text
Is policy X compliant?
```

I can assess:

```text
Production Security Baseline
├── Encryption       ✓
├── Logging          ✓
├── Public networking ✗
└── Tags             ✓
```

This is particularly valuable for security and regulatory-control bundles.

Microsoft also provides built-in initiatives for standards such as regulatory/compliance frameworks. ([Microsoft Learn][6])

---

> **In an interview, I would say:**
> “A Policy initiative, also called a policy set definition, groups multiple related Policy definitions into one governance package. For example, I might create a Production Security Baseline initiative containing policies for approved regions, mandatory diagnostics, encryption, tags, and public-network restrictions. I can assign that initiative once at the Production Management Group rather than maintaining many separate assignments. Initiatives can also expose shared parameters and simplify compliance reporting.”

**Memory line:**
**Policy = one rule; initiative = bundle of related rules.**

**Interview trap:**
An initiative does **not replace Policy definitions**—it references and groups them.

**Keywords:**
Policy initiative, policy set, policy definitions, governance baseline, parameters, compliance

**Likely follow-ups:**

* Initiative vs Policy definition?
* Can an initiative have parameters?
* Why use initiatives at management-group scope?
* What is a built-in regulatory-compliance initiative?
