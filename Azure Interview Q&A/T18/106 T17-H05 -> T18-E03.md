### **T17-H05. How would you provide secure administrative access to hundreds of private Azure VMs?**

**Answer:**
For hundreds of private VMs, I would avoid giving every VM a public IP or exposing SSH/RDP individually. I would centralize administrative access through **Azure Bastion**, keep the VMs private, use **Microsoft Entra ID/Azure RBAC and preferably PIM for privileged access**, restrict network paths with NSGs, and send Bastion/audit logs to centralized monitoring.

For a high-security environment, I would evaluate **Azure Bastion Premium private-only deployment**, so even the Bastion resource itself doesn't require a public IP. Microsoft currently positions Bastion Standard/Premium for scalable administrative access, with Standard supporting scalable host instances and Premium adding capabilities such as private-only deployment and session recording. ([Microsoft Learn][1])

### **Architecture**

```text
                   Administrators
                         │
                 Entra ID / RBAC
                         │
                       PIM
                         ↓
                ┌────────────────┐
                │ Azure Bastion  │
                │ Standard /     │
                │ Premium        │
                └───────┬────────┘
                        │
                  Private network
            ┌───────────┼───────────┐
            ↓           ↓           ↓
          VM001       VM002       VM300
          10.x.x.x    10.x.x.x    10.x.x.x

VM public IPs = NONE
Public SSH/RDP = NONE
```

The core security principle is:

```text
Internet
   X
VM TCP/22 or TCP/3389

Admin
  ↓
Controlled Bastion path
  ↓
Private VM IP
```

---

### **1. Keep the VMs private**

I would enforce:

```text
VM public IP = none
```

and avoid rules such as:

```text
Internet → TCP/22
Internet → TCP/3389
```

Across hundreds of VMs, even carefully restricted public management endpoints create unnecessary attack surface.

Azure Bastion is specifically designed to provide RDP/SSH access without requiring a public IP on the VM. ([Microsoft Learn][2])

---

### **2. Use Bastion as the shared administrative layer**

Rather than managing:

```text
300 VMs
×
300 public IPs
×
300 management exposure points
```

I centralize:

```text
Administrators
      ↓
Azure Bastion
      ↓
private VMs
```

For larger teams, **Bastion Standard** supports scaling its host instances and native-client workflows, while Premium is appropriate when stronger controls such as private-only Bastion and session recording are required. ([Microsoft Learn][2])

---

### **3. Separate network access from authorization**

Bastion answers:

> How can an administrator reach the private VM?

It does not by itself answer:

> Which administrator should be allowed to manage which VM?

So I combine it with:

```text
Microsoft Entra ID
       ↓
Azure RBAC
       ↓
PIM / time-bound elevation
       ↓
VM login permission
```

For example, an engineer might receive privileged access only during an approved maintenance window rather than being permanently privileged.

---

### **4. Use least privilege**

I would separate roles such as:

```text
Helpdesk
→ limited VM administration

Platform team
→ broader operational access

Security team
→ audit access

Break-glass admins
→ emergency privileged access
```

The goal is not:

```text
300 VMs
+
20 engineers
+
everyone = Owner
```

Instead, administration should be scoped according to job responsibility.

---

### **5. Use PIM for privileged access**

For production administration, I prefer:

```text
Eligible role
     ↓
administrator requests activation
     ↓
MFA / approval / justification
     ↓
temporary privilege
     ↓
expires automatically
```

rather than permanent elevated access.

This limits the damage from compromised administrator accounts.

---

### **6. Network restrictions still matter**

I would restrict VM management ports so they are reachable only from the intended Bastion/network path.

Conceptually:

```text
NSG

SSH/RDP
Source:
approved Bastion/private administration path

Internet:
DENY
```

Bastion does not mean I stop designing subnet security.

---

### **7. For the strictest environment, use private-only Bastion**

Bastion Premium supports a private-only deployment model.

```text
Corporate admin
      ↓
VPN / ExpressRoute
      ↓
Private Bastion
      ↓
Private VM
```

Now:

```text
VM public IP       = none
Bastion public IP  = none
```

This is attractive in regulated or very tightly isolated networks. ([Microsoft Learn][2])

---

### **8. Centralize auditing**

For hundreds of servers, I don't want administrative activity scattered across individual machines without centralized visibility.

I would collect relevant:

```text
Azure Activity Logs
Bastion/session telemetry
VM authentication logs
Defender/security events
```

into the organization's central monitoring/SIEM platform.

Bastion Premium also supports session recording for stronger audit requirements. ([Microsoft Learn][1])

---

### **What about Just-in-Time VM access?**

JIT is useful when VMs **still have externally reachable management paths** and you want management ports opened only temporarily.

```text
Normally
22/3389 = closed

Admin requests JIT
      ↓
temporary allow rule
      ↓
access
      ↓
rule expires
```

Microsoft positions JIT as a way to reduce exposure for VMs that retain public IP connectivity, whereas Bastion eliminates the need for a public VM management endpoint altogether. ([Microsoft Learn][2])

For my preferred private-VM design:

```text
No public IP
+
Bastion
```

is cleaner than depending on temporary public SSH/RDP openings.

---

### **Bastion vs P2S VPN**

If administrators only need:

```text
SSH/RDP → VMs
```

Bastion fits well.

If engineers need broad access to:

```text
VMs
Databases
internal APIs
Private Endpoints
AKS private endpoints
```

then P2S VPN may be part of the design because it provides broader network-level access. ([Microsoft Learn][2])

---

### **Strong interview answer**

> “For hundreds of private VMs, I wouldn't expose SSH or RDP publicly. I would centralize administrative access through Azure Bastion, keep the VMs without public IP addresses, and use Microsoft Entra ID, Azure RBAC and preferably PIM so privileged access is least-privilege and time-bound. For a high-security environment I would consider Bastion Premium private-only deployment and session recording. I would restrict management traffic with NSGs and centralize audit logs. If administrators need general private-network access rather than just SSH/RDP, I would complement or replace that workflow with P2S VPN.”

**Memory line:**
**At scale: private VMs + centralized Bastion + Entra/RBAC/PIM + audit—not hundreds of public SSH endpoints.**

**Interview trap:**
Bastion solves the **secure access path**; it does not replace identity, authorization, NSGs, or auditing.

**Keywords:**
Azure Bastion, private VM, Entra ID, Azure RBAC, PIM, private-only Bastion, session recording

**Likely follow-ups:**

* Bastion vs P2S VPN?
* How would you give temporary admin privileges?
* What does Bastion Premium add?
* Would you still use JIT with Bastion?

# **18. 🟠 IMP — Azure Governance**

### **T18-E01. What are Azure management groups?**

**Answer:**
Azure management groups are **governance containers above subscriptions** in the Azure resource hierarchy. They let organizations group multiple subscriptions together and apply **Azure Policy and Azure RBAC centrally**, with those governance settings inherited by child management groups, subscriptions, resource groups, and resources. ([Microsoft Learn][3])

### **Hierarchy**

```text
Microsoft Entra Tenant
        ↓
Tenant Root Management Group
        ↓
Management Groups
        ↓
Subscriptions
        ↓
Resource Groups
        ↓
Resources
```

Example:

```text
Tenant Root
│
├── Platform
│   ├── Connectivity Subscription
│   └── Identity Subscription
│
├── Production
│   ├── Prod Subscription A
│   └── Prod Subscription B
│
└── Non-Production
    ├── Dev
    └── Test
```

---

### **Why do we need them?**

Imagine an enterprise has:

```text
100 Azure subscriptions
```

and wants every production subscription to enforce:

```text
Allowed regions
No public IPs
Required tags
Security baselines
Specific RBAC assignments
```

Instead of assigning those controls separately 100 times:

```text
Production Management Group
            ↓
Azure Policy / RBAC
            ↓
all child subscriptions
```

Management groups therefore provide a scalable governance boundary. Microsoft describes them specifically as a scope above subscriptions for efficiently managing policy, access, and compliance. ([Microsoft Learn][3])

---

### **Inheritance**

Suppose I assign:

```text
Policy:
Allowed locations =
Central India
West Europe
```

at:

```text
Production Management Group
```

It applies down the hierarchy:

```text
Production MG
      ↓
Subscriptions
      ↓
Resource Groups
      ↓
Resources
```

unless the governance configuration has an applicable exclusion/exemption or other supported exception.

---

### **Root management group**

Every Microsoft Entra directory has one top-level:

```text
Tenant Root Group
```

All management groups and subscriptions eventually exist beneath it.

An assignment at the root can therefore affect the **entire tenant hierarchy**, which is why Microsoft recommends putting only true organization-wide controls there. ([Microsoft Learn][3])

---

### **Management groups vs resource groups**

Do not confuse them:

```text
Management Group
→ organizes/governs subscriptions

Resource Group
→ contains Azure resources
  inside a subscription
```

A VM doesn't live directly inside a management group.

The hierarchy is:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
VM
```

---

### **Strong interview answer**

> “Management groups are governance scopes above Azure subscriptions. I use them when an organization has multiple subscriptions and wants to apply policies and RBAC consistently. For example, I can create Production and Non-Production management groups and apply stricter Azure Policy controls to Production. Those assignments are inherited by the child subscriptions and resources. Every tenant also has a Tenant Root Management Group above the rest of the hierarchy.”

**Memory line:**
**Management Group = governance container for subscriptions.**

**Interview trap:**
A management group does **not contain VMs directly**; it contains management groups and subscriptions in the governance hierarchy.

**Keywords:**
Management Group, subscription hierarchy, inheritance, Tenant Root Group, Azure Policy, RBAC

**Likely follow-ups:**

* What is the Tenant Root Management Group?
* Can policies be assigned at management-group scope?
* Management group vs resource group?
* Why not apply every policy at tenant root?

### **T18-E02. What is Azure Policy?**

**Answer:**
Azure Policy is Azure's **governance and compliance service for defining rules about how Azure resources should be configured or what resources may be created**. It can evaluate resources for compliance and, depending on the policy effect, **audit, deny, modify, or deploy required configuration**.

Microsoft describes Azure Policy as a service for enforcing organizational standards and assessing compliance at scale. ([Microsoft Learn][4])

### **Simple model**

```text
Policy Definition
       ↓
What rule should resources follow?

Policy Assignment
       ↓
Where should the rule apply?

Azure resources
       ↓
Evaluate
       ↓
Compliant / Non-compliant
```

---

### **Example**

Requirement:

> Production resources may only be deployed to approved Azure regions.

Policy:

```text
IF
resource location
NOT IN
[Central India, West Europe]

THEN
Deny
```

Then:

```text
Developer
    ↓
tries East US deployment
    ↓
Azure Policy evaluation
    ↓
DENIED
```

Azure Policy evaluates resource properties and applies the configured effect when the policy condition matches. ([Microsoft Learn][5])

---

### **Common things Azure Policy can enforce**

Typical examples include:

```text
Allowed Azure regions
Required resource tags
Approved VM SKUs
No public IPs
Diagnostic settings
Encryption requirements
Security baselines
Allowed resource types
```

---

### **Policy effects**

You'll cover these individually later, but the important mental model is:

```text
Audit
→ report violation

Deny
→ block operation

Modify
→ alter/add supported properties

DeployIfNotExists
→ deploy required configuration
```

Azure Policy can therefore do more than merely report compliance. ([Microsoft Learn][6])

---

### **Policy vs RBAC**

This distinction is extremely important:

```text
Azure RBAC
→ WHO can perform an action?

Azure Policy
→ WHAT configurations/actions are allowed?
```

Example:

```text
User has Contributor
       ↓
RBAC says:
"You may create a VM."

Azure Policy says:
"Not in East US."
       ↓
East US deployment denied
```

So RBAC permission doesn't bypass Policy.

---

### **Scope and inheritance**

Policy can be assigned at scopes such as:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Resource
```

Assignments apply to the selected scope and its child resources, subject to supported exclusions and exemptions. ([Microsoft Learn][7])

---

### **Existing resources**

Azure Policy is also a **compliance engine**.

If I introduce:

```text
Audit resources without required tag
```

Azure evaluates applicable existing resources and reports them as:

```text
Compliant
or
Non-compliant
```

Some `modify` and `DeployIfNotExists` policies can also use **remediation tasks** to bring existing resources into compliance. ([Microsoft Learn][8])

---

### **Strong interview answer**

> “Azure Policy is the governance service I use to enforce and assess resource configuration standards. A policy definition contains a condition and an effect, and I assign it at a management group, subscription, resource group, or resource scope. For example, I can deny deployments outside approved regions, audit missing tags, or automatically deploy required diagnostic settings. I distinguish it from RBAC: RBAC controls who is authorized to perform an action, while Policy controls whether the resulting resource configuration is allowed.”

**Memory line:**
**RBAC = who can do it; Policy = what they're allowed to deploy/configure.**

**Interview trap:**
Azure Policy is **not just a reporting tool**. Effects such as `Deny`, `Modify`, and `DeployIfNotExists` can actively enforce configuration. ([Microsoft Learn][6])

**Keywords:**
Azure Policy, compliance, policy definition, assignment, effect, Deny, Audit, remediation

**Likely follow-ups:**

* Azure Policy vs RBAC?
* What is a policy definition?
* What is a policy initiative?
* What are common Policy effects?

### **T18-E03. What is an Azure resource lock?**

**Answer:**
An Azure resource lock protects important Azure resources from **accidental deletion or modification**, even when the user otherwise has sufficient Azure RBAC permissions. Azure currently supports two lock types:

```text
CanNotDelete
→ resource may be modified
→ resource cannot be deleted

ReadOnly
→ resource cannot be modified
→ resource cannot be deleted
```

In the Azure portal these appear as **Delete** and **Read-only** locks. ([Microsoft Learn][9])

---

### **Example**

Suppose:

```text
Production SQL Database
```

has:

```text
CanNotDelete lock
```

An administrator with broad RBAC permissions tries:

```text
Delete SQL Database
```

Azure returns:

```text
Blocked by resource lock
```

The lock takes precedence over the user's normal resource-management permissions. ([Microsoft Learn][9])

---

### **CanNotDelete**

Think:

```text
Read      ✓
Modify    ✓
Delete    ✗
```

This is useful for resources where configuration changes are still expected but deletion would be catastrophic.

Example:

```text
Production Key Vault
Production Database
Critical VNet
```

---

### **ReadOnly**

Think:

```text
Read      ✓
Modify    ✗
Delete    ✗
```

This is much stronger.

It can also cause unexpected operational issues because some services perform control-plane write operations during normal administration.

So I would use `ReadOnly` carefully rather than applying it indiscriminately.

---

### **Lock scope and inheritance**

Locks can be placed at:

```text
Subscription
Resource Group
Resource
```

A lock applied to a parent scope is inherited by resources underneath it. ([Microsoft Learn][9])

For example:

```text
Resource Group
Delete Lock
     ↓
├── VM
├── Storage Account
└── SQL Database
```

All inherit the restriction.

And if locks exist at several levels:

```text
the most restrictive applicable lock wins
```

Microsoft explicitly documents this inheritance behavior. ([Microsoft Learn][9])

---

### **Interesting deletion behavior**

Suppose:

```text
Resource Group
├── VM
└── Storage Account
    └── Delete Lock
```

Someone attempts:

```text
Delete entire Resource Group
```

Azure will block the resource-group deletion because one of its contained resources is locked; it doesn't partially delete the group around that locked resource. ([Microsoft Learn][9])

---

### **Resource lock vs RBAC**

Again, distinguish:

```text
RBAC
→ gives permissions

Resource Lock
→ places a management restriction
  even on otherwise authorized users
```

Example:

```text
User = Owner
        ↓
has delete permission through RBAC
        ↓
CanNotDelete lock exists
        ↓
delete blocked
```

The administrator would first need the appropriate permission to remove the lock itself.

---

### **Resource locks protect the control plane**

A very important nuance:

Resource locks apply to **Azure Resource Manager/control-plane operations**, not necessarily the service's internal **data plane**. ([Microsoft Learn][9])

For example, a lock on a Storage Account can prevent deletion of the **Storage Account resource**, but that doesn't universally mean individual blobs are protected from data-plane deletion.

So:

```text
Resource Lock
≠
Backup
≠
data-retention policy
```

For actual data protection, I also use service-specific capabilities such as backup, soft delete, versioning, retention, or immutability where required.

---

### **Strong interview answer**

> “Azure resource locks protect critical resources against accidental control-plane changes. `CanNotDelete` allows reading and modification but blocks deletion, while `ReadOnly` blocks both modification and deletion. Locks can be applied at subscription, resource-group, or resource scope and are inherited downward, with the most restrictive applicable lock taking precedence. They override normal RBAC permissions for the protected operation, but they aren't a substitute for backups or data-plane protection.”

**Memory line:**
**CanNotDelete = change but don't delete; ReadOnly = look but don't change.**

**Interview trap:**
A resource lock is **not a backup mechanism** and does not universally protect the resource's underlying data-plane objects.

**Keywords:**
Resource lock, `CanNotDelete`, `ReadOnly`, inheritance, control plane, accidental deletion

**Likely follow-ups:**

* Can an Owner delete a locked resource?
* Do locks inherit from resource groups?
* Resource lock vs RBAC?
* Does a Storage Account lock prevent deleting individual blobs?
