### **T18-M08. What does `Audit` do?**

**Answer:**
The Azure Policy **`Audit` effect allows the resource operation to continue but marks a matching resource as non-compliant and records an audit event for create/update operations**. It is useful when I want to **measure violations without breaking deployments**.

The easiest distinction is:

```text
Audit
→ Detect and report

Deny
→ Detect and block
```

Microsoft documents that `Audit` creates a warning event in the Activity Log for a non-compliant create/update request but does not stop that request. ([Microsoft Learn][1])

---

### **Example**

Suppose I want production VMs to have:

```text
Environment = Production
```

but I'm not ready to enforce it.

Policy:

```text
IF
Environment tag is missing

THEN
Audit
```

Developer deploys:

```text
VM
Environment tag = missing
```

Result:

```text
Deployment
   ↓
Azure Policy
   ↓
Violation detected
   ↓
Deployment ALLOWED
   ↓
Resource = Non-compliant
```

That is fundamentally different from:

```text
Deny
→ deployment rejected
```

---

### **What happens during a create/update?**

For a Resource Manager policy:

```text
Create/update request
        ↓
Policy evaluates
        ↓
Audit condition matches
        ↓
Microsoft.Authorization/policies/audit/action
recorded in Activity Log
        ↓
Request continues to
Resource Provider
```

The resource is then shown as:

```text
Non-compliant
```

in Azure Policy compliance results. ([Microsoft Learn][1])

---

### **What about existing resources?**

Azure Policy also runs periodic compliance evaluations.

For an existing resource:

```text
Existing resource
      ↓
Policy scan
      ↓
Audit condition matches
      ↓
Non-compliant
```

Azure does **not modify or delete the resource**.

During these standard evaluation cycles, Microsoft notes that the compliance state is updated rather than generating the same create/update audit operation. ([Microsoft Learn][1])

---

### **Why use Audit before Deny?**

This is how I would introduce an enterprise policy safely:

```text
New policy
    ↓
Audit
    ↓
Observe violations
    ↓
Find false positives
    ↓
Fix existing resources
    ↓
Create approved exemptions
    ↓
Switch to Deny
```

Microsoft recommends validating new policies using audit-style behavior before allowing them to block or modify workloads. ([Microsoft Learn][2])

---

### **Production example**

Requirement:

> Production resources shouldn't have public IPs.

Instead of immediately:

```text
Deny public IP
```

I could initially deploy:

```text
Audit public IP
```

and discover:

```text
Production
├── VM01 → compliant
├── VM02 → public IP → NON-COMPLIANT
├── VM03 → compliant
└── LegacyJumpBox → public IP → NON-COMPLIANT
```

Then determine:

```text
VM02
→ remediate

LegacyJumpBox
→ temporary approved exemption
```

before changing the policy to `Deny`.

> **In an interview, I would say:**
> “The Audit effect detects resources that violate a Policy rule without blocking their creation or update. Azure marks those resources as non-compliant, and for new or updated resources it also records an audit action in the Activity Log. I commonly use Audit when introducing new enterprise controls so I can understand the blast radius and false positives before changing the policy to Deny.”

**Memory line:**
**Audit tells me what's wrong without stopping the deployment.**

**Interview trap:**
`Audit` does **not remediate the resource** and does **not block deployment**.

**Keywords:**
Audit, non-compliant, Activity Log, compliance, policy evaluation, safe rollout

**Likely follow-ups:**

* Audit vs Deny?
* Does Audit modify resources?
* How would you move safely from Audit to Deny?
* What happens to existing resources?

### **T18-M09. What is `DeployIfNotExists`?**

**Answer:**
`DeployIfNotExists` is an Azure Policy effect that checks whether a **required related resource or configuration exists**, and if it doesn't, Azure Policy can deploy that missing configuration using an ARM template.

A classic use case is:

```text
Resource exists
     ↓
Required diagnostic setting exists?
     ↓
No
     ↓
DeployIfNotExists
     ↓
Create diagnostic setting
```

Microsoft documents that `DeployIfNotExists` executes a template deployment when the required related resource or `existenceCondition` isn't satisfied. ([Microsoft Learn][3])

---

### **Why is it different from normal `Deny`?**

`Deny` says:

```text
Wrong configuration
       ↓
BLOCK
```

`DeployIfNotExists` says:

```text
Required related configuration missing
       ↓
DEPLOY IT
```

So:

```text
Deny
→ preventative

DeployIfNotExists
→ corrective/deployment-oriented
```

---

### **Classic example: diagnostic settings**

Requirement:

> Every production Key Vault must send logs to a central Log Analytics workspace.

Policy logic:

```text
Key Vault created
       ↓
Diagnostic setting exists?
   /             \
 Yes              No
 ↓                 ↓
Compliant      DeployIfNotExists
                    ↓
             Create diagnostic
             setting pointing to
             central workspace
```

This is one of the strongest real-world uses of Azure Policy.

---

### **How evaluation works**

Conceptually:

```text
IF
resource matches target condition

THEN
look for related configuration

IF related resource/configuration
does not exist or fails existenceCondition

THEN
deploy ARM template
```

Microsoft's current documentation states that the effect runs after the Resource Provider successfully handles the create/update request and then evaluates the related resource before triggering deployment. ([Microsoft Learn][3])

---

### **It requires a Managed Identity**

This is extremely important.

Azure Policy itself needs permission to deploy the missing resource/configuration.

Architecture:

```text
Policy Assignment
      ↓
Managed Identity
      ↓
Azure RBAC role
      ↓
Deploy required configuration
```

For example:

```text
Policy assignment identity
      ↓
permission to create
diagnosticSettings
      ↓
target resource
```

Microsoft explicitly requires a Managed Identity on assignments using `DeployIfNotExists` for remediation/deployment operations. ([Microsoft Learn][3])

---

### **What about existing resources?**

Suppose:

```text
100 VMs already exist
```

and only 40 have the required configuration.

When the policy evaluates:

```text
40 → compliant
60 → non-compliant
```

Azure does not necessarily deploy the missing configuration to all 60 just because they were discovered in a compliance scan.

For existing non-compliant resources:

```text
DeployIfNotExists Policy
        ↓
Remediation Task
        ↓
deploy missing configuration
```

Microsoft explicitly documents remediation tasks for existing resources under `DeployIfNotExists`. ([Microsoft Learn][3])

---

### **DeployIfNotExists vs AuditIfNotExists**

Very useful distinction:

```text
AuditIfNotExists
→ required related resource missing
→ mark non-compliant

DeployIfNotExists
→ required related resource missing
→ can deploy it
```

Example:

```text
No diagnostic setting

AuditIfNotExists
→ report only

DeployIfNotExists
→ deploy diagnostic setting
```

---

### **Important ARM-template detail**

The effect contains deployment information such as:

```text
resource type
existence condition
deployment scope
ARM template
required roles
```

The template defines **what Azure should create** when the required configuration is absent. ([Microsoft Learn][3])

---

### **Production example**

I might create an initiative containing:

```text
Production Monitoring Baseline
│
├── Deploy diagnostic settings for Key Vault
├── Deploy diagnostic settings for Storage
├── Deploy diagnostic settings for NSGs
└── Deploy required monitoring configuration
```

Then assign it at:

```text
Production Management Group
```

with:

```text
Policy Managed Identity
+
least-privilege RBAC
```

That turns monitoring configuration into a governance baseline instead of relying on every application team to remember it.

> **In an interview, I would say:**
> “`DeployIfNotExists` checks whether a required related configuration exists for a resource and deploys it using an ARM template if it's missing. A common example is automatically deploying diagnostic settings so every production resource sends logs to a central workspace. The Policy assignment needs a Managed Identity with the necessary RBAC permissions. For existing non-compliant resources, I use a remediation task to trigger those deployments.”

**Memory line:**
**DeployIfNotExists = required configuration missing → deploy it automatically.**

**Interview trap:**
Do not confuse it with `Modify`. `DeployIfNotExists` typically deploys **related resources/configuration through a template**, while `Modify` changes supported properties or tags on the evaluated resource/request.

**Keywords:**
DeployIfNotExists, ARM template, existenceCondition, Managed Identity, diagnostic settings, remediation

**Likely follow-ups:**

* DeployIfNotExists vs Modify?
* Why does it require Managed Identity?
* What happens to existing resources?
* DeployIfNotExists vs AuditIfNotExists?

### **T18-M10. What is a remediation task?**

**Answer:**
An Azure Policy **remediation task applies a `Modify` or `DeployIfNotExists` policy to resources that are already non-compliant**, bringing existing infrastructure toward the desired configuration.

This solves an important problem:

```text
New policy introduced today
        ↓
Existing resources already violate it
        ↓
How do I fix them?
        ↓
Remediation Task
```

Microsoft defines remediation tasks as the mechanism that runs the assigned policy's `modify` operations or `deployIfNotExists` template against existing non-compliant resources. ([Microsoft Learn][4])

---

### **Why is remediation necessary?**

Suppose:

```text
500 resources already exist
```

and today I assign:

```text
Modify
→ add CostCenter tag
```

For new/updated resources:

```text
Policy can modify them
```

But the 500 old resources don't magically receive the tag immediately.

Compliance scan:

```text
500 resources
   ↓
150 compliant
350 non-compliant
```

Then:

```text
Remediation Task
      ↓
Modify existing 350
      ↓
add CostCenter tag
```

---

### **Which effects use remediation tasks?**

Primarily:

```text
Modify
DeployIfNotExists
```

Microsoft specifically documents remediation for resources that are non-compliant with assignments using these two effects. ([Microsoft Learn][4])

It is not:

```text
Audit
→ remediation task automatically fixes resource
```

`Audit` only evaluates/reports.

---

### **Example 1 — Modify**

Policy:

```text
All resources require:
CostCenter = CC-1001
```

Existing:

```text
VM01 → missing
VM02 → missing
Storage01 → missing
```

Remediation:

```text
Policy Modify operations
       ↓
VM01
VM02
Storage01
       ↓
tag added
```

---

### **Example 2 — DeployIfNotExists**

Policy:

```text
Every Key Vault
must have diagnostic settings
```

Existing estate:

```text
KeyVault01 → diagnostics ✓
KeyVault02 → diagnostics ✗
KeyVault03 → diagnostics ✗
```

Remediation task:

```text
KeyVault02
KeyVault03
     ↓
Deploy ARM template
     ↓
Diagnostic settings created
```

---

### **Managed Identity and RBAC**

A remediation task doesn't execute with some magical unlimited Azure privilege.

It uses:

```text
Managed Identity
associated with
Policy Assignment
```

That identity needs:

```text
minimum required Azure RBAC permissions
```

Example:

```text
Policy Managed Identity
       ↓
Tag Contributor / required role
       ↓
modify resource tags
```

or the specific role needed for diagnostic settings.

Microsoft states that Policy remediation uses the assignment's Managed Identity for Azure authorization and that this identity should have the minimum required RBAC roles. ([Microsoft Learn][4])

---

### **Evaluation identity vs remediation identity**

Nice advanced distinction:

```text
Policy evaluation
→ doesn't require the assignment MI
  just to determine compliance

Remediation/deployment
→ uses the assignment Managed Identity
```

Microsoft explicitly distinguishes the two. ([Microsoft Learn][4])

---

### **Safe remediation workflow**

I would not blindly remediate thousands of production resources.

Instead:

```text
Policy assigned
     ↓
Review compliance
     ↓
Understand non-compliant resources
     ↓
Test small scope
     ↓
Create remediation task
     ↓
Monitor failures
     ↓
Expand
```

For large estates, remediation tasks support controls around resource counts, parallel processing, filtering, and failure behavior. ([Microsoft Learn][5])

---

### **Policy does not mean instant correction**

This is important:

```text
Policy assigned
≠
every historical resource
instantly fixed
```

For existing non-compliant resources:

```text
Modify / DeployIfNotExists
        +
Remediation Task
```

provides the correction mechanism.

---

> **In an interview, I would say:**
> “A remediation task is how Azure Policy applies `Modify` or `DeployIfNotExists` behavior to existing non-compliant resources. For example, if I introduce a Policy today requiring a CostCenter tag, new resources can be modified during create/update, but hundreds of existing resources may still be missing that tag. I create a remediation task, which uses the Policy assignment's Managed Identity and RBAC permissions to perform the required modifications or deployments.”

**Memory line:**
**Policy finds old non-compliance; remediation task fixes it for Modify/DeployIfNotExists policies.**

**Interview trap:**
Assigning a Policy doesn't mean every existing resource is immediately corrected.

**Keywords:**
Remediation task, existing resources, Modify, DeployIfNotExists, Managed Identity, RBAC

**Likely follow-ups:**

* Which Policy effects support remediation?
* Which identity performs remediation?
* Can remediation fail because of RBAC?
* How would you safely remediate thousands of resources?

### **T18-H01. How would you enforce mandatory tags across an enterprise?**

**Answer:**
I would enforce enterprise tags centrally using **Azure Policy assigned at the management-group level**, not rely on developers manually adding them.

I would separate tags into two categories:

```text
1. Tags whose value must be supplied explicitly
   → Require / Deny

2. Tags that can be inherited or standardized centrally
   → Modify
```

Then I would use **remediation tasks** to bring existing resources into compliance and package the policies into a reusable **initiative**.

Microsoft provides built-in Policy definitions for requiring tags, adding/replacing tags, and inheriting tags from resource groups or subscriptions. ([Microsoft Learn][6])

---

### **Enterprise architecture**

```text
Tenant Root
    ↓
Enterprise Governance MG
    ↓
Tagging Initiative
    │
    ├── Require CostCenter
    ├── Require Application
    ├── Inherit Environment
    ├── Inherit Owner
    └── Add ManagedBy
    ↓
Production / NonProduction MGs
    ↓
Subscriptions
    ↓
Resources
```

---

### **1. Define a small mandatory tag taxonomy**

I would first standardize something like:

```text
Environment
Application
Owner
CostCenter
DataClassification
```

Not:

```text
37 mandatory tags
```

because overly complex tag taxonomies are difficult to maintain and lead to meaningless data.

Each tag should have:

```text
purpose
owner
allowed values
source of truth
```

---

### **2. Use `Deny` where the creator must supply the value**

Example:

```text
CostCenter
```

If Azure cannot determine the correct value automatically:

```text
IF
CostCenter tag missing

THEN
Deny
```

Deployment:

```text
Developer
   ↓
Create resource
without CostCenter
   ↓
Policy
   ↓
DENY
```

Microsoft provides built-in policies such as:

```text
Require a tag on resources
Require a tag and its value on resources
```

using the `Deny` effect. ([Microsoft Learn][6])

---

### **3. Use `Modify` where the value can be inherited**

Suppose Resource Group:

```text
rg-payments-prod

Environment = Production
Owner       = Payments-Team
```

Resources inside it should inherit those values.

Policy:

```text
Resource created
       ↓
Environment tag missing?
       ↓
Modify
       ↓
copy Environment
from Resource Group
```

Result:

```text
Resource Group
Environment = Production
       ↓
VM
Environment = Production
```

Microsoft provides built-in `Modify` policies for inheriting tags from both resource groups and subscriptions. ([Microsoft Learn][6])

---

### **4. Why not use Deny for everything?**

If Azure already knows the correct value:

```text
Environment
Owner
BusinessUnit
```

forcing developers to type it repeatedly introduces:

```text
typos
inconsistent capitalization
bad data
friction
```

Better:

```text
central source
    ↓
Modify
    ↓
automatic inheritance
```

Use `Deny` for information Azure genuinely cannot infer.

---

### **5. Build a tagging initiative**

Instead of:

```text
12 unrelated assignments
```

create:

```text
Enterprise Tagging Initiative
│
├── Require CostCenter
├── Require Application
├── Inherit Environment
├── Inherit Owner
└── Add ManagedBy
```

Then assign:

```text
Enterprise Management Group
```

This gives:

```text
one governance package
+
central reporting
+
consistent assignment
```

---

### **6. Assign at the right management-group scope**

For global enterprise tags:

```text
Enterprise MG
```

For environment-specific tags:

```text
Production MG
→ Environment = Production

NonProduction MG
→ Environment = NonProduction
```

Example:

```text
Tenant Root
│
├── Production
│   └── Environment=Prod Policy
│
└── NonProduction
    └── Environment=NonProd Policy
```

I avoid putting every policy at Tenant Root unless it truly applies everywhere.

---

### **7. Roll it out safely**

I would not immediately introduce broad Deny policies across hundreds of subscriptions.

Rollout:

```text
Step 1
Inventory existing tags

Step 2
Policy = Audit
      ↓
Measure violations

Step 3
Correct taxonomy / false positives

Step 4
Remediate existing resources

Step 5
Pilot on dev subscriptions

Step 6
Enable Modify / Deny

Step 7
Expand to production
```

Microsoft recommends testing Policy impact and using audit-style evaluation before broad enforcement. ([Microsoft Learn][2])

---

### **8. Remediate existing resources**

For `Modify` policies:

```text
Existing resources
missing Owner
      ↓
Non-compliant
      ↓
Remediation Task
      ↓
Owner inherited
```

Microsoft explicitly supports remediation of existing tagged resources using `Modify`. ([Microsoft Learn][7])

---

### **9. Use Managed Identity for Modify remediation**

Policy assignment:

```text
Tagging Initiative
      ↓
Managed Identity
      ↓
required Azure RBAC
      ↓
existing resources
```

Without the necessary permissions:

```text
remediation fails
```

even if the Policy definition itself is valid. ([Microsoft Learn][4])

---

### **10. Handle exceptions formally**

Some resource types do not support tags, and some resources may have legitimate exceptions. Microsoft explicitly notes that tag support isn't universal across every resource type. ([Microsoft Learn][6])

I would use:

```text
Policy exemption
+
business justification
+
owner
+
expiration where appropriate
```

rather than weakening the entire enterprise policy.

---

### **11. Use tags for FinOps**

Once consistent:

```text
CostCenter
Application
Environment
```

becomes valuable for:

```text
Azure Cost Management
chargeback
showback
budget analysis
resource ownership
automation
```

Bad tagging:

```text
Environment = prod
Environment = Prod
Environment = production
Environment = PRD
```

makes reporting unreliable.

Policy solves that by establishing standard behavior.

---

### **Complete design**

```text
Management Group
      ↓
Tagging Initiative
      │
      ├── Deny
      │   ├── CostCenter required
      │   └── Application required
      │
      └── Modify
          ├── inherit Environment
          ├── inherit Owner
          └── add ManagedBy
               ↓
        Managed Identity
               ↓
       Remediation Tasks
               ↓
 Existing + future resources
```

> **In an interview, I would say:**
> “I would enforce enterprise tagging through an Azure Policy initiative assigned at management-group scope. I first define a small controlled taxonomy such as Environment, Application, Owner, and CostCenter. For values developers must explicitly provide, such as CostCenter, I can use a Require Tag policy with the Deny effect. For deterministic values such as Environment or Owner, I prefer Modify policies that inherit them from the resource group or subscription. I would start in Audit mode, identify false positives and unsupported resource types, remediate existing resources using remediation tasks and the Policy assignment Managed Identity, and then progressively enable enforcement. This gives consistent tags for governance and FinOps without relying on manual discipline.”

**Memory line:**
**Enterprise tags = management-group Policy initiative + Deny for required input + Modify for inherited values + remediation for existing resources.**

**Interview trap:**
Do not say:

> “Tags automatically inherit from the Resource Group.”

They **do not**; Azure Policy can implement that inheritance. ([Microsoft Learn][6])

**Keywords:**
Azure Policy, mandatory tags, Modify, Deny, management groups, initiative, remediation, FinOps

**Likely follow-ups:**

* Why use Modify instead of Deny for Environment?
* How do you fix existing untagged resources?
* Do tags automatically inherit?
* How would you handle resource types that don't support tags?
