### **T18-M04. What is a policy assignment?**

**Answer:**
A **policy assignment** is what makes an Azure Policy definition or initiative apply to a specific scope. The definition says **what the rule is**; the assignment says **where that rule applies**, with which parameter values, exclusions, and enforcement settings.

```text
Policy Definition
"What should the rule be?"
        ↓
Policy Assignment
"Where should it apply?"
        ↓
Management Group / Subscription /
Resource Group / Resource
```

Azure Policy assignments can target a scope and all applicable resources beneath that scope. ([Microsoft Learn][1])

---

### **Example**

Policy definition:

```text
Allowed locations
```

Assignment:

```text
Scope:
Production Management Group

Parameter:
Allowed locations =
- Central India
- West Europe
```

Result:

```text
Production MG
    ↓
Subscription A
Subscription B
Subscription C
    ↓
Resources
```

All applicable child resources are evaluated against that assignment.

---

### **What can an assignment contain?**

A policy assignment can specify things such as:

```text
Policy / Initiative being assigned
Scope
Parameter values
Excluded scopes — notScopes
Enforcement mode
Non-compliance messages
Managed Identity when required
Resource selectors
```

The assignment's `scope` controls inclusion, while `notScopes` can exclude particular child scopes from evaluation. ([Microsoft Learn][2])

---

### **Definition vs assignment**

This is the most important distinction:

```text
Definition
→ reusable policy logic

Assignment
→ activates that logic
  at a particular scope
```

For example:

```text
Definition:
Require Environment tag

Assignment A:
Production MG
Environment = Production

Assignment B:
Development MG
Environment = Development
```

Same definition, different assignments and parameters.

---

### **Enforcement mode**

A useful production feature is:

```text
enforcementMode = Default
→ enforce policy effects

enforcementMode = DoNotEnforce
→ evaluate compliance
  without enforcing certain effects
```

This is useful for safely testing a new policy before turning enforcement on. Microsoft describes `DoNotEnforce` as a what-if style rollout mechanism. ([Microsoft Learn][3])

Example:

```text
New Deny policy
     ↓
DoNotEnforce
     ↓
Observe impact
     ↓
Fix workloads / exceptions
     ↓
Default
     ↓
Enforce
```

---

### **Assignment scope example**

```text
Tenant
 ↓
Production MG       ← Policy assigned here
 ├── Sub A
 │    ├── RG1
 │    └── RG2
 └── Sub B
      └── RG3
```

Unless excluded or exempted, applicable resources underneath that management group are evaluated.

> **In an interview, I would say:**
> “A policy assignment applies a Policy definition or initiative to a particular Azure scope. The definition specifies the compliance rule, while the assignment determines where it applies and can also supply parameters, exclusions, enforcement mode, and non-compliance messages. For example, I can assign an Allowed Locations policy at the Production Management Group and pass Central India and West Europe as the allowed-region parameters.”

**Memory line:**
**Definition = what rule; assignment = where and how that rule applies.**

**Interview trap:**
Creating a Policy definition does **not enforce anything until it is assigned**.

**Keywords:**
Policy assignment, scope, parameters, `notScopes`, enforcement mode, initiative

**Likely follow-ups:**

* Definition vs assignment?
* What does `notScopes` do?
* What is `DoNotEnforce`?
* Can the same definition have multiple assignments?

### **T18-M05. What is a policy exemption?**

**Answer:**
An Azure Policy exemption is an explicit, tracked exception that says a particular resource or resource hierarchy **does not need to be evaluated against a specific Policy assignment**, usually because there is a formally approved waiver or another control already mitigates the risk.

The resource remains visible in Policy compliance reporting as:

```text
Exempt
```

rather than simply disappearing from governance visibility. ([Microsoft Learn][4])

---

### **Example**

Organization policy:

```text
Storage accounts
must disable
public network access
```

But one legacy integration temporarily requires:

```text
Public Storage access
```

Instead of deleting the policy:

```text
Production Policy
      ↓
StorageAcc1
      ↓
Policy Exemption
      ↓
Category: Waiver
Expires: 2026-12-31
Ticket: SEC-4821
```

The exception is documented and auditable.

---

### **Two exemption categories**

Azure Policy supports:

```text
Waiver
→ requirement temporarily/permanently
  doesn't apply to this resource

Mitigated
→ requirement isn't directly satisfied,
  but another control addresses the risk
```

Microsoft currently defines `Waiver` and `Mitigated` as the exemption categories. ([Microsoft Learn][4])

---

### **Example: Waiver**

Policy:

```text
Public endpoints prohibited
```

Legacy vendor application cannot use Private Link yet.

Approved exception:

```text
Waiver
Expires in 90 days
Owner = Payments team
Ticket = SEC-212
```

This is better than permanently weakening the policy for the entire subscription.

---

### **Example: Mitigated**

Policy expects:

```text
Control A
```

but the organization implements:

```text
Control B
```

that provides equivalent risk mitigation.

Then:

```text
Exemption category
→ Mitigated
```

can document that reasoning.

---

### **Exemptions can expire**

A powerful governance feature is:

```text
expiresOn
```

Example:

```text
Legacy exception
Expires:
2026-10-31
```

That prevents:

```text
temporary exception
→ forgotten forever
```

Microsoft recommends exemptions particularly for specific or time-bound exceptions and supports expiration metadata. ([Microsoft Learn][4])

---

### **Exemption vs `notScopes`**

This is an excellent interview distinction.

#### `notScopes`

```text
Policy Assignment
       ↓
exclude this scope completely
```

Resources aren't evaluated or counted in that assignment's compliance results. ([Microsoft Learn][2])

#### Exemption

```text
Policy Assignment
       ↓
resource is applicable
       ↓
formal exemption
       ↓
Compliance state = Exempt
```

So exemption provides much better governance context:

```text
Who approved it?
Why?
Until when?
Which assignment?
```

---

### **Exempt only part of an initiative**

Suppose:

```text
Security Initiative
├── Require encryption
├── Deny public IP
└── Require diagnostic settings
```

One resource may need an exemption only from:

```text
Deny public IP
```

not from the entire initiative.

Azure Policy supports targeting specific Policy definitions inside an assigned initiative using policy definition reference IDs. ([Microsoft Learn][4])

---

### **Production governance pattern**

I would require exemptions to include:

```text
Business justification
Owner
Approver
Ticket/reference
Expiration date
Compensating control
```

and review them periodically.

> **In an interview, I would say:**
> “A Policy exemption is a formal exception to an Azure Policy assignment. I use it when a specific resource legitimately can't meet a policy requirement or the risk is mitigated another way. Azure supports Waiver and Mitigated categories, and exemptions can include expiration dates and metadata such as approval tickets. Unlike `notScopes`, which simply removes a scope from evaluation, an exemption remains visible in compliance reporting as Exempt, which gives much better governance and auditability.”

**Memory line:**
**Exemption = documented exception that stays visible in compliance reporting.**

**Interview trap:**
Do not confuse an **exemption** with `notScopes`; exclusions remove resources from evaluation, while exemptions explicitly record why a resource is excepted.

**Keywords:**
Policy exemption, Waiver, Mitigated, expiration, `notScopes`, compliance

**Likely follow-ups:**

* Waiver vs Mitigated?
* Exemption vs `notScopes`?
* Can exemptions expire?
* Can you exempt only one policy within an initiative?

### **T18-M06. What are common Azure Policy effects?**

**Answer:**
A Policy **effect** tells Azure what to do when the Policy condition matches a resource. Common effects include:

```text
Audit
Deny
Modify
Append
AuditIfNotExists
DeployIfNotExists
Disabled
```

Azure also currently supports effects such as:

```text
Manual
DenyAction
```

for more specialized governance scenarios. ([Microsoft Learn][5])

---

### **Quick mental model**

```text
Audit
→ detect

Deny
→ block

Modify
→ change

Append
→ add

AuditIfNotExists
→ verify related config exists

DeployIfNotExists
→ create missing config

Disabled
→ don't evaluate

Manual
→ compliance determined through attestation

DenyAction
→ block specific action
  currently DELETE
```

---

### **1. Audit**

```text
Violation found
    ↓
Deployment allowed
    ↓
Resource marked non-compliant
```

Use when you want visibility before enforcement.

Example:

```text
Audit VMs
without managed disks
```

---

### **2. Deny**

```text
Violation detected
      ↓
Request blocked
```

Example:

```text
Only approved locations
```

User tries:

```text
East US
```

Result:

```text
403 Forbidden
```

We'll cover `Deny` immediately in **T18-M07**. ([Microsoft Learn][6])

---

### **3. Modify**

Used to:

```text
add
update
remove
```

supported resource properties or tags.

Classic example:

```text
Missing CostCenter tag
       ↓
Modify
       ↓
Add/replace CostCenter
```

Existing non-compliant resources can also be corrected with remediation tasks when the policy supports it. ([Microsoft Learn][7])

---

### **4. Append**

Adds supported fields or values to the request during creation/update.

Conceptually:

```text
Incoming resource request
        ↓
Policy Append
        ↓
additional property/value
        ↓
Resource Provider
```

`Modify` is generally more flexible for many modern tag/property scenarios.

---

### **5. AuditIfNotExists**

Checks whether a required **related resource/configuration exists**.

Example:

```text
VM exists
   ↓
Does required related
monitoring configuration exist?
   ↓
No
   ↓
Mark non-compliant
```

It detects but doesn't deploy the missing configuration. ([Microsoft Learn][8])

---

### **6. DeployIfNotExists**

Similar check:

```text
Required related configuration exists?
             ↓
            No
             ↓
Deploy missing configuration
```

Typical use:

```text
Automatically deploy
diagnostic settings
```

`DeployIfNotExists` assignments require an appropriate Managed Identity for deployment/remediation. ([Microsoft Learn][9])

---

### **7. Disabled**

```text
Policy effect = Disabled
      ↓
Policy rule isn't evaluated
```

Useful when a definition supports configurable effects and you want to turn one off.

Don't confuse this with assignment:

```text
enforcementMode = DoNotEnforce
```

because `DoNotEnforce` can still evaluate compliance while suppressing enforcement behavior. ([Microsoft Learn][10])

---

### **8. Manual**

Used for controls that require:

```text
human attestation
```

rather than automatic Azure-resource evaluation.

This is particularly useful in regulatory initiatives where a control cannot be proven automatically from Azure resource state. ([Microsoft Learn][11])

---

### **9. DenyAction**

`DenyAction` blocks an intended management action.

Current Azure support is:

```text
DELETE
```

so it can protect resources against deletion at scale. ([Microsoft Learn][12])

This is distinct from ordinary `Deny`, which evaluates resource creation/update configuration.

---

### **Interview table**

| Effect              | Main purpose                           |
| ------------------- | -------------------------------------- |
| `Audit`             | Report violation                       |
| `Deny`              | Block non-compliant request            |
| `Modify`            | Change/add/remove supported properties |
| `Append`            | Add supported values to request        |
| `AuditIfNotExists`  | Check related config exists            |
| `DeployIfNotExists` | Deploy missing related config          |
| `Disabled`          | Turn evaluation off                    |
| `Manual`            | Human-attested compliance              |
| `DenyAction`        | Block action such as delete            |

> **In an interview, I would say:**
> “The common Azure Policy effects I remember are Audit, Deny, Modify, Append, AuditIfNotExists, DeployIfNotExists, and Disabled. Audit reports violations, Deny blocks them, Modify changes supported properties or tags, and DeployIfNotExists can deploy missing configuration such as diagnostic settings. Azure also has Manual for attested controls and DenyAction, which currently supports blocking DELETE operations.”

**Memory line:**
**Audit detects, Deny blocks, Modify changes, DeployIfNotExists fixes missing configuration.**

**Interview trap:**
`AuditIfNotExists` **doesn't deploy anything**; `DeployIfNotExists` does.

**Keywords:**
Audit, Deny, Modify, Append, AuditIfNotExists, DeployIfNotExists, Manual, DenyAction

**Likely follow-ups:**

* Audit vs Deny?
* Modify vs DeployIfNotExists?
* What requires a Managed Identity?
* `Disabled` vs `DoNotEnforce`?

### **T18-M07. What does the `Deny` effect do?**

**Answer:**
The Azure Policy **`Deny` effect blocks a create or update request when the resource matches the Policy condition and violates the required standard**.

For Azure Resource Manager-mode policies, Azure Policy evaluates the request **before it reaches the Resource Provider**, and a denied request is returned as:

```text
403 Forbidden
```

Existing matching resources aren't automatically deleted; they are reported as **non-compliant**. ([Microsoft Learn][6])

---

### **Example**

Policy:

```text
Allowed locations:
- Central India
- West Europe
```

Developer has:

```text
Contributor
```

and tries:

```text
Create VM
Location = East US
```

Flow:

```text
Developer
   ↓
Authentication ✓
   ↓
Azure RBAC ✓
Contributor may create VM
   ↓
Azure Policy
location violates rule
   ↓
Deny
   ↓
403 Forbidden
```

So again:

```text
RBAC
→ user is authorized

Policy
→ requested configuration isn't allowed
```

---

### **When does `Deny` run?**

For Resource Manager-mode policies:

```text
Create / Update request
        ↓
Azure Policy evaluates
        ↓
Violation?
    /          \
   No          Yes
   ↓            ↓
Resource      Deny
Provider      403
```

Microsoft explicitly states that `Deny` prevents a matching non-compliant request **before it is sent to the Resource Provider**. ([Microsoft Learn][6])

---

### **What happens to existing resources?**

Suppose the policy is introduced today:

```text
Deny public IPs
```

but 50 public IP resources already exist.

Azure doesn't immediately do:

```text
Delete 50 public IPs
```

Instead:

```text
Existing resources
      ↓
Policy evaluation
      ↓
Non-compliant
```

Future applicable create/update operations are then subject to the Deny policy. ([Microsoft Learn][6])

---

### **Safe rollout strategy**

I generally wouldn't introduce a broad enterprise `Deny` blindly.

Better:

```text
1. Start with Audit
        ↓
2. Measure existing violations
        ↓
3. Fix legitimate workloads
        ↓
4. Create approved exemptions
        ↓
5. Test assignment with DoNotEnforce
        ↓
6. Enable Deny
```

Microsoft explicitly recommends evaluating the impact of new policies before moving to enforcement. ([Microsoft Learn][5])

---

### **Example enterprise guardrails**

`Deny` is useful for rules such as:

```text
No public IPs in production
Only approved Azure regions
Only approved VM SKUs
Require specific security configuration
Prevent unapproved resource types
```

when the organization wants a **hard preventative control**.

---

### **Deny vs Audit**

```text
Audit
Violation
   ↓
Allow deployment
   ↓
Report non-compliance
```

versus:

```text
Deny
Violation
   ↓
Block deployment
```

This is why I often:

```text
Audit first
→ Deny later
```

for enterprise rollouts.

---

### **Deny vs DenyAction**

Current distinction:

```text
Deny
→ blocks create/update requests
  based on resource configuration

DenyAction
→ blocks an action
  currently DELETE
```

So if the requirement is:

> “Prevent someone from deleting this class of resources.”

I would evaluate:

```text
DenyAction
```

or resource locks depending on the governance requirement—not ordinary `Deny`. ([Microsoft Learn][12])

> **In an interview, I would say:**
> “The `Deny` effect is a preventative Azure Policy control. When a create or update request matches the Policy condition and violates the standard, Azure Policy blocks the request and returns a 403 before the Resource Provider processes it. Existing violating resources are normally marked non-compliant rather than automatically removed. In production I typically roll a new rule out as Audit or DoNotEnforce first, understand the impact and approved exceptions, and only then switch to Deny.”

**Memory line:**
**Deny = stop the non-compliant create/update before it reaches the Resource Provider.**

**Interview trap:**
`Deny` does **not automatically fix or delete existing non-compliant resources**.

**Keywords:**
Deny, 403 Forbidden, preventative control, Resource Provider, non-compliant, Audit-first rollout

**Likely follow-ups:**

* What happens to existing resources?
* Deny vs Audit?
* Deny vs DenyAction?
* How would you safely roll out a new Deny policy?
