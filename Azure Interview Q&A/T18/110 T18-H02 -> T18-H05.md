### **T18-H02. How would you prevent creation of public IP addresses in production?**

**Answer:**
I would enforce this centrally using **Azure Policy with a `Deny` effect at the Production management-group scope**, targeting `Microsoft.Network/publicIPAddresses` and, where necessary, adding **service-specific policies that disable public network access**. I would first run the control in `Audit`/non-enforcing mode to identify legitimate exceptions, then move production to hard enforcement.

The goal is:

```text
Developer / Terraform / CI
           ↓
Create Public IP
           ↓
Azure RBAC
"You're allowed to create networking resources"
           ↓
Azure Policy
Production prohibits Public IP
           ↓
DENY
```

So even a user with `Contributor` or `Network Contributor` cannot simply deploy around the production networking standard.

---

### **1. Enforce at the management-group level**

Example hierarchy:

```text
Tenant Root
│
├── Platform
│
├── Production
│   ├── Prod Subscription A
│   ├── Prod Subscription B
│   └── Prod Subscription C
│
└── NonProduction
```

I assign:

```text
Deny Public IP Addresses
```

to:

```text
Production Management Group
```

Then every child production subscription inherits the control.

Azure Policy definitions created at a management-group level can be assigned throughout that management group's child hierarchy. ([Microsoft Learn][1])

---

### **2. Policy rule**

Conceptually:

```json
{
  "if": {
    "field": "type",
    "equals": "Microsoft.Network/publicIPAddresses"
  },
  "then": {
    "effect": "deny"
  }
}
```

Meaning:

```text
IF
resource type =
Microsoft.Network/publicIPAddresses

THEN
Deny
```

This provides a straightforward preventative control.

Microsoft exposes `Microsoft.Network/publicIPAddresses/write` as the control-plane operation used to create or update public IP resources, so policy can govern creation independent of whether the caller otherwise has network permissions. ([Microsoft Learn][2])

---

### **3. Don't stop at the Public IP resource type**

This is important.

Preventing:

```text
Microsoft.Network/publicIPAddresses
```

is useful, but production public exposure can also come from **PaaS services that have their own public endpoints**, such as:

```text
Storage
Key Vault
App Service
SQL
Event Grid
App Configuration
etc.
```

Those may not require creating a standalone:

```text
Microsoft.Network/publicIPAddresses
```

resource.

Therefore an enterprise initiative might contain:

```text
Production Network Security Initiative
│
├── Deny standalone Public IP resources
├── App Configuration public access disabled
├── Storage public access restricted/disabled
├── SQL public access restricted/disabled
├── Key Vault network controls
└── Require Private Endpoints where applicable
```

Azure's current built-in policy catalog contains many service-specific controls whose effects include `Audit`, `Deny`, and `Disabled` for public-network access. ([Microsoft Learn][3])

---

### **4. Start with Audit**

I wouldn't suddenly apply:

```text
Deny all Public IPs
```

to hundreds of production subscriptions.

Safer rollout:

```text
Policy created
     ↓
Audit
     ↓
Discover current usage
     ↓
Classify:
legitimate / legacy / unnecessary
     ↓
Migrate workloads
     ↓
Create narrow exemptions
     ↓
Enable Deny
```

This avoids breaking things such as:

```text
legacy ingress
third-party integration
temporary migration path
```

before replacements exist.

---

### **5. Prefer private ingress/egress designs**

Preventing public IPs doesn't mean production can never communicate externally.

For inbound applications I might use:

```text
Internet
   ↓
Azure Front Door / approved edge
   ↓
private/or controlled origin
```

For PaaS:

```text
Application
   ↓
Private DNS
   ↓
Private Endpoint
   ↓
Azure SQL / Storage / Key Vault
```

For VM administration:

```text
Administrator
   ↓
Azure Bastion / P2S VPN
   ↓
Private VM
```

For outbound:

```text
Workload
   ↓
NAT Gateway / Azure Firewall
   ↓
Internet
```

The policy should enforce the architecture—not just block people without providing an approved alternative.

---

### **6. Handle exceptions formally**

Suppose a third-party appliance genuinely needs a public IP.

I would not:

```text
disable policy for Production
```

Instead:

```text
Specific resource/subscription
        ↓
Policy Exemption
        ↓
Business justification
Owner
Security approval
Expiry date
Compensating controls
```

That keeps the exception visible and auditable.

---

### **7. IaC and CI should fail early too**

Azure Policy is the final platform guardrail.

I would also fail earlier with:

```text
Terraform validation
Checkov / policy-as-code
PR checks
```

so developers learn during CI rather than only after ARM rejects the deployment.

Defense:

```text
PR
 ↓
static policy check
 ↓
Terraform plan review
 ↓
Azure Policy
 ↓
Azure platform
```

---

> **In an interview, I would say:**
> “I would assign a Deny Azure Policy at the Production management-group level targeting standalone `Microsoft.Network/publicIPAddresses`, so even users with RBAC permission to create networking resources can't create public IPs. I would also include service-specific policies because many PaaS services expose public endpoints without using a standalone public-IP resource. I would roll the policy out in Audit first, identify legitimate dependencies, migrate those services toward Private Endpoints or approved ingress patterns, create narrowly scoped and time-bound exemptions where necessary, and then enable Deny.”

**Memory line:**
**Production public exposure should be blocked centrally by Policy, not left to developer discipline.**

**Interview trap:**
Denying `Microsoft.Network/publicIPAddresses` alone does **not guarantee every PaaS resource is private**.

**Keywords:**
Azure Policy, `Deny`, management group, public IP, public network access, Private Endpoint, exemption

**Likely follow-ups:**

* Can Contributor bypass this policy?
* How would you handle a legitimate exception?
* Why isn't blocking Public IP resources enough for PaaS?
* Would you deploy this policy directly in Deny mode?

### **T18-H03. How would you restrict deployments to approved Azure regions?**

**Answer:**
I would use the Azure Policy built-in **`Allowed locations`** definition, assign it at the appropriate management-group scope, pass the organization's approved regions as parameters, and use `Deny` for production once the impact is validated.

For example:

```text
Approved:
Central India
West Europe
```

Anything else:

```text
East US
North Europe
Japan East
etc.
```

is rejected unless specifically exempted.

Microsoft's current built-in `Allowed locations` policy supports `Audit`, `Deny`, and `Disabled`, and is specifically intended to enforce geo-location requirements. ([Microsoft Learn][3])

---

### **Architecture**

```text
Production Management Group
        ↓
Allowed Locations Policy
        ↓
Allowed:
centralindia
westeurope
        ↓
Production subscriptions
        ↓
Developers / Terraform / CI
```

Request:

```text
Create VM
Location = eastus
```

Result:

```text
Azure Policy
    ↓
location not approved
    ↓
DENY
```

---

### **1. Use parameters rather than hardcoding separate policies**

The policy definition contains:

```text
allowedLocations = [
  "centralindia",
  "westeurope"
]
```

The same reusable definition can then have different assignments.

Example:

```text
Production
Allowed =
Central India
West Europe
```

while:

```text
Development
Allowed =
Central India
East US
West Europe
```

Microsoft's documented `Allowed locations` definition uses an array parameter containing the permitted Azure locations and denies resources outside that list. ([Microsoft Learn][1])

---

### **2. Assign it at the correct management-group scope**

Example:

```text
Tenant Root
│
├── Platform
│
├── Production
│   ├── Sub-A
│   └── Sub-B
│
└── Sandbox
```

I would usually put the production location rule at:

```text
Production MG
```

rather than Tenant Root if platform or sandbox subscriptions legitimately need other locations.

Microsoft recommends using management groups to group subscriptions with common security, compliance, connectivity, and feature requirements. ([Microsoft Learn][4])

---

### **3. Understand global/non-regional resources**

Not every Azure resource behaves like:

```text
VM in Central India
```

Some resources are:

```text
global
```

or have special location semantics.

The current built-in `Allowed locations` policy excludes resources that use the `global` region and some other special cases. ([Microsoft Learn][3])

So I wouldn't write an oversimplified custom rule that accidentally breaks:

```text
global Azure services
tenant-level resources
locationless child resources
```

without testing aliases and resource behavior.

---

### **4. Resource-group location is separate**

Azure has another built-in policy:

```text
Allowed locations for resource groups
```

because the Resource Group itself has a location used for its control-plane metadata.

So if the company requires both:

```text
Resources
AND
Resource Groups
```

to use approved geography, I would include both controls in the initiative.

Azure currently lists separate built-ins for `Allowed locations` and `Allowed locations for resource groups`. ([Microsoft Learn][3])

---

### **5. This is useful for data residency—but isn't the whole story**

Suppose the requirement says:

> “Customer data must remain in India.”

`Allowed locations = Central India` helps prevent accidental resource deployments elsewhere.

But that alone does **not prove total data residency**.

I would also evaluate:

```text
service data-replication behavior
geo-redundant backup settings
paired-region behavior
global services
logs/monitoring destinations
DR architecture
data export
```

Policy is one technical guardrail within a broader compliance design.

---

### **6. Safe rollout**

Start:

```text
Allowed Locations
Effect = Audit
```

Then identify:

```text
What currently exists outside approved regions?
```

Maybe:

```text
Log Analytics → East US
legacy Storage → West Europe
DR resources → North Europe
```

Then:

```text
fix
migrate
approve exception
or update architecture
```

before:

```text
Effect = Deny
```

Azure's policy guidance emphasizes assessing policy impact before enforcement; recent sovereign-governance guidance similarly recommends beginning initiatives in audit and transitioning critical controls to deny after validation. ([Microsoft Learn][5])

---

### **7. Exempt legitimate DR where required**

Suppose:

```text
Primary region = Central India
DR region      = South India
```

Then don't create an impossible policy:

```text
Only Central India
```

if the architecture requires:

```text
South India DR
```

Instead, parameterize the policy to include:

```text
centralindia
southindia
```

or use a carefully governed exception where a different regulatory reason applies.

---

### **Strong interview answer**

> “I would use the Azure Policy built-in `Allowed locations` and assign it at the appropriate management-group level. The allowed regions are supplied as parameters—for example Central India and West Europe—and in production I use the Deny effect so deployments outside those regions are rejected even if the caller has Contributor permission. I would also include `Allowed locations for resource groups` if the organization wants Resource Group metadata governed. I roll the control out in Audit first, account for global services and DR regions, then enable Deny and manage exceptions formally.”

**Memory line:**
**Allowed Locations Policy + management-group assignment = enterprise regional deployment guardrail.**

**Interview trap:**
Restricting Azure resource locations does **not automatically guarantee complete legal data residency** for every service.

**Keywords:**
Allowed locations, Azure Policy, regions, management group, `Deny`, data residency

**Likely follow-ups:**

* What about global Azure resources?
* Resource location vs Resource Group location?
* How would you handle a DR region?
* Does allowed-location Policy guarantee regulatory compliance?

### **T18-H04. How would you prevent accidental deletion of critical production resources?**

**Answer:**
I would use **`CanNotDelete` resource locks on critical production resources or resource groups**, combine them with **least-privilege Azure RBAC/PIM**, protect the actual data separately using backup/soft-delete/retention mechanisms, and use Policy where the organization needs deletion protection at broader scale.

The key idea is:

```text
RBAC
→ Can the user normally delete?

Resource Lock
→ Should Azure still prevent deletion?
```

Microsoft documents that a `CanNotDelete` lock allows read and modification but prevents deletion, and that the lock overrides normal user permissions. ([Microsoft Learn][6])

---

### **1. Use `CanNotDelete` for critical resources**

Example:

```text
rg-prod-core
│
├── Key Vault
├── Production SQL
├── Recovery Vault
├── Traffic Manager
└── Critical network resources
```

I might apply:

```text
CanNotDelete
```

at:

```text
resource
or
resource-group scope
```

depending on the blast radius I want protected.

Result:

```text
Owner
   ↓
tries delete
   ↓
ARM checks lock
   ↓
BLOCKED
```

Even broad RBAC doesn't bypass the lock automatically. ([Microsoft Learn][6])

---

### **2. `CanNotDelete` vs `ReadOnly`**

For most production resources I would prefer:

```text
CanNotDelete
```

because normal administration can continue.

```text
CanNotDelete:
Read    ✓
Modify  ✓
Delete  ✗
```

Whereas:

```text
ReadOnly:
Read    ✓
Modify  ✗
Delete  ✗
```

`ReadOnly` can easily break legitimate control-plane operations.

So I reserve it for rare cases where configuration must effectively be frozen.

---

### **3. Use inherited locks carefully**

If I place:

```text
CanNotDelete
```

on:

```text
rg-prod
```

resources beneath the group inherit the restriction.

That can be very useful:

```text
rg-prod-database
       ↓
all DB-related resources
protected
```

But it also means planned deployments or replacement workflows may require controlled lock removal.

Microsoft documents lock inheritance and states that the most restrictive applicable lock takes precedence. ([Microsoft Learn][6])

---

### **4. Restrict who can remove locks**

A lock is useless if every contributor can casually remove it.

I would separate:

```text
Application Contributor
→ manage workload

Platform/SRE privileged role
→ lock administration
```

and use:

```text
PIM
```

for temporary elevated access where possible.

Operational process:

```text
Need planned deletion
      ↓
Change approval
      ↓
PIM elevation
      ↓
Remove lock
      ↓
Perform operation
      ↓
Reapply lock
```

---

### **5. Lock ≠ data protection**

This is extremely important.

A lock protects **ARM control-plane resource operations**.

It does not universally mean:

```text
Storage blobs can't be deleted
SQL rows can't be deleted
Key Vault secret data is indestructible
```

Therefore I separately enable service-level protections such as:

```text
Backup
Soft delete
Purge protection
Blob versioning
Immutable storage/retention
Database PITR
Recovery Services
```

depending on the workload.

A production database needs:

```text
Resource protection
+
Data protection
```

not one or the other.

---

### **6. Example: Key Vault**

I would potentially combine:

```text
Key Vault
│
├── CanNotDelete resource lock
├── Soft delete
├── Purge protection
├── Private networking
└── RBAC
```

Different controls solve different problems:

```text
Lock
→ prevent accidental ARM deletion

Soft delete
→ recover deleted vault/secrets

Purge protection
→ prevent premature permanent purge

RBAC
→ control who can manage/read
```

---

### **7. Example: Traffic Manager**

Deleting a production Traffic Manager profile can immediately break DNS-based routing.

Microsoft's current Traffic Manager security guidance specifically recommends a `CanNotDelete` lock on production profiles to protect against accidental deletion. ([Microsoft Learn][7])

That is a nice concrete interview example.

---

### **8. Policy `DenyAction` can help at scale**

Azure Policy also supports:

```text
DenyAction
```

with delete blocking scenarios.

Conceptually:

```text
Critical resource class
       ↓
Policy
       ↓
DELETE
       ↓
DenyAction
```

This is useful when the organization wants centrally governed protection across large resource populations.

But I would distinguish:

```text
Resource Lock
→ direct resource/scope protection

Azure Policy DenyAction
→ policy-driven delete protection
  across governed scopes
```

The exact choice depends on the governance model.

---

### **9. Don't lock everything**

If I apply locks indiscriminately:

```text
all dev resources
all transient resources
all deployment components
```

I can break:

```text
Terraform destroy
blue/green cleanup
resource replacement
autoscaling workflows
platform upgrades
```

So I protect:

```text
critical + stateful + high-blast-radius
```

resources, not every disposable resource.

---

### **10. Production pattern**

```text
Critical Resource
      │
      ├── Azure RBAC least privilege
      ├── PIM for privileged changes
      ├── CanNotDelete lock
      ├── Backup/soft delete
      ├── Monitoring
      └── Change-management process
```

> **In an interview, I would say:**
> “For critical production resources I would normally apply a `CanNotDelete` resource lock so authorized users can still manage the resource but cannot accidentally delete it. I would restrict lock removal to a small privileged group and preferably use PIM for temporary elevation. I wouldn't rely on locks alone because they protect ARM control-plane operations, not necessarily underlying data, so I also use service-specific protections such as backup, soft delete, purge protection, versioning, or retention. At large scale I can also evaluate Azure Policy `DenyAction` for centrally governed deletion prevention.”

**Memory line:**
**Lock the resource, protect the data separately, and tightly control who can remove the lock.**

**Interview trap:**
`CanNotDelete` is **not a backup** and doesn't universally protect data-plane objects.

**Keywords:**
`CanNotDelete`, `ReadOnly`, resource lock, PIM, RBAC, soft delete, backup, `DenyAction`

**Likely follow-ups:**

* Can an Owner delete a locked resource?
* Resource lock vs Azure Policy `DenyAction`?
* Does a Storage lock protect individual blobs?
* When would you use `ReadOnly` instead?

### **T18-H05. How would you apply common governance controls across hundreds of subscriptions?**

**Answer:**
I would build a **management-group hierarchy**, organize subscriptions according to common governance requirements, define reusable **Azure Policy initiatives at management-group scope**, apply baseline **Azure RBAC**, tagging, security, diagnostic, networking, and regional controls through inheritance, and manage the entire governance layer through Infrastructure as Code.

I would **not configure hundreds of subscriptions independently**.

Microsoft's Cloud Adoption Framework specifically recommends management groups for organizing and governing subscriptions at scale and applying policies/RBAC according to common workload requirements. ([Microsoft Learn][4])

---

### **High-level hierarchy**

```text
Tenant Root
│
├── Platform
│   ├── Identity
│   ├── Connectivity
│   └── Management
│
├── Landing Zones
│   ├── Corp
│   │   ├── App Subscription 001
│   │   ├── App Subscription 002
│   │   └── ...
│   │
│   └── Online
│       ├── App Subscription 101
│       └── ...
│
├── Sandbox
│
└── Decommissioned
```

Each level receives only the controls appropriate to that class of subscription.

This is broadly aligned with Azure Landing Zone principles: subscriptions are placed under management groups so inherited Policy and access controls can provide the required security and compliance baseline. ([Microsoft Learn][4])

---

### **1. Start with management groups, not subscription-by-subscription configuration**

Bad model:

```text
Subscription 001
→ 37 manual policies

Subscription 002
→ another 37

Subscription 003
→ slightly different 37
```

After 300 subscriptions:

```text
configuration drift
```

Better:

```text
Management Group
      ↓
Policy assignments
      ↓
hundreds of subscriptions inherit
```

---

### **2. Group subscriptions by governance requirements**

Don't make the hierarchy merely copy the company's org chart.

A better question is:

> Which subscriptions need the same security, compliance, connectivity, and operational controls?

For example:

```text
Platform
→ central shared services

Corp
→ internally connected enterprise workloads

Online
→ internet-facing workloads

Sandbox
→ low-risk experimentation
```

Microsoft's current management-group guidance explicitly recommends organizing around workload/security/compliance/connectivity needs and gives workload types such as `corp`, `online`, and `sandbox` as examples. ([Microsoft Learn][4])

---

### **3. Build governance as initiatives**

Instead of hundreds of individual Policy assignments, I package them.

Example:

```text
Enterprise Security Baseline
│
├── Restrict public networking
├── Require encryption
├── Require diagnostics
├── Approved SKUs
├── Approved regions
└── Security configuration
```

Then:

```text
Tagging Baseline
│
├── Require CostCenter
├── Require Application
├── Inherit Environment
└── Inherit Owner
```

And:

```text
Monitoring Baseline
│
├── Deploy diagnostic settings
├── Log to central workspace/Event Hub
└── Required monitoring config
```

Azure guidance explicitly recommends grouping related controls into initiatives and applying those initiatives to management groups for scalable governance. ([Microsoft Learn][5])

---

### **4. Separate global controls from workload-specific controls**

At root I might put only truly universal requirements:

```text
Tenant Root
├── baseline audit
├── critical security baseline
└── organizational standards
```

Then:

```text
Production
├── Deny public IPs
├── restrictive regions
└── stronger diagnostics

Sandbox
├── cost controls
├── limited SKUs
└── looser networking
```

Microsoft explicitly recommends **limiting the number of Policy assignments at the root management group**, because excessive root-level inheritance makes downstream troubleshooting difficult. ([Microsoft Learn][4])

This is an excellent architecture-interview detail.

---

### **5. RBAC also follows the hierarchy**

Example:

```text
Platform MG
→ Platform Engineering team

Production MG
→ Security Reader
→ central operations permissions

Individual Subscription
→ workload team Contributor
```

So the operating model becomes:

```text
Central team
→ owns guardrails

Application team
→ owns workload inside guardrails
```

Rather than:

```text
central team owns every single deployment
```

---

### **6. Subscription vending/onboarding**

At hundreds of subscriptions, subscription creation should be automated.

I would build a process like:

```text
Application team request
        ↓
Subscription vending pipeline
        ↓
Create/attach subscription
        ↓
Place into correct Management Group
        ↓
Apply inherited Policy/RBAC
        ↓
Configure:
tags
budgets
logging
networking
security contacts
        ↓
Hand over to team
```

This means a new subscription becomes compliant **by placement into the hierarchy**, rather than requiring 30 manual portal tasks.

---

### **7. Use Policy for baseline configuration**

A good baseline could include:

```text
Governance
├── Allowed regions
├── Required tags
├── Allowed resource/SKU types
│
Security
├── Disable public network access
├── Require encryption
├── Defender configuration
│
Operations
├── Deploy diagnostic settings
├── Central logging
│
Networking
└── Approved connectivity patterns
```

Not all controls should necessarily be `Deny`.

I choose:

```text
Audit
Deny
Modify
DeployIfNotExists
```

according to the requirement.

---

### **8. Use IaC for the governance layer**

I would define:

```text
Management Groups
Policy definitions
Initiatives
Assignments
RBAC
Diagnostic configuration
```

through:

```text
Terraform
or
Bicep
```

rather than manually managing portal state.

Advantages:

```text
version control
pull-request review
repeatability
change history
rollback/reconciliation
```

At hundreds of subscriptions, governance itself is effectively a platform product.

---

### **9. Introduce new controls progressively**

For a new enterprise policy:

```text
New initiative
    ↓
Audit
    ↓
Compliance dashboard
    ↓
Find existing violations
    ↓
Remediation
    ↓
Approved exemptions
    ↓
Deny / Modify / DINE
```

Recent Microsoft governance guidance explicitly recommends introducing initiatives in audit, validating their signal quality, and then moving critical controls to deny. ([Microsoft Learn][5])

---

### **10. Compliance should be centrally observable**

I want the platform/security team to answer:

```text
Which subscriptions are compliant?
Which policies fail most?
Which exemptions expire soon?
Which resources don't have diagnostics?
Which subscriptions violate region policy?
```

without opening each subscription.

Conceptually:

```text
Hundreds of Subscriptions
           ↓
Azure Policy compliance
           ↓
Central governance dashboard
           ↓
Platform / Security
```

---

### **11. Use exemptions instead of weakening baselines**

Suppose one application legitimately can't meet a specific baseline.

Bad:

```text
Turn off policy for entire Corp MG
```

Better:

```text
Workload
  ↓
Policy exemption
  ↓
Reason
Owner
Compensating control
Expiration
```

This keeps the exception narrow.

---

### **12. Design for autonomy**

The strongest enterprise design isn't:

```text
developers can't do anything
```

It is:

```text
Platform team defines paved road
           ↓
Policy + RBAC + networking
           ↓
Application teams deploy freely
inside safe boundaries
```

Microsoft's modern landing-zone guidance recommends environment/subscription separation and consistent archetype-level policies while allowing workload owners to add workload-specific policies where necessary. ([Microsoft Learn][8])

---

### **Complete governance architecture**

```text
                    Tenant Root
                        │
             Organization-wide baseline
                        │
       ┌────────────────┼────────────────┐
       ↓                ↓                ↓
    Platform        Landing Zones      Sandbox
       │                │
 ┌─────┼─────┐      ┌───┴────┐
 ↓     ↓     ↓      ↓        ↓
Identity Mgmt Network Corp   Online
                   │         │
               Subs 1..N  Subs 1..N
                   │         │
                 Workload Teams
```

Controls inherited:

```text
Management Groups
       ↓
Policy Initiatives
       ↓
RBAC
       ↓
Subscriptions
       ↓
Resource Groups
       ↓
Resources
```

> **In an interview, I would say:**
> “For hundreds of subscriptions I would use management groups as the governance hierarchy rather than configuring subscriptions individually. I organize subscriptions based on common security, compliance, connectivity, and workload requirements, then assign reusable Policy initiatives and RBAC at those management-group scopes. I keep only truly universal controls near the tenant root and apply stronger environment-specific controls lower down. Subscription onboarding is automated so a new subscription is placed into the correct management group and automatically inherits policies, RBAC, logging, budgets, tags, and networking standards. I manage the governance layer with IaC, roll new controls out in Audit first, remediate existing resources, use formal exemptions for legitimate exceptions, and then enforce critical controls with Deny or other appropriate effects.”

**Memory line:**
**At enterprise scale, govern the hierarchy—not hundreds of individual subscriptions.**

**Interview trap:**
Do not put every possible Policy at the Tenant Root just because it reaches everything; excessive root inheritance becomes difficult to operate and troubleshoot. ([Microsoft Learn][4])

**Keywords:**
Management groups, Azure Policy initiative, landing zones, inheritance, subscription vending, RBAC, IaC, governance baseline

**Likely follow-ups:**

* What policies belong at Tenant Root?
* How would you onboard a new subscription?
