### **T23-E02. What is Azure Event Grid?**

**Answer:**
Azure Event Grid is a **managed event-routing service** used to deliver events from event producers to interested consumers. It is designed for **event-driven architectures**, where something happens—such as a blob being created—and downstream services react to that event.

### **How it works**

```text
Event Source
    ↓
Event Grid
    ↓
Event Handler
```

For example:

```text
Blob Storage
    ↓
BlobCreated event
    ↓
Event Grid
    ↓
Azure Function
```

The storage account publishes the event, Event Grid routes it, and the Function reacts.

Common event sources include:

* Azure Storage
* Resource Groups and subscriptions
* Azure services
* custom applications

Common handlers include:

* Azure Functions
* Logic Apps
* webhooks
* Service Bus
* Event Hubs

Event Grid supports filtering, so subscribers only receive events they care about.

### **Important distinction**

Event Grid is mainly about:

> **“Something happened.”**

For example:

```text
BlobCreated
ResourceDeleted
OrderCreated
```

It is not primarily a durable business-command queue where consumers hold messages for long processing workflows.

**Memory line:**
**Event Grid routes events so services can react when something happens.**

**Interview trap:**
Do not describe Event Grid as a general-purpose message queue. For durable enterprise commands and workflows, Service Bus is usually the stronger fit.

**Keywords:**
Event-driven, event routing, publisher, subscriber, event handler, filtering, webhook.

### **T23-E03. What is Azure Event Hubs?**

**Answer:**
Azure Event Hubs is a **managed high-throughput event-streaming platform** designed to ingest and process very large volumes of events, such as telemetry, logs, clickstreams, and IoT data. It is optimized for streaming rather than traditional message-queue workflows.

### **How it works**

```text
Producers
   ↓
Event Hubs
   ↓
Partitions
   ↓
Consumers
```

Multiple producers can continuously send events:

```text
IoT devices
Applications
Servers
Containers
     ↓
 Event Hubs
     ↓
Stream processors
```

Consumers might include:

* Azure Stream Analytics
* Azure Functions
* Databricks
* custom applications

Event Hubs scales using **partitions**, which allow events to be processed in parallel.

### **Production example**

Imagine thousands of application instances sending telemetry:

```text
AKS Pods
   ↓
Telemetry events
   ↓
Event Hubs
   ↓
Analytics pipeline
```

Event Hubs is a good fit because the requirement is large-scale streaming rather than individual business-message processing.

### **Important distinction**

Think:

```text
Service Bus
→ reliable business messages

Event Grid
→ event notification/routing

Event Hubs
→ high-volume event streaming
```

**Memory line:**
**Event Hubs is Azure's high-throughput ingestion service for streaming events at scale.**

**Interview trap:**
Do not confuse Event Hubs with Service Bus queues. Event Hubs is optimized for streams and consumer processing, not per-message business workflows.

**Keywords:**
Streaming, ingestion, partitions, consumer groups, telemetry, high throughput.

### **T23-E04. What is a queue?**

**Answer:**
A queue is a messaging pattern where producers place messages into a buffer and consumers process them asynchronously. Typically, each message is processed by **one consumer from a competing-consumer group**, which makes queues useful for distributing work reliably.

### **How it works**

```text
Producer
   ↓
 Queue
   ↓
Consumer
```

With multiple workers:

```text
           ┌→ Worker 1
Producer → Queue → Worker 2
           └→ Worker 3
```

Each worker competes for messages, allowing processing to scale horizontally.

### **Production example**

An API could enqueue order-processing work:

```text
Order API
   ↓
Service Bus Queue
   ↓
Order Processor
```

The API can respond quickly without waiting for the background work to finish.

A queue also helps absorb traffic spikes:

```text
Sudden traffic spike
        ↓
      Queue
        ↓
Workers process at sustainable rate
```

**Memory line:**
**A queue buffers work so producers and consumers do not have to operate at the same speed or at the same time.**

**Interview trap:**
Do not assume every consumer receives every queued message. In a normal queue pattern, a message is generally processed by one competing consumer, not broadcast to all consumers.

**Keywords:**
Queue, producer, consumer, asynchronous processing, competing consumers, buffering.

### **T23-E05. What is a topic?**

**Answer:**
A topic is a **publish-subscribe messaging pattern** where a producer sends a message once and multiple independent subscribers can receive their own copy. In Azure Service Bus, a topic works together with **subscriptions**.

### **How it works**

```text
Publisher
    ↓
Service Bus Topic
    ├── Subscription A → Billing
    ├── Subscription B → Inventory
    └── Subscription C → Notifications
```

Each subscription acts somewhat like its own virtual queue.

So one published message can independently be processed by several systems.

### **Production example**

Suppose an application publishes:

```text
OrderCreated
```

Different services may need it:

```text
Order Service
     ↓
Service Bus Topic
     ├── Payment Subscription
     ├── Inventory Subscription
     └── Email Subscription
```

Each subscription receives and processes the message independently.

Subscriptions can also use filters.

For example:

```text
Topic: Orders
   │
   ├── HighValueOrders
   └── InternationalOrders
```

### **Queue vs topic**

```text
Queue
Producer → Message → One consumer

Topic
Producer → Message
             ├→ Subscriber A
             ├→ Subscriber B
             └→ Subscriber C
```

**Memory line:**
**Queue means one work stream; topic means one publication with multiple independent subscribers.**

**Interview trap:**
A Service Bus topic does not deliver directly to consumers without subscriptions. Consumers read from the subscriptions attached to the topic.

**Keywords:**
Topic, subscription, publish-subscribe, fan-out, filtering, Service Bus.
