### **T23-M09. What is a consumer group?**

**Answer:**
A consumer group in Azure Event Hubs is an **independent view of the same event stream**. Each consumer group maintains its own reading progress, so multiple applications can process the same events independently without interfering with each other.

### **How it works**

```text
                Event Hub
                    ↓
        ┌───────────┼───────────┐
        ↓           ↓           ↓
Consumer Group A Consumer Group B Consumer Group C
    Analytics       Alerts       Archiving
```

All three groups can read the same underlying events.

The important point is that they do **not compete with each other across consumer groups**.

Within a single consumer group, however, consumer instances typically divide partition ownership among themselves:

```text
Consumer Group A

Consumer 1 → Partition 0
Consumer 2 → Partition 1
Consumer 3 → Partition 2
Consumer 4 → Partition 3
```

### **Checkpointing**

Each consumer group tracks its own position using checkpoints.

Conceptually:

```text
Partition:
E1 → E2 → E3 → E4 → E5 → E6

Analytics group: processed through E5
Alerting group:  processed through E3
```

So one application can lag behind without affecting another.

In production, checkpoint state is usually stored in durable storage by the Event Hubs client framework, for example Azure Blob Storage when using Event Processor clients.

### **Production example**

Suppose Event Hubs receives application telemetry:

```text
AKS applications
      ↓
Event Hubs
      ↓
├── Consumer Group: realtime-alerts
├── Consumer Group: analytics
└── Consumer Group: long-term-processing
```

Each workload sees the same telemetry but processes it for a different purpose.

### **Important distinction**

Do not confuse:

```text
Consumer instances
vs
Consumer groups
```

Multiple consumers **inside one consumer group** cooperate and split partitions.

Different consumer groups independently read the same stream.

### **Interview answer condensed**

> “A consumer group gives an application its own independent view of an Event Hubs stream. Different consumer groups can consume the same events at different speeds and maintain separate checkpoints. Within one consumer group, consumer instances share partition ownership to scale processing.”

**Memory line:**
**Consumer groups separate applications; consumers inside a group share the work.**

**Interview trap:**
Do not say multiple consumer groups divide the events between themselves. Each consumer group can independently read the full stream.

**Keywords:**
Consumer group, checkpoint, partition ownership, independent stream view, Event Processor.

**Likely follow-ups:**

* What is checkpointing?
* What happens if two consumers in the same consumer group read the same partition?
* Why create multiple consumer groups?
* Where are checkpoints stored?

### **T23-H01. Which service would you use for processing millions of telemetry events per second?**

**Answer:**
For processing millions of telemetry events per second, I would normally choose **Azure Event Hubs** because it is designed for very high-throughput streaming ingestion. I would partition the stream appropriately, scale capacity based on throughput, and use consumer groups so multiple downstream systems can process the same telemetry independently.

### **Why Event Hubs**

The requirement immediately tells me:

```text
Millions of events
      +
Telemetry
      +
Continuous stream
      ↓
Azure Event Hubs
```

This is different from reliable business-message processing.

Examples of suitable data:

* IoT sensor readings
* application telemetry
* logs
* clickstreams
* metrics
* device events

Architecture:

```text
Millions of producers
        ↓
    Event Hubs
        ↓
   Partitions
   ├── P0
   ├── P1
   ├── P2
   └── Pn
        ↓
Consumer Groups
   ├── Real-time analytics
   ├── Alerting
   └── Data lake ingestion
```

### **Production design**

#### 1. Size throughput correctly

I would estimate:

```text
events/sec
×
average event size
=
ingress throughput
```

Then choose the Event Hubs tier and capacity model that can support the required ingress and egress.

I would leave headroom rather than sizing exactly to current peak traffic.

---

#### 2. Use enough partitions

Partitions determine parallel processing capacity.

```text
Event Hub
│
├── Partition 0
├── Partition 1
├── Partition 2
├── Partition 3
└── ...
```

More partitions allow more consumer instances to process events in parallel.

But I would not create arbitrary partition keys that cause skew.

---

#### 3. Choose partition keys carefully

If per-device ordering matters:

```text
PartitionKey = deviceId
```

Then all events from a device stay on the same partition.

But I would ensure that the partition key has enough cardinality to avoid a hot partition.

---

#### 4. Separate downstream workloads with consumer groups

```text
Event Hubs
    ↓
├── Consumer Group: fraud-detection
├── Consumer Group: analytics
├── Consumer Group: monitoring
└── Consumer Group: archive
```

Each workload can read independently.

---

#### 5. Checkpoint processing

Consumers should checkpoint their progress so they can resume after restarts without rereading the entire stream unnecessarily.

### **Why not Service Bus?**

Service Bus is excellent for:

```text
ProcessOrder
ChargePayment
GenerateInvoice
```

where I care about message settlement, DLQs, sessions, and business-processing semantics.

But:

```text
5 million telemetry events/sec
```

is fundamentally a streaming-ingestion problem.

### **Why not Event Grid?**

Event Grid is excellent for distributing discrete events and notifications, but it is not the service I would choose as the primary ingestion backbone for massive telemetry streams.

### **Interview answer condensed**

> “For millions of telemetry events per second, I would use Azure Event Hubs. It is designed for high-throughput streaming ingestion and scales through partitions and configurable capacity. I’d distribute events across partitions using a well-designed partition key if ordering is required, and use separate consumer groups for analytics, monitoring, and archival workloads.”

**Memory line:**
**Massive telemetry stream = Event Hubs.**

**Interview trap:**
Do not choose Service Bus just because both services handle messages. Service Bus is optimized for reliable business messaging, while Event Hubs is optimized for streaming at scale.

**Keywords:**
Event Hubs, partitions, throughput, consumer groups, checkpointing, partition key, telemetry streaming.

**Likely follow-ups:**

* How do partitions affect Event Hubs throughput?
* How would you avoid hot partitions?
* What happens when consumers fall behind?
* How would you retain or archive the telemetry?

### **T23-H02. Which service would you use for reliable business-command processing?**

**Answer:**
For reliable business-command processing, I would normally choose **Azure Service Bus** because it provides durable queues, message settlement, retries, dead-letter queues, duplicate detection, and sessions. Those capabilities are much more appropriate for commands such as `ProcessOrder` or `ChargePayment` than a streaming service like Event Hubs.

### **Why Service Bus**

A business command usually means:

```text
"Do this work reliably"
```

For example:

```text
ProcessOrder
ChargeCustomer
ReserveInventory
GenerateInvoice
```

The desired flow is:

```text
API / Producer
      ↓
Service Bus Queue
      ↓
Worker
      ↓
Business operation
```

The producer and consumer are decoupled, and the command remains durable until it is processed or moved to the DLQ.

### **Production processing pattern**

I would normally use **Peek-Lock** processing:

```text
Receive message
      ↓
Lock message
      ↓
Process command
      ↓
├── Success → Complete
│
└── Failure → Retry / Abandon
                   ↓
             Max attempts reached
                   ↓
                  DLQ
```

This provides much safer processing than deleting the message immediately upon receipt.

### **Example: payment command**

```text
Checkout API
     ↓
ChargePayment command
     ↓
Service Bus Queue
     ↓
Payment Worker
```

The worker should be idempotent.

For example:

```text
paymentId = pay-123
```

Before charging:

```text
Already processed pay-123?
      │
      ├── Yes → return success safely
      └── No  → perform charge
```

This protects against duplicate delivery.

### **Useful Service Bus features**

For reliable command workflows, I may use:

* **DLQ** for poison messages
* **duplicate detection** for producer retries
* **sessions** when per-entity ordering matters
* **scheduled delivery** for delayed commands
* **topics/subscriptions** when multiple independent handlers need the same business event
* **Peek-Lock** for reliable processing

### **Important distinction: command vs event**

A command normally expresses intent:

```text
ChargePayment
```

An event normally states a fact:

```text
PaymentCompleted
```

For a command, I usually want a clearly responsible processor.

That makes a Service Bus queue a natural fit.

### **Interview answer condensed**

> “For reliable business commands I would use Azure Service Bus. It gives me durable queues, Peek-Lock processing, retries, dead-lettering, duplicate detection, and sessions. I’d also design the consumer to be idempotent because message redelivery is still possible. A command like `ChargePayment` is a much better fit for Service Bus than Event Hubs.”

**Memory line:**
**Reliable business work = Service Bus.**

**Interview trap:**
Do not claim Service Bus guarantees exactly-once business execution. The consumer still needs idempotency.

**Keywords:**
Service Bus, command, Peek-Lock, DLQ, retries, idempotency, duplicate detection, sessions.

**Likely follow-ups:**

* Why does the consumer still need to be idempotent?
* When would you use a topic instead of a queue?
* What happens if processing exceeds the lock duration?
* How would you handle poison messages?

### **T23-H03. How would you design an asynchronous microservice workflow with retries and dead-letter handling?**

**Answer:**
I would decouple the microservices using **Azure Service Bus**, use queues or topics depending on whether one or multiple consumers need each message, process messages with Peek-Lock, retry only transient failures with bounded backoff, move poison messages to the DLQ, and make every consumer idempotent. I would also monitor queue depth, processing latency, retry rate, and DLQ growth.

### **Architecture**

For example, an order workflow:

```text
Client
  ↓
Order API
  ↓
Orders Queue
  ↓
Order Worker
  ↓
OrderCreated Topic
  ├── Payment Subscription
  ├── Inventory Subscription
  └── Notification Subscription
```

This separates synchronous request handling from downstream work.

---

### **Implementation order**

#### 1. Keep the initial request small and durable

The API should validate the request and persist or enqueue the durable work.

```text
Client
   ↓
Order API
   ↓
Service Bus
   ↓
Return accepted response
```

The API does not wait synchronously for every downstream service to finish.

---

#### 2. Use Peek-Lock processing

Each worker should:

```text
Receive
   ↓
Lock
   ↓
Process
   ↓
Complete
```

If processing fails before completion, the message can be retried.

---

#### 3. Classify failures before retrying

This is critical.

I would separate:

```text
Transient failure
vs
Permanent failure
```

Examples:

**Transient:**

* HTTP 503
* temporary database outage
* network timeout
* rate limiting

These can be retried.

**Permanent:**

* invalid account ID
* malformed payload
* unsupported business state

Retrying these repeatedly is pointless.

A good flow is:

```text
Processing failure
      ↓
Is transient?
   ├── Yes → Retry with backoff
   └── No  → Dead-letter
```

---

#### 4. Use bounded retries with backoff

I would avoid immediate infinite retries.

For example:

```text
Attempt 1
   ↓
wait
   ↓
Attempt 2
   ↓
longer wait
   ↓
Attempt 3
```

This protects a failing dependency from a retry storm.

Where appropriate I would combine:

* exponential backoff
* jitter
* retry limits
* Service Bus delivery-count behavior

---

#### 5. Dead-letter poison messages

After repeated failures:

```text
Main Queue
    ↓
Consumer
    ↓
Repeated failure
    ↓
DLQ
```

The DLQ should be monitored.

I would capture useful diagnostic properties such as:

```text
messageId
correlationId
business entity ID
failure reason
timestamp
retry count
```

Then operations can:

```text
Investigate
   ↓
Fix underlying issue
   ↓
Replay safely
```

---

#### 6. Make consumers idempotent

This is one of the most important design requirements.

Suppose:

```text
Worker charges customer
        ↓
Worker crashes before Complete()
        ↓
Message redelivered
```

Without idempotency, the customer could be charged twice.

I would use a stable operation ID:

```text
paymentId = payment-123
```

and track processing:

```text
payment-123 already processed?
       │
       ├── Yes → acknowledge safely
       └── No  → execute + persist result
```

### **7. Use correlation IDs for tracing**

For a multi-service workflow:

```text
Order API
   ↓
Payment
   ↓
Inventory
   ↓
Notification
```

I would propagate something like:

```text
CorrelationId = order-9182
```

through every message.

Then logs and traces can reconstruct the end-to-end flow.

---

### **8. Monitor the broker and consumers**

Important signals include:

```text
Active queue depth
DLQ depth
Oldest message age
Processing latency
Retry rate
Consumer failures
Throughput
```

A rapidly increasing queue depth usually means:

```text
Ingress rate > processing rate
```

or consumers are unhealthy.

### **9. Avoid a distributed transaction**

I generally would not attempt a single database transaction across multiple microservices.

For a workflow such as:

```text
Order
  ↓
Payment
  ↓
Inventory
  ↓
Shipping
```

I would use eventual consistency and, for complex workflows, a **Saga-style pattern** with compensating actions.

Example:

```text
Payment succeeds
      ↓
Inventory reservation fails
      ↓
Compensating action
      ↓
Refund / cancel payment
```

### **Production flow**

```text
Producer
   ↓
Service Bus
   ↓
Consumer
   ↓
Process idempotently
   │
   ├── Success
   │      ↓
   │   Complete
   │
   └── Failure
          ↓
     Transient?
      ├── Yes → bounded retry
      └── No / max retries
                 ↓
                DLQ
                 ↓
           Alert + investigate
                 ↓
              Safe replay
```

### **Interview answer condensed**

> “I would use Service Bus to decouple the microservices and process messages in Peek-Lock mode. Consumers would be idempotent, because redelivery can occur. I’d retry only transient failures using bounded exponential backoff, and after the retry limit—or immediately for permanent failures—I’d dead-letter the message. I’d propagate correlation IDs and monitor queue depth, oldest-message age, retry rate, and DLQ growth. For multi-step workflows, I’d prefer eventual consistency and a Saga pattern rather than distributed transactions.”

**Memory line:**
**Queue the work, process idempotently, retry transient failures, dead-letter poison messages, and monitor the backlog.**

**Interview trap:**
The biggest mistake is blindly retrying every error. Permanent failures should not create infinite retry loops.

**Keywords:**
Service Bus, Peek-Lock, idempotency, exponential backoff, DLQ, poison message, correlation ID, Saga, eventual consistency.

**Likely follow-ups:**

* How would you implement idempotency?
* When would you dead-letter immediately rather than retry?
* How would you replay DLQ messages safely?
* What is the Saga pattern and when would you use it?
