### **T23-H04. How would you design idempotent consumers?**

**Answer:**
I would design the consumer so processing the same message more than once produces the **same final business result** as processing it once. The usual approach is to give every business operation a stable unique ID, record successful processing durably, and check that record before applying side effects.

### **Why idempotency is necessary**

With Service Bus, duplicate delivery can happen.

For example:

```text
Consumer receives message
        ↓
Charges customer
        ↓
Crashes before Complete()
        ↓
Message lock expires
        ↓
Same message is delivered again
```

If the consumer simply repeats the operation:

```text
Charge #1
Charge #2
```

you have a serious production bug.

So I assume:

> **At-least-once delivery means duplicate processing is possible.**

---

### **Implementation pattern**

Suppose the message contains:

```json
{
  "messageId": "pay-8472",
  "orderId": "ORD-123",
  "amount": 500
}
```

I would use a stable business or idempotency key such as:

```text
pay-8472
```

Then:

```text
Receive message
      ↓
Check processed_messages table
      ↓
Already processed?
   ├── Yes → return success / Complete message
   │
   └── No
        ↓
   Perform business operation
        ↓
Record pay-8472 as processed
        ↓
Complete Service Bus message
```

### **Critical part: make the check and update atomic**

A weak implementation does this:

```text
1. Check database
2. See "not processed"
3. Perform operation
4. Insert processed record
```

Two consumer attempts could race:

```text
Consumer A → not processed
Consumer B → not processed
```

and both execute.

So I prefer a database-level guarantee such as:

```text
UNIQUE(idempotency_key)
```

or an atomic transaction.

For example:

```text
BEGIN TRANSACTION

Insert idempotency key
    ↓
If duplicate → already processed
    ↓
Otherwise perform local DB change

COMMIT
```

### **Production example**

For an inventory reservation:

```text
Message:
ReserveInventory
operationId = reserve-ORD123-SKU77
```

The consumer stores:

```text
processed_operations
--------------------
reserve-ORD123-SKU77
```

If Service Bus redelivers the message, the second attempt sees the operation already completed and safely acknowledges it.

---

### **External side effects are harder**

If the consumer calls an external payment API:

```text
Service Bus
    ↓
Payment Worker
    ↓
External Payment Provider
```

a local database transaction cannot make the remote HTTP call atomic.

In that case I would ideally pass an **idempotency key** to the external service if it supports one:

```text
Idempotency-Key: pay-8472
```

Then retries with the same key should return the original result rather than execute a second payment.

For systems I control, I would build this capability into the downstream API.

---

### **Useful patterns**

Depending on the workflow, I may use:

* unique constraints
* processed-message/inbox table
* idempotency keys
* transactional inbox/outbox patterns
* conditional updates
* business-state checks

For example:

```text
UPDATE orders
SET status = 'SHIPPED'
WHERE id = '123'
AND status = 'PAID'
```

Repeated execution will not repeatedly transition the order.

### **Important distinction**

**Duplicate detection** and **idempotency** solve different problems:

```text
Service Bus duplicate detection
→ prevents some duplicate sends

Idempotent consumer
→ prevents duplicate business effects
```

I still design consumers idempotently even when duplicate detection is enabled.

### **Interview answer condensed**

> “I assume a message may be delivered more than once, so every consumer should be safe to retry. I’d include a stable operation or message ID, store successfully processed IDs using a unique constraint or atomic transaction, and skip the business side effect if that ID has already been handled. For external APIs such as payments, I’d propagate an idempotency key where supported. Service Bus duplicate detection helps, but it does not replace consumer idempotency.”

**Memory line:**
**Same message twice must not mean same side effect twice.**

**Interview trap:**
Do not implement idempotency using only an in-memory cache; a restart or another consumer instance would lose that protection.

**Keywords:**
Idempotency key, unique constraint, inbox pattern, duplicate delivery, atomic transaction, at-least-once delivery.

**Likely follow-ups:**

* How would you make the idempotency check race-safe?
* What if the consumer crashes after the side effect but before recording success?
* How would you make payment processing idempotent?
* Is Service Bus duplicate detection enough?

### **T23-H05. How would you troubleshoot continuously increasing queue depth?**

**Answer:**
An increasing queue depth means messages are arriving faster than they are being successfully removed. I would first compare **ingress rate versus processing/completion rate**, then determine whether the consumers are under-scaled, slow, unhealthy, retrying, blocked by dependencies, or unable to complete messages.

### **Diagnostic flow**

```text
Queue depth increasing
        ↓
Producer rate > consumer completion rate?
        ↓
Consumer health/capacity
        ↓
Processing latency
        ↓
Retries / lock failures / DLQ
        ↓
Downstream dependency
        ↓
Service Bus limits/configuration
```

### **1. Confirm the backlog pattern**

First I would look at:

* active message count
* incoming messages/sec
* completed messages/sec
* oldest message age
* dead-letter count
* throttling/errors

The important equation is:

```text
Ingress = 5,000 msg/sec
Processing = 3,000 msg/sec

Backlog growth = 2,000 msg/sec
```

That immediately tells me this is a capacity or processing-rate problem.

I would also check whether the queue depth:

```text
steadily increases
```

or:

```text
spikes briefly and drains afterward
```

A temporary spike may simply be expected buffering behavior.

---

### **2. Check consumer availability**

Next I would verify that consumers are actually running.

For AKS-based consumers:

```bash
kubectl get pods
kubectl get hpa
kubectl get events
kubectl logs <consumer-pod>
```

I would look for:

* crashed consumers
* `CrashLoopBackOff`
* pods not Ready
* insufficient replicas
* deployment failures
* recent rollout problems

Architecture:

```text
Service Bus
    ↓
AKS consumers
│
├── Pod 1
├── Pod 2
└── Pod 3
```

If one or more consumers disappeared, queue depth will increase even though Service Bus itself is healthy.

---

### **3. Compare consumer throughput with ingress**

If consumers are healthy but cannot keep up:

```text
Producer rate
     >
Consumer rate
```

I would check whether processing can safely scale horizontally.

For example:

```text
3 consumer pods × 100 msg/sec
= 300 msg/sec

Incoming
= 900 msg/sec
```

Then I may need more consumers.

For AKS, this could be automated using KEDA with Service Bus queue metrics:

```text
Service Bus queue depth
        ↓
KEDA
        ↓
Scale AKS consumer replicas
```

This is a common event-driven autoscaling pattern.

---

### **4. Check processing latency**

The consumer may be alive but slow.

I would break processing time down:

```text
Receive message
    ↓
Application logic
    ↓
Database call
    ↓
External API
    ↓
Complete message
```

For example:

```text
Yesterday:
100 ms/message

Today:
2 sec/message
```

Queue depth can rise dramatically even if the number of consumers has not changed.

Potential causes include:

* slow database queries
* downstream API latency
* connection pool exhaustion
* locks/contention
* CPU or memory pressure
* throttled dependencies

---

### **5. Check retries and message settlement**

A particularly important symptom is:

```text
Consumers look busy
but queue depth does not decrease
```

I would check whether messages are repeatedly:

* abandoned
* timing out
* losing locks
* throwing exceptions
* being redelivered

For example:

```text
Receive
  ↓
Process for 90 sec
  ↓
60-sec lock expires
  ↓
Complete fails
  ↓
Message redelivered
```

The application may appear to process lots of messages while making almost no progress.

I would inspect:

* delivery count
* lock-lost exceptions
* processing duration
* lock renewal behavior

---

### **6. Check the DLQ separately**

If active queue depth decreases but DLQ depth increases:

```text
Main queue
    ↓
Failure/retries
    ↓
DLQ ↑↑↑
```

the issue is not solved—it has simply moved.

I would inspect:

* dead-letter reason
* malformed payloads
* application exceptions
* max delivery count

---

### **7. Look for poison messages or ordered-session bottlenecks**

If sessions are enabled:

```text
Session A → slow/stuck
Session B → healthy
Session C → healthy
```

a problematic session can become a localized bottleneck.

I would inspect whether:

* one `SessionId` dominates traffic
* a session lock is repeatedly lost
* one business entity has huge message volume

Similarly, a poison message that repeatedly consumes processing time can reduce throughput.

---

### **8. Check broker and dependency limits**

Finally, I would verify whether the issue is caused by limits or throttling involving:

* Service Bus tier/capacity
* connection limits
* concurrent receiver configuration
* message size
* downstream database quotas
* API rate limits

I would not immediately increase Service Bus capacity if the real bottleneck is:

```text
Database
or
External API
```

because additional consumers could actually make that dependency fail harder.

### **Production remediation**

The fix depends on the bottleneck:

```text
Not enough consumers
→ scale consumers

Slow dependency
→ optimize/protect dependency

Lock expiry
→ renew locks / shorten work

Poison messages
→ DLQ

Traffic burst
→ KEDA autoscaling

Producer overload
→ throttling/backpressure if required
```

### **Interview answer condensed**

> “A continuously increasing queue means arrival rate is exceeding successful completion rate. I’d first compare incoming versus completed messages and oldest-message age, then check whether consumers are running and whether their throughput has dropped. Next I’d investigate processing latency, downstream dependencies, retries, lock-expiry/redelivery, DLQ growth, and Service Bus throttling. If the workload is bursty and consumers run on AKS, I’d consider KEDA scaling based on queue depth, but only after confirming the downstream systems can handle the additional concurrency.”

**Memory line:**
**Queue growing = producers are outrunning successful consumers; find why before blindly scaling.**

**Interview trap:**
Do not automatically add consumer replicas. If the bottleneck is a database or rate-limited API, more consumers may make the outage worse.

**Keywords:**
Queue depth, ingress rate, processing rate, oldest message age, KEDA, lock expiry, redelivery, DLQ, backpressure.

**Likely follow-ups:**

* How would KEDA scale Service Bus consumers?
* What metric is better: queue depth or oldest-message age?
* What if consumers are CPU-idle but the queue keeps growing?
* What happens if you scale consumers beyond database capacity?

### **T24-E01. What is Git?**

**Answer:**
Git is a **distributed version-control system** used to track changes to source code and other text-based files. It lets developers maintain history, create branches, collaborate safely, compare changes, and return to earlier versions.

### **How it works**

Each Git repository contains a history of commits:

```text
Commit A
   ↓
Commit B
   ↓
Commit C
   ↓
Commit D
```

A developer can work on a branch without immediately affecting the main branch:

```text
main
A ── B ── C
         \
          D ── E
          feature
```

Once the feature is reviewed, it can be merged through a pull request.

### **DevOps example**

A common infrastructure workflow is:

```text
Terraform change
      ↓
Git branch
      ↓
Pull request
      ↓
CI validation / terraform plan
      ↓
Review
      ↓
Merge to main
      ↓
Deployment pipeline
```

Git therefore provides the source-of-truth history behind many CI/CD and GitOps workflows.

### **Important distinction**

Git is the **version-control technology**.

GitHub, Azure Repos, and GitLab are platforms that can **host Git repositories** and add collaboration features such as:

* pull requests
* permissions
* CI/CD
* issue tracking

**Memory line:**
**Git tracks file history and lets teams safely develop changes in parallel.**

**Interview trap:**
Do not say Git and GitHub are the same thing. Git is the VCS; GitHub is a hosting/collaboration platform built around Git.

**Keywords:**
Distributed version control, repository, commit, branch, merge, history.

### **T24-E02. What is a commit?**

**Answer:**
A Git commit is a **recorded snapshot of changes in a repository at a specific point in history**. Each commit has metadata such as an author, timestamp, commit message, and a unique identifier, and it normally references one or more parent commits.

### **How it works**

A simple history looks like:

```text
A ── B ── C ── D
```

Each letter represents a commit.

For example:

```text
A → initial application
B → add Dockerfile
C → add Kubernetes manifests
D → update deployment replicas
```

A commit records the repository state associated with that change.

### **Typical command**

```bash
git add deployment.yaml
git commit -m "Increase API replica count"
```

`git add` stages the desired change, and `git commit` records the staged snapshot into Git history.

### **Why good commits matter**

A useful commit should generally represent one logical change:

```text
Good:
"Add health probe to API deployment"

Less useful:
"changes"
```

Clear, focused commits make:

* reviews easier
* troubleshooting easier
* `git bisect` more useful
* reverting safer
* history easier to understand

### **Important distinction**

A commit is **local by default**.

```text
git commit
```

records the change in your local Git repository.

```text
git push
```

sends commits to a remote repository such as GitHub or Azure Repos.

**Memory line:**
**A commit is a named point in Git history representing a recorded repository snapshot.**

**Interview trap:**
Do not say `git commit` automatically uploads code to GitHub; pushing is a separate action.

**Keywords:**
Commit, snapshot, staging area, commit hash, parent commit, commit message.
