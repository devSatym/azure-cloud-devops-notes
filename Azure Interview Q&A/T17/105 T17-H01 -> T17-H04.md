### **T17-H01. How would you design redundant connectivity between an on-premises data center and Azure?**

**Answer:**
For production, I would avoid making a **single VPN tunnel, single router, single ExpressRoute circuit, or single Azure gateway** the only hybrid path. The design depends on the required SLA, bandwidth, and budget, but for an important enterprise workload I would typically use **redundant ExpressRoute connectivity as the primary path**, with geographically/provider-diverse circuits for high resilience, and optionally a **site-to-site VPN as an independent backup path**.

Microsoft's current guidance recommends geo-redundant ExpressRoute circuits across different peering locations for the strongest resilience; S2S VPN can be used as backup when its lower bandwidth and less predictable performance are acceptable during failover. ([Microsoft Learn][1])

### **Production architecture**

```text
                       ON-PREMISES
                  ┌─────────────────┐
                  │ Application LAN │
                  └────────┬────────┘
                           │
                 ┌─────────┴─────────┐
                 ↓                   ↓
             Router A             Router B
                 │                   │
        ┌────────┘                   └────────┐
        ↓                                     ↓
 ExpressRoute Circuit 1              ExpressRoute Circuit 2
 Peering Location A                  Peering Location B
        │                                     │
        └───────────────┬─────────────────────┘
                        ↓
                 Microsoft network
                        ↓
             Zone-redundant ER Gateway
                        ↓
                       Hub
                        ↓
                    Azure VNets

Backup path:
On-prem VPN devices
        ↓
Internet / IPsec
        ↓
Azure VPN Gateway
        ↓
Hub
```

---

### **1. Eliminate the on-premises single point of failure**

I would use at least:

```text
Router A
+
Router B
```

preferably connected through:

```text
independent physical paths
independent provider equipment
independent power/network infrastructure
```

Otherwise:

```text
2 Azure circuits
+
1 on-prem router
=
still one failure domain
```

---

### **2. Understand ExpressRoute's built-in redundancy**

One ExpressRoute circuit already provides two redundant connections/BGP sessions toward Microsoft's edge.

Conceptually:

```text
Customer/provider edge
      │       │
      ↓       ↓
    MSEE-1  MSEE-2
```

Microsoft operates those paths active-active. ([Microsoft Learn][2])

But this only protects against failures **inside one peering-location design**.

It does not completely protect against:

```text
peering-location outage
provider outage
metro-level failure
regional disaster
```

---

### **3. For mission-critical connectivity, use two ExpressRoute circuits**

I would terminate them at:

```text
different peering locations
```

and ideally use:

```text
different connectivity providers
```

where practical.

Example:

```text
Data Center
   │
   ├── ER Circuit A → Provider A → Peering Location A
   │
   └── ER Circuit B → Provider B → Peering Location B
```

Microsoft specifically recommends circuits across different peering locations—and provider diversity where possible—for stronger disaster resilience. ([Microsoft Learn][1])

---

### **4. Use zone-redundant ExpressRoute gateways**

Inside Azure, I would use an Availability Zone-enabled ExpressRoute gateway SKU where supported:

```text
ErGw*AZ
```

Conceptually:

```text
ExpressRoute circuits
        ↓
Zone-redundant
ExpressRoute Gateway
   /      |      \
Zone 1  Zone 2  Zone 3
        ↓
      Hub VNet
```

This protects the Azure gateway layer against a single-zone failure. ([Microsoft Learn][1])

---

### **5. For regional DR, one regional gateway isn't enough**

This is an important advanced point.

Even if I have:

```text
dual providers
dual circuits
dual Microsoft edge paths
```

if everything ultimately terminates through:

```text
one Azure regional VNet gateway
```

that region remains part of the failure domain.

For workloads requiring **regional connectivity resilience**, I would design:

```text
Primary Azure Region
├── Hub VNet
└── ER Gateway

Secondary Azure Region
├── Hub VNet
└── ER Gateway
```

with appropriately geo-redundant ExpressRoute connectivity. Microsoft explicitly notes that end-to-end regional resilience requires connectivity into a second Azure region as well. ([Microsoft Learn][2])

---

### **6. Optionally add S2S VPN as a separate backup**

Architecture:

```text
             On-premises
                 │
        ┌────────┴────────┐
        ↓                 ↓
 ExpressRoute          S2S VPN
   PRIMARY             BACKUP
        ↓                 ↓
        └────── Azure ────┘
```

When both advertise the same prefix, Azure normally prefers the ExpressRoute path, while longest-prefix-match still matters. I would also configure the on-premises routers to prefer the ExpressRoute-learned routes so both directions behave consistently. ([Microsoft Learn][3])

---

### **7. Don't use VPN backup blindly**

S2S VPN is excellent as a backup when an application can temporarily tolerate:

```text
lower bandwidth
higher latency
less predictable internet transport
```

But Microsoft explicitly advises against relying on a VPN backup as the sole resilience mechanism for workloads that are:

```text
latency-sensitive
mission-critical
bandwidth-intensive
```

For those, use **multi-site ExpressRoute resiliency**. ([Microsoft Learn][3])

---

### **8. Use BGP for automatic failover**

I would dynamically advertise equivalent prefixes over the available connectivity paths.

Normal:

```text
On-prem
   ↓
ExpressRoute route preferred
   ↓
Azure
```

Failure:

```text
ExpressRoute routes withdrawn
          ↓
BGP reconverges
          ↓
VPN / secondary ER route selected
```

If using dual ExpressRoute paths, I can influence preferences using routing policy on the customer side.

---

### **9. Prevent asymmetric routing**

A bad state is:

```text
On-prem → Azure
via ExpressRoute

Azure → On-prem
via VPN
```

Stateful firewalls can break this.

So I verify route advertisements and preferences in **both directions**.

For example:

```text
ER routes
→ higher local preference on-prem

VPN routes
→ lower preference
```

while ensuring Azure sees equivalent prefixes unless a more-specific route is intentional. Microsoft calls this out directly in its ExpressRoute-with-VPN failover design. ([Microsoft Learn][3])

---

### **10. Test failover before calling it redundant**

I would run controlled tests:

```text
Normal traffic
      ↓
Confirm ER path

Disable primary ER path
      ↓
Measure BGP convergence
      ↓
Confirm secondary ER/VPN

Restore path
      ↓
Confirm traffic returns as designed
```

I would capture:

```text
RTO / convergence time
packet loss
latency
route tables
BGP state
application impact
```

A backup that has never been tested is only theoretical redundancy.

> **In an interview, I would say:**
> “For critical hybrid connectivity, I would remove failure domains end to end: redundant on-prem routers, redundant provider paths, dual ExpressRoute circuits through different peering locations, ideally different providers, and zone-redundant ExpressRoute gateways. If the business can tolerate VPN performance during an outage, I can also use a route-based S2S VPN as an independent backup. BGP handles dynamic route withdrawal and failover, but I configure route preferences in both directions to avoid asymmetric routing. For regional disaster resilience I also need connectivity into a second Azure region, and I regularly test failover rather than assuming redundancy works.”

**Memory line:**
**Hybrid HA means redundant path end-to-end—not merely two tunnels terminating on the same failure point.**

**Interview trap:**
A single ExpressRoute circuit has built-in redundancy, but it does **not** eliminate peering-location, provider, or regional failure risk.

**Keywords:**
ExpressRoute, dual circuits, peering locations, provider diversity, zone-redundant gateway, S2S failover, BGP

**Likely follow-ups:**

* Why use two ExpressRoute circuits if one already has two connections?
* When is VPN backup not sufficient?
* How do you make ExpressRoute and VPN failover automatically?
* How would you avoid asymmetric routing?

### **T17-H02. How would you route traffic between on-premises networks and multiple Azure spokes?**

**Answer:**
I would normally build a **hub-and-spoke topology**, terminate the VPN or ExpressRoute gateway in the **hub**, and enable **gateway transit** so the spokes can reuse that central hybrid gateway instead of deploying a separate gateway in every spoke.

On hub-to-spoke peering:

```text
Allow gateway transit = Enabled
```

On spoke-to-hub peering:

```text
Use remote gateways = Enabled
```

This allows the spokes to learn on-premises routes through the hub gateway, while their prefixes can be advertised back toward on-premises. ([Microsoft Learn][4])

### **Architecture**

```text
                    ON-PREMISES
                         │
                 VPN / ExpressRoute
                         │
                         ↓
                ┌────────────────┐
                │    HUB VNet    │
                │                │
                │ VPN / ER GW    │
                │ Azure Firewall │
                └───────┬────────┘
                        │
           ┌────────────┼────────────┐
           ↓            ↓            ↓
        Spoke A       Spoke B      Spoke C
      10.1.0.0/16   10.2.0.0/16  10.3.0.0/16
```

---

### **1. Put the hybrid gateway in the hub**

Instead of:

```text
Spoke A → VPN Gateway
Spoke B → VPN Gateway
Spoke C → VPN Gateway
```

I use:

```text
Hub
└── GatewaySubnet
    └── VPN/ExpressRoute Gateway
```

This centralizes:

```text
hybrid connectivity
BGP
routing
security controls
cost
operations
```

---

### **2. Configure gateway transit**

Hub-side peering:

```text
Hub → Spoke
Allow gateway transit = true
```

Spoke-side:

```text
Spoke → Hub
Use remote gateways = true
```

Then:

```text
Spoke A
   ↓
Hub remote gateway
   ↓
On-prem prefixes
```

Microsoft documents gateway transit precisely for sharing a hub VPN/ExpressRoute gateway across spokes. ([Microsoft Learn][4])

---

### **3. Route propagation gives spokes on-prem routes**

Suppose on-prem advertises:

```text
192.168.0.0/16
```

through BGP.

After gateway transit:

```text
Spoke A effective routes

192.168.0.0/16
→ hub/gateway path
```

and similarly for other spokes.

I would verify this using the spoke VM/NIC's **effective routes**, not merely assume route propagation occurred. ([Microsoft Learn][4])

---

### **4. Advertise spoke prefixes toward on-prem**

Suppose:

```text
Spoke A = 10.1.0.0/16
Spoke B = 10.2.0.0/16
Spoke C = 10.3.0.0/16
```

The hub gateway can advertise these Azure prefixes through BGP to on-premises when gateway transit is correctly configured.

Then on-prem learns:

```text
10.1.0.0/16
10.2.0.0/16
10.3.0.0/16
        ↓
Azure hybrid connection
```

---

### **5. If traffic must be inspected, route through Azure Firewall/NVA**

A more controlled architecture:

```text
On-prem
   ↓
Gateway
   ↓
Azure Firewall
   ↓
Spoke
```

and reverse:

```text
Spoke
   ↓
Azure Firewall
   ↓
Gateway
   ↓
On-prem
```

Now I need UDRs.

For example:

```text
Spoke route:
192.168.0.0/16
→ next hop Azure Firewall
```

and the gateway path may require routes for the exact spoke prefixes pointing toward the firewall.

---

### **6. Longest-prefix-match can surprise you**

Suppose:

```text
GatewaySubnet UDR:
10.0.0.0/8
→ Firewall
```

but VNet peering injects:

```text
10.1.0.0/16
→ Spoke A
```

The `/16` is more specific than `/8`, so Azure prefers it.

Result:

```text
Gateway
→ direct spoke
```

instead of:

```text
Gateway
→ Firewall
→ Spoke
```

Microsoft's current Azure Firewall hub/spoke guidance explicitly warns that broad summary routes don't override more-specific peering routes; exact spoke prefixes may be required. ([Microsoft Learn][5])

---

### **7. Gateway route propagation can bypass a firewall**

Another subtle failure:

Spoke has:

```text
0.0.0.0/0
→ Azure Firewall
```

but gateway transit injects:

```text
192.168.0.0/16
→ VPN/ExpressRoute gateway
```

Since:

```text
/16 > /0
```

traffic to on-prem bypasses the firewall.

If the requirement is:

```text
ALL spoke → on-prem
must traverse firewall
```

I may need to manage route propagation and explicitly route those prefixes through the firewall.

Microsoft calls out this exact interaction in its multi-hub/firewall guidance. ([Microsoft Learn][5])

---

### **8. Think about both directions**

I always sketch:

```text
On-prem → Spoke
```

and separately:

```text
Spoke → On-prem
```

because one direction working does not guarantee the reverse direction.

Example failure:

```text
On-prem
→ Azure Gateway
→ Firewall
→ Spoke
✓

Spoke
→ directly Gateway
→ On-prem
✗ stateful firewall asymmetry
```

---

### **9. Avoid overlapping address spaces**

Hub-and-spoke hybrid routing becomes painful if:

```text
On-prem
192.168.0.0/16

Spoke
192.168.10.0/24
```

overlap.

I plan distinct ranges such as:

```text
On-prem:
172.16.0.0/12

Hub:
10.0.0.0/16

Spoke A:
10.1.0.0/16

Spoke B:
10.2.0.0/16
```

because BGP and normal routing require unambiguous prefixes.

---

### **10. Verify with effective routes**

From a VM in Spoke A I want something conceptually like:

```text
Destination          Next hop

192.168.0.0/16       hub gateway/firewall path
10.2.0.0/16          peering/firewall as designed
0.0.0.0/0            firewall/NAT as designed
```

Tools:

```text
Effective routes
Network Watcher Next Hop
Connection Troubleshoot
Azure Firewall logs
BGP learned/advertised routes
```

> **In an interview, I would say:**
> “I would terminate ExpressRoute or VPN connectivity in a central hub and use VNet peering gateway transit. On the hub-to-spoke peering I enable Allow gateway transit, and on the spoke side I enable Use remote gateways. This propagates the on-premises routes into the spokes and allows spoke prefixes to be advertised toward on-premises. If security policy requires Azure Firewall inspection, I add explicit UDRs and validate both forward and return paths. I pay close attention to longest-prefix matching and gateway-route propagation because they can cause traffic to bypass the firewall. I verify the final design using effective routes rather than relying only on the configured route tables.”

**Memory line:**
**Hub gateway + gateway transit = one hybrid gateway shared by many spokes.**

**Interview trap:**
A `0.0.0.0/0 → Firewall` route does **not** automatically force on-prem traffic through the firewall if more-specific BGP routes are being propagated.

**Keywords:**
Hub-and-spoke, gateway transit, Use Remote Gateways, BGP propagation, UDR, Azure Firewall, longest prefix match

**Likely follow-ups:**

* What does `Allow gateway transit` do?
* Why might a spoke bypass Azure Firewall?
* How would you force on-prem-to-spoke traffic through the firewall?
* Can every spoke deploy its own gateway while using the remote gateway?

### **T17-H03. How would you troubleshoot an Azure VPN tunnel that shows connected but carries no traffic?**

**Answer:**
`Connected` tells me that the **IKE/IPsec tunnel has been established**, but it does not prove that the correct routes exist or that application packets are allowed through. I would troubleshoot from the exact source to destination in this order:

```text
Tunnel state
   ↓
IP prefixes / traffic selectors
   ↓
Routes / BGP
   ↓
NSG / firewall
   ↓
Return route
   ↓
Application port
```

For BGP-based VPNs, Microsoft explicitly notes that the IPsec tunnel can be connected while BGP routes are absent or incorrectly advertised. ([Microsoft Learn][6])

---

### **1. Define the exact flow**

Not:

> “VPN isn't working.”

But:

```text
Source:
192.168.10.25

Destination:
10.20.2.10

Protocol:
TCP

Port:
443
```

Then investigate that exact path.

---

### **2. Verify tunnel state**

Azure connection:

```text
Status = Connected
```

This proves approximately:

```text
IKE negotiation ✓
IPsec SA established ✓
```

It does **not** prove:

```text
route exists ✗/?
NSG permits ✗/?
application listens ✗/?
return path works ✗/?
```

---

### **3. Check prefixes on both sides**

Suppose Azure thinks on-prem is:

```text
192.168.0.0/16
```

but actual source is:

```text
172.20.10.5
```

then:

```text
VPN = Connected
Traffic = no matching route
```

Likewise, verify the on-prem VPN device knows the Azure prefixes:

```text
10.20.0.0/16
```

A typo in a Local Network Gateway prefix can leave the tunnel up while traffic goes nowhere.

---

### **4. If using BGP, check the BGP session separately**

Architecture:

```text
IPsec tunnel
    ↓
BGP session
    ↓
route exchange
```

So:

```text
Tunnel = Connected
BGP = Disconnected
```

is completely possible.

Microsoft explicitly says BGP runs **on top of** the IPsec tunnel. ([Microsoft Learn][6])

Check:

```text
Virtual network gateway
→ Monitoring
→ BGP peers
```

Healthy:

```text
State = Connected
Routes received > 0
```

---

### **5. Inspect learned routes**

For Azure:

```powershell
Get-AzVirtualNetworkGatewayLearnedRoute ...
```

I look for the on-prem prefix:

```text
192.168.10.0/24
Origin: EBgp
```

If missing:

```text
Azure doesn't know
how to return to on-prem
```

Microsoft specifically recommends checking learned route counts and verifying that the on-prem BGP device is actually advertising the expected networks. ([Microsoft Learn][6])

---

### **6. Inspect advertised routes**

I also verify what Azure sends to the on-prem router:

```powershell
Get-AzVirtualNetworkGatewayAdvertisedRoute ...
```

Expected:

```text
10.20.0.0/16
```

If Azure advertises it but the on-prem router doesn't install it:

```text
on-prem BGP filter
routing policy
route preference
```

may be responsible. ([Microsoft Learn][6])

---

### **7. Check effective routes on the Azure workload**

For:

```text
Azure VM
10.20.2.10
```

I inspect effective routes.

I expect:

```text
192.168.10.0/24
→ VirtualNetworkGateway
```

But perhaps a UDR says:

```text
192.168.10.0/24
→ Virtual Appliance
10.20.0.4
```

Then the VPN is fine—the workload is sending traffic somewhere else.

---

### **8. Check NSGs**

Tunnel connectivity does not bypass:

```text
NSG
```

Example:

```text
On-prem
192.168.10.25
      ↓
VPN
      ↓
VM subnet NSG
      ↓
Deny TCP/443
```

Tunnel:

```text
Connected ✓
```

Application:

```text
Fails ✗
```

I inspect:

```text
Effective security rules
Network Watcher IP Flow Verify
```

when applicable.

---

### **9. Check Azure Firewall/NVA**

Maybe path is:

```text
On-prem
   ↓
VPN Gateway
   ↓
Azure Firewall
   ↓
VM
```

Then I check firewall logs for:

```text
source
destination
port
action
timestamp
```

For example:

```text
192.168.10.25
→ 10.20.2.10:443
DENY
```

The VPN itself has nothing to fix.

---

### **10. Check the on-prem firewall**

The opposite direction matters too.

Maybe:

```text
Azure → on-prem
```

leaves Azure successfully but gets blocked by:

```text
corporate firewall
host firewall
ACL
```

I inspect both devices where possible.

---

### **11. Test the actual application port**

Use:

```bash
nc -vz 10.20.2.10 443
```

or:

```bash
curl -vk https://10.20.2.10
```

depending on the workload.

Interpretation:

```text
timeout
→ route/firewall/path

connection refused
→ destination reached,
  service not listening

HTTP 401/403
→ network works,
  move to application/auth
```

---

### **12. Check return routing**

This is one of the biggest hybrid issues.

Forward:

```text
On-prem
→ VPN
→ Azure VM
```

Return:

```text
Azure VM
→ 0.0.0.0/0
→ Azure Firewall
→ Internet
```

The return packet never comes back through VPN.

Result:

```text
request reaches server
client still times out
```

So I always prove:

```text
source → destination
AND
destination → source
```

---

### **13. Use VPN Gateway diagnostic logs**

Microsoft exposes several useful log categories:

```text
GatewayDiagnosticLog
TunnelDiagnosticLog
RouteDiagnosticLog
IKEDiagnosticLog
```

`RouteDiagnosticLog` is especially useful for:

```text
BgpRouteUpdate
BgpConnectedEvent
BgpDisconnectedEvent
```

while `IKEDiagnosticLog` helps with IKE/IPsec details. ([Microsoft Learn][7])

---

### **Troubleshooting tree**

```text
VPN says Connected
       ↓
Exact source/destination?
       ↓
Correct prefixes?
       ↓
BGP used?
  /           \
Yes            No
 ↓              ↓
BGP up?      static routes
routes?      correct?
       \      /
        ↓    ↓
Effective route
       ↓
NSG/firewall
       ↓
Return route
       ↓
Application
```

> **In an interview, I would say:**
> “A Connected VPN only proves that the IPsec tunnel is established. I first define the exact source, destination, protocol, and port. Then I verify the local and Azure network prefixes and, if BGP is enabled, independently verify the BGP peer state plus learned and advertised routes. On the Azure VM I inspect effective routes and NSG rules, then any Azure Firewall or NVA in the path. I test the destination port and finally verify the return path because asymmetric routing is a common reason a connected tunnel carries no usable application traffic. I also use VPN Gateway Route, Tunnel, and IKE diagnostic logs rather than repeatedly resetting the tunnel.”

**Memory line:**
**VPN connected ≠ routes correct; prove route, policy, and return path.**

**Interview trap:**
Do not restart the gateway as the first response to a `Connected but no traffic` incident.

**Keywords:**
IPsec, BGP, learned routes, advertised routes, effective routes, NSG, RouteDiagnosticLog, asymmetric routing

**Likely follow-ups:**

* Can BGP be down while the VPN tunnel is up?
* What if only one direction works?
* What logs would you enable?
* What does `connection refused` prove compared with a timeout?

### **T17-H04. What would you investigate if ExpressRoute connectivity worked for some prefixes but not others?**

**Answer:**
If ExpressRoute works for some networks but not others, I would **not start by blaming the circuit itself**, because successful connectivity to any prefix already proves a large part of the physical circuit and peering path works. I would investigate the **BGP route advertisements, learned routes, filters/policies, prefix limits, route specificity, Azure UDRs, and return path for the missing prefix**.

Microsoft's current ExpressRoute troubleshooting guidance specifically recommends validating BGP session state, route tables, advertised prefixes, traffic direction, and return-path routing. ([Microsoft Learn][8])

### **Example**

Works:

```text
On-prem
192.168.10.0/24
       ↓
ExpressRoute
       ↓
Azure
10.1.0.0/16
✓
```

Fails:

```text
On-prem
192.168.20.0/24
       ↓
ExpressRoute
       ↓
Azure
10.2.0.0/16
✗
```

Since the same circuit carries some traffic successfully, I immediately compare:

```text
10.1.0.0/16
vs
10.2.0.0/16
```

---

### **1. Verify whether the missing prefix is actually advertised**

On the relevant BGP session, I ask:

```text
Is 10.2.0.0/16 advertised?
```

Maybe:

```text
10.1.0.0/16 ✓
10.2.0.0/16 ✗
```

Then the problem isn't physical ExpressRoute connectivity.

It's:

```text
route advertisement
```

---

### **2. Check Azure-side and on-prem BGP tables**

There are two different questions:

```text
Was the prefix advertised?
```

and:

```text
Was the prefix accepted/installed?
```

Example:

```text
Azure advertises
10.2.0.0/16
        ↓
On-prem router receives it
        ↓
routing policy rejects it
```

So I check:

```text
BGP advertised table
BGP received table
actual routing table
```

A route can exist in the BGP database without being selected as the forwarding route.

---

### **3. Check route filters / prefix lists**

On-prem equipment may have something like:

```text
permit 10.1.0.0/16
deny everything else
```

Then adding:

```text
10.2.0.0/16
```

in Azure won't magically make the corporate router accept it.

I inspect:

```text
prefix lists
route maps
import filters
export filters
BGP communities/policy
```

---

### **4. Check route specificity**

Suppose ExpressRoute provides:

```text
10.0.0.0/8
→ ExpressRoute
```

but a UDR provides:

```text
10.2.0.0/16
→ Azure Firewall
```

For destination `10.2.x.x`:

```text
/16
beats
/8
```

So traffic follows the UDR.

Likewise, Azure may prefer a more-specific prefix learned through another network path.

Always apply:

```text
Longest prefix match first
```

before assuming route-source preference.

---

### **5. Check effective routes on the affected Azure resource**

Example working VM:

```text
10.1.1.5
```

failing VM:

```text
10.2.1.5
```

Compare their effective routes.

Maybe:

```text
Spoke A
on-prem prefix
→ ExpressRoute

Spoke B
on-prem prefix
→ Azure Firewall
```

or perhaps Spoke B simply doesn't receive the gateway route because:

```text
Use remote gateways = false
```

---

### **6. Check hub/spoke gateway-transit configuration**

If one spoke works but another doesn't:

```text
Hub
├── Spoke A ✓
└── Spoke B ✗
```

I check Spoke B peering:

```text
Hub side:
Allow gateway transit?

Spoke side:
Use remote gateways?
```

One missing checkbox can produce:

```text
ER works for one prefix
but not another
```

while the circuit itself remains healthy.

---

### **7. Check ExpressRoute route/prefix limits**

Another possibility is that a routing limit is being reached.

Current ExpressRoute private-peering prefix limits depend on circuit/SKU configuration; Microsoft documents higher limits with ExpressRoute Premium, and BGP sessions can be impacted if supported limits are exceeded. ([Microsoft Learn][9])

So if:

```text
first N routes work
new routes missing
```

I inspect:

```text
prefix count
circuit SKU
route summarization opportunities
BGP session health
```

rather than assuming an Azure subnet failure.

---

### **8. Verify route summarization**

Instead of advertising:

```text
10.1.1.0/24
10.1.2.0/24
10.1.3.0/24
...
```

I may be able to advertise:

```text
10.1.0.0/16
```

provided the summarized address space is genuinely owned/reachable through that path.

This reduces route-table pressure.

But incorrect summarization can black-hole traffic, so it must reflect real reachability.

---

### **9. Check the return path**

Suppose on-prem can send:

```text
192.168.1.5
→ 10.2.1.10
```

through ExpressRoute.

But Azure VM `10.2.1.10` has:

```text
192.168.0.0/16
→ Azure Firewall
```

rather than:

```text
→ ExpressRoute Gateway
```

Then:

```text
forward path = ER
return path  = firewall/other path
```

and the session can fail.

Microsoft's ExpressRoute troubleshooting guidance specifically interprets one-way test results as evidence of return-route problems and recommends checking advertised prefixes and UDR overrides. ([Microsoft Learn][8])

---

### **10. Compare working vs failing prefix**

This is often the fastest technique.

```text
                  WORKING            FAILING

Azure VNet        10.1.0.0/16        10.2.0.0/16
Advertised?       yes                ?
On-prem learned?  yes                ?
Route installed?  yes                ?
Gateway transit?  yes                ?
UDR?              none               ?
NSG?              allowed            ?
Return route?     ER                 ?
```

Find the **first difference**.

---

### **11. Check both ExpressRoute paths/MSEEs**

An ExpressRoute circuit has redundant Microsoft edge paths.

If traffic works inconsistently, Microsoft troubleshooting guidance suggests verifying traffic and route state on both MSEE paths; one path may be unhealthy even if the other is working. ([Microsoft Learn][8])

Conceptually:

```text
             ExpressRoute Circuit
                /            \
             MSEE1          MSEE2
              ✓               ✗
```

This can create intermittent or path-specific symptoms.

---

### **12. Use layered troubleshooting**

My order:

```text
Circuit provisioned?
       ↓
Private peering up?
       ↓
BGP sessions up?
       ↓
Missing prefix advertised?
       ↓
Remote side receives prefix?
       ↓
Route installed/preferred?
       ↓
Azure effective route?
       ↓
NSG/firewall?
       ↓
Return path?
```

I only escalate to:

```text
connectivity provider
or
Microsoft
```

after identifying which network zone is failing:

```text
Customer network
Provider network
Microsoft network
```

Microsoft uses this same three-zone model in its ExpressRoute troubleshooting guidance. ([Microsoft Learn][10])

> **In an interview, I would say:**
> “If ExpressRoute works for some prefixes, I assume the circuit itself is at least partially healthy and compare a working and failing network. I first verify whether the failing prefix is actually advertised through BGP, whether the other side receives it, and whether it is installed in the routing table rather than rejected by a prefix list or route map. Then I check longest-prefix matching, UDRs, hub-spoke gateway transit, and effective routes on the affected Azure workload. I also verify the return route because ExpressRoute can appear one-way if a UDR or firewall sends responses through a different path. If route counts are large, I check ExpressRoute prefix limits and summarization. Finally I compare both redundant MSEE paths and involve the provider or Microsoft only after identifying which network zone is failing.”

**Memory line:**
**Some ER prefixes work = compare route advertisement, acceptance, preference, and return path—not the whole circuit first.**

**Interview trap:**
`BGP session = Established` does **not** guarantee every desired prefix is being advertised, accepted, or selected.

**Keywords:**
ExpressRoute, advertised routes, learned routes, prefix list, BGP, UDR, longest prefix match, return path, MSEE

**Likely follow-ups:**

* What if the prefix appears in BGP but not the routing table?
* How can a UDR override an ExpressRoute path?
* What happens if prefix limits are exceeded?
* How would you identify whether the provider or Microsoft side is failing?
