### **T17-M03. What is BGP?**

**Answer:**  
**BGP — Border Gateway Protocol — is a dynamic routing protocol used to exchange network reachability information between different networks or autonomous systems.** In Azure hybrid networking, BGP lets Azure VPN Gateway, ExpressRoute, and on-premises routers **advertise and learn IP prefixes automatically instead of relying only on manually maintained static routes**. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/vpn-gateway/bgp-howto?utm_source=chatgpt.com "Configure BGP for VPN Gateway: Portal - Azure VPN Gateway | Microsoft Learn"))

### **Simple example**

Suppose:

```text
On-premises
192.168.0.0/16
      │
      │ BGP
      ↓
Azure VPN Gateway
      │
      ↓
Azure VNet
10.20.0.0/16
```

The on-prem router advertises:

```text
192.168.0.0/16
```

Azure advertises:

```text
10.20.0.0/16
```

Both routers then learn:

```text
To reach 192.168.0.0/16
→ go toward on-prem

To reach 10.20.0.0/16
→ go toward Azure
```

That routing information is exchanged dynamically. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/vpn-gateway/bgp-howto?utm_source=chatgpt.com "Configure BGP for VPN Gateway: Portal - Azure VPN Gateway | Microsoft Learn"))

---

### **BGP peers**

Routers exchanging BGP routes are called:

```text
BGP peers
or
BGP neighbors
```

For example:

```text
Azure VPN Gateway
      ↕ BGP session
On-prem VPN device
```

Each side has information such as:

```text
ASN
BGP peer IP
advertised prefixes
learned prefixes
```

---

### **What is an ASN?**

**ASN = Autonomous System Number.**

It identifies a routing domain participating in BGP.

Conceptually:

```text
On-prem network
ASN 65010

      ↕ BGP

Azure VPN Gateway
ASN 65515
```

Azure VPN Gateway commonly uses:

```text
65515
```

as its default ASN. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-coexist-resource-manager?utm_source=chatgpt.com "Configure ExpressRoute and S2S VPN coexisting connections with Azure PowerShell | Microsoft Learn"))

---

### **Static routing vs BGP**

Without BGP:

```text
New subnet created
10.30.0.0/16
      ↓
administrator updates
routes manually
      ↓
multiple routers/firewalls
```

With BGP:

```text
New prefix
10.30.0.0/16
      ↓
advertised dynamically
      ↓
BGP peers learn route
```

So BGP becomes especially valuable when the network grows.

---

### **BGP doesn't carry application traffic**

This is an important distinction.

BGP primarily exchanges:

```text
routing/reachability information
```

It tells routers:

> “Which path should I use to reach this prefix?”

Actual application traffic then follows the learned routes.

---

### **Strong interview answer**

> “BGP, or Border Gateway Protocol, is a dynamic routing protocol that exchanges reachability information between networks. In Azure I commonly see it with VPN Gateway and ExpressRoute. Azure and the on-premises router become BGP peers and advertise prefixes to each other, so routes can be learned and updated dynamically rather than being manually maintained. Each BGP routing domain is identified by an ASN.”

**Memory line:**  
**BGP dynamically tells networks which prefixes are reachable through which routers.**

**Interview trap:**  
Do not describe BGP as a VPN or encryption protocol. It is a **routing protocol**.

**Keywords:**  
BGP, ASN, peer, neighbor, route advertisement, learned routes, prefixes

**Likely follow-ups:**

- What is an ASN?
    
- Why use BGP instead of static routes?
    
- Does Azure VPN Gateway support BGP?
    
- How does ExpressRoute use BGP?

### **T17-M04. Why is BGP useful with Azure networking?**

**Answer:**  
BGP is useful in Azure because it allows **dynamic route exchange between Azure and external or connected networks**. Instead of manually adding routes whenever a subnet, branch, or network path changes, routers can advertise those prefixes automatically. It also enables more sophisticated hybrid designs involving **multiple sites, redundant paths, ExpressRoute, VPN Gateway, and transit routing**. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/vpn-gateway/bgp-howto?utm_source=chatgpt.com "Configure BGP for VPN Gateway: Portal - Azure VPN Gateway | Microsoft Learn"))

### **Without BGP**

Imagine an organization has:

```text
Azure
├── 10.10.0.0/16
├── 10.20.0.0/16
└── 10.30.0.0/16
```

and on-premises:

```text
192.168.10.0/24
192.168.20.0/24
192.168.30.0/24
```

With static routing, administrators might need to maintain all these prefixes manually on both sides.

As networks grow:

```text
new branch
new VNet
new subnet
new DR environment
```

manual route management becomes increasingly error-prone.

---

### **With BGP**

```text
On-prem router
advertises
192.168.0.0/16
      ↓
BGP
      ↓
Azure VPN Gateway

Azure advertises
10.0.0.0/8 or specific prefixes
      ↓
BGP
      ↓
On-prem router
```

The peers dynamically learn routing changes. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/vpn-gateway/bgp-howto?utm_source=chatgpt.com "Configure BGP for VPN Gateway: Portal - Azure VPN Gateway | Microsoft Learn"))

---

### **1. Dynamic route propagation**

Suppose a new network becomes available:

```text
10.40.0.0/16
```

Rather than updating many route tables manually:

```text
BGP advertisement
      ↓
neighbor learns prefix
      ↓
routing table updates
```

This is one of BGP's biggest advantages.

---

### **2. Better redundancy**

Consider:

```text
             Azure
               │
        ┌──────┴──────┐
        ↓             ↓
     Path A         Path B
        ↓             ↓
            On-prem
```

BGP can advertise network reachability through both paths.

If one disappears:

```text
Path A fails
    ↓
routes withdrawn
    ↓
alternative route remains
    ↓
traffic moves to Path B
```

Actual failover behavior still depends on routing policy and convergence, but BGP provides the dynamic routing mechanism needed for this design.

---

### **3. Multiple on-premises locations**

Example:

```text
Branch A ─┐
Branch B ─┼── Azure VPN Gateway
Branch C ─┘
```

BGP helps Azure learn:

```text
Branch A → 192.168.10.0/24
Branch B → 192.168.20.0/24
Branch C → 192.168.30.0/24
```

without manually representing every network as a static route everywhere.

---

### **4. Transit routing**

Azure documentation notes that BGP can propagate routes learned from one peer to other peers, enabling certain transit-routing scenarios. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/vpn-gateway/bgp-howto?utm_source=chatgpt.com "Configure BGP for VPN Gateway: Portal - Azure VPN Gateway | Microsoft Learn"))

Conceptually:

```text
Site A
   ↓
BGP
   ↓
Azure Gateway
   ↓
BGP
   ↓
Site B
```

Whether the complete transit design is supported depends on the Azure services and topology, so I still verify the specific architecture.

---

### **5. ExpressRoute depends heavily on BGP**

ExpressRoute uses BGP to exchange routes between:

```text
Customer network
       ↕
Provider/Microsoft edge
       ↕
Azure
```

So for serious ExpressRoute troubleshooting, I immediately think about:

```text
BGP session state
advertised prefixes
learned prefixes
ASN
route filters/policies
```

not merely whether the circuit says `Provisioned`.

---

### **Strong interview answer**

> “BGP is valuable in Azure because it replaces large amounts of static route management with dynamic route exchange. Azure gateways and on-premises routers advertise their reachable prefixes, so route changes can propagate automatically. This is particularly useful for ExpressRoute, multi-site VPN, redundant hybrid links, and larger hub-and-spoke environments. It also supports failover because a failed route can be withdrawn and another learned path can become preferred.”

**Memory line:**  
**BGP makes hybrid routing dynamic, scalable, and better suited to redundant paths.**

**Interview trap:**  
BGP doesn't automatically make the network highly available. You still need **redundant physical/tunnel paths and correct routing policy**.

**Keywords:**  
Dynamic routing, route propagation, failover, ExpressRoute, hybrid networking, BGP peers

**Likely follow-ups:**

- How does BGP support failover?
    
- What happens when a BGP route is withdrawn?
    
- What would you inspect if BGP is up but traffic fails?
    
- Does BGP replace UDRs everywhere?

### **T17-M05. Can VPN Gateway and ExpressRoute coexist?**

**Answer:**  
**Yes. Azure supports ExpressRoute and a site-to-site VPN Gateway coexisting for the same VNet.** A common production pattern is to use **ExpressRoute as the primary hybrid path and site-to-site VPN as a backup path** if ExpressRoute becomes unavailable. VPN can also connect sites that aren't connected through ExpressRoute. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-coexist-resource-manager?utm_source=chatgpt.com "Configure ExpressRoute and S2S VPN coexisting connections with Azure PowerShell | Microsoft Learn"))

### **Typical design**

```text
                    Azure VNet
                        │
                 GatewaySubnet
                  /           \
                 /             \
 ExpressRoute Gateway       VPN Gateway
        ↑                       ↑
        │                       │
 ExpressRoute circuit       IPsec tunnel
        ↑                       ↑
        └────── On-premises ────┘
```

Normal operation:

```text
On-prem
  ↓
ExpressRoute
  ↓
Azure
```

Failure:

```text
ExpressRoute unavailable
         ↓
S2S VPN backup
         ↓
Azure
```

Microsoft explicitly documents S2S VPN as a secure failover path for ExpressRoute private peering connectivity. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-coexist-resource-manager?utm_source=chatgpt.com "Configure ExpressRoute and S2S VPN coexisting connections with Azure PowerShell | Microsoft Learn"))

---

### **Important: these are separate gateways**

I don't convert the ExpressRoute Gateway into a VPN Gateway.

Instead, the VNet can have:

```text
GatewaySubnet
├── ExpressRoute virtual network gateway
└── VPN virtual network gateway
```

with supported coexistence configuration.

---

### **Requirements**

Current Microsoft guidance includes important coexistence requirements such as:

```text
VPN Gateway
→ RouteBased

Basic VPN Gateway SKU
→ not supported

GatewaySubnet
→ /27 or larger address space
   (/27, /26, /25...)
```

for the documented coexistence design. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-coexist-resource-manager?utm_source=chatgpt.com "Configure ExpressRoute and S2S VPN coexisting connections with Azure PowerShell | Microsoft Learn"))

---

### **Which path is preferred?**

For matching routes in the normal failover design:

```text
ExpressRoute
→ primary/preferred

S2S VPN
→ backup
```

Microsoft notes that ExpressRoute is preferred over S2S VPN when the same routes are present, while **longest-prefix matching still applies** to route selection. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-coexist-resource-manager?utm_source=chatgpt.com "Configure ExpressRoute and S2S VPN coexisting connections with Azure PowerShell | Microsoft Learn"))

So I don't simply assume:

```text
ER always wins every possible route
```

because:

```text
more-specific prefix
```

can still change the selected route.

---

### **On-prem routing also matters**

To make the design behave correctly:

```text
On-prem network
should prefer
ExpressRoute
over VPN
```

when both paths advertise the same destinations.

Otherwise:

```text
Azure → ExpressRoute
On-prem → VPN
```

could produce an asymmetric design.

Microsoft recommends configuring the local network to prefer the ExpressRoute path when S2S VPN is used for failover. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-coexist-resource-manager?utm_source=chatgpt.com "Configure ExpressRoute and S2S VPN coexisting connections with Azure PowerShell | Microsoft Learn"))

---

### **Another coexistence use case**

Not every site needs ExpressRoute.

Example:

```text
Head Office
   ↓
ExpressRoute
   ↓
Azure

Branch Office
   ↓
S2S VPN
   ↓
Azure
```

This is also a supported coexistence reason. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-coexist-resource-manager?utm_source=chatgpt.com "Configure ExpressRoute and S2S VPN coexisting connections with Azure PowerShell | Microsoft Learn"))

---

### **Transit between ER-connected and VPN-connected sites**

There is an important advanced nuance.

If I want:

```text
On-prem Site A
connected through ExpressRoute
        ↓
Azure
        ↓
Site B
connected through S2S VPN
```

Microsoft's current coexistence guidance requires additional design, including **Azure Route Server** for the documented transit-routing scenario. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-howto-coexist-resource-manager?utm_source=chatgpt.com "Configure ExpressRoute and S2S VPN coexisting connections with Azure PowerShell | Microsoft Learn"))

So coexistence does not automatically mean:

```text
Every ER network
can transit through Azure
to every VPN network
```

---

### **Strong interview answer**

> “Yes. ExpressRoute and a route-based site-to-site VPN Gateway can coexist for the same VNet. A common enterprise design uses ExpressRoute as the primary path and S2S VPN as a secure backup. They use separate virtual network gateways in the GatewaySubnet, and there are coexistence requirements such as a non-Basic route-based VPN Gateway and adequate GatewaySubnet sizing. I also configure on-prem routing to prefer ExpressRoute so failover is predictable and doesn't introduce asymmetric routing.”

**Memory line:**  
**ExpressRoute primary + S2S VPN backup is a supported Azure hybrid pattern.**

**Interview trap:**  
Do not say:

> “Just attach a VPN tunnel to the ExpressRoute Gateway.”

They are separate gateway types.

**Keywords:**  
ExpressRoute coexistence, VPN failover, route-based VPN, GatewaySubnet, asymmetric routing

**Likely follow-ups:**

- Which path does Azure prefer?
    
- What happens if ExpressRoute fails?
    
- Can ER-connected sites transit to VPN-connected sites automatically?
    
- Why must the VPN Gateway be route-based?

### **T17-M06. Why is Azure Bastion preferable to exposing SSH/RDP publicly?**

**Answer:**  
Azure Bastion is preferable because it lets administrators use **SSH or RDP to a VM's private IP without assigning a public IP to the VM or exposing TCP 22/3389 directly to the internet**. This significantly reduces the VM's external attack surface while providing a centrally managed administrative access path. Microsoft describes Bastion specifically as secure RDP/SSH connectivity that prevents direct VM exposure to the public internet. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/bastion/secure-bastion?utm_source=chatgpt.com "Secure Your Azure Bastion Deployment | Microsoft Learn"))

### **Public SSH/RDP design**

```text
Internet
   ↓
VM Public IP
   ↓
NSG
Allow TCP/22
   ↓
Linux VM
```

or:

```text
Internet
   ↓
VM Public IP
   ↓
TCP/3389
   ↓
Windows VM
```

The risk is that the administrative endpoint is:

```text
internet-reachable
```

and continuously exposed to:

```text
port scanning
credential attacks
brute-force attempts
unpatched protocol/service risk
```

---

### **Bastion design**

```text
Administrator
      ↓
TLS / Bastion access
      ↓
Azure Bastion
      ↓
private VNet connectivity
      ↓
VM private IP
10.20.1.5
```

VM configuration:

```text
Public IP = None
```

That removes the need to expose:

```text
22
3389
```

directly to the internet. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/bastion/secure-bastion?utm_source=chatgpt.com "Secure Your Azure Bastion Deployment | Microsoft Learn"))

---

### **1. Smaller attack surface**

Without Bastion:

```text
VM01 → Public IP
VM02 → Public IP
VM03 → Public IP
VM04 → Public IP
```

Each server can become an externally reachable management endpoint.

With Bastion:

```text
Bastion
  ↓
private management path
  ↓
VM01
VM02
VM03
VM04
```

The administrative entry point is centralized.

---

### **2. No public IP required on every VM**

This improves:

```text
security
IP management
governance
```

and lets me create a policy such as:

```text
Production VM
→ public IP prohibited
```

while still retaining emergency/admin SSH or RDP access through Bastion.

---

### **3. Centralized administration**

Instead of maintaining:

```text
50 VM public endpoints
+
50 sets of inbound management rules
```

I can centralize remote administration.

Microsoft's security guidance describes Bastion as a critical gateway that controls how users connect to private VMs. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/bastion/secure-bastion?utm_source=chatgpt.com "Secure Your Azure Bastion Deployment | Microsoft Learn"))

---

### **4. Bastion doesn't eliminate VM authentication**

Bastion secures the **network access path**.

You still need:

```text
SSH key
Windows credentials
Entra-based access where configured
RBAC/access controls
```

depending on the VM and connection method.

So:

```text
Bastion
→ secure reachability

VM identity/authentication
→ who may log in
```

These are different controls.

---

### **5. Bastion vs NSG restriction**

Someone might say:

> “I'll just allow SSH from my office public IP.”

That is certainly better than:

```text
0.0.0.0/0 → TCP/22
```

but the VM still has:

```text
public IP
+
publicly routed management endpoint
```

With Bastion, I can remove that endpoint altogether.

A strong security preference is:

```text
No public management interface
>
restricted public management interface
```

when the architecture permits it.

---

### **6. Bastion vs P2S VPN**

Both can securely help administrators reach private VMs, but the purposes differ.

```text
Bastion
→ focused SSH/RDP administrative access

P2S VPN
→ gives the client broader
  private network connectivity
```

If an operator only needs:

```text
SSH/RDP to private VMs
```

Bastion may be simpler.

If a developer needs:

```text
VMs
internal APIs
SQL
private endpoints
many internal services
```

P2S VPN may be more appropriate.

---

### **Production example**

Bad:

```text
Internet
   ↓
NSG allow 22
   ↓
20 production VMs
with public IPs
```

Better:

```text
Admins
   ↓
Azure Bastion
   ↓
Private VNet
   ↓
20 private VMs

VM public IPs = none
Public TCP/22/3389 = none
```

---

### **Strong interview answer**

> “Azure Bastion is preferable because my VMs don't need public IP addresses and I don't need to expose SSH or RDP ports directly to the internet. Bastion becomes the managed administrative access layer and connects to the VMs over their private IPs. That dramatically reduces the external attack surface and centralizes management access. I would still enforce VM authentication, RBAC, logging, and least privilege because Bastion secures the access path rather than replacing identity controls.”

**Memory line:**  
**Bastion lets me administer private VMs without public SSH/RDP exposure.**

**Interview trap:**  
Do not say Bastion makes authentication unnecessary. It removes **public management exposure**, not VM/user security requirements.

**Keywords:**  
Azure Bastion, private IP, SSH, RDP, attack surface, no public IP, secure administration

**Likely follow-ups:**

- Bastion vs P2S VPN?
    
- Does a VM need a public IP when using Bastion?
    
- Does Bastion replace NSGs?

This is particularly useful for ExpressRoute, multi-site VPN, redundant hybrid links, and larger hub-and-spoke environments. It also supports failover because a failed route can be withdrawn and another learned path can become preferred.”

**Memory line:**
**BGP makes hybrid routing dynamic, scalable, and better suited to redundant paths.**

**Interview trap:**
BGP doesn't automatically make the network highly available. You still need **redundant physical/tunnel paths and correct routing policy**.

**Keywords:**
Dynamic routing, route propagation, failover, ExpressRoute, hybrid networking, BGP peers

**Likely follow-ups:**

* How does BGP support failover?
* What happens when a BGP route is withdrawn?
* What would you inspect if BGP is up but traffic fails?
* Does BGP replace UDRs everywhere?

---

### **T17-M05. Can VPN Gateway and ExpressRoute coexist?**

**Answer:**
**Yes. Azure supports ExpressRoute and a site-to-site VPN Gateway coexisting for the same VNet.** A common production pattern is to use **ExpressRoute as the primary hybrid path and site-to-site VPN as a backup path** if ExpressRoute becomes unavailable. VPN can also connect sites that aren't connected through ExpressRoute. ([Microsoft Learn][2])

### **Typical design**

```text
                    Azure VNet
                        │
                 GatewaySubnet
                  /           \
                 /             \
 ExpressRoute Gateway       VPN Gateway
        ↑                       ↑
        │                       │
 ExpressRoute circuit       IPsec tunnel
        ↑                       ↑
        └────── On-premises ────┘
```

Normal operation:

```text
On-prem
  ↓
ExpressRoute
  ↓
Azure
```

Failure:

```text
ExpressRoute unavailable
         ↓
S2S VPN backup
         ↓
Azure
```

Microsoft explicitly documents S2S VPN as a secure failover path for ExpressRoute private peering connectivity. ([Microsoft Learn][2])

---

### **Important: these are separate gateways**

I don't convert the ExpressRoute Gateway into a VPN Gateway.

Instead, the VNet can have:

```text
GatewaySubnet
├── ExpressRoute virtual network gateway
└── VPN virtual network gateway
```

with supported coexistence configuration.

---

### **Requirements**

Current Microsoft guidance includes important coexistence requirements such as:

```text
VPN Gateway
→ RouteBased

Basic VPN Gateway SKU
→ not supported

GatewaySubnet
→ /27 or larger address space
   (/27, /26, /25...)
```

for the documented coexistence design. ([Microsoft Learn][2])

---

### **Which path is preferred?**

For matching routes in the normal failover design:

```text
ExpressRoute
→ primary/preferred

S2S VPN
→ backup
```

Microsoft notes that ExpressRoute is preferred over S2S VPN when the same routes are present, while **longest-prefix matching still applies** to route selection. ([Microsoft Learn][2])

So I don't simply assume:

```text
ER always wins every possible route
```

because:

```text
more-specific prefix
```

can still change the selected route.

---

### **On-prem routing also matters**

To make the design behave correctly:

```text
On-prem network
should prefer
ExpressRoute
over VPN
```

when both paths advertise the same destinations.

Otherwise:

```text
Azure → ExpressRoute
On-prem → VPN
```

could produce an asymmetric design.

Microsoft recommends configuring the local network to prefer the ExpressRoute path when S2S VPN is used for failover. ([Microsoft Learn][2])

---

### **Another coexistence use case**

Not every site needs ExpressRoute.

Example:

```text
Head Office
   ↓
ExpressRoute
   ↓
Azure

Branch Office
   ↓
S2S VPN
   ↓
Azure
```

This is also a supported coexistence reason. ([Microsoft Learn][2])

---

### **Transit between ER-connected and VPN-connected sites**

There is an important advanced nuance.

If I want:

```text
On-prem Site A
connected through ExpressRoute
        ↓
Azure
        ↓
Site B
connected through S2S VPN
```

Microsoft's current coexistence guidance requires additional design, including **Azure Route Server** for the documented transit-routing scenario. ([Microsoft Learn][2])

So coexistence does not automatically mean:

```text
Every ER network
can transit through Azure
to every VPN network
```

---

### **Strong interview answer**

> “Yes. ExpressRoute and a route-based site-to-site VPN Gateway can coexist for the same VNet. A common enterprise design uses ExpressRoute as the primary path and S2S VPN as a secure backup. They use separate virtual network gateways in the GatewaySubnet, and there are coexistence requirements such as a non-Basic route-based VPN Gateway and adequate GatewaySubnet sizing. I also configure on-prem routing to prefer ExpressRoute so failover is predictable and doesn't introduce asymmetric routing.”

**Memory line:**
**ExpressRoute primary + S2S VPN backup is a supported Azure hybrid pattern.**

**Interview trap:**
Do not say:

> “Just attach a VPN tunnel to the ExpressRoute Gateway.”

They are separate gateway types.

**Keywords:**
ExpressRoute coexistence, VPN failover, route-based VPN, GatewaySubnet, asymmetric routing

**Likely follow-ups:**

* Which path does Azure prefer?
* What happens if ExpressRoute fails?
* Can ER-connected sites transit to VPN-connected sites automatically?
* Why must the VPN Gateway be route-based?

### **T17-M06. Why is Azure Bastion preferable to exposing SSH/RDP publicly?**

**Answer:**
Azure Bastion is preferable because it lets administrators use **SSH or RDP to a VM's private IP without assigning a public IP to the VM or exposing TCP 22/3389 directly to the internet**. This significantly reduces the VM's external attack surface while providing a centrally managed administrative access path. Microsoft describes Bastion specifically as secure RDP/SSH connectivity that prevents direct VM exposure to the public internet. ([Microsoft Learn][3])

### **Public SSH/RDP design**

```text
Internet
   ↓
VM Public IP
   ↓
NSG
Allow TCP/22
   ↓
Linux VM
```

or:

```text
Internet
   ↓
VM Public IP
   ↓
TCP/3389
   ↓
Windows VM
```

The risk is that the administrative endpoint is:

```text
internet-reachable
```

and continuously exposed to:

```text
port scanning
credential attacks
brute-force attempts
unpatched protocol/service risk
```

---

### **Bastion design**

```text
Administrator
      ↓
TLS / Bastion access
      ↓
Azure Bastion
      ↓
private VNet connectivity
      ↓
VM private IP
10.20.1.5
```

VM configuration:

```text
Public IP = None
```

That removes the need to expose:

```text
22
3389
```

directly to the internet. ([Microsoft Learn][3])

---

### **1. Smaller attack surface**

Without Bastion:

```text
VM01 → Public IP
VM02 → Public IP
VM03 → Public IP
VM04 → Public IP
```

Each server can become an externally reachable management endpoint.

With Bastion:

```text
Bastion
  ↓
private management path
  ↓
VM01
VM02
VM03
VM04
```

The administrative entry point is centralized.

---

### **2. No public IP required on every VM**

This improves:

```text
security
IP management
governance
```

and lets me create a policy such as:

```text
Production VM
→ public IP prohibited
```

while still retaining emergency/admin SSH or RDP access through Bastion.

---

### **3. Centralized administration**

Instead of maintaining:

```text
50 VM public endpoints
+
50 sets of inbound management rules
```

I can centralize remote administration.

Microsoft's security guidance describes Bastion as a critical gateway that controls how users connect to private VMs. ([Microsoft Learn][3])

---

### **4. Bastion doesn't eliminate VM authentication**

Bastion secures the **network access path**.

You still need:

```text
SSH key
Windows credentials
Entra-based access where configured
RBAC/access controls
```

depending on the VM and connection method.

So:

```text
Bastion
→ secure reachability

VM identity/authentication
→ who may log in
```

These are different controls.

---

### **5. Bastion vs NSG restriction**

Someone might say:

> “I'll just allow SSH from my office public IP.”

That is certainly better than:

```text
0.0.0.0/0 → TCP/22
```

but the VM still has:

```text
public IP
+
publicly routed management endpoint
```

With Bastion, I can remove that endpoint altogether.

A strong security preference is:

```text
No public management interface
>
restricted public management interface
```

when the architecture permits it.

---

### **6. Bastion vs P2S VPN**

Both can securely help administrators reach private VMs, but the purposes differ.

```text
Bastion
→ focused SSH/RDP administrative access

P2S VPN
→ gives the client broader
  private network connectivity
```

If an operator only needs:

```text
SSH/RDP to private VMs
```

Bastion may be simpler.

If a developer needs:

```text
VMs
internal APIs
SQL
private endpoints
many internal services
```

P2S VPN may be more appropriate.

---

### **Production example**

Bad:

```text
Internet
   ↓
NSG allow 22
   ↓
20 production VMs
with public IPs
```

Better:

```text
Admins
   ↓
Azure Bastion
   ↓
Private VNet
   ↓
20 private VMs

VM public IPs = none
Public TCP/22/3389 = none
```

---

### **Strong interview answer**

> “Azure Bastion is preferable because my VMs don't need public IP addresses and I don't need to expose SSH or RDP ports directly to the internet. Bastion becomes the managed administrative access layer and connects to the VMs over their private IPs. That dramatically reduces the external attack surface and centralizes management access. I would still enforce VM authentication, RBAC, logging, and least privilege because Bastion secures the access path rather than replacing identity controls.”

**Memory line:**
**Bastion lets me administer private VMs without public SSH/RDP exposure.**

**Interview trap:**
Do not say Bastion makes authentication unnecessary. It removes **public management exposure**, not VM/user security requirements.

**Keywords:**
Azure Bastion, private IP, SSH, RDP, attack surface, no public IP, secure administration

**Likely follow-ups:**

* Bastion vs P2S VPN?
* Does a VM need a public IP when using Bastion?
* Does Bastion replace NSGs?
* How would you secure administrative access to hundreds of VMs?
