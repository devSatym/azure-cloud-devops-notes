### **T16-H05. How would you troubleshoot a private endpoint showing approved but remaining unreachable?**

**Answer:**
`Approved` only proves that the **Private Link connection was authorized**. It does **not** prove that DNS, routing, NSGs, firewalls, peering, or the application path is correct. I would troubleshoot in this order:

```text
Private Endpoint = Approved
        ↓
DNS → private IP?
        ↓
TCP to service port?
        ↓
Effective route / Next Hop
        ↓
NSG / Firewall / NVA
        ↓
Peering / return path
        ↓
Service configuration
        ↓
Authentication / authorization
```

Microsoft's current Private Endpoint troubleshooting guidance similarly separates endpoint approval from actual traffic-flow failures and highlights DNS and routing/security as major failure domains. ([Microsoft Learn][1])

---

### **1. Start from the actual failing client**

I troubleshoot from:

```text
the VM
the AKS pod
the App Service
the on-prem client
```

that is actually failing—not merely from another VM that happens to work.

For example:

```bash
nslookup mystorage.blob.core.windows.net
```

The first question is:

> **Does the service FQDN resolve to the expected Private Endpoint IP?**

Expected:

```text
mystorage.blob.core.windows.net
        ↓
private DNS path
        ↓
10.20.5.7
```

If instead I get:

```text
20.x.x.x
```

I'm not even testing the Private Endpoint yet.

---

### **2. If DNS returns public IP → fix DNS first**

I check:

```text
Correct privatelink.* zone?
        ↓
A record exists?
        ↓
A record = PE private IP?
        ↓
Source VNet linked?
        ↓
Custom DNS forwarding correct?
```

For example:

```text
Blob Storage
→ privatelink.blob.core.windows.net

Azure SQL
→ privatelink.database.windows.net

Key Vault
→ privatelink.vaultcore.azure.net
```

A very common situation is:

```text
Private Endpoint = Approved ✓
Private DNS zone exists ✓
Application VNet link missing ✗
```

Result:

```text
application → public endpoint
```

So `Approved` tells me nothing about name resolution.

---

### **3. If DNS returns the private IP, test the service port**

Now I know the request is attempting the correct destination.

Examples:

```bash
nc -vz mystorage.blob.core.windows.net 443
```

For SQL:

```bash
nc -vz myserver.database.windows.net 1433
```

Or:

```bash
curl -vk https://<service-fqdn>
```

Interpret the result:

```text
DNS = private IP
TCP timeout
→ network path/security problem

DNS = private IP
TCP succeeds
HTTP 403
→ network probably works;
  investigate authorization/service policy
```

This split saves a lot of time.

---

### **4. Check effective routing**

I want to know:

> **Where is Azure actually sending packets for the Private Endpoint IP?**

Example:

```text
Client = 10.1.1.4
PE     = 10.20.5.7
```

Expected route might be:

```text
10.20.5.7
   ↓
VirtualNetwork / Peering
```

But perhaps a UDR says:

```text
10.20.0.0/16
→ Virtual Appliance
10.0.0.4
```

Now traffic takes:

```text
VM
 ↓
NVA
 ↓
???
```

instead of the expected path.

I inspect:

```bash
az network nic show-effective-route-table \
  --resource-group <rg> \
  --name <nic> \
  --output table
```

and use **Network Watcher Next Hop** when the source is supported.

Microsoft's current troubleshooting guidance explicitly calls out route selection and routing overrides as causes of approved Private Endpoints remaining unreachable. ([Microsoft Learn][1])

---

### **5. Watch for Private Endpoint `/32` routing behavior**

This is a stronger interview point.

Azure can have a highly specific route for the Private Endpoint IP:

```text
10.20.5.7/32
```

Because route selection uses longest-prefix matching:

```text
10.20.5.7/32
```

is more specific than:

```text
10.20.0.0/16
```

or:

```text
0.0.0.0/0
```

So if the architecture expects Private Endpoint traffic to traverse an Azure Firewall/NVA, I verify the actual effective route rather than assuming my broad UDR automatically wins.

Microsoft's current troubleshooting decision map specifically identifies Private Endpoint `/32` routing behavior and routing overrides as an important diagnostic area. ([Microsoft Learn][1])

---

### **6. Check NSGs and Private Endpoint network policies**

If routing is correct:

```text
Client
  ↓
correct next hop
  ↓
Private Endpoint subnet
```

I inspect:

```text
source subnet NSG
destination/PE subnet policy
Azure Firewall rules
NVA rules
```

A packet can have:

```text
correct DNS ✓
correct route ✓
```

and still get denied by a security layer.

---

### **7. Check Azure Firewall / NVA**

If the route intentionally goes:

```text
Client
  ↓
Azure Firewall
  ↓
Private Endpoint
```

I check the firewall logs using the exact:

```text
source IP
destination PE IP
destination port
timestamp
```

Possible evidence:

```text
10.1.1.4
→ 10.20.5.7:443
→ DENY
```

Then the problem is obvious.

For a third-party NVA I additionally check:

```text
IP forwarding
forwarding policy
health
routing table
return route
```

---

### **8. Check VNet peering**

If the Private Endpoint sits in another VNet:

```text
Spoke A
  ↓
Peering
  ↓
Shared-services VNet
  ↓
Private Endpoint
```

I verify:

```text
Peering = Connected
Address spaces don't overlap
Correct routes exist
Firewall path exists if required
```

Remember:

```text
Private DNS resolution ✓
```

does not prove:

```text
network reachability ✓
```

---

### **9. Check asymmetric return routing**

Example:

```text
Forward:
Spoke → Firewall → PE

Return:
PE → direct Spoke
```

If a stateful firewall sees only one side:

```text
session can fail
```

So when forced routing/NVAs are involved, I always verify:

```text
forward path
+
return path
```

---

### **10. Confirm the Private Endpoint targets the correct subresource**

Many Azure PaaS services expose different Private Link subresources.

For Storage, for example:

```text
blob
file
queue
table
```

may need different Private Endpoints depending on what the application accesses.

So:

```text
Blob PE created
```

does not automatically mean:

```text
Azure Files path works
```

I verify:

```text
resource
+
subresource
+
DNS zone
```

all match the workload.

---

### **11. Only after TCP connectivity works, troubleshoot authorization**

Suppose:

```text
DNS → 10.20.5.7 ✓
TCP/443 ✓
HTTP response = 403
```

Now I inspect:

```text
Managed Identity
Workload Identity
Azure RBAC
SAS
service-specific permissions
```

For example:

```text
AKS pod
   ↓
Private Endpoint connectivity ✓
   ↓
Storage
   ↓
403
```

could simply mean:

```text
Workload Identity lacks
Storage Blob Data Contributor
```

Networking is already working.

---

### **Production troubleshooting summary**

```text
PE Approved
    ↓
nslookup
    ↓
Private IP?
 /          \
No           Yes
↓             ↓
DNS        TCP test
             ↓
           timeout?
          /       \
        Yes        No
         ↓          ↓
 route/security   HTTP/service
                    ↓
               auth/RBAC
```

> **In an interview, I would say:**
> “An Approved state only proves that the Private Endpoint connection was accepted. I would start from the failing workload and resolve the normal service FQDN. If it doesn't return the Private Endpoint IP, I troubleshoot Private DNS, VNet links, and custom DNS forwarding. If DNS is correct, I test the actual service port and inspect effective routes and Network Watcher Next Hop, then NSGs, Azure Firewall/NVA rules, peering and return routing. I also verify that the Private Endpoint targets the right service subresource. Once TCP works, a 403 moves me to Managed Identity, RBAC, or service authorization rather than networking.”

**Memory line:**
**Approved PE → DNS → TCP → route → security → service → identity.**

**Interview trap:**
`Approved` means **connection authorization succeeded**, not that clients can actually reach the service.

**Keywords:**
Private Endpoint, Private DNS, effective routes, `/32`, Next Hop, NVA, asymmetric routing, subresource

**Likely follow-ups:**

* What if DNS resolves to a public IP?
* What if DNS returns private IP but TCP times out?
* Why might a UDR not affect the Private Endpoint as expected?
* What does a 403 after successful TCP connectivity suggest?

# **17. 🟠 IMP — VPN, ExpressRoute, Bastion & Hybrid Networking**

### **T17-E01. What is Azure VPN Gateway?**

**Answer:**
Azure VPN Gateway is an Azure-managed virtual network gateway that provides **encrypted connectivity using VPN protocols between Azure VNets, on-premises networks, and individual remote clients**. Common connection types are **site-to-site, point-to-site, and VNet-to-VNet VPNs**. Azure VPN Gateway uses technologies such as IPsec/IKE for encrypted connectivity over the public internet. ([Microsoft Learn][2])

### **Basic architecture**

For hybrid connectivity:

```text
On-premises
    ↓
VPN device
    ↓
Encrypted IPsec/IKE tunnel
    ↓
Internet
    ↓
Azure VPN Gateway
    ↓
Azure VNet
```

So instead of exposing:

```text
private application servers
```

directly to the internet, the networks communicate through an encrypted tunnel.

---

### **Main connection types**

#### **Site-to-Site**

```text
On-prem network
      ↓
VPN device
      ↓
Azure VPN Gateway
      ↓
Azure VNet
```

Used for:

```text
office/data center
↔
Azure
```

---

#### **Point-to-Site**

```text
Developer laptop
      ↓
VPN client
      ↓
Azure VPN Gateway
      ↓
Azure VNet
```

Used for individual users working remotely.

---

#### **VNet-to-VNet**

```text
Azure VNet A
     ↓
VPN Gateway
     ↓
IPsec/IKE tunnel
     ↓
VPN Gateway
     ↓
Azure VNet B
```

Although VNet peering is generally simpler for many Azure-to-Azure connectivity scenarios, VPN Gateway supports encrypted VNet-to-VNet connections as well. ([Microsoft Learn][2])

---

### **GatewaySubnet**

VPN Gateway is deployed into a special subnet named:

```text
GatewaySubnet
```

within the VNet.

Conceptually:

```text
VNet
│
├── AppSubnet
├── DataSubnet
│
└── GatewaySubnet
      ↓
   VPN Gateway
```

I don't place normal workloads inside `GatewaySubnet`.

---

### **Route-based VPN**

For modern production architectures I generally think in terms of **route-based VPN gateways**, especially where requirements include:

```text
multiple connections
BGP
point-to-site + site-to-site
ExpressRoute coexistence
```

rather than treating the VPN as a simple static pair of networks.

---

### **Encryption**

Traffic crossing:

```text
Internet
```

between the VPN peers is encrypted using VPN protocols such as:

```text
IPsec
IKE
```

Microsoft describes Azure VPN Gateway as providing encrypted cross-premises and VNet connectivity over the public internet. ([Microsoft Learn][3])

---

### **VPN Gateway vs ExpressRoute preview**

```text
VPN Gateway
→ encrypted tunnel over public internet

ExpressRoute
→ private connectivity through a provider
  instead of ordinary internet routing
```

VPN Gateway is usually:

```text
faster to deploy
lower cost
```

but ExpressRoute can provide more predictable private enterprise connectivity.

We'll cover that distinction directly later.

---

### **Redundancy**

For production, VPN Gateway can support highly available designs such as:

```text
active-active gateway
+
redundant on-prem VPN devices
```

so a single gateway instance or tunnel isn't the whole hybrid-connectivity design. Microsoft provides active-active VPN Gateway configurations for higher availability. ([Microsoft Learn][4])

---

> **In an interview, I would say:**
> “Azure VPN Gateway is Microsoft's managed VPN gateway for securely connecting Azure VNets to on-premises networks, remote clients, or other VNets. It supports site-to-site, point-to-site and VNet-to-VNet connectivity, typically using IPsec/IKE encryption over the public internet. The gateway is deployed into the VNet's dedicated `GatewaySubnet`, and for production hybrid environments I would normally use a route-based, highly available design.”

**Memory line:**
**VPN Gateway = encrypted connectivity between Azure VNets, on-prem networks, and remote users.**

**Interview trap:**
Do not confuse VPN Gateway with:

```text
NAT Gateway
```

NAT Gateway provides outbound SNAT; VPN Gateway provides encrypted network connectivity.

**Keywords:**
VPN Gateway, IPsec/IKE, GatewaySubnet, S2S, P2S, VNet-to-VNet

**Likely follow-ups:**

* Site-to-site vs point-to-site?
* VPN Gateway vs ExpressRoute?
* What is `GatewaySubnet`?
* What does route-based VPN mean?

### **T17-E02. What is a site-to-site VPN?**

**Answer:**
A **site-to-site (S2S) VPN** securely connects an entire on-premises network or site to an Azure VNet through an **IPsec/IKE tunnel**. One side is Azure VPN Gateway and the other side is normally an on-premises VPN device with a public IP address. Once routing is configured, multiple machines at the site can access Azure resources without each machine establishing its own VPN session. ([Microsoft Learn][4])

### **Architecture**

```text
Office / Data Center
192.168.0.0/16
        │
        ↓
On-prem VPN Device
Public IP
        │
        │ IPsec/IKE
        │ encrypted tunnel
        ↓
   Public Internet
        ↓
Azure VPN Gateway
        ↓
Azure VNet
10.0.0.0/16
```

---

### **Why “site-to-site”?**

Because it connects:

```text
Network/Site A
      ↕
Network/Site B
```

rather than:

```text
one individual laptop
      ↕
Azure
```

Users at the office normally don't start a VPN client individually.

Their traffic follows:

```text
Laptop
  ↓
corporate router
  ↓
VPN device
  ↓
S2S tunnel
  ↓
Azure
```

---

### **Azure-side components**

Typical Azure resources:

```text
VNet
  ↓
GatewaySubnet
  ↓
VPN Gateway
  ↓
Connection
```

and:

```text
Local Network Gateway
```

which represents information about the on-premises side, such as:

```text
on-prem public VPN IP
on-prem address prefixes
BGP information when used
```

---

### **On-premises requirement**

The classic S2S design requires:

```text
VPN device
+
public-facing IP
```

at the on-premises site.

Microsoft explicitly distinguishes this from P2S, which doesn't require a dedicated on-premises VPN appliance or site public IP. ([Microsoft Learn][4])

---

### **Example**

Company:

```text
Office network
192.168.10.0/24
```

Azure:

```text
VNet
10.20.0.0/16
```

After S2S VPN:

```text
Office PC
192.168.10.50
       ↓
VPN tunnel
       ↓
Azure VM
10.20.1.10
```

without giving that Azure VM:

```text
a public SSH/RDP endpoint
```

---

### **Routing**

The two sides must know:

```text
which prefixes are reachable
through the VPN tunnel
```

Routes can be:

```text
statically configured
```

or dynamically exchanged using:

```text
BGP
```

depending on the architecture.

We'll cover BGP later.

---

### **Typical use cases**

```text
Data center ↔ Azure
Branch office ↔ Azure
Hybrid applications
On-prem AD/DNS ↔ Azure
Private database access
Backup/DR connectivity
```

---

### **S2S vs ExpressRoute preview**

S2S:

```text
encrypted
+
public internet transport
```

ExpressRoute:

```text
private provider connectivity
+
doesn't use normal public internet path
```

For many companies:

```text
ExpressRoute
+
S2S VPN backup
```

can also coexist. Microsoft explicitly supports VPN Gateway as a secure failover path for ExpressRoute. ([Microsoft Learn][2])

---

> **In an interview, I would say:**
> “A site-to-site VPN connects an entire on-premises network to an Azure VNet through an IPsec/IKE tunnel. Azure VPN Gateway is one endpoint and an on-premises VPN device is the other. Once the tunnel and routes are configured, machines on the corporate network can reach Azure private resources without running individual VPN clients. I would typically use it for hybrid connectivity between an office or data center and Azure.”

**Memory line:**
**S2S = network-to-network VPN.**

**Interview trap:**
Do not say every employee machine establishes the S2S tunnel individually—that describes more of a **point-to-site** model.

**Keywords:**
Site-to-Site, S2S, IPsec/IKE, Local Network Gateway, VPN device, hybrid network

**Likely follow-ups:**

* What is a Local Network Gateway?
* What ports/protocols are involved?
* Can S2S VPN use BGP?
* How would you make an S2S VPN highly available?

### **T17-E03. What is a point-to-site VPN?**

**Answer:**
A **point-to-site (P2S) VPN** securely connects an **individual client computer** to an Azure VNet. The connection is initiated from the user's laptop or workstation using a VPN client, making it useful for remote developers, administrators, or employees who need private Azure access without being connected through a corporate site-to-site network. ([Microsoft Learn][5])

### **Architecture**

```text
Developer laptop
Home / Hotel / Conference
        ↓
Azure VPN Client
        ↓
Encrypted VPN connection
        ↓
Internet
        ↓
Azure VPN Gateway
        ↓
Azure VNet
        ↓
Private VM / internal service
```

---

### **Why “point-to-site”?**

Because:

```text
One endpoint/client
       ↕
Azure network/site
```

Compare:

```text
P2S
Laptop → Azure

S2S
Entire office network → Azure
```

Microsoft specifically describes P2S as a secure connection initiated from an individual client computer. ([Microsoft Learn][5])

---

### **Typical use case**

Suppose an engineer needs SSH access to:

```text
VM
10.20.1.10
```

but the VM has:

```text
no public IP
```

The engineer can:

```text
Laptop
 ↓
P2S VPN
 ↓
10.20.1.10
```

and connect privately.

This is much better than exposing:

```text
TCP/22
```

to the entire internet.

---

### **No on-premises VPN appliance required**

Unlike S2S:

```text
P2S
→ does not require
  a corporate VPN appliance
```

The client itself establishes the tunnel.

Microsoft explicitly notes this as a major difference between P2S and S2S. ([Microsoft Learn][4])

---

### **Authentication options**

Depending on the P2S configuration and protocol, Azure supports methods such as:

```text
Microsoft Entra ID
certificate authentication
RADIUS
```

Microsoft's current P2S guidance includes Microsoft Entra ID, certificate, and RADIUS-based authentication options depending on the chosen configuration. ([Microsoft Learn][5])

For workforce access, I would strongly consider:

```text
Microsoft Entra authentication
+
MFA / Conditional Access
```

where the selected P2S protocol/configuration supports it.

---

### **Supported protocols**

Azure P2S configurations can use protocols including:

```text
OpenVPN
IKEv2
SSTP
```

depending on gateway configuration and client platform. ([Microsoft Learn][2])

---

### **Client address pool**

P2S users receive an address from a configured VPN client address pool.

For example:

```text
Azure VNet
10.20.0.0/16

P2S client pool
172.16.100.0/24
```

Connected laptop:

```text
172.16.100.5
```

Routes then tell the laptop how to reach Azure prefixes through the tunnel.

I ensure this pool doesn't overlap with:

```text
Azure VNets
home networks
on-premises networks
```

because overlapping IP ranges create routing problems.

---

### **P2S and S2S can coexist**

A single route-based Azure VPN Gateway can support compatible:

```text
Site-to-Site
+
Point-to-Site
```

configurations at the same time. ([Microsoft Learn][4])

For example:

```text
                 Azure VNet
                     ↑
               VPN Gateway
                /          \
               /            \
       S2S tunnel           P2S
          ↑                  ↑
    Office network       Developer
```

---

### **When would I use it?**

```text
Remote developers
Administrators
Small number of remote users
Temporary private Azure access
Users without corporate-site VPN access
```

For hundreds/thousands of globally distributed users, I would evaluate the broader remote-access and Virtual WAN architecture rather than automatically scaling a simple lab-style P2S configuration.

---

> **In an interview, I would say:**
> “A point-to-site VPN connects an individual laptop or workstation securely to an Azure VNet. The user starts the connection through a VPN client, making it useful for remote administrators and developers who need access to private Azure resources. Unlike site-to-site VPN, it doesn't require an on-premises VPN appliance. Azure supports P2S authentication methods such as Microsoft Entra ID, certificates, or RADIUS and protocols such as OpenVPN and IKEv2 depending on the configuration.”

**Memory line:**
**P2S = individual client-to-Azure VPN; S2S = entire network-to-Azure VPN.**

**Interview trap:**
Do not describe P2S as a connection between an office router and Azure—that's **site-to-site**.

**Keywords:**
Point-to-Site, P2S, Azure VPN Client, Microsoft Entra ID, OpenVPN, IKEv2, client address pool

**Likely follow-ups:**

* P2S vs S2S?
* How can P2S users authenticate?
* Does P2S require a VPN appliance?
* Can P2S and S2S use the same VPN Gateway?
