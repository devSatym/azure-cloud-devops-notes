### **T22-H03. How would you troubleshoot connection exhaustion between AKS and a managed database?**

**Answer:**
If AKS workloads are exhausting database connections, I would first determine whether the problem is **too many application connections, leaking connections, poor pooling, or a database-side connection limit**. I would trace it from the application pods to the database rather than immediately scaling the database.

### **Troubleshooting flow**

```text
Application pods
     ↓
Connection pool behavior
     ↓
Pod replica count / scaling
     ↓
Network path
     ↓
Database connection limits
```

#### 1. Check the symptom at the application layer

I would look for errors such as:

```text
too many connections
connection pool exhausted
timeout acquiring connection
remaining connection slots are reserved
```

Then correlate them with:

* request latency
* pod count
* HPA scaling events
* recent deployments
* database connection count

A common pattern is:

```text
10 pods
×
50 connections per pod
=
500 possible DB connections
```

If HPA suddenly scales to 40 pods:

```text
40 × 50 = 2,000 possible connections
```

So the application may overwhelm the database even though each pod individually looks healthy.

---

#### 2. Inspect connection pooling

I would verify:

* maximum pool size
* minimum/idle pool size
* connection timeout
* idle timeout
* connection lifetime
* whether connections are returned to the pool correctly

The most important question is:

> Is the application opening a connection per request, or reusing a bounded connection pool?

Opening new database connections for every request is expensive and can rapidly cause exhaustion.

---

#### 3. Look for connection leaks

I would compare:

```text
active application traffic
vs
database open connections
```

If traffic drops but connections remain high, that suggests:

* leaked connections
* transactions not closed
* broken connection lifecycle
* excessive idle connections

For example, code that gets a connection but fails to release it on exception paths can slowly exhaust the pool.

---

#### 4. Check AKS scaling behavior

I would inspect:

```bash
kubectl get pods
kubectl get hpa
kubectl describe hpa <name>
```

I want to know whether a traffic spike caused a large number of pod replicas.

A Kubernetes autoscaler does **not** understand the database's maximum connection capacity unless I explicitly design around it.

So I might limit application pool sizes based on:

```text
Database connection limit
        ÷
Maximum expected pod count
        =
Safe connection budget per pod
```

with some headroom for administration and other workloads.

---

#### 5. Check database-side limits and sessions

On the managed database, I would inspect:

* current connection count
* maximum supported connections
* active versus idle connections
* long-running transactions
* blocking sessions
* connection failures
* server resource metrics

The database can have low CPU and still reject connections because the **connection limit is independent of CPU utilization**.

For PostgreSQL, for example, I would investigate session state and `max_connections`. For Azure SQL, I would inspect sessions, worker/resource limits, and connection-related metrics.

---

#### 6. Check network only if connection establishment itself is failing

If connections are timing out rather than being explicitly rejected, I would also check:

```text
AKS pod
  ↓
DNS resolution
  ↓
Private Endpoint / service endpoint
  ↓
NSG / UDR / firewall
  ↓
Database
```

I would especially check for:

* DNS intermittently resolving incorrectly
* SNAT exhaustion where applicable
* firewall rules
* private endpoint connectivity
* transient network failures

But I would not start here if the error clearly says **connection pool exhausted** or **too many connections**.

### **Production fix**

A typical production design is:

```text
AKS pods
   ↓
Bounded connection pool
   ↓
Managed database
```

I would combine:

* sensible per-pod pool limits
* proper connection reuse
* idle connection cleanup
* connection timeouts
* HPA maximum replica limits
* database monitoring
* application-side retry with backoff for transient failures

For PostgreSQL-heavy workloads, a connection pooler such as PgBouncer can also be useful when the workload creates very large numbers of short-lived client connections.

### **Important distinction**

A **connection pool timeout** does not necessarily mean the database is slow.

It can mean:

```text
Application requests
      ↓
No free pooled connection
      ↓
Requests wait
```

even when:

```text
Database CPU = 20%
```

### **Interview answer condensed**

> “I would first determine whether connections are being exhausted at the application pool or at the database. I’d inspect per-pod pool size, connection leaks, current AKS replica count, and database connection limits. A common AKS issue is that HPA increases replicas, and every replica creates its own connection pool, so the total connection count grows dramatically. I’d then bound pool sizes, ensure connections are reused and released correctly, and size the total connection budget against the database limit.”

**Memory line:**
**Database connections = connections per pod × number of pods, so AKS scaling can create connection exhaustion very quickly.**

**Interview trap:**
Do not assume low database CPU means the database has capacity; connection/session limits can be exhausted independently.

**Keywords:**
Connection pooling, connection leak, HPA, `max_connections`, idle connections, pool timeout, PgBouncer, connection budget.

**Likely follow-ups:**

* How would you calculate an appropriate connection-pool size per pod?
* Can HPA make database connection exhaustion worse?
* What is the role of PgBouncer?
* What is the difference between a connection timeout and a query timeout?

### **T22-H04. How would you migrate an application database with minimal downtime?**

**Answer:**
For minimal downtime, I would avoid a simple stop-copy-start migration. I would first migrate the schema and baseline data, then use **continuous replication or change-data capture** to keep the target synchronized, validate it, briefly quiesce writes during cutover, apply the remaining changes, and switch the application to the new database.

### **Migration flow**

```text
Source DB
   │
   ├── Initial schema/data migration
   │
   └── Continuous change replication
                ↓
            Target DB
                ↓
         Validate / test
                ↓
        Short write freeze
                ↓
             Cutover
```

### **Production implementation order**

#### 1. Assess the source and target first

Before moving anything, I would identify:

* database engine and version
* total data size
* write rate
* unsupported features
* schema incompatibilities
* extensions
* logins/users
* stored procedures
* downtime requirement
* required RPO/RTO

For example, migrating SQL Server to Azure SQL Database may require more compatibility work than SQL Server to Azure SQL Managed Instance.

---

#### 2. Prepare the target database

I would create the destination with:

* required compute/storage capacity
* private networking if production requires it
* Microsoft Entra authentication where applicable
* backups
* monitoring
* encryption
* firewall/private endpoint configuration

Then deploy the schema and verify compatibility.

---

#### 3. Perform the initial data load

The bulk historical data can be copied while the existing application continues running.

```text
Production app
     ↓
Source DB  ──────────► Target DB
        initial copy
```

The problem is that new writes continue happening during this copy.

---

#### 4. Replicate ongoing changes

To minimize downtime, I would keep the target synchronized using a suitable replication mechanism such as:

* Azure Database Migration Service where applicable
* native database replication
* transactional replication
* logical replication for PostgreSQL
* change-data capture-based tooling

The exact technology depends on source and target engines.

```text
Source writes
    ↓
Change stream
    ↓
Target DB
```

---

#### 5. Validate before cutover

I would compare:

* row counts
* checksums where practical
* critical business records
* schema versions
* indexes
* permissions
* application query performance
* replication lag

I would run the application against the target in a controlled environment before switching production.

---

#### 6. Perform a short cutover window

At cutover:

```text
1. Stop or pause writes
2. Allow replication lag to reach ~0
3. Validate final consistency
4. Change application connection target
5. Restart/reload application if necessary
6. Run smoke tests
```

For AKS, ideally the database endpoint comes from configuration or a secret reference rather than being hardcoded.

---

#### 7. Keep rollback available

I would not immediately destroy the original database.

The rollback decision depends on whether the new system has accepted writes.

A clean rollback is easiest before new writes begin on the target.

Once the target becomes writable, rollback gets harder because data may diverge.

### **Example**

Suppose:

```text
AKS application
      ↓
Azure Database for PostgreSQL — Source
```

and I am migrating to another PostgreSQL server.

I might use logical replication:

```text
Old PostgreSQL
      ↓
Logical replication
      ↓
New PostgreSQL
```

Then during cutover:

```text
Stop writes
   ↓
Wait for replication lag = 0
   ↓
Update application DB endpoint
   ↓
Smoke test
   ↓
Resume traffic
```

Downtime can then be minutes or potentially less, rather than the entire duration of copying the database.

### **Important distinction**

**Data migration time is not the same as application downtime.**

A 2 TB database may take hours to copy, while actual application downtime can be only a few minutes if changes are continuously replicated.

### **Interview answer condensed**

> “For minimal downtime, I would pre-provision the target database, migrate the schema and bulk data while production continues running, and then continuously replicate ongoing changes. Before cutover I’d validate data consistency and application compatibility. During the final window I’d temporarily stop writes, wait for replication lag to reach zero, switch the application connection to the target, run smoke tests, and keep the old database available until the migration is confirmed.”

**Memory line:**
**Copy first, replicate changes, freeze writes briefly, catch up, validate, then cut over.**

**Interview trap:**
Do not say “take a backup, restore it, and change the connection string” when the requirement is minimal downtime; that approach may create a large outage and lose writes after the backup.

**Keywords:**
Replication, CDC, Azure Database Migration Service, cutover, replication lag, validation, rollback, write freeze.

**Likely follow-ups:**

* How would you handle schema changes during migration?
* How would you roll back after the target has already accepted writes?
* How would you validate that source and target data match?
* What determines whether Database Migration Service can provide online migration?

### **T22-H05. When would you choose Cosmos DB over Azure SQL?**

**Answer:**
I would choose Azure Cosmos DB when the workload requires **massive horizontal scale, very low predictable latency, flexible or rapidly changing data models, and global distribution**. I would choose Azure SQL when the workload is naturally relational and requires strong SQL capabilities such as joins, complex transactions, relational constraints, and mature relational querying.

### **Decision model**

```text
Need relational model,
joins, constraints,
complex SQL?
      │
     Yes
      ↓
 Azure SQL
```

```text
Need massive scale,
global distribution,
flexible schema,
partitioned access?
      │
     Yes
      ↓
 Cosmos DB
```

### **When Cosmos DB is a strong choice**

Typical examples include:

* globally distributed user-profile data
* IoT/device metadata
* gaming state
* product catalogs
* session/state stores
* high-volume event-driven applications
* workloads needing predictable low-latency reads/writes at large scale

Cosmos DB is designed around **partitioning**.

```text
Cosmos Container
│
├── Partition A
├── Partition B
├── Partition C
└── Partition D
```

A good partition key lets Azure distribute data and throughput horizontally.

For example:

```text
customerId
tenantId
deviceId
regionId
```

depending on the access pattern.

---

### **When Azure SQL is the better choice**

I would prefer Azure SQL for workloads like:

* finance
* billing
* order processing with complex relationships
* ERP-style systems
* reporting-heavy transactional applications
* applications with many joins
* strict relational constraints

Example:

```text
Customers
   ↓
Orders
   ↓
OrderItems
   ↓
Payments
```

This model naturally benefits from:

* foreign keys
* joins
* relational transactions
* SQL querying

---

### **Important comparison**

| Requirement          | Azure SQL                                                                | Cosmos DB                                                                        |
| -------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| Relational data      | Excellent                                                                | Usually not the primary model                                                    |
| Complex joins        | Excellent                                                                | Avoid cross-item relational-style querying                                       |
| Horizontal scale     | Available, but relational scaling patterns differ                        | Core design strength                                                             |
| Global distribution  | Supported through Azure SQL capabilities, but more relationally oriented | Core Cosmos DB capability                                                        |
| Flexible schema      | Possible with JSON, but relational-first                                 | Strong fit                                                                       |
| Partition-key design | Not normally the central application design concept                      | Critical                                                                         |
| Transaction model    | Strong relational transactions                                           | Transactions are primarily scoped to a logical partition                         |
| Consumption model    | vCore/DTU/serverless options                                             | RU-based or vCore-based depending on API/model, with request-cost considerations |

### **Why partitioning matters**

Cosmos DB performance depends heavily on choosing a good partition key.

A poor key such as:

```text
country
```

when 90% of users are in one country can create a **hot partition**.

A better key should usually provide:

* high cardinality
* even traffic distribution
* alignment with common queries

So I would never say “use Cosmos DB because NoSQL is faster.”

The data-access pattern matters much more.

### **Example**

Imagine a global gaming platform storing player state:

```text
India users
Europe users
US users
     ↓
Cosmos DB
     ↓
Globally distributed replicas
```

Cosmos DB can be very attractive because the application can keep data geographically close to users and scale horizontally.

But if the same system had complex financial reconciliation involving:

```text
Players
Subscriptions
Invoices
Payments
Refunds
TaxRecords
```

I would likely keep that transactional financial subsystem in Azure SQL.

It is perfectly reasonable for one architecture to use both.

### **Interview answer condensed**

> “I would choose Cosmos DB when I need global distribution, high horizontal scalability, predictable low-latency access, and a partition-friendly flexible data model. I would choose Azure SQL when the system is relational and needs joins, foreign keys, complex SQL, and rich transactional behavior. The key Cosmos DB design decision is the partition key, so I’d choose based on access patterns rather than simply choosing NoSQL for performance.”

**Memory line:**
**Azure SQL is relationship-first; Cosmos DB is partition-and-scale-first.**

**Interview trap:**
Do not claim Cosmos DB is simply a “faster Azure SQL.” They solve different data-model and scaling problems.

**Keywords:**
Partition key, RU, horizontal scaling, global distribution, relational model, joins, transactions, hot partition.

**Likely follow-ups:**

* What makes a good Cosmos DB partition key?
* What is a hot partition?
* Can Cosmos DB perform transactions?
* Can an application use both Azure SQL and Cosmos DB?

### **T23-E01. What is Azure Service Bus?**

**Answer:**
Azure Service Bus is a **managed enterprise message broker** used to decouple applications and reliably exchange messages between producers and consumers. It supports queues for point-to-point messaging and topics/subscriptions for publish-subscribe messaging.

### **How it works**

```text
Producer
   ↓
Service Bus Queue
   ↓
Consumer
```

The producer does not need the consumer to be online at the same time. Service Bus stores the message until a consumer can process it.

For publish-subscribe:

```text
Producer
   ↓
Service Bus Topic
   ├── Subscription A → Billing
   ├── Subscription B → Email
   └── Subscription C → Analytics
```

It also provides enterprise messaging capabilities such as:

* message locks
* retries
* dead-letter queues
* duplicate detection
* sessions
* scheduled messages

### **Production example**

An order API could publish:

```text
OrderCreated
```

to Service Bus instead of synchronously calling several downstream services.

```text
Order API
    ↓
Service Bus
    ├── Payment Worker
    ├── Inventory Worker
    └── Notification Worker
```

That improves decoupling and resilience.

**Memory line:**
**Service Bus is Azure's reliable message broker for asynchronous business messaging.**

**Interview trap:**
Do not confuse Service Bus with Event Hubs. Service Bus is primarily for reliable business messages and workflows; Event Hubs is designed for high-volume event streaming.

**Keywords:**
Message broker, queue, topic, subscription, asynchronous messaging, dead-letter queue, reliable delivery.
