## **T22-E04. What is Azure Cosmos DB?**

**Answer:**
Azure Cosmos DB is Microsoft's **fully managed, globally distributed database service designed for very low latency, elastic horizontal scaling, and high availability**.

For the classic Azure interview use case, think of it primarily as a **distributed NoSQL database** for applications that need to scale across huge amounts of data and traffic without manually managing database servers or sharding infrastructure. Microsoft's current Cosmos DB engine supports flexible JSON data, automatic indexing, partition-based horizontal scaling, multiple consistency choices, and multi-region replication. ([Microsoft Learn][1])

The simplest mental model is:

```text
Application
     ↓
Azure Cosmos DB
     ↓
┌───────────────┬───────────────┐
│ Partition 1   │ Partition 2   │ ...
└───────────────┴───────────────┘
       ↓
multiple Azure regions
       ↓
users served close to them
```

---

### **1. Why Cosmos DB exists**

Imagine an application with:

```text
Millions of users
Huge JSON dataset
Global traffic
Very high request rate
```

With a traditional single database server:

```text
One DB server
     ↓
CPU/storage ceiling
     ↓
manual sharding
     ↓
complex replication
     ↓
global latency problems
```

Cosmos DB instead provides:

```text
automatic partitioning
horizontal scaling
global replication
managed availability
```

so developers don't have to manually build the distributed database layer.

---

### **2. It is designed for horizontal scale**

Traditional scale-up:

```text
Small DB
   ↓
bigger VM
   ↓
even bigger VM
```

Cosmos DB primarily scales horizontally:

```text
              Cosmos container
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
     Partition 1 Partition 2 Partition 3
```

A good **partition key** determines how items are distributed across logical partitions, which then map to physical partitions.

This matters enormously for:

```text
performance
scalability
cost
hot-partition avoidance
```

Microsoft's current documentation calls partition-key selection one of the key design decisions for Cosmos DB. ([Microsoft Learn][1])

We'll cover that properly in **T22-M07** and **T22-M08**.

---

### **3. Request Units — RU/s**

Cosmos DB uses **Request Units**, or RUs, as a normalized measurement of database work.

Conceptually:

```text
Read item
Write item
Query
Index update
     ↓
consume some number of RUs
```

You might provision:

```text
10,000 RU/s
```

or use an autoscale/serverless model depending on the workload.

The nice abstraction is:

```text
CPU + memory + IOPS
        ↓
normalized as
Request Units
```

so application capacity planning focuses on workload cost rather than server hardware. Microsoft describes the RU model as the abstraction used to provide predictable throughput and cost for reads, writes, and queries. ([Microsoft Learn][1])

---

### **4. Global distribution**

Suppose users are in:

```text
India
Europe
North America
```

Cosmos DB can replicate data across associated Azure regions:

```text
                 Cosmos DB
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
     India         Europe         US
    replica        replica       replica
```

Applications can then access regional replicas closer to users.

Microsoft states that Cosmos DB automatically replicates data to the regions configured on the account and supports multi-region reads and writes. ([Microsoft Learn][2])

---

### **5. Multi-region writes**

For some architectures:

```text
India application
      ↓ writes

Europe application
      ↓ writes

US application
      ↓ writes
```

Cosmos DB can support:

```text
multiple writable regions
```

rather than having all writes cross the world to one single writer region.

That's useful for:

```text
global SaaS
gaming
IoT
large consumer applications
```

but it introduces important questions around:

```text
consistency
conflict resolution
cost
```

---

### **6. Five consistency levels**

Cosmos DB is famous for providing multiple well-defined consistency models.

The standard five are:

```text
Strong
Bounded Staleness
Session
Consistent Prefix
Eventual
```

Think of them roughly as a spectrum:

```text
More consistency                         More availability/
                                             lower latency

Strong
  ↓
Bounded Staleness
  ↓
Session
  ↓
Consistent Prefix
  ↓
Eventual
```

The important interview principle isn't memorizing only the list.

It's understanding:

```text
stronger consistency
      ↕
latency / availability / throughput trade-offs
```

Microsoft's current Cosmos DB documentation continues to expose multiple consistency choices so applications can balance correctness, performance, and availability. ([Microsoft Learn][3])

---

### **7. Session consistency is a common choice**

For many applications, **Session consistency** is a useful balance.

Example:

```text
User updates profile
      ↓
same user/session
immediately sees update
```

without requiring every reader everywhere in the world to behave like a globally synchronous strongly consistent database.

That is why it's frequently used for user-facing applications.

---

### **8. Flexible JSON/document model**

With the API for NoSQL, items commonly look like:

```json
{
  "id": "order-1001",
  "customerId": "cust-501",
  "status": "paid",
  "items": [
    {
      "sku": "A100",
      "qty": 2
    }
  ]
}
```

Another document doesn't have to have exactly the same fields.

This is useful for:

```text
rapidly changing application models
semi-structured data
product catalogs
IoT/device data
user profiles
```

---

### **9. Automatic indexing**

Cosmos DB indexes properties automatically by default.

That means developers can start querying without first manually defining every index.

Later, in production, I can tune the indexing policy to improve:

```text
write cost
query performance
RU consumption
```

Microsoft's current overview says JSON properties are automatically indexed by default, with customizable indexing policies available when optimization is needed. ([Microsoft Learn][1])

---

### **10. Common use cases**

Cosmos DB is a strong fit for:

```text
IoT telemetry
gaming
product catalogs
shopping carts
global user profiles
real-time applications
high-scale web/mobile apps
event-driven systems
```

where I need some combination of:

```text
massive scale
low latency
flexible schema
global availability
```

Microsoft specifically highlights globally distributed workloads such as gaming, e-commerce, and IoT. ([Microsoft Learn][1])

---

### **Cosmos DB vs Azure SQL**

At a high level:

```text
Azure SQL Database
→ relational
→ tables/relations
→ strong SQL relational model
→ joins/transactions familiar to SQL Server

Cosmos DB
→ distributed NoSQL-first model
→ horizontal partitioning
→ massive/global scale
→ flexible JSON model
```

Don't choose Cosmos DB simply because:

```text
"NoSQL is faster."
```

Choose based on the **data and access pattern**.

---

### **Strong interview answer**

> “Azure Cosmos DB is Microsoft's fully managed globally distributed database service designed for low latency, elastic horizontal scale, and high availability. For NoSQL workloads, it stores flexible JSON-style data and automatically partitions data across physical infrastructure based on a partition key. Capacity is measured using Request Units, and Cosmos DB supports multi-region replication and five consistency levels so applications can trade consistency against latency and availability. I would consider it for globally distributed, high-throughput workloads such as IoT, gaming, product catalogs or large consumer applications.”

**Memory line:**
**Cosmos DB = globally distributed + horizontally partitioned + low-latency database at massive scale.**

**Interview trap:**
Do not answer:

> “Cosmos DB is just Microsoft's MongoDB.”

It is its **own distributed database platform** with multiple APIs and its own partitioning, consistency, and RU architecture.

**Keywords:**
Cosmos DB, NoSQL, global distribution, Request Units, partition key, consistency levels, horizontal scaling

**Likely follow-ups:**

* What is a Request Unit?
* What are Cosmos DB consistency levels?
* What is a partition key?
* When would you choose Cosmos DB over Azure SQL?

# **T22-E05. What is Azure Cache for Redis?**

**Answer:**
Azure Cache for Redis is Microsoft's managed **in-memory Redis service**, traditionally used to keep frequently accessed data in memory so applications can retrieve it much faster than repeatedly querying a database or another slower backend.

Typical flow:

```text
Application
     ↓
Redis cache
     │
  cache hit
     ↓
fast response

cache miss
     ↓
Database
     ↓
result
     ↓
Redis
```

Its classic use cases include:

```text
database caching
session state
distributed caching
leaderboards/counters
temporary application state
```

---

## **Important 2026 update**

For an interview **today**, I would immediately add this:

> **Azure Cache for Redis is being retired, and Microsoft recommends Azure Managed Redis for new/migrated workloads.**

As of September 2026, Microsoft says:

```text
Azure Cache for Redis
Basic / Standard / Premium
→ retirement: September 30, 2028
```

For new Azure customers, creation of those tiers has already been blocked since **April 1, 2026**. Existing qualifying customers can continue creating them until retirement. Microsoft recommends migrating to **Azure Managed Redis**. ([Microsoft Learn][4])

So for a modern interview answer:

```text
Question:
"What is Azure Cache for Redis?"

Answer concept:
managed Redis in-memory cache

Current architecture recommendation:
Azure Managed Redis
```

---

### **1. Why use a cache?**

Suppose every request does:

```text
API
 ↓
Azure SQL
 ↓
complex query
 ↓
50 ms
```

and the same product is requested millions of times.

Instead:

```text
                API
                 │
             Check Redis
            /           \
         HIT             MISS
          ↓               ↓
        1 ms-ish          SQL
          ↓               ↓
       return          query result
                          ↓
                     write to Redis
                          ↓
                        return
```

Now the database receives far fewer repetitive reads.

Benefits:

```text
lower latency
higher throughput
lower database load
better scalability
```

Microsoft describes the current Redis service family as a way to improve application performance by serving frequently accessed information directly from memory. ([Microsoft Learn][5])

---

### **2. Cache-aside pattern**

The most common pattern is:

```text
Application
    ↓
GET customer:100
    ↓
Redis
```

If found:

```text
cache HIT
→ return data
```

If missing:

```text
cache MISS
    ↓
database
    ↓
retrieve data
    ↓
SET Redis
    ↓
return
```

This is:

```text
cache-aside
```

Microsoft explicitly lists cache-aside as one of the core managed Redis patterns. ([Microsoft Learn][5])

---

### **3. TTL / expiry**

Cached entries normally shouldn't live forever.

Example:

```text
product:101
TTL = 300 sec
```

After five minutes:

```text
key expires
```

The next request reloads fresh data from the source.

This helps control:

```text
memory
stale data
cache invalidation
```

---

### **4. Cache is normally not my primary database**

Important interview distinction:

```text
Azure SQL/PostgreSQL
→ source of truth

Redis
→ high-speed transient/access layer
```

For example:

```text
Customer balance
```

should generally not exist **only** in a normal cache with no durable authoritative store unless the application is deliberately designed around persistence features and understands the guarantees.

Azure Cache for Redis documentation explicitly notes that data loss is possible during cache failures in relevant configurations. ([Microsoft Learn][6])

---

### **5. Session storage**

Suppose an application has:

```text
App instance 1
App instance 2
App instance 3
```

If user session data is stored only in instance 1:

```text
request 1 → instance 1 ✓

request 2 → instance 3
           session missing ✗
```

With centralized Redis:

```text
             Redis
               ↑
      ┌────────┼────────┐
      │        │        │
    App1     App2     App3
```

all instances can access the shared session data.

This helps applications remain more stateless at the compute layer.

---

### **6. Other Redis patterns**

Redis can also be used for:

```text
distributed counters
rate limiting
leaderboards
deduplication
distributed state
messaging-style use cases
```

The current Azure Managed Redis documentation goes beyond caching and specifically highlights scenarios such as ingestion, deduplication, messaging, and leaderboards. ([Microsoft Learn][5])

---

### **7. Why in-memory is fast**

Traditional DB:

```text
request
 ↓
database processing
 ↓
indexes/storage/data pages
```

Redis:

```text
request
 ↓
RAM
 ↓
value
```

Keeping hot data in memory makes access extremely low latency and high throughput.

---

### **8. Don't create a cache stampede**

Suppose one popular item expires:

```text
product:iphone
TTL expires
```

Then:

```text
10,000 simultaneous requests
      ↓
all get cache miss
      ↓
10,000 queries hit SQL
```

That's a:

```text
cache stampede
```

Mitigations can include:

```text
locking/single-flight
TTL jitter
refresh ahead
stale-while-revalidate patterns
```

This is a good production-level follow-up.

---

### **Current recommendation: Azure Managed Redis**

For new architecture in 2026:

```text
Azure Managed Redis
```

is the important service to know.

Microsoft describes it as a fully managed in-memory store based on **Redis Enterprise**, with compatibility for common Redis application patterns. ([Microsoft Learn][5])

So I'd say:

```text
Legacy/current question bank:
Azure Cache for Redis

Forward-looking answer:
Know it, but build new designs around Azure Managed Redis.
```

---

### **Strong interview answer**

> “Azure Cache for Redis is Microsoft's managed in-memory Redis service traditionally used to reduce application latency and offload databases by storing frequently accessed data in memory. A common design is cache-aside: the application checks Redis first, queries the database on a cache miss, then stores the result in Redis with an expiry. Redis can also be used for session state, counters and similar low-latency patterns. One important current point is that Azure Cache for Redis is being retired, so for new Azure designs I would use Azure Managed Redis and migrate existing Azure Cache for Redis workloads according to Microsoft's retirement timeline.”

**Memory line:**
**Redis keeps hot data in memory so the application doesn't repeatedly hit the slower source of truth.**

**Interview trap:**
Do not treat a normal cache as automatically equivalent to a durable primary database.

**Keywords:**
Redis, in-memory cache, cache-aside, TTL, cache hit, cache miss, Azure Managed Redis

**Likely follow-ups:**

* What is cache-aside?
* What happens when cached data becomes stale?
* What is a cache stampede?
* What is replacing Azure Cache for Redis?

## **T22-M01. What is the difference between Azure SQL Database and SQL Managed Instance?**

**Answer:**
Both are **fully managed Azure SQL PaaS services**, but they target different workloads:

```text
Azure SQL Database
→ database-focused cloud-native PaaS
→ best fit for many new applications

Azure SQL Managed Instance
→ instance-focused PaaS
→ much higher SQL Server compatibility
→ best fit for many existing SQL Server migrations
```

Microsoft currently describes Managed Instance as providing **almost 100% SQL Server database-engine feature parity**, while SQL Database is optimized for modern cloud applications and offers models such as serverless, elastic pools, and Hyperscale. ([Microsoft Learn][7])

---

## **Core mental model**

### Azure SQL Database

```text
Logical SQL server
│
├── Database A
├── Database B
└── Database C
```

The primary management unit is:

```text
database
```

---

### SQL Managed Instance

```text
SQL Managed Instance
│
├── Database A
├── Database B
├── Database C
├── SQL Agent
└── richer instance-level capabilities
```

The service behaves much more like:

```text
managed SQL Server instance
```

while remaining PaaS.

---

## **1. New cloud app vs SQL Server migration**

Suppose I'm building:

```text
new SaaS API
new web application
microservice
```

with no special instance dependency.

I'd usually start by evaluating:

```text
Azure SQL Database
```

Suppose instead I'm migrating:

```text
15-year-old ERP
SQL Server Agent jobs
cross-database queries
instance-level dependencies
native backup/restore expectations
```

Then:

```text
SQL Managed Instance
```

is often the better candidate.

Microsoft specifically positions Managed Instance as the managed Azure SQL choice for many existing SQL Server migrations. ([Microsoft Learn][7])

---

## **2. SQL Server compatibility**

Managed Instance offers deeper compatibility for SQL Server features.

Examples can include:

```text
SQL Server Agent
cross-database functionality
instance-level configuration/features
native backup/restore migration scenarios
```

So:

```text
Legacy SQL Server application
      ↓
Managed Instance
      ↓
fewer application/database changes
```

SQL Database deliberately uses a more cloud-native database-level service model.

---

## **3. SQL Server Agent**

This is a very common interview differentiator.

```text
SQL Managed Instance
→ SQL Server Agent supported
```

while Azure SQL Database doesn't expose the same traditional full SQL Server Agent instance model.

If a legacy application relies heavily on jobs such as:

```text
nightly ETL
scheduled stored procedures
database maintenance jobs
```

that can strongly influence the Managed Instance decision.

---

## **4. Cross-database capabilities**

Suppose application queries depend heavily on:

```sql
SELECT ...
FROM SalesDB.dbo.Orders o
JOIN CustomerDB.dbo.Customers c
...
```

Traditional instance-level cross-database behavior is much closer to the Managed Instance model.

That can significantly reduce migration effort.

---

## **5. Networking**

Managed Instance is built around:

```text
native VNet deployment/integration
```

which is especially convenient for private enterprise migration patterns.

Azure SQL Database instead exposes a logical-server endpoint and can be made private using:

```text
Azure Private Endpoint / Private Link
```

So conceptually:

```text
SQL Database
→ public service endpoint model
  + optional Private Endpoint

Managed Instance
→ deeply VNet-integrated managed instance model
```

---

## **6. Scaling features**

Azure SQL Database has cloud-native deployment/scaling options such as:

```text
Single Database
Elastic Pool
Serverless
Hyperscale
```

depending on requirements.

For example, a SaaS provider with:

```text
500 tenant databases
```

may use:

```text
Elastic Pool
```

so many databases share a pool of compute.

Managed Instance is more naturally:

```text
instance capacity
→ databases hosted within it
```

Microsoft's current comparison lists autoscale specifically for SQL Database's serverless model, while Managed Instance uses reserved/provisioned compute that you resize rather than serverless autoscaling. ([Microsoft Learn][8])

---

## **7. Geo-replication differs**

Azure SQL Database supports:

```text
Active geo-replication
```

at database level.

Managed Instance instead commonly uses:

```text
failover groups
```

for cross-region managed-instance DR.

Microsoft's current feature comparison explicitly lists Active geo-replication for SQL Database and failover groups as the Managed Instance alternative. ([Microsoft Learn][8])

---

## **8. Both are still PaaS**

This is important.

Both remove a lot of infrastructure work:

```text
OS management
SQL installation
platform patching
underlying HA
automated backups
```

So:

```text
SQL Database
≠ PaaS while MI = IaaS
```

Both are PaaS.

Microsoft states that both services reduce administration because you don't manage the VMs, OS, database software, underlying HA, or backup infrastructure. ([Microsoft Learn][7])

---

## **9. When SQL Server on VM is still needed**

Suppose the application needs:

```text
OS-level access
unsupported SQL Server feature
custom agents/drivers
specific Windows integration
absolute full SQL Server control
```

Then:

```text
SQL Server on Azure VM
```

may be more appropriate.

Decision continuum:

```text
Most managed
     ↑
Azure SQL Database

SQL Managed Instance

SQL Server on Azure VM
     ↓
Most control
```

---

## **Comparison table**

| Area                             | Azure SQL Database               | SQL Managed Instance          |
| -------------------------------- | -------------------------------- | ----------------------------- |
| Service model                    | PaaS                             | PaaS                          |
| Main scope                       | Database                         | Managed instance              |
| Best for                         | New/cloud-native apps            | Existing SQL Server migration |
| SQL Server compatibility         | High                             | **Near-full**                 |
| SQL Server Agent                 | Not traditional full Agent model | **Yes**                       |
| Cross-DB instance behavior       | More constrained                 | Strong support                |
| Elastic pools                    | **Yes**                          | No equivalent model           |
| Serverless                       | **Available**                    | No                            |
| Hyperscale                       | **Available**                    | Different scaling model       |
| Native VNet instance model       | No                               | **Yes**                       |
| Private connectivity             | Private Endpoint                 | Native VNet architecture      |
| Migration effort for legacy apps | Potentially more                 | Often less                    |

---

### **Strong interview answer**

> “Both Azure SQL Database and SQL Managed Instance are managed PaaS databases, but Azure SQL Database is optimized for modern database-level cloud applications, while Managed Instance is designed for workloads that need much greater SQL Server instance compatibility. SQL Database gives me capabilities such as elastic pools, serverless and Hyperscale. Managed Instance supports more traditional SQL Server instance features such as SQL Server Agent and richer cross-database behavior and has native VNet integration. For a new SaaS application I would generally evaluate SQL Database first; for a legacy SQL Server application that I want to migrate with minimal changes, Managed Instance is often the better fit.”

**Memory line:**
**SQL Database = cloud-native database PaaS; Managed Instance = SQL Server-like instance PaaS.**

**Interview trap:**
Do not say Managed Instance is a VM. It's still **PaaS**.

**Keywords:**
Azure SQL Database, Managed Instance, PaaS, SQL Agent, cross-database, serverless, elastic pool, migration

**Likely follow-ups:**

* When would you still use SQL Server on Azure VM?
* Does Managed Instance support SQL Agent?
* Which is better for a new SaaS application?
* How do their DR options differ?

# **T22-M02. How can Azure SQL be accessed privately?**

**Answer:**
For **Azure SQL Database**, the standard secure design is to create an **Azure Private Endpoint** for the logical SQL server using Azure Private Link, configure the corresponding **Private DNS zone**, and then disable public network access.

The resulting path is:

```text
Application
     ↓
Azure VNet
     ↓
Private DNS
     ↓
Private Endpoint
10.x.x.x
     ↓
Azure Private Link
     ↓
Azure SQL Database
```

A Private Endpoint places a **private IP from your VNet** in front of the Azure SQL service. Microsoft explicitly supports Azure SQL Database through Private Link, and current guidance recommends disabling public access when private endpoints are used. ([Microsoft Learn][9])

---

## **1. Create the Private Endpoint**

Suppose:

```text
SQL logical server:
sql-prod-01.database.windows.net
```

I create:

```text
Private Endpoint:
pe-sql-prod

Subnet:
snet-private-endpoints

Private IP:
10.20.3.5
```

Target:

```text
Microsoft.Sql/servers
subresource = sqlServer
```

Microsoft's current Private Endpoint tutorial uses exactly this `SqlServer` subresource model. ([Microsoft Learn][10])

---

## **2. Configure Private DNS**

The standard Azure SQL Private Link DNS zone is:

```text
privatelink.database.windows.net
```

Microsoft's current Private Endpoint DNS documentation lists:

```text
Azure SQL Database
→ privatelink.database.windows.net
```

as the corresponding Private DNS zone. ([Microsoft Learn][11])

Then link that zone to the VNet.

---

## **3. The application still uses the normal SQL hostname**

This is a very important interview point.

My connection string should still use:

```text
sql-prod-01.database.windows.net
```

**not**:

```text
10.20.3.5
```

and generally not:

```text
sql-prod-01.privatelink.database.windows.net
```

directly.

DNS does this internally:

```text
sql-prod-01.database.windows.net
       ↓ CNAME
sql-prod-01.privatelink.database.windows.net
       ↓ A
10.20.3.5
```

Microsoft explicitly states that SQL clients should continue using:

```text
<server>.database.windows.net
```

and that connecting directly to the Private Link hostname or private IP fails by design because the SQL Gateway relies on the proper server FQDN. ([Microsoft Learn][9])

---

## **4. Verify DNS from the workload**

From an Azure VM or appropriate troubleshooting pod:

```bash
nslookup sql-prod-01.database.windows.net
```

Expected:

```text
sql-prod-01.database.windows.net
      ↓
sql-prod-01.privatelink.database.windows.net
      ↓
10.20.3.5
```

Microsoft's current tutorial uses this exact style of `nslookup` validation and expects the private endpoint's private IP. ([Microsoft Learn][10])

---

## **5. Disable public network access**

Once private connectivity is validated:

```text
Azure SQL logical server
       ↓
Public network access
       ↓
Disabled
```

Now:

```text
Internet
   ↓
public SQL endpoint
   ↓
DENIED
```

while:

```text
VNet
 ↓
Private Endpoint
 ↓
SQL
```

continues working.

Microsoft says that when Public network access is disabled, connections through public endpoints are rejected and only private endpoint connectivity is allowed. ([Microsoft Learn][12])

---

## **6. Private Endpoint vs firewall rule**

This distinction is crucial.

### Public firewall rule

```text
Client public IP
      ↓
Azure SQL public endpoint
      ↓
SQL firewall allows IP
```

The SQL service is still accessed via its:

```text
public endpoint
```

although access is restricted.

---

### Private Endpoint

```text
Application
     ↓
VNet
     ↓
10.x private endpoint
     ↓
Private Link
     ↓
Azure SQL
```

Now the connectivity path uses a private IP within the VNet.

---

## **7. Private Endpoint vs Service Endpoint**

Another common interview trap.

A **Virtual Network service endpoint / VNet firewall rule** can restrict Azure SQL public-service access to selected subnets.

Conceptually:

```text
Subnet
   ↓
Azure backbone
   ↓
SQL public service endpoint
```

but Azure SQL still uses its service/public endpoint model.

Private Endpoint:

```text
Subnet
   ↓
private IP
10.x.x.x
   ↓
Private Link
   ↓
SQL
```

So:

```text
Service Endpoint
≠ Private Endpoint
```

If the requirement is:

> “The database must have no public network exposure.”

I prefer:

```text
Private Endpoint
+
Public network access disabled
```

## **9. Hub-and-spoke DNS**

Enterprise setup:

```text
             Hub
              │
        DNS Private Resolver
              │
      ┌───────┼─────────┐
      ↓       ↓         ↓
   Spoke A  Spoke B   On-prem
```

Private DNS can be centrally managed so all application networks resolve:

```text
*.database.windows.net
```

correctly through the private link DNS path.

For hybrid environments:

```text
On-prem DNS
     ↓ conditional forwarding
Azure DNS Private Resolver
     ↓
Private DNS
     ↓
SQL Private Endpoint
```

is a common architecture.

## **10. Network path still must work**

Private Endpoint existing doesn't automatically mean connectivity succeeds.

I still verify:

```text
DNS
 ↓
correct private IP?

Routing
 ↓
correct path?

NSG / firewall
 ↓
TCP 1433 allowed?

SQL authentication
 ↓
valid identity?
```

Troubleshooting order:

```text
Name resolution
     ↓
TCP connectivity
     ↓
TLS
     ↓
Authentication
     ↓
Database authorization
```

## **What about SQL Managed Instance?**

SQL Managed Instance has a different networking architecture.

It is designed with:

```text
native VNet integration
```

rather than Azure SQL Database's logical-server + Private Endpoint model.

So if an interviewer says simply:

> “Azure SQL”

I clarify mentally which product we're discussing:

```text
Azure SQL Database
→ Private Endpoint is common pattern

SQL Managed Instance
→ natively deployed/integrated into VNet
```

### **Production design**

```text
                    Application VNet
                           │
                     AKS / App Service
                           │
                     Private DNS
                           │
          sql-prod.database.windows.net
                           │
                           ↓
                  Private Endpoint
                     10.20.3.5
                           │
                      Private Link
                           │
                           ↓
                   Azure SQL Database

Public Network Access:
DISABLED
```

---

### **Strong interview answer**

> “For Azure SQL Database, I would create a Private Endpoint for the SQL logical server in an application or private-endpoint subnet, integrate it with the `privatelink.database.windows.net` Private DNS zone, and link that zone to the required VNets. Applications continue using the normal `<server>.database.windows.net` FQDN, but inside the VNet DNS resolves it through the Private Link name to the private endpoint's RFC1918 address. Once connectivity is verified, I disable public network access on the SQL logical server. I distinguish this from a service endpoint or firewall rule, which can restrict public-service access but doesn't give the SQL service a private endpoint in my VNet.”

**Memory line:**
**Private Azure SQL = Private Endpoint + Private DNS + public access disabled.**

**Interview trap:**
Do **not** put the private IP directly in the SQL connection string. Use:

```text
<server>.database.windows.net
```

and let Private DNS resolve it correctly. ([Microsoft Learn][9])
