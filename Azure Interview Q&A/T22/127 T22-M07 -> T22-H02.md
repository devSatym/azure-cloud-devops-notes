## **T22-M07. What is Cosmos DB partitioning?**

**Answer:**
Cosmos DB partitioning is the mechanism Azure Cosmos DB uses to **divide a large container's data and throughput across multiple partitions so the database can scale horizontally**.

Instead of eventually hitting the limits of one database server:

```text
Large Cosmos container
        ↓
partition key values
        ↓
Logical partitions
        ↓
Physical partitions
        ↓
Azure distributes storage + RU/s
```

Microsoft states that Cosmos DB automatically partitions containers as their **storage or provisioned throughput grows**. ([Microsoft Learn][1])

---

### **Logical partitions**

A **logical partition** contains all items that have the same partition-key value.

Suppose an `Orders` container uses:

```text
/customerId
```

as its partition key.

Data:

```text
customerId = C001
├── order-1
├── order-2
└── order-3

customerId = C002
├── order-4
└── order-5

customerId = C003
└── order-6
```

Then Cosmos DB creates logical partitions conceptually like:

```text
Logical Partition C001
Logical Partition C002
Logical Partition C003
```

Microsoft defines a logical partition exactly this way: items sharing one partition-key value belong to the same logical partition. ([Microsoft Learn][1])

---

### **Logical partition limits**

For a normal single-level partition key, one logical partition currently supports up to:

```text
20 GB data
```

and because one logical partition maps to a single physical partition, it is also bounded by the physical partition's throughput ceiling of:

```text
10,000 RU/s
```

Microsoft currently documents both limits. ([Microsoft Learn][1])

This matters enormously.

If I choose:

```text
partition key = /country
```

and 80% of my users are in:

```text
India
```

then one logical partition:

```text
India
```

could become enormous and extremely busy.

That's a poor partition strategy for a very large workload.

---

### **Physical partitions**

Physical partitions are internal Cosmos DB infrastructure.

Conceptually:

```text
Logical partitions

C001 ──┐
C002 ──┼──→ Physical Partition 1
C003 ──┘

C004 ──┐
C005 ──┼──→ Physical Partition 2
C006 ──┘
```

You don't manually create or manage these physical partitions.

Cosmos DB manages:

```text
creation
splitting
placement
replicas
redistribution
```

automatically.

Microsoft currently documents that each physical partition can store up to **50 GB** and support up to **10,000 RU/s**, and that Cosmos DB automatically adds/splits physical partitions as required. ([Microsoft Learn][1])

---

### **Example: throughput distribution**

Suppose my container has:

```text
30,000 RU/s
```

and Cosmos DB currently has three physical partitions.

Conceptually:

```text
30,000 RU/s
     ↓
┌──────────┬──────────┬──────────┐
│ 10k RU/s │ 10k RU/s │ 10k RU/s │
│    P1    │    P2    │    P3    │
└──────────┴──────────┴──────────┘
```

Provisioned throughput is distributed across physical partitions.

Now imagine almost all application requests target:

```text
customerId = C001
```

and C001 lives on P1.

Traffic:

```text
P1 → needs 20k RU/s
P2 → needs 2k
P3 → needs 1k
```

But P1 cannot simply borrow all unused capacity from P2/P3 in the ordinary partition distribution model.

Result:

```text
P1
→ hot partition
→ 429 rate limiting

while

P2/P3
→ underused
```

This is why a partitioning problem can happen even when **total provisioned RU/s looks sufficient**. Microsoft specifically warns that uneven request distribution can create hot partitions, throttling, and inefficient throughput utilization. ([Microsoft Learn][1])

---

### **What is a hot partition?**

A hot partition is one receiving a disproportionate amount of:

```text
requests
RU consumption
writes
or data
```

compared with the others.

Example:

```text
Partition key = /tenantId

Tenant A
→ 60% of all traffic

10,000 other tenants
→ remaining 40%
```

Even though `/tenantId` has high cardinality, Tenant A itself can still become:

```text
hot
```

This is why partition-key design requires understanding **both cardinality and workload distribution**.

---

### **Partitioning affects queries too**

Suppose `/customerId` is the partition key.

Query:

```sql
SELECT *
FROM c
WHERE c.customerId = "C001"
```

Cosmos DB knows which partition contains that customer.

Conceptually:

```text
Query
 ↓
Partition C001 only
```

This is efficient.

But:

```sql
SELECT *
FROM c
WHERE c.status = "pending"
```

without a customer/partition-key filter may require:

```text
P1
P2
P3
P4
...
```

a **cross-partition query**.

That can increase:

```text
latency
RU consumption
```

as the container grows.

Microsoft recommends selecting partition keys that not only distribute writes/storage well but also align with common query predicates. ([Microsoft Learn][1])

---

### **Transactions are also partition-scoped**

Another important Cosmos DB detail:

```text
multi-item ACID transaction
```

using stored procedures/triggers is scoped to:

```text
one logical partition
```

For example:

```text
Customer C001
├── order A
├── order B
└── order C
```

can participate in partition-scoped transactional operations more naturally because they share:

```text
customerId = C001
```

Microsoft explicitly states that stored procedures and triggers execute within a single logical partition. ([Microsoft Learn][1])

---

### **Hierarchical partitioning**

If one logical grouping can itself become too large, Cosmos DB now supports **hierarchical partition keys** for the API for NoSQL.

Example:

```text
TenantId
   ↓
UserId
   ↓
OrderId
```

Microsoft currently supports up to **three partition-key hierarchy levels**. This can allow a top-level grouping such as a large tenant to scale beyond the traditional single logical-partition 20-GB/10,000-RU/s limitations while retaining useful query locality by prefix. ([Microsoft Learn][2])

---

### **Strong interview answer**

> “Cosmos DB partitioning is how Cosmos DB scales horizontally. Items with the same partition-key value form a logical partition, and Cosmos DB automatically maps logical partitions across internal physical partitions. As storage or throughput grows, Cosmos DB creates and splits physical partitions automatically. The critical design decision is therefore the partition key: if traffic or data is unevenly concentrated in a small number of logical partitions, those partitions can become hot and get throttled even when the container has plenty of total RU/s. Good partitioning distributes both storage and request-unit consumption while also aligning with common query patterns.”

**Memory line:**
**Logical partitions come from my partition key; physical partitions are Cosmos DB's automatically managed scale units.**

**Interview trap:**
Do not say Cosmos DB automatically fixes a bad logical partition key by splitting that one logical partition across arbitrary physical partitions.

**Keywords:**
logical partition, physical partition, horizontal scaling, RU/s, hot partition, cross-partition query, 20 GB

**Likely follow-ups:**

* What is a Cosmos DB partition key?
* What causes a hot partition?
* Logical vs physical partition?
* Why are cross-partition queries expensive?

# **T22-M08. What is a Cosmos DB partition key?**

**Answer:**
A Cosmos DB **partition key is the item property—or hierarchy of properties—that Cosmos DB uses to determine how data is grouped into logical partitions and distributed across physical partitions**.

For example:

```json
{
  "id": "order-1001",
  "customerId": "customer-501",
  "amount": 500
}
```

If I configure:

```text
Partition key path:
/customerId
```

then:

```text
customerId = customer-501
```

is that item's partition-key value.

All items with the same value belong to the same logical partition. ([Microsoft Learn][1])

---

### **Why partition-key choice matters so much**

It influences:

```text
scalability
throughput distribution
storage distribution
query cost
query latency
transaction boundaries
hot partitions
```

So selecting:

```text
/customerId
```

versus:

```text
/status
```

is not just a schema preference.

It changes the database's scaling characteristics.

---

### **A good partition key should have high cardinality**

Suppose:

```text
/status
```

has only:

```text
pending
paid
failed
cancelled
```

Then the entire container has roughly four logical partition-key values.

If 70% of orders are:

```text
paid
```

you may create:

```text
one huge/hot logical partition
```

Microsoft specifically warns against low-cardinality keys such as `status`, `type`, or `country` for large workloads because they can produce uneven storage and RU distribution. ([Microsoft Learn][3])

---

### **Better example**

Suppose I have:

```text
10 million customers
```

and choose:

```text
/customerId
```

Now there can be millions of possible partition-key values:

```text
C000001
C000002
C000003
...
```

That's:

```text
high cardinality
```

which gives Cosmos DB much more opportunity to distribute data.

---

### **But high cardinality alone is not enough**

Imagine:

```text
partition key = random GUID
```

This distributes writes beautifully.

But the application always asks:

```sql
WHERE customerId = ?
```

and never knows the random GUID.

Then almost every query becomes:

```text
cross-partition
```

Microsoft explicitly warns that a high-cardinality key that doesn't align with query patterns can still be a poor design. ([Microsoft Learn][3])

So a good key needs both:

```text
good distribution
+
query alignment
```

---

### **Good design criteria**

The key should ideally:

```text
have many distinct values
distribute storage evenly
distribute RU consumption evenly
appear in frequent query filters
avoid a few extremely hot values
```

Microsoft's current guidance emphasizes high cardinality and even distribution of both storage and RU consumption. ([Microsoft Learn][1])

---

### **Example: e-commerce orders**

Suppose access patterns are:

```text
Get customer's orders
Get one order
Write customer order
```

Possible partition key:

```text
/customerId
```

Now:

```text
Customer C123
├── Order 1
├── Order 2
├── Order 3
└── Order 4
```

Query:

```sql
SELECT *
FROM c
WHERE c.customerId = "C123"
```

can be routed efficiently.

But I must check:

```text
Can one customer exceed 20 GB?
Can one customer exceed 10k RU/s?
Are there giant enterprise customers?
```

If yes, I might need:

```text
synthetic key
or
hierarchical partition key
```

instead.

---

### **Bad example: current date**

Suppose:

```text
partition key = /date
```

and every new order today has:

```text
date = 2026-09-05
```

All today's writes converge on:

```text
one logical partition
```

creating a classic:

```text
hot partition
```

even though tomorrow's data gets a different value.

---

### **Synthetic partition key**

Sometimes no natural property gives the right distribution.

You can create something like:

```text
customerId + yyyyMM
```

Example:

```text
C123-202609
C123-202610
```

This spreads one giant customer's data across multiple logical partitions.

Trade-off:

```text
better write/storage distribution
↕
queries may need multiple partitions
```

Microsoft includes synthetic partition keys among the recommended strategies when a single field doesn't satisfy distribution and query requirements. ([Microsoft Learn][3])

---

### **Hierarchical partition key**

Another current option:

```text
/customerId
/orderId
```

or:

```text
/tenantId
/userId
/sessionId
```

Cosmos DB currently supports up to three hierarchy levels for NoSQL hierarchical partition keys. ([Microsoft Learn][2])

This can be useful for large multitenant workloads where:

```text
one tenant
```

may itself exceed traditional logical-partition scaling limits.

---

### **Partition key is effectively immutable for an item**

Once an item exists, you cannot simply replace it and change its partition-key value in place.

To move it conceptually:

```text
Old partition
     ↓
create new item
in new partition
     ↓
delete old item
```

Microsoft explicitly notes that changing a partition-key value requires creating the item under the new key and deleting the original. ([Microsoft Learn][1])

That's why partition-key design should happen carefully **before huge amounts of data exist**.

---

### **Point reads use ID + partition key**

For Cosmos DB point reads, the efficient lookup is essentially:

```text
id
+
partition key
```

Example:

```text
id = order-1001
customerId = C123
```

Then Cosmos DB can directly locate the item rather than searching across partitions.

This is one reason knowing your partition key is important for efficient data access.

---

### **Strong interview answer**

> “A Cosmos DB partition key is the property used to group items into logical partitions and ultimately distribute data and throughput across Cosmos DB's physical partitions. I want a key with high cardinality and an even distribution of both data and request-unit consumption, but it should also match my dominant query patterns so I avoid excessive cross-partition queries. For example, `customerId` can be a good choice if most operations are customer-scoped, provided one customer can't become disproportionately large or hot. I avoid low-cardinality values such as status or country for large workloads, and for very large tenants I would evaluate synthetic or hierarchical partition keys.”

**Memory line:**
**A good partition key spreads writes evenly but keeps common reads targeted.**

**Interview trap:**
Do not answer only:

> “Choose a high-cardinality field.”

A random high-cardinality key can still make nearly every query cross-partition.

**Keywords:**
partition key, high cardinality, hot partition, query alignment, synthetic key, hierarchical partition key

**Likely follow-ups:**

* Can you change the partition key later?
* Why is `/status` usually bad?
* What is a synthetic partition key?
* What is a hot partition?

## **T22-H01. How would you design database high availability across Azure regions?**

**Answer:**
I would design database HA in **two layers**:

```text
1. In-region HA
   → survive node / Availability Zone failure

2. Cross-region DR
   → survive complete Azure region failure
```

Then I choose the exact database feature based on:

```text
RTO
RPO
database technology
consistency requirements
read/write topology
cost
```

For a production Azure SQL Database workload, a strong design could be:

```text
                    Global application routing
                             │
               ┌─────────────┴─────────────┐
               ↓                           ↓
        Primary Region                DR Region
             │                            │
        zone-resilient                application
        application                     stack
             │                            │
             ↓                            ↓
       Azure SQL DB ───── async ───→ Geo-secondary
             │
          zone HA
```

with an Azure SQL **Failover Group** providing stable database connection endpoints and coordinated failover.

Azure SQL currently supports both **Active geo-replication** for individual databases and **Failover Groups** for groups of databases with listener endpoints. ([Microsoft Learn][4])

---

### **1. Start with RTO and RPO**

I never start with:

> “Let's deploy databases in three regions.”

I start with:

```text
RTO:
How quickly must service recover?

RPO:
How much data can we lose?
```

Example:

```text
RTO = 10 minutes
RPO = 5 minutes
```

This might justify:

```text
hot/warm secondary
+
continuous geo-replication
```

A workload with:

```text
RTO = 24 hours
RPO = 12 hours
```

may be adequately protected using:

```text
geo-redundant backups
+
restore
```

at dramatically lower cost.

---

### **2. Protect against zone failure inside the primary region**

Cross-region replication shouldn't replace local HA.

I want:

```text
Primary region
│
├── Zone 1
├── Zone 2
└── Azure-managed database HA
```

because:

```text
single VM/node failure
or
single AZ failure
```

shouldn't immediately become:

```text
cross-region DR incident
```

For example, Azure Database for PostgreSQL Flexible Server supports zone-redundant HA with synchronous replication to a standby in another Availability Zone and automatic failover with zero committed-data loss for the zone-level HA event. ([Microsoft Learn][5])

---

### **3. Use asynchronous replication across regions**

Across large geographic distances, synchronous writes would significantly increase application latency.

Therefore cross-region DR commonly uses:

```text
Primary
    ↓
asynchronous replication
    ↓
secondary region
```

Trade-off:

```text
good production write latency
       ↕
possible replication lag
```

That means:

```text
forced regional failover
→ potentially non-zero RPO
```

For Azure SQL Active geo-replication, the secondary is continuously synchronized and can be promoted after a regional failure. ([Microsoft Learn][4])

---

### **4. Azure SQL: Failover Group for an application with multiple databases**

Suppose the application uses:

```text
Orders DB
Payments DB
Customers DB
```

Instead of managing each independently:

```text
DB1 failover
DB2 failover
DB3 failover
```

I would strongly evaluate:

```text
Azure SQL Failover Group
```

Architecture:

```text
Primary SQL logical server
│
├── Orders
├── Payments
└── Customers
      │
      │ geo-replication
      ↓
Secondary SQL logical server
│
├── Orders
├── Payments
└── Customers
```

Failover Groups support:

```text
grouped database failover
stable connection endpoints
primary/secondary role management
```

Microsoft explicitly says Failover Groups build on Active geo-replication and provide connection endpoints that automatically direct connections to the current primary. ([Microsoft Learn][4])

---

### **5. Stable endpoint is extremely valuable**

Application connection:

```text
orders-prod.database.windows.net
```

shouldn't require an emergency deployment just because the DB moved regions.

With the appropriate failover-group listener:

```text
Application
     ↓
stable listener
     ↓
current primary
```

After failover:

```text
Application
     ↓
same listener
     ↓
former secondary
```

This reduces application-level DR complexity.

---

### **6. PostgreSQL design differs**

If the workload uses Azure Database for PostgreSQL Flexible Server, I might use:

```text
Primary region
→ zone-redundant HA

Secondary region
→ cross-region read replica
```

The cross-region replica is asynchronous.

During a regional disaster:

```text
primary unavailable
      ↓
promote cross-region replica
      ↓
new writable PostgreSQL server
```

Microsoft currently documents cross-region read replicas as a DR option and notes that asynchronous replication means they can lag the primary. ([Microsoft Learn][6])

Current PostgreSQL guidance estimates cross-region read-replica DR RPO commonly in the range of seconds to minutes, with data-loss risk dependent on replication lag. ([Microsoft Learn][7])

---

### **7. Backups are still mandatory**

Replication is **not backup**.

Suppose:

```sql
DELETE FROM customers;
```

runs successfully against the primary.

Then:

```text
Primary
DELETE
   ↓
replication
   ↓
Secondary
DELETE
```

Both copies now contain the mistake.

Therefore:

```text
HA/replication
→ infrastructure/region failure

Backups/PITR
→ corruption, deletion,
   operational recovery
```

I need both.

For PostgreSQL, Azure supports geo-redundant backups that can be restored to another region as a slower but less expensive regional-recovery option. ([Microsoft Learn][6])

---

### **8. Prepare the application region too**

Database HA alone doesn't create application HA.

Bad:

```text
Secondary database ✓

Secondary application ✗
DNS ✗
Key Vault permissions ✗
Private networking ✗
```

Better:

```text
DR Region
├── application compute
├── database replica
├── Private Endpoints / network
├── DNS
├── identities/RBAC
├── secrets/configuration
└── monitoring
```

Then a regional failover is an **application recovery**, not merely a database promotion.

---

### **9. Private networking must survive failover**

If SQL is private:

```text
Primary app
 ↓
Private DNS
 ↓
Primary SQL Private Endpoint
```

I also need the DR-side network architecture prepared.

Questions:

```text
Does DR VNet exist?
Is Private DNS correct?
Are Private Endpoints prepared?
Do NSGs/routes allow connectivity?
Can on-prem DNS resolve the DR path?
```

A database that successfully fails over but cannot be resolved/reached by the application still fails the business RTO.

---

### **10. Authentication/authorization must exist in DR**

Likewise:

```text
Managed Identity
Entra authentication
database users
database/server permissions
```

must work after failover.

I test:

```text
DR application
→ authenticates
→ opens DB connection
→ performs expected transaction
```

before declaring the architecture production-ready.

---

### **11. Planned failover testing**

I would periodically perform:

```text
DR drill
     ↓
planned DB failover
     ↓
application routing switch
     ↓
measure actual RTO
     ↓
validate data/RPO
     ↓
fail back
```

Azure SQL supports manual region-failure simulation through no-data-loss or forced failover operations, which makes DR testing practical. ([Microsoft Learn][4])

---

### **12. Don't over-engineer every database**

Tier databases by criticality:

```text
Tier 0:
payments
→ zone HA + cross-region hot replica
→ aggressive RTO/RPO

Tier 1:
customer portal
→ zone HA + DR replica

Tier 2:
internal system
→ zone HA + geo-backup

Tier 3:
dev/test
→ backup only
```

Because:

```text
more availability
=
more replicated infrastructure
=
more cost
```

The architecture should follow business requirements.

---

### **Strong interview answer**

> “I design database availability in two layers. First, I use in-region HA—preferably zone redundancy—to survive node and Availability Zone failures without invoking disaster recovery. Second, for workloads whose RTO and RPO require regional protection, I maintain an asynchronous replica in another Azure region. For Azure SQL Database with multiple application databases, I would typically evaluate a Failover Group because it builds on geo-replication, can fail databases over together, and provides stable connection endpoints. For PostgreSQL Flexible Server I can combine zone-redundant HA in the primary region with a cross-region read replica that can be promoted during a regional disaster. I also retain backups because replication doesn't protect against logical corruption or accidental deletion, and I prebuild networking, identities, DNS and application capacity in the secondary region. Finally, I regularly test planned failover and measure actual RTO and RPO.”

**Memory line:**
**Zones handle local HA; cross-region replicas handle regional DR; backups handle history and logical mistakes.**

**Interview trap:**
Do not say:

```text
Cross-region replica
=
zero-data-loss under every regional failure
```

Cross-region replication is commonly asynchronous, so forced failover can have a non-zero RPO.

**Keywords:**
zone redundancy, geo-replication, Failover Group, read replica, RTO, RPO, asynchronous replication, DR

**Likely follow-ups:**

* Failover Group vs Active geo-replication?
* Why do you still need backups?
* Planned vs forced failover?
* Why use synchronous replication within a region but asynchronous across regions?

## **T22-H02. What would you investigate if database CPU is low but application requests are slow?**

**Answer:**
Low database CPU tells me one important thing:

```text
The database probably isn't
CPU-saturated.
```

It does **not** tell me:

```text
The database is healthy.
```

Queries can spend most of their time **waiting instead of executing on CPU**.

So my investigation becomes:

```text
Where is the latency?

Application?
Connection pool?
Network?
Database waits?
Blocking?
I/O?
Query plan?
External dependency?
```

Microsoft's Azure SQL troubleshooting guidance separates query-performance problems into running problems and **waiting problems**, including locking, I/O, `tempdb`, and memory-grant waits. ([Microsoft Learn][8])

---

### **1. Break down end-to-end latency first**

Suppose API latency is:

```text
2.5 seconds
```

I want to know:

```text
HTTP request received
      ↓
connection-pool wait     1.5 s?
      ↓
network/TLS              100 ms?
      ↓
SQL execution            80 ms?
      ↓
application processing   800 ms?
```

If SQL execution is only:

```text
80 ms
```

then scaling the database CPU is completely the wrong fix.

I use:

```text
Application Insights traces
OpenTelemetry traces
database query duration
dependency telemetry
```

to separate:

```text
application latency
from
database latency
```

---

### **2. Check connection-pool exhaustion**

This is especially important for AKS.

Suppose:

```text
Database CPU = 15%
```

but every application request waits:

```text
2 seconds
```

to get a free pooled connection.

Architecture:

```text
Request
   ↓
connection pool
   ↓
NO FREE CONNECTION
   ↓
wait
   ↓
eventually SQL
   ↓
query executes in 20 ms
```

Database CPU remains low because requests aren't even reaching it fast enough.

I inspect:

```text
pool utilization
pool wait duration
active/idle connections
connection timeouts
connection leaks
max pool size
pod count × pool size
```

Microsoft recommends correct pooling because connection reuse reduces latency, while pool configuration must reflect concurrency and workload requirements. ([Microsoft Learn][9])

---

### **3. Look for blocking**

Low CPU + slow queries is a classic blocking signature.

Example:

```text
Session 51

BEGIN TRANSACTION
UPDATE Orders...
     ↓
holds lock for 30 sec
```

Meanwhile:

```text
Session 61 ─┐
Session 62 ─┼─→ WAITING FOR LOCK
Session 63 ─┘
```

Waiting queries consume very little CPU.

So:

```text
CPU = low
latency = terrible
```

I check:

```text
sys.dm_exec_requests
sys.dm_exec_sessions
sys.dm_tran_locks
blocking_session_id
Query Store waits
```

The objective is to find:

```text
head blocker
```

not kill random blocked sessions.

Microsoft's Azure SQL guidance recommends finding the head blocker, determining which transaction holds locks for too long, and then correcting the transaction/query behavior. ([Microsoft Learn][10])

---

### **4. Check wait statistics**

Instead of guessing, ask:

> What is SQL waiting for?

Useful Azure SQL sources include:

```text
Query Store wait statistics
sys.dm_db_wait_stats
sys.dm_os_waiting_tasks
```

Microsoft specifically recommends these for distinguishing categories of query waits. ([Microsoft Learn][8])

Examples:

```text
LCK_*
→ blocking/locks

PAGEIOLATCH_*
→ storage/page I/O

WRITELOG
→ transaction-log write wait

RESOURCE_SEMAPHORE
→ memory grant

tempdb-related waits
→ spills/contention
```

This turns:

> “SQL feels slow.”

into:

> “Queries are waiting 80% of their time on locks.”

---

### **5. Check data I/O and log I/O—not only CPU**

Azure SQL can be constrained by another service-tier resource while CPU remains low.

Example:

```text
CPU         20%
Data I/O   100%
```

Then queries are spending their time:

```text
waiting for pages
```

rather than burning CPU.

Or:

```text
CPU       15%
Log IO    maxed
```

for a write-heavy workload.

Microsoft's Azure SQL DMV guidance explicitly includes separate diagnosis for CPU, I/O, `tempdb`, transactions, memory grants, connections, blocking, and query performance. ([Microsoft Learn][11])

So I inspect:

```text
CPU %
Data IO %
Log IO %
workers
sessions
storage latency
```

rather than just the CPU graph.

---

### **6. Check query plans**

A bad execution plan may still produce low overall CPU if:

```text
query waits on I/O
or
only a small number of slow queries run
```

I use:

```text
Query Store
```

to compare:

```text
current plan
vs
previous good plan
```

Potential causes:

```text
missing index
stale statistics
cardinality misestimate
parameter sensitivity
plan regression
large table scan
bad join strategy
```

Microsoft lists missing indexes, stale statistics, inaccurate cardinality estimates, and poor execution plans among common Azure SQL performance causes. ([Microsoft Learn][8])

---

### **7. Check `tempdb` spills**

Suppose query requests a large sort/hash but doesn't get enough memory:

```text
sort/hash
     ↓
doesn't fit memory
     ↓
spills to tempdb
     ↓
extra I/O
     ↓
slow query
```

CPU might remain fairly modest while latency rises.

I inspect:

```text
execution plan warnings
tempdb waits
memory grant behavior
```

Microsoft explicitly includes `tempdb` throughput and memory-grant problems among waiting-related Azure SQL bottlenecks. ([Microsoft Learn][8])

---

### **8. Check long transactions**

Even if the original query finished most of its work:

```text
BEGIN TRANSACTION
...
application waits on external API
...
COMMIT
```

the transaction can hold locks while doing almost no database CPU work.

Result:

```text
SQL CPU low
+
other requests blocked
+
application latency high
```

So I inspect:

```text
open transactions
transaction age
sleeping sessions with open transaction
```

rather than only currently running SQL.

---

### **9. Check networking and DNS**

If application is in:

```text
AKS Central India
```

and database is accidentally in:

```text
West Europe
```

each DB round trip incurs cross-region network latency.

An application performing:

```text
100 sequential queries
```

with an extra:

```text
100 ms RTT
```

could add roughly:

```text
10 seconds
```

even though:

```text
DB CPU ≈ almost nothing
```

I verify:

```text
application region
database region
DNS target
Private Endpoint IP
routes
Azure Firewall/NVA
connection RTT
```

---

### **10. Private Endpoint/DNS path**

A bad private-DNS configuration can cause an unexpected path:

```text
App
 ↓
SQL hostname
 ↓
public IP instead of private IP
 ↓
firewall/NVA/path
 ↓
higher latency / failures
```

So I check:

```bash
nslookup <server>.database.windows.net
```

from the actual workload environment.

Then:

```text
expected private IP?
```

If no:

```text
fix DNS/networking before query tuning
```

---

### **11. Check application query pattern**

The database may execute every query quickly, but the application may do:

```text
for each order:
    query customer
```

For 1,000 orders:

```text
1 query
+
1,000 child queries
```

This is the classic:

```text
N+1 query problem
```

If every query takes only:

```text
5 ms
```

then:

```text
1,000 × 5 ms
≈ 5 sec
```

and CPU can still look surprisingly low.

A distributed trace makes this obvious:

```text
HTTP request
├── SQL 5 ms
├── SQL 4 ms
├── SQL 6 ms
├── SQL 5 ms
├── ...
└── 1000 times
```

The fix is application/query redesign, not database scaling.

---

### **12. Check connection establishment**

If the app opens a fresh connection for every request:

```text
DNS
 ↓
TCP
 ↓
TLS
 ↓
Entra authentication
 ↓
SQL query
 ↓
close connection
```

connection setup may dominate the query itself.

Microsoft specifically recommends connection pooling to avoid repeated connection-establishment overhead. ([Microsoft Learn][9])

So I verify:

```text
pooling enabled?
connections reused?
pool fragmentation?
token auth handled correctly?
```

---

### **13. Check downstream dependencies too**

Maybe:

```text
Application request
      ↓
SQL query = 50 ms
      ↓
third-party API = 3 sec
```

and someone says:

> “The API uses SQL, so SQL must be slow.”

This is why I start with an end-to-end trace rather than assuming the database is guilty.

---

### **Diagnostic order**

```text
Slow API + low DB CPU
          ↓
Distributed trace:
where is time spent?
          ↓
 ┌────────┼─────────┐
 ↓        ↓         ↓
App    Network      DB
                   waits
                     ↓
       ┌─────────────┼──────────────┐
       ↓             ↓              ↓
    Blocking         I/O        Query plan
       ↓             ↓              ↓
 transactions    data/log IO    indexes/stats

Also:
connection pool
N+1 queries
tempdb/memory
cross-region latency
```

---

### **Strong interview answer**

> “Low database CPU doesn't mean the database is healthy; it often means requests are waiting rather than consuming CPU. I first use distributed tracing or dependency telemetry to determine whether the latency occurs before the query, during SQL execution, or afterward. If the database is slow, I inspect Query Store and wait statistics rather than looking only at CPU. I check blocking and long transactions, data and log I/O saturation, `tempdb` or memory-grant waits, and execution-plan regressions such as missing indexes or stale statistics. On the application side I check connection-pool exhaustion, connection leaks, excessive connection creation, and N+1 query patterns. I also verify DNS and network placement because a cross-region or incorrect Private Endpoint path can produce high latency while database CPU stays very low.”

**Memory line:**
**Low CPU + high latency usually means: find what the request is waiting on.**

**Interview trap:**
Do not immediately scale the database up because the application is slow. If CPU is low and the bottleneck is blocking, I/O, connection pooling, or network latency, larger compute may solve nothing.

**Keywords:**
wait statistics, Query Store, blocking, I/O, connection pool, execution plan, `tempdb`, N+1, network latency

**Likely follow-ups:**

* How would you detect blocking?
* What Azure SQL wait types would you inspect?
* How can AKS connection pooling make the API slow?
* How would you distinguish database latency from network latency?
