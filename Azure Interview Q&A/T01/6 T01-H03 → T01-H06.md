# 1. 🔴 M IMP — Azure Fundamentals, Architecture & Resource Hierarchy

## Hard

### **T01-H03. How would you separate development, staging, and production Azure environments?**

**Answer:**
For a production-grade setup, I would normally separate **development, staging, and production using different Azure subscriptions**, especially when I need strong isolation for security, policy, cost, quotas, and deployment permissions.

A typical structure could be:

```text
Management Group: Application Landing Zones
│
├── app-dev-sub
├── app-staging-sub
└── app-prod-sub
```

Microsoft's current Azure Landing Zone guidance recommends giving each application environment its own subscription where practical because this isolates security and policy controls and limits the blast radius of mistakes. ([Microsoft Learn][1])

Within each subscription, I would then use separate resource groups based on application lifecycle.

For example:

```text
app-prod-sub
├── rg-network-prod
├── rg-app-prod
├── rg-data-prod
└── rg-monitoring-prod
```

I would also keep the environments isolated at several other layers:

* **Identity:** separate groups, managed identities, or workload identities.
* **Terraform:** separate remote state for every environment.
* **CI/CD:** separate deployment identities and production approvals.
* **Secrets:** separate Key Vaults or strong environment-specific separation.
* **Networking:** separate VNets where appropriate.
* **Monitoring:** environment-aware logs and alerts.
* **RBAC:** developers can have broader access in dev but limited or just-in-time production access.
* **Policy:** production receives stricter controls.

Microsoft specifically recommends separate security configurations and identities for different application environments rather than sharing them across dev/test and production. ([Microsoft Learn][2])

**Example:**
My GitHub Actions deployment identities could be:

```text
github-app-dev
github-app-staging
github-app-prod
```

The dev identity can deploy only to the dev subscription, while the production identity can deploy only to production and may require an approval/environment protection gate before deployment.

The same Terraform modules can be reused across environments, but the **state, configuration, identities, and credentials remain isolated**.

**Important trade-off:**
Separate subscriptions are a strong default, but they are not mandatory for every application. Some services or deployment patterns can make a shared subscription more practical, so the architecture should reflect the workload requirements. Microsoft explicitly documents cases where multiple environments in one subscription can be appropriate. ([Microsoft Learn][1])

**Rule of thumb:**
**Reuse the IaC and deployment pattern; isolate the environment, state, identities, and permissions.**

**Interview trap:**
Do not say that creating:

```text
rg-dev
rg-staging
rg-prod
```

automatically provides strong environment isolation.

Resource groups provide management boundaries, but subscriptions provide stronger separation for governance, quotas, cost, and blast radius.

**Keywords:** environment isolation, subscriptions, separate Terraform state, RBAC, CI/CD identities, Key Vault, blast radius

**Likely follow-ups:**

* Would you always use one subscription per environment?
* Why should production have a separate deployment identity?
* Would you share a VNet between environments?
* How would you structure Terraform for these environments?

### **T01-H04. How would you design Azure resources for multiple business units while maintaining centralized governance?**

**Answer:**
I would use a **centralized-governance, delegated-ownership model**.

The central platform team controls the organization-wide guardrails at the **management-group level**, while each business unit receives its own workload subscriptions and controlled RBAC within those subscriptions.

A simplified hierarchy could look like:

```text
Tenant Root
│
├── Platform
│   ├── Identity Subscription
│   ├── Connectivity Subscription
│   ├── Management Subscription
│   └── Security Subscription
│
└── Landing Zones
    │
    ├── Business-Unit-A
    │   ├── App-A-Prod Subscription
    │   └── App-A-NonProd Subscription
    │
    └── Business-Unit-B
        ├── App-B-Prod Subscription
        └── App-B-NonProd Subscription
```

I would centralize things such as:

* Azure Policy
* security standards
* centralized networking
* Azure Firewall
* DNS
* monitoring standards
* Defender controls
* privileged-access policies
* mandatory tagging and regions

at the platform or management-group level.

Management groups exist specifically to organize and govern subscriptions at scale, with policies and RBAC inherited down the hierarchy. ([Microsoft Learn][3])

Then each business unit gets delegated access inside its own landing-zone subscription.

For example:

```text
Business Unit A DevOps Team
       │
       └── Contributor
           on App-A subscriptions only
```

They can manage their own workloads but cannot remove the enterprise policies inherited from higher management groups.

Microsoft's landing-zone guidance recommends placing application-level role assignments at subscription or resource-group scope while keeping policy controls at management-group scope. ([Microsoft Learn][2])

### **Shared platform services**

I would normally keep shared services in dedicated platform subscriptions:

**Connectivity subscription**

* hub VNets
* Azure Firewall
* ExpressRoute/VPN
* centralized DNS

**Management subscription**

* monitoring
* automation
* operational tooling

**Security subscription**

* enterprise security services where applicable

Workload subscriptions then consume those shared capabilities.

### **Why this model works**

It provides:

**Central team**
→ governance and security control

**Business units**
→ enough autonomy to deploy and operate workloads

without giving each team the ability to bypass enterprise requirements.

**Rule of thumb:**
**Centralize guardrails; delegate workload ownership.**

**Interview trap:**
I would not automatically create management groups purely because organizational departments exist.

Management groups should primarily represent **governance differences**. If several business units have exactly the same policy requirements, putting them under a common workload management group may be cleaner than creating unnecessary hierarchy. Microsoft's guidance recommends keeping management-group structures relatively flat. ([Microsoft Learn][3])

**Keywords:** centralized governance, delegated ownership, management groups, landing zones, Policy inheritance, platform subscriptions, RBAC

**Likely follow-ups:**

* Where would you put Azure Firewall?
* How would business units access centralized networking?
* Can application teams modify inherited Azure Policies?
* How would you onboard a new business unit?

### **T01-H05. What happens internally when you deploy a resource through ARM?**

**Answer:**
At a high level, an Azure resource deployment follows this flow:

```text
Client
  ↓
Authentication
  ↓
Azure Resource Manager
  ↓
Authorization / Governance
  ↓
Resource Provider
  ↓
Underlying Azure service
  ↓
Deployment state returned
```

Suppose I run:

```bash
az vm create ...
```

or deploy through Terraform or Bicep.

### **1. The client authenticates**

The tool obtains an identity token through Microsoft Entra ID.

The caller might be:

* a user,
* service principal,
* managed identity,
* or federated workload identity.

---

### **2. The request reaches Azure Resource Manager**

The request contains information such as:

* subscription,
* resource group,
* resource type,
* resource name,
* API version,
* desired configuration.

ARM acts as the Azure **control-plane gateway** for resource management.

---

### **3. Azure evaluates authorization**

Azure checks whether the identity has the required Azure RBAC action at the requested scope.

For example, creating a VM requires the appropriate `Microsoft.Compute` management permission.

Resource-provider permission strings follow a structure such as:

```text
Microsoft.Compute/virtualMachines/write
```

Azure resource-provider operations form the permissions used by Azure built-in and custom RBAC roles. ([Microsoft Learn][4])

---

### **4. Governance controls are evaluated**

The deployment may also be affected by controls such as:

* Azure Policy
* deny assignments
* resource locks
* subscription quotas
* regional restrictions

So having an RBAC role does not guarantee that the deployment will succeed.

---

### **5. ARM routes the request to the resource provider**

ARM identifies the namespace.

For example:

```text
Microsoft.Compute/virtualMachines
```

is handled through the `Microsoft.Compute` resource provider.

A networking resource might instead go through:

```text
Microsoft.Network
```

---

### **6. The resource provider provisions the resource**

The resource provider validates service-specific requirements and communicates with the underlying Azure infrastructure.

For a VM deployment, this can involve dependent resources such as:

* NIC
* disk
* VNet/subnet
* public IP
* VM compute capacity

ARM coordinates the management operations, but the individual resource providers implement service-specific provisioning.

---

### **7. Azure tracks the operation**

Many Azure deployments are asynchronous.

The API might initially return an accepted/provisioning state while Azure continues creating the resource.

Eventually the resource reaches a state such as:

```text
Succeeded
Failed
Updating
Deleting
```

### **Interview-ready summary**

I would describe it as:

> “The caller authenticates through Entra ID, sends a control-plane request to ARM, ARM evaluates authorization and governance, routes the request to the appropriate resource provider, and that provider provisions the underlying Azure service. ARM then exposes the deployment and provisioning state back to the client.”

**Memory flow:**
**Authenticate → ARM → Authorize/Govern → Resource Provider → Provision → Status**

**Interview trap:**
ARM does **not itself implement every Azure service**.

ARM is the management layer. Service-specific resource providers such as `Microsoft.Compute` or `Microsoft.Network` handle their respective resources.

**Keywords:** Entra authentication, ARM, Azure RBAC, Azure Policy, resource provider, API version, provisioning state

**Likely follow-ups:**

* Where is Azure Policy evaluated?
* What role does the resource provider play?
* What happens if the provider isn't registered?
* How is Terraform involved in this flow?

### **T01-H06. How do Azure resource-provider registration and subscription permissions affect resource deployment?**

**Answer:**
For an Azure resource deployment to succeed, two separate things must be true:

**1. The subscription must be able to use the required resource provider.**
**2. The deploying identity must have permission to perform the required operations.**

These are related, but they are not the same thing.

---

### **1. Resource-provider registration**

Azure services expose their ARM operations through resource-provider namespaces.

For example:

```text
Microsoft.Compute
Microsoft.Network
Microsoft.Storage
Microsoft.ContainerService
```

If I want to create AKS resources, Azure needs access to:

```text
Microsoft.ContainerService
```

within that subscription.

Provider registration effectively enables the subscription to work with that provider.

Some providers are registered by default, and Azure automatically registers some required providers when certain portal or ARM deployments are performed. Others may need explicit registration. ([Microsoft Learn][5])

I can check it using:

```bash
az provider show \
  --namespace Microsoft.ContainerService \
  --query registrationState
```

and register it with:

```bash
az provider register \
  --namespace Microsoft.ContainerService
```

---

### **2. Permission to register the provider**

The caller also needs permission to perform provider registration.

Conceptually, this is a subscription-level action such as:

```text
Microsoft.Resources/subscriptions/providers/register/action
```

so an identity with only narrow resource-level permissions may not necessarily be able to register a new provider.

Microsoft's documentation for provider registration emphasizes that provider registration itself requires appropriate subscription permissions. ([Microsoft Learn][6])

---

### **3. Permission to deploy the actual resource**

Provider registration alone gives the subscription access to the service.

It does **not** give the user permission to create resources.

The identity still requires the correct Azure RBAC actions.

For example, an AKS deployment might require permission to create or manage:

```text
Microsoft.ContainerService/managedClusters/*
Microsoft.Network/*
```

depending on the architecture.

---

### **4. Other controls can still block deployment**

Even with:

```text
Provider = Registered
RBAC = Allowed
```

deployment can still fail because of:

* Azure Policy
* deny assignments
* resource locks
* service quota
* unsupported region/SKU
* dependency permissions
* feature registration requirements

So my troubleshooting order would be:

```text
Provider registration
        ↓
RBAC / scope
        ↓
Policy / deny assignment
        ↓
Quota / region / SKU
        ↓
Dependency permissions
```

### **Example**

Suppose Terraform fails while creating AKS with:

```text
SubscriptionNotRegisteredForFeature
```

or a provider-not-registered error.

I would check `Microsoft.ContainerService` registration.

But if it instead returns:

```text
AuthorizationFailed
```

I would inspect the deployment identity's RBAC assignments and the exact denied action.

Those are fundamentally different failure classes.

**Memory line:**
**Provider registration = can this subscription use the service?
RBAC = can this identity perform this operation?**

**Interview trap:**
A registered provider does **not** mean every identity in the subscription can deploy that service.

Registration enables the subscription's use of the provider; Azure RBAC still decides who can perform its operations.

**Keywords:** resource-provider registration, Azure RBAC, register/action, subscription scope, AuthorizationFailed, Azure Policy, quota
