# 1. 🔴 M IMP — Azure Fundamentals, Architecture & Resource Hierarchy

## Medium

### **T01-M01. What is the Azure resource hierarchy?**

**Answer:**
The Azure resource-management hierarchy is:

**Management Group → Subscription → Resource Group → Resource**

Each level provides a scope for governance and access control.

* **Management Groups** organize multiple subscriptions.
* **Subscriptions** provide billing, quota, and management boundaries.
* **Resource Groups** logically organize related resources.
* **Resources** are the actual Azure services, such as VMs, VNets, storage accounts, and AKS clusters.

Permissions and Azure Policy assignments applied at a higher scope are generally inherited by lower scopes.

**Example:**

```text
Tenant
└── Management Group: Production
    ├── Subscription: App-Prod
    │   ├── Resource Group: rg-web-prod
    │   │   ├── VM
    │   │   ├── VNet
    │   │   └── Storage Account
    │   └── Resource Group: rg-db-prod
    └── Subscription: Data-Prod
```

If I assign an Azure Policy at the **Production management group**, subscriptions below that management group inherit the policy.

**Important distinction:**
The **Microsoft Entra tenant is the identity boundary**. It is related to Azure subscriptions, but it is not another Azure Resource Manager scope in the management hierarchy.

**Memory line:**
**Management Group → Subscription → Resource Group → Resource.**

**Interview trap:**
Do not say:

**Tenant → Subscription → Resource Group → Resource**

as the Azure RBAC/resource-management hierarchy.

A tenant is the identity directory. The ARM scope hierarchy starts with **management groups**.

**Keywords:** management group, subscription, resource group, resource, scope, inheritance, governance

**Likely follow-ups:**

* What is the difference between a management group and a subscription?
* At which levels can Azure RBAC be assigned?
* How does Azure Policy inheritance work?
* Where does the Entra tenant fit into this model?

### **T01-M02. What is the relationship between a tenant, management group, subscription, resource group, and resource?**

**Answer:**
I separate this into **identity structure and resource-management structure**.

A **Microsoft Entra tenant** is the organization's identity directory. It contains users, groups, applications, service principals, and managed identities.

Inside Azure resource management, the hierarchy is:

**Management Groups → Subscriptions → Resource Groups → Resources**

A subscription has a trust relationship with an Entra tenant so identities from that tenant can be authorized to manage Azure resources.

So, practically:

* **Tenant** → who the identities are.
* **Management Group** → organizes subscriptions and applies enterprise governance.
* **Subscription** → billing, quota, and resource-management boundary.
* **Resource Group** → logical lifecycle/management container.
* **Resource** → actual Azure service.

**Example:**
A company could have one corporate Entra tenant with:

```text
Corporate Entra Tenant
│
├── Management Group: Platform
│   ├── Connectivity Subscription
│   └── Management Subscription
│
└── Management Group: Landing Zones
    ├── Production Subscription
    │   ├── rg-orders-prod
    │   │   ├── AKS
    │   │   ├── Key Vault
    │   │   └── Storage
    │
    └── Non-Production Subscription
```

Users and workload identities come from the tenant, while their permissions to these Azure resources are controlled through Azure RBAC.

**Memory line:**
**Tenant = identities.
Management Group = subscription governance.
Subscription = billing/resource boundary.
Resource Group = lifecycle container.
Resource = actual service.**

**Interview trap:**
A management group does **not contain resource groups directly**. It contains subscriptions or other management groups. Resource groups exist inside subscriptions.

**Keywords:** Entra tenant, management group, subscription, resource group, Azure resource, identity boundary, management scope

**Likely follow-ups:**

* Can one tenant have multiple subscriptions?
* Can a subscription belong to multiple tenants?
* Why would an organization use management groups?
* Where should enterprise-wide Azure Policies be assigned?

### **T01-M03. Can an Azure resource belong to multiple resource groups?**

**Answer:**
No. An Azure resource can belong to **only one resource group at a time**.

A resource group is part of the resource's Azure Resource Manager identity and management scope. If the resource type supports Azure resource moves, I can move it from one resource group to another, but it cannot simultaneously belong to both.

**Example:**
Suppose a VM is located in:

```text
rg-app-prod
```

I cannot also make that same VM a member of:

```text
rg-network-prod
```

I could move the VM to another resource group if the resource type and its dependencies support the move.

This is why I normally design resource groups around **lifecycle and ownership**, rather than trying to use them like folders or tags.

**Important point:**
Resources that work together do **not** have to be in the same resource group.

For example, a VM can be in one resource group while the VNet it uses is in another.

**Memory line:**
**One resource → one resource group at a time.**

**Interview trap:**
Do not confuse **resource groups with tags**.

A resource can have multiple tags for organization and cost allocation, but it belongs to only one resource group.

**Keywords:** one resource group, resource lifecycle, resource move, dependencies, ARM

**Likely follow-ups:**

* Can resources communicate across resource groups?
* Can resources be moved between resource groups?
* Can a resource group contain resources from different regions?
* How should resource groups be designed?

### **T01-M04. Can resources inside one resource group exist in different Azure regions?**

**Answer:**
Yes. Resources inside the same Azure resource group can be deployed in **different Azure regions**.

A resource group itself has a location, but that location primarily determines where Azure stores the **resource-group metadata**. It does not force every resource inside the group to be deployed in that same region.

**Example:**

```text
Resource Group: rg-global-app
Location: Central India

Resources:
├── Storage Account → Central India
├── VM → Central India
├── Log Analytics Workspace → West Europe
└── Another supported resource → East US
```

Those resources can still belong to the same resource group.

The key design question is usually not:

> “Are these resources in the same region?”

but rather:

> “Do these resources share the same lifecycle, ownership, and management boundary?”

**Practical implication:**
Because the resource group's metadata is stored in its selected location, a serious outage affecting that region can temporarily affect **management operations on the resource group**, even if some resources inside it are running in other regions.

**Memory line:**
**Resource Group location ≠ location of every resource inside it.**

**Interview trap:**
A resource group is a **logical management container, not a regional boundary**.

If I need regional isolation for reliability or disaster recovery, I design that explicitly at the resource/service architecture level rather than relying on resource groups.

**Keywords:** multi-region, resource-group location, metadata, logical container, lifecycle

**Likely follow-ups:**

* Why does a resource group itself need a location?
* Can you move a resource group to another region?
* Should production resources from multiple regions be kept in one resource group?
* How would you structure resource groups for a multi-region application?
