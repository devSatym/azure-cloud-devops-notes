# 1. 🔴 M IMP — Azure Fundamentals, Architecture & Resource Hierarchy

## Medium

### **T01-M05. Can you move an Azure resource from one resource group to another?**

**Answer:**
Yes, **many Azure resources can be moved from one resource group to another**, as long as that resource type supports the move and its dependency requirements are satisfied.

A resource-group move changes the resource's **ARM resource ID**, because the resource-group name is part of that ID. However, it does **not move the resource to another Azure region**, and the resource normally continues running during the move. ([Microsoft Learn][1])

Before moving a production resource, I would check:

* whether that resource type supports moves,
* whether dependent resources must move together,
* whether resource locks exist,
* whether scripts, dashboards, IaC, or automation reference the old resource ID,
* and whether the destination has the required configuration.

During the move, Azure temporarily locks the **source and destination resource groups for management operations**, so resources continue operating but cannot be modified until the move completes. ([Microsoft Learn][1])

**Example:**
If a VM was accidentally created in:

`rg-temp`

and should belong to:

`rg-app-prod`

I can move it if the VM and its required dependent resources satisfy Azure's move requirements.

**Memory line:**
**Resource-group move = management move, not geographic move.**

**Interview trap:**
Moving a resource to another resource group does **not** move it to another Azure region.

**Keywords:** resource move, resource ID, dependencies, move validation, management lock

**Likely follow-ups:**

* Does moving a resource cause downtime?
* Does its resource ID change?
* Can every Azure resource be moved?
* How would you move a resource to another region?

### **T01-M06. Can you move Azure resources between subscriptions?**

**Answer:**
Yes, many Azure resource types can be moved between subscriptions, but there are additional requirements compared with a resource-group move.

For a standard ARM subscription move:

1. The resource type must support subscription moves.
2. The source and destination subscriptions must be **active**.
3. They must belong to the **same Microsoft Entra tenant**.
4. Required dependent resources may need to be moved together.
5. The destination subscription must have the required **resource provider registered** and enough quota.
6. The identity performing the move must have the necessary permissions at both source and destination. ([Microsoft Learn][1])

The resource stays in the same physical Azure region, but its **resource ID changes** because the subscription ID forms part of the resource ID.

**Example:**
Suppose an application was initially deployed in a shared development subscription but is now being transferred to a dedicated production subscription.

If its services support subscription moves, I can move the resources to the production subscription after validating dependencies, quotas, provider registration, and permissions.

**Important caveat:**
Azure moves the **resources**, not the resource group object itself. If I want everything in a resource group moved to another subscription, I create or select a destination resource group and move the supported resources into it. ([Microsoft Learn][1])

Also, settings associated with the old scope, such as some **role assignments, policies, or tags on the resource group**, should be reviewed separately rather than assuming they automatically migrate.

**Memory line:**
**Cross-subscription move changes ownership scope, not Azure region.**

**Interview trap:**
Do not assume that having `Contributor` somewhere automatically means you can move resources. The move operation requires permissions on both the **source and destination**, plus resource-specific requirements.

**Keywords:** subscription move, same Entra tenant, resource ID, provider registration, quota, dependencies

**Likely follow-ups:**

* Can resources be moved between subscriptions in different Entra tenants?
* Does the IP address change after a subscription move?
* What happens to RBAC assignments?
* What happens to the ARM resource ID?

### **T01-M07. What happens when you delete an Azure resource group?**

**Answer:**
Deleting an Azure resource group tells Azure Resource Manager to **delete the resources contained inside that resource group as part of the operation**.

ARM determines an appropriate deletion order based on dependencies and sends delete operations to the relevant resource providers. Azure verifies that resources have been deleted before completing the resource-group deletion. ([Microsoft Learn][2])

Because of that, I treat resource-group deletion as a **high-impact operation**, especially in production.

Before deleting one, I would check:

* which resources it contains,
* resource locks,
* backups and recovery requirements,
* dependencies from resources outside the group,
* and whether any resources have their own soft-delete or recovery capability.

**Example:**
If `rg-orders-prod` contains:

* an App Service,
* storage account,
* Key Vault,
* monitoring resources,

deleting the resource group initiates deletion of those contained resources.

That does **not necessarily mean every piece of data is instantly unrecoverable**, because individual Azure services may implement soft-delete or retention features. But the resource-group deletion itself is considered irreversible. ([Microsoft Learn][2])

**Memory line:**
**Delete the resource group → delete the resources inside it.**

**Interview trap:**
Do not assume that deleting a resource group deletes resources that are merely **referenced by** its resources but live in another resource group.

The deletion scope is based on resource ownership and dependencies, not simply logical application relationships.

**Keywords:** resource-group deletion, ARM, dependency order, resource locks, soft delete, lifecycle boundary

**Likely follow-ups:**

* Can a deleted resource group be recovered?
* How can you prevent accidental deletion?
* What happens if a resource has a `CanNotDelete` lock?
* Why should resource groups follow lifecycle boundaries?

### **T01-M08. What is Azure Resource Manager?**

**Answer:**
Azure Resource Manager, or **ARM**, is Azure's **deployment and management layer**.

When I create, update, or delete Azure resources through tools such as the Azure portal, Azure CLI, PowerShell, Bicep, Terraform using Azure APIs, SDKs, or REST, the management request ultimately goes through Azure's resource-management APIs and the appropriate resource provider. ([Microsoft Learn][3])

ARM gives Azure a consistent management model for capabilities such as:

* **Azure RBAC**
* resource groups
* tags
* resource locks
* Azure Policy integration
* declarative deployments
* dependency management
* management scopes

**Example:**
If I deploy a VM through Terraform, the request ultimately targets Azure's management APIs. ARM processes the management request and works with providers such as:

`Microsoft.Compute`
`Microsoft.Network`
`Microsoft.Storage`

to provision the required resources.

A useful high-level flow is:

**Client/tool → Azure Resource Manager → Resource Provider → Azure Resource**

**Memory line:**
**ARM = Azure's control-plane management layer.**

**Interview trap:**
ARM does not normally handle the application's actual data traffic.

For example:

* Creating a storage account → **ARM/control plane**
* Uploading a blob into that storage account → **Storage data plane**

That control-plane versus data-plane distinction is very important in Azure interviews.

**Keywords:** ARM, management layer, control plane, deployment, RBAC, resource provider, declarative infrastructure

**Likely follow-ups:**

* What is the difference between ARM and an ARM template?
* What is a resource provider?
* What is control plane versus data plane?
* What happens internally when an ARM request is submitted?
