# 1. 🔴 M IMP — Azure Fundamentals, Architecture & Resource Hierarchy

## Medium

### **T01-M09. What is a control plane versus a data plane in Azure?**

**Answer:**
The simplest distinction is:

**Control plane = manage the Azure resource.**
**Data plane = use the service provided by that resource.**

Control-plane operations go through **Azure Resource Manager** and include actions such as creating, updating, configuring, or deleting a resource.

Data-plane operations interact directly with the service after it has been created. ([Microsoft Learn][1])

**Examples:**

| Resource        | Control plane                 | Data plane                    |
| --------------- | ----------------------------- | ----------------------------- |
| Storage Account | Create/delete storage account | Upload/download a blob        |
| Azure VM        | Create/resize/delete VM       | SSH/RDP into the VM           |
| Cosmos DB       | Create database account       | Query or modify database data |
| Key Vault       | Create/configure vault        | Read a secret                 |
| AKS             | Create/upgrade AKS cluster    | Kubernetes API operations     |

This distinction is especially important for **RBAC and troubleshooting**, because an identity may have permission to manage the resource but still not have permission to access the data inside it.

For example, being **Contributor on a storage account does not automatically mean I can read all blobs**. Blob data access can require a data-plane role such as `Storage Blob Data Reader`.

**Memory line:**
**Control plane = manage it.
Data plane = use it.**

**Interview trap:**
Do not assume an Azure management role automatically gives access to the service's data plane. Control-plane and data-plane permissions can be separate.

**Keywords:** control plane, data plane, Azure Resource Manager, management API, service endpoint, Azure RBAC

**Likely follow-ups:**

* Can Contributor read data in a Storage Account?
* What is the difference between management-plane and data-plane RBAC roles?
* Does Azure Resource Manager handle application traffic?
* Is accessing a Key Vault secret a control-plane or data-plane operation?

### **T01-M10. What are Azure resource providers?**

**Answer:**
An Azure resource provider is a service that exposes a set of **Azure resource types and management operations through Azure Resource Manager**.

Each provider has a namespace.

For example:

* `Microsoft.Compute` → Virtual Machines and VM Scale Sets
* `Microsoft.Network` → VNets, NSGs, load balancers, public IPs
* `Microsoft.Storage` → Storage Accounts
* `Microsoft.ContainerService` → AKS
* `Microsoft.KeyVault` → Key Vault

When ARM receives a deployment request, it identifies the provider from the resource type and sends the request to the relevant provider.

For example:

```text
Microsoft.Compute/virtualMachines
```

means:

```text
Resource provider: Microsoft.Compute
Resource type: virtualMachines
```

A provider must generally be **registered with the subscription** before its resource types can be used. Some providers are automatically registered by Azure when you use the related service or perform certain deployments. ([Microsoft Learn][2])

**Example:**
If I deploy an AKS cluster and receive an error saying:

```text
The subscription is not registered to use namespace
'Microsoft.ContainerService'
```

I would check the provider registration state and register it if required.

For example:

```bash
az provider show \
  --namespace Microsoft.ContainerService \
  --query registrationState
```

and if required:

```bash
az provider register \
  --namespace Microsoft.ContainerService
```

**Memory line:**
**ARM receives the request; the resource provider knows how to provision that Azure resource.**

**Interview trap:**
A **resource provider is not the same as a Terraform provider**.

`Microsoft.Compute` is an Azure Resource Manager resource provider.

`azurerm` is a Terraform provider that communicates with Azure APIs.

**Keywords:** resource provider, namespace, Microsoft.Compute, registration, ARM, resource type

**Likely follow-ups:**

* Why does a resource provider need registration?
* How do you check whether a provider is registered?
* What happens if a provider is not registered?
* What is the difference between AzureRM and an Azure resource provider?

# Hard

### **T01-H01. How would you design the Azure subscription hierarchy for a large enterprise?**

**Answer:**
For a large enterprise, I would design the hierarchy around **governance requirements, workload types, security boundaries, and operational ownership**, rather than simply copying the company's department structure.

At a high level:

```text
Microsoft Entra Tenant
│
└── Tenant Root Management Group
    │
    └── Organization
        │
        ├── Platform
        │   ├── Identity Subscription
        │   ├── Connectivity Subscription
        │   ├── Management Subscription
        │   └── Security Subscription
        │
        ├── Landing Zones
        │   ├── Corp
        │   │   ├── Application Subscription
        │   │   └── Application Subscription
        │   │
        │   └── Online
        │       ├── Application Subscription
        │       └── Application Subscription
        │
        ├── Sandbox
        │
        └── Decommissioned
```

This is broadly aligned with Azure Landing Zone principles. Microsoft recommends keeping the management-group hierarchy relatively flat and grouping subscriptions based on similar **policy, security, compliance, connectivity, and operational requirements**. ([Microsoft Learn][3])

### **My design approach**

**1. Central platform subscriptions**

I would separate shared enterprise services such as:

* connectivity,
* identity-related infrastructure,
* management/monitoring,
* security tooling

into dedicated subscriptions.

For example, the connectivity subscription might contain:

* hub VNets,
* Azure Firewall,
* VPN/ExpressRoute gateways,
* centralized DNS.

This keeps shared infrastructure separate from application workloads.

---

**2. Workload subscriptions**

Applications or workload teams receive their own subscriptions where justified.

For production-grade workloads, I would normally isolate application environments using separate subscriptions, especially when I need stronger security and governance isolation. Current Azure Landing Zone guidance recommends separate subscriptions for application environments where practical. ([Microsoft Learn][4])

For example:

```text
Orders-Dev Subscription
Orders-Test Subscription
Orders-Prod Subscription
```

---

**3. Management groups provide governance**

I would assign common controls at management-group scope.

For example:

```text
Landing Zones
    │
    ├── Policy: Require Defender configuration
    ├── Policy: Restrict deployment regions
    ├── Policy: Require diagnostic settings
    └── RBAC: Central security Reader
```

Child subscriptions automatically inherit the relevant governance.

---

**4. Keep production access tightly controlled**

Production subscriptions should have:

* stronger Azure Policy,
* least-privilege RBAC,
* privileged access through PIM,
* tighter networking controls,
* mandatory monitoring,
* stronger deletion protection,
* controlled CI/CD deployment paths.

---

**5. Use automated subscription provisioning**

At enterprise scale, I would not create and configure subscriptions manually.

I would use a **subscription vending process** that automatically:

* creates or assigns the subscription,
* places it under the right management group,
* establishes networking,
* configures logging,
* applies RBAC,
* assigns policies,
* creates budgets,
* deploys baseline security controls.

Microsoft's Azure Landing Zone architecture explicitly recommends scalable subscription provisioning for this purpose. ([Microsoft Learn][5])

**Rule of thumb:**
**Management groups define enterprise guardrails; subscriptions isolate workloads and environments; resource groups organize lifecycle-related resources.**

**Interview trap:**
I would avoid creating management groups for every department, team, region, application, dev environment, staging environment, etc. That creates a deep and difficult-to-manage hierarchy.

Microsoft specifically recommends keeping management groups relatively flat and designing them around governance requirements. ([Microsoft Learn][3])

**Keywords:** Azure Landing Zones, management groups, subscription isolation, platform subscriptions, workload subscriptions, Policy inheritance, RBAC, subscription vending

**Likely follow-ups:**

* Why use separate subscriptions for production?
* Why not create one subscription per business department?
* Where would Azure Firewall and ExpressRoute live?
* Where should Azure Policies be assigned?
* How would you automate creation of new workload subscriptions?

### **T01-H02. When would you create separate subscriptions rather than separate resource groups?**

**Answer:**
I would create separate subscriptions when I need a **stronger management, governance, quota, cost, or security boundary** than a resource group provides.

A resource group is mainly a **lifecycle and management container**. A subscription provides a much stronger boundary around how a workload is governed and operated.

### **I would prefer separate subscriptions when I need:**

**1. Production versus non-production isolation**

For example:

```text
payments-nonprod-sub
payments-prod-sub
```

This limits the blast radius of:

* incorrect RBAC,
* Terraform mistakes,
* Azure Policy changes,
* accidental deletion,
* quota exhaustion.

Current Azure Landing Zone guidance generally favors separate subscriptions for different application environments where practical. ([Microsoft Learn][4])

---

**2. Different security or compliance requirements**

For example:

```text
General Workloads Subscription
PCI Workloads Subscription
```

The PCI subscription can inherit much stricter Azure Policy and security controls.

---

**3. Separate billing or cost ownership**

If two business units need clear independent cost accountability, subscriptions provide a natural billing and cost-management boundary.

---

**4. Quota isolation**

Many Azure quotas are applied at subscription and regional scope.

If one workload consumes all available quota, it can affect other workloads in the same subscription.

Separate subscriptions reduce that risk.

---

**5. Different RBAC administration**

Suppose Team A should have broad administrative rights over its application but absolutely no access to Team B.

Separate subscriptions make that access model cleaner and reduce the chance of accidentally granting permissions too broadly.

---

**6. Blast-radius reduction**

If a pipeline or administrator is compromised, subscription isolation helps prevent that identity from automatically affecting unrelated workloads, assuming permissions are scoped correctly.

---

### **When would I use resource groups instead?**

I would use different resource groups when workloads:

* share the same subscription-level governance,
* have the same security requirements,
* can share quota and billing boundaries,
* but have different ownership or lifecycle.

For example:

```text
Subscription: shared-nonprod

├── rg-orders-dev
├── rg-payments-dev
└── rg-inventory-dev
```

For a small environment, that may be perfectly reasonable.

---

### **Interview-ready decision**

If the requirement is:

> “I just need logical organization.”

I use **resource groups**.

If the requirement is:

> “I need stronger isolation for security, governance, cost, quotas, or blast radius.”

I strongly consider **separate subscriptions**.

**Rule of thumb:**
**Resource Group = lifecycle boundary.
Subscription = stronger governance and isolation boundary.**

**Interview trap:**
Separate subscriptions do **not** automatically provide network isolation.

Two resources in different subscriptions can still communicate if the networking is configured to allow it.

Subscription isolation is primarily a **management/governance boundary**, while network isolation must still be designed using VNets, firewalls, NSGs, private endpoints, routing, and related controls.

**Keywords:** subscription boundary, resource group, environment isolation, billing, quotas, governance, blast radius, RBAC
