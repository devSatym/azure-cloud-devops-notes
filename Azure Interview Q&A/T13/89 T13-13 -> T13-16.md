### **T13-13. Pods can reach public internet endpoints but not an Azure private endpoint; what would you investigate?**

**Answer:**
Because public internet access works, I would not start with general AKS outbound connectivity. I would focus specifically on the **private-endpoint path: DNS → private IP → routing/peering → NSG/firewall → Private Endpoint connection state → service authorization**. The most common issue is that the pod resolves the Azure service to its **public address instead of the Private Endpoint IP**, usually because the Private DNS zone isn't linked correctly or custom DNS isn't forwarding `privatelink.*` queries properly. ([Microsoft Learn][1])

### **Troubleshooting flow**

```text
Pod can reach internet
        ↓
Resolve private service FQDN
        ↓
Private IP or public IP?
      /             \
 public             private
   ↓                   ↓
DNS issue          Test TCP/443
                       ↓
                 Route / NSG / Firewall
                       ↓
               Private Endpoint status
                       ↓
                 Service auth/RBAC
```

### **1. Test from inside the pod**

I troubleshoot from the actual workload context:

```bash
kubectl exec -it <pod> -n <ns> -- sh
```

Then:

```bash
nslookup <service-fqdn>
```

For example, for Key Vault:

```text
myvault.vault.azure.net
```

or for SQL:

```text
myserver.database.windows.net
```

I want to know the final IP.

If the design uses a Private Endpoint, I expect:

```text
FQDN
 ↓
privatelink.<service-domain>
 ↓
10.x.x.x private IP
```

If I get:

```text
20.x.x.x / other public IP
```

I focus on DNS.

Microsoft's current Private Link troubleshooting guidance says resolving the FQDN to a public IP is most commonly caused by a missing Private DNS zone link, missing/stale A record, or custom DNS forwarding issues. ([Microsoft Learn][1])

---

### **2. Check the Private DNS zone**

Depending on the service:

```text
Key Vault
→ privatelink.vaultcore.azure.net

Azure SQL
→ privatelink.database.windows.net

Blob Storage
→ privatelink.blob.core.windows.net
```

I check:

```text
Correct Private DNS zone exists?
        ↓
Correct A record exists?
        ↓
AKS VNet linked to that zone?
```

If AKS is in a spoke VNet and the Private Endpoint is elsewhere:

```text
AKS Spoke
    ↓
Private DNS resolution
    ↓
Hub / DNS resolver
    ↓
Private DNS Zone
```

the DNS path must still work from the AKS VNet.

---

### **3. Custom DNS can break Private Link resolution**

If AKS uses:

```text
custom DNS
on-prem DNS
DNS forwarder
Azure DNS Private Resolver
```

I verify that queries for the Azure private-link zones are correctly forwarded toward Azure DNS.

A common problem:

```text
Pod
 ↓
Custom DNS
 ↓
Public recursive DNS
 ↓
Public service IP
```

instead of:

```text
Pod
 ↓
Custom DNS
 ↓
Azure Private DNS
 ↓
Private Endpoint IP
```

Microsoft specifically calls out missing conditional forwarding for `privatelink.*` zones as a cause of Private Endpoint DNS failures. ([Microsoft Learn][1])

---

### **4. Once DNS returns a private IP, test the port**

For HTTPS:

```bash
nc -vz <private-ip> 443
```

or:

```bash
curl -vk https://<service-fqdn>
```

Now I distinguish:

```text
DNS correct
+
TCP fails
→ routing / NSG / firewall
```

from:

```text
DNS correct
+
TCP works
+
403
→ authorization/service configuration
```

---

### **5. Check VNet peering/routing**

If the Private Endpoint is in another VNet:

```text
AKS VNet
   ↓
VNet peering
   ↓
Private Endpoint VNet
```

I verify:

```text
Peering Connected?
Address spaces non-overlapping?
Correct routes propagated?
UDR not overriding the path?
```

Microsoft recommends checking effective routes and Network Watcher Next Hop when peering exists but connectivity fails. ([Microsoft Learn][2])

---

### **6. Check NSGs / UDRs / firewalls**

AKS subnet may have:

```text
UDR → Azure Firewall
```

or:

```text
NSG outbound restrictions
```

A rule could allow:

```text
Internet TCP/443
```

while denying:

```text
10.20.5.4:443
```

which explains why public internet works but Private Endpoint access fails.

Microsoft's Private Endpoint connectivity troubleshooting explicitly identifies NSG denies, missing peering, and routing problems as common failure causes. ([Microsoft Learn][3])

---

### **7. Verify Private Endpoint state**

Check:

```text
Private Endpoint connection state
→ Approved
```

not:

```text
Pending
Rejected
Disconnected
```

Microsoft's current decision tree specifically says a `Pending` or `Rejected` Private Endpoint connection must be approved or recreated before connectivity can work. ([Microsoft Learn][3])

---

### **8. Only after networking works, check authorization**

Suppose:

```text
DNS → private IP ✓
TCP 443 → works ✓
HTTP response → 403
```

Then Private Link connectivity is likely working.

Now I investigate:

```text
Managed Identity
Workload Identity
Azure RBAC
service-specific permissions
```

because:

```text
Can privately reach service
≠
authorized to use service
```

---

### **Strong interview answer**

> “Because the pods can already reach the public internet, I would focus on the Private Link path. From inside the pod I would resolve the Azure service FQDN and verify that it returns the Private Endpoint's private IP. If it returns a public IP, I check the Private DNS zone, VNet link, A record, and any custom DNS forwarding. If DNS is correct, I test TCP connectivity to the private IP and then inspect AKS subnet UDRs, NSGs, Azure Firewall and VNet peering. I would also confirm that the Private Endpoint connection is Approved. Once network connectivity succeeds, a 403 would move me to Workload Identity or service RBAC rather than networking.”

**Memory line:**
**Private Endpoint issue → DNS first, then route/security, then authorization.**

**Interview trap:**
Do not assume that because a Private Endpoint exists, AKS automatically resolves the service to it.

**Keywords:**
Private Endpoint, Private DNS, `privatelink.*`, VNet peering, UDR, NSG, Workload Identity

**Likely follow-ups:**

* Why does Private Endpoint depend so heavily on DNS?
* What if the FQDN resolves to a public IP?
* Can the Private Endpoint be in a different VNet from AKS?
* What does `403` tell you after TCP connectivity succeeds?

### **T13-14. Users in one geographic region experience high latency while others do not; how would you troubleshoot it?**

**Answer:**
Because only one geographic region is affected, I would first determine whether the latency originates in the **client/ISP path, the global edge, the selected Azure origin, or the application dependency path from that origin**. I would compare telemetry for affected and unaffected regions instead of treating it as a global application-performance problem.

Microsoft's current Front Door troubleshooting guidance breaks regional latency issues into exactly these areas: the requesting client, network path, Front Door, or origin. ([Microsoft Learn][4])

### **Troubleshooting flow**

```text
Only one geography slow
        ↓
Client-side or server-side?
        ↓
DNS / ISP / network path
        ↓
Which edge/origin serves them?
        ↓
Origin latency
        ↓
Dependency latency
        ↓
Routing/configuration issue?
```

### **1. Quantify the affected population**

I would determine:

```text
Country?
City?
ISP?
Corporate network?
Only mobile users?
One Azure geography?
```

For example:

```text
India users → P95 = 2.5 s
Europe users → P95 = 300 ms
US users → P95 = 350 ms
```

This is much stronger than:

```text
"Some users say it feels slow."
```

I would use:

```text
Application Insights
Front Door logs
Real User Monitoring if available
synthetic probes
```

grouped by geography.

---

### **2. Separate application processing from network latency**

Suppose Application Insights shows:

```text
Server processing = 200 ms
```

for both India and Europe.

But user-observed latency is:

```text
India = 2.5 sec
Europe = 350 ms
```

Then the missing time likely exists:

```text
before/after origin processing
```

which points toward:

```text
network path
ISP
edge routing
TLS/connectivity
```

rather than application CPU.

---

### **3. Check which origin is serving affected users**

With Azure Front Door:

```text
India user
    ↓
Front Door edge
    ↓
Which origin?
```

Perhaps the intended architecture is:

```text
India → Central India
Europe → West Europe
```

but affected users are actually being routed:

```text
India → West Europe
```

because:

```text
India origin unhealthy
priority configuration wrong
latency routing settings wrong
origin disabled
```

Front Door uses health and latency measurements when selecting healthy origins according to the configured routing method. ([Microsoft Learn][5])

---

### **4. Check Front Door origin health**

If the nearby origin is marked unhealthy:

```text
Nearby origin
      ↓
probe failures
      ↓
Front Door removes it
      ↓
users routed to distant origin
      ↓
latency increases
```

I inspect:

```text
Origin health percentage
Probe logs
HTTP status
Probe path
TLS/backend certificate
```

A badly designed probe can also cause a healthy region to be removed unnecessarily.

---

### **5. Check ISP/network-path issues**

If the affected users all share:

```text
one ISP
one enterprise proxy
one geographic carrier
```

I investigate:

```text
route path
packet loss
TCP/TLS establishment
DNS resolver
```

Useful external measurements include:

```text
traceroute / mtr
regional synthetic probes
Front Door edge metrics
```

The important thing is comparison:

```text
Affected geography
vs
healthy geography
```

---

### **6. Check DNS behavior**

Maybe users in one geography resolve:

```text
old endpoint
wrong CNAME
different CDN/global endpoint
```

because of:

```text
DNS cache
split DNS
corporate resolver
regional DNS configuration
```

I compare:

```bash
dig app.example.com
```

from multiple locations.

---

### **7. Check regional origin dependencies**

Maybe all regions serve the same frontend, but the India app instance calls:

```text
database in West Europe
```

on every request.

Then:

```text
India frontend
  ↓
cross-region SQL call
  ↓
high latency
```

while another origin might have a local data path.

I use distributed tracing:

```text
Request
  ↓
Origin processing
  ↓
DB/API dependency
```

to find where the extra milliseconds occur.

---

### **8. Check regional capacity**

Maybe the affected region is simply overloaded:

```text
India origin
CPU = normal
but
connection pool saturated
queue depth high
DB DTU/vCore pressure
```

or:

```text
autoscaling max reached
```

So I compare:

```text
P95/P99
request rate
dependency latency
instance count
queue depth
```

per origin.

---

### **9. Check recent changes**

If the problem started suddenly:

```text
Front Door routing change
DNS change
new origin
certificate change
WAF rule
deployment
network policy
```

might explain why only one region changed.

---

### **Real example**

```text
India users slow
      ↓
App processing = 180 ms
      ↓
Front Door shows India origin unhealthy
      ↓
traffic routed to West Europe
      ↓
probe endpoint was changed during deployment
      ↓
fix probe
      ↓
India origin healthy
      ↓
latency normal
```

> **In an interview, I would say:**
> “Since only one geography is affected, I would compare affected and unaffected regions rather than troubleshoot the whole application. I would split end-user latency into network time and server processing time, then check which Front Door edge and origin serve the affected users. If the local origin is unhealthy, users may be failing over to a distant region. I would also compare DNS, ISP/network path, regional capacity and distributed traces for downstream dependencies. The objective is to identify which hop—client, edge, origin or dependency—is adding the extra latency.”

**Memory line:**
**Regional latency → compare geographies and find which hop differs.**

**Interview trap:**
Do not assume a geographic latency problem means the VM or application is globally slow.

**Keywords:**
Front Door, geography, P95/P99, origin health, ISP, DNS, distributed tracing, regional routing

**Likely follow-ups:**

* How would you prove the latency is network rather than application?
* Why might Front Door send users to a distant region?
* How would you compare latency from multiple geographies?
* Could the database location cause regional latency?

### **T13-15. An application works from a VM but not from AKS in the same VNet; what would you investigate?**

**Answer:**
“Same VNet” does not mean the VM and AKS have identical networking. They can use **different subnets, route tables, NSGs, DNS settings, Kubernetes network policies, source IPs, and identities**. I would compare the working VM path against the failing AKS path layer by layer: **DNS → source subnet → effective route → NSG/firewall → Kubernetes network policy → identity/service authorization**.

### **Troubleshooting model**

```text
VM works
AKS fails
   ↓
What differs?
   ↓
DNS?
Subnet?
Route table?
NSG?
Firewall?
NetworkPolicy?
Identity?
```

### **1. Test from inside the pod**

First:

```bash
kubectl exec -it <pod> -n <ns> -- sh
```

Then:

```bash
nslookup <destination>
nc -vz <destination> <port>
curl -vk https://<destination>
```

I want an exact error:

```text
DNS failure
timeout
connection refused
403
TLS error
```

---

### **2. Compare DNS**

From VM:

```bash
nslookup service.example.com
```

From pod:

```bash
kubectl exec <pod> -- nslookup service.example.com
```

If:

```text
VM → 10.20.3.5
AKS → public IP
```

the problem is almost certainly DNS-related.

AKS uses CoreDNS, and CoreDNS may in turn rely on VNet/custom DNS depending on configuration.

So I inspect:

```text
CoreDNS
custom DNS
Private DNS links
conditional forwarding
```

especially for Private Endpoints.

---

### **3. Compare subnets**

Maybe:

```text
VM
→ subnet-vm

AKS nodes
→ subnet-aks
```

Both belong to the same VNet, but each subnet may have different:

```text
NSG
UDR
NAT Gateway
service endpoints
policy
```

Therefore:

```text
Same VNet
≠ same effective network policy
```

This is a key interview point.

---

### **4. Compare route tables**

Example:

```text
VM subnet
0.0.0.0/0 → Internet
```

while:

```text
AKS subnet
0.0.0.0/0 → Azure Firewall
```

Now:

```text
VM succeeds
AKS gets blocked by firewall
```

even though both are in the same VNet.

I inspect effective routes/next hop from the relevant network path.

Network Watcher Next Hop and effective routes are the right Azure tools for identifying UDR/peering differences. ([Microsoft Learn][6])

---

### **5. Compare NSGs**

Maybe:

```text
VM subnet
→ outbound 443 allowed
```

but:

```text
AKS subnet
→ deny destination subnet / service
```

I inspect both:

```text
subnet NSG
NIC/effective security rules where applicable
```

Network Watcher **IP Flow Verify** is specifically designed to prove whether a security rule permits or denies traffic. ([Microsoft Learn][7])

---

### **6. Check Kubernetes NetworkPolicy**

This is something the VM does not have.

For example:

```yaml
NetworkPolicy:
  default-deny-egress
```

could block the pod while node/VM-level networking remains healthy.

Check:

```bash
kubectl get networkpolicy -A
```

Then inspect namespace-level policies.

Pattern:

```text
Node can reach service
Pod cannot
        ↓
Kubernetes network policy / CNI path
```

is a strong clue.

---

### **7. Check source IP differences**

A downstream firewall might allow:

```text
VM subnet
10.10.1.0/24
```

but not:

```text
AKS subnet
10.10.2.0/24
```

Or the workload may SNAT through a different address.

This matters for:

```text
Azure Firewall rules
PaaS firewall allowlists
on-prem firewall rules
third-party APIs
```

So I determine the actual source IP observed by the destination.

---

### **8. Check AKS network model**

Depending on AKS networking:

```text
Azure CNI
Azure CNI Overlay
kubenet in older environments
```

the pod IP and route/SNAT behavior can differ.

I do not assume:

```text
pod IP == node IP
```

or that the downstream sees the same source address as a VM.

I inspect:

```bash
kubectl get pods -o wide
kubectl get nodes -o wide
```

and map the actual traffic path.

---

### **9. Check identity differences**

Maybe networking is fine.

Example:

```text
VM
→ Managed Identity
→ Key Vault Secrets User
→ success
```

but:

```text
AKS
→ Workload Identity
→ no Key Vault role
→ 403
```

Then:

```text
VM works
AKS fails
```

has nothing to do with the VNet.

So after connectivity succeeds, I compare:

```text
VM Managed Identity
vs
AKS Workload Identity
```

and their roles.

---

### **10. Use the working VM as the control**

This is the most powerful approach.

I compare:

| Layer                | VM | AKS |
| -------------------- | -- | --- |
| DNS result           | ?  | ?   |
| Source subnet        | ?  | ?   |
| Route                | ?  | ?   |
| Firewall path        | ?  | ?   |
| Source IP            | ?  | ?   |
| Identity             | ?  | ?   |
| Destination response | ?  | ?   |

The first meaningful difference usually reveals the problem quickly.

> **In an interview, I would say:**
> “I would use the VM as a known-good control and compare it against the pod. Same VNet does not mean same path because AKS can be in another subnet with different UDRs, NSGs, NAT and DNS behavior, and the pod can also be affected by Kubernetes NetworkPolicy. I would resolve the destination from both environments, test the same TCP port, compare routes and firewall rules, and determine the source IP the destination sees. If networking works but AKS gets 403, I would compare the VM's Managed Identity against the pod's Workload Identity and their RBAC permissions.”

**Memory line:**
**Same VNet does not mean same subnet, route, DNS, policy, source IP, or identity.**

**Interview trap:**
Do not say “the VNet is fine because the VM works.” That only proves the VM's network path works.

**Keywords:**
AKS, NetworkPolicy, NSG, UDR, CoreDNS, source IP, Workload Identity, Network Watcher

**Likely follow-ups:**

* Why can VM and AKS traffic take different paths in the same VNet?
* How can NetworkPolicy block a pod when the node itself works?
* How would you identify the pod's effective source IP?
* How would you distinguish RBAC from networking?

### **T13-16. After adding a UDR, several services become unreachable; how would you identify the problem?**

**Answer:**
Because connectivity broke immediately after adding the UDR, I would treat that route change as the leading suspect and determine **which prefixes are affected, which next hop the new UDR forces, and whether return traffic is symmetric**. I would inspect effective routes and use Network Watcher **Next Hop** before changing NSGs or applications.

Azure's current guidance recommends effective routes and Next Hop specifically for identifying which route is actually selected and whether a UDR is overriding a system or peering route. ([Microsoft Learn][6])

### **Troubleshooting flow**

```text
UDR added
   ↓
Services unreachable
   ↓
Which destinations?
   ↓
What route now matches?
   ↓
What next hop?
   ↓
Firewall/NVA reachable?
   ↓
Return path symmetric?
   ↓
Fix route / firewall / propagation
```

### **1. Identify exactly what broke**

I list affected destinations:

```text
Internet?
Private Endpoint?
Peered VNet?
On-prem?
Azure control-plane/service endpoints?
DNS?
```

For example:

```text
Internet     ✗
Key Vault PE ✗
Peered VNet  ✓
```

That pattern tells me which prefixes likely changed.

---

### **2. Inspect the UDR**

Suppose someone added:

```text
0.0.0.0/0
    ↓
Virtual Appliance
10.0.10.4
```

Now almost all previously default-routed traffic may be forced through the NVA.

Or perhaps they added:

```text
10.0.0.0/8
→ Firewall
```

which accidentally captures:

```text
Private Endpoint IPs
peered VNets
internal services
```

that previously used direct VNet routes.

---

### **3. Check effective routes**

For a VM/NIC:

```bash
az network nic show-effective-route-table \
  --resource-group <rg> \
  --name <nic>
```

I look at:

```text
Destination prefix
Next hop
Route source
State
```

Example:

```text
10.20.0.0/16
Before:
VirtualNetworkPeering

After:
UserDefined → VirtualAppliance
```

That is strong evidence.

Microsoft explicitly recommends effective route inspection when troubleshooting UDR and peering problems. ([Microsoft Learn][2])

---

### **4. Use Network Watcher Next Hop**

For destination:

```text
10.20.5.8
```

I test:

```text
Source VM
      ↓
Next Hop?
```

Possible outputs:

```text
VirtualNetwork
VirtualNetworkPeering
VirtualAppliance
Internet
None
```

If I expected:

```text
VirtualNetworkPeering
```

but get:

```text
VirtualAppliance
```

the UDR is overriding the intended path.

Network Watcher Next Hop exists specifically to determine the selected next hop and the route responsible. ([Microsoft Learn][6])

---

### **5. Remember longest-prefix matching**

Azure routing chooses the most specific matching route first.

Conceptually:

```text
0.0.0.0/0
10.0.0.0/8
10.20.0.0/16
10.20.1.0/24
```

For destination:

```text
10.20.1.50
```

the `/24` route is more specific than `/16`, `/8`, or `/0`.

So I check not only:

```text
default route
```

but all overlapping route prefixes.

---

### **6. Verify the NVA / Azure Firewall**

If the route correctly points to:

```text
Azure Firewall / NVA
```

I ask:

```text
Is it healthy?
Can it reach the destination?
Does it allow the traffic?
Does it SNAT correctly?
Is IP forwarding enabled for NVA?
```

Network Watcher Connection Troubleshoot can detect NSG, UDR, next-hop, or missing-route conditions along the path. ([Microsoft Learn][8])

---

### **7. Check asymmetric routing**

A very common issue is:

```text
Request:
VM → Firewall → destination
```

but:

```text
Response:
destination → directly back to VM
```

or the reverse.

Stateful devices may then see:

```text
only half the connection
```

and drop it.

So I verify:

```text
forward path
+
return path
```

especially after adding a firewall/NVA route.

---

### **8. Check routes to Private Endpoints**

A new broad UDR can unexpectedly alter Private Endpoint traffic.

For example:

```text
Private Endpoint
10.20.5.4
```

A broad:

```text
10.0.0.0/8 → NVA
```

could affect the intended path depending on routing configuration and private-endpoint network policy settings.

Microsoft's current Private Endpoint troubleshooting guidance specifically includes UDR/next-hop behavior among the key checks when Private Endpoint connectivity breaks. ([Microsoft Learn][3])

---

### **9. Check BGP interaction**

In hybrid networks:

```text
ExpressRoute / VPN
      ↓
BGP routes
```

may also exist.

I compare:

```text
System route
BGP route
UDR
```

and determine which route wins.

If a route was unexpectedly propagated from on-prem or an NVA, the effective table will expose it.

---

### **10. Roll back the route if production impact is broad**

If:

```text
UDR change
   ↓
multiple production services unavailable
```

and reverting is known safe, I would usually:

```text
rollback UDR
      ↓
restore service
      ↓
investigate offline
```

rather than spending 45 minutes debugging while production remains down.

This is especially reasonable when:

```text
change timestamp
==
outage timestamp
```

and rollback is low-risk.

---

### **Example**

```text
Before:
AKS → Key Vault PE directly
        ↓
works

Change:
0.0.0.0/0 → NVA

After:
AKS → NVA → Key Vault
        ↓
NVA rule missing
        ↓
timeout
```

Evidence:

```text
Effective route → VirtualAppliance
Next Hop → NVA
Firewall logs → denied
```

Fix:

```text
correct route/firewall policy
```

rather than:

```text
change Key Vault RBAC
```

---

> **In an interview, I would say:**
> “Because the outage started after adding the UDR, I would first identify which destination prefixes broke and inspect the effective route table on an affected source. I would use Network Watcher Next Hop to see which route and next hop Azure now selects. Then I would check whether the UDR is overriding a peering or system route, whether the firewall/NVA is healthy and permits the traffic, and whether the forward and return paths are symmetric. If production impact is broad and the UDR is clearly correlated, I would safely roll back first, restore service, and then validate the corrected routing design.”

**Memory line:**
**After a UDR change, prove which route won and where it sends the packet.**

**Interview trap:**
Do not assume the route you configured is the route Azure is actually using—inspect the **effective route table**.

**Keywords:**
UDR, effective routes, Next Hop, longest-prefix match, NVA, Azure Firewall, asymmetric routing

**Likely follow-ups:**

* How does Azure decide which route wins?
* What does Next Hop tell you?
* Why can forced tunneling break Azure services?
* How would asymmetric routing cause connection failures?
