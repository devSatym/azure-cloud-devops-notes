### **T13-09. CPU usage suddenly reaches 100%; how would you investigate it?**

**Answer:**
I would first determine **whether the CPU spike is real, how long it has lasted, whether it affects one instance or the whole service, and what changed immediately before it started**. Then I would narrow from infrastructure metrics to the process/application level instead of immediately resizing the VM.

### **Troubleshooting flow**

```text
CPU = 100%
   ↓
One VM or all?
   ↓
Temporary spike or sustained?
   ↓
What changed?
   ↓
Which process/thread?
   ↓
Traffic increase or bad workload?
   ↓
Dependency/retry loop?
   ↓
Fix cause or scale
```

### **1. Confirm the pattern**

In Azure Monitor Metrics I would check:

```text
Percentage CPU
```

over:

```text
last 30 min
last 6 hours
last 24 hours
```

I want to know:

```text
When did it begin?
Was it sudden or gradual?
Is CPU still high?
Does it happen periodically?
```

For a scale set or multi-instance application:

```text
One instance at 100%
→ probably instance/process-specific

Every instance at 100%
→ traffic/workload/systemic issue
```

That distinction immediately narrows the failure domain.

---

### **2. Correlate with other signals**

I would compare the same timestamp against:

```text
Request rate
Application latency
5xx errors
Memory
Disk I/O
Network traffic
Queue depth
```

Examples:

```text
Requests ↑
CPU ↑
→ genuine traffic surge
```

versus:

```text
Requests normal
CPU ↑
→ runaway process / application defect
```

or:

```text
Dependency starts failing
Retries ↑
CPU ↑
→ retry storm
```

---

### **3. Check what changed**

Because the question says **suddenly**, I look for:

```text
Deployment
Configuration change
Autoscaling change
Scheduled job
Security scan
Database batch
Traffic event
```

For example:

```text
14:00 deployment
14:03 CPU 100%
```

makes the new release a strong suspect.

I would inspect Azure Activity Log, deployment history, CI/CD timestamps, and application telemetry around that window.

---

### **4. Identify the process**

On Linux:

```bash
top
```

or:

```bash
ps -eo pid,cmd,%cpu,%mem --sort=-%cpu | head
```

Suppose:

```text
java-api       340% CPU
backup-agent     5%
sshd             1%
```

Now I know the application is responsible.

For a multithreaded process, CPU can exceed 100% in tools such as `top` depending on how usage is represented across cores.

---

### **5. Drill into application behavior**

If the application process is hot, I investigate:

```text
expensive request
infinite loop
serialization/deserialization
regex issue
garbage collection
large batch job
retry loop
thread contention
crypto/compression
```

Using Application Insights / distributed tracing, I would look for:

```text
Which operation increased?
Which endpoint?
Which dependency?
Which deployment version?
```

Example:

```text
POST /reports
    ↓
request volume normal
    ↓
duration ↑
    ↓
new code performs huge in-memory calculation
    ↓
CPU saturated
```

---

### **6. Check whether the VM is simply undersized**

If:

```text
traffic legitimately doubled
+
application behaving normally
+
all instances near 100%
```

then the problem may genuinely be capacity.

Possible response:

```text
Scale out
→ more instances

Scale up
→ larger VM
```

For VMSS or AKS, I would verify autoscaling actually triggered and isn't blocked by:

```text
max replica count
quota
SKU capacity
bad metric
pending pods
```

---

### **7. Stabilize production**

If users are affected:

```text
Scale temporarily
or
rollback bad deployment
or
stop runaway scheduled job
```

before doing a long forensic investigation.

For example:

```text
New release
   ↓
CPU 100%
   ↓
latency ↑
   ↓
rollback
   ↓
CPU returns to 35%
```

That is strong evidence linking the incident to the release.

---

> **In an interview, I would say:**
> “I would first confirm whether the CPU saturation affects one instance or all instances and correlate the exact start time with traffic, latency, errors and recent deployments. Then I would move inside the guest OS and identify the process consuming CPU using tools such as `top` or `ps`. If it's the application, I would use Application Insights and traces to find expensive operations, retry loops or changes introduced by the latest deployment. If all instances are saturated because of legitimate load, I would investigate autoscaling and capacity. During a production incident I would stabilize the service first through rollback or scaling, then complete root-cause analysis.”

**Memory line:**
**100% CPU → scope it → correlate it → identify the process → determine bad workload versus insufficient capacity.**

**Interview trap:**
Do not immediately resize the VM. A runaway process or bad deployment will happily consume 100% of the larger VM too.

**Keywords:**
Azure Monitor, Percentage CPU, process, Application Insights, retry storm, scaling, rollback

**Likely follow-ups:**

* What if only one VM has high CPU?
* What if every VM is at 100%?
* How would you distinguish traffic growth from a bad deployment?
* Scale up versus scale out—which would you choose?

### **T13-10. Azure resources are healthy but users report that the application is unavailable; what would you check?**

**Answer:**
“Resource healthy” only tells me the Azure resource itself is operating; it does **not prove the complete user request path works**. I would test the application from the user's perspective and walk the request path from **DNS → edge/load balancer → network → application → dependencies → data layer**.

### **Troubleshooting flow**

```text
Azure resources = Healthy
Users = Application unavailable
                ↓
Can I reproduce externally?
                ↓
DNS
                ↓
Front Door / App Gateway / LB
                ↓
Backend health
                ↓
Application endpoint
                ↓
Dependencies / database
```

### **1. Reproduce the user-visible failure**

I start with:

```bash
curl -vk https://app.example.com
```

I want to know whether I get:

```text
DNS failure
Timeout
TLS error
403
502
503
500
```

because each points to a different layer.

For example:

```text
503
```

could mean the frontend exists but has no healthy backend.

---

### **2. Check DNS**

```bash
nslookup app.example.com
```

or:

```bash
dig app.example.com
```

Verify:

```text
Correct hostname?
Correct CNAME/A record?
Correct Front Door/App Gateway endpoint?
TTL/cached old record?
```

A perfectly healthy application does not help if:

```text
app.example.com
→ old IP
```

---

### **3. Check the edge service**

If using:

```text
Azure Front Door
Application Gateway
Load Balancer
```

I inspect:

```text
Backend/origin health
Health probe status
WAF blocks
Routing rules
Listener configuration
Certificate
```

Example:

```text
Front Door = Healthy
App Service = Healthy
but
Origin health = Unhealthy
```

Users can still see an outage.

---

### **4. Test the backend directly**

I want to distinguish:

```text
Ingress problem
```

from:

```text
Application problem
```

Conceptually:

```text
Public endpoint fails
      ↓
Direct backend health test succeeds
      ↓
Ingress/routing layer suspect
```

versus:

```text
Public endpoint fails
Direct backend also fails
      ↓
Application/dependency suspect
```

I would only bypass normal security controls for testing in a safe and authorized way.

---

### **5. Check application-level health**

Azure may report:

```text
VM running
AKS cluster running
App Service running
```

while the application itself has:

```text
deadlocked worker
failed startup
broken configuration
database unavailable
empty connection pool
```

So I check:

```text
/health
/readiness
Application Insights
application logs
exceptions
request telemetry
```

---

### **6. Check dependencies**

Example:

```text
Application process = running
Database = unreachable
```

Users still see:

```text
503 / timeout
```

So I follow:

```text
App
├── Database
├── Key Vault
├── Storage
├── Redis
├── Service Bus
└── downstream API
```

A cloud resource being “healthy” does not guarantee:

```text
the application can authenticate to it
```

or:

```text
the network path is allowed
```

---

### **7. Check identity and secrets**

Common scenario:

```text
App Service healthy
     ↓
Managed Identity permission removed
     ↓
Key Vault reads fail
     ↓
app cannot start requests
```

or:

```text
secret rotated
     ↓
app still uses old credential
```

So I inspect:

```text
Managed Identity
Workload Identity
Azure RBAC
Key Vault access
secret/certificate expiry
```

---

### **8. Check user scope**

I ask:

```text
All users?
One ISP?
One country?
One tenant?
Only logged-in users?
Only one endpoint?
```

For example:

```text
Anonymous home page works
Login fails
```

points toward:

```text
identity provider
session/authentication layer
```

rather than Azure VM health.

---

### **9. Synthetic availability matters**

This is why I would configure monitoring from the **user perspective**:

```text
Synthetic test
   ↓
https://app.example.com
   ↓
actual application path
```

rather than monitoring only:

```text
VM = Running
```

Infrastructure health and application availability are different things.

> **In an interview, I would say:**
> “I wouldn't equate Azure Resource Health with application availability. I would reproduce the problem externally and walk the request path from DNS to Front Door or Application Gateway, inspect backend health and health probes, then test the application itself and its downstream dependencies. I would also check TLS certificates, WAF rules, identities, Key Vault access and database connectivity. If only certain users are affected, I would segment by geography, ISP, endpoint or authentication state. Ultimately I monitor the real user endpoint with synthetic availability tests because healthy infrastructure does not guarantee a healthy service.”

**Memory line:**
**Healthy resources do not equal a healthy user journey.**

**Interview trap:**
Do not stop at Azure Resource Health and conclude “Azure is fine.” Resource Health does not validate your DNS, application, credentials, dependencies, or business transactions.

**Keywords:**
Resource Health, synthetic monitoring, DNS, backend health, Front Door, Application Gateway, dependency

**Likely follow-ups:**

* What is the difference between Resource Health and application health?
* How would you distinguish DNS from backend failure?
* Why are synthetic availability tests valuable?
* What if only one geographic region is affected?

### **T13-11. Application latency increased after deployment even though CPU and memory are normal; how would you investigate it?**

**Answer:**
Normal CPU and memory tell me the application probably isn't **compute constrained**, but latency can still increase because it is **waiting**—on a database, downstream API, DNS, network, connection pool, lock, queue, or retry. Because the issue started after deployment, I would compare the new version against the previous version and use distributed tracing to find where request time increased.

### **Troubleshooting flow**

```text
Deployment
   ↓
Latency ↑
CPU/memory normal
   ↓
Compare old vs new
   ↓
Which request got slower?
   ↓
Distributed trace
   ↓
App processing or dependency wait?
   ↓
DB / API / network / retries / pool
```

### **1. Correlate the timing**

First:

```text
13:55 old version healthy
14:00 deployment starts
14:05 latency rises
```

This makes the deployment a strong suspect.

I compare:

```text
Before deployment
vs
After deployment
```

for:

```text
P50
P95
P99 latency
request rate
error rate
dependency duration
```

Average latency alone can hide severe tail-latency problems.

---

### **2. Identify which operation became slow**

Using Application Insights:

```text
GET /profile      normal
GET /products     normal
POST /checkout    4x slower
```

Now I avoid troubleshooting the entire platform.

I focus on:

```text
POST /checkout
```

---

### **3. Follow the distributed trace**

Suppose:

```text
POST /checkout = 4.5 sec
```

Trace:

```text
Checkout API
│
├── application processing  80 ms
├── Redis                   20 ms
├── SQL                    120 ms
└── Payment API           4.1 sec
```

CPU can remain perfectly healthy because the application spends most of its time:

```text
waiting for Payment API
```

not executing CPU instructions.

That makes dependency telemetry more useful than CPU in this incident.

---

### **4. Compare dependency telemetry before and after deployment**

I ask:

```text
Did dependency call count increase?
Did timeout change?
Did retries increase?
Did query duration increase?
```

Example:

Before:

```text
1 SQL query × 50 ms
```

After:

```text
100 SQL queries × 50 ms
```

Classic N+1 behavior:

```text
CPU normal
DB dependency calls ↑
request latency ↑
```

---

### **5. Check connection pools**

A deployment may modify:

```text
DB pool size
HTTP client configuration
keep-alive
Redis connection configuration
```

Then requests may spend time:

```text
waiting for free connection
```

while:

```text
CPU = 25%
Memory = 40%
```

So I investigate:

```text
connection wait time
pool exhaustion
open connections
timeouts
```

---

### **6. Check retries**

A subtle deployment regression:

```text
Dependency occasionally returns 503
```

Old version:

```text
1 request → fail quickly
```

New version:

```text
request
 ↓
retry
 ↓
retry
 ↓
retry
```

Users now experience:

```text
4-second latency
```

even though dependency failure rate may look modest.

Distributed tracing often reveals repeated dependency spans.

---

### **7. Check database behavior**

A new deployment may introduce:

```text
N+1 queries
missing index usage
larger result set
lock contention
long-running transaction
different execution plan
```

I would correlate:

```text
slow request
→ SQL dependency
→ query duration
```

and then inspect database-side metrics/query performance.

---

### **8. Check networking and DNS only where evidence points**

A deployment could change:

```text
service hostname
Private Endpoint
DNS resolver
HTTP proxy
connection reuse
```

but I would not randomly inspect every NSG if traces already show:

```text
SQL = 20 ms
Payment API = 3.8 sec
```

The evidence tells me where to focus.

---

### **9. Compare configuration**

Often the code is correct but configuration differs.

I compare:

```text
environment variables
ConfigMaps
feature flags
connection strings
timeout values
service endpoints
deployment manifest
```

between the old and new versions.

---

### **10. Roll back as an experiment**

If production is impacted and rollback is safe:

```text
v2 latency = 4 sec
       ↓
rollback v1
       ↓
latency = 300 ms
```

That provides powerful evidence that:

```text
deployment introduced regression
```

and restores user experience quickly.

Then I can investigate v2 outside production.

---

> **In an interview, I would say:**
> “Because CPU and memory are normal, I would suspect waiting rather than compute saturation. I would compare P95/P99 latency before and after the deployment, identify which operation became slow, and use Application Insights distributed tracing to break request time into application processing and downstream dependencies. I would look for increased database queries, dependency latency, retries, connection-pool waits, locking or configuration changes. If production impact is significant and the previous version was healthy, I would rollback first and then investigate the regression.”

**Memory line:**
**Normal CPU + high latency often means the request is waiting, not computing.**

**Interview trap:**
Do not conclude “infrastructure is healthy” just because CPU and memory are normal.

**Keywords:**
P95, P99, distributed tracing, dependency latency, connection pool, N+1, retries, rollback

**Likely follow-ups:**

* Why can latency rise without CPU increasing?
* What is an N+1 database-query problem?
* How would you identify connection-pool exhaustion?
* Why look at P95/P99 instead of only averages?

### **T13-12. An AKS application experiences intermittent 503 errors; how would you troubleshoot it?**

**Answer:**
For intermittent AKS `503` errors, I would first identify **which component is actually returning the 503**, then correlate failures with specific pods, nodes, deployments, readiness state, ingress/backend health, and load. Intermittent behavior strongly suggests that **some requests are reaching an unhealthy or unavailable backend while others reach healthy ones**.

### **Troubleshooting flow**

```text
Intermittent 503
      ↓
Who returns 503?
Ingress / App / Front Door?
      ↓
All pods or one pod?
      ↓
Endpoints/readiness
      ↓
Pod restarts / resource pressure
      ↓
Node/network issue
      ↓
Load / scaling / deployment timing
```

---

### **1. Identify where the 503 originates**

The request path may be:

```text
User
 ↓
Front Door
 ↓
Application Gateway / Ingress
 ↓
Kubernetes Service
 ↓
Pod
```

A `503` could be generated by:

```text
Front Door
Application Gateway
NGINX ingress
service mesh
application itself
```

So I inspect:

```text
response headers
edge logs
ingress logs
application logs
```

before blaming Kubernetes.

---

### **2. Check Kubernetes Service endpoints**

```bash
kubectl get svc -n <namespace>
kubectl get endpoints -n <namespace>
kubectl get pods -n <namespace> -o wide
```

or EndpointSlices:

```bash
kubectl get endpointslices -n <namespace>
```

I want to verify:

```text
Service selector
      ↓
correct ready pods
```

Suppose:

```text
Service expects 5 backends
Endpoints show only 2
```

That immediately explains reduced capacity or intermittent failures.

---

### **3. Check readiness probes**

This is one of the biggest causes.

Kubernetes should send traffic only to pods that are:

```text
Ready
```

If readiness is incorrectly designed:

```text
Pod starts
   ↓
application not actually ready
   ↓
readiness says healthy anyway
   ↓
traffic arrives
   ↓
503
```

I inspect:

```bash
kubectl describe pod <pod> -n <ns>
```

and look for:

```text
Readiness probe failed
Liveness probe failed
Unhealthy
```

Also check:

```bash
kubectl get pods -n <ns>
```

for fluctuating:

```text
READY
1/1 → 0/1 → 1/1
```

---

### **4. Check whether one pod is bad**

Intermittent failures often look like:

```text
Pod A → healthy
Pod B → healthy
Pod C → broken
```

Load balancing:

```text
Request 1 → A → 200
Request 2 → B → 200
Request 3 → C → 503
Request 4 → A → 200
```

I correlate request logs with:

```text
pod name
pod IP
node
version
```

If every failure maps to:

```text
pod-c
```

the scope becomes very small.

---

### **5. Check pod restarts**

```bash
kubectl get pods -n <ns>
```

and:

```bash
kubectl describe pod <pod> -n <ns>
```

Look for:

```text
Restart Count
OOMKilled
CrashLoopBackOff
probe failures
termination reason
```

For previous container logs:

```bash
kubectl logs <pod> -n <ns> --previous
```

A pod that repeatedly crashes may periodically disappear from backend availability.

---

### **6. Check resource pressure**

Look at:

```text
CPU throttling
memory limits
OOM
node pressure
```

Commands:

```bash
kubectl top pods -n <ns>
kubectl top nodes
```

Potential pattern:

```text
traffic spike
   ↓
pods hit CPU limits
   ↓
requests slow
   ↓
health/readiness fails
   ↓
backend temporarily removed
   ↓
503
```

---

### **7. Check HPA and capacity**

If 503s correlate with load:

```text
traffic rises
    ↓
existing pods saturated
    ↓
HPA requests more replicas
    ↓
new pods take time to become ready
    ↓
temporary capacity shortage
```

Check:

```bash
kubectl get hpa -n <ns>
```

I inspect:

```text
current replicas
desired replicas
max replicas
metrics
```

Also:

```text
Pending pods?
```

If HPA says:

```text
Desired = 20
Maximum = 10
```

the service may simply be capped too low.

---

### **8. Check rolling deployment behavior**

Suppose intermittent 503s started during release.

I inspect:

```text
maxUnavailable
maxSurge
readiness probe
terminationGracePeriodSeconds
preStop
```

Bad rollout:

```text
old pod terminated
      ↓
new pod not ready
      ↓
insufficient healthy endpoints
      ↓
503
```

For production I want enough overlap so healthy capacity remains available throughout the rollout.

---

### **9. Check ingress/backend health**

If using ingress:

```bash
kubectl logs <ingress-controller-pod> -n <ingress-namespace>
```

Look for:

```text
no live upstreams
upstream unavailable
upstream timed out
connection refused
```

If Application Gateway or Front Door is involved, I also inspect backend health there.

---

### **10. Check node correlation**

Use:

```bash
kubectl get pods -o wide -n <ns>
```

Maybe every failing pod is on:

```text
node-03
```

Then investigate:

```text
node network
CNI
kube-proxy
node pressure
disk
packet drops
```

rather than the application.

---

### **11. Check dependencies**

The application itself may return 503 when:

```text
database unavailable
Redis timeout
downstream API unavailable
```

So I correlate the 503 request using:

```text
Application Insights
OpenTelemetry trace
Operation/Trace ID
```

to determine whether:

```text
AKS routing failed
```

or:

```text
application intentionally returned 503
because its dependency failed
```

---

### **Real example**

```text
503 occurs ~20% requests
       ↓
5 replicas
       ↓
trace shows failures only from pod-4
       ↓
pod-4 readiness probe checks only process
       ↓
its DB connection never initialized
       ↓
pod still marked Ready
       ↓
Service routes requests to it
```

Fix:

```text
make readiness probe validate
actual serving readiness
```

Now Kubernetes removes unhealthy pods before user traffic reaches them.

> **In an interview, I would say:**
> “I would first identify whether the 503 comes from Front Door, ingress, the Kubernetes service path, or the application itself. Then I would inspect Service EndpointSlices and correlate failed requests with individual pods and nodes. Intermittent 503s often come from one unhealthy backend, incorrect readiness probes, pod restarts, rollout gaps, resource pressure or insufficient HPA capacity. I would inspect pod events and previous logs, ingress/backend health, HPA behavior and deployment strategy. Finally I would use distributed tracing to determine whether the application itself returns 503 because a downstream dependency is unavailable.”

**Memory line:**
**Intermittent 503 usually means some requests have a healthy path and some don't—find what differs between them.**

**Interview trap:**
Do not restart every pod immediately. You may destroy the evidence showing that failures correlate with one pod, node, or rollout condition.

**Keywords:**
503, readiness probe, EndpointSlice, ingress, HPA, rolling update, OOMKilled, backend health

**Likely follow-ups:**

* Liveness vs readiness probe—which affects traffic routing?
* How can a rolling deployment cause 503s?
* What if failures occur only on one AKS node?
* How would you distinguish ingress 503 from application-generated 503?
