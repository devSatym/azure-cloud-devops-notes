### **T13-05. Terraform receives `AuthorizationFailed`; what would you investigate?**

**Answer:**
`AuthorizationFailed` normally means Terraform **successfully authenticated to Azure, but the identity does not have permission to perform a specific Azure operation at the required scope**. I would read the error carefully to identify the **principal, action, and scope**, verify Terraform is using the identity/subscription I expect, then inspect Azure RBAC and any conditions or deny assignments before changing permissions. ([Microsoft Learn][1])

### **Troubleshooting flow**

```text
Terraform → AuthorizationFailed
            ↓
Which principal?
            ↓
Which Azure action?
            ↓
At what scope?
            ↓
Correct tenant/subscription?
            ↓
RBAC role sufficient?
            ↓
Role assignment inherited?
            ↓
ABAC condition / deny assignment?
            ↓
Refresh credentials and retry
```

### **1. Read the error instead of guessing**

A typical error contains something like:

```text
The client '<client-id>'
with object id '<object-id>'
does not have authorization
to perform action
'Microsoft.Network/virtualNetworks/write'
over scope
'/subscriptions/.../resourceGroups/rg-prod/...'
```

That gives me three critical pieces:

```text
Principal
→ object ID

Action
→ Microsoft.Network/virtualNetworks/write

Scope
→ exact resource/resource group/subscription
```

I would troubleshoot those first.

---

### **2. Verify which identity Terraform is actually using**

Terraform might authenticate using:

```text
GitHub Actions OIDC
Service principal
Managed Identity
Azure CLI credentials
```

I want to prove the identity rather than assume it.

For example:

```bash
az account show
```

or within the pipeline, safely inspect:

```text
tenant ID
subscription ID
client/principal ID
```

without printing credentials.

A common issue is:

```text
Expected:
prod deployment identity

Actual:
dev service principal
```

or:

```text
Expected subscription:
Prod

Actual subscription:
Dev
```

---

### **3. Verify the target subscription and tenant**

Terraform provider configuration might point at the wrong environment:

```hcl
provider "azurerm" {
  features {}

  subscription_id = var.subscription_id
}
```

I check:

```text
Tenant ID
Subscription ID
Resource Group
Terraform workspace/environment variables
Provider alias
```

A valid identity can still receive `AuthorizationFailed` if it is trying to modify a resource in a subscription where it has no role assignment.

---

### **4. Check Azure RBAC at the exact scope**

Suppose Terraform is deploying:

```text
Subscription
 └── rg-platform-prod
      └── AKS
```

and the identity has:

```text
Contributor
at rg-dev
```

That doesn't help with `rg-platform-prod`.

I inspect role assignments at:

```text
Resource
Resource Group
Subscription
Management Group
```

because RBAC assignments can be inherited downward.

Useful command:

```bash
az role assignment list \
  --assignee <principal-object-id> \
  --all \
  --output table
```

---

### **5. Check whether the role contains the required action**

For ordinary resource creation:

```text
Contributor
```

may be sufficient in many cases.

But a classic Terraform problem occurs when Terraform also creates:

```text
Azure RBAC role assignments
```

For example:

```hcl
resource "azurerm_role_assignment" "acr_pull" {
  ...
}
```

Terraform then needs permission for:

```text
Microsoft.Authorization/roleAssignments/write
```

A normal **Contributor** cannot generally grant Azure RBAC roles.

An appropriate access-management role such as:

```text
Role Based Access Control Administrator
```

at the required scope may be needed. Microsoft specifically identifies missing `Microsoft.Authorization/roleAssignments/write` as a cause of authorization failures during role assignment creation. ([Microsoft Learn][1])

### **Very important interview distinction**

```text
Contributor
→ manage Azure resources

RBAC Administrator / appropriate access-management role
→ manage role assignments
```

So:

```text
"I have Contributor"
```

doesn't automatically mean:

```text
"I can create role assignments."
```

---

### **6. Check RBAC conditions or deny assignments**

Even if a role exists, I would check whether:

```text
ABAC condition
Deny assignment
restricted delegation
```

prevents that specific operation.

For example:

```text
Role assignment exists
        ↓
but condition restricts
which roles/principals may be assigned
        ↓
Terraform operation denied
```

Azure RBAC troubleshooting explicitly calls out role-assignment conditions as another reason apparently sufficient permissions can still fail. ([Microsoft Learn][1])

---

### **7. If permission was just granted, refresh authentication**

Suppose:

```text
10:00
RBAC role assigned

10:01
same old token used
```

The running Terraform process may not immediately see the new authorization context.

I would:

```text
wait for RBAC propagation
+
obtain a fresh token/session
+
retry
```

rather than assigning increasingly powerful roles.

---

### **8. Use least privilege when fixing it**

I would not solve:

```text
AuthorizationFailed
```

by immediately assigning:

```text
Owner at subscription scope
```

Instead:

```text
Required operation
      ↓
Required role
      ↓
Narrowest practical scope
```

For example:

```text
Terraform app deployment
→ Contributor
→ specific app resource group
```

and separate role-assignment permissions only when genuinely required.

> **In an interview, I would say:**
> “`AuthorizationFailed` normally means Terraform authenticated successfully but the identity isn't authorized for the requested operation. I would read the error to identify the object ID, Azure action, and exact scope, then confirm Terraform is using the intended tenant, subscription and identity. I would inspect that identity's effective RBAC assignments and whether the role actually includes the failing action. A common example is Terraform having Contributor but attempting to create an Azure role assignment, which requires `Microsoft.Authorization/roleAssignments/write`. I would also check RBAC conditions or deny assignments and refresh credentials if access was granted recently.”

**Memory line:**
**`AuthorizationFailed` → identify principal + action + scope, then verify effective RBAC.**

**Interview trap:**
Do not immediately give Terraform **Owner**. First determine the exact missing permission and scope.

**Keywords:**
`AuthorizationFailed`, Azure RBAC, scope, Contributor, Role Based Access Control Administrator, `roleAssignments/write`, least privilege

**Likely follow-ups:**

* Why can Contributor deploy resources but fail to create role assignments?
* How would you determine which identity Terraform is using?
* At what scopes can Azure RBAC roles be assigned?
* What if the correct role was assigned five minutes ago?

### **T13-06. A GitHub Actions workflow cannot log in to Azure using OIDC; what would you check?**

**Answer:**
I would troubleshoot the OIDC chain in this order: **GitHub token permission → workflow identity values → federated credential matching → Microsoft Entra application/service principal → Azure subscription/RBAC**. The most common problems are missing `id-token: write`, incorrect tenant/client/subscription IDs, or a federated credential whose **issuer, subject, or audience does not match the token GitHub actually sends**. GitHub currently recommends OIDC for Azure because it avoids storing long-lived Azure credentials. ([GitHub Docs][2])

### **Authentication flow**

```text
GitHub Actions
      ↓
GitHub OIDC token
      ↓
Issuer / Subject / Audience
      ↓
Entra Federated Credential
      ↓
Token exchange
      ↓
Azure access token
      ↓
Azure RBAC
```

The first goal is to determine whether failure happens:

```text
before Azure login
```

or:

```text
after login while accessing Azure
```

because those are different issues.

---

### **1. Check workflow permissions**

The workflow/job needs:

```yaml
permissions:
  id-token: write
  contents: read
```

Without:

```text
id-token: write
```

GitHub cannot issue the OIDC token that `azure/login` needs.

A current pattern is:

```yaml
- name: Azure Login
  uses: azure/login@v3
  with:
    client-id: ${{ secrets.AZURE_CLIENT_ID }}
    tenant-id: ${{ secrets.AZURE_TENANT_ID }}
    subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
```

The current Azure Login documentation explicitly requires `id-token: write` for OIDC. ([GitHub][3])

### **Important point**

These values:

```text
AZURE_CLIENT_ID
AZURE_TENANT_ID
AZURE_SUBSCRIPTION_ID
```

are **identifiers**, not reusable Azure client secrets.

OIDC removes the need for:

```text
AZURE_CLIENT_SECRET
```

---

### **2. Verify client, tenant, and subscription IDs**

I check that:

```text
Client ID
→ correct Entra application / user-assigned identity

Tenant ID
→ correct Microsoft Entra tenant

Subscription ID
→ intended Azure subscription
```

Common mistake:

```text
client ID from prod identity
+
tenant ID from another tenant
```

or:

```text
workflow points to old subscription
```

---

### **3. Inspect the federated identity credential**

This is usually the most important OIDC troubleshooting step.

Entra must trust the token claims from GitHub.

The key claims are:

```text
Issuer
Subject
Audience
```

For GitHub Actions, the issuer is based on GitHub's OIDC provider and the commonly recommended Azure audience is:

```text
api://AzureADTokenExchange
```

GitHub's Azure OIDC documentation explicitly recommends that audience. ([GitHub Docs][2])

---

### **4. Check the subject EXACTLY**

For example, a federated credential could trust:

```text
repo:myorg/myrepo:ref:refs/heads/main
```

but the workflow may actually run from:

```text
feature/payment
```

Then:

```text
OIDC subject
≠
federated credential subject
```

and token exchange fails.

Another common pattern is using a GitHub **environment**:

```text
repo:myorg/myrepo:environment:production
```

instead of a branch-based subject.

The safest troubleshooting approach is:

```text
GitHub run
   ↓
inspect Federated token details
   ↓
compare actual subject
   ↓
Entra federated credential subject
```

The current `azure/login` guidance explicitly says the configured subject should match the subject claim issued to the workflow. ([GitHub][3])

---

### **5. Check workflow trigger/environment changes**

A workflow can work yesterday and fail today if someone changed:

```text
branch
GitHub environment
repository
organization/repository configuration
workflow trigger
```

because those can change the OIDC subject.

For example:

```text
Yesterday:
push → main

Today:
environment = production
```

may result in a different subject claim.

So I compare:

```text
trusted subject
vs
actual run context
```

rather than recreating credentials immediately.

---

### **6. Check the Entra application/service principal**

I verify:

```text
Application exists?
Service principal exists?
Federated credential exists?
Credential attached to correct identity?
Tenant correct?
```

A federated credential on:

```text
App A
```

does nothing if GitHub's:

```text
AZURE_CLIENT_ID
```

points to:

```text
App B
```

---

### **7. Separate OIDC authentication from Azure authorization**

This is a critical distinction.

Suppose:

```text
Azure Login
→ successful
```

but:

```text
az aks get-credentials
→ AuthorizationFailed
```

OIDC is **working**.

The problem is now:

```text
Azure RBAC
```

not federation.

Conceptually:

```text
OIDC
→ authentication

Azure RBAC
→ authorization
```

So after successful login I verify that the federated identity has:

```text
Contributor
AcrPush
AKS-related role
etc.
```

at the correct scope for whatever the workflow needs.

---

### **8. Check the exact error**

Examples:

```text
Unable to get ACTIONS_ID_TOKEN_REQUEST_URL
→ likely id-token permission issue
```

```text
No matching federated identity record found
→ issuer/subject/audience mismatch
```

```text
AuthorizationFailed after successful login
→ Azure RBAC
```

The error stage tells me which layer to investigate.

> **In an interview, I would say:**
> “I troubleshoot GitHub-to-Azure OIDC as a trust chain. First I verify the workflow has `id-token: write` and that `azure/login` is using the correct client ID, tenant ID and subscription ID. Then I inspect the federated credential in Entra and compare its issuer, audience and especially subject against the token produced by the actual workflow—branch and environment changes commonly cause subject mismatches. If Azure Login succeeds but the next Azure operation fails, OIDC is already working and I move to Azure RBAC rather than changing the federation.”

**Memory line:**
**OIDC failure → `id-token` → IDs → issuer/subject/audience → Entra identity → RBAC.**

**Interview trap:**
Do not confuse **successful OIDC login followed by `AuthorizationFailed`** with an OIDC failure. That is usually authorization.

**Keywords:**
GitHub Actions, OIDC, Workload Identity Federation, `id-token: write`, `azure/login@v3`, subject, audience, issuer

**Likely follow-ups:**

* Why is OIDC safer than storing an Azure client secret?
* What does `id-token: write` actually allow?
* What is the recommended Azure OIDC audience?
* Why might using a GitHub Environment change the subject claim?

### **T13-07. A deployment worked yesterday but fails today; how would you approach the problem?**

**Answer:**
Because it worked yesterday, I would start with **“what changed?”** rather than rebuilding everything. I would first identify the exact failing stage, compare the last successful execution with the first failed execution, and investigate changes in **code, configuration, credentials, permissions, dependencies, runner/tool versions, quotas, and Azure platform health**.

### **Diagnostic order**

```text
Worked yesterday
      ↓
Find exact failing step
      ↓
Compare last good vs first bad
      ↓
What changed?
      ↓
Code / Config / Identity / Dependency /
Platform / Capacity
      ↓
Reproduce and prove cause
      ↓
Rollback or fix
```

---

### **1. Identify exactly where the deployment fails**

I don't start with:

> “The pipeline is broken.”

I narrow it to:

```text
Checkout?
Build?
Unit tests?
Docker build?
ACR push?
Azure login?
Terraform plan?
Terraform apply?
Helm deployment?
AKS rollout?
Health check?
```

For example:

```text
Build ✓
ACR Push ✓
Terraform ✓
Helm upgrade ✗
```

Now most of the pipeline is already eliminated from investigation.

---

### **2. Compare last successful run against first failed run**

I would identify:

```text
Last successful deployment:
commit abc123

First failed deployment:
commit def456
```

Then compare:

```bash
git diff abc123..def456
```

I want to know whether anything changed in:

```text
application code
Dockerfile
Terraform
Helm values
workflow YAML
dependencies
configuration
```

This is one of the highest-value troubleshooting steps.

---

### **3. Check environment changes too**

Sometimes:

```text
Git commit = unchanged
```

but the environment changed.

Examples:

```text
secret expired
certificate expired
RBAC changed
Key Vault secret rotated
federated credential changed
NSG changed
Azure Policy changed
quota reached
DNS changed
```

So I compare:

```text
Application changes
+
Azure environment changes
```

---

### **4. Check authentication and authorization**

Credential problems are a common:

```text
worked yesterday
fails today
```

scenario.

I inspect whether:

```text
service-principal secret expired
certificate expired
federated credential changed
GitHub environment/branch changed
role assignment removed
PIM access expired
```

For OIDC:

```text
No secret expiry
```

is one of its advantages, but federation or RBAC configuration can still change.

---

### **5. Check external dependencies**

The pipeline may depend on:

```text
GitHub
ACR
Azure APIs
package registries
Docker Hub
Helm repository
Terraform Registry
third-party scanner
```

So:

```text
My configuration unchanged
```

doesn't necessarily mean:

```text
Everything external unchanged
```

I would inspect the exact upstream error rather than immediately modifying pipeline code.

---

### **6. Check unpinned dependencies and mutable artifacts**

This is a common hidden source of failure.

For example:

```text
ubuntu-latest
latest image
unversioned Helm dependency
floating Terraform provider
npm package range
```

could resolve differently today.

Example:

```text
Yesterday:
provider 4.35

Today:
provider 4.36
```

If behavior changed, the code may fail without any repository commit.

Similarly:

```text
image: latest
```

can point to a completely different artifact today.

This is why production systems should pin important versions and prefer immutable image digests.

---

### **7. Check Azure quotas and capacity**

Perhaps the deployment is valid but Azure says:

```text
QuotaExceeded
SkuNotAvailable
InsufficientCapacity
```

Then:

```text
pipeline logic
```

isn't necessarily the problem.

I check:

```text
subscription quota
regional SKU availability
IP address limits
node/VM capacity
resource limits
```

based on the actual failure.

---

### **8. Check Azure Service Health**

If multiple unrelated deployments suddenly fail:

```text
same region
same Azure service
same time
```

I would inspect:

```text
Azure Service Health
Resource Health
```

before modifying application configuration.

---

### **9. Correlate using timestamps**

Suppose:

```text
14:02 deployment begins
14:05 Azure login succeeds
14:06 ACR push succeeds
14:07 AKS rollout fails
```

Then I inspect:

```text
AKS events
pod events
container logs
image pull errors
admission-policy errors
```

around:

```text
14:07
```

rather than reading every log from the day.

---

### **10. Roll back when impact matters**

If this is production and:

```text
new release
→ outage
```

my priority is often:

```text
Restore service
      ↓
Then investigate deeply
```

For example:

```text
rollback deployment
```

or:

```text
return traffic to previous slot/version
```

if rollback is known safe.

I wouldn't debug for an hour while customers remain affected just to preserve the failed release.

---

### **Example**

```text
Worked yesterday
      ↓
Today Helm deployment fails
      ↓
Pods = ImagePullBackOff
      ↓
Image reference uses :latest
      ↓
latest tag now points to new broken image
      ↓
Deploy previous digest
      ↓
service restored
```

The lesson is:

```text
immutable artifact
> mutable tag
```

> **In an interview, I would say:**
> “Because it worked yesterday, I start by identifying the last successful run and first failed run and comparing them. I narrow the failure to one pipeline stage, then investigate changes in code, configuration and Azure, including RBAC, secrets, certificates, policies, quotas and networking. I also check things outside Git such as unpinned dependencies, mutable image tags, runner/tool updates and Azure Service Health. If production is affected, I prioritize restoring the previous known-good version and then complete root-cause analysis from the timestamps and evidence.”

**Memory line:**
**Worked yesterday, fails today → find the first changed thing between the last good and first bad run.**

**Interview trap:**
Do not assume **“no Git commit changed” means nothing changed**—credentials, permissions, dependencies, quotas, images, and cloud services can change independently.

**Keywords:**
Change correlation, last known good, immutable artifact, dependency pinning, rollback, Service Health, RCA

**Likely follow-ups:**

* What if there were no code changes?
* When would you rollback instead of troubleshooting in place?
* Why is `latest` dangerous?
* How would you investigate an intermittent deployment failure?

### **T13-08. A VM is running out of disk space; how would you investigate and fix it?**

**Answer:**
I would first establish **which filesystem is full and why**, because adding disk capacity before understanding consumption often postpones the same incident. I would check filesystem usage and inode exhaustion, identify the largest directories/files and deleted-but-open files, safely clean or rotate unnecessary data, and only resize the Azure managed disk if the workload genuinely needs more capacity. Resizing has two layers: **increase the Azure disk, then extend the partition/filesystem inside the guest OS**. ([Microsoft Learn][4])

### **Troubleshooting flow**

```text
Disk alert
   ↓
Which filesystem?
   ↓
Space or inode exhaustion?
   ↓
What consumed it?
   ↓
Can it be safely cleaned?
   ↓
Root cause?
   ↓
Need more capacity?
   ↓
Resize Azure disk
   ↓
Extend guest partition/filesystem
   ↓
Add monitoring/retention
```

---

### **1. Check filesystem usage**

Linux:

```bash
df -hT
```

Example:

```text
Filesystem     Size  Used  Avail Use%
/dev/sda1       64G   62G   2G    97%   /
/dev/sdc1      256G  80G  176G    32%   /data
```

Now I know:

```text
Root filesystem
→ problem

Data disk
→ healthy
```

---

### **2. Check inode exhaustion too**

A filesystem can report problems even when GB capacity remains because there are no free inodes.

```bash
df -i
```

For example:

```text
IUse% = 100%
```

with disk capacity:

```text
Use% = 60%
```

may indicate millions of tiny files.

So:

```text
Disk full
```

can mean:

```text
bytes exhausted
OR
inodes exhausted
```

---

### **3. Find the largest directories**

I narrow downward rather than run an uncontrolled scan of everything.

For example:

```bash
sudo du -xhd1 / | sort -h
```

Then perhaps:

```bash
sudo du -xhd1 /var | sort -h
```

I might find:

```text
/var/log          25G
/var/lib/docker   28G
/home              3G
```

Now the cause is clearer.

---

### **4. Check common growth sources**

Typical production offenders include:

```text
application logs
systemd journal
Docker/container layers
package caches
temporary files
database files
core dumps
backup files
old deployment artifacts
```

For journal logs:

```bash
journalctl --disk-usage
```

For container hosts:

```bash
docker system df
```

But I do **not** immediately run:

```bash
docker system prune -a
```

on production without understanding what will be deleted.

---

### **5. Check deleted-but-open files**

This is a very useful Linux troubleshooting point.

Suppose:

```text
10 GB application.log
```

is deleted, but the running process still has the file open.

Then:

```text
ls
→ file appears gone

df
→ space still consumed
```

Check:

```bash
sudo lsof +L1
```

The process may need to:

```text
reopen logs
restart safely
```

before the filesystem releases that space.

---

### **6. Stabilize the VM before it completely fills**

If `/` reaches 100%, critical services may fail:

```text
SSH
Azure agent
package manager
applications
logging
cloud-init
```

Microsoft documents full OS disks causing Linux service and even boot/connectivity failures. ([Microsoft Learn][5])

So during an incident I might safely remove:

```text
obsolete logs
old temporary files
known-safe caches
```

to create breathing room before deeper remediation.

---

### **7. Fix the root cause**

Suppose:

```text
/var/log/app.log
→ 30 GB
```

Then adding 100 GB isn't the real fix.

I should implement:

```text
logrotate
retention
compression
maximum log size
central log shipping
```

Similarly:

```text
Docker artifacts accumulating
→ cleanup lifecycle

Temporary files
→ scheduled cleanup

Database unexpectedly growing
→ application/data investigation
```

---

### **8. Resize if more capacity is genuinely required**

If:

```text
normal business data growth
```

requires a larger disk, I would first create an appropriate backup/snapshot and then increase the Azure managed disk.

For example:

```bash
az disk update \
  --resource-group rg-prod \
  --name vm01-osdisk \
  --size-gb 128
```

But the important point is:

```text
Azure disk: 64 GB → 128 GB
```

does **not automatically guarantee**:

```text
Linux filesystem: 64 GB → 128 GB
```

Microsoft explicitly treats resizing as two stages:

```text
1. Expand Azure managed disk
2. Extend guest volume/filesystem
```

([Microsoft Learn][4])

---

### **9. Extend the partition/filesystem**

What I run depends on:

```text
partition layout
LVM or non-LVM
ext4 or XFS
OS distribution
```

For a common non-LVM Linux setup, the steps might involve tools such as:

```bash
lsblk
```

then:

```text
grow partition
```

and:

```text
resize2fs
```

for ext4, or:

```text
xfs_growfs
```

for XFS.

I would inspect the actual disk layout before running resize commands.

Microsoft's Linux disk-expansion documentation specifically warns to understand the partition/filesystem layout and recommends backup/snapshot protection before expanding disks. ([Microsoft Learn][6])

---

### **10. Don't assume every disk can always resize live**

Many Azure managed-disk scenarios support online resizing, but some combinations of:

```text
VM SKU
disk type/configuration
shared disk
```

may require the VM to be deallocated.

Current Azure troubleshooting documentation explicitly lists scenarios where live disk resize isn't supported and deallocation is required. ([Microsoft Learn][7])

So I check support before promising:

> “There will definitely be zero downtime.”

---

### **11. Prevent recurrence**

After recovery I configure monitoring such as:

```text
Disk > 70%
→ warning

Disk > 85%
→ actionable alert

Disk growth rate abnormal
→ investigate
```

and fix retention before:

```text
97–100%
```

becomes the first signal.

For important systems I would also capacity-plan based on:

```text
GB growth/day
```

so I know roughly when storage will reach capacity.

> **In an interview, I would say:**
> “I first use `df -hT` and `df -i` to determine whether the issue is filesystem capacity or inode exhaustion, then use `du` and tools such as `journalctl --disk-usage` to identify what is consuming space. I also check deleted-but-open files with `lsof +L1`. I safely free enough space to stabilize the system and fix the cause—for example log rotation—before resizing. If genuine workload growth requires more capacity, I expand the Azure managed disk and then extend the partition and filesystem inside Linux, because those are separate steps. Finally I add disk-usage and growth alerts so the next incident is caught earlier.”

**Memory line:**
**Disk full → find what grew first; resize only after understanding whether growth is legitimate.**

**Interview trap:**
Increasing the Azure managed disk size is only **half the job**; the guest partition/filesystem may still need to be expanded.

**Keywords:**
`df`, `du`, inodes, `lsof +L1`, log rotation, managed disk resize, filesystem expansion, capacity monitoring

**Likely follow-ups:**

* What is inode exhaustion?
* Why can `df` show a full disk after you deleted a large log?
