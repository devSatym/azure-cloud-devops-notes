### **T13-21. Logs show no errors but users report failed requests; how would you proceed?**

**Answer:**
I would not conclude that the application is healthy just because its logs contain no errors. I would first **reproduce the failure from the user's perspective**, capture the exact HTTP status/timeout and request timestamp, then trace the complete path through **DNS → edge/load balancer → application → dependencies**. “No errors in logs” can simply mean I am looking at the wrong layer, the failed request never reached the application, or the application lacks sufficient telemetry.

### **Troubleshooting flow**

```text
Users report failures
        ↓
Reproduce externally
        ↓
What exactly fails?
DNS / timeout / 403 / 5xx / TLS
        ↓
Did request reach edge?
        ↓
Did request reach application?
        ↓
Did application call dependencies?
        ↓
Find the first layer where evidence disappears
```

### **1. Reproduce the exact user request**

I would capture:

```text
Affected URL/API
Exact timestamp
User geography
HTTP status
Timeout vs immediate error
Request/correlation ID
```

For example:

```bash
curl -v https://app.example.com/api/orders
```

The difference matters:

```text
DNS error
→ DNS layer

TLS failure
→ certificate/edge

403
→ WAF/auth/network policy

502/503
→ ingress/backend availability

500
→ application/dependency

Timeout
→ network/backend/slow dependency
```

---

### **2. Check whether the request reached the application**

I would work backward from the public entry point.

For example:

```text
User
 ↓
Azure Front Door
 ↓
Application Gateway / Ingress
 ↓
Application
```

Check:

```text
Front Door access/WAF logs
Application Gateway logs
Ingress logs
Application Insights requests
```

Suppose the user reports:

```text
14:03:20 → failed request
```

but Application Insights has **no corresponding request**.

That suggests:

```text
failure occurred before application
```

so I investigate:

```text
DNS
Front Door
WAF
TLS
Application Gateway
routing
```

instead of application code.

---

### **3. If the request reached the application, trace it**

With Application Insights/OpenTelemetry:

```text
Request
   ↓
Trace / OperationId
   ↓
Dependencies
   ↓
Exception / response
```

A request might show:

```text
API returned 503
Application log contains no exception
```

because the application deliberately returned 503 when:

```text
database unavailable
queue unavailable
dependency timed out
```

No stack trace is required for a user-visible failure.

---

### **4. Check successful-looking application logs carefully**

A common anti-pattern:

```text
log:
"Request processed"
```

followed by:

```text
downstream response generation fails
```

or:

```text
reverse proxy drops response
```

So I correlate:

```text
incoming request
response status
duration
dependency result
trace ID
```

rather than searching only for the text:

```text
ERROR
```

Observability should answer:

> What happened to this specific user request?

not merely:

> Did the application print an error?

---

### **5. Check edge/WAF failures**

Example:

```text
User → Front Door WAF → blocked
```

The application receives:

```text
nothing
```

and therefore logs:

```text
nothing
```

The relevant evidence exists at:

```text
Front Door / WAF
```

not inside the container.

Similarly:

```text
Application Gateway has no healthy backends
→ user gets 502/503
→ application may log nothing
```

---

### **6. Check client-side failures**

If the backend request succeeds but users still say the application failed, I would consider:

```text
JavaScript error
browser/CORS issue
frontend API mismatch
expired authentication token
client-side timeout
```

For example:

```text
Backend API → 200
Browser frontend → JS exception
User → "application failed"
```

Server logs can be perfectly clean.

---

### **7. Check whether telemetry itself is incomplete**

“No errors” might mean:

```text
wrong Log Analytics workspace
wrong application role
wrong time range
logging level changed
telemetry sampling
agent/collector issue
missing exception instrumentation
```

I would confirm:

```text
requests still arriving?
traces arriving?
dependencies arriving?
exceptions arriving?
```

before trusting the absence of errors.

---

### **8. Compare affected and successful requests**

This is especially powerful.

| Dimension  | Successful | Failed   |
| ---------- | ---------- | -------- |
| Region     | India      | India    |
| Version    | v2         | v2       |
| Pod        | pod-1      | pod-4    |
| Origin     | region-a   | region-b |
| Status     | 200        | 503      |
| Dependency | 80 ms      | timeout  |

The first systematic difference often reveals the cause.

---

> **In an interview, I would say:**
> “No application errors don't prove requests succeeded. I would reproduce the exact user request, capture its status, timestamp and correlation ID, and trace the request from DNS and the edge through the application and dependencies. If Front Door sees the request but Application Insights doesn't, I know the failure happened before the application. If the application receives it, I use distributed tracing to inspect dependencies and the returned status. I would also check WAF, ingress and client-side errors and verify that telemetry itself hasn't stopped. My goal is to find the first layer where the failed request differs from a successful one.”

**Memory line:**
**No error log does not mean no failure—trace the user's request end to end.**

**Interview trap:**
Do not search only for `ERROR` strings. A request can fail in DNS, WAF, ingress, dependencies, or the browser without generating an application exception.

**Keywords:**
Correlation ID, distributed tracing, Application Insights, WAF logs, ingress logs, synthetic testing, client-side failure

**Likely follow-ups:**

* What if the request never appears in Application Insights?
* What if Application Insights shows HTTP 200 but the user still sees failure?
* Why might a 503 generate no application exception?
* How would correlation IDs help?

### **T13-22. An NSG appears correct but connectivity still fails; what else would you inspect?**

**Answer:**
An NSG is only **one control in the packet path**. If the effective NSG rules allow the traffic, I would next inspect **routing/next hop, UDRs, Azure Firewall or NVA, DNS, guest OS firewall, VNet peering, Private Endpoint configuration, service-side firewall, load-balancer health, and—in AKS—NetworkPolicy**. I would prove each layer rather than continuing to modify an NSG that is already allowing the packet.

### **Troubleshooting path**

```text
NSG appears correct
       ↓
Prove effective NSG decision
       ↓
Effective route / Next Hop
       ↓
Firewall / NVA
       ↓
DNS
       ↓
Destination/service policy
       ↓
Guest/Kubernetes firewall/policy
```

---

### **1. Verify the *effective* rule**

Do not trust only the NSG resource you opened.

Traffic can be affected by:

```text
Subnet NSG
+
NIC NSG
+
Azure Virtual Network Manager
  security admin rules
```

I would use **Network Watcher IP Flow Verify**, which can tell me whether a packet is allowed or denied and which rule made the decision. Microsoft's current networking guidance recommends IP Flow Verify as an early troubleshooting step. ([Microsoft Learn][1])

If it says:

```text
Allow
```

I move on.

---

### **2. Check effective routes**

A packet can be permitted by the NSG but sent completely the wrong way.

Example:

```text
10.20.5.10
   ↓
UDR
   ↓
NVA 10.1.0.4
```

when I expected:

```text
VNet peering
```

I inspect:

```text
Effective Routes
Network Watcher Next Hop
```

Next Hop shows the selected next-hop type, IP, and route table, helping identify bad UDR or NVA routing. ([Microsoft Learn][2])

---

### **3. Check Azure Firewall / NVA**

If:

```text
Next Hop = VirtualAppliance
```

then the next question is:

```text
Does that firewall allow this flow?
```

I inspect:

```text
Azure Firewall rules/logs
NVA policy
IP forwarding
SNAT/DNAT
NVA health
return route
```

Possible situation:

```text
NSG → Allow
Azure Firewall → Deny
```

Connectivity still fails.

---

### **4. Check asymmetric routing**

Example:

```text
Request:
VM → Firewall → Server
```

but:

```text
Response:
Server → directly to VM
```

A stateful firewall may see only one side of the session and drop traffic.

So I validate:

```text
forward path
+
return path
```

---

### **5. Check DNS**

Maybe connectivity to:

```text
10.20.4.5
```

works, but:

```text
db.example.internal
```

resolves incorrectly.

Test:

```bash
nslookup <hostname>
```

For Private Endpoint workloads, verify the service resolves to the expected private IP.

---

### **6. Check VNet peering**

For cross-VNet traffic:

```text
Peering state = Connected?
Address spaces overlap?
Required gateway transit configured?
Routes propagated?
```

A healthy NSG cannot fix a broken VNet path.

---

### **7. Check destination-side controls**

Examples:

```text
Azure SQL firewall
Storage firewall
Key Vault public/private networking
Private Endpoint connection state
App Service access restrictions
```

So:

```text
source NSG allows
```

doesn't mean:

```text
destination service allows
```

---

### **8. Check guest OS**

For VM-to-VM traffic:

```text
Azure NSG → Allow
Linux nftables → Deny
```

is entirely possible.

Check:

```bash
sudo nft list ruleset
sudo ufw status
ss -lntp
```

Also confirm the destination application is actually listening on the expected port.

---

### **9. For AKS, check Kubernetes NetworkPolicy**

Another layer exists:

```text
Azure network allows
      ↓
Kubernetes NetworkPolicy denies
```

Check:

```bash
kubectl get networkpolicy -A
```

A VM on the same subnet may work while a pod is blocked.

---

### **10. Use Connection Troubleshoot**

Rather than manually guessing every layer, I would use **Network Watcher Connection Troubleshoot** where supported. It can run connectivity, NSG, and next-hop diagnostics and identify issues such as missing routes or traffic filtering. ([Microsoft Learn][3])

> **In an interview, I would say:**
> “If the NSG looks correct, I first prove the effective security decision using IP Flow Verify rather than assuming the portal configuration tells the whole story. If traffic is allowed, I check effective routes and Network Watcher Next Hop, then any Azure Firewall or NVA, VNet peering and return path. I also validate DNS, the destination service's own firewall or Private Endpoint configuration, and the guest OS firewall. For AKS I add Kubernetes NetworkPolicy. An NSG can allow the packet while another layer still drops it.”

**Memory line:**
**NSG allow only proves one layer; routing, firewall, destination, and guest policy still matter.**

**Interview trap:**
Do not keep adding wider NSG rules once IP Flow Verify already proves the packet is allowed.

**Keywords:**
IP Flow Verify, effective routes, Next Hop, UDR, Azure Firewall, NVA, VNet peering, NetworkPolicy

**Likely follow-ups:**

* What's the difference between IP Flow Verify and Next Hop?
* How can asymmetric routing break a connection?
* Can a service firewall deny traffic even when the NSG allows it?
* Why might a VM work while an AKS pod fails?

### **T13-23. How would you determine whether an outage is caused by your application, Azure networking, DNS, or an Azure platform issue?**

**Answer:**
I would use a **layered fault-isolation approach** and find the first point where the request fails. I would start with the real user endpoint, independently test DNS, then test raw network connectivity, then test the application directly and its dependencies, and finally correlate the timing with Azure Resource Health and Service Health. I would avoid declaring “Azure outage” or “application bug” until evidence isolates the layer.

### **Fault-isolation model**

```text
User
 ↓
DNS
 ↓
Azure edge/network
 ↓
Load balancer / ingress
 ↓
Application
 ↓
Dependencies
 ↓
Azure platform
```

---

### **1. Start with the external symptom**

Test:

```bash
curl -vk https://app.example.com
```

Capture:

```text
DNS error?
Timeout?
TLS error?
403?
502/503?
500?
High latency?
```

This immediately narrows the search.

---

### **2. Isolate DNS**

Run:

```bash
nslookup app.example.com
```

or:

```bash
dig app.example.com
```

If DNS fails but connecting through a known-valid endpoint/IP works:

```text
Application/network path may be healthy
DNS is suspect
```

Check:

```text
Azure DNS
Private DNS
custom DNS
CNAME/A records
Traffic Manager records
Private Endpoint resolution
```

---

### **3. Isolate Azure networking**

If DNS resolves correctly, test the destination port:

```bash
nc -vz <destination> 443
```

Then use Network Watcher:

```text
Connection Troubleshoot
IP Flow Verify
Next Hop
Effective Routes
```

Microsoft recommends Network Watcher as the starting point for Azure network connectivity diagnosis; IP Flow Verify checks filtering, Next Hop validates routing, and Packet Capture can be used for deeper analysis. ([Microsoft Learn][1])

If:

```text
DNS ✓
TCP ✗
```

I focus on:

```text
NSG
UDR
Firewall/NVA
peering
Private Endpoint
route
```

---

### **4. Isolate the application**

If:

```text
DNS ✓
TCP ✓
TLS ✓
```

but:

```text
HTTP 500
```

I move up the stack.

Test:

```text
/health
/readiness
```

and check:

```text
Application Insights
requests
exceptions
dependencies
container/application logs
```

If a direct backend request also fails:

```text
application/dependency
```

becomes more likely.

If:

```text
backend direct ✓
public frontend ✗
```

I focus on:

```text
Front Door
Application Gateway
Ingress
WAF
routing
```

---

### **5. Isolate dependencies**

The application may be running but unusable because:

```text
Azure SQL unavailable
Key Vault denied
Redis unavailable
Storage unavailable
downstream API timeout
```

Using distributed tracing:

```text
User request
  ↓
App = 100 ms
  ↓
SQL dependency = timeout
```

points me toward the dependency path rather than the web tier.

---

### **6. Check Azure Resource Health**

Resource Health answers questions around an individual resource:

```text
Is Azure reporting this VM/resource as available?
```

But Microsoft explicitly notes that a resource can appear healthy while users still experience issues caused by the application, misconfiguration, or networking. ([Microsoft Learn][4])

So:

```text
Resource Health = Healthy
```

does **not** close the investigation.

---

### **7. Check Azure Service Health**

I then check whether Azure has an active service event affecting:

```text
my subscription
my Azure service
my region
```

Azure Service Health provides the personalized view of service issues, planned maintenance, and advisories relevant to the services and regions you use. ([Microsoft Learn][5])

For broad incidents, Azure Status can provide global visibility, but Microsoft recommends Service Health for the personalized impact view. ([Microsoft Learn][6])

---

### **8. Correlate the timestamp**

For example:

```text
14:02
Azure Firewall policy deployed

14:03
synthetic test begins failing

14:03
application receives zero requests

14:04
Resource Health still Healthy
```

That evidence strongly suggests:

```text
customer networking/configuration issue
```

instead of application or Azure platform.

Another example:

```text
Region-wide SQL failures
+
Service Health reports SQL issue
+
no application deployment
```

makes:

```text
Azure service issue
```

far more likely.

---

### **Useful decision tree**

```text
Endpoint fails
   ↓
DNS resolves?
 ┌───────┴───────┐
 No              Yes
 ↓                ↓
DNS            TCP works?
problem        ┌───┴───┐
              No       Yes
              ↓         ↓
          Network     HTTP/app
                       ↓
                   Backend works?
                  ┌────┴────┐
                  No        Yes
                  ↓          ↓
             App/dependency Edge/WAF
```

In parallel:

```text
Resource Health
+
Service Health
```

to identify Azure-platform impact.

> **In an interview, I would say:**
> “I isolate the outage by moving through the stack. I first test the real endpoint, then resolve DNS independently. If DNS is correct I test TCP connectivity and use Network Watcher tools to check filtering and routing. If networking works, I test the backend application and use Application Insights to inspect requests, exceptions and dependencies. A healthy backend with a failing public endpoint points toward Front Door, WAF or ingress; a failing backend points toward application or dependencies. In parallel I check Resource Health for individual-resource impact and Service Health for Azure service or regional incidents. I only assign the outage to a layer once the evidence shows where the request stops.”

**Memory line:**
**Find the first broken hop: DNS → network → edge → app → dependency → Azure platform.**

**Interview trap:**
Do not blame Azure just because multiple Azure resources are involved—and do not blame the application merely because Resource Health says Azure is healthy.

**Keywords:**
Fault isolation, DNS, Network Watcher, Application Insights, Resource Health, Service Health, dependency tracing

**Likely follow-ups:**

* What's the difference between Resource Health and Service Health?
* What if DNS and TCP work but users still get 503?
* How would you prove a network issue rather than an application issue?
* What would you do if Service Health shows no outage but you suspect Azure?

### **T13-24. What Azure tools would you use during a production networking incident?**

**Answer:**
My primary Azure networking troubleshooting toolkit would be **Azure Network Watcher**, especially **Connection Troubleshoot, IP Flow Verify, Next Hop, Effective Security Rules, Packet Capture, Connection Monitor, Topology, and flow logs/Traffic Analytics**. I would combine those with **Azure Monitor/Log Analytics, Azure Firewall logs, Resource Health, and Service Health** depending on the incident. I would choose tools based on the question I'm trying to answer rather than dumping every tool into the investigation.

Microsoft's current guidance calls Network Watcher the first stop for diagnosing Azure connectivity issues. ([Microsoft Learn][1])

### **My practical order**

```text
Connectivity incident
       ↓
Connection Troubleshoot
       ↓
IP Flow Verify
       ↓
Next Hop / Effective Routes
       ↓
Firewall / flow logs
       ↓
Packet Capture
       ↓
Continuous monitoring
```

---

### **1. Connection Troubleshoot**

Use it when I want:

> **Can source A reach destination B on this protocol/port, and what appears to be wrong?**

Example:

```text
VM
 ↓ TCP/443
Key Vault / Server / FQDN
```

Connection Troubleshoot can combine connectivity, NSG diagnostics, and next-hop information in a point-in-time test. ([Microsoft Learn][3])

This is often my first tool during a live incident.

---

### **2. IP Flow Verify**

Question:

> **Would Azure's network security rules allow this specific packet?**

It evaluates details such as:

```text
Source IP
Destination IP
Source port
Destination port
Protocol
```

and reports:

```text
Allow / Deny
+
responsible rule
```

Current Microsoft guidance says it evaluates NSG and Azure Virtual Network Manager security admin rules. ([Microsoft Learn][1])

Use it for:

```text
"Is an NSG/security rule blocking TCP 443?"
```

---

### **3. Next Hop**

Question:

> **Where is Azure actually sending this packet?**

It can report next-hop types such as:

```text
Internet
VirtualAppliance
VirtualNetworkGateway
VirtualNetwork
VirtualNetworkPeering
None
```

and identifies the route involved. ([Microsoft Learn][2])

Perfect for:

```text
bad UDR
wrong firewall path
routing to on-prem unexpectedly
```

---

### **4. Effective routes / Effective security rules**

These show what is **actually effective** after inheritance and configuration are combined.

I use:

```text
Effective security rules
→ what traffic filtering applies?

Effective routes
→ what routing applies?
```

instead of reading one NSG or one route table and assuming it tells the whole story.

---

### **5. Packet Capture**

When higher-level tools don't explain the failure:

```text
SYN sent?
SYN-ACK returned?
RST?
TLS handshake?
Retransmissions?
```

I use Network Watcher **Packet Capture**.

It can remotely capture VM/VMSS traffic for deeper protocol analysis. ([Microsoft Learn][7])

Typical use:

```text
Application says timeout
NSG says Allow
route looks correct
       ↓
Packet Capture
       ↓
SYN leaves
no SYN-ACK comes back
```

Now I know which direction to investigate.

---

### **6. Network Watcher Topology**

Topology helps visualize:

```text
VNets
Peerings
VMs
network resources
relationships
```

and gives contextual access to diagnostics such as:

```text
Connection Troubleshoot
Packet Capture
Next Hop
```

Microsoft's current topology view can cover resources across subscriptions, regions, and resource groups. ([Microsoft Learn][8])

Useful when I'm unfamiliar with a complicated production topology.

---

### **7. Connection Monitor**

Connection Troubleshoot is:

```text
point-in-time diagnosis
```

Connection Monitor is:

```text
continuous connectivity monitoring
```

It can continuously measure:

```text
reachability
latency
packet loss
```

across TCP, ICMP, and HTTP tests and provide path insights. ([Microsoft Learn][9])

Great for answering:

> Did connectivity degrade at exactly 14:03, or has latency been rising for hours?

---

### **8. VNet flow logs + Traffic Analytics**

For longer-term traffic visibility:

```text
VNet traffic
   ↓
VNet flow logs
   ↓
Traffic Analytics / Log Analytics
```

This can help identify:

```text
traffic patterns
top talkers
open ports
geographic flows
anomalies
```

Current best-practice note: Microsoft recommends moving to **VNet flow logs**. No new NSG flow logs can be created after **June 30, 2025**, and Microsoft says to migrate before **September 30, 2027**. ([Microsoft Learn][1])

So in a 2026 interview I would say:

```text
Prefer VNet flow logs for new designs
```

rather than designing new monitoring around NSG flow logs.

---

### **9. Azure Firewall logs**

If:

```text
Next Hop = Azure Firewall
```

I inspect firewall logs for:

```text
Allow
Deny
Network rule
Application rule
DNAT
```

and correlate:

```text
source
destination
port
timestamp
```

with the failed request.

---

### **10. VPN Troubleshoot**

For:

```text
On-prem
   ↓
VPN Gateway
   ↓
Azure
```

Network Watcher provides **VPN troubleshoot** for gateway and connection diagnostics. Network Watcher currently lists this among its core diagnostic tools. ([Microsoft Learn][10])

For ExpressRoute I would additionally inspect the circuit, peering, route/BGP state, and Azure Monitor metrics relevant to ExpressRoute.

---

### **11. Azure Monitor + Log Analytics**

I use these for correlation:

```text
network failure timestamp
       ↓
Firewall logs
Application logs
metrics
Activity Log
```

Example:

```text
14:01 UDR modified
14:02 packet loss starts
14:03 application 503s start
```

That creates an incident timeline instead of independent guesses.

---

### **12. Resource Health + Service Health**

If customer configuration looks healthy, I check:

```text
Resource Health
→ individual resource status

Service Health
→ Azure service/region incidents relevant to me
```

Azure Service Health is specifically intended to show service issues and planned events affecting the subscriptions, regions, and services you use. ([Microsoft Learn][5])

---

### **Tool → Question mapping**

| Tool                     | Question it answers                              |
| ------------------------ | ------------------------------------------------ |
| Connection Troubleshoot  | Can A reach B? Why not?                          |
| IP Flow Verify           | Is security filtering allowing the packet?       |
| Next Hop                 | Where will Azure route it?                       |
| Effective Routes         | Which routes actually apply?                     |
| Effective Security Rules | Which filtering rules actually apply?            |
| Packet Capture           | What is happening at packet/protocol level?      |
| Connection Monitor       | Is connectivity/latency degrading over time?     |
| Topology                 | How are my network resources connected?          |
| VNet flow logs           | What traffic actually traversed the VNet?        |
| Traffic Analytics        | What traffic patterns/anomalies exist?           |
| Firewall logs            | Did the firewall allow or deny it?               |
| Service Health           | Is Azure itself reporting an impacting incident? |

> **In an interview, I would say:**
> “During a production network incident I usually start with Network Watcher Connection Troubleshoot to test the actual source, destination and port. Then I use IP Flow Verify for security filtering and Next Hop/effective routes for routing. If traffic goes through Azure Firewall I correlate its logs, and if the cause is still unclear I use Packet Capture. Connection Monitor gives me historical reachability, latency and packet-loss trends, while VNet flow logs and Traffic Analytics provide broader traffic visibility. I also use Topology to understand complex environments and Resource Health/Service Health to rule in or out Azure platform issues.”

**Memory line:**
**Filtering → IP Flow Verify; routing → Next Hop; end-to-end → Connection Troubleshoot; packets → Packet Capture.**

**Interview trap:**
Do not answer this question with a random list of Azure tools. Explain **which diagnostic question each tool answers and the order you would use them in**.

**Keywords:**
Network Watcher, Connection Troubleshoot, IP Flow Verify, Next Hop, Packet Capture, Connection Monitor, VNet flow logs, Traffic Analytics

**Likely follow-ups:**

* IP Flow Verify vs Connection Troubleshoot?
* Connection Monitor vs Connection Troubleshoot?
* When would you use Packet Capture?
* What should new deployments use instead of NSG flow logs?
