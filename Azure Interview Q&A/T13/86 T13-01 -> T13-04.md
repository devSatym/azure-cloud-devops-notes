### **T13-01. A VM cannot access the internet; what would you check?**

**Answer:**
I would troubleshoot this **from the VM outward**, first proving whether the problem is DNS or general outbound connectivity, then checking the VM's effective route, explicit Azure egress path, NSGs, any Azure Firewall/NVA, and finally guest OS configuration. I would avoid randomly changing NSGs before identifying where the packet is failing.

### **Troubleshooting flow**

```text
VM cannot reach internet
        ↓
IP connectivity or DNS?
        ↓
Effective route / next hop
        ↓
Explicit outbound method
        ↓
NSG outbound rules
        ↓
Firewall / NVA / UDR
        ↓
Guest firewall / proxy / DNS
```

### **1. First determine whether it is DNS or networking**

From Linux:

```bash
curl -I https://1.1.1.1
curl -I https://www.microsoft.com
```

or:

```bash
nslookup www.microsoft.com
```

I am trying to distinguish:

```text
IP works + hostname fails
→ DNS problem

Both fail
→ routing / egress / firewall problem
```

I wouldn't rely only on `ping`, because ICMP behavior isn't necessarily representative of normal TCP/HTTPS internet connectivity.

---

### **2. Check whether the VM actually has an outbound path**

This is especially important **now**.

For API versions released after **March 31, 2026**, new Azure VNets default to **private subnets**, so a VM might not receive implicit default outbound connectivity. An explicit outbound mechanism such as **NAT Gateway, Azure Firewall/NVA, Load Balancer outbound rules, or a directly associated public IP** may be required. Microsoft recommends explicit outbound connectivity instead of relying on default outbound access. ([Microsoft Learn][1])

For production, I would normally prefer:

```text
Private VM
   ↓
Subnet
   ↓
NAT Gateway
   ↓
Internet
```

or:

```text
Private VM
   ↓
0.0.0.0/0 UDR
   ↓
Azure Firewall
   ↓
Internet
```

rather than assigning every VM a public IP.

---

### **3. Check effective routes**

I would inspect the NIC's **effective routes**.

CLI:

```bash
az network nic show-effective-route-table \
  --resource-group <rg> \
  --name <nic>
```

I specifically want to know what happens to:

```text
0.0.0.0/0
```

Possible results:

```text
Internet
→ direct/default path

VirtualAppliance
→ traffic goes through firewall/NVA

None
→ routing problem
```

Azure Network Watcher's **Next hop** is also useful for proving which route Azure actually chooses. ([Microsoft Learn][2])

---

### **4. Check NSG outbound rules**

Next I inspect effective NSG rules on:

```text
NIC
+
Subnet
```

I look for something like:

```text
Deny
Destination = Internet
Port = 443
```

or a broad:

```text
DenyInternetOutbound
```

Azure Network Watcher Connection Troubleshoot can identify an NSG rule blocking outbound traffic and show the effective next hop. ([Microsoft Learn][3])

For example:

```bash
az network watcher test-connectivity \
  --resource-group <rg> \
  --source-resource <vm-name> \
  --dest-address www.microsoft.com \
  --protocol TCP \
  --dest-port 443
```

That helps answer:

> Is Azure networking actually allowing TCP/443 from this VM?

---

### **5. Check UDR / Azure Firewall / NVA**

Suppose:

```text
0.0.0.0/0
    ↓
Azure Firewall
```

Then the VM itself may be configured perfectly, but the firewall could block:

```text
HTTPS
DNS
specific FQDN
application rule
network rule
```

So I would follow:

```text
VM
 ↓
NSG
 ↓
UDR
 ↓
Firewall/NVA
 ↓
Internet
```

If using an NVA, I would also verify:

```text
IP forwarding
NVA health
NVA routing
SNAT
firewall policy
```

Network Watcher tools such as **IP Flow Verify** and Connection Troubleshoot help narrow that path. ([Microsoft Learn][4])

---

### **6. Check DNS**

If:

```bash
curl https://<known-ip>
```

works but:

```bash
curl https://example.com
```

does not, I focus on DNS.

Check:

```bash
cat /etc/resolv.conf
nslookup microsoft.com
```

Potential causes:

```text
Custom DNS server unavailable
Wrong DNS IP configured on VNet
Firewall blocking DNS
DNS forwarder failure
```

---

### **7. Check guest OS**

Only after the Azure path looks correct would I investigate:

```text
iptables / nftables
local firewall
proxy variables
broken network configuration
application-specific proxy settings
```

For example:

```bash
ip route
ip addr
env | grep -i proxy
```

---

### **Strong interview flow**

```text
1. Is VM healthy?
2. IP connectivity vs DNS?
3. Effective route / next hop?
4. Explicit outbound path?
5. NSG blocking?
6. Firewall/NVA blocking?
7. Guest OS/proxy/DNS?
```

> **In an interview, I would say:**
> “I would first determine whether the VM has a general networking problem or only a DNS problem. Then I would inspect effective routes and the next hop for `0.0.0.0/0`, confirm that the subnet has an explicit outbound path such as NAT Gateway or Azure Firewall, and review effective NSG outbound rules. If traffic is forced through an NVA or Azure Firewall, I would check its policy and SNAT path. I would use Network Watcher Connection Troubleshoot to identify exactly where the connection is blocked, and only after the Azure network path is healthy would I investigate the VM's local firewall, proxy, or DNS configuration.”

**Memory line:**
**Outbound failure → DNS/IP → route → egress → NSG → firewall → guest OS.**

**Interview trap:**
Do not assume every Azure VM automatically gets internet access. For new VNet API versions after **March 31, 2026**, private subnets are the default and explicit outbound connectivity may be required. ([Microsoft Learn][1])

**Keywords:**
Effective routes, NAT Gateway, NSG, UDR, Azure Firewall, Network Watcher, Next Hop, explicit outbound

**Likely follow-ups:**

* How does a private VM access the internet without a public IP?
* NAT Gateway vs Azure Firewall for outbound access?
* What does a `0.0.0.0/0` UDR do?
* Which Network Watcher tools would you use?

### **T13-02. You cannot SSH into an Azure VM; how would you troubleshoot it?**

**Answer:**
I would narrow the failure domain in this order: **VM health → network path → port 22 → SSH service → authentication**. I would first identify whether the TCP connection cannot reach the VM or whether SSH reaches the server and then rejects the login, because those are completely different problems.

### **Troubleshooting tree**

```text
Cannot SSH
    ↓
VM running/healthy?
    ↓
Can TCP/22 reach VM?
    ↓
NSG / route / public-private path
    ↓
Is sshd listening?
    ↓
Guest firewall
    ↓
SSH key/user/Entra permissions
```

---

### **1. Read the actual SSH error**

The error tells me where to start.

#### Timeout

```text
ssh: connect to host x.x.x.x port 22: Connection timed out
```

Usually points toward:

```text
network path
NSG
route
firewall
wrong IP
VM unavailable
```

#### Connection refused

```text
Connection refused
```

Often means:

```text
VM reachable
but sshd not listening
or local firewall/service issue
```

#### Permission denied

```text
Permission denied (publickey)
```

Usually means:

```text
network works
SSH server responded
authentication failed
```

That distinction saves a lot of troubleshooting time.

---

### **2. Check VM and boot health**

First:

```text
VM power state = Running?
Resource Health = Healthy?
Boot Diagnostics = normal?
```

If the OS didn't boot successfully, changing NSGs won't help.

Microsoft's SSH troubleshooting guidance recommends checking VM Resource Health and Boot Diagnostics early in the investigation. ([Microsoft Learn][5])

---

### **3. Verify the connectivity model**

I ask:

```text
Does VM have public IP?
```

If yes:

```text
Laptop
 ↓
Internet
 ↓
VM public IP
```

If the VM is private:

```text
Laptop
 ↓
Bastion / VPN / ExpressRoute / jump host
 ↓
Private VM
```

A private VM without a public path cannot simply be SSHed into from the internet.

For production I would generally prefer:

```text
Azure Bastion
```

or private connectivity rather than opening SSH globally.

---

### **4. Check NSG port 22**

I inspect effective inbound rules on:

```text
Subnet
+
NIC
```

I need an allowed path such as:

```text
Source = admin IP / Bastion subnet
Protocol = TCP
Port = 22
Action = Allow
```

not:

```text
Source = *
Port = 22
```

unless there is a justified temporary need.

Microsoft recommends using effective security rules or Network Watcher IP Flow Verify to confirm whether an NSG is blocking SSH. ([Microsoft Learn][5])

---

### **5. Check effective routes**

Next:

```text
Client → VM
VM → Client return path
```

If a UDR sends traffic through:

```text
NVA / Firewall
```

I verify the return path isn't asymmetric or blocked.

Network Watcher's **Next Hop** and Connection Troubleshoot help here.

---

### **6. Test TCP/22**

From an allowed source:

```bash
nc -vz <vm-ip> 22
```

or use Network Watcher.

If TCP/22 cannot be established:

```text
stay in networking
```

If TCP/22 succeeds:

```text
move to guest OS / authentication
```

---

### **7. Check SSH inside the VM**

If networking looks healthy, I use:

```text
Azure Serial Console
```

or:

```text
Run Command
```

because these don't depend on a working SSH session.

Microsoft specifically recommends Serial Console for situations where SSH itself is unavailable. ([Microsoft Learn][5])

Inside Linux:

```bash
systemctl status ssh
```

or:

```bash
systemctl status sshd
```

and:

```bash
ss -lntp | grep :22
```

I want:

```text
sshd running
+
listening on TCP/22
```

Then check guest firewall:

```bash
sudo ufw status
sudo nft list ruleset
```

---

### **8. Check authentication**

If I get:

```text
Permission denied (publickey)
```

I verify:

```text
Correct username?
Correct private key?
Matching public key in authorized_keys?
Correct permissions?
```

Typical Linux permissions:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

If using Microsoft Entra SSH login, the identity also needs an appropriate role such as:

```text
Virtual Machine User Login
```

or:

```text
Virtual Machine Administrator Login
```

Microsoft documents missing Entra VM login role assignment as a cause of `Permission denied (publickey)`. ([Microsoft Learn][5])

---

### **9. Reset only after diagnosis**

Azure supports operations such as:

```text
Reset SSH configuration
Reset SSH public key
```

and VMAccess.

But I would not start there.

My preference is:

```text
Find cause
   ↓
Fix targeted issue
```

rather than resetting configuration and potentially hiding the original problem.

> **In an interview, I would say:**
> “I first classify the error. A timeout usually means networking, while `Permission denied` means TCP and SSH are already working and authentication is the problem. I check VM health and boot diagnostics, confirm whether access should come through a public IP, Bastion, or private network, then inspect effective NSG rules and routing for TCP 22. If TCP reaches the VM, I use Serial Console or Run Command to check `sshd`, the guest firewall and whether port 22 is listening. Finally I validate the username, SSH key, file permissions, or Entra VM-login RBAC role.”

**Memory line:**
**SSH troubleshooting = VM → network → port 22 → sshd → credentials.**

**Interview trap:**
If you already receive `Permission denied (publickey)`, don't waste time troubleshooting the NSG first—the connection has already reached SSH.

**Keywords:**
SSH, NSG, TCP 22, Boot Diagnostics, Serial Console, Run Command, `sshd`, VM Login RBAC

**Likely follow-ups:**

* How would you access a private VM without a public IP?
* What does `Connection refused` indicate?
* What is Azure Serial Console useful for?
* How does Entra-based SSH differ from SSH-key authentication?

### **T13-03. An application cannot connect to an Azure SQL database; what would you investigate?**

**Answer:**
I would troubleshoot Azure SQL connectivity in layers: **DNS → network reachability → SQL endpoint/firewall or Private Endpoint → authentication/authorization → connection-string/application configuration**. The first thing I want to establish is whether the application can reach the SQL endpoint over the network at all or whether the failure happens after reaching SQL.

### **Troubleshooting flow**

```text
Application cannot connect
          ↓
DNS resolves correctly?
          ↓
TCP connectivity?
          ↓
Public firewall OR Private Endpoint
          ↓
Authentication works?
          ↓
Database permissions?
          ↓
Connection string / app pool / TLS
```

---

### **1. Capture the exact error**

Examples matter.

```text
Connection timeout
→ network/DNS/firewall likely

Login failed
→ authentication/authorization likely

Server not found
→ DNS/hostname/network likely

TLS/certificate error
→ client/TLS configuration
```

Do not treat every database connection failure as a firewall issue.

---

### **2. Verify the server name**

For Azure SQL Database:

```text
<server>.database.windows.net
```

I verify the application isn't using:

```text
old server
wrong environment
wrong database
hard-coded IP
```

Azure SQL should normally be addressed through its FQDN, not a manually hardcoded IP.

---

### **3. Check DNS**

From the application host:

```bash
nslookup <server>.database.windows.net
```

If using a **Private Endpoint**, I expect the DNS chain to resolve through:

```text
<server>.privatelink.database.windows.net
```

and ultimately return the **private IP** of the SQL Private Endpoint.

Microsoft's current Azure SQL troubleshooting guidance specifically recommends validating the Private Endpoint state and confirming private DNS resolution first when troubleshooting private connectivity. ([Microsoft Learn][6])

If:

```text
AKS → resolves public SQL IP
```

while I expect:

```text
AKS → private endpoint IP
```

I investigate:

```text
privatelink.database.windows.net zone
VNet link
custom DNS forwarding
Azure DNS Private Resolver
```

---

### **4. Test TCP connectivity**

From the application host:

```bash
nc -vz <server>.database.windows.net 1433
```

This separates:

```text
TCP cannot connect
→ networking path

TCP connects
→ investigate SQL authentication/application
```

For Private Endpoint:

```text
AKS/VM
  ↓
Private DNS
  ↓
Private Endpoint
  ↓
Azure SQL
```

I also inspect:

```text
NSG
UDR
Azure Firewall/NVA
Private Endpoint status
```

---

### **5. Determine public vs private access**

#### Public endpoint design

Check:

```text
SQL public network access
SQL firewall configuration
expected source/egress IP
```

For example, an application behind NAT Gateway will reach public SQL using the NAT Gateway's public egress IP.

#### Private Endpoint design

Check:

```text
Private Endpoint = Approved?
Correct VNet?
Correct subnet?
Private DNS resolving correctly?
Public access intentionally disabled?
```

Private Endpoint DNS problems are one of the most common causes of:

```text
works from laptop
fails from AKS
```

or the reverse.

---

### **6. Check authentication**

Once networking works, I check how the application authenticates.

Possible methods:

```text
Microsoft Entra identity
Managed Identity / Workload Identity
SQL username/password
```

Preferred where supported:

```text
Application
    ↓
Managed/Workload Identity
    ↓
Microsoft Entra ID
    ↓
Azure SQL
```

instead of embedding SQL credentials.

For Entra authentication I verify:

```text
identity is correct
token audience correct
Entra admin/configuration
database user exists
permissions granted
```

For SQL authentication:

```text
username correct
password current
secret hasn't rotated
account isn't misconfigured
```

---

### **7. Authentication vs authorization**

A login can authenticate successfully and still lack permission.

```text
Authentication
→ Who are you?

Authorization
→ Can you SELECT/INSERT/etc.?
```

So I check the database user and required roles/permissions.

For example:

```text
Connection established
+
SELECT denied
```

is not a network problem.

---

### **8. Check application configuration**

Finally:

```text
Connection string correct?
Database name correct?
Encryption/TLS settings correct?
Connection timeout sensible?
Connection pool exhausted?
Secret stale?
```

If this started right after a deployment:

```text
Deployment
     ↓
new ConfigMap/secret?
new connection string?
new identity?
new network policy?
```

I correlate the failure timestamp with the change.

---

### **Real diagnostic example**

```text
App → SQL timeout
       ↓
nslookup SQL
       ↓
resolves public IP
       ↓
expected Private Endpoint
       ↓
Private DNS zone not linked to AKS VNet
       ↓
link zone
       ↓
resolves 10.20.4.7
       ↓
connection succeeds
```

That is a much stronger troubleshooting answer than simply:

> “Check the SQL firewall.”

> **In an interview, I would say:**
> “I first capture the exact SQL error and separate connectivity from authentication. From the application's own runtime environment I resolve the SQL FQDN and test TCP connectivity. If the design uses a Private Endpoint, I verify that it is approved and that `server.database.windows.net` resolves through the `privatelink.database.windows.net` zone to the private IP. If networking works, I move to authentication—Managed Identity/Entra or SQL credentials—and then database permissions and the connection string. I also correlate the failure with recent deployments, secret rotation, firewall, DNS, or network changes.”

**Memory line:**
**SQL connection failure → DNS → TCP → endpoint/firewall → identity → DB permissions → app config.**

**Interview trap:**
Do not immediately modify SQL firewall rules before checking whether the architecture is supposed to use a **Private Endpoint**.

**Keywords:**
Azure SQL, TCP 1433, Private Endpoint, Private DNS, `privatelink.database.windows.net`, Entra authentication, Managed Identity

**Likely follow-ups:**

* How would AKS connect to Azure SQL without a password?
* Why can Private Endpoint DNS cause connection failures?
* How would you distinguish a network error from a login error?
* Why should the application use the SQL FQDN rather than a hardcoded IP?

### **T13-04. A user gets `403 Forbidden` while accessing Blob Storage; what would you check?**

**Answer:**
A Blob Storage `403` means the request reached Storage but access was refused. I would first inspect the **Storage error code** because `403` can represent different problems: authentication failure, insufficient data-plane permission, invalid SAS, storage firewall/network restrictions, or—if using ADLS Gen2—ACL problems. Microsoft currently documents all of these as common Blob `403` causes. ([Microsoft Learn][7])

### **Troubleshooting flow**

```text
Blob returns 403
      ↓
Read Storage error code
      ↓
Which auth method?
      ↓
Entra RBAC / SAS / Shared Key
      ↓
Network/firewall/private endpoint
      ↓
ADLS ACL if applicable
      ↓
Storage diagnostic logs
```

---

### **1. Read the detailed error code**

Do not stop at:

```text
HTTP 403
```

Examples:

```text
AuthorizationPermissionMismatch
→ authenticated but insufficient permission

AuthenticationFailed
→ bad/expired credential or SAS

AuthorizationFailure
→ can include network/firewall restrictions

PublicAccessNotPermitted
→ anonymous public access disabled
```

The detailed error usually narrows the investigation immediately. ([Microsoft Learn][7])

---

### **2. Identify how the user is authenticating**

Could be:

```text
Microsoft Entra ID
SAS
Storage account key
Anonymous access
```

Each has a different troubleshooting path.

---

### **3. If using Microsoft Entra ID, check DATA-PLANE RBAC**

This is a classic Azure interview trap.

A user might have:

```text
Contributor
```

or:

```text
Reader
```

on the Storage Account resource.

That does **not necessarily give them permission to read Blob data**.

For blob contents, roles include:

```text
Storage Blob Data Reader
→ read blobs

Storage Blob Data Contributor
→ read/write/delete blob data

Storage Blob Data Owner
→ broad blob data permissions
```

Microsoft's current Blob 403 guidance specifically identifies insufficient Azure RBAC or incorrect role scope as causes of `AuthorizationPermissionMismatch`. ([Microsoft Learn][7])

So I check:

```text
Principal
   +
Role
   +
Scope
```

For example:

```text
User
  ↓
Storage Blob Data Reader
  ↓
container scope
```

---

### **4. Check RBAC propagation**

If the role was assigned seconds ago:

```text
role assignment exists
```

but the user still receives `403`, I account for propagation/cache delay rather than immediately changing more permissions.

I may also acquire a fresh token/login where appropriate.

---

### **5. If using SAS, validate it**

I check:

```text
Expiry time
Start time
Permissions
Resource/service scope
Signed IP
Protocol
Signature
```

Example:

```text
SAS permissions = r
```

but the user tries:

```text
Upload blob
```

→ `403`.

Or:

```text
SAS expired
```

→ authentication failure.

Microsoft specifically calls out expired SAS tokens, start-time/clock issues, wrong permissions and service mismatch as common 403 causes. ([Microsoft Learn][7])

A useful security habit is not to set an unnecessary SAS start time for immediate usage, avoiding clock-skew problems.

---

### **6. Check Storage networking**

Even perfect RBAC can still fail if the network isn't allowed.

I inspect:

```text
Public network access
Storage firewall
Allowed IPs
Allowed VNets
Private Endpoint
Private DNS
Network Security Perimeter if used
```

Example:

```text
User
 ↓
correct Blob Data Reader role
 ↓
Storage firewall denies user's IP
 ↓
403
```

Microsoft explicitly documents firewall, selected-network restrictions, disabled public access, Private Endpoint configuration, and Network Security Perimeter rules as possible `403` causes. ([Microsoft Learn][7])

---

### **7. Private Endpoint case**

If Storage is private-only:

```text
Client
  ↓
blob.core.windows.net
  ↓
Private DNS
  ↓
privatelink.blob.core.windows.net
  ↓
Private Endpoint
```

I verify DNS resolves to:

```text
private IP
```

from the client's network.

A user sitting on their home internet cannot reach a private-only Blob endpoint simply because they have the right RBAC role.

This illustrates:

```text
Authorization
+
Network reachability
```

are independent controls.

---

### **8. If ADLS Gen2, check ACLs too**

For hierarchical namespace-enabled storage:

```text
Azure RBAC
+
POSIX-style ACLs
```

may matter depending on how access is configured.

I check:

```text
Execute permission on parent directories
Read/write permission on target
Group membership
Sticky-bit behavior if relevant
```

Microsoft has documented ADLS Gen2 `403 Access Denied` scenarios caused by ACL and sticky-bit permissions. ([Microsoft Learn][8])

---

### **9. Check whether Shared Key access is disabled**

If an application uses:

```text
Storage account key
```

but policy/configuration disallows Shared Key authorization, the request will fail.

The fix should usually be:

```text
Microsoft Entra ID
```

rather than simply weakening security to allow old credentials.

---

### **10. Use Storage diagnostic logs**

If the cause is still unclear, Storage resource logs can reveal:

```text
AuthenticationType
Requester
Operation
StatusCode
StatusText
URI
```

Microsoft explicitly recommends resource logs for identifying the authorization context behind Blob 403 errors. ([Microsoft Learn][7])

---

### **Real example**

```text
User receives 403
      ↓
Error = AuthorizationPermissionMismatch
      ↓
User has Contributor
      ↓
but no blob data-plane role
      ↓
Assign Storage Blob Data Reader
at required container scope
      ↓
retry after propagation
      ↓
success
```

This is a very common interview scenario.

> **In an interview, I would say:**
> “I would first inspect the Blob Storage error code because 403 alone is too broad. Then I determine the authentication method. For Entra access I verify the user has an appropriate **data-plane role**, such as Storage Blob Data Reader, at the correct scope—having Contributor on the Storage Account doesn't automatically grant blob-data access. For SAS I check expiry, start time, scope and permissions. I then inspect public network access, firewall rules or Private Endpoint DNS, and for ADLS Gen2 I also check ACLs. If needed, I use Storage diagnostic logs to identify the exact authorization failure.”

**Memory line:**
**Blob 403 = identify error code → auth method → data RBAC/SAS → network → ACL.**

**Interview trap:**
**Contributor on a Storage Account does not automatically mean the user can read blob contents.** Management-plane and data-plane authorization are different.

**Keywords:**
403, Storage Blob Data Reader, data plane, SAS, `AuthorizationPermissionMismatch`, Storage firewall, Private Endpoint, ACL

**Likely follow-ups:**

* Why doesn't Contributor automatically allow blob access?
* What role would you assign for read-only Blob access?
* Can a firewall cause HTTP 403?
* How would you troubleshoot an expired or incorrectly scoped SAS?
