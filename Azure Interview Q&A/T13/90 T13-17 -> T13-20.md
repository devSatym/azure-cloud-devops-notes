### **T13-17. A private endpoint resolves to a public IP address; what is likely wrong?**

**Answer:**
If a Private Endpoint exists but the service FQDN still resolves to a **public IP from a client that should use private connectivity**, the most likely problem is **Private DNS configuration**, not the Private Endpoint itself. I would check the correct `privatelink.*` Private DNS zone, its A record, the VNet link, and any custom DNS forwarding. Microsoft currently lists a missing VNet link as the most common cause. ([Microsoft Learn][1])

### **Expected DNS flow**

For example, Blob Storage:

```text
myapp
  ↓
mystorage.blob.core.windows.net
  ↓ CNAME
mystorage.privatelink.blob.core.windows.net
  ↓
10.20.4.7
```

I expect:

```text
Private Endpoint
→ private RFC1918 address
```

such as:

```text
10.x.x.x
172.16–31.x.x
192.168.x.x
```

from the VNet that should use the Private Endpoint.

---

### **1. Prove the DNS result**

From the affected VM/pod:

```bash
nslookup mystorage.blob.core.windows.net
```

If it returns:

```text
20.x.x.x
```

or another public address:

```text
DNS isn't using the Private DNS path
```

If it returns:

```text
10.20.4.7
```

then DNS is already correct, and I move to networking instead. Microsoft explicitly recommends this as the first split in Private Endpoint troubleshooting. ([Microsoft Learn][1])

---

### **2. Check the correct Private DNS zone**

Examples:

```text
Storage Blob
→ privatelink.blob.core.windows.net

Azure SQL
→ privatelink.database.windows.net

Key Vault
→ privatelink.vaultcore.azure.net
```

I verify:

```text
Correct zone exists?
       ↓
Correct A record exists?
       ↓
A record points to Private Endpoint IP?
```

A missing or stale A record can make the FQDN resolve incorrectly. ([Microsoft Learn][1])

---

### **3. Check the VNet link**

This is often the root cause.

```text
Private DNS Zone
      ↓
VNet Link
      ↓
Application VNet
```

If the querying VNet isn't linked:

```text
Azure Private DNS zone
→ never consulted

Public DNS
→ public service IP returned
```

Useful check:

```bash
az network private-dns link vnet list \
  --zone-name privatelink.blob.core.windows.net \
  --resource-group <dns-rg> \
  --output table
```

Microsoft identifies an unlinked querying VNet as the most common cause of a Private Endpoint FQDN returning the public endpoint. ([Microsoft Learn][1])

---

### **4. Check DNS zone group integration**

For Azure-managed Private Endpoint DNS integration:

```text
Private Endpoint
      ↓
DNS Zone Group
      ↓
Private DNS Zone
      ↓
A record
```

A DNS zone group is preferable to manually managing records because Azure can maintain the Private Endpoint DNS record automatically. ([Microsoft Learn][1])

---

### **5. Check custom DNS**

Suppose the VNet uses:

```text
10.10.0.4
→ corporate DNS
```

instead of Azure-provided DNS.

Then:

```text
VM
 ↓
Custom DNS
 ↓
Public DNS
 ↓
public IP
```

can occur even if:

```text
Private DNS zone ✓
VNet link ✓
A record ✓
```

The custom DNS infrastructure must resolve/forward Azure Private Link namespaces correctly, typically using Azure DNS resolution through an appropriate forwarder or Azure DNS Private Resolver design. Microsoft explicitly lists missing `privatelink.*` conditional forwarding as a common cause. ([Microsoft Learn][1])

---

### **6. Check the Private Endpoint itself**

I also verify:

```text
Connection state = Approved
Provisioning state = Succeeded
Private IP assigned
```

If it is:

```text
Pending
Rejected
Disconnected
```

I fix that first.

However, if:

```text
Private Endpoint = Approved
+
FQDN = public IP
```

that strongly points toward DNS configuration. ([Microsoft Learn][1])

---

### **7. Flush stale DNS caches**

If the DNS configuration was just fixed:

```bash
sudo resolvectl flush-caches
```

or the appropriate OS/application DNS-cache refresh.

A client may otherwise continue using an older public answer until its cached record expires.

---

### **Strong troubleshooting flow**

```text
FQDN resolves public IP
       ↓
Correct privatelink zone?
       ↓
A record exists?
       ↓
VNet linked?
       ↓
Custom DNS forwarding?
       ↓
Private Endpoint Approved?
       ↓
Flush cache and retest
```

> **In an interview, I would say:**
> “If a Private Endpoint FQDN resolves publicly from a VNet that should use private connectivity, I would treat it primarily as a DNS problem. I would verify the correct `privatelink.*` Private DNS zone exists, its A record points to the Private Endpoint IP, and the source VNet is linked to that zone. If custom DNS is used, I would check forwarding toward Azure private DNS. I would also verify the Private Endpoint is Approved. If the FQDN instead already resolves to a private IP, then DNS is fine and I would move to NSGs, routes, firewalls and connectivity.”

**Memory line:**
**Private Endpoint exists + public DNS result = check Private DNS zone, A record, VNet link, and custom DNS.**

**Interview trap:**
Creating a Private Endpoint does **not automatically guarantee every VNet will resolve the service to its private IP**.

**Keywords:**
Private Endpoint, Private DNS, `privatelink.*`, VNet link, DNS zone group, A record, custom DNS

**Likely follow-ups:**

* What if DNS resolves correctly to the private IP but connectivity still fails?
* Why does a Private Endpoint still use the normal service FQDN?
* How would this work across hub-and-spoke VNets?
* What would custom corporate DNS need to do?

### **T13-18. An Azure VM can resolve DNS names but cannot establish HTTPS connections; what would you check?**

**Answer:**
Because DNS resolution already works, I would move immediately to the **TCP/HTTPS path**: test TCP port 443, inspect effective routes and NSGs, verify the VM's outbound method and any Azure Firewall/NVA, then check the guest OS firewall/proxy and finally the TLS handshake itself. Azure Network Watcher Connection Troubleshoot can identify NSG, route, DNS, guest-firewall, and platform connectivity problems. ([Microsoft Learn][2])

### **Troubleshooting flow**

```text
DNS works
   ↓
Can TCP/443 connect?
   ↓
Route / next hop
   ↓
NSG
   ↓
NAT / Firewall / NVA
   ↓
Guest firewall / proxy
   ↓
TLS handshake
```

---

### **1. Prove DNS really succeeds**

For example:

```bash
nslookup www.microsoft.com
```

returns an IP.

So I already know:

```text
Hostname resolution ✓
```

I don't spend the next 20 minutes debugging Azure Private DNS unless other evidence points back there.

---

### **2. Test TCP/443**

```bash
nc -vz www.microsoft.com 443
```

or:

```bash
curl -v https://www.microsoft.com
```

Now:

```text
TCP timeout
→ network path/firewall

TCP connects but TLS fails
→ HTTPS/TLS/proxy/certificate problem
```

This is the most important split.

---

### **3. Check effective route / next hop**

I inspect where the VM sends internet-bound traffic.

```text
0.0.0.0/0
    ↓
Internet?
NAT?
Azure Firewall?
NVA?
```

If:

```text
0.0.0.0/0 → Virtual Appliance
```

then HTTPS depends on that firewall/NVA.

A broken UDR could produce:

```text
DNS works
but
TCP 443 times out
```

because DNS queries and HTTPS traffic can take different paths.

---

### **4. Check NSG outbound rules**

I inspect the **effective security rules**, not only the obvious NSG.

Potential issue:

```text
Outbound
Destination = Internet
Port = 443
Action = Deny
```

or a rule denying the destination network.

Network Watcher Connection Troubleshoot can specifically identify NSG rules denying the connection. ([Microsoft Learn][2])

---

### **5. Check explicit outbound connectivity**

The VM needs an actual egress path, such as:

```text
NAT Gateway
Azure Firewall
Load Balancer outbound configuration
Public IP
```

depending on architecture.

For example:

```text
Private VM
   ↓
NAT Gateway
   ↓
Internet
```

If DNS goes to a reachable internal DNS resolver but the VM has no usable internet egress path, this exact symptom is possible.

---

### **6. Check Azure Firewall / NVA**

If the route is:

```text
VM
 ↓
Azure Firewall
 ↓
Internet
```

I inspect:

```text
Network rules
Application rules
FQDN rules
TLS/proxy policy if relevant
SNAT
Firewall logs
```

Example:

```text
DNS UDP/53
→ allowed

HTTPS TCP/443
→ denied
```

explains the symptom perfectly.

---

### **7. Check guest OS firewall**

If Azure networking looks clean:

```bash
sudo nft list ruleset
```

or:

```bash
sudo ufw status
```

Network Watcher can also identify guest firewall blocking as a connectivity issue. ([Microsoft Learn][2])

---

### **8. Check proxy settings**

Very common in enterprise environments:

```bash
env | grep -i proxy
```

Look for:

```text
HTTPS_PROXY
HTTP_PROXY
NO_PROXY
```

A stale proxy can produce:

```text
DNS resolution works
+
HTTPS fails
```

because applications are attempting to establish HTTPS through an unavailable proxy.

---

### **9. If TCP succeeds, investigate TLS**

Use:

```bash
curl -vk https://example.com
```

or:

```bash
openssl s_client -connect example.com:443 \
  -servername example.com
```

Then investigate:

```text
Expired certificate
Untrusted CA
TLS-version mismatch
Cipher mismatch
Wrong system time
TLS-inspection proxy
SNI issue
```

For example:

```text
TCP 443 = success
TLS handshake = failure
```

means I should stop changing NSGs.

---

### **10. Consider intermittent SNAT exhaustion**

If HTTPS:

```text
works sometimes
fails under heavy outbound load
```

I would also investigate SNAT-port exhaustion/NAT behavior.

But for a total persistent failure, I would first prioritize:

```text
route
NSG
firewall
egress path
```

---

> **In an interview, I would say:**
> “Since DNS resolves successfully, I would immediately test TCP port 443. If TCP fails, I inspect the VM's effective route, NSG outbound rules, explicit outbound path and any Azure Firewall or NVA using Network Watcher Connection Troubleshoot. If TCP succeeds but HTTPS still fails, I move to guest firewall, proxy configuration and the TLS handshake using `curl -v` or `openssl s_client`. That prevents me from wasting time troubleshooting DNS when the failure is actually at TCP or TLS.”

**Memory line:**
**DNS works + HTTPS fails → TCP 443 first, then route/firewall, then TLS.**

**Interview trap:**
Do not equate:

```text
nslookup works
```

with:

```text
internet connectivity works
```

DNS proves name resolution, not TCP/443 connectivity.

**Keywords:**
TCP 443, effective route, NSG, Azure Firewall, NAT Gateway, proxy, TLS, Network Watcher

**Likely follow-ups:**

* What if `nc` to port 443 succeeds but `curl` fails?
* How would an Azure Firewall cause this?
* Can DNS work even if the VM has no general internet access?
* How would you diagnose SNAT exhaustion?

### **T13-19. A storage account works from a developer laptop but not from production; how would you troubleshoot it?**

**Answer:**
I would use the developer laptop as a **known-good control** and compare it against production across three dimensions: **network path, authentication identity, and authorization**. The fact that the laptop works proves the Storage service exists, but it does not prove production is allowed through the Storage firewall, resolves a Private Endpoint correctly, uses the same identity, or has the same Blob data-plane permissions.

### **Troubleshooting flow**

```text
Laptop ✓
Production ✗
     ↓
Exact production error?
     ↓
DNS / endpoint difference
     ↓
Storage firewall / Private Endpoint
     ↓
Production source IP/subnet
     ↓
Authentication identity
     ↓
Blob data-plane RBAC / SAS
```

---

### **1. Capture the production error**

Examples:

```text
Timeout
→ connectivity/DNS

403
→ network policy or authorization

AuthenticationFailed
→ credential/SAS

AuthorizationPermissionMismatch
→ RBAC/data permission
```

I want the Storage-specific error code—not just:

```text
“Storage doesn't work.”
```

---

### **2. Compare DNS**

From the laptop:

```bash
nslookup mystorage.blob.core.windows.net
```

From production:

```bash
nslookup mystorage.blob.core.windows.net
```

Maybe:

```text
Laptop
→ public Storage endpoint

Production
→ should use Private Endpoint
but resolves public IP
```

If public network access is disabled, production then fails even though the developer laptop works through some separately allowed path.

For private-only Storage, Microsoft recommends Private Endpoint connectivity and disabling public network access when appropriate. ([Microsoft Learn][3])

---

### **3. Check Storage firewall configuration**

Storage may be configured:

```text
Public network access = Enabled from selected networks
```

with:

```text
Developer laptop public IP
→ allowed
```

but:

```text
Production NAT/firewall IP
→ not allowed
```

Azure Storage firewall rules allow only explicitly permitted source networks when restricted networking is configured. ([Microsoft Learn][4])

So I determine the **actual source** seen from production:

```text
Production subnet?
NAT Gateway public IP?
Azure Firewall public IP?
Service Endpoint?
Private Endpoint?
```

not what I assume the source should be.

---

### **4. If production should use Private Endpoint**

I check:

```text
Private Endpoint = Approved
Private DNS = private IP
VNet connectivity = working
Public access = expected state
```

Architecture:

```text
Production workload
       ↓
Private DNS
       ↓
10.x.x.x
       ↓
Storage Private Endpoint
```

If it instead resolves:

```text
public Storage IP
```

the production network may be hitting a disabled/restricted public path. ([Microsoft Learn][1])

---

### **5. Compare authentication identities**

Developer laptop might authenticate using:

```text
Developer's Entra account
```

while production uses:

```text
Managed Identity
Service Principal
AKS Workload Identity
```

So:

```text
Laptop works
```

doesn't prove:

```text
Production identity has permission
```

I explicitly identify:

```text
Who is the laptop?

Who is production?
```

---

### **6. Check data-plane RBAC**

For Blob operations:

```text
Storage Blob Data Reader
Storage Blob Data Contributor
```

may be needed depending on required action.

Production might have:

```text
Reader
or
Contributor
```

at management scope but lack the necessary **Blob data-plane permission**.

So I check:

```text
Principal
+
Role
+
Scope
```

not just whether “some Azure role” exists.

---

### **7. If using SAS, compare SAS restrictions**

A SAS can be restricted by:

```text
Permissions
Expiry
Start time
IP
Protocol
Resource scope
```

Example:

```text
Developer laptop
→ SAS works

Production
→ source IP doesn't satisfy SAS IP restriction
```

or production may simply be using an expired secret copied into its deployment.

---

### **8. Check service endpoints**

If the production subnet has a **Storage service endpoint**, traffic behavior differs from normal public internet egress.

Azure Storage documents that traffic from a subnet using a service endpoint is identified through that virtual-network path rather than simply relying on the subnet's public outbound IP allowlist. ([Microsoft Learn][4])

Therefore:

```text
“I allowlisted the NAT public IP”
```

may not be the relevant rule for that architecture.

---

### **9. Check production routing/firewall**

Production may have:

```text
0.0.0.0/0 → Azure Firewall
```

while the laptop doesn't.

I therefore inspect:

```text
UDR
NSG
Azure Firewall
proxy
Private Endpoint route
```

from production.

---

### **10. Compare the two paths explicitly**

| Layer          | Laptop          | Production              |
| -------------- | --------------- | ----------------------- |
| DNS IP         | Public/private? | Public/private?         |
| Source network | Home/office IP  | VNet/NAT/firewall       |
| Endpoint       | Public          | Public/Private          |
| Identity       | Developer       | MI/SP/Workload Identity |
| RBAC           | ?               | ?                       |
| SAS            | ?               | ?                       |
| Result         | Works           | Fails                   |

The **first meaningful difference** usually finds the root cause.

---

### **Example**

```text
Laptop works
      ↓
Developer IP is Storage-firewall allowlisted

Production fails 403
      ↓
Production exits via NAT Gateway
      ↓
NAT public IP not allowlisted
```

or, preferably for production:

```text
Configure Private Endpoint
      +
Private DNS
      +
Managed/Workload Identity
```

instead of expanding public exposure unnecessarily.

> **In an interview, I would say:**
> “I would use the laptop as a known-good comparison and first capture the exact production error. Then I compare DNS and endpoint selection—public versus Private Endpoint—followed by Storage firewall rules and the actual production source subnet or NAT IP. If network connectivity is correct, I compare the developer's Entra identity with the Managed Identity or Workload Identity used in production and check Blob data-plane RBAC. I would also inspect SAS restrictions if applicable. The key is that laptop and production often use completely different network and identity paths even though they access the same Storage Account.”

**Memory line:**
**Laptop works, production fails → compare network path + identity + data authorization.**

**Interview trap:**
Do not solve this by simply setting:

```text
Storage network access = Allow all networks
```

That hides the root cause and weakens production security.

**Keywords:**
Storage firewall, Private Endpoint, Private DNS, service endpoint, NAT Gateway, Managed Identity, Blob data-plane RBAC

**Likely follow-ups:**

* Why can the laptop's public IP work while an Azure VM's public IP doesn't?
* How would you privately connect production to Storage?
* Why might Contributor still get a Blob 403?
* How would a service endpoint change the network path?

### **T13-20. A production deployment caused errors for only 20% of users; what deployment or infrastructure issues would you investigate?**

**Answer:**
The fact that only **about 20%** of users fail is a strong clue that the problem is associated with **one subset of the serving path** rather than the entire application. I would immediately correlate failed requests with **application version, backend instance/pod, region, zone, deployment slot, Front Door origin, and session affinity**. For example, one bad instance out of five or a canary receiving 20% of traffic could produce exactly this pattern.

### **Troubleshooting flow**

```text
Deployment
   ↓
~20% users fail
   ↓
What do failed users share?
   ↓
Version?
Pod/instance?
Slot?
Origin?
Region/zone?
Session?
   ↓
Find bad serving subset
```

---

### **1. First suspect traffic segmentation**

An exact-ish percentage is valuable evidence.

For example:

```text
5 backend instances

4 healthy
1 broken
```

If traffic is roughly evenly distributed:

```text
~20% requests
→ broken instance
```

Likewise:

```text
Canary v2 = 20% traffic
Stable v1 = 80%
```

and:

```text
Only v2 is broken
```

produces approximately the same symptom.

I would not assume that is definitely the cause—but it is where I would look first.

---

### **2. Correlate failed requests by application version**

Every request should ideally expose enough telemetry to correlate:

```text
version
commit SHA
deployment ID
pod
instance
region
```

Example:

```text
v1.8.3
→ 0.2% errors

v1.9.0
→ 48% errors
```

If all failed users hit:

```text
v1.9.0
```

the new deployment is the leading suspect.

---

### **3. Check canary / weighted traffic**

Azure Front Door supports weighted origins specifically for gradual deployments, where only a configured proportion of traffic reaches a new origin. ([Microsoft Learn][5])

Similarly, App Service deployment slots can route a percentage of production traffic to another slot. ([Microsoft Learn][6])

So I inspect whether:

```text
20% traffic
→ new origin/slot/version
```

was intentionally configured.

Example:

```text
Front Door
│
├── v1 origin → weight 80
└── v2 origin → weight 20
```

If:

```text
all v2 requests fail
```

the percentage immediately makes sense.

---

### **4. Check individual instances/pods**

For AKS:

```bash
kubectl get pods -n <namespace> -o wide
```

Suppose there are five replicas:

```text
pod-1 → v2 healthy
pod-2 → v2 healthy
pod-3 → v2 healthy
pod-4 → v2 healthy
pod-5 → v2 broken config
```

Intermittent failures can occur depending on which pod receives the request.

I correlate:

```text
failed request
→ pod name
→ node
→ image digest
→ configuration
```

---

### **5. Verify that all replicas actually run the same artifact**

A deployment can leave:

```text
80% new version
20% old version
```

or the reverse if rollout fails midway.

Check:

```bash
kubectl get pods \
  -o custom-columns=NAME:.metadata.name,IMAGE:.spec.containers[0].image
```

I prefer immutable image digests so:

```text
same deployment reference
```

actually means:

```text
same artifact
```

and not a mutable `latest` tag.

---

### **6. Check rolling-update configuration**

A deployment may cause partial errors if old pods disappear before new pods are genuinely ready.

For AKS/Kubernetes I inspect:

```text
readinessProbe
maxUnavailable
maxSurge
minReadySeconds
terminationGracePeriodSeconds
preStop
```

Microsoft's current AKS reliability guidance recommends controlling `maxUnavailable` so enough application replicas remain available during rolling updates. ([Microsoft Learn][7])

Example:

```text
5 replicas

maxUnavailable = 1
```

means up to:

```text
20% of replicas
```

can be unavailable during rollout.

That percentage could be highly relevant depending on capacity and probe behavior.

---

### **7. Check readiness probes**

A particularly dangerous scenario:

```text
new pod starts
     ↓
readiness says Ready too early
     ↓
Service sends user traffic
     ↓
application dependency not ready
     ↓
errors
```

Then only the users routed to newly created/bad pods fail.

The readiness probe should validate **serving readiness**, not simply:

```text
process exists
```

---

### **8. Check deployment-slot configuration**

With App Service:

```text
Production slot
+
Staging slot
```

I compare:

```text
connection strings
Key Vault references
slot settings
Managed Identity permissions
VNet integration
Private Endpoint/DNS
```

A staging/canary slot could have:

```text
wrong DB
missing Key Vault permission
wrong API endpoint
```

while production remains fine.

If 20% of users are deliberately routed to that slot, only they fail. App Service supports percentage-based traffic routing for precisely these gradual-release scenarios. ([Microsoft Learn][6])

---

### **9. Check region / zone / origin**

Maybe:

```text
Region A = 80%
Region B = 20%
```

and only Region B has:

```text
bad configuration
DB connectivity failure
expired certificate
unhealthy dependency
```

Similarly with Azure Front Door weighted origins. ([Microsoft Learn][5])

I group failed requests by:

```text
Region
Origin
Backend pool
Availability Zone
```

---

### **10. Check session affinity**

If sticky/session-affinity routing is enabled:

```text
User A
→ always healthy origin

User B
→ always broken origin
```

then some users may report:

> “It always fails for me.”

while others never see the issue.

Azure Front Door can use session affinity to keep subsequent requests from one user on the selected origin. ([Microsoft Learn][5])

---

### **11. Check configuration drift**

One replica/region may differ in:

```text
environment variables
ConfigMap
Secret
certificate
feature flag
database migration level
Managed Identity
RBAC
network configuration
```

Example:

```text
4 instances
→ DB_PASSWORD version 8

1 instance
→ stale version 7
```

Only traffic reaching that instance fails.

---

### **12. Check database migration compatibility**

A rollout may temporarily have:

```text
old app version
+
new app version
```

both serving traffic.

If the deployment included a breaking schema migration:

```text
new DB schema
    ↓
new app works
old app breaks
```

then only the users reaching the older replicas fail.

This is why production DB migrations should normally be **backward compatible during rolling deployment**.

---

### **13. Stabilize quickly**

If I identify:

```text
20% canary
→ causing errors
```

I would usually:

```text
shift canary traffic to 0%
```

or roll back that deployment first.

For Front Door/App Service:

```text
20% new
→ 0% new
→ users restored
```

Then investigate safely.

The point of canary deployment is specifically to make failure blast radius small.

---

### **Practical diagnostic table**

| Failed request field | What I'm looking for         |
| -------------------- | ---------------------------- |
| Version              | new vs old build             |
| Pod/instance         | one bad backend              |
| Region               | regional issue               |
| Zone                 | zone-specific problem        |
| Origin               | Front Door routing           |
| Slot                 | canary/staging configuration |
| User/session         | affinity/sticky routing      |
| Dependency           | only one backend path broken |

---

> **In an interview, I would say:**
> “The 20% failure rate is a clue that one subset of the deployment or routing path may be unhealthy. I would immediately group failed requests by application version, pod or instance, deployment slot, Front Door origin, region and zone. One bad instance out of five, or a canary configured for 20% traffic, could explain the pattern. For AKS I would inspect rolling-update state, readiness probes, image digests, `maxUnavailable` and configuration differences between pods. I would also check whether a database migration breaks only the old or new version during mixed-version rollout. If the failing 20% is the canary, I would route traffic back to the known-good version first and then troubleshoot.”

**Memory line:**
**Partial failure after deployment → find what the failing users share.**

**Interview trap:**
Do not treat a 20% error rate as a random statistic. It may directly correspond to **one of five instances, a 20% canary, one region, or one deployment slot**.

**Keywords:**
Canary deployment, weighted traffic, readiness probe, rolling update, `maxUnavailable`, session affinity, configuration drift, backward-compatible migration

**Likely follow-ups:**

* How would you prove one pod is responsible?
* How could a database migration break only part of the traffic?
* What would you do if the canary causes errors?
* Why should deployment telemetry include version and instance information?
