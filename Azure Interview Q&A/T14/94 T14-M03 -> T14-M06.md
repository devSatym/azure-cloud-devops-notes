### **T14-M03. What is ACR authentication?**

**Answer:**
ACR authentication is the process of **proving the identity of a user, CI/CD pipeline, Azure service, or Kubernetes cluster before it can access Azure Container Registry**. For production, I prefer **Microsoft Entra-based authentication** using users, managed identities, workload identities, or service principals rather than shared registry passwords. Azure RBAC then determines what that authenticated identity is allowed to do. ([Microsoft Learn][1])

### **Authentication vs authorization**

This distinction is important:

```text
Authentication
→ Who are you?

Authorization
→ What can you do in ACR?
```

Example:

```text
AKS kubelet identity
      ↓
Authenticates using Entra ID
      ↓
ACR evaluates RBAC
      ↓
Allowed to pull image?
```

So an identity can:

```text
authenticate successfully
```

but still get:

```text
unauthorized / denied
```

because it lacks the required ACR permission.

---

### **Common ACR authentication methods**

#### **1. Interactive user authentication**

For a developer:

```bash
az login
az acr login --name myacr
```

Flow:

```text
Developer
   ↓
Microsoft Entra ID
   ↓
Azure CLI obtains token
   ↓
ACR
```

Good for:

```text
development
administration
manual troubleshooting
```

but not ideal for unattended pipelines.

Microsoft lists individual Entra login as one of ACR's main authentication methods. ([Microsoft Learn][1])

---

### **2. Managed Identity**

For Azure workloads, this is usually one of the strongest approaches:

```text
AKS / VM / Container App
        ↓
Managed Identity
        ↓
Microsoft Entra ID
        ↓
ACR
```

No registry password needs to be stored.

For AKS specifically:

```text
AKS kubelet managed identity
        ↓
ACR permission
        ↓
pull image
```

---

### **3. Service principal**

For unattended automation that cannot use managed identity or federation:

```text
Automation
   ↓
Service Principal
   ↓
Microsoft Entra
   ↓
ACR
```

The service principal can receive narrowly scoped pull/push permissions. Microsoft specifically documents service principals for unattended or “headless” ACR authentication. ([Microsoft Learn][1])

For CI/CD today, however, I would prefer:

```text
OIDC / workload identity federation
```

over storing a long-lived client secret whenever the CI platform supports it.

---

### **4. Admin account**

ACR can also provide an admin username/password.

Conceptually:

```text
ACR admin username
+
password
```

But I would avoid this for normal production workloads because:

```text
shared credential
broad access
credential rotation burden
poor identity attribution
```

It can be useful for limited troubleshooting or integrations that cannot use Entra authentication, but it should not be the default production model.

---

### **RBAC after authentication**

Once authenticated, access depends on registry permission configuration.

Conceptually:

```text
CI identity
→ push permission

AKS kubelet
→ pull permission

Developer
→ perhaps read-only
```

Traditional ACR RBAC commonly uses roles such as:

```text
AcrPull
AcrPush
```

while ACR's newer repository-permission/ABAC mode provides repository-oriented roles. Microsoft currently supports assigning ACR permissions to users, managed identities, and service principals through Microsoft Entra-based role assignments. ([Microsoft Learn][2])

---

### **Production example**

```text
GitHub Actions
      ↓
OIDC
      ↓
Microsoft Entra ID
      ↓
CI deployment identity
      ↓
Push permission
      ↓
ACR
      ↓
AKS kubelet identity
      ↓
Pull permission
      ↓
AKS
```

Notice there is no:

```text
shared ACR password
```

between CI, ACR, and AKS.

> **In an interview, I would say:**
> “ACR authentication verifies the identity accessing the registry, while authorization determines what that identity can do. I prefer Microsoft Entra-based authentication—for example a developer identity interactively, a managed identity for Azure workloads, or federated/service identities for automation. AKS normally uses its kubelet managed identity to authenticate when pulling images. After authentication, Azure RBAC or ACR repository permissions control whether that identity can pull, push, or manage artifacts. I avoid the ACR admin account for normal production use because it's a shared credential.”

**Memory line:**
**ACR authentication proves identity; ACR RBAC decides pull/push permissions.**

**Interview trap:**
Do not confuse:

```text
successful login
```

with:

```text
permission to push/pull
```

Authentication and authorization are separate.

**Keywords:**
ACR authentication, Microsoft Entra ID, Managed Identity, service principal, OIDC, Azure RBAC, `AcrPull`, `AcrPush`

**Likely follow-ups:**

* How does AKS authenticate to ACR?
* Why avoid the ACR admin account?
* Authentication vs authorization?
* Managed Identity vs service principal for ACR?

### **T14-M04. Why should production deployments use immutable image identifiers?**

**Answer:**
Production deployments should use immutable image identifiers so that **the artifact I tested, scanned, approved, and deployed cannot silently change underneath the same reference**. The strongest identifier is an **image digest**, such as `sha256:...`, because it identifies one exact manifest. Unique non-reused build tags are also much safer than reusable tags. Microsoft recommends unique tags for deployments and notes that pulling by digest guarantees the exact image version. ([Microsoft Learn][3])

### **Problem with mutable references**

Suppose production uses:

```text
api:production
```

Today:

```text
api:production
      ↓
sha256:AAA
```

Later someone pushes:

```text
api:production
      ↓
sha256:BBB
```

Now the deployment configuration still says:

```text
api:production
```

but the artifact has changed.

That's dangerous because:

```text
Deployment YAML unchanged
≠
running artifact guaranteed unchanged
```

---

### **Immutable deployment**

Better:

```text
api@sha256:AAA
```

Then:

```text
Deploy
   ↓
sha256:AAA
```

will always refer to that exact manifest.

Microsoft explicitly notes that pulling by digest guarantees the image version even if an identically named tag is pushed later. ([Microsoft Learn][4])

---

### **1. Reproducibility**

With an immutable reference:

```text
Dev      → sha256:AAA
Staging  → sha256:AAA
Prod     → sha256:AAA
```

I can prove:

```text
same artifact
```

was promoted through environments.

That is much stronger than:

```text
Dev      → api:latest
Prod     → api:latest
```

because those two pulls might happen at different times and retrieve different images.

---

### **2. Supply-chain security**

A strong pipeline can do:

```text
Build image
    ↓
Digest = sha256:AAA
    ↓
Vulnerability scan AAA
    ↓
Generate SBOM for AAA
    ↓
Sign / attest AAA
    ↓
Deploy AAA
```

Then:

```text
Scanned
=
Signed
=
Approved
=
Deployed
```

This is one of the key reasons immutable artifact identity matters in DevSecOps.

---

### **3. Reliable rollback**

Suppose:

```text
v42 digest = AAA
v43 digest = BBB
```

Deployment of BBB fails.

Rollback:

```text
BBB
 ↓
AAA
```

is deterministic.

With a mutable tag such as:

```text
production
```

I may no longer know exactly which image represented the previous release.

---

### **4. Consistent scaling**

Imagine five AKS replicas:

```text
Pod 1 → image pulled yesterday
Pod 2 → image pulled yesterday
Pod 3 → image pulled yesterday
```

Then the tag changes.

Autoscaling adds:

```text
Pod 4 → pulls new image
Pod 5 → pulls new image
```

Now:

```text
same Deployment
```

could potentially contain different application builds depending on tag/pull behavior.

Microsoft recommends unique tags specifically to avoid inconsistent versions when deployments scale across multiple nodes. ([Microsoft Learn][3])

---

### **5. Auditability**

During an incident I want to answer:

> Which exact artifact was running?

With:

```text
sha256:4ba91...
```

I can map directly to:

```text
Build
SBOM
scan
signature
commit
deployment
```

That makes incident investigation and compliance much easier.

---

### **Unique tag vs digest**

A unique CI tag is good:

```text
api:build-842
```

or:

```text
api:git-a82f4c1
```

provided the organization never reuses it.

But the strongest identity is:

```text
api@sha256:...
```

because the digest comes from the artifact content itself.

### **Important distinction**

An immutable **reference** does not necessarily mean the registry can never delete the artifact.

For additional protection ACR can also lock deployed repository content against accidental overwrite/deletion. Microsoft recommends locking deployed image tags where appropriate. ([Microsoft Learn][3])

> **In an interview, I would say:**
> “Production should use immutable image identifiers so the artifact that passed testing, vulnerability scanning, signing and approval is exactly the artifact that gets deployed. I prefer a manifest digest for the strongest guarantee, or at minimum a unique build tag that is never reused. This gives reproducible deployments, prevents tag drift during scaling or restarts, enables deterministic rollback, and makes it possible to correlate the deployed artifact with its SBOM, scan result, signature and build provenance.”

**Memory line:**
**Immutable artifact identity guarantees that approved image X remains image X.**

**Interview trap:**
A semantic-looking tag such as:

```text
:v1.2.3
```

is not automatically immutable—it can still be overwritten unless policies prevent it.

**Keywords:**
Immutable image, digest, unique tag, reproducibility, rollback, provenance, SBOM, supply chain

**Likely follow-ups:**

* Unique tag vs digest?
* Does deploying by digest prevent image deletion?
* How does immutability improve container security?
* How would you map a deployed digest back to a Git commit?

### **T14-M05. Why is deploying `latest` considered risky?**

**Answer:**
Deploying `latest` is risky because **`latest` is just a mutable tag**. It can point to one image today and a different image tomorrow without the Kubernetes manifest changing. That makes deployments non-deterministic, complicates rollbacks and auditing, and can cause different replicas to run different builds after restarts or scaling. Microsoft recommends unique tags for deployments and specifically warns against using reusable stable tags for deployed workloads. ([Microsoft Learn][3])

### **The misconception**

```text
latest
```

does **not** mean:

```text
"Azure automatically selects
the newest safe production image"
```

It's simply a normal tag name.

If no Docker tag is specified, Docker conventionally uses `latest`. ([Microsoft Learn][4])

---

### **Example**

Monday:

```text
api:latest
   ↓
sha256:AAA
```

Production deploys:

```text
Pod 1 → AAA
Pod 2 → AAA
Pod 3 → AAA
```

Tuesday someone pushes:

```text
api:latest
   ↓
sha256:BBB
```

The manifest still says:

```yaml
image: myacr.azurecr.io/api:latest
```

but now the registry reference represents different content.

---

### **Problem 1: inconsistent replicas**

Suppose one pod restarts:

```text
Pod 1 → AAA
Pod 2 → AAA
Pod 3 restarted → BBB
```

Now:

```text
same Kubernetes Deployment
```

may be serving multiple application builds.

That creates extremely confusing bugs:

```text
Request 1 → works
Request 2 → fails
Request 3 → works
```

depending on which replica handles the request.

---

### **Problem 2: rollback becomes unclear**

Suppose `latest` breaks production.

You want:

```text
rollback
```

but:

> What was `latest` before the bad push?

Unless you separately recorded the old digest, the deployment manifest itself doesn't tell you.

With immutable releases:

```text
build-100 → AAA
build-101 → BBB
```

rollback is simply:

```text
BBB → AAA
```

---

### **Problem 3: poor auditability**

Security asks:

> Which image was running at 14:00 yesterday?

Manifest:

```text
api:latest
```

doesn't provide a deterministic answer because the tag could have moved.

Digest:

```text
api@sha256:AAA
```

does.

---

### **Problem 4: scan/deploy mismatch**

Bad pipeline:

```text
Scan api:latest
      ↓
latest = AAA
      ↓
someone overwrites latest
      ↓
latest = BBB
      ↓
Deploy latest
```

Now:

```text
Scanned AAA
but
Deployed BBB
```

With a digest:

```text
Scan AAA
Sign AAA
Deploy AAA
```

the chain remains consistent.

---

### **Better options**

Use:

```text
api:build-842
```

or:

```text
api:a82f4c1
```

and preferably promote/deploy the resolved digest:

```text
api@sha256:abc123...
```

Microsoft's ACR guidance recommends unique tags for deployments so deliberate versions are used consistently across nodes. ([Microsoft Learn][3])

---

> **In an interview, I would say:**
> “`latest` is risky because it's a mutable tag rather than a version guarantee. Someone can push a different image under `latest` without changing the deployment manifest. During a restart or scale-out, new replicas could then pull a different build from existing replicas, and rollback or audit becomes difficult because the manifest doesn't tell me which image `latest` represented at a previous point in time. In production I use unique build identifiers and preferably deploy the exact image digest.”

**Memory line:**
**`latest` tells you a label, not exactly what code you're running.**

**Interview trap:**
Do not say:

```text
latest = newest image in registry
```

It is only a conventional tag and can point wherever it was last assigned.

**Keywords:**
`latest`, mutable tag, tag drift, immutable digest, rollback, reproducibility

**Likely follow-ups:**

* Does Kubernetes automatically update running pods when `latest` changes?
* Why can replicas end up running different images?
* What should you use instead of `latest`?
* Git SHA tag vs digest—which is stronger?

### **T14-M06. What is ACR geo-replication?**

**Answer:**
ACR geo-replication is a **Premium-tier feature that creates registry replicas in multiple Azure regions**. Images and artifacts are automatically replicated between those regions so globally distributed workloads can pull from a nearby registry replica and the registry data plane can continue operating if one region becomes unavailable. ACR geo-replication currently uses an **active-active** model with asynchronous, eventually consistent replication. ([Microsoft Learn][5])

### **Architecture**

```text
                 ACR
          myacr.azurecr.io
                  |
        ---------------------
        |         |         |
        v         v         v
     East US   West Europe  Central India
      Replica     Replica      Replica
        |            |            |
       AKS          AKS          AKS
```

You manage:

```text
one logical registry
```

rather than operating three unrelated registries.

---

### **1. Why use it?**

Two major reasons:

```text
Performance
+
Regional resiliency
```

#### Performance

Without geo-replication:

```text
AKS India
   ↓
pull image
   ↓
ACR in US
```

Large image pulls may cross continents.

With geo-replication:

```text
AKS India
   ↓
nearby ACR replica
```

which can reduce image-pull latency for geographically distributed deployments. ([Microsoft Learn][5])

---

### **2. Regional outage protection**

Suppose:

```text
East US replica
    ↓
region outage
```

Healthy replicas remain available:

```text
West Europe ✓
Central India ✓
```

ACR's global endpoint routing can stop directing data-plane requests to the unavailable replica and use healthy replicas instead. Microsoft's current reliability documentation says ACR uses Azure Traffic Manager to route data-plane requests and automatically fail over between geo-replicas. ([Microsoft Learn][5])

---

### **3. Active-active behavior**

This is an important interview point.

ACR geo-replication is not simply:

```text
Primary → read-only backup
```

Current ACR geo-replication is:

```text
Replica A → active
Replica B → active
Replica C → active
```

Microsoft states that geo-replicas can handle data-plane operations including:

```text
push
pull
delete
```

and changes propagate to the other replicas. ([Microsoft Learn][5])

---

### **4. Replication is asynchronous**

Suppose:

```text
Push image v42
→ India replica
```

Then:

```text
India
  ↓
async replication
  ↓
Europe
  ↓
US
```

So immediately after a write there can be a brief period in which every replica hasn't received the change yet.

Microsoft describes ACR geo-replication as:

```text
asynchronous
+
eventually consistent
```

and says replication typically completes within minutes, without a guaranteed fixed replication time. ([Microsoft Learn][5])

### **Important consequence**

Do not assume:

```text
push completed in Region A
=
artifact instantly exists everywhere
```

---

### **5. One global endpoint**

Normally clients can continue using:

```text
myacr.azurecr.io
```

and ACR routes them toward an appropriate healthy regional replica.

Conceptually:

```text
AKS Europe
     ↓
myacr.azurecr.io
     ↓
Europe replica
```

while:

```text
AKS India
     ↓
myacr.azurecr.io
     ↓
nearby replica
```

ACR now also supports explicit regional endpoints in Premium registries, but the normal global endpoint remains an important geo-replication model. ([Microsoft Learn][6])

---

### **6. Premium requirement**

Geo-replication requires:

```text
ACR Premium
```

Basic and Standard registries don't provide this feature. ([Microsoft Learn][5])

---

### **7. Important control-plane limitation**

This is a strong hardening/detail point.

The registry's **control plane is associated with the home region**.

If the home region is unavailable:

```text
push/pull via healthy replicas
→ can continue

registry configuration changes
→ may be unavailable
```

Microsoft explicitly calls out this distinction. ([Microsoft Learn][5])

So geo-replication improves data-plane regional resilience, but I shouldn't claim every ACR operation remains unaffected during home-region loss.

---

### **8. Cost tradeoff**

Each replica adds:

```text
Premium registry cost
+
cross-region data transfer/replication cost
```

so I wouldn't replicate into ten regions automatically.

I choose regions based on:

```text
AKS deployment regions
DR requirements
pull latency
data residency
cost
```

---

### **Production example**

```text
GitHub Actions
      ↓
push image digest
      ↓
myacr.azurecr.io
      ↓
ACR geo-replication
   /       |        \
India    Europe      US
  |        |          |
AKS      AKS        AKS
```

Benefits:

```text
nearby image pulls
+
one logical registry
+
regional data-plane resilience
```

> **In an interview, I would say:**
> “ACR geo-replication is a Premium feature that replicates one logical registry into multiple Azure regions. This gives globally distributed AKS clusters network-close image access and helps the registry data plane survive a regional outage. The replicas use an active-active model, and registry content is asynchronously replicated with eventual consistency. Clients can normally continue using the same global registry endpoint, which is routed to an appropriate healthy replica. I would also mention that the control plane remains tied to the home region, so configuration operations can still be affected by a home-region outage.”

**Memory line:**
**ACR geo-replication = one Premium registry, multiple active regional replicas.**

**Interview trap:**
Do not say geo-replication is:

```text
synchronous
```

or:

```text
primary + read-only standby
```

It is currently **active-active with asynchronous eventual replication**. ([Microsoft Learn][5])

**Keywords:**
ACR Premium, geo-replication, active-active, asynchronous replication, eventual consistency, regional resilience

**Likely follow-ups:**

* Does ACR geo-replication require Premium?
* Is replication synchronous?
* What happens if the home region fails?
* Geo-replication vs zone redundancy?
