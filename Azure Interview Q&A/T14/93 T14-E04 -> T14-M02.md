### **T14-E04. What is an image digest?**

**Answer:**
An image digest is a **content-derived, immutable SHA-256 identifier for a container image manifest**. Unlike a tag such as `v1` or `latest`, which can be moved to another image, the digest identifies one exact image manifest. ([Microsoft Learn][1])

### **Tag vs digest**

```text
Tag
api:v1
   ↓
can later point somewhere else

Digest
api@sha256:abc123...
   ↓
one exact image
```

For example:

```text
myacr.azurecr.io/api:v1
```

might currently resolve to:

```text
sha256:7ca0e0ae...
```

If someone later pushes another image using the same `v1` tag:

```text
api:v1
→ new digest
```

But:

```text
api@sha256:7ca0e0ae...
```

still identifies the original artifact.

Microsoft describes each ACR image/artifact manifest as having a unique SHA-256 digest and specifically notes that pulling by digest guarantees the exact image version even if the tag is reused later. ([Microsoft Learn][1])

### **Kubernetes example**

Instead of:

```yaml
image: myacr.azurecr.io/payment-api:production
```

I can deploy:

```yaml
image: myacr.azurecr.io/payment-api@sha256:abc123...
```

Now Kubernetes requests exactly that image.

This improves:

```text
Reproducibility
Supply-chain security
Rollback confidence
Deployment traceability
```

### **Why this matters in DevSecOps**

A secure pipeline can do:

```text
Build image
    ↓
Push to ACR
    ↓
Get digest
    ↓
Scan digest
    ↓
Sign digest
    ↓
Deploy same digest
```

Then I know:

```text
Scanned artifact
=
Signed artifact
=
Deployed artifact
```

instead of trusting a mutable tag.

> **In an interview, I would say:**
> “An image digest is the immutable SHA-256 identifier of an image manifest. A tag is a human-readable mutable reference, while a digest points to one exact artifact. For production and supply-chain security, deploying by digest is stronger because the image I scanned and approved is guaranteed to be the image Kubernetes pulls.”

**Memory line:**
**Tag tells me a name; digest tells me the exact content.**

**Interview trap:**
Do not call tags immutable. Even `v1.0.0` can technically be repointed unless additional controls prevent it.

**Keywords:**
Digest, SHA-256, manifest, immutable image, content addressability

**Likely follow-ups:**

* Tag vs digest?
* Why deploy by digest?
* Can multiple tags point to one digest?
* How does image signing use digests?

### **T14-E05. How does AKS pull images from ACR?**

**Answer:**
AKS normally pulls private images from ACR using the **AKS kubelet managed identity**. That identity is granted permission to pull from the registry, traditionally through the `AcrPull` Azure RBAC role. The kubelet authenticates to ACR and downloads the image required by the pod. ([Microsoft Learn][2])

### **Flow**

```text
Pod scheduled
     ↓
Kubelet sees image reference
     ↓
AKS kubelet managed identity
     ↓
Microsoft Entra ID
     ↓
ACR authorization
     ↓
Pull image
     ↓
Start container
```

Example manifest:

```yaml
containers:
- name: api
  image: myacr.azurecr.io/api:v2
```

AKS needs permission to access:

```text
myacr.azurecr.io
```

---

### **Common integration**

CLI:

```bash
az aks update \
  --resource-group rg-platform \
  --name aks-prod \
  --attach-acr myacr
```

For traditional ACR RBAC mode, this integration grants the AKS **kubelet identity** `AcrPull` permission on the registry. ([Microsoft Learn][2])

Terraform conceptually:

```hcl
resource "azurerm_role_assignment" "acr_pull" {
  scope                = azurerm_container_registry.acr.id
  role_definition_name = "AcrPull"
  principal_id         = azurerm_kubernetes_cluster.aks.kubelet_identity[0].object_id
}
```

---

### **Important: kubelet identity vs workload identity**

Do not confuse these.

```text
Kubelet identity
→ AKS node/kubelet pulls container image

Workload Identity
→ application inside pod accesses Azure services
```

Example:

```text
Kubelet Identity
   ↓
ACR
   ↓
pull api image

Pod ServiceAccount
   ↓
Workload Identity
   ↓
Key Vault
```

They solve different problems.

---

### **Current ACR ABAC nuance**

There is an important newer distinction.

For an ACR configured with:

```text
RBAC Registry + ABAC Repository Permissions
```

Microsoft says `az aks --attach-acr` isn't supported for that permission mode. Instead, the AKS kubelet identity should be manually granted:

```text
Container Registry Repository Reader
```

rather than the traditional `AcrPull` role. ([Microsoft Learn][2])

So the interview-safe answer is:

```text
Traditional registry permissions
→ kubelet identity + AcrPull

ABAC repository-permission mode
→ kubelet identity + Container Registry Repository Reader
```

---

### **What if authentication is wrong?**

Pods commonly show:

```text
ImagePullBackOff
ErrImagePull
```

Then I check:

```bash
kubectl describe pod <pod>
```

and investigate:

```text
Wrong registry/image name
Kubelet identity permission
ACR networking
Private DNS
Image/tag doesn't exist
```

> **In an interview, I would say:**
> “AKS normally pulls private ACR images using the kubelet managed identity. That identity receives image-pull permission on the registry, commonly `AcrPull`, and the kubelet authenticates to ACR when starting the pod. I distinguish that from AKS Workload Identity, which is used by the application inside the pod to access Azure resources. For newer ACR ABAC repository-permission mode, I would use the appropriate repository-reader role rather than `attach-acr`.”

**Memory line:**
**Kubelet identity pulls the image; Workload Identity serves the application.**

**Interview trap:**
Do not say the pod's Workload Identity normally pulls its own image. The image must be pulled **before the container starts**.

**Keywords:**
AKS kubelet identity, ACR, `AcrPull`, `attach-acr`, Managed Identity, `ImagePullBackOff`

**Likely follow-ups:**

* Kubelet identity vs Workload Identity?
* What causes `ImagePullBackOff`?
* How would AKS access a private ACR?
* What changes with ACR ABAC repository permissions?

### **T14-M01. What are ACR SKUs?**

**Answer:**
Azure Container Registry currently has **three pricing tiers: Basic, Standard, and Premium**. They expose broadly the same core registry APIs, but differ in **included storage, throughput, concurrency, scaling limits, and advanced features**. Premium adds major enterprise capabilities such as **Private Link/private endpoints and geo-replication**. ([Microsoft Learn][3])

### **Quick comparison**

| SKU          | Best fit                          | Key point                                    |
| ------------ | --------------------------------- | -------------------------------------------- |
| **Basic**    | Dev/test, low usage               | Lowest-cost entry tier                       |
| **Standard** | Many normal production workloads  | Higher storage/throughput                    |
| **Premium**  | Large/secure/enterprise workloads | Private Link, geo-replication, highest scale |

Microsoft's current limits show included storage of approximately:

```text
Basic     → 10 GiB
Standard  → 100 GiB
Premium   → 500 GiB
```

with higher overall storage and concurrency limits in Premium. ([Microsoft Learn][3])

---

### **Basic**

Use when:

```text
Learning
Development
Small CI workloads
Low image pull/push volume
```

It still supports capabilities such as:

```text
Microsoft Entra authentication
image management
webhooks
repository permissions
```

but has lower throughput and limits. ([Microsoft Learn][3])

---

### **Standard**

Standard provides:

```text
same core registry functionality
+
more storage
+
higher image throughput
```

Microsoft states Standard is suitable for **many production scenarios**. ([Microsoft Learn][3])

---

### **Premium**

Premium is where many enterprise features appear:

```text
Private Link / Private Endpoint
Geo-replication
Higher concurrency
Higher bandwidth/throughput
More webhooks and scale limits
```

([Microsoft Learn][3])

For example, if I need:

```text
AKS private cluster
      ↓
Private ACR
      ↓
no registry public exposure
```

I need **Premium** for ACR Private Link. ([Microsoft Learn][4])

---

### **Important distinction**

I would not say:

```text
Basic = non-production
Standard = production
Premium = production
```

as an absolute rule.

The choice should depend on:

```text
Image volume
Pull/push rate
Concurrent deployments
Private networking
Geo-replication
Required limits
Cost
```

For example:

```text
Small production service
→ Standard may be enough

Private AKS platform
→ Premium required for Private Link
```

---

> **In an interview, I would say:**
> “ACR has Basic, Standard and Premium tiers. Basic targets lower-volume development scenarios, Standard increases storage and throughput and works for many production workloads, while Premium provides the highest scale and advanced capabilities such as Private Link/private endpoints and geo-replication. I choose the SKU based on throughput, storage, concurrency and networking or HA requirements rather than simply choosing Premium for every production registry.”

**Memory line:**
**Basic = low scale, Standard = normal production scale, Premium = advanced networking + geo + highest scale.**

**Interview trap:**
Do not say Private Endpoint is available on every ACR SKU—it currently requires **Premium**. ([Microsoft Learn][4])

**Keywords:**
Basic, Standard, Premium, Private Link, geo-replication, throughput, concurrency

**Likely follow-ups:**

* Which SKU supports Private Endpoint?
* Which SKU supports geo-replication?
* Would you always use Premium in production?
* Can you change ACR SKU later?

### **T14-M02. How can ACR be made private?**

**Answer:**
The strongest standard approach is to use **ACR Premium + Azure Private Link**, create a **Private Endpoint** in the required VNet, configure Private DNS so `myregistry.azurecr.io` resolves to private addresses from that network, and then **disable public network access** to the registry. Traffic then stays on Azure's private network path rather than reaching the registry through its public endpoint. ([Microsoft Learn][4])

### **Architecture**

```text
AKS
 │
 │ private network
 ↓
Private DNS
 │
 ↓
ACR Private Endpoint
10.x.x.x
 │
 ↓
Azure Private Link
 │
 ↓
ACR
```

No desired path:

```text
AKS
 ↓
Public Internet
 ↓
ACR public endpoint
```

---

### **1. Use Premium SKU**

Private Link/private endpoints are currently available on:

```text
ACR Premium
```

not Basic or Standard. ([Microsoft Learn][4])

---

### **2. Create the Private Endpoint**

Conceptually:

```text
ACR
  ↓
Private Endpoint
  ↓
Private IP in VNet
```

For example:

```text
10.20.4.10
```

The endpoint lets clients inside the VNet communicate privately with the registry. ([Microsoft Learn][4])

---

### **3. Configure DNS**

This is critical.

Applications continue using the normal registry name:

```text
myregistry.azurecr.io
```

but DNS inside the permitted network must ultimately resolve ACR's private-link endpoints to the allocated **private IP addresses**. Microsoft explicitly calls out Private Endpoint DNS configuration as a requirement for private registry connectivity. ([Microsoft Learn][4])

Conceptually:

```text
myregistry.azurecr.io
       ↓
Private Link DNS resolution
       ↓
10.x.x.x
```

For ACR, be careful to configure all registry/data endpoint DNS records created or required by the Private Endpoint integration rather than manually guessing a single record.

---

### **4. Disable public network access**

Once Private Endpoint connectivity works:

```bash
az acr update \
  --name myregistry \
  --public-network-enabled false
```

Now the public registry endpoint cannot be used by arbitrary external networks. ([Microsoft Learn][5])

This produces:

```text
Allowed:
AKS/VNet → Private Endpoint → ACR

Blocked:
Laptop over internet → ACR public endpoint
```

unless the laptop connects through:

```text
VPN
ExpressRoute
other private connectivity
```

Microsoft notes that Private Link can also make ACR reachable privately from on-premises through VPN or ExpressRoute connectivity. ([Microsoft Learn][4])

---

### **5. Identity is still required**

Private networking does not replace authentication.

```text
Private Endpoint
→ Where can traffic come from?

Azure RBAC/Entra
→ Who can pull/push?
```

For AKS:

```text
AKS kubelet identity
      ↓
AcrPull / appropriate repository permission
      ↓
Private Endpoint
      ↓
ACR
```

So I need both:

```text
Network authorization
+
Identity authorization
```

---

### **6. CI/CD needs network line of sight**

This is a practical production consideration.

If:

```text
ACR public access = disabled
```

then a CI runner on the public internet cannot simply push images to it.

I may need:

```text
Self-hosted GitHub runner
inside VNet
```

or another runner/network design with access to the Private Endpoint.

Microsoft specifically warns that network-restricted/private ACR configurations require compatible network access from build/automation services. ([Microsoft Learn][4])

---

### **Private Endpoint vs service endpoint**

ACR also has service-endpoint-based VNet access in supported scenarios, but Microsoft currently recommends **Private Endpoint/Private Link in most networking scenarios**. ([Microsoft Learn][6])

The distinction is:

```text
Service Endpoint
→ still uses service public endpoint
  but restricts it to selected VNets

Private Endpoint
→ service represented by private IP in your VNet
```

For a strong private AKS architecture, I would normally choose:

```text
Private Endpoint
```

---

> **In an interview, I would say:**
> “To make ACR private, I would use the Premium SKU and create an Azure Private Endpoint for the registry in a VNet reachable by AKS. I would configure Private DNS so the registry FQDN resolves to the Private Endpoint addresses from that network, validate image pulls, and then disable ACR public network access. AKS would still authenticate using its kubelet managed identity and ACR RBAC. I would also make sure CI/CD runners have private network connectivity because disabling public access can otherwise prevent them from pushing images.”

**Memory line:**
**Private ACR = Premium + Private Endpoint + Private DNS + public access disabled + identity authorization.**

**Interview trap:**
A Private Endpoint alone does **not** automatically make ACR private if the public endpoint remains enabled.

**Keywords:**
ACR Premium, Private Link, Private Endpoint, Private DNS, public network access, AKS kubelet identity
