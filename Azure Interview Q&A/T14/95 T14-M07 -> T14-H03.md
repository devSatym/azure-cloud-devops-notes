### **T14-M07. What are ACR Tasks?**

**Answer:**
ACR Tasks are an Azure Container Registry feature for **building, testing, running, and pushing container images inside Azure without needing a local Docker build environment or a separate build server**. Tasks can run manually or automatically in response to **source-code commits, base-image updates, or schedules**. ([Microsoft Learn][1])

### **Simple idea**

Instead of:

```text
Developer/CI runner
      ↓
Docker build locally
      ↓
Push image
      ↓
ACR
```

I can use:

```text
Source code
    ↓
ACR Task
    ↓
Build inside Azure
    ↓
Push image
    ↓
ACR
```

---

### **1. Quick Tasks / on-demand builds**

For a simple cloud build:

```bash
az acr build \
  --registry myacr \
  --image api:v1 \
  .
```

Conceptually:

```text
Dockerfile + source
        ↓
ACR cloud build
        ↓
api:v1
        ↓
ACR
```

This is useful when:

```text
local Docker unavailable
CI runner should stay lightweight
build should happen close to registry
```

Microsoft describes ACR Tasks as allowing native Azure container builds without requiring a local Docker installation. ([Microsoft Learn][2])

---

### **2. Stored ACR Tasks**

I can create a persistent task:

```text
Task definition
     ↓
Dockerfile / YAML
     ↓
Trigger
     ↓
Build/test/push
```

For example:

```bash
az acr task create \
  --registry myacr \
  --name build-api \
  --image api:{{.Run.ID}} \
  --context https://github.com/org/repo.git \
  --file Dockerfile
```

The task can then run automatically.

---

### **3. Source-code trigger**

Example:

```text
Developer pushes commit
        ↓
Git trigger
        ↓
ACR Task
        ↓
Build image
        ↓
Push into ACR
```

So ACR Tasks can provide a lightweight container-focused CI capability.

---

### **4. Base-image update trigger**

This is one of the more interesting features.

Suppose:

```dockerfile
FROM node:24
```

and the base image gets updated with security fixes.

ACR Tasks can trigger a rebuild:

```text
node:24 updated
      ↓
Base-image trigger
      ↓
Rebuild API
      ↓
New application image
```

Microsoft specifically documents source-commit and base-image update triggers for ACR Tasks. ([Microsoft Learn][1])

This is useful for:

```text
OS patching
runtime patching
base-image CVE remediation
```

---

### **5. Scheduled tasks**

Tasks can also run using cron-like schedules.

For example:

```text
Every night
   ↓
Rebuild base images
   ↓
Run maintenance/security task
```

ACR Tasks supports timer triggers that can be combined with source and base-image triggers. ([Microsoft Learn][3])

---

### **6. Multi-step tasks**

For more complicated workflows, ACR Tasks supports YAML-based multi-step tasks.

For example:

```text
Build
  ↓
Unit test
  ↓
Security test
  ↓
Push image
```

Supported step types include:

```text
build
push
cmd
```

and steps can depend on earlier steps. ([Microsoft Learn][4])

Example:

```text
                ┌→ Test container
Build image ────┤
                └→ Scan/check
                      ↓
                    Push
```

---

### **ACR Tasks vs GitHub Actions**

They overlap, but they are not identical.

```text
ACR Tasks
→ container-focused Azure build automation

GitHub Actions
→ general CI/CD orchestration
```

GitHub Actions can handle:

```text
tests
Terraform
security scanning
approvals
deployment
GitOps changes
```

while ACR Tasks is especially convenient for:

```text
container build
base-image rebuild
registry-centric automation
```

They can also be combined.

> **In an interview, I would say:**
> “ACR Tasks is Azure Container Registry's built-in container build and automation capability. It can build and push images in Azure without a local Docker daemon, and tasks can run manually or be triggered by Git commits, base-image updates, or schedules. For more complex workflows, ACR Tasks supports YAML multi-step tasks with build, push and container-command steps. I see it as container-focused build automation rather than a full replacement for general CI/CD systems like GitHub Actions.”

**Memory line:**
**ACR Tasks = build and automate container-image lifecycle operations close to ACR.**

**Interview trap:**
Do not describe ACR Tasks as a Kubernetes deployment controller. Its main focus is **container build/test/patch automation**, not managing AKS application state.

**Keywords:**
ACR Tasks, cloud build, source trigger, base-image trigger, timer trigger, multi-step task

**Likely follow-ups:**

* ACR Tasks vs GitHub Actions?
* How can ACR Tasks help patch vulnerable base images?
* Can ACR Tasks run on a schedule?
* What are multi-step tasks?

### **T14-H01. How would you secure the flow from source code to ACR to AKS?**

**Answer:**
I would secure the pipeline as a **software supply-chain trust chain**. Only reviewed source should reach the trusted build workflow; the workflow should authenticate to Azure using OIDC rather than stored secrets; the produced container should be scanned, assigned an immutable digest, have an SBOM/provenance generated and be signed; ACR should be private and least-privileged; and AKS admission should verify that only approved, trusted images can run.

### **Architecture**

```text
Developer
   ↓
Protected Git repository
   ↓
PR security gates
   ↓
Trusted main branch
   ↓
GitHub Actions
   │
   └── OIDC → Microsoft Entra ID
                  ↓
             ACR push identity
                  ↓
         Build immutable image
                  ↓
          Vulnerability scan
                  ↓
             Generate SBOM
                  ↓
       Sign + provenance/attestation
                  ↓
            Private ACR
                  ↓
             Image digest
                  ↓
        AKS admission control
                  ↓
         Verify trust policy
                  ↓
                 AKS
```

---

### **1. Protect the source**

My first trust boundary is Git.

I would require:

```text
Pull requests
Code review
Protected main branch
Required CI checks
No direct production pushes
Secret scanning
Dependency/security scanning
```

because:

```text
Untrusted source
      ↓
trusted pipeline
```

still produces an untrusted application.

I would also pin critical CI actions and dependencies where practical.

---

### **2. Separate PR workflows from trusted release workflows**

A pull request from an untrusted contributor should not automatically receive:

```text
Azure credentials
ACR push permission
production deployment permission
signing authority
```

A safer model:

```text
PR
 ↓
Build locally/in runner
Test
SAST
Dependency scan
Image scan
No Azure write token
```

Then after merge:

```text
Protected main
      ↓
Trusted release workflow
      ↓
Azure OIDC
      ↓
Build / push / sign / deploy
```

This keeps production authority out of untrusted PR execution.

---

### **3. Use GitHub OIDC instead of client secrets**

Authentication:

```text
GitHub Actions
      ↓
GitHub OIDC token
      ↓
Entra federated credential
      ↓
short-lived Azure token
```

not:

```text
AZURE_CLIENT_SECRET
stored for months
```

The CI identity receives only the permissions it actually needs.

For example:

```text
CI identity
→ push to application repository in ACR

not

CI identity
→ Owner on subscription
```

---

### **4. Build once and create immutable identity**

Build:

```text
Git SHA abc123
      ↓
Container image
      ↓
Digest sha256:XYZ
```

I would use:

```text
api:abc123
```

for human traceability but promote/deploy:

```text
api@sha256:XYZ
```

for exact artifact identity.

This lets me prove:

```text
source commit
   ↕
build
   ↕
digest
   ↕
deployment
```

---

### **5. Scan before promotion**

Before production:

```text
Source scan
Dependency scan
Dockerfile/IaC scan
Container image vulnerability scan
```

For example:

```text
Build image
    ↓
Trivy / equivalent CI scanner
    ↓
Critical vulnerability?
   / \
 Yes  No
 ↓     ↓
Fail   continue
```

I wouldn't wait until after deployment to discover known critical CVEs.

---

### **6. Generate an SBOM**

I would produce an SBOM such as SPDX:

```text
Image sha256:XYZ
      ↓
SBOM
      ↓
Packages + versions + dependencies
```

This provides evidence of:

> What exactly is inside this artifact?

and becomes valuable when a new vulnerability is announced later.

---

### **7. Produce provenance**

Provenance answers:

```text
Who built it?
From which repository?
From which commit?
Using which workflow?
```

Conceptually:

```text
Source
+
Builder identity
+
Workflow
+
Commit
+
Artifact digest
      ↓
Provenance
```

That lets admission/security policy verify more than merely:

```text
image exists in ACR
```

---

### **8. Sign the exact digest**

Current Azure guidance is moving away from legacy Docker Content Trust. Microsoft recommends **Notary Project** for modern ACR image signing and verification; Docker Content Trust is being retired and can no longer be newly enabled after May 31, 2026. ([Microsoft Learn][5])

Conceptually:

```text
Image digest
sha256:XYZ
      ↓
Sign using trusted identity/key
      ↓
Signature stored as OCI artifact
```

Now a consumer can prove:

```text
integrity
+
publisher identity
```

---

### **9. Secure ACR**

For production I would configure:

```text
Private Endpoint
Private DNS
Public access disabled where practical
Admin account disabled
Entra authentication
Least-privilege repository permissions
Defender vulnerability assessment
Retention/lifecycle policies
Diagnostic logs
```

Traffic:

```text
Trusted CI runner
      ↓ private network
Private ACR
      ↓
AKS
```

---

### **10. Separate push and pull identities**

CI:

```text
GitHub CI identity
→ push
```

AKS:

```text
Kubelet managed identity
→ pull only
```

The AKS identity should not need:

```text
push
delete
registry administration
```

This reduces blast radius if the cluster identity is compromised.

---

### **11. Enforce admission in AKS**

The most important security control is:

```text
CI says image is safe
```

is not enough.

AKS itself should enforce trust.

At minimum:

```text
Only images from approved registries
```

Azure Policy currently includes:

**Kubernetes cluster containers should only use allowed images**

which can audit or deny non-approved image sources. ([Microsoft Learn][6])

Stronger:

```text
Approved ACR
+
immutable digest
+
signature verification
```

Microsoft documents using **Ratify + Azure Policy** to validate Notary Project image signatures at admission. With `Deny`, unsigned or untrusted images are rejected. ([Microsoft Learn][7])

Conceptually:

```text
kubectl/Argo CD
      ↓
Admission
      ↓
Registry approved?
Digest pinned?
Signature valid?
Signer trusted?
      ↓
YES → admit
NO  → reject
```

---

### **12. Deploy through GitOps where appropriate**

A strong pattern is:

```text
CI
→ builds and signs image
→ updates Git with trusted digest

Argo CD
→ sees Git change
→ deploys to AKS
```

This separates:

```text
Build authority
```

from:

```text
cluster reconciliation
```

and leaves a strong Git audit trail.

---

### **13. Runtime protection still matters**

Supply-chain controls protect what enters the cluster.

They do not eliminate:

```text
runtime exploit
credential theft
container escape attempt
malicious process execution
```

So I complement them with:

```text
Defender for Containers
runtime detection
least-privilege pods
NetworkPolicy
read-only root filesystem
seccomp/capability restrictions
```

Defender for Containers currently covers posture, image vulnerability assessment, supply-chain protection, and runtime threat detection. ([Microsoft Learn][8])

---

### **Full trust chain**

```text
Reviewed source
      ↓
Trusted workflow
      ↓
OIDC identity
      ↓
Build
      ↓
Scan
      ↓
SBOM
      ↓
Provenance
      ↓
Sign digest
      ↓
Private ACR
      ↓
Admission verification
      ↓
AKS
      ↓
Runtime detection
```

> **In an interview, I would say:**
> “I would secure source-to-ACR-to-AKS as a complete trust chain. Source goes through protected branches and PR security gates. The trusted release workflow authenticates to Azure using OIDC and gets only repository-level push permission. I build once, identify the artifact by digest, scan it, generate an SBOM and provenance, and sign that digest. ACR is protected with private networking, Entra authentication and least privilege. AKS uses a separate kubelet pull identity, and admission policy allows only approved registries and verifies signatures before deployment. Finally, Defender and Kubernetes runtime controls protect the workload after admission.”

**Memory line:**
**Secure pipeline = trusted source → trusted build → trusted artifact → trusted registry → enforced admission → protected runtime.**

**Interview trap:**
Do not stop at “we scan the image.” Scanning finds known vulnerabilities; it does **not prove who built the image or prevent somebody from deploying another unsigned artifact**.

**Keywords:**
OIDC, immutable digest, SBOM, provenance, Notary Project, Ratify, Azure Policy, Private ACR, admission control

**Likely follow-ups:**

* Why sign an image after scanning it?
* How would AKS reject an unsigned image?
* Why should CI and AKS use different identities?
* Why isn't vulnerability scanning alone enough?

### **T14-H02. How would you ensure that only trusted container images can run in AKS?**

**Answer:**
I would enforce trust **at Kubernetes admission time**, not rely only on developer discipline or CI. My production policy would require images to come from an approved registry, use immutable references, and—where stronger supply-chain assurance is required—carry a valid signature from a trusted signer. An image that fails policy should never create a pod.

### **Trust policy**

```text
New Pod request
      ↓
Admission control
      ↓
Approved registry?
      ↓
Immutable digest?
      ↓
Valid signature?
      ↓
Trusted signer?
      ↓
Security policy satisfied?
      ↓
ALLOW / DENY
```

---

### **1. Restrict image registries**

First, prevent workloads from using arbitrary public registries:

```text
Allowed:
mycompany.azurecr.io/*

Denied:
docker.io/random/*
attacker.example/*
```

Azure currently has a built-in policy:

**Kubernetes cluster containers should only use allowed images**

which can operate with `Audit` or `Deny`. ([Microsoft Learn][6])

That prevents:

```yaml
image: attacker.example/malware:latest
```

from bypassing the corporate registry.

---

### **2. Require immutable references**

Instead of:

```yaml
image: myacr.azurecr.io/api:production
```

I want:

```yaml
image: myacr.azurecr.io/api@sha256:abc...
```

because the digest identifies one exact artifact.

Otherwise:

```text
Allowed registry ✓
Trusted repository ✓
Mutable tag ✗
```

still permits the artifact behind the tag to change later.

---

### **3. Sign images**

After:

```text
Build
Scan
Test
SBOM
```

the trusted pipeline signs the exact digest.

Modern Azure guidance recommends **Notary Project** rather than legacy Docker Content Trust. DCT is being retired on March 31, 2028, and new enablement stopped after May 31, 2026. ([Microsoft Learn][5])

Example:

```text
api@sha256:AAA
      ↓
signed by
Production CI signer
```

Now I can cryptographically establish:

```text
image integrity
+
trusted publisher
```

---

### **4. Verify signature at AKS admission**

Microsoft documents:

```text
Notation / Notary Project
        ↓
signature in ACR
        ↓
Ratify
        ↓
Azure Policy / Gatekeeper
        ↓
AKS admission
```

With a `Deny` policy:

```text
Signed by trusted identity
→ admitted

Unsigned
→ denied

Signed by unknown identity
→ denied
```

([Microsoft Learn][7])

This is much stronger than merely checking:

```text
image starts with myacr.azurecr.io
```

because even a compromised registry repository cannot automatically introduce an artifact signed by a trusted signing identity.

---

### **5. Define trusted signer identities**

Policy shouldn't say:

```text
any signature = trusted
```

It should trust specific publishers.

For example:

```text
Trusted:
production CI signing identity

Denied:
developer laptop signer
unknown certificate
another repository's signer
```

Trust may be based on:

```text
certificate identity
Trusted Signing identity
Key Vault-backed signing certificate
```

depending on implementation.

---

### **6. Enforce policy on every container field**

I make sure enforcement covers:

```text
containers
initContainers
ephemeralContainers where relevant
```

Otherwise an attacker may bypass:

```text
main container trusted
+
untrusted initContainer
```

and execute code before the main application starts.

---

### **7. Keep AKS pull permission read-only**

AKS kubelet identity:

```text
ACR pull permission only
```

not:

```text
push
delete
sign
```

That separates:

```text
consumer identity
```

from:

```text
publisher identity
```

If AKS is compromised, it should not automatically gain the ability to publish a “trusted” production artifact.

---

### **8. Restrict ACR itself**

I also secure the registry:

```text
Private Endpoint
Public access disabled where required
Admin account disabled
Least-privilege repository RBAC
Diagnostic logging
```

because trusted-image enforcement is stronger when the artifact store itself has a small attack surface.

---

### **9. Vulnerability policy is another trust dimension**

Cryptographically trusted does not necessarily mean secure.

An image may be:

```text
correctly signed
+
contains critical CVE
```

So I combine:

```text
Signature trust
+
Vulnerability policy
```

Defender for Containers now supports software supply-chain protection capabilities that associate vulnerability findings with container images and can support gated Kubernetes deployment based on vulnerability policy. ([Microsoft Learn][8])

---

### **Production policy**

```text
Image must:
✓ come from approved ACR
✓ use immutable digest
✓ pass vulnerability gate
✓ have valid signature
✓ be signed by approved publisher
✓ satisfy admission policy

Otherwise:
✗ deployment denied
```

> **In an interview, I would say:**
> “I would enforce trusted images at AKS admission. First, Azure Policy or another admission policy restricts images to approved ACR repositories. I require immutable digests so tags can't silently change. The trusted CI pipeline signs the approved image digest using Notary Project or another supported signing system, and AKS verifies that signature at admission—for example with Ratify and Azure Policy. Unsigned images or images signed by an untrusted identity are denied. I also keep the AKS kubelet identity pull-only and combine signature trust with vulnerability gates, because a correctly signed image can still contain a critical CVE.”

**Memory line:**
**Trusted image = approved source + exact digest + trusted signature + enforced admission.**

**Interview trap:**
An image being stored in your ACR does **not automatically make it trusted**.

**Keywords:**
Admission control, Azure Policy, Ratify, Notary Project, signature verification, immutable digest, allowed registry

**Likely follow-ups:**

* Registry allowlist vs signature verification?
* Why isn't an approved ACR enough?
* What happens to an unsigned image?
* Can a signed image still be vulnerable?

### **T14-H03. How would you scan images for vulnerabilities before deployment?**

**Answer:**
I would make vulnerability scanning a **mandatory CI gate before an image can be promoted to production**. I build the exact image once, scan that exact digest for OS and application-package vulnerabilities, fail the pipeline according to an agreed severity policy, remediate and rebuild when necessary, and only after the image passes do I sign and deploy that same digest. I would use Microsoft Defender for Containers as an additional continuous Azure-native vulnerability assessment layer rather than relying on only one scanner.

### **Pipeline**

```text
Source
  ↓
Build image
  ↓
Resolve digest
  ↓
Scan image
  ↓
Critical/High violation?
  / \
Yes  No
 ↓    ↓
Fail  Generate SBOM
       ↓
      Sign
       ↓
      Push/promote
       ↓
      Deploy
```

---

### **1. Scan the exact built image**

The important rule is:

```text
Build once
Scan once
Deploy same digest
```

Bad:

```text
Build A
 ↓
scan A
 ↓
rebuild
 ↓
deploy B
```

because:

```text
Scanned image
≠
deployed image
```

Better:

```text
Build → sha256:ABC
Scan  → sha256:ABC
Sign  → sha256:ABC
Deploy→ sha256:ABC
```

---

### **2. Scan OS and application dependencies**

The scanner should inspect more than the base OS.

For example:

```text
Ubuntu packages
npm dependencies
Python packages
Java libraries
Go modules where supported
```

An image can have:

```text
clean OS packages
+
vulnerable application dependency
```

so both layers matter.

---

### **3. Define a real gating policy**

I wouldn't blindly say:

```text
Any CVE
→ fail pipeline
```

because real production images can contain findings with no available fix.

A better policy might consider:

```text
Severity
Exploitability
Fix availability
Internet exposure
Runtime relevance
Accepted exception
```

Example:

```text
Critical + fix available
→ block

High exploitable vulnerability
→ block

Medium
→ ticket/remediation SLA

Approved temporary exception
→ time-limited and documented
```

The exact policy is an organizational risk decision.

---

### **4. Example CI scanner**

A commonly used DevSecOps pattern is:

```bash
trivy image \
  --severity HIGH,CRITICAL \
  --exit-code 1 \
  myacr.azurecr.io/api@sha256:<digest>
```

Meaning:

```text
matching vulnerabilities
      ↓
non-zero exit code
      ↓
CI fails
```

The important interview concept is the **gate**, not a particular vendor.

Alternatives include:

```text
Microsoft Defender
Trivy
Snyk
Aqua
Prisma
other enterprise scanners
```

---

### **5. Use Defender for Containers continuously**

Microsoft Defender for Containers currently performs agentless vulnerability assessment across ACR images, with coverage for OS and language packages, remediation guidance, daily rescanning, and exploitability context. ([Microsoft Learn][8])

Its ACR findings can be reviewed in Defender for Cloud as container-image vulnerability recommendations. ([Microsoft Learn][9])

This gives me a second layer:

```text
CI scan
→ stop bad image before deployment

Defender scan
→ continuously reassess stored/running images
```

because:

```text
Image safe on Monday
```

can become:

```text
Known vulnerable on Friday
```

when a new CVE is published.

---

### **6. Defender now also supports deployment gating**

Current Defender for Containers documentation includes **software supply-chain protection** where vulnerability findings associated with images can be used for gated Kubernetes deployment policies. ([Microsoft Learn][8])

Conceptually:

```text
Image
 ↓
Defender vulnerability findings
 ↓
Policy threshold
 ↓
Admission
 ├── compliant → allow
 └── violates policy → block/audit
```

That strengthens the architecture beyond CI alone.

---

### **7. Remediate correctly**

If a vulnerability is found:

```text
Vulnerability
    ↓
Find fixed package/base image
    ↓
Update Dockerfile/dependency
    ↓
Rebuild
    ↓
New digest
    ↓
Rescan
```

I do not patch the running container manually.

For example:

```dockerfile
FROM node:24.3
```

becomes a patched current base or pinned digest as appropriate.

Then CI builds a **new immutable image**.

Microsoft recommends rebuilding affected images with updated base images/packages and rescanning the new image. ([Microsoft Learn][10])

---

### **8. Keep base images minimal**

I would also reduce the number of packages present:

```text
Large general-purpose image
→ many packages
→ larger CVE surface

Minimal/distroless runtime
→ fewer packages
→ smaller attack surface
```

Using multi-stage builds:

```text
Builder image
  ↓
compile
  ↓
copy only runtime artifacts
  ↓
minimal runtime image
```

reduces unnecessary vulnerabilities.

---

### **9. Generate an SBOM**

After the image is built:

```text
sha256:ABC
    ↓
SBOM
```

The SBOM allows me to answer later:

> Which deployed images contain package X?

This matters because new vulnerabilities appear **after deployment**.

---

### **10. Sign only the approved artifact**

A good ordering is:

```text
Build
 ↓
Scan
 ↓
Policy PASS
 ↓
SBOM / provenance
 ↓
Sign
 ↓
Deploy
```

not:

```text
Build
 ↓
Sign
 ↓
Discover critical CVE
```

Signing should represent:

```text
this artifact passed our release trust process
```

where possible.

---

### **11. Block image mutation**

Once:

```text
sha256:ABC
```

has passed:

```text
scan
SBOM
signature
approval
```

production references that digest.

No rebuild should replace it.

A new fix means:

```text
new image
→ new digest
→ new scan
→ new approval
```

---

### **12. Monitor running images too**

The final security loop:

```text
Build-time scan
      ↓
Registry scan
      ↓
Admission gate
      ↓
Runtime inventory
      ↓
New CVE discovered
      ↓
Identify affected workload
      ↓
Rebuild and redeploy
```

Defender for Containers currently provides vulnerability assessment for both registry images and running containers in supported environments. ([Microsoft Learn][8])

---

> **In an interview, I would say:**
> “I would build the image once and scan the exact digest in CI before promotion. The scanner checks OS and language dependencies, and the pipeline fails based on an agreed vulnerability policy—for example blocking exploitable critical vulnerabilities with available fixes. If it fails, I update the base image or dependency, rebuild to a new digest and scan again. Only a passing digest gets an SBOM, provenance, signature and production deployment. I would additionally enable Defender for Containers so ACR and running images are continuously reassessed as new CVEs appear, because a clean image today may become vulnerable later.”

**Memory line:**
**Build once → scan exact digest → pass policy → sign → deploy same digest → keep rescanning.**

**Interview trap:**
Do not scan:

```text
api:latest
```

and later deploy whatever `latest` happens to point to. Scan and deploy the **same immutable artifact**.

**Keywords:**
Image scanning, CVE, CI gate, Defender for Containers, Trivy, immutable digest, SBOM, continuous reassessment
