### **T13-25. What would you examine before restarting a production service during an incident?**

**Answer:**
Before restarting a production service, I would first **capture evidence and determine what state will be destroyed by the restart**. A restart can restore service temporarily, but it can also erase the best clues to the root cause—process state, memory pressure, open connections, thread stacks, temporary files, and current logs.

My order would be:

```text
Impact / severity
      ↓
Current symptoms
      ↓
Logs + metrics + traces
      ↓
Process/container state
      ↓
Dependencies
      ↓
Recent changes
      ↓
Capture diagnostics
      ↓
Then restart if justified
```

### **1. Determine whether restarting is actually appropriate**

I first ask:

```text
Is the service completely down?
Is it degraded?
Is only one instance affected?
Are healthy replicas still serving users?
```

For example, with five application instances:

```text
Instance 1  Healthy
Instance 2  Healthy
Instance 3  Hung
Instance 4  Healthy
Instance 5  Healthy
```

I can isolate/restart:

```text
Instance 3
```

without restarting the entire service.

In AKS:

```bash
kubectl get pods -n <namespace> -o wide
```

If only one pod is unhealthy, I don't immediately restart the entire Deployment.

---

### **2. Capture the exact failure symptoms**

Before changing state, I record:

```text
HTTP errors
latency
affected users
affected instance/pod
timestamp
request IDs
dependency failures
```

Example:

```text
14:21
pod-api-4 starts returning 503

14:23
DB connection errors begin

14:24
readiness fails
```

That incident timeline may be extremely useful later.

---

### **3. Capture logs before they disappear**

For a Linux service:

```bash
journalctl -u <service> --since "30 minutes ago"
```

For Kubernetes:

```bash
kubectl logs <pod> -n <ns>
```

If a container has already restarted:

```bash
kubectl logs <pod> -n <ns> --previous
```

I would preserve important logs externally if they might disappear after recreation.

---

### **4. Check metrics**

I inspect the period immediately before failure:

```text
CPU
Memory
Disk
Network
Request rate
P95/P99 latency
Error rate
Queue depth
Connection count
```

Example:

```text
Memory
40% → 60% → 80% → 99%
```

followed by:

```text
service becomes unresponsive
```

strongly suggests a memory leak or pressure issue.

If I simply restart first:

```text
memory resets
service works
```

but I've hidden the symptom.

---

### **5. Check process/container state**

For Linux:

```bash
ps aux
top
free -m
df -h
ss -s
```

I look for:

```text
high CPU
OOM
disk full
too many connections
zombie processes
file-descriptor exhaustion
```

For AKS:

```bash
kubectl describe pod <pod> -n <ns>
```

Check:

```text
OOMKilled
Restart Count
probe failures
Events
termination reason
```

---

### **6. Preserve deeper diagnostics when useful**

For a hung or crashing process, I may need:

```text
thread dump
heap dump
core dump
process dump
```

depending on the runtime.

Examples:

```text
Java
→ thread dump / heap dump

.NET
→ process dump

Linux process
→ core dump / strace where appropriate
```

A restart may remove the opportunity to collect that evidence.

---

### **7. Check dependencies**

The service might only be a victim.

Example:

```text
Application
    ↓
Database unavailable
    ↓
connection pool exhausted
    ↓
application hangs
```

Restarting the application:

```text
temporarily clears pool
```

but:

```text
DB is still unavailable
```

so the service fails again.

I check:

```text
Database
Redis
Key Vault
Storage
Service Bus
external APIs
DNS
```

before assuming the application itself is broken.

---

### **8. Check recent changes**

I correlate the incident with:

```text
deployment
configuration change
secret rotation
certificate update
RBAC change
firewall/NSG change
database migration
```

Example:

```text
14:00 deployment
14:03 errors begin
```

In that case:

```text
rollback
```

might be a better remediation than:

```text
restart
```

---

### **9. Understand restart blast radius**

Before restarting I ask:

```text
Will active requests be dropped?
Will queue jobs be duplicated?
Will sessions be lost?
Will leader election occur?
Will storage need recovery?
Will all replicas restart together?
```

For stateful services this matters even more.

Restarting:

```text
one stateless API pod
```

is very different from restarting:

```text
primary database
```

---

### **10. Restart can still be the right mitigation**

If:

```text
production is severely impacted
+
diagnostics captured
+
restart is known safe
```

then restoring service takes priority.

The sequence is:

```text
Capture enough evidence
       ↓
Mitigate/restart
       ↓
Verify service
       ↓
Continue RCA
```

not:

```text
Spend two hours debugging
while users remain down
```

### **Strong interview answer**

> “Before restarting a production service, I would capture enough evidence to understand the current failure state because restart can destroy valuable diagnostic information. I would record timestamps and affected instances, collect logs, metrics and traces, check CPU, memory, disk, connections and process state, inspect dependencies, and correlate the incident with recent deployments or configuration changes. For a hung process I may capture a thread or process dump. I would also assess the blast radius of the restart. Once enough evidence is preserved, if restart is the safest way to restore service, I would do it and then continue root-cause analysis.”

**Memory line:**
**Before restarting: preserve evidence, understand dependencies and blast radius, then restore service.**

**Interview trap:**
Do not make **“restart the service”** your first troubleshooting step. It may fix the symptom while destroying the evidence needed to find the cause.

**Keywords:**
Incident evidence, logs, metrics, traces, process dump, blast radius, mitigation, RCA

**Likely follow-ups:**

* When would you restart immediately?
* What evidence could disappear after a restart?
* Restart versus rollback—which would you choose?
* Why might a restarted service fail again shortly afterward?

# **14. 🟠 IMP — Azure Container Registry & Container Security**

### **T14-E01. What is Azure Container Registry?**

**Answer:**
Azure Container Registry, or **ACR**, is Microsoft's managed private container-registry service for storing, managing, and distributing **container images and OCI artifacts**. It commonly sits between CI/CD pipelines and deployment targets such as AKS, App Service, or Azure Container Apps. ([Microsoft Learn][1])

### **Basic flow**

```text
Developer
   ↓
Git repository
   ↓
CI pipeline
   ↓
Build container image
   ↓
Azure Container Registry
   ↓
AKS / App Service / Container Apps
```

For example:

```text
mycompany.azurecr.io
```

might contain:

```text
frontend
backend
worker
```

repositories.

---

### **What ACR stores**

ACR can store:

```text
Docker-compatible images
OCI images
OCI artifacts
other supported registry artifacts
```

Microsoft describes an ACR registry as containing repositories, where each repository contains related image/artifact manifests and tags. ([Microsoft Learn][2])

For example:

```text
myacr.azurecr.io/payment-api:v1
myacr.azurecr.io/payment-api:v2
```

Both belong to:

```text
payment-api
```

repository.

---

### **Why use ACR instead of a public registry?**

ACR gives an organization control over:

```text
authentication
Azure RBAC
network access
private connectivity
artifact lifecycle
Azure integration
```

For production, this is particularly useful with:

```text
AKS
Managed Identity
Private Endpoint
CI/CD
Defender for Cloud
```

depending on the architecture and SKU.

---

### **Example**

```bash
docker push myacr.azurecr.io/api:v1
```

Then AKS can deploy:

```yaml
image: myacr.azurecr.io/api:v1
```

Conceptually:

```text
Pipeline
   ↓ push
ACR
   ↓ pull
AKS
```

---

### **ACR is not a container runtime**

Important distinction:

```text
ACR
→ stores/distributes images

AKS
→ runs containers
```

ACR does not execute the application.

---

> **In an interview, I would say:**
> “Azure Container Registry is Azure's managed private registry for storing and distributing container images and OCI artifacts. In a typical DevOps flow, CI builds an image, pushes it to ACR, and AKS or another Azure compute service pulls that image for deployment. ACR integrates with Azure identity and RBAC and can also support private networking and other enterprise registry capabilities.”

**Memory line:**
**ACR stores container artifacts; AKS runs them.**

**Interview trap:**
Do not describe ACR as a Kubernetes service or container runtime.

**Keywords:**
ACR, container image, OCI artifact, repository, CI/CD, AKS

**Likely follow-ups:**

* How does AKS authenticate to ACR?
* Can ACR be private?
* What is the difference between an ACR repository and registry?
* What are ACR SKUs?

### **T14-E02. What is a container registry?**

**Answer:**
A container registry is a service that **stores and distributes container images and related artifacts**. Developers or CI pipelines push images into the registry, and deployment platforms such as Kubernetes pull those images when starting containers. ([Microsoft Learn][2])

### **Basic model**

```text
Source code
    ↓
docker build
    ↓
Container image
    ↓
docker push
    ↓
Container Registry
    ↓
docker/container runtime pull
    ↓
Running container
```

Examples include:

```text
Azure Container Registry
Docker Hub
GitHub Container Registry
```

---

### **Registry vs repository**

This distinction is commonly asked.

A **registry** contains many repositories:

```text
myacr.azurecr.io
│
├── frontend
├── backend
└── worker
```

A **repository** contains related versions of one named image/artifact:

```text
backend
│
├── :v1
├── :v2
└── :abc123
```

Microsoft defines an ACR repository as a collection of container images or artifacts sharing the same name but potentially having different tags. ([Microsoft Learn][2])

---

### **Example image reference**

```text
myacr.azurecr.io/payment-api:v2
```

Breakdown:

```text
myacr.azurecr.io
→ registry

payment-api
→ repository

v2
→ tag
```

Another form:

```text
myacr.azurecr.io/payment-api@sha256:...
```

uses a digest rather than a tag.

---

### **What is actually stored?**

A container image consists conceptually of:

```text
Manifest
+
Layers
+
Metadata
```

The manifest describes the layers, and the manifest has a content digest that uniquely identifies it. ([Microsoft Learn][3])

---

### **Why registries matter in DevOps**

Without a registry:

```text
CI builds image
```

but production has no controlled place from which to retrieve that artifact.

With a registry:

```text
Build once
   ↓
Store artifact
   ↓
Deploy same artifact
across environments
```

This supports:

```text
Dev
Staging
Production
```

using the same image rather than rebuilding the application for every environment.

---

> **In an interview, I would say:**
> “A container registry is a centralized service used to store and distribute container images and related artifacts. CI pipelines push built images to the registry, and platforms like Kubernetes pull them during deployment. A registry contains repositories, and each repository can contain multiple versions of an image identified by tags or immutable digests.”

**Memory line:**
**Registry = image/artifact store; repository = versions of one named image.**

**Interview trap:**
Do not confuse:

```text
registry
repository
image
container
```

They are different things.

**Keywords:**
Registry, repository, image, manifest, layers, push, pull

**Likely follow-ups:**

* Registry vs repository?
* Image vs container?
* Tag vs digest?
* Why should CI push images to a registry?

### **T14-E03. What is a Docker image tag?**

**Answer:**
A Docker image tag is a **human-readable label attached to an image manifest**, commonly used to identify a version or build such as `v1.2.0`, `20260903`, or a Git commit SHA. Importantly, a tag is generally a **mutable reference**—the same tag can later be moved to another image. ([Microsoft Learn][2])

### **Example**

```text
myacr.azurecr.io/api:v1
```

Breakdown:

```text
myacr.azurecr.io
→ registry

api
→ repository

v1
→ tag
```

Another image might be:

```text
myacr.azurecr.io/api:v2
```

Both belong to the same repository:

```text
api
```

---

### **One image can have multiple tags**

For example:

```text
Image digest
sha256:abc123...
```

might have:

```text
:v2.1.0
:production
:build-729
```

All three tags could currently reference the **same manifest**.

Microsoft states that one artifact can have one or many tags. ([Microsoft Learn][2])

---

### **Tags are usually mutable**

Suppose today:

```text
api:production
      ↓
sha256:AAA
```

Tomorrow somebody pushes:

```text
api:production
      ↓
sha256:BBB
```

The name:

```text
api:production
```

stayed the same, but its content changed.

That's the key distinction between:

```text
Tag
→ mutable alias
```

and:

```text
Digest
→ content-derived immutable identifier
```

---

### **`latest` is just a tag**

This is very important.

```text
latest
```

does **not** mean:

```text
"Azure automatically finds the newest safe production version."
```

It is simply a conventional tag name.

Docker commonly uses `latest` when no explicit tag is provided. Microsoft also notes that the `latest` tag is used by default when a tag isn't supplied in standard Docker operations. ([Microsoft Learn][2])

---

### **Production tagging**

A better CI/CD approach is often:

```text
api:git-a82f4c1
```

or:

```text
api:build-742
```

because each build gets a unique identifier.

Microsoft recommends **unique tags for deployment artifacts** and warns against relying on reusable stable tags for deployments because their content can change. ([Microsoft Learn][4])

Even stronger for immutable production identity:

```text
api@sha256:...
```

which points to one exact manifest.

---

### **Example pipeline**

```text
Git commit
a82f4c1
   ↓
docker build
   ↓
api:a82f4c1
   ↓
push ACR
   ↓
deploy
```

Now I can immediately answer:

> Which build is running?

```text
a82f4c1
```

---

> **In an interview, I would say:**
> “A Docker image tag is a human-readable reference used to label an image version, such as `v1.2` or a Git commit SHA. Tags are convenient, but they're generally mutable—a tag can later point to a different image. That's why production pipelines should prefer unique tags and, where exact immutability matters, deploy by image digest. Also, `latest` is only a conventional tag; it doesn't guarantee anything about freshness or safety.”

**Memory line:**
**Tag = human-friendly alias; digest = exact immutable image identity.**

**Interview trap:**
Do not say a tag uniquely and permanently identifies an image. Tags can move.

**Keywords:**
Image tag, mutable reference, unique tag, `latest`, Git SHA, digest

**Likely follow-ups:**

* What is an image digest?
* Why is `latest` risky?
* Can multiple tags point to the same image?
* Tag vs digest—which should production use?
