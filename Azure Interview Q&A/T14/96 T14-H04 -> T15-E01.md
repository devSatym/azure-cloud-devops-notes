### **T14-H04. What is an SBOM?**

**Answer:**
An **SBOM, or Software Bill of Materials**, is a structured inventory of the software components used to build an application or container image—such as operating-system packages, libraries, frameworks, and their versions. I think of it as an **ingredient list for software**. Microsoft describes an SBOM as a build manifest listing the components used to build a piece of software, and Azure container supply-chain guidance shows SBOMs being attached to container images as related OCI artifacts. ([Microsoft Learn][1])

### **Simple example**

Suppose I build:

```text
payment-api@sha256:ABC
```

Its SBOM might tell me:

```text
payment-api
│
├── Ubuntu package: openssl 3.x
├── Node.js 24.x
├── express 5.x
├── jsonwebtoken x.x
└── other dependencies...
```

So if tomorrow:

```text
Critical CVE found in package X
```

I can search SBOMs and answer:

```text
Which images contain package X?
Which version?
Which workloads are affected?
```

---

### **1. Why do we need an SBOM?**

Without one:

```text
Security advisory
"CVE affects library xyz"
        ↓
Teams manually investigate
every repository/image
```

With an SBOM:

```text
CVE affects xyz 4.1
        ↓
Query SBOM inventory
        ↓
image-a affected
image-b not affected
image-c affected
```

That dramatically improves vulnerability-response speed.

---

### **2. Typical SBOM contents**

An SBOM normally contains metadata such as:

```text
Package/component name
Version
Supplier
Package identifier
Dependency relationships
Licensing information
Hashes/checksums
```

depending on the SBOM format and generator.

Common standardized formats include:

```text
SPDX
CycloneDX
```

Microsoft's container supply-chain example currently generates an **SPDX** SBOM and attaches its JSON representation to the image. ([Microsoft Learn][1])

---

### **3. Container supply-chain flow**

A good pipeline could be:

```text
Source
  ↓
Build image
  ↓
sha256:ABC
  ↓
Generate SBOM
  ↓
Attach SBOM to ABC
  ↓
Sign image/SBOM
  ↓
Push to ACR
```

Microsoft documents using `sbom-tool` to generate an SPDX manifest and ORAS to attach the SBOM to the image in ACR. ([Microsoft Learn][1])

Conceptually:

```text
Image digest
sha256:ABC
     |
     ├── Signature
     ├── SBOM
     └── Provenance
```

These related artifacts collectively strengthen the supply-chain story.

---

### **4. SBOM vs vulnerability scan**

This is an important distinction:

```text
SBOM
→ what components are inside?

Vulnerability scan
→ are known vulnerabilities associated
  with those components right now?
```

An SBOM is **not itself a vulnerability scanner**.

Example:

```text
SBOM:
openssl 3.0.x exists

Scanner:
CVE-XXXX affects this version
```

Also:

```text
SBOM generated today
```

remains useful six months later when a **new CVE** is discovered.

---

### **5. SBOM vs image signature**

Another important distinction:

```text
SBOM
→ what's inside the software?

Signature
→ who signed this artifact,
  and has the signed artifact changed?
```

They solve different supply-chain problems.

A signed malicious image could still contain dangerous packages.

A detailed SBOM also doesn't prove the image came from a trusted builder.

That's why a mature flow combines:

```text
SBOM
+
Vulnerability scan
+
Signature
+
Provenance
```

---

### **6. SBOM should map to the exact artifact**

I would associate the SBOM with:

```text
image@sha256:ABC
```

rather than loosely saying:

```text
api:latest has this SBOM
```

because `latest` may change.

The ideal mapping is:

```text
Git commit
     ↓
Image digest ABC
     ↓
SBOM for ABC
```

so I can trace the exact production artifact.

---

### **7. SBOM can itself be protected**

Microsoft's secure container supply-chain guidance demonstrates:

```text
Image
  ↓
SBOM attached
  ↓
SBOM digest
  ↓
SBOM signed
```

so consumers can verify that the SBOM hasn't been silently replaced or modified. ([Microsoft Learn][1])

---

### **Production example**

Suppose a vulnerability is announced:

```text
Critical vulnerability
in libxyz <= 3.8
```

My response becomes:

```text
Search SBOM inventory
       ↓
Find:
payment-api ABC → libxyz 3.7
catalog-api DEF → libxyz 4.2
       ↓
payment-api affected
catalog-api safe
       ↓
rebuild payment-api
       ↓
new digest + new SBOM
```

That is much faster than manually opening dozens of Dockerfiles.

> **In an interview, I would say:**
> “An SBOM is a Software Bill of Materials—a machine-readable inventory of the components and versions contained in a software artifact. For containers, I generate the SBOM for the exact image digest during CI and associate it with that image in the registry. It helps vulnerability response because when a new CVE is published, I can identify which production images contain the affected package without rebuilding or manually inspecting everything. I distinguish an SBOM from a vulnerability scan: the SBOM tells me what is inside, while the scanner tells me which known vulnerabilities currently affect those components.”

**Memory line:**
**SBOM = ingredient list for the exact software artifact.**

**Interview trap:**
Do not say an SBOM proves an image is secure. It is primarily an **inventory**, not a security verdict.

**Keywords:**
SBOM, SPDX, CycloneDX, components, dependencies, vulnerability management, OCI artifact

**Likely follow-ups:**

* SBOM vs vulnerability scan?
* SPDX vs CycloneDX?
* Why associate the SBOM with an image digest?
* Why would you sign an SBOM?

### **T14-H05. What is container-image signing?**

**Answer:**
Container-image signing is the process of **cryptographically signing an exact container image digest so consumers can verify the artifact's integrity and the identity of its trusted publisher**. The important point is that I sign the immutable digest, not merely a mutable tag. Microsoft's current ACR guidance recommends **Notary Project/Notation** for modern OCI image signing and verification. ([Microsoft Learn][2])

### **Core idea**

```text
Container image
     ↓
sha256:ABC
     ↓
Signing identity/key
     ↓
Digital signature
```

At deployment:

```text
Image ABC
   +
Signature
   +
Trust policy
     ↓
Verify
     ↓
Trusted / Untrusted
```

---

### **1. What does signing prove?**

A successful signature verification can help answer:

```text
Has this signed artifact been changed?
```

and:

```text
Was it signed by an identity
that I trust?
```

Microsoft describes image signing as a way to verify both the image's integrity and the publisher's identity. ([Microsoft Learn][3])

---

### **2. Sign the digest, not a mutable tag**

Bad mental model:

```text
Sign api:latest
```

because:

```text
latest today → ABC
latest tomorrow → DEF
```

The cryptographic trust must correspond to:

```text
api@sha256:ABC
```

the exact artifact.

Pipeline:

```text
Build
  ↓
Digest ABC
  ↓
Scan ABC
  ↓
Sign ABC
  ↓
Deploy ABC
```

Now:

```text
Scanned artifact
=
Signed artifact
=
Deployed artifact
```

---

### **3. Modern Azure tooling**

For ACR, Microsoft's current direction is:

```text
Notary Project
   ↓
Notation CLI
   ↓
Signing certificate/key
   ↓
ACR OCI artifact/signature
```

Signing keys/certificates can be backed by mechanisms such as:

```text
Azure Key Vault
```

or newer Azure Artifact Signing workflows depending on the chosen implementation. Microsoft documents both Notation with Key Vault and Notation with Artifact Signing. ([Microsoft Learn][2])

---

### **4. Docker Content Trust is legacy**

This is important for a **2026 interview**.

Azure Container Registry's Docker Content Trust is being retired:

```text
New enablement stopped:
May 31, 2026

Full retirement:
March 31, 2028
```

Microsoft recommends transitioning to **Notary Project**. ([Microsoft Learn][4])

So I would not design a new ACR signing system around DCT.

---

### **5. Verification**

A consumer must have a **trust policy**.

Example:

```text
Artifact:
myacr.azurecr.io/api@sha256:ABC

Signature:
signed by Production Release certificate
```

Then:

```text
Verify signature
       ↓
Signature cryptographically valid?
       ↓
Signer matches trusted identity?
       ↓
artifact allowed
```

A technically valid signature from:

```text
Unknown developer certificate
```

should not automatically be trusted.

---

### **6. Enforce verification at deployment**

The strongest design is not:

```text
CI verifies image
then hopes nobody deploys another one
```

but:

```text
Pod request
   ↓
AKS admission
   ↓
Signature verification
   ↓
Trusted signer?
 /       \
Yes       No
 ↓         ↓
Admit     Deny
```

That creates an actual security boundary.

---

### **7. Signing vs vulnerability scanning**

Very important:

```text
Signature
→ integrity + publisher trust

Vulnerability scan
→ known vulnerabilities

SBOM
→ components

Provenance
→ how/where artifact was built
```

A signed image could still contain:

```text
critical CVE
```

Signing does not magically make its contents safe.

---

### **8. Signing prevents substitution attacks**

Suppose CI approves:

```text
sha256:ABC
```

An attacker later pushes:

```text
sha256:XYZ
```

under:

```text
api:production
```

If deployment requires the trusted signature on ABC:

```text
XYZ
→ signature missing/untrusted
→ rejected
```

That is exactly why signing + immutable digests are powerful together.

---

> **In an interview, I would say:**
> “Container-image signing means cryptographically signing the immutable image digest so consumers can verify that the artifact hasn't changed and that it was published by a trusted signer. In Azure I would use the current Notary Project ecosystem, typically the Notation CLI with a securely managed signing certificate or Artifact Signing. CI builds, scans and signs the exact digest, and AKS admission can verify the signature before allowing the workload. I also distinguish signing from scanning—a valid signature proves integrity and publisher identity, not that the image has no vulnerabilities.”

**Memory line:**
**Image signing answers: “Is this the exact artifact signed by someone I trust?”**

**Interview trap:**
A valid signature does **not** mean the image has no vulnerabilities or malware.

**Keywords:**
Image signing, Notary Project, Notation, digital signature, trusted signer, digest, integrity

**Likely follow-ups:**

* Why sign the digest rather than the tag?
* What is Notation?
* Image signing vs vulnerability scanning?
* How would AKS reject an unsigned image?

### **T14-H06. What is software provenance?**

**Answer:**
Software provenance is **verifiable metadata describing where a software artifact came from and how it was built**. For a container image, provenance can connect the final digest to its **source repository, commit, build workflow, builder identity, and build process**. It gives me evidence that the production artifact actually came from the trusted pipeline I expect.

Current Microsoft Defender for Cloud guidance describes cryptographically verifiable build provenance as linking container images to their exact source repository, commit, and build identity. ([Microsoft Learn][5])

### **Think of it as the artifact's history**

```text
Container image
sha256:ABC
     ↑
Built by?
     ↑
Which CI workflow?
     ↑
Which repository?
     ↑
Which Git commit?
```

Provenance provides those answers.

---

### **Example**

For:

```text
myacr.azurecr.io/payment-api@sha256:ABC
```

provenance might establish:

```text
Repository:
github.com/company/payment-api

Commit:
a82f4c1

Builder:
GitHub Actions trusted workflow

Workflow:
release.yml

Artifact:
sha256:ABC
```

So I can prove:

```text
Git commit a82f4c1
       ↓
Trusted workflow
       ↓
Image ABC
```

instead of merely trusting an image name.

---

### **1. Why provenance matters**

Suppose an attacker somehow pushes:

```text
myacr.azurecr.io/payment-api@sha256:MALICIOUS
```

into the registry.

The image might even:

```text
pass some basic vulnerability checks
```

but its provenance may show:

```text
Source repository: unknown
Builder: developer laptop
Trusted workflow: no
```

My policy can reject it.

---

### **2. Provenance vs signature**

These are related but different.

```text
Signature
→ who vouched for this artifact?
→ has the signed artifact changed?

Provenance
→ how was this artifact produced?
→ source repo?
→ commit?
→ builder?
→ workflow?
```

Example:

```text
Artifact signed by trusted key ✓
```

but provenance says:

```text
built from unexpected repository ✗
```

A mature policy may reject it.

---

### **3. Provenance vs SBOM**

Another key distinction:

```text
SBOM
→ what's inside?

Provenance
→ where/how was it built?
```

Together:

```text
Image ABC
│
├── SBOM
│    └── packages/components
│
├── Provenance
│    └── repo/commit/builder/workflow
│
└── Signature
     └── trusted publisher/integrity
```

That's a very strong interview diagram.

---

### **4. SLSA**

A common framework associated with software provenance is:

```text
SLSA
Supply-chain Levels for Software Artifacts
```

The key idea is to increase confidence that:

```text
source
→ build system
→ artifact
```

has not been tampered with.

In modern CI/CD, provenance is often represented as a cryptographically verifiable **attestation** bound to an artifact digest.

---

### **5. GitHub Actions example**

Conceptually:

```text
Protected Git repo
      ↓
Commit abc123
      ↓
GitHub Actions trusted workflow
      ↓
Build
      ↓
Image digest XYZ
      ↓
Provenance attestation
```

Then verification asks:

```text
Was XYZ built
from org/repo
at approved ref
by approved workflow?
```

Microsoft Defender for Cloud's current code-to-runtime mapping can use GitHub artifact attestations containing cryptographically verifiable provenance to associate an image with its exact repository, commit, and build identity. ([Microsoft Learn][5])

---

### **6. Admission-policy example**

Production policy could require:

```text
Image from approved ACR
        +
Signature valid
        +
Provenance says:
  repository = company/payment-api
  workflow = release.yml
        ↓
ALLOW
```

But:

```text
Same ACR
+
valid image
+
provenance from unknown repo
        ↓
DENY
```

That protects against:

```text
"Someone pushed an image to the trusted registry,
therefore it must be trusted."
```

---

### **7. Provenance helps incident response too**

During an incident:

> Where did this image come from?

With provenance:

```text
Running digest
      ↓
build attestation
      ↓
Git commit
      ↓
pull request
      ↓
developer/review history
```

That gives end-to-end traceability.

---

### **Strong supply-chain model**

```text
Source
 ↓
Commit
 ↓
Trusted Build
 ↓
Digest
 ├── SBOM
 ├── Vulnerability results
 ├── Signature
 └── Provenance
 ↓
Admission policy
 ↓
AKS
```

> **In an interview, I would say:**
> “Software provenance is metadata that proves the origin and build history of an artifact. For a container image, I want to know which repository and commit it came from, which trusted workflow built it, which builder identity executed the build, and which final image digest was produced. Provenance is usually represented as a verifiable attestation tied to that digest. I distinguish it from an SBOM, which tells me what components are inside, and from a signature, which proves integrity and signer identity. Together they let me enforce that production runs only artifacts produced by an approved source and trusted build process.”

**Memory line:**
**SBOM = what is inside; provenance = where it came from and how it was built.**

**Interview trap:**
Do not reduce provenance to simply storing the Git SHA as an image tag. A tag provides traceability convention; provenance provides **verifiable build-origin metadata**.

**Keywords:**
Software provenance, SLSA, attestation, source repository, Git commit, builder identity, supply-chain security

**Likely follow-ups:**

* Provenance vs SBOM?
* Provenance vs signature?
* What is SLSA?
* How would you enforce trusted provenance in Kubernetes?

# **15. 🟠 IMP — App Service, Functions & Container Apps**

### **T15-E01. What is Azure App Service?**

**Answer:**
Azure App Service is a **fully managed Platform as a Service (PaaS)** for hosting **web applications, REST APIs, mobile back ends, and custom containers** without having to manage the underlying servers and operating-system infrastructure yourself. Microsoft currently supports stacks such as .NET, Java, Node.js, Python, and PHP on Windows or Linux, as well as custom containers. ([Microsoft Learn][6])

### **Basic idea**

With VMs:

```text
You manage
│
├── VM
├── OS
├── patching
├── web server
├── runtime
└── application
```

With App Service:

```text
Azure manages
├── underlying compute
├── OS/platform
├── runtime platform
└── much of the hosting infrastructure

You manage
├── application
├── configuration
├── scaling choices
├── identity
└── networking/security settings
```

That's the key PaaS value.

---

### **Typical architecture**

```text
Users
   ↓
Azure Front Door
   ↓
App Service
   ↓
Azure SQL
   ↓
Storage / Key Vault
```

or simply:

```text
Internet
   ↓
App Service
   ↓
Application
```

depending on requirements.

---

### **What can it run?**

App Service supports application stacks including:

```text
.NET
Java
Node.js
Python
PHP
```

and:

```text
Custom container images
```

on supported platforms. ([Microsoft Learn][6])

So for example:

```text
Node.js REST API
```

can run directly on App Service without me managing an Ubuntu VM and installing Node/Nginx manually.

---

### **Built-in capabilities**

App Service provides platform capabilities such as:

```text
Autoscaling
Custom domains
TLS/certificates
Managed Identity
VNet Integration
Private Endpoint support
Deployment slots
CI/CD integration
Application monitoring
Authentication features
```

depending on the tier/configuration.

Microsoft specifically highlights built-in CI/CD integration, scaling, networking isolation options, authentication, and reliability capabilities. ([Microsoft Learn][6])

---

### **App Service vs VM**

```text
VM
→ I manage infrastructure/OS

App Service
→ Azure manages the platform
```

If I just need to host:

```text
Web API
website
backend service
```

without Kubernetes-level orchestration requirements, App Service can greatly reduce operational overhead.

---

### **App Service vs AKS**

Very simple distinction:

```text
App Service
→ managed web application PaaS

AKS
→ managed Kubernetes platform
```

AKS provides much more flexibility around:

```text
microservices
Kubernetes APIs
custom scheduling
operators
sidecars
network policies
advanced orchestration
```

but also introduces much more operational complexity.

App Service is often preferable when:

```text
I have a standard web/API workload
and don't need Kubernetes
```

---

### **App Service Plan**

App Service applications run on compute defined by an:

```text
App Service Plan
```

The plan determines:

```text
Region
Compute resources
Pricing tier
Scaling capability
```

Microsoft defines the App Service Plan as the compute resources on which App Service applications run. ([Microsoft Learn][7])

We'll cover that directly in the next question.

---

> **In an interview, I would say:**
> “Azure App Service is a fully managed PaaS for hosting web applications, REST APIs and custom containers. Azure manages the underlying infrastructure and platform so I can focus on the application instead of patching and maintaining VMs. It supports common runtimes such as .NET, Java, Node.js, Python and PHP, and provides capabilities such as scaling, deployment slots, Managed Identity, VNet integration and CI/CD. I would typically choose it for standard web/API workloads when I don't need the control and orchestration complexity of AKS.”

**Memory line:**
**App Service = managed PaaS for web apps and APIs without managing the underlying servers.**

**Interview trap:**
Do not describe App Service as serverless. It is a managed PaaS, and its compute generally runs inside an **App Service Plan**.

**Keywords:**
Azure App Service, PaaS, web app, REST API, custom container, App Service Plan
