# **T32-15. Design networking for 20 application teams using hub-and-spoke architecture.**

**Answer:**

For 20 application teams, I would use a **platform-owned hub-and-spoke network**, where application workloads live in isolated spoke VNets and shared network services live in one or more regional hubs.

Each team—or major workload/environment where stronger isolation is needed—would get its own spoke VNet, typically in its own workload subscription. The central hub would contain services such as **Azure Firewall, VPN/ExpressRoute Gateway, Azure Bastion, and Azure DNS Private Resolver**.

I would use centralized IP address management so spoke CIDRs never overlap, connect spokes to the hub using VNet peering or **Azure Virtual Network Manager** at scale, route internet and controlled inter-spoke traffic through Azure Firewall, and use Private Endpoints plus centralized Private DNS for PaaS services.

By default, I would **not allow every spoke to communicate with every other spoke**. Teams get isolation by default, with explicitly approved flows added when applications genuinely need to communicate.

```text
                        On-premises
                             │
                   ExpressRoute / VPN
                             │
                             ▼
                  ┌─────────────────────┐
                  │      HUB VNET       │
                  │                     │
                  │ Azure Firewall      │
                  │ Private DNS Resolver│
                  │ Bastion             │
                  │ ER/VPN Gateway      │
                  └──────────┬──────────┘
                             │
          ┌──────────┬───────┼───────┬──────────┐
          │          │       │       │          │
          ▼          ▼       ▼       ▼          ▼
       Spoke 1    Spoke 2  Spoke 3  ...      Spoke 20
       Team A     Team B   Team C            Team T
          │          │       │                  │
        Apps       Apps    Apps               Apps
        PEs        PEs     PEs                PEs
```

Microsoft's current hub-and-spoke guidance explicitly recommends keeping application workloads in spokes while the hub hosts shared networking capabilities such as Azure Firewall, gateways, Bastion, and DNS. It also notes that VNet peering is non-transitive, which is an important part of the isolation model. ([Microsoft Learn][1])

## **1. Separate platform ownership from application ownership**

I'd organize responsibilities something like:

```text
Platform Networking Team
│
├── Hub subscription
├── Azure Firewall
├── ExpressRoute/VPN
├── Private DNS
├── IPAM
├── Routing standards
└── Network policies

Application Teams
│
├── Team A subscription + spoke
├── Team B subscription + spoke
├── Team C subscription + spoke
└── ...
```

The networking team owns:

```text
connectivity
routing
DNS
firewall policy
hybrid connectivity
```

while application teams own resources inside their spokes.

That prevents 20 teams from independently building:

```text
20 firewalls
20 VPN gateways
20 DNS designs
```

with inconsistent security.

# **2. Do not put applications in the hub**

The hub should be primarily shared infrastructure.

Good:

```text
Hub
├── Azure Firewall
├── Gateway
├── Bastion
└── DNS Resolver
```

Application:

```text
Spoke
├── AKS
├── App Service integration subnet
├── VMs
└── Private Endpoints
```

Microsoft's current guidance explicitly recommends keeping application workloads out of the hub so the platform team can manage shared services independently. ([Microsoft Learn][1])



# **6. At 20 teams, I would strongly consider Azure Virtual Network Manager**

Manually maintaining:

```text
20 VNets
×
peering relationships
×
network policies
```

becomes operational toil.

Azure Virtual Network Manager can organize VNets into **network groups** and deploy connectivity configurations across subscriptions.

For example:

```text
AVNM
│
├── Network Group: Production
├── Network Group: NonProduction
├── Network Group: PCI
└── Network Group: SharedServices
```

Membership can be static or dynamically driven through Azure Policy-based conditions. Current Microsoft guidance specifically supports dynamic network groups and hub-and-spoke connectivity configurations. ([Microsoft Learn][2])

### Through Azure Firewall

```text

  ↓
```

Advantages:


Trade-offs:


For workloads requiring high-volume low-latency communication, direct connectivity may be more appropriate if security policy permits it.

Current Azure Virtual Network Manager can enable direct connectivity inside selected spoke network groups, eliminating the hub hop for those approved spokes. ([Microsoft Learn][2])

### **Interview answer condensed**

> “For 20 application teams I'd make the hub a platform-owned shared-services network containing Azure Firewall, hybrid gateways, Bastion and central DNS, while each team or workload gets an isolated spoke, preferably aligned with its workload subscription. I'd centrally allocate nonoverlapping address spaces, connect spokes using VNet peering or Azure Virtual Network Manager at scale, and route controlled internet and east-west traffic through Azure Firewall. Spokes wouldn't communicate by default; approved dependencies would get explicit connectivity and identity permissions. Private Endpoints would use a consistent central Private DNS design, and ExpressRoute or VPN gateway transit would be provided through the hub. I'd provision new spokes through reusable IaC/landing-zone modules rather than twenty teams manually creating networking.”

**Memory line:**
**Hub = shared connectivity and security; spokes = isolated application ownership.**

**Interview trap:**
VNet peering is **non-transitive**—peering 20 spokes with the hub does not automatically allow those 20 spokes to communicate with each other.

**Keywords:**
Hub-spoke, Azure Firewall, VNet peering, Azure Virtual Network Manager, UDR, Private DNS Resolver, ExpressRoute, gateway transit, IPAM, spoke isolation.

**Likely follow-ups:**

* How would you allow two specific spokes to communicate?
* Why use Azure Virtual Network Manager instead of managing peerings individually?
* Would you route all spoke-to-spoke traffic through Azure Firewall?
* How would you handle Private Endpoint DNS across 20 teams?
* What happens if the centralized hub fails?

# **T32-16. Design CI/CD for 50 microservices deployed to AKS.**

**Answer:**

For 50 microservices, I would avoid both **50 independently handcrafted pipelines** and **one giant pipeline that rebuilds and redeploys all 50 services for every commit**.

I would create a standardized CI/CD platform based on reusable workflows/templates. Each service uses the same pipeline contract: test, scan, build an immutable container image, push it to ACR, and promote that exact image through environments.

If the services are in a monorepo, CI should identify which services changed and build only those services plus affected dependencies. If they're in separate repositories, each repository can call the same centrally maintained reusable workflow.

I would separate **CI from deployment**, authenticate GitHub/Azure pipelines using OIDC rather than long-lived Azure secrets, sign or at least scan generated images, and use Helm/Kustomize or GitOps for Kubernetes configuration.

The key principle is:

> **Build once, promote the same immutable artifact—don't rebuild production separately.**

```text
                    50 Microservices
                          │
                    Git repositories
                          │
                          ▼
                  Reusable CI workflow
                          │
          ┌───────────────┼────────────────┐
          ▼               ▼                ▼
        Tests       Security checks      Build
                                          │
                                          ▼
                                         ACR
                                  image: git-SHA
                                          │
                                          ▼
                                   Deployment flow
                                Dev → Stage → Prod
                                          │
                                          ▼
                                         AKS
```

## **1. Standardize instead of copying pipelines**

Bad design:

```text
service-1
→ custom YAML

service-2
→ completely different YAML

...

service-50
→ another custom pipeline
```

After a year:

```text
50 different ways
to build and deploy
```

Updating security tooling becomes painful.

Better:

```text
Central reusable workflow
        ↑
        │
 ┌──────┼────────┐
Svc A  Svc B   Svc C ... Svc 50
```

Each service supplies only variables such as:

```text
service name
Dockerfile path
image repository
Helm chart
test command
```

The platform team owns the pipeline implementation.

# **3. Monorepo: build only changed services**

Suppose:

```text
/services
├── checkout
├── payment
├── catalog
├── cart
└── ... 46 more
```

A documentation change to:

```text
catalog
```

should not necessarily trigger:

```text
50 Docker builds
```

CI can determine:

```text
git diff
   ↓
changed paths
   ↓
affected services
```

Then create a build matrix:

```text
checkout = unchanged → skip
payment  = changed   → build
catalog  = unchanged → skip
```

At scale this dramatically reduces pipeline duration and cost.

# **16. Health probes are part of deployment safety**



### **Interview answer condensed**

> “For 50 microservices I would build a standardized pipeline platform, not 50 handcrafted pipelines or one giant pipeline that redeploys everything. Each service would call reusable CI workflows that test, scan, build once and push an immutable image to ACR using the Git SHA and digest. In a monorepo I'd detect changed services and build only affected services; in multi-repo I'd reuse the same central workflow. CI permissions would normally stop at artifact production, while a separate deployment or GitOps identity controls AKS. I'd promote the exact same image digest from Dev to Stage to Prod, use common Helm/Kustomize patterns for probes, resources, HPA and PDBs, and use rolling or progressive deployment with SLO/error health gates. **Standardize the pipeline, build only what changed, build once, and promote the same immutable artifact.**

**Interview trap:**
Microservices don't provide independent delivery if one giant pipeline **rebuilds and redeploys all 50 services for every change**.

# **T32-17. Design a GitOps deployment architecture using GitHub Actions, ACR, AKS, and Argo CD.**

**Answer:**

I would clearly separate **CI from CD**.

GitHub Actions would own CI: test the application, scan it, build the container image, push that immutable image to ACR, and update the desired image version in a dedicated GitOps repository.

**GitHub Actions would not normally run `kubectl apply` directly against production.**

Argo CD would run as the CD controller, continuously watching the GitOps repository. When the desired manifests or Helm values change, Argo CD detects the difference and reconciles AKS toward that Git-defined state.

That gives me:

```text
Application repo
      ↓
GitHub Actions
      ↓
Build + scan
      ↓
ACR
      ↓
Update GitOps repo
      ↓
Argo CD
      ↓
AKS
```

The important principle is:

> **Git records desired deployment state, ACR stores the immutable artifact, and Argo CD—not CI—is responsible for making AKS match Git.**

Argo CD currently supports automated synchronization as well as self-healing and pruning behavior, although I would enable those deliberately based on environment and risk. ([Argo CD][4])

---

# **T32-18. Design Azure authentication for GitHub Actions without storing client secrets.**

**Answer:**

I would use **GitHub Actions OIDC federation with Microsoft Entra ID**.

Instead of creating a service principal client secret and storing that secret in GitHub, I would create either an Entra application/service principal or a user-assigned managed identity and configure a **federated identity credential** that trusts a specific GitHub repository, branch, tag, or GitHub Environment.

At workflow runtime, GitHub issues a short-lived OIDC JWT. `azure/login` sends that identity assertion to Microsoft Entra ID, Entra validates the issuer, audience, and subject against the configured federated credential, and then issues a short-lived Azure access token.

So the flow is:

```text
GitHub Actions
      ↓
short-lived GitHub OIDC JWT
      ↓
Microsoft Entra ID
      ↓
federated trust validation
      ↓
short-lived Azure access token
      ↓
Azure Resource Manager / ACR / etc.
```

There is **no stored Azure client secret to steal or rotate**.

GitHub and Microsoft currently document this as the recommended secretless authentication pattern for GitHub Actions to Azure. ([GitHub Docs][5])

---

Traditional pipeline authentication:

```text

      ↓
client ID
client secret
      ↓
GitHub Secret
AZURE_CLIENT_SECRET
      ↓
azure/login
```

Problems:

```text

secret must rotate

```

Production outage example:

```text

      ↓
```

OIDC removes this long-lived credential.

```text

```

```text

```

The workflow still authenticates—but without possessing a permanent Azure password.

# **6. Subject restricts who is trusted**

A classic branch-based trust is conceptually:

```text
repo:myorg/payment:ref:refs/heads/main
```

Meaning:

> Only this repository, running from this branch, matches the trust.

Environment-based:

```text
repo:myorg/payment:environment:Production
```

Meaning:

> Only a job associated with the Production GitHub Environment matches.

GitHub specifically recommends environment protection rules when environments are used in OIDC policies. ([GitHub Docs][5])

---

# **7. Important current 2026 GitHub nuance**

As of current GitHub documentation, repositories created after **July 15, 2026** use an **immutable default OIDC subject format** that includes owner and repository IDs. Older repositories retain the previous format unless they opt in; repository renames/transfers can also move to the immutable format. ([GitHub Docs][8])

So for a newly created repository, the subject may look conceptually like:

```text
repo:myorg@OWNER-ID/payment@REPO-ID:ref:refs/heads/main
```

instead of only:

```text
repo:myorg/payment:ref:refs/heads/main
```

This is why in production I would verify the actual GitHub OIDC subject expected for the repository rather than blindly copying an old tutorial.

That's a very useful current interview/detail point.

---

# **8. Why immutable subjects improve security**

Suppose:

```text
org/repo
```

is deleted and later its name is reused.

A trust based solely on:

```text
repository name
```

could conceptually become ambiguous.

Immutable IDs make trust bind to:

```text
specific repository identity
```

rather than only a reusable name.

GitHub introduced this specifically to make OIDC subjects more durable across namespace changes. ([GitHub Docs][8])

```text
terraform apply
```

No Azure client secret.

# **24. Production security model**

```text
GitHub
│
├── branch protection
├── environment approval
└── id-token permission
       │
       ▼
GitHub OIDC issuer
       │
       ▼
Microsoft Entra ID
│
├── Federated credential
└── Workload identity
       │
       ▼
Azure RBAC
       │
       ▼
Target resource
```

Every boundary answers a different question:

```text
GitHub protection
→ Who can cause this workflow to run?

Federated credential
→ Which workflow identity do we trust?

Azure RBAC
→ What can that identity do?
```

That's the architecture I want.

### **Interview answer condensed**

> “I would use GitHub Actions OIDC federation with Microsoft Entra ID instead of storing a service-principal client secret. I'd create an Entra application/service principal or user-assigned managed identity, add a federated identity credential that trusts only the required GitHub repository and preferably the protected Production environment or branch, and grant that Azure identity least-privilege RBAC at the target resource scope. The workflow gets `id-token: write`, GitHub issues a short-lived OIDC JWT, `azure/login` exchanges it with Entra, and Entra returns a short-lived Azure access token. There is no Azure secret to store or rotate. For Production I'd combine this with GitHub Environment approvals and a separate Prod identity. I'd also verify the repository's actual OIDC subject format because current GitHub repositories created after July 15, 2026 use immutable owner/repository IDs in the default subject.”

**Memory line:**
**GitHub proves the workflow's identity to Entra; Entra issues a temporary token—no Azure password is stored in GitHub.**

**Interview trap:**
OIDC eliminates the **long-lived credential**, but it does **not eliminate RBAC or trust design**—an overbroad federated subject plus Owner access is still dangerously overprivileged.

**Keywords:**
OIDC, Workload Identity Federation, GitHub Actions, Microsoft Entra ID, federated credential, `id-token: write`, `azure/login`, audience, subject, Azure RBAC.

**Likely follow-ups:**

* What exactly does `id-token: write` permit?
* What happens if Azure login succeeds but the deployment gets HTTP 403?
* How would you restrict OIDC authentication to Production only?
* Why would you use separate Dev and Prod federated identities?
* What changed in GitHub's default OIDC subject format in July 2026?
