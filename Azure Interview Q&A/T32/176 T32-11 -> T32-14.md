# **T32-11. Design an Azure architecture for an internet-facing application serving millions of users.**

**Answer:**

For an internet-facing application serving millions of users, I would design for **global traffic distribution, horizontal scalability, zone and regional resilience, security at the edge, private backend services, caching, asynchronous processing, and strong observability**.

For a large HTTP application, a strong starting architecture would be **Azure Front Door Premium with WAF** as the global entry point. It gives global Layer-7 routing, TLS termination, WAF, health-based regional routing, and CDN/caching capabilities. Behind it I would deploy the application into at least two Azure regions, with each regional stack independently capable of serving users.

Within each region I'd use a horizontally scalable compute platform such as App Service, Container Apps, or AKS depending on the application's requirements. The application tier should be stateless wherever practical, with session/state externalized into appropriate managed data services.

The most important architectural principle is:

> **Scale horizontally and eliminate shared regional single points of failure.**

```text
                              Internet
                                  │
                                  ▼
                    ┌─────────────────────────┐
                    │ Azure Front Door Premium│
                    │ WAF + TLS + CDN/Cache   │
                    └────────────┬────────────┘
                                 │
                    Health-based global routing
                     ┌───────────┴───────────┐
                     ▼                       ▼
                REGION A                 REGION B
            ┌──────────────┐          ┌──────────────┐
            │ Zone-resilient│          │ Zone-resilient│
            │ App Platform │          │ App Platform │
            └──────┬───────┘          └──────┬───────┘
                   │                          │
             ┌─────┼──────┐             ┌────┼──────┐
             ▼     ▼      ▼             ▼    ▼      ▼
           Cache  Queue  Data          Cache Queue  Data
                    \                    /
                     \──── replication ─/
```

Azure Front Door is specifically designed as a global HTTP/HTTPS load balancer and CDN, and Microsoft's current multi-region guidance uses it to distribute requests and fail traffic away from an unhealthy region. ([Microsoft Learn][1])

## **1. Start from requirements**

Before choosing services, I would quantify:

```text
Peak requests/sec?
Geographic user distribution?
Latency target?
Availability SLO?
RTO?
RPO?
Read/write ratio?
Payload sizes?
Static vs dynamic traffic?
Compliance/data residency?
```

“Millions of users” alone doesn't tell me the required capacity.

For example:

```text
10 million registered users
but
2,000 concurrent users
```

is completely different from:

```text
2 million concurrent users
during a live event
```

So I'd capacity-plan from **peak concurrency and transaction rate**, not account count.

# **2. Global entry: Azure Front Door**

For a global web/API workload:

```text
Users
  ↓
Azure Front Door
```

Front Door provides:

* global HTTP/HTTPS routing,
* edge termination,
* health probes,
* regional failover,
* WAF integration,
* caching/CDN where applicable.

For large-scale traffic, caching static or cacheable content at the edge is extremely valuable:

```text
10 million requests
        ↓
Front Door cache
    /           \
 HIT             MISS
 ↓                ↓
served edge      application origin
```

Every cache hit is a request the backend does **not** need to process.

# **3. WAF at the edge**

Place:

```text
Internet
   ↓
Front Door WAF
```

to reduce exposure to:

* SQL injection patterns,
* XSS patterns,
* malformed HTTP,
* abusive requests,
* known attack signatures.

Also consider:

```text
rate limiting
bot protection
custom WAF rules
```

where appropriate.

But:

```text
WAF
≠
secure application code
```

I still need proper input validation, parameterized SQL, authorization, dependency patching, etc.

---

# **4. Block origin bypass**

A common mistake:

```text
Users → Front Door → App

but also:

Users ───────────→ App public endpoint
```

Attackers can then bypass:

```text
WAF
rate limits
edge policies
```

For high-security architectures, I'd restrict origins so traffic enters through the approved edge path. Front Door Premium can use Private Link connectivity to supported origins, reducing public origin exposure. ([Microsoft Learn][2])

---

# **5. Use multiple Azure regions**

For millions of users and a stringent availability requirement, I'd normally evaluate at least:

```text
Region A
+
Region B
```

Each should contain a **self-contained application stack**.

Active-active:

```text
Front Door
   ├── 50% → Region A
   └── 50% → Region B
```

During Region A failure:

```text
Front Door health probe
       ↓
Region A unhealthy
       ↓
100% → Region B
```

Microsoft's current guidance describes this active-active pattern and explicitly notes the surviving region must be capable of handling increased traffic after failover. ([Microsoft Learn][3])

---

# **6. Capacity each region for failure**

This is critical.

Suppose:

```text
Region A handles 50%
Region B handles 50%
```

Normally each sees:

```text
50,000 requests/sec
```

Region A fails.

Now Region B receives:

```text
100,000 requests/sec
```

If Region B's maximum capacity is:

```text
60,000 requests/sec
```

then regional failover technically works but the application still goes down.

I need:

```text
sufficient warm capacity
+
autoscale limits
+
Azure subscription quota
```

for failover conditions.

# **7. Zone resilience inside each region**

Multi-region does not remove the need for Availability Zones.

I want:

```text
Region A
├── Zone 1
├── Zone 2
└── Zone 3

Region B
├── Zone 1
├── Zone 2
└── Zone 3
```

Then:

```text
single VM failure
      ↓
handled locally

zone failure
      ↓
handled inside region

region failure
      ↓
handled globally
```

This creates layered reliability.

# **9. Make application instances stateless**

Suppose:

```text
User session
stored in memory of App1
```

Then:

```text
Request 1 → App1
Request 2 → App7
```

can fail.

Better:

```text
               App instances
             /      |       \
            ↓       ↓        ↓
         Shared managed state/cache
```

Externalize:

```text
sessions
files
queues
durable data
```

so compute instances are disposable.

This allows:

```text
10 instances
→ 100 instances
→ 20 instances
```

without losing state.

# **10. Cache aggressively where safe**

Three caching layers can exist.

### Edge cache

```text
Front Door CDN
```

for static/cacheable HTTP content.

### Application/distributed cache

```text
API
 ↓
Managed cache
```

for frequently read objects.

### Database-side optimization

```text
indexes
read replicas
materialized/cached results
```

depending on data platform.

Example:

```text
Product catalog requested
1,000,000 times/min
```

If 95% is safely cacheable:

```text
Database load
can fall dramatically
```

But never cache business-critical mutable values without defining freshness semantics.

# **13. The database must be designed independently**

Compute can scale to hundreds of instances very easily.

A database often cannot.

A dangerous flow is:

```text
10 API instances
      ↓
scale to 200
      ↓
each opens 50 DB connections
      ↓
10,000 connections
      ↓
database collapses
```

So I would design:

```text
connection pooling
bounded concurrency
read scaling
partitioning if required
appropriate database tier
```

before unlimited application autoscaling.

```text
health probe removes it
```


### Database dependency slows

### **Interview answer condensed**

> “For a web application serving millions of users, I'd put Azure Front Door Premium with WAF at the global edge for TLS, Layer-7 routing, health-based regional failover and caching. I'd deploy stateless application stacks across at least two Azure regions, with each region itself zone resilient and capable of handling full production load after failover. Depending on the workload I'd use App Service, Container Apps, or AKS rather than assuming Kubernetes. I'd externalize state, use edge and application caching where safe, decouple noncritical work through messaging, scale horizontally, and protect databases with connection limits and appropriate geo-resilience. Backend PaaS services would use private connectivity and workload identities, and I'd use SLO-based Azure Monitor/Application Insights telemetry plus progressive deployments. Most importantly, I'd load-test both normal traffic and full regional-failover traffic.”

**Memory line:**
**Global edge → multiple self-contained regions → multiple zones → stateless horizontal compute → scalable data and messaging.**

**Interview trap:**
Deploying two regions does **not** make the application region-resilient if the surviving region cannot handle 100% load or both regions depend on the same regional database.

**Keywords:**
Azure Front Door, WAF, multi-region, Availability Zones, autoscaling, CDN, caching, Service Bus, Managed Identity, SLO.

* What would happen if one entire Azure region failed?
* How would you prove the second region can handle full traffic?

# **T32-12. Design a highly available AKS platform across Availability Zones.**

**Answer:**

I would build the AKS cluster in an Azure region with Availability Zone support and spread **both system and application node pools across multiple zones**. I would then make Kubernetes workloads zone-aware by running multiple replicas with topology-spread constraints or appropriate anti-affinity, use PodDisruptionBudgets for voluntary disruptions, and configure readiness/liveness probes.

I would use HPA for Pod scaling and Cluster Autoscaler for node capacity, ensuring minimum node capacity remains available across failure domains. The ingress path and stateful dependencies must also be zone resilient; otherwise a zone-resilient node pool doesn't make the application highly available.

The important point is:

> **AKS being configured for zones is only the infrastructure foundation; your Pods, storage, ingress, dependencies, and upgrade strategy must also respect those failure domains.**

Microsoft currently replicates the managed AKS control plane across multiple zones, while customer node pools can be configured as zone-spanning or zone-aligned. ([Microsoft Learn][4])

```text
                    Application Gateway / Ingress
                              │
                              ▼
                        AKS Cluster
                              │
        ┌─────────────────────┼────────────────────┐
        │                     │                    │
     Zone 1                Zone 2               Zone 3
        │                     │                    │
   System Node          System Node          System Node
   User Nodes           User Nodes           User Nodes
        │                     │                    │
      Pod A1                 Pod A2                Pod A3
        └─────────────────────┼────────────────────┘
                              │
                         HA Data Tier
```

---

## **1. Control plane**

AKS control plane components include:

```text
API server
scheduler
etcd
controllers
```

and are managed by Microsoft.

Current AKS documentation states that Microsoft replicates the control plane across multiple zones. ([Microsoft Learn][4])

So my primary responsibility is designing the **customer-managed node pools and workloads** correctly.

---

# **2. Create a zone-spanning system node pool**

For a three-zone region:

```text
System pool
├── Zone 1 node
├── Zone 2 node
└── Zone 3 node
```

Example:

```bash
az aks create \
  --resource-group rg-prod \
  --name aks-prod \
  --node-count 3 \
  --zones 1 2 3
```

The point is not the exact command; it proves we're explicitly creating a node pool across the failure domains.

Current AKS guidance supports zone-spanning pools and can balance nodes among selected zones. ([Microsoft Learn][4])

---

# **3. Separate system and user workloads**

I prefer:

```text
AKS
│
├── System Node Pool
│   ├── CoreDNS
│   ├── metrics-server
│   └── platform components
│
└── User Node Pool
    └── application workloads
```

Why?

Because application pressure should not starve:

```text
DNS
cluster agents
system components
```

of CPU/memory.

---

# **4. Spread user node pools across zones**

For example:

```text
User Pool
├── 2 nodes Zone 1
├── 2 nodes Zone 2
└── 2 nodes Zone 3
```

Current AKS supports both:

```text
zone-spanning node pools
```

and:

```text
zone-aligned node pools
```

Zone-spanning is a strong default for general HA workloads, while zone-aligned pools can provide more explicit zone-level scaling/control. ([Microsoft Learn][4])

---

# **5. Regional node pool is not enough**

If I omit zone configuration:

```text
nodes may exist somewhere in region
```

but Microsoft explicitly states a regional pool provides **no guarantee that instances are balanced across zones**. ([Microsoft Learn][4])

So for an explicit zone-failure requirement, I configure zones intentionally.

---

# **6. Multiple Pods aren't enough either**

Suppose:

```text
replicas = 3
```

but scheduler places:

```text
Zone 1:
Pod 1
Pod 2
Pod 3
```

Zone 1 failure:

```text
all replicas lost simultaneously
```

So I use topology spreading.

---

# **7. TopologySpreadConstraints**

Example:

```yaml
spec:
  replicas: 3
  template:
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: checkout
```

Conceptually:

```text
checkout-1 → Zone 1
checkout-2 → Zone 2
checkout-3 → Zone 3
```

AKS/Kubernetes exposes the zone through:

```text
topology.kubernetes.io/zone
```

and current AKS guidance specifically demonstrates topology spread across zones. ([Microsoft Learn][4])

---

# **8. Replicas must tolerate failure**

If I deploy:

```text
replicas = 2
```

across three zones, losing one may leave:

```text
1 replica
```

which might be enough or not.

For critical services I size replicas around:

```text
normal load
+
one-zone loss
+
maintenance headroom
```

rather than simply choosing `replicas: 3` because there are three zones.

---

# **9. Readiness probes are critical**

When a Pod can't serve traffic:

```text
readiness fails
      ↓
Pod removed from Service endpoints
      ↓
traffic goes to healthy Pods
```

Without proper readiness:

```text
Pod exists
but dependency isn't ready
      ↓
traffic still sent
      ↓
5xx
```

Availability is about **serving capability**, not process existence.

---

# **10. PodDisruptionBudget**

During planned node drains/upgrades:

```text
Node drain
    ↓
Pod eviction
```

A PDB can constrain how many replicas are voluntarily unavailable.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: checkout
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: checkout
```

Current AKS best-practice guidance recommends PDBs for replicated workloads during voluntary disruptions such as node drains. ([Microsoft Learn][5])

Important:

```text
PDB
does NOT stop hardware/zone failure
```

It governs voluntary evictions.

---

# **11. Don't make the PDB impossible**

Suppose:

```text
replicas = 1
minAvailable = 1
```

Node upgrade tries to drain.

Result:

```text
ALLOWED DISRUPTIONS = 0
```

and the drain can be blocked.

So I verify:

```bash
kubectl get poddisruptionbudgets -A
```

before upgrades.

Microsoft specifically warns that over-restrictive PDBs or insufficient replicas can block AKS drains. ([Microsoft Learn][5])

---

# **12. HPA handles application demand**

```text
Traffic ↑
  ↓
HPA
  ↓
3 Pods → 12 Pods
```

HPA does not add nodes.

---

# **13. Cluster Autoscaler handles node capacity**

If additional Pods can't schedule:

```text
HPA creates Pods
      ↓
Pods Pending
      ↓
Cluster Autoscaler
      ↓
new nodes
```

Current AKS documentation defines Cluster Autoscaler exactly around unschedulable Pods caused by resource constraints. ([Microsoft Learn][6])

# **14. Keep capacity for a zone outage**

Suppose:

```text
3 zones
10 nodes each
30 nodes total
```

and application consumes all 30 nodes at normal load.

Zone 1 disappears:

```text
20 nodes remain
```

If the application requires 28:

```text
HA fails
```

even though nodes were spread perfectly.

So design:

```text
capacity after one-zone loss
>= required critical workload capacity
```

or ensure fast scale-out into surviving zones, quota permitting.

---

# **15. Check quotas**

Cluster Autoscaler can't create:

```text
20 new VMs
```

if Azure says:

```text
regional vCPU quota exceeded
```

Before production:

```text
verify VM SKU
regional quota
zone capacity assumptions
```

Current AKS documentation even provides `az aks list-vm-skus` for checking zone/SKU support. ([Microsoft Learn][4])

---

# **16. Storage is a major hidden problem**

Stateful Pod:

```text
Pod → disk
```

may be spread across zones, but its storage behavior matters.

Current AKS documentation notes that Kubernetes 1.29+ default managed disk storage classes use zone-redundant storage for PVCs, while LRS disks remain zonal and cannot simply attach to a node in a different zone. ([Microsoft Learn][4])

So for stateful applications I explicitly review:

```text
StorageClass
replication
zone affinity
RPO/RTO
application-level replication
```

Do not assume Kubernetes replicas automatically make data HA.

---

# **17. Ingress must also survive zones**

For example:

```text
Application Gateway
or
Azure Standard Load Balancer + ingress
```

must remain available.

Current AKS docs state Standard Load Balancer distributes inbound traffic across zones and sends traffic to healthy nodes. ([Microsoft Learn][4])

Ingress-controller Pods themselves should also be:

```text
multiple replicas
+
spread across zones
```

---

# **18. Dependencies must be HA**

A perfect AKS platform:

```text
Zone 1 + 2 + 3
```

still fails if every Pod requires:

```text
single VM PostgreSQL
in Zone 1
```

So review:

```text
Database
Registry
Key Vault
Messaging
DNS
External APIs
```

as part of the same reliability design.

# **19. Upgrades**

During an AKS upgrade:

```text
surge node
      ↓
cordon/drain
      ↓
Pods rescheduled
```

I combine:

```text
PDB
topology spreading
multiple replicas
max surge
sufficient free capacity
```

so upgrades don't create an outage.

# **20. Verify zone distribution**

Azure-side:

```bash
az aks show \
  --resource-group rg-prod \
  --name aks-prod \
```

This proves which zones the pools are configured for.


```text

```

This proves the actual nodes' zone locations. Microsoft provides the same verification approach in current documentation. ([Microsoft Learn][4])

I would actually test:

and in an appropriate controlled environment simulate broader failure conditions.

Measure:


# **T32-13. Design an AKS platform where the Kubernetes API, nodes, database, registry, and Key Vault have no public exposure.**

**Answer:**

I would build a **private AKS platform with private data-plane dependencies and controlled management/egress paths**.

The AKS API server would use private-cluster mode, and for a strict requirement I would also disable its public FQDN. Nodes would live only on private VNet addresses with no node public IPs. Azure Container Registry, Key Vault, and the database would each be accessed using Private Endpoints with their public network access disabled.

Private DNS would resolve all service FQDNs to the corresponding private addresses. Cluster administrators and CI/CD agents would connect from a network with private reachability—such as a peered management VNet, VPN/ExpressRoute, Bastion-hosted management environment, or self-hosted CI runners.

For outbound traffic, I would either route AKS through Azure Firewall using UDRs and tightly allow required destinations, or, where the requirement is stricter, evaluate AKS Network Isolated Cluster capabilities.

```text
                   Corporate / Management Network
                         │
                  VPN / ExpressRoute
                         │
                         ▼
               ┌───────────────────┐
               │   Hub VNet        │
               │ Azure Firewall/DNS│
               └────────┬──────────┘
                        │ VNet peering
                        ▼
              ┌──────────────────────┐
              │      AKS VNet        │
              │                      │
```

# **T32-14. Design a multi-region Azure application capable of surviving a complete region failure.**

**Answer:**

I would design two **independent, zone-resilient regional stacks**, put a global traffic layer such as Azure Front Door in front of them, and ensure every critical dependency—not just compute—has a regional failover strategy.

For a low-RTO internet-facing workload, I would strongly consider active-active: both regions continuously serve production traffic, Front Door monitors both, and if one region fails it directs all new traffic to the healthy region.

Each regional stack must have enough capacity to handle full production load, and the data layer must support the required RPO through a suitable cross-region replication mechanism. For example, Azure SQL Database can use active geo-replication or failover groups; other data platforms require their own replication model.

I would also avoid automatic failback immediately after the primary recovers. I'd validate application health and data consistency before returning traffic because a region becoming reachable doesn't prove the entire stack is ready.

```text
                              Users
                                │
                                ▼
                     Azure Front Door + WAF
                         Health Probes
                        /             \
                       /               \
                      ▼                 ▼
                REGION A           REGION B
              ┌───────────┐       ┌───────────┐
              │ Zone 1-3  │       │ Zone 1-3  │
              │ App Stack │       │ App Stack │
              └─────┬─────┘       └─────┬─────┘
                    │                   │
                 Data A ◄────────────► Data B
                       replication
```

Current Microsoft guidance recommends multi-region architecture when workloads must tolerate a complete Azure region failure, and identifies Azure Front Door as the global delivery layer for web applications. ([Microsoft Learn][13])

---

## **1. Start with RTO and RPO**

First:

```text
Required RTO?
Required RPO?
```

Example:

```text
RTO = 2 minutes
RPO = < 1 minute
```

This almost certainly requires:

```text
pre-provisioned secondary region
+
continuous replication
+
automated traffic failover
```

Compare:

```text
RTO = 8 hours
RPO = 4 hours
```

which could support a much cheaper restore-based DR strategy.

Architecture follows recovery requirements.

---

# **2. Choose active-active or active-passive**

## **Active-active**

```text
Front Door
├── Region A
└── Region B
```

Both serve production.

Advantages:

```text
very low RTO
both regions continuously tested
capacity is actually used
```

Disadvantages:

```text
data complexity
higher baseline cost
cross-region consistency challenges
```

---

## **Active-passive**

```text
Front Door
      ↓
Region A active

Region B
ready but not receiving normal traffic
```

Advantages:

```text
simpler write model
potentially cheaper
```

Disadvantages:

```text
higher RTO
passive environment can drift
capacity scale-up may take time
```

Microsoft's current multi-region networking guidance makes the same distinction: active-active has the lowest RTO and continuously exercised paths, while active-passive is often preferable for strict write-region models or lower cost. ([Microsoft Learn][13])

For the question:

> “capable of surviving complete region failure”

I might propose:

```text

+
appropriately replicated data
```

because both regions already serve traffic.

Normal:

```text

50% B
```

Failure:

```text
0% A
100% B
```

No deployment needs to happen during the disaster.

# **4. Front Door performs global health routing**

```text
Front Door
   ↓
health probes
   ↓
Region A healthy?
Region B healthy?
```

If A fails:

```text
A removed from routing
      ↓

```

Microsoft's current App Service multi-region reference describes Front Door detecting an unhealthy regional origin and sending traffic only to the operational region. ([Microsoft Learn][3])

# **5. Health endpoint must be meaningful**

Bad health endpoint:

```text
/health
→ process running
→ 200
```

even though:

```text
database unavailable
```

Then Front Door thinks:

```text
Region healthy
```

while users fail.

Better health design:

```text
/liveness
→ process alive

/readiness or regional health
→ critical dependencies usable
```

The global health check should reflect whether that **region can safely serve production traffic**.

# **6. Each region should survive a zone failure too**

Architecture:

```text
Region A
├── Zone 1
├── Zone 2
└── Zone 3
```

same in B.

Why?

A zone failure should not unnecessarily trigger:

```text
cross-region DR
```

if the region still has healthy capacity.

So failure hierarchy:

```text
Instance failure
→ local redundancy

Zone failure
→ zone redundancy

Region failure
→ multi-region failover
```

---

# **7. Secondary capacity must handle 100%**

This is one of the biggest real-world failures.

Suppose:

```text
Region A = 50%
Region B = 50%
```

After A fails:

```text
Region B = 100%
```

So Region B needs:

```text
enough instances
or
fast autoscaling
+
sufficient quotas
```

Current Microsoft guidance explicitly says active-active regional stacks must be able to accept increased load during geo-failover. ([Microsoft Learn][3])

---

# **8. Pre-approve quotas**

Failover is the worst possible time to discover:

```text
vCPU quota exceeded
```

or:

```text
DB tier scale limit
```

So validate:

```text
compute quota
networking quota
database capacity
Public IP/load-balancer quotas if applicable
```

in both regions.

---

# **9. The data layer determines the real RPO**

Compute is easy:

```text
Deploy same image twice
```

Data is hard.

Suppose:

```text
Region A database
      ↓ async replication
Region B database
```

At failure, last replicated transaction is:

```text
20 seconds old
```

Then:

```text
RPO ≈ up to 20 sec
```

depending on actual replication guarantees and failure timing.

A zero-data-loss requirement is significantly harder.

```text

    ↓

    ↓
Azure SQL B
```

Microsoft's current SQL Database reliability guidance identifies active geo-replication and failover groups for cross-region resilience. ([Microsoft Learn][14])

I would choose between them based on:

```text

connection management
read/write model
```

rather than assume one feature solves every application.

# **11. Fail over data and application in the correct order**

Consider:

```text
Region A fails
```

If Front Door immediately sends writes to B but:

```text
Database B
still read-only
```

then:

```text
application 5xx
```

So failover orchestration must coordinate:

```text
1. Confirm primary failure
2. Establish/confirm secondary data authority
3. Verify application dependencies
4. Allow regional health endpoint
5. Route traffic
```

Depending on the data platform, some pieces can be automatic.

---

# **12. Avoid split brain**

Danger:

```text
DB A accepts writes
+
DB B accepts independent writes
```

without a data model designed for multi-write.

That can create:

```text
conflicting transactions
duplicate orders
lost updates
```

So choose either:

```text
single write-primary with failover
```

or a database explicitly designed for:

```text
multi-region writes
```

with well-understood consistency/conflict semantics.

> “I would build two independent, zone-resilient regional stacks and put Azure Front Door with WAF in front of them.
