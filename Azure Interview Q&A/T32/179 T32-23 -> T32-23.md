# **T32-23. Design infrastructure that allows outbound internet traffic only through a centralized firewall.**

**Answer:**

I would use a **hub-and-spoke network with Azure Firewall in the hub** and force every workload subnet to send its default route through the firewall.

Each spoke workload subnet would have a User Defined Route:

```text
0.0.0.0/0
    ↓
Virtual appliance
    ↓
Azure Firewall private IP
```

I would also remove alternative outbound paths such as workload public IPs or independent NAT Gateways in the spokes, use private subnets where appropriate, and control internet destinations through Azure Firewall application/network rules.

For high outbound connection volume, I would consider attaching **Azure NAT Gateway to `AzureFirewallSubnet`** so the firewall uses scalable, predictable SNAT addresses.

Then I'd prove the design by checking effective routes from workloads and verifying that their observed public source IP is one of the centralized firewall/NAT addresses.

Microsoft's current Azure networking guidance recommends exactly this centralized egress pattern: spoke workloads use a `0.0.0.0/0` UDR pointing to the hub firewall, replacing uncontrolled default outbound access. ([Microsoft Learn][1])

# **1. Put Azure Firewall in the hub**

The centralized firewall becomes the approved outbound control point.

```text
Spokes
   ↓
Hub
   ↓
Azure Firewall
   ↓
Internet
```

Advantages:

* one egress-policy boundary,
* consistent logging,
* centralized FQDN filtering,
* predictable public source IPs,
* easier auditing,
* application teams can't independently bypass security controls.

This is preferable to:

```text
Team A → Public IP
Team B → NAT Gateway
Team C → random proxy
Team D → default outbound
```

which creates inconsistent controls.

---

# **2. Force workload traffic with a UDR**

On each workload subnet:

```text
Address prefix: 0.0.0.0/0
Next hop type: Virtual appliance
Next hop: <Azure Firewall private IP>
```

Traffic flow becomes:

```text
VM / AKS node / workload
        ↓
effective route:
0.0.0.0/0
        ↓
Azure Firewall
        ↓
SNAT
        ↓
Internet
```

Microsoft's current egress design guidance explicitly recommends applying this default UDR to spoke workload subnets. ([Microsoft Learn][1])

---

# **3. Understand why the route wins**

Azure has system routes.

Without an explicit design, workloads may receive an outbound path depending on resource/subnet configuration.

By adding:

```text
0.0.0.0/0
→ Virtual appliance
```

I override the normal default route for internet-bound traffic.

So packets don't choose:

```text
Azure default internet path
```

but instead:

```text
Azure Firewall
```

---

# **4. Remove bypass paths**

This is just as important as adding the firewall route.

If a workload still has:

```text
public IP
```

or a separate uncontrolled egress design, my centralized architecture may not provide the security boundary I intended.

I would review:

```text
VM public IPs
AKS outbound configuration
NAT Gateways
public load-balancer outbound rules
App Service outbound architecture
other NVAs/proxies
```

and eliminate or explicitly govern alternate egress paths.

The requirement is:

> **Not merely “traffic can use the firewall,” but “internet traffic cannot bypass the firewall.”**

---

# **5. Private subnets strengthen the design**

For new Azure designs, I would prefer subnets that don't rely on implicit/default outbound connectivity.

Then the only explicitly configured outbound method is:

```text
UDR
→ firewall
```

Microsoft's current guidance notes that default outbound access is being phased out and recommends explicit outbound connectivity rather than relying on implicit public connectivity. ([Microsoft Learn][1])

---

# **6. Azure Firewall performs SNAT**

Outbound request:

```text
Source:
10.20.1.15

Destination:
api.vendor.com:443
```

Firewall receives it and sends it externally using an approved public address.

Conceptually:

```text
10.20.1.15
    ↓
Azure Firewall
    ↓ SNAT
20.x.x.x
    ↓
Internet
```

The external vendor sees:

```text
20.x.x.x
```

rather than the private workload IP.

This gives a stable allow-listable outbound identity.

---

# **7. NAT Gateway on AzureFirewallSubnet for high SNAT scale**

A centralized firewall serving hundreds of workloads can create many outbound connections.

A risk is:

```text
SNAT port exhaustion
```

particularly with high connection counts to internet destinations.

Microsoft's current centralized-egress guidance recommends NAT Gateway on `AzureFirewallSubnet` for scalable SNAT and predictable public egress IPs. ([Microsoft Learn][1])

Architecture:

```text
Spokes
  ↓
Azure Firewall
  ↓
NAT Gateway
  ↓
Internet
```

Important:

```text
NAT Gateway
```

is attached to the **firewall subnet**, not independently to every workload spoke if the goal is centralized inspection.

---

# **8. Use application rules for FQDN-based control**

Suppose payment workload only needs:

```text
api.stripe.com
packages.microsoft.com
```

I would prefer rules such as:

```text
Source:
Payments subnet

Protocol:
HTTPS

Destination:
approved FQDNs
```

rather than:

```text
Payments subnet
→ Internet
→ Any
```

Application rules are useful for HTTP/HTTPS FQDN filtering.

---

# **9. Network rules for non-HTTP protocols**

Some workloads may require:

```text
NTP
specific TCP/UDP destinations
DNS depending architecture
```

Then Azure Firewall network rules are more appropriate.

The rule type follows the traffic.

---

# **10. Default deny**

My rule philosophy:

```text
Known required destination
→ ALLOW

Unknown internet destination
→ DENY
```

not:

```text
Allow internet
and log everything
```

For initial migrations, broader rules may temporarily be necessary to discover dependencies, but I would tighten them afterward. Microsoft's current migration guidance specifically suggests gradually tightening outbound rules after required destinations are understood. ([Microsoft Learn][1])

---

# **11. DNS must also be designed**

If firewall application rules depend on FQDNs:

```text
application
   ↓
DNS
   ↓
destination IP
```

needs to work consistently.

In enterprise hub/spoke designs I may use:

```text
Azure DNS Private Resolver
or
approved custom DNS
```

for centralized resolution.

DNS failure can look like firewall failure even when routing is correct.

---

# **12. AKS needs special consideration**

Suppose AKS is in a spoke.

I might configure:

```text
AKS
outboundType = userDefinedRouting
```

with:

```text
node subnet
0.0.0.0/0
→ Azure Firewall
```

so AKS does not create an independent managed outbound route that bypasses the intended network architecture.

But I must ensure required AKS/Azure dependencies remain reachable through the firewall policy.

Otherwise:

```text
Pods cannot pull images
nodes cannot reach required services
cluster operations fail
```

---

# **13. PaaS workloads need their outbound architecture considered separately**

A UDR on a VM subnet doesn't magically govern every PaaS service.

For example:

```text
App Service
```

needs:

```text
VNet Integration
+
route-all design where required
```

if I want its outbound application traffic forced into the VNet/firewall architecture.

So for each compute type I ask:

> Does the service actually inject outbound traffic into the subnet that contains my UDR?

---

# **14. Hybrid routing needs care**

Suppose the hub also has:

```text
ExpressRoute
```

and receives:

```text
0.0.0.0/0
```

from on-premises via BGP.

Now the firewall itself could learn an unexpected default route.

Microsoft's hybrid-firewall guidance specifically warns about default routes learned through BGP and describes maintaining the appropriate direct internet or forced-tunneling configuration depending on the intended architecture. ([Microsoft Learn][2])

So route propagation needs deliberate design.

---

# **15. Forced tunneling can mean two different requirements**

There are two common patterns.

### Centralize Azure egress through Azure Firewall

```text
Spoke
  ↓
Azure Firewall
  ↓
Internet
```

### Force even firewall internet traffic through on-premises

```text
Spoke
  ↓
Azure Firewall
  ↓
ExpressRoute/VPN
  ↓
On-premises security appliance
  ↓
Internet
```

The latter is generally called **forced tunneling** in the stricter hybrid sense.

I would clarify which security requirement the organization has.

---

# **16. Don't accidentally create asymmetric routing**

Suppose outbound traffic:

```text
Spoke
→ Firewall
→ Internet
```

but return traffic follows some unrelated direct path.

A stateful firewall expects symmetric flows.

Similarly, directly peered VNet traffic can follow system peering routes unless more-specific UDRs are provided for east-west inspection. Microsoft's firewall routing documentation calls out the need for explicit routes when forcing directly connected subnet/spoke traffic through the firewall. ([Microsoft Learn][2])

# **17. Verify effective routes**

For a VM NIC I would inspect:

```bash
az network nic show-effective-route-table \
  --resource-group rg-app \
  --name nic-app01 \
  --output table
```

I'm looking for:

```text
0.0.0.0/0
NextHopType = VirtualAppliance
NextHopIP   = <firewall-private-IP>
```

If I see:

```text
NextHopType = Internet
```

for the winning default route, my centralized-egress design is not being enforced as expected.

---

# **18. Verify actual egress IP**

From the workload, make a controlled outbound request to an endpoint that reports source IP.

Expected:

```text
Observed source
=
Azure Firewall/NAT Gateway public IP
```

If different workloads show:

```text
unexpected public IPs
```

I investigate bypass paths.

---

# **19. Verify firewall logs**

I want evidence like:

```text
Source: 10.20.1.15
Destination: api.vendor.com
Action: Allow
Rule collection: ApprovedSaaS
```

and for an unauthorized destination:

```text
Action: Deny
```

Then centralize logs in:

```text
Azure Monitor / Log Analytics
```

and alert on unusual denied/allowed patterns as appropriate.

---

# **20. Use Azure Policy as a guardrail**

At enterprise scope, policy can help prevent drift such as:

```text
unexpected public IPs
unapproved networking resources
missing diagnostics
```

while the actual network path is still enforced primarily through:

```text
routing
+
firewall
+
resource architecture
```

Policy complements the design.

## **Troubleshooting example: VM has no internet after enforcing firewall**

Dependency order:

```text
VM
 ↓
DNS
 ↓
Effective route
 ↓
Azure Firewall
 ↓
Firewall rule
 ↓
SNAT
 ↓
Internet
```

### Step 1 — DNS

```bash
nslookup packages.microsoft.com
```

If resolution fails:

```text
DNS problem
```

not necessarily firewall routing.

### Step 2 — Route

Check effective routes.

Expected:

```text
0.0.0.0/0 → Firewall
```

### Step 3 — Firewall logs

If:

```text
DENY
```

then rule/policy is the issue.

If no firewall log appears:

```text
traffic probably never reached firewall
```

so investigate routing/NSG.

### Step 4 — SNAT

If firewall allows the request but connections fail intermittently at very high scale:

```text
SNAT exhaustion
```

becomes a candidate.

# **T32-24. Design a platform where developers cannot manually change production infrastructure.**

**Answer:**

I would make **Git and an approved deployment pipeline the normal production control plane**, while human developers have either Reader access or no direct write access to production Azure resources.

The production CI/CD identity would receive the narrow Azure permissions required to deploy infrastructure, authenticated through OIDC/workload identity federation rather than a client secret. Developers would propose Terraform/Bicep changes through pull requests, required reviewers and automated validation; after approval, the pipeline performs the production deployment.

For emergencies, I would use **PIM-based time-limited elevation** for a tightly controlled break-glass/operator group rather than permanent Contributor or Owner access.

I would also use Azure Policy to enforce architectural guardrails and detect or deny prohibited configurations. I would **not rely primarily on resource locks**, because a ReadOnly lock would block the deployment pipeline as well as humans.

The model is:

```text
Developer
   ↓
Git PR
   ↓
Review + checks
   ↓
Approved CI/CD identity
   ↓
Terraform/Bicep
   ↓
Azure Production

Developer → Azure Prod directly
           ↓
        Reader only
```

# **1. Remove standing production write access**

Developers:

```text
Dev
→ Contributor

Production
→ Reader
or
→ no direct access
```

This is the strongest simple control.

If a developer opens Azure Portal and tries:

```text
Delete VM
Change NSG
Create Public IP
Resize database
```

Azure RBAC denies the operation.

The requirement is enforced at the authorization layer—not by asking people politely not to use the portal.

---

# **2. Do not give developers Owner**

Remember:

```text
Contributor
→ manage resources

Owner
→ manage resources
  + grant RBAC
```

For production, even Contributor should not normally be permanently assigned to application developers if infrastructure changes are meant to be pipeline-only.

Standing Owner should be especially rare.

---

# **3. Give deployment rights to a non-human identity**

Production Terraform pipeline:

```text
GitHub Actions / Azure DevOps
       ↓
OIDC / Workload Identity Federation
       ↓
Microsoft Entra identity
       ↓
limited Azure role
       ↓
Prod scope
```

For example:

```text
infra-prod identity
→ Contributor
→ only workload production subscription/RG
```

or an appropriate custom role if Contributor is broader than required.

The identity should not automatically have:

```text
Owner
User Access Administrator
Global permissions
```

unless the deployment genuinely manages role assignments and that authority is deliberately designed.

---

# **4. Git becomes the requested state**

Infrastructure changes:

```text
Developer
   ↓
edit Terraform
   ↓
PR
```

not:

```text
Developer
   ↓
Portal
   ↓
click Edit
```

PR contains:

```text
exact diff
reason
ticket/change reference if needed
review history
```

This gives an auditable desired state.

# **5. Require peer review**

Production branch:

```text
Protected
```

Require:

```text
PR
required reviewer(s)
CI checks
no direct push
CODEOWNERS/platform approval where appropriate
```

Example:

```text
networking/*.tf
→ Network Platform team review

security/*.tf
→ Security review

app infrastructure
→ Application/platform review
```

The approval model should reflect risk.

# **6. Pipeline runs validation before apply**

Typical:

```text
terraform fmt -check
      ↓
terraform validate
      ↓
security/policy checks
      ↓
terraform plan
      ↓
publish reviewed plan
      ↓
approval
      ↓
terraform apply
```

For production I would ideally apply the reviewed plan artifact rather than silently generate a completely new plan after approval if the pipeline/tooling supports that workflow safely.

That prevents:

```text
reviewed change A
but
different change B applied
```

because the branch changed in between.

# **7. Production approval belongs outside the code being deployed**

If a developer can modify:

```yaml
approvalRequired: false
```

inside the same PR and thereby remove the production approval, the control is weak.

I want production protection enforced by:

```text
GitHub Environment
Azure DevOps Environment/checks
protected pipeline templates
repository governance
```

that the normal developer cannot bypass through the workload PR.

Microsoft's current Terraform/GitHub sample explicitly recommends governed pipeline templates and Production environment approval controls for production deployments. ([Microsoft Learn][3])

---

# **8. Separate Dev and Prod identities**

Avoid:

```text
one pipeline identity
→ Contributor everywhere
```

Use:

```text
terraform-dev
→ Dev subscription

terraform-stage
→ Stage subscription

terraform-prod
→ Prod subscription
```

Then compromise of the Dev pipeline doesn't automatically mean production access.

---

# **9. Use OIDC rather than stored secrets**

Production pipeline:

```text
GitHub
  ↓
OIDC
  ↓
Entra
  ↓
short-lived Azure token
```

rather than storing:

```text
ARM_CLIENT_SECRET
```

for months.

This reduces credential leakage and rotation risk.

---

# **10. Azure Policy provides guardrails**

Even the approved Terraform pipeline can contain a bad change.

Examples:

```text
Create public Storage Account
Deploy resource in prohibited region
Create unapproved public IP
Disable required security setting
```

Azure Policy can:

```text
Deny
Audit
Modify
DeployIfNotExists
```

depending on policy type.

So:

```text
Git review
```

is one control,

and:

```text
Azure Policy
```

is another independent control.

Defense in depth.

---

# **11. Policy does not generically mean “pipelines allowed, humans denied”**

This distinction matters.

Azure Policy generally evaluates the **resource/request configuration**, not:

```text
"Was this click done through Portal?"
```

So I would not try to make Policy the primary mechanism differentiating:

```text
human vs pipeline
```

That is primarily:

```text
Azure RBAC
+
identity separation
```

Policy controls **what configurations are allowed**, regardless of who requested them.

---

# **12. Resource locks are not the primary solution**

You might think:

```text
ReadOnly lock on Production
```

would stop manual changes.

It would.

But it would also stop:

```text
Terraform pipeline changes
```

because resource locks apply to authorized control-plane requests broadly.

Similarly:

```text
CanNotDelete
```

is useful for protecting critical resources from deletion, but doesn't prevent normal modifications.

So locks are useful for selected critical resources, not as the general “humans cannot modify Prod but pipeline can” mechanism.

---

# **13. Azure Policy `denyAction` has a specific scope**

Current Azure Policy supports a `denyAction` effect, but currently its supported action is **DELETE**. It can block applicable delete operations and returns `403`. ([Microsoft Learn][4])

Therefore:

```text
denyAction
```

is not a generic mechanism for preventing every kind of manual modification.

This is why RBAC remains the main boundary.

# **14. PIM for emergency access**

There will eventually be a scenario like:

```text
SEV-1
pipeline unavailable
urgent production fix required
```

I don't want the security model to force engineers to share credentials.

Instead:

```text
Engineer
   ↓
PIM activation request
   ↓
MFA
justification
approval if required
time limit
   ↓
temporary production Contributor
```

Then after the incident:

```text
role expires
```

and manual changes must be reconciled into Git.

---

# **15. Break-glass is not normal operations**

Emergency access should be:

```text
rare
logged
alerted
reviewed afterward
```

If PIM is activated every day because:

```text
pipeline is inconvenient
```

the platform design has failed operationally.

# **16. Detect drift**

Even with strong controls, drift can happen through:

```text
emergency PIM
platform admins
Azure service behavior
legacy automation
```

So run:

```text
terraform plan
```

periodically against production.

Expected:

```text
No changes.
```

If:

```text

```

appears without a Git change, investigate.

# **17. Decide how to resolve drift**

Suppose someone changed:

```text
NSG rule
```

during an incident.

Terraform later says:

```text
Azure actual
!=
Git desired
```

Do not automatically overwrite it.

First ask:

```text
Was the manual change valid?
```

If yes:

```text
update Terraform
review
apply
```

If no:

```text
Terraform returns Azure to desired state
```

Git must eventually represent reality.

---

# **18. Activity Logs provide audit evidence**

Azure Activity Log can show:

```text
who changed resource?
which operation?
when?
result?
```

So manual production writes should generate monitoring signals.

For example:

```text
Caller != approved deployment identity
AND
operation is write/delete
AND
scope = Production
```

could be surfaced for investigation.

That helps detect privileged bypass.

---

# **19. Protect the state backend separately**

Even if developers can't modify Azure resources directly, somebody who can alter:

```text
Terraform state
```

can create dangerous future plans.

Therefore state storage needs:

```text
least-privilege RBAC
private networking where appropriate
versioning/backup
audit logs
locking
```

and developers should not broadly have direct production-state write access.

---

# **20. Protect pipeline code**

Another subtle attack path:

```text
Developer cannot change Prod Azure
but
Developer can directly edit Production pipeline
```

Then they could make the pipeline do anything its identity can do.

Therefore:

```text
pipeline templates
workflow files
environment protection
CODEOWNERS
```

need strong review rules.

Security of the deployment path matters just as much as Azure RBAC.

# **T32-25. Design a Terraform workflow for several teams and multiple Azure subscriptions.**

**Answer:**

I would design Terraform around **small, independently deployable root configurations with separate state and identities**, rather than one giant state file controlling every team and every Azure subscription.

The platform team would own reusable versioned modules for standard capabilities such as VNets, AKS, monitoring, Key Vault, and landing-zone components. Application teams would consume those modules from workload-specific root configurations.

Each production workload/environment would normally have its **own remote Azure Storage state key or backend boundary**, and CI/CD would authenticate using OIDC/workload identity federation. A pipeline for Team A should have permission only to Team A's subscription or resource scope, while Team B gets a separate identity.

For cross-subscription deployments inside one root module I can use **AzureRM provider aliases**, but I would use them only when those resources genuinely belong to one lifecycle. I would not combine unrelated subscriptions into one state merely because Terraform technically can.

Workflow:

```text
Team change
   ↓
PR
   ↓
fmt + validate
   ↓
security/policy tests
   ↓
terraform plan
   ↓
peer/platform review
   ↓
environment approval
   ↓
OIDC authentication
   ↓
terraform apply
   ↓
separate Azure subscription/state
```

Two different authorization paths.

# **7. Azure Blob backend locking**

Pipeline A:

```text
terraform apply
```

acquires the backend lock.

Pipeline B attempts another operation against the same state:

```text
lock error
```

This is desirable.

HashiCorp states that the AzureRM backend uses Azure Blob native capabilities for **state locking and consistency checking**. ([HashiCorp Developer][5])

I would not bypass that lock unless I had proven the previous operation is dead and understand the consequences.

Backend locking prevents simultaneous state mutation, but waiting until apply time to discover concurrency is not ideal.

I'd also configure:

```text

```

at the pipeline level.

Microsoft's current production Terraform/GitHub example similarly uses workflow concurrency controls to prevent parallel deployments. ([Microsoft Learn][3])

# **T33-01. Your production deployment fails halfway through; what do you do?**

**Answer:**

My first priority is to **stop the rollout from increasing customer impact**, establish exactly what portion of the deployment succeeded, and decide quickly whether rollback or fix-forward is safer.

I would not immediately rerun the pipeline, because a halfway failure means production may now be in a mixed state: some Pods or VMs might run the new version, configuration may have changed, and a database migration may already have executed.

I would check user-facing health first—5xx rate, latency and critical transactions—then inspect the deployment controller and pipeline to determine what completed and what failed.

If the previous version is known-good and the change is safely reversible, I would rollback. If the deployment contains an irreversible or backward-incompatible database change, blindly rolling the application back could make the incident worse, so I may need to fix forward or restore/reconcile the data layer.

After service is stable, I would preserve evidence, find why partial deployment was possible, and improve the pipeline with progressive delivery, health gates, idempotency and automatic rollback where appropriate.

My incident sequence is:

```text
Deployment fails
      ↓
STOP further rollout
      ↓
Measure customer impact
      ↓
Identify actual partial state
      ↓
Rollback safe?
   /             \
 Yes              No
 ↓                 ↓
Rollback       Fix forward /
known-good     data recovery
      \             /
       ↓           ↓
       Validate service
             ↓
        Monitor closely
             ↓
             RCA
```

---

## **1. Stop making the situation worse**

Suppose deployment is:

```text
10 instances
```

and:

```text
4 updated successfully
5 old version
1 failed
```

I don't want the pipeline continuing blindly toward:

```text
10 broken instances
```

So first:

```text
pause rollout
cancel deployment if appropriate
stop automated promotion
```

while preserving enough evidence to understand what happened.

---

# **2. Confirm whether users are actually affected**

Check:

```text
availability
5xx
p95/p99 latency
critical transaction success
```

Possible cases:

### Case A

```text
Deployment failed
but
users unaffected
```

Maybe new Pods never became Ready and Kubernetes continued routing to the old replicas.

### Case B

```text
Deployment failed
and
20% users getting 5xx
```

Now it's a production incident.

The urgency and response differ.

---

# **3. Establish the deployment model**

I need to know whether it was:

```text
Rolling
Blue-green
Canary
GitOps
VM deployment
App Service slot
Terraform/IaC
```

because “halfway” means different things.

For rolling deployment:

```text
old + new versions coexist
```

For blue-green:

```text
new environment may be incomplete
but old still available
```

For Terraform:

```text
some Azure resource operations may already be committed
```

There's no universal transactional rollback across an entire deployment.

---

# **4. Identify the actual running versions**

For AKS:

```bash
kubectl get deployments
kubectl get replicasets
kubectl get pods -o wide
```

I'm looking for:

```text
Desired replicas
Updated replicas
Available replicas
old ReplicaSet
new ReplicaSet
Pod states
```

Then:

```bash
kubectl rollout status deployment/checkout
```

tells me whether the Kubernetes rollout has completed, is progressing, or is stuck.

---

# **5. Inspect the failing Pods**

If new Pods fail:

```bash
kubectl describe pod <pod>
kubectl logs <pod>
```

Interpret:

### `ImagePullBackOff`

```text
image/registry/authentication/network
```

### `CrashLoopBackOff`

```text
application starts then repeatedly fails
```

### Readiness failed

```text
process may run
but isn't safe to receive traffic
```

### `Pending`

```text
scheduling/capacity/placement
```

This immediately narrows the failure domain.

---

# **6. Check deployment events and pipeline step**

Ask:

```text
Which exact stage failed?
```

For example:

```text
Build        PASS
Push image   PASS
DB migration PASS
Deploy       PARTIAL
Health check FAIL
```

This is very different from:

```text
DB migration FAIL
before application changed
```

The completed stages determine rollback safety.

---

# **7. Compare the new and old versions**

Check:

```text
image digest
configuration
ConfigMaps
Secrets references
environment variables
feature flags
database schema assumptions
```

A common failure:

```text
new app
expects new env variable
```

but production config didn't contain it.

Another:

```text
new image expects DB schema v12
but migration stopped at v11
```

The partial-state boundary matters.

---

# **8. Decide rollback versus fix-forward**

I use several factors:

```text
Customer impact
Rollback safety
Time to repair
Data/schema changes
Confidence in diagnosis
Blast radius
```

### Rollback when

```text
previous version known healthy
change reversible
rollback fast
customer impact active
```

### Fix-forward when

```text
rollback unsafe
data already transformed
issue understood
repair faster than rollback
```

The goal is:

```text
restore service safely
```

not ideological loyalty to rollback.

# **9. Kubernetes rollback**

If Kubernetes Deployment rollback is safe:

```bash
kubectl rollout history deployment/checkout
```

shows rollout revisions.

Then potentially:

```bash
kubectl rollout undo deployment/checkout
```

Expected:

```text
Deployment returns
to previous ReplicaSet/template
```

Afterward:

```bash
kubectl rollout status deployment/checkout
```

and monitor actual application health.

But if using GitOps, I would prefer to restore the desired version in Git so Git remains the source of truth.

---

# **10. GitOps rollback**

If Argo CD owns production:

Bad long-term response:

```text
kubectl rollout undo
```

while Git still says:

```text
bad version
```

Argo may reconcile it back.

Better:

```text
GitOps repo
bad digest
   ↓
revert
   ↓
known-good digest
   ↓
Argo sync
```

In a severe incident an emergency manual change may be justified, but Git must be reconciled immediately afterward.

# **11. Database migration changes everything**

Suppose deployment sequence:

```text
1. DB schema migration
2. Application rollout
```

Migration executes:

```sql
DROP COLUMN legacy_status;
```

Then app deployment fails halfway.

Old version still requires:

```text
legacy_status
```

Blind rollback:

```text
new → old
```

could now break every Pod.

This is why database changes should preferably be backward compatible around deployment boundaries.

---

# **12. Expand-and-contract reduces this risk**

Safer sequence:

### Release A

```text
Add new column
Old app still works
```

### Release B

```text
New app writes old + new
```

### Release C

```text
Readers migrated
```

### Later

```text
Remove old column
```

Then application rollback during early phases remains much safer.

This is **expand-and-contract**.

---

# **13. Configuration changes also need rollback**

Suppose pipeline already changed:

```text
Key Vault secret reference
feature flag
App Configuration
network rule
```

Rolling back only the container image may not restore the old runtime behavior.

I need to inventory:

```text
code
configuration
schema
infrastructure
feature flags
```

that changed in the release.

A deployment is often more than one artifact.

---

# **14. Don't simply rerun the whole pipeline**

Why is this dangerous?

Suppose initial pipeline:

```text
Step 1 create DB migration
→ succeeded

Step 2 modify infrastructure
→ succeeded

Step 3 deploy app
→ failed
```

Blind rerun might:

```text
rerun migration
re-trigger destructive script
produce duplicate side effects
```

Pipeline steps should be:

```text
idempotent
```

where practical.

Before rerun I need to know which stages are safe to execute again.

---

# **15. Health probes can contain a failed rollout**

Good Kubernetes rollout:

```text
New Pod starts
    ↓
readiness fails
    ↓
never receives traffic
```

Old healthy replicas continue serving users.

That's much safer than:

```text
Pod process starts
    ↓
marked Ready immediately
    ↓
traffic sent
    ↓
5xx
```

Deployment safety depends heavily on meaningful readiness checks.

---

# **16. Maintain enough old capacity**

During rolling deployment:

```text
new Pods
```

should not replace all old healthy instances before proving themselves.

Tune:

```text
maxUnavailable
maxSurge
```

according to capacity and availability needs.

For example:

```yaml
strategy:
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

can preserve old capacity during cautious rollouts, though it requires enough cluster resources for the surge.

# **17. Progressive deployment makes halfway failure smaller**

Instead of:

```text
100% production
→ new version
```

use:

```text

 ↓
health
 ↓
25%
 ↓
health
 ↓
50%
 ↓
100%
```

If new version fails at 5%:

```text
95% users
still on known-good version
```

Much smaller blast radius.

### **Interview answer condensed**

> “If a production deployment failed halfway, I would first stop further rollout and measure user impact. Then I'd establish exactly what changed—how many instances are on the new version, which pipeline stages completed, whether configuration or database migrations already ran, and whether the old version is still safe. If the previous release is known-good and the deployment is reversible, I'd rollback quickly; on AKS I'd inspect rollout status/history and, in GitOps, revert the desired image in Git rather than create long-lived manual drift. **Stop the blast radius, establish the exact partial state, then choose rollback or fix-forward based on what is actually reversible.**

Never assume **“deployment failed = rerun pipeline”** or **“deployment failed = rollback app”**—a partially applied database/configuration change can make both actions dangerous.
