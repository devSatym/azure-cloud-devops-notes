# **T32-19. Design secretless authentication from AKS workloads to Azure services.**

**Answer:**

I would use **Microsoft Entra Workload ID for AKS** so individual Pods can authenticate to Azure services without storing service-principal client secrets, certificates, or Azure access keys inside Kubernetes.

I would enable the AKS OIDC issuer and Workload Identity, create a Kubernetes ServiceAccount for each workload identity boundary, create or select a user-assigned managed identity, and configure a **federated identity credential** that trusts only the specific Kubernetes namespace and ServiceAccount.

The Pod receives a projected Kubernetes service-account token. Microsoft Entra validates that token against the AKS OIDC issuer, exchanges it for a short-lived Azure access token, and the application uses that token to call services such as Key Vault, Storage, or Cosmos DB.

I would then grant the Azure identity only the required data-plane permissions—for example `Storage Blob Data Reader` on one Storage Account or the appropriate Key Vault secret role—not broad subscription Contributor access.

```text
AKS Pod
   │
   │ uses Kubernetes ServiceAccount
   ▼
Projected ServiceAccount token
   │
   │ signed by AKS OIDC issuer
   ▼
Microsoft Entra ID
   │
   │ validates federated trust
   ▼
Short-lived Azure access token
   │
   ├────► Key Vault
   ├────► Storage
   ├────► Cosmos DB
   └────► other Entra-protected service
```

Microsoft currently recommends Microsoft Entra Workload ID for Pod-to-Azure authentication; it uses projected Kubernetes service-account tokens federated to an Entra application or user-assigned managed identity and avoids storing Azure credentials in the cluster. ([Microsoft Learn][1])

## **1. Understand the identities involved**

An AKS cluster can have several different identities.

```text
AKS cluster identity
→ Azure control-plane operations

Kubelet identity
→ node/kubelet operations such as ACR pulls

Workload identity
→ application Pod accessing Azure resources
```

These should not be confused.

If my checkout Pod needs to read a Key Vault secret:

```text
checkout Pod
```

should not simply reuse:

```text
AKS cluster identity
```

or:

```text
kubelet identity
```

with broad permissions.

It should have its own workload identity boundary. Microsoft distinguishes these identities explicitly; the kubelet identity is used for node-level operations such as registry authentication, while Workload ID is for Pods accessing Entra-protected resources. ([Microsoft Learn][1])

# **2. Enable the AKS OIDC issuer and Workload Identity**

For AKS Standard, conceptually:

```bash
az aks update \
  --resource-group rg-prod \
  --name aks-prod \
  --enable-oidc-issuer \
  --enable-workload-identity
```

On a new cluster the options can be enabled during creation.

The OIDC issuer is important because Microsoft Entra needs a trusted way to verify that:

```text
this Kubernetes token
really came from
this AKS cluster
```

Current AKS documentation says Workload ID requires the AKS OIDC issuer; AKS Automatic includes these capabilities as defaults, while Standard clusters may require explicit configuration depending on cluster state/version. ([Microsoft Learn][2])

---

# **3. Obtain the issuer**

For example:

```bash
az aks show \
  --resource-group rg-prod \
  --name aks-prod \
  --query "oidcIssuerProfile.issuerUrl" \
  -o tsv
```

This produces an issuer URL.

Microsoft Entra uses its discovery/JWKS endpoints to validate the cryptographic signature of the Kubernetes service-account token. ([Microsoft Learn][3])

The flow internally is:

```text
AKS signs ServiceAccount token
          ↓
Token says:
issuer = AKS OIDC issuer
subject = system:serviceaccount:payments:checkout
audience = Azure token exchange
          ↓
Entra retrieves issuer signing keys
          ↓
Valid signature?
          ↓
Federated trust matches?
          ↓
Azure token issued
```

Suppose the checkout service needs Key Vault.

Create:

```text
User Assigned Managed Identity
name: mi-checkout-prod
```

Then grant only what it needs.

Example conceptually:

```text
mi-checkout-prod
      ↓

      ↓

```

Not:

```text
mi-checkout-prod
      ↓
Owner
      ↓
Production subscription
```

Workload Identity solves **authentication**, but Azure RBAC or service-specific permissions still define **authorization**.

# **5. Create a Kubernetes ServiceAccount**

For example:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: checkout
  namespace: payments
  annotations:
    azure.workload.identity/client-id: "<managed-identity-client-id>"
```

Current AKS documentation uses the `azure.workload.identity/client-id` ServiceAccount annotation to associate the Kubernetes identity with the intended Microsoft Entra identity. ([Microsoft Learn][3])

# **6. Create the federated identity credential**

The critical binding is:

```text
Issuer
=
AKS OIDC issuer

Subject
=
system:serviceaccount:payments:checkout

Audience
=
api://AzureADTokenExchange
```

Conceptually:

```text
Entra managed identity
     trusts
ONLY
ServiceAccount "checkout"
inside namespace "payments"
from this AKS issuer
```

This is much stronger than:

```text
Every Pod in the cluster
→ one shared credential
```

The federation model specifically uses issuer, subject, and audience to establish the trust relationship. ([Microsoft Learn][4])

# **7. Pod configuration**

The Pod should use the ServiceAccount and include the required Workload Identity label:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
spec:
  template:
    metadata:
      labels:
        azure.workload.identity/use: "true"
    spec:
      serviceAccountName: checkout
      containers:
      - name: checkout
        image: myacr.azurecr.io/checkout:v42
```

Current AKS documentation states that `azure.workload.identity/use: "true"` is required on Pods using Workload ID so the admission webhook injects the necessary projected token and Azure environment information. ([Microsoft Learn][3])

# **8. What gets injected?**

The Workload Identity webhook arranges for the Pod to receive a projected token and supporting environment configuration.

Conceptually:

```text
Pod
├── AZURE_CLIENT_ID
├── AZURE_TENANT_ID
└── AZURE_FEDERATED_TOKEN_FILE
```

Then an Azure Identity SDK can use:

```text

```

or the appropriate workload identity credential flow.

The SDK exchanges the projected Kubernetes token for an Entra access token.

The important point:

```text
Pod does NOT receive
managed identity password
```

because no password exists.


# **13. Private networking is separate too**

Suppose Key Vault has:

```text
Public network access = Disabled
```

and uses:

```text
Private Endpoint
```

The Pod needs **both**:

```text
Network:
Pod → Private DNS → Private Endpoint → Key Vault

Identity:
Pod → Workload ID → Entra token → Key Vault permission
```

If networking fails:

```text
timeout
```

Workload Identity won't fix it.

If identity/authorization fails:

```text
401 / 403
```

network connectivity may be perfectly healthy.

# **14. Troubleshooting flow**

Symptom:

> Pod cannot access Key Vault.

I troubleshoot in this order:

```text
Pod
 ↓
ServiceAccount
 ↓
Workload Identity mutation
 ↓
OIDC federation
 ↓
Entra token
 ↓
DNS/network
 ↓
Key Vault authorization
```

### Check ServiceAccount

```bash
kubectl get sa checkout -n payments -o yaml
```

Expected:

```text
azure.workload.identity/client-id
```

matches the intended managed identity.

---

### Check Pod label

```bash
kubectl get pod <pod> -n payments -o yaml
```

Expected:

```text
azure.workload.identity/use: "true"
```

Without it, the expected Workload Identity mutation doesn't occur. ([Microsoft Learn][3])

---

### Check federated credential subject

Expected exactly:

```text
system:serviceaccount:payments:checkout
```

A trust for:

```text
system:serviceaccount:default:checkout
```

will not match.

Namespace is part of the security identity.

---

### If token acquisition fails

Investigate:

```text
issuer
subject
audience
client ID
OIDC configuration
```

This is the **federation/authentication** layer.

---

### If token works but Key Vault returns 403

Move to:

```text
Azure RBAC / Key Vault permissions
```

because authentication likely succeeded.

---

### If request times out

Move to:

```text
Private DNS
Private Endpoint
NSG
UDR
Azure Firewall
```

not RBAC.

That is worth stating in a modern Azure interview.

### **Interview answer condensed**

> “I would use Microsoft Entra Workload ID. I'd enable the AKS OIDC issuer and Workload Identity, create a dedicated Kubernetes ServiceAccount for each workload identity boundary, create a user-assigned managed identity, and add a federated credential that trusts exactly that AKS issuer plus the `system:serviceaccount:<namespace>:<serviceaccount>` subject. The Pod gets a projected service-account token, Entra verifies it through OIDC and exchanges it for a short-lived Azure token. I'd then give the managed identity only the required data-plane role, such as Key Vault Secrets User or Storage Blob Data Contributor. No client secret is stored in Kubernetes. Workload Identity solves **authentication**, not networking or authorization—a Pod can authenticate successfully and still receive 403 because its Azure role is insufficient.

AKS Workload Identity, OIDC issuer, ServiceAccount, federated identity credential, user-assigned managed identity, projected token, Entra ID, Azure RBAC.

# **T32-20. Design centralized monitoring for VMs, AKS, PaaS applications, and databases.**

**Answer:**

I would build the monitoring platform around **Azure Monitor**, with Log Analytics for centralized logs, Azure Monitor Metrics for platform metrics, Application Insights/OpenTelemetry for application telemetry, Azure Monitor Agent and Data Collection Rules for VM guest telemetry, and the AKS monitoring integrations for Kubernetes.

I would standardize resource diagnostic settings through Azure Policy or IaC so platform/resource logs automatically reach the correct central workspace instead of depending on each team to configure logging manually.

I would retain the distinction between **metrics, logs, and traces** rather than pushing everything into one giant log store. Metrics are useful for fast dashboards and alerts, logs for investigation, and traces for request-level dependency analysis.

For a large enterprise, I would decide whether to use one workspace or multiple workspaces based on RBAC, regional/data-residency requirements, security separation, retention, and cost. Centralized monitoring means centralized operational visibility—it does not necessarily mean literally one workspace for every piece of telemetry.

```text
           VMs
            │
      AMA + DCRs
            │
            ├─────────────┐
            │             │
          AKS           PaaS
       logs/metrics    diagnostics
            │             │
            └─────┬───────┘
                  ▼
              Azure Monitor
             /      |       \
            /       |        \
      Metrics    Logs       Traces
                  │
          Log Analytics
                  │
         ┌────────┼─────────┐
         ▼        ▼         ▼
        KQL    Workbooks   Alerts
                             │
                         Action Groups
```

Azure Monitor automatically collects platform metrics for many Azure services, while resource logs generally require diagnostic settings; VM guest telemetry is commonly collected using Azure Monitor Agent governed by Data Collection Rules. ([Microsoft Learn][5])

# **T32-21. Design disaster recovery for an application with a five-minute RPO.**

**Answer:**

A five-minute RPO means the business can tolerate **at most roughly five minutes of lost committed data after a disaster**, so I would design DR primarily around continuous replication of every stateful component—not around nightly backups.

I would first identify all state: database transactions, blobs/files, queues/messages, and any VM-hosted state. Then I would choose Azure services whose cross-region replication model can support the required RPO and continuously monitor their actual replication lag.

For a typical web application, I might run compute in a primary region with a fully prepared secondary region, use Azure Front Door for traffic failover, use Azure SQL geo-replication/failover groups for the relational database, use an appropriate Storage geo-redundancy strategy for objects, and use Service Bus Geo-Replication if message data also has to survive the region loss.

The important point is that I would **not claim “five-minute RPO” just because replication is enabled**. I need measurable evidence that every critical stateful dependency stays within five minutes of the primary and I need regular DR tests proving it.

```text
                         Azure Front Door
                            /        \
                           /          \
                    Primary Region   DR Region
                         │              │
                       App A          App B
                         │              │
                         ├──── DB ──────┤
                         │ replication  │
                         │              │
                         ├── Storage ───┤
                         │ geo replica  │
                         │              │
                         └── Queue ─────┘
                            replication
```

## **1. RPO is about data, not restart speed**

Suppose:

```text
Region fails at 14:00
```

DR system contains data through:

```text
13:56
```

Then:

```text
RPO ≈ 4 minutes
```

Good for a five-minute RPO.

But if target contains:

```text
13:50
```

then:

```text
RPO ≈ 10 minutes
```

Requirement failed.

RTO is separate:

```text
RPO
→ how much data can be lost

RTO
→ how long recovery can take
```


for grouped databases/stable endpoints.

Current Azure SQL documentation states that active geo-replication continuously synchronizes a readable secondary and failover groups build on that model for groups of databases and stable connection endpoints. It also explicitly notes that geo-replication is asynchronous, so forced failover can lose data. ([Microsoft Learn][10])

Therefore I monitor:

```text
replication lag
```

and treat:

```text
lag > 5 minutes
```

as an RPO breach risk before a disaster occurs.

---

# **5. Don't claim asynchronous replication guarantees zero loss**

If the business instead said:

```text
RPO = 0
```

normal asynchronous geo-replication may not satisfy that without additional application design.

Microsoft explicitly notes that asynchronous SQL geo-replication can lose the latest transactions during a forced regional failover. ([Microsoft Learn][10])

So:

```text
5-minute RPO
```

is not:

```text
zero-data-loss requirement
```

They require different designs.

---

# **6. Blob/Storage strategy**

For object data, I would evaluate:

```text
GZRS / RA-GZRS
```

or another strategy based on application needs.

GZRS provides:

```text
ZRS within primary region
+
asynchronous replication
to secondary region
```

which protects against both zone and regional failures. ([Microsoft Learn][11])

But important:

Azure Storage geo-replication is asynchronous, and Microsoft explicitly warns that regional failover can result in data loss. Standard GRS/GZRS doesn't automatically promise an arbitrary five-minute RPO. ([Microsoft Learn][11])

So I would confirm that the actual storage replication mechanism and measured/contractual behavior match the five-minute requirement rather than merely selecting “geo-redundant.”

---

# **7. Important current Storage nuance**

Microsoft currently documents a Geo Priority Replication option for Block Blobs that targets an RPO of 15 minutes or less—not five minutes. ([Microsoft Learn][11])

Therefore if the business requires:

```text
Blob RPO <= 5 minutes
```

I should not casually claim standard Azure Storage geo-replication alone guarantees it.

I may need an application-level dual-write/replication strategy or another service/design whose commitment satisfies the exact requirement.

This is exactly the kind of detail an experienced interview answer should acknowledge.

---

# **8. Messaging strategy**

If pending Service Bus messages must survive a regional disaster, the old assumption:

```text
Geo-DR
= message replication
```

is wrong.

Current Service Bus distinguishes:

```text
Geo-Disaster Recovery
→ metadata/configuration replication

Geo-Replication
→ metadata + message data/state replication
```

Microsoft currently recommends Geo-Replication for most Service Bus DR scenarios where message data must be preserved. ([Microsoft Learn][12])

For a five-minute RPO application, I would use the feature that actually protects the required message state and configure/monitor its replication behavior accordingly.

---

# **9. Service Bus can support bounded async lag**

Current Service Bus Geo-Replication allows asynchronous replication with a configurable maximum replication-lag value, and also supports synchronous replication mode. ([Microsoft Learn][12])

So if queue data is part of the five-minute RPO:

```text
Maximum replication lag
<= required threshold
```

becomes part of the design.

But synchronous replication introduces latency/availability trade-offs, so I wouldn't enable it without evaluating workload requirements.

---

# **10. VM workloads**

For VM-hosted state or legacy components:

```text
Azure Site Recovery
```

may be appropriate.

Azure-to-Azure Site Recovery uses continuous replication and currently generates crash-consistent recovery points every five minutes. ([Microsoft Learn][13])

However:

```text
5-minute crash-consistent recovery point
```

does not automatically mean:

```text
5-minute application-consistent database RPO
```

because crash-consistent state is equivalent to abrupt power loss.

Current Site Recovery guidance says application-consistent recovery points are separate and may be generated at a different frequency. ([Microsoft Learn][14])

For transactional databases I generally prefer the database-native replication mechanism.

# **11. DR region preparation**

With a strict RPO, I likely also need reasonably strong RTO.

I'd pre-provision:

```text
VNet
Private DNS
Firewall
Identity
Key Vault
App platform
Database secondary
Monitoring
```

in the DR region.

Then:

```text
Region A failure
```

doesn't require:

```text
start building VNet from scratch
```

during the disaster.

# **12. Traffic failover**

For an HTTP application:

```text
Users
  ↓
Azure Front Door
  ↓
Primary region
```

with:

```text
Secondary region
```

already configured as another origin.

When region A cannot serve:

```text

       ↓
region unavailable
       ↓
route traffic → region B
```

But I would coordinate data failover first where the database must change write ownership.

# **13. Correct failover order**

A dangerous sequence:

```text
1. Send all users to Region B
2. Later discover DB B is still read-only
```

Better:

```text
1. Declare regional incident
2. Determine data replication health
3. Establish DR database as write authority
4. Verify dependencies
5. Mark Region B application healthy
6. Route traffic
7. Validate transactions
```

The exact automation depends on services, but state ownership needs to be clear.

---

# **14. Monitor the RPO continuously**

Don't wait for the disaster.

For each state source:

```text
SQL replication lag
Storage replication status/last sync
Service Bus replication lag
ASR replication health
```

Create alerts such as:

```text
SQL lag > 3 minutes
→ warning

SQL lag approaching 5 minutes
→ critical RPO-risk alert
```

That turns RPO into an operational metric.

# **15. Five minutes needs safety margin**

If business says:

```text
RPO <= 5 min
```

I don't design for:

```text
normal replication lag = 4m59s
```

because any network degradation would violate it.

I want a normal operating lag substantially below the maximum.

For example:

```text
normal < 30 sec
warning > 2 min
critical > 4 min
```

depending on the service.

# **16. Backup is still required**

Continuous replication protects against:

```text
regional failure
```

but it can replicate:

```text
accidental deletion
corruption
malicious change
```

to the secondary.

Therefore:

```text
Replication
≠
Backup
```

I still need:

```text
point-in-time recovery
immutable/soft-delete protection
backup retention
```

appropriate to the data source.

```text
      ↓

      ↓

      ↓

      ↓
```

Then compare:

If difference is:

then:

regardless of the architecture diagram.

### **Interview answer condensed**

> “A five-minute RPO is fundamentally a data-replication requirement. I would inventory every authoritative state source and choose a regional replication mechanism for each. For example, Azure SQL could use active geo-replication or failover groups, Service Bus message state could use Premium Geo-Replication, and VM workloads might use Site Recovery where appropriate. I'd be careful with Azure Storage because geo-replication is asynchronous and I wouldn't claim a five-minute RPO unless the selected mechanism actually guarantees or consistently proves it. **RPO is proven by the age of the newest recoverable data, not by whether a “geo-replication enabled” checkbox is green.**

**Interview trap:**
Five-minute Site Recovery crash-consistent recovery points do **not automatically guarantee five-minute application-consistent RPO for a transactional database**.

# **T32-22. Design an Azure architecture that meets PCI-DSS-style isolation requirements.**

**Answer:**

I would start by defining a clear **Cardholder Data Environment, or CDE**, and reduce its scope as much as possible. The payment-processing components would live in dedicated Azure subscriptions and isolated VNets rather than sharing broad network and administrative boundaries with normal corporate workloads.

All inbound traffic would pass through controlled ingress such as Front Door/Application Gateway with WAF. The CDE would use deny-by-default segmentation through Azure Firewall, NSGs, and tightly controlled routes. Backend databases, Key Vault, Storage, ACR, and other PaaS dependencies would use Private Endpoints with public network access disabled wherever appropriate.

Administratively, production CDE access would use Microsoft Entra ID, MFA, PIM, least-privilege Azure RBAC, dedicated deployment identities, and minimal standing privilege. Workloads would use Managed Identity or Workload Identity rather than stored secrets.

I would centralize security logs, WAF/firewall logs, Activity Logs, Entra logs, Key Vault audit data, and application security events; apply Azure Policy/Defender controls continuously; encrypt data in transit and at rest; and maintain vulnerability management, patching, incident response, evidence collection, and regular access reviews.

Most importantly, I would **not say that using Azure makes the application PCI compliant**. Azure is PCI DSS validated as a cloud service provider, but the customer remains responsible for designing, operating, documenting, and validating its own CDE. ([Microsoft Learn][15])

```text
                            Internet
                               │

                    Front Door / WAF
                               │

                               │
```

# **26. Be careful with the phrase “PCI compliant architecture”**

Azure itself has PCI DSS service-provider validation, but Microsoft explicitly states that this does **not automatically make a customer's application PCI DSS compliant**. The customer remains responsible for their own environment and obligations. ([Microsoft Learn][15])

So in an interview I would say:

> “This architecture is designed to support PCI-DSS-style control objectives and reduce CDE scope; formal compliance still requires validation against the applicable standard and assessor requirements.”

That is much more credible than claiming:

> “Azure SQL + Firewall = PCI compliant.”
