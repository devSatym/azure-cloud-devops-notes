# **T32-07. How would you configure alerts for production?**

**Answer:**

For production, I would configure alerts around **user impact and actionable operational conditions**, not simply alert on every metric.

I would first define the critical service signals—availability, error rate, latency, dependency failures, capacity saturation, queue backlog, database health, certificate expiry, and security events. Then I would use **Azure Monitor alert rules** with appropriate thresholds, evaluation windows, severity levels, and **Action Groups** to route notifications to the correct on-call channel or automation.

I would also distinguish between:

```text
Symptoms
→ user-facing 5xx, SLO burn, latency

Causes
→ CPU, memory, disk, connection pool, queue depth
```

Production paging should focus mainly on symptoms that require action, while lower-level metrics can support diagnosis.

My goal is:

```text
Alert
  ↓
Correct team
  ↓
Useful context
  ↓
Clear action
  ↓
Fast mitigation
```

not:

```text
Alert
  ↓
Nobody knows what to do
```

---

## **1. Start from service objectives**

For a checkout API, I would first define:

```text
Availability SLO
Latency SLO
Error budget
```

Then alert on conditions that threaten those objectives.

For example:

```text
5xx rate > 5%
for 5 minutes
```

or:

```text
p95 latency > 1 second
for 10 minutes
```

These are more meaningful than:

```text
CPU = 82%
for 30 seconds
```

because CPU might be high while users are completely unaffected.

---

# **2. Use layered alerts**

I usually think in three layers.

### **Layer 1 — User-impact alerts**

Examples:

```text
API availability drops
5xx rises
p95/p99 latency increases
critical transaction fails
SLO burn rate high
```

These deserve the highest priority.

---

### **Layer 2 — Dependency alerts**

Examples:

```text
Azure SQL unavailable
Service Bus dead-letter queue growing
Key Vault access failures
Redis unavailable
external dependency timeout rate high
```

These explain why Layer 1 may be degrading.

---

### **Layer 3 — Capacity/infrastructure alerts**

Examples:

```text
VM memory pressure
disk space low
AKS Pods Pending
node pressure
database CPU high
queue backlog
```

These can be early warning signals.

---

# **3. Assign sensible severity**

Example:

```text
Sev 0 / Critical
→ complete production outage

Sev 1
→ major user-facing degradation

Sev 2
→ partial degradation / capacity risk

Sev 3
→ warning / nonurgent
```

The exact numbering differs by organization, but the important thing is that severity maps to:

```text
business impact
+
response urgency
```

not simply technical metric value.

---

# **4. Use evaluation windows to reduce noise**

Bad alert:

```text
CPU > 80%
for 1 data point
```

This can trigger on a harmless 20-second spike.

Better:

```text
CPU > 85%
for 10 minutes
```

if sustained CPU pressure is actually actionable.

For user-facing failures, I may want shorter windows:

```text
5xx > 10%
for 2 minutes
```

because fast detection matters.

Alert windows should match the failure type.

---

# **5. Dynamic vs static thresholds**

For stable limits:

```text
disk free < 10%
```

a static threshold makes sense.

For highly variable metrics:

```text
requests/sec
latency
```

dynamic thresholds or anomaly-based detection may be useful, depending on the service and telemetry quality.

But I wouldn't blindly trust anomaly detection for critical paging without understanding its behavior.

---

# **6. Route through Action Groups**

Typical:

```text
Azure Monitor Alert
      ↓
Action Group
      ↓
├── Email
├── SMS / push
├── Teams / webhook
├── ITSM
├── Function / Logic App
└── Automation
```

Different severities can route differently.

Example:

```text
Sev 1
→ on-call paging

Sev 2
→ Teams + ticket

Sev 3
→ dashboard / email
```

---

# **7. Include context in the alert**

A useful alert should tell me:

```text
Which service?
Which environment?
Which region?
Which endpoint?
What changed?
When did it start?
Current value?
Threshold?
Dashboard/runbook link?
```

Example:

```text
PROD checkout-api
centralindia
5xx = 18%
threshold = 5%
started 14:07
version = v2.4.1
```

Much better than:

> “Metric threshold violated.”

---

# **8. Add deployment context**

If possible, correlate alerts with:

```text
deployment version
Git commit
release timestamp
```

Then:

```text
5xx increased
2 minutes after v2.4.1
```

immediately suggests:

```text
deployment regression
```

rather than making operators investigate blindly.

---

# **9. SLO burn-rate alerts**

For mature production systems, I prefer to supplement raw threshold alerts with **error-budget burn-rate alerts**.

Example:

```text
30-day SLO = 99.95%
```

If the service starts consuming error budget rapidly:

```text
Fast burn
→ page immediately

Slow burn
→ ticket/investigation
```

This aligns alert urgency with the actual reliability objective.

---

# **10. Avoid alerting on everything**

Suppose the monitoring platform produces:

```text
5,000 alerts/day
```

People will eventually ignore them.

That's **alert fatigue**.

A good rule:

> If an alert wakes someone up, there should be a clear action they can take.

Otherwise it may belong on:

```text
dashboard
report
ticket
```

rather than paging.

---

# **11. Example production alert set**

For an internet-facing API:

```text
Availability
→ synthetic endpoint unavailable

Errors
→ 5xx > threshold

Latency
→ p95/p99 over SLO

Database
→ connection failures / failover / saturation

Queue
→ backlog or dead-letter queue growth

AKS
→ Pending Pods / unhealthy nodes

Certificates
→ expiry approaching

Security
→ suspicious/critical Defender findings
```

This gives meaningful coverage without drowning the team.

---

# **12. Test alerts**

A monitoring rule isn't useful until tested.

I would intentionally create safe conditions such as:

```text
generate controlled 500
```

or:

```text
trigger test alert
```

and verify:

```text
Alert fired?
Correct severity?
Correct Action Group?
Correct engineer notified?
Runbook useful?
```

A “configured” alert that doesn't reach anyone is effectively nonexistent.

---

### **Interview answer condensed**

> “For production I would alert primarily on user-facing and actionable signals such as availability, error rate, latency, SLO burn, dependency failures and capacity saturation. I would configure Azure Monitor alert rules with appropriate thresholds and evaluation windows, assign severity based on business impact, and route them through Action Groups to on-call, Teams, ITSM or automation. I would include service, environment, region, version and runbook context in the notification and avoid paging on noisy low-value metrics. For mature services I'd also use error-budget burn-rate alerts so paging reflects actual reliability risk.”

**Memory line:**
**Alert on what needs action, not on every metric that moves.**

**Interview trap:**
A monitoring dashboard full of metrics is **not the same as a good alerting system**.

**Keywords:**
Azure Monitor, alert rules, Action Groups, SLO, burn rate, severity, latency, 5xx, alert fatigue.

**Likely follow-ups:**

* What is the difference between a metric alert and a log alert?
* How would you reduce alert fatigue?
* When would you use dynamic thresholds?
* What would make an alert page the on-call engineer?

# **T32-08. How would you manage application secrets?**

**Answer:**

I would first try to **eliminate secrets wherever possible** by using identity-based authentication such as Managed Identity or Workload Identity.

For secrets that still exist—API keys, certificates, legacy passwords—I would store them in **Azure Key Vault**, never in source code, container images, Terraform files, or pipeline YAML.

Applications would authenticate to Key Vault through Managed Identity and receive only the minimum secret permissions they need. I would separate Key Vault access by environment, use private networking where required, enable logging, define rotation procedures, and make sure CI/CD identities cannot read more secrets than necessary.

The preferred model is:

```text
Application
   ↓
Managed Identity
   ↓
Microsoft Entra ID
   ↓
Azure service

No secret required
```

and only when unavoidable:

```text
Application
   ↓
Managed Identity
   ↓
Key Vault
   ↓
Secret
```

---

## **1. First ask: can I remove the secret?**

Suppose the application needs Azure SQL access.

Bad:

```text
DB_USER=appuser
DB_PASSWORD=...
```

Better:

```text
Application
   ↓
Managed Identity
   ↓
Microsoft Entra ID
   ↓
Azure SQL
```

Now:

```text
no password
no rotation
no secret leakage
```

Identity-based access is generally much safer operationally.

---

# **2. Use Managed Identity for Azure-hosted applications**

Examples:

```text
App Service
Functions
VM
Container Apps
AKS
```

can use Azure identity mechanisms.

Conceptually:

```text
Workload
   ↓
Managed Identity
   ↓
Entra token
   ↓
Key Vault / Storage / SQL
```

The token is short-lived.

No long-lived Azure credential needs to be stored in the application.

---

# **3. AKS: use Workload Identity**

For AKS:

```text
Pod
 ↓
Kubernetes ServiceAccount
 ↓
OIDC federation
 ↓
Microsoft Entra ID
 ↓
Azure identity
 ↓
Key Vault / Storage / SQL
```

This is preferable to:

```text
Kubernetes Secret
containing service-principal client secret
```

because no long-lived Azure credential sits inside the cluster.

---

# **4. Store unavoidable secrets in Key Vault**

Examples:

```text
Stripe API key
third-party database password
certificate private key
legacy application password
```

Store them in:

```text
Azure Key Vault
```

not:

```text
Git repository
.env committed to source
Terraform .tfvars in Git
Dockerfile
Helm values
pipeline logs
```

---

# **5. Separate environments**

Use different vaults or clearly isolated secret scopes.

Example:

```text
kv-app-dev
kv-app-stage
kv-app-prod
```

Then:

```text
Dev application
→ Dev vault only
```

and:

```text
Prod workload
→ Prod vault only
```

A compromised Dev environment should not provide access to Prod credentials.

---

# **6. Use least privilege**

Suppose the application only needs:

```text
Get secret X
```

It should not receive:

```text
Manage all keys
Delete certificates
List every secret
Modify access policy
```

Grant only what it needs.

And distinguish:

```text
Control plane
→ manage Key Vault resource

Data plane
→ read secrets/keys/certificates
```

Those are different authorization surfaces.

---

# **7. Prefer Azure RBAC for Key Vault access where appropriate**

Use:

```text
Microsoft Entra identity
+
Azure RBAC
```

to grant:

```text
Key Vault Secrets User
```

or another appropriately scoped role, rather than giving broad management permissions.

The workload should be able to **use** secrets, not administer the entire vault.

---

# **8. Network protection**

For sensitive production vaults:

```text
Application
   ↓
VNet
   ↓
Private Endpoint
   ↓
Key Vault
```

with public access disabled where the architecture supports and requires it.

Then ensure:

```text
Private DNS
```

resolves the Key Vault hostname to the private IP.

Remember:

```text
Private Endpoint
≠
authorization
```

The identity still needs secret access.

---

# **9. Secret retrieval pattern**

A good model:

```text
Application starts
      ↓
gets Entra token
      ↓
calls Key Vault
      ↓
retrieves required secret
```

But don't call Key Vault on **every request** if the secret changes infrequently.

That can create:

```text
latency
throttling
Key Vault dependency
```

Applications often cache secrets safely in memory for a reasonable period while still supporting rotation.

---

# **10. Rotation**

For secrets that must exist:

```text
Secret v1
      ↓
Create v2
      ↓
Application accepts/uses v2
      ↓
Validate
      ↓
Retire v1
```

Avoid:

```text
delete old secret
then create new one
```

if doing so creates downtime.

The general pattern is:

```text
add
→ transition
→ verify
→ remove old
```

---

# **11. Versioned secrets help rotation**

Key Vault maintains versions.

This can support:

```text
Secret
├── version 1
├── version 2
└── version 3
```

Depending on application design, using the unversioned secret URI can allow the latest active version to be consumed.

But I still need to understand application caching behavior.

---

# **12. CI/CD secrets**

For Azure authentication from pipelines:

Prefer:

```text
GitHub Actions / Azure DevOps
      ↓
OIDC federation
      ↓
Microsoft Entra
```

not:

```text
AZURE_CLIENT_SECRET
```

stored in the pipeline.

For unavoidable third-party secrets:

```text
Pipeline identity
      ↓
Key Vault
```

rather than duplicating them across many pipeline secret stores.

---

# **13. Terraform secrets**

Never put real production secrets in:

```text
terraform.tf
terraform.tfvars committed to Git
```

Even worse, remember that if Terraform manages a secret value:

```text
secret may appear in Terraform state
```

even if the CLI marks it sensitive.

So:

```text
sensitive output
```

does **not** mean:

```text
not stored in state
```

This is a very important Terraform interview point.

Remote state must therefore be:

```text
encrypted
access-controlled
not public
protected from broad read access
```

---

# **14. Logs and secret leakage**

Applications and pipelines should never log:

```text
passwords
access tokens
connection strings
Key Vault secret values
```

A secret can be securely stored in Key Vault and still leak through:

```text
debug logs
CI output
exception traces
```

So secret handling includes observability hygiene.

---

# **15. Rotation failure scenario**

Suppose production goes down because:

```text
client secret expired
```

Long-term fix:

```text
Can we replace it with:
Managed Identity?
Workload Identity?
OIDC?
```

If yes:

```text
remove secret entirely
```

That's stronger than simply:

```text
increase expiry to 2 years
```

which only delays the same outage.

---

# **16. Example**

```text
App Service
   ↓
System/User Assigned Managed Identity
   ↓
Entra ID
   ↓
Key Vault Secrets User
   ↓
Key Vault private endpoint
   ↓
Third-party API secret
```

App then uses:

```text
Managed Identity
```

for Azure authentication and retrieves only the unavoidable third-party secret.

---

### **Interview answer condensed**

> “My first preference is secretless authentication. For Azure services I'd use Managed Identity, and for AKS I'd use Workload Identity, so the workload obtains short-lived Entra tokens instead of storing service-principal credentials. Any unavoidable secret such as a third-party API key goes into Azure Key Vault. I'd separate Dev and Prod vault access, give each workload least-privilege data-plane permissions, use private endpoints where required, audit access, and rotate secrets using overlapping versions rather than disruptive replacement. For pipelines I'd prefer OIDC federation, and I'd remember that Terraform can still store sensitive values in state even when output is marked sensitive.”

**Memory line:**
**The best-managed secret is the secret you no longer need.**

**Interview trap:**
Marking a Terraform value **sensitive** hides CLI output but does **not guarantee it is absent from Terraform state**.

**Keywords:**
Key Vault, Managed Identity, Workload Identity, OIDC, Azure RBAC, secret rotation, Private Endpoint, Terraform state.

**Likely follow-ups:**

* Managed Identity vs service principal?
* How would an AKS Pod access Key Vault without a client secret?
* How would you rotate a secret without downtime?
* Why is Terraform state sensitive?

# **T32-09. How would you implement automatic scaling?**

**Answer:**

I would first identify **what layer needs to scale and which metric represents demand**.

For a web application, I might scale App Service or VM Scale Sets using request rate, CPU, or another meaningful metric. For AKS, I would typically use **Horizontal Pod Autoscaler** to scale application replicas and **Cluster Autoscaler** to add or remove nodes when Pods cannot be scheduled due to insufficient cluster capacity.

For queue-driven workloads, I would prefer scaling based on backlog or message count rather than CPU if that better represents actual work.

The sequence I want is:

```text
Demand increases
      ↓
Application metric exceeds target
      ↓
Scale application instances/Pods
      ↓
If infrastructure capacity insufficient
      ↓
Scale underlying nodes/VMs
```

Then I would define sensible minimums, maximums, cooldown behavior, headroom, and validate scaling through load testing.

---

## **1. First decide what you're scaling**

There are several layers.

```text
Application instances
VM instances
Kubernetes Pods
Kubernetes Nodes
Database capacity
Queue workers
```

These are different problems.

Example:

```text
HPA
→ scales Pods

Cluster Autoscaler
→ scales Nodes
```

Confusing these is a common interview mistake.

---

# **2. App Service autoscaling**

Conceptually:

```text
Traffic ↑
   ↓
Metric threshold
   ↓
App Service scale-out
   ↓
More instances
```

Potential signals:

```text
CPU
HTTP queue
requests
custom metric
schedule
```

depending on platform capabilities and requirements.

Scale-out is usually preferable to constantly scaling one huge instance if the application supports horizontal scaling.

---

# **3. VM Scale Sets**

For VM-hosted workloads:

```text
Load Balancer
      ↓
VMSS
├── VM1
├── VM2
└── VM3
```

Autoscale can adjust instance count.

Example:

```text
CPU > 70%
for 10 min
→ +2 VMs

CPU < 30%
for 20 min
→ -1 VM
```

with:

```text
min = 2
max = 20
```

The thresholds and windows should avoid constant scale oscillation.

---

# **4. AKS HPA**

Suppose:

```text
Deployment replicas = 3
```

and CPU target:

```text
60%
```

Traffic rises.

```text
Pods CPU ↑
   ↓
HPA
   ↓
desired replicas = 8
```

Kubernetes then creates additional Pods.

But:

```text
HPA
```

can only create Pods.

It cannot create Azure worker nodes.

---

# **5. Cluster Autoscaler**

If HPA creates more Pods but nodes have no space:

```text
New Pods
   ↓
Pending
   ↓
unschedulable
   ↓
Cluster Autoscaler
   ↓
adds node
```

Then the scheduler places those Pods.

So:

```text
Traffic spike
     ↓
HPA
     ↓
More Pods
     ↓
Pods Pending
     ↓
Cluster Autoscaler
     ↓
More Nodes
```

This distinction is crucial.

---

# **6. Resource requests matter**

HPA/Cluster Autoscaler behavior depends heavily on proper Pod resource requests.

Example:

```yaml
resources:
  requests:
    cpu: 500m
    memory: 512Mi
```

If requests are unrealistically high:

```text
Pods appear unschedulable
→ Cluster Autoscaler adds too many nodes
→ unnecessary cost
```

If requests are too low:

```text
too many Pods fit
→ nodes become overloaded
```

So resource sizing directly affects scaling behavior.

---

# **7. Queue-based autoscaling**

Suppose worker workload consumes:

```text
Azure Service Bus
```

CPU may be low even while:

```text
queue backlog = 1,000,000 messages
```

A better metric is:

```text
messages waiting
```

For Kubernetes, KEDA is often used for event-driven scaling.

Conceptually:

```text
Service Bus queue depth
      ↓
KEDA
      ↓
more worker Pods
```

This scales according to **work waiting**, not generic CPU.

---

# **8. Scale-to-zero where appropriate**

Some event-driven workloads can:

```text
0 workers
```

when no work exists.

Then:

```text
message arrives
      ↓
scale workers
```

This can reduce cost significantly.

But it introduces:

```text
cold-start latency
```

so it may not suit every real-time application.

---

# **9. Minimum capacity is important**

For production user-facing services, I might set:

```text
min replicas = 3
```

instead of:

```text
min = 0
```

because I need:

```text
warm capacity
HA
zone resilience
lower latency
```

Autoscaling should not eliminate the minimum reliable baseline.

---

# **10. Set maximums**

Without a maximum:

```text
bug
→ runaway requests
→ uncontrolled scaling
→ uncontrolled cost
```

So define:

```text
min
desired baseline
max
```

based on:

```text
capacity
quotas
database capability
business cost
```

Autoscaling cannot grow infinitely.

---

# **11. Scaling one tier can overload another**

Suppose:

```text
API Pods
3 → 100
```

but Azure SQL supports only:

```text
500 connections
```

Now each Pod opens:

```text
20 connections
```

Potential:

```text
100 × 20
= 2,000 DB connections
```

Result:

```text
database saturation
```

So autoscaling must consider dependency limits.

---

# **12. Add backpressure**

If the database cannot scale as quickly as the frontend:

```text
API traffic
      ↓
rate limiting
queue
bounded concurrency
      ↓
database
```

can protect downstream services.

Autoscaling alone is not a resilience strategy.

---

# **13. Avoid thrashing**

Bad:

```text
CPU > 60%
→ scale out

10 sec later
CPU < 60%
→ scale in

10 sec later
CPU > 60%
→ scale out
```

This is oscillation.

Use:

```text
evaluation windows
cooldowns
stabilization windows
sensible step sizes
```

to avoid constant scaling activity.

---

# **14. Scaling delay matters**

Suppose traffic doubles instantly.

### HPA:

```text
seconds/minutes
```

### New AKS node:

```text
takes additional time
```

### New VM:

```text
takes boot/startup time
```

Therefore very spiky traffic may require:

```text
headroom
pre-scaling
scheduled scaling
queueing
```

rather than waiting for reactive autoscaling.

---

# **15. Load-test scaling**

I would test:

```text
Normal load
→ expected baseline

2× load
→ scale out?

5× burst
→ any errors?

Load drops
→ scale in safely?
```

Observe:

```text
replica count
node count
latency
5xx
CPU
memory
database load
queue depth
```

If scaling occurs but latency still explodes:

```text
wrong bottleneck
```

has been scaled.

---

# **16. Example AKS architecture**

```text
Users
 ↓
Ingress
 ↓
API Deployment
 ├── Pod
 ├── Pod
 └── Pod
      ↓
HPA
      ↓
More Pods
      ↓
Need capacity?
      ↓
Cluster Autoscaler
      ↓
Node Pool grows
```

Supporting:

```text
Azure Monitor / Prometheus
```

to observe:

```text
CPU
memory
request rate
pending Pods
node utilization
```

---

### **Interview answer condensed**

> “I would first decide which layer actually needs to scale and choose a metric that represents workload demand. For App Service or VM Scale Sets I can use Azure autoscale rules, while in AKS I use HPA to scale Pods and Cluster Autoscaler to scale nodes when Pods become unschedulable. For queue-driven workers I would prefer event-driven metrics such as Service Bus backlog, potentially using KEDA. I would configure realistic minimums, maximums, cooldowns and resource requests, consider downstream limits such as database connections, and load-test both scale-out and scale-in behavior. Autoscaling is only useful if I scale the real bottleneck.”

**Memory line:**
**HPA adds Pods; Cluster Autoscaler adds nodes—scale the layer where capacity is actually missing.**

**Interview trap:**
More application instances can **make the system worse** if the real bottleneck is a shared database or dependency.

**Keywords:**
autoscaling, HPA, Cluster Autoscaler, VMSS, App Service, KEDA, queue depth, resource requests, cooldown, scale-out.

**Likely follow-ups:**

* What happens if HPA creates Pods but there is no node capacity?
* How would you scale Service Bus consumers?
* Why do resource requests matter for Cluster Autoscaler?
* When would you pre-scale instead of relying on reactive scaling?

# **T32-10. How would you protect the application from common web attacks?**

**Answer:**

I would use **defense in depth**, starting at the internet edge and continuing through the application, identity, network, and data layers.

At the edge I would use **Azure Front Door WAF or Application Gateway WAF** with managed rules to detect or block common attacks such as SQL injection, cross-site scripting, malicious request patterns, and protocol anomalies. I would enforce HTTPS, apply rate limiting where appropriate, protect APIs with authentication and authorization, keep backend and database tiers private, store secrets in Key Vault, patch dependencies, scan application/container artifacts, and centralize security telemetry.

The architecture might look like:

```text
Internet
   ↓
Front Door / App Gateway
   ↓
WAF
   ↓
Authentication / rate limiting
   ↓
Private backend
   ↓
Private database
```

But WAF is only one layer. It reduces common web threats; it does not replace secure application code.

---

## **1. Put a WAF in front of the application**

For regional web applications:

```text
Internet
   ↓
Application Gateway WAF
```

For global applications:

```text
Internet
   ↓
Azure Front Door WAF
```

WAF managed rules help detect common OWASP-style attack patterns.

Examples:

```text
SQL injection
cross-site scripting
malformed requests
protocol violations
known attack signatures
```

---

# **2. Detection vs Prevention mode**

WAF can conceptually operate in:

```text
Detection
→ log suspicious traffic

Prevention
→ block matching requests
```

A safe rollout pattern:

```text
Enable managed rules
      ↓
Detection
      ↓
Review false positives
      ↓
Tune exclusions
      ↓
Prevention
```

For a mature application, Production should normally use blocking where appropriately tuned.

---

# **3. Protect against SQL injection**

WAF helps, but the application must still use:

```text
parameterized queries
prepared statements
ORM parameter binding
```

Bad:

```text
"SELECT * FROM Users WHERE name='" + input + "'"
```

Better:

```text
parameterized statement
```

because SQL injection is fundamentally an application-input handling problem.

WAF is an extra layer, not the primary correctness mechanism.

---

# **4. Protect against XSS**

Use:

```text
output encoding
input handling
Content Security Policy
secure templating
```

plus WAF detection.

Do not trust user-controlled HTML/JavaScript.

For example:

```text
comment field
→ render as raw HTML
```

can create XSS.

Application-layer encoding is essential.

---

# **5. HTTPS everywhere**

Enforce:

```text
HTTP → HTTPS
```

and strong TLS.

Traffic paths:

```text
Client → Front Door/AppGW
```

and, where required:

```text
Gateway → backend
```

should use TLS.

Private networking does not justify plaintext.

---

# **6. Authentication**

Use Microsoft Entra ID where appropriate:

```text
User
 ↓
OIDC/OAuth2
 ↓
Entra ID
 ↓
token
 ↓
Application
```

Application should validate:

```text
issuer
audience
signature
expiry
scopes/roles
```

Authentication tells you:

```text
who is calling
```

---

# **7. Authorization**

After authentication:

```text
User A
→ Reader

User B
→ Admin
```

The application must enforce:

```text
role/scope/ownership
```

correctly.

A valid token should not give access to every object.

This protects against broken access-control problems.

---

# **8. API protection**

For APIs, I may use:

```text
Azure API Management
```

for:

```text
JWT validation
rate limits
quotas
request policies
API versioning
```

depending on the architecture.

Flow:

```text
Client
 ↓
WAF
 ↓
APIM
 ↓
Private API
```

This gives a strong controlled API entry point.

---

# **9. Rate limiting**

Protect against abusive clients and accidental floods.

Example:

```text
Client A
→ 100 req/sec limit
```

rather than allowing:

```text
100,000 req/sec
```

to consume all backend capacity.

Rate limiting protects:

```text
availability
database connections
upstream dependencies
```

It is not only a security feature—it is also resilience.

---

# **10. DDoS protection**

For public network endpoints, I would consider Azure's DDoS capabilities according to application criticality and network design.

Think of:

```text
DDoS
→ volumetric/network attack

WAF
→ HTTP/application-layer attack
```

They solve different problems.

Do not confuse:

```text
WAF
```

with:

```text
DDoS mitigation
```

---

# **11. Keep backend private**

Desired:

```text
Internet
  ↓
WAF/gateway
  ↓
private backend
```

not:

```text
Internet
→ gateway

and separately

Internet
→ backend public endpoint
```

because attackers could bypass the WAF by calling the backend directly.

If possible:

```text
backend public access = disabled
```

or restricted to the gateway path.

---

# **12. Keep database private**

Database:

```text
Backend
   ↓
Private Endpoint
   ↓
Azure SQL
```

with:

```text
Public network access = Disabled
```

where architecture permits.

Then even if an attacker scans the internet:

```text
database has no direct public path
```

---

# **13. Protect secrets**

Avoid:

```text
API keys in code
DB passwords in Git
connection strings in images
```

Use:

```text
Managed Identity
+
Key Vault
```

for Azure service access and unavoidable secrets.

Credential theft often turns a web vulnerability into a much larger breach.

Useful HTTP controls include:

```text
Content-Security-Policy
Strict-Transport-Security
X-Content-Type-Options
Referrer-Policy
```

depending on application requirements.

These help reduce browser-based attack surface.

# **15. Patch dependencies**

Application attack surface includes:

```text
framework
libraries
container base image
OS
web server
runtime
```

CI should include:

```text
dependency scanning
container image scanning
SAST
secret scanning
```

A perfect WAF doesn't help if the application runs a known critical RCE vulnerability that bypasses the rule set.

# **16. Container security**

For containerized apps:

```text
Source
 ↓
Build
 ↓
Image scan
 ↓
ACR
 ↓
Deploy
```

Block or review images with:

```text
critical CVEs

known vulnerable base images
```

```text
drop unnecessary Linux capabilities
```

# **17. WAF false positives**

Managed rules can occasionally block valid requests.

Example:

```text
legitimate JSON
contains SQL-like string
```

If rule fires:

```text
403
```

Investigate WAF logs.

Don't immediately disable the entire rule set.

Prefer a narrowly scoped exclusion based on:

```text
specific rule
parameter
path
```

where justified.

# **19. Example attack flow**

SQL injection attempt:

```text
Attacker
   ↓
"' OR 1=1 --"
   ↓
WAF
   ↓
rule match
   ↓
blocked
```

If it somehow reaches application:

```text

   ↓

   ↓
query remains safe
```

Two independent controls.

That's defense in depth.

### **Interview answer condensed**

> “I would protect a public Azure application using defense in depth. At the edge I'd use Front Door WAF or Application Gateway WAF with managed rules for common attacks such as SQL injection and XSS, enforce HTTPS, and add rate limiting/API policies where appropriate. I would keep the actual backend and database private so users cannot bypass the gateway, authenticate users through Entra ID, enforce application-level authorization, use parameterized SQL and secure output encoding, store secrets in Key Vault or remove them using Managed Identity, scan dependencies and container images, and centralize WAF/application/security logs. WAF helps significantly, but it doesn't replace secure application code.”

**Memory line:**
**WAF filters attacks at the edge; secure code, identity, private networking, and monitoring stop what the WAF cannot.**

**Interview trap:**
Putting a WAF in front of an application while leaving the backend's public endpoint directly reachable can allow attackers to **bypass the WAF entirely**.

**Keywords:**
WAF, Front Door, Application Gateway, SQL injection, XSS, TLS, rate limiting, Entra ID, Key Vault, Private Endpoint, DDoS.
