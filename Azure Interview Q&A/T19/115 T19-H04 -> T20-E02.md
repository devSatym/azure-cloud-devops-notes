## **T19-H04. How do federated identity credentials reduce secret-management risks?**

**Answer:**
Federated identity credentials reduce risk by replacing **stored, long-lived credentials such as client secrets or certificates with a trust relationship between Microsoft Entra ID and an external identity provider**.

The external workload—such as GitHub Actions or an AKS pod—gets a **short-lived signed token from its own identity provider**. Microsoft Entra validates that token against the configured federation rules and exchanges it for an Azure access token.

So instead of:

```text
Application
    ↓
stored Azure client secret
    ↓
Microsoft Entra
```

we have:

```text
Workload
   ↓
short-lived external identity token
   ↓
Microsoft Entra federation
   ↓
short-lived Azure access token
```

Microsoft specifically positions Workload Identity Federation as a way to eliminate manually managed secrets and the risks of credential leakage or certificate expiration. ([Microsoft Learn][1])

---

### **1. The traditional secret problem**

Suppose GitHub Actions authenticates like this:

```text
GitHub Repository
      ↓
AZURE_CLIENT_SECRET
      ↓
Service Principal
      ↓
Azure
```

Someone must store the secret in:

```text
GitHub Actions secrets
CI variable store
Vault
Environment variables
```

Now the organization must manage:

```text
creation
storage
access
rotation
expiration
revocation
leak detection
```

Microsoft currently says client secrets are less secure than certificates or federated credentials and recommends avoiding them for production applications where stronger mechanisms are available. ([Microsoft Learn][2])

---

### **2. Federation removes the stored Azure credential**

Federated design:

```text
GitHub Actions
      ↓
GitHub OIDC token
      ↓
Microsoft Entra
      ↓
Federated Identity Credential
      ↓
Azure access token
```

There is no reusable:

```text
AZURE_CLIENT_SECRET
```

stored in GitHub.

Likewise with AKS:

```text
AKS Pod
   ↓
ServiceAccount token
   ↓
AKS OIDC issuer
   ↓
Microsoft Entra federation
   ↓
Azure token
```

No Azure password is stored in a Kubernetes Secret.

---

### **3. Tokens are short-lived**

Compare the blast radius.

#### Client secret

```text
Secret validity:
months
   ↓
secret leaked
   ↓
attacker may reuse it
until expiry/revocation
```

#### Federated token

```text
OIDC token
   ↓
short-lived
   ↓
used for token exchange
   ↓
expires automatically
```

The workload doesn't hold a durable Microsoft Entra credential that an attacker can simply copy and reuse for months.

---

### **4. Trust is constrained by identity claims**

A standard federated identity credential validates:

```text
issuer
subject
audience
```

Example:

```text
Issuer:
GitHub

Subject:
repo:company/payment-api:
environment:production

Audience:
api://AzureADTokenExchange
```

Microsoft Entra requires these configured values to match the incoming external token's claims for standard federated credentials. ([Microsoft Learn][1])

So I can say:

```text
Trust:
payment-api production workflow
```

instead of:

```text
Trust:
anyone possessing this secret
```

That is a major security improvement.

---

### **5. It removes rotation-related outages**

Secret authentication can fail like this:

```text
Service principal secret
       ↓
expires Saturday night
       ↓
pipeline deploys
       ↓
AADSTS authentication failure
       ↓
production deployment blocked
```

Federation removes that manually maintained client-secret expiration cycle.

Microsoft specifically cites avoidance of credential expiry and manual credential maintenance as benefits of federation. ([Microsoft Learn][3])

---

### **6. Federation reduces credential distribution**

With a static secret:

```text
Secret
├── stored in CI
├── maybe copied locally
├── maybe copied to another pipeline
├── maybe logged accidentally
└── maybe shared between environments
```

Every copy increases exposure.

Federation instead establishes:

```text
Trust configuration
      ↓
specific external workload identity
```

The Azure credential isn't distributed to those systems.

---

### **7. Federation improves environment isolation**

I can create:

```text
Development identity
      ↑
GitHub dev environment

Production identity
      ↑
GitHub production environment
```

with different:

```text
federated subjects
RBAC scopes
approvals
```

Then:

```text
dev workflow
→ cannot obtain production identity
```

if the trust conditions are correctly designed.

---

### **8. But federation doesn't eliminate identity risk**

This is important.

Suppose an attacker can modify:

```text
.github/workflows/deploy-prod.yml
```

and that workflow is trusted by the production federated credential.

The attacker may be able to run the **legitimate trusted workflow** and obtain a legitimate token.

Therefore I still protect:

```text
branch protection
CODEOWNERS
production environments
required reviewers
workflow modification permissions
third-party Actions
least-privilege Azure RBAC
```

Federation eliminates one major problem:

```text
long-lived secret theft
```

but doesn't eliminate:

```text
CI supply-chain compromise
```

---

### **9. Authentication vs authorization remains separate**

Federation answers:

```text
Can Microsoft Entra trust
this external workload identity?
```

Azure RBAC answers:

```text
What may that identity do?
```

So:

```text
Federation succeeds
       ↓
Azure access token issued
       ↓
No RBAC permission
       ↓
AuthorizationFailed / 403
```

Federation should therefore be paired with least privilege.

---

### **Strong interview answer**

> “Federated identity credentials remove the need to store a long-lived Azure client secret or certificate in an external workload. Instead, Microsoft Entra establishes trust with an external identity provider such as GitHub or an AKS OIDC issuer. The workload gets a short-lived signed token, Entra validates claims such as issuer, subject and audience, and exchanges it for an Azure access token. This reduces secret leakage, distribution, rotation and expiration risks. I still protect the trusted CI or Kubernetes identity and apply least-privilege RBAC, because federation improves authentication security but doesn't remove authorization or supply-chain risks.”

**Memory line:**
**Federation replaces “whoever knows this secret” with “prove you're this specific trusted workload.”**

**Interview trap:**
Do not say federation removes **all credentials**. It removes the need to manage a reusable Microsoft Entra secret; short-lived tokens are still used.

**Keywords:**
Federated identity credential, OIDC, issuer, subject, audience, short-lived token, secretless authentication

**Likely follow-ups:**

* What happens if the `subject` doesn't match?
* Can federation be compromised?
* Federation vs Managed Identity?
* Why is a client secret less secure?

# **T19-H05. How would you troubleshoot a managed identity receiving HTTP 403 from Key Vault?**

**Answer:**
A Key Vault `403` usually means I have progressed beyond basic authentication and should investigate **the actual calling identity, Key Vault authorization model and data-plane permissions, followed by Key Vault network restrictions**.

Microsoft's current Key Vault documentation states that HTTP 403 commonly means the caller was authenticated but either lacks appropriate permissions or is blocked by the Key Vault firewall. ([Microsoft Learn][4])

My troubleshooting order is:

```text
Exact error
   ↓
Actual Managed Identity?
   ↓
Correct Key Vault?
   ↓
RBAC or legacy access-policy model?
   ↓
Correct data-plane permissions?
   ↓
Correct scope?
   ↓
Propagation?
   ↓
Firewall / Private Endpoint / DNS?
   ↓
Key Vault logs
```

---

### **1. Capture the exact 403**

I don't troubleshoot only:

> “Key Vault says forbidden.”

I capture:

```text
HTTP status
inner error code
request URI
operation
caller identity
timestamp
```

Especially look for things like:

```text
ForbiddenByFirewall
```

because that immediately shifts the investigation toward networking rather than RBAC.

Microsoft specifically documents `403 ForbiddenByFirewall` for incorrectly configured Key Vault private connectivity/firewall scenarios. ([Microsoft Learn][5])

---

### **2. Verify which Managed Identity the application actually used**

This is one of the first things I check.

Suppose an App Service has:

```text
System-assigned MI:
principal A

User-assigned MI:
principal B
```

and I granted:

```text
Key Vault Secrets User
→ principal B
```

but the application actually authenticated as:

```text
principal A
```

Result:

```text
Authentication ✓
Authorization ✗
403
```

Microsoft notes that 403 problems frequently occur because the application isn't using the client identity administrators think it is using. ([Microsoft Learn][4])

---

### **3. Check `DefaultAzureCredential` behavior**

During local development:

```text
DefaultAzureCredential
→ developer Azure CLI identity
```

may have been used.

In Azure:

```text
DefaultAzureCredential
→ Managed Identity
```

So something can:

```text
work locally ✓
fail in Azure ✗
```

because two different identities are accessing Key Vault.

If multiple UAMIs are attached, I may explicitly select the intended client ID.

---

### **4. Verify Key Vault authorization model**

Key Vault supports:

```text
Azure RBAC         ← recommended/current
Legacy access policy
```

I first check which one the vault uses.

Microsoft currently recommends Azure RBAC for Key Vault data-plane authorization, and starting with Key Vault API version `2026-02-01`, Azure RBAC is the default access model for newly created vaults. ([Microsoft Learn][6])

If:

```text
Permission model = Azure RBAC
```

then adding only a legacy access policy isn't the answer.

Likewise, if the vault is using:

```text
Legacy access policies
```

I troubleshoot the applicable access policy instead.

---

### **5. Verify a data-plane role, not merely management permissions**

Very common mistake:

```text
Managed Identity
      ↓
Reader
```

or:

```text
Key Vault Contributor
```

and expecting:

```text
secret value access
```

That is wrong.

`Key Vault Contributor` manages the **vault resource/control plane** but doesn't grant secret/key/certificate data access. ([Microsoft Learn][6])

For reading secret values, a common role is:

```text
Key Vault Secrets User
```

For administering secret values:

```text
Key Vault Secrets Officer
```

depending on the workload requirement. ([Microsoft Learn][6])

---

### **6. Check exact role-assignment scope**

Suppose:

```text
payment-api MI
      ↓
Key Vault Secrets User
      ↓
kv-orders-prod
```

but application accesses:

```text
kv-payments-prod
```

then:

```text
403
```

is correct.

I inspect:

```text
Principal
Role
Scope
Inherited role assignments
```

Example desired:

```text
Principal:
id-payment-api

Role:
Key Vault Secrets User

Scope:
/.../vaults/kv-payments-prod
```

---

### **7. Check propagation delay**

If someone says:

> “I assigned the role 30 seconds ago and it still fails.”

I don't immediately redesign networking.

Role/access changes can take time to propagate.

For a newly granted permission I use sensible retry/backoff rather than repeatedly recreating the Managed Identity.

Microsoft's Key Vault troubleshooting guidance explicitly recommends retry behavior when a 403 occurs immediately after access is granted. ([Microsoft Learn][4])

---

### **8. If permissions are correct, check the Key Vault firewall**

Key Vault's authentication flow includes a network-security check.

Even with:

```text
Managed Identity ✓
RBAC ✓
```

the request can still be rejected if:

```text
source network isn't allowed
```

Microsoft documents that Key Vault checks its firewall/private-link configuration after authentication. ([Microsoft Learn][7])

So:

```text
Identity
   ↓
Token ✓
   ↓
RBAC ✓
   ↓
Key Vault firewall
   ↓
DENY
```

can still produce a forbidden response.

---

### **9. Private Endpoint? Check DNS**

For a private-only Key Vault:

```text
Application
   ↓
kv-prod.vault.azure.net
   ↓
Private DNS
   ↓
Private Endpoint IP
```

From the failing workload I check:

```bash
nslookup <vault-name>.vault.azure.net
```

Expected:

```text
private IP
```

If it resolves incorrectly:

```text
public endpoint
      ↓
Key Vault public access disabled
      ↓
failure / ForbiddenByFirewall
```

Microsoft's private-link diagnostics specifically calls out both public-IP DNS resolution and `ForbiddenByFirewall` as common private-link failure modes. ([Microsoft Learn][5])

---

### **10. Check the network path**

If DNS returns the correct private IP:

```text
DNS ✓
```

I test:

```text
TCP/443
```

and inspect:

```text
effective routes
NSGs
Azure Firewall/NVA
peering
Private Endpoint configuration
```

Remember:

```text
Managed Identity
→ identity

RBAC
→ authorization

Private Endpoint
→ network path
```

Three independent layers.

---

### **11. Turn on Key Vault logging**

I use Key Vault logs to determine:

```text
Which identity called?
Which operation?
Which result?
Was it firewall or authorization?
```

Microsoft explicitly recommends enabling Key Vault logging as an early 403 troubleshooting step. ([Microsoft Learn][4])

This is much better than blindly adding:

```text
Owner
```

until the application works.

---

### **Diagnostic tree**

```text
Key Vault 403
     ↓
Which identity actually called?
     ↓
Correct?
  /      \
 No       Yes
 ↓         ↓
fix MI   Permission model?
            ↓
       RBAC / Access Policy
            ↓
       Correct data-plane role?
            ↓
       Correct scope?
            ↓
         Still 403?
            ↓
      Firewall / private access
            ↓
          DNS
            ↓
      logs + inner error
```

---

### **Strong interview answer**

> “For a Key Vault 403, I first capture the exact error and confirm which Managed Identity actually obtained the token, especially if the resource has multiple identities or uses `DefaultAzureCredential`. Then I check whether the vault uses Azure RBAC or the legacy access-policy model and verify the identity has the appropriate **data-plane** permission—for example `Key Vault Secrets User` for reading secret contents—at the correct vault scope. I remember that `Key Vault Contributor` is only a control-plane role. If authorization is correct, I investigate the Key Vault firewall, Private Endpoint and Private DNS, especially if the inner error is `ForbiddenByFirewall`. Finally I use Key Vault logs to prove whether the failure is identity, authorization or networking rather than granting broader permissions blindly.”

**Memory line:**
**Key Vault 403: actual identity → data-plane authorization → network restrictions.**

**Interview trap:**
`Key Vault Contributor` does **not** grant permission to read secret values. ([Microsoft Learn][6])

**Keywords:**
403, Managed Identity, Key Vault Secrets User, control plane, data plane, `ForbiddenByFirewall`, Private Endpoint

**Likely follow-ups:**

* What does `Key Vault Contributor` actually allow?
* Why can it work locally but fail from App Service?
* How do you tell firewall 403 from RBAC 403?
* What if the Key Vault uses a Private Endpoint?

# **20. 🟠 IMP — Azure Cost Management & FinOps**

## **T20-E01. What is Azure Cost Management?**

**Answer:**
Azure Cost Management—currently part of **Microsoft Cost Management**—is Microsoft's suite of **FinOps tools for analyzing, monitoring, allocating, reporting, and optimizing cloud spending**.

It helps answer questions such as:

```text
How much are we spending?
What is causing the cost?
Which team/application owns it?
Are we exceeding budget?
Where can we optimize?
```

Microsoft currently describes Cost Management as a suite of FinOps tools for analyzing, monitoring, and optimizing Microsoft Cloud costs. ([Microsoft Learn][8])

---

### **Core capabilities**

Think:

```text
Microsoft Cost Management
│
├── Cost Analysis
├── Budgets & alerts
├── Cost allocation
├── Exports
├── Anomaly monitoring
├── Reservation utilization
└── Optimization workflows
```

---

### **1. Cost Analysis**

This is normally my first stop when investigating spending.

Example:

```text
September cost
₹ / $
   ↓
Group by:
Service
Resource
Resource Group
Subscription
Tag
Region
```

I might discover:

```text
Total = $10,000

AKS / Compute       $4,500
Log Analytics       $2,000
Azure SQL           $1,700
Networking          $900
Storage             $500
Other               $400
```

Microsoft recommends Cost Analysis as the primary Azure portal experience for understanding where spending occurs and identifying trends. ([Microsoft Learn][9])

---

### **2. Cost scopes**

Cost Management can operate at different organizational scopes where supported:

```text
Billing scope
Management Group
Subscription
Resource Group
```

For example:

```text
Management Group
      ↓
all production subscriptions
      ↓
central FinOps analysis
```

rather than opening every subscription independently. ([Microsoft Learn][8])

---

### **3. Budgets**

Example:

```text
Production Subscription

Monthly Budget:
$5,000

80%  → email FinOps
90%  → alert platform team
100% → escalate
```

Budgets help monitor spending against expected limits.

Important:

```text
Budget alert
≠ automatic spending cap
```

We'll cover this in **T20-E02**.

---

### **4. Cost allocation**

With disciplined tags:

```text
CostCenter = 101
Application = Payments
Team = Checkout
Environment = Prod
```

I can analyze:

```text
How much did Payments spend?
```

or:

```text
How much does Production cost
compared with Development?
```

Microsoft Cost Management also supports capabilities such as tag inheritance and cost-allocation rules for shared costs. ([Microsoft Learn][8])

---

### **5. Exports**

For larger organizations:

```text
Cost Management
      ↓
scheduled export
      ↓
Azure Storage
      ↓
Power BI / FinOps system
```

Microsoft's current Cost Management exports can automate recurring cost-data exports rather than requiring manual CSV downloads. ([Microsoft Learn][10])

---

### **6. Optimization**

Cost Management is not only:

```text
view the invoice
```

It supports the broader FinOps process:

```text
Inform
→ understand cost

Optimize
→ find waste / efficiency opportunities

Operate
→ budgets, accountability,
   allocation, ongoing controls
```

Typical optimization decisions may involve:

```text
rightsizing
Reservations
Savings Plans
Spot VMs
autoscaling
storage tiering
log-retention changes
deleting idle resources
```

some of which are supported by other Azure services such as Azure Advisor alongside Cost Management.

---

### **Simple scenario**

Company's monthly spend:

```text
June   $8k
July   $9k
August $15k
```

Using Cost Analysis:

```text
August
   ↓
Group by Service
   ↓
Log Analytics
$2k → $7k
```

Now I have a direction:

```text
Why did Log Analytics ingestion
increase by 3.5×?
```

rather than randomly shutting resources down.

---

### **Strong interview answer**

> “Azure Cost Management is Microsoft's FinOps capability for understanding and controlling cloud spending. I use Cost Analysis to break costs down by subscription, resource, service or tag, budgets and alerts to monitor spending thresholds, cost allocation to associate spending with teams and applications, and scheduled exports for external reporting or FinOps platforms. It helps me understand where money is being spent and identify optimization opportunities rather than treating the Azure invoice as one number.”

**Memory line:**
**Cost Management = understand, allocate, monitor and optimize Azure spend.**

**Interview trap:**
Cost Management is **not the same as simply viewing an invoice**; it includes analytics, budgets, allocation, exports and optimization workflows.

**Keywords:**
Microsoft Cost Management, FinOps, Cost Analysis, budgets, cost allocation, exports, optimization

**Likely follow-ups:**

* What is an Azure budget?
* How do tags help with cost allocation?
* How would you investigate a sudden cost spike?
* How does Azure Advisor complement Cost Management?

## **T20-E02. What is an Azure budget?**

**Answer:**
An Azure budget lets me define an **expected spending or usage threshold for a Cost Management scope and receive alerts when actual or forecasted costs cross configured percentages of that budget**.

The most important interview point is:

```text
Azure Budget
→ monitors + alerts

Azure Budget
≠ hard spending cap
```

Microsoft explicitly states that exceeding a budget threshold **does not stop Azure resources or consumption**. ([Microsoft Learn][11])

---

### **Example**

Suppose:

```text
Monthly production budget:
$10,000
```

I configure:

```text
50%  → notification
80%  → FinOps alert
90%  → engineering alert
100% → escalation
110% → critical alert
```

During the month:

```text
Spend reaches $8,100
       ↓
80% threshold crossed
       ↓
Budget notification
```

Resources continue running.

---

### **Actual vs forecasted thresholds**

Azure budgets can alert on:

```text
Actual cost
```

and:

```text
Forecasted cost
```

Example:

```text
Today's actual spend:
$6,000

Azure forecast:
$11,500 by month end

Budget:
$10,000
```

A forecasted-cost alert can warn me **before** the actual spend reaches $10,000. ([Microsoft Learn][11])

That's much more useful operationally than waiting until the money is already spent.

---

### **Budget periods**

Current Cost Management budgets support recurring periods such as:

```text
Monthly
Quarterly
Annually
```

and reset for the next period according to the configured budget lifecycle. ([Microsoft Learn][11])

---

### **What happens when the budget is exceeded?**

Not:

```text
Budget = $1,000
      ↓
Spend = $1,001
      ↓
VMs shut down automatically
```

Instead:

```text
Spend / forecast
      ↓
threshold reached
      ↓
notification / configured action
```

Microsoft explicitly says Azure resources are unaffected and consumption isn't stopped simply because the budget threshold is crossed. ([Microsoft Learn][11])

---

### **Can I trigger automation?**

Budgets can integrate with **Action Groups** in supported subscription scenarios.

Conceptually:

```text
Budget threshold
      ↓
Action Group
      ↓
Automation / notification workflow
```

But I would be careful about automatically stopping production resources.

Better examples:

```text
Notify FinOps
Create incident
Notify Slack/Teams through automation
Investigate abnormal spending
```

rather than:

```text
100% budget
→ destroy production AKS
```

---

### **Budgets aren't real-time**

Another useful interview nuance: cloud cost data has ingestion delay.

Microsoft currently notes that cost/usage data is typically available after a delay, and budgets are evaluated periodically—currently generally against cost data every 24 hours. ([Microsoft Learn][11])

Therefore:

```text
Budget
≠ instantaneous billing circuit breaker
```

---

### **Example production setup**

```text
Subscription:
prod-platform

Monthly budget:
$8,000

Thresholds:
70% actual
→ Platform team

90% forecast
→ FinOps + Engineering Manager

100% actual
→ High-priority alert
```

Then when spend begins accelerating:

```text
Cost Analysis
      ↓
group by resource/service/tag
      ↓
find cause
      ↓
optimize
```

---

### **Strong interview answer**

> “An Azure budget is a Cost Management control that tracks spending against an expected amount and can notify stakeholders when actual or forecasted cost crosses configured thresholds. For example, I could set an $8,000 monthly production budget and alert at 70%, 90%, and 100%. The important distinction is that a budget is normally a monitoring and accountability mechanism—not a hard spending cap. Crossing the budget doesn't automatically stop Azure resources, and cost data isn't real-time, so budgets shouldn't be treated as an instantaneous shutdown control.”

**Memory line:**
**Budget warns you about spending; it doesn't automatically stop spending.**

**Interview trap:**
Never say:

```text
Budget reached
→ Azure automatically shuts down resources.
```

It doesn't. ([Microsoft Learn][11])

**Keywords:**
Azure budget, actual cost, forecasted cost, threshold, Action Group, Cost Management

**Likely follow-ups:**

* Does a budget stop Azure resources?
* Actual vs forecasted budget alerts?
* How would you automate responses to a budget alert?
* How would you investigate a budget breach?
