### **T19-E04. What is a user-assigned managed identity?**

**Answer:**
A **user-assigned managed identity (UAMI)** is a standalone Azure resource that represents a Microsoft Entra workload identity whose credentials are managed by Azure. Unlike a system-assigned identity, its lifecycle is **independent of the Azure resources that use it**, and the same UAMI can be associated with multiple supported Azure resources. ([Microsoft Learn][1])

The simplest distinction is:

```text
System-assigned MI
→ belongs to one Azure resource
→ dies with that resource

User-assigned MI
→ separate Azure resource
→ can be attached to multiple resources
→ survives resource replacement/deletion
```

---

### **Basic architecture**

Suppose three application instances need identical access:

```text
              UAMI: payments-reader
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
      App Service   Function   Container App
          │           │           │
          └───────────┼───────────┘
                      ↓
             Microsoft Entra ID
                      ↓
          Storage Blob Data Reader
                      ↓
                Storage Account
```

Instead of creating three separate identities and three separate RBAC assignments, the workloads can share one identity **when they genuinely share the same security boundary and permissions**.

Microsoft documents that user-assigned identities can be associated with multiple Azure resources and have an independent lifecycle. ([Microsoft Learn][1])

---

### **It is created independently**

A UAMI is an Azure resource in its own right.

For example:

```bash
az identity create \
  --resource-group rg-platform \
  --name id-payment-api
```

It gets important identifiers such as:

```text
clientId
principalId
resourceId
```

The distinction matters:

```text
clientId
→ identifies the identity during authentication/configuration

principalId
→ identifies its Entra service principal
  for RBAC assignments
```

Microsoft's current guidance specifically notes that the `principalId` is used when assigning permissions while `clientId` is commonly used by application configuration. ([Microsoft Learn][1])

---

### **Lifecycle independence**

Imagine:

```text
UAMI:
id-payment-api

App Service:
payment-api-v1
```

The App Service is deleted during redeployment:

```text
payment-api-v1
     ↓
DELETED
```

But:

```text
id-payment-api
     ↓
still exists
```

A replacement:

```text
payment-api-v2
```

can then be attached to the same UAMI.

The RBAC associated with that identity can remain consistent.

This is particularly useful for:

```text
blue/green infrastructure
ephemeral VMs
VMSS instances
resource replacement
recreated App Services
automated environments
```

Microsoft specifically recommends UAMIs for workloads where resources are frequently replaced but the workload's permissions should remain stable. ([Microsoft Learn][2])

---

### **Pre-authorizing the identity**

This is a major advantage.

Suppose infrastructure deployment requires:

```text
Application
→ access Key Vault
```

With a UAMI I can do:

```text
1. Create UAMI
      ↓
2. Grant Key Vault Secrets User
      ↓
3. Deploy application
      ↓
4. Attach UAMI
```

So the application is authorized **before it even starts**.

With a newly created system-assigned identity:

```text
Create application
      ↓
Identity is created
      ↓
Discover principal ID
      ↓
Create RBAC assignment
```

which introduces an additional provisioning dependency.

Microsoft cites pre-authorization as an important reason to use user-assigned Managed Identities. ([Microsoft Learn][3])

---

### **Example: Key Vault**

```text
User-assigned MI
id-orders-prod
      ↓
Key Vault Secrets User
      ↓
kv-orders-prod
```

Attach that identity to:

```text
App Service instance A
App Service instance B
```

Both can obtain Entra tokens as:

```text
id-orders-prod
```

and access only the permissions granted to that identity.

---

### **Important security nuance: sharing is optional, not mandatory**

The fact that a UAMI **can** be shared doesn't mean I should attach one identity to every workload.

Bad:

```text
one UAMI
   ↓
App A
App B
App C
Database worker
CI pipeline
Monitoring service
```

with broad access.

Then compromising one workload potentially exposes everything the identity can access.

Better:

```text
id-orders-api
→ permissions needed by orders API

id-payment-worker
→ permissions needed by payment worker

id-monitoring
→ monitoring permissions
```

Microsoft's latest guidance also recommends avoiding reuse of a user-assigned identity across unrelated workloads merely for convenience. ([Microsoft Learn][4])

---

### **System-assigned vs user-assigned**

| Area                          | System-assigned                | User-assigned              |
| ----------------------------- | ------------------------------ | -------------------------- |
| Azure resource                | Part of source resource        | Separate Azure resource    |
| Lifecycle                     | Tied to source                 | Independent                |
| Can be shared                 | No                             | Yes                        |
| Pre-create identity           | No                             | Yes                        |
| Pre-create RBAC               | Difficult before source exists | Yes                        |
| Good for resource replacement | Less convenient                | Excellent                  |
| Cleanup                       | Automatic with resource        | Must be explicitly managed |

Microsoft's current developer guidance recommends user-assigned identities for many scenarios because of this lifecycle and reuse flexibility. ([Microsoft Learn][1])

> **In an interview, I would say:**
> “A user-assigned Managed Identity is a standalone Azure resource representing a Microsoft Entra workload identity. Azure manages its credentials, but unlike a system-assigned identity, its lifecycle isn't tied to one application or VM. I can create it ahead of time, grant its RBAC permissions, and associate it with one or more supported Azure resources. This is useful when resources are frequently recreated or multiple instances genuinely need the same identity. I still avoid sharing one identity across unrelated workloads because that increases the blast radius.”

**Memory line:**
**User-assigned MI = reusable, pre-created identity whose lifecycle is independent of the workloads using it.**

**Interview trap:**
Do not say:

```text
User-assigned MI
→ automatically belongs to every resource
```

It must be explicitly associated with supported source resources and separately authorized to its target resources.

**Keywords:**
User-assigned Managed Identity, UAMI, lifecycle, reusable identity, pre-authorization, `clientId`, `principalId`

**Likely follow-ups:**

* System-assigned vs user-assigned?
* Can multiple resources share a UAMI?
* Why pre-create an identity?
* What security risk comes from over-sharing one UAMI?

### **T19-E05. What is workload identity federation?**

**Answer:**
**Workload identity federation allows a workload to authenticate to Microsoft Entra ID using a trusted short-lived token issued by another identity provider instead of storing a Microsoft Entra client secret or certificate.**

Microsoft Entra establishes a trust relationship with an external identity provider such as:

```text
GitHub Actions
Kubernetes / AKS
GitLab
Terraform Cloud
other OIDC-compatible identity providers
```

The external workload presents its signed token to Microsoft Entra, Entra validates the configured trust, and then issues an Azure access token. ([Microsoft Learn][5])

---

### **Classic authentication**

Without federation:

```text
GitHub Actions
      ↓
AZURE_CLIENT_SECRET
      ↓
Microsoft Entra ID
      ↓
Azure access token
      ↓
Azure
```

Problems:

```text
secret must be stored
secret can leak
secret must be rotated
secret can expire
```

---

### **Federated model**

```text
GitHub Actions
      ↓
GitHub OIDC token
      ↓
Microsoft Entra ID
      ↓
Validate federation trust
      ↓
Short-lived Azure access token
      ↓
Azure
```

There is:

```text
NO long-lived Azure client secret
```

in GitHub.

Microsoft specifically positions workload identity federation as a way to eliminate secret/certificate management and the associated leakage and expiry risks. ([Microsoft Learn][5])

---

### **What is being trusted?**

A federated identity credential typically defines important token claims:

```text
issuer
subject
audience
```

Example conceptually for GitHub:

```text
issuer:
https://token.actions.githubusercontent.com

subject:
repo:company/payment-api:ref:refs/heads/main

audience:
api://AzureADTokenExchange
```

Microsoft Entra checks that the incoming token's:

```text
issuer
subject
audience
```

match the configured federated trust. Microsoft currently requires those standard federated-credential values to match the corresponding token claims case-sensitively. ([Microsoft Learn][5])

---

### **Why the subject is important**

Suppose I trust:

```text
repo:company/payment-api:ref:refs/heads/main
```

Then:

```text
payment-api
main branch
→ trusted
```

but ideally:

```text
random-repository
→ not trusted

feature branch
→ not trusted
```

This makes identity trust much narrower than:

```text
anyone who knows this client secret
```

---

### **Token exchange flow**

The full conceptual flow is:

```text
External workload
      ↓
External IdP authenticates workload
      ↓
Short-lived signed OIDC/JWT
      ↓
Microsoft Entra token endpoint
      ↓
Federated identity credential checked
      ↓
Entra access token
      ↓
Azure service
```

Microsoft describes this as an external token being exchanged for a Microsoft identity-platform access token. ([Microsoft Learn][5])

---

### **What Azure identity receives the trust?**

Federation can be configured against:

```text
App registration
or
User-assigned Managed Identity
```

depending on the scenario. ([Microsoft Learn][5])

Example:

```text
GitHub
   ↓
OIDC
   ↓
UAMI
id-github-deploy
   ↓
Contributor on rg-app
```

Or:

```text
GitHub
   ↓
OIDC
   ↓
App registration / service principal
   ↓
Azure RBAC
```

---

### **Example: GitHub Actions**

```text
GitHub repository
       ↓
workflow on protected main
       ↓
GitHub issues OIDC token
       ↓
Entra validates:
issuer
subject
audience
       ↓
Azure access token
       ↓
Terraform / az CLI
       ↓
Azure
```

GitHub configuration generally includes:

```yaml
permissions:
  id-token: write
  contents: read
```

`id-token: write` lets the workflow request the GitHub OIDC token.

We'll go much deeper into that in **T19-M07**.

---

### **Example: AKS Workload Identity**

The same federation principle appears with Kubernetes:

```text
AKS Pod
  ↓
Kubernetes ServiceAccount token
  ↓
AKS OIDC issuer
  ↓
Microsoft Entra federation
  ↓
User-assigned Managed Identity
  ↓
Azure access token
  ↓
Key Vault
```

No Azure client secret needs to live in:

```text
Kubernetes Secret
```

Microsoft explicitly supports workload identity federation for Kubernetes workloads including AKS, EKS, GKE, and on-prem Kubernetes. ([Microsoft Learn][5])

---

### **Federation does not grant authorization**

Very important:

```text
Federation
→ proves workload identity

Azure RBAC
→ determines what it can access
```

For example:

```text
GitHub OIDC authentication ✓
```

but no RBAC assignment:

```text
az group create
→ AuthorizationFailed
```

So:

```text
Authentication
≠
Authorization
```

---

### **Security improvement**

Long-lived secret:

```text
Secret validity
6 months / 1 year
      ↓
leaked today
      ↓
potentially usable until revoked/expired
```

Federated token:

```text
Short lifetime
+
specific issuer
+
specific subject
+
specific audience
```

dramatically reduces reusable credential exposure.

---

### **2026 nuance**

Microsoft has also introduced **Flexible Federated Identity Credentials** in preview for some app-registration scenarios, allowing restricted expression-based matching instead of requiring one exact `subject` for every case. This helps large GitHub/GitLab/Terraform Cloud federation designs, but the standard exact issuer/subject/audience model remains the core concept you should explain in an interview. ([Microsoft Learn][6])

> **In an interview, I would say:**
> “Workload identity federation lets an external workload authenticate to Microsoft Entra using a short-lived token from a trusted identity provider instead of storing an Azure client secret. For example, GitHub Actions receives an OIDC token from GitHub, Entra validates its issuer, subject, and audience against a federated identity credential, and then exchanges that token for an Azure access token. The Azure identity still needs RBAC permissions. The same idea powers scenarios such as AKS Workload Identity.”

**Memory line:**
**Federation = trust an external short-lived identity token instead of sharing an Azure secret.**

**Interview trap:**
Federation does **not** mean:

```text
GitHub's token itself
is directly accepted by Azure Resource Manager.
```

Microsoft Entra validates/exchanges it and issues the Azure access token.

**Keywords:**
Workload Identity Federation, OIDC, federated identity credential, issuer, subject, audience, token exchange

**Likely follow-ups:**

* How does GitHub Actions OIDC work?
* What are issuer, subject, and audience?
* Federation vs Managed Identity?
* How does AKS Workload Identity use federation?

## **T19-M01. What is the difference between a managed identity and service principal?**

**Answer:**
A **service principal** is a Microsoft Entra security principal representing an application or workload in a tenant. A **Managed Identity is a special Azure-managed workload identity backed by a service principal**, where Azure manages the authentication credentials and their lifecycle for you.

So the strongest interview distinction is:

```text
Service Principal
→ general application/workload identity

Managed Identity
→ Azure-managed form of workload identity
  with no credential lifecycle for you to manage
```

Microsoft recommends Managed Identity for workloads hosted on Azure where supported, and a service principal/app identity for scenarios where Managed Identity isn't applicable. ([Microsoft Learn][7])

---

### **Traditional service principal**

A typical service principal might authenticate with:

```text
Client ID
+
Client Secret
```

or:

```text
Client ID
+
Certificate
```

or preferably:

```text
Federated credential
```

Example:

```text
External CI server
      ↓
Service Principal
      ↓
Microsoft Entra
      ↓
Azure RBAC
```

If client-secret authentication is used, somebody must manage:

```text
storage
rotation
expiration
revocation
```

Microsoft now explicitly recommends federation or certificates instead of client secrets for production app credentials. ([Microsoft Learn][8])

---

### **Managed Identity**

For an Azure workload:

```text
App Service
    ↓
Managed Identity
    ↓
Microsoft Entra
    ↓
short-lived access token
    ↓
Key Vault
```

Azure handles the Managed Identity credential infrastructure.

The application does not contain:

```text
client secret
certificate private key
password
```

---

### **Side-by-side**

| Area                                 | Service Principal                     | Managed Identity         |
| ------------------------------------ | ------------------------------------- | ------------------------ |
| Represents workload/app              | Yes                                   | Yes                      |
| Microsoft Entra principal            | Yes                                   | Yes                      |
| Azure manages underlying credentials | Not necessarily                       | Yes                      |
| Client secret possible               | Yes                                   | No need                  |
| Certificate possible                 | Yes                                   | No need                  |
| Federation possible                  | Yes                                   | UAMI supports federation |
| Best fit                             | General/external workload integration | Azure-hosted workload    |
| Credential rotation by app team      | Depending on auth method              | No                       |
| Azure RBAC                           | Yes                                   | Yes                      |

---

### **Important nuance: don't say they are completely unrelated**

This answer:

> “A Managed Identity is completely different from a service principal.”

is technically poor.

When Azure creates a Managed Identity, an associated service principal exists in Microsoft Entra.

The real distinction is:

```text
Managed Identity
→ lifecycle and credentials
  managed by Azure

Ordinary app/service principal
→ identity lifecycle/authentication
  configured by you
```

---

### **Example: App Service**

If App Service needs Key Vault:

Best option:

```text
App Service
    ↓
Managed Identity
    ↓
Key Vault Secrets User
```

rather than:

```text
App Service
    ↓
Client ID + client secret
    ↓
Service Principal
    ↓
Key Vault
```

because the second architecture creates a credential-management problem.

Microsoft explicitly recommends Managed Identity when the workload is hosted in Azure and the service supports it. ([Microsoft Learn][7])

---

### **Example: GitHub Actions**

GitHub-hosted runners aren't Azure resources to which I simply attach a normal Managed Identity.

A modern option is:

```text
GitHub Actions
     ↓
OIDC federation
     ↓
App registration/service principal
or UAMI federation
     ↓
Azure RBAC
```

So the correct identity model depends on **where the workload runs and which federation mechanisms are available**.

---

### **Both still require authorization**

Whether:

```text
Service Principal
```

or:

```text
Managed Identity
```

I still grant:

```text
Azure RBAC
```

Example:

```text
Managed Identity
       ↓
Storage Blob Data Reader
       ↓
Storage Account
```

or:

```text
Service Principal
       ↓
Contributor
       ↓
Resource Group
```

Identity type doesn't inherently determine permissions.

---

### **Security preference**

A useful order for an Azure workload is:

```text
Managed Identity
      ↓
preferred when supported

Federated service principal/UAMI
      ↓
strong option for external/federated workloads

Certificate
      ↓
when federation isn't available

Client secret
      ↓
last-resort / legacy style
```

This is not an absolute rule for every application, but it captures the modern secretless direction Microsoft recommends. ([Microsoft Learn][9])

> **In an interview, I would say:**
> “A service principal is the general Microsoft Entra security identity used by an application or workload. A Managed Identity is an Azure-managed workload identity backed by a service principal, but Azure manages its credentials so I don't have a client secret or certificate to rotate. For an Azure-hosted workload such as App Service or a VM, I prefer Managed Identity where supported. For an external workload such as GitHub Actions, I can use an app/service principal or user-assigned identity with workload identity federation. Both still need explicit RBAC authorization.”

**Memory line:**
**Service principal = general app identity; Managed Identity = Azure-managed secretless form of workload identity.**

**Interview trap:**
Do not say Managed Identity eliminates RBAC or that it has no relationship to service principals.

**Keywords:**
Service principal, Managed Identity, workload identity, credentials, Azure RBAC, federation

**Likely follow-ups:**

* Is a Managed Identity technically a service principal?
* Which would you use for GitHub Actions?
* Why are Managed Identities more secure than client secrets?
* Can Managed Identities work outside Azure?

## **T19-M02. When would you use a user-assigned managed identity?**

**Answer:**
I would use a **user-assigned Managed Identity when I need the identity lifecycle to be independent of one Azure resource**, when multiple instances/resources genuinely need the same permissions, when I want to **pre-create and pre-authorize the identity before deploying the workload**, or when resources are frequently replaced but should keep the same identity and RBAC.

Microsoft's current best-practice guidance recommends UAMIs for many of these scenarios and generally favors them across a broader set of deployment patterns than system-assigned identities. ([Microsoft Learn][1])

---

### **1. Multiple resources genuinely need the same identity**

Example:

```text
Payment workload

App Service A ─┐
App Service B ─┼→ id-payment-runtime
Function App  ─┘
                     ↓
              Key Vault Secrets User
                     ↓
              kv-payment-prod
```

If all three are components of the **same security boundary** and require exactly the same access, one UAMI can reduce duplicated identity and role-assignment management.

Microsoft explicitly lists multi-resource workloads as a UAMI use case. ([Microsoft Learn][2])

---

### **2. I need to pre-authorize identity before deploying compute**

Suppose Terraform needs to provision:

```text
UAMI
 ↓
RBAC
 ↓
App Service
```

I can do:

```text
Phase 1
Create id-payment-prod

Phase 2
Assign:
Key Vault Secrets User

Phase 3
Deploy App Service

Phase 4
Attach id-payment-prod
```

This is deterministic.

With a system-assigned identity:

```text
Create App Service
      ↓
identity created
      ↓
principal becomes known
      ↓
create RBAC assignment
```

That ordering can make deployment workflows more complex.

Microsoft specifically calls out **pre-authorization before the workload exists** as a major UAMI advantage. ([Microsoft Learn][3])

---

### **3. Resource replacement should not change identity**

Imagine blue-green App Service deployment:

```text
Blue App
  ↓
id-orders-prod
  ↓
Key Vault

Deploy Green App
  ↓
attach same id-orders-prod
```

After cutover:

```text
Blue
→ deleted

id-orders-prod
→ survives
```

No need to recreate all downstream RBAC merely because the compute resource changed.

This is particularly valuable in immutable-infrastructure designs.

---

### **4. Ephemeral or rapidly created compute**

Example:

```text
VMSS
      ↓
100 VMs created
      ↓
instances replaced frequently
```

If every VM gets a new system-assigned identity, Microsoft Entra must continually create and eventually clean up many service-principal objects.

A UAMI can be created once and attached to the relevant compute instances.

Microsoft specifically recommends UAMI for rapid resource creation because it reduces identity-object creation overhead and potential Entra throttling/replication issues. ([Microsoft Learn][3])

---

### **5. Separation of duties**

A UAMI lets identity administration happen separately from application deployment.

For example:

```text
Security/Platform Team
      ↓
creates UAMI
      ↓
grants RBAC

Application Team
      ↓
deploys App Service
      ↓
attaches approved UAMI
```

The app team doesn't need permission to:

```text
create arbitrary Entra identities
create arbitrary role assignments
```

This is very useful in enterprise platform engineering.

Microsoft explicitly identifies separation of resource creation and identity administration as a UAMI benefit. ([Microsoft Learn][3])

---

### **6. AKS Workload Identity**

A very important use case:

```text
AKS Pod
  ↓
Kubernetes ServiceAccount
  ↓
OIDC token
  ↓
Federated identity credential
  ↓
User-assigned Managed Identity
  ↓
Key Vault
```

A UAMI can represent the Azure-side workload identity.

Example:

```text
namespace: payments
serviceAccount: payment-api
        ↓
UAMI: id-payment-api
        ↓
Key Vault Secrets User
        ↓
kv-payments
```

No Azure credential is stored in:

```text
Kubernetes Secret
```

---

### **7. GitHub/OIDC federation**

Another use case:

```text
GitHub Actions
      ↓
OIDC
      ↓
UAMI federated identity credential
      ↓
Azure RBAC
```

For example:

```text
id-github-acr-push
      ↓
only repository-writer permissions
      ↓
specific ACR/repository
```

This gives the CI workflow a stable Azure identity without storing a client secret. Microsoft supports workload identity federation directly on user-assigned Managed Identities. ([Microsoft Learn][5])

---

### **When would I prefer system-assigned instead?**

If I have:

```text
one Azure resource
+
unique permissions
+
identity should disappear
with the resource
```

then system-assigned can be simpler.

Example:

```text
one Function App
      ↓
unique Storage access
```

and nobody else should ever use that identity.

Microsoft's current best-practice guidance says system-assigned identities remain appropriate when each resource requires its own unique identity and the identity should follow the resource lifecycle. ([Microsoft Learn][3])

---

### **Don't create one enterprise-wide UAMI**

Bad architecture:

```text
id-everything-prod
       ↓
VMs
Functions
App Services
AKS
Automation
Monitoring
       ↓
Contributor everywhere
```

Compromise one workload:

```text
↓
inherit enormous permission blast radius
```

Better:

```text
id-payment-api
→ payment-api permissions

id-order-worker
→ queue/storage permissions

id-monitoring
→ monitoring permissions
```

Microsoft's newer guidance explicitly advises against reusing UAMIs across unrelated workloads simply because reuse is technically possible. ([Microsoft Learn][4])

---

### **Decision model**

```text
Need Managed Identity
       ↓
Does identity need independent lifecycle?
       │
      Yes → UAMI
       │
Does same trusted workload span multiple resources?
       │
      Yes → UAMI
       │
Need pre-authorization before compute exists?
       │
      Yes → UAMI
       │
Resource frequently replaced?
       │
      Yes → UAMI

Otherwise:
One resource + unique identity + coupled lifecycle
→ System-assigned may be simpler
```

> **In an interview, I would say:**
> “I use a user-assigned Managed Identity when I need a stable identity independent of any one compute resource. Typical cases are multiple instances of the same workload sharing identical permissions, blue-green or frequently recreated resources, VM scale sets, pre-authorizing RBAC before the application exists, AKS Workload Identity, or OIDC federation from CI. It also supports separation of duties because the platform team can provision and authorize the identity before the application team attaches it. I don't reuse one UAMI across unrelated workloads, because that increases the compromise blast radius.”

**Memory line:**
**Use UAMI when the identity should outlive, precede, or safely span the compute resources using it.**

**Interview trap:**
“Can be shared” does **not** mean “should be shared everywhere.”

**Keywords:**
UAMI, independent lifecycle, pre-authorization, resource replacement, AKS Workload Identity, OIDC, separation of duties

**Likely follow-ups:**

* When would system-assigned be better?
* Can a UAMI be attached to multiple resources?
* Why is UAMI useful for Terraform deployment ordering?
* How does UAMI work with AKS Workload Identity?
