## **T19-M03. What happens to a system-assigned identity when its Azure resource is deleted?**

**Answer:**
A **system-assigned Managed Identity is automatically deleted when its parent Azure resource is deleted**, because the identity's lifecycle is tied directly to that resource. It cannot simply be detached and reused by another Azure resource. ([Microsoft Learn][1])

```text
App Service / VM / Function
          │
          └── System-assigned MI
                    │
             Resource deleted
                    ↓
        Managed Identity deleted
```

This is the fundamental difference from a **user-assigned Managed Identity**, whose lifecycle is independent.

---

### **Example**

Suppose:

```text
App Service:
payment-api

System-assigned identity:
Principal ID = abc-123
```

And RBAC contains:

```text
abc-123
   ↓
Key Vault Secrets User
   ↓
kv-payment-prod
```

If I delete:

```text
payment-api
```

Azure also deletes its system-assigned identity:

```text
payment-api          → deleted
abc-123 identity     → deleted
```

A newly created `payment-api` does **not** automatically get the same identity.

Instead:

```text
New App Service
      ↓
Enable system-assigned MI
      ↓
NEW principal/object ID
```

So permissions may need to be assigned again.

---

### **Important nuance: RBAC assignments can remain**

This is a strong interview detail.

Deleting the Managed Identity does **not necessarily clean up all Azure RBAC role assignments referring to it**.

You can end up with:

```text
Role Assignment
      ↓
Principal:
Identity not found
```

Microsoft recommends cleaning up these orphaned role assignments because they still consume role-assignment quota. ([Microsoft Learn][1])

So lifecycle can look like:

```text
Azure resource deleted
       ↓
System-assigned MI deleted
       ↓
Some old RBAC assignments
may remain orphaned
       ↓
Clean them up
```

---

### **What about already-issued access tokens?**

Another useful nuance: deleting the identity prevents it from requesting **new tokens**, but an access token issued before deletion may remain valid until its normal expiry depending on the target service's authorization behavior. ([Microsoft Learn][2])

So:

```text
Identity deleted
      ↓
New token request ✗

Already-issued token
      ↓
may work until expiry
```

This is normal token-based authentication behavior and one reason access tokens are intentionally short-lived.

---

### **System-assigned vs user-assigned lifecycle**

```text
SYSTEM-ASSIGNED

Azure Resource
      │
      └── Identity
             ↓
Delete resource
             ↓
Delete identity
```

versus:

```text
USER-ASSIGNED

UAMI ──────────────┐
                   │
Azure Resource A ←─┤
Azure Resource B ←─┘

Delete Resource A
      ↓
UAMI still exists
```

That lifecycle difference is one of the main reasons to choose UAMI for immutable or frequently recreated infrastructure.

> **In an interview, I would say:**
> “A system-assigned Managed Identity shares the lifecycle of its Azure resource. When the VM, App Service, Function, or other parent resource is deleted, Azure automatically deletes that identity as well. If I recreate the resource, it receives a new identity and principal ID, so permissions may need to be recreated. One operational nuance is that Azure RBAC assignments referencing the deleted identity can remain as orphaned `Identity not found` assignments, so I clean those up.”

**Memory line:**
**System-assigned identity lives and dies with its Azure resource.**

**Interview trap:**
Do not assume recreating a resource recreates **the same identity**. It gets a new principal.

**Keywords:**
System-assigned Managed Identity, lifecycle, principal ID, orphaned RBAC assignment, access token

**Likely follow-ups:**

* What happens to its RBAC assignments?
* Does recreating the resource restore the same identity?
* How is user-assigned identity different?
* What happens to already-issued tokens?

## **T19-M04. Why are managed identities preferred over client secrets?**

**Answer:**
Managed Identities are preferred because they let Azure workloads authenticate to Microsoft Entra ID **without storing or managing a long-lived client secret or certificate**. Azure manages the identity's underlying credential lifecycle, while the workload obtains short-lived Entra access tokens when required. Microsoft recommends Managed Identity for Azure-hosted service-to-service authentication where supported. ([Microsoft Learn][3])

### **Client-secret model**

```text
Application
    ↓
CLIENT_ID
CLIENT_SECRET
    ↓
Microsoft Entra
    ↓
Access token
```

Now I have to solve:

```text
Where is the secret stored?
Who can read it?
When does it expire?
Who rotates it?
How is the new value deployed?
What if Git/CI logs expose it?
```

---

### **Managed Identity model**

```text
Azure App
   ↓
Managed Identity
   ↓
Microsoft Entra ID
   ↓
short-lived access token
   ↓
Key Vault / Storage / SQL
```

Application configuration no longer contains:

```text
AZURE_CLIENT_SECRET
```

Microsoft specifically describes Managed Identities as a way to replace secrets, passwords, keys, and application-managed certificates for supported Azure service-to-service authentication. ([Microsoft Learn][3])

---

### **1. No long-lived secret to leak**

With a client secret:

```text
Client secret
valid for months
     ↓
accidentally committed to Git
     ↓
attacker obtains reusable credential
```

Potential exposure locations include:

```text
Git repository
CI/CD variables
pipeline logs
.env files
Terraform variables
container environment
Kubernetes Secrets
developer laptops
```

With Managed Identity:

```text
No reusable Azure client secret
stored by the application
```

That removes an entire secret-management attack surface.

---

### **2. No manual secret rotation**

Client secret lifecycle:

```text
Create
 ↓
Store
 ↓
Distribute
 ↓
Monitor expiration
 ↓
Rotate
 ↓
Update workloads
 ↓
Remove old secret
```

Managed Identity:

```text
Azure manages underlying credential
          ↓
Application requests token
          ↓
Microsoft Entra issues token
```

No yearly:

> “Production is down because the service principal secret expired.”

type of incident.

---

### **3. Short-lived access tokens**

Managed Identity gives the workload an Entra access token for the target resource.

Conceptually:

```text
Managed Identity
      ↓
request token for
https://vault.azure.net
      ↓
short-lived token
      ↓
Key Vault
```

The application doesn't receive the long-lived credential Azure uses internally to establish that identity.

---

### **4. Works naturally with Azure RBAC**

Authentication:

```text
Managed Identity
→ who is calling?
```

Authorization:

```text
Azure RBAC
→ what may it access?
```

Example:

```text
payment-api MI
       ↓
Storage Blob Data Reader
       ↓
storage-payment-prod
```

Not:

```text
payment-api MI
       ↓
Contributor
       ↓
entire subscription
```

Managed Identity makes secretless authentication easier, but **least privilege is still my responsibility**.

---

### **5. Easier credential governance**

Imagine 100 applications using client secrets:

```text
100 applications
      ↓
100+ secrets
      ↓
expiration inventory
rotation workflows
secret storage
leak monitoring
```

With Managed Identities:

```text
100 Azure workloads
      ↓
Azure-managed identities
      ↓
RBAC assignments
```

The operational focus shifts from:

```text
credential lifecycle
```

toward:

```text
identity + authorization lifecycle
```

which is far cleaner.

---

### **6. Better example: App Service → Key Vault**

Avoid:

```text
App Service
     ↓
client-secret environment variable
     ↓
service principal
     ↓
Key Vault
```

Prefer:

```text
App Service
     ↓
Managed Identity
     ↓
Entra token
     ↓
Key Vault Secrets User
     ↓
Key Vault
```

---

### **7. Managed Identity isn't always available**

Important distinction:

Managed Identity is ideal when the workload runs on a supported Azure service.

For something external such as:

```text
GitHub-hosted runner
GitLab SaaS runner
another cloud
```

I generally can't just “attach a normal Azure Managed Identity” to that external compute.

Instead, the modern pattern is:

```text
External workload
      ↓
OIDC
      ↓
Workload Identity Federation
      ↓
Microsoft Entra identity
```

rather than falling back to a client secret.

---

### **Security preference**

For modern Azure architectures:

```text
Azure-hosted workload
        ↓
Managed Identity

External CI/workload
        ↓
Workload Identity Federation / OIDC

Only when necessary
        ↓
Certificate / secret-based credentials
```

> **In an interview, I would say:**
> “Managed Identities are preferred because Azure manages the workload identity's credentials, so my application doesn't need to store or rotate a client secret or certificate. The workload obtains short-lived Microsoft Entra access tokens and I authorize the identity with least-privilege RBAC. That removes common risks such as secrets leaking into repositories or CI logs and production outages caused by expired credentials. For workloads outside Azure, I would normally use workload identity federation rather than reverting to a long-lived secret.”

**Memory line:**
**Managed Identity removes the long-lived credential; RBAC still controls what the workload can do.**

**Interview trap:**
Do not say Managed Identity is more secure because it needs **no credentials at all**. Credentials exist internally; **Azure manages them rather than your application**.

**Keywords:**
Managed Identity, secretless authentication, short-lived token, credential rotation, Entra ID, Azure RBAC

**Likely follow-ups:**

* Does Managed Identity eliminate RBAC?
* How does the application obtain a token?
* What would you use for GitHub Actions?
* What if the target service doesn't support Entra authentication?

## **T19-M05. What is an Entra application registration?**

**Answer:**
A **Microsoft Entra application registration registers an application with Microsoft Entra ID so Entra can identify the application and participate in its authentication and authorization flows**. Registering an application creates an **application object** in its home tenant and, normally, a corresponding **service principal** for that tenant. ([Microsoft Learn][4])

The easiest mental model is:

```text
App Registration
      ↓
Creates application identity definition
      ↓
Application Object
      ↓
Service Principal
in the tenant
```

---

### **What does the application object represent?**

Think of the application object as the application's **identity definition or blueprint**.

It contains configuration such as:

```text
Application / Client ID
Supported account types
Redirect URIs
Authentication configuration
Certificates / secrets
Federated credentials
API permissions
Exposed APIs/scopes
Application roles
```

Microsoft describes the application object as the template from which service principals are created. ([Microsoft Learn][4])

---

### **Example**

You build:

```text
internal-company-api
```

and register it with Microsoft Entra.

You receive something like:

```text
Application name:
internal-company-api

Application (client) ID:
11111111-2222-3333-4444-555555555555

Directory (tenant) ID:
aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee
```

Now Microsoft Entra knows that:

```text
this software application exists
```

and can participate in authentication/token flows involving it.

---

### **Application ID vs Object ID**

Common interview trap.

```text
Application / Client ID
→ identifies the application logically

Object ID
→ identifies this specific directory object
  inside Microsoft Entra
```

For a multitenant application:

```text
Application ID
→ same application identity across tenants

Service Principal Object ID
→ different in each tenant
```

Microsoft explicitly distinguishes the globally identifying Application/Client ID from tenant-specific object IDs. ([Microsoft Learn][5])

---

### **Example: web application login**

```text
User
  ↓
Web Application
  ↓
Microsoft Entra
  ↓
Authentication
  ↓
ID/access token
  ↓
Application
```

The app registration contains information Entra needs for that integration, such as:

```text
redirect URI
supported account types
permissions/scopes
```

---

### **Example: automation**

An application registration can also represent a non-interactive workload:

```text
Terraform automation
      ↓
Application Registration
      ↓
Service Principal
      ↓
Azure RBAC
      ↓
Azure
```

Authentication could use:

```text
OIDC federation        ← preferred where possible
certificate
client secret
```

The application registration identifies the application; the service principal is the security principal operating in the tenant.

---

### **App registrations vs Enterprise applications**

A very useful portal distinction:

```text
Microsoft Entra
│
├── App registrations
│     ↓
│   Application objects
│
└── Enterprise applications
      ↓
    Service principals
```

Microsoft's documentation explicitly says the **App registrations** experience manages application objects, while **Enterprise applications** primarily exposes service principal objects in the tenant. ([Microsoft Learn][4])

---

### **Strong interview answer**

> “An Entra application registration registers software with Microsoft Entra ID and creates an application object in its home tenant. That application object acts as the identity blueprint and contains settings such as the client ID, redirect URIs, authentication configuration, API permissions, roles, and credentials or federated credentials. A corresponding service principal represents the application as a security principal in a tenant. In the portal, App registrations primarily shows application objects, while Enterprise applications primarily shows service principals.”

**Memory line:**
**App registration creates the application identity blueprint that Entra understands.**

**Interview trap:**
Do not use **App Registration**, **application object**, and **service principal** as if they are exactly the same object.

**Keywords:**
App Registration, application object, Client ID, Object ID, redirect URI, API permissions, Enterprise Applications

**Likely follow-ups:**

* App registration vs service principal?
* Client ID vs Object ID?
* What is shown under Enterprise Applications?
* Can one application registration have multiple service principals?

## **T19-M06. What is the relationship between an application registration and service principal?**

**Answer:**
The **application registration creates the application's application object—the global/home-tenant definition or blueprint—while a service principal is the tenant-local security identity representing an instance of that application**.

The relationship is generally:

```text
One Application Object
        ↓
One or more Service Principals
```

Microsoft describes this as a **one-to-many relationship**: one application object can have service principals in multiple tenants where that application is used. ([Microsoft Learn][4])

---

### **Think “class vs instance”**

A useful interview analogy:

```text
Application Object
→ class / blueprint

Service Principal
→ instance of that application
  inside a tenant
```

Example:

```text
Application Registration
HR SaaS Application
        ↓
Application Object
Client ID = abc123
        │
        ├── Service Principal
        │   Contoso tenant
        │
        ├── Service Principal
        │   Fabrikam tenant
        │
        └── Service Principal
            Adatum tenant
```

The same application can therefore have different tenant-local:

```text
permissions
consent
assignments
policies
```

through each service principal. ([Microsoft Learn][4])

---

### **Single-tenant application**

For a normal internal application:

```text
Home tenant
    ↓
Application Registration
    ↓
Application Object
    ↓
Service Principal
```

So you commonly have:

```text
1 application object
+
1 application-type service principal
```

in that home tenant.

When you register an application, Microsoft Entra normally creates the home-tenant service principal automatically. ([Microsoft Learn][4])

---

### **Multitenant application**

Suppose company A develops:

```text
Payroll SaaS
```

Home tenant:

```text
Company A
   ↓
Application Object
App ID = XYZ
```

Company B uses the application and grants consent:

```text
Company B tenant
      ↓
Service Principal
for App ID = XYZ
```

Company C also uses it:

```text
Company C tenant
      ↓
another Service Principal
for App ID = XYZ
```

Architecture:

```text
                Application Object
                 App ID = XYZ
                       │
             ┌─────────┼─────────┐
             ↓         ↓         ↓
           SP-A       SP-B      SP-C
         Tenant A   Tenant B  Tenant C
```

The application ID remains the same, but each service principal has its own tenant-specific object ID. ([Microsoft Learn][5])

---

### **Where do permissions live?**

This needs a little nuance.

The application object can define things such as:

```text
requested API permissions
application roles
OAuth scopes
authentication configuration
```

The tenant-local service principal represents:

```text
consented permissions
tenant-local assignments
access policies
users/groups assigned to application
```

So:

```text
Application Object
→ what the application is / declares

Service Principal
→ how that application instance
  operates inside this tenant
```

---

### **Azure RBAC example**

Suppose:

```text
Application:
terraform-deployer

Application Client ID:
abc123
```

Its service principal in the production tenant has:

```text
Object ID:
sp-789
```

Then Azure RBAC assignment is conceptually made to:

```text
Service Principal object
sp-789
      ↓
Contributor
      ↓
rg-platform-prod
```

The service principal is the actual **security principal** Microsoft Entra/Azure uses for tenant-local access. ([Microsoft Learn][4])

---

### **Portal mapping**

```text
Entra ID
│
├── App registrations
│      ↓
│   Application Object
│
└── Enterprise applications
       ↓
   Service Principal
```

That's a very handy way to remember it in interviews.

---

### **Important exception: Managed Identities**

A subtle but excellent distinction:

Not **every** service principal necessarily has a normal app-registration application object.

Managed Identities are represented in Entra by a special **Managed Identity type of service principal**, and Microsoft notes that these don't have the normal associated application object that application-type service principals do. ([Microsoft Learn][4])

So when discussing:

```text
App Registration ↔ Service Principal
```

we're specifically talking about the **application-type service principal relationship**.

---

### **Strong interview answer**

> “An application registration creates an application object in its home tenant. I think of that object as the application's global definition or blueprint. A service principal is the concrete tenant-local security identity representing that application where it is used. For a single-tenant application there's usually one application object and one corresponding service principal in the home tenant. For a multitenant application, the same application object can be represented by a different service principal in every customer tenant, each with its own object ID, consent, assignments, and tenant-specific configuration.”

**Memory line:**
**Application object = blueprint; service principal = tenant-local instance/security identity.**

**Interview trap:**
Do not say:

```text
1 application registration
=
always exactly 1 service principal
```

A multitenant application can have **multiple service principals across tenants**.

**Keywords:**
Application object, service principal, App Registration, Enterprise Application, tenant, Client ID, Object ID, multitenant

**Likely follow-ups:**

* Why does a multitenant app have multiple service principals?
* Client ID vs service-principal Object ID?
* What appears under Enterprise Applications?
* Does a Managed Identity have an application object?
