## **T19-M07. How does GitHub Actions OIDC authentication to Azure work?**

**Answer:**
GitHub Actions OIDC authentication uses **workload identity federation** so a GitHub workflow can authenticate to Microsoft Entra ID **without storing an Azure client secret**.

The workflow gets a short-lived OIDC token from GitHub. Microsoft Entra validates that token against a configured **federated identity credential**, then exchanges it for an Azure access token. The Azure identity—an application/service principal or user-assigned managed identity—still needs appropriate Azure RBAC. ([Microsoft Learn][1])

### **Authentication flow**

```text
GitHub Actions workflow
        ↓
GitHub OIDC provider
        ↓
short-lived OIDC token
        ↓
Microsoft Entra ID
        ↓
validate federated trust
        ↓
Azure access token
        ↓
ARM / ACR / Key Vault / Azure APIs
```

There is no:

```text
AZURE_CLIENT_SECRET
```

required.

---

### **1. Create an Azure-side workload identity**

I can use either:

```text
Microsoft Entra App Registration
        ↓
Service Principal
```

or:

```text
User-assigned Managed Identity
```

Microsoft currently supports federated credentials on both for GitHub Actions authentication. ([Microsoft Learn][1])

Example:

```text
UAMI:
id-github-prod-deploy
```

Then give that identity only the Azure permissions the workflow needs.

For example:

```text
id-github-prod-deploy
        ↓
Contributor
        ↓
rg-payment-prod
```

rather than:

```text
Owner
↓
entire subscription
```

---

### **2. Configure the federated identity credential**

The important trust claims are:

```text
Issuer
Subject
Audience
```

Conceptually:

```text
Issuer:
GitHub OIDC provider

Subject:
specific repository /
branch / environment

Audience:
api://AzureADTokenExchange
```

For example, I can restrict trust to:

```text
Repository:
company/payment-api

Environment:
production
```

rather than:

```text
all GitHub repositories
```

Microsoft Entra validates the external token against this trust relationship before issuing its own access token. ([Microsoft Learn][2])

---

### **3. Workflow needs `id-token: write`**

A GitHub Actions job needs permission to request its OIDC token:

```yaml
permissions:
  id-token: write
  contents: read
```

Then Azure Login can authenticate:

```yaml
- uses: azure/login@v2
  with:
    client-id: ${{ secrets.AZURE_CLIENT_ID }}
    tenant-id: ${{ secrets.AZURE_TENANT_ID }}
    subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
```

Microsoft's current Azure Login example explicitly requires `id-token: write`. ([Microsoft Learn][1])

Importantly:

```text
Client ID
Tenant ID
Subscription ID
```

identify where to authenticate.

They are **not equivalent to a reusable Azure client secret**.

---

### **4. What actually happens at runtime?**

```text
Workflow starts
      ↓
azure/login requests
GitHub OIDC token
      ↓
GitHub signs short-lived JWT
      ↓
azure/login sends token
to Microsoft Entra
      ↓
Entra checks:
issuer
subject
audience
      ↓
match?
  /       \
no         yes
↓           ↓
fail      issue Azure token
```

Then commands such as:

```bash
az account show
az acr login ...
terraform apply
```

operate using that Azure token.

---

### **5. Authentication and authorization remain separate**

OIDC succeeds:

```text
GitHub → Entra authentication ✓
```

but if the Azure identity has no permissions:

```text
terraform apply
        ↓
AuthorizationFailed
```

So:

```text
OIDC / federation
→ Authentication

Azure RBAC
→ Authorization
```

---

### **6. Why this is better than a client secret**

Old pattern:

```text
GitHub Secret
AZURE_CLIENT_SECRET
      ↓
valid for months
```

Risk:

```text
repository compromise
log leakage
secret copying
rotation failure
expiration outage
```

OIDC:

```text
workflow
  ↓
short-lived token
  ↓
specific trusted repository/context
  ↓
expires automatically
```

This dramatically reduces reusable credential exposure.

---

### **Production hardening**

For production CI/CD I would combine OIDC with:

```text
Protected GitHub environment
        ↓
required reviewers
        ↓
restricted OIDC subject
        ↓
short-lived federation
        ↓
least-privilege Azure RBAC
```

and also protect the workflow itself through branch protections and trusted/pinned actions.

> **In an interview, I would say:**
> “GitHub Actions OIDC uses workload identity federation. The workflow receives a short-lived OIDC token from GitHub and presents it to Microsoft Entra. Entra validates the token's issuer, subject, and audience against a federated identity credential configured on an application or user-assigned Managed Identity. If the trust matches, Entra issues an Azure access token. The workflow therefore doesn't need a long-lived Azure client secret, although the Azure identity still requires least-privilege RBAC.”

**Memory line:**
**GitHub OIDC = GitHub proves the workflow identity, Entra exchanges that proof for a short-lived Azure token.**

**Interview trap:**
`id-token: write` does **not give the workflow Azure permissions**. It only lets GitHub issue the OIDC token.

**Keywords:**
GitHub Actions, OIDC, `azure/login`, federated identity credential, `id-token: write`, issuer, subject, audience

**Likely follow-ups:**

* What happens if the federated subject doesn't match?
* Why is OIDC safer than a client secret?
* What RBAC role should GitHub receive?
* Can a UAMI be used instead of an App Registration?

# **Hard**

## **T19-H01. How would you eliminate long-lived Azure credentials from CI/CD?**

**Answer:**
I would replace stored service-principal secrets with **workload identity federation/OIDC wherever the CI platform supports it**. The CI system proves its identity using a short-lived token, Microsoft Entra exchanges that token for an Azure access token, and the resulting Azure identity receives **least-privilege RBAC at the smallest required scope**.

For GitHub Actions:

```text
GitHub Actions
      ↓
OIDC
      ↓
Microsoft Entra
      ↓
App Registration / UAMI
      ↓
Azure RBAC
      ↓
Azure resources
```

No long-lived:

```text
AZURE_CLIENT_SECRET
```

is stored. Microsoft explicitly supports this model for GitHub Actions. ([Microsoft Learn][1])

---

### **1. Inventory existing credentials first**

I would identify:

```text
CI/CD credentials
│
├── Service-principal client secrets
├── Certificates/private keys
├── Storage account keys
├── ACR passwords/admin credentials
└── Other static Azure credentials
```

Then map:

```text
Which pipeline uses it?
What resource does it access?
What permissions does it actually need?
```

Otherwise I may replace the authentication mechanism while leaving excessive authorization intact.

---

### **2. Replace service-principal secrets with federation**

Old:

```text
CI
 ↓
Client ID
Client Secret
 ↓
Entra
```

New:

```text
CI identity provider
      ↓
short-lived OIDC token
      ↓
Federated Identity Credential
      ↓
Microsoft Entra
      ↓
short-lived Azure token
```

The external token is validated against the Entra trust relationship before the Azure token is issued. ([Microsoft Learn][2])

---

### **3. Make the trust narrow**

I wouldn't create federation like:

```text
any repo
→ production identity
```

Instead restrict it to the intended:

```text
organization
repository
branch
environment
```

For example:

```text
payment-api
+
production environment
      ↓
id-payment-prod-deploy
```

while:

```text
feature branch
fork
other repository
```

cannot impersonate the production identity.

---

### **4. Give every workflow only the permissions it needs**

Bad:

```text
CI identity
→ Owner
→ Subscription
```

Better:

```text
Infrastructure pipeline
→ Contributor
→ specific Resource Group
```

And perhaps:

```text
Image build pipeline
→ ACR push role
→ specific registry/repository
```

while:

```text
Deployment pipeline
→ only deployment-specific permissions
```

This reduces blast radius if CI is compromised.

---

### **5. Separate identities by trust boundary**

I wouldn't use:

```text
id-all-ci
```

for:

```text
development
staging
production
security automation
image build
infrastructure deployment
```

Instead:

```text
id-github-dev
id-github-prod
id-image-publisher
id-terraform-platform
```

with different federated trusts and RBAC.

Then compromise of:

```text
development pipeline
```

doesn't automatically become:

```text
production subscription compromise
```

---

### **6. Azure-hosted self-hosted runners can use Managed Identity**

If a self-hosted CI runner runs on a supported Azure resource:

```text
Azure VM runner
      ↓
Managed Identity
      ↓
Microsoft Entra
      ↓
Azure
```

can be another secretless pattern.

For an external SaaS runner such as GitHub-hosted runners:

```text
OIDC federation
```

is generally the cleaner model.

---

### **7. Remove legacy credentials after migration**

A common mistake is:

```text
OIDC configured ✓
but
old client secret still valid
```

Then the long-lived attack path still exists.

Migration should finish with:

```text
Validate OIDC
      ↓
remove CI secret
      ↓
delete/revoke old
service-principal credential
      ↓
verify pipeline still succeeds
```

---

### **8. Protect the workflow identity itself**

Secretless authentication doesn't make CI trustworthy by magic.

I still protect:

```text
main branch
production environment
workflow files
third-party actions
required reviewers
CODEOWNERS
```

because an attacker who can modify a trusted workflow may be able to request the legitimate federated token.

The threat shifts from:

```text
steal stored Azure secret
```

toward:

```text
compromise trusted CI execution context
```

So CI controls still matter.

---

### **Production architecture**

```text
Developer
    ↓
Pull Request
    ↓
Protected main
    ↓
Approved GitHub workflow
    ↓
OIDC token
    ↓
Microsoft Entra
    ↓
id-prod-deploy
    ↓
least-privilege RBAC
    ↓
Production Azure scope
```

> **In an interview, I would say:**
> “I would inventory every static Azure credential used by CI and replace service-principal secrets with workload identity federation wherever possible. For GitHub Actions I configure an Entra application or UAMI with a federated credential restricted to the trusted repository, branch, or environment. The workflow requests a short-lived GitHub OIDC token, Entra exchanges it for an Azure token, and I give that identity least-privilege RBAC at the smallest scope. I use separate identities for production and lower environments, protect the workflow and environment with branch controls and approvals, and finally revoke the old client secrets so there is no legacy authentication path left.”

**Memory line:**
**Secretless CI = short-lived federation + narrow trust + narrow RBAC + delete the old secret.**

**Interview trap:**
Simply adding OIDC while leaving the old client secret active **does not eliminate the long-lived credential risk**.

**Keywords:**
CI/CD, OIDC, workload identity federation, secretless, least privilege, RBAC, protected environment

**Likely follow-ups:**

* What happens if the CI repository is compromised?
* Should dev and prod use the same federated identity?
* How would you restrict federation to `main`?
* What do you do with the old service-principal secret?

## **T19-H02. How would a pod running in AKS access Key Vault without a Kubernetes Secret containing Azure credentials?**

**Answer:**
I would use **Microsoft Entra Workload Identity for AKS**. The pod uses a Kubernetes ServiceAccount identity, AKS exposes an OIDC issuer, and Microsoft Entra trusts that ServiceAccount through a **federated identity credential**. The pod's short-lived ServiceAccount token is exchanged for an Entra access token, which the application or Key Vault CSI provider then uses to access Key Vault.

There is no:

```text
AZURE_CLIENT_SECRET
```

stored in a Kubernetes Secret. Microsoft currently recommends Workload Identity for this pattern. ([Microsoft Learn][3])

---

### **Architecture**

```text
AKS Pod
   ↓
Kubernetes ServiceAccount
   ↓
projected ServiceAccount token
   ↓
AKS OIDC issuer
   ↓
Microsoft Entra federation
   ↓
User-assigned Managed Identity
   ↓
Key Vault Secrets User
   ↓
Azure Key Vault
```

This is one of the most important AKS identity architectures to know.

---

### **1. Enable AKS OIDC and Workload Identity**

Cluster needs:

```text
OIDC issuer
+
Workload Identity
```

Conceptually:

```bash
az aks create \
  ... \
  --enable-oidc-issuer \
  --enable-workload-identity
```

The OIDC issuer gives Entra a trusted place to validate the Kubernetes ServiceAccount token. ([Microsoft Learn][4])

---

### **2. Create a workload-specific Azure identity**

For example:

```text
UAMI:
id-payment-api
```

Then grant:

```text
Key Vault Secrets User
```

at:

```text
kv-payment-prod
```

Microsoft currently recommends `Key Vault Secrets User` for reading secrets when Key Vault uses Azure RBAC. ([Microsoft Learn][3])

Not:

```text
Owner
→ subscription
```

---

### **3. Create the Kubernetes ServiceAccount**

Example:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-api
  namespace: payments
  annotations:
    azure.workload.identity/client-id: "<UAMI-client-id>"
```

Now the Kubernetes identity is:

```text
namespace:
payments

service account:
payment-api
```

---

### **4. Configure federated identity**

On the Azure identity:

```text
Issuer
→ AKS OIDC issuer

Subject
→ system:serviceaccount:payments:payment-api

Audience
→ api://AzureADTokenExchange
```

Microsoft's current AKS guidance uses this exact ServiceAccount subject structure. ([Microsoft Learn][3])

Flow:

```text
Pod claims:
"I am payments/payment-api"
         ↓
Entra checks configured federation
         ↓
matches?
         ↓
Azure token issued
```

Another ServiceAccount such as:

```text
system:serviceaccount:orders:orders-api
```

doesn't match that trust.

---

### **5. Pod uses the ServiceAccount**

Conceptually:

```yaml
spec:
  serviceAccountName: payment-api
```

and Workload Identity injects/projects the required identity-token information into the workload.

The Azure Identity SDK can then use:

```text
DefaultAzureCredential
```

or the appropriate workload identity credential flow to obtain the Azure token.

Microsoft explains that Entra verifies the ServiceAccount token using the AKS OIDC issuer and exchanges it for an Entra token. ([Microsoft Learn][5])

---

### **6. Application can access Key Vault directly**

Preferred if the application can use the Azure SDK:

```text
Pod
 ↓
Azure Identity SDK
 ↓
Workload Identity
 ↓
Entra token
 ↓
Key Vault SDK
 ↓
secret
```

No Azure credential is stored in Kubernetes.

This provides strong workload-level isolation.

---

### **7. Or use Key Vault Secrets Store CSI Driver**

If the application expects file-based secrets:

```text
Key Vault
    ↓
CSI Provider
    ↓
Pod volume
/mnt/secrets-store/...
```

With Workload Identity:

```text
CSI Driver requests
Kubernetes ServiceAccount token
        ↓
Azure Key Vault provider
        ↓
exchange for Entra token
        ↓
retrieve Key Vault secret
        ↓
mount file into pod
```

Microsoft's latest AKS guidance explicitly supports this workflow. ([Microsoft Learn][3])

---

### **Important distinction**

The question is:

> without a Kubernetes Secret containing **Azure credentials**

Workload Identity eliminates:

```text
client ID + client secret
```

as Kubernetes credentials.

If using the CSI driver, the actual application secret can be mounted directly from Key Vault:

```text
/mnt/secrets-store/database-password
```

without synchronizing it into a Kubernetes Secret.

So I can avoid both:

```text
Azure credential in K8s Secret
```

and, if desired:

```text
Key Vault secret copied into K8s Secret
```

---

### **8. Identity and networking are separate**

Even perfect Workload Identity can fail if Key Vault is private and networking is wrong.

For private Key Vault:

```text
Pod
 ↓
Private DNS
 ↓
Private Endpoint
 ↓
Key Vault
```

must work too.

So:

```text
Workload Identity
→ authentication

Key Vault RBAC
→ authorization

Private Endpoint/DNS
→ network reachability
```

Three separate layers.

---

### **Production example**

```text
Namespace: payments
        │
        └── ServiceAccount: payment-api
                    │
                    ↓
          Federated Identity
                    ↓
            UAMI: id-payment-api
                    │
                    ↓
          Key Vault Secrets User
                    │
                    ↓
            kv-payments-prod
```

Another workload:

```text
orders/orders-api
```

has:

```text
different ServiceAccount
different UAMI
different Key Vault permission
```

This gives workload-level least privilege.

> **In an interview, I would say:**
> “I would use AKS Workload Identity. I enable the cluster's OIDC issuer and Workload Identity, create a dedicated Kubernetes ServiceAccount and an Azure workload identity such as a UAMI, then create a federated identity credential whose issuer is the AKS OIDC issuer and whose subject is `system:serviceaccount:<namespace>:<serviceaccount>`. The UAMI gets only `Key Vault Secrets User` on the required vault. The pod's projected ServiceAccount token is exchanged for a short-lived Entra token, so no Azure client secret needs to exist in Kubernetes. The application can call Key Vault with the Azure SDK, or I can use the Key Vault Secrets Store CSI Driver to mount secrets as files.”

**Memory line:**
**AKS ServiceAccount token → OIDC federation → Entra token → Key Vault; no Azure secret in Kubernetes.**

**Interview trap:**
Do not confuse:

```text
AKS node/kubelet identity
```

with:

```text
pod Workload Identity
```

The goal here is **workload-specific pod identity**.

**Keywords:**
AKS Workload Identity, OIDC issuer, ServiceAccount, UAMI, federated identity credential, Key Vault, CSI Driver

**Likely follow-ups:**

* What is the federated credential subject?
* Workload Identity vs kubelet identity?
* CSI Driver vs direct SDK access?
* What if Key Vault returns HTTP 403?

## **T19-H03. How would you grant one workload access to one storage account without allowing access to others?**

**Answer:**
I would give that workload a **dedicated Managed Identity or workload identity** and assign the minimum required **Storage data-plane RBAC role directly at that one Storage Account's scope**, not at the Resource Group or Subscription.

For example:

```text
payment-worker identity
        ↓
Storage Blob Data Contributor
        ↓
storage-payment-prod
```

No role assignment exists on:

```text
storage-orders-prod
storage-analytics-prod
other Storage Accounts
```

Microsoft explicitly recommends assigning RBAC at the **smallest scope required**, and specifically gives a Managed Identity accessing one Storage Account as an example where the role should be scoped to that Storage Account rather than the Resource Group or Subscription. ([Microsoft Learn][6])

---

### **Architecture**

```text
                   Azure
                     │
         ┌───────────┼───────────┐
         ↓           ↓           ↓
     Storage A    Storage B   Storage C
     payments     orders      analytics
         ↑
         │
Blob Data Contributor
         │
 payment-worker MI
         ↑
         │
      Workload
```

Result:

```text
Payment workload
→ Storage A ✓

Payment workload
→ Storage B ✗

Payment workload
→ Storage C ✗
```

---

### **1. Give the workload its own identity**

For App Service:

```text
System-assigned MI
```

or:

```text
UAMI:
id-payment-worker
```

For AKS:

```text
Kubernetes ServiceAccount
      ↓
Workload Identity
      ↓
UAMI
```

The important design principle is:

```text
one security boundary
→ dedicated identity
```

rather than sharing:

```text
id-all-applications
```

across unrelated workloads.

---

### **2. Pick the correct data-plane role**

If it only needs to read blobs:

```text
Storage Blob Data Reader
```

If it needs to write/delete blob data:

```text
Storage Blob Data Contributor
```

Do **not** automatically grant:

```text
Contributor
```

because Azure's generic `Contributor` role primarily controls Azure resource management and is not the correct least-privilege answer for blob data access.

---

### **3. Assign the role at Storage Account scope**

Conceptually:

```bash
az role assignment create \
  --assignee-object-id <identity-principal-id> \
  --role "Storage Blob Data Contributor" \
  --scope <storage-account-resource-id>
```

Hierarchy:

```text
Subscription
   ↓
Resource Group
   ↓
Storage Account   ← ROLE HERE
```

Not:

```text
Subscription      ← too broad
```

and normally not:

```text
Resource Group    ← gives access to matching
                     resources throughout RG
```

Microsoft explicitly recommends the smallest appropriate role-assignment scope. ([Microsoft Learn][6])

---

### **4. Scope determines blast radius**

Bad:

```text
payment-worker
       ↓
Storage Blob Data Contributor
       ↓
Subscription
```

Now it may access:

```text
Storage A
Storage B
Storage C
Storage D
...
```

Good:

```text
payment-worker
       ↓
Storage Blob Data Contributor
       ↓
/storageAccounts/stpaymentprod
```

Blast radius:

```text
one identity
+
one role
+
one Storage Account
```

---

### **5. Don't give it Storage Account keys**

Avoid:

```text
STORAGE_ACCOUNT_KEY=...
```

because account keys effectively behave like broad shared credentials and don't provide workload-specific Entra RBAC in the same way.

Prefer:

```text
Managed/Workload Identity
        ↓
Entra token
        ↓
Storage data-plane RBAC
```

This gives:

```text
identity-specific authorization
central revocation
auditable role assignment
no shared account key
```

---

### **6. Network isolation can strengthen it further**

Identity answers:

```text
Who may access this account?
```

Networking answers:

```text
From where may it be reached?
```

For sensitive production Storage:

```text
Workload
   ↓
VNet
   ↓
Private DNS
   ↓
Private Endpoint
   ↓
Storage Account
```

and:

```text
Public network access
→ disabled/restricted
```

So even another identity can't reach the account unless its network path is also allowed.

But importantly:

```text
Private Endpoint
≠ authorization
```

I still need the Storage data-plane role.

---

### **7. AKS example**

```text
Namespace: payments
ServiceAccount: settlement-worker
         ↓
AKS Workload Identity
         ↓
UAMI: id-settlement-worker
         ↓
Storage Blob Data Contributor
         ↓
stpaymentprod
```

Orders pod:

```text
namespace: orders
ServiceAccount: orders-api
```

has no role on:

```text
stpaymentprod
```

so:

```text
authentication may succeed
        ↓
Storage authorization
        ↓
403
```

That's exactly what least privilege should look like.

---

### **8. Be careful with inherited role assignments**

Even if I correctly assign:

```text
Storage Blob Data Reader
→ Storage A
```

the identity may already have:

```text
Storage Blob Data Contributor
→ Subscription
```

from an inherited assignment.

Then the narrow assignment doesn't restrict it.

Azure RBAC permissions are cumulative.

So I inspect:

```text
Role assignments
+
inherited assignments
```

for that identity.

This is a very good troubleshooting/security point.

---

### **9. Complete least-privilege model**

```text
Workload
   ↓
Dedicated Identity
   ↓
Exact data-plane role
   ↓
Exact Storage Account scope
   ↓
Optional private networking
```

I would avoid:

```text
shared identity
+
subscription-wide role
+
Storage account key
```

> **In an interview, I would say:**
> “I would create a dedicated Managed Identity or AKS Workload Identity for that workload and assign only the required Storage data-plane role—for example `Storage Blob Data Reader` or `Storage Blob Data Contributor`—directly at the target Storage Account's resource scope. I wouldn't assign the role at Resource Group or Subscription scope, because that could grant access to other Storage Accounts. I would also avoid Storage account keys and check for inherited broader RBAC assignments. For a sensitive production account I would additionally use a Private Endpoint and restrict public networking, while remembering that networking and RBAC solve different problems.”

**Memory line:**
**Dedicated workload identity + exact data role + exact resource scope = least privilege.**

**Interview trap:**
Adding a narrow role on one Storage Account does **not cancel a broader role already inherited from the Resource Group or Subscription**.

**Keywords:**
Managed Identity, Storage Blob Data Reader, Storage Blob Data Contributor, RBAC scope, least privilege, Private Endpoint

**Likely follow-ups:**

* Why not use `Contributor`?
* What if the identity has a broader inherited role?
* Could you restrict access to only one blob container?
* What would an HTTP 403 from Storage indicate?
