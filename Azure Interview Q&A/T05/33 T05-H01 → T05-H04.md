# 5. 🔴 M IMP — Azure Storage

## Hard

### **T05-H01. How would you prevent a storage account from being accessible from the public internet?**

**Answer:**
For a production storage account that should be private, I would use a **Private Endpoint and disable Public Network Access** on the storage account.

That gives the storage service a private IP inside my VNet and prevents clients from reaching the storage account through its public endpoint. Microsoft specifically recommends this combination when all consumers can reach the account through Private Link. ([Microsoft Learn][1])

A typical design is:

```text
Application / VM / AKS
        │
        │ Private IP
        ↓
Private Endpoint
        │
        ↓
Azure Storage
Public network access = Disabled
```

### **1. Create the appropriate Private Endpoint**

Suppose an application needs Blob Storage.

I create:

```text
Private Endpoint
Subresource: blob
```

inside an appropriate subnet.

The storage endpoint then resolves to a private address such as:

```text
10.20.3.5
```

instead of requiring the application's traffic to reach the public Storage endpoint.

One important detail is that private endpoints are generally **service/subresource-specific**.

If I need both:

```text
Blob
+
File
```

I may need the corresponding private endpoints/DNS configuration for each service.

---

### **2. Configure Private DNS**

This part is critical.

For Blob Storage, I typically integrate the private endpoint with the relevant Azure Private DNS zone, conceptually:

```text
privatelink.blob.core.windows.net
```

The application still connects using the normal storage hostname:

```text
mystorage.blob.core.windows.net
```

but DNS resolves it through the Private Link configuration to:

```text
10.20.3.5
```

So:

```text
Application
    ↓
DNS lookup
    ↓
Private IP
    ↓
Private Endpoint
    ↓
Storage
```

A huge percentage of Private Endpoint problems are actually **DNS problems**.

---

### **3. Disable public network access**

After confirming private connectivity works:

```text
Storage Account
→ Networking
→ Public network access
→ Disabled
```

With public network access disabled, access through the public endpoint is rejected and private endpoint connectivity remains available. ([Microsoft Learn][1])

I would usually configure the Private Endpoint and DNS **before** disabling public access, so I don't accidentally lock out the application.

---

### **4. Authentication is still required**

Private Endpoint solves:

```text
Who can reach the service?
```

It does **not** solve:

```text
Who is authorized to read/write data?
```

So I would combine it with:

```text
Private Endpoint
        +
Microsoft Entra ID
        +
Managed Identity
        +
Azure RBAC
```

For example:

```text
AKS workload
   ↓
Private Endpoint
   ↓
Blob Storage

Authentication:
Workload Identity
   ↓
Entra ID
   ↓
Storage Blob Data Reader
```

### **5. Harden the account further**

Depending on requirements, I would also:

* disable anonymous Blob access,
* prefer Entra ID over Shared Key,
* disable Shared Key authorization where compatible,
* enforce HTTPS,
* use least-privilege data roles,
* use Azure Policy to prevent storage accounts from being deployed with public access.

Microsoft provides built-in policies specifically to audit or deny storage accounts that permit public network access. ([Microsoft Learn][2])

### **If Private Endpoint cannot be used**

A weaker alternative is:

```text
Public endpoint still enabled
+
Storage firewall default deny
+
Allow only specific VNets/IPs
```

That reduces exposure, but it is **not the same as removing public-endpoint exposure**. If the requirement literally says "not accessible from the public internet," my preferred answer is:

> **Private Endpoint + Public Network Access Disabled.**

### **Troubleshooting flow**

If the app cannot connect after privatization:

```text
1. nslookup storage hostname
2. Does it resolve to private IP?
3. Private Endpoint connection approved?
4. VNet/peering/VPN path exists?
5. NSG/route allows traffic?
6. Correct Blob/File subresource?
7. Entra/RBAC permission correct?
```

**Memory line:**
**Private Endpoint makes the path private; disabling public access removes the internet path.**

**Interview trap:**
Do not confuse these:

```text
Private Endpoint created ✅
Public network access still enabled ✅
```

with:

```text
Storage is private-only
```

A Private Endpoint alone does not necessarily mean the public endpoint has been disabled.

**Keywords:** Private Endpoint, Private Link, public network access, Private DNS, Storage firewall, RBAC

**Likely follow-ups:**

* Private Endpoint vs Service Endpoint?
* Why is Private DNS needed?
* Does Private Endpoint replace authentication?
* How would on-premises clients reach the private storage account?

### **T05-H02. How would an application access Blob Storage without storing credentials?**

**Answer:**
For an Azure-hosted application, I would use a **Managed Identity with Microsoft Entra ID and Azure RBAC**.

That allows the application to request short-lived OAuth tokens at runtime instead of storing:

```text
Storage account key
Client secret
SAS token
```

inside application configuration.

Microsoft explicitly recommends Entra ID with managed identities for Blob access where possible. ([Microsoft Learn][3])

### **Example: App Service**

Suppose:

```text
App Service
     ↓
needs to upload files
     ↓
Blob Storage
```

I would do this:

```text
1. Enable managed identity on App Service

2. Assign:
   Storage Blob Data Contributor

3. Application obtains Entra token automatically

4. Blob Storage validates token + RBAC

5. Application reads/writes blobs
```

The architecture becomes:

```text
App Service
    │
    │ Managed Identity
    ↓
Microsoft Entra ID
    │
    │ OAuth token
    ↓
Blob Storage
    │
    ↓
Azure RBAC authorization
```

There is no long-lived Blob password stored in the application.

---

### **System-assigned vs user-assigned identity**

I can use either.

**System-assigned managed identity**

```text
Lifecycle tied to application resource
```

If the App Service or VM is deleted, the identity is deleted.

**User-assigned managed identity**

```text
Independent Azure resource
```

It can be reused by multiple resources and survives replacement of an individual workload.

For a simple single workload, system-assigned identity is often sufficient.

For shared or more controlled identity lifecycle:

```text
User-assigned identity
```

can be useful.

---

### **RBAC must be a data-plane role**

Suppose the application only reads blobs.

I would assign:

```text
Storage Blob Data Reader
```

If it needs read/write/delete:

```text
Storage Blob Data Contributor
```

at the smallest reasonable scope.

For example:

```text
Storage account
     ↓
Container
```

Microsoft distinguishes these data roles from management-plane roles such as ordinary Reader or Contributor. ([Microsoft Learn][4])

### **Application code**

Using a modern Azure SDK, the app can use a credential chain such as `DefaultAzureCredential`.

Conceptually:

```text
BlobServiceClient
        ↓
DefaultAzureCredential
        ↓
Managed Identity
        ↓
Entra token
```

In Azure, it can use the managed identity.

During local development, the same code can often use the developer's Azure CLI or IDE identity.

That means:

```text
Same application code
       ↓
Local → developer Entra identity
Azure → managed identity
```

without putting production secrets into the codebase.

---

### **AKS example**

For AKS, I would use **Microsoft Entra Workload ID**:

```text
AKS Pod
   ↓
Workload Identity
   ↓
Entra ID
   ↓
Storage Blob Data Contributor
   ↓
Blob Storage
```

rather than:

```text
Kubernetes Secret
AZURE_STORAGE_KEY=<long-lived-secret> ❌
```

### **Network access is separate**

Even with correct identity:

```text
Managed Identity ✅
RBAC ✅
```

the request can still fail if:

```text
Private Endpoint / DNS / Firewall ❌
```

So I separate troubleshooting into:

```text
Network path
+
Authentication
+
Authorization
```

**Memory line:**
**Managed Identity → Entra token → RBAC → Blob Storage. No stored secret.**

**Interview trap:**
Do not answer merely:

> “Store the key in Key Vault.”

That protects a credential better, but you're **still managing a credential**.

If the Azure service supports managed identity, the cleaner architecture is to **remove the secret altogether**.

**Keywords:** Managed Identity, Microsoft Entra ID, OAuth, Azure RBAC, DefaultAzureCredential, Workload Identity

**Likely follow-ups:**

* System-assigned vs user-assigned managed identity?
* Which RBAC role would you assign?
* How would AKS access Blob Storage?
* Managed Identity vs storing a secret in Key Vault?

### **T05-H03. What happens during a storage-account regional outage with GRS?**

**Answer:**
With GRS, Azure keeps the primary copy in one region and **asynchronously replicates it to a secondary geographic region**.

If the primary region experiences a major outage, the secondary copy preserves the data, but with ordinary GRS the application **cannot simply start writing to the secondary immediately**. A failover must occur before the secondary becomes the new read/write primary. ([Microsoft Learn][5])

### **Normal GRS state**

```text
Primary Region
    ↓
LRS — Read + Write
    ↓
Asynchronous replication
    ↓
Secondary Region
    ↓
LRS — DR replica
```

For ordinary:

```text
GRS
```

the secondary isn't directly readable during normal operation.

For:

```text
RA-GRS
```

the secondary can be read using its secondary endpoint.

---

### **Regional outage occurs**

Suppose:

```text
Primary Region ❌
```

With GRS:

```text
Application
     ↓
Primary endpoint unavailable
```

Data remains replicated in the secondary, but write operations won't simply redirect automatically in the way an active-active database might.

I would assess the outage and, depending on the situation, initiate a supported **storage account failover**.

---

### **During failover**

Conceptually:

```text
Primary Region ❌
        ↓
Account failover
        ↓
Secondary promoted
        ↓
Storage DNS updated
        ↓
Secondary becomes new primary
        ↓
Read + Write resumes
```

Azure updates the DNS records for the storage service endpoints as part of the failover. ([Microsoft Learn][6])

That is useful because applications can continue using the normal account hostname once DNS propagation/resolution reflects the new primary.

---

### **Critical point: potential data loss**

Geo-replication is:

```text
Asynchronous
```

not synchronous.

Suppose:

```text
12:00:00 → Blob A written in primary
12:00:03 → Region catastrophically fails
```

If that write had not reached the secondary yet:

```text
Secondary may not contain Blob A
```

So customer-managed unplanned failover can involve **data loss equal to replication lag**.

This is the Storage DR concept of:

```text
RPO
Recovery Point Objective
```

Microsoft describes the gap between the latest primary write and the last replicated secondary write as the RPO. ([Microsoft Learn][5])

Before failover, where possible, I would inspect the storage account's replication status / **Last Sync Time** to understand the potential loss window.

### **GRS vs RA-GRS during outage**

With normal GRS:

```text
Primary unavailable
Secondary exists
but no normal secondary read access
```

With RA-GRS:

```text
Primary unavailable
      ↓
Application can read secondary
      ↓
Read-only degraded mode possible
```

This can let an application continue some functionality while deciding whether to fail over. ([Microsoft Learn][7])

For example:

```text
E-commerce outage

Browse products ✅
Read catalog ✅
Upload/change Blob data ❌

until failover restores writes
```

---

### **Do I rely on Microsoft to fail it over automatically?**

No.

Microsoft may perform a platform-managed failover in an extreme catastrophe, but Microsoft's guidance is to build and test your own DR process and not depend solely on a Microsoft-managed failover. ([Microsoft Learn][6])

### **Important post-failover detail**

For a customer-managed failover of **GRS/RA-GRS**, the new primary can become **LRS** after failover, so I must consider restoring the desired geo-redundancy configuration afterward. ([Microsoft Learn][8])

### **My production DR procedure**

```text
1. Confirm primary outage
2. Check Azure Service Health
3. Check replication/Last Sync Time
4. Estimate potential RPO/data loss
5. If RA-GRS, use secondary for reads if designed
6. Decide whether business impact justifies failover
7. Initiate failover
8. Validate DNS/endpoints
9. Validate application read/write
10. Re-establish required redundancy
```

**Memory line:**
**GRS regional outage: secondary has an async copy → failover promotes it → possible RPO/data loss.**

**Interview trap:**
Do not say:

> “GRS automatically gives zero-data-loss regional failover.”

Two problems:

1. geo-replication is **asynchronous**, so RPO isn't necessarily zero;
2. ordinary GRS doesn't provide normal read access to the secondary until failover.

**Keywords:** GRS, regional outage, failover, secondary region, asynchronous replication, RPO, Last Sync Time

**Likely follow-ups:**

* GRS vs RA-GRS during an outage?
* Can recent data be lost?
* What happens to the storage endpoint after failover?
* Is failover automatic?

### **T05-H04. How would you protect critical blobs from accidental or malicious deletion?**

**Answer:**
I would use **layered protection**, because no single Azure Storage feature covers every deletion scenario.

For critical Blob data, my baseline would usually be:

```text
Least-privilege RBAC
        +
Blob versioning
        +
Blob soft delete
        +
Container soft delete
        +
Immutability where required
        +
Backup for broader recovery scenarios
```

Microsoft recommends combining Blob soft delete, container soft delete, and versioning for strong in-account Blob protection, with Azure Backup considered for broader scenarios such as ransomware or account deletion. ([Microsoft Learn][9])

### **1. Prevent unnecessary delete permission**

Protection starts with identity.

If an application only needs to read:

```text
Storage Blob Data Reader
```

I don't give:

```text
Storage Blob Data Contributor
```

If an application needs writes but shouldn't perform broad administration, I design a suitable least-privilege role.

I also prefer:

```text
Managed Identity
+
Entra ID
```

over broadly distributed storage account keys.

The first security principle is:

> **Don't give delete permission to identities that don't need it.**

---

### **2. Enable Blob versioning**

If someone overwrites:

```text
config.json
```

versioning gives me:

```text
v1 → original
v2 → overwritten current
```

so I can restore the previous version.

This is especially useful against:

```text
Accidental overwrite
Bad deployment
Incorrect application write
```

---

### **3. Enable Blob soft delete**

If a blob or version is deleted:

```text
Delete
   ↓
Soft-deleted
   ↓
Recoverable for retention window
```

For example:

```text
Retention = 30 days
```

gives administrators time to recover accidental deletions.

Microsoft recommends enabling soft delete alongside versioning. ([Microsoft Learn][9])

---

### **4. Enable container soft delete**

Blob soft delete and container soft delete solve different problems.

Suppose an administrator accidentally deletes:

```text
Container: production-backups
```

Blob soft delete alone isn't the complete answer.

I also enable:

```text
Container soft delete
```

so the deleted container can be recovered within the configured retention window. ([Microsoft Learn][9])

---

### **5. Use immutable/WORM storage for truly critical data**

For audit, compliance, or security evidence, recovery after deletion may not be enough.

I may need to ensure the blob **cannot be deleted in the first place**.

Then I use:

```text
Immutable Blob Storage
```

with:

```text
Time-based retention
or
Legal hold
```

Example:

```text
Security audit logs
       ↓
WORM policy
Retention: 1 year
       ↓
Read ✅
Modify ❌
Delete ❌
```

An active immutability policy provides a much stronger control against malicious modification/deletion than simple recoverability features. ([Microsoft Learn][10])

---

### **6. Protect the storage account itself**

This is an important distinction.

Blob soft delete protects:

```text
Blob-level deletion
```

but Microsoft explicitly notes that Blob soft delete does **not protect against deletion of the entire storage account**. ([Microsoft Learn][9])

So for the management plane I can add an Azure resource lock such as:

```text
CanNotDelete
```

on the storage account/resource group where appropriate.

But here is the crucial interview detail:

> A resource lock protects management-plane resource deletion. It does **not** prevent someone with Blob data-plane permission from deleting individual blobs.

So:

```text
Resource lock
→ protects storage account resource

Soft delete/versioning/immutability
→ protect Blob data
```

Different layers.

---

### **7. Consider Azure Backup**

For especially important data, I would consider **Azure Backup for Blobs** as another independent recovery layer.

This becomes important for scenarios beyond simple accidental deletion, such as:

* ransomware,
* malicious operations,
* wider recovery requirements,
* storage account-level disasters.

Microsoft's current guidance specifically suggests Azure Backup in addition to in-account data-protection features for broader data-loss scenarios. ([Microsoft Learn][9])

---

### **8. Secure the network and credentials**

To reduce malicious deletion risk further:

```text
Disable public network access
        +
Private Endpoint
        +
Managed Identity
        +
least-privilege RBAC
```

If attackers cannot reach the data plane or obtain powerful credentials, the likelihood of malicious deletion falls substantially.

### **Strong production design**

For something like compliance/security logs:

```text
Producer
   ↓
Managed Identity
   ↓
Private Endpoint
   ↓
Blob Storage
   │
   ├── Versioning
   ├── Soft delete
   ├── Container soft delete
   ├── WORM immutability
   └── Backup where required
```

with tightly restricted administrative access.

### **How each protection helps**

| Threat                                        | Protection                                   |
| --------------------------------------------- | -------------------------------------------- |
| Accidental overwrite                          | **Versioning**                               |
| Accidental blob deletion                      | **Blob soft delete**                         |
| Accidental container deletion                 | **Container soft delete**                    |
| Malicious deletion/tampering during retention | **Immutability / WORM**                      |
| Storage-account deletion                      | **Resource lock + broader backup strategy**  |
| Credential misuse                             | **Managed Identity + least privilege**       |
| Internet attack path                          | **Private Endpoint + disable public access** |

### **Interview answer condensed**

> “For critical blobs, I use layered controls: Entra ID and least-privilege RBAC to prevent unnecessary delete access, versioning for overwrites, blob and container soft delete for recovery, immutable WORM retention for data that must not be tampered with, and Azure Backup for broader recovery scenarios. I may also place a CanNotDelete lock on the storage account, but I remember that resource locks protect the management plane, not individual blob data-plane deletes.”

**Memory line:**
**Prevent → preserve versions → recover deletions → make critical records immutable → keep independent recovery.**

**Interview trap:**
Do not say:

> “I'll put a resource lock on the storage account, so blobs can't be deleted.”

That's incorrect.

A resource lock protects the **Azure resource/control plane**, while blob deletion is typically a **data-plane operation**.

For malicious deletion protection, **immutability + least privilege** are particularly important.
