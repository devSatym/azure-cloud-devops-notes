# 5. 🔴 M IMP — Azure Storage

## Medium

### **T05-M07. What is a SAS token?**

**Answer:**
SAS stands for **Shared Access Signature**. It is a time-bound token that gives a client **delegated, limited access to Azure Storage resources without giving them the storage account key**.

A SAS can restrict things such as:

* which resource can be accessed,
* allowed operations like read/write/delete,
* start and expiry time,
* allowed IP range,
* HTTPS-only access.

Microsoft recommends using a **user delegation SAS** where possible because it is secured through Microsoft Entra credentials instead of the storage account key. ([Microsoft Learn][1])

### **Example**

Suppose a user needs to download one private blob for 15 minutes.

Instead of exposing the storage account key, my application can generate a SAS URL:

```text
https://stprod.blob.core.windows.net/reports/report.pdf
        ?
        SAS-token
```

The SAS might allow:

```text
Resource: report.pdf
Permission: Read
Expiry: 15 minutes
Protocol: HTTPS only
```

So the user gets temporary access only to what they need.

### **Why SAS is useful**

Without SAS, I might be tempted to give an external application:

```text
Storage Account Key ❌
```

That is far too powerful.

With SAS:

```text
Storage Account
      ↓
Restricted SAS
      ↓
Specific resource
Specific permission
Limited lifetime
```

This follows least privilege much better.

### **Security considerations**

A SAS is effectively a **bearer credential**.

Anyone who obtains a valid SAS may be able to use the permissions contained in it, so I would:

* use HTTPS,
* keep the validity period short,
* grant minimum permissions,
* avoid putting SAS tokens in logs or source code,
* prefer managed identity/Entra authentication when direct identity-based access is possible.

Microsoft explicitly advises protecting SAS tokens similarly to account keys. ([Microsoft Learn][2])

**Memory line:**
**SAS = temporary, scoped delegated access to storage.**

**Interview trap:**
A SAS is not automatically safer just because it expires.

A SAS like:

```text
Permission: Read + Write + Delete
Resource: entire account
Expiry: 1 year
```

is still dangerous.

The security comes from:

> **minimum scope + minimum permissions + short lifetime.**

**Keywords:** SAS, delegated access, expiry, permissions, least privilege, HTTPS

### **T05-M08. What is the difference between account SAS, service SAS, and user-delegation SAS?**

**Answer:**
The main differences are **what they can access and what credential is used to sign them**.

The three types are:

```text
Account SAS
Service SAS
User Delegation SAS
```

Microsoft's current Azure Storage documentation distinguishes them primarily by scope and authorization method. ([Microsoft Learn][1])

### **Quick comparison**

| SAS type                | Signed with                                       | Scope                                | Security preference      |
| ----------------------- | ------------------------------------------------- | ------------------------------------ | ------------------------ |
| **Account SAS**         | Storage account key                               | One or more storage services         | Broadest; use carefully  |
| **Service SAS**         | Storage account key                               | Resources within one storage service | More scoped              |
| **User delegation SAS** | Microsoft Entra credentials / user delegation key | Delegated storage-resource access    | Preferred when supported |

---

### **1. Account SAS**

An Account SAS can grant access across **multiple Azure Storage services**.

For example:

```text
Blob
+
Queue
+
Files
```

using one account-level SAS where configured.

It can also authorize some service-level operations that a service SAS cannot. ([Microsoft Learn][3])

The important security point is:

```text
Account SAS
→ signed using storage account key
```

So whoever generates it needs access to a highly privileged account credential.

---

### **2. Service SAS**

A Service SAS delegates access to resources in **one storage service**.

For example:

```text
Blob container
or
File share
or
Queue
```

but not multiple services through the same SAS.

For example:

```text
Service SAS
Resource: invoices container
Permissions: Read
Expiry: 1 hour
```

A service SAS is also signed using the **storage account key**. ([Microsoft Learn][2])

---

### **3. User Delegation SAS**

A User Delegation SAS is authorized using **Microsoft Entra credentials** rather than directly signing with the storage account key.

Conceptually:

```text
Managed Identity / User / Service Principal
          ↓
Microsoft Entra authentication
          ↓
User Delegation Key
          ↓
User Delegation SAS
```

The permissions of the identity requesting the delegation key matter, and the SAS then further restricts what the recipient can do.

Microsoft recommends this approach over account-key-signed SAS where possible. ([Microsoft Learn][1])

### **Why is user delegation more secure?**

Because I don't need to expose or rely on:

```text
Storage Account Key
```

for SAS creation.

Instead, I can use:

```text
Managed Identity
+
RBAC
+
short-lived delegated SAS
```

which fits modern Azure identity design much better.

### **Practical example**

Suppose an App Service needs to give a customer temporary download access.

I would prefer:

```text
App Service
   ↓
Managed Identity
   ↓
Microsoft Entra ID
   ↓
User Delegation SAS
   ↓
Customer downloads one blob
```

instead of:

```text
App stores Storage Account Key ❌
   ↓
Generates SAS from long-lived secret
```

**Memory line:**
**Account SAS = broad account scope.
Service SAS = one storage service.
User Delegation SAS = Entra-backed SAS and generally preferred.**

**Interview trap:**
Do not say all SAS tokens are authenticated through Microsoft Entra ID.

Traditional:

```text
Account SAS
Service SAS
```

are signed using **Shared Key**.

User Delegation SAS is the Entra-backed option. ([Microsoft Learn][1])

**Keywords:** account SAS, service SAS, user delegation SAS, Shared Key, Microsoft Entra ID, delegation

### **T05-M09. What are storage account access keys?**

**Answer:**
Storage account access keys are **long-lived shared secrets that provide Shared Key authorization to an Azure Storage account**.

They are powerful credentials and should be treated almost like a root password for storage.

Azure provides **two account keys**, typically:

```text
key1
key2
```

so one can be rotated while applications temporarily continue using the other.

### **How they are used**

An application may historically use:

```text
Storage account name
+
Storage account key
```

to construct a connection string:

```text
DefaultEndpointsProtocol=https;
AccountName=stprod;
AccountKey=<secret>;
EndpointSuffix=core.windows.net
```

Azure Storage then validates requests using Shared Key authorization.

### **Why are account keys risky?**

They are very broad credentials.

If an attacker steals the account key, they may gain extensive access to storage data depending on the service and configuration.

Unlike Azure RBAC:

```text
Storage account key
→ not tied to a person's/application's granular identity
```

So it is harder to enforce least privilege.

Microsoft now recommends Microsoft Entra ID and managed identities instead of Shared Key for supported workloads. ([Microsoft Learn][4])

### **Why are there two keys?**

Mainly for **key rotation without downtime**.

For example:

```text
Application currently uses key1
          ↓
Regenerate key2
          ↓
Update application to key2
          ↓
Verify
          ↓
Regenerate key1
```

Then repeat this rotation process periodically.

### **If I absolutely must use an access key**

I would never place it in:

```text
source code
GitHub repository
Terraform variables committed to Git
plain-text config
```

Instead I would store it in something such as:

```text
Azure Key Vault
```

and retrieve it securely at runtime.

Microsoft explicitly recommends protecting and rotating account keys if Shared Key cannot be avoided. ([Microsoft Learn][5])

### **Modern production preference**

Instead of:

```text
Application
    ↓
Storage account key
    ↓
Blob Storage
```

I prefer:

```text
Application
    ↓
Managed Identity
    ↓
Microsoft Entra ID
    ↓
Azure RBAC
    ↓
Blob Storage
```

That removes the long-lived credential from the application.

**Memory line:**
**Storage key = powerful shared secret; managed identity + Entra ID is usually better.**

**Interview trap:**
Do not treat the two keys as:

```text
Primary key
+
Read-only key
```

They are both powerful account credentials.

The main reason for having two is **safe rotation**.

**Keywords:** storage access key, Shared Key, key1, key2, rotation, Key Vault, long-lived secret

### **T05-M10. How can Microsoft Entra authentication be used with Azure Storage?**

**Answer:**
Azure Storage can use **Microsoft Entra ID for identity-based authentication and Azure RBAC for authorization**, so applications and users can access storage without storing account keys.

The process is:

```text
User / Application / Managed Identity
             ↓
Microsoft Entra ID authentication
             ↓
OAuth 2.0 access token
             ↓
Azure Storage
             ↓
RBAC permission checked
             ↓
Allow / Deny
```

Azure supports Entra-based authorization across Blob, File, Queue, and Table scenarios, although the exact authentication model varies by service/protocol. ([Microsoft Learn][6])

### **Example with managed identity**

Suppose an Azure App Service needs to read blobs.

First, I enable:

```text
System-assigned managed identity
```

on the App Service.

Then assign:

```text
Storage Blob Data Reader
```

to that identity at the appropriate scope.

The flow becomes:

```text
App Service
     ↓
Managed Identity
     ↓
Microsoft Entra ID
     ↓
OAuth token
     ↓
Blob Storage
```

No storage password or key is stored in the application.

### **RBAC controls what it can do**

For example:

```text
Storage Blob Data Reader
→ read blobs

Storage Blob Data Contributor
→ read/write/delete blob data

Storage Blob Data Owner
→ broader blob-data permissions
```

And I can scope the assignment at an appropriate level such as:

```text
Storage account
     ↓
Container
```

depending on the supported resource and access requirements. ([Microsoft Learn][6])

### **Important distinction: management plane vs data plane**

This is a very common Azure interview point.

Suppose someone has:

```text
Contributor
```

on the storage account.

That lets them manage the Azure resource, but it does **not automatically mean they have permission to read Blob data using Entra data-plane authorization**.

For blob access, they may also require a role such as:

```text
Storage Blob Data Reader
```

So:

```text
Contributor
→ management plane

Storage Blob Data Reader
→ storage data plane
```

This separation is important for least privilege.

### **Why managed identity is ideal**

Without managed identity:

```text
App
 ↓
Secret / key
 ↓
Storage
```

With managed identity:

```text
App
 ↓
Azure-managed identity
 ↓
OAuth token
 ↓
Storage
```

Azure manages the identity credentials, so I do not need to rotate an application secret manually.

Microsoft recommends Entra ID with managed identities for supported Blob, Queue, and Table access because it provides better security and manageability than Shared Key. ([Microsoft Learn][7])

### **Real production example**

For an AKS workload, I could use:

```text
AKS Pod
   ↓
Workload Identity
   ↓
Microsoft Entra ID
   ↓
Storage Blob Data Contributor
   ↓
Blob Storage
```

instead of putting:

```text
AZURE_STORAGE_KEY
```

inside a Kubernetes Secret.

That is much better from a DevSecOps perspective.

**Memory line:**
**Entra authenticates the identity; RBAC determines what that identity can do in Storage.**

**Interview trap:**
Do not say:

> “If I have Contributor on the storage account, I can automatically read every blob.”

Azure distinguishes **management-plane permissions from data-plane permissions**.

Also, authentication and networking are separate:

```text
Correct RBAC ✅
Private Endpoint/network path ❌
=
Storage access still fails
```

**Keywords:** Microsoft Entra ID, managed identity, OAuth 2.0, Azure RBAC, data plane, Storage Blob Data Contributor
