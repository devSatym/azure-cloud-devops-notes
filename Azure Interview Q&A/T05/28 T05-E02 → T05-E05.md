# 5. 🔴 M IMP — Azure Storage

## Easy

### **T05-E02. What is Blob Storage?**

**Answer:**
Azure Blob Storage is Microsoft's **object storage service for storing massive amounts of unstructured data** such as images, videos, backups, logs, documents, and application artifacts.

Instead of exposing a traditional mounted filesystem, data is stored as **blobs inside containers**.

The hierarchy is:

```text
Storage Account
      ↓
Container
      ↓
Blob
```

For example:

```text
stprodapp01
└── product-images
    ├── laptop.jpg
    ├── phone.jpg
    └── tablet.jpg
```

### **What kind of data is Blob Storage designed for?**

Typical use cases include:

* application images/videos,
* static website files,
* backups and archives,
* log files,
* data-lake datasets,
* software artifacts,
* large documents.

### **Main blob types**

The most important is **Block Blob**, which is used for normal files such as:

```text
.jpg
.mp4
.pdf
.zip
.log
```

Azure also supports:

```text
Append Blob
→ optimized for append operations, such as logs

Page Blob
→ random read/write workloads; historically used for Azure VM disks
```

For interviews, **Block Blob** is the one you should remember first.

### **Example**

Suppose an application lets users upload profile pictures.

Instead of storing those images on the application's VM:

```text
User
 ↓
Application
 ↓
Blob Storage container
 ↓
profile-123.jpg
```

This is better because the application instances remain stateless and the objects can be accessed independently of any particular VM.

### **Access and security**

Blob Storage can be secured using:

* Microsoft Entra ID + RBAC,
* managed identities,
* SAS tokens,
* storage account keys,
* private endpoints,
* firewall/network restrictions.

For Azure workloads, I would normally prefer **managed identity + RBAC** rather than embedding account keys.

**Memory line:**
**Blob Storage = scalable object storage for unstructured data.**

**Interview trap:**
Blob Storage is not normally used like a traditional shared mounted filesystem.

If applications require an SMB/NFS-style shared file share, **Azure Files** is usually the more natural service.

**Keywords:** Blob Storage, object storage, container, block blob, unstructured data, SAS

### **T05-E03. What is Azure Files?**

**Answer:**
Azure Files provides **fully managed cloud file shares** that multiple machines can access using standard file-sharing protocols such as **SMB**, and in supported configurations, **NFS**.

The important distinction is that Azure Files behaves much more like a traditional shared filesystem than Blob Storage.

Conceptually:

```text
Azure Storage Account
        ↓
Azure File Share
        ↓
Shared folders/files
        ↓
Multiple clients
```

### **Example**

Suppose three application servers need the same configuration and uploaded files:

```text
VM-1 ─┐
VM-2 ─┼──→ Azure File Share
VM-3 ─┘
```

All three servers can access the same shared directory.

For example on Linux, it can conceptually be mounted as:

```text
/mnt/shared
```

and on Windows it behaves similarly to a network share.

### **Typical use cases**

Azure Files is useful for:

* shared application files,
* lift-and-shift applications expecting file shares,
* shared configuration,
* user home directories,
* replacing or extending traditional file servers,
* persistent shared storage for suitable workloads.

### **Why use Azure Files instead of managing a file server VM?**

Without Azure Files:

```text
VM acting as file server
├── OS management
├── patching
├── HA design
├── storage management
└── backups
```

With Azure Files:

```text
Managed Azure file service
        ↓
Clients mount share
```

Azure handles much more of the underlying storage infrastructure.

**Memory line:**
**Azure Files = managed shared filesystem over SMB/NFS.**

**Interview trap:**
Do not answer:

> “Azure Files and Blob Storage both just store files.”

They expose fundamentally different storage models:

```text
Blob → object storage

Azure Files → shared filesystem
```

**Keywords:** Azure Files, SMB, NFS, file share, shared storage, managed file service

### **T05-E04. What is Azure Queue Storage?**

**Answer:**
Azure Queue Storage is a **simple managed message queue** used to decouple application components and enable asynchronous processing.

Instead of one component waiting synchronously for another component to finish work, it can place a message into a queue and continue.

For example:

```text
Web Application
      ↓
"Process order 123"
      ↓
Azure Queue Storage
      ↓
Background Worker
      ↓
Processes order
```

### **Why is that useful?**

Suppose a user uploads a video.

Without a queue:

```text
User request
    ↓
Upload
    ↓
Video processing
    ↓
Thumbnail generation
    ↓
User waits for everything
```

With Queue Storage:

```text
User uploads video
       ↓
Application stores job message
       ↓
Returns quickly to user

Meanwhile:

Queue
 ↓
Worker
 ↓
Process video
```

The frontend and worker are now **loosely coupled**.

### **Main benefits**

Queue Storage helps with:

* asynchronous processing,
* workload buffering,
* decoupling services,
* handling traffic spikes,
* background jobs.

For example, if 10,000 jobs arrive suddenly:

```text
10,000 messages
      ↓
Queue buffers them
      ↓
Workers process them gradually
```

This can prevent the backend from being overwhelmed instantly.

### **Important behavior**

A consumer typically:

```text
Reads message
      ↓
Message becomes temporarily invisible
      ↓
Processes work
      ↓
Deletes message after success
```

If processing fails and the message isn't deleted, it can become visible again after the visibility timeout so another processing attempt can occur.

That means applications should generally be designed to tolerate **duplicate processing**.

### **Queue Storage vs Service Bus**

Queue Storage is intentionally simple.

For advanced enterprise messaging requirements such as:

* topics/subscriptions,
* sessions,
* transactions,
* richer dead-lettering,
* sophisticated routing,

I would consider **Azure Service Bus** instead.

**Memory line:**
**Queue Storage = simple asynchronous messaging that decouples producers from consumers.**

**Interview trap:**
A queue doesn't mean:

> “Exactly one message will always be processed exactly once.”

Distributed messaging systems can involve retries and duplicate delivery scenarios, so consumers should preferably be **idempotent**.

**Keywords:** Queue Storage, asynchronous messaging, producer, consumer, decoupling, visibility timeout

### **T05-E05. What is Azure Table Storage?**

**Answer:**
Azure Table Storage is a **managed NoSQL key-value / wide-column style datastore** designed for storing large amounts of structured, non-relational data.

Unlike a relational database, it does not require:

* joins,
* foreign-key relationships,
* a rigid relational schema.

Data is stored as:

```text
Table
  ↓
Entities
  ↓
Properties
```

Each entity is primarily identified by:

```text
PartitionKey
+
RowKey
```

Together, they uniquely identify an entity.

### **Example**

Suppose I want to store device status:

```text
PartitionKey: factory-01
RowKey: device-1001

Temperature: 42
Status: Healthy
Location: Delhi
```

Another entity could be:

```text
PartitionKey: factory-01
RowKey: device-1002

Temperature: 38
Status: Healthy
```

### **Why is PartitionKey important?**

The `PartitionKey` determines how entities are logically grouped and strongly influences:

* scalability,
* query efficiency,
* distribution.

For example:

```text
PartitionKey = customer ID
RowKey       = device ID
```

can make it efficient to query devices belonging to one customer.

So data-model design matters significantly in Table Storage.

### **Typical use cases**

Table Storage works well for simple large-scale datasets such as:

* device metadata,
* application metadata,
* user preference data,
* catalogs,
* simple operational datasets.

It's most suitable when I need simple key-based access and **don't require relational querying or joins**.

### **Table Storage vs SQL**

Think:

```text
Azure SQL
→ relational
→ schemas
→ joins
→ SQL queries
→ transactions/relationships

Table Storage
→ NoSQL
→ flexible entities
→ PartitionKey + RowKey
→ simple massively scalable access
```

### **Table Storage vs Cosmos DB**

Azure Cosmos DB provides much richer capabilities such as:

* global distribution,
* multiple consistency options,
* broader APIs and querying,
* lower-latency globally distributed architectures.

Table Storage is simpler and can be attractive when the requirement is straightforward and cost-sensitive.

**Memory line:**
**Table Storage = simple NoSQL storage organized around PartitionKey + RowKey.**

**Interview trap:**
The word **Table** does not mean it is a relational SQL table.

Azure Table Storage is a **NoSQL service**, not a relational database.

**Keywords:** Table Storage, NoSQL, entity, PartitionKey, RowKey, key-value, non-relational
