# 5. 🔴 M IMP — Azure Storage

## Medium

### **T05-M03. What is GRS?**

**Answer:**
GRS stands for **Geo-Redundant Storage**. It protects Azure Storage against a **regional disaster** by keeping copies of the data in both a primary Azure region and a geographically separate secondary region.

The replication pattern is essentially:

```text
Primary Region
   ↓
LRS: 3 local copies
   ↓
Asynchronous geo-replication
   ↓
Secondary Region
   ↓
LRS: 3 local copies
```

So GRS effectively maintains **six copies** of the data: three in the primary region and three in the secondary region. ([Microsoft Learn][1])

### **How replication works**

Inside the primary region, writes are replicated synchronously using LRS.

Then Azure copies those changes **asynchronously** to the secondary region.

```text
Application write
      ↓
Primary Region
      ↓
3 LRS copies
      ↓
Write acknowledged
      ↓
Async replication
      ↓
Secondary Region
      ↓
3 LRS copies
```

The word **asynchronous** is important.

If the primary region suffers a catastrophic failure immediately after a write, the newest data might not yet have reached the secondary region.

Therefore, geo-replication can have a non-zero **RPO**. Microsoft explicitly warns that some recent data can be lost during a regional disaster because the secondary can lag behind the primary. ([Microsoft Learn][1])

### **Can applications directly read from the secondary region?**

With normal:

```text
GRS
```

**No**, not during normal operation.

The secondary copy exists for disaster recovery, but applications don't normally have direct read access to it.

To get secondary-region read access, I would use:

```text
RA-GRS
```

which we'll cover shortly. ([Microsoft Learn][1])

### **What happens if the primary region fails?**

A storage-account failover can promote the secondary region so it becomes the new primary.

Conceptually:

```text
Before disaster

Primary Region → Read/Write
Secondary      → DR replica


Primary fails ❌

        ↓ Failover

Former Secondary
        ↓
New Primary
        ↓
Read/Write
```

During failover, Azure updates the storage endpoints so clients can use the new primary location. ([Microsoft Learn][2])

### **When would I choose GRS?**

I'd choose GRS when:

* regional disaster protection matters,
* some potential RPO is acceptable,
* I don't need normal read access to the secondary,
* cost should be lower than more advanced geo-zone configurations.

**Memory line:**
**GRS = LRS in primary + asynchronous copy to another region.**

**Interview trap:**
GRS does **not** mean:

> “My application automatically reads from both regions.”

Normal GRS keeps the secondary for DR. For readable secondary access, use **RA-GRS**.

**Keywords:** GRS, geo-replication, secondary region, asynchronous replication, regional DR, RPO

### **T05-M04. What is GZRS?**

**Answer:**
GZRS stands for **Geo-Zone-Redundant Storage**.

It combines:

```text
ZRS
+
Geo-replication
```

So it protects against both:

* an **Availability Zone failure inside the primary region**, and
* a **complete primary-region disaster**.

Microsoft recommends GZRS for workloads that need both strong in-region availability and regional disaster resilience. ([Microsoft Learn][1])

### **How GZRS works**

In the primary region:

```text
Primary Region
├── Zone 1 → replica
├── Zone 2 → replica
└── Zone 3 → replica
```

Azure uses ZRS and synchronously distributes data across **three or more Availability Zones**.

Then:

```text
Primary Region
      ↓
Asynchronous geo-replication
      ↓
Secondary Region
      ↓
LRS copies
```

So:

```text
Primary = ZRS
Secondary = LRS
```

This is the key difference from GRS. ([Microsoft Learn][1])

### **GRS vs GZRS**

```text
GRS
Primary   → LRS
Secondary → LRS

GZRS
Primary   → ZRS
Secondary → LRS
```

Therefore, GZRS gives better protection **before a regional disaster even occurs**.

For example, if one primary Availability Zone fails:

```text
Zone 1 ❌
Zone 2 ✅
Zone 3 ✅
```

the application can continue using storage from surviving zones without needing a regional failover.

### **If the entire region fails**

The geo-replicated secondary provides the regional DR copy.

Because geo-replication to that secondary is asynchronous, the same basic RPO consideration applies: the newest writes may not yet have reached the secondary when a sudden disaster occurs. ([Microsoft Learn][1])

### **When would I choose GZRS?**

For a business-critical production workload where I need:

```text
Zone resilience
+
Regional disaster protection
```

GZRS is a very strong choice where supported.

Example:

```text
Critical application storage
        ↓
Must survive Zone 1 outage
        ↓
Must also have regional DR
        ↓
GZRS
```

**Memory line:**
**GZRS = ZRS in primary + geo-replication to secondary.**

**Interview trap:**
Do not say GZRS means:

> “ZRS in both regions.”

Azure currently uses **ZRS in the primary region and LRS in the secondary region**. ([Microsoft Learn][1])

**Keywords:** GZRS, ZRS, geo-replication, Availability Zones, regional DR, asynchronous replication

**Likely follow-ups:**

### **T05-M05. What is RA-GRS?**

**Answer:**
RA-GRS stands for **Read-Access Geo-Redundant Storage**.

It provides the same geo-replication architecture as GRS, but additionally allows applications to **read from the secondary region without waiting for a failover**. ([Microsoft Learn][1])

Think of it as:

```text
GRS
+
Read access to secondary
=
RA-GRS
```

### **Architecture**

```text
Primary Region
LRS
   ↓
Read + Write
   ↓
Async replication
   ↓
Secondary Region
LRS
   ↓
Read Only
```

During normal operations:

```text
Primary endpoint
→ Read + Write

Secondary endpoint
→ Read only
```

### **Secondary endpoint**

Azure exposes a secondary endpoint using `-secondary`.

For example, if the primary Blob endpoint is:

```text
mystorage.blob.core.windows.net
```

the secondary endpoint is:

```text
mystorage-secondary.blob.core.windows.net
```

Applications can explicitly read from that secondary endpoint. ([Microsoft Learn][1])

### **Why is that useful?**

Suppose the primary region experiences an outage.

With normal GRS:

```text
Primary unavailable
      ↓
Need failover to regain service
```

With RA-GRS, an application designed for it can temporarily:

```text
Primary read fails
      ↓
Read from secondary
      ↓
Application provides degraded/read-only service
```

For example, an e-commerce system might temporarily allow users to:

```text
View products ✅
View existing content ✅
Create new order ❌
```

until full write service is restored.

### **Important consistency point**

Because geo-replication is asynchronous:

```text
Secondary
≠ necessarily latest primary state
```

The secondary is **eventually consistent** with the primary.

So an application reading from the secondary could see slightly older data. ([Microsoft Learn][3])

This is a critical interview point.

### **RA-GRS vs GRS**

| Feature                            | GRS | RA-GRS |
| ---------------------------------- | --: | -----: |
| Primary read/write                 |   ✅ |      ✅ |
| Secondary geo-copy                 |   ✅ |      ✅ |
| Secondary readable before failover |   ❌ |      ✅ |
| Regional DR                        |   ✅ |      ✅ |
| Secondary may lag                  |   ✅ |      ✅ |

### **RA-GZRS**

The same idea also exists for GZRS:

```text
GZRS + secondary read access
=
RA-GZRS
```

Microsoft currently recommends RA-GZRS where maximum storage availability and durability are required. ([Microsoft Learn][2])

**Memory line:**
**RA-GRS = GRS plus read-only access to the secondary region.**

**Interview trap:**
RA-GRS does **not** provide:

```text
Active-active writes across two regions
```

The secondary is read-only during normal operation.

Also, because replication is asynchronous, secondary data can lag behind primary data.

**Keywords:** RA-GRS, secondary endpoint, read-only secondary, eventual consistency, geo-replication

### **T05-M06. When would you choose ZRS instead of GRS?**

**Answer:**
I would choose **ZRS instead of GRS when my primary requirement is high availability inside one Azure region and I need the application to survive an Availability Zone failure without performing regional failover**.

The choice comes down to:

```text
ZRS
→ Zone-level high availability

GRS
→ Regional disaster recovery
```

Microsoft recommends ZRS when high availability inside the primary region is the main requirement. ([Microsoft Learn][1])

### **Architecture difference**

#### ZRS

```text
Same Azure Region

Zone 1 ─┐
Zone 2 ─┼─ synchronous replicas
Zone 3 ─┘
```

If one zone fails:

```text
Zone 1 ❌
Zone 2 ✅
Zone 3 ✅

Application continues
```

No regional failover is normally necessary.

---

#### GRS

```text
Primary Region
      ↓
LRS
      ↓
Async
      ↓
Secondary Region
      ↓
LRS
```

GRS is designed primarily for a **regional disaster**, but its primary-region storage is LRS rather than zone-redundant.

### **Scenario 1 — I would choose ZRS**

Suppose I have a production application running entirely in one region:

```text
App → Zone 1/2/3
Database → zone resilient
Storage → ?
```

Requirement:

> “If one Availability Zone goes down, the application must keep running immediately.”

I'd choose:

```text
ZRS
```

because storage should match the application's zone-resilient architecture.

Microsoft specifically recommends ZRS for high availability and, where supported, for Azure Files workloads. ([Microsoft Learn][1])

### **Scenario 2 — I would choose GRS**

Suppose the requirement instead says:

> “A total regional disaster must not destroy our backup data.”

Then:

```text
GRS
```

may be more appropriate because a copy exists in another geographic region.

### **The ideal answer isn't always either/or**

For a critical workload that needs:

```text
Zone HA
+
Region DR
```

I would not force myself to choose between ZRS and GRS.

I would consider:

```text
GZRS
```

because it combines both protections.

### **Comparison**

| Requirement                  | ZRS |                   GRS |
| ---------------------------- | --: | --------------------: |
| Hardware failure             |   ✅ |                     ✅ |
| Zone failure resilience      |   ✅ |      Primary uses LRS |
| Immediate in-region zone HA  |   ✅ | Not its core strength |
| Secondary region copy        |   ❌ |                     ✅ |
| Regional disaster protection |   ❌ |                     ✅ |
| Geo replication              |   ❌ |        ✅ asynchronous |

### **Another reason to choose ZRS: data residency**

If compliance says:

> “This data must stay in this Azure region.”

then geo-replication might be undesirable.

Microsoft explicitly recommends ZRS for scenarios that need both high availability and replication restricted to a single region for governance reasons. ([Microsoft Learn][1])

### **Interview answer condensed**

> “I choose ZRS when I need synchronous replication across Availability Zones and immediate resilience to a zone failure while keeping data in one region. I choose GRS when regional disaster recovery is more important because it asynchronously replicates data to another region. If I need both zone resilience and regional DR, I would consider GZRS.”

**Memory line:**
**ZRS = survive a zone.
GRS = survive a region.
GZRS = protect against both.**

**Interview trap:**
Do not automatically say:

> “GRS is better because it has more copies.”

“Better” depends on the failure you need to survive.

For a workload that must remain available during a **single-zone failure without regional failover**, ZRS can be the more appropriate architecture.

**Keywords:** ZRS, GRS, zone resilience, regional DR, data residency, GZRS, synchronous vs asynchronous
