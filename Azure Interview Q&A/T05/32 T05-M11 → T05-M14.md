# 5. 🔴 M IMP — Azure Storage

## Medium

### **T05-M11. What are lifecycle-management policies?**

**Answer:**
Azure Blob Storage lifecycle-management policies are **rule-based policies that automatically move blobs to cheaper access tiers or delete them when they meet age or filtering conditions**.

They are mainly used for **storage cost optimization and automatic data retention management**. ([Microsoft Learn][1])

### **Example**

Suppose application logs are stored in Blob Storage.

I might configure:

```text
0–30 days
→ Hot

After 30 days
→ Cool

After 90 days
→ Cold

After 180 days
→ Archive

After 7 years
→ Delete
```

Instead of someone manually moving millions of blobs, Azure evaluates the lifecycle policy automatically.

### **What can policies act on?**

Rules can target blobs using conditions such as:

* blob age,
* blob type,
* container/prefix,
* blob index tags,
* current versions,
* previous versions.

For example:

```text
Container: logs

logs/prod/*
   ↓
Older than 30 days
   ↓
Move to Cool
```

### **Typical production use case**

Suppose I collect diagnostic logs:

```text
Recent logs
→ frequently queried
→ Hot

Older logs
→ occasionally queried
→ Cool / Cold

Historical compliance logs
→ rarely queried
→ Archive
```

This reduces storage cost without requiring application changes.

### **Lifecycle management + versioning**

If Blob versioning creates many old versions, lifecycle rules can also remove old versions.

For example:

```text
Current blob
→ retain

Previous versions > 90 days
→ delete
```

Microsoft specifically recommends lifecycle management to control storage growth caused by versioning. ([Microsoft Learn][2])

### **Interaction with soft delete**

If lifecycle management deletes a blob while **soft delete is enabled**, the blob goes into the soft-deleted state and remains recoverable for the configured soft-delete retention period. ([Microsoft Learn][2])

So:

```text
Lifecycle delete
      ↓
Soft delete enabled?
      ↓ Yes
Soft-deleted state
      ↓
Retention expires
      ↓
Permanent deletion
```

**Memory line:**
**Lifecycle policy = automatically tier or delete Blob data based on rules.**

**Interview trap:**
Lifecycle management is not a backup mechanism.

It manages **data lifecycle and cost**. Protection against accidental deletion requires features such as soft delete, versioning, backup, or immutability depending on the requirement.

**Keywords:** lifecycle management, Hot, Cool, Cold, Archive, retention, automated tiering

### **T05-M12. What is Blob versioning?**

**Answer:**
Blob versioning automatically keeps **previous versions of a blob whenever that blob is modified or deleted**, allowing me to recover an earlier state.

When versioning is enabled, an overwrite doesn't simply destroy the previous content.

Instead:

```text
report.pdf v1
      ↓ overwrite

report.pdf v2  ← current
report.pdf v1  ← previous version
```

Azure assigns each version a unique version ID. ([Microsoft Learn][3])

### **Example**

Suppose someone accidentally replaces:

```text
production-config.json
```

with an incorrect configuration.

Without versioning:

```text
Old content
→ overwritten
→ potentially lost
```

With versioning:

```text
v1 → correct configuration
v2 → accidental overwrite ← current

Restore/promote v1
→ recover previous state
```

### **What happens on deletion?**

When versioning is enabled and the current blob is deleted, the current version can become a **previous version**, leaving no current version until another version is restored or created. ([Microsoft Learn][4])

So versioning protects particularly well against:

```text
Accidental overwrite
+
Accidental changes
```

### **Cost consideration**

Every version consumes storage.

For a frequently modified large blob:

```text
1 GB blob
×
100 versions
≈ substantial additional storage
```

So I would combine versioning with a lifecycle policy such as:

```text
Previous versions older than 90 days
→ delete
```

Microsoft explicitly recommends lifecycle policies for controlling version-storage cost. ([Microsoft Learn][4])

### **Versioning + soft delete**

For stronger protection:

```text
Versioning
→ protects previous states

Soft delete
→ protects deleted versions/blobs for a retention window
```

Microsoft recommends using them together when protection against both overwrites and deletions is needed. ([Microsoft Learn][5])

### **Important limitation**

Blob versioning is not supported for storage accounts with **hierarchical namespace enabled**, such as ADLS Gen2 HNS scenarios. ([Microsoft Learn][4])

**Memory line:**
**Versioning = preserve the blob's previous state whenever it changes.**

**Interview trap:**
Versioning is not free.

A heavily modified blob may accumulate many versions, so lifecycle management should usually be considered alongside it.

**Keywords:** Blob versioning, version ID, overwrite protection, previous version, recovery

### **T05-M13. What is Blob soft delete?**

**Answer:**
Blob soft delete protects against accidental deletion by keeping deleted Blob data in a **recoverable state for a configured retention period** instead of permanently removing it immediately.

So:

```text
Delete blob
    ↓
Soft-deleted
    ↓
Recoverable during retention period
    ↓
Retention expires
    ↓
Permanent deletion
```

Azure supports soft-delete protection for blobs, and container soft delete exists separately for deleted containers. ([Microsoft Learn][4])

### **Example**

Suppose an engineer accidentally deletes:

```text
customer-contract.pdf
```

If soft delete has a retention period such as:

```text
14 days
```

then during those 14 days:

```text
Blob deleted
     ↓
Still retained by Azure
     ↓
Administrator restores it
```

After the retention period expires, Azure can permanently remove it.

### **Soft delete vs versioning**

This is an important comparison.

```text
Versioning
→ protects previous states from overwrite/change

Soft delete
→ gives deleted data a recovery window
```

For strong protection I often use:

```text
Versioning
+
Soft delete
```

Microsoft recommends enabling both when protection is needed against accidental overwrites and deletion. ([Microsoft Learn][5])

### **Example**

Suppose someone overwrites:

```text
appsettings.json
```

Versioning helps me recover the older version.

Suppose someone then deletes that old version.

Soft delete can give me another recovery window.

That's why the two features complement each other.

### **Important distinction: blob vs container soft delete**

There are separate protections for:

```text
Blob soft delete
→ deleted blobs / versions / snapshots

Container soft delete
→ deleted blob containers
```

For important production storage, I would assess both.

### **Is soft delete enough against ransomware?**

Not necessarily.

Soft delete is useful for accidental deletion, but broader protection may require:

* versioning,
* immutability,
* Azure Backup,
* strict RBAC,
* storage-network isolation.

Microsoft specifically recommends considering Azure Backup for broader scenarios such as ransomware or storage-account deletion. ([Microsoft Learn][4])

**Memory line:**
**Soft delete = delete now, permanently remove later.**

**Interview trap:**
Soft delete and versioning are **not the same thing**.

```text
Versioning → preserves changes
Soft delete → preserves deletions temporarily
```

And soft delete does not provide the same tamper resistance as immutable/WORM storage.

**Keywords:** soft delete, retention period, recovery, accidental deletion, versioning

### **T05-M14. What is immutable Blob Storage?**

**Answer:**
Immutable Blob Storage lets me store blob data in a **WORM—Write Once, Read Many—state**, meaning protected data can be read but cannot be modified or deleted while the applicable immutability policy is active.

It is mainly used for:

* regulatory compliance,
* audit records,
* financial records,
* security logs,
* evidence,
* records that must not be tampered with.

Azure supports **time-based retention policies and legal holds** for immutable Blob Storage. ([Microsoft Learn][6])

### **1. Time-based retention**

I specify a retention period.

For example:

```text
Audit logs
Retention = 7 years
```

During that period:

```text
Create ✅
Read   ✅

Modify ❌
Delete ❌
```

After the retention period ends, the data can eventually be deleted according to policy. ([Microsoft Learn][6])

### **2. Legal hold**

A legal hold does not necessarily have a predefined expiration date.

```text
Investigation starts
      ↓
Legal hold enabled
      ↓
Blob cannot be changed/deleted
      ↓
Authorized person removes hold
```

This is useful for litigation or regulatory investigations.

### **Example**

Suppose financial regulations require audit logs to remain unchanged for seven years.

A normal permission model isn't sufficient because an administrator with enough permissions might potentially delete data.

With locked immutable storage:

```text
Audit Blob
    ↓
7-year WORM policy
    ↓
Even privileged users cannot simply delete/overwrite it
```

That's fundamentally different from ordinary RBAC-based protection.

### **Locked vs unlocked retention policy**

A time-based retention policy may initially be left **unlocked** while it is tested.

Once it is **locked**, the commitment becomes much stronger.

Microsoft notes that a locked policy cannot simply be shortened or deleted; retention can generally only be extended. ([Microsoft Learn][7])

So I would validate carefully before locking it.

### **Immutability vs soft delete**

This is one of the most important storage-security distinctions:

```text
Soft Delete
→ deleted data can be recovered

Immutability
→ protected data cannot be deleted/modified in the first place
```

For critical data I might combine:

```text
Versioning
+
Soft delete
+
Immutable retention
```

depending on the compliance and recovery requirements.

Microsoft specifically recommends soft delete as an additional protection layer alongside immutability. ([Microsoft Learn][6])

### **Version-level WORM**

Azure also supports **version-level immutability**, allowing WORM protection to apply at finer granularity.

Version-level WORM relies on Blob versioning and can be configured at supported account/container/version scopes. ([Microsoft Learn][3])

### **Production example**

For security audit logs:

```text
Application / Security Tools
          ↓
Blob Storage
          ↓
Immutable container/version
          ↓
WORM retention: 365 days
          ↓
Cannot modify/delete
```

Even if credentials are compromised, the active immutability policy provides an additional layer of protection against tampering.

**Memory line:**
**Immutable Blob = WORM: write it, read it, but don't change or delete it during retention.**

**Interview trap:**
Do not confuse:

```text
Soft delete
```

with:

```text
Immutable storage
```

Soft delete allows deletion but provides recovery.

Immutability is designed to **prevent modification/deletion while the policy applies**.

Also, locking an immutability policy is a serious action—test the retention requirements before locking it.

**Keywords:** WORM, immutable storage, time-based retention, legal hold, compliance, tamper protection
