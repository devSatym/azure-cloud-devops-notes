# 5. 🔴 M IMP — Azure Storage

## Easy

### **T05-E06. What is the difference between Blob Storage and Azure Files?**

**Answer:**
The main difference is the **storage model and how applications access the data**.

**Azure Blob Storage** is **object storage** designed for unstructured data such as images, videos, logs, backups, and documents.

**Azure Files** provides a **managed shared filesystem** that applications and VMs can mount using protocols such as SMB or NFS.

### **Quick comparison**

| Area                  | Blob Storage                              | Azure Files                                        |
| --------------------- | ----------------------------------------- | -------------------------------------------------- |
| Storage type          | Object storage                            | File storage                                       |
| Structure             | Container → Blob                          | File share → directories → files                   |
| Main access           | REST/API/SDK                              | SMB/NFS                                            |
| Mount as normal share | Not its primary model                     | Yes                                                |
| Best for              | Images, backups, logs, objects            | Shared files, legacy apps, file-server replacement |
| Access tiers          | Hot/Cool/Cold/Archive for supported blobs | Different file-share performance/tiering model     |

### **Example: Blob Storage**

Suppose an application stores user images:

```text
Application
    ↓
Blob container
    ↓
image001.jpg
image002.jpg
image003.jpg
```

The application accesses those objects through:

```text
HTTPS / REST API / Azure SDK
```

That's a natural Blob Storage use case.

### **Example: Azure Files**

Now suppose five Windows servers expect:

```text
\\shared-server\documents
```

Instead of running my own Windows file server, I can provide an Azure File Share:

```text
VM-1 ─┐
VM-2 ─┤
VM-3 ─┼──→ Azure Files
VM-4 ─┤     shared-data
VM-5 ─┘
```

The application continues working with a familiar filesystem/share model.

### **How I choose**

If the application says:

> “Give me an object URL/API and I'll store files myself.”

I choose:

**Blob Storage**

If it says:

> “I need a shared filesystem that several machines can mount.”

I choose:

**Azure Files**

**Memory line:**
**Blob = objects through APIs.
Files = filesystem through SMB/NFS.**

**Interview trap:**
Don't choose Azure Files merely because the data happens to be a “file.”

A `.jpg` can perfectly well belong in Blob Storage. The deciding factor is usually the **required access pattern**, not the filename.

**Keywords:** Blob Storage, Azure Files, object storage, SMB, NFS, REST API, file share

### **T05-E07. What are Hot, Cool, Cold, and Archive storage tiers?**

**Answer:**
Azure Blob Storage access tiers let me optimize cost based on **how frequently data is accessed and how quickly I need to retrieve it**.

The general trade-off is:

```text
Frequent access
     ↓
Higher storage cost
Lower retrieval cost

Rare access
     ↓
Lower storage cost
Higher retrieval cost
```

Azure currently provides **Hot, Cool, Cold, and Archive** tiers for appropriate blob scenarios. ([Microsoft Learn][1])

### **1. Hot tier**

Used for data accessed or modified frequently.

Examples:

* website images,
* active application data,
* frequently downloaded documents.

```text
Access frequency: High
Storage cost:     Highest of these online tiers
Access cost:      Lowest
Latency:          Milliseconds
```

---

### **2. Cool tier**

Used for data accessed less frequently but still requiring immediate online access.

Examples:

* older application data,
* short-term backup,
* infrequently downloaded documents.

For GPv2 accounts, data is generally expected to remain in Cool for at least **30 days**; early deletion can incur charges. ([Microsoft Learn][1])

```text
Access frequency: Low
Storage cost:     Lower than Hot
Access cost:      Higher than Hot
Latency:          Milliseconds
```

---

### **3. Cold tier**

Cold is also an **online tier**, but for data accessed even less frequently.

The important interview distinction is:

> **Cold does not mean offline.**

Cold data can still be retrieved with millisecond-level access characteristics, unlike Archive.

It is intended for data retained for around **90 days or longer** in the common GPv2 case. ([Microsoft Learn][1])

Example:

```text
Old reports
Security logs
Longer-term backups
```

---

### **4. Archive tier**

Archive provides the **lowest storage cost**, but the data is offline.

Before normal access, the blob generally needs to be **rehydrated** into an online tier.

So retrieval can take:

```text
Hours
```

rather than milliseconds.

Archive is intended for very rarely accessed long-term data, commonly with a minimum retention expectation of **180 days**. ([Microsoft Learn][1])

Examples:

```text
Compliance archives
Historical backups
Old audit datasets
Long-term records
```

### **Easy comparison**

```text
Hot
 ↓
frequently accessed

Cool
 ↓
infrequently accessed

Cold
 ↓
rarely accessed but still online

Archive
 ↓
almost never accessed and can tolerate hours to retrieve
```

### **Lifecycle management**

In production I would often automate tier changes.

For example:

```text
Day 0
Hot

After 30 days
   ↓
Cool

After 90 days
   ↓
Cold

After 180 days
   ↓
Archive

After 7 years
   ↓
Delete
```

using Azure Blob lifecycle-management policies.

This is a common storage cost-optimization pattern.

**Memory line:**
**Hot → Cool → Cold → Archive = less frequent access and generally cheaper storage, but more expensive/slower retrieval.**

**Interview trap:**
Do not say Cold and Archive are basically the same.

```text
Cold    → online, fast retrieval
Archive → offline, rehydration required
```

Also, Archive isn't supported with every redundancy configuration; for example, current Azure documentation lists Archive support with LRS/GRS/RA-GRS rather than ZRS/GZRS variants. ([Microsoft Learn][1])

**Keywords:** Hot, Cool, Cold, Archive, lifecycle management, rehydration, access tier

### **T05-M01. What is LRS?**

**Answer:**
LRS stands for **Locally Redundant Storage**.

With LRS, Azure maintains multiple copies of the storage data **within a single physical datacenter in the primary Azure region**.

Currently, Azure maintains **three copies** for LRS. ([Microsoft Learn][2])

Conceptually:

```text
Azure Region
└── Datacenter
    ├── Copy 1
    ├── Copy 2
    └── Copy 3
```

### **What does LRS protect against?**

LRS protects against failures such as:

* disk failure,
* server failure,
* rack-level hardware failure.

Azure automatically maintains the copies.

### **What does it NOT protect against?**

This is the important part.

Because all copies are within one datacenter, LRS does not give strong protection against a complete datacenter-level disaster such as:

```text
Datacenter-wide outage
Fire
Flood
Major zone/datacenter failure
```

Microsoft describes LRS as the **lowest-cost redundancy option**, but also the option with the least protection compared with ZRS and geo-redundant choices. ([Microsoft Learn][2])

### **Example**

Suppose:

```text
Storage Account
Redundancy = LRS
```

A single disk fails:

```text
Copy 1 ❌
Copy 2 ✅
Copy 3 ✅
```

Azure can continue relying on its replicas.

But if the entire datacenter becomes unavailable:

```text
Datacenter ❌

Copy 1 ❌
Copy 2 ❌
Copy 3 ❌
```

all LRS replicas are affected by that same failure boundary.

### **When would I choose LRS?**

I might use it when:

* cost is the main concern,
* data can easily be recreated,
* higher redundancy isn't justified,
* data must remain within a particular regional boundary and zone resilience isn't required.

For critical production data, I would normally assess **ZRS, GRS, or GZRS** instead.

**Memory line:**
**LRS = 3 copies, one datacenter, lowest-cost redundancy.**

**Interview trap:**
LRS does **not** mean:

> “Three copies across three Availability Zones.”

That is **ZRS**, not LRS.

Also remember: replication protects against infrastructure failure, not accidental deletion. If I delete or overwrite data, that logical change can be replicated too—so features such as soft delete, versioning, backup, or immutability solve different problems. ([Microsoft Learn][2])

**Keywords:** LRS, three copies, single datacenter, redundancy, durability

* Does replication protect against accidental deletion?

### **T05-M02. What is ZRS?**

**Answer:**
ZRS stands for **Zone-Redundant Storage**.

ZRS synchronously replicates Azure Storage data across **three or more Availability Zones within the same Azure region**. ([Microsoft Learn][2])

Conceptually:

```text
Azure Region
│
├── Availability Zone 1
│      └── Replica
│
├── Availability Zone 2
│      └── Replica
│
└── Availability Zone 3
       └── Replica
```

So compared with LRS:

```text
LRS
→ replicas within one datacenter

ZRS
→ replicas across multiple Availability Zones
```

### **What failure does ZRS protect against?**

Suppose Zone 1 becomes unavailable:

```text
Zone 1 ❌
Zone 2 ✅
Zone 3 ✅
```

ZRS is designed so the storage service can remain available from the surviving zones.

That's why ZRS provides significantly better **in-region availability** than LRS.

Microsoft recommends ZRS in the primary region for applications requiring high availability. ([Microsoft Learn][2])

### **Synchronous replication**

The word **synchronous** is important.

For a write to be successfully committed, Azure replicates it across the required zones before acknowledging it according to the service's consistency/redundancy design.

That gives strong protection against a single-zone failure.

### **Does ZRS protect against a complete regional disaster?**

No.

All ZRS copies remain within:

```text
One Azure region
```

So if the **entire region** becomes unavailable:

```text
Region ❌

Zone 1 ❌
Zone 2 ❌
Zone 3 ❌
```

ZRS alone doesn't give secondary-region disaster recovery.

For that requirement, I would consider:

```text
GRS
or
GZRS
```

depending on whether I also want zone redundancy in the primary region.

### **Example choice**

Suppose I have an important Azure Files workload and need to survive one zone going down without moving to another geographic region.

I would strongly consider:

```text
ZRS
```

Microsoft currently specifically recommends ZRS for Azure Files workloads where supported. ([Microsoft Learn][2])

### **LRS vs ZRS**

```text
             LRS                     ZRS

Copies       3                       3+ across zones
Location     One datacenter          Multiple AZs
Rack fault   ✅                      ✅
Zone fault   ❌                      ✅
Region fault ❌                      ❌
Cost         Lower                   Higher
```

**Memory line:**
**LRS = local copies.
ZRS = copies across zones.**

**Interview trap:**
Do not say ZRS replicates data to another Azure region.

That's **geo-redundancy**.

ZRS provides **multi-zone resilience inside one region**. ([Microsoft Learn][2])

**Keywords:** ZRS, Availability Zones, synchronous replication, zone failure, high availability
