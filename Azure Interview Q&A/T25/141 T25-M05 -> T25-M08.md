### **T25-M05. What is build provenance?**

**Answer:**

Build provenance is verifiable information describing **how a software artifact was produced**—for example which source repository and commit it came from, which build system or workflow created it, and which builder identity executed the build.

I think of it as the artifact's **build history and origin evidence**.

```text
Source repository
      ↓
Commit abc123
      ↓
Trusted CI workflow
      ↓
Build environment
      ↓
Container image
sha256:XYZ
      ↓
Build provenance
```

The important production use is that, before deploying an artifact, I can verify not only *what* the artifact is, but also whether it was created through the expected trusted build process.

For an AKS supply chain, that could mean accepting only images whose provenance shows they were built from an approved repository and protected branch by the organization's trusted CI workflow.

---

### **What build provenance is trying to answer**

Suppose I have:

```text
acr.azurecr.io/payment@sha256:abc123
```

The digest tells me exactly which image content I'm referring to.

But I may still want to know:

```text
Where did it come from?
Which Git commit produced it?
Which repository?
Which CI workflow?
Which build identity?
Which build environment?
```

Build provenance provides evidence for those questions.

Conceptually:

```text
Artifact
   ↓
"Where did you come from?"
   ↓
Provenance
```

---

### **Why this matters in software-supply-chain security**

Without provenance, the organization might simply trust:

```text
Image exists in ACR
        ↓
Therefore deployable
```

But that is weak.

Imagine an attacker gets permission to push images into ACR and uploads:

```text
payment:2.7
```

If production trusts anything stored in the registry:

```text
Registry write compromise
          ↓
Malicious image
          ↓
Production
```

the registry becomes the whole trust boundary.

With provenance enforcement:

```text
Image requested
      ↓
Does trusted provenance exist?
      ↓
Built by approved CI?
      ↓
From approved repository?
      ↓
Expected source branch/commit?
      ↓
Yes → continue
No  → reject
```

Now having registry push permission alone may not be enough to make arbitrary software trusted.

---

### **Typical provenance information**

Depending on the implementation, build provenance can describe things such as:

```text
Artifact digest
Source repository
Source commit
Build system
Workflow/job identity
Build parameters
Builder identity
Build timestamp
```

The exact schema depends on the ecosystem.

The key concept is:

> The provenance should be tied to the **specific immutable artifact**, not just to a mutable tag like `latest`.

---

### **Example**

Imagine CI builds:

```text
Source:
github.com/company/payment

Commit:
9af3e12

Workflow:
release.yml

Builder:
trusted GitHub-hosted workflow identity

Output:
sha256:77abc...
```

Provenance can conceptually say:

```text
Artifact sha256:77abc...
was produced
from commit 9af3e12
in company/payment
by approved release workflow
```

That evidence can later be evaluated by deployment policy.

---

## **Build provenance vs SBOM**

This is an important distinction.

```text
SBOM
→ What is inside the artifact?

Build provenance
→ How and from where was the artifact produced?
```

Example:

```text
SBOM:
├── OpenSSL version X
├── package A
└── package B

Provenance:
├── repository: payment-api
├── commit: abc123
├── builder: trusted CI
└── workflow: release
```

Both are useful but answer different questions.

---

## **Build provenance vs image signing**

Also different:

```text
Image signing
→ cryptographically verifies trust/integrity associated with the artifact

Build provenance
→ provides claims about the artifact's build origin/process
```

Often provenance itself is made verifiable through signing or an attestation mechanism.

So these concepts work together:

```text
Artifact
   │
   ├── Signature
   ├── SBOM
   └── Provenance attestation
```

---

## **Build provenance vs artifact attestation**

This follows directly from the previous question.

```text
Attestation
→ general mechanism for a verifiable claim about an artifact

Build provenance
→ one specific kind of claim
```

So:

```text
Artifact attestation
      ↓
      ├── Provenance attestation
      ├── SBOM attestation
      └── other evidence
```

Build provenance is therefore **not synonymous with every attestation**.

---

### **Production AKS example**

A mature pipeline might look like:

```text
Developer
   ↓
Pull Request
   ↓
Review + CI
   ↓
Protected main
   ↓
Trusted build workflow
   ↓
Build container
   ↓
Image digest
   ↓
Generate SBOM
   ↓
Generate provenance
   ↓
Scan
   ↓
Sign / attest
   ↓
ACR
   ↓
AKS deployment request
   ↓
Admission policy
   ↓
Verify trusted evidence
   ↓
ALLOW / DENY
```

This establishes a traceable chain:

```text
Source
  ↓
Commit
  ↓
Build
  ↓
Artifact
  ↓
Deployment
```

---

### **Why protected source matters**

Suppose provenance correctly proves:

```text
Image was built from commit abc123
```

but any developer could directly push arbitrary commits into `main`.

Then the provenance is technically valid but the source-control boundary is weak.

So trustworthy provenance depends on upstream controls too:

```text
Protected main
+
Code review
+
Required CI
+
Trusted builder
+
Artifact provenance
```

Software-supply-chain security is a chain; weakness in one link affects the whole model.

---

### **What if the build system is compromised?**

Very important caveat.

If an attacker fully compromises the trusted CI builder:

```text
Trusted CI compromised
        ↓
Malicious image
        ↓
Apparently valid provenance
```

Provenance cannot magically make that artifact safe.

This is why you also secure:

* CI workflow modifications,
* runner environments,
* CI identities,
* third-party actions/tasks,
* repository branch protections,
* cloud permissions.

Provenance increases traceability and policy enforcement, but the builder itself still has to be trusted.

---

### **Build once, promote the same artifact**

Provenance is strongest when you follow:

```text
Build once
   ↓
sha256:ABC
   ↓
Dev
   ↓
Staging
   ↓
Production
```

rather than:

```text
Build Dev image
Build Staging image
Build Production image
```

If you rebuild for every environment, you are no longer proving that the exact artifact tested in staging is the one running in production.

With build-once-deploy-many:

```text
Same digest
+
same provenance
+
different environment configuration
```

is easier to audit and trust.

---

### **Interview answer condensed**

> “Build provenance is verifiable information describing how a particular artifact was created—typically its source repository and commit, the build system or workflow, and the builder identity. I would associate provenance with the immutable artifact digest so production can verify that the image was produced by the approved CI pipeline from approved source rather than trusting anything that happens to exist in ACR. It's different from an SBOM, which describes what's inside the artifact, and from signing, which provides cryptographic trust. Provenance is commonly represented as a type of artifact attestation.”

**Memory line:**
**SBOM tells me what is inside; provenance tells me where the artifact came from and how it was built.**

**Interview trap:**
Valid provenance does **not** guarantee secure software if the trusted build system itself has been compromised.

**Keywords:**
Build provenance, source commit, trusted builder, CI workflow, artifact digest, attestation, supply chain, traceability.

### **T25-M06. Why should CI pipelines use short-lived credentials?**

**Answer:**

CI pipelines should use short-lived credentials because they significantly reduce the exposure window if a credential is stolen.

Instead of storing a client secret or access key that may remain valid for months, I prefer workload identity federation such as OIDC where the CI workload proves its identity to Microsoft Entra ID and receives a temporary Azure access token.

For example, with GitHub Actions:

```text
GitHub Actions job
       ↓
OIDC token
       ↓
Microsoft Entra ID
       ↓
Federated identity validation
       ↓
Short-lived Azure access token
       ↓
Azure resource
```

This removes the need to store a long-lived Azure client secret in GitHub and means a captured access token expires relatively quickly.

But short-lived credentials must still be combined with **least-privilege Azure RBAC**. A temporary token with subscription-wide Owner access is still dangerous while it is valid.

---

### **The problem with long-lived credentials**

A traditional CI setup might use:

```text
AZURE_CLIENT_ID
AZURE_TENANT_ID
AZURE_CLIENT_SECRET
```

with a client secret valid for:

```text
6 months
12 months
24 months
```

The secret may be stored in:

```text
CI secret store
```

which is better than committing it to source, but it still exists as a reusable credential.

If compromised:

```text
Secret leaked
    ↓
Attacker copies secret
    ↓
Uses it from another machine
    ↓
Continues until:
secret expires
or
administrator revokes it
```

The attacker doesn't necessarily need to compromise CI again.

---

## **Short-lived/federated model**

Instead:

```text
CI job starts
    ↓
CI platform proves workload identity
    ↓
Microsoft Entra ID validates federation
    ↓
Temporary access token issued
    ↓
Job uses Azure
    ↓
Token expires
```

There is no reusable Azure password sitting around for months.

That changes the threat model significantly.

---

### **GitHub Actions example**

Conceptually:

```text
GitHub repository
      ↓
Workflow
      ↓
GitHub OIDC issuer
      ↓
OIDC token containing claims
      ↓
Microsoft Entra ID
      ↓
Federated Identity Credential
      ↓
Validation
      ↓
Azure token
```

The federated trust can be constrained to expected workload attributes, for example a specific:

```text
organization
repository
branch/environment
```

depending on how the federation is configured.

The important idea is:

```text
No Azure client secret
```

needs to be stored in GitHub.

---

## **Authentication vs authorization**

This is an important Azure interview distinction.

OIDC federation answers:

```text
Who is this workflow?
```

That is **authentication**.

Azure RBAC answers:

```text
What is this workflow allowed to do?
```

That is **authorization**.

So a secure CI design might be:

```text
GitHub Actions
      ↓
OIDC authentication
      ↓
Entra workload identity
      ↓
Azure RBAC
      ↓
Contributor only on RG-app-dev
```

instead of:

```text
GitHub Actions
      ↓
OIDC
      ↓
Owner at subscription
```

OIDC doesn't automatically create least privilege.

---

## **Why short-lived credentials reduce risk**

### **1. Smaller theft window**

If an access token is stolen:

```text
Token stolen
   ↓
Token usable
   ↓
Token expires
```

The window is limited.

Compare that with a client secret:

```text
Secret stolen
   ↓
Reusable again and again
   ↓
Potentially months
```

---

### **2. Less secret rotation**

With long-lived secrets:

```text
Create
 ↓
Store
 ↓
Track expiration
 ↓
Rotate
 ↓
Update CI
 ↓
Ensure old one revoked
```

This becomes operational overhead.

It also creates incidents such as:

```text
Secret expires unexpectedly
        ↓
Production deployment fails
```

Federation eliminates much of that secret-lifecycle burden.

---

### **3. Lower accidental-exposure risk**

Long-lived secrets can leak through:

* logs,
* copied environment variables,
* debugging output,
* misconfigured secret stores,
* screenshots,
* accidental source commits.

With federation, there is no permanent Azure client secret to steal.

---

### **4. Better workload identity**

Federation can identify the workload rather than pretending a pipeline is a human user.

That's cleaner operationally:

```text
Human engineer
→ human Entra identity

GitHub workflow
→ workload identity

AKS workload
→ workload identity
```

Different principals can receive different permissions.

---

### **5. Easier revocation of trust**

If GitHub should no longer deploy:

```text
Delete/disable federated trust
```

instead of searching for all copies of a reusable client secret.

---

## **What short-lived credentials do NOT solve**

This is where interview answers often become too simplistic.

Imagine the pipeline receives a temporary token with:

```text
Owner
at subscription scope
```

for one hour.

During that hour, a compromised workflow can still:

```text
delete resources
create privileged identities
change RBAC
extract accessible data
```

So the complete model is:

```text
Short-lived authentication
       +
Least privilege authorization
       +
Trusted pipeline
       +
Repository protection
```

not merely:

```text
OIDC = secure
```

---

### **If the CI pipeline itself is malicious**

Suppose someone modifies:

```yaml
deploy.yml
```

to run:

```text
malicious Azure commands
```

If that workflow is allowed to obtain the trusted federated token, the commands can still execute within the identity's permissions.

So I also protect:

```text
Workflow files
     ↓
PR review
     ↓
Branch protection
     ↓
Required CI
     ↓
Controlled production environment
```

and keep Azure permissions narrow.

---

## **Separate identities per environment**

I would avoid one super-identity such as:

```text
ci-deployer
→ Contributor across Dev + Stage + Prod
```

when practical.

A cleaner model:

```text
Dev workflow
   ↓
dev deployment identity
   ↓
Dev RG only

Staging workflow
   ↓
staging deployment identity
   ↓
Staging RG only

Production workflow
   ↓
production deployment identity
   ↓
Prod scope only
```

Potentially with stronger controls on production.

This reduces blast radius.

---

## **Example: GitHub Actions to Azure**

```text
Developer
   ↓
PR
   ↓
Protected main
   ↓
Deployment workflow
   ↓
GitHub OIDC
   ↓
Microsoft Entra ID
   ↓

   ↓

```

Notice that two security boundaries exist:

```text

→ establishes identity

```

---

## **Why not just put the client secret in Key Vault?**

That's better than putting it in YAML, but it doesn't eliminate the credential.

You now have:

```text
Pipeline
   ↓
must authenticate somehow
   ↓
Key Vault
   ↓
retrieve long-lived secret
   ↓
Azure
```

There may still be scenarios where stored credentials are unavoidable, but where federation is supported, eliminating the secret is generally preferable.

---

### **Interview answer condensed**

> “CI pipelines should use short-lived credentials because a stolen reusable secret can remain useful to an attacker for months, while a temporary token has a limited lifetime. For GitHub Actions targeting Azure, I'd normally use OIDC workload identity federation: GitHub presents an OIDC token to Microsoft Entra ID, Entra validates the configured federated identity, and issues a short-lived Azure access token. That removes the need to store an Azure client secret and reduces rotation overhead. But federation only solves authentication—I would still give the workload identity least-privilege Azure RBAC at the smallest practical scope.”

**Memory line:**
**Remove reusable secrets, issue credentials only when the workload needs them, and keep their lifetime and permissions small.**

**Interview trap:**
OIDC federation does **not** automatically provide least privilege; a short-lived token with excessive RBAC can still cause major damage.

**Keywords:**
Short-lived credentials, OIDC, Workload Identity Federation, Microsoft Entra ID, Azure RBAC, least privilege, token, client secret, blast radius.

* What happens if a federated workflow itself is compromised?
* Why is putting a client secret in a secure secret store still weaker than eliminating it?

### **T25-M07. What is policy as code?**

**Answer:**

Policy as code means expressing security, compliance, and operational rules in **machine-readable, version-controlled code** so they can be reviewed, tested, automated, and enforced consistently.

Instead of relying on a document saying, “Production storage accounts must not be public,” I would encode that requirement as a policy and evaluate infrastructure or deployment changes automatically.

```text
Human requirement
      ↓
"Production must not expose storage publicly"
      ↓
Policy code
      ↓
CI / deployment / platform enforcement
      ↓
Pass or Fail
```

In Azure and DevOps environments, policy as code can be applied at several levels—for example Azure Policy for Azure-resource governance, IaC scanning for Terraform, and Kubernetes admission policies for AKS workloads.

The major advantage is that controls become **repeatable and auditable**, but a policy is only effective if it is attached to a real enforcement point and tested properly.

---

### **Why policy as code exists**

Traditional governance might look like:

```text
Security document:
"Don't create public databases."
```

Then developers are expected to remember it.

That creates:

```text
Human interpretation
+
manual review
+
inconsistent enforcement
```

Policy as code turns it into:

```text
Resource configuration
       ↓
Policy engine
       ↓
Compliant?
   /          \
Yes           No
 ↓             ↓
allow       warn/deny
```

The rule becomes executable.

---

## **Important characteristics**

Good policy as code is typically:

```text
Version controlled
Reviewable
Testable
Automatable
Repeatable
Auditable
```

So policy changes themselves can follow:

```text
Policy change
    ↓
Pull Request
    ↓
Review
    ↓
Tests
    ↓
Merge
    ↓
Controlled rollout
```

That is important because a bad policy can block legitimate production deployments just as a bad application change can.

---

## **Where policy as code can operate**

There isn't only one layer.

### **1. Source / IaC layer**

Before deployment:

```text
Terraform
   ↓
Policy/scanner
   ↓
Misconfiguration?
```

Example:

```text
azurerm_network_security_rule
allows:
source = 0.0.0.0/0
destination_port = 22
```

A policy can flag or block it during PR validation.

---

### **2. Azure resource-governance layer**

Azure Policy can evaluate Azure resources against governance rules.

Conceptually:

```text
ARM deployment request
       ↓
Azure Policy
       ↓
Policy evaluation
       ↓
Allowed / Denied / Audited / Remediated
```

Example organizational requirements:

```text
Only approved regions
No public IP in production
Required diagnostic configuration
Mandatory resource configuration
```

The exact effect depends on the Azure Policy definition.

---

### **3. Kubernetes admission layer**

For AKS:

```text
kubectl / GitOps
      ↓
Kubernetes API server
      ↓
Admission policy
      ↓
Workload compliant?
   /              \
Yes               No
 ↓                 ↓
store object      reject
```

Examples:

```text
No privileged containers
Require resource limits
Only trusted registries
Require security context
Require image trust evidence
```

depending on the policy engine and organizational controls.

## **Policy as code and CI/CD**

A strong workflow might be:

```text
Developer
   ↓

   ↓
terraform fmt
   ↓
terraform validate
   ↓
terraform plan
   ↓
Policy checks
   ↓

   ↓

```

Notice the **two layers**:

```text
CI policy
→ catches issue before deployment

Azure Policy
→ protects the actual Azure environment
```

This is defense in depth.

---

### **Why both CI scanning and platform enforcement?**

Suppose CI rejects public storage:

```text
Terraform PR
     ↓
CI policy rejects
```

Great.

But what if someone goes directly to:

```text
Azure Portal
```

and changes the resource manually?

CI never sees that.

Azure-side governance can still evaluate or deny the configuration.

So:

```text
CI policy
→ developer feedback

Platform policy
→ environmental enforcement
```

They complement each other.

---

## **Policy as code vs RBAC**

A very important distinction:

```text
RBAC
→ Who is allowed to perform an action?

Policy
→ What configurations/actions are allowed?
```

For example:

An engineer may have:

```text
Contributor
```

so Azure RBAC says:

```text
Yes, this identity can create a VM.
```

But Azure Policy may say:

```text
VM location = unapproved region
→ DENY
```

So:

```text
Authorization succeeded
but
governance policy rejected configuration
```

Policy and RBAC solve different problems.

---

## **Policy as code vs validation**

Another subtle distinction:

```text
terraform validate
```

answers:

> Is this Terraform configuration syntactically and structurally valid?

It does **not** mean:

> Is this configuration compliant with my organization's security policy?

For example:

```hcl
resource "azurerm_network_security_rule" "ssh" {
  source_address_prefix      = "*"
  destination_port_range     = "22"
  access                     = "Allow"
}
```

may be perfectly valid Terraform.

But organizational security policy might reject it.

So:

```text
Valid configuration
      ≠
Secure/compliant configuration
```

---

## **Production example**

Suppose an organization requires:

```text
Production Storage:
├── no public network access
├── HTTPS only
└── private connectivity
```

The rule may be enforced at multiple points:

```text
Terraform PR
     ↓
IaC policy check
     ↓
Pass
     ↓
terraform apply
     ↓
Azure Policy
     ↓
Resource remains compliant
```

If somebody later attempts an out-of-band deployment that violates policy:

```text
Portal / CLI / another pipeline
      ↓
Azure Policy
      ↓
DENY
```

That's much stronger than relying on one CI pipeline.

---

## **Audit vs deny**

Not every new rule should immediately block production.

For an existing environment with thousands of resources, I may introduce a new rule as:

```text
Audit
```

first.

Then:

```text
Evaluate violations
      ↓
Understand impact
      ↓
Remediate
      ↓
Move toward Deny
```

Otherwise a poorly understood policy can unexpectedly break legitimate deployments.

This is a production-governance lesson worth mentioning.

---

## **Policy testing**

Because policies are code, they can have bugs.

I would test:

```text
Expected-compliant resource
→ should pass

Expected-noncompliant resource
→ should fail
```

and verify exemptions/edge cases.

For example:

```text
Policy:
"No public IPs"

Exception:
Approved Azure Bastion/public ingress architecture
```

If exceptions are legitimate, they should be controlled rather than silently bypassed.

This is different from RBAC—RBAC decides who can perform an operation, while policy decides whether the requested configuration is acceptable. I'd also treat policy changes like software: peer review them, test them, and often introduce new rules in audit mode before moving to deny in production.”

**Memory line:**
**RBAC controls who can act; policy as code controls what configurations are allowed.**

**Interview trap:**
Passing `terraform validate` does **not** mean infrastructure is secure or policy-compliant.

### **T25-M08. How can Terraform configurations be security scanned?**

**Answer:**

I would security-scan Terraform **before `terraform apply`**, ideally during pull-request validation.

The workflow would first run normal Terraform quality checks such as `terraform fmt` and `terraform validate`, then use an IaC security scanner or policy engine to inspect the configuration for risky settings—for example public exposure, overly permissive NSGs, weak storage configuration, insecure AKS settings, or missing encryption/security controls.

For stronger validation, I may also evaluate the **Terraform plan**, because some effective values are not obvious from individual `.tf` files.

```text
Terraform code
     ↓
terraform fmt
     ↓
terraform validate
     ↓
IaC security scan
     ↓
terraform plan
     ↓
Plan/policy evaluation
     ↓
Review
     ↓
Apply
     ↓
Azure
```

I would then keep Azure Policy or equivalent platform controls in place because CI scanning can be bypassed and cannot prevent every portal or out-of-band change.

The key distinction is that `terraform validate` checks whether Terraform understands the configuration; a security scanner checks whether the configuration is **safe according to security rules**.

---

### **What security scanning is looking for**

Suppose Terraform contains:

```hcl
resource "azurerm_network_security_rule" "ssh" {
  direction                  = "Inbound"
  access                     = "Allow"
  protocol                   = "Tcp"
  source_address_prefix      = "*"
  destination_port_range     = "22"
}
```

Terraform may consider that completely valid.

```text
terraform validate
       ↓
Success
```

But a security scanner can reason:

```text
SSH
+
Internet source
+
Inbound allow
     ↓
Potential security exposure
```

and flag it.

A realistic flow:

```text
Developer modifies main.tf
       ↓
PR opened
       ↓
terraform fmt -check
       ↓
terraform init -backend=false
       ↓
terraform validate
       ↓
IaC scanner
       ↓
terraform plan
       ↓
policy evaluation
       ↓
Required status check
       ↓
Review
       ↓
Merge
```

The exact sequence depends on tooling, but the important principle is:

> Detect insecure configuration before it reaches Azure.

---

## **Why `terraform fmt` and `validate` aren't security scanning**

Commands such as:

```bash
terraform fmt -check
terraform validate
```

are valuable, but they do not perform broad security analysis.

Think of it like:

```text
terraform fmt
→ formatting

terraform validate
→ configuration validity

Security scanner
→ configuration risk

terraform plan
→ proposed infrastructure changes
```

These answer different questions.

---

## **Configuration scanning vs plan scanning**

Scanning raw Terraform code is useful:

```text
.tf files
   ↓
Scanner
```

but sometimes configuration values come indirectly from:

```text
variables
modules
locals
conditional expressions
environment-specific inputs
```

For example:

```hcl
source_address_prefix = var.allowed_source
```

The source file does not tell the scanner exactly what `var.allowed_source` will become in production.

The plan may resolve it to:

```text
0.0.0.0/0
```

So plan evaluation can provide additional context:

```text
Terraform configuration
        +
Production variables
        ↓
terraform plan
        ↓
Resolved proposed changes
        ↓
Policy evaluation
```

This can be more accurate for environment-specific controls.

---

## **Scanning Terraform modules**

Modules are another important concern.

Suppose:

```text
root module
    ↓
network module
    ↓
security module
```

A scanner should ideally analyze the expanded/effective configuration rather than only the ten lines in the root module.

Otherwise risk can hide inside reused modules.

This is also why you should review and control module sources.

For third-party modules:

```text
Terraform Registry/Git source
        ↓
module code
        ↓
your infrastructure privileges
```

Treat them as supply-chain dependencies.

---

## **Security scan results should be pipeline gates**

A weak implementation:

```text
Scanner finds Critical issue
        ↓
prints warning
        ↓
pipeline continues
```

means the scanner may provide very little protection.

A stronger policy:

```text
Critical policy violation
     ↓
CI failure
     ↓
PR merge blocked
```

with documented exception handling when necessary.

But, as with vulnerability scanning, you need sensible rules to avoid teams simply bypassing noisy controls.

---

## **Example policy reasoning**

Suppose scanner finds:

```text
NSG allows 0.0.0.0/0 → port 443
```

Is that automatically wrong?

Not necessarily.

If it's:

```text
public web ingress
```

HTTPS may intentionally be internet-facing.

But:

```text
0.0.0.0/0 → port 22
```

on a production VM may be unacceptable.

So good policy understands **context**, not merely patterns.

---

## **Terraform state is another security concern**

This is easy to overlook.

Terraform configuration scanning primarily examines infrastructure definitions, but Terraform state can contain sensitive values.

So separately, I would protect state with:

```text
Remote Azure Storage backend
        ↓
restricted Azure RBAC
        ↓
private/network controls where required
        ↓
encryption
        ↓
no tfstate committed to Git
```

Security scanning a `.tf` file does not protect a poorly secured remote state backend.

---

## **Secrets in Terraform**

I would avoid:

```hcl
password = "SuperSecret123"
```

because:

```text
Git exposure
+
potential state exposure
```

Even if I mark a variable:

```hcl
sensitive = true
```

that primarily limits display in certain Terraform outputs; it does **not automatically guarantee the value is absent from state**.

That's an important interview trap.

For Azure, prefer identity-based access where practical:

```text
Managed Identity
Workload Identity
OIDC federation
```

instead of embedding credentials into Terraform-managed configuration.

---

## **IaC security scanning plus Azure Policy**

These are complementary:

```text
Terraform PR
    ↓
IaC scanning
    ↓
Catch issue early
```

then:

```text
terraform apply
    ↓
Azure Resource Manager
    ↓
Azure Policy
    ↓
environment-level enforcement
```

Why both?

Because somebody might use:

```text
Azure Portal
Azure CLI
Bicep
another pipeline
```

instead of your Terraform pipeline.

Azure Policy protects the destination environment regardless of the deployment client.

---

## **Practical production pipeline**

```text
Git PR
  ↓
terraform fmt -check
  ↓
terraform validate
  ↓
IaC security scanning
  ↓
Secret scanning
  ↓
terraform plan
  ↓
Plan policy evaluation
  ↓
Human review
  ↓
Merge
  ↓
Approved deployment pipeline
  ↓
terraform apply
  ↓
Azure Policy
  ↓
Azure resources
```

This combines:

```text
code quality
+
security
+
review
+
platform governance
```

rather than relying on one scanner.

---

### **What if the scanner disagrees with reality?**

Security scanners produce false positives and false negatives.

So if a finding is false positive:

```text
Finding
 ↓
Review evidence
 ↓
Document justified exception
 ↓
Time-bound/scope-bound suppression
```

I would avoid globally disabling the rule.

For example:

```text
Bad:
disable rule organization-wide

Better:
suppress specific resource
with documented reason
and owner
```

That preserves the control elsewhere.

---

### **Interview answer condensed**

> “I would scan Terraform during PR validation before `apply`. I'd run `fmt` and `validate` first, then an IaC security scanner or policy engine to detect things such as overly permissive NSGs, public exposure, insecure storage or Key Vault configuration, and excessive RBAC. I'd also consider evaluating the Terraform plan because variables and modules can make the effective configuration different from what is obvious in the raw `.tf` files. Security findings that violate production policy should normally block the PR. Finally, I'd still use Azure Policy as a platform-level guardrail because CI scanning can't protect against changes made through the portal, CLI, or another pipeline.”

**Memory line:**
**`terraform validate` asks “is this valid Terraform?”; security scanning asks “is this safe Terraform?”**

**Interview trap:**
Marking a Terraform value `sensitive` does **not** automatically prevent that value from being stored in Terraform state.

**Keywords:**
Terraform security scanning, IaC scanning, `terraform validate`, `terraform plan`, policy as code, NSG, public exposure, RBAC, remote state, Azure Policy.
