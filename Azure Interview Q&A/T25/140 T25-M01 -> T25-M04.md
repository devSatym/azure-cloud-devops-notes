### **T25-M01. Where should security scanning occur in a CI/CD pipeline?**

**Answer:**

I would place security scanning at **multiple stages of the pipeline**, because different controls are effective at different points.

I would scan as early as possible for fast developer feedback—for example secret scanning, SAST, dependency scanning, and IaC scanning during pull-request validation. Then after building the artifact, I would scan the container image or package that will actually be deployed. Before production, I would enforce security gates based on policy, and after deployment I would still keep runtime monitoring and threat detection.

So my model is not:

```text
Build
 ↓
One security scan
 ↓
Production
```

It is:

```text
Developer
   ↓
Pull Request
   ├── Secret scanning
   ├── SAST
   ├── Dependency scanning
   └── IaC scanning
   ↓
Build artifact
   ↓
Container / artifact scanning
   ↓
Sign / attest artifact
   ↓
Deployment policy
   ↓
Production
   ↓
Runtime monitoring
```

The goal is **defense in depth with fast feedback early and stronger enforcement closer to production**.

---

### **How I would structure the pipeline**

For an application being deployed to AKS, I would normally think about the pipeline in stages.

#### **1. Developer / pre-commit stage**

Useful lightweight checks:

```text
Developer workstation
      ↓
Secret detection
Linting
Basic security checks
```

This gives the fastest possible feedback.

For example, if someone accidentally writes:

```text
AZURE_CLIENT_SECRET=<credential>
```

I want that caught before it even reaches the central repository.

But I would **not rely only on developer-side hooks**, because developers can disable or bypass them.

The server-side CI pipeline remains the enforcement point.

---

#### **2. Pull-request stage**

This is one of the most important security gates.

```text
Pull Request
   │
   ├── SAST
   ├── secret scan
   ├── dependency scan
   ├── Terraform/IaC scan
   ├── lint
   └── tests
       ↓
Required checks
       ↓
Merge allowed
```

Why here?

Because the vulnerability is still cheap to fix.

The developer still knows:

```text
what they changed
why they changed it
which files are affected
```

and insecure code hasn't entered the trusted `main` branch yet.

---

### **What each PR-time scan is looking for**

#### **SAST**

Looks primarily at application code:

```text
Source code
    ↓
Static analysis
    ↓
Potential security weakness
```

Examples:

* injection patterns,
* unsafe APIs,
* insecure input handling.

---

#### **Dependency scanning**

Looks at third-party components:

```text
package-lock.json
go.mod
pom.xml
requirements.txt
        ↓
known vulnerability database
```

It answers:

> “Does this application depend on a package with a known vulnerability?”

---

#### **Secret scanning**

Looks for exposed credentials:

```text
Source / config
     ↓
API key?
Password?
Token?
Private key?
```

---

#### **IaC scanning**

For Terraform/Bicep/Kubernetes manifests:

```text
Infrastructure code
       ↓
Security policy
       ↓
Misconfiguration?
```

For example:

```text
Storage public access enabled
NSG allows 0.0.0.0/0 to SSH
Key Vault public access unrestricted
AKS API exposed unnecessarily
```

could be identified before infrastructure is created.

---

## **3. Build stage**

Once the source passes initial checks, I build the actual deployable artifact.

For containers:

```text
Source
  ↓
docker build
  ↓
Immutable image
```

Now I can scan **what will actually run**.

This matters because source/dependency scans may not fully represent the final image.

The container may contain:

```text
Base image packages
OS libraries
Runtime packages
Application dependencies
```

So:

```text
Source scan
     ≠
Final image scan
```

---

## **4. Container-image / artifact scanning**

For AKS:

```text
Build Image
    ↓
Container Scanner
    ↓
Critical CVEs?
   /             \
Yes              No
 ↓                ↓
Fail pipeline    Continue
```

For example:

```text
frontend:v1.8.3
      ↓
OpenSSL CVE
severity: Critical
```

The security policy may block promotion.

---

## **5. Sign and attest the trusted artifact**

A stronger supply-chain pipeline adds trust metadata after successful validation:

```text
Build
 ↓
Test
 ↓
Scan
 ↓
Generate SBOM
 ↓
Sign / attest
 ↓
Trusted artifact
```

This provides stronger answers to questions like:

```text
Who built this artifact?
From which source?
Which workflow produced it?
Was it modified afterward?
```

The important production principle is:

> **The artifact you validate should be the artifact you deploy.**

Do not:

```text
Build image A
scan image A
then rebuild image B for production
```

because the production artifact was never actually validated.

Instead:

```text
Build once
   ↓
scan once
   ↓
promote same immutable digest
   ↓
Dev → Staging → Production
```

---

## **6. Deployment-time policy**

Scanning can tell us:

```text
"This artifact violates policy."
```

but we also want deployment controls that can say:

```text
"You are not allowed to run it."
```

For example:

```text
AKS admission request
       ↓
Policy
       ↓
Trusted/signature requirements
       ↓
Allow / Deny
```

This protects against someone bypassing the normal CI/CD path and trying to deploy an untrusted artifact manually.

---

## **7. Runtime security still matters**

Even a pipeline where every scan passes can still be compromised.

Why?

Because:

```text
new CVE discovered after deployment
runtime exploit
stolen application identity
unexpected behavior
misconfiguration
zero-day vulnerability
```

may appear later.

So:

```text
Shift left
      +
Protect delivery
      +
Monitor runtime
```

is stronger than treating pre-production scanning as the final security step.

For Azure workloads, runtime controls may involve technologies such as:

* Microsoft Defender for Cloud/Containers,
* Azure Monitor,
* Kubernetes audit/diagnostic telemetry,
* workload/runtime security controls.

---

### **What should actually block the pipeline?**

A common mistake is:

```text
Every scanner finding
      ↓
Fail everything
```

That can produce alert fatigue and eventually cause teams to bypass security.

Instead, I would establish an explicit policy.

For example:

```text
Critical exploitable vulnerability
→ block

High vulnerability with fix available
→ normally block

Medium
→ policy-dependent remediation SLA

Low
→ track unless context raises risk
```

But **severity alone isn't enough**.

I would also consider:

```text
Exploitability
Internet exposure
Affected component
Fix availability
Compensating controls
Business criticality
```

For example:

```text
Critical vulnerability
but vulnerable library code path unreachable
```

versus:

```text
High vulnerability
in internet-facing authentication service
with active exploitation
```

The second situation may be more urgent operationally.

---

### **A production pipeline example**

```text
GitHub PR
   ↓
Secret Scan
   ↓
SAST
   ↓
Dependency Scan
   ↓
Terraform Scan
   ↓
Code Review
   ↓
Merge
   ↓
Build Image
   ↓
Image Vulnerability Scan
   ↓
SBOM
   ↓
Sign / Attest
   ↓
ACR
   ↓
Deploy to AKS staging
   ↓
DAST / Integration testing
   ↓
Production policy gate
   ↓
AKS
   ↓
Runtime monitoring
```

This is much stronger than having one giant “security stage” just before deployment.

---

### **Important distinction: scanning vs enforcement**

```text
Scanning
→ identifies a potential problem

Policy / gate
→ decides whether the pipeline may proceed
```

For example:

```text
Scanner:
Critical CVE found

Pipeline policy:
Critical CVE → FAIL
```

The scanner alone does not automatically create a secure delivery process.

---

### **Interview answer condensed**

> “I would distribute security scanning across the pipeline rather than create one security stage. During PR validation I'd run secret scanning, SAST, dependency scanning and IaC checks so developers get fast feedback before code reaches `main`. After building I'd scan the exact container or artifact that will be deployed, generate supply-chain metadata such as an SBOM where appropriate, and then promote that same immutable artifact through environments. Deployment policies should enforce the security result, and runtime monitoring should continue after release because pre-production scans cannot detect every threat or newly discovered vulnerability.”

**Memory line:**
**Scan early for fast feedback, scan the final artifact for accuracy, enforce before deployment, and monitor after deployment.**

**Interview trap:**
Putting every security tool into one late “security stage” is **not** effective DevSecOps; security controls belong at the point where they provide the strongest signal and cheapest remediation.

**Keywords:**
Shift left, PR validation, SAST, dependency scanning, secret scanning, IaC scanning, image scanning, security gate, immutable artifact, runtime security.

**Likely follow-ups:**

* Which scans would you run on a pull request versus after building an image?
* Should every vulnerability fail the pipeline?
* Why should you scan the actual final container image?
* What's the difference between security scanning and policy enforcement?

### **T25-M02. What is an SBOM?**

**Answer:**

An SBOM is a **Software Bill of Materials**. It is a structured inventory of the software components contained in or associated with an application or artifact.

You can think of it like an ingredient list for software. It can describe application libraries, package versions and other components so that when a vulnerability is announced, an organization can quickly determine which applications or container images contain the affected component.

For example:

```text
Container Image
   ↓
SBOM
   ├── openssl 3.x
   ├── libc ...
   ├── express ...
   ├── lodash ...
   └── application components
```

If a new CVE appears for one of those packages, I can search the SBOM inventory and identify potentially affected workloads without manually inspecting every application.

An SBOM improves **software-supply-chain visibility**, but it does not by itself prove that the artifact is secure or trustworthy.

---

### **Why SBOMs became important**

Modern applications are dependency graphs.

A service that looks like:

```text
My API
```

may actually contain:

```text
My API
  ↓
Framework
  ↓
Direct libraries
  ↓
Transitive libraries
  ↓
Operating-system packages
```

So a developer might write:

```text
20,000 lines of custom code
```

while the complete runtime contains hundreds or thousands of third-party components.

Without an inventory, answering:

> “Are we affected by vulnerability X?”

can become extremely difficult.

---

### **Mental model**

An SBOM answers:

```text
What is inside this software?
```

It does **not primarily answer**:

```text
Is everything inside secure?
```

That second question requires vulnerability analysis and context.

---

### **Example**

Suppose a container SBOM contains:

```text
payment-service:v4.2
│
├── Node.js 24.x
├── express 5.x
├── package-A 2.4
├── package-B 7.1
└── openssl 3.x
```

Three months later a vulnerability is announced for:

```text
package-B 7.1
```

Instead of:

```text
Open every repository
 ↓
inspect package files
 ↓
inspect every image
```

the security team can query its software inventory:

```text
Which SBOMs contain package-B 7.1?
             ↓
payment-service:v4.2
order-service:v8.6
customer-service:v3.9
```

Now the response can be targeted.

---

## **SBOM and transitive dependencies**

This becomes especially valuable for transitive dependencies.

You may directly use:

```text
Framework A
```

which internally depends on:

```text
Library B
```

which depends on:

```text
Library C
```

The vulnerable component may be:

```text
Library C
```

even though nobody intentionally added it.

```text
Application
    ↓
Framework A
    ↓
Library B
    ↓
Library C ← CVE
```

An accurate software inventory helps make that dependency visible.

---

## **Where I would generate an SBOM**

In a mature pipeline, I prefer generating it as part of the trusted build:

```text
Source
   ↓
Trusted CI
   ↓
Build artifact
   ↓
Generate SBOM
   ↓
Scan
   ↓
Sign / attest
   ↓
Registry
```

This lets me associate:

```text
artifact digest
     ↔
SBOM
```

For example:

```text
sha256:abc123...
      ↓
SBOM describing exactly that artifact
```

This is better than generating an inventory from an arbitrary local environment unrelated to what actually reached production.

---

## **SBOM and container images**

For AKS workloads:

```text
Dockerfile
    ↓
Build image
    ↓
Image digest
    ↓
SBOM
```

The SBOM may describe:

```text
OS packages
+
language dependencies
+
application components
```

depending on the generation tool and format.

This is important because a container includes more than application dependencies.

---

## **Common formats**

Two common SBOM ecosystems/formats you should recognize in an interview are:

```text
SPDX
CycloneDX
```

You don't need to memorize every schema field for most Cloud/DevOps interviews.

The conceptual value is much more important.

---

## **SBOM vs vulnerability scan**

This is probably the most important distinction.

```text
SBOM
→ inventory of components

Vulnerability scanner
→ compares components/configuration against known vulnerability intelligence
```

Example:

SBOM says:

```text
openssl version X exists
```

Scanner says:

```text
openssl version X is affected by CVE-YYYY-ZZZZ
```

So:

```text
SBOM = evidence of contents

Vulnerability database + analysis
= security assessment
```

An SBOM does **not** mean:

```text
"No CVEs exist."
```

---

## **SBOM vs artifact signature**

These are also different.

```text
SBOM
→ what components are present?

Signature
→ can I verify artifact integrity and signer identity?
```

You might have:

```text
Unsigned image
+
perfect SBOM
```

The component inventory could be accurate, but you still haven't established that the artifact came from a trusted producer.

Likewise:

```text
Signed image
+
no SBOM
```

can prove provenance/integrity properties without telling you everything inside the image.

Good supply-chain security may use both.

---

## **SBOM vs provenance**

Another useful distinction:

```text
SBOM
→ WHAT is inside the software?

Provenance
→ HOW / WHERE / FROM WHAT was it built?
```

For example:

```text
SBOM:
package X version Y

Provenance:
built from commit abc123
using workflow release.yml
by trusted CI
```

Together they give significantly stronger supply-chain visibility.

---

## **Production Azure example**

Consider:

```text
GitHub
 ↓
GitHub Actions
 ↓
Build payment-service
 ↓
Generate SBOM
 ↓
Scan
 ↓
Push image to ACR
 ↓
AKS
```

Now during a vulnerability incident:

```text
Critical CVE announced
       ↓
Search SBOM inventory
       ↓
Identify affected ACR image digests
       ↓
Identify AKS workloads running them
       ↓
Patch / rebuild / redeploy
```

That can drastically reduce incident-response time.

---

### **What an SBOM doesn't solve**

An SBOM cannot guarantee:

* the source was trustworthy,
* the CI environment was uncompromised,
* the artifact wasn't replaced,
* no zero-day exists,
* the application is securely configured,
* the application behaves securely at runtime.

So an SBOM is one evidence layer:

```text
SBOM
+
signing
+
provenance
+
scanning
+
policy
+
runtime controls
```

---

### **Interview answer condensed**

> “An SBOM, or Software Bill of Materials, is a structured inventory of the components contained in a software artifact, including direct and potentially transitive dependencies. I would typically generate it during the trusted CI build and associate it with the exact immutable artifact or container digest. Its main operational value is vulnerability response: when a new CVE appears, we can quickly identify which applications or images contain the affected package. But an SBOM is only an inventory—it doesn't itself prove that the artifact is vulnerability-free, signed, or built by a trusted pipeline.”

**Memory line:**
**An SBOM is the ingredient list of a software artifact.**

**Interview trap:**
An SBOM does **not** mean the software is secure; it tells you what components are present so you can assess them.

**Keywords:**
SBOM, Software Bill of Materials, SPDX, CycloneDX, dependency inventory, transitive dependencies, CVE response, artifact digest, supply chain.

### **T25-M03. What is image signing?**

**Answer:**

Image signing is a mechanism for attaching a **cryptographically verifiable signature** to a container image—ideally to its immutable digest—so a consumer can verify that the image came from an expected signer and hasn't been replaced with different content.

In a secure AKS supply chain, I would build and scan the image in trusted CI, push it to a registry such as ACR, sign the image digest, and then enforce a deployment policy that only permits images satisfying the organization's trust requirements.

Conceptually:

```text
Trusted CI
   ↓
Build image
   ↓
sha256:abc123
   ↓
Sign digest
   ↓
ACR
   ↓
AKS admission policy
   ↓
Verify signature
   ↓
Allow / Deny
```

The purpose isn't encryption—the container remains readable. Signing provides **integrity and authenticity evidence**.

---

### **Why image tags aren't enough**

Suppose production deploys:

```text
myapp:1.5
```

A tag is essentially a human-friendly reference.

It can potentially be repointed:

```text
myapp:1.5
   ↓
sha256:AAA
```

and later:

```text
myapp:1.5
   ↓
sha256:BBB
```

depending on registry controls and workflow.

So if I sign only a conceptual label without binding trust to immutable content, my security guarantee is weak.

What I really care about is:

```text
sha256:AAA...
```

because the digest identifies the actual image content.

Thus:

```text
Tag
→ convenient reference

Digest
→ immutable content identity
```

For strong supply-chain verification, the digest is critical.

---

## **What problem does signing solve?**

Imagine a normal pipeline:

```text
Git
 ↓
CI
 ↓
Build image
 ↓
ACR
 ↓
AKS
```

Now suppose somebody with registry access pushes a different image.

Without verification:

```text
Registry
  ↓
AKS trusts whatever is referenced
```

With signing and admission verification:

```text
Image requested
      ↓
Verify trusted signature
      ↓
Expected signer?
      ↓
Yes → allow
No  → deny
```

That turns trust into an enforceable control.

---

## **What cryptographic verification establishes**

At a high level:

```text
Signer
   ↓
signs identity/content reference
   ↓
Signature
```

Verifier checks:

```text
artifact content/digest
+
signature
+
trusted signer identity/key
```

If verification succeeds, it provides evidence that:

1. the signed content matches what was signed, and
2. the signature corresponds to the trusted signer/signing identity.

It does **not** mean the application's code is secure.

A trusted CI pipeline can still sign a vulnerable artifact unless other pipeline controls exist.

---

## **Signing should happen after validation**

I would generally structure the workflow as:

```text
Build
 ↓
Test
 ↓
SAST/dependency checks
 ↓
Image scan
 ↓
Sign trusted artifact
 ↓
Promote
```

Signing too early creates a misleading trust signal.

For example:

```text
Build
 ↓
Sign
 ↓
Scan finds critical vulnerability
```

Technically the image may be authentically signed, but it isn't approved for production.

Organizations therefore need to define what the signature means.

Ideally:

> “This artifact was produced by the approved build process and passed the required controls.”

---

## **Signing vs scanning**

Very important distinction:

```text
Image scanning
→ Is this image known to contain vulnerable components?

Image signing
→ Can I verify this image came from an expected trusted signer and matches the signed content?
```

You need both.

For example:

```text
Signed malicious image
```

is possible if the trusted signer itself is compromised.

And:

```text
Unsigned vulnerability-free image
```

may still violate your supply-chain policy because you cannot establish its origin.

---

## **Signing vs image digest**

Another useful distinction:

```text
Digest
→ identifies content

Signature
→ establishes cryptographic trust over that content
```

A digest alone tells me:

```text
"This is exactly image X."
```

It does not tell me:

```text
"Trusted CI created image X."
```

The signature provides that additional trust evidence.

## **Production AKS architecture**

```text
Developer
   ↓
GitHub
   ↓
Protected PR
   ↓
Trusted GitHub Actions
   ↓
Build image
   ↓
Scan image
   ↓
Generate SBOM
   ↓
Push image to ACR
   ↓
Sign digest
   ↓
ACR stores artifact/signature metadata
   ↓

   ↓

   ↓

```

Now compromising a developer's local Docker environment is not enough to get an arbitrary image into production.

The attacker would also need to satisfy the organization's signing/admission trust policy.

---

## **Key-based vs keyless concepts**

Traditional signing might involve:

```text
Private signing key
        ↓
sign image
```

The difficult question becomes:

```text
How do we protect the signing key?
```

Modern supply-chain systems can also support identity-based or “keyless” signing approaches where short-lived identity credentials and transparency/evidence mechanisms reduce reliance on permanently stored signing keys.

For interview purposes, the key point is:

```text
Trust a verified workload identity
rather than distribute long-lived signing secrets
```

where the chosen platform supports it.

---

## **What if the signing pipeline is compromised?**

Signing isn't magic.

If an attacker controls:

```text
trusted CI
```

they may be able to produce:

```text
malicious image
+
valid trusted signature
```

That's why the CI identity and pipeline itself must also be protected.

For example:

```text
Protected main
+
review requirements
+
restricted workflow modifications
+
short-lived Azure identity
+
least privilege
+
pinned dependencies/actions
+
audit logs
```

Signing is part of a **chain of trust**.

---

### **Interview answer condensed**

> “Image signing cryptographically associates a trusted signer with a container image, ideally using the immutable image digest. In a production AKS pipeline I'd build, test and scan the image in trusted CI, sign the approved digest, push or associate the signature with the artifact in ACR, and enforce verification at deployment time so untrusted images are denied. Signing is different from scanning: scanning asks whether the image contains known vulnerabilities, while signing establishes authenticity and integrity evidence. A valid signature also doesn't guarantee secure code if the trusted build pipeline itself is compromised.”

**Memory line:**
**The digest tells me which image it is; the signature helps tell me whether I should trust where that image came from.**

**Interview trap:**
A signed image is not automatically a secure image—signing verifies trust/integrity properties, not absence of vulnerabilities.

**Keywords:**
Image signing, cryptographic signature, image digest, authenticity, integrity, ACR, AKS admission control, trust policy, keyless signing, supply chain.

### **T25-M04. What is artifact attestation?**

**Answer:**

Artifact attestation is **signed or otherwise verifiable metadata that makes a claim about a software artifact**.

Instead of only saying:

```text
"This image came from signer X"
```

an attestation can provide claims such as:

```text
This image was built from commit abc123
This build ran in an approved CI workflow
This artifact has a particular SBOM
This artifact passed a particular control
```

So in a secure software supply chain, the artifact has not just an image but evidence associated with it:

```text
Container image
      │
      ├── Signature
      ├── SBOM attestation
      ├── Provenance attestation
      └── Other policy evidence
```

Then a deployment policy can evaluate those claims before allowing the artifact into production.

---

### **Why an attestation is useful**

Consider an image:

```text
sha256:abc123
```

Knowing its digest proves that we're referring to specific content.

A signature might tell us:

```text
Trusted build identity signed sha256:abc123
```

But security may want deeper evidence:

```text
Was it built from the approved repository?

Was the source commit on protected main?

Which workflow built it?

Which dependencies were inside it?

Did the expected build process produce it?
```

An attestation gives a structured way to carry those claims.

---

## **Mental model**

Think of:

```text
Artifact
   =
Thing we deploy

Attestation
   =
Verifiable statement about that thing
```

For example:

```text
Artifact:
payment-service@sha256:abc123

Attestation:
"Built from commit 913be2 by workflow production-build"
```

The attestation should be bound to the artifact so it cannot simply be reused for unrelated content.

---

## **Attestation vs signature**

These terms are related but not identical.

```text
Signature
→ cryptographic evidence associated with content or a statement

Attestation
→ the statement/claim about the artifact, typically made verifiable using signing or equivalent trust mechanisms
```

An easy way to think about it:

```text
Signature:
"Trusted party approves/authenticates this object."

Attestation:
"Trusted party makes this specific claim about this object."
```

For example:

```text
"Image digest X is signed by release pipeline"
```

versus:

```text
"Image digest X was built from repository Y,
commit Z, using workflow W."
```

The second contains richer evidence.

---

## **Common attestation categories**

For DevSecOps interviews, two especially useful ones are:

### **1. Provenance attestation**

Answers:

```text
Where did this artifact come from?
```

Potential information:

```text
Source repository
Source commit
Build system
Workflow
Builder identity
Build parameters
```

---

### **2. SBOM attestation**

Answers:

```text
What components are associated with this artifact?
```

For example:

```text
Image digest X
      ↓
SBOM
      ↓
packages A, B, C...
```

The attestation creates verifiable evidence connecting the SBOM to the artifact.

---

## **Why this matters for AKS**

Imagine a developer tries to deploy:

```text
acr.azurecr.io/payment@sha256:abc123
```

An admission policy could conceptually ask:

```text
Does this artifact have trusted provenance?
        ↓
Was it produced by approved CI?
        ↓
Does required evidence exist?
        ↓
Yes → allow
No  → deny
```

Now the deployment decision isn't based merely on:

```text
Image exists in registry
```

but on:

```text
Image exists
+
required trust evidence exists
+
evidence passes policy
```

This is a much stronger software-supply-chain model.

## **End-to-end example**

```text
Developer
   ↓
Pull Request
   ↓
Review + CI
   ↓
Merge to protected main
   ↓
Trusted build workflow
   ↓
Build container
   ↓
sha256:ABC
   │
   ├── SBOM generated
   ├── vulnerability scan
   └── provenance generated
          ↓
Attestations associated with sha256:ABC
          ↓
Push / store with artifact ecosystem
          ↓
AKS deployment
          ↓
Admission policy evaluates evidence
          ↓
ALLOW / DENY
```

This creates a chain from:

```text
Source
 ↓
Build
 ↓
Artifact
 ↓
Deployment
```

with verifiable evidence along the way.

## **Artifact attestation vs build provenance**

These are related but not synonymous.

```text
Attestation
→ general mechanism for making a verifiable claim

Build provenance
→ one particular type of claim describing how an artifact was built
```

So:

```text
All provenance evidence may be expressed as an attestation

but

Not every attestation is provenance
```

because an attestation could describe:

```text
SBOM
test result
security scan
policy result
```

depending on the system.

---

## **Attestation vs SBOM**

```text
SBOM
→ component inventory

SBOM attestation
→ verifiable claim that this SBOM belongs to this particular artifact
```

That's a subtle but very useful distinction.

---

## **Why provenance matters when CI is compromised**

Suppose an attacker manually builds:

```text
malicious payment image
```

and somehow uploads it to ACR.

Without supply-chain policy:

```text
ACR image exists
     ↓
possibly deployable
```

With attestation requirements:

```text
Image exists
    ↓
Where is trusted provenance?
    ↓
No approved build attestation
    ↓
Deployment denied
```

So compromising only registry push access may not be sufficient to bypass the deployment trust boundary.

Again, if the **trusted CI itself** is compromised, the attacker may be able to generate apparently valid evidence, which is why build-system protection remains critical.

---

## **What a production policy might require**

Conceptually:

```text
Production artifact must:

1. be referenced by digest
2. have trusted signature
3. have provenance from approved CI
4. originate from approved repository
5. have required SBOM evidence
6. satisfy vulnerability policy
```

Then:

```text
Deploy request
    ↓
Evidence evaluation
    ↓
Pass all requirements?
    ↓
Yes → production
No  → blocked
```

This is far stronger than trusting a container solely because it is inside your registry.

---

### **Security implication**

Attestations shift the question from:

> “Can this identity deploy?”

to two separate questions:

```text
1. Is the deployer authorized?

2. Is the artifact itself trusted?
```

That is a powerful security distinction.

Azure RBAC might allow a deployment identity to interact with AKS, but the cluster can independently require that the actual workload artifact satisfy supply-chain policy.

```text
Identity authorization
        ≠
Artifact trust
```

Both are needed.

### **Interview answer condensed**

> “Artifact attestation is verifiable metadata containing a claim about a specific software artifact. For example, an attestation might state that a container image was built from a particular Git commit by an approved CI workflow, or associate an SBOM with that exact image digest. In a secure AKS supply chain I'd generate provenance and other evidence during trusted CI and then allow deployment only when required attestations satisfy policy. Attestation is broader than image signing: signing establishes cryptographic trust, while an attestation carries a specific claim such as provenance or SBOM information that can itself be cryptographically verified.”

**Memory line:**
**An artifact is what I deploy; an attestation is verifiable evidence describing something I claim to know about that artifact.**

**Interview trap:**
Artifact attestation and image signing are related but not identical—a signature can establish trust, while an attestation carries a specific claim such as provenance or SBOM information.
