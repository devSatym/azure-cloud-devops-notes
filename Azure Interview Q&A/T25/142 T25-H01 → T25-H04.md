# **T25-H01. How would you design a secure software-supply-chain pipeline targeting AKS?**

**Answer:**

I would secure the pipeline as a chain of trust from **source code → CI identity → build → artifact → registry → deployment → runtime**.

I would protect `main` with PR reviews and required CI, run SAST, dependency, secret, IaC and container-image scanning, then **build the container once** and identify it by immutable digest. I would generate an SBOM and provenance, sign the approved image using Notation, store it in ACR, and deploy that exact digest to AKS.

For identity, I would avoid long-lived Azure client secrets. GitHub Actions or Azure Pipelines would authenticate to Azure using workload identity federation where possible and receive only the Azure RBAC permissions needed—for example ACR push rights rather than subscription-wide Contributor.

Finally, I would enforce trust again at AKS admission time so bypassing CI doesn't allow an unsigned or untrusted image to run. Microsoft currently documents Notation-based signing for ACR and signature verification on AKS using Ratify with Azure Policy. ([Microsoft Learn][1])

```text
Developer
   ↓
Protected Git branch
   ↓
Pull Request
   ├── Code review
   ├── SAST
   ├── Secret scan
   ├── Dependency scan
   └── IaC scan
   ↓
Trusted CI
   ↓
Build ONCE
   ↓
Container image
sha256:ABC...
   ├── Vulnerability scan
   ├── SBOM
   ├── Provenance
   └── Signature / Attestation
   ↓
Azure Container Registry
   ↓
Deployment by digest
   ↓
AKS Admission Control
   ↓
Signature / policy verification
   ↓
Trusted? ── No → DENY
   │
  Yes
   ↓
Running workload
   ↓
Defender / Azure Monitor / Runtime detection
```

---

## **1. Protect the source before protecting the image**

The supply chain begins at Git, not at ACR.

If an attacker can freely change:

```text
application code
Dockerfile
Terraform
Helm manifests
CI workflow
```

then later signing the artifact does not save me—the trusted pipeline could faithfully sign malicious source.

So first:

```text
main
│
├── direct pushes blocked
├── PR required
├── reviewers required
├── required CI checks
└── workflow/IaC changes reviewed
```

For especially sensitive repositories, I would use CODEOWNERS or equivalent controls for:

```text
.github/workflows/*
azure-pipelines.yml
Dockerfile
terraform/*
helm/*
```

because those files can change the behavior of the trusted build system itself.

---

# **2. Separate PR validation from trusted release**

I don't want an arbitrary pull request to receive production permissions.

```text
Untrusted / less-trusted PR
        ↓
Build + test + scan
        ↓
NO production credentials
```

After approved code reaches the protected branch:

```text
Protected main
     ↓
Trusted release workflow
     ↓
Federated Azure identity
     ↓
Build/publish permissions
```

That protects against a contributor changing a PR to execute:

```bash
az account show
az acr login ...
```

and stealing privileged credentials.

---

# **3. Use short-lived workload identity**

For GitHub Actions targeting Azure:

```text
GitHub workflow
     ↓
GitHub OIDC token
     ↓
Microsoft Entra ID
     ↓
Federated Identity Credential
     ↓
Short-lived Azure access token
     ↓
Azure RBAC
```

Then scope the identity tightly.

For example, the image-publishing job might receive permission only to:

```text
ACR repository / registry
        ↓
push image
```

instead of:

```text
Owner
at subscription scope
```

These are separate controls:

```text
OIDC federation
→ authentication

Azure RBAC
→ authorization
```

OIDC does **not** make an overprivileged identity safe.

---

# **4. Scan before building and after building**

I'd use several different controls because they answer different questions.

```text
Source
├── SAST
├── dependency scanning
├── secret scanning
└── IaC scanning

        ↓

Container
└── image vulnerability scanning
```

Why image scanning separately?

Because the final image may contain vulnerabilities in:

```text
base image
OS packages
runtime libraries
language packages
```

that aren't obvious from application source.

Microsoft Defender for Containers currently provides vulnerability assessment for ACR images as well as visibility into vulnerabilities affecting running AKS containers. ([Microsoft Learn][2])

---

# **5. Build once and identify by digest**

I would strongly prefer:

```text
Build
 ↓
myapp@sha256:ABC
 ↓
Dev
 ↓
Staging
 ↓
Production
```

rather than:

```text
Build for Dev
Build again for Staging
Build again for Prod
```

Why?

Because with separate builds:

> The artifact that passed staging may not be byte-for-byte identical to the artifact deployed to production.

The digest gives immutable identity:

```text
Tag:
myapp:v4

may point to different content

Digest:
myapp@sha256:ABC...

identifies exact content
```

---

# **6. Generate SBOM and provenance**

I would attach evidence to the artifact.

```text
sha256:ABC
│
├── SBOM
│     └── What is inside?
│
└── Provenance
      └── How was it built?
```

For example:

```text
SBOM:
openssl X
package A
package B

Provenance:
repo = payment-api
commit = 37abc...
builder = approved CI
workflow = release
```

That helps both security verification and later CVE response.

---

# **7. Sign the image after successful validation**

Current Azure guidance supports OCI/container signing using **Notation**, with Azure Key Vault or Azure Artifact Signing-based approaches. ([Microsoft Learn][3])

Conceptually:

```text
Build
 ↓
Test
 ↓
Scan
 ↓
Approved
 ↓
Sign SHA256 digest
 ↓
ACR
```

Not:

```text
Build
 ↓
Sign immediately
 ↓
Critical vulnerability discovered later
```

I want a signature to represent a meaningful organizational trust decision.

# **8. Enforce trust at AKS—not only in CI**

This is one of the strongest answers you can give in an interview.

Suppose CI verifies signatures:

```text
CI
 ↓
signature valid
 ↓
deploy
```

But someone with Kubernetes permissions manually runs:

```bash
kubectl run bad --image=some-untrusted-image
```

They bypass CI completely.

Therefore:

```text
CI verification
       +
AKS admission verification
```

is stronger.

Microsoft documents Ratify integrated with Azure Policy to evaluate image signatures during admission. With a `Deny` policy, images that don't satisfy signature verification are rejected. ([Microsoft Learn][4])

```text
kubectl / Helm / Argo CD
          ↓
Kubernetes API
          ↓
Admission
          ↓
Ratify verification
          ↓
Trusted signature?
    ┌──────────┴──────────┐
   Yes                    No
    ↓                      ↓
 Admit                   Deny
```

---

# **9. Separate registry access from image trust**

Another interview-quality distinction:

```text
Image exists in ACR
        ≠
Image is trusted
```

ACR authentication answers:

> Can this identity push/pull this artifact?

Image verification answers:

> Should this artifact be allowed to run?

These are different security controls.

---

# **10. Protect ACR**

For production I would also consider:

* private networking where required,
* least-privilege ACR roles,
* separate push and pull identities,
* disabling unnecessary admin credentials,
* immutable deployment references,
* audit/monitoring.

For AKS:

```text
AKS kubelet identity
       ↓
AcrPull
       ↓
ACR
```

doesn't require giving application developers broad ACR administration.

---

# **11. Runtime security completes the chain**

Passing CI doesn't mean the workload is permanently secure.

A new CVE may be discovered tomorrow.

Or the workload might be exploited at runtime despite a clean image scan.

So:

```text
Secure Build
      +
Secure Admission
      +
Runtime Monitoring
```

Microsoft Defender for Containers currently covers ACR image vulnerability assessment, AKS posture and runtime-threat signals. ([Microsoft Learn][2])

---

## **Failure domains I would think about**

A good interviewer might ask, “What could still go wrong?”

### Source compromised

```text
Malicious source
↓
valid trusted build
↓
valid signature
```

Therefore protect source control.

### CI compromised

```text
Trusted builder compromised
↓
malicious signed artifact
```

Therefore secure runners, workflow files, third-party tasks and identities.

### Registry compromised

Attacker pushes unsigned image.

Admission signature verification should reject it.

### Signing key compromised

Attacker can make arbitrary artifacts appear trusted.

Protect signing material or use managed/short-lived signing mechanisms.

### AKS policy bypassed

A cluster-admin could potentially weaken admission configuration.

Control privileged Kubernetes and Azure administration separately.

---

## **Production rollout strategy**

I would not introduce a hard admission policy blindly.

I'd generally do:

```text
Audit
 ↓
observe legitimate workloads
 ↓
fix exceptions / trust configuration
 ↓
test signed + unsigned images
 ↓
Deny
```

Microsoft's Ratify/Azure Policy guidance supports both `Audit` and `Deny` behavior. ([Microsoft Learn][4])

---

### **Interview answer condensed**

> “I would secure the AKS supply chain end to end. Source starts on a protected branch with mandatory review and CI. PRs run SAST, secret, dependency and IaC scanning without production credentials. Trusted CI uses workload identity federation to Azure, builds the container once, scans it, generates an SBOM and provenance, and identifies it by immutable digest. After validation I'd sign that digest using a trusted signing identity and store the artifact in ACR. Production deploys the exact digest, and AKS admission policy verifies the signature so a user can't bypass the trusted pipeline and deploy an unsigned image manually. I would then continue with Defender for Containers and runtime monitoring because supply-chain controls don't replace runtime security.”

**Memory line:**
**Trust must be established from source to build to artifact to deployment—not simply because an image exists in ACR.**

**Interview trap:**
A **signed image can still be malicious or vulnerable** if the source, build system, or signing identity was compromised.

**Keywords:**
Protected branch, OIDC, workload identity federation, ACR, immutable digest, SAST, SBOM, provenance, Notation, Ratify, Azure Policy, admission control, Defender for Containers.

**Likely follow-ups:**

* Why deploy by digest instead of image tag?
* What happens if the trusted CI pipeline is compromised?
* Why do you need AKS admission enforcement if CI already verifies images?
* How would GitHub Actions authenticate to ACR without storing a client secret?
* What is the difference between SBOM, provenance and signing?

# **T25-H02. How would you prevent unsigned images from running in production?**

**Answer:**

I would solve this at the **Kubernetes admission layer**, not only in CI.

First, the trusted CI pipeline would build and scan the container, sign the immutable image digest using a trusted signing identity, and push the image and its signature to ACR. For Azure today, I would use the Notary Project/Notation approach rather than designing a new solution around legacy Docker Content Trust.

Then on production AKS I would configure signature verification—for example Ratify with Azure Policy—and use a `Deny` enforcement policy. When a Pod deployment reaches the Kubernetes API, admission control verifies that the referenced image has a valid signature from an approved identity. A trusted signed image is admitted; an unsigned image or an image signed by an untrusted identity is rejected. Microsoft documents exactly those three expected cases. ([Microsoft Learn][4])

```text
CI
 ↓
Build image
 ↓
Scan
 ↓
Sign digest
 ↓
ACR
 ↓
Deployment request
 ↓
AKS Admission
 ↓
Signature verification
 ↓
     Valid + trusted?
      /          \
    Yes          No
     ↓            ↓
   Admit         DENY
```

---

## **Step 1 — Sign the immutable artifact**

Suppose CI produces:

```text
myacr.azurecr.io/payment@sha256:ABC123...
```

I sign:

```text
sha256:ABC123...
```

rather than relying on:

```text
payment:latest
```

because tags can move.

Microsoft's current ACR documentation uses Notation trust policies and verification for signed OCI artifacts. ([Microsoft Learn][3])

Typical verification conceptually looks like:

```bash
notation verify \
  myacr.azurecr.io/payment@sha256:<digest>
```

I'm looking for successful validation against the configured trust policy.

---

# **Step 2 — Define WHO is trusted**

A signature is meaningless without a trust policy.

I don't want:

```text
signed by anyone
→ accepted
```

I want:

```text
signed by approved production signer
→ accepted
```

The trust policy should define things such as:

```text
Registry/repository scope
Trusted certificate / identity
Verification level
Trusted CA / trust store
```

So:

```text
Signed with attacker certificate
```

must fail just like:

```text
Unsigned image
```

---

# **Step 3 — Enforce at Kubernetes admission**

The actual control point is:

```text
Pod CREATE
     ↓
Kubernetes API server
     ↓
Admission control
     ↓
Signature verifier
```

Microsoft's current documented Ratify pattern integrates Ratify with Azure Policy/Gatekeeper for AKS. Ratify retrieves the signature metadata and evaluates the Notary trust policy; with the Azure Policy `Deny` effect, failed verification blocks admission. ([Microsoft Learn][4])

This means these paths are all covered:

```text
GitHub Actions
Helm
Argo CD
kubectl
Azure DevOps
      ↓
Kubernetes API
      ↓
same admission policy
```

That's why admission enforcement is superior to trusting the deployment pipeline alone.

---

## **Step 4 — Test all three cases**

I would explicitly verify the control.

### Case 1: trusted signed image

```text
Trusted signature
       ↓
ALLOW
```

### Case 2: unsigned image

```text
No signature
    ↓
DENY
```

### Case 3: signed by untrusted identity

```text
Valid cryptographic signature
        ↓
Wrong signer
        ↓
DENY
```

This last case is often missed.

**Signed ≠ trusted.**

Microsoft's documented Ratify/Azure Policy flow shows trusted signed images being admitted and unsigned/untrusted-signer images being rejected under `Deny`. ([Microsoft Learn][4])

---

## **What would denial look like?**

A deployment may fail with an admission error such as:

```text
Error from server (Forbidden):
admission webhook denied the request:
Subject failed verification
```

Then I would investigate:

```text
Deployment denied
      ↓
Correct image digest?
      ↓
Signature exists?
      ↓
Correct trust policy scope?
      ↓
Trusted signer?
      ↓
Verifier can access ACR?
      ↓
Certificate/trust store valid?
```

Useful checks include:

```bash
notation ls <image@digest>
notation verify <image@digest>

kubectl get pods -n <ratify-namespace>
kubectl logs <ratify-pod> -n <ratify-namespace>
```

The first group proves whether signing metadata and local trust verification work.

The Ratify logs help prove why admission verification failed.

---

# **Step 5 — Use Workload Identity for the verifier**

The verifier may need access to ACR and possibly certificate material.

I wouldn't store Azure credentials in a Kubernetes Secret if avoidable.

Conceptually:

```text
Ratify ServiceAccount
       ↓
AKS OIDC
       ↓
Azure Workload Identity
       ↓
User-assigned Managed Identity
       ↓
AcrPull / required Key Vault access
```

Microsoft's Ratify guidance specifically documents a user-assigned managed identity plus federated identity credential for this access path. ([Microsoft Learn][4])

---

# **Step 6 — Roll out Audit before Deny**

Imagine enabling `Deny` and discovering that:

```text
CoreDNS sidecar image
monitoring agent
third-party controller
```

isn't covered by your trust policy.

You could break legitimate operations.

So:

```text
Audit
 ↓
find violations
 ↓
sign/approve required images
 ↓
validate trust configuration
 ↓
Deny
```

is safer.

---

## **Current Azure terminology: don't default to Docker Content Trust**

This is a useful current interview detail.

Azure Container Registry's legacy Docker Content Trust is on the way out: Microsoft states that from **May 31, 2026**, DCT can't be enabled on new registries or registries that hadn't already enabled it, and complete removal is planned for **March 31, 2028**. Microsoft directs customers toward the Notary Project/Notation model. ([Microsoft Learn][5])

So in a current design I would say:

```text
Notation / Notary Project
```

rather than proposing DCT as the future architecture.

---

## **Important distinction: signature enforcement vs vulnerability enforcement**

These are separate controls.

```text
Signature verification
→ Is this artifact from a trusted source?

Vulnerability gate
→ Does this image satisfy vulnerability policy?
```

An image can be:

```text
validly signed
+
contain Critical CVE
```

Microsoft Defender for Containers now also provides gated deployment based on vulnerability findings, but that is a **different** question from signature verification. ([Microsoft Learn][6])

A strong platform can require both:

```text
Trusted signature
        +
acceptable vulnerability posture
        ↓
Production
```

---

### **Interview answer condensed**

> “I wouldn't rely only on CI to prevent unsigned images because a user could bypass CI and deploy directly to Kubernetes. I'd build and scan the image in trusted CI, sign the immutable image digest with Notation using an approved signing identity, and store the signature with the image in ACR. On production AKS I'd enforce verification at admission time—for example using Ratify with Azure Policy set to `Deny`. The trust policy would require not just any signature but a signature from the expected trusted identity. I'd test three cases: trusted signed image succeeds, unsigned image fails, and image signed by an untrusted identity also fails. I'd normally introduce this in Audit mode before switching production to Deny.”

**Memory line:**
**Sign at build time; verify and enforce again at deployment time.**

**Interview trap:**
**Signed does not mean trusted**—a valid signature from an unapproved signer must still be rejected.

**Keywords:**
Notation, Notary Project, ACR, image digest, Ratify, Azure Policy, admission control, `Deny`, trust policy, Workload Identity.

**Likely follow-ups:**

* Why isn't CI-only signature verification enough?
* What happens if somebody signs an image using another valid certificate?
* How would you troubleshoot an image unexpectedly rejected by Ratify?
* What's the difference between signature enforcement and vulnerability gating?
* Would you use Docker Content Trust for a new ACR implementation today?

# **T25-H03. What would you do if a critical vulnerability were found in an image already running in production?**

**Answer:**

I would treat it as a risk-based production security incident, but I would not blindly terminate every pod simply because the scanner says “Critical.”

First I would identify the **exact vulnerable image digest**, which workloads and clusters are running it, whether the vulnerability is actually applicable and exploitable in our environment, whether the workload is internet-facing or privileged, and whether there is evidence of active exploitation.

If exposure is severe or exploitation is suspected, containment comes first—for example isolate the workload, restrict traffic, disable the vulnerable feature, scale it down if business impact allows, and rotate credentials if compromise is possible.

Then I would patch the dependency or base image, **rebuild a new immutable image through the trusted CI pipeline**, rescan it, generate fresh supply-chain evidence, sign it, deploy it progressively, and verify both security findings and application health. I would not “patch the running container” because containers should be replaced with a new known artifact.

Microsoft Defender for Containers currently exposes vulnerability findings for ACR images and vulnerable images actually running in AKS, which helps identify affected runtime workloads. ([Microsoft Learn][7])

```text
Critical CVE detected
       ↓
Confirm affected digest/workloads
       ↓
Assess exploitability + exposure
       ↓
Active exploitation?
   /                 \
 Yes                  No
  ↓                    ↓
Contain immediately   Prioritized remediation
  \                    /
   ↓
Patch dependency/base image
       ↓
Rebuild image
       ↓
Rescan
       ↓
Sign
       ↓
Deploy progressively
       ↓
Verify
       ↓
Investigate recurrence / prevent
```

---

# **Step 1 — Confirm what is actually affected**

I don't start by looking only at the tag.

Suppose:

```text
payment:v7
```

has been reused.

Production may actually run:

```text
payment@sha256:AAA
```

while the latest `v7` now points to:

```text
sha256:BBB
```

So I need the actual runtime digest.

For Kubernetes:

```bash
kubectl get pods -A \
  -o custom-columns='NAMESPACE:.metadata.namespace,POD:.metadata.name,IMAGE:.spec.containers[*].image'
```

Then correlate against registry/Defender findings.

I want to know:

```text
Which digest?
Which cluster?
Which namespace?
Which pods?
How many replicas?
Which environment?
```

---

# **Step 2 — Understand the vulnerability, not just the CVSS label**

I would examine:

```text
Affected package
Installed version
Fixed version
Exploit prerequisites
Network exposure
Required privileges
Known exploitation
Reachability
Runtime configuration
Business criticality
```

For example:

```text
Critical CVE
requires local root access
package unused
```

has a different emergency profile from:

```text
Critical RCE
internet-facing API
no authentication required
active exploits available
```

Severity is an input into prioritization, not the entire decision.

---

# **Step 3 — Look for active exploitation**

If the vulnerability could already have been exploited, patching alone isn't enough.

I would inspect:

* Defender for Containers alerts,
* Kubernetes audit activity,
* unusual process execution,
* unexpected outbound connections,
* application logs,
* identity/sign-in logs,
* Key Vault/Storage/database access patterns.

Microsoft Defender for Containers provides runtime threat detection in addition to vulnerability assessment, which is important for distinguishing “vulnerable” from “possibly compromised.” ([Microsoft Learn][2])

---

# **Step 4 — Contain based on the risk**

Potential containment options, ordered from least disruptive to most disruptive:

```text
Disable vulnerable feature
        ↓
Restrict ingress
        ↓
Restrict egress / NetworkPolicy
        ↓
Remove workload from public routing
        ↓
Scale affected deployment down
        ↓
Emergency isolation
```

The choice depends on availability requirements.

For an internet-facing RCE with known exploitation, I'd favor rapid containment over preserving perfect availability.

For a vulnerability requiring an impossible configuration in our environment, I might keep service available while accelerating patching.

---

## **If compromise is suspected: rotate identity material**

Suppose the pod can access:

```text
Key Vault
Storage
Database
Service Bus
```

and there is evidence an attacker may have executed code inside it.

I would assume accessible credentials/tokens could have been exposed.

Potential actions:

```text
Compromised pod
     ↓
revoke/rotate secrets where applicable
     ↓
review managed identity permissions
     ↓
review access logs
     ↓
invalidate sessions/tokens where possible
```

With Managed Identity/Workload Identity, there may not be a permanent Azure password to rotate, which is one benefit of secretless authentication—but I still need to review what the workload identity accessed.

---

# **Step 5 — Fix the source, not the running container**

Bad response:

```text
kubectl exec
apt upgrade
```

Why?

Because:

```text
running pod fixed manually
      ↓
pod recreated
      ↓
old vulnerable image returns
```

and the actual supply-chain artifact remains vulnerable.

Instead:

```text
Dockerfile / dependency manifest
        ↓
update vulnerable component
        ↓
commit
        ↓
trusted CI
```

Microsoft's remediation guidance for ACR vulnerability findings recommends rebuilding images with updated base images/packages and scanning again. ([Microsoft Learn][8])

---

# **Step 6 — Rebuild a new artifact**

Example:

```text
Vulnerable:
payment@sha256:OLD

Patch dependency/base image
        ↓
Build
        ↓
payment@sha256:NEW
```

Then run the same trusted pipeline:

```text
Tests
 ↓
SAST / dependency scan
 ↓
Image scan
 ↓
SBOM
 ↓
Provenance
 ↓
Sign
```

Do not just retag the old image.

---

# **Step 7 — Verify the fix before production**

I would check:

```text
Does scanner still find the CVE?
Did base image actually update?
Did tests pass?
Any regression?
Does image have expected signature/provenance?
```

If the scanner still reports it, possible causes include:

```text
wrong package upgraded
transitive dependency remains
base image still old
scanner database differences
no fixed version exists
```

---

# **Step 8 — Deploy progressively**

If the application supports it:

```text
New patched image
      ↓
small canary
      ↓
health checks
      ↓
error rate / latency
      ↓
larger rollout
      ↓
100%
```

I would watch:

* HTTP 5xx,
* latency,
* pod restarts,
* readiness,
* business transaction success,
* security alerts.

Security remediation that breaks production is still a production failure.

---

# **Step 9 — Remove the vulnerable version from active use**

After successful rollout:

```text
kubectl workloads
      ↓
confirm OLD digest absent
```

Then deal with registry lifecycle according to retention/audit requirements.

Simply deleting the tag is not proof that no running pod still references the digest.

---

# **Step 10 — Prevent recurrence**

I would ask:

> Why did a critical vulnerable image make it into production or remain there?

Possible improvements:

```text
CI image scanning
      ↓
vulnerability policy
      ↓
deployment gate
      ↓
periodic registry/runtime rescan
      ↓
automated rebuild when base image changes
```

Microsoft Defender for Containers' current gated-deployment capability can audit or deny Kubernetes deployments based on vulnerability findings and supports policy conditions/exemptions. ([Microsoft Learn][6])

That provides a separate control from signature verification.

---

## **What if there is no patch yet?**

Then I would evaluate compensating controls.

For example:

```text
No fixed package
     ↓
Can vulnerable feature be disabled?
     ↓
Can ingress be restricted?
     ↓
Can WAF/network rules reduce exposure?
     ↓
Can workload privilege be reduced?
     ↓
Can alternative dependency/base image be used?
```

If the risk remains unacceptable, I may have to remove the service or functionality temporarily.

An exception should be:

```text
documented
scope-limited
time-limited
owned
monitored
```

—not “ignore until someone remembers.”

---

## **Rollback consideration**

If the patched image causes severe regressions, I don't automatically roll back to a known exploitable artifact.

The decision is:

```text
Operational impact of patch
          vs
Security risk of vulnerable version
```

Options could include:

* fix forward urgently,
* roll back behind additional containment,
* disable vulnerable functionality,
* temporarily restrict traffic.

---

### **Interview answer condensed**

> “I would first identify the exact vulnerable image digest and every workload currently running it, then assess exploitability, exposure and whether there's evidence of active exploitation. For an internet-facing actively exploitable issue I'd contain first—for example restrict traffic or remove the workload from service—and investigate whether identities or secrets may have been compromised. I would fix the dependency or base image in source, rebuild a new immutable image through trusted CI, rescan it, regenerate SBOM/provenance, sign it and deploy it progressively. I would never manually patch containers and consider the problem solved, because a restarted pod would return to the vulnerable image. Finally I'd verify the old digest is no longer running and strengthen CI/runtime vulnerability gates so the same condition doesn't recur.”

**Memory line:**
**Fix the artifact, replace the workload, and investigate compromise—not just the CVE.**

**Interview trap:**
A **Critical severity score alone doesn't prove active exploitability**, but a clean application log also doesn't prove the vulnerable workload wasn't compromised.

**Keywords:**
CVE, image digest, exploitability, containment, Defender for Containers, rebuild, rescan, immutable image, canary rollout, credential rotation, compensating controls.

**Likely follow-ups:**

* Would you immediately stop production for every Critical CVE?
* Why shouldn't you patch a running container manually?
* What would you do if no fixed package version exists?
* How would you determine which AKS workloads run the affected digest?
* What changes if you suspect the vulnerability was already exploited?

# **T25-H04. How would you secure third-party GitHub Actions or Azure Pipeline tasks?**

**Answer:**

I treat third-party CI/CD actions and tasks as **third-party code executing inside my trusted pipeline**, often with access to source code, tokens, filesystem data and sometimes cloud credentials.

For GitHub Actions, I would first minimize the number of external actions, use trusted publishers, review the source and release history, and pin external actions to a **full immutable commit SHA**, not just `@main` or a mutable tag. GitHub's current security guidance says pinning to a full-length commit SHA is the only way to consume an action as an immutable release, and GitHub can enforce SHA pinning at repository or organization level. ([GitHub Docs][9])

Then I would minimize `GITHUB_TOKEN` permissions, keep production secrets out of untrusted PR jobs, use OIDC instead of stored Azure credentials, protect workflow files with review requirements, and tightly control self-hosted runners.

For Azure Pipelines, I would prefer built-in or thoroughly vetted Marketplace tasks, review the publisher and extension scopes, limit who can install or update extensions, avoid unnecessary high-privilege extensions or pipeline decorators, and reference explicit task versions. Microsoft specifically warns that high-privilege Azure DevOps extensions can read/write sensitive organization resources and recommends trusting the publisher and reviewing requested scopes. ([Microsoft Learn][10])

---

# **First principle: the task is code execution**

When a workflow contains:

```yaml
- uses: random-org/some-action@v3
```

that action isn't just metadata.

It may execute:

```text
JavaScript
Docker container
shell commands
```

on my runner.

So conceptually:

```text
Third-party action
      ↓
Code executes on CI runner
      ↓
Potential access to:
├── repository
├── GITHUB_TOKEN
├── environment variables
├── workspace
├── network
└── cloud credentials available to job
```

That means selecting an action is a **software-supply-chain decision**.

---

# **1. Prefer the smallest dependency set**

Every external action adds:

```text
another repository
another publisher
another release process
another dependency chain
```

So I would avoid:

```text
20 community actions
```

where:

```text
5 shell commands
```

could accomplish the same thing clearly.

But I wouldn't blindly rewrite mature, trusted actions either.

The objective is to reduce unnecessary trust dependencies.

---

# **2. Pin GitHub Actions to a full commit SHA**

Avoid:

```yaml
uses: vendor/action@main
```

because `main` changes.

Also weaker:

```yaml
uses: vendor/action@v3
```

because tags can potentially be moved or compromised at the source.

Strongest immutable reference:

```yaml
uses: vendor/action@0123456789abcdef...
```

GitHub explicitly recommends full-length commit-SHA pinning and states this is currently the only way to consume an action as an immutable release. ([GitHub Docs][9])

For maintainability I can comment the human-readable version:

```yaml
uses: actions/checkout@<FULL_SHA> # v4.x
```

Then use dependency tooling/processes to intentionally update the SHA after review.

---

# **3. Verify where that SHA came from**

Pinning to an arbitrary SHA isn't enough.

I need to verify:

```text
SHA belongs to official upstream repository
          ↓
corresponds to expected reviewed release
```

GitHub's guidance specifically says to verify that the pinned SHA comes from the action's repository rather than a fork. ([GitHub Docs][9])

---

# **4. Allowlist approved GitHub Actions**

At organization/enterprise level, I can restrict which actions and reusable workflows are permitted.

For example:

```text
Allowed
├── GitHub-maintained actions
├── organization-owned actions
└── explicitly approved vendors

Denied
└── arbitrary Marketplace action
```

GitHub organization policy supports restricting actions and requiring full-length SHA pinning. ([GitHub Docs][11])

This prevents every developer from silently introducing a new supply-chain dependency.

---

# **5. Give `GITHUB_TOKEN` minimum permissions**

A third-party action can only abuse permissions that are available to its job.

Instead of broad:

```yaml
permissions: write-all
```

prefer something like:

```yaml
permissions:
  contents: read
```

and grant additional capabilities only where required.

Think:

```text
Third-party action compromised
          ↓
What can its current job token do?
```

Least privilege limits blast radius.

---

# **6. Separate build jobs from deployment jobs**

Don't create:

```text
PR job
  ↓
third-party scanners
  ↓
Azure production credentials
```

Instead:

```text
PR validation
├── untrusted input
├── minimal token
└── no prod Azure access

Trusted deployment
├── protected source
├── restricted external dependencies
└── OIDC to Azure
```

This is one of the strongest architectural controls.

---

# **7. Use OIDC rather than an Azure client secret**

Even if an action leaks the environment:

```text
No reusable AZURE_CLIENT_SECRET
```

is much better than:

```text
AZURE_CLIENT_SECRET valid for 12 months
```

With GitHub OIDC:

```text
Trusted workflow
      ↓
OIDC
      ↓
Entra federation
      ↓
Short-lived token
```

Then keep the corresponding Azure RBAC narrow.

Again:

```text
short-lived
+
least privilege
```

not just short-lived.

---

# **8. Protect workflow changes**

Attackers don't necessarily need to compromise an external action.

They might change:

```text
.github/workflows/deploy.yml
```

from:

```yaml
permissions:
  contents: read
```

to something more dangerous.

So workflow files should receive strong review.

Example:

```text
.github/workflows/*
       ↓
CODEOWNER / required reviewer
       ↓
protected main
```

A pipeline is production infrastructure and should be reviewed accordingly.

---

# **9. Be especially careful with self-hosted runners**

A compromised third-party action on a persistent self-hosted runner may potentially leave artifacts behind for later jobs.

Conceptually:

```text
Malicious action
     ↓
persistent runner
     ↓
modify filesystem
steal cached credentials
install persistence
     ↓
future trusted deployment job
```

For high-trust workloads I prefer strong isolation and, where practical, ephemeral runners/agents that are discarded after the job.

Also separate pools:

```text
Untrusted PR runner pool
          ≠
Production deployment runner pool
```

---

# **Azure Pipelines: third-party tasks and Marketplace extensions**

Azure DevOps uses a somewhat different model.

A YAML task might look like:

```yaml
- task: SomeVendorTask@3
```

Third-party tasks can come from Marketplace extensions installed into the Azure DevOps organization.

So I care about two things:

```text
Task code
+
Extension privileges
```

---

## **10. Vet Azure DevOps publishers and scopes**

Before installing an extension I would review:

```text
Publisher
Maintenance activity
Requested scopes
Security history
Business necessity
```

Microsoft warns that high-privilege extensions may have permissions capable of reading/updating/deleting source, identities, groups, projects and other sensitive resources. It specifically recommends using such extensions only when the publisher/code is trusted and the requested scopes are justified. ([Microsoft Learn][10])

---

## **11. Restrict who can install extensions**

Don't let every developer add organization-wide pipeline functionality.

```text
Extension install/update
       ↓
small authorized admin group
```

Azure DevOps exposes extension security permissions so installation/management can be limited to authorized users. ([Microsoft Learn][12])

---

## **12. Be careful with pipeline decorators**

This is an especially good Azure DevOps interview detail.

A pipeline decorator can effectively modify many or all pipelines in the organization.

That gives it a very wide blast radius.

Microsoft classifies pipeline decorators alongside high-privilege extension concerns and recommends using them cautiously. ([Microsoft Learn][10])

So:

```text
Third-party task used by 1 pipeline
```

is one risk level.

```text
Extension injecting behavior into every pipeline
```

is much higher.

---

# **13. Pin Azure Pipeline task versions deliberately**

Azure Pipelines requires a task version such as:

```yaml
- task: PublishTestResults@2
```

Microsoft notes that when only the major version is specified, minor task versions are automatically updated; full task versions can also be specified where needed. ([Microsoft Learn][13])

So for highly sensitive pipelines I would understand the update model and deliberately control version upgrades instead of assuming:

```text
@2
```

is necessarily immutable forever.

That's an important difference from GitHub's full-SHA model.

---

# **14. Never expose secrets unnecessarily to third-party tasks**

Suppose a security scanner needs only:

```text
repository files
```

It doesn't need:

```text
Azure production credentials
Key Vault secrets
Kubernetes admin config
```

So I would structure jobs such that privileged values exist only in the minimum required step/job.

```text
Build/scan job
      ↓
No prod access

Deployment job
      ↓
OIDC + restricted identity
```

---

# **15. Have an incident response plan for compromised dependencies**

If a widely used action is compromised:

```text
Identify workflows using it
        ↓
Disable/deny dependency
        ↓
Determine affected versions/SHAs
        ↓
Inspect CI logs
        ↓
Assess token/secret exposure
        ↓
Rotate compromised credentials
        ↓
Replace/pin trusted version
        ↓
Review Azure activity
```

If we used:

```text
action@main
```

determining exactly what code ran may be difficult.

If we used:

```text
action@<SHA>
```

we know precisely which source version was executed.

That's another operational value of immutable pinning.

---

## **Security hierarchy I would apply**

```text
1. Avoid unnecessary third-party code
           ↓
2. Trust/vet publisher
           ↓
3. Pin immutable version where possible
           ↓
4. Allowlist approved dependencies
           ↓
5. Limit pipeline token permissions
           ↓
6. Separate untrusted and trusted jobs
           ↓
7. Use short-lived cloud identity
           ↓
8. Isolate runners
           ↓
9. Monitor and update intentionally
```

### **Interview answer condensed**

> “I treat third-party actions and pipeline tasks as code executing inside my trusted build environment. For GitHub Actions I'd minimize external dependencies, vet the publisher and source, and pin actions to a full commit SHA rather than `main` or a mutable tag. I'd enforce an organization allowlist where appropriate, minimize `GITHUB_TOKEN` permissions, keep production credentials out of PR jobs, use OIDC for Azure, protect workflow changes, and isolate self-hosted runners. For Azure Pipelines I'd prefer built-in or vetted Marketplace tasks, review the extension publisher and requested scopes, tightly restrict who can install extensions, be especially cautious with high-privilege extensions and pipeline decorators, and deliberately control task versions. The main goal is that compromising one third-party task should not automatically give an attacker control of our repository, Azure subscription, or production environment.”

**Memory line:**
**A third-party pipeline task is third-party code running inside one of your most privileged systems.**

**Interview trap:**
Using `action@v3` is convenient, but in GitHub it is **not equivalent to immutable full-SHA pinning**.

Full commit SHA, GitHub Actions, allowlist, `GITHUB_TOKEN`, OIDC, least privilege, self-hosted runner, Azure Pipeline task, Marketplace extension, high-privilege scope, pipeline decorator.
