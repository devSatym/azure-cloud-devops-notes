### **T25-E04. What is DAST?**

**Answer:**

DAST stands for **Dynamic Application Security Testing**. It tests a **running application from the outside** by sending real requests and observing how the application behaves.

Unlike SAST, which analyzes source code without executing it, DAST interacts with the deployed application and tries to identify runtime vulnerabilities such as injection flaws, authentication problems, insecure headers, exposed endpoints, and other web application weaknesses.

```text
Running Application
       ↑
       │ HTTP/HTTPS requests
       │
DAST Scanner
       │
       ↓
Responses / behavior
       ↓
Security findings
```

### **How it fits into DevSecOps**

A typical pipeline might look like:

```text
Code
 ↓
SAST
 ↓
Build
 ↓
Deploy to test environment
 ↓
DAST
 ↓
Security gate
 ↓
Production
```

DAST normally needs a deployed and reachable environment, so it usually runs **later than SAST**.

### **SAST vs DAST**

```text
SAST
→ analyzes code
→ application doesn't need to run
→ good for early feedback

DAST
→ attacks/tests a running application
→ application must be deployed
→ validates runtime behavior
```

For example, a DAST tool might send malicious input such as:

```text
' OR 1=1 --
```

to an application endpoint and observe whether the application behaves in an unsafe way.

### **Practical example**

Suppose you deploy an API to a staging environment on AKS:

```text
PR
 ↓
CI
 ↓
Container image
 ↓
AKS staging namespace
 ↓
DAST scanner
 ↓
API endpoints
```

The scanner might detect:

* missing security headers,
* insecure cookies,
* injection behavior,
* exposed debug endpoints,
* weak TLS configuration,
* authentication issues.

### **Limitations**

DAST usually does not know exactly which source-code line caused a vulnerability.

It sees:

```text
Input
 ↓
Application behavior
 ↓
Vulnerability
```

while SAST may give more direct code-level context.

Also, DAST cannot reliably detect every vulnerability, especially issues that require deep internal code understanding.

**Memory line:**
**DAST tests the running application from the outside, while SAST analyzes the code from the inside.**

**Interview trap:**
DAST is not a replacement for SAST; the two detect different classes of problems and are strongest when used together.

**Keywords:**
DAST, dynamic testing, running application, runtime behavior, HTTP requests, staging, security testing.

### **T25-E05. What is dependency scanning?**

**Answer:**

Dependency scanning identifies **known vulnerabilities in third-party libraries, packages, frameworks, and other software dependencies** used by an application.

Instead of primarily analyzing how my own code is written, it checks whether components such as npm packages, Python libraries, Java dependencies, OS packages, or container dependencies have known CVEs or security advisories.

```text
Application
   ↓
Dependency manifest / lock file
   ↓
Dependency scanner
   ↓
Package versions
   ↓
Known vulnerability database
   ↓
Security findings
```

For example:

```text
package.json
package-lock.json
requirements.txt
pom.xml
go.mod
```

can be analyzed to determine which versions are being used.

### **Why it matters**

Modern applications may contain far more third-party code than custom-written code.

So even if:

```text
Our source code = secure
```

we may still depend on:

```text
Library X v1.2
   ↓
Known critical CVE
```

and inherit that risk.

### **Typical CI/CD flow**

```text
Pull Request
      ↓
Dependency scan
      ↓
Known critical CVE?
   ┌──────┴──────┐
  Yes            No
   ↓              ↓
Block/fix       Continue
```

Teams can set policies such as:

```text
Critical severity → block merge
High severity     → require remediation
Medium/Low        → track based on policy
```

### **Practical example**

Suppose an AKS microservice uses:

```text
Node.js application
   ↓
npm dependencies
```

The scanner finds:

```text
library-a 2.1.0
→ CVE with remote code execution
```

The fix might be:

```text
upgrade dependency
 ↓
run tests
 ↓
rebuild image
 ↓
rescan
 ↓
deploy
```

### **Dependency scanning vs SAST**

```text
SAST
→ analyzes security issues in application code

Dependency scanning
→ identifies known vulnerabilities in third-party components
```

Both belong in a mature DevSecOps pipeline.

### **Transitive dependencies**

An important point is that the vulnerable package may not have been added directly.

For example:

```text
Your application
      ↓
Package A
      ↓
Package B
      ↓
Package C ← vulnerable
```

Package C is a **transitive dependency**.

A good scanner should analyze the full dependency tree, not just direct packages.

**Memory line:**
**Dependency scanning asks whether the third-party software my application depends on contains known vulnerabilities.**

**Interview trap:**
A dependency vulnerability can exist even when your own code is perfectly written, including through transitive dependencies.

**Keywords:**
Dependency scanning, CVE, third-party libraries, transitive dependency, package version, vulnerability database, supply chain.

### **T25-E06. What is container-image scanning?**

**Answer:**

Container-image scanning analyzes a container image for **known vulnerabilities and insecure components** before or after the image is deployed.

It typically examines the operating-system packages and application dependencies inside image layers and compares their versions against vulnerability databases.

```text
Container Image
      ↓
Image Scanner
      ↓
Image layers
      ↓
OS packages + application packages
      ↓
Known CVEs
      ↓
Findings
```

For an Azure DevOps workflow, I would ideally scan the image **before promoting it to production**.

### **Typical flow**

```text
Source code
    ↓
Build container
    ↓
Image scan
    ↓
Critical vulnerabilities?
   ┌───────┴───────┐
  Yes              No
   ↓                ↓
Block/fix        Push/promote
                     ↓
                    ACR
                     ↓
                    AKS
```

### **What can be found**

For example, the image may contain:

```text
Ubuntu base layer
├── openssl vulnerable version
├── curl vulnerable version
└── libc vulnerable version

Application
├── npm package vulnerability
└── Python package vulnerability
```

The scanner can identify those packages and their associated CVEs.

### **Why base images matter**

Suppose the Dockerfile uses:

```dockerfile
FROM ubuntu:old-version
```

Even if application code hasn't changed, new CVEs may later be discovered in packages inside that base image.

So:

```text
Image was clean yesterday
        ≠
Image is guaranteed clean forever
```

Images should be rescanned periodically as vulnerability intelligence changes.

### **Practical ACR/AKS workflow**

Conceptually:

```text
GitHub Actions / Azure Pipeline
          ↓
docker build
          ↓
vulnerability scan
          ↓
push trusted image to ACR
          ↓
deploy approved image to AKS
```

In a stronger supply-chain model:

```text
Build
 ↓
Scan
 ↓
Sign
 ↓
Push
 ↓
Admission policy verifies trusted artifact
 ↓
AKS
```

### **Image scanning is not runtime security**

Scanning tells you about known vulnerabilities in image contents.

It does not automatically tell you whether a running container:

* starts a reverse shell,
* performs privilege escalation,
* accesses unexpected files,
* makes suspicious network connections.

Those are runtime-security concerns.

**Memory line:**
**Container-image scanning checks what is packaged inside the image for known vulnerabilities before it is trusted for deployment.**

**Interview trap:**
A clean image scan does not mean the running container is secure, and images can become vulnerable later as new CVEs are discovered.

**Keywords:**
Container image, CVE, image layers, base image, OS packages, application dependencies, ACR, AKS, vulnerability scanning.

### **T25-E07. What is secret scanning?**

**Answer:**

Secret scanning detects sensitive credentials that have been accidentally committed or exposed in source code or repositories.

Examples include:

* API keys,
* client secrets,
* passwords,
* private keys,
* access tokens,
* cloud credentials.

The goal is to stop secrets from entering source control because Git history is persistent and repositories are frequently copied, cloned, cached, and integrated with other systems.

```text
Developer code
     ↓
Secret scanner
     ↓
Credential pattern detected?
   ┌───────┴───────┐
  Yes              No
   ↓                ↓
Block/fix        Continue
```

### **Where secret scanning should run**

Ideally at multiple points:

```text
Developer machine
      ↓
pre-commit / IDE scan
      ↓
Pull Request
      ↓
CI scan
      ↓
Repository monitoring
```

The earlier the secret is caught, the smaller the potential exposure.

### **Practical Azure example**

Suppose a developer accidentally commits:

```text
AZURE_CLIENT_SECRET=...
```

or:

```text
Storage Account key
```

A secret scanner detects it.

The correct response is **not only to delete the line from Git**.

If a credential has been exposed, I assume compromise is possible.

I would:

```text
Secret discovered
      ↓
Revoke / rotate credential
      ↓
Remove credential from source
      ↓
Replace with secure identity mechanism
      ↓
Review logs / exposure
```

For Azure workloads, I would often redesign the authentication method using:

```text
Managed Identity
or
Workload Identity Federation / OIDC
```

rather than simply generating another long-lived secret.

### **Why deleting the commit is not enough**

Once a credential has been committed:

```text
Git commit
   ↓
remote repository
   ↓
developer clones
   ↓
CI logs/caches
   ↓
forks/backups
```

you cannot confidently assume that removing the visible file means nobody still has the secret.

That's why credential rotation is critical.

### **Secret scanning vs Key Vault**

These solve different problems.

```text
Secret scanning
→ detects accidentally exposed credentials

Azure Key Vault
→ securely stores and manages secrets/keys/certificates
```

A scanner does not replace a secret-management solution.

### **Better design**

Instead of:

```text
GitHub Actions
     ↓
Azure client secret stored for 12 months
```

prefer, where supported:

```text
GitHub Actions
      ↓
OIDC token
      ↓
Microsoft Entra ID
      ↓
short-lived Azure access token
```

That reduces the number of long-lived secrets that could ever be leaked.

**Memory line:**
**Secret scanning detects leaked credentials, but once a real secret is exposed, rotate it rather than merely deleting it from Git.**

**Interview trap:**
Removing a secret from the latest Git commit does **not** make the credential safe again; revoke or rotate it.

**Keywords:**
Secret scanning, credentials, API key, client secret, token, Git history, rotation, Key Vault, Managed Identity, OIDC.
