# **T25-H05. How would you prevent CI/CD compromise from becoming an Azure subscription compromise?**

**Answer:**

I would assume that a CI/CD system can eventually be compromised and design the Azure permissions so that compromising one workflow, runner, or third-party task gives the attacker only a **small, predefined blast radius**.

My main controls would be: no long-lived Azure secrets, workload identity federation with tightly constrained GitHub OIDC claims, a separate Azure identity for each environment and function, least-privilege RBAC at the smallest scope, and no normal deployment pipeline having `Owner`, `User Access Administrator`, or permission to create role assignments.

I would also separate ordinary application deployment from privileged infrastructure/bootstrap operations, protect production with repository and environment approvals, use Azure Policy as a guardrail, harden runners, and monitor Azure Activity Logs and identity activity for privilege changes or unusual pipeline actions.

The mental model is:

```text
Compromised CI
     ↓
What credentials can it obtain?
     ↓
What Azure identity does that represent?
     ↓
What RBAC role?
     ↓
At what scope?
     ↓
What can that identity actually change?
```

I want the answer at the bottom to be:

```text
One application / one environment
```

not:

```text
Entire Azure subscription
```

---

## **Architecture I would aim for**

```text
GitHub Repository
      ↓
Protected main
      ↓
Production Environment approval
      ↓
GitHub Actions
      ↓
OIDC
      ↓
Microsoft Entra ID
      ↓
Federated workload identity
      ↓
Short-lived Azure token
      ↓
Narrow Azure RBAC
      ↓
Specific production resource
      ↓
Azure Policy / platform guardrails
```

Then separately:

```text
CI deploy identity
      ≠
Subscription administrator identity
```

That separation is one of the most important controls.

# **1. Start by assuming CI is a high-value attack target**

CI/CD frequently has access to:

* source code,
* artifacts,
* registry credentials,
* infrastructure tools,
* deployment environments,
* cloud APIs.

An attacker may compromise CI through:

```text
Malicious PR
Third-party action
Compromised dependency
Stolen CI token
Compromised runner
Workflow-file modification
CI platform account compromise
```

Therefore my security objective isn't merely:

> “Prevent CI from ever getting compromised.”

It's also:

> “If CI is compromised, prevent lateral movement into broad Azure administration.”

That is **blast-radius engineering**.

---

# **2. Eliminate long-lived Azure credentials**

I would avoid storing:

```text
AZURE_CLIENT_SECRET
subscription-wide service-principal password
certificate private key
storage account key
```

inside CI wherever federation is supported.

For GitHub Actions:

```text
GitHub job
   ↓
OIDC token
   ↓
Microsoft Entra ID
   ↓
Federated identity credential
   ↓
Short-lived Azure access token
```

GitHub's Azure OIDC guidance specifically recommends federation so workflows can access Azure without storing long-lived Azure credentials. It also recommends constraining token issuance so untrusted repositories or refs cannot obtain cloud access. ([GitHub Docs][1])

The advantage is important.

### Long-lived secret stolen

```text
Attacker steals secret
        ↓
uses it tomorrow
        ↓
uses it next week
        ↓
continues until revoked/expired
```

### Temporary token stolen

```text
Attacker steals token
        ↓
limited lifetime
        ↓
expires
```

That doesn't eliminate risk, but it reduces persistence.

---

# **3. Constrain the federation itself**

A common mistake is:

```text
We use OIDC
→ therefore secure
```

Not enough.

The federated identity must trust only the intended workload.

For example:

```text
GitHub organization
      +
specific repository
      +
specific production environment/ref
             ↓
allowed to request Azure token
```

Not:

```text
Any repository in organization
          ↓
production Azure identity
```

GitHub's current Azure guidance recommends conditions on OIDC trust and specifically recommends GitHub environment protection when environments are used. ([GitHub Docs][1])

So production might conceptually be:

```text
repo:company/payment-api
environment:production
        ↓
production Entra workload identity
```

while another repository cannot use that trust.

---

# **4. Never give the normal deployment identity subscription Owner**

This is probably the biggest Azure-specific point.

Suppose CI has:

```text
Owner
Scope: Subscription
```

If compromised:

```text
CI compromise
     ↓
Owner
     ↓
Create role assignments
Modify infrastructure
Delete resources
Potential privilege persistence
     ↓
Subscription compromise
```

Instead, Azure recommends assigning roles at the smallest scope needed. Azure RBAC can be scoped at management group, subscription, resource group, or individual resource level, and Microsoft explicitly recommends using the smallest required scope. ([Microsoft Learn][2])

So for an application deployment:

```text
payment-prod pipeline identity
        ↓
required deployment role
        ↓
payment-prod resource group
```

or even narrower:

```text
specific ACR
specific AKS cluster/namespace
```

when possible.

---

# **5. Contributor is safer than Owner—but still often too broad**

Important interview nuance:

`Contributor` doesn't normally allow creating Azure RBAC role assignments.

That's valuable because an attacker can't simply say:

```text
az role assignment create ...
```

and make themselves Owner using normal Contributor privileges.

But:

```text
Contributor at subscription
```

still allows enormous infrastructure control.

An attacker could potentially:

* delete applications,
* modify VMs,
* change many network resources,
* change application configuration,
* alter workloads.

So this:

```text
Not Owner
```

does **not automatically equal**:

```text
Least privilege
```

I would still reduce scope and role permissions.

---

# **6. Keep `Microsoft.Authorization/roleAssignments/write` out of ordinary pipelines**

This deserves special attention.

If an application pipeline can create role assignments:

```text
Compromised pipeline
        ↓
Create powerful role assignment
        ↓
Escalate privileges
        ↓
Persist access
```

So I'd separate:

```text
Normal application deployment
```

from:

```text
Privileged identity/bootstrap changes
```

For example:

```text
Application pipeline
├── update deployment
├── update app resources
└── NO RBAC administration

Privileged infrastructure pipeline
├── tightly controlled
├── additional approval
├── rare execution
└── permitted to manage selected RBAC
```

This is especially important with Terraform.

A convenient but dangerous pattern is:

```text
Terraform pipeline
→ Owner at subscription
because Terraform might create everything
```

For production I'd try to decompose that responsibility.

---

# **7. Separate identities by environment**

Don't use:

```text
github-cicd
   ↓
Dev
Stage
Prod
```

with one giant identity.

Use:

```text
github-payment-dev
       ↓
Dev only

github-payment-stage
       ↓
Stage only

github-payment-prod
       ↓
Prod only
```

Now compromising the development workflow doesn't automatically compromise production.

You can also apply stricter GitHub environment protection to production:

```text
main
 ↓
production deployment job
 ↓
required environment approval
 ↓
OIDC token
 ↓
production Azure identity
```

---

# **8. Separate CI identities by function too**

Even within one environment I may split responsibilities.

For example:

```text
Build identity
     ↓
ACR write only

Deployment identity
     ↓
AKS namespace deployment only

Infrastructure identity
     ↓
specific infrastructure scope
```

Then:

```text
Compromise image-building job
```

doesn't automatically give:

```text
AKS cluster administration
```

This is much stronger than one “DevOps service principal” that can do everything.

---

# **9. Protect the workflow that can request the identity**

If an attacker can modify:

```text
.github/workflows/prod.yml
```

they might make the trusted job execute arbitrary Azure commands.

So source-control controls become part of Azure security:

```text
Workflow changes
      ↓
Pull request
      ↓
CODEOWNER/security/platform review
      ↓
Required CI
      ↓
Protected main
```

The identity may be perfectly configured, but if anyone can rewrite the workflow authorized to use it, that trust boundary is weak.

---

# **10. Keep PR pipelines away from production Azure access**

A pull request contains code that hasn't been trusted yet.

I would want:

```text
PR workflow
├── build
├── test
├── SAST
├── IaC scan
└── no production deployment token
```

Then:

```text
protected main
      ↓
trusted deployment workflow
      ↓
production OIDC identity
```

Never assume code running inside PR tests is harmless.

Tests and build scripts are executable code.

---

# **11. Harden runners**

A compromised runner can steal whatever credentials are available to its current job and potentially tamper with subsequent jobs if it persists.

For production, I prefer:

```text
Ephemeral runner
      ↓
one job
      ↓
destroy runner
```

over:

```text
Permanent shared VM
      ↓
PR jobs
      ↓
Production deployment jobs
```

If self-hosted runners are needed because production resources are private, I would separate runner pools:

```text
PR / untrusted runners
        ≠
Production deployment runners
```

and apply strong network restrictions.

---

# **12. Use Azure Policy as a second boundary**

Even if CI has legitimate infrastructure permissions, Azure Policy can prevent certain dangerous configurations.

Example:

```text
Compromised CI identity
      ↓
tries to create public IP
      ↓
RBAC says identity may deploy resources
      ↓
Azure Policy evaluates request
      ↓
Deny
```

Potential guardrails include:

```text
approved regions only
no public exposure for selected resources
required security configuration
required diagnostic settings
```

This demonstrates:

```text
Identity permissions
        +
Resource governance
```

rather than depending entirely on CI trust.

---

# **13. Separate subscriptions where the risk justifies it**

For stronger environment isolation:

```text
Management Group
│
├── Dev Subscription
├── Stage Subscription
└── Prod Subscription
```

Now a compromised Dev identity scoped only to the Dev subscription doesn't automatically inherit access to production.

Subscriptions are useful as:

* RBAC boundaries,
* policy boundaries,
* billing boundaries,
* quota boundaries,
* blast-radius boundaries.

I wouldn't create subscriptions solely because “more subscriptions = more secure,” but environment separation can materially limit impact.

---

# **14. Prevent pipelines from modifying their own security boundary**

I don't want the deployment pipeline able to change:

```text
its own federated identity
its own RBAC assignments
management-group policy
production security controls
```

Otherwise:

```text
Compromised pipeline
       ↓
modify its own permissions
       ↓
become privileged
```

The security plane should generally be administered by a separate, more privileged workflow or administrator path.

---

# **15. Monitor privilege-changing operations**

I would alert aggressively on actions such as:

```text
Role assignment created
Role assignment deleted
Policy assignment changed
Federated credential modified
Critical production networking changed
Key Vault access model changed
```

During an incident I would correlate:

```text
GitHub workflow execution
        ↓
Entra workload identity
        ↓
Azure Activity Log
        ↓
resource modifications
```

The goal is to answer:

> Exactly what did the compromised workload identity do?

---

# **16. Incident response if CI is actually compromised**

I would respond in dependency order.

```text
CI compromise confirmed
       ↓
Stop compromised workflows/runners
       ↓
Block Azure token issuance
       ↓
Remove/disable federated credential
       ↓
Remove suspicious Azure role assignments
       ↓
Rotate any reusable credentials exposed
       ↓
Inspect Azure Activity Log
       ↓
Inspect Entra workload/service-principal activity
       ↓
Check changed resources
       ↓
Restore known-good configuration
       ↓
Re-establish CI trust
```

The first goal is:

```text
Stop attacker obtaining new Azure tokens
```

Then:

```text
determine what they already changed
```

If we only fix the GitHub workflow but leave a malicious Azure role assignment created by the attacker, persistence remains.

## **Defense-in-depth model**

```text
Repository protection
        ↓
Trusted workflow
        ↓
OIDC federation constraints
        ↓
Short-lived credentials
        ↓
Separate identities
        ↓
Least-privilege Azure RBAC
        ↓
Small resource scope
        ↓
Azure Policy
        ↓

```

The security value comes from the combination.

### **Interview answer condensed**

> “I would assume CI/CD could eventually be compromised and design Azure so that the pipeline identity has a limited blast radius. I'd use GitHub OIDC workload identity federation instead of long-lived client secrets and restrict the federation to the specific repository and production environment. I'd use separate identities for dev, staging, production, and ideally for build versus deployment. The normal pipeline would never have subscription Owner or User Access Administrator, and I would avoid giving it role-assignment permissions. Azure RBAC would be assigned at the smallest practical scope, such as the application resource group, ACR, or AKS namespace. I'd protect workflow files and production environments, isolate runners, use Azure Policy as an independent guardrail, and alert on RBAC and security-control changes. If CI were compromised, I'd immediately stop token issuance and then audit Azure for persistence such as malicious role assignments or resource changes.”

**Memory line:**
**Assume the pipeline can be compromised; design its Azure identity so the attacker still cannot become the subscription administrator.**

**Interview trap:**
Using **OIDC instead of secrets does not prevent subscription compromise** if the federated identity still has `Owner` at subscription scope.

# **T25-H06. How would you implement least privilege from GitHub Actions through ACR to AKS?**

**Answer:**

I would treat the GitHub-to-ACR-to-AKS path as **three separate identity and authorization boundaries**, rather than giving one service principal Contributor across everything.

First, GitHub Actions would authenticate to Azure using OIDC workload identity federation, restricted to the expected repository and environment. The build identity would receive only permission to push the required image repository in ACR. For modern ABAC-enabled ACR, I would prefer `Container Registry Repository Writer` with a repository-specific ABAC condition; for a legacy RBAC-only registry, `AcrPush` is the typical role.

Second, the AKS **kubelet managed identity**, not the GitHub identity, would receive only pull permission to the image repository—`Container Registry Repository Reader` on ABAC-enabled ACR or `AcrPull` on a legacy registry.

Third, if GitHub deploys directly to AKS, I would give its deployment identity only Kubernetes API permissions needed for the target namespace, not cluster-admin or Azure Contributor. For example, Azure RBAC for Kubernetes supports namespace-scoped `Azure Kubernetes Service RBAC Writer`, although for very strict privilege boundaries I'd consider a narrower custom Kubernetes RBAC role because the built-in Writer can read Secrets and run Pods as service accounts. ([Microsoft Learn][3])

```text
GitHub Actions
      │
      │ OIDC
      ▼
Microsoft Entra ID
      │
      ├──── Build Identity
      │         ↓
      │     ACR repository WRITE only
      │
      └──── Deploy Identity
                ↓
          AKS namespace WRITE only


AKS Kubelet Identity
       ↓
ACR repository READ only
```

That separation is the core of least privilege.

---

# **1. Separate authentication from authorization**

First:

```text
GitHub OIDC
     ↓
Authentication
```

answers:

> Which workflow is requesting access?

Then:

```text
Azure RBAC
     ↓
Authorization
```

answers:

> What Azure operation may that workflow perform?

GitHub's current Azure OIDC model allows a workflow to exchange its GitHub-issued OIDC token for an Azure access token without storing long-lived Azure credentials. ([GitHub Docs][1])

I would constrain that federation to:

```text
Repository
+
production environment/ref
```

not broadly trust arbitrary GitHub jobs.

---

# **2. Do not use one identity for build and deployment**

A weaker architecture:

```text
GitHub identity
       ↓
Contributor
       ↓
ACR + AKS + Resource Group
```

If compromised:

```text
Can push malicious image
+
Can deploy malicious image
+
Can modify unrelated resources
```

A better model:

```text
Build identity
     ↓
ACR only


Deploy identity
     ↓
AKS only
```

This creates separation of duties.

---

# **3. Give the build job only ACR write access**

Suppose GitHub builds:

```text
payment-service
```

The build job needs to:

```text
push payment-service image
```

It generally does **not** need:

```text
AKS cluster admin
Storage Contributor
Subscription Contributor
Key Vault Administrator
```

---

## **Current ACR RBAC-only model**

For a traditional RBAC-only ACR:

```text
GitHub build identity
        ↓
AcrPush
        ↓
ACR
```

`AcrPush` allows pushing and pulling artifacts. ([Microsoft Learn][4])

The role can be scoped to the ACR resource rather than the entire resource group/subscription.

---

# **4. For ABAC-enabled ACR, go repository-specific**

This is an important **current Azure detail**.

ACR now supports:

```text
RBAC Registry
+
ABAC Repository Permissions
```

For ABAC-enabled registries, Microsoft states that legacy:

```text
AcrPush
AcrPull
AcrDelete
```

are not honored. Instead, roles include:

```text
Container Registry Repository Reader
Container Registry Repository Writer
Container Registry Repository Contributor
```

and ABAC conditions can restrict access to specific repositories. ([Microsoft Learn][5])

So I could design:

```text
GitHub payment build identity
        ↓
Container Registry Repository Writer
        ↓
condition:
repository = payment-service
```

It cannot write:

```text
order-service
auth-service
platform-controller
```

inside the same registry.

That's much closer to true least privilege.

---

# **5. Don't give GitHub pull permission just because AKS needs it**

This is a subtle identity-flow distinction.

After GitHub pushes:

```text
ACR
```

who pulls the image when a Pod starts?

Not GitHub.

The flow is:

```text
Kubernetes Deployment
       ↓
Scheduler selects node
       ↓
Kubelet
       ↓
AKS kubelet managed identity
       ↓
ACR
       ↓
Pull image
```

Therefore ACR pull authorization belongs to:

```text
AKS kubelet identity
```

not the GitHub deployment identity.

---

# **6. Give the AKS kubelet identity read-only registry permission**

For traditional RBAC-only ACR:

```text
AKS kubelet identity
      ↓
AcrPull
      ↓
ACR
```

Microsoft's AKS-ACR integration uses the kubelet managed identity for image pulls. ([Microsoft Learn][6])

So:

```text
GitHub → push

AKS kubelet → pull
```

are separate identities.

---

## **ABAC-enabled ACR changes this**

For ABAC-enabled registries, Microsoft states:

* `AcrPull` isn't honored;
* use `Container Registry Repository Reader`;
* `az aks --attach-acr` isn't supported for ABAC-enabled repository permissions;
* the role must be assigned manually to the kubelet identity. ([Microsoft Learn][6])

So the stronger model becomes:

```text
Kubelet Identity
      ↓
Container Registry Repository Reader
      ↓
condition:
repository = payment-service
```

Now the cluster doesn't automatically gain pull access to every image repository in the registry.

---

# **7. GitHub deployment access to AKS is a separate permission**

GitHub now needs to update Kubernetes resources.

That is:

```text
Kubernetes API data-plane authorization
```

not simply:

```text
Azure resource Contributor
```

Very important distinction.

Giving:

```text
Contributor on AKS resource
```

doesn't automatically mean:

```text
Kubernetes cluster-admin
```

and giving Kubernetes authorization doesn't require granting Contributor across the Azure subscription.

---

# **8. Scope direct deployment to one namespace**

Suppose GitHub deploys only:

```text
namespace: payment
```

Then:

```text
GitHub production deploy identity
          ↓
payment namespace only
```

is preferable to:

```text
cluster-admin
```

AKS currently allows the `Azure Kubernetes Service RBAC Reader` and `Azure Kubernetes Service RBAC Writer` roles to be assigned at namespace scope. ([Microsoft Learn][3])

Conceptually:

```bash
az role assignment create \
  --role "Azure Kubernetes Service RBAC Writer" \
  --assignee <deploy-identity> \
  --scope "$AKS_ID/namespaces/payment"
```

That means:

```text
payment namespace
       ✓

other namespaces
       ✗
```

---

# **9. But understand the RBAC Writer caveat**

This is a fantastic interview trap.

Microsoft documents that `Azure Kubernetes Service RBAC Writer` can access **Secrets** and can run Pods using service accounts in the namespace. That can allow the identity to gain the permissions of those service accounts. ([Microsoft Learn][3])

So:

```text
Namespace scoped
```

does not necessarily mean:

```text
Low privilege
```

If I need stricter control, I might design a custom Kubernetes RBAC role that allows only operations such as:

```text
Deployments
Services
ConfigMaps
```

but denies:

```text
Secrets
RoleBindings
arbitrary privileged resources
```

For example conceptually:

```text
GitHub deployer
      ↓
Role
      ├── patch Deployment
      ├── get Deployment
      ├── update Deployment
      └── NO Secrets
```

This is closer to actual least privilege.

---

# **10. Don't give the workflow AKS admin credentials**

Avoid normal automation based on:

```text
cluster-admin kubeconfig
```

or:

```text
AKS local administrator credential
```

stored in GitHub secrets.

Prefer:

```text
GitHub OIDC
      ↓
Microsoft Entra identity
      ↓
authorized Kubernetes access
```

That gives us identity, revocation, RBAC, and auditing without distributing powerful static kubeconfigs.

---

# **11. An even stronger design is GitOps**

If using Argo CD or Flux, GitHub Actions may not need Kubernetes API access at all.

```text
GitHub Actions
      ↓
Build image
      ↓
ACR
      ↓
Update Git manifest/digest
      ↓
Git repository
      ↓
Argo CD inside AKS
      ↓
Kubernetes API
```

Now GitHub's cloud permissions could be:

```text
ACR repository writer
```

while deployment permission lives inside the GitOps controller.

This removes:

```text
GitHub → direct AKS privileged access
```

from the architecture.

For many production platforms, that's an excellent security improvement.

---

# **12. Deploy immutable image digests**

Even if RBAC is perfect, avoid:

```yaml
image: myacr.azurecr.io/payment:latest
```

Prefer:

```yaml
image: myacr.azurecr.io/payment@sha256:...
```

because the deployment then refers to exactly the artifact that was built and validated.

```text
GitHub builds digest ABC
      ↓
scan ABC
      ↓
sign ABC
      ↓
AKS deploys ABC
```

No tag mutation can silently swap the production artifact.

---

# **13. Put admission controls behind the identity controls**

Even if the GitHub deployer has legitimate namespace write permission, it shouldn't automatically be allowed to deploy arbitrary images.

```text
Authorized GitHub deploy identity
            ↓
Kubernetes API
            ↓
Admission policy
            ↓
trusted registry?
signed image?
security policy?
            ↓
Allow / Deny
```

This establishes two independent conditions:

```text
Is the caller authorized?
       +
Is the workload acceptable?
```

# **Full least-privilege flow**

```text
                     ┌────────────────────────┐
                     │ GitHub Actions Build   │
                     └───────────┬────────────┘
                                 │ OIDC
                                 ▼
                        Entra build identity
                                 │
                                 │ WRITE
                                 ▼
                 payment repository in ACR
                                 ▲
                                 │ READ
                                 │
                     AKS kubelet identity
                                 │
                                 ▼
                           AKS Node/Pod


                     GitHub Deploy Job
                           │ OIDC
                           ▼
                    Entra deploy identity
                           │
                           │ Kubernetes
                           │ namespace access
                           ▼
                     AKS payment namespace
```

Each arrow gets only the permission it actually requires.

## **Example permission matrix**

| Identity                 | Needs                           | Should NOT need                      |
| ------------------------ | ------------------------------- | ------------------------------------ |
| GitHub build identity    | Push payment image              | AKS admin                            |
| GitHub deploy identity   | Update payment workload         | ACR delete, subscription Contributor |
| AKS kubelet identity     | Pull payment image              | Push/delete images                   |
| Application Pod identity | Its application Azure resources | ACR administration or AKS admin      |

This is the mental model I'd explain to an interviewer.

# **Failure/troubleshooting reasoning**

Suppose the pipeline builds successfully but deployment gets:

```text
ImagePullBackOff
```

I'd reason:

```text
GitHub push succeeded
       ↓
So build identity → ACR WRITE probably works
       ↓
Pod cannot pull
       ↓
Different identity is involved
       ↓
Check AKS kubelet identity
       ↓
Check ACR Reader/AcrPull role
       ↓
Check registry permission mode
       ↓
Check network connectivity to ACR
```

This demonstrates why understanding identity separation matters.

For the kubelet identity:

```bash
az aks show \
  -g <rg> \
  -n <cluster> \
  --query identityProfile.kubeletidentity
```

Then:

```bash
az role assignment list \
  --assignee <kubelet-object-id> \
  --all
```

I'm checking whether the identity that **actually performs the pull** has the correct ACR data-plane role.

### **Interview answer condensed**

> “I would split GitHub-to-ACR-to-AKS into separate identities and scopes. GitHub authenticates through OIDC federation rather than a stored client secret. The build identity gets only ACR write access—preferably `Container Registry Repository Writer` restricted by ABAC to the specific repository on an ABAC-enabled registry. AKS doesn't use that identity to pull images; its kubelet managed identity gets read-only access, such as repository-scoped `Container Registry Repository Reader`. For deployment, I would use another GitHub identity with only Kubernetes permissions for the target namespace, not subscription Contributor or cluster-admin. Azure Kubernetes Service RBAC Writer can be namespace-scoped, but because it can access Secrets and run Pods as service accounts, I'd use narrower Kubernetes RBAC where the deployment workflow requires less. With GitOps I can go even further and remove direct GitHub-to-AKS access entirely.”

**Memory line:**
**Push, pull, and deploy are three different operations and should normally belong to three different permission boundaries.**

**Interview trap:**
The GitHub identity that pushes the image is **not the identity AKS uses to pull it**; AKS image pulls normally use the kubelet managed identity.

**Keywords:**
OIDC, build identity, deploy identity, kubelet identity, ACR, ABAC, Repository Writer, Repository Reader, AcrPush, AcrPull, namespace RBAC, GitOps, immutable digest.

**Likely follow-ups:**

* Which identity actually pulls images from ACR in AKS?
* What changes when ACR uses ABAC repository permissions?
* Why might `Azure Kubernetes Service RBAC Writer` still be too powerful?
* Could GitHub Actions deploy without any direct AKS access?
* How would you troubleshoot `ImagePullBackOff` after the CI push succeeded?

# **26. 🟡 GOOD — Azure CLI, PowerShell & Cloud Shell**

## **T26-E01. What is Azure CLI?**

**Answer:**

Azure CLI is Microsoft's **cross-platform command-line tool for managing Azure resources**. Its main executable is `az`, and I can use it interactively or in shell scripts to create, inspect, configure, and automate Azure resources.

For example:

```bash
az login
az account show
az group list
az vm list
az aks show -g my-rg -n my-aks
```

It is especially useful for operational tasks, troubleshooting, scripting, and CI/CD automation.

---

### **How it fits into Azure**

Conceptually:

```text
User / Script
     ↓
Azure CLI (`az`)
     ↓
Azure APIs / Resource Manager
     ↓
Azure Resources
```

For example:

```bash
az group create \
  --name rg-demo \
  --location centralindia
```

asks Azure to create or update the requested resource group.

Azure CLI covers a large number of Azure services through command groups:

```text
az group
az vm
az network
az storage
az aks
az acr
az monitor
az role
```

---

### **Useful output/query capability**

Azure CLI commonly returns JSON and lets me control output:

```bash
az vm list -o table
```

or query data:

```bash
az account show \
  --query "{name:name,id:id}" \
  -o table
```

This makes it useful in automation and troubleshooting.

---

### **Azure CLI vs Terraform**

Azure CLI is primarily an **imperative management tool**:

```text
Run this command
then this command
then this command
```

Terraform is declarative IaC:

```text
This is the desired infrastructure state.
```

So I might use:

```text
Terraform
→ provision production AKS/VNet/ACR

Azure CLI
→ inspect resources, troubleshoot, run operational actions
```

You *can* provision infrastructure with CLI scripts, but for large repeatable environments I'd generally prefer declarative IaC.

**Memory line:**
**Azure CLI is the cross-platform `az` command-line interface for operating and automating Azure.**

**Interview trap:**
Using Azure CLI scripts is **not automatically equivalent to declarative Infrastructure as Code or idempotent Terraform**.

**Keywords:**
Azure CLI, `az`, command line, automation, scripting, JSON, Azure Resource Manager.

---

## **T26-E02. What is Azure PowerShell?**

**Answer:**

Azure PowerShell is Microsoft's set of **PowerShell cmdlets for managing Azure**, primarily provided through the `Az` PowerShell module.

Instead of using Azure CLI commands such as:

```bash
az group list
```

I can use PowerShell cmdlets such as:

```powershell
Connect-AzAccount
Get-AzSubscription
Get-AzResourceGroup
Get-AzVM
Get-AzAksCluster
```

It is especially useful when an organization already uses PowerShell heavily, or when I want to combine Azure operations with PowerShell's object-oriented scripting and automation capabilities.

---

### **How it works**

Conceptually:

```text
PowerShell script
      ↓
Az PowerShell module
      ↓
Azure APIs
      ↓
Azure resources
```

Example:

```powershell
Connect-AzAccount

Get-AzResourceGroup
```

The major difference from many shell-based CLI workflows is that PowerShell passes **objects** through its pipeline.

For example:

```powershell
Get-AzVM |
Where-Object {$_.Location -eq "centralindia"}
```

PowerShell receives objects that can be filtered and manipulated directly.

---

### **Azure PowerShell vs Azure CLI**

Think of them as two administrative interfaces to Azure:

```text
Azure CLI
→ `az`
→ shell/CLI-oriented
→ JSON + JMESPath commonly used

Azure PowerShell
→ `Az` module
→ PowerShell cmdlets
→ PowerShell/.NET objects
```

Both can be used for:

* interactive administration,
* scripting,
* automation,
* troubleshooting,
* CI/CD tasks.

The choice is often based on the team's scripting ecosystem rather than one being universally better.

For example, a Bash-oriented Linux team may prefer:

```bash
az aks get-credentials ...
```

while a PowerShell-heavy operations team may prefer Az cmdlets and PowerShell objects.

**Memory line:**
**Azure PowerShell manages Azure through the `Az` module and integrates Azure operations with PowerShell's object-based scripting model.**

**Interview trap:**
Azure PowerShell isn't simply “Azure CLI written in PowerShell”; they are separate tooling interfaces with different command models, even though both manage Azure resources.

**Keywords:**
Azure PowerShell, `Az` module, cmdlets, `Connect-AzAccount`, PowerShell objects, automation.
