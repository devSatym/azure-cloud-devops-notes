# 3. 🔴 M IMP — Azure Virtual Networking

## Medium

### **T03-M07. What is an Application Security Group?**

**Answer:**
An Application Security Group, or **ASG**, lets me group Azure VM network interfaces logically and then use those groups as **sources or destinations in NSG rules**.

Instead of writing NSG rules using individual IP addresses, I can create logical groups such as:

```text
asg-web
asg-app
asg-db
```

and then write rules like:

```text
Source: asg-web
Destination: asg-app
Port: 8080
Action: Allow
```

This makes NSG rules easier to manage because security policy is based on **application role rather than IP address**.

### **Example**

Suppose I have multiple web and application VMs:

```text
Web VMs
├── web01
├── web02
└── web03

App VMs
├── app01
├── app02
└── app03
```

I can place their NICs into:

```text
web01, web02, web03
        ↓
      asg-web

app01, app02, app03
        ↓
      asg-app
```

Then one NSG rule can allow:

```text
asg-web → asg-app
TCP 8080
```

If I later add another application VM to `asg-app`, I do not need to rewrite the NSG rule.

### **Why use ASGs?**

They help with:

* simpler NSG management,
* reducing hard-coded IP rules,
* role-based network segmentation,
* scaling VM-based applications.

**Memory line:**
**ASG = logical grouping of VM NICs for simpler NSG rules.**

**Interview trap:**
An ASG does **not itself allow or deny traffic**.

The ASG only groups network interfaces.

The **NSG rule** still performs the actual traffic filtering.

**Keywords:** Application Security Group, ASG, NSG, NIC grouping, logical segmentation, security rules

### **T03-M08. What is a User Defined Route?**

**Answer:**
A User Defined Route, or **UDR**, is a custom route that I create to override or influence Azure's default system routing.

Azure automatically provides system routes, but when I need traffic to follow a specific path—such as through Azure Firewall or a network virtual appliance—I use a UDR inside an Azure route table.

A route typically contains:

```text
Destination prefix
+
Next-hop type
+
Next-hop address when required
```

### **Example**

Suppose my application subnet is:

```text
10.10.2.0/24
```

and all outbound internet traffic must pass through Azure Firewall.

I could configure:

```text
Destination: 0.0.0.0/0
Next hop: Virtual appliance
Next-hop IP: 10.10.0.4
```

The resulting traffic path becomes:

```text
Application VM
      ↓
UDR
      ↓
Azure Firewall
      ↓
Internet
```

### **Common use cases**

I use UDRs for:

* routing traffic through Azure Firewall,
* routing through third-party NVAs,
* hub-and-spoke architectures,
* forced tunneling,
* custom hybrid-network routing.

### **Route selection**

Azure generally chooses routes using the **most specific matching prefix**.

For example, if effective routes contain:

```text
10.20.0.0/16 → Firewall
10.20.1.0/24 → Different path
```

traffic to:

```text
10.20.1.10
```

matches `/24`, which is more specific than `/16`.

**Memory line:**
**UDR = custom instruction telling Azure where traffic should go.**

**Interview trap:**
A UDR controls **routing**, not security filtering.

```text
UDR → where traffic goes
NSG → whether traffic is allowed
Firewall → inspection/filtering and routing capabilities
```

**Keywords:** UDR, route table, next hop, virtual appliance, Azure Firewall, custom routing

**Likely follow-ups:**

### **T03-M09. What is the Azure system route table?**

**Answer:**
Azure automatically creates **system routes for every subnet** so that basic network connectivity works without me manually creating routes.

These routes determine paths for things such as:

* communication within the VNet,
* internet-bound traffic,
* and certain connected network scenarios.

I do not manually create these system routes; Azure maintains them.

### **Example**

Suppose I create:

```text
VNet: 10.0.0.0/16

Subnet-Web: 10.0.1.0/24
Subnet-App: 10.0.2.0/24
```

Azure automatically provides a route similar conceptually to:

```text
Destination: 10.0.0.0/16
Next hop: Virtual network
```

That is why the web subnet can route traffic to the application subnet without me creating a route table manually.

Azure also provides a default route conceptually like:

```text
0.0.0.0/0
→ Internet
```

although actual outbound connectivity still depends on the resource's outbound configuration and Azure networking design.

### **Can system routes be changed?**

I cannot directly edit Azure's system routes.

Instead, I can influence routing by adding:

* **User Defined Routes**
* BGP-learned routes
* VNet peering-related routes
* other Azure-generated routes.

For many destinations, a more specific route takes precedence.

### **Effective routes**

When troubleshooting, I do not look only at my route table.

I inspect the VM NIC's **effective routes**, because that view combines routes from sources such as:

```text
System routes
+
UDRs
+
BGP
+
VNet peering
```

That tells me the routing table Azure is actually using for that NIC.

**Memory line:**
**System routes = Azure's default routing; UDRs = my custom routing.**

**Interview trap:**
Do not assume:

> “If I didn't create a route table, there are no routes.”

Azure always has system routing in place.

**Keywords:** system routes, effective routes, virtual network route, UDR, BGP, routing

### **T03-M10. What is the purpose of `0.0.0.0/0`?**

**Answer:**
`0.0.0.0/0` represents **all IPv4 addresses**, so in routing it is commonly used as the **default route**.

It matches traffic when no more specific route exists.

For example:

```text
0.0.0.0/0
→ Internet
```

means:

> Send traffic for any destination not matched by a more specific route toward the internet path.

### **Azure Firewall example**

In a secured Azure environment, I might override the normal default route with:

```text
0.0.0.0/0
→ Virtual Appliance
→ Azure Firewall private IP
```

Then the flow becomes:

```text
Workload subnet
      ↓
0.0.0.0/0 UDR
      ↓
Azure Firewall
      ↓
Internet / external destination
```

This is commonly used for **centralized outbound traffic inspection**.

### **Why doesn't it override everything?**

Routing uses prefix specificity.

Suppose effective routes include:

```text
10.20.0.0/16 → VNet peering
0.0.0.0/0    → Azure Firewall
```

Traffic to:

```text
10.20.1.5
```

uses the `/16` route because it is more specific.

Traffic to something like:

```text
8.8.8.8
```

does not match a more specific internal route, so the `/0` default route is used.

### **Security context**

`0.0.0.0/0` can also appear in security configuration to mean **any IPv4 address**, but the meaning depends on context.

For example:

```text
Route:
0.0.0.0/0
→ default destination route
```

versus:

```text
NSG source:
0.0.0.0/0
→ any IPv4 source
```

The first controls routing; the second controls which addresses a security rule applies to.

**Memory line:**
**`0.0.0.0/0` = anywhere in IPv4; in routing, it usually means the default route.**

**Interview trap:**
Do not assume `0.0.0.0/0 → Firewall` means **literally every packet** will go through the firewall.

A more specific route can take precedence.

**Keywords:** `0.0.0.0/0`, default route, UDR, longest-prefix match, Azure Firewall, outbound traffic
