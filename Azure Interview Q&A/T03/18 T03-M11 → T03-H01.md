# 3. 🔴 M IMP — Azure Virtual Networking

## Medium

### **T03-M11. What is Azure NAT Gateway?**

**Answer:**
Azure NAT Gateway is a **managed outbound connectivity service** that provides scalable and predictable internet egress for resources in an Azure subnet.

When I associate a NAT Gateway with a subnet, workloads in that subnet can initiate outbound internet connections using the NAT Gateway’s public IP address or public IP prefix.

The key point is:

```text
Private workloads
      ↓
NAT Gateway
      ↓
Public IP / IP Prefix
      ↓
Internet
```

NAT Gateway performs **source network address translation, or SNAT**, so private source addresses are translated to the gateway’s public IP for outbound connections.

### **Why would I use it?**

I use NAT Gateway when I need:

* predictable outbound public IP addresses,
* high-scale SNAT,
* centralized subnet-level outbound internet access,
* workloads without individual public IPs,
* reduced risk of SNAT-port exhaustion.

Each NAT Gateway public IP provides a large SNAT-port pool, and additional public IPs or prefixes can increase scale. Microsoft currently recommends explicit outbound connectivity and positions NAT Gateway as the preferred option for high-scale outbound SNAT. ([Microsoft Learn][1])

### **Example**

Suppose AKS nodes or VMs are in:

```text
Subnet: 10.10.2.0/24
```

and external services must allowlist one predictable IP.

I can configure:

```text
Subnet
   ↓
NAT Gateway
   ↓
Public IP: 20.x.x.x
```

Now outbound connections from that subnet appear to external systems as originating from the NAT Gateway public IP.

### **Inbound behavior**

NAT Gateway is primarily for **outbound connections**.

It does not create unsolicited inbound internet connectivity to the VMs. Only response traffic for connections initiated from inside is allowed back through the NAT path. ([Microsoft Learn][2])

**Memory line:**
**NAT Gateway = scalable, predictable outbound internet access for a subnet.**

**Interview trap:**
NAT Gateway is **not an inbound load balancer** and not a firewall.

```text
NAT Gateway → outbound SNAT
Load Balancer → traffic distribution
Azure Firewall → traffic filtering/inspection + routing capabilities
```

**Keywords:** NAT Gateway, outbound connectivity, SNAT, public IP, predictable egress, subnet

**Likely follow-ups:**

* Why use NAT Gateway instead of public IPs on every VM?
* How does NAT Gateway help with SNAT-port exhaustion?
* Can NAT Gateway accept unsolicited inbound traffic?
* NAT Gateway vs Azure Firewall?

### **T03-M12. How does Azure assign outbound connectivity?**

**Answer:**
In current Azure designs, I should use an **explicit outbound connectivity method** rather than depend on implicit/default outbound access.

Common explicit options include:

* Azure NAT Gateway,
* a public IP directly associated with a resource,
* Standard Load Balancer outbound configuration,
* Azure Firewall or another NVA reached through routing.

A very important current Azure change is that **new virtual networks created with API versions after March 31, 2026 default to private subnets**, which means workloads require an explicit outbound method to reach public endpoints. Existing VNets are not automatically changed, but Microsoft recommends migrating away from legacy default outbound access. ([Microsoft Learn][3])

### **Preferred production approach**

For general outbound internet access from private VM subnets, I would commonly use:

```text
VM private IP
    ↓
Subnet
    ↓
NAT Gateway
    ↓
Known Public IP
    ↓
Internet
```

If I need security inspection:

```text
Workload subnet
      ↓
UDR 0.0.0.0/0
      ↓
Azure Firewall
      ↓
Internet
```

The second architecture lets me inspect and control egress traffic.

### **Legacy default outbound access**

Historically, Azure could assign an implicit Microsoft-owned outbound public IP to VMs that had no explicit outbound method.

That behavior was problematic because:

* the IP was not deterministic,
* it could change,
* it was implicit,
* and it was harder to control operationally.

Microsoft now recommends **explicit outbound configuration** instead. ([Microsoft Learn][3])

### **What I would choose**

For predictable general-purpose outbound SNAT:

> **NAT Gateway**

For centrally inspected and policy-controlled egress:

> **Azure Firewall/NVA with UDRs**

For a deliberately internet-facing individual resource:

> **Public IP**, only where justified.

**Memory line:**
**Modern Azure outbound = configure it explicitly; don't depend on default outbound access.**

**Interview trap:**
Older interview material may say:

> “Azure automatically gives VMs default internet outbound connectivity.”

That describes legacy behavior and is no longer the right design assumption for new VNets using post-March-2026 API versions. ([Microsoft Learn][3])

**Keywords:** explicit outbound, NAT Gateway, Azure Firewall, SNAT, private subnet, default outbound access

**Likely follow-ups:**

* What changed with default outbound access?
* Which outbound method would you choose for AKS?
* NAT Gateway vs Azure Firewall?
* Why is predictable outbound IP useful?

### **T03-M13. What is IP forwarding?**

**Answer:**
IP forwarding allows an Azure VM’s network interface to **receive and forward traffic that is not originally destined for that VM itself**, or to send traffic whose source IP differs from the NIC’s assigned IP configuration.

It is typically required when the VM is acting as a **network virtual appliance**, such as:

* a firewall,
* router,
* proxy,
* WAN optimizer,
* or other packet-forwarding appliance.

Azure requires IP forwarding to be enabled on each NIC that needs to forward such traffic. ([Microsoft Learn][4])

### **Example**

Suppose I have:

```text
Spoke subnet
    ↓
UDR
    ↓
NVA VM: 10.0.1.4
    ↓
Other network
```

The UDR tells Azure:

```text
Send this traffic to 10.0.1.4
```

But the NVA VM must also be allowed to forward that traffic.

So I enable:

```text
IP forwarding = Enabled
```

on its NIC.

### **Azure setting alone is not enough**

This is an important point.

Enabling IP forwarding on the Azure NIC only tells Azure that forwarded traffic is allowed.

The **guest operating system or network appliance must also be configured to actually forward packets**.

For example, on Linux I might also need OS-level IP forwarding enabled.

Microsoft explicitly notes that an application or OS inside the VM must perform the forwarding; the Azure NIC setting by itself does not turn the VM into a router. ([Microsoft Learn][4])

### **Typical architecture**

```text
Source VM
   ↓
UDR
   ↓
NVA NIC
IP forwarding enabled
   ↓
NVA OS forwards packet
   ↓
Destination
```

**Memory line:**
**UDR sends traffic to the appliance; IP forwarding lets the appliance forward it.**

**Interview trap:**
Turning on IP forwarding in Azure does **not automatically configure routing inside Linux or Windows**.

You need both:

```text
Azure NIC IP forwarding
+
Guest OS / NVA forwarding
```

**Keywords:** IP forwarding, NVA, router, firewall, UDR, NIC, packet forwarding

**Likely follow-ups:**

* Why is IP forwarding needed for an NVA?
* Is enabling it on the NIC enough?
* How do UDRs and IP forwarding work together?
* Where else must forwarding be enabled?

## Hard

### **T03-H01. How would you troubleshoot two Azure VMs that cannot communicate?**

**Answer:**
I would troubleshoot it **along the packet path**, starting with the simplest checks and moving from Azure networking to the guest OS and application.

My flow would be:

```text
VM state / IP
   ↓
NSG
   ↓
Route
   ↓
VNet / Peering
   ↓
Firewall / NVA
   ↓
Guest OS firewall
   ↓
Application listener
```

### **1. Confirm both VMs and the destination port**

First I verify:

* both VMs are running,
* source and destination private IPs are correct,
* the destination application is expected to listen on the requested port,
* and I test the specific protocol/port rather than relying only on ping.

For example:

```bash
nc -zv 10.20.1.5 443
```

or:

```bash
curl -v https://10.20.1.5
```

If ICMP is blocked, `ping` failing alone does not prove general connectivity is broken.

---

### **2. Check whether a valid network path should exist**

If the VMs are:

**Same VNet**
→ Azure normally provides system routing.

**Different VNets**
→ I verify VNet peering, VPN, Virtual WAN, or another connectivity mechanism.

For peering I check:

* peering status,
* address ranges,
* remote network configuration,
* whether the required forwarded-traffic or gateway options apply.

---

### **3. Check NSGs on both sides**

I inspect:

* source NIC NSG,
* source subnet NSG,
* destination subnet NSG,
* destination NIC NSG.

For the connection to work, the applicable outbound rules on the source and inbound rules on the destination must allow it.

Rather than manually reading every rule first, I can use **Network Watcher IP Flow Verify**, which identifies whether a specific flow is allowed or denied and which rule caused the result. ([Microsoft Learn][5])

---

### **4. Check effective routes**

Next I inspect the source NIC’s **effective routes**.

I am looking for problems such as:

* incorrect UDR,
* next hop `None`,
* traffic accidentally sent to an NVA,
* unexpected BGP route,
* missing peering route.

I can also use Network Watcher **Next Hop** to see where Azure would send traffic for the destination. ([Microsoft Learn][6])

For example:

```text
Destination: 10.20.1.5
Expected next hop: VirtualNetwork
Actual next hop: VirtualAppliance
```

That immediately suggests a routing issue.

---

### **5. Check Azure Firewall or NVA**

If the route goes through:

```text
Azure Firewall
or
Network Virtual Appliance
```

I check:

* firewall rules,
* UDRs,
* IP forwarding,
* appliance routing,
* return path.

I also verify that traffic is not following an **asymmetric route**, where the forward and return packets take different paths.

---

### **6. Check the guest operating systems**

If the Azure network path is correct, I move inside the VMs.

On the destination I verify:

* OS firewall,
* service status,
* listening socket,
* binding address.

For Linux:

```bash
ss -lntp
```

If the application is listening only on:

```text
127.0.0.1:8080
```

other VMs cannot reach it even if Azure networking is correct.

It may need to listen on:

```text
0.0.0.0:8080
```

or the VM’s private IP.

---

### **7. Use Network Watcher Connection Troubleshoot**

For a production incident, I would use **Azure Network Watcher Connection Troubleshoot** because it can evaluate multiple layers including:

* connectivity,
* NSG blocking,
* next hop,
* missing routes,
* destination listener,
* DNS issues,
* guest firewall problems,
* latency.

Microsoft currently positions Connection Troubleshoot as the broad diagnostic tool for identifying Azure network connectivity faults. ([Microsoft Learn][7])

### **Example troubleshooting sequence**

Suppose:

```text
VM-A: 10.10.1.4
VM-B: 10.10.2.5
Port: 8080
```

I would test:

```text
1. VM-B running?
2. Is :8080 actually listening?
3. Effective NSG rules allow A → B:8080?
4. Effective route from A to 10.10.2.5 correct?
5. Firewall/NVA in path?
6. VM-B OS firewall allows 8080?
7. Application bound to correct interface?
```

Only after locating the failing layer would I change configuration.

**Memory line:**
**IP → NSG → Route → Peering/Firewall → OS → Application.**

**Interview trap:**
Do not immediately modify NSGs just because connectivity fails.

A VM-to-VM issue can be caused by:

* routing,
* peering,
* UDRs,
* NVA/firewall,
* OS firewall,
* or simply no application listening on the port.

A good engineer first identifies **which layer is failing**.

**Keywords:** Network Watcher, Connection Troubleshoot, IP Flow Verify, effective routes, Next Hop, NSG, UDR, guest firewall

**Likely follow-ups:**

* What if the two VMs are in the same VNet?
* What if the NSGs look correct?
* How would you identify which NSG rule is blocking traffic?
* How would you determine whether a UDR is causing the problem?
