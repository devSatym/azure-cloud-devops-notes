# 3. 🔴 M IMP — Azure Virtual Networking

## Hard

### **T03-H06. How do you route spoke-to-spoke traffic through Azure Firewall?**

**Answer:**
Because VNet peering is **non-transitive**, two spokes connected only to a hub do not automatically communicate through that hub. To force spoke-to-spoke traffic through Azure Firewall, I use **UDRs on the spoke subnets**, with Azure Firewall's private IP as the next hop. ([Microsoft Learn][1])

A typical architecture is:

```text
Spoke-A
10.10.0.0/16
     │
     │ UDR: 10.20.0.0/16
     │      → Virtual Appliance
     │      → 10.0.1.4
     ↓
Azure Firewall
10.0.1.4
     ↓
     │
     │ Firewall allows traffic
     │
     ↓
Spoke-B
10.20.0.0/16
```

I also configure the **return path**:

```text
Spoke-B
UDR: 10.10.0.0/16
→ Azure Firewall 10.0.1.4
```

That is important because the firewall is stateful; both directions should follow the expected firewall path.

### **Configuration approach**

**1. Peer both spokes with the hub**

```text
Spoke-A ↔ Hub
Spoke-B ↔ Hub
```

The peering must allow the required forwarded traffic.

**2. Create UDRs on the spoke workload subnets**

For Spoke-A:

```text
Destination: 10.20.0.0/16
Next hop: Virtual appliance
Next hop IP: <Azure Firewall private IP>
```

For Spoke-B:

```text
Destination: 10.10.0.0/16
Next hop: Virtual appliance
Next hop IP: <Azure Firewall private IP>
```

**3. Create Azure Firewall network rules**

For example:

```text
Source:      10.10.0.0/16
Destination: 10.20.0.0/16
Ports:       Required application ports
Action:      Allow
```

Microsoft's current hub-and-spoke guidance uses this pattern: UDRs send traffic from each spoke toward the hub firewall, the firewall evaluates its policy, and the return spoke routes traffic back through the same firewall. ([Microsoft Learn][1])

### **Important routing caveat**

If the two spokes are also **directly peered**, Azure has a specific route for the remote VNet.

In that situation, simply having:

```text
0.0.0.0/0 → Firewall
```

may not force spoke-to-spoke traffic through the firewall, because the more specific peering route wins.

Microsoft therefore recommends explicit UDRs for the **remote spoke address prefix** when directly peered networks must still traverse the firewall. ([Microsoft Learn][2])

### **How I would validate it**

I would inspect:

```text
Effective Routes
```

on both spoke VM NICs and use Network Watcher:

```text
Next Hop
```

to verify:

```text
Spoke-A → Spoke-B
Next hop = Virtual Appliance
```

and that the next-hop IP is the Azure Firewall.

**Memory flow:**
**Spoke-A → UDR → Azure Firewall → Spoke-B → UDR → Azure Firewall → Spoke-A**

**Interview trap:**
Do not assume hub peering automatically makes the hub a router.

```text
Spoke-A ↔ Hub ↔ Spoke-B
```

does **not** create transitive routing by itself. UDRs and a forwarding device such as Azure Firewall/NVA are required for this design.

**Keywords:** hub-and-spoke, UDR, Azure Firewall, Virtual Appliance, non-transitive peering, symmetric routing

**Likely follow-ups:**

* Why are UDRs needed?
* Why must the return path also use the firewall?
* What if the spokes are directly peered?
* How would you verify that traffic is actually crossing Azure Firewall?

### **T03-H07. What is forced tunneling?**

**Answer:**
Forced tunneling means **forcing traffic that would normally go directly to the internet to follow a specified private or centralized network path instead**.

In Azure, a common example is sending internet-bound Azure traffic through:

* an on-premises firewall,
* a centralized NVA,
* or another security inspection path

rather than allowing workloads to egress directly to the internet. Azure Firewall also supports a dedicated forced-tunneling configuration. ([Microsoft Learn][3])

### **Example**

Normally:

```text
Azure workload
      ↓
Internet
```

With forced tunneling:

```text
Azure workload
      ↓
Azure Firewall
      ↓
VPN / ExpressRoute
      ↓
On-premises Firewall
      ↓
Internet
```

A default route such as:

```text
0.0.0.0/0
```

can be advertised through BGP or configured with a UDR so internet traffic follows the required next hop. ([Microsoft Learn][3])

### **Why organizations use it**

Typical reasons are:

* centralized security inspection,
* compliance requirements,
* central internet egress,
* URL/domain filtering,
* consistent logging,
* data-loss prevention controls.

### **Azure Firewall-specific consideration**

Azure Firewall itself needs connectivity for its own management operations.

For Azure Firewall forced tunneling, Microsoft separates **customer traffic from firewall management traffic** using a Firewall Management NIC and an:

```text
AzureFirewallManagementSubnet
```

This management path maintains the connectivity Azure Firewall needs while customer internet traffic is forced toward the configured next hop. ([Microsoft Learn][4])

A simplified model is:

```text
                 Azure Firewall
                 ┌───────────────┐
Customer traffic │ Data interface│ → On-prem/NVA
                 │               │
Management       │ Management NIC│ → Azure platform
                 └───────────────┘
```

### **Routing risk**

Forced tunneling must be designed carefully because an incorrect default route can:

* blackhole internet traffic,
* break firewall dependencies,
* create asymmetric routing,
* or unexpectedly send Azure service traffic through on-premises infrastructure.

**Memory line:**
**Forced tunneling = don't let internet-bound traffic exit directly; force it through the required security path.**

**Interview trap:**
Do not confuse:

```text
Forced tunneling
```

with:

```text
VPN tunneling in general
```

Forced tunneling specifically refers to **forcing traffic onto a designated route**, commonly a default route toward centralized/on-premises inspection.

**Keywords:** forced tunneling, `0.0.0.0/0`, UDR, BGP, Azure Firewall, on-premises firewall, centralized egress

**Likely follow-ups:**

* Why does Azure Firewall need a management interface for forced tunneling?
* Can ExpressRoute participate in forced tunneling?
* What problems can an incorrect default route cause?
* Forced tunneling vs split tunneling?

### **T03-H08. How would you inspect the effective routes of an Azure VM?**

**Answer:**
I would inspect the **Effective routes on the VM's network interface**, because that shows the routing information Azure is actually applying rather than looking at just one route table.

Effective routes combine sources such as:

```text
Azure system routes
+
User Defined Routes
+
BGP-learned routes
+
Routes introduced through network connectivity such as peering
```

Microsoft specifically recommends effective routes when troubleshooting VM routing problems. ([Microsoft Learn][5])

### **Azure portal**

I would navigate roughly through:

```text
Virtual Machine
   ↓
Networking
   ↓
Network Interface
   ↓
Effective routes
```

There I can inspect fields such as:

* address prefix,
* next-hop type,
* next-hop IP,
* route source.

### **Azure CLI**

I can use:

```bash
az network nic show-effective-route-table \
  --resource-group <resource-group> \
  --name <nic-name>
```

Microsoft documents this command specifically for retrieving a NIC's effective route table. ([Microsoft Learn][5])

### **What I look for**

Suppose my VM cannot reach:

```text
10.20.1.5
```

I look for the most specific matching route.

Expected:

```text
10.20.0.0/16
→ VirtualNetworkPeering
```

But perhaps I find:

```text
10.20.0.0/16
→ VirtualAppliance
→ 10.0.1.4
```

That tells me Azure is intentionally sending the traffic through an NVA or firewall.

Or I might find:

```text
Next hop: None
```

which can explain why the traffic is dropped.

### **Use Network Watcher Next Hop**

For a specific destination, I can also use:

```text
Network Watcher → Next Hop
```

or CLI:

```bash
az network watcher show-next-hop ...
```

This asks Azure directly:

> For this source NIC and destination IP, what next hop would be used?

Microsoft recommends Next Hop alongside effective routes for routing diagnosis. ([Microsoft Learn][5])

### **My troubleshooting flow**

```text
Destination IP
     ↓
Find most specific effective route
     ↓
Check route source
     ↓
Check next-hop type/IP
     ↓
Use Network Watcher Next Hop
     ↓
Validate firewall/NVA/peering path
```

**Memory line:**
**Route table shows what I configured; Effective Routes show what the VM actually sees.**

**Interview trap:**
Do not inspect only the manually attached route table.

The VM's effective routing can also be influenced by:

* system routes,
* BGP,
* peering,
* gateway-learned routes.

**Keywords:** effective routes, UDR, system routes, BGP, Next Hop, Network Watcher, NIC

**Likely follow-ups:**

* What sources make up effective routes?
* Which route wins if several routes match?
* What does next hop `None` mean?
* How would you verify a VM is sending traffic to Azure Firewall?

### **T03-H09. How would you inspect effective NSG rules?**

**Answer:**
I would inspect the **Effective security rules on the VM's NIC**, because that gives me the combined NSG rules affecting the network interface instead of checking subnet and NIC NSGs separately.

This is particularly useful when both:

```text
Subnet NSG
+
NIC NSG
```

apply to the same VM.

Azure exposes the resulting effective security rules for a NIC attached to a running VM. ([Microsoft Learn][6])

### **Azure portal**

I would navigate roughly through:

```text
Virtual Machine
      ↓
Networking
      ↓
Network Interface
      ↓
Effective security rules
```

I then check:

* inbound rules,
* outbound rules,
* source/destination,
* protocol,
* port,
* allow/deny result,
* priority,
* which NSG contributed the rule.

### **Azure CLI**

I can use:

```bash
az network nic list-effective-nsg \
  --resource-group <resource-group> \
  --name <nic-name>
```

Microsoft documents this command for viewing the effective NSG rules associated with a network interface. ([Microsoft Learn][7])

### **Example**

Suppose HTTPS connectivity fails.

I might initially see:

```text
Subnet NSG
Allow TCP 443
```

and assume networking is correct.

But effective rules could reveal:

```text
NIC NSG
Deny TCP 443 from source range
```

Since both NSGs apply, the traffic is ultimately blocked.

### **Use IP Flow Verify for a specific flow**

If I know the exact flow:

```text
Source: 10.10.1.4
Destination: 10.20.1.5
TCP 443
```

I can use Network Watcher **IP Flow Verify**.

Instead of manually reasoning through every rule, it tells me whether the traffic is:

```text
Allow
or
Deny
```

and identifies the NSG rule responsible.

That is usually faster during troubleshooting.

### **My troubleshooting flow**

```text
Source / Destination / Port
          ↓
Effective security rules
          ↓
Subnet + NIC NSGs
          ↓
IP Flow Verify
          ↓
Identify exact Allow/Deny rule
```

**Memory line:**
**Effective NSG rules = what security rules actually apply to this NIC.**

**Interview trap:**
Do not inspect only the subnet NSG.

A NIC-level NSG may also affect the VM, and **both applicable NSGs must allow the traffic**.

Also remember that priorities are evaluated **within each NSG**, not globally between different NSGs.

**Keywords:** effective security rules, NSG, NIC, subnet NSG, IP Flow Verify, Network Watcher

**Likely follow-ups:**

* Which tool identifies the exact NSG rule blocking traffic?
* What if the subnet NSG allows but NIC NSG denies?
* Can effective security rules be viewed on a stopped/deallocated VM?
* What is the difference between Effective Security Rules and IP Flow Verify?
