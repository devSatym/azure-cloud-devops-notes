# 3. 🔴 M IMP — Azure Virtual Networking

## Easy

### **T03-E07. What is a route table?**

**Answer:**
An Azure route table is a collection of **routing rules that control where network traffic from a subnet is sent**.

Azure automatically provides **system routes**, but I can associate a route table with a subnet and add **User Defined Routes, or UDRs**, when I need to override Azure's default routing behavior. ([Microsoft Learn][1])

A route typically contains:

* destination address prefix,
* next-hop type,
* and, when required, a next-hop IP address.

### **Example**

Suppose my application subnet is:

```text
10.10.2.0/24
```

By default, Azure can route internet-bound traffic according to its system routes.

If security requires all outbound traffic to pass through Azure Firewall, I can create:

```text
Destination: 0.0.0.0/0
Next hop: Virtual appliance
Next-hop IP: 10.10.0.4
```

and associate that route table with the application subnet.

The flow becomes:

```text
Application VM
     ↓
Subnet
     ↓
Route table
     ↓
Azure Firewall
     ↓
Internet
```

### **Important point**

Route tables are associated with **subnets**, not directly with individual VMs.

The routes applicable to a VM are determined from the subnet it belongs to, along with Azure system routes and other routing sources.

**Memory line:**
**Route table = where should this packet go next?**

**Interview trap:**
A route table does **not filter traffic**.

```text
Route table → decides path
NSG         → allows or denies traffic
```

Both may affect the same connection, but they solve different problems.

**Keywords:** route table, UDR, next hop, subnet, system route, routing

### **T03-E08. What is VNet peering?**

**Answer:**
VNet peering connects **two Azure Virtual Networks so resources in them can communicate privately using their private IP addresses**.

Traffic between peered VNets travels over the **Microsoft backbone network**, rather than traversing the public internet. VNets can be peered within the same Azure region or across regions using global VNet peering. ([Microsoft Learn][1])

### **Example**

Suppose I have:

```text
VNet-App
10.10.0.0/16
```

and:

```text
VNet-Database
10.20.0.0/16
```

After peering them:

```text
VNet-App
    ⇄
VNet-Database
```

a VM at:

```text
10.10.1.4
```

can communicate privately with:

```text
10.20.1.5
```

assuming NSGs, routes, firewalls, and the application itself allow the traffic.

### **Important characteristics**

VNet peering provides:

* private connectivity,
* low latency,
* high bandwidth,
* Microsoft backbone routing,
* no requirement for a VPN gateway just to connect the VNets.

A critical property is:

> **VNet peering is not transitive.**

If:

```text
VNet-A ↔ VNet-B
VNet-B ↔ VNet-C
```

that does **not automatically mean**:

```text
VNet-A ↔ VNet-C
```

Azure's current networking guidance explicitly notes that peering is a direct relationship rather than a transitive one. ([Microsoft Learn][1])

### **Address planning**

Peered VNet address spaces must not conflict.

For example:

```text
VNet-A: 10.0.0.0/16
VNet-B: 10.0.0.0/16
```

would create overlapping-address problems and is not a valid normal peering design.

**Memory line:**
**VNet peering = private VNet-to-VNet connectivity over Microsoft's backbone.**

**Interview trap:**
VNet peering does **not automatically provide transitive routing**.

That becomes especially important in hub-and-spoke architectures.

**Keywords:** VNet peering, private connectivity, Microsoft backbone, global peering, non-transitive

## Medium

### **T03-M01. How does traffic flow between subnets in the same VNet?**

**Answer:**
By default, Azure creates **system routes that allow subnets within the same VNet to communicate with each other** using private IP addresses. ([Microsoft Learn][1])

For example:

```text
VNet: 10.0.0.0/16

Subnet-Web
10.0.1.0/24

Subnet-App
10.0.2.0/24
```

Azure automatically provides routing between them:

```text
Web VM
10.0.1.4
    ↓
Azure VNet routing
    ↓
App VM
10.0.2.4
```

I do not need a router appliance or VNet peering because both subnets belong to the same VNet.

### **But routing does not guarantee connectivity**

Even though Azure knows how to route the packet, the connection can still be blocked by:

* subnet NSGs,
* NIC NSGs,
* user-defined routes,
* Azure Firewall or an NVA,
* guest OS firewall,
* application not listening on the destination port.

So I think of connectivity as:

```text
Route exists
     +
Security permits
     +
Application listens
     =
Connection works
```

### **Example**

Suppose:

```text
Web subnet → App subnet
TCP 8080
```

The Azure system route allows the network path.

But if the App subnet NSG contains:

```text
Deny TCP 8080 from Web subnet
```

the connection still fails.

### **Can I force same-VNet traffic through a firewall?**

Yes.

I can associate a UDR with a subnet that sends selected traffic to a **virtual appliance or Azure Firewall**, overriding the normal system route where applicable.

For example:

```text
Spoke/Application subnet
        ↓
UDR
        ↓
Azure Firewall
        ↓
Destination subnet/network
```

This is common when centralized inspection is required. ([Microsoft Learn][1])

**Memory line:**
**Same VNet = routing exists by default; security controls still decide whether traffic is allowed.**

**Interview trap:**
Do not say:

> “Subnets in the same VNet always communicate.”

The correct statement is:

> Azure provides routing between them by default, but NSGs, UDRs, firewalls, or host-level controls can block or redirect the traffic.

**Keywords:** system routes, same VNet, subnet communication, NSG, UDR, Azure Firewall

**Likely follow-ups:**

* Do subnets in the same VNet need VNet peering?
* Can an NSG block traffic between two subnets?
* Can you route same-VNet traffic through Azure Firewall?
* What would you check if two subnets cannot communicate?

### **T03-M02. What is the difference between inbound and outbound NSG rules?**

**Answer:**
The difference is the **direction of traffic relative to the protected Azure resource**.

**Inbound rules** control traffic entering the resource.

**Outbound rules** control traffic leaving the resource.

An NSG keeps separate inbound and outbound rule sets. ([Microsoft Learn][2])

### **Example**

Suppose a web VM receives HTTPS traffic:

```text
Internet
    ↓ TCP 443
Web VM
```

I need an **inbound rule** such as:

```text
Source: Internet
Destination: Web VM/subnet
Port: 443
Action: Allow
```

Now suppose that VM needs to connect to a database:

```text
Web VM
    ↓ TCP 5432
Database
```

From the web VM's perspective, this is **outbound traffic**, so the relevant outbound NSG rules apply.

### **If NSGs exist on both subnet and NIC**

For inbound traffic, Azure evaluates:

```text
Subnet NSG
    ↓
NIC NSG
    ↓
VM
```

For the connection to succeed, the traffic must be allowed through the applicable NSGs. ([Microsoft Learn][3])

For outbound traffic, the processing direction is reversed relative to the VM:

```text
VM
 ↓
NIC NSG
 ↓
Subnet NSG
 ↓
Destination
```

### **Stateful behavior**

NSGs are **stateful**.

Suppose the VM initiates an allowed outbound HTTPS connection:

```text
VM → Internet:443
```

Azure automatically allows the return traffic for that established flow.

I do not need a separate inbound rule just to allow the response packets.

Likewise, response traffic for an allowed inbound flow is automatically handled by the NSG state.

**Memory line:**
**Inbound = traffic coming in.
Outbound = traffic going out.
NSGs are stateful.**

**Interview trap:**
Do not create matching inbound and outbound rules just for the **response traffic of an already allowed connection**.

Because NSGs are stateful, return traffic for an established allowed flow is automatically permitted.

**Keywords:** inbound, outbound, NSG, direction, stateful, subnet NSG, NIC NSG

**Likely follow-ups:**

* In what order are subnet and NIC NSGs evaluated?
* Are NSGs stateful or stateless?
* Do I need an inbound rule for response traffic?
* What happens if the NIC NSG allows traffic but the subnet NSG denies it?
