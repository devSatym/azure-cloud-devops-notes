# 3. 🔴 M IMP — Azure Virtual Networking

## Medium

### **T03-M03. How are NSG rules prioritized?**

**Answer:**
NSG rules are evaluated by **priority number**, where a **lower number means higher priority**.

Custom NSG rule priorities range from:

```text
100 to 4096
```

So:

```text
Priority 100
```

is evaluated before:

```text
Priority 200
```

Once traffic matches a rule, Azure stops evaluating later NSG rules for that direction. ([Microsoft Learn][1])

### **Example**

Suppose I have:

```text
Priority 100 → Allow TCP 443 from Internet
Priority 200 → Deny all traffic from Internet
```

HTTPS traffic on port 443 matches the priority-100 rule first and is allowed.

Other internet traffic reaches the priority-200 rule and is denied.

### **Default rules**

Every NSG also contains default rules with much lower precedence, such as:

```text
AllowVNetInBound
AllowAzureLoadBalancerInBound
DenyAllInBound
```

Custom rules are evaluated before those defaults because custom priorities are numerically lower. ([Microsoft Learn][1])

**Memory line:**
**Lower number = higher priority. First matching rule wins.**

**Interview trap:**
Do not say:

> “A higher priority number is evaluated first.”

In Azure NSGs, **priority 100 beats priority 200**.

**Keywords:** NSG priority, first match, lower number, allow, deny, default rules

### **T03-M04. What happens when two NSG rules match the same traffic?**

**Answer:**
If multiple NSG rules could match the same traffic, Azure evaluates them in priority order and uses the **first matching rule**.

Because a lower number has higher priority, that rule wins and Azure stops processing additional NSG rules in that NSG. ([Microsoft Learn][1])

### **Example**

Suppose I have:

```text
Priority 100
Allow TCP 443
Source: Internet

Priority 300
Deny all traffic
Source: Internet
```

For HTTPS traffic:

```text
Internet → TCP 443
```

the priority-100 rule matches first:

```text
ALLOW
```

Azure does not continue to priority 300.

But traffic to:

```text
TCP 22
```

does not match the first rule, so evaluation continues until the deny rule matches.

### **Another example**

```text
Priority 100 → Deny 10.1.0.0/16
Priority 200 → Allow 10.1.1.0/24
```

Traffic from:

```text
10.1.1.5
```

matches **both rules**, but the priority-100 deny is evaluated first.

Result:

```text
DENY
```

The more specific CIDR does not automatically win.

The **priority determines the order**, not subnet specificity.

**Memory line:**
**First matching NSG rule wins.**

**Interview trap:**
NSGs do **not** behave like longest-prefix routing.

A more specific IP range does not automatically take precedence over a broader rule. You must assign the correct priorities.

**Keywords:** first match, NSG evaluation, priority, allow, deny, rule ordering

### **T03-M05. Can an NSG be attached to both a subnet and a network interface?**

**Answer:**
Yes. An NSG can be associated with a **subnet, a NIC, or both**.

When an NSG is attached to a subnet, its rules apply to resources in that subnet.

When an NSG is attached to a specific NIC, its rules apply to traffic for that NIC.

If both exist, Azure evaluates **both NSGs**, so traffic must satisfy the applicable rules at both levels. ([Microsoft Learn][2])

### **Example**

```text
Subnet: app-subnet
NSG: nsg-app-subnet

VM NIC
NSG: nsg-vm01
```

For inbound traffic:

```text
Internet
   ↓
Subnet NSG
   ↓
NIC NSG
   ↓
VM
```

For outbound traffic:

```text
VM
 ↓
NIC NSG
 ↓
Subnet NSG
 ↓
Destination
```

Azure documents this evaluation order explicitly. ([Microsoft Learn][2])

### **Practical design**

In most environments, I prefer **subnet-level NSGs for common security policy**, because every workload in that subnet receives the same baseline rules.

NIC-level NSGs can be used when a particular VM needs more specific restrictions, but too many NIC-level rules can make troubleshooting harder.

**Memory line:**
**Subnet NSG = common subnet policy.
NIC NSG = individual NIC policy.**

**Interview trap:**
If both subnet and NIC NSGs exist, Azure does not choose one and ignore the other.

Both participate in traffic filtering.

**Keywords:** subnet NSG, NIC NSG, cumulative evaluation, inbound, outbound

### **T03-M06. What happens when subnet NSG and NIC NSG rules conflict?**

**Answer:**
When both a subnet NSG and NIC NSG apply, the traffic must be **allowed by both applicable NSGs**.

If one allows the traffic but the other denies it, the connection is blocked. ([Microsoft Learn][3])

### **Inbound traffic**

Azure evaluates:

```text
Source
  ↓
Subnet NSG
  ↓
NIC NSG
  ↓
VM
```

So if:

```text
Subnet NSG → Allow TCP 443
NIC NSG    → Deny TCP 443
```

result:

```text
DENIED
```

The packet never reaches the VM.

### **Outbound traffic**

The order is reversed:

```text
VM
 ↓
NIC NSG
 ↓
Subnet NSG
 ↓
Destination
```

Again, the traffic must pass both. ([Microsoft Learn][2])

### **Important distinction**

The rule priority is only compared **inside each individual NSG**.

For example:

```text
Subnet NSG:
Priority 100 → Allow 443

NIC NSG:
Priority 400 → Deny 443
```

You do **not** compare `100` versus `400` globally.

Azure first evaluates the relevant rules inside each NSG according to that NSG's own priority ordering.

If either NSG blocks the traffic, the overall connection fails.

### **Troubleshooting**

If traffic should work but does not, I would check the VM NIC's:

```text
Effective security rules
```

because Azure combines the applicable subnet- and NIC-level rules there.

I can also use **Network Watcher IP Flow Verify** to determine which rule allowed or denied a specific flow. ([Microsoft Learn][4])

**Memory line:**
**With subnet + NIC NSGs, both must allow the traffic.**

**Interview trap:**
Do not compare priority numbers across two different NSGs.

```text
Priority 100 in subnet NSG
```

does not automatically override:

```text
Priority 200 in NIC NSG
```

Each NSG is evaluated independently, and the traffic must pass both.

**Keywords:** cumulative filtering, subnet NSG, NIC NSG, effective security rules, IP Flow Verify, deny
