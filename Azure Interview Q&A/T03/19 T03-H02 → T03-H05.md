# 3. 🔴 M IMP — Azure Virtual Networking

## Hard

### **T03-H02. How would you troubleshoot asymmetric routing in Azure?**

**Answer:**
Asymmetric routing means the **forward path and return path take different network routes**.

That becomes a problem especially when traffic passes through a **stateful firewall or NVA**, because the device may see the outbound flow but never see the return flow, so it cannot maintain the connection state correctly.

My troubleshooting approach would be:

```text
Forward path
     ↓
Effective route / Next Hop
     ↓
Firewall or NVA
     ↓
Destination
     ↓
Return path
     ↓
Does it pass through the same stateful device?
```

### **1. Identify both directions**

Suppose traffic should be:

```text
VM-A
 ↓
Azure Firewall
 ↓
VM-B
```

I verify both:

```text
A → B
```

and:

```text
B → A
```

independently.

The key question is:

> Does the return traffic follow the same intended path?

### **2. Inspect effective routes**

I check the effective routes on:

* source NIC,
* destination NIC,
* relevant subnets.

I look for:

* conflicting UDRs,
* unexpected BGP routes,
* direct peering routes bypassing the firewall,
* default routes pointing somewhere different.

Azure Network Watcher **Next Hop** is especially useful because it shows where Azure intends to send traffic toward a specific destination. ([Microsoft Learn][1])

### **3. Check the NVA or firewall**

If an NVA is involved, I verify:

* IP forwarding is enabled,
* OS/appliance forwarding is configured,
* internal routing tables are correct,
* firewall policies allow both directions,
* the NVA is not overloaded.

Microsoft recommends checking both Azure UDRs and the NVA's own routing configuration when diagnosing NVA path problems. ([Microsoft Learn][1])

### **4. Check peering and hybrid routes**

Asymmetry commonly appears when one side learns a more specific route through:

* ExpressRoute,
* VPN/BGP,
* VNet peering,
* direct spoke peering,

while the other side uses:

* Azure Firewall,
* NVA,
* another gateway.

For example:

```text
Forward:
Spoke-A → Firewall → Spoke-B

Return:
Spoke-B → Direct Peering → Spoke-A
```

That bypasses the firewall on the return path.

### **5. Capture traffic if needed**

If the route tables look correct, I would capture packets on:

* source,
* NVA/firewall where supported,
* destination.

If the NVA sees the SYN but never the return packet, that strongly indicates path asymmetry or downstream routing issues.

**Memory line:**
**Asymmetric routing = forward and return paths differ; stateful devices usually need both sides of the flow.**

**Interview trap:**
A connection can fail even when **both source and destination have valid routes**.

The problem may be that those routes create different forward and return paths.

**Keywords:** asymmetric routing, effective routes, Next Hop, UDR, BGP, NVA, stateful firewall

**Likely follow-ups:**

* Why does asymmetric routing break stateful firewalls?
* How would you identify the return path?
* Can direct VNet peering cause a firewall bypass?
* Which Network Watcher tools would you use?

### **T03-H03. What happens if two peered VNets have overlapping CIDR ranges?**

**Answer:**
Azure VNet peering requires the VNet address spaces to be **non-overlapping**.

If two VNets use overlapping address ranges, Azure will not allow normal VNet peering between them. Microsoft explicitly states that VNets with matching or overlapping address spaces cannot be peered. ([Microsoft Learn][2])

### **Example**

Suppose:

```text
VNet-A
10.0.0.0/16
```

and:

```text
VNet-B
10.0.0.0/20
```

These ranges overlap because `10.0.0.0/20` sits inside `10.0.0.0/16`.

So normal peering cannot be created.

### **Why is overlap a problem?**

Because routing becomes ambiguous.

If a VM in VNet-A tries to reach:

```text
10.0.1.10
```

Azure cannot cleanly determine whether that address belongs to:

* the local VNet,
* or the remote peered VNet.

This is why IP-address planning is extremely important before building large Azure environments.

### **How would I fix it?**

My preferred solution is to **renumber one network** to a non-overlapping address space.

For example:

```text
VNet-A
10.0.0.0/16

VNet-B
10.20.0.0/16
```

Then peering can be established normally.

If renumbering is difficult, there are specialized architectures involving NAT or network appliances, but I would not make those the default solution because they add operational complexity.

### **Enterprise lesson**

Before building hub-and-spoke networks, I would create a centralized IP-address plan covering:

* Azure regions,
* spokes,
* on-premises networks,
* VPN/ExpressRoute-connected environments,
* future expansion.

Microsoft's hub-and-spoke guidance also requires non-overlapping hub and spoke address spaces. ([Microsoft Learn][3])

**Memory line:**
**Overlapping VNets cannot be normally peered—plan address space before deployment.**

**Interview trap:**
Do not say:

> “Azure uses longest-prefix matching, so overlapping peered VNets are fine.”

Longest-prefix matching is relevant to routing, but Azure **does not permit standard VNet peering with overlapping address spaces**.

**Keywords:** overlapping CIDR, VNet peering, IP planning, address space, renumbering

**Likely follow-ups:**

* Can two subnets inside one VNet overlap?
* What if Azure and on-premises networks overlap?
* How would you fix overlapping networks after deployment?
* Why is IP planning important for hub-and-spoke?

### **T03-H04. Is VNet peering transitive?**

**Answer:**
No. **Azure VNet peering is non-transitive.**

If I have:

```text
VNet-A ↔ VNet-B
VNet-B ↔ VNet-C
```

that does not automatically provide:

```text
VNet-A ↔ VNet-C
```

Microsoft explicitly defines VNet peering as a non-transitive relationship. ([Microsoft Learn][4])

### **Why this matters**

This is fundamental in a hub-and-spoke architecture.

Suppose:

```text
Spoke-A
   ↕
  Hub
   ↕
Spoke-B
```

Even though both spokes are peered with the hub, they do not automatically communicate through it.

I need an explicit architecture for spoke-to-spoke connectivity.

### **Common options**

#### **Option 1 — Route through Azure Firewall or NVA**

```text
Spoke-A
   ↓
UDR
   ↓
Azure Firewall in Hub
   ↓
Spoke-B
```

This is common when centralized inspection is required. ([Microsoft Learn][3])

#### **Option 2 — Direct spoke-to-spoke peering**

```text
Spoke-A ↔ Spoke-B
```

This gives a lower-latency direct path but can increase peering complexity and may bypass centralized inspection.

#### **Option 3 — Azure Virtual Network Manager**

For large environments, Azure Virtual Network Manager can manage connectivity patterns centrally.

### **Gateway transit**

A spoke can also use a VPN or ExpressRoute gateway located in the hub through gateway transit, but that is different from saying VNet peering itself is transitive. ([Microsoft Learn][5])

**Memory line:**
**Peering connects A to B, not A through B to C.**

**Interview trap:**
A very common incorrect answer is:

> “If every spoke peers to the hub, all spokes can automatically communicate.”

They cannot unless you configure routing, a firewall/NVA, direct peering, or another supported connectivity mechanism.

**Keywords:** non-transitive peering, spoke-to-spoke, hub-and-spoke, UDR, Azure Firewall, direct peering

**Likely follow-ups:**

* How do spokes communicate through a hub?
* When would you directly peer two spokes?
* What is gateway transit?
* How does Azure Virtual Network Manager help?

### **T03-H05. How would you implement hub-and-spoke networking?**

**Answer:**
I would use a **central hub VNet for shared networking and security services**, and separate spoke VNets for individual applications, environments, or teams.

A typical design is:

```text
                    On-Premises
                        │
                 VPN / ExpressRoute
                        │
                        ↓
                ┌───────────────┐
                │    HUB VNET   │
                │               │
                │ Azure Firewall│
                │ VPN/ER Gateway│
                │ Bastion       │
                │ DNS Services  │
                └───────┬───────┘
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ↓             ↓             ↓
      Spoke-A        Spoke-B       Spoke-C
      Orders         Payments      Analytics
```

Microsoft's current design guidance uses the hub for shared services such as Azure Firewall, VPN/ExpressRoute gateways, Bastion, and centralized connectivity, while spokes host isolated workloads. ([Microsoft Learn][3])

### **1. Create the hub VNet**

The hub would normally contain shared networking components such as:

* Azure Firewall,
* VPN Gateway or ExpressRoute Gateway,
* Azure Bastion,
* DNS infrastructure or Private Resolver,
* shared network services.

For example:

```text
Hub VNet
10.0.0.0/16

├── AzureFirewallSubnet
├── GatewaySubnet
├── AzureBastionSubnet
└── Shared-services subnet
```

### **2. Create separate spoke VNets**

Each workload gets an isolated address space.

For example:

```text
Spoke-Orders
10.10.0.0/16

Spoke-Payments
10.20.0.0/16

Spoke-Analytics
10.30.0.0/16
```

All address ranges must be planned so they do not overlap. ([Microsoft Learn][3])

### **3. Peer each spoke to the hub**

I configure bidirectional peering:

```text
Hub ↔ Spoke-A
Hub ↔ Spoke-B
Hub ↔ Spoke-C
```

I do not assume spoke-to-spoke connectivity because VNet peering is non-transitive.

### **4. Route traffic through the firewall**

If centralized inspection is required, I associate UDRs with workload subnets.

For example:

```text
0.0.0.0/0
   ↓
Azure Firewall private IP
```

For standard hub-and-spoke designs, Microsoft documents routing spoke traffic through the hub firewall for inspection and logging. ([Microsoft Learn][3])

The path can then be:

```text
Spoke-A
   ↓
Azure Firewall
   ↓
Spoke-B
```

or:

```text
Spoke
  ↓
Azure Firewall
  ↓
Internet
```

### **5. Configure peering options correctly**

If the hub has a VPN or ExpressRoute gateway and spokes should use it:

**Hub peering:**

```text
Allow gateway transit
```

**Spoke peering:**

```text
Use remote gateway
```

If traffic is being routed through a firewall/NVA, I also make sure the relevant peering configuration allows forwarded traffic. ([Microsoft Learn][5])

### **6. Apply layered security**

I would normally use:

```text
NSGs
→ workload-level segmentation

Azure Firewall
→ centralized inspection and policy

UDRs
→ enforce network path
```

For example:

```text
Internet
   ↓
Azure Firewall / controlled ingress
   ↓
Spoke workload
```

and:

```text
Spoke-A
   ↓
Firewall inspection
   ↓
Spoke-B
```

### **7. Centralize DNS**

For private endpoints and hybrid connectivity, I would design DNS centrally using services such as:

* Azure DNS Private Resolver,
* Private DNS Zones,
* forwarding rules where required.

DNS design is especially important because workloads across spokes and on-premises networks need consistent private-name resolution.

### **Why hub-and-spoke?**

It gives me:

* workload isolation,
* centralized security,
* shared connectivity,
* centralized hybrid networking,
* simpler governance,
* reduced duplication of gateways/firewalls.

### **Trade-off**

A centralized hub can become a:

* performance bottleneck,
* operational dependency,
* cost concentration point,

if it is poorly sized.

At larger scale or across multiple regions, I would consider **one hub per region** or Azure Virtual WAN depending on requirements. Microsoft also recommends regional hub designs for multi-region environments. ([Microsoft Learn][6])

**Rule of thumb:**
**Hub = shared connectivity and security.
Spokes = isolated workloads.
UDRs decide the path.
Firewall inspects the path.**

**Interview trap:**
Do not assume:

```text
Spoke-A ↔ Hub ↔ Spoke-B
```

means Spoke-A automatically reaches Spoke-B.

Peering is non-transitive; spoke-to-spoke connectivity must be explicitly designed.

**Keywords:** hub-and-spoke, Azure Firewall, VNet peering, UDR, gateway transit, DNS, centralized security
