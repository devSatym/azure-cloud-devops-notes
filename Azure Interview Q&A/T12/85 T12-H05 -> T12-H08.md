### **T12-H05. What parts of an AKS application require backup?**

**Answer:**
For AKS, I separate **recreatable infrastructure** from **state that must be protected**. The cluster itself should ideally be reproducible from Terraform/Bicep and GitOps, while I back up the **Kubernetes application state, persistent volumes, and every external stateful dependency the application needs**. Azure Backup for AKS currently supports backing up cluster resources and supported CSI-based persistent volumes such as Azure Disk and Azure SMB Files. ([Microsoft Learn][1])

### **What I would protect**

```text
AKS Application
│
├── Kubernetes objects
│   ├── Deployments
│   ├── StatefulSets
│   ├── Services
│   ├── ConfigMaps
│   ├── selected Secrets
│   ├── PVCs
│   └── selected cluster-scoped resources
│
├── Persistent application data
│   └── Azure Disk / supported Azure Files PVs
│
├── External data
│   ├── Azure SQL / PostgreSQL
│   ├── Storage
│   ├── Cosmos DB
│   └── other databases
│
└── Recovery source
    ├── Terraform
    ├── Helm/Kustomize
    ├── GitOps repository
    └── container images
```

---

### **1. Kubernetes cluster state**

I would protect the Kubernetes objects needed to reconstruct the workload.

For example:

```text
Namespace
├── Deployment
├── Service
├── ConfigMap
├── Secret
├── PVC
└── NetworkPolicy
```

Azure Backup for AKS lets me select namespaces and resources by labels or API group/kind, and it can optionally include cluster-scoped resources and Kubernetes Secrets. ([Microsoft Learn][2])

This is particularly valuable for objects that are not perfectly reproduced from Git.

---

### **2. Persistent volumes**

This is usually the most important in-cluster backup target.

For a stateless pod:

```text
Pod deleted
    ↓
Deployment recreates it
```

No meaningful application data is lost.

But for:

```text
StatefulSet
   ↓
PVC
   ↓
Azure Disk
```

losing the disk can mean losing application state.

Current Azure Backup for AKS uses CSI snapshot capabilities and supports Azure Disk and supported Azure SMB Files persistent volumes, subject to current limitations. ([Microsoft Learn][3])

---

### **3. Application-consistent state**

A disk snapshot alone might not be enough for a database running inside Kubernetes.

For example:

```text
MySQL Pod
   ↓
writes in memory / transaction activity
   ↓
disk snapshot occurs
```

I may get only crash-consistent storage.

Azure Backup for AKS supports custom pre/post backup hooks that can help quiesce applications such as databases before the persistent-volume snapshot is taken. ([Microsoft Learn][4])

Conceptually:

```text
Pre-hook
→ flush / freeze DB

Snapshot
→ capture PV

Post-hook
→ resume DB
```

---

### **4. External databases must have their own backup**

This is crucial.

Suppose AKS connects to:

```text
Azure Database for PostgreSQL
```

The database is not inside the AKS cluster.

Therefore:

```text
AKS backup
≠ database backup
```

I need a separate backup/DR strategy for that database.

The same applies to:

```text
Azure SQL
Cosmos DB
Blob Storage
Redis where state matters
Service Bus/message state where required
```

---

### **5. Secrets and Key Vault**

If secrets are stored only in:

```text
Azure Key Vault
```

I would protect Key Vault through:

```text
soft delete
purge protection
RBAC
recovery procedures
```

rather than treating Kubernetes backup as the Key Vault backup.

If the application stores Kubernetes-native Secrets that are required for recovery, I would decide explicitly whether to include them in the AKS backup.

Azure Backup for AKS currently exposes an **Include Secrets** option in its resource-selection configuration. ([Microsoft Learn][5])

---

### **6. Infrastructure should normally be rebuilt, not restored from backup**

For the AKS infrastructure itself:

```text
VNet
AKS cluster
node pools
ACR
Private Endpoints
role assignments
monitoring configuration
```

my primary recovery source should ideally be:

```text
Terraform
+
Git
```

So recovery becomes:

```text
Terraform apply
      ↓
New AKS cluster
      ↓
GitOps deploys workloads
      ↓
Restore persistent/application state
```

That is generally cleaner than treating every piece of infrastructure as something that must be restored from a snapshot.

---

### **7. GitOps repository is part of recoverability**

If I use Argo CD:

```text
Git
 ↓
Argo CD
 ↓
AKS
```

Git contains much of the desired state.

So I also protect:

```text
Git repository
Helm charts
environment values
Terraform code
pipeline configuration
```

through the source-control platform's own resilience/backup procedures.

---

### **8. Container images**

If a disaster destroys the environment, I still need the application artifact.

```text
Git commit
   ↓
container build
   ↓
ACR image
```

So I need either:

```text
resilient/replicated registry strategy
```

or the proven ability to rebuild the exact artifact reproducibly.

Do not assume AKS Backup is backing up the images stored in ACR.

---

### **Production recovery model**

```text
Terraform
→ recreate Azure infrastructure

GitOps
→ recreate desired Kubernetes configuration

AKS Backup
→ recover Kubernetes objects + supported PV data

Database backup/replication
→ recover external databases

Key Vault protections
→ recover secrets/keys

ACR/artifact strategy
→ recover deployable images
```

> **In an interview, I would say:**
> “I don't treat AKS backup as simply backing up the cluster VM nodes. Nodes are disposable. I protect the Kubernetes objects required to reconstruct the application, especially anything not fully represented in Git, and I back up persistent volumes containing application state. Any database or storage service outside AKS needs its own backup and DR strategy. Infrastructure should ideally be recreated from Terraform and applications redeployed through GitOps, while Azure Backup for AKS restores cluster state and supported persistent volumes.”

**Memory line:**
**AKS nodes are replaceable; configuration and persistent business data are what matter.**

**Interview trap:**
Do not spend your backup strategy protecting ephemeral pods or nodes while forgetting the **PVCs and external database**.

**Keywords:**
AKS Backup, Kubernetes state, persistent volume, Azure Disk, Azure Files, GitOps, Terraform, application-consistent backup

**Likely follow-ups:**

* Do AKS worker nodes need backup?
* Does AKS Backup protect Azure SQL?
* How would you recover an AKS cluster into another region?
* What is the difference between GitOps recovery and backup recovery?

### **T12-H06. How would you protect critical data from ransomware?**

**Answer:**
I would assume ransomware may compromise not just the workload but also an administrator account, so I need **independent, immutable, recoverable copies that the compromised production identity cannot easily delete**. I would combine Azure Backup with soft delete, vault immutability, Multi-User Authorization using Resource Guard, least privilege, isolated backup administration, security monitoring, and regular clean-restore testing. Microsoft specifically recommends MUA and Resource Guard to protect critical backup operations from rogue administrators. ([Microsoft Learn][6])

### **Defense model**

```text
Production Data
      ↓
Backups
      ↓
Independent recovery copies
      ↓
Soft Delete
      +
Immutability
      +
MUA / Resource Guard
      ↓
Attacker cannot easily destroy recovery path
```

---

### **1. Keep historical recovery points**

Replication alone isn't enough.

If ransomware encrypts:

```text
Primary data
```

and that change replicates:

```text
Primary encrypted
      ↓
replication
      ↓
Secondary encrypted
```

then redundancy has preserved the attack.

I need historical clean recovery points:

```text
Day -7
Day -6
Day -5
...
Attack
```

so I can restore from the last known clean state.

---

### **2. Use soft delete**

If an attacker or administrator deletes the backup:

```text
Delete backup
     ↓
Soft-deleted
     ↓
Still recoverable
```

Azure Backup's ransomware guidance recommends keeping soft delete enabled because otherwise deleted backup data might not be recoverable. ([Microsoft Learn][6])

---

### **3. Use immutable backups**

For critical systems I would enable vault immutability where supported.

Conceptually:

```text
Recovery Point
      ↓
Immutable retention
      ↓
Cannot be modified/deleted before retention allows
```

This protects against:

```text
Ransomware
Compromised admin
Accidental deletion
```

because the backup copy isn't simply another writable piece of production data.

---

### **4. Use Multi-User Authorization**

This is one of the strongest Azure-specific answers.

For dangerous operations such as:

```text
Disable soft delete
Reduce retention
Delete protection
Disable immutability
```

I would use:

```text
Backup Administrator
       +
Resource Guard authorization
       ↓
Critical operation allowed
```

instead of one compromised administrator being able to destroy backups alone.

Azure Backup MUA uses **Resource Guard** to add authorization protection around these critical operations. ([Microsoft Learn][7])

---

### **5. Separate backup privileges from production privileges**

Bad:

```text
Production Admin
     ↓
Owner
     ↓
Production + Backup + Resource Guard
```

One compromised account can destroy everything.

Better:

```text
Production Ops
→ manage workloads

Backup Admin
→ manage backups

Security/Recovery authority
→ Resource Guard
```

with separate scopes and PIM/JIT where appropriate.

This implements:

```text
separation of duties
```

and reduces blast radius.

---

### **6. Secure credentials and identities**

I would also reduce the chance ransomware reaches Azure control-plane resources by using:

```text
MFA
PIM
Conditional Access
Managed Identity
Workload Identity
OIDC
least-privilege Azure RBAC
```

and avoiding long-lived admin/service-principal secrets.

Because:

```text
Compromised VM
```

should not automatically mean:

```text
Permission to delete every backup vault
```

---

### **7. Protect backup networking and storage paths**

Where supported and appropriate:

```text
Private Endpoints
restricted public access
firewall controls
```

can reduce unnecessary exposure.

But network isolation alone is not enough.

The critical controls are still:

```text
authorization
immutability
independent recovery
```

---

### **8. Detect the attack early**

I would monitor for:

```text
mass file modifications
unusual encryption behavior
Defender alerts
mass backup deletion attempts
backup policy changes
retention reduction
RBAC changes
unusual privileged sign-ins
```

using:

```text
Defender for Cloud
Defender for Endpoint
Azure Monitor
Activity Log
Microsoft Sentinel
```

depending on the environment.

---

### **9. Restore from the last clean point—not simply the newest**

During ransomware recovery:

```text
Determine attack start
       ↓
Find recovery point before compromise
       ↓
Restore into isolated environment
       ↓
Scan / validate
       ↓
Recover production
```

Microsoft's ransomware recovery guidance specifically recommends reviewing the incident timeline and choosing the last healthy recovery point from before the impact. ([Microsoft Learn][6])

I would not immediately restore:

```text
latest recovery point
```

because it may already contain encrypted or malicious data.

---

### **10. Regularly prove backups are usable**

The ransomware strategy is incomplete if:

```text
Backup Job = Successful
```

but:

```text
Restore = never tested
```

I would regularly restore representative workloads into isolated environments and verify:

```text
files open
database starts
application works
credentials function
malware is absent
```

---

### **Layered architecture**

```text
Identity protection
       ↓
Least privilege
       ↓
Defender detection
       ↓
Backup
       ↓
Soft delete
       ↓
Immutable vault
       ↓
MUA / Resource Guard
       ↓
Isolated restore testing
```

> **In an interview, I would say:**
> “For ransomware I wouldn't rely on replication because ransomware can replicate too. I would keep historical Azure Backup recovery points and protect them using soft delete, immutability and Multi-User Authorization with Resource Guard so even a compromised backup administrator can't easily destroy the recovery path. I would separate production and backup privileges, use PIM and least privilege, monitor destructive backup operations, and during an incident restore the last known clean point into an isolated environment before returning it to production.”

**Memory line:**
**Ransomware protection means attackers must not be able to encrypt production and destroy your recovery copies too.**

**Interview trap:**
Geo-replication is **not ransomware protection by itself**—encrypted/corrupted data can also be replicated.

**Keywords:**
Ransomware, immutable backup, soft delete, MUA, Resource Guard, separation of duties, clean recovery point

**Likely follow-ups:**

* What is Resource Guard?
* Why doesn't replication protect against ransomware?
* How would you choose the recovery point after an attack?
* Why should backup administrators be separate from production administrators?

### **T12-H07. What tradeoffs exist between active-active and active-passive architectures?**

**Answer:**
**Active-active** gives lower failover time and makes productive use of both regions, but it is significantly harder to design because both regions simultaneously serve traffic and often need complex multi-region data consistency. **Active-passive** is simpler and usually cheaper, but failover takes longer and the standby environment has a higher risk of configuration drift or insufficient capacity because it isn't continuously exercised. Microsoft currently characterizes active-active as appropriate for the lowest RTO, while active-passive is useful when state or cost constraints make simultaneous regional operation impractical. ([Microsoft Learn][8])

### **Core architecture**

Active-active:

```text
             Front Door
              /      \
             /        \
            ↓          ↓
        Region A    Region B
          ACTIVE      ACTIVE
```

Active-passive:

```text
             Front Door
                 |
                 ↓
              Region A
               ACTIVE

              Region B
              PASSIVE
```

---

### **1. RTO**

#### Active-active

Both regions already serve traffic:

```text
Region A fails
      ↓
Stop routing to A
      ↓
Region B already running
```

Therefore RTO can be:

```text
seconds / very low
```

depending on health detection and application design.

#### Active-passive

Failover may require:

```text
detect outage
      ↓
activate/scale secondary
      ↓
database failover
      ↓
traffic switch
      ↓
warm caches
```

so RTO is normally higher.

Microsoft's current multi-region guidance describes active-active as offering the lowest RTO, while active-passive tolerates activation time in the secondary. ([Microsoft Learn][8])

---

### **2. Cost**

Active-active usually requires:

```text
Region A full capacity
+
Region B full capacity
```

so infrastructure cost is higher.

However, both environments are actually used.

Active-passive can run:

```text
Primary = full capacity
Secondary = reduced capacity
```

and scale the secondary during failover.

This reduces cost but introduces:

```text
scale-up delay
```

which directly affects RTO.

Microsoft's current App Service reference classifies active-active as high-cost and active-passive as medium-cost. ([Microsoft Learn][9])

---

### **3. Operational risk**

Active-active has more architectural complexity:

```text
both regions active
+
global traffic routing
+
cross-region data coordination
+
deployments to both regions
+
state consistency
```

But one advantage is:

```text
Both regions are continuously exercised
```

so failures and drift tend to be discovered earlier.

Active-passive has:

```text
simpler request model
```

but the passive region may become stale:

```text
old config
wrong NSG
expired certificate
insufficient capacity
broken DNS
```

because nobody is normally using it.

Microsoft's network guidance explicitly notes higher drift/untested-configuration risk in passive regions. ([Microsoft Learn][8])

---

### **4. Data consistency**

This is often the hardest part of active-active.

If both regions accept writes:

```text
Region A writes customer X
Region B writes customer X
```

the datastore must answer:

```text
Which value wins?
How are conflicts handled?
What consistency model exists?
```

This might require:

```text
Cosmos DB multi-region writes
partitioning
conflict resolution
single-write region
eventual consistency
```

depending on the application.

Active-passive is often simpler:

```text
Primary region
→ accepts writes

Secondary
→ receives replication
```

which avoids simultaneous writers.

---

### **5. User latency**

Active-active can route:

```text
India users
→ nearby active region

Europe users
→ nearby active region
```

and improve latency.

Active-passive sends everybody to:

```text
one primary region
```

during normal operation, so geographically distant users may have higher latency.

---

### **6. Capacity planning**

With active-active:

```text
Region A = 50%
Region B = 50%
```

if one region fails:

```text
remaining region
→ suddenly needs 100%
```

So I still need spare capacity or fast autoscaling.

Active-active does **not** mean I can size each region only for its normal half-load without considering failure.

For active-passive:

```text
Passive region
```

might be intentionally undersized, which means I must include scale-up time in RTO.

---

### **7. Deployment risk**

In active-active, a bad release deployed simultaneously to both regions can remove the redundancy:

```text
Bad v2
→ Region A
→ Region B
→ global outage
```

I would normally use progressive deployment:

```text
Deploy Region B
      ↓
Validate
      ↓
shift some traffic
      ↓
deploy Region A
```

or another safe rollout strategy.

Multi-region reliability adds operational complexity, so deployment coordination matters. ([Microsoft Learn][10])

---

### **When I would choose each**

#### Active-active

Choose when:

```text
Very low RTO
Global users
Both regions can independently serve
Application supports multi-region state
Cost is acceptable
```

#### Active-passive

Choose when:

```text
Cost sensitivity
Single-writer database requirement
Moderate RTO
Legacy workload
Simpler operations desired
```

Microsoft's current guidance similarly recommends active-passive where strict write-region requirements or state constraints make active-active difficult. ([Microsoft Learn][8])

---

### **Interview comparison**

| Area                   | Active-active    | Active-passive           |
| ---------------------- | ---------------- | ------------------------ |
| RTO                    | Lowest           | Higher                   |
| Cost                   | Higher           | Lower                    |
| State design           | Harder           | Simpler                  |
| Normal utilization     | Both regions     | Primary mainly           |
| Drift risk             | Lower            | Higher                   |
| Global latency         | Better potential | Primary-region dependent |
| Failover activation    | Minimal          | More steps               |
| Operational complexity | Highest          | Moderate                 |

> **In an interview, I would say:**
> “Active-active minimizes RTO because both regions are already serving traffic, and it can improve latency for global users, but it costs more and makes data consistency, deployment coordination and capacity planning significantly harder. Active-passive usually has a simpler single-writer model and can run a smaller standby environment, so it costs less, but failover takes longer and the passive environment can drift because it isn't continuously exercised. I choose based on RTO/RPO, workload state model, user geography, cost and operational maturity.”

**Memory line:**
**Active-active buys faster recovery with money and complexity; active-passive saves cost but spends recovery time.**

**Interview trap:**
Do not choose active-active just because it sounds “more highly available.” Many stateful applications cannot safely support multi-region active writes without additional architecture.

**Keywords:**
Active-active, active-passive, RTO, state consistency, cost, capacity, drift, global routing

**Likely follow-ups:**

* Can active-active still have a single-write database?
* How much capacity should each active region have?
* How would you deploy safely to two active regions?
* When would active-passive be preferable even for an important application?

### **T12-H08. How would you prove that your disaster-recovery plan actually meets its required RTO and RPO?**

**Answer:**
I would prove it through **repeated, measured disaster-recovery exercises**, not architecture diagrams or successful replication status. I would simulate the agreed failure scenario, recover the application using the actual runbook, measure when the service becomes usable again for RTO, identify the timestamp of the newest successfully recovered business data for RPO, and compare both measurements with the documented targets.

Azure Site Recovery supports test failovers specifically so DR can be validated without disrupting ongoing production or replication. ([Microsoft Learn][11])

### **Evidence model**

```text
Required:
RTO ≤ 15 min
RPO ≤ 5 min

          ↓

Run real DR drill

          ↓

Measure:
Actual RTO = ?
Actual RPO = ?

          ↓

Pass / Fail
```

---

### **1. Define exactly what "recovered" means**

I would not define RTO as:

```text
VM started
```

The service is recovered when the **business application is usable**.

For example:

```text
Frontend reachable
      ↓
Login works
      ↓
API works
      ↓
DB reads/writes work
      ↓
Key Vault works
      ↓
Critical transaction succeeds
```

Only then do I stop the RTO timer.

---

### **2. Record the disaster start time**

Suppose:

```text
10:00:00
Primary region declared unavailable
```

That is:

```text
T0
```

Then execute the documented recovery path:

```text
failover
   ↓
database recovery
   ↓
application recovery
   ↓
traffic switch
   ↓
validation
```

---

### **3. Measure actual RTO**

Suppose:

```text
10:00:00 → outage begins

10:04:00 → data tier ready

10:07:00 → application ready

10:09:30 → Front Door/DNS sends traffic

10:11:20 → end-to-end business transaction passes
```

Then:

```text
Actual RTO
=
11 minutes 20 seconds
```

If requirement is:

```text
RTO ≤ 15 minutes
```

then:

```text
PASS
```

I would use timestamps from:

```text
DR automation
Azure Monitor
ASR jobs
traffic-management logs
application telemetry
synthetic tests
```

rather than relying only on someone writing down approximate times.

---

### **4. Measure actual RPO**

Suppose disaster occurs at:

```text
10:00:00
```

After recovery, the newest committed transaction present is:

```text
09:57:40
```

Then:

```text
Actual data loss
=
2 minutes 20 seconds
```

So:

```text
Actual RPO ≈ 2m20s
```

If requirement is:

```text
RPO ≤ 5 min
```

then:

```text
PASS
```

This is much stronger than saying:

```text
"We configured async replication,
so RPO should be fine."
```

I need to verify the **actual recovered business data**.

---

### **5. Seed known test transactions**

A practical technique is to generate timestamped synthetic records before and during the drill.

Example:

```text
09:55 transaction-1955
09:56 transaction-1956
09:57 transaction-1957
09:58 transaction-1958
09:59 transaction-1959
10:00 disaster
```

After recovery:

```text
transaction-1958 present
transaction-1959 absent
```

Now I know roughly where the recovery point actually landed.

This gives concrete RPO evidence.

---

### **6. Test the real dependency chain**

A DR test should include:

```text
Compute
Networking
DNS
Database
Storage
Key Vault
Managed identities
Private Endpoints
Certificates
Queues
External dependencies
Monitoring
```

Otherwise I might prove:

```text
VM recovery RTO
```

but not:

```text
application RTO
```

---

### **7. Test under realistic conditions**

If production normally receives:

```text
10,000 requests/minute
```

I should not declare success just because the secondary can serve:

```text
one curl request
```

I need to verify:

```text
capacity
latency
autoscaling
connection pools
database performance
```

under representative load.

---

### **8. Use isolated test failover where possible**

With ASR:

```text
Production
   ↓
replication continues

Test failover
   ↓
isolated VNet
```

Microsoft states that a test failover validates replication and DR without impacting ongoing replication or the production environment. ([Microsoft Learn][11])

That lets me run the exercise regularly instead of saving DR testing only for rare maintenance windows.

---

### **9. Record evidence**

For each drill I would generate a report containing:

```text
Scenario tested
Date/time
Required RTO
Actual RTO
Required RPO
Actual RPO
Recovery point used
Recovery steps
Failed dependencies
Manual interventions
Traffic-switch duration
Issues discovered
Remediation owner
```

For example:

```text
Required RTO: 15m
Actual RTO:   11m20s   PASS

Required RPO: 5m
Actual RPO:   2m20s    PASS
```

That is proof.

---

### **10. Repeat after changes**

One successful drill does not permanently prove DR.

Changes to:

```text
networking
database
application
Key Vault
Terraform
DNS
CI/CD
```

can quietly break recovery.

Therefore:

```text
Architecture change
      ↓
DR validation
```

and scheduled drills should continue.

Active-passive environments especially need regular validation because unused standby infrastructure can drift. Microsoft's current multi-region guidance explicitly warns of configuration drift and recommends regular failover testing. ([Microsoft Learn][8])

---

### **11. Failure is valuable**

Suppose the drill produces:

```text
RTO target = 15 min
Actual = 28 min
```

I would break down where those 28 minutes went:

```text
Detection           2 min
DB failover          5 min
AKS scale-up        12 min  ← bottleneck
DNS                  3 min
Validation           6 min
```

Now I have a concrete engineering action:

```text
Pre-warm secondary AKS capacity
```

instead of guessing.

---

> **In an interview, I would say:**
> “I would prove RTO and RPO through measured DR drills. I start the timer when the defined disaster occurs and stop the RTO timer only when a real end-to-end business transaction succeeds in the recovery environment—not when a VM simply starts. For RPO, I compare the disaster timestamp with the newest valid transaction recovered, ideally using timestamped synthetic records. I would use ASR test failover or an equivalent isolated exercise, capture evidence from monitoring and recovery jobs, document actual versus target values, fix any bottlenecks, and repeat the drill regularly.”

**Memory line:**
**RTO/RPO are proven by timestamps and recovered business data, not by architecture diagrams.**

**Interview trap:**
`Replication healthy` does **not** prove either RTO or RPO.

**Keywords:**
DR drill, RTO measurement, RPO measurement, test failover, synthetic transaction, evidence, recovery validation

**Likely follow-ups:**

* When exactly should the RTO timer stop?
* How would you measure RPO objectively?
* What if DR works functionally but exceeds RTO?
* How frequently should DR tests be repeated?
