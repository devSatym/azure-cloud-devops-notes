### **T12-E06. What is Azure Site Recovery?**

**Answer:**
Azure Site Recovery, or **ASR**, is Azure’s managed **disaster-recovery orchestration and replication service**. It replicates supported workloads from a primary location to a secondary location and helps orchestrate **failover, recovery, testing, and failback** when the primary environment becomes unavailable. ([Microsoft Learn][1])

### **How it works**

For Azure VMs:

```text
Primary Azure Region
        │
        │ continuous replication
        ↓
Secondary Azure Region
        │
        │ disaster
        ↓
Failover
        ↓
VMs created/started from replicated data
```

ASR supports scenarios such as:

```text
Azure VM → another Azure region

VMware → Azure

Hyper-V → Azure

Physical servers → Azure
```

depending on the supported configuration. ([Microsoft Learn][1])

### **What Site Recovery manages**

ASR can help with:

```text
Replication
Failover
Test failover
Recovery points
Recovery plans
Failback
```

A **Recovery Plan** can also define the startup sequence of a multi-tier application.

For example:

```text
1. Database
      ↓
2. Backend/API
      ↓
3. Web tier
```

rather than starting every VM randomly. ([Microsoft Learn][2])

### **Production example**

Suppose:

```text
Primary: East US
Secondary: West US
```

Production VMs continuously replicate to the secondary region.

If East US becomes unavailable:

```text
Outage detected
      ↓
ASR failover
      ↓
Choose recovery point
      ↓
Secondary VMs start
      ↓
Network/traffic switched
      ↓
Application validated
```

When the primary environment becomes healthy again:

```text
Reprotect
   ↓
Failback
```

### **Site Recovery vs Azure Backup**

This distinction matters:

```text
Azure Backup
→ historical recovery points
→ protects data

Azure Site Recovery
→ replicates workloads
→ orchestrates DR and failover
```

Microsoft describes them as complementary BCDR services rather than replacements for each other. ([Microsoft Learn][1])

**Memory line:**
**Azure Site Recovery replicates workloads and orchestrates disaster-recovery failover/failback.**

**Interview trap:**
Do not say ASR is simply another backup service. Its main purpose is **workload replication and DR orchestration**.

**Keywords:**
Azure Site Recovery, ASR, replication, failover, failback, Recovery Plan, BCDR

### **T12-E07. What is a Recovery Services vault?**

**Answer:**
A Recovery Services vault is an Azure **management and storage entity used by services such as Azure Backup and Azure Site Recovery**. It stores backup recovery points and configuration/metadata required to manage protected workloads and DR operations. ([Microsoft Learn][3])

### **How it fits**

For Azure Backup:

```text
Azure VM
   ↓
Backup policy
   ↓
Azure Backup
   ↓
Recovery Services vault
   ↓
Recovery points
```

For supported Site Recovery scenarios:

```text
Primary workload
      ↓
Site Recovery
      ↓
Recovery Services vault
      ↓
Replication / recovery configuration
```

### **What you manage through the vault**

A Recovery Services vault can provide management for things such as:

```text
Backup policies
Recovery points
Restore operations
Protected items
Backup jobs
Site Recovery configuration
Monitoring
Security settings
```

Microsoft currently uses Recovery Services vaults for workloads including Azure VMs, SQL Server/SAP HANA in Azure VMs, Azure Files, and various on-premises backup scenarios. ([Microsoft Learn][4])

### **Production example**

Suppose I protect ten production VMs.

```text
Recovery Services Vault: rsv-prod
             │
             ├── Backup Policy
             ├── VM01 recovery points
             ├── VM02 recovery points
             └── ...
```

From the vault I can perform operations such as:

```text
Backup now
Restore
Change retention
Monitor backup jobs
```

### **Recovery Services vault vs Backup vault**

A useful modern distinction is that Azure Backup now has **multiple vault types**.

```text
Recovery Services vault
→ traditional workloads such as Azure VM backup
→ Azure Site Recovery support

Backup vault
→ used for several newer Azure Backup workloads
```

So I would not say every Azure Backup datasource necessarily uses a Recovery Services vault. ([Microsoft Learn][5])

### **Security**

For production backups I would also consider:

```text
Soft delete
Immutability
Encryption
RBAC
Multi-user authorization where required
```

Microsoft currently supports immutable vault protections to help protect recovery points from premature deletion and ransomware scenarios. ([Microsoft Learn][6])

**Memory line:**
**Recovery Services vault is the management container for many Azure Backup and Site Recovery operations.**

**Interview trap:**
Do not assume a Recovery Services vault is just an ordinary Storage Account that you manually manage.

**Keywords:**
Recovery Services vault, Recovery Points, Azure Backup, Site Recovery, backup policy, restore

### **T12-M01. What is the difference between backup and disaster recovery?**

**Answer:**
Backup and disaster recovery solve related but different problems. **Backup protects data by keeping historical recovery points**, while **disaster recovery protects business-service continuity by restoring or failing over an application after a major outage**.

### **Core distinction**

```text
Backup
→ "Can I recover my data?"

DR
→ "Can I recover my service?"
```

For example:

```text
User accidentally deletes database records
        ↓
Backup / point-in-time restore
```

versus:

```text
Entire Azure region unavailable
        ↓
Disaster Recovery
        ↓
Run application in secondary region
```

### **Comparison**

| Area                                    | Backup                    | Disaster Recovery                               |
| --------------------------------------- | ------------------------- | ----------------------------------------------- |
| Primary goal                            | Recover data              | Restore service                                 |
| Typical event                           | Deletion/corruption       | Site/region outage                              |
| Usually measured by                     | Recovery points/retention | RTO + RPO                                       |
| Azure example                           | Azure Backup              | Azure Site Recovery / multi-region architecture |
| Requires running secondary environment? | Usually no                | Often yes or partially prepared                 |
| Traffic failover                        | No                        | Usually required                                |

### **Why replication alone is not backup**

Suppose I have two replicated databases:

```text
Primary
   ↓ replication
Secondary
```

Someone executes:

```sql
DELETE FROM Customers;
```

Replication can quickly copy the bad operation:

```text
Primary data deleted
      ↓
Secondary data deleted
```

So replication/DR does not necessarily give me a historical clean recovery point.

That is why a strong design may include:

```text
HA
+
DR replication
+
Backups
```

rather than choosing only one.

### **Production example**

For an e-commerce system:

```text
Azure Backup
→ protect recoverable historical data

Cross-region database replication
→ meet RPO target

Secondary application environment
→ meet RTO target

Front Door / DNS failover
→ redirect users
```

All of these contribute to resilience but solve different parts of the problem.

### **Important distinction**

Microsoft describes Azure Backup as keeping data safe and recoverable, while Site Recovery focuses on keeping applications/workloads available by replicating to a secondary location and orchestrating failover/failback. ([Microsoft Learn][1])

> **In an interview, I would say:**
> “Backup is primarily about recovering data from historical recovery points after deletion, corruption, or other data-loss events. Disaster recovery is about restoring the complete application after a major outage, including compute, networking, dependencies, data and traffic routing. Replication does not replace backup because logical corruption or deletion can replicate to the secondary environment, so production systems often need both.”

**Memory line:**
**Backup restores data; DR restores the business service.**

**Interview trap:**
Do not say geo-replication means backups are unnecessary.

**Keywords:**
Backup, disaster recovery, recovery point, replication, RTO, RPO, failover

**Likely follow-ups:**

* Why doesn't replication replace backup?
* Can Azure Backup alone satisfy a 15-minute RTO?
* How are RPO and backup frequency related?
* Would you use both Azure Backup and Site Recovery?

### **T12-M02. What is the difference between Availability Zones and multi-region deployment?**

**Answer:**
Availability Zones provide resiliency against **datacenter or zone failures inside a single Azure region**, while multi-region deployment places the workload in **two or more Azure regions** to protect against an entire regional outage and potentially serve geographically distributed users. ([Microsoft Learn][7])

### **Architecture**

Availability Zones:

```text
Azure Region: East US
│
├── Zone 1
│    └── Application instance
│
├── Zone 2
│    └── Application instance
│
└── Zone 3
     └── Application instance
```

All remain:

```text
inside one Azure region
```

Multi-region:

```text
East US
├── App
└── Data
      │
      │ cross-region replication
      ↓
West US
├── App
└── Data
```

### **What each protects against**

```text
Availability Zones
→ datacenter failure
→ power/cooling/networking failure in one zone
```

Azure Availability Zones have independent power, cooling and networking within the region. ([Microsoft Learn][8])

But:

```text
Whole region unavailable
        ↓
Availability Zones alone may not help
```

Microsoft explicitly notes that Availability Zones **do not protect against a complete regional outage**. ([Microsoft Learn][8])

For that:

```text
Multi-region architecture
→ another Azure region remains available
```

---

### **HA vs DR perspective**

A useful interview model is:

```text
Multiple zones
→ primarily regional high availability

Multiple regions
→ primarily regional-disaster resilience
```

Although multi-region designs can also provide high availability and performance benefits.

---

### **Latency**

Zones within one region are designed for relatively low-latency communication.

```text
Zone 1 ↔ Zone 2
→ comparatively low latency
```

Regions may be geographically far apart:

```text
East US ↔ West Europe
→ much higher latency
```

This matters especially for synchronous database replication.

Microsoft notes that inter-region latency can make synchronous replication impractical for many workloads. ([Microsoft Learn][7])

---

### **Cost and complexity**

Availability-zone design:

```text
Lower complexity
Lower cost than full multi-region
```

usually.

Multi-region:

```text
Duplicate infrastructure
Cross-region networking
Data replication
Global traffic routing
Failover logic
Operational complexity
```

so it generally costs more and is harder to operate. ([Microsoft Learn][7])

### **Production architecture**

For a mission-critical workload, I might combine both:

```text
Region A
├── Zone 1
├── Zone 2
└── Zone 3
       │
       │ replication
       ↓
Region B
├── Zone 1
├── Zone 2
└── Zone 3
```

This provides:

```text
Zone failure resilience
        +
Region failure resilience
```

Microsoft's current guidance specifically says mission-critical workloads should consider both multi-zone and multi-region designs. ([Microsoft Learn][7])

> **In an interview, I would say:**
> “Availability Zones are separate datacenter groups within one Azure region, so they protect primarily against a zone or datacenter failure while maintaining relatively low latency. A multi-region architecture deploys the workload into separate Azure regions, so it can survive an entire regional outage. Multi-region gives stronger geographic resiliency but adds more cost, replication latency, traffic-management complexity, and operational overhead. For mission-critical systems I may use multiple zones inside each of multiple regions.”

**Memory line:**
**Zones protect within a region; multi-region protects across regions.**

**Interview trap:**
Do not say that three Availability Zones mean the application can survive the loss of the entire Azure region.

**Keywords:**
Availability Zones, multi-region, zone failure, regional outage, HA, DR, latency, redundancy

**Likely follow-ups:**

* Can Availability Zones survive an Azure region outage?
* Why not deploy every application multi-region?
* What would you use to route traffic between regions?
* Would you combine multi-zone and multi-region designs?
