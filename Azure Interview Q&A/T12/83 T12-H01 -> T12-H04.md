### **T12-H01. Design a solution with an RTO of 15 minutes and an RPO of 5 minutes.**

**Answer:**
With an **RTO of 15 minutes**, I cannot depend on rebuilding the entire environment after a disaster. I need the secondary environment **already provisioned or warm enough to become production quickly**. With an **RPO of 5 minutes**, the data layer must replicate or back up frequently enough that a regional failure loses no more than about five minutes of committed data.

My design would therefore be a **two-region architecture with pre-provisioned application capacity, global traffic failover, and continuous cross-region data replication**.

### **Reference architecture**

```text
                         Users
                           |
                           v
                  Azure Front Door
                   + WAF + probes
                    /           \
                   /             \
                  v               v
        Primary Region       Secondary Region
        --------------       ----------------
        App / AKS /          App / AKS /
        App Service          App Service
             |                    |
             +---------+----------+
                       |
                Replicated data
                       |
              Azure SQL / other
             geo-capable datastore
```

The critical point is:

```text
Secondary compute
→ already deployed

Application version
→ already synchronized

Networking
→ already configured

Secrets / identity
→ already available

Database
→ continuously replicated
```

not:

```text
Region fails
   ↓
Start Terraform
   ↓
Wait 40 minutes
```

because that would risk missing the 15-minute RTO.

---

### **1. Translate the business objectives**

I would first define:

```text
RTO = 15 minutes
→ users must regain usable service within 15 minutes

RPO = 5 minutes
→ recovered data should be no more than 5 minutes behind
```

I would treat those as **measurable requirements**, not just architecture labels.

---

### **2. Deploy into two regions**

For example:

```text
Primary:   East US
Secondary: Central US
```

Each region contains the necessary application stack.

I would generally make each region internally zone-resilient as well:

```text
Region A
├── Zone 1
├── Zone 2
└── Zone 3

Region B
├── Zone 1
├── Zone 2
└── Zone 3
```

That lets Availability Zones handle smaller failures while the second region handles a full regional disaster.

---

### **3. Use Azure Front Door for global HTTP failover**

For a web application:

```text
Users
  ↓
Azure Front Door
  ↓
Health probes
  ↓
Healthy region
```

I can use either:

```text
Active-active
```

or:

```text
Active-passive
```

For a strict 15-minute RTO, even an active-passive secondary should already exist and have enough capacity to scale quickly.

Microsoft's current multi-region guidance uses Azure Front Door health probes to detect an unhealthy regional origin and route requests to the remaining healthy region. In active-active, both regions normally serve traffic; in active-passive, the secondary takes over after the primary fails. ([Microsoft Learn][1])

For the strongest RTO:

```text
Active-active
```

is attractive because the secondary is already:

```text
running
tested
receiving traffic
capacity validated
```

so there is less to activate during a disaster.

---

### **4. Design the data layer specifically for RPO ≤ 5 minutes**

This is where RPO is really won or lost.

I need:

```text
Primary data
    ↓
continuous cross-region replication
    ↓
Secondary data
```

For example, with an Azure SQL workload I could use an appropriate geo-replication/failover-group architecture.

But I would **not simply claim that enabling geo-replication guarantees an RPO of five minutes**.

I would verify:

```text
Replication mode
Replication lag
Failover behavior
Data-service guarantees
Observed lag under peak load
```

and prove during DR tests that:

```text
actual recovered-data age <= 5 minutes
```

---

### **5. Replicate more than the database**

A real application usually also depends on:

```text
Blob/object data
Certificates
Key Vault
DNS
Container images
Configuration
Queues/messages
Infrastructure configuration
```

So I would map all stateful dependencies.

Example:

```text
Application state
│
├── SQL
│    └── geo replication
│
├── Blob Storage
│    └── geo-redundant strategy
│
├── Container images
│    └── registry availability/replication strategy
│
└── Infrastructure
     └── Terraform
```

A secondary web server with no access to the required data is not a DR solution.

---

### **6. Keep deployments synchronized**

CI/CD should deploy compatible application versions to both regions:

```text
Git
 ↓
CI
 ↓
Artifact
 ↓
Primary region
+
Secondary region
```

I want:

```text
Primary version   = v3.8
Secondary version = v3.8
```

not:

```text
Primary = v3.8
Secondary = v2.9
```

when failover occurs.

---

### **7. Preconfigure networking and identity**

Before a disaster occurs, I would ensure the secondary already has:

```text
VNets/subnets
Private Endpoints
Private DNS
NSGs/firewall rules
Managed identities
Workload identities
Key Vault permissions
certificates
monitoring
```

Otherwise the actual RTO becomes:

```text
Failover time
+
network troubleshooting
+
DNS debugging
+
permission debugging
```

and 15 minutes disappears very quickly.

---

### **8. Automate the failover runbook**

Example:

```text
0 min
Region failure detected

1–3 min
Confirm incident / automatic health detection

3–6 min
Data-service failover

4–8 min
Front Door routes users to secondary

8–12 min
Application/dependency validation

< 15 min
Service declared operational
```

The exact timeline depends on the workload, but this is the type of budget I would design and repeatedly test against.

---

### **9. Monitor both RTO and RPO**

I would record:

```text
Failure timestamp
Recovery initiation timestamp
Application healthy timestamp
Newest recovered-data timestamp
```

Then calculate:

```text
Actual RTO
=
application usable time
-
failure time
```

and:

```text
Actual RPO
=
failure time
-
newest successfully recovered data
```

Architecture alone does not prove the objective.

---

### **10. Backups still remain necessary**

Cross-region replication handles availability and low RPO, but I would still maintain backups.

Why?

```text
Bad DELETE
    ↓
Primary corrupted
    ↓
Replication
    ↓
Secondary corrupted
```

A historical backup can protect against logical corruption or ransomware scenarios that replication simply copies.

---

> **In an interview, I would say:**
> “For a 15-minute RTO and 5-minute RPO, I would deploy the application into two Azure regions rather than rebuilding the secondary after failure. Azure Front Door would provide health-based global routing, and the secondary application stack would already be deployed and capacity-ready. The stateful tier would use continuous cross-region replication capable of meeting a five-minute data-loss requirement. I would also preconfigure networking, identity, secrets and monitoring in both regions, deploy identical application versions through CI/CD, and automate the failover runbook. Most importantly, I would regularly run DR drills and measure actual recovery time and recovered-data age to prove that RTO ≤15 minutes and RPO ≤5 minutes.”

**Memory line:**
**15-minute RTO needs a ready secondary; 5-minute RPO needs continuous, tested data replication.**

**Interview trap:**
Do not claim that having a backup every five minutes automatically gives a 15-minute RTO—the restore process itself may take much longer.

**Keywords:**
RTO, RPO, Azure Front Door, multi-region, geo-replication, warm standby, active-active, DR testing

**Likely follow-ups:**

* Would you choose active-active or active-passive?
* How would you prove the database really meets a five-minute RPO?
* What if the secondary region takes 20 minutes to scale?
* Why do you still need backups if you have geo-replication?

### **T12-H02. How would you design a web application to survive an entire Azure region outage?**

**Answer:**
I would design the application as **multi-region from the start**. I would use Azure Front Door as the global HTTP entry point, deploy independent application stacks in at least two regions, make each region able to serve production traffic, replicate stateful data across regions, and ensure networking, identity, secrets, monitoring, and deployment pipelines work independently in both regions.

Microsoft's current architecture guidance describes both active-active and active-passive multi-region App Service designs using Azure Front Door. Front Door health probes detect an unavailable origin and route traffic to the healthy region. ([Microsoft Learn][1])

### **Architecture**

```text
                              Internet
                                 |
                                 v
                         Azure Front Door
                         + WAF + TLS
                       + health probes
                         /          \
                        /            \
                       v              v
              Region A              Region B
          ┌────────────────┐   ┌────────────────┐
          │ Web/API        │   │ Web/API        │
          │ AKS/AppService │   │ AKS/AppService │
          └───────┬────────┘   └───────┬────────┘
                  │                    │
                  └────────┬───────────┘
                           v
                    Replicated Data
```

---

### **1. Remove the region as a single point of failure**

Bad:

```text
Front Door
    ↓
East US only
```

Front Door itself can be healthy while the only application region is gone.

Better:

```text
Front Door
   ├── Region A
   └── Region B
```

Both regions need independent:

```text
compute
networking
application deployment
identity
dependencies
monitoring
```

---

### **2. Choose active-active or active-passive**

#### **Active-active**

```text
Front Door
  ├── Region A ← traffic
  └── Region B ← traffic
```

Advantages:

```text
Very low failover activation work
Both regions continuously tested
Capacity already being exercised
Better geographic latency
```

During regional outage:

```text
Region A fails
     ↓
Front Door health probe detects failure
     ↓
Region A removed from routing
     ↓
Region B receives traffic
```

Microsoft's current Azure Architecture Center guidance describes this exact pattern. ([Microsoft Learn][1])

---

#### **Active-passive**

```text
Front Door
  ↓
Region A

Region B
→ standby
```

Using Front Door priorities:

```text
Region A priority = 1
Region B priority = 2
```

If the priority-1 origin becomes unhealthy, Front Door can route traffic to the next healthy priority. ([Microsoft Learn][2])

This can reduce cost but creates more failover risk:

```text
secondary scale-up time
cold caches
less frequently exercised capacity
```

---

### **3. Make the application stateless where possible**

I want:

```text
Request
→ any healthy application instance
```

not:

```text
User session exists only
inside one VM's memory
```

For session or application state, I would use an appropriate external resilient datastore.

That makes:

```text
Region A request
```

and:

```text
Region B request
```

behave consistently.

---

### **4. Replicate the database**

A multi-region frontend with a single-region database is still:

```text
single-region architecture
```

in practice.

I need a data strategy such as:

```text
Primary database
       ↓
cross-region replication
       ↓
secondary database
```

The exact Azure technology depends on requirements:

```text
Azure SQL
Cosmos DB
PostgreSQL
Storage
etc.
```

I would design from required:

```text
RPO
RTO
consistency
write model
latency
cost
```

rather than selecting multi-region blindly.

---

### **5. Handle storage and other state**

I would identify:

```text
Uploads
Blob data
Queues
Caches
Search indexes
Certificates
Secrets
Container artifacts
```

and decide how each survives a regional loss.

For storage-backed data, Microsoft notes that GRS/GZRS cross-region replication is asynchronous, so potential replication lag must be included in the RPO design. ([Microsoft Learn][1])

---

### **6. Make origins inaccessible except through the intended ingress**

For an internet-facing application:

```text
Internet
   ↓
Azure Front Door
   ↓
Application
```

I would avoid allowing:

```text
Internet
   ─────────→ backend directly
```

because this can bypass:

```text
WAF
central TLS policy
routing rules
edge controls
```

Microsoft recommends restricting direct access to application origins when Front Door is the public ingress. ([Microsoft Learn][1])

---

### **7. Design meaningful health probes**

Bad probe:

```text
GET /health
→ process responds 200
```

even though:

```text
database unavailable
critical dependency unavailable
application can't serve users
```

Better readiness/health logic should prove enough of the critical serving path to decide whether that region should receive traffic.

Front Door periodically probes origins and excludes unhealthy ones from normal routing. ([Microsoft Learn][3])

---

### **8. Capacity-plan for losing a region**

If active-active traffic is:

```text
Region A = 50%
Region B = 50%
```

then after Region A fails:

```text
Region B = 100%
```

Region B must be able to accept that traffic.

Microsoft explicitly recommends planning surviving-region capacity for this condition. ([Microsoft Learn][1])

I might use:

```text
autoscaling
+
minimum reserved capacity
```

rather than hoping that scale-out completes quickly enough during a disaster.

---

### **9. Deploy configuration identically**

I would use:

```text
Terraform
+
GitHub Actions / Azure DevOps
```

to build both regional stacks.

```text
One codebase
    ↓
Region A
+
Region B
```

Configuration drift is dangerous during DR.

---

### **10. Test an actual regional failure scenario**

I would test:

```text
Disable/unroute Region A
       ↓
Front Door detects failure
       ↓
All traffic reaches Region B
       ↓
Login works
       ↓
Writes work
       ↓
Key Vault works
       ↓
Monitoring works
```

and measure actual RTO/RPO.

> **In an interview, I would say:**
> “I would remove the Azure region as a single point of failure by deploying identical application stacks in two regions behind Azure Front Door. I would choose active-active when low RTO is critical, or active-passive when cost matters more, but the secondary would still be preconfigured. The application tier would be stateless, all stateful dependencies such as databases and storage would have an explicit cross-region replication strategy, and each region would have independent networking, identities and secrets. Front Door health probes would stop sending traffic to an unhealthy region, and I would capacity-plan the remaining region to handle the full workload.”

**Memory line:**
**Multi-region web resilience requires multi-region compute AND multi-region state—not just a global load balancer.**

**Interview trap:**
Deploying the web tier to two regions while leaving the database only in one region does **not** create true regional resilience.

**Keywords:**
Azure Front Door, active-active, active-passive, multi-region, health probe, geo-replication, stateless application

**Likely follow-ups:**

* How would you keep users' sessions working across regions?
* What happens to writes if the primary database region fails?
* Why would you choose Front Door instead of Traffic Manager?
* How much capacity should the secondary region have?

### **T12-H03. How would you test disaster recovery without affecting production?**

**Answer:**
I would run a **test failover into an isolated non-production network**, use replicated recovery data, validate the full application and its dependencies there, record RTO/RPO observations, and then clean up the test environment. With Azure Site Recovery specifically, **Test Failover** is designed to validate DR without affecting ongoing replication or the production environment. ([Microsoft Learn][4])

### **Architecture**

```text
                     Production
                        VM
                         |
                         | replication continues
                         v
                Site Recovery replica
                         |
                         | Test Failover
                         v
                 Isolated Test VNet
                  /      |       \
               Test DB  App     DNS
```

while:

```text
Real production users
        ↓
Production environment
```

continue working normally.

---

### **1. Create a dedicated isolated test VNet**

I would create something like:

```text
vnet-dr-test
```

that:

```text
does NOT have normal production connectivity
does NOT advertise production routes
does NOT share production endpoints unnecessarily
```

Microsoft specifically recommends using a separate network for Site Recovery test failover so the drill does not interfere with the production recovery-site network. ([Microsoft Learn][4])

The test network should still mimic production closely enough to be useful:

```text
same subnet design
similar IP structure
DNS configured appropriately
```

Microsoft recommends matching subnet names and address ranges where practical. ([Microsoft Learn][4])

---

### **2. Trigger Site Recovery Test Failover**

For a replicated VM or Recovery Plan:

```text
Recovery Services vault
       ↓
Replicated Item
       ↓
Test Failover
       ↓
Choose recovery point
       ↓
Choose isolated VNet
```

ASR then creates test VM instances from the replicated recovery state.

Importantly:

```text
Production replication
→ continues
```

and production is not failed over. ([Microsoft Learn][4])

---

### **3. Choose the recovery point intentionally**

For example:

```text
Latest
Latest processed
Latest app-consistent
Custom
```

depending on what I am trying to validate.

Microsoft notes that:

```text
Latest
→ lowest RPO
```

because it processes the latest replicated data, while:

```text
Latest processed
→ lower RTO
```

because no extra processing is required. ([Microsoft Learn][5])

That itself is useful DR testing.

---

### **4. Prevent the test environment from doing production actions**

This is essential.

Suppose the recovered application contains:

```text
email worker
payment worker
queue consumer
scheduler
```

I do **not** want the DR test to:

```text
send real emails
charge customers
consume production queues
modify production DB
call real third-party systems
```

So I would:

```text
isolate egress
use test dependencies
disable destructive workers
redirect integrations
```

where required.

---

### **5. Recreate critical dependencies**

A VM booting successfully proves very little.

The test environment should validate:

```text
DNS
identity
database
Key Vault
certificates
internal routing
load balancer
application startup
```

Microsoft's ASR guidance specifically calls out DNS and Active Directory preparation in isolated failover environments when those dependencies are required. ([Microsoft Learn][6])

---

### **6. Run real functional checks**

Example:

```text
GET /health
→ 200

Login
→ success

Read customer record
→ success

Create test transaction
→ success

Key Vault read
→ success

Database write
→ success
```

Then:

```text
Application is actually usable
```

rather than just:

```text
VM status = Running
```

---

### **7. Measure the drill**

I would record timestamps:

```text
10:00:00
test failover initiated

10:06:30
VMs recovered

10:09:00
application passed tests
```

Actual test recovery:

```text
9 minutes
```

Then inspect the newest recovered data to estimate actual RPO.

---

### **8. Test recovery plans, not just individual VMs**

For a three-tier application:

```text
Database
   ↓
API
   ↓
Frontend
```

I would test the **Recovery Plan** so dependency order and automation are validated together.

Site Recovery supports test failover for a Recovery Plan containing multiple VMs. ([Microsoft Learn][4])

---

### **9. Clean up after testing**

After validation:

```text
Cleanup Test Failover
       ↓
Test VMs removed
       ↓
Observations recorded
```

Microsoft's test-failover process provides a cleanup action and a place to record observations. ([Microsoft Learn][4])

Then every discovered problem becomes:

```text
IaC fix
runbook fix
network fix
monitoring fix
```

and I test again.

> **In an interview, I would say:**
> “With Azure Site Recovery I would use Test Failover rather than touching the live failover path. I would recover replicated workloads into an isolated non-production VNet so production and ongoing replication remain unaffected. The test network would reproduce the required DNS, identity and application dependencies but would be isolated from real payment systems, queues and other destructive integrations. Then I would validate complete business transactions, measure recovery time and recovered-data age, record issues, and use Cleanup Test Failover afterward.”

**Memory line:**
**Test DR using real recovery data in an isolated network, not by experimenting on production.**

**Interview trap:**
A VM successfully starting in a test VNet does **not** prove DR works. The application, dependencies, identity, DNS, and data must all be validated.

**Keywords:**
ASR Test Failover, isolated VNet, Recovery Plan, DR drill, recovery point, RTO, RPO

**Likely follow-ups:**

* Does an ASR test failover stop production replication?
* Why should the test VNet be isolated?
* What is the difference between Latest and Latest Processed?
* How would you test external dependencies safely?

### **T12-H04. How would DNS affect your RTO during regional failover?**

**Answer:**
DNS can directly increase RTO because clients and recursive DNS resolvers **cache DNS responses for the record's TTL**. Even after the traffic-management service recognizes that the primary region is down, clients holding an old DNS answer may continue connecting to the failed endpoint until that cached record expires. This is particularly important with **Azure Traffic Manager because it is DNS-based**. ([Microsoft Learn][7])

### **Failover timeline**

Consider:

```text
Primary fails
     ↓
Traffic Manager health probe detects failure
     ↓
Traffic Manager stops returning primary
     ↓
BUT
     ↓
Client still has cached old DNS answer
     ↓
TTL expires
     ↓
Client performs new DNS lookup
     ↓
Gets secondary endpoint
```

So approximate failover time involves:

```text
Failure detection
+
DNS propagation/cache expiry
+
Application recovery time
```

not simply:

```text
DNS changed instantly
```

---

### **Example**

Suppose:

```text
Traffic Manager TTL = 300 seconds
```

and a client resolved the primary endpoint one second before it failed.

That client could potentially continue using the cached answer for almost:

```text
5 minutes
```

before querying DNS again.

Microsoft explicitly states that shorter TTL values cause cached answers to expire sooner and allow faster redirection away from failed endpoints, while longer TTLs can delay failover. ([Microsoft Learn][7])

---

### **Traffic Manager health detection also adds time**

For example, if health probes run every:

```text
30 seconds
```

with multiple tolerated failures:

```text
Primary dies
   ↓
probe failure
   ↓
more probe failures
   ↓
endpoint marked degraded
```

only then does Traffic Manager stop returning the endpoint to **new DNS requests**.

Meanwhile:

```text
existing cached DNS
```

can still point to the failed region until TTL expiry. Microsoft's Traffic Manager monitoring documentation describes this exact sequence. ([Microsoft Learn][8])

---

### **Therefore TTL is part of the RTO design**

If my target is:

```text
RTO = 15 minutes
```

I would not casually set:

```text
DNS TTL = 1 hour
```

for a DNS-based failover path.

Current Microsoft Well-Architected guidance for Traffic Manager recommends a low TTL—preferably **below 60 seconds**—when quicker failover is important, while balancing the additional DNS query load. ([Microsoft Learn][9])

---

### **But very low TTL has tradeoffs**

Lower TTL:

```text
faster DNS convergence
+
more DNS queries
+
greater resolver/query activity
```

Higher TTL:

```text
fewer DNS queries
+
better cache efficiency
-
slower failover
```

So I select TTL based on:

```text
RTO requirement
traffic volume
DNS architecture
failover behavior
```

rather than blindly choosing the smallest number.

---

### **Existing connections are another issue**

Traffic Manager controls **DNS answers**, not live TCP connections.

If a user already has:

```text
existing session
→ Primary Region
```

changing DNS does not magically move that live connection to another server.

Microsoft explicitly notes that Traffic Manager cannot redirect existing connections; it influences new connections/resolutions. ([Microsoft Learn][8])

Applications therefore also need:

```text
connection timeout
retry logic
stateless sessions
```

for good failover behavior.

---

### **Front Door behaves differently**

This is an excellent distinction in interviews.

```text
Azure Traffic Manager
→ DNS-based
```

Client receives an endpoint address and connects to it.

Therefore:

```text
DNS caching directly affects regional failover
```

Azure Front Door is instead a **global reverse-proxy/HTTP edge service**.

Conceptually:

```text
Client
  ↓
Front Door endpoint
  ↓
Front Door chooses healthy origin
```

If:

```text
Region A origin fails
```

Front Door can stop routing new requests to that origin based on its health probes and route them to Region B without requiring the client's DNS record to change from Region A to Region B. Microsoft documents health-based origin selection and automatic routing to healthy origins. ([Microsoft Learn][3])

That is one reason I often prefer Front Door for global HTTP workloads with aggressive failover targets.

---

### **DNS should also exist in the DR runbook**

During failover I would verify:

```text
Public DNS
Private DNS
CNAMEs
Private Endpoint DNS
Custom domains
certificate bindings
```

A secondary application can be perfectly healthy and still inaccessible because:

```text
private DNS
→ still resolves primary-region endpoint
```

or:

```text
public record
→ wrong destination
```

---

### **Testing**

I would test using:

```bash
nslookup app.example.com
```

or:

```bash
dig app.example.com
```

and inspect:

```text
resolved destination
TTL
resolver behavior
```

Microsoft's Traffic Manager testing guidance specifically recommends waiting for the profile TTL when testing endpoint failover because cached DNS answers remain valid until expiration. ([Microsoft Learn][10])

> **In an interview, I would say:**
> “DNS can become part of my RTO because DNS responses are cached. With Traffic Manager, once the primary endpoint becomes unhealthy, Traffic Manager stops returning it for new DNS queries, but clients or recursive resolvers may still have the old response cached until its TTL expires. So failover time includes health-probe detection plus DNS-cache expiry, and I would configure a TTL aligned with the RTO and test actual resolver behavior. For global HTTP applications with very low failover targets, Azure Front Door can reduce this dependency because clients keep connecting to the same Front Door endpoint while Front Door changes the healthy backend origin.”

**Memory line:**
**With DNS-based failover, RTO includes failure detection + DNS cache expiry.**

**Interview trap:**
Changing a DNS record does **not** instantly redirect every user; caches and existing connections can continue using the old endpoint.

**Keywords:**
DNS TTL, Traffic Manager, caching, health probe, failover, Azure Front Door, RTO

**Likely follow-ups:**

* Why not always set TTL to zero?
* What is the difference between Traffic Manager and Front Door during failover?
* Does Traffic Manager terminate existing connections?
* How would you test DNS failover before production?
