### **T12-M07. What is backup retention?**

**Answer:**
Backup retention defines **how long Azure keeps recovery points before they expire and can be deleted**. I configure retention according to business, compliance, and recovery requirements—for example, keeping daily backups for 30 days, monthly backups for 12 months, and yearly backups for several years.

### **How it works**

```text
Production workload
        ↓
Backup policy
        ↓
Recovery points
        ↓
Retention rules
        ↓
Keep for configured period
        ↓
Expire/delete when no longer required
```

For example:

```text
Daily   → retain 30 days
Weekly  → retain 12 weeks
Monthly → retain 12 months
Yearly  → retain 7 years
```

The exact retention options depend on the Azure Backup workload and policy type.

### **Why retention matters**

Retention has to balance three things:

```text
Recoverability
     +
Compliance
     +
Cost
```

If retention is too short:

```text
Data corrupted 3 months ago
        ↓
Only 30 days of backups retained
        ↓
No clean recovery point available
```

If retention is unnecessarily long:

```text
More recovery points
      ↓
Higher backup storage cost
```

### **Production example**

Suppose a company needs:

```text
Operational recovery
→ last 30 days

Audit requirement
→ monthly copies for 1 year

Legal requirement
→ yearly copies for 7 years
```

I would encode those requirements into the backup policy rather than manually preserving individual backups.

### **Retention vs backup frequency**

This distinction is important:

```text
Backup frequency
→ how often I create recovery points

Retention
→ how long I keep them
```

For example:

```text
Backup every 4 hours
Retain for 30 days
```

means these are two separate policy decisions.

> **In an interview, I would say:**
> “Backup retention defines how long recovery points are preserved. I would derive it from business recovery needs and compliance requirements—for example, frequent recent backups for operational recovery and longer monthly or yearly retention for compliance. I also distinguish retention from backup frequency: frequency determines how often I create a recovery point, while retention determines how long I keep it.”

**Memory line:**
**Frequency decides how often I back up; retention decides how long I keep the backups.**

**Interview trap:**
Do not assume “daily backup with 30-day retention” means only one recovery point exists.

**Keywords:**
Backup retention, recovery point, backup policy, compliance, long-term retention, LTR

**Likely follow-ups:**

* What is the difference between retention and backup frequency?
* How would retention affect backup cost?
* How would compliance requirements affect your retention policy?
* Why might you keep monthly/yearly backups longer than daily backups?

### **T12-M08. What is a DR failover?**

**Answer:**
A DR failover is the process of **switching production operation from the primary environment to a disaster-recovery environment when the primary environment is unavailable or unusable**. It can involve starting recovered workloads, selecting a recovery point, validating dependencies, and redirecting user traffic to the secondary site or region.

### **Basic flow**

```text
Primary Region
      ↓
Major failure
      ↓
Declare disaster
      ↓
Failover
      ↓
Secondary Region
      ↓
Validate application
      ↓
Redirect users
```

For Azure Site Recovery:

```text
Primary Azure VM
       ↓
replicated continuously
       ↓
Secondary region
       ↓
ASR failover
       ↓
Recovered VM starts
```

### **Failover is more than starting servers**

A real application might require:

```text
1. Recover database
       ↓
2. Recover backend services
       ↓
3. Recover frontend
       ↓
4. Validate dependencies
       ↓
5. Redirect DNS/global traffic
```

If I recover the VMs but:

```text
DNS still points to primary
```

the users still see an outage.

Likewise, if:

```text
application starts
but database isn't available
```

the DR environment isn't actually usable.

### **Planned vs unplanned failover**

Conceptually:

```text
Planned failover
→ primary is available
→ controlled transition
→ useful during planned migration/maintenance scenarios
```

versus:

```text
Unplanned failover
→ primary has failed
→ recover using already replicated state
```

The exact options depend on the Azure service.

### **RTO and RPO**

Failover directly affects both:

```text
RTO
→ how long until secondary serves users?

RPO
→ how recent is the recovered data?
```

For example:

```text
Disaster: 10:00
Service restored: 10:12
Recovered data: 09:57
```

Then approximately:

```text
Actual recovery time = 12 min
Actual data loss = 3 min
```

Those results should be compared with the required RTO and RPO.

> **In an interview, I would say:**
> “A DR failover is the controlled switch from the failed primary environment to the secondary recovery environment. It includes more than simply starting replicas—I need to select the appropriate recovery point, recover services in dependency order, validate networking and data, and redirect user traffic. I then measure how long the process took and how much data was lost against the required RTO and RPO.”

**Memory line:**
**Failover moves production operation from primary to the recovery environment.**

**Interview trap:**
Do not consider failover complete just because the secondary VMs have started. The **application must actually serve users successfully**.

**Keywords:**
DR failover, secondary region, recovery point, RTO, RPO, traffic switching, recovery plan

**Likely follow-ups:**

* What is planned versus unplanned failover?
* How would you select a recovery point?
* How does DNS affect failover?
* What should you validate before declaring DR successful?

### **T12-M09. What is failback?**

**Answer:**
Failback is the process of **moving production workloads from the disaster-recovery environment back to the original primary environment—or another preferred production environment—after it has been repaired and validated**. It should be a controlled process because the secondary environment may now contain newer production data that must be synchronized back first.

### **Lifecycle**

```text
Primary Region
      ↓
Disaster
      ↓
Failover
      ↓
Secondary becomes production
      ↓
Primary repaired
      ↓
Reprotect / synchronize
      ↓
Failback
      ↓
Primary becomes production again
```

### **Why synchronization matters**

Suppose:

```text
10:00 → primary fails
10:15 → secondary starts serving users
14:00 → primary repaired
```

Between:

```text
10:15–14:00
```

users have created new data in the **secondary environment**.

I cannot simply redirect traffic back to the old primary because:

```text
Secondary
→ contains newer production data

Old Primary
→ stale data
```

So first I need:

```text
Secondary
     ↓
reverse replication / synchronization
     ↓
Primary
```

and only then perform the controlled switch.

### **Azure Site Recovery concept**

A typical ASR flow is:

```text
Failover to secondary
       ↓
Commit/operate there
       ↓
Primary available again
       ↓
Reprotect
       ↓
Reverse replication
       ↓
Planned failback
```

The exact sequence depends on the supported Site Recovery scenario.

### **Production failback checks**

Before failback, I would verify:

```text
Primary infrastructure healthy?
Networking restored?
Security controls restored?
Data synchronized?
Application version correct?
Dependencies reachable?
Monitoring working?
Traffic-routing path ready?
```

Then:

```text
Maintenance/change window
      ↓
final synchronization
      ↓
switch traffic
      ↓
validate
```

### **Important distinction**

```text
Failover
→ primary → secondary

Failback
→ secondary → preferred primary
```

But failback is **not necessarily immediate**.

If the secondary environment is stable, I would rather keep production there temporarily than rush traffic back into a barely recovered primary environment.

> **In an interview, I would say:**
> “Failback is the controlled return from the DR environment to the original or preferred production environment after it is healthy again. Because the secondary may have been serving users for hours or days, I first synchronize its newer data back to the primary, validate the primary environment, and then switch traffic during a controlled window. With Site Recovery that normally involves reprotection or reverse replication before the final failback.”

**Memory line:**
**Failover gets me away from the disaster; failback gets me safely back afterward.**

**Interview trap:**
Do not switch immediately back to the recovered primary without synchronizing data created while the secondary was active.

**Keywords:**
Failback, reprotect, reverse replication, synchronization, failover, DR

**Likely follow-ups:**

* What is reprotection?
* Why might you delay failback even after the primary region recovers?
* What happens to data written in the secondary region?
* How would you minimize downtime during failback?

### **T12-M10. What is a DR drill?**

**Answer:**
A DR drill is a **planned test of the disaster-recovery process** used to prove that systems, people, procedures, dependencies, and recovery automation actually work before a real disaster occurs. A good drill measures the actual RTO and RPO and exposes problems such as broken networking, outdated runbooks, missing secrets, or incorrect startup dependencies.

### **Why it matters**

Having:

```text
Backups ✓
Replication ✓
Secondary region ✓
```

does **not automatically mean**:

```text
DR works ✓
```

The real test is:

```text
Can we restore the service
within the required time
with acceptable data loss?
```

### **Typical DR drill**

```text
Define scenario
      ↓
Record start time
      ↓
Trigger test recovery/failover
      ↓
Start services in correct order
      ↓
Validate network + identity + data
      ↓
Run application tests
      ↓
Measure RTO/RPO
      ↓
Clean up
      ↓
Document gaps
```

### **Azure Site Recovery example**

With ASR, I would normally use a **test failover** instead of failing over the real production environment.

Conceptually:

```text
Production VM
      │
      ├──────── continues operating
      │
      ↓
ASR replicated state
      ↓
Test failover
      ↓
Isolated test VNet
      ↓
Recovered test VM
```

The isolated network is important because I do not want the test VM to:

```text
send production emails
process production queues
update production databases
conflict with production IP/DNS
```

### **What I would validate**

I would test much more than:

```text
"VM booted successfully."
```

I would verify:

```text
DNS resolution
Load balancer/frontend
Application startup
Database connectivity
Key Vault access
Managed identities
Certificates
Private Endpoints
Firewall rules
External dependencies
Monitoring
Login/user journey
Data consistency
```

For example:

```text
GET /health        → 200
User login         → works
Place test order   → works
Database query     → works
Key Vault lookup   → works
```

### **Measure RTO**

Suppose:

```text
DR declared:       10:00
Application ready: 10:11
```

Actual recovery time:

```text
11 minutes
```

If:

```text
Required RTO = 15 minutes
```

then the test meets that RTO.

### **Measure RPO**

Suppose:

```text
Disaster point:      10:00
Newest recovered data: 09:57
```

Actual data loss:

```text
3 minutes
```

If:

```text
Required RPO = 5 minutes
```

then the RPO requirement was also met.

### **After the drill**

The most useful result is usually the list of problems discovered:

```text
Private DNS missing
Certificate expired
Recovery Plan starts API before DB
Terraform module missing secondary-region setting
Engineer followed outdated runbook
```

Then I:

```text
Fix
  ↓
Update runbook/IaC
  ↓
Repeat drill
```

> **In an interview, I would say:**
> “A DR drill is a controlled exercise that proves the recovery design works before a real outage. I would preferably perform a non-disruptive test failover into an isolated network, validate the complete application rather than only VM startup, and measure the actual recovery duration and recovered-data age against the required RTO and RPO. Any gap becomes an action item and the drill is repeated periodically because an untested DR plan is only an assumption.”

**Memory line:**
**A DR drill turns a recovery plan from documentation into proven capability.**

**Interview trap:**
Do not call a successful backup job a DR test. A DR drill must prove that the **usable application can actually recover**.

**Keywords:**
DR drill, test failover, isolated VNet, RTO, RPO, runbook, validation, recovery testing

**Likely follow-ups:**

* How can you test ASR without affecting production?
* What should be validated during a DR drill?
* How would you measure actual RTO and RPO?
* How often should DR drills be performed?
