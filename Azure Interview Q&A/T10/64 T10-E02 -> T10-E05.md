### **T10-E02. What are Azure metrics?**

**Answer:**
Azure metrics are **numerical, time-series measurements** that describe the health and performance of Azure resources and applications. They are optimized for fast monitoring and alerting on values such as CPU percentage, request count, latency, disk operations, or memory-related signals.

### **How it works**

A metric is essentially:

```text
Timestamp
   +
Metric name
   +
Numeric value
   +
Optional dimensions
```

For example:

```text
VM CPU Percentage
10:00 → 42%
10:01 → 67%
10:02 → 91%
```

Because metrics are structured numeric data, they are ideal for:

```text
Dashboards
Alerts
Trend analysis
Autoscaling
```

### **Production example**

For an Azure VM, I might monitor:

```text
CPU Percentage
Disk IOPS
Network traffic
```

For an application or AKS workload, I might monitor:

```text
Request rate
Latency
Failure rate
CPU / memory utilization
```

A common alert could be:

```text
CPU > 80%
for 10 minutes
      ↓
Azure Monitor Alert
      ↓
Action Group
```

### **Important distinction**

Metrics tell me **what is happening numerically**.

They usually do not provide the same level of detailed context as logs.

```text
Metric
→ CPU = 95%

Log
→ which process/request/error contributed to the problem
```

**Memory line:**
**Metrics are fast numerical time-series signals used to monitor health and performance.**

**Interview trap:**
Do not describe metrics as detailed event records. Metrics are aggregated numeric measurements; logs contain richer event-level details.

**Keywords:**
Metrics, time series, dimensions, CPU, latency, alerts, Azure Monitor

### **T10-E03. What are Azure logs?**

**Answer:**
Azure logs are **detailed records of events, operations, and telemetry** generated by Azure resources, applications, operating systems, and the Azure platform. In Azure Monitor, logs are commonly stored in a Log Analytics workspace and queried using KQL.

### **How it works**

Logs contain richer information than a simple numeric metric.

For example:

```text
Timestamp
Resource
Operation
Status
IP address
Message
Exception
Request ID
```

They can answer questions such as:

```text
Who changed this resource?
Why did this request fail?
Which pods restarted?
Which IP attempted access?
What exception occurred?
```

### **Production example**

Suppose users report application failures.

I might query logs to find:

```text
HTTP 500 responses
application exceptions
AKS pod restarts
authentication failures
database connection errors
```

The flow is typically:

```text
Azure Resource / Application
            ↓
       Log telemetry
            ↓
Log Analytics Workspace
            ↓
           KQL
            ↓
Troubleshooting / Alerts / Dashboards
```

### **Important distinction**

```text
Metrics
→ numeric, lightweight, fast

Logs
→ detailed, contextual, queryable records
```

For example:

```text
Metric:
Error rate = 8%

Logs:
Which requests failed,
what exception occurred,
which backend was involved
```

**Memory line:**
**Metrics show that something is wrong; logs often help explain why.**

**Interview trap:**
Do not say all Azure logs automatically go to Log Analytics. Many resource logs require **diagnostic settings or another collection configuration** before they are sent there.

**Keywords:**
Logs, Log Analytics, KQL, events, diagnostics, troubleshooting, telemetry

### **T10-E04. What is a Log Analytics workspace?**

**Answer:**
A Log Analytics workspace is an Azure Monitor data store used to **collect and analyze log and telemetry data** from Azure resources, VMs, AKS, applications, and other sources. Once the data is stored there, I can query it using KQL, create dashboards, investigate incidents, and build log-based alerts.

### **How it works**

```text
VMs
AKS
Azure Services
Applications
      │
      ↓
Azure Monitor collection
      ↓
Log Analytics Workspace
      ↓
      KQL
      ↓
Queries / Alerts / Workbooks
```

The workspace contains tables such as:

```text
AzureActivity
Heartbeat
ContainerLogV2
KubePodInventory
```

depending on which data sources and monitoring solutions are configured.

### **Production example**

For AKS, I might configure Container Insights so telemetry goes into a Log Analytics workspace.

Then I could investigate:

```text
Pod restarts
Container logs
Node health
Kubernetes inventory
```

using KQL.

For example, conceptually:

```kusto
KubePodInventory
| where PodStatus == "Failed"
```

The important point is not the exact query—it is that the workspace provides the centralized log store that KQL queries operate against.

### **Important distinction**

A Log Analytics workspace is **not Azure Monitor itself**.

```text
Azure Monitor
→ overall monitoring platform

Log Analytics workspace
→ log data store and query environment within Azure Monitor
```

Also, a workspace is not merely a folder for logs. It provides structured tables, retention settings, access control, querying, and integration with alerts and workbooks.

**Memory line:**
**Log Analytics workspace = centralized Azure Monitor log store queried with KQL.**

**Interview trap:**
Do not confuse **Log Analytics** with **Application Insights**. Application Insights focuses on application observability, while a Log Analytics workspace is the underlying/log-centric analytics store used across many Azure monitoring scenarios.

**Keywords:**
Log Analytics workspace, KQL, tables, centralized logs, Azure Monitor, retention

### **T10-E05. What is Application Insights?**

**Answer:**
Application Insights is the **application performance monitoring and observability capability in Azure Monitor**. It helps me understand application behavior using telemetry such as requests, dependencies, exceptions, traces, availability, and performance data.

### **How it works**

An instrumented application can generate:

```text
Requests
Dependencies
Exceptions
Traces
Performance data
```

which flows into Application Insights:

```text
User Request
     ↓
Application
     │
     ├── Request telemetry
     ├── Dependency calls
     ├── Exceptions
     └── Traces
            ↓
    Application Insights
            ↓
Performance analysis
Failure analysis
Distributed tracing
Alerts
```

### **Production example**

Suppose an API becomes slow.

Application Insights can help me trace:

```text
Client request
     ↓
API request = 4.2 sec
     ↓
SQL dependency = 3.8 sec
```

That tells me the application itself may not be CPU-bound; most of the latency is coming from the database dependency.

Similarly, if users receive HTTP 500 errors, I can correlate:

```text
Failed request
     ↓
Exception
     ↓
Dependency failure
     ↓
Trace context
```

### **Important distinction**

```text
Application Insights
→ application-level observability/APM

Log Analytics
→ general-purpose log analytics workspace

Azure Monitor
→ broader monitoring platform containing these capabilities
```

Application Insights is especially useful for answering:

```text
Which endpoint is slow?
Which requests fail?
Which dependency caused latency?
What exception occurred?
```

rather than only checking infrastructure health.

**Memory line:**
**Application Insights tells me what is happening inside the application and its dependencies.**

**Interview trap:**
Do not describe Application Insights as only a log-storage service. Its main value is **application performance monitoring, request/dependency correlation, exceptions, traces, and distributed observability**.

**Keywords:**
Application Insights, APM, requests, dependencies, exceptions, traces, latency, distributed tracing
