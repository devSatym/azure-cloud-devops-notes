### **T10-E06. What is KQL?**

**Answer:**
KQL, or **Kusto Query Language**, is the query language used to analyze log and telemetry data in services such as **Azure Monitor Logs, Log Analytics, and Application Insights**. I use it to filter, aggregate, correlate, and troubleshoot operational data.

### **How it works**

A simple KQL query might be:

```kusto
AzureActivity
| where TimeGenerated > ago(1h)
| where ActivityStatusValue == "Failure"
| project TimeGenerated, ResourceGroup, OperationNameValue
```

This means:

```text
AzureActivity table
      ↓
Last 1 hour
      ↓
Only failures
      ↓
Show selected columns
```

Common operators include:

```text
where       → filter rows
project     → select columns
summarize   → aggregate data
extend      → calculate new columns
order by    → sort results
```

### **Production example**

If users report failures in an AKS application, I might use KQL to investigate:

```text
Container logs
Pod restarts
Failed requests
Exceptions
Azure resource events
```

Instead of manually reading thousands of log lines, I can query exactly the events I need.

**Memory line:**
**KQL is the language I use to ask questions of Azure Monitor log data.**

**Interview trap:**
KQL is not SQL, even though some concepts look similar. It is optimized for querying telemetry and time-series/log data.

**Keywords:**
KQL, Kusto Query Language, Log Analytics, Azure Monitor Logs, filtering, aggregation

### **T10-E07. What is an Azure Monitor alert?**

**Answer:**
An Azure Monitor alert automatically evaluates monitoring data and **notifies or triggers an action when a defined condition is met**. For example, I can alert when VM CPU stays above 80%, an application has too many HTTP 500 errors, or a Log Analytics query detects repeated failures.

### **How it works**

```text
Azure Resource / Application
          ↓
   Metric or Log data
          ↓
     Alert Rule
          ↓
Condition becomes true
          ↓
       Alert
          ↓
    Action Group
          ↓
Email / SMS / webhook / automation
```

An alert rule normally defines:

```text
What to monitor
      +
Condition
      +
Threshold / query
      +
Evaluation frequency
      +
Action
```

### **Production example**

For a VM:

```text
CPU > 85%
for several minutes
      ↓
Alert fires
      ↓
Operations team notified
```

For an application:

```text
HTTP 5xx rate exceeds threshold
       ↓
Azure Monitor Alert
       ↓
Action Group
```

Alerts can be built from different signal types, including **metrics and logs**.

### **Important distinction**

An **alert rule** defines the condition.

An **Action Group** defines what should happen after the alert fires.

```text
Alert Rule
→ WHEN should I react?

Action Group
→ WHAT should happen?
```

**Memory line:**
**Azure Monitor alerts turn telemetry conditions into operational action.**

**Interview trap:**
An alert is not the same as an Action Group. The alert detects the condition; the Action Group handles notifications or automated responses.

**Keywords:**
Azure Monitor Alert, alert rule, condition, threshold, metrics, logs, Action Group

### **T10-E08. What is an Action Group?**

**Answer:**
An Action Group is a reusable Azure Monitor configuration that defines **who should be notified or what automation should run when an alert fires**. Multiple alert rules can reuse the same Action Group.

### **How it works**

```text
Metric / Log Condition
        ↓
    Alert Rule
        ↓
    Action Group
        ↓
├── Email
├── SMS
├── Push notification
├── Webhook
└── Automation / integration
```

Instead of configuring recipients separately on every alert, I might create:

```text
ag-platform-team
ag-database-team
ag-security-team
```

and attach the correct Action Group to each alert rule.

### **Production example**

Suppose AKS has a critical availability alert:

```text
AKS availability issue
        ↓
Azure Monitor Alert
        ↓
Action Group: ag-prod-platform
        ↓
Platform engineer notification
        +
Incident-management integration
```

For a database alert, I could use a different Action Group so it reaches the database operations team.

### **Important distinction**

```text
Alert Rule
→ detects the problem

Action Group
→ communicates or acts on the problem
```

An Action Group does not independently monitor CPU, logs, or applications.

**Memory line:**
**Alert rule detects; Action Group reacts.**

**Interview trap:**
Do not describe an Action Group as the place where thresholds are configured. Thresholds and conditions belong to the alert rule.

**Keywords:**
Action Group, notifications, email, webhook, automation, alert routing, reusable actions

### **T10-M01. What is the difference between metrics and logs?**

**Answer:**
Metrics are **numeric time-series measurements** optimized for fast monitoring, dashboards, and alerting, while logs are **detailed event records** containing richer context that I query for investigation and troubleshooting. In practice, metrics often tell me **that something is wrong**, while logs help explain **why**.

### **How they differ**

```text
Metrics
│
├── Numeric
├── Time-series
├── Lightweight
├── Fast to query
└── Good for thresholds and trends

Logs
│
├── Detailed records
├── Rich context
├── Queryable with KQL
├── Higher data volume
└── Good for investigation
```

For example:

```text
Metric:
CPU = 95%
```

tells me a resource is under pressure.

Logs might tell me:

```text
Process X started consuming CPU
Request Y failed
Pod Z restarted
Database connection timed out
```

### **Production example**

Imagine users report slow API responses.

My investigation might start with:

```text
Metric
   ↓
API latency increased from 200 ms → 2 sec
```

That narrows the time window.

Then I inspect logs:

```text
Application logs
      ↓
Dependency timeout
      ↓
Database connection issue
```

So the two signal types complement each other.

### **Operational trade-off**

Metrics are generally better for:

```text
CPU
memory
request rate
latency percentile
queue depth
availability
```

because I want fast aggregation and alerting.

Logs are better when I need details such as:

```text
request ID
exception
user/session context
resource operation
source IP
error message
```

### **Important distinction**

A metric is not simply a log with fewer fields.

They are different telemetry models optimized for different purposes:

```text
Metrics
→ efficient numerical monitoring

Logs
→ detailed investigation
```

A strong monitoring strategy usually uses **both** rather than choosing one.

> **In an interview, I would say:**
> “Metrics are numerical time-series data optimized for fast monitoring and alerting, while logs are detailed event records that provide richer troubleshooting context. For example, a metric might tell me API latency jumped to two seconds, while logs help identify that database calls are timing out. I normally use metrics to detect and scope problems, then logs to investigate the cause.”

**Memory line:**
**Metrics tell me what changed; logs give me the details behind the change.**

**Interview trap:**
Do not say logs are always better because they contain more detail. Metrics are intentionally optimized for efficient real-time monitoring, trend analysis, and alerting.

**Keywords:**
Metrics, logs, time series, KQL, troubleshooting, alerting, telemetry, context

**Likely follow-ups:**

* When would you choose a metric alert instead of a log-search alert?
* Are Azure metrics stored in a Log Analytics workspace?
* Why can logs cost more than metrics at scale?
* How would you investigate high CPU using both metrics and logs?
