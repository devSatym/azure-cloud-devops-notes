### **T10-H06. How would you design alerts that avoid excessive alert noise?**

**Answer:**
I would design alerts around **actionable user impact and sustained abnormal conditions**, not every possible metric spike. I would choose the right signal, tune threshold and evaluation windows, use dynamic thresholds where they make sense, suppress notifications during planned maintenance, and make sure each alert has a clear owner and response action. Azure Monitor currently recommends dynamic thresholds where appropriate and alert processing rules for controlling alert behavior at scale. ([Microsoft Learn][1])

### **My alert-design order**

```text
What failure actually matters?
          ↓
Choose strongest signal
          ↓
Define severity
          ↓
Set threshold + duration
          ↓
Test against historical behavior
          ↓
Route to correct team
          ↓
Suppress planned noise
          ↓
Review false positives regularly
```

---

### **1. Alert on symptoms that matter**

I would prioritize:

```text
User impact
    ↓
Service health
    ↓
Platform health
    ↓
Capacity warnings
```

For example:

**Better production alert:**

```text
5xx rate > 5%
for 10 minutes
```

than:

```text
CPU briefly reached 82%
```

A CPU spike might be harmless, while sustained 5xx errors directly indicate user impact.

---

### **2. Require sustained failure**

Instead of:

```text
CPU > 80%
once
→ alert
```

I might use:

```text
CPU > 85%
for 10 minutes
→ alert
```

or require several violations inside the evaluation window.

Azure Monitor's dynamic-threshold configuration supports requiring multiple violations, which helps filter transient spikes. ([Microsoft Learn][2])

---

### **3. Use dynamic thresholds when normal behavior varies**

Suppose traffic normally looks like:

```text
Day:
CPU 60–75%

Night:
CPU 15–30%
```

A single static threshold may not capture unusual behavior well.

Dynamic thresholds can learn:

```text
hourly
daily
weekly
patterns
```

and identify deviations from expected behavior. Microsoft specifically recommends dynamic thresholds where appropriate to reduce noisy thresholds and management overhead. ([Microsoft Learn][1])

I would not blindly use them everywhere, though. For hard limits such as:

```text
disk free space dangerously low
```

a clear static threshold may be simpler.

---

### **4. Use stateful alerts where appropriate**

Azure metric alerts are stateful by default.

Conceptually:

```text
Problem begins
    ↓
Alert fires once
    ↓
Problem continues
    ↓
No repeated notification every minute
    ↓
Condition clears
    ↓
Alert resolves
```

That behavior helps reduce duplicate notifications during one continuing incident. ([Microsoft Learn][3])

---

### **5. Suppress planned maintenance noise**

Suppose every Sunday:

```text
02:00–03:00
Database maintenance
```

causes expected alerts.

I would not permanently weaken the alert.

Instead I can use an **alert processing rule** to suppress actions during that maintenance window.

```text
Alert condition fires
        ↓
Alert Processing Rule
        ↓
Maintenance window?
     /        \
   Yes         No
    ↓           ↓
Suppress      Notify
notification
```

Alert processing rules can add or suppress action groups and apply filtering or scheduling logic. ([Microsoft Learn][4])

---

### **6. Apply meaningful severity**

For example:

```text
Sev 0 / Critical
→ service unavailable

Sev 1
→ major degradation

Sev 2
→ partial degradation

Sev 3+
→ warning / capacity risk
```

Not every infrastructure warning should wake someone at 3 AM.

A good question is:

```text
"If this fires tonight, does somebody need to act immediately?"
```

If the answer is no, it probably should not page the on-call engineer.

---

### **7. Combine related symptoms carefully**

Suppose:

```text
CPU high
memory high
request latency high
```

all result from one overloaded service.

I don't want three unrelated pages for the same event if I can design the monitoring to highlight the primary service-health symptom and leave supporting telemetry for diagnosis.

---

### **8. Continually review alerts**

I would measure:

```text
How often did this alert fire?
How often was action required?
Was it a duplicate?
Was it ignored?
Did it identify user impact early?
```

An alert that fires 200 times and is ignored 199 times is not a good alert.

---

> **In an interview, I would say:**
> “I reduce alert noise by alerting on actionable symptoms, requiring sustained violations rather than single spikes, and tuning thresholds using historical behavior. I use dynamic thresholds when workloads have changing baselines, stateful alerts to avoid repeated notifications for one incident, and alert processing rules to suppress planned-maintenance notifications. I also define severity and ownership so only genuinely urgent conditions page the on-call team.”

**Memory line:**
**A good alert is actionable, sustained, owned, and tied to real impact.**

**Interview trap:**
More alerts do **not** mean better monitoring. Excessive alerts create alert fatigue and can cause engineers to miss the one event that actually matters.

**Keywords:**
Alert fatigue, dynamic thresholds, sustained condition, stateful alerts, alert processing rules, severity, SLO

**Likely follow-ups:**

* What are dynamic thresholds?
* How would you suppress alerts during maintenance?
* Why are stateful alerts useful?
* Which alerts should page an on-call engineer?

### **T10-H07. How would you route different Azure alerts to different operations teams?**

**Answer:**
I would separate **alert detection from notification routing**. Alert rules determine when a problem exists, while **Action Groups** define who or what gets notified. For more advanced routing at scale, I can use **Alert Processing Rules** to filter fired alerts by scope, severity, resource, or other conditions and attach the appropriate Action Group. ([Microsoft Learn][5])

### **Architecture**

```text
Azure Resources
      ↓
Alert Rules
      ↓
Fired Alerts
      ↓
Alert Processing Rules
      ↓
      ├── Platform Team
      ├── Database Team
      ├── Security Team
      └── Application Team
             ↓
         Action Groups
```

---

### **Action Group design**

For example:

```text
ag-platform-prod
→ Platform on-call
→ incident-management webhook

ag-database-prod
→ DB team
→ database Pager/ITSM integration

ag-security-prod
→ SOC
→ SIEM / security workflow
```

Action Groups are reusable and can contain notifications or automation such as email, webhooks, Functions, or Logic Apps. Multiple alert rules can reuse the same Action Group. ([Microsoft Learn][5])

---

### **Production example**

Imagine I have:

```text
AKS node NotReady
Azure SQL storage pressure
Key Vault security event
Application 5xx spike
```

I would route:

```text
AKS node alert
      ↓
Platform Action Group

SQL capacity alert
      ↓
Database Action Group

Security alert
      ↓
Security Action Group

Application availability alert
      ↓
Application/Platform on-call
```

Not:

```text
Every Azure alert
      ↓
Everyone
```

That creates noise and unclear ownership.

---

### **Alert Processing Rules**

For large environments, I can define routing policies such as:

```text
Severity = Sev0 or Sev1
AND
Resource Group = prod-*
        ↓
Production on-call Action Group
```

or:

```text
Subscription = data-platform
        ↓
Database Operations Action Group
```

Azure Alert Processing Rules can add Action Groups to fired alerts based on scope and conditions, and can also suppress actions on a schedule. ([Microsoft Learn][4])

### **Important distinction**

```text
Alert Rule
→ detects condition

Alert Processing Rule
→ changes/routs actions for fired alerts

Action Group
→ actual notification or automated action
```

That distinction is excellent interview material.

---

### **Design at enterprise scale**

I would typically combine:

```text
Management Group / Subscription structure
            +
Resource naming/tagging
            +
Alert severity
            +
Alert Processing Rules
            ↓
Team-specific Action Groups
```

For example:

```text
Production Subscription
│
├── AKS / Platform
│      ↓
│  Platform Team
│
├── SQL / PostgreSQL
│      ↓
│  Data Team
│
└── Security services
       ↓
   Security Team
```

I would manage these rules through IaC rather than configuring hundreds manually.

---

### **Avoid over-routing**

A critical service outage may legitimately notify:

```text
Application Team
+
Platform Team
```

But every informational alert should not notify three departments.

Each alert should have a **clear primary owner**.

> **In an interview, I would say:**
> “I separate detection from routing. Alert rules detect conditions, Action Groups define the notification or automation destination, and Alert Processing Rules let me apply routing policies at scale. For example, AKS and node alerts can go to the platform Action Group, SQL alerts to the database team, and security alerts to the SOC. I would route primarily by resource ownership, environment and severity, and manage that configuration using IaC.”

**Memory line:**
**Alert rule detects; processing rule routes; Action Group notifies.**

**Interview trap:**
Do not create a separate copy of every alert rule just because different teams need different notification routing. Alert Processing Rules and reusable Action Groups can separate those concerns.

**Keywords:**
Action Group, Alert Processing Rule, routing, severity, ownership, webhook, ITSM

**Likely follow-ups:**

* What is the difference between an Action Group and Alert Processing Rule?
* Can several alert rules share one Action Group?
* How would you suppress notifications during maintenance?
* How would you manage alert routing across hundreds of resources?

### **T10-H08. What would you investigate if logs suddenly stopped appearing in Log Analytics?**

**Answer:**
I would first determine **whether all logs stopped or only one source/table**, and identify exactly when ingestion stopped. Then I would follow the data path from **source → collection configuration → agent/diagnostic setting → network → ingestion → Log Analytics workspace**. I would not start by restarting agents randomly because the issue may be workspace-wide, DCR-related, or caused by an ingestion limit.

### **Diagnostic order**

```text
Logs missing
    ↓
Scope the failure
    ↓
Source still generating data?
    ↓
Collection configuration
    ↓
Agent / Diagnostic Setting
    ↓
Network connectivity
    ↓
Azure ingestion
    ↓
Workspace/query
```

---

### **1. Scope the problem**

First I ask:

```text
All resources affected?
or
one VM?

All tables?
or
only Syslog?

All subscriptions?
or
one resource group?

Stopped suddenly?
or
never worked?
```

For example:

```text
Heartbeat stopped
+
Syslog stopped
+
Perf stopped
```

suggests a broader AMA/data-collection problem.

But:

```text
Heartbeat present
+
Syslog missing
```

suggests the agent is alive and I should focus on the DCR's Syslog configuration.

Microsoft's troubleshooting guidance specifically recommends determining whether one data type or all collection has stopped and how many machines are affected. ([Microsoft Learn][6])

---

### **2. Verify timestamps and query**

I would ensure I'm querying:

```text
correct workspace
correct table
correct time range
```

and remember that:

```text
TimeGenerated
```

is UTC-based.

A basic check might be:

```kusto
Heartbeat
| where TimeGenerated > ago(30m)
| summarize LastHeartbeat = max(TimeGenerated) by Computer
```

For AMA, Microsoft recommends using the `Heartbeat` table to verify whether the agent is still reporting. ([Microsoft Learn][7])

---

### **3. If it is an AMA source, check AMA → DCR → DCRA**

The path is:

```text
VM
 ↓
Azure Monitor Agent
 ↓
DCR Association
 ↓
DCR
 ↓
Log Analytics Workspace
```

I check:

1. Is AMA installed?
2. Is the service running?
3. Is the VM associated with the correct DCR?
4. Does the DCR collect the missing source?
5. Does the DCR target the correct workspace?

Microsoft's current AMA troubleshooting guidance explicitly recommends verifying agent health, DCR association, configuration download, and destination configuration. ([Microsoft Learn][7])

For Linux:

```bash
systemctl status azuremonitoragent
```

is a useful evidence check. ([Microsoft Learn][8])

---

### **4. If it is Azure resource logs, inspect diagnostic settings**

For something like Key Vault, Azure Firewall, or another PaaS resource:

```text
Azure Resource
      ↓
Diagnostic Setting
      ↓
Log Analytics
```

I would verify:

```text
Diagnostic setting still exists?
Correct log category enabled?
Correct workspace destination?
Was it changed/deleted recently?
```

I would also inspect the Azure Activity Log for configuration changes around the time data stopped.

---

### **5. Check network connectivity**

For AMA, the machine must reach Azure Monitor's required endpoints.

A failure could come from:

```text
NSG
Firewall
UDR
Proxy
DNS
Private Link configuration
```

If a new firewall rule was deployed immediately before logs stopped, that is a strong lead.

Microsoft's AMA troubleshooting guidance specifically includes checking outbound connectivity to Azure Monitor configuration endpoints when the agent cannot download its DCR. ([Microsoft Learn][8])

---

### **6. Check workspace ingestion limits**

A very important workspace-wide cause is:

```text
Daily ingestion cap reached
```

If the Log Analytics workspace reaches its configured daily cap, data collection can stop until the cap resets or is changed. Microsoft lists this as a primary reason data can suddenly stop appearing. ([Microsoft Learn][6])

I would also investigate ingestion-rate throttling or related workspace errors if the volume suddenly increased.

---

### **7. Inspect DCR ingestion telemetry**

Azure Monitor now exposes telemetry specifically for DCR-based collection.

For example:

```text
DCR errors
DCR metrics
ingestion troubleshooting logs
```

The `DCRLogTroubleshooting` table can contain errors related to DCR ingestion and transformation processing. ([Microsoft Learn][9])

That lets me distinguish:

```text
Agent never sent data
```

from:

```text
Azure received data but DCR processing failed
```

---

### **8. Check what changed**

Because the question says **suddenly stopped**, I would correlate the timestamp against:

```text
DCR changes
Diagnostic Setting changes
Firewall / NSG changes
Workspace configuration changes
Agent upgrade/failure
Azure Policy changes
Resource deletion/redeployment
```

That frequently finds the cause faster than inspecting every component independently.

---

### **Real troubleshooting tree**

```text
No logs
  ↓
Heartbeat present?
  │
  ├── Yes
  │    ↓
  │  Agent alive
  │    ↓
  │  Check specific DCR/data source
  │
  └── No
       ↓
     Check AMA
       ↓
     DCR association
       ↓
     Network
       ↓
     Workspace ingestion
```

For PaaS:

```text
Resource still healthy?
      ↓
Diagnostic Setting
      ↓
Log category
      ↓
Destination workspace
      ↓
Ingestion / workspace limits
```

> **In an interview, I would say:**
> “I first scope whether all logs stopped or only one source and identify the exact timestamp. For VM logs I check Heartbeat, then AMA health, DCR/DCRA association, the configured data source and destination, and network connectivity to Azure Monitor. For PaaS resource logs I inspect diagnostic settings and log categories. If multiple sources stopped at once, I check workspace-wide issues such as ingestion caps or throttling. Finally I correlate the failure time with Activity Log changes to DCRs, diagnostic settings, networking, or the workspace.”

**Memory line:**
**Follow the telemetry path: source → collector → configuration → network → ingestion → workspace.**

**Interview trap:**
Do not immediately restart AMA. If many resources stopped simultaneously, the problem is more likely centralized—such as a DCR, diagnostic setting, network policy, or workspace ingestion issue.

**Keywords:**
Heartbeat, AMA, DCR, DCRA, diagnostic settings, ingestion cap, `DCRLogTroubleshooting`, Log Analytics

**Likely follow-ups:**

* What does the `Heartbeat` table tell you?
* What if Heartbeat exists but Syslog doesn't?
* What happens when a Log Analytics daily cap is reached?
* How would you troubleshoot DCR processing failures?

### **T10-K01. What does the KQL `where` operator do?**

**Answer:**
The KQL `where` operator **filters rows based on a Boolean condition**. Only records where the condition evaluates to true continue to the next stage of the query.

For example:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where ResultCode == "500"
```

means:

```text
AppRequests
      ↓
Keep only last-hour records
      ↓
Keep only HTTP 500 records
```

Another example:

```kusto
KubePodInventory
| where PodStatus == "Failed"
```

returns only records where:

```text
PodStatus = Failed
```

### **Practical tip**

I normally apply selective `where` filters early:

```text
Table
  ↓
Time filter
  ↓
Resource/filter conditions
  ↓
summarize / join / project
```

because narrowing the dataset early makes queries easier to reason about and can improve efficiency.

**Memory line:**
**`where` decides which rows stay in the query.**

**Interview trap:**
`where` filters **rows**, while `project` chooses **columns**.

**Keywords:**
`where`, filter, Boolean condition, rows, KQL
