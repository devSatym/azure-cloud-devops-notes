### **T10-H02. A VM has high CPU usage every night; how would you investigate it using Azure Monitor?**

**Answer:**
Because the problem is **recurring every night**, I would first use Azure Monitor metrics to establish the exact pattern and time window, then move from **host-level CPU → guest OS metrics → process/application evidence → scheduled activity or dependency**. I would avoid immediately resizing the VM because that treats the symptom before identifying what is consuming CPU.

### **Troubleshooting flow**

```text
High CPU every night
        ↓
Confirm exact time/pattern
        ↓
Azure VM host metrics
        ↓
Guest OS metrics
        ↓
Which process/workload?
        ↓
Scheduled job / traffic / backup?
        ↓
Root cause
        ↓
Fix + alert
```

### **1. Confirm the pattern in Azure Monitor Metrics**

I would open the VM in **Metrics Explorer** and graph:

```text
Percentage CPU
```

over something like:

```text
Last 7–14 days
```

I want to establish:

```text
When does CPU increase?
How long does it remain high?
Does it happen at the same time every day?
Is it one VM or several VMs?
```

Azure provides VM host-level CPU and other platform metrics without additional guest-agent configuration. ([Microsoft Learn][1])

For example:

```text
00:00   18%
01:00   22%
02:00   95%  ← every night
03:00   94%
04:00   20%
```

A pattern like that immediately makes me suspect a scheduled activity rather than random capacity pressure.

---

### **2. Correlate CPU with other infrastructure metrics**

Next I would compare the same time window against:

```text
Disk IOPS / throughput
Network traffic
memory if guest metrics are available
```

For example:

```text
CPU ↑
Disk I/O ↑
at exactly 02:00
```

might indicate:

```text
backup
batch processing
log rotation/compression
database maintenance
antivirus/security scan
```

Whereas:

```text
CPU ↑
Network ingress ↑
```

could indicate scheduled traffic or workload processing.

---

### **3. Move inside the guest OS**

Host CPU tells me:

> “The VM is busy.”

It does not necessarily tell me:

> “Which process is busy?”

For guest-level monitoring I would use **Azure Monitor Agent + a Data Collection Rule**, or VM Insights where appropriate. Azure Monitor can collect guest performance counters and OS events, while optional process/dependency monitoring can provide deeper workload visibility. ([Microsoft Learn][1])

Conceptually:

```text
Azure VM
   ↓
AMA
   ↓
DCR
   ↓
Guest performance data
   ↓
Log Analytics
```

If I need per-process CPU specifically, I would ensure the appropriate process performance data is collected rather than assuming the basic platform CPU metric identifies the process.

---

### **4. Investigate the process or workload**

At the affected time:

```text
02:00–03:00
```

I would identify which process consumes CPU.

Possible causes:

```text
cron job
backup agent
database maintenance
application batch worker
security scanner
log compression
scheduled ETL process
unexpected process
```

Azure's Performance Diagnostics/PerfInsights can also help investigate high CPU, memory, disk, and other VM performance problems and can capture process information during diagnostics. ([Microsoft Learn][2])

---

### **5. Correlate with logs and Azure changes**

Once I know the time window, I would query OS/application logs around that period:

```text
01:50 → 03:10
```

and check whether anything changed recently.

I would also inspect the Azure Activity Log if the timing coincides with Azure-side automation or configuration changes.

So my evidence may look like:

```text
02:00 CPU = 96%
        ↓
process = backup-agent
        ↓
disk throughput also spikes
        ↓
backup schedule starts at 02:00
```

Now I have a root cause rather than merely an alert.

---

### **6. Fix according to the cause**

The solution depends on what I find:

```text
Scheduled batch job
→ optimize or move schedule

Backup causing contention
→ reschedule / tune backup

Application workload
→ optimize application or scale

Legitimate sustained workload
→ resize / autoscale architecture

Unexpected process
→ investigate security/process behavior
```

Only if the workload is legitimate and CPU capacity is genuinely insufficient would I then consider resizing.

---

### **7. Add monitoring**

After fixing it, I would create an alert such as:

```text
CPU > 85%
for 10 minutes
      ↓
Azure Monitor Alert
      ↓
Action Group
```

but tune the threshold according to the application's normal behavior.

> **In an interview, I would say:**
> “Because the CPU spike happens every night, I would first use Azure Monitor Metrics over several days to confirm the exact recurring window and correlate CPU with disk and network activity. Then I would move into guest-level monitoring using AMA, DCRs, VM Insights, or Performance Diagnostics to identify the process consuming CPU. I would correlate that with cron jobs, backups, database maintenance, application logs, and any Azure changes at that time. Only after identifying whether the workload is expected would I optimize, reschedule, or resize the VM.”

**Memory line:**
**Recurring CPU → find the time pattern first, then drill from VM → OS → process → scheduled workload.**

**Interview trap:**
Do not jump directly to **“resize the VM.”** High CPU may be caused by a badly scheduled or inefficient process rather than insufficient VM capacity.

**Keywords:**
Metrics Explorer, Percentage CPU, AMA, DCR, VM Insights, PerfInsights, process, correlation

**Likely follow-ups:**

* How would you identify which process is consuming CPU?
* What is the difference between host and guest VM metrics?
* When would you resize instead of optimize?
* How would you alert on sustained high CPU?

### **T10-H03. How would you detect repeated pod restarts using KQL?**

**Answer:**
With AKS Container Insights enabled, I would query the **`KubePodInventory`** table, which includes fields such as `ContainerRestartCount`, `PodRestartCount`, namespace, pod name, status, and restart information. I would restrict the query to a recent time window, group by pod/container, and alert when restart counts exceed an operational threshold. Microsoft currently documents `KubePodInventory` as containing both container and pod restart counts. ([Microsoft Learn][3])

### **Basic investigation query**

For example:

```kusto
KubePodInventory
| where TimeGenerated > ago(30m)
| summarize RestartCount = max(ContainerRestartCount)
    by Namespace, Name, ContainerName
| where RestartCount >= 3
| order by RestartCount desc
```

Conceptually:

```text
KubePodInventory
       ↓
Last 30 minutes
       ↓
Group by pod/container
       ↓
Find restart count
       ↓
RestartCount >= 3
```

This quickly identifies containers with unusually high restart counts.

---

### **CrashLoopBackOff-specific query**

If I suspect crash loops:

```kusto
KubePodInventory
| where TimeGenerated > ago(30m)
| where ContainerStatus == "waiting"
| where ContainerStatusReason in ("CrashLoopBackOff", "Error")
| summarize
    RestartCount = max(ContainerRestartCount)
    by Namespace, Name, ContainerName
| order by RestartCount desc
```

Microsoft's current Container Insights example similarly uses `KubePodInventory`, `ContainerStatusReason`, and restart counts for CrashLoopBackOff detection. ([Microsoft Learn][4])

---

### **Important issue: cumulative restart counters**

One thing I would be careful about is that:

```text
ContainerRestartCount
```

is a **counter**, not simply “number of restarts during this query window.”

So:

```text
RestartCount = 20
```

could mean the container accumulated 20 restarts over its lifetime.

For alerting on **new/repeated restarts**, I would use recent records and compare values over time, or use Microsoft's restart alert pattern that combines restart count with recent start information.

Microsoft's Container Insights alert example specifically shows detecting container restart counts over a recent window using `KubePodInventory`. ([Microsoft Learn][5])

---

### **Production diagnostic order**

An alert should lead into:

```text
Restart alert
    ↓
Which namespace/pod?
    ↓
kubectl describe pod
    ↓
Previous container logs
    ↓
Exit code / reason
    ↓
Configuration / resources / dependency
```

Useful commands:

```bash
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace> --previous
```

The `--previous` log is particularly valuable after a container restarts because it can show what the previous container instance logged immediately before termination.

I would then distinguish causes such as:

```text
OOMKilled
→ memory/resource problem

CrashLoopBackOff
→ application repeatedly failing

Liveness probe failures
→ health check or application problem

Configuration error
→ ConfigMap / Secret / startup problem

Dependency unavailable
→ application dependency problem
```

---

### **Turning it into an alert**

The architecture would be:

```text
AKS
 ↓
Container Insights
 ↓
Log Analytics
 ↓
KQL scheduled query
 ↓
Restart threshold exceeded
 ↓
Azure Monitor Alert
 ↓
Action Group
```

I would choose a threshold that avoids alerting on a single harmless restart.

For example:

```text
3+ recent restarts
within 10 minutes
```

may be more operationally meaningful than:

```text
1 restart
```

depending on the workload.

> **In an interview, I would say:**
> “With Container Insights enabled, I would use the `KubePodInventory` table because it contains pod and container restart counts. I would query a recent time window, group by namespace, pod, and container, and identify workloads whose restart count is increasing beyond a threshold. For CrashLoopBackOff I would also filter on `ContainerStatusReason`. Then I would create a log-search alert and, when it fires, use `kubectl describe` and `kubectl logs --previous` to find whether the cause is OOMKilled, probe failure, configuration, or an application crash.”

**Memory line:**
**KQL finds the restarting pod; `describe` and previous logs explain why it restarted.**

**Interview trap:**
Do not blindly treat `ContainerRestartCount` as “restarts during the last 10 minutes”—it is a restart counter, so alert logic should account for its behavior.

**Keywords:**
`KubePodInventory`, `ContainerRestartCount`, `PodRestartCount`, CrashLoopBackOff, KQL, log-search alert

**Likely follow-ups:**

* How would you identify an OOMKilled container?
* Why use `kubectl logs --previous`?
* How would you turn the KQL query into an Azure Monitor alert?
* What is the difference between a pod restart and pod recreation?

### **T10-H04. How would you find HTTP 500 errors using Application Insights?**

**Answer:**
I would start with Application Insights **Failures** to confirm the affected operation and time window, then query `AppRequests` in the workspace-based Log Analytics schema. I would filter the request result code for HTTP 500—or more broadly 5xx responses—and then group by operation, URL, or application role to identify where failures are concentrated. The current `AppRequests` table includes `ResultCode`, `Success`, `Name`, `Url`, `OperationId`, and duration information. ([Microsoft Learn][6])

### **Basic HTTP 500 query**

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where ResultCode == "500"
| project
    TimeGenerated,
    Name,
    Url,
    ResultCode,
    DurationMs,
    OperationId,
    AppRoleName
| order by TimeGenerated desc
```

This answers:

```text
When?
Which endpoint?
Which service?
How long did it run?
Which operation ID?
```

---

### **Find the worst endpoints**

I would then aggregate:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where ResultCode == "500"
| summarize
    Failures = sum(ItemCount)
    by Name
| order by Failures desc
```

That turns:

```text
Thousands of individual failures
```

into:

```text
POST /checkout     850
GET /orders         34
GET /profile         3
```

Now I know where to investigate first.

Microsoft's current `AppRequests` examples similarly use `Success == false`, `ItemCount`, and grouping by request or operation to identify failed requests. ([Microsoft Learn][7])

---

### **For all server errors**

If the interviewer asks for all 5xx responses rather than exactly 500:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where toint(ResultCode) between (500 .. 599)
| summarize Failures = sum(ItemCount) by ResultCode, Name
| order by Failures desc
```

This captures:

```text
500
502
503
504
...
```

which is usually more useful operationally.

---

### **Correlate with exceptions**

Finding the 500 is only step one.

Next:

```text
HTTP 500 request
      ↓
OperationId
      ↓
Exception
      ↓
Dependency call
```

For example:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where Success == false
| join kind=leftouter (
    AppExceptions
    | where TimeGenerated > ago(1h)
) on OperationId
| project
    TimeGenerated,
    Name,
    ResultCode,
    ExceptionType = Type,
    ExceptionMessage = Message,
    OperationId
```

Microsoft currently provides an official example joining failed `AppRequests` with `AppExceptions` through `OperationId` to identify exceptions behind request failures. ([Microsoft Learn][7])

---

### **Diagnostic flow**

```text
500 errors reported
      ↓
Failures / AppRequests
      ↓
Which endpoint/service?
      ↓
OperationId
      ↓
AppExceptions
      ↓
AppDependencies
      ↓
Application or downstream cause?
```

For example:

```text
POST /checkout → 500
        ↓
TimeoutException
        ↓
Payment dependency failed
```

Now I know the HTTP 500 is a **symptom**, while the dependency timeout is closer to the root cause.

### **Important schema distinction**

In a workspace-based Log Analytics query I would commonly see:

```text
AppRequests
AppDependencies
AppExceptions
```

Some older Application Insights examples or app-specific query contexts use names such as:

```text
requests
dependencies
exceptions
```

So I would check the actual query scope/schema rather than assuming a table name.

> **In an interview, I would say:**
> “I would first identify the affected time window in Application Insights Failures, then query `AppRequests` for `ResultCode == "500"` or the full 5xx range. I would summarize by operation or URL to identify the worst endpoint, then use `OperationId` to correlate the failed request with `AppExceptions` and `AppDependencies`. That lets me move from ‘the API returned 500’ to the actual exception or downstream dependency that caused it.”

**Memory line:**
**Find the 500 → group it → follow its OperationId to the cause.**

**Interview trap:**
Do not stop after counting 500 errors. An HTTP 500 is usually the symptom; the real value of Application Insights is correlating it with exceptions and dependencies.

**Keywords:**
`AppRequests`, `ResultCode`, 5xx, `OperationId`, `AppExceptions`, Failures, KQL

**Likely follow-ups:**

* How would you find all 5xx responses rather than only 500?
* How would you correlate a failed request with an exception?
* What is `OperationId`?
* How would you alert if HTTP 500 rate increases?

### **T10-H05. How would you correlate a slow API request with its downstream dependency?**

**Answer:**
I would start with the slow request in Application Insights, capture its **`OperationId`**, and then correlate that request with `AppDependencies` using the same operation context. I would compare the request duration with dependency durations to identify whether the latency is in my application code or in a downstream HTTP service, database, storage service, or another dependency. Application Insights explicitly supports correlating dependency calls with their parent requests and viewing them as end-to-end transactions. ([Microsoft Learn][8])

### **Diagnostic flow**

```text
Slow API request
      ↓
Find request
      ↓
OperationId
      ↓
Related dependencies
      ↓
Which dependency consumed the time?
      ↓
Investigate that service
```

### **1. Find slow requests**

For example:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where DurationMs > 2000
| project
    TimeGenerated,
    Name,
    DurationMs,
    ResultCode,
    OperationId,
    Id
| order by DurationMs desc
```

Suppose I find:

```text
GET /orders
Duration = 4,800 ms
OperationId = abc123
```

---

### **2. Find dependencies for the same operation**

Then:

```kusto
AppDependencies
| where OperationId == "abc123"
| project
    Name,
    Target,
    DependencyType,
    DurationMs,
    Success,
    ResultCode
| order by DurationMs desc
```

I might discover:

```text
Request: GET /orders        4800 ms

Dependencies:
Azure SQL                    180 ms
Redis                         20 ms
Inventory API               4300 ms
```

The likely bottleneck is obvious:

```text
Inventory API
```

The current `AppDependencies` schema contains fields including `DurationMs`, `Target`, `DependencyType`, `OperationId`, `ParentId`, `ResultCode`, and `Success`. ([Microsoft Learn][9])

---

### **3. Join requests and dependencies**

For broader analysis:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where DurationMs > 2000
| project
    OperationId,
    RequestName = Name,
    RequestDurationMs = DurationMs
| join kind=inner (
    AppDependencies
    | project
        OperationId,
        DependencyName = Name,
        Target,
        DependencyType,
        DependencyDurationMs = DurationMs,
        DependencySuccess = Success
) on OperationId
| order by RequestDurationMs desc, DependencyDurationMs desc
```

This lets me find patterns such as:

```text
Slow endpoint
     ↓
same downstream dependency
     ↓
repeated across many requests
```

rather than analyzing only one transaction.

Microsoft documents correlating dependency calls and requests through operation IDs for exactly this type of investigation. ([Microsoft Learn][8])

---

### **4. Use Transaction Diagnostics / Application Map**

I would not always start by writing KQL manually.

Application Insights provides:

```text
Performance
Failures
Transaction Diagnostics
Application Map
```

which let me drill from:

```text
Slow request
     ↓
Dependency calls
     ↓
Downstream operation
```

Application Insights' transaction diagnostics view is specifically designed to display end-to-end requests and their related dependency operations. ([Microsoft Learn][8])

For a microservice system:

```text
Frontend
   ↓ 50 ms
Orders API
   ↓ 100 ms
Inventory API
   ↓ 3.5 sec
Database
   ↓ 50 ms
```

Application Map or distributed traces can quickly show which hop is responsible.

---

### **5. Follow the dependency into the downstream service**

If the downstream service is also instrumented correctly with distributed tracing:

```text
Service A request
     ↓
dependency call
     ↓
Service B request
```

the trace context should continue across services.

Conceptually:

```text
Trace ID = abc123
│
├── Orders API request
│     │
│     └── Inventory dependency
│
└── Inventory API request
      │
      └── SQL dependency
```

Now I can determine whether:

```text
Network call itself is slow
```

or:

```text
Service B is slow internally
```

or:

```text
Service B's database is slow
```

That is the advantage of distributed tracing over isolated logs.

---

### **6. Don't assume the slowest dependency is automatically the root cause**

I would also consider:

```text
Sequential dependencies
Parallel dependencies
Retries
Connection-pool waits
Application CPU time
Queueing
DNS / networking latency
```

For example:

```text
10 dependencies × 400 ms sequentially
```

can produce major latency even though no single dependency looks catastrophic.

So I compare the **critical path**, not just the largest number.

---

> **In an interview, I would say:**
> “I would start from the slow request in Application Insights and capture its `OperationId`. Then I would query or inspect the related dependency telemetry and compare each dependency's duration with the overall request duration. For example, if `/orders` takes 4.8 seconds and an inventory-service dependency takes 4.3 seconds, I would drill into that downstream service. With distributed tracing enabled, the dependency span in the first service correlates to the request span in the downstream service, so I can continue tracing until I find the actual bottleneck.”

**Memory line:**
**Slow request → OperationId → dependency spans → slow downstream service → continue the trace.**

**Interview trap:**
Do not diagnose latency from CPU alone. A request can be slow while application CPU and memory are perfectly healthy because it is waiting on a downstream dependency.

**Keywords:**
`OperationId`, `AppRequests`, `AppDependencies`, distributed tracing, Transaction Diagnostics, Application Map, latency

**Likely follow-ups:**

* How does `OperationId` help with correlation?
* What if the downstream application is not instrumented?
* How would you distinguish application latency from database latency?
* What is the relationship between a dependency span and a downstream request span?
