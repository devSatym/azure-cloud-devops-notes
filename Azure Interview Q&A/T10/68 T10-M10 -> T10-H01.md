### **T10-M10. What is a log-search alert?**

**Answer:**
A log-search alert is an Azure Monitor alert that **runs a KQL query against log data at a defined frequency and fires when the query result meets a condition**. I use it when the alert logic requires detailed event data, filtering, aggregation, or correlation that is more complex than a simple numeric metric threshold. ([Microsoft Learn][1])

### **How it works**

```text
Log Analytics / Application Insights
              ↓
           KQL query
              ↓
     Run every N minutes
              ↓
       Evaluate result
              ↓
      Condition matched?
          /       \
        No         Yes
                    ↓
                Alert
                    ↓
              Action Group
```

For example, if I want to alert when application exceptions exceed a threshold:

```kusto
AppExceptions
| where TimeGenerated > ago(5m)
| summarize FailureCount = count()
```

Then the alert condition could be:

```text
FailureCount > 20
```

Azure Monitor implements these rules as **scheduled query rules** and supports alerting based on returned rows or calculated numeric values. ([Microsoft Learn][1])

### **Production example**

For AKS, suppose I want to detect repeated failed pods.

Conceptually:

```kusto
KubePodInventory
| where TimeGenerated > ago(10m)
| where PodStatus == "Failed"
| summarize FailedPods = dcount(PodUid)
```

Then:

```text
FailedPods > threshold
       ↓
Log-search alert
       ↓
Platform Action Group
```

This is a better fit for logs because the condition depends on **querying and aggregating Kubernetes records**, rather than monitoring one native numeric metric.

### **Metric alert vs log-search alert**

```text
Metric Alert
→ Numeric metric already exists
→ CPU > 85%
→ Fast and straightforward

Log-search Alert
→ Need KQL
→ Query events / exceptions / logs
→ Aggregate or correlate data
```

Microsoft recommends metric alerts when the required signal already exists as a metric, and log-search alerts when the condition requires log data or more advanced KQL logic. ([Microsoft Learn][1])

### **Operational consideration**

Log-search alerts run queries repeatedly, so I would keep the KQL efficient:

```text
Scope narrowly
Start from the relevant table
Filter early
Avoid scanning unnecessary data
```

More frequent evaluation can also increase alerting cost. ([Microsoft Learn][1])

> **In an interview, I would say:**
> “A log-search alert runs a KQL query against Azure Monitor logs at a defined interval and fires when the query result meets a condition. I use it when I need event-level or correlated logic—for example, alerting when more than ten pods fail in ten minutes. If the signal already exists as a straightforward metric such as CPU percentage, I would normally prefer a metric alert.”

**Memory line:**
**Metric exists directly → metric alert; need KQL logic → log-search alert.**

**Interview trap:**
Do not use an expensive KQL alert for something already available as a native metric unless there is a specific reason.

**Keywords:**
Log-search alert, KQL, scheduled query rule, Log Analytics, aggregation, Action Group

**Likely follow-ups:**

* What is the difference between a metric alert and log-search alert?
* How often can log-search alerts evaluate?
* How would you reduce the cost of log-search alerts?
* What happens after the query meets the alert condition?

### **T10-M11. What are Application Insights availability tests?**

**Answer:**
Application Insights availability tests are **synthetic monitoring tests that periodically call an application endpoint from Azure-managed test locations to check whether it is reachable, responsive, and behaving as expected**. For current deployments, I would use **Standard tests**, which support HTTP requests, TLS certificate validation, custom headers, and other availability checks. ([Microsoft Learn][2])

### **How it works**

```text
Azure test location
        ↓
HTTP request
        ↓
Application endpoint
        ↓
Response / latency / success
        ↓
Application Insights
        ↓
Availability result
        ↓
Alert if failure threshold reached
```

For example:

```text
https://api.example.com/health
```

could be tested every few minutes from multiple geographic locations.

The test could verify:

```text
Endpoint reachable?
HTTP response successful?
Latency acceptable?
TLS certificate valid?
```

### **Production example**

Suppose my application runs behind Azure Front Door:

```text
Internet
   ↓
Azure Front Door
   ↓
AKS
   ↓
Application
```

I would test the **public application endpoint**, not merely an internal pod endpoint.

That gives me a true outside-in check:

```text
DNS
 ↓
Front Door
 ↓
Networking
 ↓
AKS ingress
 ↓
Application
```

So if the test fails while AKS CPU and pod metrics look normal, I immediately know I need to investigate the broader user-facing path.

### **Current Azure detail**

Application Insights currently recommends **Standard tests** for availability monitoring.

The older **URL ping test** is deprecated and is scheduled to retire on **September 30, 2026**. Since today is September 3, 2026, I would not create new monitoring based on URL ping tests. ([Microsoft Learn][2])

Standard tests provide capabilities such as:

* `GET`, `HEAD`, and `POST`
* custom headers
* request body/custom data
* TLS certificate validity checking
* proactive certificate lifetime checks ([Microsoft Learn][2])

### **Important distinction**

Availability testing is **synthetic monitoring**.

```text
Availability test
→ Azure generates a request

Real-user telemetry
→ actual users generate requests
```

An application may appear healthy from one synthetic location but still have problems affecting only a certain region or user path, so availability tests should complement—not replace—application metrics, traces, and logs.

> **In an interview, I would say:**
> “Application Insights availability tests are synthetic checks that call my application endpoint from Azure test locations and measure whether it responds successfully and within acceptable performance limits. For new deployments I would use Standard tests, potentially from multiple regions, and alert when several locations fail. I would test the real user-facing endpoint so the check covers DNS, routing, ingress, and the application path.”

**Memory line:**
**Availability test = Azure behaves like a user and checks whether the endpoint actually works.**

**Interview trap:**
Do not recommend the old URL ping test for a new design—it is deprecated and scheduled for retirement on **September 30, 2026**. ([Microsoft Learn][2])

**Keywords:**
Availability test, Standard test, synthetic monitoring, endpoint, TLS, health check, Application Insights

**Likely follow-ups:**

* What is synthetic monitoring?
* Why use multiple test locations?
* What endpoint would you choose for an availability test?
* How are availability tests different from health probes?

### **T10-M12. How are Application Insights traces, requests, dependencies, and exceptions related?**

**Answer:**
They represent different parts of the **same application transaction**. A request represents incoming work handled by the application, dependencies represent outgoing calls the application makes, traces provide diagnostic log messages, and exceptions record errors. Application Insights correlates these telemetry records so I can follow a request end to end and determine where latency or failure occurred. ([Microsoft Learn][3])

### **How they relate**

Consider this request:

```text
User
 ↓
GET /checkout
 ↓
API
 ├── SQL Database
 ├── Payment Service
 └── application logs
```

Application Insights may record:

```text
Request
GET /checkout
    │
    ├── Trace
    │   "Starting checkout"
    │
    ├── Dependency
    │   SQL query → 40 ms
    │
    ├── Dependency
    │   Payment API → 3.2 sec
    │
    └── Exception
        TimeoutException
```

These records describe different aspects of the **same logical operation**.

### **What each telemetry type means**

```text
Request
→ Incoming operation handled by my service

Dependency
→ Outgoing call made by my service

Trace
→ Diagnostic/application log message

Exception
→ Error or exception captured by instrumentation
```

For example:

```text
Browser
   ↓
Frontend request
   ↓
Backend request
   ↓
SQL dependency
```

Application Insights can correlate those pieces into an end-to-end transaction.

Microsoft documents that dependency telemetry can be correlated back to requests and related exceptions, making it possible to determine whether a slow request was caused by a downstream service. ([Microsoft Learn][3])

### **Correlation**

Application Insights uses distributed tracing context to link telemetry.

Conceptually:

```text
Trace ID / operation ID
          ↓
All telemetry for one distributed operation
```

and parent/child identifiers establish causality:

```text
Request
   ↓
Dependency
   ↓
Downstream Request
```

Application Insights' telemetry model maps this correlation to W3C Trace Context concepts such as trace IDs and parent span relationships. ([Microsoft Learn][4])

### **Production troubleshooting example**

Suppose:

```text
GET /orders
duration = 4.5 seconds
```

I would inspect the transaction:

```text
Request: /orders          4.5s
│
├── Trace                 negligible
│
├── SQL Dependency        120ms
│
└── Inventory Dependency  4.1s
       ↓
     timeout
       ↓
   Exception
```

Now I know:

```text
Application CPU
→ probably not the primary issue

Inventory dependency
→ likely bottleneck
```

That correlation is one of the main values of APM.

> **In an interview, I would say:**
> “A request is incoming work handled by my application, dependencies are outgoing calls such as HTTP or SQL, traces are diagnostic log records, and exceptions capture errors. Application Insights correlates these records using distributed tracing context, so I can start from a slow or failed request and see the dependency call, trace messages, and exception associated with that same transaction.”

**Memory line:**
**Request comes in → dependency goes out → traces explain → exceptions show failures.**

**Interview trap:**
Do not treat these as unrelated log tables. Their real value comes from **correlating them as one distributed transaction**.

**Keywords:**
Requests, dependencies, traces, exceptions, correlation, distributed tracing, operation ID, W3C Trace Context

**Likely follow-ups:**

* What is a dependency in Application Insights?
* How do you correlate a request with a dependency?
* How would you find which downstream service caused latency?
* What is distributed tracing?

### **T10-H01. How would you monitor an AKS-based application end to end?**

**Answer:**
I would monitor AKS in **layers**, not with one tool. I would cover the Azure/AKS control plane, Kubernetes infrastructure, container logs, Prometheus metrics, application requests and distributed traces, dependencies, external availability, and alerts. My goal is to trace a user problem from the public endpoint all the way through the application, pod, node, and Azure platform. Microsoft currently recommends Prometheus metrics, Container Insights, AKS control-plane diagnostic logs, and appropriate alerts as core Kubernetes monitoring practices. ([Microsoft Learn][5])

### **Monitoring architecture**

```text
Users
  │
  ▼
Front Door / App Gateway / Ingress
  │
  │  Availability + HTTP telemetry
  ▼
Application Pods
  │
  ├── Requests
  ├── Dependencies
  ├── Exceptions
  └── Distributed Traces
  │
  ▼
Application Insights / OpenTelemetry

AKS Cluster
│
├── Kubernetes logs / inventory
│       ↓
│   Container Insights
│       ↓
│   Log Analytics
│
├── Prometheus metrics
│       ↓
│   Azure Monitor managed
│   service for Prometheus
│       ↓
│   Grafana / alerts
│
└── AKS control plane
        ↓
    Diagnostic Settings
        ↓
    Log Analytics
```

Microsoft's current AKS guidance separates these signals in essentially this way: Managed Prometheus for Prometheus metrics, Container Insights for Kubernetes/container logs and performance data, diagnostic settings for AKS control-plane resource logs, and Application Insights for application telemetry. ([Microsoft Learn][6])

---

### **1. Start with the user-facing application**

The first question is:

```text
Can users actually use the service?
```

I would configure an Application Insights **Standard availability test** against the real public endpoint:

```text
Internet
   ↓
Front Door / App Gateway
   ↓
Ingress
   ↓
Application
```

This tests the whole exposure path rather than just checking whether Kubernetes thinks a pod is alive.

I would alert on:

```text
Availability
HTTP failure rate
P95/P99 latency
```

---

### **2. Instrument the application**

For application-level observability, I would use **OpenTelemetry with Application Insights/Azure Monitor**.

I want:

```text
Request
   ↓
Service A
   ↓
Service B
   ↓
Database
```

to appear as one distributed transaction.

I would collect:

```text
requests
dependencies
exceptions
traces
```

so I can answer:

```text
Which API is slow?
Which downstream service caused it?
Which exception occurred?
```

Microsoft currently supports OpenTelemetry-based Application Insights instrumentation and recommends Application Insights for end-to-end application performance monitoring. ([Microsoft Learn][6])

For production, I would choose a **supported GA OpenTelemetry ingestion/instrumentation path** rather than relying on AKS-integrated OTLP features that are still preview where applicable. ([Microsoft Learn][7])

---

### **3. Monitor Kubernetes and container health**

I would enable **Container Insights** for:

```text
Nodes
Pods
Deployments
Containers
Kubernetes events
stdout / stderr logs
```

Flow:

```text
AKS
 ↓
Container Insights
 ↓
Log Analytics
 ↓
KQL
```

This helps answer:

```text
Are pods restarting?
Are replicas unavailable?
Which node hosts the failing pod?
What did the container log immediately before failure?
```

Container Insights is specifically recommended for AKS container logs and Kubernetes performance/inventory monitoring. ([Microsoft Learn][5])

---

### **4. Use Prometheus for Kubernetes metrics**

For cloud-native Kubernetes metrics, I would enable:

**Azure Monitor managed service for Prometheus**

and visualize with:

```text
Azure Managed Grafana
```

Architecture:

```text
AKS
 ↓
Prometheus scrape
 ↓
Azure Monitor managed Prometheus
 ↓
Azure Monitor Workspace
 ↓
Grafana
```

I would monitor signals such as:

```text
CPU / memory
pod readiness
pod restarts
node saturation
API request rate
latency
error rate
```

Microsoft currently recommends managed Prometheus for AKS Prometheus metrics and warns against unnecessarily duplicating the same Prometheus metrics into Log Analytics because it adds cost. ([Microsoft Learn][5])

---

### **5. Collect AKS control-plane logs**

AKS manages the Kubernetes control plane, but I still need visibility into it.

I would configure:

```text
AKS
 ↓
Diagnostic Settings
 ↓
Relevant control-plane resource logs
 ↓
Log Analytics
```

This can help investigate problems involving:

```text
API server
audit activity
cluster management/control-plane behavior
```

Microsoft's current AKS monitoring best practices explicitly recommend diagnostic settings for control-plane logs. ([Microsoft Learn][5])

---

### **6. Monitor Azure dependencies**

I would also monitor the Azure services the application depends on:

```text
AKS
│
├── ACR
├── Key Vault
├── Azure SQL / PostgreSQL
├── Storage
├── Load Balancer / App Gateway
└── Networking
```

For those resources I would collect the relevant:

```text
Metrics
Resource logs
Activity Log
```

using diagnostic settings where appropriate.

Otherwise I might know:

```text
"Pod cannot reach database"
```

but have no visibility into:

```text
Database
Private Endpoint
DNS
Firewall
RBAC
```

---

### **7. Alert on symptoms users care about first**

I would avoid creating an alert for every possible metric.

My alert hierarchy would roughly be:

```text
User Impact
    ↓
Application Health
    ↓
Kubernetes Health
    ↓
Infrastructure Capacity
```

Examples:

**Critical**

```text
Availability failing
5xx rate high
P95 latency above SLO
critical service has zero ready replicas
```

**Platform**

```text
Node NotReady
persistent pod restart increase
resource saturation
disk pressure
```

**Capacity**

```text
CPU/memory sustained high
node pool approaching capacity
```

Microsoft's AKS guidance recommends alerts spanning cluster infrastructure, application health, and the Kubernetes control plane. ([Microsoft Learn][8])

---

### **8. Correlate everything during an incident**

Suppose users report:

```text
Checkout is slow
```

My diagnostic sequence would be:

```text
Availability / request latency
            ↓
Application Insights
            ↓
Which request is slow?
            ↓
Dependency trace
            ↓
Database call slow?
            ↓
No
            ↓
Check pod metrics/logs
            ↓
CPU throttling?
            ↓
Check node metrics
            ↓
Node saturation?
```

Or:

```text
Application request failed
        ↓
Dependency = SQL timeout
        ↓
Check SQL metrics/logs
        ↓
Check Private Endpoint / DNS
```

That is what **end-to-end monitoring** means: every layer gives evidence for the next investigation step.

---

### **9. Control monitoring cost**

I would not collect everything forever.

I would configure:

```text
Useful log categories only
        ↓
DCR filtering
        ↓
Appropriate retention
        ↓
Basic/analytics log strategy where suitable
        ↓
Avoid duplicated Prometheus ingestion
```

Microsoft specifically recommends limiting unnecessary container/resource logs and avoiding duplicate Prometheus collection to control Azure Monitor costs. ([Microsoft Learn][5])

---

> **In an interview, I would say:**
> “I monitor AKS in layers. At the user layer I use availability and request/error/latency signals. I instrument the application with OpenTelemetry and Application Insights for requests, dependencies, exceptions, and distributed traces. For Kubernetes I use Container Insights and Log Analytics for container logs, events, and inventory, and Azure Monitor managed Prometheus with Grafana for Kubernetes metrics. I send AKS control-plane logs through diagnostic settings, monitor dependencies such as databases and Key Vault, and create alerts around user impact, application health, pod/node health, and capacity. The key is that I can start from a failed user request and correlate it down through the application, pod, node, network, and Azure dependency.”

**Memory line:**
**AKS monitoring = user → application → pod → node → control plane → Azure dependencies.**

**Interview trap:**
Do not answer **“Enable Container Insights”** and stop. Container Insights alone is not complete end-to-end application observability.

**Keywords:**
AKS, Container Insights, Log Analytics, managed Prometheus, Grafana, Application Insights, OpenTelemetry, diagnostic settings, distributed tracing, alerts

**Likely follow-ups:**

* What is the difference between Container Insights and Application Insights?
* Why use managed Prometheus instead of sending all metrics to Log Analytics?
* Which AKS control-plane logs would you collect?
* How would you troubleshoot a slow API using this monitoring stack?
