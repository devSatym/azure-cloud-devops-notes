### **T10-K02. What does `project` do?**

**Answer:**
The KQL `project` operator **selects which columns should appear in the query output**. I use it to keep only the fields that matter, which makes troubleshooting results cleaner and easier to read.

### **How it works**

Example:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| project TimeGenerated, Name, ResultCode, DurationMs
```

The flow is:

```text
AppRequests
     ↓
Filter last hour
     ↓
Keep only:
TimeGenerated
Name
ResultCode
DurationMs
```

If the original table has dozens of columns, `project` reduces the output to only the useful ones.

### **Production example**

Suppose I am investigating HTTP failures.

Instead of returning every request field:

```kusto
AppRequests
| where Success == false
```

I could use:

```kusto
AppRequests
| where Success == false
| project
    TimeGenerated,
    Name,
    ResultCode,
    DurationMs,
    OperationId
```

That gives me the fields I actually need for troubleshooting.

### **Important distinction**

```text
where
→ filters rows

project
→ selects columns
```

For example:

```kusto
AppRequests
| where ResultCode == "500"
| project Name, ResultCode
```

means:

```text
First:
keep only HTTP 500 rows

Then:
show only Name and ResultCode columns
```

`project` can also create renamed or calculated output columns, but its main interview-level purpose is **shaping the result set**.

**Memory line:**
**`where` chooses the rows; `project` chooses the columns.**

**Interview trap:**
Do not confuse `project` with `where`. `project` does not filter records based on a condition.

**Keywords:**
`project`, columns, output shaping, KQL, field selection

### **T10-K03. What does `summarize` do?**

**Answer:**
The KQL `summarize` operator **aggregates rows into calculated results**, optionally grouped by one or more fields. I use it for things like counting failures, calculating averages, finding maximum values, or grouping events by resource, status, endpoint, or time interval.

### **How it works**

Example:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| summarize RequestCount = count() by ResultCode
```

This transforms many request records into:

```text
ResultCode    RequestCount
200           12000
400             350
500              47
```

Conceptually:

```text
Thousands of rows
      ↓
Group by ResultCode
      ↓
Count each group
      ↓
Small summary table
```

### **Common aggregation functions**

Examples include:

```text
count()
sum()
avg()
min()
max()
dcount()
```

For example:

```kusto
AppRequests
| summarize
    AvgDuration = avg(DurationMs),
    MaxDuration = max(DurationMs)
    by Name
```

This could tell me:

```text
GET /orders
Average = 420 ms
Maximum = 3.8 sec
```

### **Production example**

To find which AKS namespaces are producing the most records:

```kusto
KubePodInventory
| where TimeGenerated > ago(1h)
| summarize Events = count() by Namespace
| order by Events desc
```

Or to count application failures:

```kusto
AppRequests
| where Success == false
| summarize Failures = count() by Name
```

This is much more useful than manually examining thousands of individual rows.

### **Important distinction**

Without a `by` clause:

```kusto
AppRequests
| summarize Total = count()
```

I get one aggregated result.

With:

```kusto
AppRequests
| summarize Total = count() by ResultCode
```

I get one result **per ResultCode group**.

```text
summarize
→ calculate

by
→ decide how to group
```

**Memory line:**
**`summarize` turns many rows into useful aggregated numbers.**

**Interview trap:**
Do not assume `summarize` only counts records. It supports many aggregate functions such as `avg()`, `sum()`, `max()`, and `dcount()`.

**Keywords:**
`summarize`, aggregation, `count()`, `avg()`, grouping, `by`, KQL

### **T10-K04. What does `extend` do?**

**Answer:**
The KQL `extend` operator **adds one or more calculated columns to the current result set without removing the existing columns**. I use it when I need to derive a value during a query, such as converting units, categorizing responses, extracting data, or calculating a new field.

### **How it works**

Suppose duration is stored in milliseconds:

```kusto
AppRequests
| extend DurationSeconds = DurationMs / 1000.0
```

Now the result contains:

```text
Original columns
+
DurationSeconds
```

Conceptually:

```text
Existing row
│
├── Name
├── ResultCode
├── DurationMs
└── DurationSeconds  ← calculated with extend
```

### **Production example**

I could classify HTTP responses:

```kusto
AppRequests
| extend StatusClass = case(
    toint(ResultCode) >= 500, "Server Error",
    toint(ResultCode) >= 400, "Client Error",
    "Success"
)
```

Then summarize them:

```kusto
AppRequests
| extend StatusClass = case(
    toint(ResultCode) >= 500, "Server Error",
    toint(ResultCode) >= 400, "Client Error",
    "Success"
)
| summarize Requests = count() by StatusClass
```

That could produce:

```text
Success        15,000
Client Error      500
Server Error       40
```

### **`extend` vs `project`**

This is the important distinction:

```text
extend
→ adds calculated columns
→ keeps existing columns

project
→ selects/restructures output columns
```

For example:

```kusto
AppRequests
| extend IsServerError = toint(ResultCode) >= 500
```

keeps the existing request data and adds `IsServerError`.

Whereas:

```kusto
AppRequests
| project Name, ResultCode
```

returns only those selected fields.

### **Another useful example**

Extracting part of a string:

```kusto
AppRequests
| extend Method = tostring(split(Name, " ")[0])
```

or calculating a normalized metric:

```kusto
AppRequests
| extend DurationSeconds = DurationMs / 1000.0
```

**Memory line:**
**`extend` keeps the row and adds a calculated column to it.**

**Interview trap:**
Do not describe `extend` as permanently modifying the underlying Log Analytics table. It only creates columns within the query result.

**Keywords:**
`extend`, calculated column, derived field, expressions, KQL, transformation

### **T10-K05. What does `order by` do?**

**Answer:**
The KQL `order by` operator **sorts query results by one or more columns**, either ascending or descending. I commonly use it to put the newest events, highest failure counts, or slowest requests at the top of the result.

### **How it works**

For newest events first:

```kusto
AzureActivity
| order by TimeGenerated desc
```

For oldest first:

```kusto
AzureActivity
| order by TimeGenerated asc
```

The keywords are:

```text
asc
→ ascending

desc
→ descending
```

### **Production example**

To find the slowest API requests:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| project TimeGenerated, Name, DurationMs
| order by DurationMs desc
```

This gives:

```text
Slowest request
      ↓
next slowest
      ↓
next slowest
```

Similarly, after aggregation:

```kusto
AppRequests
| where Success == false
| summarize Failures = count() by Name
| order by Failures desc
```

shows the endpoints with the most failures first.

### **Using multiple columns**

You can sort on more than one field:

```kusto
AppRequests
| order by ResultCode asc, DurationMs desc
```

Conceptually:

```text
First group/order by ResultCode
      ↓
Within those results,
order by DurationMs descending
```

### **Important distinction**

`order by` only changes the **presentation order** of returned rows.

It does not:

```text
filter rows
aggregate data
select columns
```

Those are handled by operators such as:

```text
where
summarize
project
```

**Memory line:**
**`order by` controls which results appear first.**

**Interview trap:**
Do not confuse sorting with limiting. If I want only the top few results, I would typically combine sorting with `take`, `top`, or another limiting operation.

**Keywords:**
`order by`, `asc`, `desc`, sorting, KQL
