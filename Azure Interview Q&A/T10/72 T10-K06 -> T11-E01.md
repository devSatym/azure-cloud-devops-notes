### **T10-K06. What is `bin()` used for?**

**Answer:**
In KQL, `bin()` is used to **group numeric or datetime values into fixed-size buckets**. In monitoring queries, I most commonly use it with `TimeGenerated` so I can aggregate events into intervals such as **5 minutes, 15 minutes, or 1 hour**.

### **How it works**

Suppose I have thousands of request records.

Instead of looking at every timestamp individually:

```text
10:01:03
10:01:19
10:02:45
10:04:58
...
```

I can group them into five-minute windows:

```kusto
AppRequests
| summarize Requests = count()
    by bin(TimeGenerated, 5m)
```

Conceptually:

```text
Raw timestamps
      ↓
bin(TimeGenerated, 5m)
      ↓
10:00–10:05
10:05–10:10
10:10–10:15
      ↓
Aggregate each interval
```

### **Production example**

To see HTTP failures over time:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where Success == false
| summarize Failures = count()
    by bin(TimeGenerated, 5m)
| order by TimeGenerated asc
```

This helps me identify patterns such as:

```text
10:00  2 failures
10:05  3 failures
10:10  48 failures  ← deployment/problem begins
10:15  63 failures
```

That is much more useful operationally than one total such as:

```text
116 failures in the last hour
```

because now I can correlate the spike with a deployment or infrastructure event.

### **Another common use**

Average latency over 10-minute intervals:

```kusto
AppRequests
| where TimeGenerated > ago(6h)
| summarize AvgLatency = avg(DurationMs)
    by bin(TimeGenerated, 10m)
```

This is useful for:

* charts
* trends
* alert queries
* incident timelines
* before/after deployment comparisons

### **Important distinction**

```text
summarize
→ performs aggregation

bin()
→ defines the buckets used for that aggregation
```

They are commonly used together:

```kusto
| summarize count() by bin(TimeGenerated, 5m)
```

**Memory line:**
**`bin()` puts timestamps or numbers into fixed-size buckets.**

**Interview trap:**
`bin()` does not itself count or average anything. It creates the grouping intervals; `summarize` performs the aggregation.

**Keywords:**
`bin()`, time bucket, aggregation, `TimeGenerated`, time series, KQL

### **T10-K07. How would you count events grouped by resource?**

**Answer:**
I would use KQL's `summarize` operator with `count()` and group by the column that identifies the resource. For Azure resource telemetry, that might be `_ResourceId`, `Resource`, `ResourceId`, or another resource-specific field depending on the table.

### **Basic pattern**

```kusto
AzureActivity
| where TimeGenerated > ago(1h)
| summarize EventCount = count()
    by _ResourceId
| order by EventCount desc
```

Conceptually:

```text
All events
    ↓
Group by resource
    ↓
Count rows in each group
    ↓
Resource A → 120
Resource B → 45
Resource C → 8
```

### **Production example**

Suppose I want to identify which Azure resources have generated the most failed Activity Log operations:

```kusto
AzureActivity
| where TimeGenerated > ago(24h)
| where ActivityStatusValue == "Failure"
| summarize FailureCount = count()
    by _ResourceId
| order by FailureCount desc
```

This can quickly reveal:

```text
AKS cluster        37
Storage Account    12
VM                   3
```

Then I can investigate the resource with the highest failure count first.

### **With time grouping**

If I also want to know **when** events occurred:

```kusto
AzureActivity
| where TimeGenerated > ago(24h)
| summarize Events = count()
    by _ResourceId, bin(TimeGenerated, 1h)
```

Now I get:

```text
Resource
   +
Hourly timeline
```

which helps identify spikes.

### **Important distinction**

The exact resource identifier column depends on the table.

For example:

```text
AzureActivity
Container logs
Application Insights
Key Vault logs
```

do not necessarily expose identical column names.

So in production I would inspect the table schema rather than blindly assuming `_ResourceId` exists everywhere.

> **In an interview, I would say:**
> “I would use `summarize count()` and group by the resource identifier. For example, `AzureActivity | summarize EventCount=count() by _ResourceId`. If I also need a trend, I would add `bin(TimeGenerated, 1h)` so I can see event counts per resource over time.”

**Memory line:**
**Count by resource = `summarize count() by <resource-column>`.**

**Interview trap:**
Do not assume every Azure Monitor table uses the same resource column name.

**Keywords:**
`summarize`, `count()`, `_ResourceId`, grouping, `bin()`, KQL

### **T10-K08. How would you calculate the number of failures during the last hour?**

**Answer:**
I would first filter the data to the **last hour**, then filter for the table's definition of failure, and finally use `summarize count()` to calculate the total.

For Application Insights requests:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where Success == false
| summarize Failures = count()
```

The logic is:

```text
AppRequests
     ↓
Last 1 hour
     ↓
Failed requests only
     ↓
Count
```

### **For HTTP 5xx failures**

If failure specifically means server-side HTTP errors:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where toint(ResultCode) between (500 .. 599)
| summarize Failures = count()
```

This is more specific than:

```kusto
Success == false
```

because `Success == false` may include other unsuccessful outcomes depending on the telemetry.

### **Grouped by endpoint**

To understand where failures occur:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where Success == false
| summarize Failures = count()
    by Name
| order by Failures desc
```

This might show:

```text
POST /checkout    47
GET /orders       11
GET /profile       2
```

### **Grouped over time**

To see whether failures are increasing:

```kusto
AppRequests
| where TimeGenerated > ago(1h)
| where Success == false
| summarize Failures = count()
    by bin(TimeGenerated, 5m)
| order by TimeGenerated asc
```

Now I can distinguish:

```text
60 failures evenly spread
```

from:

```text
55 failures immediately after deployment
```

which is much more useful during troubleshooting.

### **Important distinction**

The definition of **failure depends on the data source**.

For example:

```text
AppRequests
→ Success == false / ResultCode

AzureActivity
→ ActivityStatusValue == "Failure"

Other tables
→ may use different fields
```

So I would always use the failure indicator appropriate for that table.

**Memory line:**
**Last hour → failure filter → `summarize count()`.**

**Interview trap:**
Don't assume every table has a `Success` column. KQL syntax may be similar, but telemetry schemas differ.

**Keywords:**
`ago(1h)`, `where`, `Success`, `ResultCode`, `summarize`, `count()`

### **T11-E01. What is Azure Key Vault?**

**Answer:**
Azure Key Vault is an Azure service for **securely storing and controlling access to sensitive information** such as secrets, cryptographic keys, and certificates. Instead of embedding credentials in source code, configuration files, or pipeline YAML, applications can authenticate using Microsoft Entra ID—often through Managed Identity or Workload Identity—and retrieve only the secrets they are authorized to access.

### **How it fits into an application**

```text
Application / AKS Pod / VM
          ↓
Managed Identity /
Workload Identity
          ↓
Microsoft Entra ID
          ↓
Authorization
          ↓
Azure Key Vault
          ↓
Secret / Key / Certificate
```

The application does **not** need to store:

```text
database password
storage credential
API key
certificate private key
```

inside its own source code.

### **What Key Vault can protect**

Key Vault commonly handles:

```text
Azure Key Vault
│
├── Secrets
│   └── passwords, connection strings, API tokens
│
├── Keys
│   └── cryptographic keys
│
└── Certificates
    └── TLS / application certificates
```

### **Production example**

Suppose an application running in AKS needs a database secret.

A poor design is:

```text
GitHub
   ↓
Kubernetes YAML
   ↓
DATABASE_PASSWORD=...
```

A better design is:

```text
AKS Pod
   ↓
AKS Workload Identity
   ↓
Microsoft Entra ID
   ↓
Key Vault RBAC
   ↓
Azure Key Vault
   ↓
Database secret
```

Depending on the application design, the workload can retrieve the secret through an SDK or integrate through the Key Vault CSI driver.

### **Security model**

There are two separate concerns:

```text
Authentication
→ Who is the workload?

Authorization
→ What may it access?
```

Microsoft Entra ID establishes identity.

Key Vault access is then controlled using mechanisms such as **Azure RBAC** in modern deployments.

For example:

```text
Application Identity
       ↓
Key Vault Secrets User
       ↓
Specific Key Vault scope
```

rather than granting broad subscription-level access.

### **Important distinction**

Key Vault does not eliminate every secret automatically.

It gives you a secure place and controlled mechanism for managing them.

Even better, where Azure supports identity-based authentication, I would eliminate the password completely:

```text
Application
    ↓
Managed Identity
    ↓
Azure SQL / Storage / Key Vault
```

rather than creating a credential simply so I can store it inside Key Vault.

**Memory line:**
**Key Vault centralizes sensitive secrets, keys, and certificates so applications don't have to embed them.**

**Interview trap:**
Do not say Key Vault is just a password store. It manages **secrets, cryptographic keys, and certificates**, with different capabilities for each.

**Keywords:**
Azure Key Vault, secrets, keys, certificates, Microsoft Entra ID, Managed Identity, Workload Identity, Azure RBAC
