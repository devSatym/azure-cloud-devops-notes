### **T10-M02. What is the Azure Activity Log?**

**Answer:**
The Azure Activity Log is a **subscription-level control-plane log** that records events involving Azure Resource Manager, such as creating, updating, deleting, or modifying Azure resources. I use it mainly to answer questions like **who changed what, when, and whether the operation succeeded**. Azure collects it automatically. ([Microsoft Learn][1])

### **How it works**

Think of it as an audit trail for Azure management operations:

```text
User / Service Principal / Pipeline
              ↓
      Azure Resource Manager
              ↓
       Management operation
              ↓
        Azure Activity Log
```

Examples include:

```text
VM created
NSG modified
Storage Account deleted
RBAC assignment changed
Deployment failed
Service Health event
```

An Activity Log event can contain information such as:

* operation name
* resource
* caller
* status
* timestamp
* subscription
* correlation ID

### **Production example**

Suppose a production NSG suddenly contains an unexpected rule.

My first question is:

```text
Was this changed through Azure control plane?
```

I would inspect the Activity Log to determine:

```text
Who made the change?
        ↓
When?
        ↓
From which operation?
        ↓
Succeeded or failed?
```

That could reveal a user, service principal, Terraform pipeline, or other Azure management operation.

### **Retention / export**

Azure retains Activity Log entries in Azure for **90 days** by default. If I need longer retention, centralized KQL queries, or SIEM integration, I can export the Activity Log using a subscription-level diagnostic setting. ([Microsoft Learn][1])

For example:

```text
Activity Log
     ↓
Diagnostic Setting
     ↓
Log Analytics Workspace
```

Then the data can appear in the:

```text
AzureActivity
```

table for KQL analysis. ([Microsoft Learn][1])

### **Important distinction**

The Activity Log is mainly about the **control plane**:

```text
Create VM
Delete VNet
Modify NSG
Update resource
```

It generally does **not** tell me detailed operations happening inside the service's data plane.

For example:

```text
Activity Log
→ Key Vault configuration changed

Key Vault resource logs
→ secret was accessed
```

> **In an interview, I would say:**
> “The Azure Activity Log is the subscription-level control-plane audit log. It records Azure management events such as creating, updating, deleting, or changing resources, along with information like the caller, operation, status, and timestamp. I use it mainly to investigate who changed Azure infrastructure and when. For longer retention or KQL analysis, I export it to Log Analytics using diagnostic settings.”

**Memory line:**
**Activity Log = who changed Azure infrastructure through the control plane.**

**Interview trap:**
Do not say the Activity Log contains all application or service activity. It primarily records **Azure control-plane events**, not detailed resource data-plane operations.

**Keywords:**
Activity Log, control plane, subscription, ARM, audit trail, `AzureActivity`, 90 days

**Likely follow-ups:**

* Does Azure collect Activity Logs automatically?
* What is the difference between Activity Logs and resource logs?
* How would you retain Activity Logs for longer than 90 days?
* How would you find who deleted an Azure resource?

### **T10-M03. What is the difference between Activity Logs and resource logs?**

**Answer:**
The main difference is scope and purpose: **Activity Logs record subscription-level Azure control-plane operations**, while **resource logs contain detailed operational or data-plane information generated by an individual Azure resource**. Activity Logs help me understand changes to the infrastructure; resource logs help me understand what the resource itself is doing. ([Microsoft Learn][2])

### **Side-by-side**

| Activity Log                             | Resource Logs                                                                 |
| ---------------------------------------- | ----------------------------------------------------------------------------- |
| Subscription-level                       | Resource-specific                                                             |
| Control-plane events                     | Service/resource operations                                                   |
| Collected automatically                  | Generated automatically, but usually must be routed using diagnostic settings |
| Who changed a resource?                  | What happened inside the resource?                                            |
| ARM operations                           | Service-specific categories                                                   |
| Example: Key Vault configuration changed | Example: Key Vault secret accessed                                            |

### **Example: Azure Key Vault**

Suppose I have this sequence:

```text
Admin changes Key Vault networking
              ↓
         Activity Log
```

because this is an Azure management/control-plane operation.

But:

```text
Application requests a secret
              ↓
       Key Vault resource log
```

because this is an operation performed against the Key Vault service itself.

Microsoft describes resource logs as giving insight into operations performed by an Azure resource—for example, retrieving a Key Vault secret or making a database request. ([Microsoft Learn][3])

### **Another example**

For Azure SQL:

```text
Activity Log
→ SQL database created
→ firewall configuration changed
```

versus:

```text
Resource Logs
→ database-specific auditing
→ query/security/service events
```

The exact resource-log categories differ by Azure service.

### **Collection difference**

Activity Log:

```text
Azure
  ↓
Activity Log automatically available
```

Resource logs:

```text
Azure Resource
     ↓
generates resource logs
     ↓
Diagnostic Setting
     ↓
Log Analytics / Storage /
Event Hubs / Partner
```

Azure resources generate resource logs, but you normally need a diagnostic setting to send them to a destination such as Log Analytics. ([Microsoft Learn][2])

### **Important distinction**

This maps closely to:

```text
Activity Log
→ Control plane

Resource Logs
→ Resource/service operations,
  often including data-plane activity
```

But I would avoid saying **every** data-plane event from every Azure service is available automatically—resource-log categories depend on the specific service.

> **In an interview, I would say:**
> “Activity Logs are subscription-level control-plane logs, so I use them to investigate Azure management operations such as who changed an NSG or deleted a VM. Resource logs are generated by individual Azure services and provide more detailed information about what that resource is doing, such as Key Vault access or database operations. Activity Logs are automatically available, while resource logs normally need diagnostic settings to route them to Log Analytics or another destination.”

**Memory line:**
**Activity Log = what happened to the Azure resource; resource log = what happened inside the resource.**

**Interview trap:**
Do not say Activity Logs and resource logs are interchangeable. Their **scope, content, and collection model are different**.

**Keywords:**
Activity Log, resource logs, control plane, data plane, diagnostic settings, subscription-level, resource-specific

**Likely follow-ups:**

* Are resource logs automatically sent to Log Analytics?
* Give an example using Key Vault.
* Which log would you check if someone deleted a VM?
* Which log would you check if an application accessed a Key Vault secret?

### **T10-M04. What are diagnostic settings?**

**Answer:**
Diagnostic settings are Azure Monitor configurations that define **which platform telemetry to collect from a resource and where to send it**. I typically use them to route resource logs—and where supported platform metrics or the Activity Log—to destinations such as Log Analytics, Storage, Event Hubs, or supported partner integrations. ([Microsoft Learn][4])

### **How it works**

```text
Azure Resource
     ↓
Logs / Metrics
     ↓
Diagnostic Setting
     │
     ├── Which categories?
     │
     └── Which destination?
     ↓
Log Analytics / Storage /
Event Hubs / Partner
```

For example, a Key Vault might expose categories such as:

```text
AuditEvent
```

I choose the relevant categories and configure where those records should go.

### **Production example**

For a production Key Vault:

```text
Key Vault
   ↓
Audit logs
   ↓
Diagnostic Setting
   ↓
Log Analytics Workspace
   ↓
KQL / Alerting
```

That gives the operations or security team a queryable history of relevant Key Vault events.

A Terraform-managed implementation might conceptually configure:

```hcl
resource "azurerm_monitor_diagnostic_setting" "keyvault" {
  name                       = "diag-keyvault"
  target_resource_id         = azurerm_key_vault.main.id
  log_analytics_workspace_id = azurerm_log_analytics_workspace.main.id

  enabled_log {
    category = "AuditEvent"
  }
}
```

The important point in an interview is the architecture, not memorizing every provider argument.

### **Resource-specific configuration**

Diagnostic settings are generally configured **per Azure resource**.

Microsoft currently allows a resource to have multiple diagnostic settings, with each setting defining selected categories and destinations. ([Microsoft Learn][4])

This allows patterns such as:

```text
Production Resource
│
├── Security logs → Event Hub → SIEM
│
└── Operational logs → Log Analytics
```

### **Activity Log exception**

For the Azure Activity Log, the diagnostic setting is created at the:

```text
Subscription scope
```

rather than on an individual resource. ([Microsoft Learn][5])

### **Why they matter**

Without the correct diagnostic configuration:

```text
Resource generates telemetry
        ↓
but it may not reach
your Log Analytics workspace
```

This is why, when someone says:

> “The resource is working but no logs appear in Log Analytics,”

one of my first checks is:

```text
Diagnostic setting
→ enabled?
→ correct log category?
→ correct destination?
```

> **In an interview, I would say:**
> “Diagnostic settings tell Azure Monitor which resource log or platform metric categories I want to collect and where to route them. For example, I can send Key Vault audit logs to a Log Analytics workspace for KQL queries and alerting, send them to Event Hubs for a SIEM, or archive them to Storage. They are important because resource logs are not automatically sent to Log Analytics just because the workspace exists.”

**Memory line:**
**Diagnostic setting = what telemetry to send + where to send it.**

**Interview trap:**
Creating a Log Analytics workspace does **not** automatically make every Azure resource send its resource logs there.

**Keywords:**
Diagnostic settings, log categories, metrics, Log Analytics, Event Hubs, Storage, resource logs

**Likely follow-ups:**

* Are diagnostic settings configured globally or per resource?
* Do all Azure resources expose the same log categories?
* What would you check if resource logs stopped reaching Log Analytics?
* How would you create diagnostic settings at scale?

### **T10-M05. Where can diagnostic logs be sent?**

**Answer:**
Using Azure Monitor diagnostic settings, resource logs can currently be sent to **a Log Analytics workspace, an Azure Storage account, Azure Event Hubs, or supported Azure Monitor partner solutions**. I choose the destination based on whether I need analytics, archival, streaming to another platform, or third-party monitoring integration. ([Microsoft Learn][2])

### **The four main destinations**

```text
Azure Resource Logs
       ↓
Diagnostic Setting
       │
       ├── Log Analytics Workspace
       ├── Azure Storage
       ├── Azure Event Hubs
       └── Azure Monitor Partner Solution
```

### **1. Log Analytics workspace**

Use it when I need:

```text
KQL queries
dashboards/workbooks
log alerts
cross-resource correlation
troubleshooting
```

Example:

```text
AKS / Key Vault / Firewall
           ↓
      Log Analytics
           ↓
           KQL
```

This is usually my main operational-analysis destination. ([Microsoft Learn][2])

---

### **2. Azure Storage**

Use Storage when I need:

```text
long-term archive
audit retention
lower-cost storage
compliance evidence
```

For example:

```text
Security Logs
     ↓
Storage Account
     ↓
Long-term retention
```

Microsoft also notes that immutable storage policies can be useful where logs need stronger tamper protection. ([Microsoft Learn][4])

---

### **3. Azure Event Hubs**

Use Event Hubs when I want to **stream telemetry to another system**.

For example:

```text
Azure Resource
      ↓
Diagnostic Setting
      ↓
Event Hub
      ↓
External SIEM / analytics platform
```

This is useful for integrations with external monitoring or security platforms. ([Microsoft Learn][6])

---

### **4. Azure Monitor partner solutions**

Some supported monitoring partners can receive telemetry directly through diagnostic settings.

Conceptually:

```text
Azure
  ↓
Diagnostic Setting
  ↓
Partner monitoring platform
```

The exact integrations depend on the supported partner service. ([Microsoft Learn][4])

### **Production design example**

I could configure:

```text
Azure Firewall
│
├── Log Analytics
│      ↓
│   operations + KQL alerts
│
├── Event Hub
│      ↓
│   corporate SIEM
│
└── Storage
       ↓
    compliance archive
```

A diagnostic setting can send data to multiple destination types, subject to Azure's diagnostic-setting rules and service-specific support. ([Microsoft Learn][4])

### **How I choose**

```text
Need interactive investigation?
→ Log Analytics

Need cheap/long-term archive?
→ Storage

Need streaming to SIEM/external tool?
→ Event Hubs

Need direct supported third-party integration?
→ Partner solution
```

> **In an interview, I would say:**
> “Azure Monitor diagnostic settings can route resource logs to Log Analytics, Azure Storage, Event Hubs, or supported partner solutions. I use Log Analytics for KQL and operational troubleshooting, Storage for long-term retention or audit, and Event Hubs when logs need to stream into an external SIEM or analytics platform.”

**Memory line:**
**Analyze → Log Analytics; archive → Storage; stream → Event Hubs; integrate → partner solution.**

**Interview trap:**
Do not assume the destination is always Log Analytics. Diagnostic settings are specifically designed to support **different operational, archival, and integration requirements**.

**Keywords:**
Log Analytics, Storage Account, Event Hubs, partner solutions, diagnostic settings, archive, streaming

**Likely follow-ups:**

* Which destination would you use for a SIEM?
* Which destination is best for long-term audit retention?
* Can a diagnostic setting send data to multiple destinations?
* Can the destination be in another subscription?
