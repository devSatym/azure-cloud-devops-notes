## **T20-M02. What is Azure Advisor?**

**Answer:**
Azure Advisor is a **personalized Azure optimization service** that analyzes your deployed resources, configuration, and usage telemetry and then gives recommendations to improve the environment.

Microsoft currently groups Advisor recommendations into five categories:

```text
Reliability
Security
Performance
Cost
Operational Excellence
```

So the simplest interview definition is:

> **Azure Advisor looks at how my Azure resources are configured and used, then recommends changes based on Azure best practices.**

Microsoft describes Advisor as a digital cloud assistant that generates proactive, actionable recommendations from resource configuration and usage telemetry. ([Microsoft Learn][1])

---

### **How it works**

```text
Azure resources
     ↓
Configuration + usage telemetry
     ↓
Azure Advisor analysis
     ↓
Recommendations
     ↓
Engineer reviews
     ↓
Accept / postpone / dismiss
```

Advisor is not simply:

```text
"Here is generic Azure documentation."
```

Its recommendations are based on the resources running in **your environment**.

---

### **The five recommendation categories**

#### **1. Reliability**

Focused on maintaining availability and resilience.

Examples can include:

```text
Improve VM availability
Use zone-redundant architecture
Configure backup
Improve service resiliency
```

---

#### **2. Security**

Security recommendations help identify configurations that could weaken the workload.

Conceptually:

```text
Resource configuration
       ↓
Security recommendation
       ↓
Improve security posture
```

Azure security recommendations can integrate with broader Defender for Cloud capabilities depending on the scenario.

---

#### **3. Performance**

Examples:

```text
Resource configuration
      ↓
Advisor detects performance opportunity
      ↓
Recommended configuration change
```

Goal:

```text
better workload performance
```

without simply overprovisioning everything.

---

#### **4. Cost**

This is especially important for FinOps.

Advisor can detect things such as:

```text
Idle resources
Underutilized VMs
Oversized VMs
Reservation opportunities
Savings Plan opportunities
```

Microsoft's current cost-recommendation catalog covers many services including VM/VMSS, App Service, AKS, Storage, Azure Monitor, Container Apps, Cosmos DB, and others. ([Microsoft Learn][2])

---

#### **5. Operational Excellence**

These recommendations focus on:

```text
resource manageability
deployment practices
operational efficiency
```

So Advisor isn't just a:

```text
cost optimization tool
```

even though cost is one of its most commonly discussed uses.

---

### **Example**

Suppose:

```text
VM:
Standard_D8s_v5

CPU:
8%

Memory:
20%

Most of the week
```

Advisor may detect:

```text
VM substantially underutilized
```

and recommend something such as:

```text
Resize D8s_v5
      ↓
smaller/cheaper SKU
```

with potential savings.

Advisor's current VM rightsizing process analyzes utilization metrics including CPU, memory, and outbound network usage and attempts to recommend a cheaper SKU that can still support observed demand. ([Microsoft Learn][3])

---

### **Advisor does not automatically mean “apply everything”**

This is very important.

Suppose Advisor says:

```text
Resize production VM
D8s_v5 → D4s_v5
```

Before applying it, I would check:

```text
peak usage
business cycles
memory
disk throughput
network throughput
application SLOs
HA requirements
future growth
```

because Advisor gives:

```text
recommendation
```

not:

```text
absolute architectural truth
```

---

### **Recommendations can be configured**

For VM/VMSS rightsizing, Advisor currently lets administrators adjust the analysis lookback period to values including:

```text
7
14
21
30
60
90 days
```

This can be useful if a 7-day sample doesn't capture monthly or seasonal workload behavior. ([Microsoft Learn][3])

Example:

```text
Month-end financial system

Normal week:
10% CPU

Month end:
80% CPU
```

A longer lookback may provide a better picture.

---

### **Advisor vs Azure Monitor**

Don't confuse them:

```text
Azure Monitor
→ observes telemetry
→ metrics, logs, alerts

Azure Advisor
→ analyzes configuration/usage
→ gives optimization recommendations
```

They complement each other.

---

### **Advisor vs Cost Management**

Similarly:

```text
Cost Management
→ analyze actual cloud spending

Advisor
→ recommend ways to optimize
  resources and costs
```

Microsoft Cost Management surfaces Azure Advisor recommendations as part of its optimization workflow. ([Microsoft Learn][4])

---

### **Strong interview answer**

> “Azure Advisor is a personalized optimization service that analyzes the configuration and usage telemetry of my Azure resources and generates recommendations across Reliability, Security, Performance, Cost, and Operational Excellence. For example, it may identify an underutilized VM and recommend resizing or shutting it down. I treat Advisor as a decision-support tool rather than applying recommendations blindly; for production changes I validate workload peaks, performance requirements, SLOs, and business cycles first.”

**Memory line:**
**Azure Advisor = Azure analyzes my environment and recommends best-practice optimizations.**

**Interview trap:**
Do not describe Azure Advisor as only a **cost-saving tool**. Cost is just one of its five recommendation categories.

**Keywords:**
Azure Advisor, recommendations, Reliability, Security, Performance, Cost, Operational Excellence

**Likely follow-ups:**

* How can Advisor reduce Azure costs?
* Would you automatically apply every Advisor recommendation?
* Advisor vs Azure Monitor?
* Advisor vs Cost Management?

## **T20-M03. How can Azure Advisor reduce cost?**

**Answer:**
Azure Advisor reduces cost by identifying **idle, underutilized, oversized, or inefficient Azure resources** and recommending actions such as:

```text
Resize resources
Shut down idle resources
Purchase Reservations
Purchase Savings Plans
Optimize specific Azure services
```

It also provides estimated potential savings so teams can prioritize recommendations with the largest financial impact. ([Microsoft Learn][2])

---

### **1. Identify idle resources**

Suppose:

```text
VM01

CPU ≈ 0–1%
Network ≈ almost zero
No meaningful workload
```

Advisor may recommend:

```text
Shutdown VM01
```

Current Advisor VM shutdown recommendations analyze recent utilization and identify machines that appear essentially unused. ([Microsoft Learn][3])

This eliminates:

```text
idle compute cost
```

rather than trying to get a discount on resources that shouldn't exist at all.

---

### **2. Rightsize underutilized resources**

Example:

```text
Current VM:
D8s_v5

Observed requirement:
roughly fits D4s_v5
```

Advisor may recommend:

```text
D8s_v5
   ↓
D4s_v5
```

Result:

```text
same workload
+
lower cost
```

Advisor's current rightsizing algorithm considers metrics such as:

```text
CPU
Memory
Outbound Network
```

and checks whether the proposed SKU is cheaper while attempting to preserve sufficient workload capacity. ([Microsoft Learn][3])

---

### **3. Reduce VMSS instance count**

Suppose:

```text
VMSS
10 instances
```

but demand can consistently run on:

```text
6 instances
```

Advisor may recommend reducing the instance count.

For VMSS, Microsoft currently prioritizes instance-count recommendations when they provide a straightforward savings opportunity. ([Microsoft Learn][3])

---

### **4. Recommend Reservations**

Once actual capacity is rightsized, Advisor can identify predictable workloads that could benefit from:

```text
1-year / 3-year Reservations
```

This can reduce the unit price for long-running baseline capacity.

Important order:

```text
Remove waste
      ↓
Rightsize
      ↓
THEN buy commitment discounts
```

not:

```text
Buy reservation for oversized VM
      ↓
lock in inefficient spend
```

Microsoft's own Advisor cost-savings guidance recommends addressing rightsizing/shutdown opportunities before reservation and Savings Plan purchases. ([Microsoft Learn][5])

---

### **5. Recommend Savings Plans**

For predictable eligible compute spend that is less static than a reservation workload:

```text
Advisor
   ↓
Savings Plan recommendation
```

Savings Plan recommendations use observed on-demand usage/cost patterns. ([Microsoft Learn][6])

So the optimization sequence might become:

```text
Waste removal
      ↓
Rightsize
      ↓
Reservations for stable capacity
      ↓
Savings Plan for suitable remaining compute
```

---

### **6. Optimize more than just VMs**

Advisor cost recommendations currently span many Azure services, including:

```text
VM / VMSS
AKS
App Service
Container Apps
Storage
Azure Monitor
Cosmos DB
Application Gateway
Data Factory
Databricks
and others
```

([Microsoft Learn][2])

This matters because real Azure bills often contain:

```text
compute
+
monitoring
+
storage
+
databases
+
networking
```

—not just VMs.

---

### **7. Estimated savings help prioritize**

Imagine Advisor shows:

```text
Recommendation A
Savings = $80/year

Recommendation B
Savings = $12,000/year

Recommendation C
Savings = $4,000/year
```

I would prioritize:

```text
B
↓
C
↓
A
```

while still considering operational risk.

Advisor exposes potential savings information to help teams focus on higher-value recommendations. ([Microsoft Learn][4])

---

### **8. Never blindly execute a rightsizing recommendation**

Example:

```text
VM averages:
CPU 10%
```

But:

```text
every Friday 18:00
CPU reaches 95%
for critical settlement processing
```

If my Advisor lookback/configuration doesn't capture the relevant business cycle, downsizing could hurt production.

So before accepting:

```text
Advisor recommendation
```

I validate against:

```text
longer telemetry window
peak workload
memory
disk IOPS/throughput
network
SLO
business events
```

---

### **A strong FinOps sequence**

```text
Azure Cost Analysis
      ↓
Identify major cost driver
      ↓
Azure Advisor
      ↓
Idle?
      ↓
Delete/shutdown

Underutilized?
      ↓
Rightsize

Stable baseline?
      ↓
Reservation

Flexible predictable compute spend?
      ↓
Savings Plan

Interruptible?
      ↓
Consider Spot
```

That's much stronger than simply saying:

> “Buy reservations.”

---

### **Strong interview answer**

> “Azure Advisor reduces cost by analyzing resource usage and identifying idle or underutilized resources. It can recommend shutting down unused VMs, resizing oversized VMs or VM scale sets, and purchasing Reservations or Savings Plans for suitable baseline usage. My preferred sequence is to remove waste and rightsize first, then commit to discounted pricing, because otherwise I could purchase a reservation for capacity I never needed. I validate Advisor recommendations against peak utilization, business cycles, performance requirements, and SLOs before applying them.”

**Memory line:**
**Advisor cost optimization = eliminate waste → rightsize → then optimize the price of what remains.**

**Interview trap:**
Do not buy a Reservation first for an oversized workload. **Rightsize before committing.** ([Microsoft Learn][5])

**Keywords:**
Azure Advisor, rightsizing, idle resources, shutdown, Reservations, Savings Plan, potential savings

**Likely follow-ups:**

* What metrics does Advisor use for VM rightsizing?
* Why should rightsizing happen before Reservations?
* Would you automatically resize production VMs?
* How would you validate an Advisor recommendation?

## **T20-M04. What is rightsizing?**

**Answer:**
Rightsizing means **matching the amount and type of Azure capacity provisioned to the workload's real performance requirements instead of leaving resources overprovisioned or underprovisioned**.

The goal is not simply:

```text
make everything smaller
```

It is:

```text
just enough capacity
to meet performance + reliability requirements
at efficient cost
```

Microsoft's Well-Architected guidance explicitly recommends analyzing actual resource utilization and adjusting resource sizes so provisioned capacity matches workload needs. ([Microsoft Learn][7])

---

### **Simple example**

Suppose:

```text
VM:
Standard_D16s_v5

16 vCPU
64 GB RAM
```

but over 30 days:

```text
CPU P95      = 18%
Memory P99   = 30%
Network      = low
Disk usage   = moderate
```

That may indicate overprovisioning.

After proper testing:

```text
D16s_v5
    ↓
D8s_v5
```

could provide:

```text
lower cost
+
same required service level
```

That's rightsizing.

---

### **Rightsizing is not only downsizing**

This is important.

Suppose:

```text
Current VM:
D2s_v5

CPU:
95%

Memory:
90%
```

The resource may need:

```text
D4s_v5
```

or an entirely different VM family.

That is also rightsizing.

So:

```text
Rightsizing
≠ downsizing

Rightsizing
= correct sizing
```

---

### **Dimensions I would inspect**

For compute, I wouldn't look only at CPU.

I would evaluate:

```text
CPU
Memory
Disk IOPS
Disk throughput
Network throughput
Connection limits
GPU requirements
Latency
Peak workload
```

A VM can have:

```text
CPU = 15%
```

but still need its existing SKU because of:

```text
memory
network bandwidth
disk throughput
```

---

### **Azure Advisor can help**

Advisor's current VM/VMSS rightsizing recommendations use utilization data such as:

```text
CPU
Memory
Outbound Network
```

and propose cheaper compatible SKUs when the observed workload is expected to fit. ([Microsoft Learn][3])

So:

```text
Metrics
   ↓
Advisor
   ↓
Potential new SKU
   ↓
Engineer validates
   ↓
Test
   ↓
Resize
```

---

### **Use representative time periods**

Suppose:

```text
Normal 25 days:
CPU 10%

Month-end:
CPU 90%
```

A tiny observation window might incorrectly suggest aggressive downsizing.

That's why I look at:

```text
daily pattern
weekly pattern
month-end
seasonal events
business campaigns
failover conditions
```

Advisor currently supports VM rightsizing lookbacks up to 90 days, which can help capture longer workload patterns. ([Microsoft Learn][3])

---

### **Rightsizing AKS**

Rightsizing applies beyond VMs.

In AKS I could rightsize:

```text
node VM size
node count
pod CPU requests
pod memory requests
pod limits
```

Example:

```text
Container actual memory:
300 MiB

Request:
4 GiB
```

Across hundreds of pods:

```text
overstated request
      ↓
poor bin-packing
      ↓
more nodes
      ↓
higher AKS compute cost
```

So Kubernetes rightsizing can mean correcting both:

```text
pod requests
+
underlying node pools
```

---

### **Rightsizing App Service**

Likewise:

```text
P3v3 App Service Plan
```

may be oversized for an application that comfortably fits:

```text
P1v3
```

or perhaps should use autoscaling with smaller baseline instances.

Again:

```text
usage pattern first
pricing decision second
```

---

### **Rightsizing vs autoscaling**

This distinction matters:

```text
Rightsizing
→ correct capacity per resource / baseline

Autoscaling
→ dynamically change resource quantity
  as demand changes
```

Example:

```text
Oversized VMSS nodes
     ↓
Rightsize VM SKU

Demand changes 2 → 10 instances
     ↓
Autoscale instance count
```

They work together.

---

### **Rightsizing vs Reservation**

```text
Rightsizing
→ optimize quantity/capacity

Reservation
→ optimize price
```

Do:

```text
Rightsize
    ↓
determine stable baseline
    ↓
Reservation
```

not the opposite.

---

### **Reliability trade-off**

Overaggressive rightsizing can cause:

```text
CPU saturation
memory pressure
queue buildup
higher latency
timeouts
reduced failover headroom
```

So I never optimize only:

```text
$/month
```

I optimize:

```text
cost
+
performance
+
reliability
```

The Azure Well-Architected Framework treats cost optimization as maximizing value while maintaining workload requirements—not simply minimizing spend. ([Microsoft Learn][8])

---

### **Production rightsizing workflow**

```text
Collect representative telemetry
          ↓
Identify over/underutilization
          ↓
Advisor + engineering analysis
          ↓
Choose candidate SKU
          ↓
Load/performance test
          ↓
Change one environment/canary
          ↓
Observe SLOs
          ↓
Roll out
          ↓
Continue monitoring
```

---

### **Strong interview answer**

> “Rightsizing means matching the resource's capacity to the workload's actual requirements. It isn't simply downsizing; an underpowered resource may need to be scaled up, while an oversized one should be reduced. For a VM I look at CPU, memory, disk and network characteristics over a representative time period, including peak business events. Azure Advisor can provide rightsizing recommendations, but I validate them against performance and reliability requirements before applying them. Once I've established the correct baseline size, I can then consider autoscaling, Reservations or Savings Plans.”

**Memory line:**
**Rightsizing = the smallest practical capacity that still safely meets the workload's real requirements.**

**Interview trap:**
Low CPU alone does **not prove a VM is oversized**; memory, disk, network, and peak behavior can determine the required SKU.

**Keywords:**
Rightsizing, utilization, SKU, baseline capacity, CPU, memory, IOPS, Azure Advisor

**Likely follow-ups:**

* Rightsizing vs autoscaling?
* What metrics would you inspect?
* Why shouldn't you rightsize from average CPU alone?
* How would you rightsize AKS?

## **T20-M05. What is autoscaling from a cost perspective?**

**Answer:**
From a cost perspective, autoscaling means **dynamically matching provisioned capacity to actual workload demand so I don't continuously pay for peak capacity when demand is low**.

The economic principle is:

```text
Static capacity:
Provision for peak
→ pay for peak all day

Autoscaling:
Provision for current demand
→ scale out when busy
→ scale in when quiet
```

Azure's current autoscale guidance explicitly states that scaling in during low demand reduces resource usage and therefore cost. ([Microsoft Learn][9])

---

### **Simple example**

Static design:

```text
10 VMSS instances
24 hours/day
```

Workload actually needs:

```text
Business hours:
10

Night:
2
```

Without autoscaling:

```text
00:00 ───────────────────────── 24:00
10 10 10 10 10 10 10 10 10...
```

With autoscaling:

```text
Night        Business hours       Night
2 2 2 2  →  6 8 10 10 8 6  →   2 2 2
```

Now I pay for:

```text
high capacity
only when needed
```

instead of maintaining:

```text
10 instances continuously
```

---

### **1. Scale out protects performance**

Example rule:

```text
Average CPU > 70%
for 10 minutes
       ↓
Add instances
```

Now demand rises:

```text
2 instances
    ↓
4
    ↓
6
```

This increases cost, but intentionally:

```text
higher cost
in exchange for
maintaining service quality
```

Cost optimization does **not** mean preventing all scale-out.

---

### **2. Scale in produces savings**

Example:

```text
Average CPU < 40%
for 20 minutes
       ↓
Remove instances
```

Then:

```text
10
 ↓
8
 ↓
6
 ↓
4
```

Azure's autoscaling best practices explicitly recommend pairing scale-out with scale-in so capacity can be removed during low utilization and cost savings can actually be realized. ([Microsoft Learn][10])

---

### **3. Minimum capacity matters**

Autoscale settings normally define:

```text
Minimum
Default
Maximum
```

Example:

```text
Min     = 2
Default = 4
Max     = 12
```

Cost implications:

```text
Min
→ guaranteed baseline cost

Max
→ upper scaling/cost boundary
```

Microsoft's autoscale guidance recommends setting safe minimum and maximum values rather than allowing unconstrained scaling. ([Microsoft Learn][9])

---

### **4. Maximum capacity is also a financial guardrail**

Suppose a bug creates:

```text
massive queue buildup
```

and autoscale has:

```text
max = unlimited / excessively high
```

you could get:

```text
2
↓
20
↓
100
↓
hundreds of instances
```

and a huge bill without actually solving the underlying fault.

Azure Well-Architected guidance specifically warns that autoscaling without an appropriate upper limit can cause uncontrolled growth and unexpected cost. ([Microsoft Learn][11])

So:

```text
Max capacity
=
performance limit
+
cost safety boundary
```

---

### **5. Choose the right metric**

Scaling on:

```text
CPU
```

works for CPU-bound applications.

But perhaps the real demand indicator is:

```text
Queue length
Requests/sec
Concurrent sessions
Messages waiting
```

Example worker:

```text
Service Bus queue
       ↓
1,000 messages
       ↓
KEDA / autoscale
       ↓
more workers
```

When:

```text
queue = 0
```

workers can scale back down.

This aligns cost much more closely with actual business workload.

---

### **6. Scheduled autoscaling**

Some demand is predictable.

Example:

```text
Office application

Mon–Fri
08:00 → 20 instances

20:00 → 5 instances

Weekend → 2 instances
```

Azure Monitor supports both metric-based and schedule-based autoscaling. ([Microsoft Learn][12])

For predictable usage, scheduled scaling can sometimes react more cleanly than waiting for CPU to spike.

---

### **7. Autoscaling vs rightsizing**

Again:

```text
Rightsizing
→ each instance is appropriately sized

Autoscaling
→ number of instances matches demand
```

Bad configuration:

```text
20 oversized instances
```

Autoscaling might reduce that to:

```text
5 oversized instances
```

which is better, but still wasteful.

Better:

```text
right-sized instance
      +
autoscaling
```

---

### **8. Autoscaling vs Reservations**

These aren't opposites.

Suppose:

```text
Minimum:
4 instances

Peak:
20 instances
```

I might use:

```text
4-instance stable baseline
      ↓
Reservation/Savings Plan
```

and:

```text
additional 0–16
      ↓
Autoscale
```

So:

```text
Commitment discount
→ optimize predictable baseline price

Autoscaling
→ optimize variable capacity quantity
```

This is a very strong FinOps architecture.

---

### **9. AKS example**

Suppose AKS traffic changes throughout the day.

```text
Pods
 ↓
HPA/KEDA
 ↓
more/fewer pods
```

But if nodes remain fixed at:

```text
20 nodes
```

pod scaling alone may not create much infrastructure savings.

For actual infrastructure cost optimization:

```text
HPA / KEDA
     ↓
pod count changes
     ↓
Cluster Autoscaler
     ↓
node count changes
```

Example:

```text
day:
20 nodes

night:
4 nodes
```

This is why:

```text
HPA
≠ Cluster Autoscaler
```

HPA adjusts workloads; Cluster Autoscaler adjusts underlying node capacity.

---

### **10. Scale-to-zero can be powerful**

For suitable serverless/event-driven services:

```text
No demand
   ↓
0 replicas
```

can significantly reduce idle cost.

Examples include some configurations of:

```text
Container Apps
Functions
event-driven KEDA workloads
```

But:

```text
scale to zero
```

may introduce:

```text
cold-start latency
```

so again there is a:

```text
cost ↔ performance
```

trade-off.

---

### **11. Avoid autoscaling flapping**

Bad rules:

```text
CPU > 50%
→ scale out

CPU < 49%
→ scale in
```

Traffic around 50% can cause:

```text
out
in
out
in
out
```

which is called:

```text
flapping
```

and can create:

```text
instability
+
unnecessary scaling operations
+
potential cost inefficiency
```

Microsoft recommends carefully paired scale-out/scale-in thresholds and appropriate cooldown behavior. ([Microsoft Learn][10])

---

### **Cost-oriented architecture**

```text
             Workload demand
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
      Baseline load       Burst load
          ↓                   ↓
Right-sized minimum         Autoscale
          ↓                   ↓
Reservation /            PAYG / Spot /
Savings Plan             flexible capacity
          └─────────┬─────────┘
                    ↓
            lowest sensible cost
          while meeting the SLO
```

---

### **Strong interview answer**

> “From a cost perspective, autoscaling lets me match capacity to demand instead of provisioning for peak traffic 24/7. I keep a safe minimum capacity for reliability, scale out when metrics such as CPU, request rate or queue depth indicate additional demand, and scale in when demand drops. I also set a sensible maximum because uncontrolled autoscaling can become a cost incident. Autoscaling works best together with rightsizing: each instance should first be appropriately sized, then instance count should scale dynamically. For predictable baseline capacity I can use Reservations or a Savings Plan while autoscaling handles burst demand.”

**Memory line:**
**Rightsizing optimizes the size of each unit; autoscaling optimizes how many units run.**

**Interview trap:**
Autoscaling isn't automatically cost-efficient. **Bad metrics, no scale-in rule, or an excessive maximum can increase cost.** ([Microsoft Learn][10])
