## **T20-M06. What kinds of Azure data-transfer costs should you consider?**

**Answer:**
When estimating Azure networking cost, I don't just ask, **“How much bandwidth do we use?”** I ask **where the traffic originates, where it goes, which Azure networking service carries it, and whether it crosses a region, VNet, Availability Zone, hybrid link, or the public internet.**

The main categories I consider are:

```text
Internet egress
Cross-region traffic
VNet peering / Global VNet peering
Cross-Availability-Zone traffic
VPN / ExpressRoute data transfer
Front Door / CDN / gateway processing
Service-specific data movement
```

Azure's current bandwidth pricing says general **data transfer into Azure is free**, traffic between Azure services in the same region is generally not charged as standard bandwidth, while inter-region and internet egress can incur charges. There are also separate pricing models for constructs such as VNet peering and ExpressRoute. ([Microsoft Azure][1])

---

### **1. Internet ingress vs egress**

The basic mental model is:

```text
Internet
    ↓
Azure
Ingress
→ generally free

Azure
    ↓
Internet
Egress
→ commonly charged
```

Example:

```text
User uploads 20 GB
Internet → Azure Storage
→ ingress

User downloads 2 TB
Azure Storage → Internet
→ egress
```

The second flow is usually the one I care about financially.

Azure currently provides the first **100 GB/month of internet egress free**, after which rates depend on source geography/routing option. ([Microsoft Azure][1])

---

### **2. Same-region Azure traffic**

If two Azure services communicate inside the same Azure region:

```text
App Service
Central India
      ↓
Azure SQL
Central India
```

standard Azure bandwidth pricing generally doesn't add an inter-region data-transfer charge.

Microsoft's current bandwidth FAQ explicitly says data transfer between Azure services in the **same region** isn't charged as standard bandwidth. ([Microsoft Azure][1])

But don't turn that into:

> “All networking inside one region is always free.”

because specific networking services can have their **own processing/peering charges**.

---

### **3. VNet peering**

Suppose:

```text
VNet A
   ↓
VNet Peering
   ↓
VNet B
```

VNet peering has its own data-transfer pricing model.

Microsoft's current Virtual Network pricing states that peering traffic is billed based on data transferred across the peering, with ingress and egress considered at both ends according to the applicable peering model. ([Microsoft Azure][2])

This means:

```text
"same Azure region"
```

does not automatically mean:

```text
"every possible network construct has zero cost"
```

---

### **4. Cross-region traffic**

This is a major cost driver in multi-region architectures.

Example:

```text
Frontend
Central India
      ↓
Database / replica
West Europe
```

Now traffic crosses Azure regions.

Azure currently charges inter-region data transfer based on source/destination geography; outbound transfer is charged while inbound on the receiving side is generally free under the standard inter-region model. ([Microsoft Azure][1])

This becomes significant for:

```text
database replication
multi-region AKS
backup copies
storage replication
large analytics pipelines
cross-region APIs
```

---

### **5. Availability-Zone traffic**

For zonal architectures I also check whether a design generates high-volume cross-zone traffic.

Conceptually:

```text
Zone 1
AKS nodes
    ↓
large continuous traffic
    ↓
Zone 2
database / service
```

Azure's bandwidth pricing distinguishes same-Availability-Zone traffic, which is currently listed as free in the general bandwidth schedule. Cross-zone pricing depends on the actual service/network path and must be included in a zonal architecture's cost analysis. ([Microsoft Azure][1])

So Availability Zones improve:

```text
fault isolation
```

but can introduce:

```text
additional network cost
```

for chatty architectures.

---

### **6. Hybrid connectivity**

For:

```text
Azure
 ↕
On-premises
```

I ask which connectivity model is used.

#### VPN Gateway

Cost can include:

```text
Gateway hourly cost
+
outbound data transfer
```

#### ExpressRoute

Cost can include:

```text
ExpressRoute circuit
+
ExpressRoute Gateway
+
provider/cross-connect charges
+
data transfer depending on plan
```

For ExpressRoute, Microsoft currently states that inbound transfer is included for its standard circuit plans, while outbound handling depends on whether the circuit uses metered, unlimited, or Local pricing. ([Microsoft Learn][3])

---

### **7. Global routing and edge services**

If the architecture uses:

```text
Azure Front Door
CDN
Application Gateway
Load Balancer
NAT Gateway
Azure Firewall
```

I don't count only raw bandwidth.

Some of these services charge for things such as:

```text
data processing
requests
rules
gateway hours
capacity units
outbound traffic
```

depending on the service.

So the full networking cost may be:

```text
Network appliance/service cost
          +
Data processing
          +
Data transfer
```

---

### **8. Architecture example**

Suppose:

```text
Users in India
      ↓
Front Door
      ↓
App in Central India
      ↓
Database in West Europe
```

There can be several independent cost dimensions:

```text
Internet delivery
Front Door processing
Front Door/origin transfer model
Central India → West Europe transfer
database replication traffic
```

A common mistake is estimating only:

```text
VM cost + DB cost
```

while ignoring the **continuous cross-region data path**.

---

### **Strong interview answer**

> “For Azure data-transfer cost I look at the complete traffic path rather than just total bandwidth. I consider internet egress, cross-region communication, cross-zone traffic, VNet and Global VNet peering, VPN or ExpressRoute transfer, and any service-specific processing charges from components such as Front Door or firewalls. Inbound internet traffic is generally free and same-region Azure-service communication is generally free from standard bandwidth charges, but networking constructs such as peering still have their own pricing. Multi-region and high-egress architectures are where data-transfer cost can become significant.”

**Memory line:**
**Data-transfer cost depends on where traffic crosses boundaries—not simply how many GB the application sends.**

**Interview trap:**
Do not say:

> “Everything inside Azure is free.”

Cross-region, peering, hybrid, edge, and other networking paths can all introduce charges.

**Keywords:**
Ingress, egress, cross-region, Availability Zone, VNet peering, ExpressRoute, bandwidth

**Likely follow-ups:**

* Is inbound internet traffic charged?
* Is traffic between two Azure regions free?
* Does VNet peering cost money?
* How can multi-region architecture increase networking cost?

# **T20-M07. Why can Log Analytics become expensive?**

**Answer:**
Log Analytics can become expensive primarily because its cost is strongly influenced by **how much data you ingest**, and then by choices such as retention, table plan, querying of lower-cost tables, export, and other Azure Monitor features.

For most Azure Monitor customers:

```text
More telemetry
      ↓
More GB ingested
      ↓
Higher Log Analytics cost
```

Microsoft currently says **log ingestion is the largest Azure Monitor cost component for most customers**. ([Microsoft Learn][4])

---

### **1. High ingestion volume**

Imagine AKS has:

```text
100 pods
```

and each writes:

```text
500 MB logs/day
```

That's approximately:

```text
50 GB/day
```

before considering:

```text
node logs
container stdout/stderr
Kubernetes events
application traces
dependency telemetry
custom logs
```

Over 30 days:

```text
50 GB × 30
= 1.5 TB ingestion
```

That can become expensive quickly.

---

### **2. Verbose application logging**

A common problem is:

```text
Production logging level = DEBUG
```

which produces:

```text
request start
request headers
request body
DB query
DB timing
response payload
trace details
...
```

for every request.

Then:

```text
traffic doubles
      ↓
log volume approximately doubles
      ↓
monitoring bill jumps
```

This is why logging architecture is also a **FinOps problem**.

---

### **3. Collecting telemetry nobody uses**

Bad monitoring design:

```text
Collect everything
Keep everything
Forever
```

Examples:

```text
high-volume informational logs
health-check requests
successful load-balancer probes
verbose Kubernetes events
repetitive dependency traces
debug logs
```

If nobody uses that data for:

```text
alerts
incident response
SLO analysis
security
compliance
```

then it may not deserve expensive analytics ingestion.

---

### **4. Analytics vs Basic vs Auxiliary**

Azure Monitor Logs now supports different table plans:

```text
Analytics
→ high-value data
→ full real-time analytics

Basic
→ lower-cost troubleshooting data

Auxiliary / Lake
→ high-volume / low-touch data
```

Microsoft currently describes **Analytics** as the standard high-performance plan, **Basic** as reduced-cost ingestion for lower-touch troubleshooting data, and **Auxiliary/Lake** as the lowest-cost ingestion option for verbose or infrequently queried data. ([Microsoft Learn][5])

So one optimization is:

```text
Security / alerting / critical telemetry
→ Analytics

Verbose troubleshooting data
→ Basic

Very high-volume low-touch data
→ Auxiliary/Lake
```

where feature requirements permit it.

---

### **5. Retention costs**

Another dimension is:

```text
How long must I retain this data?
```

For Analytics tables, current Azure Monitor pricing includes a default analytics-retention window in the ingestion model, while extending interactive or long-term retention can add charges depending on configuration. Azure Monitor supports total retention for much longer periods, including up to 12 years using long-term retention. ([Microsoft Learn][6])

So instead of:

```text
2 years of expensive interactive logs
```

I might use:

```text
30–90 days
high-value interactive telemetry

+

long-term retention
for compliance/history
```

depending on requirements.

---

### **6. Query costs can matter with lower-cost plans**

For:

```text
Analytics tables
```

ordinary interactive querying isn't normally charged by scanned GB.

But:

```text
Basic
Auxiliary
```

use different query economics where scanned data can incur charges. ([Microsoft Learn][5])

Therefore:

```text
lower ingestion price
```

doesn't mean:

```text
always cheaper regardless of usage
```

If engineers continuously scan terabytes of Basic/Auxiliary logs, query cost can matter.

---

### **7. Wrong telemetry architecture**

Suppose OpenTelemetry sends:

```text
100% traces
+
all logs
+
high-cardinality metadata
```

from a busy microservices system.

Volume can explode.

A better design may use:

```text
trace sampling
DCR filtering
log-level control
transformations
table-plan selection
summary rules
```

Microsoft recommends controlling collection and filtering unneeded records before ingestion where possible because avoiding ingestion is usually the strongest cost optimization. ([Microsoft Learn][7])

---

### **8. Find which table is costing money**

Rather than guessing, I would use:

```text
Log Analytics Workspace
      ↓
Usage and Estimated Costs
```

and identify billable ingestion by solution/table. Microsoft exposes this view specifically to show estimated monthly costs and recent billable ingestion. ([Microsoft Learn][4])

A simple KQL investigation can also help identify volume patterns.

Conceptually:

```text
ContainerLogV2    600 GB
AppTraces         400 GB
AzureDiagnostics  150 GB
SecurityEvent      50 GB
```

Immediately:

```text
ContainerLogV2 + AppTraces
```

become my first targets.

---

### **Strong interview answer**

> “Log Analytics usually becomes expensive because of data ingestion volume. Common causes are verbose application logs, collecting every Kubernetes/container event, excessive traces, debug logging in production, and retaining or querying more data than the business actually needs. I first identify the tables generating the most billable volume using Usage and Estimated Costs. Then I reduce collection at the source or with DCR transformations, use sampling where appropriate, choose Analytics, Basic, or Auxiliary table plans based on how the data is used, and configure retention according to operational and compliance requirements.”

**Memory line:**
**The cheapest unnecessary log is the one you never ingest.**

**Interview trap:**
Don't solve Log Analytics cost only by:

```text
reduce retention
```

If ingestion is enormous, retention changes may barely address the main cost driver.

**Keywords:**
Log Analytics, ingestion, retention, Analytics Logs, Basic Logs, Auxiliary Logs, DCR, sampling

**Likely follow-ups:**

* How would you find which table generates the most cost?
* Basic vs Analytics logs?
* How would you reduce AKS logging cost?
* Does reducing retention below the included Analytics window always save money?

## **T20-H01. An Azure bill suddenly increases by 40%; how would you investigate it?**

**Answer:**
I would treat this as a **cost incident** and first determine exactly **when the increase started, which service/resource caused it, whether it came from increased usage or changed pricing/configuration, and what Azure change correlates with that point in time**.

My troubleshooting sequence is:

```text
Confirm increase
      ↓
Find first abnormal date
      ↓
Subscription / service
      ↓
Resource / meter
      ↓
Quantity vs unit price
      ↓
Correlate with Azure changes
      ↓
Contain waste
      ↓
Fix root cause
```

Microsoft Cost Management includes anomaly detection and Cost Analysis specifically for investigating unexpected cost changes. ([Microsoft Learn][8])

---

### **1. Confirm the scope**

First:

```text
40% of what?
```

Is it:

```text
Entire billing account?
One subscription?
One Resource Group?
One application?
One Azure service?
```

Example:

```text
August = $20,000
September forecast = $28,000
```

Difference:

```text
+$8,000
+40%
```

Then I establish the exact affected scope.

---

### **2. Use Cost Analysis and compare periods**

In:

```text
Cost Management
   ↓
Cost Analysis
```

I compare:

```text
Current period
vs
Previous period
```

Then group by:

```text
Service name
Resource
Resource Group
Subscription
Meter
Tag
Region
```

Example:

```text
Previous month     Current month

Compute     $8k      $8.5k
SQL         $4k      $4.1k
Monitor     $2k      $8k   ← suspicious
Network     $2k      $2.1k
Other       $4k      $5.3k
```

Now I don't have an “Azure bill problem.”

I have:

```text
Azure Monitor cost spike
```

---

### **3. Find the first abnormal day**

A time-series view is extremely useful.

```text
Cost/day

$700 ───────────────
$700 ───────────────
$700 ───────────────
                │
                │ Sept 12
                ↓
$1,400 ─────────────────
$1,500 ─────────────────
```

Now:

```text
What changed around September 12?
```

becomes the main investigation question.

---

### **4. Use anomaly detection**

Microsoft Cost Management can detect atypical spending patterns and lets you configure anomaly alerts. ([Microsoft Learn][8])

So I check whether Azure reports:

```text
Cost anomaly
      ↓
September 12
      ↓
Resource / service contribution
```

This can shorten the investigation significantly.

---

### **5. Drill down to resource and billing meter**

Suppose the increase is:

```text
Azure Monitor
```

Drill down:

```text
Meter:
Analytics Logs Data Ingestion
```

Resource:

```text
law-prod-platform
```

Now the likely issue is:

```text
more logs ingested
```

not:

```text
Azure Monitor pricing mystery
```

Alternatively:

```text
Service = Virtual Machines
Meter = D16as_v5
Resource = aks-userpool-123
```

could point to AKS nodes scaling unexpectedly.

---

### **6. Separate quantity increase from rate change**

I ask:

```text
Did we consume more?
or
Did each unit become more expensive?
```

Example A:

```text
100 GB/day → 600 GB/day
same ingestion rate
```

That's a **usage increase**.

Example B:

```text
same usage
but reservation expired
→ PAYG billing
```

That's a **pricing/commitment change**.

This distinction determines the root cause.

---

### **7. Correlate with resource/configuration changes**

Once I know the spike started on a specific day, I correlate with:

```text
Azure Activity Log
deployment history
Terraform changes
GitHub Actions
Azure DevOps
autoscale history
AKS changes
monitoring configuration
```

Example:

```text
September 12

Terraform deployment
      ↓
Enabled DEBUG logs
for 50 microservices
      ↓
Log Analytics:
100 GB/day → 650 GB/day
```

That's a defensible root cause.

---

### **8. Common causes I would check**

```text
Compute
├── VM left running
├── larger SKU deployed
├── VMSS scaled out
└── AKS node count increased

Monitoring
├── DEBUG logging
├── new diagnostic categories
├── trace sampling disabled
└── retention changed

Networking
├── internet egress increased
├── cross-region traffic
└── peering traffic increased

Storage
├── capacity growth
├── transaction growth
└── replication tier changed

Commitments
├── Reservation expired
├── reservation no longer matches
└── Savings Plan under/overutilization
```

---

### **9. Example: AKS spike**

Suppose Cost Analysis shows:

```text
Virtual Machines
+$6,000
```

and those VMs belong to:

```text
aks-prod-userpool
```

I inspect:

```text
Cluster Autoscaler
      ↓
2 nodes → 20 nodes
```

Then determine why:

```text
pod CPU requests increased?
pending pods?
HPA runaway?
daemonset added?
autoscaler max too high?
```

Cost is often only the **symptom** of an engineering issue.

---

### **10. Example: Log Analytics spike**

If:

```text
Log Analytics
+$5,000
```

I open:

```text
Workspace
→ Usage and Estimated Costs
```

and find:

```text
ContainerLogV2
100 GB/day
→ 500 GB/day
```

Then correlate:

```text
new release
→ DEBUG logging enabled
```

Microsoft specifically recommends using workspace Usage and Estimated Costs and Cost Analysis for this kind of investigation. ([Microsoft Learn][4])

---

### **11. Contain without causing an outage**

Once I know the cause, I separate:

```text
Waste
vs
Legitimate growth
```

If:

```text
unused test VM accidentally running
```

stop it.

If:

```text
production traffic increased 40%
```

I don't simply terminate instances to make the bill smaller.

Instead:

```text
investigate efficiency
rightsizing
autoscaling
commitment discounts
architecture
```

while preserving SLOs.

---

### **12. Prevent recurrence**

After root cause:

```text
Budget
+
forecast alerts
+
Cost anomaly alerts
+
tagging
+
FinOps dashboard
+
maximum autoscale limits
+
Policy
```

For example:

```text
Monthly budget
80% actual → alert

110% forecast → alert

Cost anomaly
→ notify FinOps + SRE
```

---

### **Strong interview answer**

> “I would first identify exactly when the 40% increase began and use Cost Analysis to compare the current period with the previous one. I group by subscription, service, resource, meter, region and tags until I isolate the cost driver. Then I determine whether the increase is caused by more consumption or by a pricing/commitment change such as an expired reservation. I correlate the first abnormal date with Activity Log, Terraform or CI/CD deployments, autoscaling history and service telemetry. For example, if Azure Monitor increased, I drill into Log Analytics ingestion by table; if Compute increased, I check VMSS or AKS node scaling. I contain obvious waste without damaging production, fix the underlying cause, and then add budgets and anomaly alerts so the same spike is detected earlier.”

**Memory line:**
**Cost spike investigation = when → service → resource → meter → usage → change that caused it.**

**Interview trap:**
Do not immediately start deleting expensive resources. First determine whether the increase is **waste or legitimate workload growth**.

**Keywords:**
Cost Analysis, anomaly detection, billing meter, Activity Log, usage, reservation, cost incident

**Likely follow-ups:**

* How would you investigate an AKS cost spike?
* How would you identify who made the cost-causing change?
* What if usage didn't increase but cost did?
* How would you prevent future cost surprises?

# **T20-H02. How would you reduce the cost of a nonproduction AKS cluster?**

**Answer:**
For nonproduction AKS, my goal is to **stop paying for idle compute first**, then rightsize the capacity that remains, and only after that optimize pricing.

My priority order would be:

```text
Stop when unused
      ↓
Scale down aggressively
      ↓
Rightsize pods
      ↓
Rightsize node pools
      ↓
Use Spot where interruption is acceptable
      ↓
Reduce observability/storage/network waste
```

Microsoft's current AKS cost guidance specifically recommends **cluster start/stop for development and test clusters**, because an idle cluster otherwise continues running system and user nodes. ([Microsoft Learn][9])

---

### **1. Stop the cluster outside working hours**

If developers use the cluster:

```text
Mon–Fri
09:00–19:00
```

why pay for:

```text
nights
weekends
holidays
```

?

AKS supports:

```bash
az aks stop \
  --resource-group rg-dev \
  --name aks-dev
```

and later:

```bash
az aks start \
  --resource-group rg-dev \
  --name aks-dev
```

Microsoft's current documentation says stopping a cluster stops the **control plane and agent nodes**, preserving most cluster state while saving compute costs. ([Microsoft Learn][10])

For a dev environment, this can be one of the biggest savings.

---

### **2. Automate start/stop**

Instead of trusting developers to remember:

```text
19:00
   ↓
scheduled automation
   ↓
az aks stop

08:30
   ↓
az aks start
```

For example:

```text
Azure Automation
Logic App
GitHub Actions schedule
Azure DevOps schedule
```

depending on organizational preference.

Nonprod cost optimization should be automated.

---

### **3. Scale user node pools to zero**

If stopping the whole cluster isn't suitable, user pools can often scale to:

```text
0
```

when not required.

Microsoft's current AKS documentation explicitly points to scaling **User** pools to zero as a cost-saving option; the system pool is still required while the overall cluster remains running. ([Microsoft Learn][11])

Mental model:

```text
System pool
→ runs Kubernetes/AKS system components

User pool
→ application workloads
→ can potentially scale to 0
```

---

### **4. Use Cluster Autoscaler**

Example:

```text
Min nodes = 1
Max nodes = 8
```

instead of:

```text
Node count = 8
24 × 7
```

Flow:

```text
Few workloads
      ↓
1–2 nodes

More pending pods
      ↓
Cluster Autoscaler
      ↓
3–8 nodes

Demand disappears
      ↓
scale back in
```

For nonproduction I can generally tolerate more aggressive minimums than production.

---

### **5. Fix pod requests before fixing nodes**

Suppose:

```yaml
resources:
  requests:
    cpu: "2"
    memory: "4Gi"
```

but actual usage is:

```text
CPU:    150m
Memory: 350 MiB
```

Kubernetes scheduler reserves based largely on **requests**, not historical usage.

Ten such pods may appear to require:

```text
20 CPUs
40 GiB RAM
```

even though they actually consume much less.

Result:

```text
inflated requests
      ↓
poor bin packing
      ↓
more AKS nodes
      ↓
higher bill
```

So I rightsize:

```text
requests
limits
```

using representative usage.

Microsoft's AKS cost guidance recommends accurate pod requests and limits because over-requesting drives unnecessary cluster capacity. ([Microsoft Learn][9])

---

### **6. Rightsize node VM SKUs**

Dev clusters often get copied from production:

```text
Production:
D8s_v5

Development:
D8s_v5
```

even though development could use:

```text
D2s_v5
or
D4s_v5
```

depending on workload requirements.

I inspect:

```text
CPU
memory
pod requests
disk/network requirements
```

and choose cheaper node types where practical.

---

### **7. Use Spot node pools for interruptible workloads**

Excellent candidates:

```text
CI jobs
load tests
batch tasks
throwaway development workloads
```

Architecture:

```text
AKS
│
├── Small Standard system/baseline pool
│
└── Spot user pool
     ↓
   cheap interruptible workloads
```

If Azure evicts Spot:

```text
workloads reschedule/retry
```

Microsoft recommends Spot node pools for fault-tolerant AKS workloads as a cost-optimization technique. ([Microsoft Learn][9])

But I wouldn't put workloads on Spot if:

```text
eviction breaks developer state
```

or the application cannot tolerate interruption.

---

### **8. Reduce Log Analytics ingestion**

AKS can quietly become:

```text
Compute bill
+
Monitoring bill
```

For nonprod, I often don't need production-level telemetry volume.

I might reduce:

```text
DEBUG logs
container stdout noise
high-volume Kubernetes logs
trace sampling percentage
retention
unneeded diagnostic categories
```

and select cheaper table plans for lower-value telemetry where supported.

---

### **9. Clean unused storage and public networking resources**

Stopping AKS does not mean:

```text
every attached Azure resource
becomes free
```

Check:

```text
Managed disks
Snapshots
Load Balancers
Public IPs
NAT Gateway
Application Gateway
Log Analytics
Container Registry
Private Endpoints
```

Some continue charging independently.

So I inspect the **entire resource group/subscription**, not just node compute.

---

### **10. Use shared nonprod clusters where isolation permits**

Instead of:

```text
Team A → cluster
Team B → cluster
Team C → cluster
Team D → cluster
```

for tiny dev workloads, an organization could use:

```text
Shared development AKS
│
├── namespace team-a
├── namespace team-b
├── namespace team-c
└── namespace team-d
```

with:

```text
ResourceQuota
LimitRange
RBAC
NetworkPolicy
```

when security and organizational boundaries permit.

Microsoft's current AKS cost guidance specifically recommends namespace resource quotas for multitenant/shared clusters. ([Microsoft Learn][9])

This can eliminate duplicated:

```text
system nodes
load balancers
monitoring infrastructure
```

across many small clusters.

---

### **11. Put cost ceilings around nonprod**

For example:

```text
Node pool

min = 0/1
max = 5
```

rather than:

```text
max = 100
```

Then configure:

```text
Azure Budget
+
forecast alerts
+
Cost anomaly alert
```

because a broken HPA or runaway test shouldn't scale a dev environment into a production-sized bill.

---

### **A strong nonprod design**

```text
                 Nonprod AKS
                     │
      ┌──────────────┼──────────────┐
      ↓              ↓              ↓
Small system     Standard user    Spot user
pool             pool             pool
      │              │              │
      │          autoscale 0-N    interruptible
      │
      └──────────────┬──────────────┘
                     ↓
             Right-sized pods
                     ↓
         Reduced nonprod telemetry
                     ↓
          Scheduled cluster stop
             nights/weekends
```

---

### **What I would optimize first**

If the cluster is used only 8 hours/day:

I would **not start by buying a 3-year commitment**.

I would first:

```text
Stop it for 16 idle hours
```

because eliminating unused consumption usually saves more than merely discounting unused consumption.

The FinOps rule is:

```text
Remove waste
   ↓
Rightsize
   ↓
Then optimize unit price
```

---

### **Strong interview answer**

> “For a nonproduction AKS cluster, my biggest objective is eliminating idle compute. If developers only need the cluster during working hours, I automate AKS start/stop for nights and weekends. If the cluster must remain available, I scale user node pools toward zero and use Cluster Autoscaler with a low minimum. Then I rightsize pod requests and node SKUs, because inflated requests cause unnecessary nodes. For fault-tolerant dev, CI, or batch workloads I can use Spot user pools. I also reduce unnecessary Log Analytics ingestion and clean up persistent disks, public IPs, gateways, and other resources that continue charging independently. Where isolation allows, I can consolidate multiple small team clusters into a shared nonproduction cluster with namespaces and quotas.”

**Memory line:**
**For nonprod AKS: eliminate idle hours before trying to discount them.**

**Interview trap:**
Stopping or scaling down AKS nodes does **not automatically eliminate every related charge**—storage, networking, monitoring, and other Azure resources can continue billing.

**Keywords:**
AKS start/stop, Cluster Autoscaler, scale-to-zero, Spot node pool, requests/limits, rightsizing, Log Analytics

**Likely follow-ups:**

* Can an AKS user node pool scale to zero?
* What happens when an AKS cluster is stopped?
* Why can oversized pod requests increase cost?
* Would you buy Reservations for a dev AKS cluster?
