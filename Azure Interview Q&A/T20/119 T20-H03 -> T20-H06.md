## **T20-H03. How would you reduce Log Analytics costs without losing critical operational data?**

**Answer:**
I would **not start by deleting logs or blindly reducing retention**. I would first determine **which tables and data sources generate the most billable ingestion**, classify telemetry by operational value, and then reduce or move only the low-value/high-volume data.

My approach would be:

```text
Measure ingestion
      ↓
Identify expensive tables/sources
      ↓
Classify telemetry by value
      ↓
Filter before ingestion
      ↓
Use appropriate table plans
      ↓
Tune sampling + retention
      ↓
Add ingestion alerts/budgets
      ↓
Continuously review
```

Microsoft's current Azure Monitor guidance says that **log ingestion is usually the largest Azure Monitor cost component** and recommends controlling collection before data reaches the workspace. ([Microsoft Learn][1])

---

### **1. Find where the money is actually going**

First I open:

```text
Log Analytics Workspace
        ↓
Usage and Estimated Costs
```

Then identify high-volume tables.

For example:

```text
ContainerLogV2        850 GB/month
AppTraces             500 GB/month
AppRequests           150 GB/month
SecurityEvent          40 GB/month
AzureActivity           5 GB/month
```

Immediately:

```text
ContainerLogV2
+
AppTraces
```

become the first targets.

I would also correlate with:

```text
deployment date
logging-level changes
new diagnostic settings
new namespaces/apps
trace-sampling changes
traffic growth
```

because a sudden increase is often caused by a configuration change rather than normal growth.

---

### **2. Classify logs by operational value**

I would not treat every log record equally.

A useful model:

```text
Tier 1 — Critical
├── security events
├── failed authentication
├── application errors
├── availability/SLO telemetry
├── audit events
└── critical dependency failures

Tier 2 — Troubleshooting
├── informational application logs
├── Kubernetes events
├── dependency details
└── detailed traces

Tier 3 — Low value / noisy
├── health-check successes
├── repetitive DEBUG messages
├── successful probes
├── verbose framework logs
└── duplicate telemetry
```

Then:

```text
Tier 1
→ retain/search quickly

Tier 2
→ cheaper storage/table plan where suitable

Tier 3
→ filter, sample, aggregate, or don't ingest
```

The goal isn't:

```text
collect less
```

for its own sake.

It is:

```text
preserve information needed
for incidents, security and SLOs
while eliminating telemetry
that provides almost no decision value
```

---

### **3. Filter before ingestion**

This is usually the highest-value optimization.

Suppose application logs contain:

```text
GET /health 200
GET /health 200
GET /health 200
GET /health 200
...
```

millions of times.

If I ingest all of them and then delete them later:

```text
collection
   ↓
ingestion charge already happened
   ↓
retention reduction
```

doesn't undo the ingestion cost.

Better:

```text
Source / DCR transformation
          ↓
drop low-value events
          ↓
Log Analytics
```

Possible techniques:

```text
Application logging levels
Azure Monitor Agent DCRs
DCR transformations
namespace/container filtering
diagnostic-setting category selection
OpenTelemetry Collector filtering
```

Microsoft's current Azure Monitor cost guidance specifically recommends limiting data collection and filtering unnecessary records. ([Microsoft Learn][1])

---

### **4. Fix production logging levels**

A classic problem:

```text
LOG_LEVEL=DEBUG
```

accidentally enabled in production.

For every request:

```text
request received
headers
request body
SQL statement
SQL result
cache lookup
dependency details
response body
```

At high traffic:

```text
1 KB useful log
→ 20 KB verbose logs

100 million requests
→ enormous ingestion increase
```

Production might instead use:

```text
ERROR
WARN
important INFO
structured business/operational events
```

while enabling DEBUG temporarily for a specific:

```text
service
pod
instance
time window
```

during troubleshooting.

---

### **5. Use different table plans based on value**

Azure Monitor Logs currently supports table plans including:

```text
Analytics
Basic
Auxiliary / Lake
```

with different feature and cost trade-offs. ([Microsoft Learn][2])

Conceptually:

```text
Analytics
→ frequently queried
→ alerting
→ investigations
→ richer capabilities

Basic
→ troubleshooting data
→ less frequently queried

Auxiliary / Lake
→ very high-volume
→ low-touch / long-term data
```

Example:

```text
SecurityEvent
AppRequests
AppExceptions
→ Analytics

Verbose container logs
that engineers inspect rarely
→ Basic if supported

Huge verbose audit/debug datasets
→ Auxiliary/Lake where requirements fit
```

---

### **But cheaper table plans have trade-offs**

This matters.

Moving everything to Basic/Auxiliary may reduce ingestion cost, but:

```text
features
query behavior
alert support
query charges
```

can differ.

For example, Microsoft currently notes that moving an Analytics table to Auxiliary can cause **alerts on that table to stop working**, and Basic/Auxiliary queries can incur scanned-data charges. ([Microsoft Learn][2])

Therefore:

```text
cheapest table
≠ automatically best table
```

I keep telemetry required for real-time alerts and incident response on the appropriate plan.

---

### **6. Use sampling for high-volume telemetry**

For distributed tracing:

```text
100% traces
×
millions of requests
```

can become extremely expensive.

Instead:

```text
Normal successful requests
→ sample

Errors
→ retain at high/100% rate

Slow requests
→ retain

Rare paths
→ retain

Interesting business transactions
→ retain
```

Example:

```text
Successful GET /catalog
→ 5–10% sampling

HTTP 500
→ 100%

Latency > SLO
→ 100%
```

With OpenTelemetry, I would consider:

```text
head sampling
or
tail sampling
```

depending on architecture.

Tail sampling is particularly useful when I want to retain:

```text
errors
high latency
interesting traces
```

while dropping routine successes.

---

### **7. Aggregate instead of logging every event**

Suppose an application records:

```text
1 million success events/hour
```

but the operational question is only:

> How many succeeded per minute?

Instead of storing:

```text
1,000,000 raw records
```

I might generate:

```text
success_count = 16,742/minute
```

through metrics or summary rules where appropriate.

General observability principle:

```text
Metrics
→ cheap aggregate health signals

Logs
→ detailed discrete events

Traces
→ request-level causality
```

Don't force every observation into logs.

---

### **8. Optimize retention intelligently**

I ask:

```text
How long must this data remain
interactively queryable?
```

Example:

```text
Operational troubleshooting:
30–90 days

Security investigation:
180 days

Compliance:
1–7 years
```

But that does **not mean all seven years must remain in expensive interactive Analytics retention**.

A better design may be:

```text
Recent period
→ interactive Analytics

Older period
→ long-term retention
```

Azure Monitor currently supports long-term retention up to **12 years**, while Analytics retention can be configured separately. ([Microsoft Learn][3])

---

### **Important retention trap**

Microsoft currently includes **31 days of Analytics retention in ingestion pricing** for most Analytics tables.

Therefore:

```text
30 days → 7 days
```

does **not necessarily reduce the bill**.

Microsoft explicitly states that reducing Analytics retention below 31 days does not reduce costs because 31 days are included in ingestion pricing. ([Microsoft Learn][3])

So if the main cost is:

```text
2 TB/day ingestion
```

changing:

```text
30-day retention
→ 7 days
```

is not the first optimization I would choose.

---

### **9. Reduce AKS telemetry intelligently**

For AKS specifically:

```text
AKS
├── application logs
├── stdout/stderr
├── kube events
├── node logs
├── control-plane logs
├── metrics
└── traces
```

I would ask which are actually needed.

For example:

```text
Production
├── errors
├── warnings
├── security events
├── important Kubernetes events
├── application SLO metrics
└── sampled traces

instead of

EVERYTHING
+
DEBUG
+
every successful probe
```

If one namespace generates most of `ContainerLogV2`, I fix that workload rather than weakening observability for the entire cluster.

---

### **10. Add cost guardrails**

After optimization:

```text
Workspace ingestion
      ↓
normal baseline established
```

I configure:

```text
ingestion-volume alerts
budget alerts
cost anomaly alerts
Advisor recommendations
```

Microsoft's current Azure Monitor cost guidance also lists **daily caps** as a possible preventative budget measure. ([Microsoft Learn][1])

However, I would be careful with a hard daily cap for production because:

```text
cap reached
     ↓
important telemetry may stop being collected
     ↓
major incident occurs
     ↓
exact logs needed are missing
```

So I treat it as a last-resort guardrail, not my primary optimization mechanism.

---

### **Strong interview answer**

> “I would first identify which tables and sources generate the most billable ingestion rather than blindly reducing retention. Then I classify telemetry by operational value. Critical error, security, audit and SLO data stays readily searchable, while noisy DEBUG logs, successful health checks and repetitive events are filtered before ingestion. I use DCR transformations or source-side filtering, apply trace sampling, and select Analytics, Basic or Auxiliary table plans according to query and alert requirements. I configure interactive versus long-term retention according to operational and compliance needs. I also remember that lowering Analytics retention below the included period doesn't necessarily save money, so reducing unnecessary ingestion is usually the strongest optimization.”

**Memory line:**
**Protect signal, remove noise—the biggest Log Analytics saving usually comes before ingestion.**

**Interview trap:**
Do not immediately reduce all retention or move all tables to cheaper plans; you may destroy alerting and incident-response capabilities while barely addressing the main ingestion cost.

**Keywords:**
Log Analytics, ingestion, DCR, table plans, Analytics, Basic, Auxiliary, sampling, retention, OpenTelemetry

**Likely follow-ups:**

* How would you find the most expensive Log Analytics table?
* Would you use a daily cap in production?
* Analytics vs Basic vs Auxiliary?
* How would you reduce OpenTelemetry cost?

# **T20-H04. When would you choose reservations instead of autoscaling or Spot capacity?**

**Answer:**
I would choose an Azure Reservation when I have a **predictable, continuously used baseline of eligible capacity that I expect to need for one or three years**.

But the important architecture answer is that:

```text
Reservations
Autoscaling
Spot
```

are **not direct substitutes**.

They optimize different things:

```text
Reservation
→ price of predictable baseline capacity

Autoscaling
→ quantity of capacity over time

Spot
→ price in exchange for interruption risk
```

Microsoft explicitly recommends purchasing reservations based on **consistent base usage**. ([Microsoft Learn][4])

---

### **Example workload**

Suppose a production API requires:

```text
Minimum:
8 VM instances

Normal:
8–12

Peak:
30
```

The wrong decision is:

```text
Reserve 30
```

because most of the day:

```text
22 reserved instances
could be unused
```

A stronger design is:

```text
Reliable baseline:
8 instances
      ↓
Reservation

Variable demand:
0–22 additional instances
      ↓
Autoscaling
      ↓
PAYG / other suitable pricing
```

---

### **1. Choose Reservations for stable baseline capacity**

Good candidates:

```text
24×7 production VMs
steady database capacity
stable App Service baseline
known enterprise infrastructure
long-running predictable compute
```

Example:

```text
Production SQL/VM estate

Minimum usage:
20 instances
every hour
for the next 3 years
```

That's exactly the kind of usage where I would evaluate Reservations.

Microsoft's latest reservation guidance says to base purchases on **consistent base usage**, and reservation benefits apply hourly. ([Microsoft Learn][5])

---

### **2. Don't choose a Reservation just because a VM exists today**

I ask:

```text
Will we still need:
this service?
this SKU/family?
this region?
this quantity?
this baseline?
```

over:

```text
1 year
or
3 years?
```

If architecture is about to migrate:

```text
VM
→ Container Apps
```

or:

```text
large VMs
→ serverless
```

then a long commitment may be a poor fit.

---

### **3. Autoscaling solves a different problem**

Autoscaling handles:

```text
demand changes
```

Example:

```text
02:00
4 instances

12:00
15 instances

Black Friday
40 instances
```

Reservation:

```text
does not automatically
change instance count
```

Autoscaling:

```text
does not automatically
give the deepest long-term discount
```

Therefore they can work together:

```text
Right-sized baseline
      ↓
Reservation

Burst capacity
      ↓
Autoscaling
```

---

### **4. Spot solves another different problem**

Spot is appropriate when the workload can tolerate:

```text
eviction
capacity unavailability
interruption
```

because Azure can reclaim Spot capacity.

Microsoft's current Spot guidance explicitly states:

```text
No SLA
No availability guarantee
Can be evicted
```

and recommends keeping enough regular capacity to satisfy uptime requirements. ([Microsoft Learn][6])

So I would not replace:

```text
8 mandatory production instances
```

with:

```text
8 Spot instances
```

for a strict availability target.

---

### **5. Production hybrid strategy**

A strong design could be:

```text
Production compute
│
├── Stable baseline
│      ↓
│   Standard capacity
│      +
│   Reservations
│
├── Variable required capacity
│      ↓
│   Autoscaling
│      ↓
│   Standard/PAYG
│
└── Fault-tolerant opportunistic capacity
       ↓
     Spot
```

Example:

```text
10 baseline nodes
→ standard + reservation

10 additional predictable peaks
→ autoscaling standard

20 batch/background workers
→ Spot when capacity exists
```

These tools complement each other.

---

### **6. Reservation vs Spot decision**

Ask:

> Can this capacity disappear at any moment?

If:

```text
No
```

and it's consistently required:

```text
Reservation candidate
```

If:

```text
Yes
```

and workload is retryable:

```text
Spot candidate
```

For example:

```text
Primary database
→ Reservation

CI runners
→ Spot

Batch image conversion
→ Spot

Core API minimum replicas
→ Reservation

Optional workers
→ Spot
```

---

### **7. Reservation vs autoscaling decision**

Ask:

> Is the capacity stable or variable?

If:

```text
stable minimum
```

→ Reservation can optimize the price.

If:

```text
variable capacity
```

→ Autoscaling optimizes quantity.

But:

```text
stable minimum + variable peak
```

means:

```text
use both
```

---

### **8. Rightsize before reserving**

This is one of the strongest FinOps rules.

Bad:

```text
D16 VM
actual requirement D4
      ↓
Buy 3-year D16 reservation
```

Now I've:

```text
discounted waste
```

Better:

```text
Measure
 ↓
Rightsize
 ↓
Determine stable baseline
 ↓
Reservation
```

---

### **9. Watch reservation utilization**

A reservation generates good savings only if it's actually used.

Microsoft says reservation savings depend on **sustained utilization**, and Azure exposes utilization percentage/history so underused reservations can be detected. ([Microsoft Learn][7])

Example:

```text
Reservation utilization

98%
→ excellent

75%
→ investigate

30%
→ likely poor commitment decision
```

Low utilization may mean:

```text
wrong SKU
wrong region
wrong scope
workload disappeared
capacity rightsized
architecture changed
```

---

### **Decision tree**

```text
Capacity required?
      ↓
Is it predictable and continuously used?
     / \
   Yes  No
   ↓     ↓
Reservation    Variable demand?
candidate          ↓
              Autoscaling

Can workload tolerate interruption?
     / \
   Yes  No
   ↓     ↓
 Spot      Standard capacity
candidate
```

Then combine these when appropriate.

---

### **Strong interview answer**

> “I choose Reservations for predictable baseline capacity that I expect to consume consistently for one or three years. I don't view Reservations, autoscaling and Spot as mutually exclusive. A Reservation optimizes the price of stable capacity; autoscaling changes the amount of capacity as demand changes; and Spot reduces price by accepting eviction risk. For a production service I might reserve the eight instances I need continuously, autoscale standard instances for normal peaks, and use Spot only for interruptible background workers. I also rightsize before buying a reservation and monitor reservation utilization afterward so I don't lock in waste.”

**Memory line:**
**Reserve the reliable baseline, autoscale the variable demand, use Spot only for interruptible capacity.**

**Interview trap:**
Do not compare these as three equivalent pricing choices. They solve **different capacity and risk problems**.

**Keywords:**
Reservations, baseline capacity, autoscaling, Spot, utilization, rightsize, predictable workload

**Likely follow-ups:**

* Why should you rightsize before buying Reservations?
* Can Reservations and autoscaling work together?
* When would Spot be inappropriate?
* What would low reservation utilization tell you?

# **T20-H05. How would you implement showback or chargeback for multiple teams sharing Azure?**

**Answer:**
I would first establish **clear cost ownership**, enforce consistent subscriptions/resource groups/tags, allocate directly attributable costs to each team, and then redistribute genuinely shared platform costs—such as Azure Firewall, ExpressRoute, central monitoring, or shared AKS—using an agreed allocation model.

The conceptual difference is:

```text
SHOWBACK
→ show teams what they consumed and cost

CHARGEBACK
→ use that allocation to financially
  charge costs back to those teams
```

Azure Cost Management can help with allocation and reporting, but Microsoft explicitly states that its cost-allocation rules **do not change the Azure invoice**; internal chargeback happens within the organization. ([Microsoft Learn][8])

---

### **1. Establish ownership hierarchy**

Ideally:

```text
Management Group
    ↓
Subscriptions
    ↓
Resource Groups
    ↓
Resources
```

map meaningfully to:

```text
business unit
application
environment
team
```

For example:

```text
Production MG
│
├── payments-prod-sub
│
├── orders-prod-sub
│
└── analytics-prod-sub
```

Then a lot of cost ownership is already obvious.

---

### **2. Enforce business tags**

For resources that share subscriptions, I would standardize tags such as:

```text
CostCenter
Application
Team
Environment
Product
BusinessUnit
```

Example:

```text
Application = Payments
Team        = Checkout
CostCenter  = FIN-142
Environment = Production
```

Then Cost Analysis can group spending by:

```text
Team
Application
CostCenter
```

instead of only technical Azure scopes.

---

### **3. Make tagging enforceable**

I would not depend on:

> “Please remember to tag everything.”

Instead:

```text
Management Group
      ↓
Azure Policy Initiative
      ↓
Require/Modify tags
      ↓
Subscriptions
```

For example:

```text
CostCenter
→ required

Application
→ required

Environment
→ inherited/modified where deterministic
```

This makes cost reports trustworthy.

---

### **4. Separate direct costs from shared costs**

Example monthly bill:

```text
Payments resources       $30,000
Orders resources         $20,000
Analytics resources      $10,000

Shared Platform
├── Azure Firewall        $6,000
├── ExpressRoute          $4,000
├── Log Analytics         $5,000
└── Shared AKS            $5,000

Shared total             $20,000
```

Direct cost:

```text
belongs clearly
to one workload
```

Shared cost:

```text
must be allocated
using an agreed model
```

---

### **5. Pick allocation drivers that reflect consumption**

I wouldn't automatically say:

```text
4 teams
→ each pays 25%
```

if usage differs dramatically.

Possible drivers:

```text
Actual Azure consumption
Compute cost
Storage cost
Network cost
Request volume
Number of workloads
Reserved capacity share
Headcount
Custom fixed percentage
```

Microsoft Cost Management cost-allocation rules currently support distributions based on:

```text
compute cost
storage cost
network cost
custom percentage
```

between supported subscriptions/resource groups/tags. ([Microsoft Learn][8])

---

### **Example: shared Firewall**

Suppose:

```text
Azure Firewall
monthly cost = $6,000
```

Teams' network usage:

```text
Payments    50%
Orders      30%
Analytics   20%
```

Allocation:

```text
Payments
→ $3,000

Orders
→ $1,800

Analytics
→ $1,200
```

Now each team's showback includes its share of the platform network cost.

---

### **6. Azure Cost Allocation Rules**

Microsoft Cost Management can redistribute shared costs from sources such as:

```text
Subscriptions
Resource Groups
Tags
```

to target:

```text
Subscriptions
Resource Groups
Tags
```

for reporting. ([Microsoft Learn][8])

Conceptually:

```text
Shared Platform Subscription
         ↓
Cost Allocation Rule
         ↓
 ┌───────┼─────────┐
 ↓       ↓         ↓
Payments Orders Analytics
50%      30%       20%
```

Allocated cost then appears in Cost Analysis for those targets.

---

### **Important current limitation**

Azure Cost Allocation doesn't change:

```text
Microsoft's actual invoice
```

and doesn't alter who legally owes Microsoft.

Microsoft explicitly states:

```text
Cost allocation
→ supports accountability/reporting

Chargeback process
→ occurs internally
```

([Microsoft Learn][8])

So:

```text
Azure
→ calculates/reports allocation

Finance/ERP
→ performs actual internal chargeback
```

---

### **7. Showback first, then chargeback**

I wouldn't immediately start financially charging teams from an immature tagging model.

Rollout:

```text
Phase 1
Showback only
      ↓
teams can see costs
      ↓
validate tagging/allocation

Phase 2
Agree allocation rules
      ↓
shared-service model

Phase 3
Chargeback
      ↓
Finance allocates budget/cost
```

Why?

Because chargeback based on bad metadata causes:

```text
political disputes
wrong incentives
teams gaming tags
loss of trust in FinOps data
```

Showback helps validate the model first.

---

### **8. Shared AKS needs deeper allocation**

Suppose four teams share one AKS cluster:

```text
AKS
├── namespace payments
├── namespace orders
├── namespace search
└── namespace analytics
```

Azure might see much of the infrastructure cost as:

```text
shared node pool
```

rather than separate team VMs.

I may combine Azure cost data with:

```text
namespace CPU requests/usage
memory requests/usage
persistent storage
network consumption
```

from Kubernetes cost tooling.

Then:

```text
Node pool cost
      ↓
allocate by normalized
CPU + memory usage/request model
```

rather than dividing evenly.

---

### **9. Central observability cost needs allocation too**

For example:

```text
One central Log Analytics Workspace
```

used by:

```text
20 teams
```

I can analyze ingestion by:

```text
resource
subscription
table
application metadata
```

and use that to allocate cost.

This also creates an incentive:

```text
Team A
500 GB/day DEBUG logs
      ↓
large showback bill
      ↓
team optimizes logging
```

which is a core FinOps behavior.

---

### **10. Use amortized cost for commitments**

For Reservations or Savings Plans, simply showing the upfront purchase against the platform/billing subscription can distort team economics.

A mature showback model should use:

```text
amortized cost
```

where appropriate so commitment costs are associated over time with the workloads that consume the benefit.

Microsoft exposes reservation utilization and cost reporting for precisely this type of analysis. ([Microsoft Learn][7])

---

### **11. Dashboard**

I would give each team something like:

```text
Payments — August

Direct Azure cost            $30,000

Allocated shared:
Firewall                      $3,000
ExpressRoute                  $1,800
Monitoring                    $2,100
Shared AKS                    $4,000
                              -------
Total                         $40,900

Budget                        $42,000
Forecast                      $43,300
Variance                      +3.1%
```

And then drill down:

```text
Service
Resource
Environment
CostCenter
Tag
```

So teams can actually act on the data.

---

### **12. Governance loop**

```text
Resource creation
      ↓
mandatory ownership metadata
      ↓
Cost Management
      ↓
direct + shared cost allocation
      ↓
team dashboard
      ↓
budget / forecast
      ↓
optimization action
      ↓
monthly FinOps review
```

That is much stronger than generating a spreadsheet after the invoice arrives.

---

### **Strong interview answer**

> “I would implement showback first by establishing reliable ownership through subscriptions, resource groups and mandatory tags such as Team, Application and CostCenter. Direct workload costs are attributed directly to the owning team. For shared platform services such as Firewall, ExpressRoute, monitoring or shared AKS, I define an agreed allocation driver—such as compute, storage, network usage or a custom percentage—and use Cost Management cost-allocation rules where applicable. Azure reallocates those costs for reporting, but it doesn't change Microsoft's invoice, so actual chargeback is performed by the internal finance process. Once teams trust the showback data, I can move toward chargeback and give each team budgets, forecasts and optimization accountability.”

**Memory line:**
**Showback makes cost visible; chargeback turns that trusted allocation into financial accountability.**

**Interview trap:**
Azure Cost Allocation **does not rewrite Microsoft's invoice or directly bill internal teams**. ([Microsoft Learn][8])

**Keywords:**
Showback, chargeback, cost allocation, tags, CostCenter, shared services, amortized cost, FinOps

**Likely follow-ups:**

* How would you allocate a shared AKS cluster?
* Showback vs chargeback?
* How would you allocate ExpressRoute or Firewall cost?
* Why start with showback instead of chargeback?

# **T20-H06. How would you balance reliability and cost for a production application?**

**Answer:**
I would start with **business-defined reliability targets—SLO, RTO, RPO and acceptable business impact—and spend only enough to meet those requirements with validated safety margin**.

I would not optimize for:

```text
maximum reliability regardless of cost
```

or:

```text
minimum cost regardless of reliability
```

The objective is:

```text
Required business reliability
          +
Efficient architecture
          =
Best value
```

Microsoft's Well-Architected Framework explicitly says cost decisions should be measured against reliability impact: if the business cost of disruption is greater than the cost of preventing or recovering from it, invest in the reliability measure; otherwise the added resilience may not be justified. ([Microsoft Learn][9])

---

### **1. Begin with business targets**

Before designing:

```text
Availability required?
99.9?
99.95?
99.99?

RTO?
4 hours?
30 minutes?
5 minutes?

RPO?
24 hours?
1 hour?
near-zero?
```

Because these architectures are radically different.

Example:

```text
Internal HR portal

SLO = 99.9%
RTO = 4 hours
RPO = 1 hour
```

doesn't automatically need:

```text
active-active
three regions
global database replication
```

But:

```text
Payment authorization API

SLO = 99.99%
RTO < 5 min
RPO ≈ 0
```

may justify much greater redundancy.

---

### **2. Quantify downtime cost**

Suppose:

```text
Outage costs:
$100,000/hour

Multi-zone architecture:
+$5,000/month
```

That extra reliability investment is easy to justify.

Another workload:

```text
Internal dev dashboard

Outage cost:
very low

Secondary active region:
+$30,000/month
```

Maybe:

```text
active-passive
backup + restore
```

is economically more sensible.

Microsoft's Well-Architected guidance directly recommends evaluating the **cost of disruption against the cost of reliability mechanisms**. ([Microsoft Learn][9])

---

### **3. Use zones before regions when they satisfy the requirement**

For many production workloads:

```text
Single instance
      ↓
cheap
      ↓
poor fault tolerance
```

Better:

```text
Zone 1   Zone 2   Zone 3
  │        │        │
  └────────┼────────┘
       Load Balancer
```

This protects against zonal failure without automatically paying the complexity and network/data-replication costs of multi-region architecture.

Then I ask:

> Is regional failure part of the business requirement?

If no:

```text
multi-zone
may be enough
```

If yes:

```text
multi-region DR/HA
```

may be required.

---

### **4. Don't jump directly to active-active multi-region**

Reliability options:

```text
Single region
      ↓
Multi-zone

Multi-region
├── Backup/restore
├── Active-passive
└── Active-active
```

Generally:

```text
reliability ↑
cost ↑
operational complexity ↑
```

Active-active can require:

```text
duplicate compute
database replication
global traffic routing
cross-region networking
duplicate monitoring
more testing
more operational expertise
```

Microsoft's mission-critical guidance explicitly calls out the additional financial cost of duplicating resources and distributing them across regions for reliability. ([Microsoft Learn][10])

---

### **5. Keep a reliable baseline, autoscale above it**

Suppose an API requires at least:

```text
4 instances
```

to survive:

```text
node failure
deployment
traffic burst
```

Then:

```text
Min = 4
Max = 30
```

can balance:

```text
reliability baseline
+
elastic cost
```

Bad FinOps:

```text
30 instances
24×7
```

Bad reliability:

```text
Min = 1
```

just to save money.

Strong design:

```text
Minimum capacity
→ enough to meet normal failure assumptions

Autoscaling
→ handles variable demand
```

Microsoft warns that aggressive scale-in or constrained scaling can save money while making a workload more vulnerable to sudden spikes or failures. ([Microsoft Learn][9])

---

### **6. Add headroom deliberately**

Running every resource at:

```text
99% utilization
```

may look financially efficient.

Operationally:

```text
one node fails
      ↓
remaining nodes have no capacity
      ↓
cascade
```

A reliable system requires some:

```text
headroom
```

for:

```text
node loss
deployments
scaling lag
traffic spikes
maintenance
```

Microsoft's reliability guidance specifically notes that some overprovisioning can be necessary because autoscaling isn't instantaneous. ([Microsoft Learn][11])

So:

```text
100% utilization
≠ perfect cost optimization
```

---

### **7. Use Reservations for the reliable baseline**

Suppose:

```text
4 instances
must always exist
```

I might:

```text
rightsize them
      ↓
reserve 4-instance baseline
```

Then:

```text
instances 5–30
→ autoscaled flexible capacity
```

This preserves reliability while lowering the cost of unavoidable baseline capacity.

---

### **8. Use Spot only where eviction doesn't threaten the SLO**

Production can use Spot—but carefully.

Example:

```text
AKS
│
├── Standard system/core node pool
├── Standard application baseline
└── Spot pool
      ↓
   async batch jobs
   background processing
   retryable workers
```

Not:

```text
All checkout API replicas
→ Spot
```

if losing them would violate availability.

Microsoft says Spot shouldn't be the only source of capacity for workloads that need uptime guarantees. ([Microsoft Learn][6])

---

### **9. Reliability isn't only compute redundancy**

I budget for:

```text
Backups
Monitoring
Alerts
DR testing
Security
Incident response
Automation
```

because:

```text
20 replicas
```

don't help if:

```text
database deleted
bad deployment corrupts all instances
DNS fails
credentials expire
nobody detects the incident
```

Microsoft's reliability guidance explicitly notes that observability, DR drills, backup retention, and operational response all introduce cost but are part of achieving a reliability target. ([Microsoft Learn][11])

---

### **10. Optimize observability without removing it**

Bad cost saving:

```text
Monitoring bill high
      ↓
disable logs + alerts
```

Now outage:

```text
MTTD ↑
MTTR ↑
```

Better:

```text
remove noisy telemetry
sample traces
optimize retention
keep SLO + error + security signals
```

Reliability still has observability; it just becomes efficient.

---

### **11. Backups based on RPO**

Example:

```text
RPO = 24 hours
```

doesn't require:

```text
continuous synchronous
cross-region replication
```

Maybe:

```text
daily backups
```

satisfy the business requirement.

But:

```text
RPO ≈ 0
```

requires a much more expensive design.

Thus:

```text
RPO
→ determines data-protection cost

RTO
→ determines recovery architecture cost
```

---

### **12. Reliability tier by workload**

I would not give every application identical architecture.

Example:

```text
Tier 0 — Payment system
SLO 99.99%
Multi-zone
Multi-region DR
strict RPO/RTO

Tier 1 — Customer portal
SLO 99.95%
Multi-zone
regional DR

Tier 2 — Internal business app
SLO 99.9%
zone-aware/simpler DR

Tier 3 — Dev tooling
business-hours availability
backup only
```

Now spending follows:

```text
business criticality
```

rather than an arbitrary company-wide template.

---

### **13. Calculate whether another nine is worth it**

Remember approximate allowable annual downtime:

```text
99.9%
≈ 8h 46m/year

99.99%
≈ 52m/year

99.999%
≈ 5m/year
```

Moving:

```text
99.9 → 99.99
```

may require:

```text
more replicas
multi-zone services
better DR
more automation
better observability
more testing
```

The question is:

> Is reducing expected downtime by roughly eight hours/year worth the additional cost for this workload?

For payments:

```text
probably
```

For an internal wiki:

```text
perhaps not
```

---

### **14. Test reliability claims**

I wouldn't pay for:

```text
secondary region
```

and simply assume:

```text
DR works
```

I would perform:

```text
failover tests
restore tests
zone-failure tests
load tests
chaos/fault tests where appropriate
```

and measure:

```text
RTO
RPO
SLO
error budget
```

Otherwise:

```text
expensive redundancy
+
untested recovery
=
false confidence
```

### **Complete decision model**

```text
Business criticality
        ↓
SLO / RTO / RPO
        ↓
Failure modes to survive
        ↓
Cheapest architecture
that satisfies those targets
        ↓
Right-size baseline
        ↓
Zones / DR as required
        ↓
Autoscale variable demand
        ↓
Reserve predictable baseline
        ↓
Spot only interruptible work
        ↓
Backup + observability
        ↓
Test reliability
        ↓
Continuously optimize cost
```

### **Strong interview answer**

> “I balance production reliability and cost by starting with business-defined SLO, RTO and RPO rather than automatically maximizing redundancy. I identify which failure modes the workload must survive and choose the least expensive architecture that still meets those targets. For many applications that means multi-zone rather than immediately going active-active multi-region. I keep enough minimum capacity and headroom to survive failures and scaling lag, then autoscale variable demand. I rightsize and reserve the predictable baseline, and use Spot only for interruption-tolerant workloads. I also preserve backups, observability and tested DR because reducing those costs can increase outage duration dramatically. The final decision comes down to comparing the financial and business impact of downtime with the cost of preventing or recovering from it.”

**Memory line:**
**Spend on reliability until the business target is met—not until architecture is maximally redundant.**

**Interview trap:**
Cost optimization does **not** mean minimizing spend. Underprovisioning, removing redundancy, reducing backups, or limiting scaling can directly violate the workload's reliability objectives. ([Microsoft Learn][9])
