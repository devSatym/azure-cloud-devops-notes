## **T20-E03. What are Azure reservations?**

**Answer:**
Azure Reservations are a **billing discount for predictable Azure usage**. You commit to eligible Azure resources for a **1-year or 3-year term**, and Azure automatically applies the reservation discount to matching usage.

The important point is:

```text
Reservation
→ billing benefit

Reservation
≠ dedicated VM sitting aside for you
≠ change to runtime configuration
```

Microsoft currently states that reservations can reduce eligible resource costs by **up to 72% compared with pay-as-you-go**, depending on the service and commitment. ([Microsoft Learn][1])

---

### **Simple example**

Suppose this VM runs continuously:

```text
Standard_D4s_v5
West Europe
24 × 7 × 365
```

With pay-as-you-go:

```text
Every hour
→ normal PAYG compute price
```

If its usage is predictable:

```text
Buy matching reservation
        ↓
1-year / 3-year commitment
        ↓
Azure detects matching VM usage
        ↓
Reservation discount applied
```

The actual VM doesn't need to become a special “reserved VM.”

---

### **Reservation is a billing construct**

This is one of the biggest interview traps.

Suppose:

```text
VM01
Standard_D4s_v5
```

is running when I purchase the reservation.

Azure can apply the discount automatically to eligible matching usage.

If VM01 disappears and another compatible VM starts:

```text
VM02
```

the reservation benefit can potentially apply to that matching usage according to the reservation's configuration and scope.

So think:

```text
Reservation
→ discount on matching consumption

NOT

Reservation
→ permanently attached to VM01
```

Microsoft explicitly says reservations are billing discounts and **do not affect the runtime state** of resources. ([Microsoft Learn][1])

---

### **What determines whether usage matches?**

Depending on the service, factors can include:

```text
SKU / resource type
Region
Quantity
Reservation scope
Instance-size flexibility where supported
```

For example:

```text
Reservation
Region = West Europe
SKU = matching VM family/size
Quantity = 5
```

Azure applies it to matching eligible usage within the reservation's benefit scope. ([Microsoft Learn][1])

---

### **Reservation scopes**

A reservation benefit can be configured for scopes such as:

```text
Resource Group
Subscription
Management Group
Shared billing scope
```

depending on the agreement/service.

Conceptually:

```text
Reservation
   ↓
Subscription scope
   ↓
matching usage in Subscription A
receives discount
```

A broader scope can improve utilization because more eligible workloads can consume the reservation benefit. ([Microsoft Learn][2])

---

### **1-year vs 3-year**

Typically:

```text
1 year
→ lower commitment
→ more flexibility

3 years
→ larger commitment
→ potentially greater savings
```

I would choose based on how confident I am that the **baseline usage will remain stable**.

---

### **Good workload for reservations**

Reservations work well for:

```text
Database running continuously
Production VM baseline
Long-running App Service capacity
Predictable Cosmos DB throughput
Stable enterprise workloads
```

They are less attractive for:

```text
very bursty workload
short-lived experiment
rapidly changing architecture
unpredictable compute demand
```

because unused reservation benefit can reduce the savings achieved.

---

### **Only reserve the baseline**

Suppose demand is:

```text
Minimum demand: 10 VMs
Peak demand:    30 VMs
```

I might reserve approximately the predictable baseline:

```text
10 VMs
→ reservation
```

and let:

```text
additional 0–20 VMs
→ PAYG / savings plan / other capacity strategy
```

This avoids committing to peak capacity that runs only occasionally.

---

### **Reservations don't necessarily cover every charge**

For a Reserved VM Instance, Microsoft says the reservation covers eligible **compute**, but additional charges such as:

```text
Storage
Networking
Some software/licensing
```

can remain separate. ([Microsoft Learn][1])

So:

```text
VM reservation
≠ entire VM-related Azure bill becomes zero
```

---

### **Reservations vs Savings Plan**

A helpful preview:

```text
Reservation
→ more specific commitment
→ typically best for stable predictable usage
→ potentially deeper discount

Savings Plan
→ hourly monetary commitment
→ more flexible across eligible compute
```

Microsoft's current guidance describes reservations as more specific while Savings Plan is better suited to changing/dynamic compute usage. ([Microsoft Learn][3])

> **In an interview, I would say:**
> “Azure Reservations provide a discounted rate in exchange for committing to eligible resource usage for one or three years. They are a billing benefit rather than dedicated reserved infrastructure, so Azure automatically applies the discount to matching usage based on attributes such as service, SKU, region and scope. I would use reservations for stable baseline workloads that I expect to run continuously, and I would avoid reserving highly variable peak capacity.”

**Memory line:**
**Reservation = long-term commitment to predictable usage in exchange for a deeper billing discount.**

**Interview trap:**
Do not say:

> “Buying a reservation creates or reserves a particular VM for me.”

It is primarily a **billing discount applied to matching usage**.

**Keywords:**
Azure Reservations, 1-year, 3-year, billing discount, baseline usage, reservation scope, utilization

**Likely follow-ups:**

* Reservation vs Savings Plan?
* What happens if a reserved VM is deleted?
* What if reservation utilization is low?
* Should you reserve peak or baseline capacity?

## **T20-E04. What is Azure Savings Plan for Compute?**

**Answer:**
Azure Savings Plan for Compute is a **billing discount where you commit to spending a fixed amount per hour on eligible Azure compute for either 1 or 3 years**.

Unlike a reservation—which is more tightly tied to specific resource characteristics—a Savings Plan is designed to be **more flexible across eligible compute services and changing workloads**. ([Microsoft Learn][3])

Think:

```text
Reservation
→ commit to specific eligible capacity

Savings Plan
→ commit to $X/hour of eligible compute
```

---

### **Simple example**

Suppose your company consistently consumes at least:

```text
$10/hour
```

of eligible Azure compute.

You purchase:

```text
Savings Plan commitment
= $8/hour
```

Each hour:

```text
Eligible compute usage
        ↓
Savings Plan discounted rate
applied up to commitment
        ↓
Usage beyond commitment
        ↓
Pay-as-you-go
```

Microsoft states that eligible usage is discounted until the hourly commitment is consumed, after which additional usage is billed at the normal on-demand rate. ([Microsoft Learn][4])

---

### **Important: commitment is hourly**

Suppose:

```text
Commitment = $10/hour
```

Hour 1:

```text
Eligible usage = $15
```

Savings-plan benefit applies up to the hourly commitment, with remaining usage billed normally.

But Hour 2:

```text
Eligible usage = $4
```

the unused commitment does **not roll over** into another hour.

Microsoft explicitly describes the hourly benefit as:

```text
use it or lose it
```

from a billing perspective. ([Microsoft Learn][4])

---

### **What compute can it cover?**

Current Savings Plan for Compute eligibility includes infrastructure costs from services such as:

```text
Azure Virtual Machines
App Service
Functions Premium
Container Instances
Dedicated Host
Container Apps
Azure Spring Apps Enterprise
```

along with eligible compute infrastructure from some additional services. It does **not generally cover storage, networking, or software charges**. ([Microsoft Learn][4])

---

### **Savings Plan vs Reservation**

This is very interview-important.

| Area                    | Reservation                 | Savings Plan for Compute                     |
| ----------------------- | --------------------------- | -------------------------------------------- |
| Commitment              | Specific eligible capacity  | $/hour                                       |
| Term                    | 1 or 3 years                | 1 or 3 years                                 |
| Flexibility             | Lower                       | Higher                                       |
| Best for                | Stable predictable workload | Changing compute usage                       |
| Across compute services | More constrained            | Broader                                      |
| Potential savings       | Often deeper                | Usually trades some discount for flexibility |

Microsoft currently describes Savings Plan discounts as up to **65%** and reservations as up to **72%** versus PAYG, though actual savings depend heavily on product and usage. ([Microsoft Learn][5])

Do not memorize those percentages as universal guarantees.

---

### **Example where Savings Plan is better**

Suppose today:

```text
10 VMs
```

six months later:

```text
5 VMs
+
Container Apps
+
App Service
```

but the organization still has a consistent amount of eligible compute spending.

A Savings Plan can be more appropriate because:

```text
workload shape changes
but
compute spend remains predictable
```

---

### **Example where Reservation may be better**

Suppose:

```text
20 SQL/VM instances
same region
same baseline
24 × 7
expected for 3 years
```

A reservation may give:

```text
higher predictability
+
potentially deeper savings
```

because the workload itself is stable.

---

### **It doesn't change runtime behavior**

Like reservations:

```text
Savings Plan
→ billing benefit
```

It does not:

```text
start compute
stop compute
reserve scaling capacity
change autoscaling
```

Microsoft explicitly states Savings Plans do not affect resource runtime state. ([Microsoft Learn][4])

---

### **Strong interview answer**

> “Azure Savings Plan for Compute lets me commit to a fixed dollar amount of eligible compute spending per hour for one or three years in exchange for discounted rates. Azure automatically applies the benefit to eligible compute within the plan's scope until the hourly commitment is consumed. Compared with reservations, Savings Plan is more flexible across eligible services and regions, so I prefer it when the workload composition may change but the organization still has predictable baseline compute spend.”

**Memory line:**
**Savings Plan = commit to predictable $/hour compute spend instead of a specific VM configuration.**

**Interview trap:**
Unused hourly commitment does **not roll over to later hours**. ([Microsoft Learn][4])

**Keywords:**
Savings Plan for Compute, hourly commitment, 1-year, 3-year, flexible compute discount, PAYG

**Likely follow-ups:**

* Savings Plan vs Reservation?
* What happens if usage is below the hourly commitment?
* Does Savings Plan cover Storage?
* Which would you choose for a changing AKS/compute estate?

## **T20-E05. What are Spot VMs?**

**Answer:**
Azure Spot VMs let you use **Azure's unused compute capacity at a substantially reduced price**, but Azure can **evict that VM when it needs the capacity back**. Therefore Spot VMs are appropriate only for workloads that can tolerate interruption.

Microsoft explicitly says Spot VMs have **no availability SLA** and may be evicted whenever Azure needs the capacity. ([Microsoft Learn][6])

The trade-off is:

```text
Much lower compute price
        ↕
No capacity/availability guarantee
```

---

### **Architecture idea**

Standard capacity:

```text
Application
    ↓
Standard VM
    ↓
Expected capacity / SLA characteristics
```

Spot:

```text
Batch workload
     ↓
Spot VM
     ↓
cheap unused capacity
     ↓
Azure needs capacity back
     ↓
EVICTION
```

So the application must be designed to survive:

```text
VM disappears
```

---

### **Good Spot workloads**

Spot works well for interruptible work such as:

```text
Batch processing
CI runners
Dev/test
Rendering
Stateless workers
Large parallel compute
Fault-tolerant data processing
```

Microsoft specifically identifies batch, dev/test and large compute workloads as strong Spot candidates. ([Microsoft Learn][6])

---

### **Bad Spot workloads**

I wouldn't make Spot the only capacity for:

```text
Primary production database
Stateful singleton
Critical API with strict SLA
Domain controller
Anything that cannot tolerate interruption
```

For production, Spot may still be used **alongside stable capacity** if the application is architected appropriately.

Example:

```text
AKS/compute pool

Baseline:
Standard nodes
★★★★★ reliable capacity

Burst:
Spot nodes
$$$$ cheaper
but interruptible
```

---

### **Eviction**

Spot VMs can be evicted because:

```text
Azure needs the capacity back
```

and, depending on pricing configuration:

```text
Spot price exceeds configured maximum price
```

Microsoft currently states Azure can provide a **best-effort Scheduled Event notification up to about 30 seconds before eviction**. ([Microsoft Learn][6])

That isn't enough time for a huge migration, so workloads should already be designed for interruption.

---

### **Eviction policies**

Current Spot VM eviction policies include:

```text
Deallocate
or
Delete
```

#### Deallocate

```text
Spot VM evicted
      ↓
Stopped / deallocated
      ↓
disk remains
      ↓
can attempt restart later
```

but capacity isn't guaranteed.

You can still incur storage charges for retained disks.

#### Delete

```text
Spot VM evicted
      ↓
VM deleted
```

and the configured associated resources are handled according to that deployment/policy. Microsoft documents both policies. ([Microsoft Learn][6])

---

### **Spot pricing is variable**

Spot price varies according to:

```text
Region
VM SKU
Available capacity
Demand
```

You can also inspect historical:

```text
Spot prices
eviction rates
```

when choosing VM sizes/regions. ([Microsoft Learn][6])

---

### **Spot is not just a “cheap VM”**

This answer is weak:

> “Spot VM is just a cheaper VM.”

The real answer is:

```text
Discount
comes specifically because
you accept interruption risk.
```

Microsoft's architecture guidance says Spot workloads must be designed around interruptibility and flexible orchestration. ([Microsoft Learn][7])

---

### **Production pattern**

Suppose an application needs 20 workers minimum and can opportunistically use another 30.

```text
Worker pool
│
├── 20 Standard VMs
│      ↓
│   reliable baseline
│
└── up to 30 Spot VMs
       ↓
    cheap burst capacity
```

If:

```text
15 Spot nodes evicted
```

the service still retains the standard baseline.

That's a much stronger use of Spot than putting every production instance on Spot.

---

### **Strong interview answer**

> “Azure Spot VMs provide discounted access to Azure's unused compute capacity, but the trade-off is that Azure can evict them whenever that capacity is needed elsewhere, and Spot VMs don't have an availability SLA. I use them for interruptible workloads such as batch jobs, dev/test, CI runners or stateless workers. The workload must handle termination and retry or reschedule work. For production I would normally keep reliable standard capacity for the baseline and use Spot only for fault-tolerant or burst capacity.”

**Memory line:**
**Spot = cheap spare compute that Azure can take back.**

**Interview trap:**
Do not build a critical workload assuming:

```text
Spot VM
→ guaranteed capacity
```

There is **no availability SLA**. ([Microsoft Learn][6])

**Keywords:**
Spot VM, unused capacity, eviction, no SLA, Scheduled Events, interruptible workload, Deallocate, Delete

**Likely follow-ups:**

* What happens during Spot eviction?
* Would you use Spot for AKS?
* Spot vs Reservation?
* How would you design an application to tolerate Spot eviction?

## **T20-M01. How can tags help with Azure cost allocation?**

**Answer:**
Tags add **business context to Azure usage**, allowing Cost Management to group costs by attributes such as:

```text
Team
Application
Environment
CostCenter
BusinessUnit
Project
```

For example:

```text
VM01
Application = Payments
CostCenter  = FIN-104
Environment = Production
```

Azure Cost Analysis can then group spending by:

```text
CostCenter
```

instead of only by technical structures such as subscription or resource group.

Microsoft describes tags as a primary way to add business context to cost data and allocate spending to organizational groups. ([Microsoft Learn][8])

---

### **Example**

Suppose one subscription contains:

```text
VM1
Application = Payments
CostCenter = 100

VM2
Application = Orders
CostCenter = 200

SQL1
Application = Payments
CostCenter = 100
```

Cost Analysis:

```text
Group by:
CostCenter
```

could show:

```text
CostCenter 100
├── VM1
└── SQL1
Total = $8,000

CostCenter 200
└── VM2
Total = $3,000
```

Now Finance can answer:

> “Which team is responsible for this spend?”

rather than only:

> “Which Azure subscription produced the bill?”

---

### **Common FinOps tags**

A practical tag strategy could include:

```text
CostCenter
Application
Environment
Owner
BusinessUnit
Project
```

For example:

```text
CostCenter  = CC-4021
Application = Checkout
Environment = Production
Owner       = Platform-Team
```

This supports:

```text
showback
chargeback
budgeting
forecasting
ownership
optimization
```

---

### **1. Cost Analysis can group by tags**

In Cost Management:

```text
Cost Analysis
      ↓
Group by
      ↓
Tag
      ↓
Application
```

Then I can see:

```text
Payments     $10,400
Orders        $7,100
Analytics     $5,800
Unknown       $1,900
```

That `Unknown` bucket itself is useful because it reveals:

```text
missing tagging discipline
```

Microsoft currently supports grouping Cost Analysis by tag values. ([Microsoft Learn][9])

---

### **2. Tags support showback**

Showback means:

```text
"We show each team
what its cloud consumption costs."
```

Example:

```text
Payments team
→ $12,000

Orders team
→ $7,000

Analytics team
→ $5,000
```

The central company still pays the Azure bill, but teams receive visibility into their consumption.

---

### **3. Tags support chargeback**

Chargeback takes the next organizational step:

```text
Shared Azure invoice
       ↓
allocate spending
       ↓
internal business units
       ↓
cost charged internally
```

Azure Cost Management's cost-allocation capabilities can help distribute shared costs for reporting, although Microsoft notes that the actual internal chargeback process happens within the organization rather than modifying Microsoft's billing responsibility. ([Microsoft Learn][10])

---

### **4. Tags don't automatically inherit on Azure resources**

Important distinction:

```text
Resource Group
CostCenter = 100
```

does **not automatically mean**:

```text
VM
CostCenter = 100
```

Azure Resource Manager tags aren't automatically inherited from parent resource groups or subscriptions. ([Microsoft Learn][11])

This is why governance often uses:

```text
Azure Policy
   ↓
Modify
   ↓
inherit/add tags
```

for the actual resource tags.

---

### **5. Cost Management also has tag inheritance**

This is a subtle but excellent distinction.

Microsoft Cost Management can apply subscription/resource-group tags to **child usage records** for reporting:

```text
Resource Group
CostCenter = 100
      ↓
Cost Management tag inheritance
      ↓
resource usage records
CostCenter = 100
```

But Microsoft explicitly notes:

```text
Cost Management inherited tags
→ modify cost/usage records

NOT
→ actual Azure resource tags
```

([Microsoft Learn][9])

So there are two different things:

```text
Azure Policy tag inheritance
→ changes resource tags

Cost Management tag inheritance
→ enriches billing/usage records
```

That is a very strong interview distinction.

---

### **6. Tags have limitations**

Cost tags aren't perfect.

For example:

```text
not every resource type supports tags
not every usage record emits them
tags may appear only after cost data refresh
```

Also, a tag added today generally doesn't magically rewrite all historical usage.

Microsoft documents these limitations in Cost Management's usage-data model. ([Microsoft Learn][12])

So for reliable enterprise FinOps I combine:

```text
Tagging standard
+
Azure Policy enforcement
+
Cost Management tag inheritance
+
Cost allocation rules
```

rather than relying on voluntary tagging.

---

### **7. Shared-service costs need additional allocation**

Suppose:

```text
Hub subscription
├── Azure Firewall
├── ExpressRoute
├── DNS
└── Monitoring
```

is used by:

```text
Payments
Orders
Analytics
```

A simple tag:

```text
Owner = Platform
```

doesn't tell me how to distribute those shared costs.

Cost allocation rules can redistribute reporting of shared costs to:

```text
Subscriptions
Resource Groups
Tags
```

using fixed or proportional allocation rules where supported. ([Microsoft Learn][10])

Example:

```text
Azure Firewall cost = $3,000

Payments  50% → $1,500
Orders    30% → $900
Analytics 20% → $600
```

---

### **Strong interview answer**

> “Tags help cost allocation by attaching business metadata such as CostCenter, Application, Environment and Owner to Azure resources and usage. In Cost Analysis I can group costs by those tags to implement showback and help with internal chargeback. At enterprise scale I enforce a consistent tagging taxonomy with Azure Policy rather than relying on developers manually tagging resources. I also distinguish normal Azure tag inheritance from Cost Management tag inheritance: Cost Management can apply parent tags to usage records for reporting, but that doesn't actually add those tags to the Azure resources themselves. For shared platform costs such as Firewall or ExpressRoute, I can additionally use Cost Management cost-allocation rules.”

**Memory line:**
**Tags turn technical Azure spend into business ownership: who, what application, which environment, and which cost center.**

**Interview trap:**
Do not say resource-group tags automatically become child-resource tags. They **do not automatically inherit at the Azure resource level**. ([Microsoft Learn][11])

**Keywords:**
Tags, CostCenter, Cost Analysis, showback, chargeback, tag inheritance, cost allocation

**Likely follow-ups:**

* Showback vs chargeback?
* Do tags apply retroactively to historical costs?
* Azure Policy tag inheritance vs Cost Management tag inheritance?
* How would you allocate the cost of a shared Azure Firewall?
