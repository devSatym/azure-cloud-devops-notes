### **T34-40. Local Terraform state vs remote state?**

**Answer:**

Terraform state records the relationship between my Terraform resource addresses and the real infrastructure Terraform manages.

With **local state**, Terraform stores that information on the machine running Terraform, normally in `terraform.tfstate`. That's acceptable for learning or an isolated personal lab, but it's a poor Production design because the file can be lost, different engineers can end up with different copies, and multiple people can accidentally run Terraform against the same infrastructure concurrently.

With **remote state**, Terraform stores the state in a shared backend such as Azure Blob Storage or HCP Terraform. For Azure Production environments, I would typically use the `azurerm` backend with Azure Storage, restrict it using Microsoft Entra ID and RBAC, preferably authenticate CI through OIDC/Workload Identity Federation, and use the backend's state-locking support.

So my rule is:

```text
Local state
→ individual/lab use

Remote state
→ team and Production use
   + central copy
   + access control
   + locking
   + recoverability
```

HashiCorp explicitly recommends a remote backend for team collaboration and warns against putting Terraform state in normal version control because state can contain secrets and Git doesn't provide Terraform's locking semantics. ([HashiCorp Developer][1])

## **1. What Terraform state actually does**

Suppose my configuration contains:

```hcl
resource "azurerm_resource_group" "prod" {
  name     = "rg-prod"
  location = "centralindia"
}
```

Terraform state maintains a mapping conceptually like:

```text
Terraform address
azurerm_resource_group.prod
             │
             ▼
Azure resource
/subscriptions/.../resourceGroups/rg-prod
```

Without state, Terraform wouldn't have the same persistent mapping between:

```text
configuration
↔
managed real-world object
```

State also stores metadata Terraform needs for dependency and lifecycle operations.

# **2. Local state**

Terraform's default backend is local.

Typical files:

```text
terraform.tfstate
terraform.tfstate.backup
```

stored beside the working directory unless configured otherwise. ([HashiCorp Developer][2])

Architecture:

```text
Engineer laptop
     │
     ├── main.tf
     ├── variables.tf
     └── terraform.tfstate
```

For one person learning Terraform, this is simple.

But imagine three engineers:

```text
Alice laptop
└── state copy A

Bob laptop
└── state copy B

CI runner
└── state copy C
```

Now you have a coordination problem.

---

# **3. The biggest local-state problem is collaboration**

Suppose Alice runs:

```bash
terraform apply
```

and creates:

```text
AKS cluster
```

Her state is updated.

Bob has yesterday's state and runs another apply.

His Terraform process may not have the same understanding of the managed infrastructure.

This can create:

```text
unexpected plans
conflicting operations
state divergence
possible destructive changes
```

HashiCorp specifically notes that teams using local state must somehow ensure everyone always has the latest copy and that nobody operates simultaneously, which is why remote state is recommended. ([HashiCorp Developer][1])

Azure example:

```text
Engineer / CI
      │
      ▼

      │

      │
      └── Blob container: tfstate
               │
```

Now:

```text
Alice

```

all work against the same authoritative backend rather than independent laptop copies.

# **5. Azure remote backend example**

A simplified backend could look like:

```hcl
terraform {
  backend "azurerm" {
    storage_account_name = "sttfstateprod"
    container_name       = "tfstate"
    key                  = "platform/prod.tfstate"

    use_azuread_auth = true
  }
}
```

For CI, I would prefer modern Entra authentication rather than embedding a Storage Account key.

HashiCorp currently recommends **Microsoft Entra ID** for the Azure backend and recommends **OIDC/Workload Identity Federation** where applicable. The backend supports Azure Blob Storage state locking and consistency checking. ([HashiCorp Developer][3])

# **6. Backend authentication and provider authentication are separate**

This is a very good Terraform interview distinction.

Terraform may need:

```text
Identity A
→ access Terraform state Blob

Identity B
→ create/update Azure resources
```

Even if the same workload identity is used for both, conceptually these are different authorization paths.

```text
Terraform CLI
   │
   ├── Backend authentication
   │       ↓
   │   Azure Storage data plane
   │       ↓
   │   read/write state
   │
   └── AzureRM provider authentication
           ↓
       Azure APIs
           ↓
       create VM/AKS/VNet/etc.
```

If Terraform can authenticate to AzureRM but cannot read state:

```text
terraform init / backend operations
→ fail
```

Giving the identity:

```text
Contributor
→ subscription
```

doesn't necessarily grant it the Blob data-plane permission required for the backend.

HashiCorp currently recommends `Storage Blob Data Contributor` at the state container for Entra-based backend access. ([HashiCorp Developer][3])

# **7. Remote locking prevents concurrent writers**

Imagine:

```text
Pipeline A
terraform apply

and simultaneously

Pipeline B
terraform apply
```

against the same state.

Without coordination:

```text
both calculate changes
both modify infrastructure
both attempt state update
```

Potential result:

```text
conflicting changes
incorrect state
state corruption
```

A backend with locking provides:

```text
Pipeline A
   ↓
acquires lock
   ↓
apply

Pipeline B
   ↓
cannot acquire lock
   ↓
wait/fail
```

Terraform automatically attempts state locking for write operations when the backend supports it. HashiCorp explicitly warns not to disable locking casually with `-lock=false`. ([HashiCorp Developer][4])

---

# **8. Azure Storage backend supports locking**

The `azurerm` backend supports state locking using Azure Storage's native capabilities. ([HashiCorp Developer][3])

So if a pipeline crashes and the state appears locked, I don't immediately run:

```bash
terraform force-unlock
```

I first determine:

```text
Is another plan/apply still active?
Was the pipeline terminated?
Who owns the lock?
When was it created?
```

Only after proving there is **no legitimate writer** would I consider:

```bash
terraform force-unlock <LOCK_ID>
```

because force-unlocking while another writer is active can create multiple concurrent writers and damage state. ([HashiCorp Developer][4])

# **9. State can contain sensitive information**

This is one of the most important Terraform security points.

Suppose Terraform creates:

```hcl
resource "azurerm_key_vault_secret" "db" {
  value = var.db_password
}
```

The secret may appear in Terraform state.

Even if:

```hcl
output "password" {
  value     = var.db_password
  sensitive = true
}
```

`sensitive = true` primarily suppresses normal display.

It does **not** mean:

```text
Terraform removes the value from state.
```

Therefore:

```text
terraform.tfstate
```

should be treated as sensitive data.

HashiCorp explicitly warns that Terraform state can contain secrets. ([HashiCorp Developer][5])

# **10. Never commit Production state to Git**

Bad:

```text
repo/
├── main.tf
├── variables.tf
└── terraform.tfstate   ❌
```

Reasons:

```text
may expose secrets
Git history preserves old versions
no Terraform locking
easy accidental modification
state becomes accessible to repo users
```

Instead:

```text
Git
→ Terraform configuration only

Azure Storage backend
→ Terraform state
```

HashiCorp explicitly recommends avoiding version-control systems for state storage. ([HashiCorp Developer][5])

For a Production backend, I'd think about:

```text
Microsoft Entra authentication
least-privilege Blob data RBAC
restricted state container access
network restrictions where operationally suitable
Storage encryption
Blob versioning / recovery strategy
diagnostic logging where needed
separate state between environments
```

I would avoid relying on:

```text

```

for new CI designs when OIDC or Managed Identity is available.

Current HashiCorp guidance recommends Entra authentication, especially OIDC federation, and marks direct SAS/access-key approaches as not recommended for new workloads. ([HashiCorp Developer][3])

# **15. Do not manually edit state JSON**

Bad approach:

```bash
vim terraform.tfstate
```

Then:

```text
delete a few JSON fields
save
```

State is not intended to be edited casually by hand.

Use supported Terraform mechanisms such as:

```bash
terraform state list
terraform state show
terraform state mv
terraform state rm
terraform import
```

or `moved` blocks where appropriate.

HashiCorp explicitly recommends using Terraform state commands rather than directly editing the file. ([HashiCorp Developer][6])

| Characteristic                  | Local state                   | Remote state                       |
| ------------------------------- | ----------------------------- | ---------------------------------- |
| Location                        | Local filesystem              | Shared backend                     |
| Good for learning               | **Yes**                       | Possible                           |
| Good for team Production        | No                            | **Yes**                            |
| Shared authoritative state      | No                            | **Yes**                            |
| Locking                         | Local process/filesystem only | Backend-dependent, usually **yes** |
| Laptop-loss risk                | High                          | Lower                              |
| Central RBAC                    | No                            | **Yes**                            |
| CI/CD-friendly                  | Poor                          | **Strong**                         |

### **Interview answer condensed**

> “Local Terraform state is stored on the machine running Terraform, usually as `terraform.tfstate`. It's fine for a lab but poor for Production because team members can have different copies, the file can be lost, and coordinating concurrent Terraform runs becomes difficult. In Production I'd use a remote backend—for Azure, typically Azure Blob Storage through the `azurerm` backend—with Entra authentication, least-privilege Blob RBAC and state locking. I also treat state as sensitive because it can contain secrets, so I never commit Production state to Git. And I keep backend authorization separate conceptually from AzureRM provider authorization: one controls access to state, the other controls access to Azure infrastructure.”

**Memory line:**
**Local state belongs to one machine; remote state gives the team one protected, lockable source of Terraform truth.**

**Interview trap:**
`terraform.tfstate` can contain secrets, and marking an output `sensitive` does **not remove the secret from state**.

**Keywords:**
Terraform state, local backend, remote backend, `azurerm`, Azure Storage, locking, OIDC, Entra ID, state security.

* What would you do if remote Terraform state becomes locked?

### **T34-41. Azure DevOps Pipelines vs GitHub Actions?**

**Answer:**

Both are mature CI/CD platforms that can build, test, secure, and deploy applications and infrastructure, and both support YAML workflows, hosted or self-hosted execution, approvals, secrets, environments, and Azure authentication.

The biggest difference for me is usually the **surrounding developer platform and operating model**.

**GitHub Actions** is deeply integrated into GitHub repositories, pull requests, GitHub environments, Actions from the marketplace, GitHub security workflows, and GitHub's OIDC identity model. If my source code and developer workflow already live in GitHub, Actions is often the most natural CI/CD choice.

**Azure Pipelines** is part of Azure DevOps and integrates strongly with Azure Repos, Boards, Artifacts, Test Plans, environments, service connections, variable groups, agent pools, and enterprise deployment checks. It is often attractive in organizations already standardized on Azure DevOps or with complex enterprise deployment governance.

So I don't answer:

```text
Azure Pipelines is always better
or
GitHub Actions is always better.
```

I answer:

```text
GitHub-centric engineering platform
→ GitHub Actions is usually natural

Azure DevOps-centric organization
or deep ADO governance/integration
→ Azure Pipelines is usually natural
```

Both can securely deploy Azure resources using federated/OIDC identity rather than long-lived credentials. GitHub documents OIDC federation for Azure specifically, and Azure Pipelines has first-class service connections and resource checks. ([GitHub Docs][7])

# **14. Security implications of self-hosted runners**

A self-hosted worker might have:

```text
network access to Prod
cached source
cloud identity
Docker socket
deployment tools
```

If an untrusted pull request runs arbitrary code there, the risk can be severe.

Hosted ephemeral runners are often safer for untrusted build code because the environment is destroyed after the job and isn't sitting permanently inside your corporate network.

Microsoft explicitly recommends extra caution with untrusted code on self-hosted agents, and GitHub similarly recommends ephemeral self-hosted runners for autoscaled secure environments. ([Microsoft Learn][13])

### **T34-42. Microsoft-hosted vs self-hosted pipeline agents?**

**Answer:**

A **Microsoft-hosted Azure Pipelines agent** is an ephemeral build machine managed by Microsoft. For each job Azure Pipelines provides a fresh VM from a supported image, runs the job, and then discards that VM. Microsoft manages patching and image maintenance.

A **self-hosted agent** runs on infrastructure that I control—for example an Azure VM, VM Scale Set, on-prem server, or another supported compute environment. That gives me full control over installed tools, hardware, caches, and especially network access to private resources, but I become responsible for patching, hardening, scaling, cleanup, reliability, and isolation.

So my rule is:

```text
Microsoft-hosted agent
→ default for standard CI/CD
→ low maintenance
→ clean ephemeral environment

Self-hosted agent
→ use when I need private networking,
   special hardware/software,
   persistent caching, or custom controls
→ but I own security and operations
```

Current Azure Pipelines documentation confirms that Microsoft-hosted agents receive a **fresh VM per job**, the VM is discarded afterward, and Microsoft maintains the image. ([Microsoft Learn][13])

If Job A creates:

```text
./build/output.zip
```

Job B won't automatically see it.

You must use:

```text
pipeline artifacts
cache
other persistent service
```

to transfer state intentionally.

Microsoft explicitly states that filesystem changes from one hosted job are unavailable to the next. ([Microsoft Learn][13])

---

# **2. Hosted agents remove infrastructure maintenance**

Microsoft manages:

```text
VM provisioning
base OS
agent image
common tools
image updates
disposal
```

Your team focuses on:

```text
pipeline code
build/test/deploy logic
```

This is why hosted agents are my default unless there's a specific requirement they can't satisfy.

---

# **3. Self-hosted architecture**

```text
Azure DevOps control plane
          ↓
      Agent pool
          ↓
┌────────────────────────┐
│ Self-hosted agent VM   │
│                        │
│ Terraform              │
│ Docker                 │
│ kubectl                │
│ custom SDK             │
│ company CA cert        │
└────────────────────────┘
          ↓
      Private VNet
          ↓
Private AKS / SQL / KV
```

You control the execution environment completely.

But that's now **your server** operationally.

---

# **4. Private networking is one of the strongest reasons for self-hosting**

Suppose AKS has:

```text
Private Kubernetes API
```

and Key Vault has:

```text
Public network access = Disabled
Private Endpoint = 10.5.2.8
```

Pipeline needs:

```bash
kubectl apply
terraform plan
```

against those private endpoints.

A public Microsoft-hosted worker does not inherently have:

```text
route into your VNet.
```

A self-hosted agent in:

```text
Hub VNet
```

can have:

```text
private DNS
VNet routes
firewall access
```

to those resources.

This is a legitimate reason for self-hosting.

---

# **5. Custom software**

Hosted agent image doesn't contain your company's:

```text
proprietary compiler
licensed build tool
special security agent
legacy SDK
internal certificate chain
```

You can install many tools during the job, but that:

```text
adds startup time
may require internet access
may be difficult for licensed/custom software
```

A self-hosted image can have everything preinstalled.

---

# **6. Custom hardware**

Suppose workload requires:

```text
64 cores
256 GB RAM
special architecture
GPU
very large local disk
```

A self-hosted agent can be sized accordingly.

This can be useful for:

```text
large monorepo builds
ML compilation
special test environments
very large container builds
```

though Microsoft now also has additional managed agent options beyond the basic hosted pool. The core interview distinction remains hosted vs customer-managed.

---

# **7. Caching**

A persistent self-hosted agent might retain:

```text
Docker layers
npm cache
Maven cache
Terraform provider cache
large build dependencies
```

between jobs.

This can dramatically speed up builds.

But persistence introduces security risk.

Example:

```text
Job 1
leaves credential/file behind

Job 2
from another repository
can potentially access it
```

if cleanup and isolation are weak.

Microsoft-hosted agents naturally avoid much of this by providing a fresh machine per job. ([Microsoft Learn][13])

---

# **8. Self-hosted does not necessarily have to mean persistent**

A stronger pattern is:

```text
Job queued
   ↓
Create ephemeral VM/agent
   ↓
Run exactly one job
   ↓
Destroy worker
```

This combines:

```text
private network/custom image
+
ephemeral isolation
```

Azure DevOps can use autoscaling/managed agent-pool approaches depending on requirements.

The general security pattern is:

```text
ephemeral self-hosted
>
long-lived shared agent
```

for sensitive or mixed-trust workloads.

GitHub explicitly recommends ephemeral runners for autoscaled self-hosted execution; the same security reasoning applies conceptually to CI workers in general. ([GitHub Docs][14])

---

# **9. Security risk of running untrusted code**

Imagine a self-hosted agent has:

```text
Prod VNet access
Azure deployment identity
Docker daemon
cached repository data
```

Then a pipeline executes code from:

```text
untrusted fork PR
```

Malicious code may try to:

```text
scan internal network
steal cached credentials
access Docker socket
alter agent machine
persist for future jobs
```

That is a serious threat model.

Microsoft explicitly notes Microsoft-hosted agents are safer than self-hosted corporate-network agents for running untrusted code because the hosted worker is isolated and reimaged after the run. ([Microsoft Learn][13])

---

# **10. Never put secrets permanently on the agent**

Bad:

```text
/home/agent/.azure/credentials
Prod client secret permanently stored
```

Better:

```text
Pipeline starts
      ↓
OIDC / Managed Identity
      ↓
short-lived token
      ↓
Azure
```

Secrets should ideally be:

```text
ephemeral
scoped
short-lived
```

not permanently baked into VM images.

---

# **11. Self-hosted agent identity**

If the agent runs on an Azure VM, one strong option is:

```text
Agent VM
   ↓
Managed Identity
   ↓
Microsoft Entra ID
   ↓
Azure RBAC
```

for supported flows.

Or use Azure DevOps service connections with federation where appropriate.

The agent's network location and its Azure identity are separate questions:

```text
Network
→ Can it reach the endpoint?

Identity
→ Who is it?

Authorization
→ Is that identity allowed?
```

---

# **12. Hosted agent security benefit isn't absolute**

Hosted agents reduce host-management burden, but the pipeline can still be dangerous if you:

```text
grant Owner at subscription
expose secrets to untrusted PRs
download malicious dependencies
skip artifact verification
```

Ephemeral compute does not fix:

```text
overprivileged cloud identity.
```

You still need:

```text
least privilege
protected environments
branch controls
OIDC
secure dependency handling
```

---

# **13. Performance trade-off**

Microsoft-hosted:

```text
Queue
→ provision fresh worker
→ reinstall some dependencies
→ build
```

Self-hosted persistent:

```text
Queue
→ existing agent
→ caches already present
→ build
```

Self-hosted can be faster.

But you're trading build speed against:

```text
maintenance
security
capacity planning
cost
```

So I would first measure whether hosted-agent performance is actually a problem before operating my own fleet.

---

# **14. Scaling**

Hosted:

```text
Microsoft supplies capacity
```

subject to purchased parallel-job/concurrency limits.

Self-hosted:

```text
you need enough agents
```

If:

```text
20 pipelines queued
1 self-hosted agent
```

then:

```text
19 wait.
```

A mature self-hosted design often needs:

```text
autoscaling
health monitoring
agent replacement
capacity limits
cost control
```

Now you've created another platform to operate.

---

# **15. Production example**

Requirements:

```text
Terraform deploy
→ private AKS
→ private ACR
→ private Key Vault

No public endpoints
```

I'd likely use:

```text
ephemeral/self-hosted agent
inside approved Azure VNet
```

with:

```text
Private DNS
Firewall rules
OIDC/Managed Identity
least-privilege Azure RBAC
```

rather than opening Production endpoints just so a public hosted agent can reach them.

Never weaken the network architecture merely to make CI easier.

---

# **16. CI and deployment can use different agent pools**

A strong pattern can be:

```text
Pull Request CI
     ↓
Microsoft-hosted agent
     ↓
build/test/scan
```

Then:

```text
Approved deployment
     ↓
private self-hosted agent
     ↓
private Production endpoints
```

This limits corporate/Prod network exposure to only jobs that actually require it.

Very good defense-in-depth architecture.

| Characteristic         | Microsoft-hosted                 | Self-hosted                   |
| ---------------------- | -------------------------------- | ----------------------------- |
| VM maintenance         | **Microsoft**                    | **You**                       |
| Fresh machine per job  | **Yes**                          | Depends on design             |
| Custom software        | Install per run/preinstalled set | **Full control**              |
| Private network access | Limited/no native corporate path | **Strong**                    |
| Custom hardware        | Limited to available offerings   | **Full control**              |
| Persistent cache       | Limited/use pipeline cache       | Possible                      |
| Security isolation     | **Strong ephemeral default**     | Your responsibility           |
| Scaling infrastructure | Microsoft-managed                | **You manage**                |
| Best default           | **Yes**                          | Use for specific requirements |

### **Interview answer condensed**

> “Microsoft-hosted Azure Pipeline agents are managed ephemeral workers. Each hosted job gets a fresh VM, Microsoft maintains the image, and the VM is discarded after the job, which gives low operational overhead and good isolation. Self-hosted agents run on infrastructure I manage. I use them when I need private VNet access, specialized software or hardware, or custom performance characteristics, but then I'm responsible for patching, hardening, scaling, cleanup and isolation. For Production, I especially avoid running untrusted pull-request code on a persistent self-hosted agent that has private-network or privileged Azure access.”

**Memory line:**
**Hosted agents save operations; self-hosted agents buy control at the cost of owning the worker platform.**

**Interview trap:**
A self-hosted agent inside the Production VNet can become a **high-value attack path** if arbitrary or untrusted pipeline code is allowed to execute on it.

**Keywords:**
Microsoft-hosted agent, self-hosted agent, ephemeral, VNet, private endpoint, custom image, pipeline security, OIDC.

* How would you secure a self-hosted agent?
* Would you run fork PR builds on a Production-connected agent?
* How would you autoscale self-hosted pipeline agents?

### **T34-43. Continuous Delivery vs Continuous Deployment?**

**Answer:**

Both practices start with **Continuous Integration** and aim to keep software in a releasable state, but the distinction is what happens after the software passes the automated pipeline.

With **Continuous Delivery**, every successful change is automatically built, tested, validated, and made **ready for Production**, but releasing it to Production still requires an explicit decision or approval.

With **Continuous Deployment**, every change that passes all automated quality and policy gates is **automatically released to Production** without a routine manual approval step.

So:

```text
Continuous Delivery
→ automatically ready to deploy
→ human/business decision controls release

Continuous Deployment
→ automatically deployed to Production
  after automated gates pass
```

The important point is that Continuous Deployment does **not** mean “deploy with no controls.” It usually requires **stronger automation**, because automated tests, security gates, progressive rollout, monitoring, and rollback replace the routine human approval as the primary safety system.

---

## **1. Start with Continuous Integration**

Both usually begin here:

```text
Developer commit
      ↓
CI
      ↓
Compile/build
      ↓
Unit tests
      ↓
Integration tests
      ↓
Security scans
      ↓
Artifact produced
```

A strong principle is:

```text
Build once
      ↓
promote same immutable artifact
      ↓
Dev → Stage → Prod
```

rather than rebuilding separate binaries for every environment.

---

# **2. Continuous Delivery flow**

```text
Commit
  ↓
Build
  ↓
Automated tests
  ↓
SAST / dependency scan
  ↓
Artifact
  ↓
Deploy Stage
  ↓
Integration/performance tests
  ↓
Production-ready
  ↓
MANUAL APPROVAL / BUSINESS DECISION
  ↓
Production
```

The important word is:

```text
ready
```

Production deployment should be routine and low-risk, but humans decide:

```text
when
or
whether
```

to release.

---

# **3. Continuous Deployment flow**

```text
Commit
  ↓
Build
  ↓
Automated tests
  ↓
Security/policy gates
  ↓
Deploy Stage
  ↓
automated validation
  ↓
Production canary
  ↓
health analysis
  ↓
automatically increase traffic
  ↓
100% Production
```

No routine person clicks:

```text
Approve
```

for every successful release.

The automated system is trusted to decide whether the candidate is healthy enough to continue.

---

# **4. Continuous Deployment still has gates**

A weak definition is:

> “Continuous Deployment means every commit immediately goes to Production.”

Not quite.

Better:

> “Every change that successfully passes the defined automated pipeline is eligible to flow automatically to Production.”

A failing:

```text
unit test
SAST gate
container CVE policy
integration test
canary health check
```

should stop deployment.

So:

```text
continuous
≠
uncontrolled.
```

---

# **5. Example Continuous Delivery pipeline**

Suppose:

```text
GitHub / Azure Repos
      ↓
CI
      ↓
Container build
      ↓
ACR
      ↓
Stage AKS
      ↓
Smoke tests
      ↓
Production approval
      ↓
Prod AKS
```

Approval might require:

```text
Product owner
Release manager
on-call engineer
change window
```

depending on governance requirements.

This is Continuous Delivery because the artifact is always releasable but Production activation has an explicit decision point.

---

# **6. Example Continuous Deployment pipeline**

```text
Commit to main
      ↓
Build image
      ↓
Unit/integration tests
      ↓
SAST/DAST/dependency scan
      ↓
Push immutable image digest
      ↓
Deploy 5% canary
      ↓
Compare candidate metrics
with stable baseline
      ↓
Healthy?
   /       \
 No         Yes
 ↓           ↓
Rollback     25%
              ↓
             50%
              ↓
            100%
```

That is much closer to production-grade Continuous Deployment.

---

# **7. Progressive delivery makes Continuous Deployment safer**

Suppose the system immediately sends:

```text
100% traffic
```

to every automatically deployed version.

Risk is high.

Instead:

```text
5%
→ observe
→ 25%
→ observe
→ 50%
→ observe
→ 100%
```

Using:

```text
canary
blue-green
feature flags
automated health gates
```

means the pipeline limits blast radius.

Continuous Deployment and progressive delivery complement each other very well.

---

# **8. Automated rollback becomes critical**

If a human isn't manually observing every deployment, the platform must detect problems quickly.

Example gate:

```text
Candidate 5xx
> baseline + 2%
for 5 minutes
```

Then:

```text
automatic rollout abort
```

or:

```text
traffic → stable version
```

The decision metrics should prioritize:

```text
availability
error rate
latency
critical business transactions
dependency health
```

not only:

```text
CPU
memory
```

because healthy infrastructure metrics do not guarantee healthy users.

---

# **9. Database changes are the hard part**

Application artifact rollback:

```text
v42 → v41
```

can be easy.

Database rollback may not be.

Suppose v42 performs:

```sql
DROP COLUMN legacy_value;
```

Then v41 expects:

```text
legacy_value
```

Rollback fails.

For high-frequency Continuous Delivery/Deployment, use backward-compatible migration patterns:

```text
Expand
  ↓
Deploy compatible app
  ↓
Migrate/backfill data
  ↓
Contract later
```

rather than destructive schema changes coupled tightly to one release.

---

# **10. Feature flags separate deployment from release**

Important distinction:

```text
Deployment
→ code reaches Production infrastructure

Release
→ users can use the feature
```

Example:

```text
v42 deployed
new-checkout = OFF
```

Then later:

```text
1% users
→ ON
```

then:

```text
10%
50%
100%
```

This lets organizations continuously deploy code while controlling business feature exposure separately.

---

# **11. Regulatory environments may favor Continuous Delivery**

Suppose bank policy requires:

```text
formal approval
change record
separation of duties
```

before Production.

That doesn't mean CI/CD is weak.

You can still automate:

```text
build
tests
security
artifact creation
Stage deployment
validation
```

until one final approval.

Then:

```text
approved immutable artifact
→ Production
```

That's strong Continuous Delivery.

---

# **12. Low-risk SaaS may use Continuous Deployment**

A mature SaaS organization with:

```text
strong test coverage
feature flags
canary releases
excellent observability
small incremental changes
fast rollback
```

may safely deploy dozens or hundreds of changes without routine manual approval.

The safety comes from:

```text
small batches
automation
observability
reversibility
```

not from lack of process.

---

# **13. Manual approval doesn't automatically make delivery safer**

Imagine:

```text
500-file monthly release
```

with:

```text
one manager clicks Approve
```

versus:

```text
small daily changes
automatic tests
canary
rollback
```

The first has a human gate but may have much greater risk.

So I don't equate:

```text
manual approval
=
safety.
```

A human approval is only useful if the reviewer has meaningful evidence to evaluate.

---

# **14. Continuous Deployment requires excellent test confidence**

Suppose unit coverage is good, but there's no:

```text
integration testing
migration testing
security gate
production health analysis
```

Then automatically deploying every passing build may simply accelerate outages.

Continuous Deployment maturity requires:

```text
test automation
security automation
artifact immutability
progressive rollout
observability
rollback
```

working together.

---

# **15. Azure/GitHub implementation**

Continuous Delivery:

```text
Pipeline
   ↓
Build
   ↓
Stage
   ↓
Production environment
   ↓
Approval/check
   ↓
Deploy
```

Both GitHub environments and Azure Pipelines environments/checks can support controlled Production gates.

Continuous Deployment:

```text
Pipeline
   ↓
automated validation
   ↓
Production deployment
```

without routine manual approval, ideally combined with progressive deployment mechanisms.

---

# **16. Continuous Delivery vs Continuous Deployment vs GitOps**

GitOps is a **deployment operating model**, not a synonym for Continuous Deployment.

Example:

```text
CI
→ build image
→ update desired-state Git repo
→ Argo CD syncs AKS
```

That could be:

### Continuous Delivery

```text
Git change approved manually
before Prod desired state updates
```

or:

### Continuous Deployment

```text
successful pipeline automatically
updates Prod desired state
and Argo syncs it
```

GitOps and CD terminology describe different dimensions.

---

# **17. A good Azure DevOps interview answer should mention artifact promotion**

Bad:

```text
Build dev image
Build test image
Build prod image
```

Potential issue:

```text
Production artifact
wasn't exactly what Stage tested.
```

Better:

```text
Git commit
      ↓
build once
      ↓
ACR:
myapp@sha256:ABC
      ↓
Dev
      ↓
Stage
      ↓
Prod
```

Same immutable digest.

Only:

```text
configuration
environment
secrets
capacity
```

change appropriately between environments.

This improves release confidence for either Continuous Delivery or Continuous Deployment.

# **18. Decision example**

Suppose organization has:

```text
critical payment platform
manual regulatory approval required
```

Choose:

```text
Continuous Delivery
```

with extremely automated validation up to the approval.

Another service:

```text
internal stateless API
excellent automated tests
canary support
easy rollback
```

could use:

```text
Continuous Deployment
```

The appropriate maturity can differ by service.

## **Quick comparison**

| Characteristic             | Continuous Delivery                | Continuous Deployment          |
| -------------------------- | ---------------------------------- | ------------------------------ |
| Build automatically        | Yes                                | Yes                            |
| Test automatically         | Yes                                | Yes                            |
| Keep artifact releasable   | **Yes**                            | **Yes**                        |
| Stage deployment automated | Usually                            | Yes                            |
| Production deployment      | Explicit decision/approval         | **Automatic after gates**      |
| Manual Production gate     | Usually **Yes**                    | No routine gate                |
| Requires strong automation | Yes                                | **Very strong**                |
| Best fit                   | Governance/manual release decision | Mature high-automation systems |

### **Interview answer condensed**

> “Continuous Delivery means every change that passes CI is kept in a deployable state and can reach Production through a routine release process, but Production release still requires an explicit decision or approval. Continuous Deployment goes one step further: once a change passes all automated tests, security checks and deployment health gates, it is automatically released to Production. Continuous Deployment doesn't mean no controls—it actually requires very strong automation, observability, progressive rollout and rollback. In either model I prefer to build an immutable artifact once and promote that exact artifact through environments.”

**Memory line:**
**Continuous Delivery makes every change ready for Production; Continuous Deployment automatically puts every qualified change into Production.**

**Interview trap:**
Continuous Deployment does **not** mean “every commit blindly goes straight to 100% of Production.”
