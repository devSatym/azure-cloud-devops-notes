### **T34-16. Azure Policy vs resource locks?**

**Answer:**

Azure Policy and resource locks are both governance controls, but they solve different problems.

**Azure Policy** evaluates whether Azure resources comply with organizational rules. It can audit, deny, modify, or deploy required configuration at scale. For example, I can enforce that Storage Accounts cannot allow anonymous Blob access, VMs must use approved regions, or required monitoring settings must exist.

**Resource locks** protect a specific subscription, resource group, or resource from accidental deletion or modification. The two lock types are `CanNotDelete` and `ReadOnly`.

So my mental model is:

```text
Azure Policy
→ "Is this resource configuration allowed?"

Resource lock
→ "Even if you're authorized, can this resource
   be changed or deleted?"
```

For example, I might use Policy to ensure all production Storage Accounts meet security requirements, while placing a `CanNotDelete` lock on a particularly critical production database.

Microsoft currently documents `CanNotDelete` as allowing reads and modifications but blocking deletion, while `ReadOnly` blocks both updates and deletion. Locks apply regardless of the caller's normal RBAC permissions. ([Microsoft Learn][1])

---

## **1. Azure Policy is primarily a configuration-governance system**

Suppose the company requires:

```text
Storage Accounts
must not allow
anonymous Blob access
```

Azure Policy can evaluate:

```text
Storage configuration
       ↓
Compliant?
   /       \
 Yes        No
              ↓
          Audit/Deny/etc.
```

Policy is useful across:

```text
Management Group
      ↓
Subscriptions
      ↓
Resource Groups
      ↓
Resources
```

because assignments at higher scopes can govern many resources consistently.

---

## **2. Resource locks are protection against destructive operations**

Suppose I have:

```text
Production SQL Database
```

that absolutely should not be accidentally deleted.

I can apply:

```text
CanNotDelete
```

Then:

```text
Authorized engineer
Terraform pipeline
Azure Portal user
        ↓
DELETE request
        ↓
BLOCKED
```

even if the principal otherwise has Azure RBAC permission to delete the resource.

That's why locks are particularly useful for:

```text
critical databases
Key Vaults
shared networking
important Storage Accounts
```

where accidental deletion would be expensive.

---

## **3. The two lock types**

### `CanNotDelete`

Allows:

```text
READ   ✓
UPDATE ✓
DELETE ✗
```

Example:

```text
SQL DB
→ change configuration ✓
→ delete database ✗
```

This is usually the more practical protection for critical Production resources.

---

### `ReadOnly`

Allows:

```text
READ   ✓
UPDATE ✗
DELETE ✗
```

Conceptually similar to forcing the management plane into a read-only state.

This is much stronger and can interfere with ordinary operations.

Microsoft notes that `ReadOnly` locks can block control-plane operations that use POST even when the operation sounds observational or operational rather than a simple configuration write. ([Microsoft Learn][1])

So I use `ReadOnly` very carefully.

---

# **4. Policy can prevent bad resources from being created**

Example:

Developer has:

```text
Contributor
→ Subscription
```

and creates:

```text
Public IP
for a production VM
```

Policy says:

```text
Production resources
must not have public IPs
```

Result:

```text
RBAC:
AUTHORIZED

Policy:
DENIED
```

The resource never reaches the forbidden configuration.

A resource lock isn't designed to solve that problem.

---

# **5. A lock usually protects something that already exists**

Suppose:

```text
prod-db
```

already exists.

I apply:

```text
CanNotDelete
```

The purpose is:

```text
keep this specific object
from being deleted
```

It doesn't mean:

```text
"all SQL databases in the organization
must follow secure configuration X"
```

That's Policy's job.

---

# **6. Policy scales much better for organization-wide standards**

Imagine:

```text
150 subscriptions
10,000 Storage Accounts
```

Requirement:

```text
Anonymous Blob access = disabled
```

It would be impractical to manually manage individual locks to enforce that configuration.

Instead:

```text
Management Group
      ↓
Policy assignment
      ↓
150 subscriptions
      ↓
all applicable Storage Accounts
```

This is where Policy shines.

---

# **7. Locks inherit downward**

Suppose I put:

```text
CanNotDelete
→ rg-prod
```

Then resources inside that Resource Group inherit the lock.

```text
rg-prod [CanNotDelete]
   │
   ├── AKS
   ├── Key Vault
   ├── SQL
   └── Storage
```

Microsoft documents that locks applied at a parent scope are inherited by child resources, and the most restrictive inherited lock takes precedence. ([Microsoft Learn][1])

This is powerful—but also dangerous if applied too broadly.

---

# **8. Policy also inherits through scope**

Suppose:

```text
Management Group: Corp
       ↓
Policy:
Allowed regions =
Central India, South India
```

Subscriptions underneath inherit the applicable policy assignment.

So both Policy and locks have hierarchical scope concepts, but they enforce different things:

```text
Policy inheritance
→ compliance rules

Lock inheritance
→ operation restrictions
```

---

# **9. Locks operate primarily on the Azure control plane**

This is an important interview distinction.

Resource locks apply to operations sent through:

```text
Azure Resource Manager
```

They don't necessarily protect the **data inside the resource**.

For example, putting:

```text
CanNotDelete
```

on a Storage Account prevents deleting the Storage Account resource itself.

It doesn't automatically mean:

```text
no Blob can ever be deleted
```

through the Storage data plane.

Microsoft explicitly states that management locks apply to control-plane operations, not all data-plane operations. ([Microsoft Learn][1])

So data protection may separately require:

```text
soft delete
versioning
immutable storage
backup
data-plane RBAC
```

depending on the service.

---

# **10. Policy can sometimes protect deletion too**

There's an interesting overlap.

Azure Policy currently supports:

```text
denyAction
```

and the supported action is currently:

```text
DELETE
```

which allows organizations to block deletion of matching resources at scale. ([Microsoft Learn][2])

So an interviewer might ask:

> If Policy can prevent deletion, why use resource locks?

Because the mechanisms and use cases differ.

### Resource lock

Simple protection:

```text
Protect this resource/RG/subscription
```

### Policy `denyAction`

Governance rule:

```text
Resources matching this policy condition
must not be deleted
```

That can scale across an organization.

---

# **11. Locks aren't identity-specific**

Suppose both:

```text
Developer
Terraform pipeline
```

have Contributor permissions.

A lock doesn't normally mean:

```text
Developer cannot delete
but pipeline can.
```

It means:

```text
Delete operation blocked
regardless of otherwise-valid RBAC
```

until the lock is removed by someone who is authorized to manage locks.

This makes locks fundamentally different from RBAC.

---

# **12. Azure Policy doesn't replace RBAC either**

Suppose requirement:

> Developers must never manually modify Production.

That is principally an:

```text
Azure RBAC / identity
```

design problem.

Use:

```text
Developers
→ Reader in Prod

Pipeline identity
→ required write permission
```

Policy can provide configuration guardrails, but it isn't generally a generic distinction between:

```text
"human Portal request"
vs
"pipeline request"
```

for every possible operation.

---

# **13. Terraform interaction**

Suppose Terraform wants:

```text
-/+ prod-storage
```

but Storage has:

```text
CanNotDelete
```

Terraform's plan can still show:

```text
destroy/create
```

but when Azure receives the deletion:

```text
Azure resource lock
     ↓
DELETE blocked
     ↓
terraform apply fails
```

That's valuable protection, but it also means locks need to be considered in legitimate infrastructure workflows.

---

# **14. Locks can interfere with lifecycle operations**

If every resource in a large Prod subscription has:

```text
ReadOnly
```

then normal Terraform deployments can fail repeatedly.

That's why I'd normally apply locks:

```text
selectively
```

to critical resources rather than reflexively locking everything.

A good design might be:

```text
Production SQL
→ CanNotDelete

Critical Key Vault
→ CanNotDelete

Normal stateless VMSS
→ no manual lock,
   protected through IaC/process
```

depending on recovery capability.

---

# **15. Example production design**

Requirement:

```text
All Storage Accounts:
must disable anonymous public access.

Critical finance Storage Account:
must also never be accidentally deleted.
```

Use:

### Azure Policy

```text
allowBlobPublicAccess = true
→ DENY
```

across the Production Management Group.

### Resource lock

```text
finance-storage
→ CanNotDelete
```

Now:

```text
Policy
→ prevents unsafe configuration

Lock
→ protects critical instance from deletion
```

This is a perfect complementary use case.

## **Quick comparison**

| Capability                  | Azure Policy                  | Resource locks               |
| --------------------------- | ----------------------------- | ---------------------------- |
| Primary goal                | Configuration governance      | Protect from change/deletion |
| Scope                       | MG/Sub/RG/resource            | Sub/RG/resource              |
| Audit compliance            | **Yes**                       | No                           |
| Deny bad configuration      | **Yes**                       | Not its purpose              |
| Modify/remediate            | Supported effects             | No                           |
| Block deletion              | `denyAction` where applicable | **CanNotDelete/ReadOnly**    |
| Block modification          | Via policy conditions         | **ReadOnly**                 |
| Identity-specific           | Generally no                  | No                           |
| Good for org-wide standards | **Excellent**                 | Limited                      |
| Good for one critical DB    | Possible                      | **Excellent**                |

---

### **Interview answer condensed**

> “Azure Policy and resource locks are both governance controls, but Policy controls what configurations are allowed while locks protect specific resources from modification or deletion. I use Policy at scale—for example to deny public Storage or enforce approved regions. I use `CanNotDelete` on selected critical resources such as a production database so even an otherwise authorized user or Terraform pipeline can't accidentally delete it. `ReadOnly` is stronger and also blocks updates, so I use it carefully. I also remember that management locks primarily protect the ARM control plane; they don't automatically protect the underlying data from data-plane deletion.”

**Memory line:**
**Policy governs acceptable configuration; locks protect important resources from destructive control-plane operations.**

**Interview trap:**
A `CanNotDelete` lock on a Storage Account **does not automatically prevent deletion of individual blobs through the Storage data plane**.

**Keywords:**
Azure Policy, resource lock, `CanNotDelete`, `ReadOnly`, `denyAction`, inheritance, control plane, governance.

**Likely follow-ups:**

* What's the difference between `CanNotDelete` and `ReadOnly`?
* Can Owner delete a locked resource directly?
* Does a Storage Account lock protect every Blob from deletion?
* When would you use Policy `denyAction` instead of a lock?

### **T34-17. Contributor vs Owner?**

**Answer:**

Both Owner and Contributor are broad Azure RBAC roles that can manage Azure resources, but the critical difference is **access management**.

**Contributor** can create, modify, and delete most Azure resources within its assigned scope, but it cannot assign Azure RBAC roles.

**Owner** has the same broad resource-management permissions **plus the ability to manage access**, including assigning Azure roles.

So:

```text
Contributor
→ manage resources

Owner
→ manage resources
   +
   manage who has access
```

Because Owner can delegate permissions and potentially grant other users highly privileged roles, I treat it as much more sensitive and assign it only when truly necessary.

Microsoft's current role definitions describe Contributor as full resource-management access without Azure RBAC role assignment capability, whereas Owner has full resource access including the ability to assign roles. ([Microsoft Learn][3])

---

## **1. Contributor example**

Alice has:

```text
Contributor
→ rg-app-prod
```

She can generally:

```text
Create VM
Update VNet
Delete App Service
Create Storage Account
Modify AKS resource
```

within that Resource Group.

But she cannot normally do:

```text
Give Bob Owner
→ rg-app-prod
```

because that requires:

```text
Microsoft.Authorization/roleAssignments/write
```

which Contributor intentionally doesn't have.

---

# **2. Owner example**

Bob has:

```text
Owner
→ rg-app-prod
```

He can:

```text
manage resources
+
manage Azure RBAC assignments
```

So Bob could potentially grant:

```text
Charlie
→ Contributor
```

or:

```text
Charlie
→ Owner
```

within the applicable scope.

That access-delegation capability is why Owner is substantially more privileged.

---

# **3. Scope is just as important as role**

Compare:

```text
Owner
→ one VM
```

with:

```text
Owner
→ Management Group
```

The role name is identical.

Blast radius is radically different.

Azure RBAC scopes form:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Resource
```

Assignments at higher scopes are inherited downward. ([Microsoft Learn][4])

Therefore my security rule is:

> Grant the smallest role at the narrowest scope that satisfies the requirement.

---

# **4. Contributor is still extremely powerful**

A common mistake is thinking:

```text
Contributor
= safe developer role
```

Not necessarily.

Contributor may be able to:

```text
delete production VM
modify firewall configuration
change an App Service
replace infrastructure
delete an AKS cluster
```

if assigned at a broad enough scope.

It only lacks certain access-management capabilities.

So:

```text
Contributor
≠ low privilege
```

It is still a high-impact role.

---

# **5. Owner is not required for normal application deployment**

Suppose GitHub Actions deploys:

```text
App Service
AKS
VM
VNet
```

The team says:

> “Give the pipeline Owner so Terraform works.”

I would first determine which action actually requires elevation.

If Terraform only manages ordinary resources:

```text
Contributor
```

at the appropriate scope may be enough.

If it also creates:

```hcl
azurerm_role_assignment
```

then it requires RBAC-management permission.

But rather than automatically granting Owner, I may use a more focused role such as:

```text
Role Based Access Control Administrator
```

at a narrow scope or separate the privileged RBAC stage.

Microsoft explicitly provides Role Based Access Control Administrator as a role focused on managing Azure RBAC without giving the full resource-management scope of Owner. ([Microsoft Learn][3])

---

# **6. Contributor does not automatically grant every data-plane permission**

This is another important distinction.

Suppose Alice is:

```text
Contributor
→ Storage Account
```

Can she necessarily read every Blob using Entra data-plane authorization?

Not automatically.

Blob data access might require:

```text
Storage Blob Data Reader
```

or:

```text
Storage Blob Data Contributor
```

depending on required operation.

Azure RBAC distinguishes:

```text
Actions
→ management/control-plane operations

DataActions
→ data-plane operations
```

for services that support Azure RBAC data authorization. ([Microsoft Learn][5])

---

# **7. But control-plane privilege can sometimes indirectly expose data**

Important security nuance:

Even if Contributor isn't granted direct data-plane roles, some Azure services expose management operations that can retrieve:

```text
access keys
connection strings
credentials
```

depending on the service and exact role definition.

Therefore I would never make the simplistic statement:

> “Contributor can never access data.”

Instead:

> Contributor doesn't automatically grant all data-plane access, but broad management access may still create indirect data-access paths depending on the resource.

That's a much stronger interview answer.

---

# **8. Owner isn't Entra Global Administrator**

Another common confusion.

### Azure Owner

```text
Azure RBAC
→ Azure resource scope
```

### Global Administrator

```text
Microsoft Entra role
→ directory administration
```

Owner at subscription scope does not automatically mean:

```text
create Entra users
manage every app registration
be Global Administrator
```

and Global Administrator doesn't automatically equal subscription Owner.

These are different authorization systems.

---

# **9. Production access design**

I would avoid:

```text
Developers
→ Owner in Prod
```

Normal model:

```text
Developers
→ Reader / monitoring roles

Pipeline identity
→ Contributor at required RG

Dedicated identity/process
→ RBAC Administrator
  if role assignments required

Emergency human access
→ PIM
```

This enforces separation of duties.

---

# **10. PIM for elevated access**

If an engineer sometimes genuinely needs:

```text
Owner
```

during a major incident, I would rather provide:

```text
PIM eligible Owner
      ↓
activate when needed
      ↓
MFA
justification
approval if configured
      ↓
temporary access
```

than permanent Owner assignment.

The principle is:

```text
eligible privilege
>
standing privilege
```

for highly privileged roles.

# **11. Example Terraform issue**

Pipeline has:

```text
Contributor
→ rg-prod
```

Terraform succeeds creating:

```text
AKS
ACR
Key Vault
```

but fails at:

```text
azurerm_role_assignment.acr_pull
```

with:

```text
403
Microsoft.Authorization/roleAssignments/write
```

Wrong solution:

```text
Give pipeline Owner on subscription
```

Better investigation:

```text
Does it only need RBAC assignment at ACR?
      ↓
Grant focused RBAC management permission
at the narrowest scope
or
move RBAC assignment into privileged platform pipeline
```

This preserves least privilege.

| Capability                       | Contributor       | Owner                       |
| -------------------------------- | ----------------- | --------------------------- |
| Read Azure resources             | Yes               | Yes                         |
| Create/update resources          | **Yes**           | **Yes**                     |
| Delete resources                 | **Yes**           | **Yes**                     |
| Assign Azure RBAC roles          | **No**            | **Yes**                     |
| Manage access                    | No                | **Yes**                     |

### **Interview answer condensed**

> “Contributor and Owner can both broadly create, modify and delete Azure resources within their assigned scope. The major difference is that Contributor cannot assign Azure RBAC roles, while Owner can manage both the resources and who has access to them. That's why I treat Owner as significantly more sensitive. I also consider scope: Contributor on one Resource Group is very different from Contributor across an entire subscription. For Production I prefer the narrowest role and scope possible and use a separate RBAC-management role or privileged process if Terraform genuinely needs to create role assignments.”

**Memory line:**
**Contributor manages resources; Owner manages resources and access.**

**Interview trap:**
Contributor is **not a harmless role**—at subscription scope it can still create, modify, or delete a very large amount of Production infrastructure.

**Keywords:**
Contributor, Owner, Azure RBAC, role assignment, scope, least privilege, RBAC Administrator, PIM.

**Likely follow-ups:**

* Why can't Contributor create an Azure role assignment?
* Does Contributor automatically let you read Blob contents?
* When would you give a pipeline Owner?
* Owner vs Global Administrator?

### **T34-18. Resource group vs subscription?**

**Answer:**

A **subscription** is a higher-level Azure management and billing boundary that contains Resource Groups and resources. It provides boundaries for things such as Azure RBAC, Policy, cost management, quotas, and resource organization.

A **Resource Group** is a logical container **inside one subscription** used to group related Azure resources, usually resources that share an application, environment, ownership model, or lifecycle.

The hierarchy is:

```text
Microsoft Entra tenant
        ↓
Management Group
        ↓
Subscription
        ↓
Resource Group
        ↓
Resource
```

So I would typically use subscriptions for stronger isolation between areas such as Production and nonproduction or between major business/platform boundaries, while Resource Groups organize related components within that subscription.

Microsoft describes a subscription as a management/billing container and a Resource Group as a logical container for related Azure resources. ([Microsoft Learn][6])

---

## **1. Subscription is a stronger boundary**

A subscription can provide a boundary for:

```text
RBAC
Policy
cost reporting
quotas
resource-provider registration
service limits
```

Example:

```text
Subscription: prod
Subscription: nonprod
```

Now:

```text
Dev pipeline credential
→ nonprod only
```

cannot accidentally manage Production if it has no assignment in the Prod subscription.

That's a much stronger isolation boundary than merely:

```text
rg-dev
rg-prod
```

inside one shared subscription.

---

# **2. Resource Group organizes related resources**

Example:

```text
Subscription: prod

rg-payments
├── AKS
├── ACR
├── Key Vault
├── Private Endpoint
└── Monitor resources
```

These resources belong to the same application/operating boundary.

Another RG:

```text
rg-connectivity
├── VNet
├── Azure Firewall
└── Bastion
```

might have a different lifecycle and owner.

Resource Groups are excellent for:

```text
lifecycle
ownership
RBAC
deployment grouping
cost visibility
```

within the subscription.

---

# **3. A Resource Group belongs to one subscription**

You cannot have:

```text
rg-app
├── resource from Subscription A
└── resource from Subscription B
```

as one Resource Group.

A Resource Group is nested under exactly one subscription.

The full resource ID demonstrates this:

```text
/subscriptions/<subscription-id>
/resourceGroups/<rg-name>
/providers/...
```

Subscription is part of the RG's identity.

---

# **4. A resource belongs to one Resource Group at a time**

A VM cannot simultaneously belong to:

```text
rg-app
and
rg-shared
```

It has one Resource Group.

Some supported resource types can be **moved** between Resource Groups or subscriptions, but that's still a move:

```text
old RG
→
new RG
```

not dual membership.

---

# **5. Resource Groups don't constrain resource region**

Suppose Resource Group location is:

```text
Central India
```

It may contain:

```text
VM → Central India
Storage → West Europe
Front Door → global service
```

where those services support those locations.

The Resource Group's `location` primarily determines where Azure stores the **Resource Group metadata**, not a hard region boundary for all child resources.

This is a very common interview question.

---

# **6. Subscription can contain many regions too**

Similarly:

```text
Subscription
```

isn't a region.

One subscription can contain:

```text
VNet → Central India
AKS → East US
Storage → West Europe
```

subject to governance and service constraints.

Azure geography and Azure management hierarchy are separate concepts.

---

# **7. RBAC can apply at both scopes**

Example:

```text
Alice
→ Reader
→ Subscription
```

means applicable resources beneath it inherit Reader access.

Then:

```text
Bob
→ Contributor
→ rg-app
```

only grants that Contributor role at the RG and descendants.

This makes Resource Groups useful for delegated administration:

```text
central platform
→ subscription-level control

application team
→ contributor on own RG
```

---

# **8. Policy also applies at both**

Example:

Subscription:

```text
Policy:
Only approved regions
```

applies broadly.

Resource Group:

```text
Policy:
Require CostCenter tag
```

could apply to resources in that RG.

Higher scopes normally give more consistent enterprise governance.

---

# **9. Locks apply at both**

You can lock:

```text
Subscription
Resource Group
Resource
```

A lock higher in the hierarchy can affect descendants.

Example:

```text
rg-prod
→ CanNotDelete
```

means contained resources inherit the protection. ([Microsoft Learn][1])

Again, scope matters.

---

# **10. Resource Group deletion is a lifecycle operation**

If you delete:

```text
rg-demo
```

Azure attempts to delete resources contained inside that group.

That's why Resource Groups should ideally contain things whose lifecycle makes sense together.

Bad organization:

```text
rg-random
├── Production SQL
├── Dev VM
├── Shared DNS
└── Test Storage
```

because:

```text
What does deleting the Resource Group mean?
```

is unclear and dangerous.

---

# **11. Subscription deletion/cancellation is much broader**

A subscription holds many:

```text
Resource Groups
Resources
Policies
Role assignments
```

and has a billing/commercial relationship.

Canceling a subscription is therefore drastically different from deleting one Resource Group.

Think:

```text
Resource Group
→ application/component lifecycle container

Subscription
→ broad resource-management/billing boundary
```

---

# **12. Quotas often operate at subscription scope**

Many Azure service quotas/capacities are tracked using:

```text
subscription
+
region
+
resource type/SKU
```

rather than by Resource Group.

For example, Compute vCPU quota traditionally behaves at subscription-region/family boundaries, though Azure also now has quota-management mechanisms that can share/manage certain compute quotas across subscriptions. ([Microsoft Learn][7])

So moving:

```text
VM
from rg-A → rg-B
```

within the same subscription doesn't inherently give it a new subscription quota boundary.

---

# **13. Billing distinction**

Usage ultimately belongs to:

```text
Subscription
```

within Azure's billing hierarchy.

Resource Groups can still be used for:

```text
cost analysis
budgets
cost allocation
```

but they don't represent a separate contractual Azure subscription.

Microsoft Cost Management explicitly describes subscriptions as resource/cost scopes and Resource Groups as lower-level logical groupings useful for organizing and allocating costs. ([Microsoft Learn][6])

---

# **14. Production vs nonproduction design**

For a small environment, you could technically have:

```text
Subscription A
├── rg-dev
├── rg-test
└── rg-prod
```

But for more mature environments I often prefer:

```text
NonProd Subscription
├── rg-app-dev
└── rg-app-test

Prod Subscription
└── rg-app-prod
```

Why?

Because the subscription boundary improves:

```text
RBAC isolation
cost separation
quota management
Policy
blast-radius control
credential separation
```

A bad Dev pipeline with access only to NonProd cannot accidentally delete Prod.

---

# **15. Tenant relationship**

An Azure subscription trusts one Microsoft Entra tenant for identity authentication at a time, while a tenant can be associated with multiple subscriptions. ([Microsoft Learn][8])

So:

```text
Entra tenant
   ├── Subscription A
   ├── Subscription B
   └── Subscription C
```

is normal.

The Resource Groups exist beneath those subscriptions.

| Billing boundary             | Cost scope, not subscription contract | **Yes / major billing scope**   |
| RBAC scope                   | **Yes**                               | **Yes**                         |

### **Interview answer condensed**

> “A subscription is a higher-level Azure management and billing boundary that contains Resource Groups and resources, while a Resource Group is a logical lifecycle and management container inside one subscription. I use subscriptions when I want stronger isolation around areas such as Production, billing, quotas, RBAC or Policy, and Resource Groups to organize related resources inside that boundary. A Resource Group can't span subscriptions, a resource belongs to one Resource Group at a time, and the Resource Group's location doesn't force all of its resources to run in that region.”

**Memory line:**
**Subscription is the broad management/billing boundary; Resource Group is the related-resource lifecycle container inside it.**

**Interview trap:**
A Resource Group's location **does not require every resource inside it to exist in that same Azure region**.

**Keywords:**
subscription, Resource Group, hierarchy, billing, RBAC, Policy, quota, lifecycle, isolation.

**Likely follow-ups:**

* Can resources in one Resource Group be in different regions?
* Can one Resource Group span two subscriptions?
* Why separate Production into another subscription rather than another RG?
* Where are Azure quotas usually enforced?

---

### **T34-19. Management group vs subscription?**

**Answer:**

A **Management Group** sits **above Azure subscriptions** and exists primarily to organize and govern multiple subscriptions as a hierarchy. I use it to apply Azure Policy and Azure RBAC consistently across groups of subscriptions.

A **subscription** is the actual Azure resource-management and billing boundary in which Resource Groups and workload resources such as VMs, VNets, AKS clusters, and Storage Accounts are normally created.

So:

```text
Management Group
→ governs groups of subscriptions

Subscription
→ contains and operates Azure workloads
```

For example:

```text
Tenant Root
     ↓
Corp
├── Platform
│    ├── Connectivity Subscription
│    └── Management Subscription
│
└── Landing Zones
     ├── Prod Subscription
     └── NonProd Subscription
```

I could assign organization-wide Policy at `Corp` and allow subscriptions beneath it to inherit those governance controls.

Microsoft recommends Management Groups for organizing and governing subscriptions at scale and specifically highlights centralized Azure Policy and RBAC inheritance as their main role. ([Microsoft Learn][9])

---

## **1. Azure hierarchy**

The core hierarchy is:

```text
Microsoft Entra tenant
        ↓
Tenant Root Management Group
        ↓
Management Groups
        ↓
Subscriptions
        ↓
Resource Groups
        ↓
Resources
```

The Management Group layer solves:

> How do I manage 10, 50, 500, or 1,000 subscriptions consistently?

Without it, you'd repeatedly configure each subscription.

---

# **2. Subscription is where normal workload resources live**

Typical subscription:

```text
Prod Subscription
├── rg-network
│    └── VNet
│
├── rg-platform
│    └── AKS
│
└── rg-data
     └── SQL
```

A Management Group doesn't normally exist to directly hold:

```text
VM
AKS
Storage
```

like a Resource Group.

Its children are primarily:

```text
other Management Groups
and
subscriptions
```

It's a governance/organization tier.

---

# **3. Policy at Management Group scale**

Suppose Contoso has:

```text
80 Production subscriptions
```

Requirement:

```text
Public IP resources prohibited
```

Without Management Groups:

```text
assign policy 80 times
```

With hierarchy:

```text
Management Group: Production
        ↓
Policy assignment
        ↓
80 subscriptions inherit it
```

That's exactly why Management Groups exist.

Microsoft documents that subscriptions beneath a Management Group inherit governance conditions such as Policy assignments applied higher in the hierarchy. ([Microsoft Learn][10])

---

# **4. RBAC can also inherit**

Suppose:

```text
Cloud Security Team
→ Security Reader
→ Corp Management Group
```

That role can apply down to relevant child subscriptions/resources.

Compare assigning the same role separately to:

```text
Subscription 1
Subscription 2
...
Subscription 150
```

The Management Group provides centralized access governance.

---

# **5. Subscription is still a stronger operational workload boundary**

A subscription has things such as:

```text
resource providers
service quotas
cost/billing context
Resource Groups
workload resources
RBAC/Policy scope
```

It is the unit most teams interact with while actually deploying Azure infrastructure.

Management Group is primarily:

```text
organization
governance
inheritance
```

above that operational boundary.

---

# **6. One subscription has one parent in the Management Group hierarchy**

A subscription cannot simultaneously be:

```text
under Management Group A
and
under Management Group B
```

in the Azure Management Group tree.

It has one direct parent.

Microsoft's current limits state that each Management Group/subscription has one parent in the hierarchy. ([Microsoft Learn][10])

You can move a subscription from one Management Group to another if authorization and hierarchy requirements are satisfied.

---

# **7. Moving a subscription changes inherited governance**

This is important operationally.

Before:

```text
Sandbox MG
   ↓
Subscription X

Policy:
public IP allowed
```

Move it to:

```text
Production MG
   ↓
Subscription X

Inherited policy:
public IP denied
```

Now deployments in that subscription can behave differently because its inherited:

```text
Policy
RBAC
```

context changed.

Moving a subscription isn't just rearranging the Portal tree.

It can materially change governance.

---

# **8. Management Groups belong to one Entra hierarchy**

Within a Microsoft Entra tenant, Management Groups and subscriptions form a single hierarchy beneath the tenant root Management Group.

Microsoft currently allows a Management Group tree of:

```text
Root
+
up to 6 Management Group levels
+
Subscription
```

and up to **10,000 Management Groups per tenant**. ([Microsoft Learn][7])

You don't need to memorize 10,000 for most interviews, but knowing the hierarchy is bounded is useful.

---

# **9. Don't build an unnecessarily deep hierarchy**

Technically:

```text
6 MG levels
```

are supported.

But Microsoft Cloud Adoption Framework guidance recommends keeping the hierarchy reasonably flat—typically around three to four meaningful levels when possible—to reduce complexity. ([Microsoft Learn][9])

Bad:

```text
Corp
 ↓
India
 ↓
Engineering
 ↓
Platform
 ↓
Production
 ↓
AKS
 ↓
Team-A
```

if every organizational detail is reflected in Management Groups.

That can make:

```text
Policy inheritance
RBAC
exceptions
moves
```

hard to reason about.

---

# **10. Management Groups shouldn't mirror the org chart blindly**

A common Azure Landing Zone lesson is:

```text
Management Group hierarchy
≠
organizational hierarchy copied literally
```

Design Management Groups around:

```text
governance requirements
security posture
policy differences
platform responsibilities
regulated boundaries
```

rather than creating one for every business team.

Microsoft's current Cloud Adoption Framework specifically cautions against making the hierarchy unnecessarily deep or mirroring every organizational structure. ([Microsoft Learn][9])

---

# **11. Environment isolation often belongs at subscription level**

Suppose you have:

```text
Dev
Test
Prod
```

A tempting hierarchy:

```text
MG-Dev
MG-Test
MG-Prod
```

But modern Azure Landing Zone guidance generally recommends using subscriptions as workload/environment boundaries when appropriate rather than automatically creating Management Groups purely for every environment label. ([Microsoft Learn][9])

For example:

```text
LandingZones MG
├── App1-Prod Subscription
├── App1-NonProd Subscription
├── App2-Prod Subscription
└── App2-NonProd Subscription
```

with Management Groups driven by governance requirements.

---

# **12. Billing distinction**

A subscription is part of the Azure billing/resource consumption model.

Management Groups primarily organize subscriptions for governance.

Azure Cost Management can report and analyze across Management Group scopes, but a Management Group itself isn't the same contractual/resource-consumption boundary as a subscription.

Conceptually:

```text
Management Group
→ aggregation/governance

Subscription
→ workload + cost/resource boundary
```

---

# **13. Example enterprise hierarchy**

A simplified Azure Landing Zone-style structure:

```text
Tenant Root
    │
    └── Contoso
         │
         ├── Platform
         │    ├── Connectivity
         │    │      └── Hub Subscription
         │    │
         │    ├── Management
         │    │      └── Monitoring Subscription
         │    │
         │    └── Identity
         │
         ├── Landing Zones
         │    ├── Corp
         │    │    └── App Subscriptions
         │    │
         │    └── Online
         │         └── Internet-facing app subscriptions
         │
         └── Sandbox
              └── Sandbox subscriptions
```

Policy can vary:

```text
Platform
→ platform governance

Landing Zones
→ workload security requirements

Sandbox
→ relaxed experimentation
```

while common policies can be inherited from:

```text
Contoso
```

above all of them.

---

# **14. Management Group vs Resource Group**

Don't confuse these names.

```text
Management Group
→ contains MGs/subscriptions

Resource Group
→ contains Azure workload resources
```

They live at very different levels.

Common interview trap:

> “Can I put a VM directly in a Management Group?”

Normal answer:

```text
No.
The VM belongs to a Resource Group/subscription.
The Management Group governs the subscription above it.
```

# **15. Practical governance example**

Requirement:

All corporate subscriptions must:

```text
Use approved regions
Enable Defender plans according to policy
Disallow insecure Storage settings
```

Production application team should only manage:

```text
its own subscription/RGs
```

Architecture:

```text
Corp MG
│
├─ Organization-wide Policy
│
└─ Production MG
      │
      ├─ Prod Subscription A
      └─ Prod Subscription B
```

At:

```text
Corp MG
```

assign shared Policy.

At:

```text
Prod Subscription A
```

assign application-team Contributor at appropriate lower scope.

Now:

```text
Management Group
→ centralized governance

Subscription
→ workload isolation/ownership
```

### **Interview answer condensed**

> “A Management Group sits above subscriptions and is mainly used to organize and govern multiple subscriptions at scale. I can assign Azure Policy or RBAC at the Management Group and let child subscriptions inherit those controls. A subscription is the actual workload and resource-management boundary where Resource Groups, VNets, AKS, Storage and other resources are deployed and where many billing and quota boundaries exist. Each subscription has one parent in the Management Group hierarchy, and moving it to another Management Group can change inherited Policy and RBAC, so it's a governance change rather than just organizational housekeeping.”

**Memory line:**
**Management Groups govern collections of subscriptions; subscriptions contain and isolate the actual Azure workloads.**

**Interview trap:**
Moving a subscription between Management Groups can change its **inherited RBAC and Azure Policy**, so the move can have real Production impact.

Management Group, subscription, hierarchy, Azure Policy, RBAC inheritance, tenant root, Azure Landing Zone, governance.
