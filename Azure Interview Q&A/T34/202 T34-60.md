### **T34-60. Azure Firewall vs NAT Gateway?**

**Answer:**

Azure Firewall and NAT Gateway can both participate in outbound internet connectivity, but they solve very different problems.

**Azure NAT Gateway** is primarily a highly scalable **outbound SNAT service**. I attach it to a subnet when private resources need predictable outbound internet connectivity using static public IP addresses. It doesn't inspect application traffic or make allow/deny decisions like a firewall.

**Azure Firewall** is a centralized, stateful **network security service**. I use it when I need to control and inspect traffic using network rules, application/FQDN rules, threat intelligence, DNAT, and—with the appropriate tier—advanced capabilities such as TLS inspection and IDPS.

So my mental model is:

```text
NAT Gateway
→ "How should this subnet reach the internet
   with scalable, predictable SNAT?"

Azure Firewall
→ "Should this traffic be allowed,
   blocked, inspected, or logged?"
```

For simple direct outbound internet connectivity, NAT Gateway is generally the better-purpose-built service. If the organization requires centralized egress inspection and policy enforcement, I route traffic through Azure Firewall. For high-volume environments, I can also **combine them**: workloads route through Azure Firewall for inspection, and a NAT Gateway on the firewall subnet provides scalable outbound SNAT. Current Microsoft guidance recommends NAT Gateway as the default direct outbound connectivity method and Azure Firewall when traffic needs centralized control or inspection. ([Microsoft Learn][1])

---

## **1. NAT Gateway is fundamentally an outbound connectivity service**

Typical architecture:

```text
Private subnet

VM / AKS node / workload
        ↓
    NAT Gateway
        ↓
 Static Public IP
        ↓
     Internet
```

The workload itself doesn't need:

```text
Public IP on VM
```

Instead, NAT Gateway translates:

```text
10.10.1.7:45123
       ↓ SNAT
20.x.x.x:xxxxx
```

for the outbound connection.

The destination sees:

```text
20.x.x.x
```

as the source.

This is useful when external systems require:

> “Tell us which public IP addresses to allowlist.”

You can give them the NAT Gateway's known public IP or prefix.

---

# **2. NAT Gateway does not provide firewall policy**

This is the most important distinction.

Attaching NAT Gateway does **not** let me define rules such as:

```text
Allow:
*.microsoft.com

Deny:
*.example-malware.com

Allow:
TCP 443 to destination X

Deny:
all other internet destinations
```

NAT Gateway's primary job is:

```text
source address translation
+
outbound connectivity
```

not traffic inspection.

If a subnet has:

```text
NAT Gateway
```

resources aren't suddenly protected by a centralized application-aware security policy.

I still need controls such as:

```text
NSGs
Azure Firewall
Private Endpoints
application security
```

depending on the requirement.

---

# **3. Azure Firewall is a security control**

Typical architecture:

```text
Spoke workloads
      ↓
UDR: 0.0.0.0/0
      ↓
Azure Firewall
      ↓
policy inspection
      ↓
Internet
```

Azure Firewall evaluates traffic against configured policy.

For example:

```text
Application rule:

Allow
Source: app-subnet
Destination:
*.ubuntu.com
*.microsoft.com
Protocol: HTTPS
```

Everything else can be denied according to policy.

That's something NAT Gateway cannot provide.

---

# **4. Azure Firewall supports different rule types**

At a high level, Azure Firewall can use:

### Network rules

For:

```text
source IP
destination IP
port
protocol
```

Example:

```text
10.20.1.0/24
→ 10.50.2.10
→ TCP 1433
```

---

### Application rules

For application-layer destinations such as:

```text
FQDN
HTTP/S-related destinations
```

Example:

```text
App subnet
→ *.microsoft.com
→ HTTPS
```

---

### DNAT rules

For publishing permitted inbound flows:

```text
Firewall Public IP:443
        ↓ DNAT
10.10.2.5:443
```

NAT Gateway does **not** provide this type of inbound publishing.

Azure Firewall's NAT rules can provide inbound DNAT, whereas NAT Gateway is outbound-oriented and doesn't permit unsolicited inbound connections. ([Microsoft Learn][2])

---

# **5. NAT Gateway is outbound-only**

This is another key interview point.

Suppose:

```text
VM
→ NAT Gateway
→ Internet
```

The VM starts a connection:

```text
VM → api.example.com:443
```

Return packets for that established outbound flow can come back.

But an internet host cannot simply initiate:

```text
Internet
→ NAT Gateway public IP
→ VM:22
```

NAT Gateway doesn't function like an inbound public load balancer or firewall DNAT service.

Microsoft specifically states that unsolicited inbound connections aren't allowed through NAT Gateway. ([Microsoft Learn][3])

So:

```text
NAT Gateway
≠
inbound NAT gateway / public load balancer
```

---

# **6. NAT Gateway is particularly strong at SNAT scalability**

Outbound connectivity needs a source port.

Large environments can create enormous numbers of simultaneous outbound connections:

```text
AKS
100 nodes

Each node:
thousands of outbound connections
```

Source NAT port exhaustion can become a real production problem.

NAT Gateway is designed specifically to handle this efficiently.

Current Microsoft documentation states that a NAT Gateway provides **64,512 SNAT ports per IPv4 public IP address** and can use up to 16 IPv4 public IP addresses, giving very large aggregate SNAT capacity. ([Microsoft Learn][4])

Conceptually:

```text
NAT Gateway
   │
   ├── Public IP 1
   │    └── large SNAT port pool
   │
   ├── Public IP 2
   │    └── large SNAT port pool
   │
   └── ...
```

Ports are dynamically allocated across subnet workloads.

---

# **7. Azure Firewall also performs SNAT—but that's not its only job**

Azure Firewall can provide:

```text
private workload
     ↓
Firewall
     ↓ SNAT
Firewall public IP
     ↓
Internet
```

So an interviewer might ask:

> If Azure Firewall already performs SNAT, why use NAT Gateway?

Because NAT Gateway is specifically optimized for scalable outbound SNAT.

Azure Firewall exists primarily for:

```text
policy
inspection
logging
threat protection
centralized control
```

Its SNAT capacity and economics are different.

Current Microsoft documentation notes that Azure Firewall has a smaller per-public-IP SNAT port allocation than NAT Gateway and explicitly recommends integrating NAT Gateway when much greater outbound SNAT scale is required. ([Microsoft Learn][5])

---

# **8. They can be used together**

This is one of the best interview points.

A mature hub-and-spoke architecture can be:

```text
Spoke A
   │
Spoke B
   │
Spoke C
   │
   └── UDR:
       0.0.0.0/0
           ↓
      Azure Firewall
           ↓
      Traffic inspection
           ↓
      NAT Gateway
      attached to
      AzureFirewallSubnet
           ↓
       Internet
```

Responsibilities:

```text
Azure Firewall
→ security decision

NAT Gateway
→ scalable final outbound SNAT
```

This gives you:

```text
centralized filtering
+
central logging
+
predictable public IPs
+
large SNAT capacity
```

Microsoft has an explicit supported architecture for combining NAT Gateway with Azure Firewall in hub-and-spoke deployments. ([Microsoft Learn][5])

---

# **9. Routing in the combined architecture is important**

Suppose workload subnet has:

```text
UDR:

0.0.0.0/0
→ Virtual appliance
→ Azure Firewall private IP
```

Traffic path:

```text
Workload
   ↓
UDR
   ↓
Azure Firewall
   ↓
security rules
   ↓
NAT Gateway on Firewall subnet
   ↓
Internet
```

Notice:

```text
NAT Gateway
```

doesn't replace the routing to the firewall.

The UDR ensures that workload traffic hits:

```text
Azure Firewall first
```

for inspection.

This distinction matters because current Azure behavior is nuanced: NAT Gateway takes precedence over other **explicit outbound connectivity mechanisms** for new flows, but it does **not override a UDR whose `0.0.0.0/0` next hop sends traffic to a virtual appliance such as Azure Firewall**. ([Microsoft Learn][6])

That's an excellent modern Azure interview detail.

---

# **10. What if I attach NAT Gateway directly to the workload subnet?**

Suppose:

```text
App subnet
├── NAT Gateway
└── UDR 0.0.0.0/0 → Firewall
```

The UDR still determines the next-hop path:

```text
App
 ↓
Firewall
```

rather than letting NAT Gateway bypass that route. ([Microsoft Learn][6])

So don't say:

> “NAT Gateway always overrides Azure Firewall.”

That's too simplistic.

Better:

> NAT Gateway has precedence over other explicit outbound SNAT mechanisms, but routing still determines where the packet goes. A UDR sending `0.0.0.0/0` to Azure Firewall still forces traffic through the firewall.

---

# **11. NAT Gateway isn't a route table**

Another common misconception.

When NAT Gateway is associated with a subnet, I don't normally need to add:

```text
0.0.0.0/0 → NAT Gateway
```

into a route table.

There isn't a:

```text
Next hop type = NAT Gateway
```

pattern like an NVA route.

It is associated directly with the subnet and automatically becomes its outbound SNAT method, subject to routing behavior. Microsoft explicitly documents that NAT Gateway doesn't require a subnet UDR simply to provide direct outbound connectivity. ([Microsoft Learn][7])

---

# **12. Azure Firewall does require traffic to be routed through it**

Simply creating:

```text
Azure Firewall
```

doesn't cause every spoke to magically send traffic through it.

You must establish the traffic path.

Typical hub/spoke:

```text
Spoke subnet route table

0.0.0.0/0
     ↓
Virtual appliance
     ↓
10.0.1.4
(Azure Firewall)
```

Then:

```text
effective routes
```

should confirm the expected firewall next hop.

This is why:

```text
Firewall policy
+
routing
```

must both be correct.

A perfect firewall rule does nothing if the packet bypasses the firewall.

# **13. Example: simple private application subnet**

Requirement:

```text
10 private VMs

Need:
apt/yum updates
third-party API access
predictable outbound IP

Don't need:
FQDN inspection
central internet filtering
IDPS
```

I'd use:

```text
Private subnet
     ↓
NAT Gateway
     ↓
static public IP
     ↓
Internet
```

plus:

```text
NSGs
Managed Identity
Private Endpoints for Azure PaaS
```

where appropriate.

Deploying Azure Firewall purely to obtain an outbound IP would usually add unnecessary cost and complexity.

# **14. Example: regulated enterprise**

Requirements:

```text
All internet egress
must be centrally controlled.

Only approved destinations allowed.

Security team needs traffic logs.

Threat inspection required.
```

Architecture:

```text
Application spokes
       ↓
UDR
       ↓
Azure Firewall
       ↓
Approved internet destinations
```

Azure Firewall is the right core control.

If outbound connection volume is extremely large:

```text
Firewall
   ↓
NAT Gateway
   ↓
Internet
```

can improve SNAT scalability.

---

# **15. Azure Firewall Premium adds deeper security capabilities**

Depending on the selected tier and configuration, Azure Firewall can provide capabilities such as:

```text
TLS inspection
IDPS
URL filtering
advanced threat protection
```

which clearly illustrates why Firewall is fundamentally a **security product**.

NAT Gateway doesn't inspect:

```text
HTTP payloads
TLS sessions
signatures
malicious traffic patterns
URLs
```

It performs address/port translation for outbound connectivity.

---

# **16. NAT Gateway does not replace NSGs either**

Suppose application subnet uses NAT Gateway.

Should I remove:

```text
NSG
```

because inbound internet initiation is blocked?

No.

NSGs still govern:

```text
subnet/NIC traffic
east-west flows
allowed ports
internal communication
```

NAT Gateway controls outbound address translation, not general subnet authorization policy.

A reasonable layering could be:

```text
NSG
→ distributed L3/L4 filtering

Azure Firewall
→ centralized inspection/policy if required

NAT Gateway
→ scalable outbound SNAT
```

Different purposes.

# **17. Private Endpoint can eliminate some NAT usage entirely**

Suppose AKS accesses:

```text
Azure SQL
Storage
Key Vault
```

Don't automatically send those connections:

```text
AKS
→ public Azure endpoint
→ NAT Gateway
→ internet/public service endpoint
```

For sensitive environments:

```text
AKS
   ↓
Private DNS
   ↓
Private Endpoint
   ↓
Azure SQL / Storage / Key Vault
```

may be preferable.

Microsoft currently recommends using Private Link where appropriate to reduce unnecessary public internet egress through NAT Gateway. ([Microsoft Learn][3])

Then reserve NAT/firewall internet egress for destinations that genuinely need public connectivity.

# **18. Troubleshooting: internet access fails with NAT Gateway**

I'd troubleshoot in dependency order.

```text
Workload
   ↓
Effective route
   ↓
Subnet/NAT association
   ↓
NSG
   ↓
NAT Gateway
   ↓
Public IP
   ↓
Destination
```

### Step 1 — verify DNS separately

If:

```text
curl https://example.com
```

fails but:

```text
curl https://1.1.1.1
```

or equivalent direct-IP testing behaves differently, investigate DNS first.

---

### Step 2 — verify effective route

If a UDR says:

```text
0.0.0.0/0
→ Firewall/NVA
```

then traffic isn't taking a simple direct-NAT path.

That's expected routing behavior.

---

### Step 3 — verify subnet association

Confirm the NAT Gateway is actually associated with the workload subnet.

If not:

```text
no NAT Gateway SNAT path
```

from that subnet.

---

### Step 4 — verify NAT Gateway public IP configuration

NAT Gateway requires appropriate associated public IP/public IP prefix to provide internet egress.

---

### Step 5 — check NSG/firewall

If outbound NSG rules or an NVA/firewall route block the destination:

```text
NAT Gateway cannot override the security decision.
```

---

### Step 6 — examine SNAT/connectivity metrics

For very high connection volumes, investigate:

```text
connection count
SNAT port usage
destination-specific limits
```

although NAT Gateway has significantly more scalable SNAT behavior than older outbound mechanisms.

---

# **19. Troubleshooting Azure Firewall egress**

If workloads routed through Firewall cannot reach internet:

```text
Workload
   ↓
Effective route
   ↓
Firewall
   ↓
Firewall policy
   ↓
SNAT/NAT Gateway if present
   ↓
Internet
```

I check:

### 1. Route

Does:

```text
0.0.0.0/0
```

actually point to Azure Firewall?

If no, don't investigate firewall rules yet—the traffic may never reach it.

### 2. Firewall health

Is Firewall healthy/provisioned?

### 3. Rule match

Does the source/destination/protocol match a:

```text
network rule
or
application rule
```

?

### 4. Logs

Look for:

```text
allow
deny
rule collection
destination
source
```

evidence.

### 5. DNS

For FQDN/application rules, confirm name resolution behaves as expected.

### 6. Outbound SNAT

If security rules allow traffic but large-scale connections fail intermittently, examine SNAT capacity. That's where a NAT Gateway integration may become relevant.

This is diagnostic reasoning:

```text
prove traffic reaches Firewall
before blaming Firewall policy.
```

# **20. Cost and complexity trade-off**

### NAT Gateway

Advantages:

```text
simple
managed
high SNAT scale
predictable public IP
low operational complexity
```

But:

```text
no centralized traffic inspection
no FQDN/application filtering
no threat detection
```

---

### Azure Firewall

Advantages:

```text
central security policy
network/application rules
logging
DNAT
threat-intelligence controls
advanced inspection by tier
```

But:

```text
higher cost
more architecture/routing complexity
security-policy operations required
```

Therefore:

> Don't pay for a firewall merely because you need outbound NAT, and don't use NAT Gateway as a substitute when the security requirement is centralized traffic inspection.

---

## **Quick comparison**

| Capability                         | Azure NAT Gateway | Azure Firewall                         |
| ---------------------------------- | ----------------- | -------------------------------------- |
| Primary purpose                    | **Outbound SNAT** | **Traffic security/inspection**        |
| Predictable outbound public IP     | **Yes**           | Yes                                    |
| High SNAT scalability              | **Excellent**     | Can scale; NAT GW can augment          |
| Network allow/deny rules           | No                | **Yes**                                |
| FQDN/application rules             | No                | **Yes**                                |
| Threat intelligence                | No                | **Yes**                                |
| IDPS/TLS inspection                | No                | **Premium capabilities**               |
| Inbound DNAT                       | No                | **Yes**                                |
| Unsolicited inbound                | **Blocked**       | Can publish via DNAT                   |
| UDR needed for direct service      | No                | **Usually route workloads through it** |
| Best for simple internet egress    | **Yes**           | Usually overkill                       |
| Best for centralized secure egress | No                | **Yes**                                |
| Can work together                  | **Yes**           | **Yes**                                |

### **Interview answer condensed**

> “Azure NAT Gateway and Azure Firewall can both participate in outbound internet connectivity, but NAT Gateway is primarily a scalable outbound SNAT service, while Azure Firewall is a centralized stateful security service. I use NAT Gateway when private workloads simply need reliable outbound internet access with predictable public IPs and high SNAT capacity. I use Azure Firewall when I need to inspect, filter and log traffic with network or application rules and threat-protection capabilities. They can also work together: spoke traffic is forced through Azure Firewall using a UDR for inspection, and a NAT Gateway attached to the firewall subnet can provide the final highly scalable outbound SNAT. The key is that NAT Gateway translates traffic; Firewall makes security decisions.” ([Microsoft Learn][1])

**Memory line:**
**NAT Gateway answers “How do I get out?”; Azure Firewall answers “Am I allowed to go there?”**

**Interview trap:**
NAT Gateway does **not** provide firewall filtering, and NAT Gateway precedence over other outbound mechanisms does **not override a UDR that explicitly routes `0.0.0.0/0` through Azure Firewall.** ([Microsoft Learn][6])

**Keywords:**
Azure Firewall, NAT Gateway, SNAT, UDR, outbound connectivity, FQDN rules, network rules, DNAT, hub-and-spoke, SNAT exhaustion.
