### **T34-28. Azure Functions vs Container Apps?**

**Answer:**

The main difference is the **programming and hosting abstraction**.

**Azure Functions** is a serverless **Functions-as-a-Service** platform optimized for small, event-driven units of code. I think in terms of **functions, triggers, and bindings**—for example, “run this code when a Service Bus message arrives” or “execute this function when an HTTP request comes in.”

**Azure Container Apps** is a managed serverless **container application platform**. I bring a complete container image and can run APIs, microservices, long-running workers, background processors, scheduled/event-driven jobs, and other containerized applications. It supports revisions, traffic splitting, KEDA-based scaling, internal service discovery, sidecars, and richer container lifecycle control.

So my rule is:

```text
Event-driven unit of code
where Functions programming model
and triggers/bindings improve productivity
→ Azure Functions

Full containerized application,
microservice, worker, sidecars,
custom runtime or revision traffic control
→ Azure Container Apps
```

One important modern nuance is that these services are **not mutually exclusive**. Azure Functions can now be hosted directly on Azure Container Apps, combining the Functions programming model with Container Apps features such as KEDA, revisions, sidecars, Dapr, and custom containers. Microsoft currently recommends **Flex Consumption** for many new standard Functions workloads, while Container Apps hosting is especially useful when Functions need to live alongside other containerized services or require container-specific capabilities. ([Microsoft Learn][1])

---

## **1. Start with the abstraction**

### Azure Functions

You think:

```text
Event
  ↓
Trigger
  ↓
Function
  ↓
Binding / SDK
  ↓
Azure service
```

Example:

```text
Service Bus message
       ↓
ServiceBusTrigger
       ↓
processOrder()
       ↓
Cosmos DB / Storage / API
```

Your deployment unit is conceptually a:

```text
function application
containing functions
```

rather than a general-purpose application container.

---

### Container Apps

You think:

```text
Container image
      ↓
Container App
      ↓
Revision
      ↓
Replicas
```

Example:

```text
orders-api
payment-api
email-worker
frontend
scheduled-job
```

Each can have its own:

```text
container image
CPU/memory
ingress
scaling rules
identity
revision
```

Container Apps is therefore a broader application-hosting abstraction.

---

# **2. Functions is built around triggers and bindings**

Azure Functions has strong built-in integration with events.

Examples:

```text
HTTP request
→ HTTP trigger

Service Bus queue
→ Service Bus trigger

Timer
→ Timer trigger

Blob event
→ Blob trigger

Event Hubs stream
→ Event Hubs trigger
```

Bindings can simplify interaction with other services.

Conceptually:

```text
Event source
   ↓
Functions runtime
   ↓
your business logic
```

This reduces infrastructure/plumbing code.

Microsoft describes triggers and bindings as a core Functions productivity model. ([Microsoft Learn][1])

---

# **3. Container Apps is not limited to function-style execution**

Container Apps can host:

```text
REST APIs
web applications
workers
long-running processes
event consumers
jobs
microservices
```

For example:

```text
frontend
   ↓
orders-api
   ↓
Service Bus
   ↓
order-worker
```

All three could run in one Container Apps environment.

That is much harder to describe purely as:

```text
three Functions
```

if they are full application components with independent container behavior.

---

# **4. Container Apps gives you container-level control**

You control:

```text
Docker image
base OS/runtime
packages
native dependencies
startup command
CPU/memory
environment variables
```

So if the workload needs:

```text
custom ffmpeg binary
special native library
nonstandard runtime
sidecar proxy
custom agent
```

Container Apps can be a better fit.

Functions can also run containerized, especially through Container Apps hosting, but the default Functions value proposition is **code-first event execution** rather than “I need full container semantics.”

---

# **5. Scaling**

Both are serverless/event-driven platforms, but their scaling model is presented differently.

### Azure Functions

The Functions platform understands:

```text
trigger workload
```

and scales function instances according to the selected hosting plan.

For new apps, Microsoft currently lists **Flex Consumption** as the recommended general serverless Functions hosting option, with fast event-driven scaling and VNet integration. ([Microsoft Learn][1])

---

### Container Apps

Container Apps uses KEDA-supported scaling.

Example:

```text
Service Bus queue depth = 0
       ↓
worker replicas = 0

Queue depth = 10,000
       ↓
KEDA
       ↓
worker replicas = 30
```

Container Apps can also scale on:

```text
HTTP
CPU
memory
TCP
KEDA event sources
```

and most compatible workloads can scale to zero. ([Microsoft Learn][2])

---

# **6. Scale-to-zero exists in both worlds**

Therefore:

```text
"Functions can scale to zero,
Container Apps cannot"
```

would be wrong.

Container Apps can scale many workloads to zero.

Likewise, serverless Functions hosting can scale down when idle depending on hosting configuration.

The decision is more about:

```text
programming abstraction
+
application architecture
```

than simply scale-to-zero.

---

# **7. Revisions are a strong Container Apps feature**

Suppose:

```text
orders revision v1
orders revision v2
```

Container Apps can route:

```text
90% → v1
10% → v2
```

Then:

```text
50 / 50
```

then:

```text
100% → v2
```

This is useful for:

```text
canary
blue-green
A/B testing
```

Container Apps exposes revisions as a first-class platform concept. ([Microsoft Learn][2])

Functions doesn't normally present the same generic revision/weighted-traffic model when hosted in the standard Functions plans.

---

# **8. Container Apps Jobs**

If a workload is:

```text
run once
run on schedule
run when an event occurs
then terminate
```

Container Apps supports **Jobs**.

Examples:

```text
nightly reconciliation
database migration
batch processor
scheduled cleanup
```

This can overlap with Functions Timer/Event triggers, so the choice depends on workload structure.

### Good Functions case

```text
Timer
→ run 100 lines of cleanup code
```

### Good Container Apps Job case

```text
Run a large existing container
that performs a complex batch process
for 45 minutes
```

The latter may map more naturally to a job container.

# **9. Long-running workloads**

Functions is optimized around event-driven execution.

While hosting options such as Premium provide more flexible execution characteristics, I generally wouldn't force a continuously running service daemon into the Functions programming model.

For:

```text
always-running consumer
custom worker process
full API server
```

Container Apps is often a more natural fit.

Suppose:

```text

└── worker
```

Functions can certainly participate in microservice architectures, but Container Apps is a broader microservice platform.

Functions Flex Consumption and Premium support VNet integration in appropriate configurations, while Container Apps environments can be connected to VNets and support internal ingress/service discovery. ([Microsoft Learn][1])


Networking should not be the only factor in the platform choice.


For example:

```text

       ↓
```

This is the nuance that makes a strong 2026 answer.

### **T34-29. ACR image tag vs image digest?**

**Answer:**

An **image tag** is a human-readable label such as:

```text
myapp:v1.4
```

or:

```text
myapp:production
```

that points to an image manifest in Azure Container Registry.

An **image digest** is the immutable, content-derived SHA-256 identifier for a specific image manifest, for example:

```text
myapp@sha256:abc123...
```

The important production difference is that a tag can normally be moved or reused to point to a different image, while the digest identifies the exact manifest content.

Therefore I usually:

```text
Use tags
→ human readability / build discovery

Use digest
→ exact production deployment identity
```

For production and supply-chain security, I strongly prefer deploying or at least recording the **digest**, because it guarantees that the artifact I deploy is the same artifact I tested, scanned, signed, and approved.

Microsoft's current ACR guidance states that every pushed image manifest gets a unique SHA-256 digest and recommends unique tagging strategies rather than repeatedly reusing tags. ([Microsoft Learn][4])

---

## **1. Tag is a pointer**

Suppose:

```text
myapp:v1
```

currently points to:

```text
sha256:AAA
```

Later someone pushes:

```text
docker push myapp:v1
```

again.

Now:

```text
myapp:v1
→ sha256:BBB
```

The tag name hasn't changed.

The artifact has.

Therefore:

```text
tag
≠
immutable identity
```

unless you explicitly enforce immutability policies/processes.

---

# **2. Digest identifies the manifest**

A digest looks like:

```text
sha256:
9ce26c52...
```

It is based on the image manifest content.

Therefore:

```text
myapp@sha256:AAA
```

always identifies that exact manifest.

If content changes:

```text
digest changes
```

That's why digest is powerful for reproducibility.

---

# **3. Tags are still useful**

Digests are:

```text
long
hard to remember
not business-friendly
```

So tags are very useful.

Example:

```text
orders:20260906.4
orders:build-1842
orders:git-a92fc81
orders:1.6.3
```

These help humans answer:

```text
Which release is this?
Which CI build created it?
Which Git version?
```

Microsoft recommends unique tags such as build IDs or other non-reused identifiers for stable deployment workflows. ([Microsoft Learn][4])

---

# **4. Avoid `latest` in Production**

Suppose Kubernetes manifest says:

```yaml
image: myacr.azurecr.io/orders:latest
```

Yesterday:

```text
latest
→ sha256:AAA
```

Today:

```text
latest
→ sha256:BBB
```

Two identical-looking manifests:

```text
image: orders:latest
```

can result in different workloads.

That's bad for:

```text
reproducibility
rollback
auditability
incident response
supply-chain security
```

---

# **5. Immutable deployment flow**

A strong pipeline looks like:

```text
Git commit
    ↓
CI build
    ↓
Container image
    ↓
Push to ACR
    ↓
Digest = sha256:BBB
    ↓
Scan BBB
    ↓
Sign/attest BBB
    ↓
Deploy BBB
```

Not:

```text
Scan :latest
      ↓
someone moves :latest
      ↓
deploy :latest
```

The first workflow ensures the **scanned artifact is the deployed artifact**.

---

# **6. Tag + digest together is often best**

Human-readable metadata:

```text
orders:build-1842
```

Machine-verifiable deployment:

```text
orders@sha256:BBB
```

Your CI metadata can store:

```text
Git SHA
Build ID
Image tag
Image digest
SBOM
Signature
```

Then you get:

```text
human traceability
+
cryptographic artifact identity
```

---

# **7. Kubernetes example**

Instead of:

```yaml
containers:
- name: orders
  image: myacr.azurecr.io/orders:v2
```

a highly reproducible Production deployment can reference:

```yaml
containers:
- name: orders
  image: myacr.azurecr.io/orders@sha256:abcdef...
```

Now restarting a Pod later still asks for the exact same manifest.

---

# **8. Tags can create rollback ambiguity**

Suppose:

```text
production
```

tag moves:

```text
Monday → v41
Tuesday → v42
```

Incident occurs Tuesday.

Engineer says:

> “Rollback to `production`.”

But:

```text
production
```

already means v42.

A known-good digest:

```text
sha256:AAA
```

provides an unambiguous rollback target.

---

# **9. ImagePullPolicy doesn't make mutable tags safe**

Kubernetes:

```yaml
imagePullPolicy: Always
```

does not magically make:

```text
orders:latest
```

immutable.

It simply tells Kubernetes to resolve/pull according to the current tag state.

If the tag moved, you may get different content.

Therefore:

```text
Always pull
≠
immutable deployment
```

---

# **10. Digests matter for signatures and attestations**

Supply-chain controls often operate over the artifact's digest.

For example:

```text
sha256:BBB
├── signature
├── SBOM
└── provenance attestation
```

Then policy can answer:

> “Is THIS exact artifact signed and approved?”

rather than:

> “Was something called `v2` signed at some point?”

That distinction is critical.

---

# **11. Multi-platform image nuance**

Container registries can store OCI/Docker image indexes containing platform-specific images, for example:

```text
linux/amd64
linux/arm64
```

A digest can identify the image index/manifest, and child platform manifests can have their own digests.

For most interviews, the key principle remains:

```text
digest = content-specific registry identity
```

rather than getting lost in manifest-index details.

---

# **12. Example incident**

Suppose:

```text
09:00 scanner approves
orders:v10
```

which resolves to:

```text
sha256:AAA
```

At 09:30 someone force-pushes:

```text
orders:v10
→ sha256:BBB
```

At 10:00 Production deploys:

```text
orders:v10
```

What was actually scanned?

```text
AAA
```

What got deployed?

```text
BBB
```

Security gate has been bypassed unintentionally.

Digest-based flow prevents this:

```text
Scan AAA
Deploy AAA
```

## **Quick comparison**

| Characteristic                       | Image tag                 | Image digest                 |
| ------------------------------------ | ------------------------- | ---------------------------- |
| Example                              | `orders:v2`               | `orders@sha256:...`          |
| Human readable                       | **Yes**                   | Poor                         |
| Can normally move                    | **Yes**                   | No for same content identity |
| Identifies exact manifest            | Not necessarily           | **Yes**                      |
| Good for build discovery             | **Yes**                   | Less convenient              |
| Good for exact Production deployment | Riskier alone             | **Excellent**                |
| Signature/SBOM correlation           | Possible but tag can move | **Strong**                   |
| Rollback certainty                   | Depends on tag discipline | **Exact**                    |

---

### **Interview answer condensed**

> “A tag is a human-readable reference such as `myapp:v2`, while a digest is the SHA-256 content identity of a specific image manifest. Tags can normally be moved or reused, so the same tag can point to different images over time. A digest identifies the exact artifact. In Production I'd use unique tags for human traceability but capture and preferably deploy the digest, so the image I scanned, signed and tested is exactly the image that runs. That's also why I avoid mutable tags like `latest` for Production.”

**Memory line:**
**Tag tells humans which image they mean; digest proves exactly which image it is.**

**Interview trap:**
`imagePullPolicy: Always` does **not** make a mutable tag such as `latest` deterministic.

**Keywords:**
ACR, image tag, digest, SHA-256, immutable artifact, `latest`, OCI manifest, supply chain.

* Why is `latest` dangerous in Production?
* Can two tags point to the same digest?
* Why are signatures and SBOMs better associated with digests?
* How would you capture an ACR digest in a CI pipeline?

### **T34-30. Azure Monitor metrics vs Log Analytics logs?**

**Answer:**

Azure Monitor **metrics** and Log Analytics **logs** are complementary telemetry types optimized for different jobs.

**Metrics** are numeric time-series values collected at intervals—for example CPU percentage, request count, memory utilization, or database DTU usage. They are optimized for fast aggregation, dashboards, near-real-time monitoring, and alerting.

**Logs** are richer timestamped records containing contextual information about events and operations. They are stored in Azure Monitor Logs, commonly in a **Log Analytics workspace**, and queried using **KQL**. Logs are better for detailed investigation and root-cause analysis.

So:

```text
Metrics
→ "Is something wrong?"

Logs
→ "Why is it wrong?"
```

That's a simplification, but it's a very useful operational mental model.

Microsoft currently describes metrics as numerical time-series data optimized for fast detection and alerting, while logs are timestamped structured/free-form records optimized for deeper contextual analysis with Log Analytics and KQL. ([Microsoft Learn][5])

---

## **1. Metrics are time-series data**

A metric has things such as:

```text
Timestamp
Metric name
Numeric value
Dimensions
```

Example:

```text
2026-09-06 10:00
CPU Percentage
82%
VM = vm-api-01
```

Then:

```text
10:01 → 84%
10:02 → 93%
10:03 → 98%
```

This is ideal for:

```text
graphs
thresholds
aggregation
alerting
trend detection
```

---

# **2. Logs contain richer context**

Example application log:

```text
2026-09-06T10:02:31Z
RequestId=abc123
Endpoint=/checkout
Status=500
UserTenant=contoso
Exception=SqlException
DurationMs=2870
```

That gives much more context.

A metric might tell me:

```text
5xx = 17%
```

The logs can tell me:

```text
which endpoints
which dependencies
which exceptions
which versions
which users/regions
```

were involved.

---

# **3. Storage systems differ**

Azure Monitor Metrics uses a specialized:

```text
time-series metrics store
```

optimized for numerical telemetry.

Azure Monitor Logs stores log data in:

```text
Log Analytics workspace
```

built on Azure Data Explorer technology and queryable with KQL. ([Microsoft Learn][5])

This optimization explains their different operational strengths.

---

# **4. Metrics are excellent for fast alerts**

Example:

```text
CPU > 90%
for 5 minutes
```

A metric alert can evaluate efficiently.

Similarly:

```text
HTTP 5xx rate
availability
requests/sec
memory usage
queue depth
```

are natural metric signals.

For a production API, I would frequently alert from:

```text
availability
error rate
latency
saturation
```

metrics.

---

# **5. Logs are better for exploratory investigation**

Suppose alert:

```text
API 5xx > 5%
```

fires.

Then I open Log Analytics and query:

```kusto
AppRequests
| where TimeGenerated > ago(30m)
| where Success == false
| summarize Failures=count() by OperationName
| order by Failures desc
```

Now I know:

```text
/api/checkout
→ majority of failures
```

Then I can correlate:

```text
requests
exceptions
dependencies
```

to identify root cause.

This kind of ad-hoc analysis is where KQL shines.

---

# **6. Metrics usually have lower contextual richness**

A metric might have dimensions:

```text
Region
Instance
StatusCode
```

but it doesn't normally contain the full stack trace or request payload context.

That's intentional.

If metrics contained all log-level context:

```text
cardinality
storage
query cost
```

could become enormous.

Metrics trade context for efficient numerical analysis.

---

# **7. Logs are more flexible but can cost more**

Suppose AKS emits:

```text
100 GB/day
```

of application/container logs.

Log ingestion and retention can become a significant cost.

Metrics generally have a much smaller telemetry footprint.

Therefore good observability doesn't mean:

```text
log absolutely everything forever.
```

It means:

```text
use metrics for aggregate health
+
logs for useful diagnostic detail
+
appropriate retention/filtering
```

---

# **8. Example AKS incident**

Alert:

```text
Pod restart count increased
```

Metric tells me:

```text
something changed
```

Then logs/events tell me:

```text
OOMKilled
```

Application logs reveal:

```text
large payload processing
→ memory allocation spike
```

Flow:

```text
Metric
→ anomaly detected

Logs
→ failure mechanism

Trace
→ request/dependency context
```

Each telemetry type answers a different question.

---

# **9. Log-based metrics also exist**

This is a useful nuance.

Not every “metric-like chart” comes from the native metrics database.

Application Insights and Azure Monitor can derive:

```text
log-based metrics
```

from logs.

For example:

```text
count failed requests
grouped per minute
```

can be computed from log records.

Microsoft distinguishes **standard/preaggregated metrics** from **log-based metrics** created at query time. ([Microsoft Learn][6])

So:

```text
chart looks like a metric
```

does not automatically prove its underlying storage is Azure Monitor Metrics.

---

# **10. Native metric alert vs log-search alert**

### Metric alert

Best when:

```text
signal already exists as metric
```

Example:

```text
CPU > 90%
p95 latency > threshold
```

Benefits:

```text
fast
efficient
simple
```

### Log-search alert

Useful when condition requires:

```text
KQL
correlation
custom log fields
complex filtering
```

Example:

```text
More than 5 OOMKilled Pods
for payment namespace
in 10 minutes
```

depending on collected tables.

# **11. Metrics tell you rate; logs tell you events**

Suppose Storage shows:

```text

↑
```

metric.

Logs may show:

```text
Request A
status 503
operation GetBlob
client IP ...
```

Metrics:

```text
aggregate system behavior
```

Logs:

```text
individual or detailed events
```

That's a very useful distinction.

---

# **12. Metrics can have dimensions**

Don't say metrics contain:

```text

```

Modern Azure metrics can be segmented using dimensions.

For example:

```text

by
ResponseCode

```

depending on service.

Dimensions make metrics much more useful without turning them into logs.

---

# **13. Logs can collect many Azure sources**

A Log Analytics workspace can contain data from:

```text

Application Insights

```

This enables correlation across services.

Microsoft explicitly describes Azure Monitor Logs as the platform where Activity Logs, resource logs, and other telemetry can be collected and analyzed together. ([Microsoft Learn][5])




### Step 2 — Logs/traces

```text

```

```text
→ 1.8 sec
```

Now:

```text
external dependency
```

rather than compute saturation is the likely issue.

Metrics narrowed the incident.

Logs explained it.

| Data shape            | **Numeric time series**   | **Timestamped records**          |
| Storage               | Metrics time-series store | Log Analytics/Azure Monitor Logs |
| Query tool            | Metrics Explorer          | **KQL / Log Analytics**          |
| Fast alerting         | **Excellent**             | Good, more flexible              |
| Root-cause detail     | Limited                   | **Excellent**                    |

### **Interview answer condensed**

> “Azure Monitor metrics are numeric time-series signals such as CPU, request rate or latency, optimized for fast dashboards, aggregation and alerts. Log Analytics works with richer timestamped log records stored in Azure Monitor Logs and queried using KQL, so it's much better for detailed troubleshooting and root-cause analysis. In practice I use metrics to detect that a service is unhealthy and logs to investigate which requests, errors, dependencies or versions caused it. They're complementary rather than competing monitoring approaches.”

**Memory line:**
**Metrics show the shape of the problem; logs give you the context behind it.**

**Interview trap:**
**Log Analytics is a query/analysis experience over Azure Monitor Logs; it is not simply another name for all of Azure Monitor.**

### **T34-31. Activity Log vs resource logs?**

**Answer:**

The easiest way to remember the difference is **control plane versus operations inside the resource**.

The **Azure Activity Log** records subscription/resource **management operations**—things such as creating or deleting a VM, modifying a Key Vault configuration, assigning Policy, changing networking configuration, or a Resource Manager deployment failure. Azure collects it automatically.

**Resource logs** provide service-specific operational telemetry generated **inside an Azure resource**. Examples include Key Vault secret access, database operations, firewall traffic events, Storage requests, or other service-specific events. Resource logs are generally **not collected into a destination automatically**; I configure diagnostic settings to send supported categories to destinations such as a Log Analytics workspace, Storage Account, or Event Hub.

So:

```text
Activity Log
→ "What happened TO the Azure resource?"

Resource logs
→ "What happened INSIDE the resource?"
```

Microsoft's current documentation explicitly describes Activity Log events as Azure Resource Manager/control-plane operations, while resource logs capture service-specific operations inside the resource. Activity Log collection is automatic and retained for 90 days by default, whereas resource logs require diagnostic configuration for collection/routing. ([Microsoft Learn][7])

## **1. Activity Log is the Azure management audit trail**

Examples:

```text
Create VM
Delete Storage Account
Update NSG
Restart VM
Change Key Vault configuration
Terraform deployment failed
```

These are operations against:

```text
Azure Resource Manager
```

or related Azure management/control-plane operations.

Activity Log helps answer:

```text
Who changed it?
What operation?
When?
Against which resource?
Did it succeed?
```

---

# **2. Example Activity Log event**

Suppose someone manually edits an NSG:

```text
10:02
Caller:
alice@company.com

Operation:
Microsoft.Network/networkSecurityGroups/securityRules/write

Resource:
nsg-prod

Status:
Succeeded
```

This is exactly the kind of evidence I would inspect after:

```text
"Networking suddenly broke."
```

because it tells me the **control-plane change history**.

---

# **3. Resource logs describe service-specific runtime activity**

Consider Key Vault.

### Activity Log

Might show:

```text
Key Vault firewall updated
```

or:

```text
Key Vault resource created
```

### Key Vault resource logs

Can contain events related to:

```text
secret retrieved
key operation attempted
authentication/authorization result
client identity
```

depending on supported logging categories.

Microsoft uses Key Vault secret retrieval as a canonical example of a resource/data-plane operation recorded through resource logs rather than the Activity Log. ([Microsoft Learn][8])

---

# **4. Database example**

### Activity Log

```text
SQL server created
Firewall configuration changed
Database SKU changed
```

### SQL resource logs

Potentially:

```text
database query/security events
connection/audit events
service-specific diagnostics
```

depending on which diagnostic/audit categories you've enabled.

So if users say:

```text
"Database query failed at 10:00"
```

Activity Log may tell me whether someone changed the database configuration.

Resource logs are more useful for understanding what happened **inside the database service**.

---

# **5. Activity Log is collected automatically**

This is a major operational distinction.

Azure automatically creates Activity Log entries.

No agent or ordinary resource diagnostic setting is needed just to have the basic Activity Log available.

Microsoft currently retains the Activity Log for:

```text
90 days
```

by default. ([Microsoft Learn][7])

For longer retention/correlation, export it.

---

# **6. Resource logs usually require diagnostic settings**

Creating:

```text
Storage Account
Key Vault
Application Gateway
Firewall
```

does not mean all supported resource log categories are automatically flowing into your Log Analytics workspace.

You typically configure:

```text
Diagnostic Setting
      ↓
selected log categories
      ↓
destination
```

Possible destinations include:

```text
Log Analytics workspace
Storage Account
Event Hub
supported partner destination
```

Microsoft explicitly states that resource logs aren't collected by default and require diagnostic configuration. ([Microsoft Learn][9])

---

# **7. This matters during incident response**

Imagine:

```text
Key Vault outage
```

You want to investigate historical secret-access failures.

You discover:

```text
No Key Vault diagnostic settings
```

Then you may still have:

```text
Activity Log
```

showing:

```text
firewall configuration changed
RBAC/config resource modified
```

but you may not have the detailed historical resource-level access events you expected.

Therefore production observability needs to be configured **before** incidents.

---

# **8. Activity Log can be exported to Log Analytics**

Although Activity Log has its own Azure platform store, you can configure export so entries go into:

```text
Log Analytics workspace
```

where they are queryable, commonly through:

```text
AzureActivity
```

and correlated with other telemetry. ([Microsoft Learn][7])

Example:

```kusto
AzureActivity
| where TimeGenerated > ago(1h)
| where ActivityStatusValue == "Failure"
| project TimeGenerated,
          Caller,
          OperationNameValue,
          ResourceGroup
```

This is useful when correlating:

```text
14:02 Terraform change
        ↓
14:03 application failure
```

---

# **9. Resource logs can also go to Log Analytics**

Example:

```text
Azure Firewall
      ↓
Diagnostic Setting
      ↓
Log Analytics
```

Then KQL can correlate:

```text
Activity Log:
Firewall rule changed at 14:00

Resource logs:
Connections denied starting 14:01
```

That's much stronger than looking at either dataset independently.

---

# **10. Not every resource has the same resource logs**

Activity Log has a relatively common Azure management-event model.

Resource logs are:

```text
service-specific
```

For example:

```text
Key Vault
→ audit-related categories

Application Gateway
→ access/performance/firewall categories

Azure Firewall
→ network/application/DNS/IDPS categories

Storage
→ service-specific request logs
```

The supported categories and schemas vary by resource provider. ([Microsoft Learn][9])

---

# **11. Activity Log does not normally capture ordinary reads**

Activity Log is focused on management operations.

For example:

```text
GET ARM metadata about a VM
```

typically isn't the central use of Activity Log.

The important events are commonly:

```text
create
update
delete
action
policy
service health
resource health
```

Microsoft notes that Activity Log generally focuses on changes/actions rather than normal read operations. ([Microsoft Learn][8])

---

# **12. Control-plane vs data-plane isn't universally one sentence**

The strongest general model is:

```text
Activity Log
→ Azure management/control-plane events

Resource logs
→ service-specific operational events
```

Many resource logs represent data-plane operations, but exact log content depends on the service.

So avoid claiming:

> “Every single data-plane request in every Azure service is automatically in resource logs.”

That's not guaranteed.

You must check:

```text
supported resource log categories
+
diagnostic configuration
```

for the specific service.

# **13. Practical Terraform drift example**

Someone manually changes:

```text
AKS node pool max_count
10 → 30
```

What do I check first?

```text
Activity Log
```

because I want:

```text
Who changed the Azure resource?
When?
What management operation?
```

Then:

```text
terraform plan
```

shows configuration drift.

Resource logs aren't the primary evidence source for that control-plane configuration change.

# **14. Practical Key Vault security example**

Question:

> “Who retrieved `prod-db-password` at 02:00?”

Activity Log alone is not the right primary data source.

I want:

```text
Key Vault resource/audit logs
```

assuming the appropriate diagnostic logging was enabled.

Why?

Because that's:

```text
operation inside the vault/data plane
```

not:

```text
change to the Key Vault ARM resource.
```

# **15. Activity Log includes more than configuration changes**

Activity Log categories can also include platform-level information such as:

```text
Service Health
Resource Health
Policy
Autoscale
Alert
Security
Administrative
```

depending on event type. ([Microsoft Learn][10])

So don't define it as only:

```text
"who edited resource settings"
```

although that is one of its most common operational uses.

# **16. Production logging architecture**

A mature model:

```text
Azure subscriptions
      │
      └── Activity Log
              │
              └── Diagnostic Setting
                     ↓
            Central Log Analytics

Azure resources
      │
      └── Resource logs
              │
              └── Diagnostic Settings
                     ↓
            Central Log Analytics
```

Then:

```text
Control-plane change
+
Runtime/service failure
```

can be correlated in one KQL investigation.

This is very powerful during incidents.

### **Interview answer condensed**

> “The Activity Log is Azure's management-plane audit trail. It records subscription-level resource-management events such as creating a VM, modifying an NSG, changing Key Vault configuration or an ARM deployment failure, and Azure collects it automatically. Resource logs are service-specific logs showing operations inside a resource—for example Key Vault access, database operations or Firewall traffic—and they normally need diagnostic settings to be collected and routed. **Memory line:**
**Activity Log tells you what happened to the Azure resource; resource logs tell you what happened inside it.**

**Interview trap:**
