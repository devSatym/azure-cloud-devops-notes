# **T33-30. How would you prioritize reliability work against feature development?**

**Answer:**

I would prioritize reliability work based on **measured business risk and service objectives**, rather than treating reliability and feature development as two unrelated competing backlogs.

For each important service, I would define SLOs—for example availability, latency, or transaction-success targets—and use the **error budget** to determine how much reliability risk the team can safely accept.

If the service is comfortably meeting its SLO and the error budget is healthy, I would continue shipping features while still investing in high-value reliability improvements. But if we're repeatedly breaching SLOs, consuming the error budget too quickly, having recurring Sev-1/Sev-2 incidents, or carrying security/data-integrity risks, reliability work should take priority until the service returns to an acceptable risk level.

The key is not:

```text
Features
vs
Reliability
```

but:

```text
How much change can we safely introduce
while still meeting the reliability
the business has promised users?
```

I would also avoid reliability gold-plating. A service with a business requirement of 99.9% availability does not automatically need an extremely expensive five-region active-active design.

---

## **1. Start with the business requirement**

Before prioritizing reliability work, ask:

```text
How reliable does this service actually need to be?
```

For example:

### Public payment API

```text
High revenue impact
No practical workaround
Customer-facing
```

might justify:

```text
99.95%+ availability
tight latency SLO
strong DR
```

### Internal weekly reporting tool

```text
Small internal audience
Workaround exists
```

might not justify the same investment.

Reliability architecture should follow **business criticality**, not engineering perfectionism.

---

# **2. Use SLOs instead of saying “make it more reliable”**

Suppose checkout has:

```text
Availability SLO = 99.95%
p95 latency SLO = < 500 ms
Payment success = > 99.5%
```

Now reliability is measurable.

Instead of:

> “AKS needs improvement.”

we can say:

> “Checkout violated its availability SLO three times this month because node capacity was exhausted during deployments.”

That produces much better prioritization.

---

# **3. Error budget provides the balancing mechanism**

If SLO is:

```text
99.9%
```

then the remaining:

```text
0.1%
```

is effectively the allowed unreliability over the measurement window.

Conceptually:

```text
Healthy error budget
      ↓
More room for change
      ↓
Feature delivery continues

Error budget rapidly consumed
      ↓
Reliability risk high
      ↓
Slow risky changes
      ↓
Prioritize reliability
```

An error budget is **not permission to intentionally cause downtime**.

It's a mechanism for balancing release velocity against demonstrated service stability.

---

# **4. Reliability immediately wins for certain risks**

Some reliability/security work shouldn't wait for an error-budget discussion.

Examples:

```text
Active data corruption
Critical security exposure
No recoverable backup
Single point of failure in critical payments
Repeated Sev-1 incident
Expiring credential about to cause outage
```

These create unacceptable business risk.

I would normally prioritize them ahead of optional feature work.

---

# **5. Recurring incidents are a strong signal**

Suppose over six weeks:

```text
Incident 1:
DB connection exhaustion

Incident 2:
same condition

Incident 3:
same condition
```

and every time the team simply:

```text
restarts Pods
```

I would stop accepting that as normal operations.

The recurring reliability work becomes high priority because operational cost is already being paid repeatedly through:

```text
outages
on-call time
lost revenue
engineering interruptions
customer trust
```

Reliability debt behaves very much like technical debt with interest.

---

# **6. Quantify reliability work in business terms**

Instead of proposing:

> “We need to redesign autoscaling.”

I would frame:

```text
Current:
3 capacity incidents/month
~40 minutes impact/month
8 engineer-hours per incident

Proposed:
HPA/CA correction + capacity test

Expected:
remove recurring capacity failure class
```

Now product/business teams can compare the investment against feature value.

---

# **7. Look at toil too**

Some systems are technically available but require:

```text
manual restart every week
manual certificate rotation
manual scaling every morning
manual failover
```

That's operational toil.

Even without a major outage yet, high toil:

```text
consumes engineers
increases human error
slows features
```

Automating recurring work can therefore increase both:

```text
reliability
and
feature velocity
```

Reliability and product delivery are often complementary rather than opposites.

---

# **8. Categorize the reliability backlog**

I might classify reliability work like this:

### Critical

```text
Security/data-integrity risk
No backup/restore capability
Recurring Sev-1
SLO significantly violated
```

Do soon/immediately.

### High-value

```text
Canary deployment
Autoscaling correction
Major alerting gap
DR test
Repeated toil
```

Schedule into near-term engineering work.

### Improvement

```text
Dashboard cleanup
small performance optimization
minor operational convenience
```

Can compete normally with feature work.

This prevents every reliability request from being treated as an emergency.

---

# **9. Don't build reliability blindly**

Suppose application currently achieves:

```text
99.99%
```

and business requires:

```text
99.9%
```

An engineer proposes:

```text
three-region active-active
+
multi-write database
+
complex global failover
```

at huge cost.

I would ask:

```text
What measurable failure are we solving?
What business requirement requires this?
```

More redundancy also creates:

```text
more moving parts
more deployment complexity
more failure modes
higher cost
```

Reliability engineering should optimize the whole system, not maximize the number of redundant services.

---

# **10. Reliability should be part of feature design**

Bad model:

```text
Feature finished
      ↓
"Now make it reliable"
```

Better:

```text
Feature design
├── capacity
├── observability
├── rollback
├── failure behavior
└── SLO implications
```

For example, a new payments feature isn't complete merely because the API code works.

It also needs:

```text
alerts
dashboards
safe rollout
resource sizing
fallback/error behavior
```

where appropriate.

# **11. Example decision**

Suppose product wants:

```text
New recommendation feature
```

but checkout has:

```text
Availability SLO: 99.95%

Current availability: 99.7%

3 recent Sev-1 incidents

Root cause:
DB saturation during traffic spikes
```

I would prioritize:

```text
connection limits
backpressure
query optimization
capacity testing
autoscaling protection
```

before another risky checkout release.

Why?

Because:

```text
New features have limited value
if customers cannot reliably complete checkout.
```

---

# **12. Opposite example**

Suppose:

```text
SLO consistently met
Error budget healthy
No serious incident trend
Recovery procedures tested
```

and engineering proposes six months of reliability redesign to move:

```text
99.96% → 99.999%
```

without a business requirement.

I would probably prioritize features instead.

Reliability work should be proportional to risk.

---

## **A practical decision framework**

```text
Reliability request
       ↓
Does it address security/data integrity?
       ├─ Yes → prioritize highly
       ↓
Are SLOs/error budgets unhealthy?
       ├─ Yes → prioritize reliability
       ↓
Is it causing recurring incidents/toil?
       ├─ Yes → prioritize based on impact
       ↓
Does business require higher reliability?
       ├─ Yes → invest
       ↓
Otherwise
       ↓
Compete normally with feature backlog
```

---

### **Interview answer condensed**

> “I would balance reliability and feature development using business criticality, SLOs, incident history and error budgets. If the service is meeting its SLO with healthy error-budget headroom, we can continue shipping features while steadily investing in reliability. If we're repeatedly violating SLOs, consuming the error budget rapidly, seeing recurring high-severity incidents, or carrying data/security risks, I would prioritize reliability until the risk is reduced. I also wouldn't gold-plate reliability—going from 99.9% to 99.999% can be extremely expensive and should be justified by business requirements. The goal is to ship as fast as we safely can, not maximize either features or reliability in isolation.”

**Memory line:**
**Healthy reliability gives you permission to move fast; exhausted reliability margin means stabilize before adding more risk.**

**Interview trap:**
An error budget is **not a downtime budget that engineers should intentionally spend**.

**Keywords:**
SLO, error budget, reliability debt, toil, business impact, incident frequency, risk, prioritization.

**Likely follow-ups:**

* What would make you temporarily stop feature releases?
* How would you justify reliability work to a product manager?
* Can a system become too reliable for its business requirement?

# **T34-01. Availability Set vs Availability Zone?**

**Answer:**

Both improve Azure VM availability, but they protect against failures at **different physical scopes**.

An **Availability Set** is a logical grouping of VMs inside an Azure region that spreads VMs across **fault domains and update domains**. It mainly reduces correlated failures from underlying hardware/rack issues and planned platform maintenance.

An **Availability Zone** is a physically separate zone within an Azure region, with independent power, cooling, and networking infrastructure. By placing application instances across multiple zones, I get protection against a much larger failure such as an entire datacenter/zone outage.

For new highly available workloads in a region that supports zones, I would generally prefer **Availability Zones**. Microsoft currently states that Availability Sets provide lower resiliency than Availability Zones and recommends zonal/zone-resilient approaches for most workloads. ([Microsoft Learn][1])

---

## **Architecture difference**

### Availability Set

```text
Azure Region
┌─────────────────────────────┐
│      Datacenter scope       │
│                             │
│ Fault Domain 1   FD 2       │
│    VM1            VM2       │
│                             │
│ Update Domain 1  UD 2       │
└─────────────────────────────┘
```

The VMs are separated across underlying hardware groupings.

But they're still vulnerable to some **datacenter-level/shared infrastructure failures**. ([Microsoft Learn][1])

---

### Availability Zones

```text
               Azure Region
┌──────────────────────────────────────┐
│                                      │
│ Zone 1          Zone 2         Zone 3│
│ ┌──────┐        ┌──────┐       ┌──────┐
│ │ VM A │        │ VM B │       │ VM C │
│ └──────┘        └──────┘       └──────┘
│                                      │
│ Separate power/cooling/network       │
└──────────────────────────────────────┘
```

A zone failure might remove VM A, while workloads in zones 2 and 3 continue operating.

Azure describes zones as physically separate locations within a region designed to tolerate local datacenter failures. ([Microsoft Learn][2])

---

## **Fault domains and update domains**

### Fault Domain

Represents groups of infrastructure that can share things such as:

```text
power
network switches
physical hardware
```

Spreading across fault domains reduces correlated hardware failure.

### Update Domain

Represents groups that Azure can update/restart together during planned platform maintenance.

If:

```text
VM1 → Update Domain 1
VM2 → Update Domain 2
```

Azure avoids planned maintenance affecting both groups simultaneously.

Availability Sets currently support up to **3 fault domains and 20 update domains**, depending on infrastructure/region. ([Microsoft Learn][1])

---

## **Failure protection**

### Server/rack failure

Availability Set:

```text
Good protection
```

Availability Zone:

```text
Good protection
```

### Planned host maintenance

Availability Set:

```text
Update Domains help
```

Zones:

```text
VMs already separated physically
```

### Entire datacenter/zone failure

Availability Set:

```text
Not sufficient protection
```

Availability Zones:

```text
Designed for this failure scope
```

That's the most important distinction.

---

## **SLA nuance**

Microsoft's current VM guidance states:

* two or more VMs in an Availability Set qualify for the **99.95% VM connectivity SLA**;
* instances distributed across multiple Availability Zones can qualify for **99.99% VM connectivity SLA**. ([Microsoft Learn][1])

But remember:

```text
VM SLA
≠
application SLA
```

Your application can still fail because:

```text
database single point of failure
bad deployment
DNS failure
shared dependency
application bug
```

---

## **Why Availability Sets still exist**

They remain useful when:

```text
region doesn't support Availability Zones
legacy workload already uses them
very low inter-VM latency is particularly important
```

Microsoft notes Availability Set VMs can have lower VM-to-VM latency because they're typically placed closer together physically. ([Microsoft Learn][1])

For modern designs, however, zones provide the stronger fault-isolation boundary.

---

## **Important architecture detail**

Simply putting:

```text
VM A → Zone 1
VM B → Zone 2
```

isn't enough.

You also need:

```text
Load Balancer / Application Gateway
      ↓
both instances
```

and dependencies that survive the zone failure.

Otherwise:

```text
App tier = zone resilient
Database = single-zone
```

still means:

```text
zone failure
→ application outage
```

High availability is end-to-end.

---

## **Quick comparison**

| Feature                              | Availability Set     | Availability Zone         |
| ------------------------------------ | -------------------- | ------------------------- |
| Scope                                | VM/hardware grouping | Physically separate zones |
| Protects rack/hardware failure       | Yes                  | Yes                       |
| Planned maintenance isolation        | Update Domains       | Physical separation       |
| Protects zone/datacenter failure     | **No**               | **Yes**                   |
| Typical VM SLA pattern               | 99.95%               | 99.99% across zones       |
| Preferred for new critical workloads | Secondary choice     | **Usually yes**           |
| Region support required              | Broad                | Zone-enabled region       |

---

### **Interview answer condensed**

> “Availability Sets and Availability Zones both improve VM availability, but at different failure scopes. An Availability Set spreads VMs across fault domains and update domains so a hardware failure or planned platform maintenance doesn't affect all instances together. Availability Zones are physically separate locations within an Azure region with independent infrastructure, so they also protect against an entire zone or datacenter-level failure. For a new highly available workload in a zone-enabled Azure region, I would generally choose Availability Zones because they provide stronger isolation.”

**Memory line:**
**Availability Set separates VMs across hardware groups; Availability Zones separate them across physical datacenter zones.**

**Interview trap:**
An Availability Set **does not protect against an entire Availability Zone/datacenter failure**.

**Keywords:**
Availability Set, Availability Zone, fault domain, update domain, zone resilience, high availability, SLA.

**Likely follow-ups:**

* What is a fault domain?
* What is an update domain?
* Does using Availability Zones protect against an Azure region failure?
* Why might someone still use an Availability Set?

# **T34-02. Azure Load Balancer vs Application Gateway?**

**Answer:**

The primary difference is the networking layer and the amount of application awareness.

**Azure Load Balancer** is primarily a **Layer 4** load balancer. It distributes TCP or UDP connections based on IP address and port and doesn't understand HTTP URLs, headers, cookies, or host names.

**Azure Application Gateway** is a **regional Layer 7 application delivery service**. It understands HTTP/HTTPS and can perform TLS termination, host-based and path-based routing, cookie-based session affinity, redirects, and Web Application Firewall protection.

So my rule is:

```text
TCP/UDP or simple regional connection distribution
→ Azure Load Balancer

Regional HTTP/HTTPS requiring application-aware routing/WAF
→ Application Gateway
```

Microsoft's current application-delivery guidance makes the same distinction: Load Balancer is Layer 4 TCP/UDP, while Application Gateway is regional Layer 7 with TLS termination, URL routing, and optional WAF. ([Microsoft Learn][3])

---

## **Layer difference**

### Load Balancer

```text
Client
   ↓ TCP/UDP
Azure Load Balancer
   ↓
Backend VM/VMSS
```

It understands:

```text
source IP
destination IP
source port
destination port
protocol
```

It does **not** understand:

```text
/api/orders
Host: shop.example.com
HTTP cookie
JWT
```

---

### Application Gateway

```text
Client
   ↓ HTTPS
Application Gateway
   ↓
Inspect HTTP request
   ↓
Routing decision
   ↓
Backend
```

It can make decisions such as:

```text
/api/*
→ API backend

/images/*
→ image backend

shop.example.com
→ shopping backend

admin.example.com
→ admin backend
```

That's Layer 7 routing.

---

# **1. Protocols**

Azure Load Balancer:

```text
TCP
UDP
```

Application Gateway is designed primarily for web/application protocols including:

```text
HTTP
HTTPS
HTTP/2 client-side
WebSocket
```

Application Gateway is therefore not the normal choice for an arbitrary UDP workload. ([Microsoft Learn][4])

---

# **2. TLS termination**

With Load Balancer:

```text
Client
 ↓ TLS
Load Balancer
 ↓ same TCP stream
Backend
```

The backend application normally handles TLS because Load Balancer isn't operating as an HTTP TLS termination proxy.

With Application Gateway:

```text
Client
 ↓ HTTPS
Application Gateway
 ↓ TLS termination
 ↓
HTTP or HTTPS
Backend
```

This allows centralized:

```text
certificate management
TLS policy
HTTP routing
```

and optionally end-to-end TLS.

---

# **3. WAF**

Azure Load Balancer:

```text
No WAF
```

because it doesn't inspect HTTP application-layer requests.

Application Gateway WAF_v2 can evaluate requests against Web Application Firewall rules.

For example:

```text
SQL injection pattern
XSS pattern
malicious HTTP request
```

can be detected/blocked.

Current Microsoft guidance recommends Application Gateway when a **regional HTTP application needs WAF**. ([Microsoft Learn][3])

---

# **4. Public and internal variants**

Both can participate in private/internal architectures.

### Internal Load Balancer

```text
Private frontend IP
      ↓
VM/AKS/backend
```

Useful for internal TCP/UDP services.

### Private Application Gateway frontend

```text
Private HTTP/HTTPS entry
      ↓
regional internal web application
```

Application Gateway is deployed into a dedicated subnet inside a VNet.

---

# **5. Health probes**

Both use health probes, but they operate differently.

Load Balancer can check endpoint health at transport/application probe level depending configuration.

Application Gateway has application-aware backend health and can probe:

```text
GET /health
```

and use HTTP response behavior when determining backend health.

That can provide richer web-application routing decisions.

---

# **6. AKS example**

Suppose AKS exposes:

```text
TCP-based custom service
```

A Layer 4 LoadBalancer Service may fit:

```text
Client
  ↓
Azure Load Balancer
  ↓
AKS nodes/services
```

For an HTTP web application requiring:

```text
WAF
TLS termination
host routing
path routing
```

Application Gateway or a modern Kubernetes-integrated application delivery option may make more sense.

---

# **7. Application Gateway version nuance**

As of 2026, **Application Gateway v1 is retired**; current designs should use the v2 SKUs such as Standard_v2 or WAF_v2. Microsoft states v1 reached retirement on **April 28, 2026**. ([Microsoft Learn][4])

That's worth knowing for a current Azure interview.

---

## **Example**

Requirements:

```text
Public website
HTTPS
/api → backend A
/images → backend B
WAF required
```

Choose:

```text
Application Gateway WAF_v2
```

because I need Layer 7 awareness.

Different requirement:

```text
Private TCP service
port 1433-like/custom TCP
multiple backend VMs
```

Choose:

```text
Azure Load Balancer
```

because I only need Layer 4 distribution.

---

## **Quick comparison**

| Capability            | Azure Load Balancer   | Application Gateway       |
| --------------------- | --------------------- | ------------------------- |
| Primary layer         | **L4**                | **L7**                    |
| TCP/UDP               | **Yes**               | Not its primary use       |
| HTTP-aware            | No                    | **Yes**                   |
| URL path routing      | No                    | **Yes**                   |
| Host-based routing    | No                    | **Yes**                   |
| TLS termination       | No                    | **Yes**                   |
| WAF                   | No                    | **Yes, WAF_v2**           |
| Scope                 | Regional              | Regional                  |
| Dedicated VNet subnet | No                    | **Yes**                   |
| Typical use           | VMSS, AKS L4, TCP/UDP | Regional web applications |

Microsoft's current comparison likewise characterizes Load Balancer as regional L4 and Application Gateway as regional L7. ([Microsoft Learn][5])

---

### **Interview answer condensed**

> “Azure Load Balancer is mainly a Layer 4 TCP/UDP load balancer. It distributes network connections using IP and port information and doesn't understand URLs, headers, or cookies. Application Gateway is a regional Layer 7 web load balancer that understands HTTP/HTTPS and supports TLS termination, path- and host-based routing, session affinity, and WAF. So I'd use Load Balancer for TCP/UDP or simple regional network distribution, and Application Gateway when a regional web application needs application-aware routing or WAF.”

**Memory line:**
**Load Balancer understands connections; Application Gateway understands web requests.**

**Interview trap:**
Azure Load Balancer **cannot perform URL-path routing or WAF inspection** because it operates at Layer 4.

**Keywords:**
Layer 4, Layer 7, TCP/UDP, Application Gateway, Load Balancer, TLS termination, WAF, path-based routing.

**Likely follow-ups:**

* Can Azure Load Balancer terminate TLS?
* When would you use an internal Load Balancer?
* Application Gateway vs Front Door?
* Can you use Load Balancer and Application Gateway together?

# **T34-03. Application Gateway vs Front Door?**

**Answer:**

Both are Layer 7 application-delivery services for HTTP/HTTPS, and both can provide WAF, TLS termination, and application-aware routing. The major difference is **scope and placement**.

**Azure Application Gateway** is a **regional service deployed into your VNet**. I use it when I need Layer 7 routing to regional/private backends, VNet integration, regional WAF, or application delivery within one Azure region.

**Azure Front Door** is a **global edge service**. Users connect to Microsoft's global edge, and Front Door routes traffic to healthy origins across regions. I use it for global entry, cross-region routing/failover, edge acceleration, CDN/caching, and global WAF.

So:

```text
Regional HTTP routing inside/into a VNet
→ Application Gateway

Global HTTP entry, acceleration,
multi-region routing/failover
→ Azure Front Door
```

And for an important multi-region architecture I may use both:

```text
Users
   ↓
Azure Front Door
   ↓
Region A Application Gateway
or
Region B Application Gateway
   ↓
regional applications
```

Microsoft's current guidance defines Front Door as global and Application Gateway as regional and explicitly supports combining them when both global and regional Layer 7 functions are needed. ([Microsoft Learn][6])

---

## **Architecture difference**

### Application Gateway

```text
             Azure Region
┌─────────────────────────────────┐
│                                 │
│ Application Gateway + WAF       │
│        ↓                        │
│      VNet                       │
│        ↓                        │
│ VM / AKS / private backend      │
│                                 │
└─────────────────────────────────┘
```

It's a **regional application delivery controller** and lives in your VNet.

Microsoft explicitly describes Application Gateway as a dedicated deployment in the customer's VNet. ([Microsoft Learn][4])

---

### Front Door

```text
              Global users
             ↙     ↓      ↘
        Microsoft global edge
                  ↓
            Azure Front Door
             ↙          ↘
        Region A       Region B
        Origin         Origin
```

Front Door sits at Microsoft's edge rather than inside one application VNet.

It can:

```text
route globally
accelerate HTTP/S
cache content
probe origins
fail over between origins/regions
```

([Microsoft Learn][6])

---

# **1. Regional vs global is the key interview distinction**

Application Gateway:

```text
Regional
```

Front Door:

```text
Global
```

Suppose:

```text
App deployed only in Central India
```

and I need:

```text
WAF + TLS + /api routing
```

Application Gateway may be enough.

Suppose:

```text
App in Central India
+
West Europe
+
East US
```

and users should reach the best healthy region.

Front Door is much more appropriate as the global entry point.

---

# **2. Front Door handles cross-region routing**

Example:

```text
India users
  ↓
Region A

Europe users
  ↓
Region B
```

Front Door health probes monitor origins.

If Region A becomes unhealthy:

```text
Front Door
    ↓
healthy Region B
```

can take new traffic according to the configured routing/origin behavior.

Application Gateway by itself is not a global multi-region routing service. ([Microsoft Learn][6])

---

# **3. Application Gateway is closer to regional backend networking**

Suppose backend has:

```text
Private AKS
VMs
internal application
```

Application Gateway can provide regional Layer 7 ingress into that VNet architecture.

Front Door operates globally and therefore uses an origin connectivity model rather than simply becoming another appliance/subnet in your VNet.

Current Microsoft comparison notes that Front Door origins need to be publicly reachable or, for supported configurations, reached through **Private Link with Front Door Premium**. ([Microsoft Learn][7])

---

# **4. Edge acceleration and caching**

Front Door provides edge capabilities such as:

```text
global edge presence
CDN/cache
dynamic site acceleration
global routing
```

Application Gateway isn't a CDN.

If I have:

```text
static web assets
users worldwide
```

Front Door can cache content near users.

Application Gateway would still require traffic to reach the Azure region.

---

# **5. Both can provide WAF**

### Front Door WAF

Protects:

```text
global edge entry
```

before traffic reaches the origin region.

### Application Gateway WAF

Protects:

```text
regional application entry
```

within the regional architecture.

Therefore architecture can be:

```text
Internet
 ↓
Front Door WAF
 ↓
Application Gateway
 ↓
Application
```

But I wouldn't automatically deploy two WAF layers everywhere.

Each additional layer creates:

```text
cost
rule-management complexity
troubleshooting complexity
```

There should be a clear requirement.

---

# **6. Why combine them?**

Microsoft specifically identifies scenarios where both are useful—for example global traffic management at Front Door combined with regional VNet-level routing at Application Gateway. ([Microsoft Learn][6])

Example:

```text
                     Users worldwide
                           ↓
                     Front Door
                       /       \
                      /         \
             Region A            Region B
                 ↓                  ↓
          App Gateway         App Gateway
                 ↓                  ↓
              AKS A                AKS B
```

Front Door responsibilities:

```text
global entry
region selection
global failover
edge acceleration
```

Application Gateway responsibilities:

```text
regional TLS/routing
regional WAF if required
path routing
private backend connectivity
```

/path routing

# **9. Region failure behavior**

Application Gateway in Region A:

```text
Region A fails
      ↓
Application Gateway A fails with region
```

It doesn't magically send users to Region B.

Front Door:

```text
Global service
    ↓
Origin A unhealthy
    ↓
Route to healthy Origin B
```

That's one of the main reasons Front Door appears in multi-region designs.

But remember:

```text
traffic failover
≠
complete DR
```

If Region B's database lacks current data, routing users there doesn't solve the outage.

---

# **10. Protocol scope**

For classic application-delivery scenarios:

```text
Application Gateway
→ regional web/app routing

Front Door
→ global HTTP/S application delivery
```

For arbitrary regional TCP/UDP load balancing, you should be thinking about:

```text
Azure Load Balancer
```

rather than forcing either service into a use case it isn't designed for.

---

## **Quick comparison**

| Capability                       | Application Gateway          | Azure Front Door                         |
| -------------------------------- | ---------------------------- | ---------------------------------------- |
| Layer                            | L7                           | L7                                       |
| Scope                            | **Regional**                 | **Global**                               |
| Placement                        | **Inside VNet**              | **Microsoft edge**                       |
| WAF                              | Yes                          | Yes                                      |
| TLS termination                  | Yes                          | Yes                                      |
| Path/host routing                | Yes                          | Yes                                      |
| Global multi-region routing      | No                           | **Yes**                                  |
| Regional private-backend ingress | **Strong fit**               | Via supported origin/Private Link design |
| CDN/edge caching                 | No                           | **Yes**                                  |
| Region failover routing          | Not by itself                | **Yes**                                  |
| Typical role                     | Regional application ingress | Global application entry point           |

Microsoft's current application-delivery guide summarizes the same split: Application Gateway is regional Layer 7, while Front Door is global Layer 7 with CDN and multiregion origin health/routing. ([Microsoft Learn][5])

---

### **Interview answer condensed**

> “Application Gateway and Front Door are both Layer 7 HTTP/S application-delivery services, but Application Gateway is regional and deployed into a VNet, while Front Door is a global edge service. I use Application Gateway for regional WAF, TLS termination and path/host routing to application backends, especially when VNet integration matters. I use Front Door when I need a global entry point, edge acceleration and caching, and routing or failover across multiple Azure regions. For a large multi-region application I may combine them—Front Door selects the healthy region globally, and Application Gateway handles regional Layer 7 routing inside each region.”

**Memory line:**
**Application Gateway is regional VNet ingress; Front Door is global edge ingress.**

**Interview trap:**
Application Gateway by itself **does not provide global cross-region failover**, and Front Door routing traffic to a healthy region does not automatically make your **data layer** multi-region resilient.
