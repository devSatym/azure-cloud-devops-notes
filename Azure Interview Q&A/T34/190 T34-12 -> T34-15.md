# **T34-12. System-assigned vs user-assigned managed identity?**

**Answer:**

Both are Microsoft Entra managed identities that let Azure workloads authenticate to Entra-enabled services **without storing client secrets**, but the main difference is their **lifecycle and reuse**.

A **system-assigned managed identity** is created directly on one Azure resource and its lifecycle is tied to that resource. If I delete the VM, App Service, or other resource, Azure deletes that managed identity as well.

A **user-assigned managed identity** is created as a separate Azure resource. Its lifecycle is independent, and I can attach the same identity to one or multiple supported Azure resources.

So I normally think:

```text
System-assigned
→ identity belongs to one resource
→ lifecycle follows that resource

User-assigned
→ identity exists independently
→ can be prepared/reused across resources
```

Current Microsoft guidance recommends **user-assigned managed identities for many/most scenarios**, particularly when identities and role assignments need to exist before workloads are created or when several resources need the same permissions. System-assigned identities remain a good choice when each resource should have a unique identity whose permissions disappear with that resource. ([Microsoft Learn][1])

---

## **How system-assigned identity works**

Suppose I enable it on an App Service:

```text
App Service
    │
    └── System-assigned MI
             │
             ↓
       Entra service principal
             │
       Azure RBAC role
             │
             ↓
          Key Vault
```

Conceptually:

```text
Create App Service
        ↓
Enable system-assigned identity
        ↓
Azure creates identity in Entra
        ↓
Grant that identity permission
        ↓
Application obtains short-lived tokens
```

If I delete the App Service:

```text
App Service deleted
      ↓
System-assigned identity deleted
```

The two lifecycles are coupled. ([Microsoft Learn][2])

---

# **1. User-assigned identity has an independent lifecycle**

A user-assigned identity is its own Azure resource:

```text
User-assigned MI
      │
      ├── VM1
      ├── VM2
      └── App Service
```

If VM1 is deleted:

```text
VM1 deleted
```

the identity remains:

```text
User-assigned MI
     ✓
```

and VM2 can continue using it.

That's a major operational difference.

---

# **2. User-assigned identity can be created before the workload**

This matters a lot for Terraform and CI/CD.

Suppose a deployment needs:

```text
App Service
   ↓
Key Vault Secrets User
   ↓
Key Vault
```

With a user-assigned identity I can do:

```text
1. Create managed identity
2. Grant Key Vault role
3. Create App Service
4. Attach identity
5. Application starts with access ready
```

With a system-assigned identity:

```text
1. Create App Service
2. Azure creates identity
3. Obtain principal ID
4. Create role assignment
```

The identity doesn't exist until the workload resource exists.

Microsoft specifically identifies this ability to **pre-authorize user-assigned identities** as an operational advantage. ([Microsoft Learn][1])

---

# **3. System-assigned gives very clean one-resource identity**

Imagine:

```text
vm-orders-01
```

needs:

```text
Storage Blob Data Reader
```

and no other workload should share its identity.

System-assigned is clean:

```text
VM
 ↓
unique identity
 ↓
specific role
```

When VM disappears:

```text
identity disappears
```

as well.

This reduces orphaned identities.

---

# **4. User-assigned can reduce role-assignment sprawl**

Imagine 20 worker instances all legitimately require exactly:

```text
Storage Blob Data Reader
→ one Storage Account
```

With separate system-assigned identities:

```text
Worker1 identity → role
Worker2 identity → role
Worker3 identity → role
...
Worker20 identity → role
```

Potentially:

```text
20 identities
20 role assignments
```

With a shared user-assigned identity:

```text
           shared-worker-mi
             /    |    \
            /     |     \
       Worker1 Worker2 ... Worker20
               │
               ↓
       one permission model
```

Microsoft specifically calls out reduced administrative overhead as a user-assigned identity benefit. ([Microsoft Learn][1])

---

# **5. But sharing one identity increases blast radius**

This is the trade-off.

Suppose:

```text
10 applications
→ same user-assigned identity
→ Key Vault Secrets User
```

If App 1 is compromised, it can act with the same Azure permissions as the shared identity.

You lose workload-level distinction:

```text
Azure sees:
shared-mi
```

rather than:

```text
app1-mi
app2-mi
app3-mi
```

So I would **not share identities purely to reduce administration** if workloads have different trust boundaries.

Least privilege is more important than minimizing identity count.

---

# **6. Auditability differs**

With system-assigned:

```text
VM-A
→ identity-A

VM-B
→ identity-B
```

An Azure log showing:

```text
principal = identity-A
```

more directly identifies which resource acted.

With shared user-assigned:

```text
VM-A
VM-B
VM-C
     ↓
same identity
```

Azure sees the same principal for all three.

Microsoft's current guidance specifically identifies system-assigned identity as advantageous when you need to know which individual resource performed an action. ([Microsoft Learn][1])

---

# **7. Credentials are managed by Azure in both cases**

Neither normally requires you to store:

```text
CLIENT_SECRET
certificate password
long-lived token
```

in application configuration.

Both can obtain:

```text
short-lived Entra access token
```

through Azure's managed identity mechanisms.

That's why managed identities are strongly preferred to manually managed credentials for supported Azure workloads.

---

# **8. Authentication is not authorization**

Enabling:

```text
System-assigned MI = On
```

does not automatically give:

```text
Key Vault access
Storage access
SQL access
```

You still need appropriate authorization.

For example:

```text
App Service
   ↓
Managed Identity
   ↓ authentication
Entra ID
   ↓
Storage
   ↓ authorization
Storage Blob Data Reader
```

If token acquisition succeeds but Storage returns:

```text
403
```

I inspect:

```text
RBAC/data-plane permissions
```

not whether the identity exists.

---

# **9. Example selection**

### Scenario A — one VM with unique access

```text
VM
→ one Key Vault
```

I'd consider:

```text
System-assigned
```

because:

* unique identity,
* lifecycle tied to VM,
* clean deletion.

---

### Scenario B — blue-green App Service environments

```text
Blue App Service
Green App Service
```

Both need identical Key Vault permissions.

If I use a user-assigned identity:

```text
payment-app-mi
     │
 ┌───┴────┐
Blue     Green
```

I can prepare permissions once and switch infrastructure without recreating RBAC every time.

That's often operationally attractive.

---

# **10. Terraform implications**

With user-assigned identity:

```hcl
resource "azurerm_user_assigned_identity" "app" {
  ...
}
```

I can reference:

```text
principal_id
client_id
```

and configure RBAC independently.

With system-assigned:

```text
resource created
      ↓
identity generated
      ↓
principal ID becomes available
      ↓
role assignment created
```

Both work with IaC, but user-assigned identity often gives cleaner dependency ordering for larger platforms.

---

## **Quick comparison**

| Characteristic                   | System-assigned      | User-assigned        |
| -------------------------------- | -------------------- | -------------------- |
| Created on workload resource     | **Yes**              | No                   |
| Separate Azure resource          | No                   | **Yes**              |
| Lifecycle tied to workload       | **Yes**              | No                   |
| Survives workload deletion       | No                   | **Yes**              |
| Can attach to multiple resources | No                   | **Yes**              |
| Can pre-create identity/RBAC     | Limited by lifecycle | **Yes**              |
| Per-resource audit identity      | **Strong**           | Less clear if shared |
| Good for shared permission model | Less efficient       | **Strong**           |
| Secret management required       | No                   | No                   |

---

### **Interview answer condensed**

> “Both system-assigned and user-assigned managed identities provide secretless Entra authentication. A system-assigned identity belongs to one Azure resource and is created and deleted with that resource, which is useful when each workload should have a unique identity. A user-assigned identity is a standalone Azure resource, can be created and authorized in advance, can survive workload replacement, and can be attached to multiple supported resources. I would choose based primarily on lifecycle, deployment ordering, reuse and security boundaries—not simply whichever creates fewer identities.”

**Memory line:**
**System-assigned follows the resource; user-assigned lives independently of the resource.**

**Interview trap:**
Sharing one user-assigned identity across many applications reduces administration but also means those applications share the **same Azure authorization identity and blast radius**.

**Keywords:**
system-assigned identity, user-assigned identity, lifecycle, Microsoft Entra ID, Azure RBAC, principal ID, secretless authentication.

**Likely follow-ups:**

* Which identity would you choose for a blue-green deployment?
* Does deleting a VM delete its system-assigned identity?
* Can multiple VMs share a user-assigned identity?
* Does enabling Managed Identity automatically give Key Vault access?

# **T34-13. Managed identity vs service principal?**

**Answer:**

A managed identity and a service principal are closely related, but they are not the same operational model.

A **service principal** is a Microsoft Entra identity representing an application, automation process, or service in a tenant. It can authenticate using mechanisms such as a client secret, certificate, or federation, and it can be used by workloads that run either inside or outside Azure.

A **managed identity** is an Azure-managed identity for supported Azure resources. Internally, it is represented in Entra by a **special type of service principal**, but Azure manages its credential lifecycle for me, so my application doesn't need to store or rotate credentials.

Therefore:

```text
Managed Identity
→ best for supported workloads running in Azure
→ Azure manages credentials

Service Principal
→ broader application identity
→ works outside Azure too
→ credential/federation configuration is managed by you
```

Microsoft recommends Managed Identity for Azure-hosted services when possible and service principals where Managed Identity isn't applicable, such as many workloads running outside Azure. ([Microsoft Learn][3])

---

## **Relationship internally**

This distinction is worth understanding.

Conceptually:

```text
Microsoft Entra ID

Service principals
├── normal application SP
└── ManagedIdentity-type SP
```

Microsoft explicitly describes managed identities internally as **service principals of a special type**. ([Microsoft Learn][2])

So saying:

> “Managed Identity has nothing to do with service principals.”

would be incorrect.

The difference is primarily:

```text
how the identity is provisioned
how credentials are managed
where it can be used
```

---

# **1. Traditional service-principal flow**

Suppose GitHub or an on-prem application authenticates to Azure using a client secret:

```text
Application
    ↓
client ID
client secret
tenant ID
    ↓
Microsoft Entra token endpoint
    ↓
access token
    ↓
Azure Resource Manager
```

You must manage:

```text
secret creation
secure storage
rotation
expiration
revocation
```

unless federation/certificates remove some of that burden.

---

# **2. Managed Identity flow**

Azure VM:

```text
Application
     ↓
Azure managed identity endpoint
     ↓
Azure-managed identity
     ↓
Microsoft Entra ID
     ↓
short-lived access token
     ↓
Key Vault / Storage / SQL
```

Application code does not need:

```text
CLIENT_SECRET
```

Azure manages the underlying identity credentials.

That is the major operational advantage.

---

# **3. Service principal does not necessarily mean client secret**

This is an important modern interview nuance.

People often say:

```text
Service Principal
=
client ID + client secret
```

That's too simplistic.

A service principal can participate in authentication using:

```text
client secret
certificate
federated identity/OIDC
```

depending on application design.

For example:

```text
GitHub Actions
    ↓
OIDC token
    ↓
federated identity credential
    ↓
Entra application/service principal
    ↓
Azure token
```

uses a service principal **without storing a client secret**.

So:

```text
Managed Identity vs Service Principal
```

is not simply:

```text
secretless vs secret
```

anymore.

---

# **4. Workload location is a major decision factor**

Suppose application runs:

```text
Azure App Service
```

and accesses:

```text
Azure Storage
```

I'd prefer:

```text
Managed Identity
```

because Azure supports the identity lifecycle.

Suppose automation runs:

```text
On-prem Jenkins
```

or:

```text
GitHub-hosted runner
```

A normal Azure Managed Identity isn't generally the direct workload identity because the compute isn't an Azure resource supporting that managed identity mechanism.

I might use:

```text
Service principal
+
OIDC federation
```

instead.

Microsoft's current service-account guidance makes this Azure-hosted versus externally hosted distinction explicitly. ([Microsoft Learn][3])

Classic scenario:

```text

```

Token acquisition succeeds.

Result:

A service principal can represent:

```text

```

For Azure workloads:

```text

       ↓ preferred

```

### **Interview answer condensed**

> “A service principal is an Entra identity representing an application or automation process. A managed identity is effectively a special Azure-managed type of service principal whose credentials Azure manages automatically for supported Azure resources. If my application runs on Azure and supports Managed Identity, I prefer it because I don't need to store, rotate or protect application credentials. For workloads outside Azure, such as GitHub Actions or on-prem automation, I'd typically use a service principal, preferably with OIDC federation rather than a long-lived secret. Both still need the correct Azure RBAC authorization.”

**Memory line:**
**A managed identity is an Azure-managed application identity; a service principal is the broader Entra application identity model.**

**Interview trap:**
A service principal **does not always require a client secret**—modern service principals can use OIDC/federated credentials.

# **T34-14. Azure RBAC vs Entra directory roles?**

**Answer:**

Azure RBAC and Microsoft Entra directory roles are two different authorization systems protecting two different resource planes.

**Azure RBAC** controls access to **Azure resources** such as subscriptions, resource groups, VMs, VNets, Storage Accounts, AKS, and Key Vault. Roles are assigned to security principals at scopes such as management group, subscription, resource group, or individual resource.

**Microsoft Entra roles** control administration of **Microsoft Entra directory resources**, such as users, groups, enterprise applications, app registrations, authentication methods, and directory configuration.

For example:

```text
Azure Contributor
→ can manage Azure resources
→ cannot automatically create Entra users

User Administrator
→ can manage Entra users
→ cannot automatically modify an Azure VM
```

Microsoft explicitly describes these as separate authorization systems with separate stores and policy-decision points. ([Microsoft Learn][4])

---

## **Two different planes**

```text
                   Microsoft Entra tenant
                          │
             ┌────────────┴─────────────┐
             │                          │
     Directory resources          Azure resources
             │                          │
       Entra roles                 Azure RBAC
             │                          │
    Users / Groups / Apps      MG / Subscription / RG
                                    / Resources
```

The identities often come from the same Entra tenant.

But authorization is evaluated by different systems.

---

# **1. Azure RBAC controls Azure Resource Manager access**

Examples:

```text
Owner
Contributor
Reader
Virtual Machine Contributor
Network Contributor
Key Vault Secrets User
Storage Blob Data Contributor
```

The basic role-assignment model is:

```text
Security principal
+
Role definition
+
Scope
```

For example:

```text
payments-team
+
Contributor
+
rg-payments-prod
```

Azure then determines whether an attempted resource operation is authorized. Microsoft documents this RBAC evaluation through applicable role assignments, deny assignments, scope, and optional conditions. ([Microsoft Learn][5])

---

# **2. Entra directory roles control directory administration**

Examples include:

```text
Global Administrator
User Administrator
Application Administrator
Authentication Administrator
Groups Administrator
```

These govern directory operations such as:

```text
create user
reset authentication method
manage app registration
manage enterprise application
manage groups
```

They don't automatically grant access to:

```text
VMs
VNets
AKS
Storage
```

---

# **3. Contributor is not a directory admin**

Suppose:

```text
Alice
→ Contributor
→ Subscription A
```

Alice can manage many Azure resources in that subscription.

But she cannot therefore automatically:

```text
create Entra users
reset another user's password
register privileged directory applications
```

Those operations fall under Entra directory authorization.

---

# **4. Global Administrator does not automatically mean Azure subscription Owner**

This is a classic interview trap.

Suppose:

```text
Bob
→ Global Administrator
```

Global Administrator provides very powerful **Entra tenant** administration.

That does **not inherently mean** Bob already has:

```text
Owner
→ every Azure subscription
```

Azure resource access is controlled separately by Azure RBAC.

There is a controlled **elevate access** capability whereby a Global Administrator can elevate to gain User Access Administrator at the root scope for Azure resources, but that is an explicit elevation operation—not automatic everyday Owner access.

The high-level separation between directory roles and Azure resource roles remains fundamental. ([Microsoft Learn][4])

---

# **5. Scope models differ**

### Azure RBAC

Typical hierarchy:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Resource
```

Assignment can inherit downward.

Example:

```text
Reader
at subscription
```

typically means read access across resources below that subscription unless narrower mechanisms affect it.

---

### Entra roles

Directory-role scopes can include:

```text
Tenant
Administrative Unit
specific directory object
```

depending on the role and scenario. ([Microsoft Learn][4])

So they're not just different role names over the same scope hierarchy.

---

# **6. Control plane vs data plane nuance**

Don't oversimplify:

```text
Azure RBAC
= control plane only
```

because Azure RBAC can also authorize **data-plane access for supported Azure services**.

For example:

```text
Storage Blob Data Reader
```

allows blob data access.

```text
Key Vault Secrets User
```

can authorize secret data operations under the Key Vault RBAC model.

So better:

> Azure RBAC governs Azure resource access and, for supported services, can govern data-plane operations too.

Entra directory roles govern directory administration.

---

Alice has:

```text

→ Storage Account
```

Can she necessarily read every blob?

Not automatically.

Contributor primarily grants resource-management actions and excludes many data-plane operations.

She may need:

```text

```

for blob contents.

That's still **Azure RBAC**, but it's a data-plane role.

This distinction often appears in interviews.

# **8. Example: creating an App Service using an Entra application**

You might need two different authorization systems.

Engineer needs:

```text
Application Administrator
```

or suitable Entra permission to manage an application registration.

Pipeline identity needs:

```text
Contributor
```

at a specific Azure Resource Group to deploy App Service.

Those are independent authorizations.

Microsoft Entra Privileged Identity Management can be used with:

```text

```

and eligible Azure RBAC roles.

Example:


### **Interview answer condensed**

> “Azure RBAC controls authorization to Azure resources, while Microsoft Entra directory roles control administration of directory objects. For example, Contributor on a subscription lets me manage many Azure resources but doesn't make me a User Administrator in Entra. Likewise, Global Administrator is a highly privileged Entra role but doesn't automatically make the user Owner of every Azure subscription. I also remember that Azure RBAC can cover some service data-plane access through roles such as Storage Blob Data Reader.”

**Memory line:**
**Azure RBAC answers “what Azure resources can you manage?”; Entra roles answer “what directory objects can you administer?”**

**Interview trap:**
**Global Administrator does not automatically equal Azure subscription Owner**, and Azure Contributor does not make someone an Entra directory administrator.

**Keywords:**
Azure RBAC, Entra roles, Contributor, Owner, Global Administrator, directory, scope, control plane, data plane.

# **T34-15. Azure Policy vs RBAC?**

**Answer:**

Azure RBAC and Azure Policy are both governance controls, but they answer fundamentally different questions.

**Azure RBAC asks:**

> **Who is allowed to perform which action at which scope?**

For example:

```text
Developer
→ Contributor
→ Dev resource group
```

allows that developer to create or modify Azure resources within that scope.

**Azure Policy asks:**

> **What resource configurations are allowed or considered compliant?**

For example:

```text
Storage Accounts
must disable public access
```

or:

```text
Resources
must deploy only in approved regions
```

Even if a user has RBAC permission to create a resource, Azure Policy can still reject the request if the resulting resource would violate an enforced policy.

So:

```text
RBAC
→ WHO can do WHAT

Policy
→ WHAT configuration is allowed
```

Microsoft's current Azure Policy documentation makes exactly this distinction: RBAC controls user actions, while Policy evaluates resource state and business rules regardless of who made the change. ([Microsoft Learn][6])

```text
                    ▼
             Resource Provider
                    │
                    ▼
               Azure resource
```

Both checks can matter.

Having permission isn't enough if the requested state violates policy.

---

# **1. RBAC example**

Developer gets:

```text
Contributor
→ rg-dev
```

Can:

```text
create VM
modify VNet
deploy App Service
```

within the permitted role actions/scope.

But cannot access another resource group if no applicable assignment exists.

RBAC evaluates:

```text
Principal
Role
Scope
Action
```

Microsoft's RBAC model evaluates role and deny assignments at the target scope to determine whether the requested action is authorized. ([Microsoft Learn][5])

---

# **2. Policy example**

Company rule:

```text
Allowed regions:
Central India
South India
```

Developer has:

```text
Contributor
→ subscription
```

Attempts:

```text
Create VM
Location = East US
```

RBAC:

```text
Contributor
→ VM create allowed
```

Policy:

```text
East US
→ not approved
→ DENY
```

Final result:

```text
deployment fails
```

because authorization and compliance are separate.

---

# **3. Owner can still be blocked by Policy**

This is probably the biggest interview trap.

Suppose Alice:

```text
Owner
→ subscription
```

Policy says:

```text
Public Storage
→ DENY
```

Alice creates:

```text
Storage Account
public network/access configuration prohibited
```

Policy can deny the resource operation even though her RBAC role includes permission to perform the management action. Microsoft explicitly notes that Policy continues to enforce resource state even when the caller is otherwise authorized by RBAC. ([Microsoft Learn][6])

Owner privilege does not mean:

```text
ignore governance controls
```

---

# **4. Policy isn't normally identity-specific authorization**

Suppose requirement:

> Developers can modify Dev but cannot modify Production.

That's primarily:

```text
Azure RBAC
```

Example:

```text
Developers
→ Contributor in Dev
→ Reader in Prod
```

Don't try to implement this merely with:

```text
Azure Policy
```

because the main question is:

```text
Who can perform writes?
```

Microsoft explicitly says that when control depends on **user information/action authorization**, RBAC is the appropriate mechanism. ([Microsoft Learn][6])

---

# **5. Policy effects**

Azure Policy can do much more than simply allow/deny.

Common effects include:

```text
Audit
Deny
Modify
DeployIfNotExists
AuditIfNotExists
```

depending on the policy scenario.

### Audit

```text
Resource created
      ↓
non-compliant
      ↓
allowed
      ↓
compliance/Activity Log evidence
```

Microsoft states that `audit` marks non-compliance without blocking the request. ([Microsoft Learn][7])

---

### Deny

```text
Bad resource configuration
      ↓
Policy
      ↓
request blocked
```

Useful for guardrails such as:

```text
No public IPs in secure subscription
Only approved regions
Required security setting
```

where supported by appropriate resource aliases/policy definitions.

---

### Modify

Policy can modify supported properties/tags during creation/update and can remediate existing resources with a managed identity where applicable. ([Microsoft Learn][8])

Example:

```text
Missing tag:
CostCenter
     ↓
Policy Modify
     ↓
add required tag
```

---

### DeployIfNotExists

Can deploy a related resource/configuration when required conditions aren't satisfied.

Typical governance patterns include automatically ensuring required monitoring or related resources exist, subject to the specific built-in/custom definition.

---

# **6. Existing resources and Policy**

Suppose I assign:

```text
Policy:
Storage public access prohibited
```

today.

Existing Storage Accounts may become:

```text
Non-compliant
```

but an assignment does not necessarily magically repair every existing resource.

Depending on policy effect:

```text
Audit
→ report

Modify / DeployIfNotExists
→ remediation task may correct supported cases

Deny
→ stops future non-compliant create/update requests
```

This distinction is important.

Policy has both:

```text
preventive
+
compliance assessment/remediation
```

roles.

---

# **7. Policy operates over ARM/resource-provider properties**

Azure Policy evaluates:

```text
resource properties
resource type
location
tags
related resource configuration
```

and supported provider-specific data modes.

It isn't simply:

```text
another role assignment system
```

Microsoft describes Policy as evaluating resource state against business rules. ([Microsoft Learn][6])

---

# **8. RBAC doesn't ensure configuration compliance**

Suppose security team gives Terraform:

```text
Contributor
```

at Prod RG.

That tells Azure:

```text
Terraform may create resources.
```

It doesn't automatically guarantee Terraform creates:

```text
private Storage
approved SKU
required diagnostics
approved locations
```

Policy supplies that additional guardrail.

---

# **9. Policy doesn't replace least privilege**

Suppose developer is:

```text
Owner
```

and you think:

> “It's okay because Policy will block dangerous things.”

Bad design.

Policy definitions will never represent every undesirable action or configuration.

Use:

```text
least-privilege RBAC
+
Policy
```

together.

Example:

```text
Developer
→ Reader in Prod

Pipeline
→ Contributor in Prod

Policy
→ prohibit public SQL
→ require approved regions
```

That's defense in depth.

---

# **10. Management Group scope makes Policy powerful**

Enterprise structure:

```text
Tenant Root
   ↓
Management Group: Corp
   ├── Prod Subscription A
   ├── Prod Subscription B
   └── Prod Subscription C
```

Assign security policy at:

```text
Corp management group
```

and relevant descendant subscriptions/resources are evaluated according to scope, exclusions, and exemptions.

Azure Policy scopes follow the ARM hierarchy and support exclusions and tracked exemptions. ([Microsoft Learn][9])

This lets platform teams enforce standards across many subscriptions.

---

# **11. Policy exemption vs weakening the policy**

Suppose one legacy application temporarily cannot comply.

Bad:

```text
Disable policy for entire company
```

Better where justified:

```text
specific exemption
+
business justification
+
expiry date
```

Azure Policy supports exemptions that can be tracked and can include expiration. ([Microsoft Learn][9])

That creates much better governance.

---

# **12. Policy can also block deletion in a specific way**

Current Azure Policy includes:

```text
denyAction
```

whose supported action is currently:

```text
DELETE
```

for applicable resources. ([Microsoft Learn][10])

But don't confuse that feature with RBAC.

RBAC still primarily decides:

```text
is this principal authorized
to perform this operation?
```

while Policy can add governance restrictions at scale.

---

# **13. Troubleshooting a failed deployment**

Terraform says:

```text
403
RequestDisallowedByPolicy
```

I don't immediately grant the deployment identity:

```text
Owner
```

That likely won't solve it.

I inspect:

```text
policy assignment
policy definition
failed expression
requested resource properties
```

Then either:

```text
fix Terraform so resource complies
```

or, if there is a legitimate exception:

```text
use approved exemption process
```

This is very different from an RBAC authorization error such as:

```text
Microsoft.Network/virtualNetworks/write
is not authorized
```

which points toward role/scope.

## **Practical example**

Requirement:

```text
Developers:
can build resources in Dev

Production:
pipeline only

All environments:
Storage must block anonymous public Blob access
```

Use:

### RBAC

```text
Developer
→ Contributor
→ Dev

Developer
→ Reader
→ Prod

Prod pipeline identity
→ Contributor
→ Prod
```

### Azure Policy

```text
Storage configuration:
anonymous public Blob access
→ DENY
```

RBAC controls:

```text
who may make changes
```

Policy controls:

```text
what kind of resource state those authorized identities may create.
```

Perfect complementary use.

## **Quick comparison**

| Characteristic                               | Azure RBAC           | Azure Policy               |
| -------------------------------------------- | -------------------- | -------------------------- |
| Main question                                | **Who can do what?** | **What state is allowed?** |
| Identity-aware authorization                 | **Yes**              | Not its main purpose       |
| Principal + role + scope                     | **Yes**              | No                         |
| Resource compliance                          | No                   | **Yes**                    |
| Can deny authorized user's bad configuration | N/A                  | **Yes**                    |
| Audit compliance                             | Limited purpose      | **Core capability**        |
| Modify/remediate resources                   | Not itself           | **Supported effects**      |
| Management-group governance                  | Yes via RBAC scope   | **Yes**                    |
| Best used together                           | **Yes**              | **Yes**                    |

---

### **Interview answer condensed**

> “Azure RBAC controls who can perform which actions at which Azure scope, while Azure Policy controls what resource configurations are allowed or compliant. For example, Contributor might authorize a developer to create a Storage Account, but Policy can still deny that deployment if the account violates the organization's public-access policy. So I use RBAC for least-privilege authorization and Policy for configuration guardrails, compliance, auditing and remediation. I don't use Policy instead of RBAC to decide whether developers can write to Production, and I don't assume Owner can automatically bypass a Policy deny.”

**Memory line:**
**RBAC controls the actor; Policy controls the acceptable resource state.**

**Interview trap:**
Giving someone **Owner does not automatically bypass an Azure Policy deny**, and Policy is not a replacement for proper least-privilege RBAC.
