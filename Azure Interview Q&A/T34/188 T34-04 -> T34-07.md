# **T34-04. Front Door vs Traffic Manager?**

**Answer:**

Both are global Azure traffic-distribution services, but they work very differently.

**Azure Front Door** is a **global Layer 7 HTTP/HTTPS reverse proxy**. Client connections terminate at Microsoft's edge, Front Door can inspect HTTP requests, apply WAF policies, terminate TLS, cache content, accelerate traffic, perform path or host-based routing, and then open a separate connection to the selected backend.

**Azure Traffic Manager**, on the other hand, is a **DNS-based global traffic manager**. It doesn't proxy or inspect the application traffic. When a client performs DNS resolution, Traffic Manager returns the DNS record of the selected endpoint, and the client then connects directly to that endpoint.

So my rule is:

```text
Global web application
HTTP/HTTPS + WAF + acceleration + L7 routing
→ Azure Front Door

Global traffic distribution
DNS-based routing
possibly non-HTTP workloads
→ Traffic Manager
```

Microsoft's current guidance says that for most architectures you would normally choose either Front Door or Traffic Manager rather than combine both. Traffic Manager directs clients through DNS, whereas Front Door actually terminates the client's connection at Microsoft's edge. ([Microsoft Learn][1])

---

## **Core architecture difference**

### Azure Front Door

```text
User
 ↓ HTTPS
Microsoft Edge PoP
 ↓
Azure Front Door
 ├─ TLS termination
 ├─ WAF
 ├─ HTTP routing
 ├─ caching
 └─ health-based origin selection
 ↓
Origin
```

Traffic passes **through Front Door**.

It is effectively a global reverse proxy.

---

### Traffic Manager

```text
User
 ↓
DNS query
 ↓
Traffic Manager
 ↓
DNS response:
app-eastus.example.com
 ↓
User connects DIRECTLY
to app-eastus.example.com
```

Application traffic does:

```text
User → endpoint
```

not:

```text
User → Traffic Manager → endpoint
```

That's the single most important distinction.

Microsoft explicitly describes Traffic Manager as DNS-based; it doesn't directly handle application traffic. ([Microsoft Learn][2])

---

## **1. Layer 7 awareness**

Front Door understands HTTP/S constructs such as:

```text
Host
URL path
headers
cookies
HTTP status
TLS
```

Therefore I can do:

```text
/api/*
→ API origin group

/images/*
→ static origin

shop.example.com
→ ecommerce origin
```

Traffic Manager cannot inspect:

```text
/api
Host header
cookie
JWT
```

because it only influences **DNS resolution**.

---

# **2. WAF**

Front Door can integrate:

```text
Azure Web Application Firewall
```

at the global edge.

That gives protection against:

```text
SQL injection
XSS
path traversal
bot/malicious HTTP patterns
```

before traffic reaches the origin.

Traffic Manager has:

```text
No WAF
```

because the user traffic doesn't pass through Traffic Manager.

---

# **3. Global acceleration**

Front Door can accept a user's connection close to them at an Azure edge PoP and use Microsoft's global network toward the origin.

```text
User in India
 ↓
nearby Microsoft edge
 ↓
Microsoft backbone
 ↓
European/US origin
```

This can improve web performance, particularly for dynamic global applications.

Traffic Manager simply returns an endpoint through DNS.

Then:

```text
User
 ↓
public network path
 ↓
selected endpoint
```

Traffic Manager itself isn't an acceleration proxy.

---

# **4. Caching**

Front Door can provide CDN/edge caching capabilities for suitable content.

Example:

```text
/logo.png
CSS
JS
static product images
```

can be served closer to users.

Traffic Manager:

```text
doesn't cache application content
```

It is a DNS routing system.

---

# **5. Both perform health-based routing—but differently**

Suppose:

```text
Region A = healthy
Region B = healthy
```

Then Region A fails.

### Front Door

Its origin health checks detect the unhealthy origin.

New application requests can be sent to:

```text
Region B
```

through the Front Door proxy.

### Traffic Manager

Traffic Manager health probes detect Region A failure and changes its future DNS answers to prefer:

```text
Region B
```

But clients may still have the old DNS answer cached.

---

# **6. DNS caching is a major Traffic Manager consideration**

Suppose DNS TTL is:

```text
60 seconds
```

Traffic Manager detects Region A failure.

Traffic Manager starts returning:

```text
Region B
```

but a client may still have:

```text
Region A
```

cached until TTL expiration.

Therefore Traffic Manager failover isn't necessarily instantaneous for every client.

With Front Door:

```text
traffic continues to Front Door
```

and backend selection happens at the proxy layer.

That generally gives Front Door much more direct control over application request routing.

---

# **7. Traffic Manager can support non-HTTP endpoints**

Because Traffic Manager operates at DNS:

```text
TCP
UDP
HTTP
HTTPS
other endpoint protocols
```

can potentially be directed, provided the application is reachable by the returned DNS target and monitoring configuration fits.

Microsoft's load-balancing guidance categorizes Traffic Manager as a global DNS-based option and explicitly notes that it can distribute traffic types beyond HTTP/S because it doesn't process the actual application traffic. ([Microsoft Learn][2])

This is a major reason to consider Traffic Manager when:

```text
global routing
+
non-HTTP protocol
```

is required.

---

# **8. Front Door is primarily HTTP/S**

Front Door is the better fit for:

```text
Web sites
REST APIs
HTTP/S microservices
global ecommerce
public web applications
```

It isn't a generic global Layer-4 load balancer for arbitrary TCP/UDP workloads.

---

# **9. Routing methods**

Traffic Manager supports DNS-based routing methods such as:

```text
Priority
Weighted
Performance
Geographic
MultiValue
Subnet
```

depending on the scenario.

Example:

```text
Priority:
Primary endpoint
      ↓ failure
Secondary endpoint
```

or:

```text
Weighted:
90 → Region A
10 → Region B
```

Front Door also has sophisticated origin selection and weighting, but it performs routing as an **application proxy**, not merely by answering DNS differently.

---

# **10. Example — global e-commerce site**

Requirements:

```text
HTTP/S
global customers
WAF
TLS
CDN
path routing
regional failover
```

I would choose:

```text
Azure Front Door
```

Architecture:

```text
Global Users
     ↓
Front Door + WAF
   /          \
Region A     Region B
```

This is exactly the kind of workload Front Door is designed for.

---

# **11. Example — global custom TCP application**

Suppose:

```text
custom TCP application
Region A endpoint
Region B endpoint
global DNS failover
```

Front Door may not fit because application traffic isn't HTTP/S.

Traffic Manager could provide:

```text
global DNS endpoint selection
```

while clients connect directly to the selected application endpoint.

---

# **12. Security consequence**

With Front Door:

```text
Client
→ Front Door
→ origin
```

I can often design the origin so that:

```text
traffic should only come
through Front Door
```

using supported origin-security mechanisms such as Private Link in appropriate Front Door Premium designs or origin filtering.

With Traffic Manager:

```text
Client
→ endpoint directly
```

so the endpoint itself must securely handle direct client exposure.

Traffic Manager is not a security proxy.

---

# **13. Do I normally combine them?**

Usually:

```text
No
```

for one normal HTTP application.

Microsoft's current Front Door best-practice guidance says most solutions should use **either** Front Door or Traffic Manager rather than both. ([Microsoft Learn][1])

There can be advanced architectures where combination makes sense, but adding both without a specific need creates unnecessary DNS/routing complexity.

---

## **Quick comparison**

| Capability                              | Azure Front Door    | Traffic Manager |
| --------------------------------------- | ------------------- | --------------- |
| Scope                                   | Global              | Global          |
| Mechanism                               | **Reverse proxy**   | **DNS-based**   |
| Traffic passes through service          | **Yes**             | **No**          |
| Layer                                   | L7                  | DNS             |
| HTTP/HTTPS aware                        | **Yes**             | No              |
| WAF                                     | **Yes**             | No              |
| TLS termination                         | **Yes**             | No              |
| CDN/cache                               | **Yes**             | No              |
| Path routing                            | **Yes**             | No              |
| Non-HTTP global routing                 | No/general mismatch | **Good fit**    |
| Failover affected by client DNS caching | Less directly       | **Yes**         |

---

### **Interview answer condensed**

> “Front Door and Traffic Manager are both global traffic-distribution services, but Front Door is a Layer 7 reverse proxy while Traffic Manager is DNS-based. With Front Door, users connect to Microsoft's edge and Front Door terminates HTTP/S, can apply WAF, cache content, perform path routing and choose a healthy regional origin. With Traffic Manager, DNS tells the client which endpoint to use and the client connects directly to that endpoint, so Traffic Manager doesn't inspect or proxy the application traffic. I'd normally use Front Door for global web applications and Traffic Manager when I need DNS-level global routing, especially for protocols that aren't HTTP/S.”

**Memory line:**
**Front Door handles the request; Traffic Manager only tells the client where to send it.**

**Interview trap:**
Traffic Manager is **not in the application data path**—it cannot terminate TLS, inspect HTTP requests, or provide WAF protection.

**Keywords:**
Azure Front Door, Traffic Manager, global routing, DNS, Layer 7, reverse proxy, WAF, CDN, TTL, health probes.

# **T34-05. NSG vs Azure Firewall?**

**Answer:**

Both filter network traffic, but they solve different layers of network security.

A **Network Security Group, or NSG**, is a distributed, stateful network filtering control attached to Azure subnets or network interfaces. It primarily makes allow/deny decisions using things such as source IP, destination IP, source/destination port, and protocol.

**Azure Firewall** is a centralized, managed, stateful firewall service that I usually place in a hub network. It can inspect and control traffic across VNets, the internet, and on-premises networks, and provides capabilities such as centralized policies, FQDN/application rules, threat intelligence, and—depending on SKU—IDPS and TLS inspection.

So I normally don't think:

```text
NSG OR Firewall?
```

I think:

```text
NSG
→ distributed subnet/workload segmentation

Azure Firewall
→ centralized traffic inspection/control

Together
→ defense in depth
```

Microsoft explicitly describes Azure Firewall and NSGs as complementary: NSGs provide distributed network filtering, while Azure Firewall provides centralized stateful network and application-level protection across networks. ([Microsoft Learn][3])

---

## **Architecture**

```text
Internet
   ↓
Azure Firewall
   ↓
Hub
   ↓
Spoke VNet
   ↓
NSG on app subnet
   ↓
Application
```

Firewall says:

```text
Which centralized flows
are allowed through the enterprise boundary?
```

NSG says:

```text
Which sources and ports
can reach this subnet/NIC?
```

Different security boundaries.

---

# **1. NSG is distributed**

You associate an NSG with:

```text
Subnet
and/or
NIC
```

Examples:

```text
Web subnet NSG
App subnet NSG
Database subnet NSG
VM NIC NSG
```

This enables local segmentation.

For example:

```text
Internet → App subnet : 22
DENY

Web subnet → App subnet : 443
ALLOW

App subnet → DB subnet : 1433
ALLOW
```

NSGs are excellent for enforcing:

```text
east-west segmentation
```

close to workloads.

---

# **2. NSG evaluates a 5-tuple-style flow**

The important fields are essentially:

```text
Source
Source port
Destination
Destination port
Protocol
```

plus:

```text
Direction
Priority
Allow/Deny
```

Example:

```text
Priority: 100
Source: 10.10.1.0/24
Destination: 10.10.2.0/24
Port: 443
Protocol: TCP
Action: Allow
```

It doesn't understand:

```text
GET /checkout
Host: api.example.com
SQL injection
URL category
```

NSG is fundamentally a network segmentation control.

---

# **3. NSGs are stateful**

Suppose inbound rule permits:

```text
Client → VM:443
```

Response traffic:

```text
VM → Client
```

is allowed as part of the established flow; you don't need a matching reverse rule just for the response.

The same stateful principle applies to Azure Firewall.

---

# **4. Azure Firewall is centralized**

Typical enterprise architecture:

```text
             Hub VNet
                │
          Azure Firewall
          /      |       \
         /       |        \
      Spoke A  Spoke B   Internet
```

UDRs can force:

```text
spoke internet traffic
spoke-to-spoke traffic where inspection required
```

through the firewall.

This allows one central security team to manage:

```text
egress
cross-network inspection
threat intelligence
central logs
```

instead of duplicating complex rules across hundreds of NSGs.

Microsoft's current networking guidance places Azure Firewall in the centralized traffic-inspection role and NSGs in workload/subnet segmentation. ([Microsoft Learn][4])

---

# **5. FQDN filtering is a major Azure Firewall advantage**

Suppose AKS workload may access:

```text
github.com
packages.microsoft.com
api.vendor.com
```

An NSG isn't designed to say:

```text
Allow HTTPS only to api.vendor.com
```

as an application-aware internet-egress policy.

Azure Firewall can use:

```text
Application rules
FQDNs
FQDN tags
web categories depending SKU/features
```

for more intelligent centralized filtering.

---

# **6. Threat intelligence**

Azure Firewall can use threat-intelligence feeds to:

```text
alert or deny traffic
to/from known malicious
IPs/domains
```

depending on configuration.

An NSG does not provide that kind of managed threat-intelligence inspection.

---

# **7. Azure Firewall Premium adds deeper security**

Premium capabilities include features such as:

```text
IDPS
TLS inspection
```

for supported traffic.

Microsoft's current Firewall guidance lists IDPS and TLS inspection among Premium's advanced threat-protection capabilities. ([Microsoft Learn][4])

An NSG doesn't decrypt or deeply inspect TLS sessions.

---

# **8. NSG does not replace Firewall**

Imagine:

```text
VM subnet
NSG:
Outbound HTTPS 443 = Allow
```

That permits HTTPS based on network-layer information.

It cannot distinguish:

```text
https://approved-vendor.com
```

from:

```text
https://malicious-site.example
```

based merely on TCP 443.

Azure Firewall can provide a centralized policy capable of much richer destination control.

---

# **9. Firewall doesn't replace NSGs either**

Suppose firewall handles:

```text
Spoke → Internet
```

but inside the spoke:

```text
Web subnet
App subnet
DB subnet
```

may communicate directly according to VNet routing.

If you want:

```text
Web → DB
DENY
```

an NSG is an efficient local segmentation layer.

Microsoft's Firewall FAQ explicitly recommends both for defense in depth rather than treating Firewall as an NSG replacement. ([Microsoft Learn][3])

---

# **10. Routing is required for Firewall inspection**

This is a major distinction.

NSG:

```text
attached to subnet/NIC
→ traffic crossing that boundary is evaluated
```

Azure Firewall:

```text
must actually be in the traffic path
```

Usually through:

```text
UDR
0.0.0.0/0
→ Firewall private IP
```

or other deliberate routing.

Simply creating an Azure Firewall in a hub:

```text
does not automatically inspect
all VNet traffic.
```

---

# **11. Example hub-spoke design**

```text
Spoke workload
    ↓
NSG
    ↓
UDR
    ↓
Azure Firewall
    ↓
Internet
```

Outbound flow:

1. NSG evaluates whether subnet/NIC allows the flow.
2. Route directs it to Firewall.
3. Firewall evaluates central policy.
4. If permitted, Firewall forwards/SNATs as appropriate.

This is layered security.

---

# **12. Operational scope**

NSGs:

```text
many distributed policies
```

Good for:

```text
application subnet boundaries
```

Azure Firewall:

```text
central security policy
```

Good for:

```text
organization-wide egress
central ingress/NAT scenarios
hub-spoke inspection
cross-subscription network governance
```

---

# **13. Cost**

NSGs are a fundamental VNet filtering capability without the same dedicated hourly/data-processing service model as Azure Firewall.

Azure Firewall is a deployed managed service and has meaningful cost.

Therefore:

```text
"I need to block port 22 between two subnets"
```

does not automatically justify deploying a large central firewall solely for that rule.

Use the control appropriate to the problem.

---

## **Quick comparison**

| Capability                       | NSG                           | Azure Firewall            |
| -------------------------------- | ----------------------------- | ------------------------- |
| Placement                        | Subnet/NIC                    | Central managed service   |
| Stateful                         | Yes                           | Yes                       |
| Basic IP/port/protocol filtering | **Yes**                       | **Yes**                   |
| Local workload segmentation      | **Excellent**                 | Possible but heavier      |
| Centralized policy               | Limited/distributed           | **Excellent**             |
| FQDN/application filtering       | Not its main capability       | **Yes**                   |
| Threat intelligence              | No                            | **Yes**                   |
| IDPS/TLS inspection              | No                            | Premium capabilities      |
| Must route traffic through it    | No separate appliance routing | **Yes**                   |
| Typical use                      | Microsegmentation             | Central inspection/egress |

---

### **Interview answer condensed**

> “An NSG is a distributed stateful filter applied to subnets or NICs, primarily using IP, port and protocol rules. I use it for local segmentation—for example allowing the web subnet to reach the application subnet on 443 while blocking direct access to the database. Azure Firewall is a centralized managed firewall that I normally place in the hub and route traffic through. It adds central policy, FQDN filtering, threat intelligence, and advanced capabilities such as IDPS and TLS inspection depending on SKU. I normally use both: NSGs for workload-level segmentation and Azure Firewall for centralized inspection and egress control.”

**Memory line:**
**NSG protects close to the workload; Azure Firewall protects centrally across networks.**

**Interview trap:**
Deploying Azure Firewall in the hub **does not automatically inspect traffic**—routing must actually send the traffic through it.

**Keywords:**
NSG, Azure Firewall, stateful, subnet, NIC, UDR, hub-spoke, FQDN, threat intelligence, IDPS, TLS inspection.

# **T34-06. Azure Firewall vs WAF?**

**Answer:**

Azure Firewall and WAF protect against **different types of threats at different layers**, so they are usually complementary rather than substitutes.

**Azure Firewall** is a centralized network security service that can inspect and filter traffic across IPs, ports, protocols and application destinations. I use it for north-south and east-west network control, outbound filtering, threat intelligence, NAT, and—particularly with Premium—capabilities such as IDPS and TLS inspection.

**Azure Web Application Firewall, or WAF**, specifically protects **HTTP/HTTPS web applications at Layer 7** against application-layer attacks such as SQL injection, cross-site scripting, malicious HTTP requests, and other OWASP-style attacks. In Azure it is integrated with services such as **Application Gateway** for regional applications and **Azure Front Door** for global edge applications.

So:

```text
Network traffic security
across protocols
→ Azure Firewall

Web application HTTP/S attack protection
→ WAF
```

Microsoft's current network-security guidance explicitly positions Azure Firewall and WAF as different layers of defense: Firewall protects network/application traffic broadly, while WAF is specialized for public-facing web application attacks such as SQL injection and XSS. ([Microsoft Learn][3])

---

## **Architecture**

```text
Internet
   ↓
Front Door / Application Gateway
   + WAF
   ↓
Web application
   ↓
VNet
   ↓
Azure Firewall
   ↓
Internet / on-prem / other VNets
```

WAF asks:

```text
Is this HTTP request malicious?
```

Firewall asks:

```text
Should this network/application flow
be allowed through this security boundary?
```

---

# **1. WAF understands HTTP attacks**

Example request:

```http
GET /products?id=1' OR '1'='1
```

Network layer sees:

```text
TCP 443
```

which looks perfectly valid.

WAF can inspect the HTTP request and recognize:

```text
possible SQL injection
```

An ordinary Layer-4 network allow rule cannot determine that.

---

# **2. WAF protects OWASP-style vulnerabilities**

Typical categories include:

```text
SQL injection
Cross-site scripting
Path traversal
protocol anomalies
malicious request patterns
```

plus additional bot/rate/custom protection capabilities depending on WAF platform and SKU.

Microsoft specifically positions Azure WAF for OWASP Top 10-style application attacks. ([Microsoft Learn][5])

---

# **3. Where does WAF run?**

Azure WAF isn't typically a standalone firewall VM in your hub.

It is integrated with application-delivery services.

### Regional

```text
Application Gateway WAF_v2
```

Architecture:

```text
Internet
 ↓
Application Gateway + WAF
 ↓
regional web application
```

### Global

```text
Azure Front Door + WAF
```

Architecture:

```text
Global users
 ↓
Front Door edge + WAF
 ↓
regional origins
```

That placement lets WAF inspect HTTP/S traffic before it reaches the application.

---

# **4. Azure Firewall handles broader protocols**

Firewall can enforce policies for traffic such as:

```text
HTTP/HTTPS
SSH
RDP
FTP
DNS
other TCP/UDP
```

depending on rule type/configuration.

Microsoft's Firewall FAQ explicitly states that Azure Firewall can protect non-HTTP/S protocols and outbound network traffic, while Application Gateway WAF is specifically focused on inbound web-application protection. ([Microsoft Learn][3])

WAF is not what I use to control:

```text
VM → Internet SSH
```

or:

```text
Spoke A → Spoke B TCP 1433
```

---

# **5. Egress control**

Suppose AKS Pods must access only:

```text
api.vendor.com
packages.microsoft.com
```

Use:

```text
Azure Firewall
```

for centralized outbound policy.

WAF does not sit there deciding which external sites workloads may call.

---

# **6. East-west filtering**

Suppose:

```text
Spoke A
→ Spoke B
```

must cross a central security device.

Azure Firewall can inspect/filter that routed traffic.

WAF is not an east-west network firewall.

It protects HTTP application entry paths.

---

# **7. Inbound architecture can use both**

Consider internet banking:

```text
Internet
 ↓
Front Door WAF
 ↓
regional application
 ↓
Azure Firewall-controlled internal/egress paths
 ↓
dependencies
```

WAF protects against:

```text
malicious web requests
```

Firewall protects against:

```text
unapproved network destinations
malicious IPs/FQDNs
east-west movement
outbound command-and-control
```

That's defense in depth.

---

# **8. WAF does not replace secure application code**

Even with WAF:

```text
parameterized queries
input validation
authorization
secure coding
```

remain necessary.

WAF reduces risk.

It isn't permission to deploy:

```text
SQL concatenation vulnerabilities
```

and assume infrastructure will catch everything.

---

# **9. Firewall also isn't equivalent to WAF**

Suppose Azure Firewall allows:

```text
Internet → web server TCP 443
```

That decision essentially means:

```text
HTTPS flow allowed
```

It doesn't mean your web app has the same specialized OWASP-rule protection as Application Gateway/Front Door WAF.

Microsoft's own Firewall FAQ distinguishes the two explicitly rather than positioning Azure Firewall as a replacement for WAF. ([Microsoft Learn][3])

---

# **10. TLS inspection can cause confusion**

Azure Firewall Premium can perform TLS inspection in supported scenarios.

An interviewer might ask:

> If Firewall can decrypt TLS, isn't it a WAF?

No.

TLS inspection enables Firewall to inspect encrypted flows for its security capabilities.

WAF has specialized:

```text
HTTP parsing
web attack rules
OWASP managed rules
application-specific protections
```

These are different security functions.

---

# **11. DDoS is a third different service**

Another common confusion:

```text
Azure Firewall
≠
WAF
≠
DDoS Protection
```

Conceptually:

```text
DDoS Protection
→ large-scale volumetric/network attacks

Azure Firewall
→ centralized network/application flow control

WAF
→ malicious HTTP/S application requests
```

Microsoft's current security guidance explicitly separates these three protection layers. ([Microsoft Learn][5])

For an internet-facing application I may use both: WAF protects the HTTP request at the edge or regional ingress, while Azure Firewall controls the broader network and egress paths.”

**Memory line:**
**Firewall protects network flows; WAF protects web requests.**

# **T34-07. Service Endpoint vs Private Endpoint?**

**Answer:**

Both provide more secure access from an Azure VNet to supported Azure PaaS services, but the connectivity model is very different.

With a **Service Endpoint**, the Azure service still uses its **public endpoint and public DNS address**. I enable the service endpoint on a subnet and configure the target service's network rules to trust that subnet. Traffic takes an optimized path across the Microsoft backbone and the service can identify the originating VNet/subnet.

With a **Private Endpoint**, Azure creates a **network interface with a private IP address inside my VNet** for one specific PaaS resource. Applications then access that resource through the private IP, usually using Private DNS so the normal service hostname resolves privately.

So:

```text
Service Endpoint
→ secure public service endpoint
   to selected VNet/subnet

Private Endpoint
→ give a specific service resource
   a private IP inside my VNet
```

For modern workloads requiring true private PaaS access, on-premises connectivity, strong isolation, or public network access disabled, I generally prefer **Private Endpoint/Private Link**. Microsoft's current guidance explicitly recommends Private Link for private PaaS access because it provides private IP connectivity, more granular resource isolation, on-premises private connectivity, and stronger data-exfiltration protection. ([Microsoft Learn][6])

---

## **Architecture difference**

### Service Endpoint

```text
VM: 10.1.1.4
    │
    │ subnet has
    │ Microsoft.Storage
    │ service endpoint
    ↓
Microsoft backbone
    ↓
Storage public endpoint
52.x.x.x
```

DNS:

```text
mystorage.blob.core.windows.net
→ public IP
```

The PaaS resource can be configured:

```text
Allow:
Subnet A
```

---

### Private Endpoint

```text
VM: 10.1.1.4
       ↓
Private DNS
       ↓
mystorage...
→ 10.1.2.5
       ↓
Private Endpoint NIC
       ↓
Storage Account
```

The selected Storage Account effectively has a private entry point inside your VNet.

Microsoft describes Private Endpoint as a special network interface assigned an IP from your VNet and Service Endpoint as access to an Azure service through its public endpoint while extending VNet identity to the service. ([Microsoft Learn][6])

---

# **1. Public vs private endpoint is the most important distinction**

### Service Endpoint

The Azure PaaS endpoint remains:

```text
publicly addressed
```

although access can be restricted using service firewall/VNet rules.

### Private Endpoint

The resource gets:

```text
private IP
```

for that Private Link path.

Example:

```text
10.20.4.7
```

inside the VNet.

This gives a much stronger private-connectivity architecture.

---

# **2. DNS behavior**

With Service Endpoint:

```text
mydb.database.windows.net
```

continues resolving to:

```text
public service IP
```

Microsoft explicitly states that DNS remains unchanged for service endpoints. ([Microsoft Learn][6])

With Private Endpoint:

```text
mydb.database.windows.net
```

should ultimately resolve, through the appropriate Private Link DNS chain, to:

```text
private endpoint IP
```

from environments that should use the private path.

Therefore:

```text
Private Endpoint
+
incorrect DNS
=
application connectivity failure
```

---

# **3. Private DNS is critical**

This is probably the most common Private Endpoint interview troubleshooting question.

Suppose:

```text
SQL Private Endpoint = 10.10.5.4
Public network access = Disabled
```

Application resolves:

```text
mydb.database.windows.net
→ public IP
```

Then:

```text
connection fails
```

even though the Private Endpoint itself is perfectly healthy.

Expected:

```text
Application
 ↓
Private DNS zone
 ↓
10.10.5.4
 ↓
Private Endpoint
```

Microsoft's App Service/private networking guidance similarly emphasizes that clients using Private Endpoints must resolve the destination hostname to the private endpoint address. ([Microsoft Learn][7])

---

# **4. Resource granularity**

Service Endpoint is enabled for an Azure **service type** on the subnet, for example:

```text
Microsoft.Storage
```

Then service firewall rules restrict which Storage resources accept traffic from that VNet/subnet.

Private Endpoint maps to:

```text
one specific service/resource/subresource
```

For example:

```text
Storage Account A
→ Private Endpoint A

Storage Account B
→ different Private Endpoint
```

This provides more granular isolation.

Microsoft's comparison explicitly notes that Private Endpoints apply at an individual service-instance level, whereas Service Endpoint configuration is broader at the Azure service scope. ([Microsoft Learn][6])

---

# **5. On-premises access**

This is another major difference.

Suppose:

```text
On-premises
    ↓
ExpressRoute/VPN
    ↓
Azure VNet
```

Can on-premises access a PaaS resource through a VNet Service Endpoint?

Generally, a classic Service Endpoint isn't an on-premises private-access mechanism.

Private Endpoint:

```text
has private VNet IP
```

so on-premises networks connected through:

```text
VPN
ExpressRoute
```

can potentially route to it, assuming:

```text
routing
DNS
NSGs/firewall
```

are configured.

Microsoft's current standard Service Endpoint comparison states that classic/basic Service Endpoints don't provide private on-premises connectivity, while Private Link does. ([Microsoft Learn][8])

---

# **6. Public network access is separate**

Suppose Storage has:

```text
Private Endpoint
```

Does that automatically mean:

```text
public access disabled?
```

**No.**

You can have:

```text
Private Endpoint
+
public endpoint still enabled
```

unless you explicitly change the service's public network access/firewall setting.

For strict private architecture:

```text
Private Endpoint
+
Private DNS
+
Public network access disabled
```

is the complete pattern.

This distinction is extremely important.

---

# **7. Service Endpoint doesn't necessarily mean internet traversal**

Even though the PaaS service uses a public IP endpoint, traffic using the Service Endpoint goes over the:

```text
Microsoft Azure backbone
```

rather than simply traversing the public internet.

Microsoft explicitly documents this. ([Microsoft Learn][9])

So saying:

> “Service Endpoint sends traffic over the public internet.”

would be incorrect.

Better:

> “The service retains a public endpoint/IP model, but the service-endpoint traffic takes Azure's backbone and carries VNet/subnet identity.”

---

# **8. Data-exfiltration protection**

Consider a compromised VM.

It is allowed to access:

```text
Microsoft.Storage
```

through Service Endpoint.

Without additional controls, an attacker may potentially try to send data to another Storage resource.

Service Endpoint Policies can improve restriction for supported scenarios, but Private Link provides stronger built-in resource-specific private connectivity.

Microsoft's current comparison identifies built-in data-exfiltration protection as an advantage of Private Endpoint over basic Service Endpoint. ([Microsoft Learn][6])

---

# **9. Cost and complexity**

Service Endpoints are comparatively simple.

```text
Enable endpoint on subnet
+
configure PaaS firewall/VNet rule
```

Classic service endpoints don't have the Private Endpoint resource/NIC and Private DNS complexity, and Microsoft currently states there is no extra charge for using classic service endpoints. ([Microsoft Learn][9])

Private Endpoints require:

```text
Private Endpoint resource
private IP capacity
Private DNS
approval/lifecycle
cost
```

So:

```text
Private Endpoint
```

provides stronger isolation but greater operational complexity.

---

# **10. IP consumption**

Service Endpoint:

```text
doesn't allocate
one new private endpoint IP
for every PaaS resource
```

Private Endpoint does.

If you have:

```text
200 private endpoints
```

you need to account for those addresses in subnet/IPAM planning.

This can matter at enterprise scale.

# **11. Example — Storage with Service Endpoint**

```text
AKS node subnet
10.20.1.0/24
       ↓
Microsoft.Storage
service endpoint
       ↓
Storage firewall
Allow VNet subnet:
10.20.1.0/24 identity
```

DNS still points toward the Storage public endpoint.

Good when:

```text
simple Azure VNet restriction
```

is sufficient.

# **12. Example — highly sensitive SQL database**

Requirements:

```text
No public exposure
AKS access
On-prem DBA access through ExpressRoute
Private DNS
```

Use:

```text
SQL
 ↓
Private Endpoint
 ↓
10.20.5.4
```

and:

```text
Public network access = Disabled
```

Clients:

```text
AKS
and
on-prem through ER/VPN
```

resolve the SQL hostname to:

```text
10.20.5.4
```

That's a strong Private Link use case.

---

# **13. Private Endpoint does not grant authorization**

Very important:

```text
Private Endpoint
```

answers:

> How can traffic privately reach the service?

It does **not** answer:

> Is the caller permitted to read the data?

You still need:

```text
Entra authentication
Managed Identity
Azure RBAC/data-plane permissions
database authentication
```

depending on the target.

Example:

```text
AKS Pod
 ↓
Private Endpoint
 ↓
Storage
 ↓
403
```

Network is working.

Authorization is not.

---

# **14. Troubleshooting Private Endpoint**

Application cannot reach Storage.

I check:

```text
1. DNS
2. Private Endpoint state
3. routing
4. NSG/firewall
5. target public/private settings
6. identity/authentication
7. data-plane authorization
```

First:

```bash
nslookup mystorage.blob.core.windows.net
```

Expected:

```text
private IP
```

If public:

```text
fix DNS first
```

If private IP works but application receives:

```text
403
```

move to:

```text
identity/RBAC
```

That's a clean troubleshooting separation.

## **Quick comparison**

| Capability                         | Service Endpoint        | Private Endpoint                                            |
| ---------------------------------- | ----------------------- | ----------------------------------------------------------- |
| Service address                    | **Public endpoint/IP**  | **Private VNet IP**                                         |
| Traffic over Azure backbone        | Yes                     | Yes                                                         |
| Extra NIC/private IP               | No                      | **Yes**                                                     |
| DNS change required                | Usually no              | **Usually yes / critical**                                  |
| Individual PaaS resource isolation | Less granular           | **Strong**                                                  |
| On-prem private access             | Limited/not classic use | **Yes**                                                     |
| Disable service public endpoint    | Not inherent            | **Common design**                                           |
| Data-exfiltration protection       | Limited / policies help | **Stronger built-in model**                                 |
| Complexity                         | Lower                   | Higher                                                      |
| Microsoft modern preference        | Use when appropriate    | **Private Link recommended for strong private PaaS access** |

### **Interview answer condensed**

> “A Service Endpoint secures access from a VNet subnet to a supported Azure PaaS service while the PaaS resource still uses its public endpoint and public DNS address. The traffic stays on the Microsoft backbone, and the service can restrict access to that VNet or subnet. A Private Endpoint is different: Azure creates a NIC with a private IP in my VNet for a specific PaaS resource, and Private DNS normally makes the service hostname resolve to that IP. Private Endpoint is therefore the stronger choice when I need true private addressing, on-premises private access, or public network access disabled. I also remember that creating a Private Endpoint doesn't automatically disable the public endpoint, and it doesn't replace authentication or RBAC.”

**Memory line:**
**Service Endpoint trusts your subnet at the service's public endpoint; Private Endpoint brings a specific service resource into your VNet through a private IP.**

**Interview trap:**
A Private Endpoint by itself **does not automatically disable public network access**, and without correct **Private DNS** the application may still resolve the public endpoint.
