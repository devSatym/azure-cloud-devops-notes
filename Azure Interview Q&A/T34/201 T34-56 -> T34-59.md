### **T34-56. Monitoring vs observability?**

**Answer:**

Monitoring and observability overlap, but I think of them at different depths.

**Monitoring** tells me whether known aspects of a system are healthy by collecting predefined signals, dashboards, and alerts. For example, I might monitor AKS Pod restarts, API error rate, CPU utilization, Azure SQL utilization, and p95 latency.

**Observability** is the broader ability to understand the **internal state and behavior of a system from its telemetry**, especially when something unexpected happens. It combines metrics, logs, traces, dependencies, topology, correlation IDs, deployment metadata, and other context so I can ask questions I didn't necessarily predict when I built the dashboards.

So my mental model is:

```text
Monitoring
→ "Is the system behaving as expected?"

Observability
→ "Why is the system behaving this way,
   even if I didn't predict this failure?"
```

Monitoring is therefore a **subset of a good observability strategy**, not a competing idea.

### **Interview answer condensed**

> “Monitoring is mainly about tracking known health signals and alerting when they cross expected boundaries—for example availability, 5xx rate, latency or Pod restarts. ### **T34-57. Logs vs metrics vs traces?**

**Answer:**

Logs, metrics, and traces are complementary telemetry signals that answer different questions.

**Metrics** are aggregated numeric time-series values such as request rate, CPU usage, error percentage, queue depth, or p95 latency. They're excellent for dashboards, trends, SLOs, and fast alerts.

**Logs** are detailed timestamped records of individual events—for example an exception, authentication failure, Kubernetes event, or application message. They're excellent for detailed investigation and forensic context.

**Traces** show the end-to-end path of a single request or operation through distributed components. They tell me which services were called, how long each step took, and where a particular transaction failed.

So I remember them as:

```text
Metrics
→ How much / how often?

Logs
→ What happened?

Traces
→ Where did this specific request go
   and where did it spend time?
```

A mature Azure observability design normally uses all three.

```text

 ↓
```

```text
 ↓
```

```text
 ↓
```


# **6. Trace vs span**

A useful follow-up distinction:

```text
Trace
→ entire distributed operation

Span
→ one unit of work inside that trace
```

For example:

```text
Trace:
checkout

Spans:
HTTP frontend
orders API
SQL query
payment call
```

Each span may contain:

```text
start time
duration
status
attributes
parent span
```

The parent-child relationships reconstruct the transaction.

# **7. Metrics summarize many events; traces preserve individual paths**

Suppose in five minutes:

```text

```

Metrics may summarize:

```text

```

Very cheap to visualize.

A trace represents specific transactions:

```text

→ frontend
→ orders
→ payment
```

If you trace every request at very high traffic, telemetry cost can become substantial.

That's why sampling is common.

# **14. Tracing requires context propagation**

Suppose:

```text
Frontend
→ Orders
→ Payments
```

Frontend creates:

```text
trace ID
```

but Orders doesn't propagate it to Payments.

Result:

```text
Trace A:
Frontend → Orders

Trace B:
Payments
```

The distributed transaction becomes disconnected.

OpenTelemetry-compatible propagation headers, such as W3C Trace Context, help carry:

```text
trace ID
span relationship
```

across service boundaries.

# **15. Sampling trade-off**

Suppose:

```text
1,000,000 requests/minute
```

Tracing every request may be expensive.

You might sample:

```text
5%
```

while retaining:

```text
100% error traces
```

if supported by your instrumentation/collector strategy.

But aggressive sampling can hide rare problems.

So sampling should balance:

```text
cost
diagnostic value
error visibility
traffic volume
```


### **Interview answer condensed**

> “Metrics are numeric time-series data, so I use them for trends, dashboards, SLOs and alerts—for example error rate or p95 latency. Logs are detailed timestamped events, so they're useful when I need exact context such as an exception, version or error code. Traces follow a specific request through distributed services using spans, so they show where that request spent time or failed. In production I normally use them together: a metric detects the incident, a trace identifies the failing dependency, and logs explain the exact failure.”

**Memory line:**
**Metrics tell me how the system is behaving, logs tell me what happened, and traces tell me where a request went.**

**Interview trap:**
A large number of logs does **not** replace distributed tracing; without propagated trace context, cross-service request causality can still be difficult to reconstruct.

### **T34-58. Azure Advisor vs Azure Monitor?**

**Answer:**

Azure Advisor and Azure Monitor both analyze information about Azure resources, but their purpose is very different.

**Azure Monitor** is the operational monitoring and observability platform. It collects and analyzes telemetry such as metrics, logs, traces, alerts, application performance, infrastructure health, and resource diagnostics. I use it to answer questions like:

```text
Is Production healthy right now?
Why is latency increasing?
Did this VM hit 95% CPU?
Which AKS Pods are failing?
```

**Azure Advisor** is a recommendation service. It analyzes Azure resource configuration and usage telemetry and gives personalized best-practice recommendations around areas such as **cost, reliability, performance, security, and operational excellence**. I use it to answer:

```text
What could I improve in my Azure environment?
Are resources underutilized?
Could this architecture be more resilient?
Are there configuration improvements I should make?
```

So:

```text
Azure Monitor
→ observe and operate the environment

Azure Advisor
→ recommend how to improve the environment
```

Current Microsoft documentation describes Advisor as a digital cloud assistant that analyzes resource configuration and usage telemetry to generate proactive recommendations for cost effectiveness, performance, reliability, security, and operational excellence. Azure Monitor remains the telemetry/monitoring platform used for operational health and diagnostics. ([Microsoft Learn][1])

```text
my end-to-end application
meets its 99.95% SLO.
```

Azure Monitor and workload testing still need to measure:

```text
actual user availability
latency
failure behavior
```

Recommendation compliance and observed reliability are different things.


For security operations, tools such as:


have specialized roles.

### **T34-59. Azure Defender for Cloud vs Microsoft Sentinel?**

**Answer:**

The current product name is **Microsoft Defender for Cloud**; the question's “Azure Defender for Cloud” refers to that service.

The easiest distinction is **cloud security posture/workload protection versus centralized security operations and SIEM**.

**Microsoft Defender for Cloud** is a cloud-native application protection platform focused on the security posture and protection of cloud workloads. It helps identify misconfigurations and attack paths, provides security recommendations and regulatory-compliance visibility, and—with Defender plans enabled—provides workload threat protection for resources such as servers, containers, databases, and other cloud services across Azure and supported multicloud environments.

**Microsoft Sentinel** is Microsoft's cloud-native **SIEM and security operations platform**. It collects and correlates security data across many sources—not only Azure resources—and helps SOC teams detect threats, create incidents, investigate attacks, hunt across telemetry, and automate response.

So:

```text
Defender for Cloud
→ "How secure are my cloud resources,
   and what threats are affecting them?"

Microsoft Sentinel
→ "What security activity is happening
   across the enterprise,
   how do I correlate it,
   investigate it, and respond?"
```

They are complementary. Defender for Cloud can generate security findings and alerts that become valuable signals for Sentinel investigations.

Current Microsoft documentation describes Defender for Cloud as providing cloud security posture and threat-protection capabilities across Azure, AWS, and GCP, while Sentinel is a cloud-native SIEM/security platform for centralized threat detection, investigation, hunting, and response across multicloud and multiplatform environments. ([Microsoft Learn][3])

## **1. Defender for Cloud starts from cloud resources**

Think:

```text
Azure / AWS / GCP
cloud workloads
      ↓
Microsoft Defender for Cloud
      ↓
┌──────────────────────────┐
│ Security posture         │
│ Recommendations          │
│ Attack paths             │
│ Compliance visibility    │
│ Workload threat alerts   │
└──────────────────────────┘
```

It asks questions like:

```text
Which cloud assets are exposed?
Which configurations increase risk?
Which resources violate recommendations?
What attack paths exist?
Are protected workloads generating threats?
```

Current Microsoft documentation describes Defender for Cloud as covering both **pre-breach security posture** and **post-breach threat protection**, with current experiences increasingly integrated into the Microsoft Defender portal. ([Microsoft Learn][3])

# **2. Sentinel starts from security telemetry across the enterprise**

Architecture:

```text
Azure logs ────────────────┐
Defender alerts ───────────┤
Microsoft 365 ─────────────┤
Identity/security data ────┤
AWS/GCP/security tools ────┤
firewalls ─────────────────┤
third-party sources ───────┘
                           ↓
                    Microsoft Sentinel
                           ↓
                ┌────────────────────┐
                │ Analytics          │
                │ Incidents          │
                │ Investigation      │
                │ Threat hunting     │
                │ Automation        │
                └────────────────────┘
                           ↓
                          SOC
```

Sentinel's value is correlation.

One alert by itself may be weak.

Ten related events across:

```text
identity
endpoint
cloud
email
network
```

can form one meaningful attack story.

Microsoft currently describes Sentinel as an AI-powered cloud-native SIEM providing detection, investigation, response, proactive hunting, and broad multi-platform correlation. ([Microsoft Learn][4])

# **5. Sentinel is a SIEM**

SIEM means:

```text
Security Information
and Event Management
```

Its job includes:


Individually these could be separate alerts.

Sentinel can help analysts investigate them as a connected security incident.

They operate at different layers of the security program.
