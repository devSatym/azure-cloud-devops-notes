# **T34-08. VPN Gateway vs ExpressRoute?**

**Answer:**

Both connect Azure to external networks such as on-premises datacenters, but the connectivity model is different.

**Azure VPN Gateway** creates an encrypted IPsec/IKE tunnel over the **public internet**. It's faster and cheaper to deploy and works well for smaller hybrid environments, branch connectivity, dev/test, remote users, or as a backup connection.

**Azure ExpressRoute** provides a **private dedicated connection** into Microsoft's network through a connectivity provider or ExpressRoute Direct. Traffic doesn't traverse the public internet, so it offers more predictable latency, higher bandwidth, and is usually preferred for enterprise production workloads with strong performance or compliance requirements.

A very important security nuance is that **ExpressRoute is private but not encrypted by default**. If the workload requires encryption, I would still use TLS at the application layer, IPsec over ExpressRoute where appropriate, or MACsec with ExpressRoute Direct.

So my rule is:

```text
Need lower-cost encrypted connectivity,
fast setup, or backup path
→ VPN Gateway

Need predictable private connectivity,
higher throughput, enterprise hybrid connectivity
→ ExpressRoute
```

Microsoft's current hybrid-connectivity guidance makes the same distinction: VPN Gateway uses encrypted IPsec/IKE over the public internet, while ExpressRoute provides a private path with more predictable performance. ([Microsoft Learn][1])

## **1. VPN Gateway is internet-based but encrypted**

Site-to-site VPN typically uses:

```text
IPsec/IKE
```

between:

```text
on-prem VPN device
↔
Azure VPN Gateway
```

This provides:

```text
confidentiality
integrity
authentication
```

for the tunnel.

But internet conditions can still affect:

```text
latency
jitter
packet loss
availability
```

because the underlying transport remains the internet.

# **2. ExpressRoute is private, but private does not mean encrypted**

This is one of the biggest interview traps.

ExpressRoute gives:

```text
private connectivity
```

but Microsoft explicitly states that ExpressRoute traffic **isn't encrypted by default**. ([Microsoft Learn][3])

So this statement is wrong:

> “ExpressRoute is more secure because all traffic is encrypted.”

Better:

> “ExpressRoute avoids the public internet and provides private connectivity, but I would still use end-to-end encryption for sensitive workloads.”

Encryption options include:

```text
TLS
IPsec over ExpressRoute
MACsec with ExpressRoute Direct
```

where appropriate. ([Microsoft Learn][2])

# **3. Performance**

VPN Gateway performance depends on:

```text
Gateway SKU
Tunnel count
Internet conditions
Encryption overhead
```

Current Microsoft guidance lists aggregate VPN Gateway throughput up to around **10 Gbps** on higher SKUs.

ExpressRoute can provide substantially higher capacity—up to **100 Gbps per circuit**, with ExpressRoute Direct supporting even higher capacities such as 400 Gbps in supported scenarios/locations. ([Microsoft Learn][2])

For an interview, the exact numbers matter less than:

```text
VPN
→ lower/more variable performance

ExpressRoute
→ higher and more predictable performance
```

---

# **4. Latency**

VPN:

```text
On-prem
→ Internet
→ Azure
```

Therefore routing conditions can change.

ExpressRoute:

```text
On-prem
→ provider
→ Microsoft network
```

gives a more predictable private route.

For:

```text
latency-sensitive databases
large data replication
high-volume enterprise hybrid apps
```

ExpressRoute is generally more attractive.

---

# **5. Cost**

VPN Gateway:

```text
gateway cost
+
data transfer
```

usually makes it easier to justify for smaller environments.

ExpressRoute additionally involves:

```text
Azure charges
+
connectivity-provider/circuit charges
```

and potentially substantial provisioning effort.

Therefore:

```text
20-person company + occasional hybrid connectivity
```

might choose VPN.

Whereas:

```text
large bank + continuous hybrid traffic
```

may justify ExpressRoute.

# **6. Provisioning time**

VPN can usually be deployed comparatively quickly once networking and the on-prem VPN device are ready.

ExpressRoute often requires coordination with:

```text
telecom/provider
colocation facility
enterprise network team
Microsoft peering
```

so lead time is typically longer.

This makes VPN useful for:

```text
rapid setup
temporary connectivity
DR backup
```

# **7. Routing**

Both can use dynamic routing.

ExpressRoute heavily uses:

```text
BGP
```

between the customer/provider/Microsoft routing domains.

VPN Gateway can also use:

```text
BGP
```

for more scalable routing instead of maintaining static route definitions.

This matters in large networks because:

```text
new subnet appears
→ BGP advertises route
```

rather than every site requiring manual route changes.

# **8. You can use both**

A very common enterprise pattern is:

```text
              ExpressRoute
On-prem ─────────────────────→ Azure
   │
   │
   └──── IPsec VPN backup ───→ Azure
```

Primary:

```text
ExpressRoute
```

Failover:

```text
Site-to-site VPN
```

Microsoft specifically supports VPN Gateway as a backup path alongside ExpressRoute. ([Microsoft Learn][4])

This protects against:

```text
provider circuit outage
```

provided the backup architecture is properly tested.

---

# **9. Point-to-site is another VPN use case**

VPN Gateway isn't only:

```text
datacenter ↔ Azure
```

It also supports:

```text
Developer laptop
   ↓
Point-to-Site VPN
   ↓
Azure VNet
```

for remote users.

ExpressRoute is not the normal solution for one developer connecting their laptop.

---

# **10. Production example**

Suppose a company has:

```text
On-prem SAP
Azure APIs
large DB replication
24×7 hybrid dependency
strict latency requirements
```

I'd probably design:

```text
ExpressRoute primary
+
VPN Gateway backup
```

The private, predictable circuit handles normal production traffic.

If ExpressRoute fails:

```text
routes converge
→ VPN backup
```

subject to routing design and capacity.

Importantly, I would size the VPN path so it can carry the **critical subset** of traffic during failover.

A backup that is 1/20th of required capacity may technically connect but still fail the business.

> “VPN Gateway provides encrypted IPsec/IKE connectivity over the public internet, while ExpressRoute provides private dedicated connectivity into Microsoft's network without traversing the public internet. **VPN = encrypted tunnel over the internet; ExpressRoute = private dedicated path to Microsoft.**

**Interview trap:**
**ExpressRoute traffic is not automatically encrypted just because the connection is private.**

# **T34-09. Azure Bastion vs public SSH/RDP?**

**Answer:**

Direct public SSH or RDP means giving the VM a public IP—or another publicly exposed forwarding path—and allowing management traffic such as port 22 or 3389 from the internet. That increases attack surface because the management endpoint can be scanned and attacked.

**Azure Bastion** is a managed PaaS service that lets me connect to the VM using its **private IP address**, so the VM itself doesn't need a public IP or internet-exposed SSH/RDP port. With the normal browser flow, the administrator connects to Bastion over TLS, and Bastion then connects privately to the VM using SSH or RDP.

For Production, I strongly prefer Bastion, VPN, or another controlled private-management path rather than exposing management ports publicly.

```text
Public SSH:

Admin
  ↓ Internet
VM public IP :22


Bastion:

Admin
  ↓ TLS/443
Azure Bastion
  ↓ private VNet
VM private IP :22
```

Microsoft confirms that VMs accessed through Bastion do not require public IP addresses and that Bastion supports SSH/RDP over TLS, including browser-based and, on supported SKUs, native-client connectivity. ([Microsoft Learn][5])

---

## **1. The main security difference is attack surface**

Public Linux VM:

```text
Public IP
22 exposed
```

Attackers can potentially:

```text
discover IP
scan port
attempt password attacks
exploit SSH vulnerabilities
```

Even strong authentication doesn't remove the exposed network surface.

With Bastion:

```text
VM
→ private IP only
```

Internet scanners can't directly connect to:

```text
VM:22
VM:3389
```

because those VM management ports aren't internet-accessible.

# **2. How Bastion works**

Typical dedicated Bastion flow:

```text
Administrator
     ↓
Azure Portal / native client
     ↓ TLS 443
Azure Bastion
     ↓
Azure VNet
     ↓
VM private IP
     ↓
SSH/RDP
```

The VM does not need:

```text
public IP
Bastion agent
special VM software
```

for ordinary Bastion connectivity. ([Microsoft Learn][5])

This is important.

Bastion provides the **network path**.

You still need valid authentication such as:

```text

```

where supported/configured.

So:

```text
Bastion
≠

```

The user still has to prove they should be allowed onto the machine.


So the old statement:

> “Bastion means you can only use a browser.”

is no longer correct.

JIT can reduce exposure for VMs that still have public management paths.

Conceptually:

```text
Port 22 closed normally

Admin requests JIT
      ↓
Port 22 temporarily allowed
      ↓
Time window expires
      ↓
Port closed
```

This is safer than:

```text
0.0.0.0/0 → 22 forever
```

but the VM still participates in a public-access model.

For strict Production designs:

```text
no VM public IP
+
Bastion/private management
```

is usually stronger.

# **11. Bastion cost trade-off**

Public SSH itself doesn't require a dedicated Bastion service.

Bastion has:

```text
service/hourly cost
+

```

and dedicated SKUs incur cost while deployed. ([Microsoft Learn][7])

Therefore for:

```text
tiny lab VM
```

a tightly restricted public IP or Developer Bastion may be acceptable depending on requirements.

For:

```text
enterprise Production
```

the reduction in management-plane attack surface is usually worth far more than the service cost.

# **T34-10. VNet peering vs VPN?**

**Answer:**

Both can connect networks, but they use very different mechanisms.

**VNet peering** directly connects two Azure VNets through the **Microsoft backbone** without requiring a VPN gateway. It provides low-latency, high-bandwidth connectivity and is normally my first choice when I simply need Azure VNets to communicate.

A **VNet-to-VNet VPN** uses Azure VPN Gateways and an **IPsec/IKE tunnel** between the networks. It adds gateway cost, throughput limits, and additional components, but it can be useful when I specifically require tunnel-based encryption, need certain gateway-based routing designs, or need consistency with a broader VPN topology.

So:

```text
Azure VNet ↔ Azure VNet
simple/high-performance connection
→ VNet peering

Need IPsec tunnel/gateway-based connectivity
→ VPN
```

Microsoft states that peering traffic travels directly over Microsoft's backbone, without a gateway or public internet, while VNet-to-VNet VPN connections use VPN gateways and IPsec/IKE. ([Microsoft Learn][8])

---

## **Architecture**

### VNet peering

```text
VNet A
10.1.0.0/16
    │
    │ Azure backbone
    │ direct peering
    ▼
VNet B
10.2.0.0/16
```

No:

```text
VPN Gateway
```

required purely for the VNet-to-VNet connection.

---

### VNet-to-VNet VPN

```text
VNet A
   ↓
VPN Gateway A
   ↓
IPsec/IKE tunnel
   ↓
VPN Gateway B
   ↓
VNet B
```

Now both gateway processing and gateway SKUs are part of the path.

---

# **1. Peering is normally lower latency**

For same-region peering, Microsoft says VM-to-VM latency is effectively comparable to connectivity within one VNet, with throughput primarily constrained by the VM/network resources rather than a peering gateway bottleneck. ([Microsoft Learn][8])

Traffic:

```text
VNet A
→ Microsoft backbone
→ VNet B
```

doesn't first traverse:

```text
gateway A
→ encrypted tunnel
→ gateway B
```

So peering is normally more efficient.

---

# **2. Peering has no VPN gateway bottleneck**

VPN throughput depends on:

```text
VPN Gateway SKU
number of tunnels
encryption
traffic characteristics
```

Peering itself doesn't impose that VPN gateway throughput ceiling.

Therefore for:

```text
high-volume east-west traffic
```

between Azure VNets, peering is usually a stronger choice.

---

# **3. Both require non-overlapping address spaces**

You generally cannot peer:

```text
VNet A = 10.0.0.0/16
VNet B = 10.0.0.0/16
```

because routing would be ambiguous.

Proper IPAM is essential.

This becomes particularly important when building:

```text
20–100 spoke VNets
```

or connecting Azure to acquired companies/on-premises environments.

---

# **4. Peering supports same-region and cross-region connections**

Azure has:

```text
VNet peering
→ VNets in same region

Global VNet peering
→ VNets across regions
```

Both use Microsoft's backbone. ([Microsoft Learn][8])

So:

> “You need VPN to connect VNets in two different Azure regions.”

is incorrect.

Global VNet peering can do that directly.

---

# **5. Peering is non-transitive**

This is probably the most important interview trap.

Suppose:

```text
Spoke A
   ↕ peering
Hub
   ↕ peering
Spoke B
```

It does **not** automatically mean:

```text
Spoke A
↔
Spoke B
```

Azure peering relationships aren't automatically transitive.

Microsoft explicitly calls this out. ([Microsoft Learn][8])

---

# **6. Hub-spoke therefore needs routing design**

If spokes need to communicate through a hub:

```text
Spoke A
   ↓
Azure Firewall/NVA
   ↓
Spoke B
```

you may configure:

```text
UDRs
Allow forwarded traffic
NVA/firewall
```

or choose other supported connectivity constructs.

Do not assume:

```text
A ↔ Hub
and
B ↔ Hub
therefore
A ↔ B
```

---

# **7. Gateway transit is different from transitive peering**

Suppose hub has:

```text
VPN Gateway
```

connected to on-premises.

Spoke can use:

```text
remote gateway
```

through peering, called **gateway transit**.

Architecture:

```text
Spoke
  ↓ peering
Hub
  ↓ VPN Gateway
On-prem
```

Microsoft supports gateway transit for peered VNets. ([Microsoft Learn][8])

But gateway transit does not mean all peering itself suddenly becomes generally transitive.

---

# **8. VPN encrypts network traffic**

A VNet-to-VNet VPN uses:

```text
IPsec/IKE
```

which provides network-level encryption.

Peering traffic stays on Microsoft's backbone but isn't an IPsec tunnel just because the VNets are peered.

For sensitive application data, I would normally still use:

```text
TLS
```

regardless of the underlying Azure connectivity.

---

# **9. VPN can provide an isolation/architecture boundary**

Sometimes an organization deliberately wants:

```text
tunnel-based connection
```

rather than direct peering.

Maybe because of:

```text
network security architecture
routing model
encryption requirement
standardized cross-cloud VPN design
```

Then the extra gateway complexity is justified.

But I wouldn't add VPN Gateways between every Azure VNet simply because VPN sounds “more secure.”

---

# **10. Cost model differs**

Peering has:

```text
data-transfer/peering charges
```

depending on region/scenario.

VPN requires:

```text
VPN Gateway resources
+
gateway running cost
+
data transfer
```

and creates additional operational components.

At scale:

```text
50 VNets
```

the architecture choice materially affects both cost and complexity.

---

# **11. Example**

You have:

```text
App VNet
Database services VNet
same Azure region
high-volume private traffic
```

I would generally use:

```text
VNet peering
```

because it gives:

```text
low latency
high bandwidth
no gateway
Microsoft backbone
```

If instead requirement is:

```text
Azure network
↔
on-prem datacenter
```

then VPN Gateway is appropriate because peering does not connect arbitrary on-premises networks.

> “VNet peering directly connects Azure VNets across the Microsoft backbone without a VPN gateway, so it normally provides lower latency and higher bandwidth and is my first choice for straightforward Azure VNet-to-VNet connectivity. # **T34-11. NAT Gateway vs Load Balancer outbound connectivity?**

**Answer:**

Both can provide explicit outbound internet connectivity for Azure VMs, but they are designed for different primary purposes.

**Azure NAT Gateway** is a dedicated **outbound-only SNAT service** attached at the subnet level. Resources in that subnet use its public IP addresses or prefixes for new outbound connections. It's Azure's recommended general-purpose outbound connectivity option because it provides predictable egress IPs and much better SNAT scale.

A **Standard Azure Load Balancer** is primarily a Layer-4 load-balancing service, but a public Load Balancer can also provide outbound SNAT for members of its backend pool through explicit **outbound rules**.

So:

```text
Need scalable, predictable outbound internet
for a subnet
→ NAT Gateway

Already need a public Load Balancer
and want its backend pool to use
the LB frontend IP for outbound
→ Load Balancer outbound rule may fit
```

Current Microsoft guidance recommends NAT Gateway for most explicit outbound-connectivity scenarios, while Standard Load Balancer outbound rules remain supported when they are appropriate. ([Microsoft Learn][9])

---

## **Architecture**

### NAT Gateway

```text
Subnet
├── VM1
├── VM2
└── VM3
    │
    │ outbound connection
    ▼
NAT Gateway
    │ SNAT
    ▼
Public IP / Prefix
    │
    ▼
Internet
```

NAT Gateway does not receive unsolicited inbound connections for those VMs.

Its purpose is:

```text
outbound connectivity
```

---

### Public Load Balancer outbound rule

```text
Internet
    ▲
    │ outbound SNAT
Public Load Balancer
    │
Backend Pool
├── VM1
├── VM2
└── VM3
```

The Load Balancer may therefore provide both:

```text
inbound load distribution
+
outbound SNAT
```

depending on configuration.

---

# **1. NAT Gateway is subnet-level**

Associate NAT Gateway with:

```text
Subnet A
```

and eligible resources in that subnet use it for new outbound connections.

You don't need to individually add every VM to:

```text
backend pool
```

for NAT purposes.

This makes it easy to standardize egress for:

```text
VMSS
VMs
certain AKS/network scenarios
```

where the compute lives in the associated subnet.

---

# **2. Load Balancer outbound applies to its backend pool**

Load Balancer outbound rule connects:

```text
specific LB backend pool
```

to:

```text
frontend public IP
```

for SNAT.

That means the outbound model is tied more closely to:

```text
Load Balancer membership
```

than to the whole subnet.

This is useful when:

```text
those same VMs already sit
behind that public Load Balancer
```

and sharing the frontend IP is intentional.

---

# **3. NAT Gateway is outbound-only**

NAT Gateway does **not** provide:

```text
Internet user
→ VM
```

inbound load balancing.

It only establishes source NAT for connections initiated from inside.

So you can have:

```text
Public Load Balancer
→ inbound application traffic

NAT Gateway
→ outbound internet traffic
```

in the same architecture.

They are not mutually exclusive.

---

# **4. SNAT port scale is a major reason NAT Gateway is preferred**

For every outbound TCP connection Azure needs a translation such as:

```text
10.1.1.4:53422
        ↓
20.x.x.x:<SNAT-port>
```

High outbound connection counts can exhaust SNAT resources.

NAT Gateway is specifically engineered for high-scale outbound SNAT and is Microsoft's recommended migration target from many legacy/default outbound designs. ([Microsoft Learn][10])

This is especially relevant for workloads doing large numbers of calls to:

```text
external APIs
package repositories
SaaS systems
internet endpoints
```

---

# **5. Predictable outbound IP**

With NAT Gateway:

```text
VM1 ─┐
VM2 ─┼→ NAT Gateway → 20.1.2.3
VM3 ─┘
```

Vendor can allow-list:

```text
20.1.2.3
```

instead of many VM public IPs.

NAT Gateway can also use supported public IP prefixes where more addresses/scale are needed.

Load Balancer outbound rules can likewise provide deterministic frontend IPs, but NAT Gateway is more purpose-built for outbound egress.

---

# **6. Current Azure behavior makes explicit outbound important**

This is especially important in a **2026 interview**.

Microsoft has moved away from relying on implicit/default outbound connectivity. Current guidance says new VNet/private-subnet designs require an **explicit outbound method**, and NAT Gateway is the recommended method for most VM scenarios. ([Microsoft Learn][11])

So I would not design:

```text
VM has no explicit egress
but Azure somehow gives it Internet
```

and depend on that behavior.

Use:

```text
NAT Gateway
Load Balancer outbound rule
Firewall/NVA
or another deliberate method
```

depending on requirements.

---

# **7. NAT Gateway takes precedence over Load Balancer outbound rules**

Important Azure-specific behavior:

If a NAT Gateway is associated with the subnet, new outbound connections normally use:

```text
NAT Gateway
```

instead of:

```text
Load Balancer outbound rule
```

for that subnet.

Microsoft explicitly documents NAT Gateway precedence over Load Balancer outbound rules for new connections. ([Microsoft Learn][12])

So if both exist:

```text
NAT Gateway
wins for new normal outbound flows
```

subject to routing behavior.

---

# **8. But UDR to Firewall/NVA overrides that egress path**

Another important nuance.

Suppose subnet has:

```text
NAT Gateway
```

but also:

```text
UDR:
0.0.0.0/0
→ Azure Firewall
```

Then the route directs traffic to:

```text
Azure Firewall
```

rather than using NAT Gateway directly as the subnet's internet egress.

Microsoft explicitly documents this distinction: NAT Gateway precedence applies among outbound methods, but a UDR to an NVA/firewall changes the route itself. ([Microsoft Learn][13])

So:

```text
Routing first determines
where the packet goes.

SNAT design then applies
to that path.
```

---

# **9. Central firewall architecture is different**

If security requirement says:

> Every internet connection must be inspected.

Then don't attach NAT Gateway to each spoke and let applications bypass inspection.

Use:

```text
Spoke subnet
   ↓ UDR
Azure Firewall
   ↓
Internet
```

If additional SNAT scale is needed, NAT Gateway can be integrated with the firewall architecture appropriately rather than becoming an alternate spoke bypass.

NAT Gateway is an egress translation service.

It is **not a security inspection firewall**.

---

# **10. Load Balancer is still necessary for inbound workloads**

Suppose:

```text
Internet users
→ Web VMs
```

Need:

```text
Azure Load Balancer
```

for Layer-4 inbound distribution.

Then outbound can still separately use:

```text
NAT Gateway
```

Architecture:

```text
               Internet
                  │
        inbound   │
                  ▼
          Public Load Balancer
                  │
              VM subnet
                  │
                  ▼ outbound
             NAT Gateway
                  │
                  ▼
               Internet
```

This cleanly separates:

```text
Inbound L4 distribution
```

from:

```text
Outbound SNAT
```

---

# **11. NAT Gateway doesn't replace Application Gateway or Load Balancer**

A common misconception:

> “If I attach NAT Gateway, I don't need a Load Balancer.”

Wrong.

NAT Gateway has no concept of:

```text
backend health
frontend listener
incoming application connections
load distribution
```

It handles outbound SNAT.

You still need the appropriate inbound service:

```text
Load Balancer
Application Gateway
Front Door
```

based on the workload.

---

# **12. Example: VMSS application**

VMSS runs:

```text
20 backend VMs
```

Requirements:

```text
Inbound TCP traffic
+
Outbound API calls
+
vendor requires fixed egress IP
+
high connection volume
```

I might use:

```text
Standard Load Balancer
→ inbound connections

NAT Gateway
→ outbound connections
```

This is often cleaner than forcing the Load Balancer to solve both requirements.

---

# **13. Troubleshooting outbound failures**

Dependency order:

```text
Application
   ↓
DNS
   ↓
Effective route
   ↓
Outbound method
   ↓
SNAT capacity
   ↓
NSG/firewall
   ↓
Internet destination
```

If no internet:

First check:

```bash
az network nic show-effective-route-table ...
```

If route says:

```text
0.0.0.0/0 → VirtualAppliance
```

traffic is going toward a firewall/NVA, not directly to the NAT Gateway.

If routing is correct but high-scale connections intermittently fail:

```text
SNAT behavior/port exhaustion
```

becomes a candidate.

## **Quick comparison**

| Capability                    | NAT Gateway       | Load Balancer outbound rule |
| ----------------------------- | ----------------- | --------------------------- |
| Main purpose                  | **Outbound SNAT** | Primarily L4 load balancing |
| Scope                         | **Subnet**        | Backend pool                |
| Inbound load balancing        | No                | **Yes**                     |
| Predictable egress IP         | **Yes**           | Yes                         |
| High SNAT scalability         | **Excellent**     | More constrained            |
| Backend pool required         | No                | **Yes**                     |
| Recommended general VM egress | **Yes**           | Supported alternative       |
| Can coexist with inbound LB   | **Yes**           | N/A                         |

---

### **Interview answer condensed**

> “NAT Gateway is a dedicated subnet-level outbound SNAT service, while Load Balancer is primarily a Layer-4 traffic-distribution service that can also provide outbound connectivity to members of its backend pool through outbound rules. For new Azure designs where I need scalable, predictable internet egress, I would normally prefer NAT Gateway. I might use Load Balancer outbound rules when those backend VMs already use the Load Balancer and the simpler outbound requirement fits. NAT Gateway doesn't replace the Load Balancer for inbound traffic, and if both NAT Gateway and LB outbound rules exist, new outbound flows generally prefer NAT Gateway. A UDR to Azure Firewall or another NVA is different because the route itself sends traffic to that appliance.”

**Memory line:**
**NAT Gateway is built for outbound SNAT; Load Balancer is built for distributing network traffic and can also provide outbound SNAT.**

**Interview trap:**
NAT Gateway **does not provide inbound load balancing or firewall inspection**, and a `0.0.0.0/0` UDR to a firewall can change the egress path even when NAT Gateway exists.

**Keywords:**
NAT Gateway, Azure Load Balancer, outbound rule, SNAT, public IP, subnet, backend pool, explicit outbound connectivity, UDR.

* If both NAT Gateway and Load Balancer outbound rules exist, which is used?
* Why is NAT Gateway less prone to outbound SNAT scaling problems?
* Can NAT Gateway receive inbound internet connections?
* What happens if the subnet also has a `0.0.0.0/0` UDR to Azure Firewall?
