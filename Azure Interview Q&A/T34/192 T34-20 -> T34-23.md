### **T34-20. LRS vs ZRS?**

**Answer:**

Both are Azure Storage redundancy options **within a single Azure region**, but they protect against different failure scopes.

**LRS — Locally Redundant Storage** keeps multiple synchronous copies of the data within a single physical datacenter in the selected Azure region. It protects against individual disk, server, and rack failures, but that datacenter remains the shared failure domain.

**ZRS — Zone-Redundant Storage** synchronously replicates data across **three or more Availability Zones within the same Azure region**. Because those zones have independent power, cooling, and networking, ZRS can keep data available for reads and writes even if one zone becomes unavailable.

So my rule is:

```text
Lowest-cost local redundancy
and zone failure isn't a requirement
→ LRS

Production workload requiring
single-region zone resilience
→ ZRS
```

Microsoft currently recommends ZRS for workloads that need high availability within a region. LRS provides at least **11 nines of annual object durability**, while ZRS provides at least **12 nines**. ([Microsoft Learn][1])

---

## **Architecture**

### LRS

```text
Azure Region
┌──────────────────────────────────┐
│                                  │
│      Single datacenter           │
│                                  │
│    Copy 1                        │
│    Copy 2                        │
│    Copy 3                        │
│                                  │
└──────────────────────────────────┘
```

The replicas protect against:

```text
Disk failure
Server failure
Rack failure
```

But they share the same larger datacenter failure domain.

A major:

```text
fire
flood
power/cooling incident
datacenter outage
```

can therefore affect all LRS replicas. ([Microsoft Learn][1])

---

## **ZRS**

```text
                   Azure Region

┌────────────┐ ┌────────────┐ ┌────────────┐
│   Zone 1   │ │   Zone 2   │ │   Zone 3   │
│            │ │            │ │            │
│ Data copy  │ │ Data copy  │ │ Data copy  │
└────────────┘ └────────────┘ └────────────┘
       │              │              │
       └──────── synchronous ────────┘
```

Each Availability Zone represents a physically separated infrastructure location.

The write succeeds only after Azure has synchronously replicated the data to the required replicas across zones. ([Microsoft Learn][1])

---

## **1. The main distinction is failure domain**

### LRS protects against

```text
disk
server
rack
```

failures.

### ZRS additionally protects against

```text
Availability Zone / datacenter failure
```

within the region.

This is the key interview answer.

---

## **2. ZRS remains available during a zone outage**

Suppose:

```text
Storage Account
→ ZRS
```

and:

```text
Zone 1 becomes unavailable
```

Azure can continue servicing:

```text
READ
WRITE
```

from the remaining zones.

There may still be transient networking/DNS effects while Azure reacts, so applications should use proper retry logic and exponential backoff. Microsoft specifically recommends transient-fault handling for ZRS applications. ([Microsoft Learn][1])

---

## **3. LRS doesn't provide the same zone resilience**

Suppose:

```text
LRS Storage
→ Datacenter A
```

and that datacenter has a major outage.

All local replicas can become unavailable together.

Therefore:

```text
3 copies
```

does not necessarily mean:

```text
3 independent failure domains.
```

That's a crucial reliability principle.

---

## **4. Both are single-region strategies**

Another important distinction:

```text
LRS
→ one region

ZRS
→ one region
```

ZRS protects against:

```text
zone failure
```

but not necessarily:

```text
complete Azure region failure
```

If regional disaster protection is required, look at:

```text
GRS
GZRS
RA-GRS
RA-GZRS
```

depending on access requirements.

---

## **5. ZRS is not asynchronous DR**

ZRS replication between zones is:

```text
synchronous
```

within the region.

Therefore after a successful write, you don't normally think:

```text
"Maybe Zone 2 is minutes behind."
```

in the same way you would with asynchronous geo-replication.

That is why ZRS can provide strong single-region consistency and availability.

---

## **6. Durability vs availability**

Don't confuse these.

Microsoft currently states approximately:

```text
LRS
≥ 99.999999999%
11 nines durability/year

ZRS
≥ 99.9999999999%
12 nines durability/year
```

([Microsoft Learn][1])

But:

```text
Durability
=
probability the stored object survives

Availability
=
ability to access it when needed
```

They're related but different.

ZRS's major operational advantage isn't merely “one extra nine.”

It's:

```text
zone failure
→ storage can continue serving
```

---

## **7. Replication isn't backup**

This is very important.

Suppose an application executes:

```text
DELETE important-file.csv
```

Azure faithfully replicates that deletion.

Likewise:

```text
overwrite good data with bad data
```

gets replicated.

Microsoft explicitly notes that all redundant replicas reflect the same current state; redundancy protects primarily against infrastructure failures, not application-level deletes or overwrites. ([Microsoft Learn][1])

Therefore:

```text
LRS/ZRS
≠
backup
```

You may still need:

```text
soft delete
versioning
snapshots
Azure Backup
immutability
```

depending on the workload.

## **8. Practical example**

### Development Storage

Requirement:

```text
Low cost
Rebuildable data
No strict zone SLA
```

LRS might be reasonable.

### Production application uploads

Requirement:

```text
Business-critical data
Application spans multiple AZs
Zone failure should not interrupt storage
```

I'd strongly consider:

```text
ZRS
```

because deploying compute across zones while using LRS would leave storage as a larger failure domain.

---

## **9. Azure Files is an especially good ZRS case**

Microsoft currently recommends ZRS for Azure Files workloads where supported.

If a zone fails, clients don't need to remount the share merely because the underlying zone became unavailable. ([Microsoft Learn][1])

Architecture:

```text
VM Zone 1 ─┐
VM Zone 2 ─┼── Azure Files ZRS
VM Zone 3 ─┘
```

This aligns compute and storage availability design.

## **10. Cost trade-off**

Generally:

```text
LRS
→ cheapest redundancy option

ZRS
→ higher cost
   for stronger availability
```

So I don't blindly choose ZRS for every disposable development artifact.

But for important Production state, saving a small amount on redundancy while operating a multi-zone application can be a poor trade-off.

| Characteristic             | LRS            | ZRS                             |
| -------------------------- | -------------- | ------------------------------- |
| Replication scope          | One datacenter | **Multiple Availability Zones** |
| Region count               | 1              | 1                               |
| Synchronous replication    | Yes            | **Yes**                         |
| Disk/server/rack failure   | Protected      | Protected                       |
| Zone/datacenter failure    | Weak           | **Protected**                   |
| Region-wide disaster       | No             | No                              |
| Annual object durability   | ≥11 nines      | **≥12 nines**                   |
| Cost                       | **Lower**      | Higher                          |
| Production zone resilience | Limited        | **Better**                      |

### **Interview answer condensed**

> “LRS and ZRS both replicate Azure Storage data within one region. LRS keeps the replicas within a single physical datacenter, so it protects against disk, server, and rack failures but not a datacenter-level failure. ZRS synchronously copies the data across three or more Availability Zones in the region, so reads and writes can continue if one zone becomes unavailable. I would generally choose LRS for lower-cost or easily recoverable workloads and ZRS for production workloads that require single-region zone resilience. Neither one by itself protects against a complete regional disaster.”

**Memory line:**
**LRS survives local hardware failure; ZRS also survives an Availability Zone failure.**

**Interview trap:**
Having multiple LRS copies does **not** mean they are spread across independent Availability Zones.

**Keywords:**
LRS, ZRS, synchronous replication, Availability Zones, durability, single region, zone resilience.

**Likely follow-ups:**

* Does ZRS protect against an entire Azure region failure?
* Is ZRS replication synchronous or asynchronous?
* Is LRS/ZRS a replacement for backups?
* Why might a multi-zone application still fail if its Storage uses LRS?

### **T34-21. GRS vs GZRS?**

**Answer:**

Both provide **cross-region Azure Storage replication**, but the difference is how the data is protected inside the **primary region**.

With **GRS — Geo-Redundant Storage**, Azure first uses **LRS in the primary region**, meaning the primary copies are within one local datacenter, and then asynchronously replicates the data to a secondary Azure region. The secondary also uses LRS.

With **GZRS — Geo-Zone-Redundant Storage**, Azure uses **ZRS across Availability Zones in the primary region** and then asynchronously replicates the data to the secondary region, where it is stored using LRS.

So:

```text
GRS
= LRS primary
+ asynchronous geo-replication
+ LRS secondary

GZRS
= ZRS primary
+ asynchronous geo-replication
+ LRS secondary
```

For a critical Production workload that needs both **zone resilience and regional disaster protection**, I would normally prefer GZRS where supported.

Both are designed for at least **16 nines of annual object durability**. ([Microsoft Learn][1])

---

## **Architecture**

### GRS

```text
             Primary Region
          Single datacenter
         ┌───────────────┐
         │ LRS copies    │
         │ 1  2  3       │
         └───────┬───────┘
                 │
                 │ asynchronous
                 ▼
          Secondary Region
         ┌───────────────┐
         │ LRS copies    │
         │ 1  2  3       │
         └───────────────┘
```

---

### GZRS

```text
                 Primary Region

        Zone 1       Zone 2       Zone 3
           \            |            /
            \------ synchronous -----/
                       ZRS
                        │
                        │ asynchronous
                        ▼
                 Secondary Region
                       LRS
                  copy copy copy
```

The geo-replication mechanism is asynchronous in both cases.

The key improvement in GZRS is:

```text
Primary region
→ already zone resilient
```

before a regional failover is needed. ([Microsoft Learn][1])

## **1. Zone outage is where GZRS clearly wins**

Suppose one primary-region Availability Zone fails.

### GZRS

Because primary storage uses:

```text
ZRS
```

applications can normally continue:

```text
READ
WRITE
```

using the remaining zones.

### GRS

Primary storage is based on:

```text
LRS
```

so it doesn't provide the same in-region zone-level availability.

This distinction is much more operationally important than merely remembering the acronyms.

---

## **2. Both protect data against regional disaster**

Both asynchronously maintain a copy in a geographically separate secondary Azure region.

Therefore, if:

```text
Primary Region
→ catastrophic outage
```

the secondary can be used through an appropriate Storage failover process. ([Microsoft Learn][2])

This provides a DR capability that:

```text
LRS
ZRS
```

alone do not provide.

---

# **3. Asynchronous replication means RPO isn't automatically zero**

This is one of the most important interview points.

Flow:

```text
Application write
      ↓
Primary commit succeeds
      ↓
response to application
      ↓
async copy to secondary
```

Suppose:

```text
Primary acknowledges write
```

but regional disaster occurs:

```text
before secondary receives it
```

That latest write can be lost during failover.

Therefore:

```text
GRS/GZRS
regional failover
can have non-zero RPO
```

Microsoft explicitly documents that geo-replication is asynchronous. ([Microsoft Learn][1])

Don't tell an interviewer:

> “GRS means zero data loss across regions.”

That's incorrect.

---

# **4. Secondary isn't normally writable**

For normal:

```text
GRS
GZRS
```

the secondary region isn't an active multi-write copy.

Before failover:

```text
Primary
→ READ/WRITE

Secondary
→ internal replica
```

After failover:

```text
Secondary
→ becomes new primary
→ READ/WRITE
```

So this isn't equivalent to an active-active database architecture.

---

# **5. Read access requires the RA variants**

Another classic Azure distinction.

### GRS

```text
secondary readable?
No, not normally
```

### RA-GRS

```text
secondary read endpoint
→ available
```

Similarly:

```text
GZRS
→ secondary isn't normally app-readable

RA-GZRS
→ secondary read access enabled
```

Microsoft specifically states that GRS/GZRS don't provide user read/write access to the secondary unless failover occurs, while RA-GRS and RA-GZRS provide read access before failover. ([Microsoft Learn][1])

---

# **6. RA does not mean writes can go to both regions**

With:

```text
RA-GZRS
```

you can have:

```text
Primary:
read/write

Secondary:
read
```

It doesn't mean:

```text
Primary:
read/write

Secondary:
read/write
```

This is not multi-master Storage.

---

# **7. Failover changes service endpoint mapping**

During account failover, Azure updates Storage DNS/service endpoint behavior so that the former secondary becomes the new primary endpoint. ([Microsoft Learn][2])

Conceptually:

```text
Before:

storageaccount endpoint
        ↓
Primary Region A


After failover:

storageaccount endpoint
        ↓
Region B
(new primary)
```

Applications shouldn't generally have to be rewritten to a completely different account name solely because of the Storage account failover.

---

# **8. Failover is not instant**

Don't think:

```text
Primary region fails
→ secondary immediately active
in zero seconds
```

Failover is an operational process.

During failover there can be a period when data is inaccessible until the secondary becomes primary. ([Microsoft Learn][3])

Therefore your DR plan must define:

```text
RTO
RPO
failover authority
testing
application behavior
```

not just select `GZRS` and declare DR solved.

---

# **9. GZRS protects against a smaller failure without invoking DR**

This is one of GZRS's strongest advantages.

Suppose:

```text
Zone 2 fails
```

### GZRS

```text
remaining primary zones
→ service continues
```

No regional failover required.

### GRS

Because primary is LRS, you don't have the same zonal distribution locally.

So GZRS handles:

```text
common/localized infrastructure failure
```

with high availability, while still keeping:

```text
secondary region
```

for full regional disaster.

# **10. Durability**

Microsoft currently lists both:

```text
GRS
GZRS
```

at:

```text
≥ 99.99999999999999%
```

So the key reason to prefer GZRS isn't:


### **Interview answer condensed**

> “GRS and GZRS both asynchronously replicate Azure Storage data to a secondary region for regional disaster protection. The difference is the primary region. GRS uses LRS in the primary, while GZRS uses ZRS across Availability Zones in the primary. The secondary copy uses LRS in both cases. So GZRS gives me both zone resilience during normal regional operation and geo-redundancy for a complete regional disaster. Because geo-replication is asynchronous, neither guarantees zero data loss during regional failover. If I need read access to the secondary before failover, I'd look at RA-GRS or RA-GZRS.”

**Memory line:**
**GRS = local primary + geo copy; GZRS = zonal primary + geo copy.**

**Interview trap:**
GRS/GZRS replication to the secondary region is **asynchronous**, so regional failover does not imply an RPO of zero.

### **T34-22. Blob Storage vs Azure Files?**

**Answer:**

The main difference is **object storage versus file-system storage**.

**Azure Blob Storage** is massively scalable **object storage**. Applications normally access objects through Azure Storage REST APIs, SDKs, HTTP/S, or data-processing tools. It's ideal for unstructured data such as images, videos, backups, logs, documents, application artifacts, and data lakes.

**Azure Files** provides a fully managed **network file share** that applications and operating systems can mount using standard protocols such as **SMB** or **NFS**. It is useful when an application expects directories, files, shared file-system semantics, or multiple machines mounting the same share.

So:

```text
Application is object-aware
and can use REST/SDK/HTTP
→ Blob Storage

Application expects a mounted
shared file system
→ Azure Files
```

Microsoft describes Blob Storage as a massively scalable object store and Azure Files as fully managed cloud file shares. Current Azure Files supports SMB and NFS file shares. ([Microsoft Learn][4])

## **Architecture**

### Blob Storage

```text
Application
    │
    ├── REST API
    ├── Azure SDK
    └── HTTPS
          ↓
      Blob endpoint
          ↓
       Container
          ↓
         Blob
```

Example:

```text
https://account.blob.core.windows.net/images/photo.jpg
```

The application treats:

```text
photo.jpg
```

primarily as an object.

### Azure Files

```text
VM1 ──┐
VM2 ──┼── SMB/NFS ── Azure File Share
VM3 ──┘
```

Clients can interact using familiar file operations:

```text
open
read
write
rename
directory traversal
file locking
```

according to the selected protocol/platform semantics.

# **1. Blob is object storage**

Object storage organizes data conceptually as:

```text
Container
   ↓
Blob object
```

An object has:

```text
data
metadata
name/key
```

This model scales extremely well for huge numbers of unstructured objects.

Typical Blob workloads:

```text
Application uploads
Videos
Images
Logs
Backups
Static content
Data Lake
Build artifacts
```

---

# **2. Azure Files is shared file storage**

Azure Files provides familiar:

```text
directories
files
mount points
shares
```

An application can mount it similarly to an on-prem file server.

Examples:

### Windows

```text
\\mystorage.file.core.windows.net\share
```

### Linux

Mounted through supported:

```text
SMB
or
NFS
```

depending on the share configuration.

Azure Files currently supports SMB and NFS as its primary industry-standard file-system protocols. ([Microsoft Learn][5])

# **3. Blob normally requires object-aware application behavior**

Suppose an old application expects:

```text
C:\Shared\Invoices\2026\invoice.pdf
```

and performs standard file-system operations.

Replacing that path with Blob Storage usually isn't transparent.

The application may need to be changed to use:

```text
Azure Blob SDK
REST API
```

and object semantics.

Azure Files may enable:

```text
lift and shift
```

with fewer code changes because the application can continue seeing a mounted file share.

Microsoft specifically lists lift-and-shift applications expecting shared files as a core Azure Files use case. ([Microsoft Learn][6])

# **4. Multiple clients**

Azure Files is designed for shared access:

```text
App VM1 ─┐
App VM2 ─┼→ Same File Share
App VM3 ─┘
```

Thousands of supported clients can access shares concurrently depending on tier/limits. ([Microsoft Learn][5])

Blob can also be accessed by huge numbers of clients, but through:

```text
object/API semantics
```

rather than presenting a traditional shared mounted filesystem to each client.

# **5. Authentication models differ in practice**

Blob commonly uses:

```text
Microsoft Entra ID
Managed Identity
Storage data-plane RBAC
SAS
Shared Key where still necessary
```

Azure Files also supports Azure/storage authentication options, but SMB enterprise workloads often need considerations such as:

```text
identity-based SMB authentication
Active Directory integration
share-level permissions
file/directory ACLs
```

depending on environment.

So migrating a traditional corporate file server to Azure Files can involve identity and ACL planning, not merely copying files.

# **6. Private networking works with both**


where supported.

For sensitive data:

```text

    ↓

```

# **7. Blob supports data lifecycle/tiering especially well**

Blob workloads often benefit from access tiers such as:

```text
Hot
Cool

```

subject to Storage account/blob capabilities.

This is attractive for:

```text

logs

```

where access frequency decreases over time.

A lifecycle policy can move objects between tiers or delete them according to rules.

That's one reason Blob is strong for large object repositories.

# **8. Azure Files is better for filesystem-dependent applications**

Examples:

```text
legacy Windows application
→ shared UNC path

→ NFS share

→ shared file location

→ shared persistent volume
```

Microsoft specifically lists shared app configuration, logs, lift-and-shift applications, and container persistent storage as Azure Files use cases. ([Microsoft Learn][6])

# **9. Blob is often better for cloud-native object workloads**

Example web application:

```text
User uploads profile picture
       ↓
API
       ↓
Blob Storage
       ↓
URL/object reference stored in DB
```

This is usually cleaner than mounting a shared network filesystem to every application instance.

Benefits can include:

```text
massive object scale
HTTP-native access
independent application instances
easy lifecycle management
```

---

# **10. Azure Files is not just “Blob with folders”**

Azure Files provides actual network file protocols and file-share semantics.

Blob paths like:

```text
images/2026/photo.jpg
```

can appear hierarchical, especially with Data Lake hierarchical namespace, but that does not make ordinary Blob Storage equivalent to an SMB/NFS file share.

Choose according to **access semantics**, not just whether the names contain `/`.

---

# **11. Performance profile differs**

Blob Storage is optimized for object workloads.

Azure Files is optimized around shared filesystem IO.

So instead of asking:

```text
Which one is faster?
```

I ask:

```text
What access pattern does the application require?
```

Examples:

```text
Millions of media objects
→ Blob

Shared app files through SMB
→ Azure Files
```

Trying to force one service into the other's semantics can produce unnecessary complexity.

Legacy:

```text

      ↓

      ↓

```

```text

      ↓
```

> “Blob Storage is Azure's object-storage service, while Azure Files provides managed shared file systems. **Blob gives applications objects; Azure Files gives machines and applications a shared filesystem.**

### **T34-23. Managed disk vs Azure Files?**

**Answer:**

The main distinction is **block storage versus shared file storage**.

An **Azure Managed Disk** is block-level storage designed primarily to be attached to an Azure VM. To the operating system it behaves like a virtual disk, similar to attaching an SSD or SAN LUN to a server. The VM partitions it, formats it with a filesystem such as NTFS, ReFS, ext4, or XFS, and uses it for an OS disk or application/data storage.

**Azure Files**, on the other hand, is a fully managed network file service. Clients mount a file share over **SMB or NFS**, and multiple machines can access the same managed filesystem concurrently.

So:

```text
VM needs local-like block storage,
OS disk, database volume,
low-latency attached disk
→ Managed Disk

Multiple machines/applications need
a managed shared filesystem
→ Azure Files
```

Microsoft describes Managed Disks as block-level storage volumes for Azure VMs and Azure Files as fully managed SMB/NFS file shares. ([Microsoft Learn][7])

---

## **Architecture**

### Managed Disk

```text
Azure VM
   │
   │ block device
   ▼
Managed Disk
   │
   ├── partitions
   └── filesystem
       NTFS/ext4/XFS/etc.
```

The OS sees something conceptually like:

```text
/dev/sdc
```

or a Windows disk volume.

---

### Azure Files

```text
VM1 ──┐
VM2 ──┼── SMB/NFS ── Azure File Share
VM3 ──┘
```

Azure runs the managed file service.

Clients see:

```text
share
directories
files
```

without managing the underlying disk filesystem themselves.

---

# **1. Managed Disk is block storage**

A managed disk exposes:

```text
blocks/sectors
```

rather than:

```text
shared directories and files
```

directly.

The operating system decides:

```text
partition table
filesystem
mount point
```

Example Linux:

```text
Managed Disk
   ↓
/dev/sdc
   ↓
ext4
   ↓
/var/lib/myapp
```

Microsoft compares Managed Disks to physical disks in traditional servers, except Azure manages the underlying storage infrastructure. ([Microsoft Learn][7])

---

# **2. Azure Files already provides the filesystem**

With Azure Files:

```text
Azure manages
the file service
```

The VM mounts:

```text
SMB share
or
NFS share
```

The client doesn't receive a raw block device that it must partition.

This is a major operational difference.

---

# **3. Managed Disk is the normal VM OS disk**

Every Azure VM requires an:

```text
OS disk
```

and Managed Disk is the standard storage model for that.

Example:

```text
VM
├── OS disk
│   → Managed Disk
│
└── Data disk
    → Managed Disk
```

You would not normally say:

```text
"Boot my Azure VM directly
from an Azure Files SMB share."
```

That's not the normal architecture.

---

# **4. Managed Disk is excellent for VM database/data volumes**

Suppose SQL Server or another database runs inside an Azure VM.

It may require:

```text
low latency
high IOPS
predictable disk throughput
```

Managed Disk tiers include options such as:

```text
Standard HDD
Standard SSD
Premium SSD
Premium SSD v2
Ultra Disk
```

according to workload needs. ([Microsoft Learn][7])

For classic VM-hosted database block storage, Managed Disk is generally a natural choice.

---

# **5. Azure Files is naturally shared**

Suppose:

```text
VM1
VM2
VM3
```

all need:

```text
/shared/reports
```

Azure Files gives them:

```text
one managed share
```

over SMB/NFS.

This is much simpler than trying to coordinate three independent ordinary VM disks.

---

# **6. Managed Disks have a shared-disk capability—but that's not Azure Files**

This is an important advanced interview nuance.

Azure supports **shared managed disks** for certain disk SKUs.

Architecture:

```text
VM1 ─┐
VM2 ─┼→ Shared Managed Disk
VM3 ─┘
```

But Azure does **not** magically provide a fully managed multi-client SMB/NFS filesystem on top of that disk.

Shared disks are intended for clustered applications and require something such as:

```text
Windows Server Failover Cluster
Pacemaker
```

to coordinate access and locking using SCSI persistent reservations. ([Microsoft Learn][8])

So:

```text
Shared Managed Disk
≠
Azure Files
```

---

# **7. Why a cluster manager is necessary for shared disks**

Imagine two VMs directly writing arbitrary filesystem metadata to the same block device without coordination:

```text
VM1 writes filesystem structure
VM2 writes same structure
```

Result can be:

```text
corruption
```

Traditional filesystems aren't automatically safe for multiple independent writers at raw block level.

Shared-disk clustering uses:

```text
SCSI Persistent Reservations
cluster coordination
```

to control which node can write.

Microsoft explicitly states that shared Managed Disks require cluster software such as WSFC or Pacemaker. ([Microsoft Learn][9])

---

# **8. Network path differs**

### Managed Disk

Presented to the VM as attached block storage through Azure's disk infrastructure.

Application typically accesses:

```text
local filesystem path
```

after OS formatting/mounting.

### Azure Files

Application accesses:

```text
network filesystem
```

over:

```text
SMB
or
NFS
```

Therefore networking considerations such as:

```text
DNS
TCP connectivity
Private Endpoint
SMB port availability
identity
```

can matter directly to Azure Files access.

---

# **9. Availability architecture differs**

Suppose:

```text
VM1
→ Managed Disk
```

VM1 goes down.

The disk remains durable, but:

```text
application availability
```

depends on whether another VM can take over and how the workload is architected.

Azure Files is itself a managed shared service, so multiple application nodes can independently mount the same share.

Example:

```text
App VM A ─┐
App VM B ─┼→ Azure Files ZRS
App VM C ─┘
```

That can make shared application-state scenarios much simpler.

Microsoft currently recommends ZRS for Azure Files when high availability within a region is required. ([Microsoft Learn][1])

---

# **10. Managed Disk performance is tightly associated with disk/VM limits**

Performance can depend on:

```text
Disk SKU
Provisioned IOPS
Provisioned throughput
Disk size/tier
VM disk limits
Host caching
```

So even if:

```text
Premium SSD supports X IOPS
```

a small VM SKU may not be capable of consuming all of that throughput.

For VM performance troubleshooting, always consider:

```text
Disk limit
AND
VM limit
```

---

# **11. Azure Files performance depends on share/service characteristics**

For Azure Files, think about:

```text
HDD vs SSD tier
share size/provisioned performance model
SMB/NFS
network path
client concurrency
```

rather than VM-attached disk limits alone.

Current Azure Files supports both HDD and SSD media for SMB scenarios, while NFS is currently SSD-based in the documented planning model. ([Microsoft Learn][5])

---

# **12. Example — web application scratch/application disk**

One VM needs:

```text
/var/lib/application
```

with high random IO and no sharing requirement.

Use:

```text
Managed Disk
```

because the workload wants attached block storage.

---

# **13. Example — shared uploaded documents**

Three web servers need:

```text
/shared/customer-documents
```

and the application expects filesystem APIs.

Use:

```text
Azure Files
```

because every server can mount the same share.

Architecture:

```text
Load Balancer
   ↓
 ┌─────┬─────┬─────┐
 VM1   VM2   VM3
   \     |     /
    \    |    /
     Azure Files
```

---

# **14. Example — SQL Server Failover Cluster**

This is where the shared-disk exception matters.

SQL Server FCI expects:

```text
shared block storage
+
cluster ownership
```

A supported shared Managed Disk can fit:

```text
Node A ─┐
        ├→ Shared Managed Disk
Node B ─┘
      WSFC controls ownership
```

That is very different from:

```text
three normal application servers
→ shared SMB files
```

where Azure Files is the natural choice.

---

# **15. Backup/recovery design remains separate**

Neither:

```text
Managed Disk
```

nor:

```text
Azure Files
```

should be selected purely because you assume redundancy means backup.

Depending on requirements, consider:

```text
Azure Backup
snapshots
File share snapshots
soft delete
application-consistent backup
```

Redundancy helps infrastructure durability.

Backup helps recover from:

```text
accidental deletion
corruption
ransomware
bad application writes
```

## **Quick comparison**

| Characteristic                    | Managed Disk                              | Azure Files                    |
| --------------------------------- | ----------------------------------------- | ------------------------------ |
| Storage type                      | **Block**                                 | **File**                       |
| Main consumer                     | Azure VM                                  | Multiple cloud/on-prem clients |
| OS disk support                   | **Yes**                                   | No normal VM OS-disk use       |
| Data disk                         | **Yes**                                   | Mounted share instead          |
| SMB/NFS managed share             | No                                        | **Yes**                        |
| Filesystem managed by             | VM/OS                                     | **Azure Files service**        |
| Multi-client sharing              | Normally single VM; shared-disk exception | **Native use case**            |
| Shared disk needs cluster manager | **Yes**                                   | No raw-disk cluster manager    |
| VM database volume                | **Strong fit**                            | Workload-specific              |
| Shared application directory      | Not normal fit                            | **Strong fit**                 |

### **Interview answer condensed**

> “Managed Disk is Azure block storage for VMs. The VM sees it like a physical disk, partitions and formats it, and uses it as an OS or data disk. Azure Files is a managed network filesystem that clients mount over SMB or NFS and is designed for shared file access from multiple machines. So I'd use Managed Disk for VM-local block workloads such as OS disks or high-performance database volumes, and Azure Files when several servers or applications need the same file share. Azure does support shared Managed Disks for clustered applications, but those are shared block devices requiring cluster coordination such as WSFC or Pacemaker—they aren't equivalent to Azure Files.”

**Memory line:**
**Managed Disk gives a VM blocks; Azure Files gives clients a managed shared filesystem.**

**Interview trap:**
A **shared Managed Disk is not an SMB/NFS file share**—multiple writers require cluster coordination such as WSFC or Pacemaker.

**Keywords:**
Managed Disk, Azure Files, block storage, file storage, SMB, NFS, OS disk, data disk, shared disk, SCSI PR.
