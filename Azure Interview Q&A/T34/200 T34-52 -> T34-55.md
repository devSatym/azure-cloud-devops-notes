### **T34-52. Azure SQL vs Cosmos DB?**

**Answer:**

I choose between Azure SQL and Cosmos DB primarily based on the **data model, transaction/query requirements, and scaling pattern**.

**Azure SQL Database** is a fully managed relational database built on the SQL Server engine. It's usually my first choice when the application has strongly relational data, needs SQL joins, constraints, relational transactions, well-defined schemas, and traditional relational reporting/query patterns.

**Azure Cosmos DB** is designed for highly distributed, horizontally scalable applications. Its most common usage is document/NoSQL-style workloads where I need very high throughput, low-latency access, partition-based horizontal scaling, flexible schemas, and potentially global multi-region reads and writes. Cosmos DB also gives configurable consistency levels.

So my rule is:

```text
Strong relational model
+ joins
+ relational transactions
+ SQL ecosystem
→ Azure SQL

Massive horizontal scale
+ flexible/document data
+ partition-based access
+ global low-latency distribution
→ Cosmos DB
```

One important 2026 nuance is that describing Cosmos DB as **“only a NoSQL database”** is increasingly too simplistic—Microsoft now describes Cosmos DB as a distributed database platform with multiple APIs and both NoSQL and relational capabilities. But for the classic interview comparison, the architectural distinction between relational Azure SQL and globally distributed Cosmos workloads remains the most useful mental model. Azure SQL is a fully managed SQL Server-based PaaS database, while Cosmos DB is designed around distributed partitioning and global distribution. ([Microsoft Learn][1])

---

## **1. Start with the data model**

### Azure SQL

Think:

```text
Customers
    │
    ├── CustomerId PK
    └── Name

Orders
    │
    ├── OrderId PK
    ├── CustomerId FK
    └── Amount

Customers
    ↓ JOIN
Orders
```

The relational engine naturally gives me:

```text
tables
rows
columns
primary keys
foreign keys
constraints
joins
indexes
transactions
```

This is excellent for:

```text
financial records
ERP
CRM
order management
inventory
business systems
```

where relationships and transactional correctness matter.

---

### Cosmos DB

For the common API for NoSQL model, I might represent an order as a self-contained document:

```json
{
  "id": "order-5829",
  "customerId": "cust-42",
  "status": "paid",
  "items": [
    {
      "sku": "ABC",
      "quantity": 2
    }
  ]
}
```

The design often favors:

```text
denormalized documents
partition-aligned access
high-volume point reads/writes
```

rather than normalizing everything into many relational tables and joining them continuously.

---

# **2. Azure SQL favors relational queries**

Suppose I need:

```sql
SELECT
    c.Name,
    SUM(o.Amount)
FROM Customers c
JOIN Orders o
    ON c.CustomerId = o.CustomerId
GROUP BY c.Name;
```

This is exactly the type of workload a relational SQL engine is designed for.

Azure SQL provides:

```text
T-SQL
joins
window functions
stored procedures
relational constraints
advanced query optimizer
```

plus modern SQL Server features.

Microsoft currently describes Azure SQL Database as a fully managed SQL engine and even a multi-model database capable of storing relational data plus JSON, vectors, XML, spatial and other formats. ([Microsoft Learn][1])

So don't oversimplify:

```text
Azure SQL
= only rigid tables
```

Modern SQL Database can handle more than that.

---

# **3. Cosmos DB scales primarily through partitioning**

Cosmos DB containers are logically partitioned using a:

```text
partition key
```

Example:

```text
/orders

partition key:
/customerId
```

Data becomes conceptually:

```text
Customer A
→ logical partition A

Customer B
→ logical partition B

Customer C
→ logical partition C
```

Azure maps those logical partitions onto physical partitions and manages the underlying distribution.

Microsoft explicitly says Cosmos DB uses partition keys to distribute data and scale storage and throughput horizontally. ([Microsoft Learn][2])

---

# **4. Partition-key design is critical in Cosmos DB**

Suppose I choose:

```text
/status
```

where only possible values are:

```text
new
paid
shipped
cancelled
```

This is low cardinality.

Millions of requests could concentrate on:

```text
status = "new"
```

creating a:

```text
hot partition
```

and poor throughput distribution.

Better partition keys often have:

```text
high cardinality
even traffic distribution
alignment with common queries
```

such as:

```text
/customerId
/tenantId
/deviceId
```

depending on the workload.

Microsoft explicitly warns that poor low-cardinality partition keys can create uneven RU/storage usage and hot partitions. ([Microsoft Learn][2])

This is one of the biggest Cosmos DB design responsibilities.

---

# **5. Azure SQL scaling model is different**

Azure SQL typically scales through:

```text
more vCores
larger service tier
Hyperscale
read replicas
elastic pools
partitioning/sharding at architecture level
```

depending on requirements.

For many business systems:

```text
vertical scaling
+
optimized indexes
+
query tuning
```

may be simpler than designing the application around distributed partitions.

Cosmos DB begins from a much more distributed model.

---

# **6. Cosmos DB uses Request Units**

Cosmos DB normalizes the cost of operations into:

```text
Request Units
RU
```

and throughput into:

```text
RU/s
```

A request consumes RUs based on resources required, including:

```text
CPU
IO
memory
query complexity
document size
```

Microsoft describes RU as the normalized performance currency for Cosmos operations. ([Microsoft Learn][3])

For example:

```text
simple point read
→ relatively cheap

cross-partition complex query
→ substantially more RU
```

This makes **data modeling and query patterns directly affect cost**.

---

# **7. Point reads are a Cosmos strength**

If I know:

```text
id
+
partition key
```

Cosmos DB can efficiently route directly to the right logical partition.

Example:

```text
id = order-5829
partition key = customer-42
```

is generally much better than:

```text
Search every partition
WHERE productDescription contains ...
```

That means Cosmos data modeling often begins with:

> “What are my application's most important access patterns?”

rather than designing a normalized model first.

---

# **8. Azure SQL gives strong relational transaction semantics**

Suppose transferring money:

```text
Account A
- ₹1,000

Account B
+ ₹1,000
```

I want:

```text
BEGIN TRANSACTION

debit A
credit B

COMMIT
```

Either both operations succeed or neither does.

Relational transactional workloads like this are very natural in Azure SQL.

Cosmos DB also provides ACID transactional semantics, but the transaction scope and distributed model are different—transactional operations are naturally strongest when aligned to a logical partition. Microsoft explicitly notes that Cosmos DB provides ACID guarantees while operating within its distributed model. ([Microsoft Learn][4])

So don't say:

```text
Cosmos DB has no transactions.
```

That's wrong.

---

# **9. Global distribution is a major Cosmos advantage**

Suppose users are in:

```text
India
Europe
United States
```

Cosmos DB can replicate data across multiple Azure regions:

```text
India
  ↕
Europe
  ↕
US
```

with applications reading from nearby replicas.

With multi-region writes enabled, multiple regions can accept writes.

Microsoft currently documents multi-region Cosmos DB with up to **99.999% read-and-write availability** for qualifying multi-region configurations and low-latency guarantees under the documented conditions. ([Microsoft Learn][5])

This is one of Cosmos DB's core strengths.

---

# **10. Cosmos DB gives five consistency levels**

From strongest to weakest:

```text
Strong
Bounded staleness
Session
Consistent prefix
Eventual
```

([Microsoft Learn][6])

That allows trade-offs among:

```text
consistency
latency
availability
throughput
```

For example:

### Strong

```text
read always observes
strongly consistent state
```

but cross-region synchronous coordination increases latency/cost trade-offs.

### Session

Often a strong application-friendly compromise:

```text
read your own writes
monotonic reads/writes
```

inside session semantics.

### Eventual

Prioritizes distribution/availability characteristics while accepting temporary replica differences.

This explicit consistency choice is a major architectural difference from the normal Azure SQL programming model.

---

# **11. Cosmos multi-region writes introduce conflict considerations**

Suppose:

```text
Region India
updates customer 42

and simultaneously

Region Europe
updates customer 42
```

Now the distributed system may need:

```text
conflict detection
conflict resolution
```

depending on workload/API/configuration.

Cosmos DB has platform mechanisms for multi-region replication and conflict management.

But application architects still need to understand:

```text
what can be written concurrently?
what does consistency require?
what should win during conflict?
```

Global writes aren't “free simplicity.”

---

# **12. Schema flexibility**

Cosmos documents can evolve naturally:

Version 1:

```json
{
  "id": "1",
  "name": "Satyam"
}
```

Later:

```json
{
  "id": "2",
  "name": "Alex",
  "preferredRegion": "india",
  "settings": {
    "theme": "dark"
  }
}
```

You don't necessarily need:

```text
ALTER TABLE
```

for every document-shape change.

That is valuable for rapidly evolving document-oriented applications.

But:

```text
schema flexible
≠
schema design unnecessary
```

You still need:

```text
validation
versioning
partition-key design
backward compatibility
```

in your application.

---

# **13. Don't choose Cosmos simply because “NoSQL is faster”**

That's a poor architectural answer.

If your workload is:

```text
10 tables
many relational joins
strong transactional workflows
complex reports
moderate scale
```

forcing it into documents could make application logic dramatically more complicated.

Likewise, if your application needs:

```text
millions of globally distributed
key/document operations per second
```

forcing everything into one traditional relational architecture may create unnecessary scaling complexity.

Choose based on access patterns.

# **16. They can coexist**

Real applications frequently use both.

Example:

```text
                     Application

               ┌─────────┴─────────┐
               ↓                   ↓
          Azure SQL             Cosmos DB
               ↓                   ↓
       Orders/payments        Session/profile/

```

This is called:

```text

```

Use each database for the access pattern it handles best.

## **Quick comparison**

| Characteristic          | Azure SQL                                     | Cosmos DB                                    |
| ----------------------- | --------------------------------------------- | -------------------------------------------- |
| Traditional model       | **Relational SQL**                            | **Distributed/document/NoSQL-oriented**      |
| Query language/model    | T-SQL                                         | API-dependent                                |
| Joins                   | **Strong**                                    | Design usually avoids relational-style joins |
| Schema                  | Structured relational                         | **Flexible**                                 |
| Transactions            | **Strong relational model**                   | Supported, distribution-aware                |
| Horizontal partitioning | Possible/architecture dependent               | **Core architecture**                        |
| Global distribution     | Supported through SQL DR/replication patterns | **Core capability**                          |
| Multi-region writes     | Different SQL architectures                   | **Native supported capability**              |
| Consistency levels      | Relational engine model                       | **5 selectable levels**                      |
| Throughput model        | vCore/DTU/service tier                        | **RU/s**                                     |
| Best fit                | Relational business systems                   | Globally distributed high-scale workloads    |

### **Interview answer condensed**

> “Azure SQL is my default when the workload is naturally relational and needs SQL joins, constraints, relational transactions and traditional reporting. Cosmos DB is designed for horizontally partitioned and globally distributed applications, particularly document/NoSQL-style workloads where I need high throughput, low-latency point access, flexible schemas and multi-region distribution. Cosmos DB also gives explicit consistency choices and uses RU/s as its throughput model. I wouldn't choose based simply on SQL versus NoSQL—I'd start from the application's access patterns, transaction boundaries, consistency requirements, partitioning needs and geographic scale.”

**Memory line:**
**Azure SQL organizes relationships; Cosmos DB organizes distributed access at scale.**

**Interview trap:**
**Cosmos DB isn't “Azure SQL but faster,” and modern Cosmos DB also isn't accurately described as only a non-relational database platform.**

**Keywords:**
Azure SQL, Cosmos DB, relational, partition key, RU/s, consistency, horizontal scaling, multi-region writes, ACID.

**Likely follow-ups:**

* How would you choose a Cosmos DB partition key?
* What causes a hot partition?
* What are the five Cosmos consistency levels?
* Can Cosmos DB support transactions?
* When would you use Azure SQL and Cosmos DB together?

### **T34-53. IaaS vs PaaS?**

**Answer:**

The main difference between IaaS and PaaS is **how much of the technology stack Microsoft operates for me**.

With **IaaS — Infrastructure as a Service**, Azure manages the physical datacenter, hardware, network infrastructure and virtualization layer, while I still manage the virtual machine's operating system, patches, runtime, middleware, application, and much of the network/security configuration.

With **PaaS — Platform as a Service**, Azure also manages the operating system and much of the application-hosting/database platform, so I primarily manage my application, data, identity, configuration and application-level security.

Examples:

```text
IaaS
→ Azure Virtual Machines

PaaS
→ App Service
→ Azure Functions
→ Azure SQL Database
→ Azure Storage
```

My default architectural preference is:

> **Use the highest-level managed service that satisfies the requirements.**

I move down to IaaS when the application genuinely needs OS-level control or capabilities the PaaS service can't provide.

Microsoft's current shared-responsibility guidance says exactly that: in IaaS the customer manages VMs, operating systems and applications; in PaaS the customer deploys applications without managing the underlying VMs or operating systems. ([Microsoft Learn][7])

Suppose App Service has:

```text

```



### **T34-54. High availability vs disaster recovery?**

**Answer:**

High availability and disaster recovery are both parts of business continuity, but they deal with **different classes of failure**.

**High availability, HA**, is about keeping the application running through normal and relatively frequent failures—such as VM failure, process failure, hardware maintenance, or an Availability Zone outage—usually through redundancy and automatic failover.

**Disaster recovery, DR**, is about recovering from larger, uncommon, catastrophic failures that exceed the normal HA design—for example an entire Azure region outage, major data corruption, ransomware, or destruction of a primary environment. DR is driven heavily by **RTO and RPO**.

So:

```text
HA
→ keep serving during expected failures

DR
→ restore service after a major disaster
```

A production system normally needs both. Availability Zones might give me strong HA within one Azure region, while a second region plus replicated data, global traffic routing, backups and a tested failover plan might provide DR.

Microsoft's current reliability guidance makes exactly this distinction: HA handles day-to-day transient/intermittent failures, while DR handles uncommon catastrophic events that exceed the workload's normal resilience. ([Microsoft Learn][8])

---

## **1. High availability focuses on expected/common failures**

Examples:

```text
VM crashes
Pod crashes
host maintenance
disk/server failure
brief network issue
Availability Zone outage
```

Depending on architecture, these failures should ideally be handled automatically.

Example:

```text
             Load Balancer
             /     |     \
            ↓      ↓      ↓
         VM-A    VM-B    VM-C
         Zone1   Zone2   Zone3
```

VM-A fails:

```text
health probe fails
      ↓
traffic removed from VM-A
      ↓
VM-B and VM-C continue
```

Users might see little or no interruption.

That's HA.

---

# **2. Disaster recovery addresses larger failure boundaries**

Now imagine:

```text
Entire Region A unavailable
```

Your three zonal VMs are all inside:

```text
Region A
```

so:

```text
Zone1 X
Zone2 X
Zone3 X
```

Your in-region HA architecture can't help.

You need something like:

```text
                 Front Door
                 /        \
                ↓          ↓
            Region A    Region B
            Primary      DR
```

plus appropriate data replication.

That's DR.

---

# **3. Failure domain is the key distinction**

Think in progressively larger failure domains:

```text
Process
  ↓
VM
  ↓
Rack
  ↓
Availability Zone
  ↓
Region
  ↓
large geographic/business disaster
```

Architecture might respond:

```text
Pod failure
→ Kubernetes restart

VM failure
→ replica elsewhere

Zone failure
→ remaining zones

Region failure
→ DR region
```

A reliable design maps a resilience mechanism to each relevant failure domain.

---

# **4. HA typically aims for automatic recovery**

Example AKS:

```text
Pod crashes
   ↓
Deployment controller
   ↓
replacement Pod
```

Example zone-resilient application:

```text
Zone 1 fails
   ↓
Load Balancer stops routing there
   ↓
Zones 2 and 3 continue
```

Users shouldn't need the operations team to declare a disaster for every normal component failure.

That's a major HA goal:

```text
failure is absorbed
without major recovery procedure
```

# **5. DR usually has explicit recovery processes**

A regional disaster may involve:

```text
detect disaster
       ↓
assess impact
       ↓
declare failover
       ↓
promote/restore data
       ↓
activate secondary
       ↓
redirect traffic
       ↓
validate business transactions
```

Depending on architecture, this may be automated, semi-automated, or manual.

DR isn't simply:

```text
more replicas.
```

It is a tested recovery capability.

---

# **6. RTO is central to DR**

Suppose:

```text
RTO = 15 minutes
```

You cannot plan:

```text
Region failure
      ↓
engineer manually creates network
      ↓
creates AKS
      ↓
restores database
      ↓
deploys app
```

if that takes four hours.

You probably need:

```text
pre-provisioned secondary
IaC
replicated data
automated routing/failover
```

depending on requirement.

RTO asks:

```text
How quickly must the service recover?
```

---

# **7. RPO is equally important**

Requirement:

```text
RPO = 5 minutes
```

means after disaster the business can tolerate approximately:

```text
≤ 5 minutes of lost committed state
```

depending on defined objective.

So a nightly backup:

```text
every 24 hours
```

probably doesn't satisfy it.

You may require:

```text
continuous replication
frequent log backup
geo-replication
```

depending on data service.

---

# **8. HA doesn't automatically provide DR**

Suppose:

```text
Region A

Zone 1 → App
Zone 2 → App
Zone 3 → App

ZRS Storage
Zone-redundant database
```

Excellent regional HA.

But if:

```text
Region A catastrophic outage
```

everything may still be unavailable.

Therefore:

```text
multi-zone
≠
multi-region DR
```

This is one of the biggest interview traps.

---

# **9. DR doesn't automatically provide HA**

Opposite mistake:

```text
Region A
→ one VM

Region B
→ backup VM
```

If VM in Region A crashes every Tuesday:

```text
do we fail over regions every time?
```

That would be poor design.

You should first have local HA:

```text
multiple healthy instances
```

for normal faults.

DR isn't a substitute for day-to-day redundancy.

---

# **10. HA example — Azure SQL**

Azure SQL Database includes built-in high availability at the service layer and can support zone redundancy depending on tier/configuration.

That helps against:

```text
infrastructure failures
compute/storage failures
some zone-level failures
```

But for a complete regional outage, I would separately evaluate SQL DR capabilities such as:

```text
failover groups
geo-replication
backup strategy
```

according to RTO/RPO.

Same service; two different reliability layers.

---

# **11. Backup is part of DR—but not the entire DR plan**

Suppose:

```text
Region A destroyed
```

Backups exist.

Great.

But DR also requires:

```text
Where do I restore?
How long does restore take?
Is networking ready?
Is DNS ready?
Are identities configured?
Are secrets available?
Can users reach the app?
```

A backup means:

```text
recoverable data exists.
```

It does not by itself prove:

```text
business service can recover within RTO.
```

---

# **12. Replication isn't backup either**

Suppose malicious code corrupts:

```text
customer table
```

and geo-replication sends corruption to:

```text
Region B
```

Now both copies are wrong.

You still need historical recovery mechanisms.

So a robust BCDR strategy often includes:

```text
HA redundancy
+
DR replication
+
backup/version history
```

Each protects against a different failure.

---

# **13. Example full architecture**

```text
                         Users
                           ↓
                      Front Door
                      /        \
                     ↓          ↓
              Region A        Region B
              ACTIVE          DR/WARM
               │               │
         ┌─────┴─────┐   ┌─────┴─────┐
       Zone1 Zone2 Zone3   replicated services
         │
       App tier
         ↓
zone-resilient data
         │
         └──── geo replication ───→ Region B
```

Inside Region A:

```text
Availability Zones
→ HA
```

Between Region A and B:

```text
geo-replication + failover
→ DR
```

Backups:

```text
historical recovery
→ corruption/ransomware/deletion protection
```

That's layered reliability.

---

# **14. HA should be tested too**

Don't assume:

```text
3 zones configured
→ HA works.
```

Test:

```text
instance loss
Pod loss
dependency timeout
zone evacuation/failure scenarios where practical
```

Validate:

```text
health probes
autoscaling
retry behavior
capacity after failure
```

An architecture diagram isn't proof.

---

# **15. DR requires drills**

A DR plan that says:

```text
"Fail over to Region B"
```

but has never been exercised is risky.

Test:

```text
traffic failover
database promotion
DNS/private DNS
Key Vault access
Managed Identity
capacity
dependencies
business transaction
```

and measure:

```text
actual RTO
actual RPO
```

Microsoft's reliability guidance treats DR as deliberate planning for uncommon catastrophic risks, not merely possession of redundant infrastructure. ([Microsoft Learn][8])

---

# **16. Capacity after failure matters**

HA example:

```text
3 zones
each normally handles 33%
```

If one zone fails:

```text
remaining zones
must handle ~50% each
```

If each was already running at:

```text
90% capacity
```

the “HA” system can collapse from overload after failover.

Similarly for DR:

```text
Region B
```

must have enough capacity—or scale fast enough—to serve critical traffic.

This is sometimes called:

```text
N-1 capacity planning
```

in resilience discussions.

## **Quick comparison**

| Characteristic  | High availability        | Disaster recovery                |
| --------------- | ------------------------ | -------------------------------- |
| Failure class   | Common/expected          | **Rare/catastrophic**            |
| Goal            | **Keep service running** | **Restore service**              |
| Typical scope   | Instance/zone            | Region/site/data disaster        |
| Automation      | Usually strong/automatic | Can be automated or orchestrated |
| Main metrics    | Availability/SLO         | **RTO/RPO**                      |
| Example         | Multi-zone replicas      | Multi-region failover            |
| Backup involved | Not primary mechanism    | **Often part of strategy**       |
| Regular testing | Yes                      | **DR drills essential**          |

### **Interview answer condensed**

> “High availability is about keeping the workload running through normal, expected failures such as a VM, Pod, host or Availability Zone failure. I usually achieve that with redundant instances, health probes, load balancing and zone-resilient services. Disaster recovery addresses larger, uncommon failures such as an entire region outage, major corruption or ransomware. DR is driven by RTO and RPO and normally involves another recovery location, replicated or backed-up data, failover procedures and regular DR testing. Multi-zone architecture gives strong HA, but it isn't automatically regional disaster recovery.”

**Memory line:**
**HA survives routine failures; DR recovers from catastrophic failures.**

**Interview trap:**
**Availability Zones provide regional HA, not automatic protection from an entire Azure region failure.**

**Keywords:**
HA, DR, business continuity, Availability Zones, multi-region, RTO, RPO, failover, backup, replication.

**Likely follow-ups:**

* Why isn't multi-zone deployment sufficient for DR?
* Why doesn't replication replace backup?
* How do RTO and RPO influence DR architecture?
* How would you test a DR environment without disrupting Production?

### **T34-55. SLA vs SLO?**

**Answer:**

An **SLA — Service Level Agreement** is a formal commitment between a service provider and a customer. It defines a guaranteed service level and usually includes specific measurement rules, exclusions, and consequences such as service credits if the commitment isn't met.

An **SLO — Service Level Objective** is an engineering or operational reliability target for a workload or user flow—for example:

```text
99.95% checkout availability per month
```

or:

```text
99% of API requests
complete within 500 ms
```

So:

```text
SLA
→ contractual commitment

SLO
→ internal measurable reliability target
```

I use Azure service SLAs as **inputs** when designing the workload, but I don't simply copy an Azure service's SLA and call it my application's SLO. My workload also depends on my own code, configuration, deployments, networking, databases, third-party services and operations.

Microsoft's current Well-Architected guidance explicitly defines SLAs as external contractual commitments and SLOs as internal reliability/performance targets used to measure workload health. ([Microsoft Learn][9])

---

## **1. SLA is the promise**

Example:

```text
Service provider
     ↓
Customer

Agreement:
99.9% availability
under defined conditions
```

If the provider doesn't meet the agreed conditions:

```text
service credit
financial consequence
contractual consequence
reputational impact
```

may apply according to the actual agreement.

Important:

```text
SLA percentage
```

means nothing without reading:

```text
what is measured?
over what period?
which operations?
which tier?
which exclusions?
what configuration is required?
```

Microsoft specifically cautions that an SLA has precise definitions, conditions and exclusions and shouldn't be interpreted merely from its headline percentage. ([Microsoft Learn][10])

---

# **2. SLO is the target engineering operates against**

Example checkout flow:

```text
User
 ↓
Front Door
 ↓
API
 ↓
SQL
```

Business requirement:

```text
Checkout success SLO:
99.95%

Latency SLO:
99% of successful checkout requests
< 800 ms
```

Engineering can now design:

```text
monitoring
alerts
capacity
redundancy
incident response
deployment gates
```

against these explicit objectives.

---

# **3. SLI is the measurement behind the SLO**

This follow-up often comes immediately.

### SLI — Service Level Indicator

Actual observed measurement.

Example:

```text
Successful checkout requests
÷
eligible checkout requests
```

Suppose:

```text
9,997 successful
10,000 total
```

SLI:

```text
99.97%
```

SLO:

```text
99.95%
```

Result:

```text
SLO met
```

So:

```text
SLI
→ What did we measure?

SLO
→ What target are we aiming for?

SLA
→ What did we promise contractually?
```

Microsoft defines SLI as the quantitative measurement used to determine whether the workload meets its SLO. ([Microsoft Learn][11])

---

# **4. Example 99.9% SLO**

Monthly time roughly:

```text
30 days
≈ 43,200 minutes
```

If availability SLO is:

```text
99.9%
```

then allowed unavailability is approximately:

```text
0.1% × 43,200
≈ 43.2 minutes/month
```

Microsoft's current reliability guidance likewise gives roughly **43.2 minutes per month** as the noncompliance allowance corresponding to 99.9%. ([Microsoft Learn][11])

This gives engineering something concrete.

---

# **5. Error budget comes from the SLO**

If:

```text
SLO = 99.9%
```

then:

```text
error budget
= 0.1%
```

Conceptually:

```text
Monthly availability budget
≈ 43.2 minutes unavailable
```

If only:

```text
5 minutes consumed
```

the service has healthy reliability margin.

If:

```text
40 minutes consumed halfway through month
```

the team should become more conservative about:

```text
risky releases
major infrastructure changes
```

and prioritize reliability.

The error budget is an **engineering control**, not permission to intentionally create downtime.

---

# **6. Don't simply set SLO equal to Azure SLA**

Suppose App Service has some published platform SLA under specific conditions.

Your application also requires:

```text
Front Door
App Service
Key Vault
SQL
third-party payment API
your application code
```

Even if every Azure component meets its own SLA:

```text
your application
```

may still fail because of:

```text
deployment bugs
bad configuration
database query bug
certificate issue
external dependency
```

Microsoft specifically warns that a platform SLA doesn't directly equal workload reliability. ([Microsoft Learn][10])

---

# **7. Composite availability**

Consider serial dependencies:

```text
User
 ↓
API
 ↓
Database
```

Assume, only as a simplified illustration:

```text
API availability = 99.9%
DB availability  = 99.9%
```

If both must work and failures are treated as independent:

```text
Composite availability
≈ 0.999 × 0.999
≈ 99.8001%
```

Not:

```text
99.9%
```

That's why architectures with many mandatory dependencies can have lower end-to-end reliability than any one component.

The independence assumption is simplified—real failures can be correlated—but the multiplication principle is useful for design reasoning.

---

# **8. Redundancy can increase workload availability**

Suppose:

```text
Region A
or
Region B
```

can independently serve users.

Now availability isn't simple serial multiplication because the regions are redundant rather than both mandatory for every request.

Architecture:

```text
                Front Door
                /        \
               ↓          ↓
           Region A    Region B
```

If one fails:

```text
other continues
```

which can dramatically improve workload availability if dependencies are also resilient.

But:

```text
both regions use same single-region DB
```

would destroy much of that benefit.

---

# **9. SLO should represent user experience**

Weak SLO:

```text
VM CPU < 80%
```

That's not usually a service-level outcome.

Better:

```text
99.95% of checkout attempts
succeed
```

or:

```text
99% of search requests
finish under 500 ms
```

CPU is a useful implementation metric, but users don't care whether CPU is:

```text
40%
or
70%
```

if checkout is broken.

Microsoft's Well-Architected guidance recommends defining SLOs around meaningful customer interactions and critical flows. ([Microsoft Learn][11])

---

# **10. Availability isn't the only possible SLO**

SLOs can cover:

```text
availability
latency
success rate
throughput
correctness
capacity
```

For example:

### Availability SLO

```text
99.95% checkout availability
```

### Latency SLO

```text
p95 checkout latency < 800 ms
```

### Correctness SLO

```text
99.999% payment records
reconciled correctly
```

depending on the business need.

Microsoft explicitly lists availability, latency, success rate, throughput and capacity as examples of SLO-relevant indicators. ([Microsoft Learn][11])

---

# **11. Different business flows can have different SLOs**

E-commerce:

```text
Checkout
→ 99.99%

Product browsing
→ 99.9%

Admin reporting
→ 99.0%
```

Why?

Because business impact differs.

If reporting is unavailable for:

```text
30 minutes
```

maybe internal staff wait.

If checkout is unavailable:

```text
revenue stops.
```

Therefore SLO design should follow:

```text
business criticality
```

not one percentage copied across every component.

---

# **12. Engineering often keeps safety margin before the SLA is breached**

Suppose customer SLA:

```text
99.9%
```

You generally don't want your engineering system to begin worrying only once you hit:

```text
99.899%
```

because then the contractual commitment is already missed.

You might therefore operate to a stronger internal objective such as:

```text
SLO = 99.95%
```

to create margin.

That is common, though **SLO does not have a universal rule requiring it always to be numerically higher than an SLA**; the business relationship and measurement definitions matter. Microsoft emphasizes that SLAs and SLOs have different intent and should be controlled independently. ([Microsoft Learn][11])

---

# **13. Azure service SLA vs your workload SLA**

Suppose Microsoft publishes an SLA for:

```text
Azure App Service
```

That is:

```text
Microsoft
→ your organization
```

for the covered Azure service.

Your company might publish:

```text
Payments API SLA
```

to your own customer.

That's:

```text
Your company
→ customer
```

Your service SLA must account for:

```text
Azure dependency
+
your application
+
other dependencies
+
your operational model
```

Azure's SLA is just one input.

---

# **14. SLA may have configuration requirements**

You should never quote an Azure SLA percentage without checking its conditions.

For example, service guarantees can depend on things such as:

```text
service tier
multiple instances
zone configuration
specific operation
deployment model
```

depending on the Azure service.

So in architecture review I ask:

```text
Which exact SLA applies
to THIS SKU
and THIS deployment configuration?
```

not:

```text
"Azure says 99.99 somewhere."
```

---

# **15. SLOs drive alerts**

Bad monitoring:

```text
CPU > 80%
→ page engineer
```

for everything.

Better:

```text
Checkout success rate
threatening SLO
→ page
```

Then infrastructure metrics help explain why.

Microsoft recommends using SLO thresholds to drive actionable health monitoring and alerts aligned to business outcomes. ([Microsoft Learn][9])

---

# **16. SLO can drive deployment rollback**

Candidate version:

```text
v42
```

After release:

```text
Stable success = 99.98%
Candidate success = 98.7%
```

If that threatens the relevant SLO:

```text
automated rollout
→ STOP
→ rollback
```

This is stronger than:

```text
CPU looks okay
→ continue deployment.
```

SLOs connect reliability engineering directly to release engineering.

---

# **17. Practical SRE example**

Service:

```text
Payments API
```

Define:

```text
SLI:
successful payment requests
÷
valid payment requests

SLO:
99.95% success over 30 days

Customer SLA:
99.9% service availability
under contractual definition
```

Engineering monitors:

```text
SLI
 ↓
SLO consumption
 ↓
error budget
```

If error budget is consumed too quickly:

```text
freeze risky changes
prioritize reliability
investigate recurring failures
```

This is SRE-style reliability management.

## **Quick comparison**

| Characteristic                        | SLA                           | SLO                                        |
| ------------------------------------- | ----------------------------- | ------------------------------------------ |
| Full name                             | Service Level Agreement       | Service Level Objective                    |
| Main nature                           | **Contractual commitment**    | **Engineering target**                     |
| Audience                              | Customer/provider             | Engineering/business stakeholders          |
| Financial/legal consequence           | Often **yes**                 | Normally no direct contractual consequence |
| Example                               | 99.9% guaranteed availability | 99.95% checkout success                    |
| Measured by                           | Contract-defined measurements | **SLIs**                                   |
| Used for alerting/error budget        | Indirect                      | **Yes**                                    |
| Azure platform SLA = workload target? | No                            | Must be designed separately                |

### **Interview answer condensed**

> “An SLA is a formal service commitment between a provider and customer, usually with defined measurement conditions and consequences such as service credits if it's missed. An SLO is an internal reliability or performance target that engineering designs and operates the workload against. For example, our checkout flow might have a 99.95% success SLO while our external customer SLA is 99.9%. I measure an SLO using SLIs such as request success rate or latency and often use the resulting error budget to guide alerts and release risk. I also don't copy an Azure service SLA directly into my workload SLO, because my application reliability includes my code, configuration and every dependency.”

**Memory line:**
**SLA is the promise; SLO is the target; SLI is the measurement.**

**Interview trap:**
An Azure service's **SLA is not automatically your application's availability**, and an SLO does not have a universal rule that it must always numerically equal or exceed the SLA.
