### **T34-24. App Service vs VM?**

**Answer:**

The biggest difference is **PaaS versus IaaS and how much of the operating system I want to manage**.

With an **Azure VM**, Microsoft manages the physical infrastructure, but I am responsible for the guest OS, patching, middleware, runtime installation, configuration, scaling architecture, availability design, and much of the operational security.

With **Azure App Service**, Azure manages the underlying servers, OS platform, web hosting infrastructure, patching, load balancing, and much of the runtime environment. I primarily deploy my application code or container, configure networking and identity, and scale the App Service plan.

So my default is:

```text
Normal web app / REST API
with supported runtime
→ App Service

Need OS-level control,
custom software, kernel/driver access,
special middleware, or legacy dependency
→ VM
```

For a modern web API, I would generally choose App Service because it gives me less infrastructure to operate. I would choose a VM only when the application requirements actually justify IaaS-level control.

Microsoft currently describes App Service as a managed web PaaS supporting .NET, Java, Node.js, Python, PHP, Windows/Linux, and custom containers, with the platform handling much of the underlying infrastructure. ([Microsoft Learn][1])

---

## **1. Responsibility model**

The easiest way to understand the difference is:

### Azure VM

```text
Microsoft manages
├── datacenter
├── physical servers
├── physical networking
└── virtualization

You manage
├── guest OS
├── OS patches
├── runtime
├── web server
├── application
├── configuration
├── antivirus/hardening
├── scaling design
└── application availability
```

### App Service

```text
Microsoft manages
├── physical infrastructure
├── VM/platform layer
├── operating platform
├── web hosting environment
├── platform patching
├── platform load distribution
└── much of runtime hosting

You manage
├── application
├── application configuration
├── identity/RBAC
├── networking choices
├── application security
└── scaling configuration
```

This reduction in operational responsibility is the core value of PaaS.

---

## **2. VM gives much more operating-system control**

With a VM I can:

```text
Install arbitrary packages
Modify OS configuration
Run custom agents
Change system services
Install proprietary middleware
Use custom filesystem layouts
Control kernel-level settings where supported
Run arbitrary background processes
```

That makes VMs appropriate for applications such as:

```text
Legacy vendor application
Custom Windows service
Special middleware
Old enterprise application
Software requiring OS-level installation
```

But that control creates responsibility.

I now own:

```text
patching
hardening
image maintenance
vulnerability remediation
availability
capacity
```

# **3. App Service deliberately removes OS management**

With standard App Service, I don't normally:

```text
SSH/RDP into the host
and treat it like my own server
```

Instead:

```text
GitHub Actions / Azure DevOps
          ↓
       artifact
          ↓
      App Service
          ↓
Azure-managed hosting platform
```

I deploy:

```text
code
or
custom container
```

and configure the application.

For most web applications, that's exactly what I want.

# **4. App Service supports both code and containers**

App Service isn't only:

```text
ZIP deploy .NET application
```

It can host supported application stacks directly or run custom containers. ([Microsoft Learn][1])

For example:

```text
Node.js API
→ App Service runtime
```

or:

```text
Docker image
→ ACR
→ App Service
```

So using Docker doesn't automatically mean:

```text
must use AKS
```

or:

```text

```

# **5. Scaling model**

### VM

One VM:

```text
VM01
```

doesn't magically become:

```text
VM01
VM02
VM03
```

when traffic grows.

I need a design such as:

```text
Load Balancer
      ↓
VM Scale Set
├── VM1
├── VM2
└── VM3
```

plus autoscaling rules.

---

### App Service

App Service uses an:

```text
App Service Plan
```

which defines underlying compute such as:

```text
OS
region
instance size
instance count
pricing tier
```

Apps in that plan run on the plan's compute resources. Microsoft notes that apps in the same plan share those compute instances and generally scale with the plan. ([Microsoft Learn][2])

Conceptually:

```text
App Service Plan
├── Instance 1
├── Instance 2
└── Instance 3

      ↑
  Web application
```

Scale out:

```text
3 → 6 instances
```

without personally creating six VMs.

---

# **6. Scaling multiple apps in one App Service Plan matters**

Suppose:

```text
App Service Plan
├── payments-api
├── reporting-api
└── admin-api
```

All share the underlying plan compute.

That means:

```text
one noisy application
```

can affect:

```text
other applications in same plan
```

through CPU/memory contention.

And Microsoft currently documents that applications placed in the same App Service plan share and scale on the same underlying VM resources. ([Microsoft Learn][2])

So for production isolation I may separate important workloads into different plans.

# **7. Deployment slots are a major App Service advantage**

App Service supports deployment slots on applicable tiers.

For example:

```text
Production slot
→ v41

Staging slot
→ v42
```

I can:

```text
deploy v42
      ↓
warm/test staging
      ↓
swap
      ↓
v42 becomes Production
```

This makes:

```text
blue-green-style deployment
```

very straightforward.

With raw VMs, I normally have to build that release-routing mechanism myself.

Suppose application requires:

```text
custom driver

special service

custom OS packages
```

A VM may be appropriate.

Standard App Service deliberately limits deep OS customization.

There is a current **Managed Instance on App Service** option for some Windows legacy scenarios needing more OS customization, but it remains a specialized App Service hosting model rather than a general replacement for unrestricted VMs. ([Microsoft Learn][3])

For interview purposes:

```text
Need full OS ownership
→ VM remains clearest answer
```

# **13. Persistent filesystem considerations**

Don't build a cloud web application assuming:


```text

```

depending on data type.

Similarly, well-designed VM applications should not rely on one VM's local state if you expect horizontal scaling.

### **Interview answer condensed**

> “App Service is a managed PaaS for web applications and APIs, while Azure VM is IaaS. With a VM I get full OS control, but I also own OS patching, runtime installation, hardening, scaling and much more of the availability design. **App Service trades OS control for lower operations; VM gives maximum control with maximum responsibility.**

### **T34-25. App Service vs Container Apps?**

**Answer:**

Both are managed Azure application platforms, but **App Service is primarily an opinionated web application/API PaaS**, while **Azure Container Apps is a container-native serverless platform designed for microservices, APIs, background workers, jobs, and event-driven workloads**.

I would choose App Service when I have a conventional web application or API and want mature web-hosting features such as deployment slots, built-in runtime hosting, custom domains, authentication integration, and simple scale-out.

I would choose Container Apps when the workload is already containerized and benefits from capabilities such as:

```text
KEDA-based event scaling
scale-to-zero
revisions
traffic splitting
background/event jobs
microservice service discovery
```

without having to operate Kubernetes directly.

So:

```text
Traditional web/API PaaS
→ App Service

Container-native microservices /
event-driven workload
without Kubernetes operations
→ Container Apps
```

Azure currently describes Container Apps as a serverless container platform with revision management, traffic splitting, KEDA-supported scaling, jobs, internal service discovery, and scale-to-zero for many workload types. ([Microsoft Learn][4])

# **4. Scaling model is a major difference**

Container Apps can scale based on:

```text
HTTP traffic
TCP traffic
CPU
memory
events
KEDA-supported scalers
```

and many workload patterns can scale to:

```text
0 replicas
```

```text

       ↓
```

# **5. App Service scaling is more plan-centric**

App Service applications run on an:

```text
App Service Plan
```

and apps in the same plan share the plan's underlying compute. Scaling that plan affects the apps sharing it. ([Microsoft Learn][2])

Conceptually:

```text
App Service Plan
├── WebApp A
├── WebApp B
└── API C
```

Scale plan:

```text
2 instances
→
5 instances
```

Those underlying instances are shared by the apps.

Container Apps gives more granular replica-level behavior per container app/revision.

# **6. Container Apps revisions**

A Container App revision is an immutable snapshot of the application's deployable configuration.

Example:

```text
orders--v1
orders--v2
```

You can route:

```text
90% → v1
10% → v2
```

then:

```text
50 / 50
```

then:

```text
100% → v2
```

Container Apps explicitly supports multiple revisions and traffic splitting for deployment strategies such as blue-green and A/B testing. ([Microsoft Learn][4])

### **T34-26. Container Apps vs AKS?**

**Answer:**

The main difference is **how much Kubernetes control and operational responsibility I need**.

**Azure Container Apps** gives me a serverless container platform. I deploy containers and configure things like ingress, scaling, revisions, secrets, and jobs, while Azure hides the Kubernetes cluster, worker-node management, control-plane configuration, and most orchestration details.

**AKS** is managed Kubernetes. Azure manages the Kubernetes control plane, but I still work with Kubernetes concepts such as Pods, Deployments, Services, namespaces, node pools, networking, RBAC, autoscaling, upgrades, policies, and cluster-level integrations. AKS therefore gives me much more control and ecosystem compatibility, but with greater operational complexity.

My rule is:

```text
Need containers/microservices/event scaling
but don't need Kubernetes-level control
→ Container Apps

Need Kubernetes APIs/ecosystem,
custom scheduling/networking,
operators, CRDs, DaemonSets,
advanced platform control
→ AKS
```

Container Apps currently provides revisions, traffic splitting, jobs and KEDA-based scaling while abstracting infrastructure. AKS is a managed Kubernetes service, and Microsoft now offers both **AKS Automatic** for more managed defaults and **AKS Standard** for deeper cluster/node-pool control. ([Microsoft Learn][4])

# **6. Important autoscaling distinction**

Do not say:

```text
Cluster Autoscaler sees CPU 80%
and adds nodes.
```

That's too simplistic.

The HPA commonly reacts to workload metrics to increase Pod replicas.

The Cluster Autoscaler primarily reacts to scheduling/resource conditions such as Pods being unable to schedule because suitable node capacity is unavailable.

That distinction is highly interview-relevant.

```text
cluster upgrade strategy
```

depending on cluster mode and design.

AKS can support much stricter/custom platform controls, but those controls have to be designed and operated.

---

# **11. Workload Identity**

Both can securely access Azure resources without embedding credentials, but the mechanisms and configuration models differ.

In AKS, a common model is:

```text
Pod
 ↓
ServiceAccount
 ↓
AKS OIDC
 ↓
Microsoft Entra Workload Identity
 ↓
Azure service
```

Container Apps exposes managed identity capabilities through its own platform abstraction.

The overall principle remains:

```text
prefer identity
over long-lived client secrets.
```

# **12. Kubernetes ecosystem**

AKS gives access to the massive Kubernetes ecosystem.

Examples:

```text
Argo CD
Argo Rollouts
Prometheus Operator
cert-manager
External Secrets
Kyverno
Gatekeeper
Istio
KEDA
custom Operators
```

Container Apps gives you selected managed capabilities, not unlimited cluster extensibility.

If your platform strategy depends heavily on Kubernetes tooling, AKS usually makes more sense.

# **13. Stateful workloads**

Container Apps can work with storage integrations, but AKS gives much more control over:

```text
PersistentVolumes
PersistentVolumeClaims
StorageClasses
StatefulSets
CSI drivers
pod scheduling
```

For complex stateful Kubernetes systems, AKS is generally the more appropriate platform.

That said, for many production architectures I would still prefer Azure-managed databases instead of running databases inside either platform unless there is a clear reason.

# **14. Operations**

### Container Apps

Azure handles much more of:

```text
infrastructure
orchestrator
nodes
platform upgrades
```

My operational focus:

```text
application
revision
scaling
observability
identity
```

### AKS

Platform team still deals with:

```text
Kubernetes versions
node images
node pools
capacity
cluster upgrades
CNI
ingress
policies
add-ons
```

though AKS Automatic now manages more of these concerns than traditional AKS Standard. ([Microsoft Learn][5])

A common architecture mistake:

```text

+

```

then:

for a workload that Container Apps could potentially run with far less operational burden.

More control is valuable only when you need it.

Opposite mistake:

Requirement says:

```text

```

Trying to force that into Container Apps is inappropriate.

Those requirements point strongly toward:


## **Quick comparison**

| Capability                   | Container Apps             | AKS                               |
| ---------------------------- | -------------------------- | --------------------------------- |
| Abstraction                  | **Application/container**  | **Kubernetes cluster**            |
| Manage control plane         | No                         | Azure-managed                     |
| Manage nodes                 | Hidden/platform managed    | Varies; customer has more control |
| Kubernetes API access        | No general cluster control | **Yes**                           |
| `kubectl` / CRDs / Operators | No                         | **Yes**                           |
| KEDA scaling                 | **Built in**               | Can install/use KEDA              |

| Platform flexibility         | Lower                      | **Much higher**                   |
| Operational burden           | **Lower**                  | Higher                            |

### **Interview answer condensed**

> “Container Apps is the higher-level serverless option. I deploy containers, configure ingress, revisions and KEDA scaling, and Azure hides the cluster and nodes. AKS is managed Kubernetes: Azure runs the control plane, but I still use Kubernetes APIs and can control Pods, node pools, networking, RBAC, operators, CRDs, policies and the broader Kubernetes ecosystem. I would use Container Apps when the workload needs container orchestration but not Kubernetes itself. I'd choose AKS when Kubernetes-level control or ecosystem compatibility is a real requirement.”

**Memory line:**
**Container Apps gives you containers without running Kubernetes; AKS gives you Kubernetes without self-managing the control plane.**

**Interview trap:**
AKS being managed does **not mean Azure manages every Kubernetes operational decision for you**, especially in Standard mode.

### **T34-27. AKS vs VM Scale Sets?**

**Answer:**

AKS and VM Scale Sets solve problems at **different layers**.

**VM Scale Sets** manage and scale groups of virtual machines. They give me consistent VM instances, autoscaling, availability distribution, and integration with Azure Load Balancer or Application Gateway, but Azure doesn't automatically orchestrate my application containers across those VMs.

**AKS** is a managed Kubernetes platform. It schedules and manages containers as Pods, provides Deployments, Services, self-healing, rolling updates, service discovery, Kubernetes networking and workload autoscaling.

In fact, the two aren't necessarily competitors: **AKS node pools commonly use Azure VM scale-set infrastructure underneath them**. AKS adds Kubernetes orchestration on top of the compute layer.

So:

```text
Need scalable fleet of VMs
running VM-based applications
→ VMSS

Need Kubernetes orchestration
for containerized applications
→ AKS
```

Microsoft describes VM Scale Sets as a way to create, manage, load-balance and autoscale groups of VMs, while AKS provides the managed Kubernetes orchestration layer for container workloads. ([Microsoft Learn][6])

---

## **1. Think in layers**

```text
Application layer
       ↓
Containers / Pods
       ↓
Kubernetes
       ↓
AKS
       ↓
Node pools
       ↓
VM infrastructure / scale sets
       ↓
Azure Compute
```

VMSS operates primarily around:

```text
VM instances
```

AKS operates primarily around:

```text
containerized workloads
```

That's the fundamental distinction.

---

# **2. VMSS scales machines**

Suppose:

```text
VMSS capacity = 3
```

Demand rises.

Autoscale:

```text
3 VMs
 ↓
6 VMs
```

Azure creates additional instances from the scale-set configuration/image.

Microsoft currently describes VMSS as supporting automatic scaling using demand or schedule-based rules and providing availability through fault-domain or Availability Zone distribution. ([Microsoft Learn][6])

But VMSS doesn't inherently know:

```text
how many application containers
should run on each VM.
```

That's application/orchestration logic you must provide.

---

# **3. AKS schedules Pods, not just machines**

Suppose Kubernetes Deployment:

```yaml
replicas: 10
```

AKS scheduler decides:

```text
Node1 → Pod1, Pod2, Pod3
Node2 → Pod4, Pod5, Pod6
Node3 → Pod7, Pod8, Pod9, Pod10
```

If Pod4 crashes:

```text
Kubernetes controller
      ↓
creates replacement Pod
```

That's application-level orchestration.

VMSS alone doesn't have a Kubernetes Deployment controller that understands your application replicas.

---

# **4. Self-healing differs**

### VMSS

Azure can detect/manage unhealthy VM instances according to configured health and repair behavior.

It operates on:

```text
VM instance
```

as the unit.

### AKS

Kubernetes understands:

```text
Pod
Container
Deployment
StatefulSet
Node
```

If one application process fails:

```text
Container fails
      ↓
Kubelet restarts container
```

or:

```text
Pod unhealthy
      ↓
controller replaces Pod
```

without necessarily replacing the entire VM.

AKS provides a much finer workload-level reconciliation model.

---

# **5. Deployment model**

### VMSS

Typical pattern:

```text
Build VM image
   ↓
Azure Compute Gallery
   ↓
VMSS model
   ↓
instances updated
```

or use:

```text
extensions/configuration tools
```

to configure instances.

This is usually infrastructure-centric.

---

### AKS

Typical pattern:

```text
Build container image
      ↓
ACR
      ↓
Deployment YAML/Helm
      ↓
Kubernetes Deployment
      ↓
Pods
```

This is application/container-centric.

Container images are much lighter deployment units than entire VM images.

---

# **6. Rolling updates**

Kubernetes Deployment:

```text
v1 Pods
 ↓
gradually replace
 ↓
v2 Pods
```

with controls such as:

```text
maxSurge
maxUnavailable
readinessProbe
```

This directly understands application replicas.

VMSS supports rolling infrastructure updates as well, but its unit is primarily:

```text
VM instance/model
```

rather than Kubernetes Pod orchestration.

---

# **7. Load balancing**

### VMSS

Common architecture:

```text
Internet
   ↓
Azure Load Balancer
   ↓
VMSS
├── VM1
├── VM2
└── VM3
```

or Application Gateway for Layer 7 requirements.

Microsoft explicitly lists Load Balancer and Application Gateway as common traffic-distribution integrations for VMSS. ([Microsoft Learn][6])

---

### AKS

Possible path:

```text
Internet
 ↓
Load Balancer / App Gateway / Front Door
 ↓
Ingress / Service
 ↓
Pods
```

Kubernetes adds another service-discovery and routing layer.

---

# **8. Autoscaling in AKS has two layers**

This is extremely important.

### HPA

```text
Pod count
```

Example:

```text
3 Pods
→ 12 Pods
```

### Cluster Autoscaler

```text
Node count
```

Example:

```text
3 nodes
→ 6 nodes
```

Combined:

```text
traffic rises
   ↓
HPA creates more Pods
   ↓
not enough node capacity
   ↓
Pods Pending
   ↓
Cluster Autoscaler adds nodes
```

This is much richer than simply scaling VM count.

---

# **9. VMSS autoscale only gives you more machines**

Suppose:

```text
VMSS
3 → 10 VMs
```

Who installs/configures your application?

Possibilities:

```text
custom VM image
cloud-init
Custom Script Extension
configuration management
application bootstrap
```

Who decides where workload processes run?

Your application/deployment architecture.

VMSS doesn't become a container scheduler because it added more compute.

---

# **10. AKS node scaling commonly uses VMSS underneath**

This is where the comparison becomes interesting.

Conceptually:

```text
AKS node pool
       ↓
Azure VM compute
       ↓
scale infrastructure
```

When Kubernetes needs more nodes:

```text
Cluster Autoscaler
      ↓
AKS/Azure compute integration
      ↓
additional node instances
```

So often:

```text
AKS
uses VM-scale infrastructure
rather than replacing the concept entirely.
```

AKS is the orchestration layer above it.

---

# **11. VMSS is better for non-container or VM-centric applications**

Examples:

```text
legacy Windows application
custom network appliance
proprietary software
application requiring full OS control
stateful VM-based cluster
```

VMSS can scale/manage the VM fleet without introducing Kubernetes.

If the software isn't naturally containerized:

```text
AKS may add complexity
without benefit.
```

---

# **12. AKS is better for container-native platforms**

Examples:

```text
20 microservices
independent deployments
sidecars
service discovery
rolling releases
horizontal workload scaling
GitOps
operators
```

AKS gives the orchestration primitives these workloads need.

Trying to recreate them manually on VMSS would mean building your own mini-orchestrator.

---

# **13. Configuration drift**

VM fleet:

```text
VM1
VM2
VM3
```

can drift if engineers manually modify instances.

Strong VMSS practice is:

```text
immutable/golden image
+
declarative infrastructure
+
replace instances
```

rather than hand-editing individual VMs.

AKS similarly encourages:

```text
immutable container image
+
declarative Kubernetes manifest
```

but at a much smaller deployment unit.

---

# **14. Upgrade responsibility**

VMSS:

You manage:

```text
OS image strategy
application image
patching
VM extensions
rolling VM upgrades
```

AKS:

Azure manages control-plane aspects, while you manage/coordinate:

```text
Kubernetes versions
node-image/node-pool lifecycle
workload compatibility
PDBs
application rollout
```

with the exact operational responsibility depending partly on AKS mode.

Neither service completely eliminates maintenance.

---

# **15. Availability**

VMSS can distribute instances across:

```text
fault domains
Availability Zones
```

and Microsoft currently supports flexible orchestration for workloads requiring more VM placement flexibility. ([Microsoft Learn][6])

AKS also supports zonal node pools and multi-zone application designs.

But important:

```text
nodes across zones
does not automatically mean
Pods are evenly distributed.
```

For AKS you may need:

```text
topologySpreadConstraints
pod anti-affinity
PDB
```

depending on failure model.

---

# **16. Cost**

VMSS itself doesn't add Kubernetes-platform operational complexity.

You pay for:

```text
VMs
disks
networking
```

and associated services.

AKS adds container orchestration and, depending on tier/mode/design, platform-related costs and engineering complexity.

The real comparison is:

```text
VMSS:
simpler infrastructure
but you build application orchestration

AKS:
more platform complexity
but Kubernetes provides orchestration
```

### **Interview answer condensed**

> “VM Scale Sets manage and autoscale groups of virtual machines, while AKS provides Kubernetes orchestration for containerized applications. VMSS understands VM instances, health, placement and capacity; it doesn't inherently understand Pods, Deployments, Services or container scheduling. AKS adds that application orchestration layer and often uses scalable Azure VM infrastructure underneath its node pools. So I'd use VMSS for VM-centric or legacy applications that need OS control, and AKS when I need Kubernetes features such as container scheduling, service discovery, self-healing, HPA, rolling deployments and the Kubernetes ecosystem.”

**Memory line:**
**VMSS scales machines; AKS orchestrates applications on machines.**

**Interview trap:**
Adding more VMSS instances does **not automatically scale or redistribute your application processes** the way Kubernetes scales and schedules Pods.
