### **T34-44. Rolling deployment vs blue-green deployment?**

**Answer:**

Both are strategies for releasing a new application version while reducing downtime, but they differ in **how much parallel capacity exists and how traffic moves between versions**.

In a **rolling deployment**, I gradually replace instances of the old version with the new version inside the same environment. For example, with 10 AKS Pods, Kubernetes might replace two or three Pods at a time until all Pods run the new version.

In a **blue-green deployment**, I maintain two complete environments: **Blue**, which currently serves Production, and **Green**, which contains the new version. I validate Green first and then switch Production traffic from Blue to Green.

So:

```text
Rolling
→ gradually replace instances
→ old and new versions coexist temporarily

Blue-green
→ build full parallel environment
→ switch traffic between environments
```

Rolling is usually more resource-efficient. Blue-green generally provides a cleaner and faster traffic rollback, but it requires additional capacity and careful handling of shared state such as databases.

---

## **1. Rolling deployment architecture**

Suppose AKS currently runs:

```text
Deployment: orders
replicas: 6

All Pods:
v1
```

A rolling update begins:

```text
Stage 1
v1 v1 v1 v1 v1 v2

Stage 2
v1 v1 v1 v2 v2 v2

Stage 3
v1 v2 v2 v2 v2 v2

Stage 4
v2 v2 v2 v2 v2 v2
```

For part of the rollout:

```text
v1
+
v2
```

are serving Production simultaneously.

That coexistence is one of the most important rolling-deployment characteristics.

---

## **2. Kubernetes rolling deployments**

For AKS, a Kubernetes Deployment commonly uses:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

Conceptually:

```text
maxSurge
→ how much temporary extra capacity
   can exist during the rollout

maxUnavailable
→ how much desired capacity
   may be unavailable during rollout
```

If:

```text
replicas = 5
maxSurge = 1
maxUnavailable = 0
```

Kubernetes can temporarily run:

```text
6 Pods
```

while replacing old Pods.

This helps maintain serving capacity.

---

# **3. Readiness is critical in rolling deployments**

Imagine Kubernetes starts a new Pod:

```text
Container process started
```

but application still needs:

```text
20 seconds
```

to:

```text
load configuration
warm cache
connect to database
initialize dependencies
```

Without a proper readiness probe:

```text
Service
→ sends traffic too early
→ users receive errors
```

A strong rolling deployment has:

```text
New Pod
   ↓
startup
   ↓
readiness probe succeeds
   ↓
only then receive Production traffic
```

So a process being **Running** does not mean the application is **Ready**.

---

# **4. Graceful shutdown matters too**

During replacement:

```text
Old Pod
   ↓
termination requested
```

If it has an active 10-second request and immediately exits:

```text
client
→ connection reset
```

A production rollout should consider:

```text
readiness removal
connection draining
SIGTERM handling
terminationGracePeriodSeconds
preStop if genuinely needed
```

The goal is:

```text
Stop new requests
     ↓
finish in-flight requests
     ↓
terminate safely
```

---

# **5. Rolling deployments use less duplicate infrastructure**

Suppose Production normally requires:

```text
20 Pods
```

Rolling might temporarily require:

```text
20 + small surge
```

depending on `maxSurge`.

Blue-green may require approximately:

```text
20 Blue
+
20 Green
```

during deployment.

Therefore rolling usually has lower temporary compute cost.

---

# **6. Blue-green architecture**

Normal state:

```text
                   Users
                     ↓
               Traffic Router
                     ↓
                  BLUE
                  v41
```

Meanwhile:

```text
GREEN
v42
```

is deployed separately.

During validation:

```text
Blue
→ Production traffic

Green
→ smoke/integration testing
```

Once Green is healthy:

```text
                   Users
                     ↓
               Traffic Router
                  /       \
                 X         ↓
              Blue       Green
              v41        v42
```

Traffic switches to Green.

---

# **7. Azure ways to implement blue-green**

Depending on platform:

```text
App Service
→ deployment slots

AKS
→ separate Deployments/Services
   + ingress/service routing

Azure Container Apps
→ revisions + traffic weights

VM/VMSS
→ separate backend pools/environments

Front Door/Application Gateway
→ route between backends
```

The pattern matters more than the exact Azure service.

---

# **8. Blue-green rollback is usually much faster**

Suppose Green receives Production traffic and immediately produces:

```text
5xx = 20%
```

If Blue remains intact:

```text
Traffic
Green → Blue
```

can be a quick rollback.

You don't necessarily need to:

```text
rebuild old containers
recreate old VM images
roll Pods backward gradually
```

because the old environment already exists.

This is one of blue-green's strongest advantages.

---

# **9. Rolling rollback is less clean**

Suppose rollout is halfway:

```text
v1 = 5 Pods
v2 = 5 Pods
```

and v2 is broken.

Kubernetes can roll back to v1, but the system still needs to:

```text
replace v2 Pods
with v1 Pods
```

gradually.

During that time:

```text
some users may continue hitting v2
```

until rollback progresses.

Blue-green can often remove the bad version from traffic much more abruptly.

---

# **10. Blue-green does not automatically make database rollback easy**

This is the biggest trap.

Suppose Green v42 deploys migration:

```sql
ALTER TABLE orders
DROP COLUMN legacy_status;
```

Then traffic goes to Green.

Green writes new data.

You discover a bug and switch traffic back:

```text
Green → Blue
```

But Blue v41 expects:

```text
legacy_status
```

which no longer exists.

So:

```text
application traffic rollback
≠
data rollback
```

This affects rolling deployments too, but blue-green can create a false sense that rollback is instant.

---

# **11. Use backward-compatible database migrations**

A safer pattern is:

```text
EXPAND
   ↓
Add new schema while old schema still works
   ↓
Deploy application compatible with both
   ↓
Backfill/migrate
   ↓
Verify
   ↓
CONTRACT
   ↓
remove old schema later
```

For example:

Instead of:

```text
rename old_column → new_column immediately
```

do:

```text
add new_column
      ↓
app temporarily handles both
      ↓
backfill
      ↓
old version retired
      ↓
remove old_column later
```

This supports both rolling coexistence and blue-green rollback.

---

# **12. Version compatibility is especially important for rolling**

Because:

```text
v1
+
v2
```

run simultaneously.

Therefore both versions may need to work with:

```text
same database schema
same queue messages
same APIs
same session/state formats
```

during the rollout.

Example:

```text
v2 produces message schema B
```

but v1 worker only understands:

```text
schema A
```

Then a rolling deployment can break even if each version works independently.

---

# **13. Blue-green provides stronger pre-production validation**

Green can be:

```text
fully deployed
fully warmed
health checked
smoke tested
```

before receiving normal Production traffic.

For example:

```text
CI/CD
  ↓
Green environment
  ↓
health checks
  ↓
synthetic transaction
  ↓
database connectivity
  ↓
dependency tests
  ↓
traffic switch
```

With a rolling deployment, the candidate enters Production progressively as instances are replaced.

---

# **14. But blue-green can hide capacity issues**

Suppose Green was tested with:

```text
10 synthetic requests/sec
```

Then switch:

```text
50,000 requests/sec
```

to Green.

Everything collapses.

Therefore before switching I need to validate:

```text
capacity
autoscaling
connection pools
dependency limits
cache warming
```

not merely:

```text
HTTP /health returned 200.
```

---

# **15. Rolling deployment failure containment**

A well-designed rolling rollout should monitor:

```text
candidate 5xx
p95/p99 latency
critical transaction success
restart rate
dependency errors
```

If new replicas are unhealthy:

```text
pause rollout
```

rather than continue replacing healthy old replicas.

The important comparison is often:

```text
new version
vs
stable version
```

not merely global service metrics.

---

# **16. Availability trade-off**

Rolling can provide near-zero downtime when:

```text
enough replicas
proper readiness
safe surge/unavailable values
backward-compatible versions
```

exist.

But if:

```text
replicas = 1
```

and:

```text
maxUnavailable = 1
```

you can absolutely create downtime.

A “rolling deployment” label doesn't magically make the deployment highly available.

---

# **17. Cost trade-off**

### Rolling

```text
+ less duplicate infrastructure
+ simpler capacity footprint
- slower clean rollback
- mixed versions during rollout
```

### Blue-green

```text
+ fast traffic switch
+ clean environment separation
+ easy pre-cutover testing
- temporary double capacity
- routing/environment complexity
- database rollback still difficult
```

## **Production example**

Suppose I run an AKS stateless REST API:

```text
20 replicas
stable schema
high deployment frequency
easy container rollback
```

I'd probably use:

```text
rolling deployments
```

for normal releases because they're efficient.

But for:

```text
major framework upgrade
high-risk release
strict rollback requirement
```

I might choose:

```text
blue-green
```

so the old environment remains intact until the new one is proven.

---

### **Interview answer condensed**

> “A rolling deployment gradually replaces old instances with new ones, so both versions temporarily serve Production traffic. It's resource-efficient and works very naturally with AKS Deployments, but I need proper readiness, graceful shutdown and backward compatibility between versions. Blue-green keeps two complete environments: Blue is the current Production version and Green is the candidate. I validate Green and then switch traffic to it, which gives a very fast application rollback because Blue is still available, but it costs more capacity and doesn't solve database rollback automatically. I usually use rolling for routine low-risk stateless releases and blue-green when environment-level isolation and fast cutback are more important.”

**Memory line:**
**Rolling replaces Production gradually; blue-green builds the replacement beside Production and then switches traffic.**

**Interview trap:**
Blue-green provides fast **traffic rollback**, not guaranteed **database rollback**.

**Keywords:**
rolling deployment, blue-green, `maxSurge`, `maxUnavailable`, readiness, graceful shutdown, deployment slots, backward-compatible migration.

* How would you implement blue-green on AKS?
* Why can database changes make blue-green rollback unsafe?
* What do `maxSurge` and `maxUnavailable` control?

### **T34-45. Blue-green vs canary deployment?**

**Answer:**

Both reduce deployment risk, but they do it differently.

In **blue-green**, I deploy the new version into a complete parallel environment, validate it, and then switch most or all Production traffic from the old environment to the new one.

In a **canary deployment**, I expose the new version to only a **small percentage of real Production traffic first**, monitor its behavior against the stable version, and gradually increase its traffic share if it remains healthy.

So:

```text
Blue-green
→ environment isolation + fast switch

Canary
→ traffic isolation + gradual risk exposure
```

Blue-green is excellent when I want a very clean cutover and immediate fallback to the old environment. Canary is better when the major question is:

> “How does the new version behave under real Production traffic before I expose everyone?”

---

## **1. Blue-green**

```text
                Production users
                      ↓
                   BLUE
                   v41

GREEN v42
→ deployed separately
→ tested separately
```

Cutover:

```text
Before:
100% → Blue

After:
100% → Green
```

Rollback:

```text
100% → Blue
```

as long as Blue is still compatible with state.

---

# **2. Canary**

Start:

```text
Stable v41
→ 95%

Canary v42
→ 5%
```

Then:

```text
Healthy?

5%
 ↓
10%
 ↓
25%
 ↓
50%
 ↓
100%
```

If unhealthy:

```text
5% → 0%
```

and:

```text
stable remains serving 95–100%
```

The entire customer base was never exposed.

---

# **3. Canary reduces blast radius**

Suppose v42 has a bug affecting:

```text
checkout
```

Blue-green switch:

```text
100% users
→ v42
```

Potential blast radius:

```text
entire user population
```

until detection and rollback.

Canary:

```text
5% users
→ v42
```

Potential initial blast radius:

```text
~5%
```

This is canary's biggest safety advantage.

---

# **4. Blue-green is simpler conceptually**

Blue-green usually asks:

```text
Is Green healthy enough
to become Production?
```

Then:

```text
switch
```

Canary requires:

```text
traffic segmentation
candidate-specific telemetry
baseline comparison
progression rules
automatic abort logic
```

So Canary is generally operationally more sophisticated.

---

# **5. Canary is only safe if telemetry distinguishes versions**

Suppose:

```text
v41 error rate = 0.2%
v42 error rate = 18%
```

but your dashboard only shows:

```text
global error rate = 1.1%
```

The overall service may look acceptable because most requests still hit v41.

This is dangerous.

Canary metrics should be segmented by:

```text
version
revision
deployment
Pod labels
region
traffic cohort
```

so I can compare:

```text
Candidate
vs
Stable
```

directly.

---

# **6. Good canary health metrics**

I prioritize:

```text
availability
5xx/error rate
p95/p99 latency
critical transaction success
dependency failures
```

Then supporting signals:

```text
CPU
memory
restarts
saturation
```

Example:

```text
Stable checkout success:
99.8%

Canary checkout success:
97.1%
```

Even if:

```text
CPU = normal
```

I stop the rollout.

Users matter more than host utilization.

---

# **7. Canary progression should be objective**

Weak:

```text
Deploy 10%
Wait 10 minutes
Looks okay
Go 100%
```

Stronger:

```text
10% canary
   ↓
evaluate for 10 min

Candidate 5xx
≤ baseline + threshold?

Candidate p95
≤ baseline + threshold?

Critical transaction success
≥ target?

No severe alerts?
   ↓
25%
```

The pipeline should have clear:

```text
continue criteria
abort criteria
```

---

# **8. Canary works best with automated analysis**

For AKS, you can use approaches such as:

```text
Argo Rollouts
service mesh
Ingress-based traffic weights
Azure-native traffic components
```

depending on architecture.

For Azure Container Apps:

```text
revisions
+
traffic weights
```

fit naturally.

Example:

```text
Revision A → 90%
Revision B → 10%
```

and progress from there.

---

# **9. Blue-green can still use staged traffic**

The terms can overlap somewhat.

You might have:

```text
Blue environment
Green environment
```

and initially send:

```text
5% → Green
95% → Blue
```

Technically you're now using a canary-like traffic progression across blue-green environments.

The concepts aren't mutually exclusive.

The distinction is the **primary release strategy**:

```text
Blue-green
→ parallel environments

Canary
→ progressive Production exposure
```

---

# **10. User cohort canaries**

Canary doesn't have to mean:

```text
random 5% of requests.
```

You might expose to:

```text
internal employees
one geography
one tenant
beta users
one customer segment
```

before everyone else.

Example:

```text
Company employees
→ v42

External users
→ v41
```

This can help validate Production behavior while limiting customer risk.

---

# **11. Be careful with stateful user sessions**

Suppose user request 1 hits:

```text
v42
```

then request 2 hits:

```text
v41
```

and versions expect incompatible session structures.

Canary may fail.

Possible controls include:

```text
backward-compatible session format
external shared session storage
sticky routing where justified
```

but sticky routing should not be used to hide fundamentally incompatible releases.

Backward compatibility is safer.

---

# **12. Database compatibility still matters**

Just like blue-green, canary often has:

```text
v41
+
v42
```

running simultaneously.

Therefore schema must support both.

Bad:

```text
Deploy v42
DROP column required by v41
```

Now 95% stable traffic can fail too.

Use:

```text
expand
migrate
contract
```

migration patterns.

---

# **13. Rollback behavior**

### Blue-green

```text
Green fails
→ switch router to Blue
```

Usually very fast.

### Canary

```text
Canary fails
→ set canary weight to 0
→ stable continues
```

Also extremely fast when traffic management is designed well.

But canary's advantage is:

```text
most users never left stable
```

in the first place.

---

# **14. Cost**

Blue-green may require:

```text
full Production capacity × 2
```

during deployment.

Canary might initially require only:

```text
stable capacity
+
small candidate capacity
```

so its temporary compute overhead can be smaller.

However, the observability and traffic-control system is more complex.

---

# **15. When I choose blue-green**

I'd lean blue-green when:

```text
environment-level isolation matters
release is large
fast cutback matters
full parallel testing is useful
traffic switch can be clean
```

Example:

```text
major App Service release
→ Staging slot
→ warm/test
→ slot swap
```

---

# **16. When I choose canary**

I'd choose canary when:

```text
real Production behavior is uncertain
release frequency is high
blast radius needs to stay small
excellent telemetry exists
traffic can be weighted
```

Example:

```text
Payment API
new payment SDK
uncertain third-party behavior
```

Start:

```text
1–5%
```

and observe actual transaction success before wider release.

---

# **17. Canary is inappropriate without observability**

If you can't tell:

```text
which version handled request
whether canary is slower
whether canary produced errors
```

then a canary rollout is mostly theatre.

You cannot safely make:

```text
progress / rollback
```

decisions without version-specific evidence.

## **Quick comparison**

| Characteristic                              | Blue-green                         | Canary                         |
| ------------------------------------------- | ---------------------------------- | ------------------------------ |
| Main isolation                              | **Environment**                    | **Traffic percentage/cohort**  |
| New version exposure                        | Usually switch largely/all at once | **Gradual**                    |
| Initial user blast radius                   | Potentially large at cutover       | **Small**                      |
| Parallel environments                       | **Usually yes**                    | Not necessarily full duplicate |
| Real production testing before full rollout | Limited/pre-switch tests           | **Core strength**              |
| Rollback                                    | Switch to Blue                     | Set candidate traffic to zero  |
| Telemetry complexity                        | Moderate                           | **High**                       |
| Capacity cost                               | Often higher                       | Can be lower initially         |

---

### **Interview answer condensed**

> “Blue-green and canary both reduce deployment risk, but blue-green does it through parallel environments while canary does it through progressive Production exposure. With blue-green, Blue serves Production and I deploy and validate Green separately, then switch traffic to Green. Rollback can be very fast because Blue is still available. With canary, I might send only 5% of Production traffic to the new version, compare its error rate, latency and transaction success against the stable version, and increase the percentage only if the candidate is healthy. I prefer canary when I need real Production validation with a small initial blast radius, but it requires excellent version-specific telemetry.”

**Memory line:**
**Blue-green asks “Can the new environment take over?”; canary asks “Can the new version earn more traffic safely?”**

**Interview trap:**
A canary without **candidate-specific metrics** can hide a badly failing new version behind the healthy stable majority.

**Keywords:**
blue-green, canary, traffic weighting, blast radius, progressive delivery, baseline, rollback, revisions, Argo Rollouts.

**Likely follow-ups:**

* What metrics would you use to promote a canary?
* Why can global metrics hide a broken canary?
* How would you canary an AKS workload?
* Can you combine blue-green and canary strategies?

### **T34-46. SAST vs DAST?**

**Answer:**

SAST and DAST are both application-security testing techniques, but they inspect the application from different perspectives.

**SAST — Static Application Security Testing** analyzes source code, bytecode, or compiled application artifacts **without needing the application to be running**. It looks for insecure coding patterns such as injection risks, unsafe API use, hardcoded secrets, or insecure data handling.

**DAST — Dynamic Application Security Testing** tests a **running application from the outside**, interacting with its HTTP/API surface much like an attacker. It looks for exploitable runtime behavior such as injection, authentication problems, security-header issues, or input-validation vulnerabilities.

So:

```text
SAST
→ inspect the code/application internally

DAST
→ attack/test the running application externally
```

A mature DevSecOps pipeline uses both because they find different classes of problems.

---

## **1. SAST works before runtime**

Pipeline:

```text
Developer commit
      ↓
Source code
      ↓
SAST scanner
      ↓
Findings
      ↓
Build
```

Typical SAST tools inspect things like:

```text
tainted input flows
dangerous functions
hardcoded credentials
unsafe deserialization
SQL query construction
weak crypto usage
```

depending on tool/language.

This makes SAST highly useful early in the SDLC.

---

# **2. Example SAST finding**

Code:

```javascript
const query =
  `SELECT * FROM users WHERE name='${req.query.name}'`;
```

Static scanner might identify:

```text
untrusted user input
       ↓
string concatenation
       ↓
SQL query
```

and report:

```text
potential SQL injection
```

without deploying the application.

The developer can fix it using:

```text
parameterized query
```

before runtime.

---

# **3. DAST requires a running target**

Flow:

```text
DAST scanner
    ↓
HTTP request
    ↓
Running app/API
    ↓
HTTP response
    ↓
Scanner analyzes behavior
```

The scanner might attempt:

```text
' OR 1=1 --
<script>
../../etc/passwd
unexpected HTTP methods
malformed parameters
```

and inspect responses.

DAST views the system:

```text
from an external attacker's perspective
```

rather than understanding source-code structure.

---

# **4. DAST can discover runtime/configuration problems**

Suppose source code is secure, but Production-like deployment has:

```text
debug mode enabled
misconfigured CORS
missing security headers
unprotected endpoint
bad authentication configuration
```

SAST may not identify the complete deployed behavior.

DAST may observe:

```text
/api/admin
→ responds without authentication
```

or:

```text
Access-Control-Allow-Origin: *
```

where inappropriate.

That's why runtime testing matters.

---

# **5. SAST gives better code-location feedback**

A SAST result can often point directly to:

```text
src/controllers/user.ts
line 182
```

with a data-flow explanation:

```text
request input
→ function A
→ function B
→ SQL call
```

This is very developer-friendly.

DAST might instead say:

```text
POST /api/users
parameter: name
SQL injection appears possible
```

It proves suspicious runtime behavior but may not know exactly which source line caused it.

---

# **6. DAST can demonstrate exploitability better**

SAST might say:

```text
potential XSS path
```

but perhaps:

```text
framework escaping
runtime validation
reverse proxy filtering
```

means it is not actually exploitable.

DAST sees the deployed application behavior and can sometimes demonstrate:

```text
payload reflected/executed
```

which provides stronger runtime evidence.

So:

```text
SAST
→ code-risk visibility

DAST
→ runtime exploitability visibility
```

roughly speaking.

---

# **7. Neither is perfect**

### SAST false positives

Static analysis may report:

```text
possible vulnerability
```

that runtime controls make unreachable.

### DAST false negatives

Dynamic scanner can only test:

```text
routes
parameters
states
authentication contexts
```

it can reach.

If an endpoint isn't discovered:

```text
it may never be tested.
```

So combining them gives stronger coverage.

---

# **8. Authentication is a DAST challenge**

Suppose application requires:

```text
Entra authentication
MFA
complex session flow
```

A DAST scanner that cannot authenticate only tests:

```text
public login surface
```

and misses:

```text
authenticated APIs
admin endpoints
business functions
```

A mature DAST configuration may require:

```text
test account
token acquisition
authenticated scan context
safe non-Production environment
```

# **9. CI/CD placement**

A practical pipeline:

```text
Pull Request
   ↓
SAST
   ↓
unit tests
   ↓
build image
   ↓
SCA / image scan
   ↓

   ↓
DAST
   ↓
promotion decision
```

SAST is naturally earlier because:

```text

```

DAST naturally comes after:

```text

```

# **10. SAST vs SCA**

Another common interview distinction:

```text
SAST
→ analyzes your application code
```

while:

```text
SCA
Software Composition Analysis
→ analyzes third-party dependencies
```

Example:

Your code:

```text
secure
```

but dependency:

```text
log4j vulnerable version
```

SAST alone may not be the right primary control.

SCA identifies:

```text
known CVE in dependency.
```

In DevSecOps:

```text
SAST
+
SCA
+
container scanning
+
DAST
```

cover different attack surfaces.

---

# **11. SAST vs secret scanning**

Likewise:

```text
secret scanning
```

specifically searches for:

```text
API keys
passwords
tokens
private keys
```

in source/history.

Some SAST products detect secrets too, but conceptually:

```text
secret scanning
≠
all static security analysis.
```

---

# **12. DAST should not casually attack Production**

An aggressive DAST tool may:

```text
submit malformed payloads
create records
trigger operations
stress endpoints
```

so I prefer:

```text
Production-like staging environment
```

for broad scans.

If scanning Production is required:

```text
use carefully scoped safe testing
approved rules
rate limits
non-destructive payloads
```

because a security tool shouldn't become the cause of an outage.

# **14. Shift left does not mean only SAST**

“Shift left” means catching issues earlier.

SAST fits shift-left extremely well.

But relying only on static security means missing:

```text
deployment configuration
runtime middleware behavior
auth integration
reverse proxy behavior
security headers
```

So mature security includes:

```text
shift left
+
runtime validation
```

rather than choosing one.

# **15. Example — SQL injection**

### SAST

Finds:

```text
user input
→ unsafe SQL string
```

before deployment.

### DAST

Sends:

```text
?id=1' OR '1'='1
```

and may observe:

```text
unexpected database behavior
```

from the running API.

Two views of the same class of weakness.

## **Quick comparison**

| Characteristic                 | SAST                                | DAST                                 |
| ------------------------------ | ----------------------------------- | ------------------------------------ |
| Full name                      | Static Application Security Testing | Dynamic Application Security Testing |
| Application running required   | **No**                              | **Yes**                              |
| Main input                     | Source/binary/artifact              | Running endpoint                     |
| Perspective                    | Inside/code                         | **Outside/attacker-like**            |
| Finds code patterns            | **Strong**                          | No source visibility                 |
| Finds runtime misconfiguration | Limited                             | **Strong**                           |
| Source-line feedback           | **Usually strong**                  | Usually weaker                       |
| Runtime exploit evidence       | Limited                             | **Stronger**                         |
| Best pipeline position         | Early/PR                            | After deployment to test env         |

---

### **Interview answer condensed**

> “SAST analyzes application code or artifacts without running the application, so I use it early in CI to detect insecure coding patterns such as injection risks or unsafe API use and give developers direct code-level feedback. DAST tests a deployed application externally by sending requests and analyzing runtime behavior, so it can identify issues such as exploitable input handling, authentication problems, or deployment misconfiguration that static analysis may miss. I use both: SAST shifts detection left, while DAST validates how the actual running application behaves.”

**Memory line:**
**SAST reads the application; DAST attacks the running application.**

**Interview trap:**
SAST and DAST are **not substitutes**, and neither replaces dependency/SCA or container-image scanning.

**Keywords:**
SAST, DAST, static analysis, runtime testing, DevSecOps, SCA, false positive, OWASP, shift left.

* Where would you run SAST and DAST in CI/CD?
* Why can SAST report false positives?
* Why can DAST miss authenticated endpoints?
* What's the difference between SAST and SCA?

### **T34-47. Authentication vs authorization?**

**Answer:**

**Authentication** determines **who or what the caller is**.
**Authorization** determines **what that authenticated identity is allowed to do**.

In Azure, authentication is commonly handled by **Microsoft Entra ID**, which validates an identity and issues a token. Authorization happens afterward—for example, **Azure RBAC** evaluates whether that identity has a required role at the appropriate scope.

So:

```text
Authentication
→ "Who are you?"

Authorization
→ "What are you allowed to do?"
```

A very useful troubleshooting rule is:

```text
401
→ usually authentication problem

403
→ identity was recognized,
   but authorization/policy denies the operation
   in many common HTTP/Azure scenarios
```

Though exact HTTP behavior depends on the service, that distinction is extremely useful when diagnosing Azure access failures.

## **1. Azure identity flow**

Consider an application accessing Azure Storage:

```text
Application
     ↓
Managed Identity
     ↓
Microsoft Entra ID
     ↓
Access token
     ↓
Storage
     ↓
Azure RBAC / data-plane authorization
     ↓
Allow or deny
```

There are two separate decisions.

### Authentication

```text
Is this token valid?
Who does it represent?
```

### Authorization

```text
Does this principal have
Storage Blob Data Reader
at this scope?
```

# **2. Example: Managed Identity**

AKS application:

```text
Pod
 ↓
ServiceAccount
 ↓
AKS OIDC federation
 ↓
Microsoft Entra Workload Identity
 ↓
access token
```

Successful token issuance means:

```text
authentication succeeded
```

It does **not** mean:

```text
Storage access automatically succeeds.
```

The identity still needs appropriate:

```text
data-plane RBAC
```

on Storage.

# **3. 403 example**

Application calls Blob Storage:

```text
GET blob
```

Result:

```text
403 Forbidden
```

Suppose token is valid.

That tells me to inspect:

```text
Identity
   ↓
Role assignment
   ↓
Scope
   ↓
DataAction
```

For example, identity has:

```text
Reader
```

at Storage Account.

But reading Blob content requires something like:

```text
Storage Blob Data Reader
```

under Entra-based Blob authorization.

So:

```text
Authentication:
✓

Control-plane visibility:
possibly ✓

Blob data-plane authorization:
✗
```

That distinction is extremely common in Azure interviews.

# **4. Azure `Reader` isn't the same as Blob Data Reader**

Azure RBAC has:

```text
management/control-plane roles
```

and service-specific:

```text
data-plane roles
```

For example:

```text
Reader
→ can view Azure resource configuration

Storage Blob Data Reader
→ can read Blob data
```

Therefore:

```text
"I can see the Storage Account
in Azure Portal"
```

does not prove:

```text
"I can read its blobs."
```

This is one of the most useful practical authz distinctions.

# **5. Authentication mechanisms**

Common Azure authentication methods include:

```text
User + MFA
Managed Identity
Workload Identity
Service Principal + OIDC federation
Certificate
Client secret
```

For modern machine workloads I prefer:

```text
Managed Identity
or
OIDC / Workload Identity Federation
```

where supported, instead of manually rotated long-lived secrets.

But whichever mechanism is used, the output of authentication is typically:

```text
identity + token
```

not unlimited access.

# **6. Authorization mechanisms**

Authorization could include:

```text

Microsoft Entra directory roles
Kubernetes RBAC
application-level roles
database permissions
Key Vault data permissions
```

depending on the protected resource.

This is another important interview nuance:

```text

```

is not always:

```text
Azure RBAC.
```

Example:

```text

```

may involve:

```text

        ↓

```

depending on AKS configuration.

# **10. Authorization failure**

Authentication works:

```text
valid token obtained
```

but operation returns:

```text
403
AuthorizationFailed
Forbidden
```

Now I check:

```text
1. What exact identity is being used?
2. What operation is being attempted?
3. What role contains that action/DataAction?
4. At what scope is role assigned?
5. Are deny assignments/policies involved?
6. Has role propagation completed?
```

This is much more precise than:


# **11. Always verify the actual principal**

This is critical in CI/CD troubleshooting.

Your own user access doesn't matter if pipeline uses:

```text

managed identity
federated identity
```

The correct question is:

```text
Which principal made the failing request?
```

Flow:

```text
Developer personal identity
           ≠
Pipeline service connection identity
```

Compare the RBAC of the actual pipeline principal.

# **15. Authentication can succeed while authorization changes over time**

Suppose token represents:

```text
principal A
```

and administrator removes:

```text
Contributor role
```

The identity hasn't disappeared.

Authentication can still succeed.

But the next resource operation may be:

```text
403
```

because authorization has changed.

This cleanly demonstrates why the two concepts must stay separate.

# **16. Least privilege belongs to authorization**

Good security design:

```text
Authentication
→ strong identity
   Managed Identity/OIDC/MFA

Authorization
→ minimum required permissions
   narrow scope
```

Example:

Bad:

```text
GitHub pipeline
→ Owner
→ Subscription
```

Better:

```text
GitHub pipeline
→ Contributor
→ rg-app-prod
```

and if it needs a separate RBAC action:

```text
grant narrowly scoped RBAC management capability
```

rather than broad Owner unnecessarily.

### **Interview answer condensed**

> “Authentication proves the identity of the caller, while authorization determines what that identity is permitted to do. In Azure, Microsoft Entra ID commonly handles authentication and issues a token, and then Azure RBAC or another authorization system checks whether that principal has permission for the requested operation. For troubleshooting, if token acquisition fails or I see a 401, I investigate authentication. If the identity is valid but the request receives 403, I inspect authorization such as the exact role, scope and required control-plane or data-plane permissions. Managed Identity or OIDC removes credential-management problems, but it does not automatically grant authorization.”

**Memory line:**
**Authentication establishes identity; authorization grants capability.**

**Interview trap:**
A valid Entra token or successful Managed Identity authentication does **not** mean the caller automatically has access to the target Azure resource.
