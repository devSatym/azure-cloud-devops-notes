# **T26-M02. How do you list resource groups using Azure CLI?**

**Answer:**

I would use:

```bash
az group list
```

By default, Azure CLI returns the resource groups visible in the **currently selected subscription** as JSON.

For day-to-day use, I normally make the output easier to read:

```bash
az group list -o table
```

And if I need only particular fields for automation, I use `--query`, for example:

```bash
az group list \
  --query "[].{Name:name,Location:location}" \
  -o table
```

Before running the command in a multi-subscription environment, I would verify the active subscription with `az account show`, because `az group list` operates against the current Azure CLI subscription context.

---

## **How the command fits into Azure**

The flow is:

```text
Azure CLI
   ↓
Current subscription context
   ↓
Azure Resource Manager
   ↓
Resource groups visible to identity
   ↓
JSON response
```

The basic command:

```bash
az group list
```

does not mean:

> “Show every resource group in every Azure subscription I can access.”

It means, conceptually:

> “List resource groups from the active subscription context.”

So I commonly check:

```bash
az account show \
  --query "{name:name,id:id}" \
  -o table
```

first.

---

## **Useful output formats**

### Human-readable table

```bash
az group list -o table
```

This is useful interactively.

Example conceptually:

```text
Name              Location
----------------  ------------
rg-network-prod   centralindia
rg-aks-prod       eastus
rg-monitoring     centralindia
```

---

### JSON

```bash
az group list -o json
```

Useful when another tool or script expects structured JSON.

---

### TSV**

If I need values for shell scripting:

```bash
az group list \
  --query "[].name" \
  -o tsv
```

Example output:

```text
rg-network-prod
rg-aks-prod
rg-monitoring
```

This is generally easier to loop over than parsing formatted table output.

---

## **Filtering resource groups**

Suppose I need only resource groups in `centralindia`.

I could use:

```bash
az group list \
  --query "[?location=='centralindia'].{Name:name,Location:location}" \
  -o table
```

Conceptually:

```text
All resource groups
       ↓
JMESPath filter
       ↓
location == centralindia
       ↓
matching groups only
```

This is useful during inventory or troubleshooting.

---

## **Listing one known resource group**

If I already know the name and want details, I wouldn't list everything and grep it.

I'd use:

```bash
az group show \
  --name rg-aks-prod
```

That's more precise.

So:

```text
az group list
→ enumerate groups

az group show
→ inspect one group
```

---

## **Authentication and authorization implication**

If:

```bash
az group list
```

returns fewer groups than expected, I wouldn't immediately assume Azure has deleted something.

I would check:

```text
1. Correct tenant?
2. Correct subscription?
3. Correct identity?
4. Does the identity have RBAC visibility?
```

For example:

```bash
az account show
az account list -o table
```

A user with limited Azure RBAC may not be able to see resources outside their assigned scope.

---

## **Production scripting example**

Suppose I want to inspect all resource groups with a prefix:

```bash
az group list \
  --query "[?starts_with(name, 'rg-prod-')].name" \
  -o tsv
```

Then:

```bash
for rg in $(az group list \
  --query "[?starts_with(name, 'rg-prod-')].name" \
  -o tsv); do
    echo "Checking $rg"
done
```

The important part is that I use structured Azure CLI output rather than fragile text parsing such as:

```bash
az group list | grep ...
```

when `--query` can return exactly what I need.

---

### **Interview answer condensed**

> “I use `az group list` to list resource groups in the currently selected subscription, usually with `-o table` for interactive use. For automation I combine it with `--query` and `-o tsv` or JSON—for example `az group list --query "[].name" -o tsv`. In a multi-subscription environment I'd first verify the current context using `az account show`, because the command operates against the active subscription and the results are also limited by the authenticated identity's permissions.”

**Memory line:**
**`az group list` lists groups; `--query` selects what I need; the active subscription determines where I'm looking.**

**Interview trap:**
`az group list` does **not automatically enumerate resource groups across every subscription** available to your account.

**Keywords:**
`az group list`, `az group show`, `--query`, `-o table`, `-o tsv`, subscription context, Azure RBAC.

# **T26-M03. How do you query JSON results from Azure CLI?**

**Answer:**

Azure CLI supports the `--query` parameter, which uses **JMESPath expressions** to filter, project, and transform the JSON returned by Azure commands.

For example, instead of returning the full object:

```bash
az vm list
```

I can request only VM names and locations:

```bash
az vm list \
  --query "[].{Name:name,Location:location}" \
  -o table
```

For scripts I often combine `--query` with `-o tsv` so I get a clean scalar or list without writing a separate JSON parser.

```text
Azure API response
      ↓
JSON
      ↓
--query / JMESPath
      ↓
Selected fields
      ↓
json / table / tsv
```

---

## **1. Azure CLI normally returns structured data**

For example:

```bash
az account show
```

may return an object containing fields such as:

```json
{
  "id": "...",
  "name": "...",
  "tenantId": "...",
  "user": {
    "name": "..."
  }
}
```

Instead of processing all of that, I can ask for one property:

```bash
az account show --query id
```

---

## **2. Getting a scalar value**

For shell automation:

```bash
SUBSCRIPTION_ID=$(az account show \
  --query id \
  -o tsv)
```

Why `-o tsv`?

Without it, JSON output might conceptually look like:

```text
"1234-..."
```

With TSV:

```text
1234-...
```

which is more convenient as a shell variable.

So:

```text
--query
→ choose data

-o
→ choose how the result is rendered
```

Those are separate concerns.

---

# **3. Querying arrays**

Suppose:

```bash
az group list
```

returns an array of resource-group objects.

To return every name:

```bash
az group list \
  --query "[].name" \
  -o tsv
```

Mental model:

```text
[
  RG object,
  RG object,
  RG object
]
   ↓
[].name
   ↓
name
name
name
```

---

# **4. Filtering**

Suppose I want only resources in `eastus`:

```bash
az group list \
  --query "[?location=='eastus']"
```

Here:

```text
[? condition]
```

filters the array.

Then I can project fields:

```bash
az group list \
  --query "[?location=='eastus'].{Name:name,Location:location}" \
  -o table
```

---

# **5. Selecting multiple fields**

Suppose I want AKS name, location and Kubernetes version:

```bash
az aks list \
  --query "[].{Name:name,Location:location,Version:kubernetesVersion}" \
  -o table
```

The result is much easier to use in an interview or operational session than printing the complete resource objects.

---

# **6. Nested properties**

If an object contains:

```text
identity
   ↓
type
```

I can query it using dotted paths.

For example:

```bash
az aks show \
  -g rg-aks \
  -n aks-prod \
  --query identity.type \
  -o tsv
```

So the general model is:

```text
topLevel.child.grandchild
```

when navigating nested JSON objects.

---

# **7. Query versus output format**

This distinction is commonly confused.

### `--query`

Changes **which data** is returned to me.

### `--output` / `-o`

Changes **how that selected data is displayed**.

Example:

```bash
az group list \
  --query "[].{Name:name,Location:location}" \
  -o table
```

```text
--query
→ Name + Location only

-o table
→ display them as a table
```

Changing:

```bash
-o json
```

to:

```bash
-o table
```

doesn't change the underlying field selection.

---

# **8. Why I prefer structured querying over `grep`**

A fragile script:

```bash
az vm list | grep prod
```

depends on:

* output formatting,
* whitespace,
* unrelated values containing `prod`,
* JSON formatting.

A structured query:

```bash
az vm list \
  --query "[?contains(name, 'prod')].name" \
  -o tsv
```

expresses what I actually mean.

```text
Text parsing
→ presentation-dependent

JMESPath
→ data-structure-aware
```

That's much safer for automation.

---

# **9. Practical troubleshooting use**

Suppose an AKS deployment cannot pull from ACR and I want the kubelet identity.

Instead of reading a huge JSON object:

```bash
az aks show -g rg-prod -n aks-prod
```

I can query:

```bash
az aks show \
  -g rg-prod \
  -n aks-prod \
  --query identityProfile.kubeletidentity.objectId \
  -o tsv
```

Now I have exactly the identity object ID I need for the next RBAC check.

This is a strong real-world use of Azure CLI queries: **extract one piece of evidence and feed it into the next troubleshooting step**.

---

# **10. Shell-variable example**

```bash
KUBELET_OBJECT_ID=$(az aks show \
  -g rg-prod \
  -n aks-prod \
  --query identityProfile.kubeletidentity.objectId \
  -o tsv)

az role assignment list \
  --assignee "$KUBELET_OBJECT_ID" \
  -o table
```

Flow:

```text
AKS resource
    ↓
query kubelet identity
    ↓
object ID
    ↓
query RBAC assignments
```

That's much cleaner than copying fields manually.

## **JMESPath versus KQL**

Don't confuse these.

```text
JMESPath
→ client-side querying/filtering of Azure CLI JSON results

KQL
→ querying telemetry/data in services such as Log Analytics
```

They solve very different problems.

---

### **Interview answer condensed**

> “Azure CLI uses `--query` with JMESPath to filter or transform the JSON returned by commands. For example, `az vm list --query "[].{Name:name,Location:location}" -o table` gives me just the fields I need. In scripts I often use `-o tsv` when extracting a single value into a variable. I distinguish `--query`, which selects data, from `-o`, which only controls its display format. I also prefer structured JMESPath queries over `grep` because they're based on JSON fields rather than output formatting.”

**Memory line:**
**`--query` decides what data I want; `-o` decides how I want to see it.**

**Interview trap:**
Azure CLI `--query` uses **JMESPath**, not KQL.

**Keywords:**
`--query`, JMESPath, JSON, `-o tsv`, `-o table`, projection, filtering, nested properties.

# **T26-M04. How would you automate creating Azure resources using CLI scripts?**

**Answer:**

I would write the Azure CLI script as a **repeatable, fail-fast automation workflow**, not just copy a series of commands from an interactive terminal.

I would first authenticate using an automation identity such as Managed Identity or workload identity federation, explicitly select and verify the subscription, parameterize environment-specific values, check or create resources in dependency order, validate the results after important operations, and return a non-zero exit code on failure.

For production I would also make the script as idempotent as practical so rerunning it doesn't accidentally create duplicates or corrupt resources.

```text
Authenticate
    ↓
Set subscription
    ↓
Validate inputs
    ↓
Create Resource Group
    ↓
Create Network
    ↓
Create dependent resources
    ↓
Validate each stage
    ↓
Log result
    ↓
Success / fail safely
```

For complex, long-lived infrastructure, however, I would normally prefer Terraform or Bicep because they provide a declarative desired-state model. CLI scripts are strongest for operational automation, bootstrapping, and relatively small workflows.

---

# **1. Start with safe shell behavior**

For Bash, I might begin with:

```bash
#!/usr/bin/env bash
set -euo pipefail
```

Conceptually:

```text
-e
→ stop when a command fails

-u
→ fail on unset variables

pipefail
→ detect failures inside pipelines
```

This helps avoid situations like:

```text
Step 2 fails
   ↓
script keeps running
   ↓
Step 7 modifies production anyway
```

---

# **2. Parameterize values**

Bad:

```bash
az group create \
  -n rg-satyam-test-123 \
  -l eastus
```

Better:

```bash
RESOURCE_GROUP="${RESOURCE_GROUP:?RESOURCE_GROUP is required}"
LOCATION="${LOCATION:-eastus}"
SUBSCRIPTION_ID="${SUBSCRIPTION_ID:?SUBSCRIPTION_ID is required}"
```

Then:

```bash
az group create \
  --name "$RESOURCE_GROUP" \
  --location "$LOCATION"
```

Now the same script can support:

```text
Dev
Stage
Prod
```

without editing source code.

---

# **3. Authenticate without human credentials**

For CI/CD I would avoid:

```text
az login with username/password
```

I would prefer:

```text
GitHub Actions
      ↓
OIDC federation
```

or, when the script runs on an Azure-hosted environment with an assigned identity:

```bash
az login --identity
```

Then Azure RBAC grants only the permissions necessary for the target scope.

---

# **4. Explicitly establish subscription context**

I would not trust the previous Azure CLI session.

```bash
az account set \
  --subscription "$SUBSCRIPTION_ID"
```

Then verify:

```bash
ACTIVE_SUB=$(az account show \
  --query id \
  -o tsv)

if [[ "$ACTIVE_SUB" != "$SUBSCRIPTION_ID" ]]; then
  echo "Wrong Azure subscription"
  exit 1
fi
```

This prevents:

```text
Valid automation
+
wrong subscription
=
production incident
```

---

# **5. Validate prerequisites**

Before creating resources:

```bash
command -v az >/dev/null || {
  echo "Azure CLI missing"
  exit 1
}
```

I might also check:

```bash
az account show >/dev/null
```

to confirm authentication.

For a particular feature, I may check that required extensions, providers, quotas or permissions exist before starting a long workflow.

---

# **6. Create resources in dependency order**

Suppose I'm creating networking and a VM.

The dependencies are roughly:

```text
Resource Group
      ↓
VNet
      ↓
Subnet
      ↓
NSG
      ↓
NIC
      ↓
VM
```

I would script in that logical order.

Why?

Because if:

```text
Subnet doesn't exist
```

then trying to create the NIC first just produces a downstream failure that hides the real prerequisite.

---

# **7. Make the script idempotent where practical**

Idempotency means:

> Running the automation again should converge safely toward the same intended result rather than creating unwanted duplicates.

For some Azure CLI `create` commands, repeated execution behaves like create-or-update, but I would **not assume every command is safely idempotent**.

For example, I can explicitly check:

```bash
if ! az group show \
    --name "$RESOURCE_GROUP" \
    >/dev/null 2>&1; then

  az group create \
    --name "$RESOURCE_GROUP" \
    --location "$LOCATION"
fi
```

Conceptually:

```text
Resource exists?
   /        \
 Yes        No
  ↓          ↓
verify     create
```

But be careful: blindly doing existence checks everywhere can also hide drift.

For production-grade infrastructure, a declarative tool handles this model much better.

---

# **8. Capture resource IDs rather than reconstructing them**

Instead of manually building:

```text
/subscriptions/.../resourceGroups/...
```

I can retrieve the authoritative value:

```bash
VNET_ID=$(az network vnet show \
  -g "$RESOURCE_GROUP" \
  -n "$VNET_NAME" \
  --query id \
  -o tsv)
```

Then use it in subsequent commands.

This avoids hardcoded assumptions.

---

# **9. Validate after important operations**

Suppose I create an AKS cluster.

I don't stop at:

```bash
az aks create ...
```

I may verify:

```bash
az aks show \
  -g "$RESOURCE_GROUP" \
  -n "$AKS_NAME" \
  --query "{State:provisioningState,Power:powerState.code}" \
  -o table
```

I'm looking for:

```text
provisioningState = Succeeded
```

For other resources I verify the properties relevant to the operation.

A command returning zero is useful evidence, but explicit validation is often stronger.

---

# **10. Log useful context without leaking secrets**

Useful log:

```text
Creating VNet vnet-prod in rg-prod...
```

Dangerous log:

```text
CLIENT_SECRET=...
DATABASE_PASSWORD=...
STORAGE_KEY=...
```

So logging should help incident analysis while avoiding credential exposure.

---

# **11. Handle expected transient failures carefully**

Azure operations can occasionally fail because of temporary conditions such as throttling or transient service/API issues.

For safe read/query operations, limited retries with exponential backoff can help.

But I would not blindly retry every destructive command.

```text
429 / transient service failure
→ retry may make sense

AuthorizationFailed
→ retrying 20 times will not fix RBAC

InvalidTemplate/configuration
→ fix configuration

Quota exceeded
→ investigate quota/capacity
```

Error type should determine the response.

---

# **12. Use functions instead of one huge script**

Example:

```bash
create_resource_group() {
  ...
}

create_network() {
  ...
}

create_aks() {
  ...
}

validate_aks() {
  ...
}
```

This makes:

* testing easier,
* logging clearer,
* failures easier to isolate,
* reuse more practical.

---

# **13. Example structure**

```bash
#!/usr/bin/env bash
set -euo pipefail

: "${SUBSCRIPTION_ID:?required}"
: "${RESOURCE_GROUP:?required}"
: "${LOCATION:?required}"

echo "Setting Azure subscription..."

az account set \
  --subscription "$SUBSCRIPTION_ID"

ACTIVE_SUB=$(az account show \
  --query id \
  -o tsv)

[[ "$ACTIVE_SUB" == "$SUBSCRIPTION_ID" ]] || {
  echo "Subscription validation failed"
  exit 1
}

echo "Ensuring resource group exists..."

az group create \
  --name "$RESOURCE_GROUP" \
  --location "$LOCATION" \
  --output none

echo "Validating resource group..."

STATE=$(az group show \
  --name "$RESOURCE_GROUP" \
  --query properties.provisioningState \
  -o tsv)

[[ "$STATE" == "Succeeded" ]] || {
  echo "Resource-group deployment failed"
  exit 1
}
```

This illustrates the structure:

```text
Input
 ↓
Context
 ↓
Action
 ↓
Validation
```

# **14. CLI scripts vs Terraform for infrastructure**

This is important.

With Azure CLI:

```text
Script
 ↓
imperative sequence
 ↓
Azure
```

The tool does not inherently maintain a Terraform-style desired-state file and state database representing managed infrastructure relationships.

Terraform uses:

```text
Configuration
      +
State
      +
Provider/API
      ↓
Diff
      ↓
Plan
```

So for:

```text
10–20 commands
one-time bootstrap
operational remediation
```

CLI may be excellent.

For:

```text
hundreds of resources
Dev/Stage/Prod
multiple engineers
reviewable infrastructure changes
drift management
```

Terraform/Bicep is usually a better infrastructure-management model.

---

### **Interview answer condensed**

> “I would automate Azure CLI as a fail-fast, parameterized and repeatable script. I'd authenticate using Managed Identity or workload federation rather than user credentials, explicitly set and verify the subscription, validate required inputs, create resources in dependency order, capture IDs using `--query`, and validate important provisioning results. I'd make reruns idempotent where practical and implement sensible error handling and logging without exposing secrets. For a small bootstrap or operational workflow Azure CLI is a good choice, but for large long-lived infrastructure I'd usually move to Terraform or Bicep because declarative IaC gives much better desired-state, review and drift-management characteristics.”

**Memory line:**
**A production CLI script needs context validation, dependency ordering, safe reruns, and explicit verification—not just a sequence of `az` commands.**

**Interview trap:**
A Bash script containing Azure CLI commands is **not automatically idempotent Infrastructure as Code**.

**Keywords:**
Azure CLI automation, idempotency, `set -euo pipefail`, subscription context, Managed Identity, OIDC, dependency order, validation, retries, Terraform.

**Likely follow-ups:**

* How would you make an Azure CLI script idempotent?
* How should a CI script authenticate to Azure?
* Why wouldn't you just retry every failed Azure CLI command?
* When would you replace the script with Terraform or Bicep?

# **T26-M05. When would you choose Azure CLI over Terraform?**

**Answer:**

I would choose Azure CLI when the task is primarily an **imperative operational action or a relatively small automation workflow**, rather than long-term declarative infrastructure management.

Examples are querying Azure during troubleshooting, restarting or scaling a service, fetching a resource ID, running a one-time migration or bootstrap step, attaching an existing resource, or automating a small operational procedure.

I would choose Terraform when the goal is:

> “This is the infrastructure state I want to define, review, reproduce and maintain over time.”

So my mental model is:

```text
Azure CLI
→ perform an action

Terraform
→ manage desired infrastructure state
```

They are complementary rather than competitors.

---

# **1. Operational troubleshooting → Azure CLI**

Suppose an AKS pod has:

```text
ImagePullBackOff
```

I may need to inspect:

```bash
az aks show ...
az acr show ...
az role assignment list ...
```

I don't modify Terraform merely to ask Azure:

> Which managed identity does this cluster currently use?

CLI is excellent for real-time inspection.

```text
Incident
   ↓
Azure CLI queries
   ↓
Evidence
   ↓
Root cause
```

Terraform is not primarily an interactive troubleshooting shell.

---

# **2. One-time operational action → Azure CLI**

Examples:

```bash
az vm restart ...
az aks get-credentials ...
az webapp restart ...
```

These are actions, not permanent desired infrastructure definitions.

It would be awkward to model:

```text
VM must be restarted now
```

as Terraform infrastructure state.

So:

```text
Operational command
→ CLI
```

---

# **3. Small bootstrap workflow → CLI can be simpler**

Suppose I need to:

```text
Create initial Terraform-state Resource Group
      ↓
Create Storage Account
      ↓
Create state container
```

This introduces a bootstrapping question:

> Terraform needs a backend, but the backend doesn't exist yet.

A small, carefully written CLI script can create that bootstrap infrastructure.

Then Terraform manages the actual workload infrastructure.

```text
CLI bootstrap
     ↓
Terraform backend exists
     ↓
Terraform manages platform
```

That's a reasonable hybrid model.

---

# **4. Quick discovery / querying → CLI**

Examples:

```bash
az account show
az resource list
az vm list
az aks list
```

If I need immediate information:

```text
"What resource exists?"
"What is its ID?"
"Which identity is configured?"
```

CLI is simpler than introducing Terraform data sources into an unrelated workflow.

---

# **5. CI helper actions → CLI**

Suppose Terraform creates ACR and AKS, but a deployment pipeline needs to:

```text
look up ACR login server
retrieve AKS information
query an Azure resource
```

Azure CLI can complement Terraform.

For example:

```bash
ACR_SERVER=$(az acr show \
  -n "$ACR_NAME" \
  --query loginServer \
  -o tsv)
```

There is no rule saying:

```text
Terraform project
→ cannot use Azure CLI anywhere
```

Use each tool for the problem it handles well.

---

# **When I would choose Terraform instead**

For infrastructure such as:

```text
Resource Groups
VNets
Subnets
NSGs
AKS
ACR
Key Vault
Private Endpoints
Role Assignments
Monitoring
```

that must be reproducible across:

```text
Dev
Stage
Prod
```

I would normally prefer Terraform.

Why?

Because it gives me:

```text
Desired configuration
        ↓
State
        ↓
Provider reads Azure
        ↓
Plan
        ↓
Reviewable difference
        ↓
Apply
```

This is very different from:

```text
Execute command A
Execute command B
Execute command C
```

# **CLI and Terraform mental models**

### Azure CLI

```text
Current Azure
     ↓
Operator says:
"Do X"
     ↓
Azure API
     ↓
X happens
```

Imperative.

---

### Terraform

```text
Desired .tf configuration
        ↕
Terraform state
        ↕
Actual Azure
        ↓
Difference calculated
        ↓
terraform plan
        ↓
terraform apply
```

Declarative infrastructure management.

---

# **State is a major difference**

Terraform tracks resource relationships and mappings through state.

For example:

```text
azurerm_resource_group.prod
      ↓
Azure resource ID
```

This enables Terraform to reason about:

```text
create
update
replace
destroy
drift
dependencies
```

A normal Azure CLI script has no equivalent built-in infrastructure state engine.

You have to build your own logic if you need it.

---

# **Terraform provides a plan**

For production infrastructure:

```bash
terraform plan
```

lets the team review proposed changes:

```text
+ create
~ update
- destroy
```

before execution.

With an imperative script, understanding the eventual changes can require reading the script and every conditional path.

That's much harder as complexity grows.

---

# **Drift handling**

Suppose Terraform declares:

```text
NSG SSH rule absent
```

but someone manually adds:

```text
0.0.0.0/0 → TCP 22
```

On a future refresh/plan, Terraform can detect the difference between desired configuration and actual infrastructure, depending on the managed attributes.

A CLI script doesn't inherently say:

```text
Actual infrastructure drifted from desired state.
```

unless you explicitly implement comparison logic.

---

# **When CLI becomes a bad replacement for Terraform**

This type of script should make me reconsider:

```bash
# 4,000 line deploy.sh

if resource_exists...
if subnet_exists...
if role_exists...
if changed...
if tag_changed...
if route_changed...
...
```

At that point I'm essentially building:

```text
my own weak declarative infrastructure engine
```

inside Bash.

Terraform already solves that class of problem.

---

# **But Terraform should not be used for every operational action**

Another common mistake is trying to force everything through Terraform.

For example:

```text
Restart VM once
Get AKS credentials
Query logs
List failed deployments
Trigger an operational command
```

These aren't necessarily desired-state infrastructure problems.

Azure CLI is often more natural.

---

# **Practical hybrid example**

A mature environment may look like:

```text
Git Repository
│
├── terraform/
│     ↓
│   VNet
│   AKS
│   ACR
│   Key Vault
│   RBAC
│
└── scripts/
      ↓
    diagnostic helpers
    bootstrap tasks
    smoke tests
    operational commands
```

Then CI might run:

```text
Terraform
→ manage infrastructure

Azure CLI
→ validate or perform small operational steps
```

The tools cooperate.

---

# **What about very new Azure functionality?**

Sometimes a new Azure capability may appear before a particular Terraform provider exposes the required resource/property.

I wouldn't immediately rewrite the entire infrastructure in Azure CLI.

Possible approaches include:

```text
AzureRM
+
AzAPI
```

for Terraform-based Azure infrastructure, or a temporary targeted CLI step where appropriate.

The principle is to avoid sacrificing the overall desired-state model just because one feature needs a workaround.

# **Comparison**

| Requirement                     | Azure CLI                         | Terraform                            |
| ------------------------------- | --------------------------------- | ------------------------------------ |
| Query live Azure                | Excellent                         | Not its primary purpose              |
| Troubleshooting                 | Excellent                         | Limited fit                          |
| One-time operation              | Excellent                         | Often unnecessary                    |
| Small bootstrap                 | Good                              | Can be awkward before backend exists |
| Repeatable large infrastructure | Possible, but cumbersome          | Strong                               |
| Desired-state model             | No built-in Terraform-style model | Yes                                  |
| State tracking                  | No Terraform-style state          | Yes                                  |
| Plan before change              | Not equivalent to Terraform plan  | Yes                                  |
| Drift management                | Must implement logic              | Built into workflow                  |
| Multi-environment IaC           | Possible with scripts             | Strong                               |

# **Security implications**

Whichever tool I use, authentication and authorization are separate concerns.

```text
Azure CLI / Terraform
        ↓
Azure identity
        ↓
Authentication
        ↓
Azure RBAC
        ↓
Allowed operations
```

Terraform doesn't magically make broad permissions safe.

Azure CLI doesn't require subscription Contributor just because it's scripting.

Both should use:

```text
Managed Identity / OIDC
+
least-privilege Azure RBAC
```

where appropriate.

### **Interview answer condensed**

> “I choose Azure CLI mainly for imperative operational tasks: querying Azure during troubleshooting, restarting or scaling resources, one-time migration or bootstrap operations, and small automation helpers. I choose Terraform when infrastructure needs to be declaratively defined, peer-reviewed, reproduced across environments and maintained over time. Terraform gives me state, dependency tracking, planning and drift detection, which a normal CLI script doesn't provide automatically. I often use both—for example Terraform to create AKS, ACR and networking, while Azure CLI handles diagnostics, bootstrap steps or small operational actions.”

**Memory line:**
**Use CLI to tell Azure what to do now; use Terraform to describe what Azure should continuously look like.**

**Interview trap:**
Terraform is not inherently “better” than Azure CLI for every task—forcing one-time operational actions into Terraform can be just as inappropriate as managing a large production platform with thousands of imperative CLI commands.
