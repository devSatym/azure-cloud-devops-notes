### **T26-E03. What is Azure Cloud Shell?**

**Answer:**

Azure Cloud Shell is a **browser-based, Microsoft-managed shell environment** for administering Azure without installing Azure CLI or Azure PowerShell locally.

It gives me an authenticated shell in the Azure portal, with common Azure tools already available. Depending on the shell I choose, I can work with **Bash/Azure CLI** or **PowerShell**.

```text
Browser
   ↓
Azure Cloud Shell
   ↓
Azure CLI / PowerShell
   ↓
Azure APIs
   ↓
Azure Resources
```

It is useful when I need quick administrative access from a machine where my local Azure tooling is not installed or configured.

### **How it fits into Azure operations**

Instead of installing and configuring tools locally:

```text
Laptop
  ↓
install Azure CLI
  ↓
authenticate
```

I can open:

```text
Azure Portal
   ↓
Cloud Shell
```

and start running Azure commands.

For example:

```bash
az account show
az group list
az vm list -o table
```

or with PowerShell:

```powershell
Get-AzSubscription
Get-AzResourceGroup
```

### **Why it's useful**

Typical use cases include:

* quick troubleshooting,
* inspecting resources,
* running one-off commands,
* learning Azure CLI/PowerShell,
* administering Azure from an unfamiliar workstation.

### **Cloud Shell vs local CLI**

```text
Cloud Shell
→ Microsoft-hosted browser environment

Local Azure CLI
→ runs on your own workstation or CI agent
```

For repeatable production automation, I would usually prefer:

```text
Git
+
Terraform / scripts
+
CI/CD
```

rather than relying on manually typed Cloud Shell commands.

**Memory line:**
**Cloud Shell is an authenticated browser-based Azure administration environment with Azure tooling ready to use.**

**Interview trap:**
Cloud Shell is convenient for administration, but it should not become a substitute for version-controlled, repeatable production automation.

**Keywords:**
Azure Cloud Shell, browser shell, Bash, PowerShell, Azure CLI, administration.

### **T26-E04. How do you authenticate Azure CLI?**

**Answer:**

For an interactive user session, the normal command is:

```bash
az login
```

That authenticates me through Microsoft Entra ID and creates a local Azure CLI session.

For automation, I would avoid interactive user login and instead use a **workload identity**, such as a managed identity when running on Azure or workload identity federation/OIDC in CI/CD, rather than storing a long-lived username and password.

```text
Human
  ↓
az login
  ↓
Microsoft Entra ID
  ↓
Azure CLI session


Automation
  ↓
Managed Identity / OIDC federation
  ↓
Microsoft Entra ID
  ↓
Short-lived token
  ↓
Azure
```

### **Interactive authentication**

The basic flow is:

```bash
az login
```

Then verify the current context:

```bash
az account show
```

If my identity can access multiple subscriptions:

```bash
az account list -o table
```

and I can select the one I need.

### **Automation authentication**

For automation, I would not normally build a script around:

```text
human username + password
```

Instead:

#### **On an Azure resource with Managed Identity**

Conceptually:

```bash
az login --identity
```

Flow:

```text
Azure VM / automation workload
        ↓
Managed Identity
        ↓
Microsoft Entra ID
        ↓
Azure token
```

No password needs to be stored.

#### **CI/CD**

For GitHub Actions or other supported CI systems:

```text
CI workload
   ↓
OIDC
   ↓
Microsoft Entra ID
   ↓
short-lived access token
```

That is preferable to a long-lived service-principal secret.

### **Authentication does not mean authorization**

After:

```bash
az login
```

succeeds, I am authenticated.

But commands may still fail with:

```text
AuthorizationFailed
```

because Azure RBAC determines whether my identity is allowed to perform the requested operation.

So:

```text
az login succeeds
      ↓
Authentication succeeded

az resource command fails 403/AuthorizationFailed
      ↓
Investigate authorization / RBAC
```

**Memory line:**
**`az login` proves who I am; Azure RBAC determines what I can do afterward.**

**Interview trap:**
A successful `az login` does **not** mean the identity has permission to manage every Azure resource.

**Keywords:**
`az login`, Microsoft Entra ID, Managed Identity, OIDC, token, authentication, Azure RBAC.

### **T26-E05. How do you check the currently selected Azure subscription?**

**Answer:**

I would use:

```bash
az account show
```

That displays the Azure subscription currently active in the CLI context.

For a cleaner output:

```bash
az account show \
  --query "{Name:name,SubscriptionId:id,TenantId:tenantId}" \
  -o table
```

This is something I check before any important production operation, especially if I have access to multiple subscriptions.

```text
Azure CLI
   ↓
Current account context
   ↓
Active subscription
```

### **Why this matters**

Suppose I have:

```text
dev-subscription
staging-subscription
production-subscription
```

and run:

```bash
az group delete ...
```

against the wrong active subscription.

The command may be perfectly valid but operationally disastrous.

So before a risky command I verify:

```bash
az account show
```

### **Listing all available subscriptions**

I can use:

```bash
az account list -o table
```

This helps identify which subscriptions the currently authenticated identity can access.

### **Typical safety workflow**

```text
az login
   ↓
az account list
   ↓
az account set
   ↓
az account show
   ↓
perform operation
```

That final `az account show` is a good production habit.

**Memory line:**
**Before modifying Azure, verify the active subscription with `az account show`.**

**Interview trap:**
Being authenticated to the correct tenant does not guarantee that the **correct subscription** is currently selected.

**Keywords:**
`az account show`, subscription context, tenant, Azure CLI, active subscription.

### **T26-M01. How do you change the active Azure subscription using CLI?**

**Answer:**

I would first list the subscriptions available to my current identity, then set the required subscription explicitly using `az account set`.

For example:

```bash
az account list -o table
```

Then:

```bash
az account set --subscription "<subscription-id-or-name>"
```

Finally, I verify:

```bash
az account show \
  --query "{name:name,id:id}" \
  -o table
```

The important production habit is to **set and verify the subscription before running destructive or deployment commands**, instead of assuming the CLI is already pointed at the correct environment.

```text
Login
  ↓
List subscriptions
  ↓
Choose target
  ↓
Set subscription
  ↓
Verify
  ↓
Execute change
```

---

### **How it works**

Azure CLI maintains an active subscription context for the current authenticated session.

Suppose my identity can access:

```text
Dev
Stage
Prod
```

I can inspect them:

```bash
az account list -o table
```

Then set Prod explicitly:

```bash
az account set \
  --subscription "00000000-0000-0000-0000-000000000000"
```

or by unique subscription name:

```bash
az account set --subscription "prod-subscription"
```

I generally prefer the subscription ID in automation because names can be changed or duplicated in operational processes.

---

### **Verification**

After switching:

```bash
az account show
```

or:

```bash
az account show \
  --query "{Subscription:name,Id:id,Tenant:tenantId}" \
  -o table
```

I am checking that:

```text
expected subscription ID
=
active subscription ID
```

before making changes.

---

### **Why this matters in production**

A very common operational failure is not:

```text
bad command
```

but:

```text
correct command
+
wrong subscription
```

For example:

```bash
az group delete \
  --name rg-app
```

may exist in both Dev and Prod.

If the active subscription is wrong, the CLI may delete the wrong resource group.

So I prefer scripts to make context explicit.

Example:

```bash
SUBSCRIPTION_ID="..."

az account set --subscription "$SUBSCRIPTION_ID"

CURRENT_SUB=$(az account show --query id -o tsv)

if [ "$CURRENT_SUB" != "$SUBSCRIPTION_ID" ]; then
  echo "Wrong subscription context"
  exit 1
fi
```

Now the script fails safely if context is incorrect.

---

### **Subscription vs tenant**

This distinction matters.

A tenant is the Microsoft Entra identity boundary.

A subscription is an Azure resource and billing/governance boundary.

One Entra identity may be able to access multiple subscriptions:

```text
Microsoft Entra Tenant
      ↓
User / Service Principal
      ↓
Subscription A
Subscription B
Subscription C
```

Changing the active subscription does not change what the identity is allowed to access.

It simply changes which subscription Azure CLI uses by default for commands that need subscription context.

---

### **What if the subscription does not appear?**

I would troubleshoot in this order:

```text
Identity authenticated?
      ↓
Correct tenant?
      ↓
Subscription exists/enabled?
      ↓
Identity has Azure RBAC access?
```

First:

```bash
az account list -o table
```

If the expected subscription isn't there, I would verify the tenant and identity.

For example, authenticate against a specific tenant if required:

```bash
az login --tenant <tenant-id>
```

Then list subscriptions again.

If the subscription still isn't visible, I would investigate whether the identity actually has Azure access.

---

### **What if `az account set` succeeds but commands still fail?**

Now I distinguish:

```text
Subscription selection
        ↓
correct

but operation fails
        ↓
authorization or resource issue
```

For example:

```text
AuthorizationFailed
```

would push me toward Azure RBAC investigation rather than repeatedly changing the subscription.

I would check:

```bash
az account show
```

then:

```bash
az role assignment list \
  --assignee <identity> \
  --all
```

depending on the identity and permissions available.

---

### **Interactive use vs automation**

For interactive administration:

```bash
az account set --subscription <id>
```

is fine.

For CI/CD I prefer the subscription context to be explicit in pipeline configuration or variables rather than relying on whatever subscription happened to be active from a previous command.

Conceptually:

```text
Pipeline environment
      ↓
Known subscription ID
      ↓
Authentication
      ↓
Explicit Azure context
      ↓
Deployment
```

Never:

```text
"Use whichever subscription happens to be active"
```

for production automation.

---

### **Production safety pattern**

For a destructive script:

```text
1. Authenticate
2. Set exact subscription ID
3. Read active subscription
4. Compare against expected ID
5. Check target resource
6. Execute
```

Example:

```bash
EXPECTED_SUB="<prod-sub-id>"

az account set --subscription "$EXPECTED_SUB"

ACTIVE_SUB=$(az account show --query id -o tsv)

if [ "$ACTIVE_SUB" != "$EXPECTED_SUB" ]; then
  echo "Subscription verification failed"
  exit 1
fi

az group show --name rg-prod-app

# destructive or modifying operation only after verification
```

This is a simple but valuable operational guardrail.

### **Interview answer condensed**

> “I would first use `az account list` to see the subscriptions available to the authenticated identity, then run `az account set --subscription <subscription-id>` to change the active context. After that I always verify it with `az account show`, especially before production or destructive operations. In automation I prefer using the immutable subscription ID rather than relying on a name or existing CLI context. If the subscription doesn't appear in `az account list`, I'd check whether I'm logged into the correct Entra tenant and whether the identity actually has Azure RBAC access to that subscription.”

**Memory line:**
**Set the subscription explicitly, verify it, then modify resources.**

**Interview trap:**
`az account set` changes the CLI's active subscription; it does **not grant the identity new permissions** in that subscription.

`az account list`, `az account set`, `az account show`, subscription ID, tenant, context, Azure RBAC, production safety.
