# **T26-H01. How would you write an idempotent Azure CLI deployment script?**

**Answer:**

I would design the script so that **running it multiple times converges on the same intended Azure configuration without creating duplicate resources or causing unnecessary destructive changes**.

I would first validate authentication, subscription, inputs, and prerequisites. Then, for each resource, I would inspect the current state, create it if it doesn't exist, and update it only when required. I would use deterministic names and resource IDs rather than generating new names on every run, handle expected “already exists” situations safely, fail immediately on real errors, and verify the final configuration.

For complex long-lived infrastructure, though, I would normally prefer Terraform or Bicep because implementing reliable desired-state convergence manually in Bash becomes difficult.

```text
Authenticate
     ↓
Verify subscription
     ↓
Validate inputs
     ↓
Read current Azure state
     ↓
Resource exists?
   /              \
 No               Yes
 ↓                 ↓
Create         Compare desired state
                    ↓
                Difference?
                /        \
              Yes         No
               ↓           ↓
             Update       Skip
                \         /
                 ↓       ↓
                  Validate
                     ↓
                   Success
```

---

## **What idempotency actually means**

Suppose I run:

```bash
./deploy.sh
```

three times.

A good idempotent result should be:

```text
Run 1
→ Creates VNet

Run 2
→ VNet already matches desired configuration
→ No duplicate

Run 3
→ Same result
```

Not:

```text
Run 1 → vnet-001
Run 2 → vnet-002
Run 3 → vnet-003
```

Idempotency means:

> **Same desired input + repeated execution → same intended infrastructure state.**

It does **not** mean every command must literally do nothing on the second execution.

An update command can still be idempotent if it converges the resource to the same state.

---

# **1. Make execution fail safely**

For Bash:

```bash
#!/usr/bin/env bash
set -euo pipefail
```

This helps prevent:

```text
Network creation fails
        ↓
script ignores failure
        ↓
later steps execute with bad assumptions
        ↓
partial/broken environment
```

I would also validate required variables:

```bash
: "${SUBSCRIPTION_ID:?SUBSCRIPTION_ID required}"
: "${RESOURCE_GROUP:?RESOURCE_GROUP required}"
: "${LOCATION:?LOCATION required}"
```

---

# **2. Never trust the existing Azure context**

The script should establish its own context.

```bash
az account set \
  --subscription "$SUBSCRIPTION_ID"
```

Then verify:

```bash
ACTIVE_SUB=$(az account show \
  --query id \
  -o tsv)

if [[ "$ACTIVE_SUB" != "$SUBSCRIPTION_ID" ]]; then
    echo "Unexpected subscription"
    exit 1
fi
```

Azure CLI's `az account set` sets the current active subscription, and `az account show` can verify it. ([Microsoft Learn][1])

This protects against:

```text
Correct script
+
wrong Azure subscription
=
serious incident
```

---

# **3. Use deterministic resource names**

Avoid:

```bash
VNET_NAME="vnet-$RANDOM"
```

if the intention is to manage one persistent VNet.

Prefer:

```bash
VNET_NAME="vnet-prod-hub"
```

derived predictably from:

```text
application
environment
region
resource type
```

For example:

```text
rg-payment-prod
vnet-payment-prod
aks-payment-prod
acrpaymentprod
```

Then every execution knows which resource it is managing.

---

# **4. Check current state before performing non-idempotent operations**

For example:

```bash
if az group show \
    --name "$RESOURCE_GROUP" \
    >/dev/null 2>&1; then

    echo "Resource group already exists"
else
    az group create \
      --name "$RESOURCE_GROUP" \
      --location "$LOCATION" \
      --output none
fi
```

Flow:

```text
Does RG exist?
   ↓
Yes → reuse
No  → create
```

But I wouldn't blindly use existence checks everywhere.

Why?

Because:

```text
Resource exists
       ≠
Resource has correct configuration
```

Suppose:

```text
NSG exists
```

but it contains:

```text
0.0.0.0/0 → TCP 22
```

when the desired state says it shouldn't.

An existence check alone would incorrectly report success.

---

# **5. Compare important configuration, not just existence**

For example:

```bash
CURRENT_LOCATION=$(az group show \
  --name "$RESOURCE_GROUP" \
  --query location \
  -o tsv)
```

Then compare with expected values.

For mutable configuration, the script may:

```text
Read current value
       ↓
Compare with desired value
       ↓
Different?
       ↓
Update
```

That is closer to actual convergence.

---

# **6. Prefer create-or-update commands where Azure semantics support them**

Many Azure CLI `create` commands can behave as create/update operations for certain resources, but I would not assume this behavior universally.

I would confirm the semantics for each command.

A production script should know whether a command means:

```text
Create only
Create or update
Patch
Replace
Append
```

because those behaviors affect idempotency.

---

# **7. Be especially careful with additive operations**

This is where many scripts stop being idempotent.

Imagine:

```bash
az role assignment create ...
```

Every execution should not blindly assume that another role assignment is required.

I'd first determine whether the intended principal already has the required assignment at the exact scope.

Conceptually:

```text
Principal
   +
Role
   +
Scope
     ↓
Assignment exists?
   /            \
 Yes            No
  ↓              ↓
skip           create
```

The same caution applies to:

* firewall-rule additions,
* DNS records,
* peering,
* secrets,
* policy assignments,
* route rules.

---

# **8. Don't hide real failures as “already exists”**

A bad pattern is:

```bash
az some-command ... || true
```

Now:

```text
Already exists
```

and:

```text
AuthorizationFailed
```

are treated identically.

That's dangerous.

Instead:

```text
Expected condition
→ handle explicitly

Unexpected error
→ stop
```

For example:

```text
409 conflict because resource already exists
→ inspect resource

403 AuthorizationFailed
→ stop and investigate RBAC

429 throttling
→ controlled retry

timeout
→ investigate connectivity/service state
```

---

# **9. Retry only transient failures**

I might implement bounded exponential backoff for genuinely transient operations:

```text
Attempt 1
  ↓ fail 429
wait
  ↓
Attempt 2
  ↓ fail temporary 5xx
wait longer
  ↓
Attempt 3
```

But don't retry:

```text
AuthorizationFailed
InvalidParameter
InvalidCIDR
QuotaExceeded
```

indefinitely.

Retries should solve **transient state**, not hide configuration defects.

---

# **10. Handle asynchronous Azure provisioning**

Some Azure operations take time.

For example:

```text
Create resource
      ↓
Accepted
      ↓
Provisioning
      ↓
Succeeded / Failed
```

Before creating a dependent resource I would check that the dependency reached the required state.

Example:

```bash
STATE=$(az aks show \
  -g "$RESOURCE_GROUP" \
  -n "$AKS_NAME" \
  --query provisioningState \
  -o tsv)

[[ "$STATE" == "Succeeded" ]] || {
    echo "AKS is not ready"
    exit 1
}
```

Otherwise:

```text
Create A
  ↓
immediately create dependent B
  ↓
A isn't ready
  ↓
B fails
```

---

# **11. Make dependencies explicit**

For example:

```text
Resource Group
      ↓
VNet
      ↓
Subnet
      ↓
NSG
      ↓
Private Endpoint
      ↓
Private DNS integration
```

Creating these in dependency order makes failures easier to understand.

---

# **12. Validate the final state**

A successful command exit code is good evidence, but I would also check important expected properties.

For example:

```bash
az network vnet show \
  -g "$RESOURCE_GROUP" \
  -n "$VNET_NAME" \
  --query "{Id:id,AddressSpace:addressSpace.addressPrefixes}" \
  -o json
```

I'm verifying:

```text
Resource exists
+
correct address space
```

not merely that the command ran.

---

# **13. Think about concurrency**

Imagine two pipelines execute the script simultaneously:

```text
Pipeline A ─┐
            ├── both inspect: resource absent
Pipeline B ─┘
              ↓
          both create
```

This creates race conditions.

Azure may reject one operation, or for some workflows you could create unexpected state.

Azure CLI doesn't give you Terraform-style remote-state locking.

Therefore for critical scripts I might ensure:

```text
one deployment per environment at a time
```

using CI concurrency controls or another locking mechanism.

This is a major reason declarative tooling with proper state handling is preferable as infrastructure complexity increases.

---

## **A practical skeleton**

```bash
#!/usr/bin/env bash
set -euo pipefail

: "${SUBSCRIPTION_ID:?required}"
: "${RESOURCE_GROUP:?required}"
: "${LOCATION:?required}"

az account set --subscription "$SUBSCRIPTION_ID"

CURRENT_SUB=$(az account show --query id -o tsv)

[[ "$CURRENT_SUB" == "$SUBSCRIPTION_ID" ]] || {
    echo "Wrong subscription"
    exit 1
}

if ! az group exists \
     --name "$RESOURCE_GROUP" |
     grep -q true; then

    az group create \
      --name "$RESOURCE_GROUP" \
      --location "$LOCATION" \
      --output none
fi

STATE=$(az group show \
  --name "$RESOURCE_GROUP" \
  --query properties.provisioningState \
  -o tsv)

[[ "$STATE" == "Succeeded" ]] || {
    echo "Resource group validation failed"
    exit 1
}

echo "Deployment converged successfully."
```

In a real script I would use structured result handling rather than growing this into thousands of lines.

## **When I would stop and use Terraform/Bicep**

If the script starts containing:

```text
exists?
compare?
update?
dependency?
drift?
delete?
replace?
rollback?
```

for 100 resources, I'm effectively trying to build my own state-management engine.

Terraform already gives me:

```text
Configuration
     +
State
     +
Actual Azure
     ↓
Difference
     ↓
Plan
     ↓
Apply
```

So CLI idempotency is valuable, but **it does not make Azure CLI equivalent to Terraform**.

---

### **Interview answer condensed**

> “I would make the script convergent rather than simply replaying create commands. I'd fail fast, validate inputs and the Azure subscription, use deterministic names, inspect the existing resource, create it only when absent and update it only when its important properties differ. I'd handle additive operations like role assignments specially so reruns don't create duplicates, retry only transient failures such as throttling, wait for asynchronous dependencies to become ready, and validate the final state. I'd also prevent concurrent executions for the same environment. If the script becomes responsible for large-scale drift, dependency and lifecycle management, I'd move that infrastructure to Terraform or Bicep rather than recreating a state engine in Bash.”

**Memory line:**
**Idempotent automation converges repeatedly on the same desired result instead of replaying side effects.**

**Interview trap:**
Checking only whether a resource **exists** does not guarantee idempotency—the existing resource could have the wrong configuration.

**Keywords:**
Idempotency, convergence, deterministic naming, current state, create/update, dependency order, retries, race condition, validation, Terraform.

# **T26-H02. How would you authenticate an automation script without storing user credentials?**

**Answer:**

I would use a **workload identity rather than a human identity**.

If the script runs on an Azure resource such as a VM, Function, App Service, or another environment supporting Managed Identity, I would assign a Managed Identity to that resource and use `az login --identity`. Azure manages the underlying credentials, so the script never stores a password or client secret.

If the automation runs externally—for example GitHub Actions—I would use **OIDC workload identity federation** with Microsoft Entra ID. For Azure Pipelines, I would use an Azure Resource Manager service connection configured with workload identity federation.

Then I would grant that workload identity the minimum Azure RBAC role at the smallest practical scope.

```text
Azure-hosted automation
        ↓
Managed Identity
        ↓
Microsoft Entra ID
        ↓
Short-lived token
        ↓
Azure RBAC
        ↓
Target Resource
```

or:

```text
External CI
    ↓
OIDC token
    ↓
Microsoft Entra ID federation
    ↓
Short-lived Azure token
    ↓
Azure RBAC
```

This avoids storing user passwords and normally avoids long-lived cloud secrets entirely.

---

## **First decision: where is the script running?**

I would choose authentication based on runtime location.

```text
Where does automation run?
          ↓
     ┌────┴─────┐
   Azure       External CI
     ↓             ↓
 Managed        OIDC/WIF
 Identity
```

---

# **1. Azure-hosted automation → Managed Identity**

Examples:

```text
Azure VM
Azure Function
App Service
Azure Automation
other supported Azure compute
```

I assign:

```text
System-assigned Managed Identity
```

or:

```text
User-assigned Managed Identity
```

then:

```bash
az login --identity
```

Microsoft's current Azure CLI documentation explicitly supports `az login --identity`; for user-assigned identities you can specify client ID, object ID, or resource ID. ([Microsoft Learn][2])

For example:

```bash
az login --identity

az account show
```

No username/password exists in the script.

---

## **System-assigned vs user-assigned for automation**

### System-assigned

Lifecycle tied to the Azure resource:

```text
VM
 ↓
Managed Identity

Delete VM
 ↓
Identity deleted
```

Useful when:

```text
one automation host
→ one identity
```

### User-assigned

Independent Azure resource:

```text
User-assigned MI
     ↓
VM A
VM B
Function
```

Useful where several automation hosts need the same workload identity or where identity lifecycle should remain independent.

---

# **2. GitHub Actions → OIDC federation**

Instead of:

```text
GitHub secret:
AZURE_CLIENT_SECRET
```

use:

```text
GitHub workflow
      ↓
OIDC token
      ↓
Entra Federated Identity Credential
      ↓
temporary Azure token
```

The important trust relationship identifies the expected workload, such as:

```text
organization
repository
environment/ref
```

No reusable Azure password has to be stored.

---

# **3. Azure Pipelines → workload identity federation service connection**

Current Microsoft guidance recommends workload identity federation for Azure Resource Manager service connections using either an app registration or Managed Identity, specifically because it eliminates secret management. ([Microsoft Learn][3])

Conceptually:

```text
Azure Pipeline
      ↓
ARM Service Connection
      ↓
Workload Identity Federation
      ↓
Microsoft Entra ID
      ↓
Azure RBAC
```

I would also avoid granting the service connection to every pipeline automatically unless that's truly required; Microsoft's documentation recommends authorizing pipelines selectively. ([Microsoft Learn][3])

---

# **4. Authentication is only half the design**

Suppose:

```text
Managed Identity authentication
             ↓
successful
```

but its RBAC role is:

```text
Owner @ subscription
```

I've removed the secret, but the automation is still overprivileged.

The complete security model is:

```text
Secretless authentication
          +
Least-privilege authorization
```

Microsoft recommends assigning Azure RBAC at the smallest scope that meets the requirement. ([Microsoft Learn][4])

For example:

```text
Automation identity
       ↓
Storage Blob Data Contributor
       ↓
specific Storage Account
```

instead of:

```text
Contributor
at subscription
```

---

# **5. Why not use a personal account?**

Historically some scripts used:

```bash
az login -u user@company.com -p password
```

That's a bad production automation model.

Problems include:

* password storage,
* MFA,
* employee lifecycle,
* poor workload attribution,
* excessive privileges,
* difficult credential rotation.

Importantly, Microsoft's current Azure CLI guidance says MFA requirements apply to **user identities** used through command-line tools, while workload identities such as service principals and Managed Identities are not affected in the same way. ([Microsoft Learn][5])

So automation should use a workload identity rather than attempting to bypass MFA with a user account.

---

# **6. What if federation/Managed Identity isn't possible?**

Then a service principal may still be necessary.

Preference order:

```text
1. Managed Identity
   when running in Azure

2. Workload Identity Federation / OIDC
   for external CI

3. Service principal using stronger managed credential mechanism

4. Client secret
   only when required by constraints
```

If I must use a secret:

* store it in a proper secret store,
* limit its lifetime,
* rotate it,
* never commit it,
* give the identity minimum RBAC.

But my first question would be:

> Can I eliminate this secret entirely?

### **Interview answer condensed**

> “I would never use a human username and password for production automation. If the script runs on Azure, I'd give the host a Managed Identity and authenticate with `az login --identity`; Azure manages the credential and the script only receives temporary tokens. If the script runs in GitHub Actions or another external CI platform, I'd use OIDC workload identity federation to Microsoft Entra ID. For Azure Pipelines I'd use an Azure Resource Manager service connection with workload identity federation. In every case I'd then assign only the required Azure RBAC role at the smallest scope. Secretless authentication solves credential management, but least-privilege RBAC still determines the blast radius.”

**Memory line:**
**Give automation its own workload identity and temporary tokens instead of pretending the automation is a human user.**

**Interview trap:**
Managed Identity or OIDC solves **authentication and secret management**; it does not automatically give the workload correct or least-privilege authorization.

**Keywords:**

# **T26-H03. How would you troubleshoot a script that works locally but fails from a CI agent?**

**Answer:**

I would start from the strongest clue: **the same script works locally**, so I would first compare what differs between my machine and the CI agent rather than immediately rewriting the script.

I would troubleshoot in dependency order:

1. identity,
2. tenant/subscription context,
3. Azure RBAC,
4. agent environment and tool versions,
5. variables/files/shell behavior,
6. network and DNS,
7. target-resource restrictions,
8. then the actual command.

The most common pattern is that my laptop runs under **my personal Entra identity**, while CI runs under a service connection, Managed Identity, or federated service principal with different permissions and network access.

```text
Script
  ↓
Identity
  ↓
Tenant / Subscription
  ↓
Authorization
  ↓
Agent environment
  ↓
DNS / Network
  ↓
Azure resource
  ↓
Operation
```

I would compare each layer until I find the first difference.

---

# **Step 1 — Capture the exact failure**

Before changing anything:

```text
What failed?
Which command?
What HTTP/error code?
Does it fail every run?
How far did the script get?
```

For example:

```text
401
→ authentication

403 / AuthorizationFailed
→ usually authorization

NXDOMAIN
→ DNS

timeout
→ connectivity/routing/firewall/service

command not found
→ agent/tool installation

file not found
→ workspace/path issue

interactive prompt hangs
→ script not CI-safe
```

The error narrows the domain.

---

# **Step 2 — Compare identities first**

Locally:

```bash
az account show \
  --query "{subscription:id,tenant:tenantId,user:user}" \
  -o json
```

In CI, output safe identity/context fields too.

I'm asking:

```text
Local:
Satyam's user identity

CI:
ci-deploy-prod service principal
```

If they're different, different behavior may be completely expected.

```text
        ↓
```

Validate presence without printing sensitive values.

```text

```


while the self-hosted agent is on subnet B.

So:

```text
Works locally
+
CI receives network deny/timeout
```

may be entirely due to source network differences.

---

# **Step 12 — Check non-interactive behavior**

Locally a command may prompt:

```text
Continue? [y/N]
```

and I type `y`.

CI cannot.

So pipeline-safe commands need explicit options where appropriate:

```text
--yes
--no-wait
```

only when their behavior is understood.

Likewise, a command that opens a browser or depends on:

```bash
az login
```

interactively is inappropriate for unattended CI.

---

# **Step 13 — Check CI runner state**

For self-hosted agents:

```text
disk full?
proxy?
certificate trust?
stale Azure session?
old cached tool?
permissions on filesystem?
```

A long-lived self-hosted agent may accumulate state that doesn't exist on a clean Microsoft-hosted agent.

That is why ephemeral CI workers are easier to reason about.

---

# **Step 14 — Reproduce CI locally where possible**

Once I identify differences:

```text
CI uses Ubuntu image + CLI version X
```

I may reproduce that environment in a container or VM.

This helps distinguish:

```text
script bug
```

from:

```text
Azure CI identity/network problem
```

---

## **Diagnostic sequence I'd actually use**

```text
CI failure
   ↓
1. Exact error/status
   ↓
2. az account show
   ↓
3. Compare principal / tenant / subscription
   ↓
4. 403? → RBAC and scope
   ↓
5. Compare CLI + extension versions
   ↓
6. Variables/files/shell
   ↓
7. Timeout/DNS? → network path
   ↓
8. Private Endpoint / firewall / route
   ↓
9. Resource-specific issue
```

This prevents random troubleshooting.

---

## **Example: personal account succeeds, service connection fails**

Symptom:

```text
Developer laptop
→ deployment succeeds

Azure Pipeline
→ AuthorizationFailed
```

I'd immediately compare:

```text
Developer user
       vs
Service connection identity
```

Then:

```text
Service connection identity
      ↓
Which role?
      ↓
At which scope?
```

Microsoft's current Azure Pipelines security guidance recommends scoping service connections only to necessary resources rather than giving broad subscription-wide Contributor rights, and recommends workload identity federation for Azure authentication. ([Microsoft Learn][6])

So the fix is not:

```text
Give CI Owner
```

The fix is:

```text
identify missing operation
        ↓
grant smallest appropriate role/scope
```

---

### **Interview answer condensed**

> “Because the same script works locally, I would compare the execution contexts before changing the code. First I'd capture the exact error, then compare `az account show` locally and in CI to confirm the identity, tenant and subscription. A 403 would push me toward RBAC and scope because the CI service principal or federated identity usually differs from my personal account. Next I'd compare Azure CLI and extension versions, shell, working directory, variables and checked-out files. If authentication and authorization are correct but the command times out, I'd move to DNS and network connectivity—especially if the Azure service uses a Private Endpoint and the local laptop has VPN access while the hosted agent does not. I troubleshoot the first differing dependency rather than giving CI broader permissions blindly.”

**Memory line:**
**When local works and CI fails, compare the environments layer by layer—the script may be identical, but the identity, network, and runtime aren't.**

**Interview trap:**
“Works with my Azure account” does **not** prove the CI identity has the same RBAC or network path.

**Keywords:**
CI agent, identity, service connection, OIDC, subscription context, RBAC, CLI version, shell, environment variables, DNS, Private Endpoint, hosted agent.

**Likely follow-ups:**

* What does a 403 tell you compared with a timeout?
* Why might a private Key Vault work locally but not from a hosted CI agent?
* What would you compare using `az account show`?
* Why shouldn't you fix `AuthorizationFailed` by immediately granting Contributor or Owner?
* How could different Azure CLI versions break an otherwise identical script?

# **T26-H04. How would you automate operations across multiple Azure subscriptions?**

**Answer:**

I would treat the subscription list as explicit input, authenticate once with a workload identity that has the required permissions in each target subscription, and then iterate through the **subscription IDs**, setting or explicitly passing the target subscription for each operation.

I would never rely on whichever subscription happens to be active from the previous loop iteration.

For enterprise-scale automation, I would also think carefully about whether permissions should be assigned individually per subscription or inherited from a management group, and I would use least privilege, bounded concurrency, per-subscription error handling, and a final success/failure summary so one failed subscription isn't silently lost.

```text
Automation identity
       ↓
Approved subscription inventory
       ↓
Subscription A → operation → verify
       ↓
Subscription B → operation → verify
       ↓
Subscription C → operation → verify
       ↓
Summary / failures
```

If subscriptions span multiple Entra tenants, I would treat tenant authentication as a separate boundary rather than assuming one login automatically covers everything.

---

# **1. Use an explicit subscription inventory**

Bad:

```bash
az account list --query "[].id" -o tsv
```

followed by destructive operations on **every subscription my identity can see**.

That may include subscriptions outside the intended scope.

Better:

```text
Approved automation inventory:

Dev  → sub-A
Test → sub-B
Prod → sub-C
```

stored in:

* pipeline configuration,
* version-controlled environment config,
* inventory database,
* controlled parameter set.

Then the automation operates only on intentionally selected subscriptions.

---

# **2. Prefer subscription IDs**

Use:

```text
11111111-....
22222222-....
```

rather than names.

Why?

Subscription names are human-friendly and can change.

The subscription ID is the stable identifier.

---

# **3. Authenticate with a workload identity**

For example:

```text
GitHub Actions
      ↓
OIDC
      ↓
Entra workload identity
```

or:

```text
Azure VM automation
      ↓
Managed Identity
```

Then that identity needs authorization in every target subscription.

There are two common models.

---

## **Model A — role assignment per subscription**

```text
Automation identity
   │
   ├── Reader @ Subscription A
   ├── Reader @ Subscription B
   └── Reader @ Subscription C
```

Good when:

```text
few subscriptions
different permissions per subscription
strong isolation required
```

---

## **Model B — role assignment at management-group scope**

For many subscriptions:

```text
Management Group
       ↓
Automation identity + Reader
       ↓
├── Subscription A
├── Subscription B
├── Subscription C
└── Subscription D
```

Azure RBAC permissions assigned at higher scopes are inherited downward. Microsoft documents management group, subscription, resource-group and resource scopes, while recommending the smallest scope required. ([Microsoft Learn][4])

This can dramatically simplify large estates, but it also expands blast radius.

So I'd use management-group scope only if the automation genuinely requires that breadth.

---

# **4. Explicitly select each subscription**

Basic pattern:

```bash
for SUB in "${SUBSCRIPTIONS[@]}"; do
    echo "Processing $SUB"

    az account set \
      --subscription "$SUB"

    ACTIVE=$(az account show \
      --query id \
      -o tsv)

    [[ "$ACTIVE" == "$SUB" ]] || {
        echo "Subscription context mismatch"
        continue
    }

    # operation
done
```

Microsoft's Azure CLI documentation confirms that `az account set --subscription` changes the active subscription. ([Microsoft Learn][1])

---

# **5. Even better: pass `--subscription` explicitly where supported**

Where a command supports it, I prefer:

```bash
az group list \
  --subscription "$SUB" \
  -o table
```

over relying entirely on mutable global CLI context.

Conceptually:

```text
Operation
+
explicit target subscription
```

is safer than:

```text
Operation
+
whatever the previous command selected
```

This becomes especially important if concurrency is introduced.

---

# **6. Be careful with parallel execution**

Sequential:

```text
set subscription A
run command

set subscription B
run command
```

is straightforward.

But imagine multiple background processes sharing the same Azure CLI configuration:

```text
Worker 1 → az account set A
Worker 2 → az account set B
Worker 1 → runs command
```

Worker 1 might now execute against B.

That's a serious race.

So for parallel processing:

> **Do not share mutable default subscription state between workers.**

Prefer explicit:

```text
--subscription "$SUB"
```

or isolated CLI contexts.

---

# **7. Validate authorization before modifying resources**

Before destructive operations I might perform a harmless read:

```bash
az group list \
  --subscription "$SUB" \
  --query "[].name" \
  -o tsv
```

I'm proving:

```text
subscription exists
+
identity can access it
```

before making changes.

---

# **8. Handle failures per subscription**

Bad:

```text
Subscription 1 succeeds
Subscription 2 fails
script exits
Subscriptions 3–50 never checked
```

For inventory/reporting tasks, I may want:

```text
Sub A → success
Sub B → AuthorizationFailed
Sub C → success
Sub D → timeout
```

and then:

```text
final result = FAILED
```

with a summary.

For destructive workflows, I may instead intentionally stop immediately.

So failure behavior depends on the operation.

### Read/report workflow

Often:

```text
continue
+
record failure
```

### Production mutation

Often:

```text
fail fast
```

or process subscriptions as separately approved stages.

---

# **9. Don't make one giant super-identity unnecessarily**

Suppose:

```text
Inventory automation
```

only needs to read VMs across subscriptions.

Give:

```text
Reader
```

not:

```text
Contributor
```

If another workflow patches VMs:

```text
patch-automation identity
```

can receive a narrower operational role.

Separate identities by purpose:

```text
inventory identity
→ Reader

cost identity
→ cost/read roles

deployment identity
→ app-specific deployment role

security remediation identity
→ narrowly scoped remediation
```

This limits blast radius.

---

# **10. Multiple subscriptions do not necessarily mean one tenant**

Consider:

```text
Tenant A
├── Subscription 1
└── Subscription 2

Tenant B
└── Subscription 3
```

Azure CLI documentation notes that switching to a subscription in another tenant also changes active tenant context. ([Microsoft Learn][7])

For enterprise automation I would explicitly model:

```text
Tenant ID
+
Subscription ID
```

rather than assuming:

```text
subscription ID alone
```

covers identity boundaries.

---

# **11. Cross-tenant automation requires a deliberate identity design**

If automation must operate across tenants, I would decide whether:

* the same application/service principal is represented appropriately in each tenant,
* separate workload identities are cleaner,
* federation relationships are needed,
* permissions should be isolated per tenant.

I wouldn't casually grant one broadly privileged identity everywhere merely because scripting becomes easier.

---

# **12. Example inventory script**

```bash
#!/usr/bin/env bash
set -euo pipefail

SUBSCRIPTIONS=(
  "11111111-1111-1111-1111-111111111111"
  "22222222-2222-2222-2222-222222222222"
  "33333333-3333-3333-3333-333333333333"
)

FAILED=()

for SUB in "${SUBSCRIPTIONS[@]}"; do
  echo "=== $SUB ==="

  if ! az group list \
       --subscription "$SUB" \
       --query "[].{Name:name,Location:location}" \
       -o table; then

      echo "Failed: $SUB"
      FAILED+=("$SUB")
  fi
done

if (( ${#FAILED[@]} > 0 )); then
  echo "Failures:"
  printf '%s\n' "${FAILED[@]}"
  exit 1
fi
```

Notice that each Azure command contains:

```text
--subscription "$SUB"
```

so it isn't dependent on the previous loop's context.

---

# **13. Production mutation needs stronger safeguards**

Suppose automation stops all nonproduction VMs across 20 subscriptions.

I would not simply do:

```text
for every subscription
    stop every VM
```

I would enforce selection criteria:

```text
Approved subscription
      ↓
Environment = nonprod
      ↓
Required tag exists?
      ↓
VM on exclusion list?
      ↓
Operation
      ↓
Verify
```

For example:

```text
AutoShutdown = true
Environment = Dev
```

rather than assuming every VM in a particular subscription should be stopped.

---

# **14. Concurrency and throttling**

For hundreds of subscriptions, sequential processing may be slow.

But launching:

```text
500 parallel Azure API calls
```

may produce throttling.

So I'd use bounded concurrency:

```text
500 subscriptions
      ↓
worker pool
      ↓
10–20 at a time
      ↓
retry 429 with backoff
```

The exact number depends on API limits and the operation.

---

# **15. Log subscription context with every operation**

Instead of:

```text
Deleting VM vm01
```

log:

```text
Tenant: A
Subscription: Prod-Europe
Subscription ID: ...
Resource Group: rg-app
Resource: vm01
Action: stop
```

This makes auditing and incident analysis much easier.

Never print credentials or access tokens.

---

# **16. When I would use management groups instead of scripting subscription-by-subscription**

Some requirements shouldn't be implemented by looping through every subscription.

For example:

```text
Restrict Azure regions
Mandatory governance
Security configuration
```

may be better implemented through:

```text
Management Group
      ↓
Azure Policy
      ↓
Subscriptions inherit governance
```

instead of:

```text
nightly script
→ inspect every subscription
→ fix each manually
```

Use centralized governance when the requirement is fundamentally a governance problem.

---

# **17. Terraform multi-subscription work is another case**

If I'm **deploying persistent infrastructure** across subscriptions, I would probably use:

```text
Terraform
+
provider aliases / separate states
+
CI
```

rather than a giant Azure CLI loop.

Azure CLI remains excellent for:

```text
inventory
operational checks
one-off remediation
cross-subscription reporting
```

but durable infrastructure is better represented declaratively.

---

### **Interview answer condensed**

> “I would maintain an explicit inventory of approved subscription IDs, authenticate with a workload identity, and make sure that identity has only the required RBAC in each subscription. For a small number of subscriptions I might assign permissions individually; for legitimate enterprise-wide read or governance operations, management-group-level RBAC can provide inherited access, although that increases blast radius. In the script I'd target each subscription explicitly—preferably using `--subscription` rather than relying on mutable CLI context—run the operation, validate it, and record failures per subscription. For hundreds of subscriptions I'd use bounded concurrency and handle throttling. If subscriptions span Entra tenants, I would model tenant and subscription independently rather than assuming one login covers everything.”

**Memory line:**
**Across subscriptions, make identity, subscription ID, scope, and operation explicit—never let “current context” decide where automation runs.**

**Interview trap:**
Parallel workers that share `az account set` state can accidentally operate on the **wrong subscription**; explicit `--subscription` targeting is safer.
