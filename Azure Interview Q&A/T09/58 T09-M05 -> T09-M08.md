### **T09-M05. What is the difference between variables and locals?**

**Answer:**
Terraform **variables** are inputs to a configuration or module, while **locals** are internal named expressions calculated inside the configuration. I use variables for values that should be supplied from outside, and locals for derived or repeated values that should stay internal.

### **How it works**

A variable represents configurable input:

```hcl
variable "environment" {
  type = string
}

variable "location" {
  type    = string
  default = "centralindia"
}
```

It can receive values from:

```text
terraform.tfvars
CLI -var
environment variables
calling module
default value
```

A local is calculated inside Terraform:

```hcl
locals {
  resource_prefix = "${var.environment}-app"
  common_tags = {
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}
```

Then:

```hcl
resource "azurerm_resource_group" "app" {
  name     = "${local.resource_prefix}-rg"
  location = var.location
  tags     = local.common_tags
}
```

The flow is:

```text
External input
     ↓
Variable
     ↓
Terraform expressions
     ↓
Local
     ↓
Resources
```

### **Production example**

Suppose the same module is used for dev and production.

I would expose these as variables:

```text
environment
location
AKS node count
VNet address space
```

because they may change between deployments.

I might calculate these as locals:

```text
resource naming convention
common tags
combined subnet names
derived resource prefixes
```

For example:

```hcl
locals {
  prefix = "${var.project}-${var.environment}"
}
```

Then:

```text
payments-prod
payments-dev
```

can be generated consistently without repeatedly rebuilding the same expression.

### **Important distinction**

Variables are normally **configuration inputs**.

Locals are **internal computed values**.

```text
variable
→ caller can provide/change it

local
→ configuration derives it internally
```

A local is also different from a programming-language variable: you don't imperatively reassign it during execution.

> **In an interview, I would say:**
> “Terraform variables are external inputs that make a configuration configurable, while locals are internal expressions used to derive or reuse values. For example, I might pass the environment and Azure region as variables, then use locals to generate a standard resource prefix and common tags.”

**Memory line:**
**Variables come in; locals are calculated inside.**

**Interview trap:**
Do not use locals merely as another way to define user-configurable inputs. If callers need to choose the value, it usually belongs in a variable.

**Keywords:**
Variables, locals, input values, expressions, `var`, `local`, module inputs

**Likely follow-ups:**

* Where can Terraform variable values come from?
* Can locals depend on variables?
* Can a module caller override a local?
* When would you use a variable default?

### **T09-M06. What are Terraform outputs?**

**Answer:**
Terraform outputs expose selected values from a Terraform configuration or module after evaluation. I use them to return useful information such as an Azure resource ID, private IP, hostname, or subnet ID so that users, automation, or other modules can consume it.

### **How it works**

Example:

```hcl
output "aks_cluster_id" {
  value = azurerm_kubernetes_cluster.main.id
}

output "acr_login_server" {
  value = azurerm_container_registry.main.login_server
}
```

After `terraform apply`:

```bash
terraform output
```

might show:

```text
acr_login_server = "myregistry.azurecr.io"
```

Outputs are especially important between modules:

```text
Network Module
     ↓
output: subnet_id
     ↓
Root Module
     ↓
AKS Module
```

Example:

```hcl
module "network" {
  source = "./modules/network"
}

module "aks" {
  source = "./modules/aks"

  subnet_id = module.network.aks_subnet_id
}
```

The network module might define:

```hcl
output "aks_subnet_id" {
  value = azurerm_subnet.aks.id
}
```

### **Production example**

Suppose Terraform creates:

```text
VNet
AKS
ACR
Key Vault
```

Useful outputs might be:

```text
AKS cluster ID
ACR login server
Key Vault URI
private subnet ID
managed identity principal ID
```

A deployment pipeline could then retrieve a required value:

```bash
terraform output -raw acr_login_server
```

That gives automation a clean interface instead of parsing Terraform state directly.

### **Important distinction**

Outputs expose **selected values**, but they are not automatically secret just because the underlying value is sensitive.

Terraform supports:

```hcl
output "database_password" {
  value     = var.database_password
  sensitive = true
}
```

`sensitive = true` prevents normal CLI display in several contexts, but it does **not remove that value from Terraform state**.

That distinction matters in production.

```text
sensitive output
→ hides normal display

not
→ removes secret from tfstate
```

> **In an interview, I would say:**
> “Terraform outputs expose useful values from a configuration or module. I commonly use them for resource IDs, endpoints, subnet IDs, or identity IDs. They are also how child modules return values to their caller. Sensitive outputs can be hidden from normal CLI output, but the value may still exist in Terraform state.”

**Memory line:**
**Variables send values into a module; outputs return values from it.**

**Interview trap:**
Marking an output as `sensitive` does **not** mean the secret disappears from state.

**Keywords:**
Output, module interface, resource ID, `terraform output`, `sensitive`, state

**Likely follow-ups:**

* How do modules consume outputs from other modules?
* What does `terraform output -raw` do?
* Does `sensitive = true` encrypt or remove data from state?
* What are good values to expose from an Azure networking module?

### **T09-M07. What is a Terraform data source?**

**Answer:**
A Terraform data source lets Terraform **read information about something that already exists** instead of creating or managing it as a resource. I use data sources when my configuration needs information from existing Azure infrastructure, such as a resource group, Key Vault, subnet, client identity, or subscription.

### **How it works**

A Terraform resource:

```hcl
resource "azurerm_resource_group" "app" {
  name     = "rg-app-prod"
  location = "centralindia"
}
```

means:

```text
Terraform manages this resource
```

A data source:

```hcl
data "azurerm_resource_group" "shared" {
  name = "rg-shared-network"
}
```

means:

```text
Terraform reads information about it
```

Then I can reference:

```hcl
data.azurerm_resource_group.shared.location
```

The distinction is:

```text
resource
   ↓
Create / update / delete

data source
   ↓
Read existing information
```

### **Production example**

Imagine a central networking team already manages a production VNet.

My AKS Terraform should not recreate that VNet.

I might read an existing subnet:

```hcl
data "azurerm_subnet" "aks" {
  name                 = "snet-aks"
  virtual_network_name = "vnet-prod"
  resource_group_name  = "rg-network-prod"
}
```

Then:

```hcl
resource "azurerm_kubernetes_cluster" "main" {
  # ...

  default_node_pool {
    name           = "system"
    vnet_subnet_id = data.azurerm_subnet.aks.id
  }
}
```

Architecture:

```text
Networking Terraform
      ↓
Existing VNet/Subnet
      ↑
      │ data source
      │
AKS Terraform
```

This lets independently managed Terraform stacks integrate without both attempting to own the same resource.

Another common example is:

```hcl
data "azurerm_client_config" "current" {}
```

which can provide information about the currently authenticated Azure context.

### **Important distinction**

A data source is **not the same as importing a resource**.

```text
Data source
→ read an existing resource
→ Terraform does not take ownership

terraform import
→ associate an existing resource with a Terraform resource block
→ Terraform starts managing it
```

This is a very common interview distinction.

> **In an interview, I would say:**
> “A Terraform data source reads information about existing infrastructure without creating or owning it. For example, if an AKS deployment needs to use a subnet maintained by another networking stack, I can read that subnet with an AzureRM data source and pass its ID into the AKS resource. If I actually want Terraform to manage that existing subnet, I would import it instead.”

**Memory line:**
**Resource manages it; data source reads it.**

**Interview trap:**
Using a data source does not bring the existing Azure resource under Terraform management.

**Keywords:**
Data source, existing resources, read-only lookup, `data`, AzureRM, import

**Likely follow-ups:**

* What is the difference between a data source and `terraform import`?
* Can a data source reference a resource created in the same configuration?
* Why are data sources useful across separate Terraform stacks?
* What happens if the object referenced by a data source does not exist?

### **T09-M08. What is `for_each`?**

**Answer:**
`for_each` is a Terraform meta-argument used to create multiple instances of a resource or module from a **map or set of unique values**. Each instance receives a stable key, which makes `for_each` especially useful when the objects have meaningful identities such as subnet names, resource-group names, or environments.

### **How it works**

For example, instead of writing three Azure resource groups:

```hcl
resource "azurerm_resource_group" "dev" {
  name     = "rg-dev"
  location = "centralindia"
}
```

and repeating that several times, I can write:

```hcl
resource "azurerm_resource_group" "env" {
  for_each = toset(["dev", "staging", "prod"])

  name     = "rg-${each.key}"
  location = "centralindia"
}
```

Terraform creates:

```text
azurerm_resource_group.env["dev"]
azurerm_resource_group.env["staging"]
azurerm_resource_group.env["prod"]
```

Inside the block I use:

```text
each.key
each.value
```

### **Using a map**

A more realistic Azure example is:

```hcl
variable "subnets" {
  default = {
    aks = "10.0.1.0/24"
    app = "10.0.2.0/24"
    db  = "10.0.3.0/24"
  }
}
```

Then:

```hcl
resource "azurerm_subnet" "this" {
  for_each = var.subnets

  name                 = "snet-${each.key}"
  address_prefixes     = [each.value]
  resource_group_name  = azurerm_resource_group.network.name
  virtual_network_name = azurerm_virtual_network.main.name
}
```

Terraform sees:

```text
subnet["aks"]
subnet["app"]
subnet["db"]
```

rather than identifying instances only as:

```text
subnet[0]
subnet[1]
subnet[2]
```

### **Why this matters in production**

Meaningful keys give instances more stable identities.

Suppose I have:

```text
dev
staging
prod
```

and remove `staging`.

With `for_each`, Terraform still identifies:

```text
["dev"]
["prod"]
```

by name.

That is one reason `for_each` is often preferable to index-based `count` when each resource represents a distinct named object.

### **Important distinction**

`for_each` expects a **map or set**, not simply any arbitrary list.

A common conversion is:

```hcl
for_each = toset(var.environments)
```

For maps:

```text
each.key   → map key
each.value → corresponding value
```

For sets of strings:

```text
each.key == each.value
```

> **In an interview, I would say:**
> “`for_each` creates multiple instances of a resource or module using a map or set. Unlike index-based instances, each object gets a meaningful key, such as `subnet["aks"]` or `subnet["database"]`. I prefer it when resources have distinct identities because adding or removing one item is generally easier to reason about than relying on numeric indexes.”

**Memory line:**
**`for_each` creates many resources and identifies each one by a meaningful key.**

**Interview trap:**
Do not assume `for_each` and `count` are interchangeable without consequences. Changing an existing resource from one addressing model to another can change Terraform resource addresses and must be handled carefully.

**Keywords:**
`for_each`, `each.key`, `each.value`, map, set, stable keys, resource instances

* Can `for_each` use a list directly?
* What are `each.key` and `each.value`?
* Why can `for_each` be safer for named resources?
