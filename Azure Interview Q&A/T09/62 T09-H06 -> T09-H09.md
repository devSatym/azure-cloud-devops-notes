### **T09-H06. How would you authenticate Terraform to Azure using workload identity federation rather than a client secret?**

**Answer:**
For CI/CD, I would create a Microsoft Entra workload identity—typically an application/service principal or user-assigned managed identity—configure a **federated identity credential** that trusts the CI system's OIDC tokens, grant that identity only the required Azure RBAC permissions, and configure Terraform to use OIDC. The pipeline then exchanges a short-lived OIDC token for an Azure access token instead of storing a long-lived client secret. This is supported by the current AzureRM provider and is the preferred pattern for GitHub Actions. ([Terraform Registry][1])

### **Authentication flow**

For GitHub Actions:

```text
GitHub Actions
      ↓
requests OIDC token
      ↓
GitHub OIDC Provider
      ↓
Microsoft Entra ID
      │
      │ validates federated credential
      ↓
Short-lived Azure access token
      ↓
Terraform AzureRM Provider
      ↓
Azure RBAC
      ↓
Azure Resources
```

There is **no client secret** in this flow.

---

### **Production implementation order**

#### **1. Create an Azure identity**

For example:

```text
Microsoft Entra application
        ↓
Service principal
```

or:

```text
User-assigned managed identity
```

This identity represents the Terraform pipeline.

---

#### **2. Create a federated identity credential**

I configure Microsoft Entra ID to trust a specific GitHub identity.

The trust is based on claims such as:

```text
Issuer
→ GitHub OIDC issuer

Subject
→ repository + branch/environment

Audience
→ api://AzureADTokenExchange
```

For example, I might allow only:

```text
repo:myorg/infrastructure:environment:production
```

rather than trusting every workflow in every branch.

This is important because federation removes a secret, but I still need to tightly control **which workload is allowed to assume the Azure identity**. GitHub documents `api://AzureADTokenExchange` as the recommended Azure audience. ([GitHub Docs][2])

---

#### **3. Assign least-privilege Azure RBAC**

For example:

```text
Terraform Production Identity
           ↓
Contributor
           ↓
rg-production
```

rather than:

```text
Terraform Identity
       ↓
Owner
       ↓
Entire subscription
```

If Terraform needs to create role assignments, I would separately evaluate the minimum permissions needed for that function rather than granting broad Owner permissions by default.

---

#### **4. Allow GitHub to request an OIDC token**

The workflow needs:

```yaml
permissions:
  contents: read
  id-token: write
```

`id-token: write` allows the job to request an OIDC token; it does **not itself grant Azure resource permissions**. Authorization still comes from Microsoft Entra ID and Azure RBAC. ([GitHub Docs][2])

---

### **5. Configure Terraform for OIDC**

A common provider configuration remains simple:

```hcl
provider "azurerm" {
  features {}
}
```

with environment variables such as:

```bash
ARM_USE_OIDC=true
ARM_CLIENT_ID=<client-id>
ARM_TENANT_ID=<tenant-id>
ARM_SUBSCRIPTION_ID=<subscription-id>
```

In GitHub Actions, the AzureRM provider can use the OIDC request information supplied by the GitHub runtime when OIDC authentication is enabled. ([Terraform Registry][3])

Conceptually:

```text
ARM_CLIENT_ID
ARM_TENANT_ID
ARM_SUBSCRIPTION_ID

        +

GitHub OIDC token

        ↓

AzureRM Provider authentication
```

Notice what is missing:

```text
ARM_CLIENT_SECRET
```

---

### **Backend authentication matters too**

This is an important interview detail.

Terraform may authenticate separately for:

```text
AzureRM Provider
→ manages Azure resources

azurerm Backend
→ accesses Terraform state
```

If my state is stored in Azure Blob Storage, I would also configure the backend for Entra/OIDC authentication instead of falling back to a Storage Account key.

Example:

```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstateprod001"
    container_name       = "tfstate"
    key                  = "prod.tfstate"

    use_oidc         = true
    use_azuread_auth = true
  }
}
```

For direct Entra-based blob access, HashiCorp recommends a data-plane role such as **Storage Blob Data Contributor**, scoped as narrowly as practical. ([HashiCorp Developer][4])

---

### **Why federation is safer**

With a client secret:

```text
Secret created
    ↓
stored in CI
    ↓
valid for months
    ↓
leak = reusable credential
```

With federation:

```text
Workflow starts
     ↓
OIDC assertion
     ↓
short-lived Azure token
     ↓
token expires
```

So I remove:

* secret storage
* secret rotation
* secret-expiry outages
* much of the risk from accidentally leaking a reusable credential

---

### **Important distinction**

```text
OIDC / federation
→ Authentication
```

does not determine:

```text
What Terraform may do
→ Authorization
```

That remains controlled by:

```text
Azure RBAC
```

So secretless authentication does **not** justify broad permissions.

> **In an interview, I would say:**
> “For Terraform CI/CD, I prefer workload identity federation rather than a service-principal secret. I configure an Entra identity with a federated credential that trusts a specific GitHub repository, branch, or environment, give that identity least-privilege Azure RBAC, enable `id-token: write` in GitHub Actions, and configure the AzureRM provider and Azure Storage backend to use OIDC. GitHub then exchanges a short-lived OIDC assertion for an Azure token, so there is no long-lived Azure client secret to store or rotate.”

**Memory line:**
**OIDC establishes trust between the pipeline and Entra ID; Azure RBAC decides what that identity can do.**

**Interview trap:**
Do not configure OIDC for the AzureRM provider but leave your Terraform backend using a long-lived Storage Account key. Provider authentication and backend authentication are separate concerns.

**Keywords:**
OIDC, Workload Identity Federation, Microsoft Entra ID, federated identity credential, `ARM_USE_OIDC`, Azure RBAC, short-lived token

**Likely follow-ups:**

* What claims are used in a federated identity credential?
* Why is `id-token: write` required in GitHub Actions?
* Does OIDC replace Azure RBAC?
* How would the Azure Storage backend authenticate without a storage key?

### **T09-H07. How would you handle a resource that someone manually modified in the Azure portal?**

**Answer:**
I would treat it as potential **Terraform drift**. I would first run `terraform plan` to understand exactly what changed, determine whether the portal modification was intentional or accidental, and then either let Terraform restore the declared configuration or update the Terraform code to formally adopt the intended change. I would never blindly apply before understanding why production differs from code.

### **Diagnostic order**

```text
Manual Azure change discovered
          ↓
Do NOT immediately apply
          ↓
terraform plan
          ↓
Identify exact drift
          ↓
Was the manual change intentional?
       /             \
     No               Yes
     ↓                 ↓
Revert using      Update Terraform
Terraform         configuration
     ↓                 ↓
terraform plan    terraform plan
       \             /
        ↓           ↓
       Controlled apply
```

---

### **Example**

Suppose Terraform declares:

```hcl
resource "azurerm_linux_virtual_machine" "app" {
  size = "Standard_D2s_v5"
}
```

Someone changes the VM through the Azure portal to:

```text
Standard_D4s_v5
```

Now I run:

```bash
terraform plan
```

Terraform may propose:

```text
Standard_D4s_v5
        ↓
Standard_D2s_v5
```

because the `.tf` configuration remains the desired state.

---

### **Case 1: The portal change was accidental**

If the manual modification was unauthorized or unnecessary:

```text
Terraform code
= authoritative desired state
```

I would:

1. review the plan,
2. confirm no dependent production issue exists,
3. apply the Terraform configuration,
4. restore the resource to the approved state.

```bash
terraform plan
terraform apply
```

---

### **Case 2: The manual change was intentional**

This is common during incidents.

For example:

```text
Production outage
      ↓
Engineer increases VM size manually
      ↓
Application recovers
```

I should **not** immediately run Terraform and resize it back.

Instead:

```text
Manual emergency fix
       ↓
Validate that fix is required
       ↓
Update Terraform code
       ↓
PR / review
       ↓
terraform plan
       ↓
Configuration and Azure converge
```

For example:

```hcl
size = "Standard_D4s_v5"
```

Now Terraform's desired state matches the operational decision.

---

### **If I only want to inspect external changes**

A useful command is:

```bash
terraform plan -refresh-only
```

That allows me to inspect changes detected in real infrastructure without proposing the normal reconciliation of configuration at that point.

But I would not confuse:

```text
refreshing state
```

with:

```text
fixing desired configuration
```

The actual goal is to bring:

```text
Configuration
    =
State
    =
Azure reality
```

back into an intentional relationship.

---

### **Should I use `ignore_changes`?**

Usually not as the first reaction.

This is a bad pattern:

```text
Portal changed something
      ↓
Terraform sees drift
      ↓
Add ignore_changes
      ↓
problem hidden
```

`ignore_changes` is appropriate only when an attribute is **intentionally owned by another system**.

For example:

```hcl
lifecycle {
  ignore_changes = [
    some_externally_managed_attribute
  ]
}
```

It is not a general-purpose drift suppression mechanism.

---

### **Preventing recurrence**

For production infrastructure, I would reduce manual drift through:

```text
Git PR
   ↓
terraform plan
   ↓
Review
   ↓
Approval
   ↓
terraform apply
```

and enforce operational controls such as:

* least-privilege Azure RBAC
* PIM for privileged changes
* Azure Policy where appropriate
* change auditing through Azure Activity Log
* CI/CD as the normal deployment path

For strict environments, humans might have Reader access by default and elevate only for controlled break-glass scenarios.

---

### **Important distinction**

Terraform does not magically prevent someone with sufficient Azure permissions from changing a managed resource.

```text
Terraform
→ desired-state management
```

versus:

```text
Azure RBAC / Policy
→ controls whether portal/API changes are permitted
```

> **In an interview, I would say:**
> “I would treat a manual portal change as drift and first run `terraform plan` to see exactly what changed. If it was accidental, I would review the plan and use Terraform to restore the desired configuration. If it was an intentional emergency or approved change, I would update the Terraform code so that change becomes part of the source of truth, then plan and apply normally. I would not hide unexpected drift with `ignore_changes` or blindly reapply production.”

**Memory line:**
**Drift is not automatically wrong—the first question is whether reality or the code represents the intended state.**

**Interview trap:**
Automatically running `terraform apply` can undo a legitimate production incident fix.

**Keywords:**
Drift, `terraform plan`, `-refresh-only`, desired state, reconciliation, `ignore_changes`, source of truth

**Likely follow-ups:**

* How would you detect Terraform drift automatically?
* When is `ignore_changes` appropriate?
* How would you prevent portal changes in production?
* What if the manual change was made during an incident?

### **T09-H08. How would you safely rename a Terraform resource without recreating it?**

**Answer:**
I would change the Terraform resource address and record the rename using a **`moved` block** so Terraform updates the state association instead of interpreting the old resource as deleted and the new one as a new resource. I would then run `terraform plan` and verify that Terraform reports a move rather than a destroy-and-create operation. HashiCorp recommends configuration-driven refactoring with `moved` blocks for this purpose. ([HashiCorp Developer][5])

### **Why a normal rename is dangerous**

Suppose I originally have:

```hcl
resource "azurerm_resource_group" "old_name" {
  name     = "rg-production"
  location = "centralindia"
}
```

Terraform state contains:

```text
azurerm_resource_group.old_name
              ↓
      Azure rg-production
```

Now I simply rename the Terraform label:

```hcl
resource "azurerm_resource_group" "prod" {
  name     = "rg-production"
  location = "centralindia"
}
```

Terraform sees different addresses:

```text
Old:
azurerm_resource_group.old_name

New:
azurerm_resource_group.prod
```

Without telling Terraform they represent the same real object, the plan may look conceptually like:

```text
- destroy old_name
+ create prod
```

even though the actual Azure resource hasn't changed.

---

### **Safe approach: `moved` block**

I would add:

```hcl
moved {
  from = azurerm_resource_group.old_name
  to   = azurerm_resource_group.prod
}
```

and rename the resource:

```hcl
resource "azurerm_resource_group" "prod" {
  name     = "rg-production"
  location = "centralindia"
}
```

Now Terraform understands:

```text
Old Terraform address
azurerm_resource_group.old_name
             ↓
          moved
             ↓
New Terraform address
azurerm_resource_group.prod
             ↓
Same Azure Resource
```

A `moved` block changes the state association during planning rather than destroying the infrastructure object. ([HashiCorp Developer][6])

---

### **Production workflow**

I would follow:

```text
1. Backup/verify remote state
          ↓
2. Rename Terraform resource
          ↓
3. Add moved block
          ↓
4. terraform fmt
          ↓
5. terraform validate
          ↓
6. terraform plan
          ↓
7. Verify:
   MOVE, not destroy/create
          ↓
8. Peer review
          ↓
9. terraform apply
```

The critical evidence is the plan.

I want something conceptually equivalent to:

```text
azurerm_resource_group.old_name
has moved to
azurerm_resource_group.prod
```

I do **not** want:

```text
1 to destroy
1 to add
```

for the rename.

---

### **Older/manual alternative: `terraform state mv`**

Terraform also supports:

```bash
terraform state mv \
  azurerm_resource_group.old_name \
  azurerm_resource_group.prod
```

This directly changes the address stored in state. ([HashiCorp Developer][7])

Conceptually:

```text
state:
old address
    ↓
state mv
    ↓
new address
```

This is still useful for some operational scenarios, but for code-based refactoring I prefer:

```text
moved block
```

because:

* the refactor is stored in version control,
* reviewers can see it,
* CI/CD can evaluate it,
* other users of a module receive the migration path automatically.

HashiCorp recommends language-level refactoring for most such cases. ([HashiCorp Developer][8])

---

### **Do not confuse two different names**

A Terraform resource has:

```text
Terraform address
azurerm_storage_account.logs
```

and an Azure resource may have:

```text
Azure name
stprodlogs001
```

Changing:

```hcl
resource "azurerm_storage_account" "logs"
```

to:

```hcl
resource "azurerm_storage_account" "audit_logs"
```

is a **Terraform address rename**.

Changing:

```hcl
name = "stprodlogs001"
```

to another Azure Storage Account name is a change to the **actual Azure resource attribute**, and because some Azure names are immutable, that may legitimately require replacement.

A `moved` block cannot magically make an immutable Azure property updateable.

---

### **Important distinction**

```text
moved block
→ tells Terraform that an object's address changed
```

It does not:

```text
rename the actual Azure resource
```

unless the underlying Terraform configuration separately changes an Azure-supported property.

> **In an interview, I would say:**
> “If I'm renaming only the Terraform resource address, I use a `moved` block from the old address to the new address. That tells Terraform that the same real Azure object is now managed at a new Terraform address, so it doesn't destroy and recreate it. I always verify the plan shows a move rather than replacement. `terraform state mv` can also do this manually, but `moved` blocks are preferable for version-controlled refactors.”

**Memory line:**
**Rename the address + move the state association = keep the real resource.**

**Interview trap:**
Renaming the Terraform label is different from renaming the Azure resource itself. An Azure property change can still require replacement even when the Terraform address is safely moved.

**Keywords:**
`moved`, `from`, `to`, resource address, `terraform state mv`, refactoring, state association

**Likely follow-ups:**

* What is the difference between a `moved` block and `terraform state mv`?
* What happens if you rename a resource without either?
* Can `moved` blocks rename module calls?
* Can `moved` prevent replacement caused by an immutable Azure property?

### **T09-H09. How would you safely refactor resources between Terraform modules?**

**Answer:**
If I move an existing resource into another module, I must preserve the association between that Azure object and its new Terraform address. For resources staying in the **same Terraform state**, I prefer `moved` blocks that map the old address to the new module address, then verify with `terraform plan` that Terraform reports moves rather than destroy-and-create operations. HashiCorp explicitly supports moving resources and module addresses this way. ([HashiCorp Developer][5])

### **The problem**

Suppose I originally manage a VNet directly in the root module:

```hcl
resource "azurerm_virtual_network" "main" {
  name                = "vnet-prod"
  address_space       = ["10.0.0.0/16"]
  location            = var.location
  resource_group_name = var.resource_group_name
}
```

State address:

```text
azurerm_virtual_network.main
```

Later I refactor:

```text
Root Module
    ↓
module "network"
    ↓
azurerm_virtual_network.main
```

The new address becomes:

```text
module.network.azurerm_virtual_network.main
```

Terraform sees:

```text
Old address:
azurerm_virtual_network.main

New address:
module.network.azurerm_virtual_network.main
```

If I just move the HCL file without migrating the address, Terraform may interpret that as:

```text
Destroy original VNet
        +
Create new VNet
```

That is unacceptable for production networking.

---

### **Safe refactor using a `moved` block**

I would create the module:

```hcl
module "network" {
  source = "./modules/network"

  resource_group_name = var.resource_group_name
  location            = var.location
  address_space       = ["10.0.0.0/16"]
}
```

Then record:

```hcl
moved {
  from = azurerm_virtual_network.main
  to   = module.network.azurerm_virtual_network.main
}
```

Conceptually:

```text
Before

Root
└── azurerm_virtual_network.main
             │
             │ same Azure VNet
             ▼
          vnet-prod


After

Root
└── module.network
       └── azurerm_virtual_network.main
                    │
                    ▼
                 vnet-prod
```

Terraform updates the **address**, not the Azure VNet itself. ([HashiCorp Developer][5])

---

### **Actual implementation order**

For production, I would do:

```text
1. Confirm current plan is clean
          ↓
2. Verify/backup remote state
          ↓
3. Create child module
          ↓
4. Move resource configuration
          ↓
5. Update references/outputs
          ↓
6. Add moved blocks
          ↓
7. terraform init
          ↓
8. terraform validate
          ↓
9. terraform plan
          ↓
10. Confirm only address moves
          ↓
11. PR review
          ↓
12. terraform apply
```

The most important checkpoint is:

```text
terraform plan
```

If I expect pure refactoring, I want something equivalent to:

```text
Resource has moved
```

not:

```text
10 to destroy
10 to create
```

If the latter appears, I stop and fix the refactor.

---

### **Updating dependencies**

Moving a resource into a module often changes references.

Originally:

```hcl
subnet_id = azurerm_subnet.aks.id
```

After refactoring, the network module may expose:

```hcl
output "aks_subnet_id" {
  value = azurerm_subnet.aks.id
}
```

and the caller uses:

```hcl
subnet_id = module.network.aks_subnet_id
```

So a module boundary should look like:

```text
Root Module
    │
    ├── inputs
    ▼
Network Module
    │
    ├── VNet
    └── Subnet
    │
    └── outputs
         ↓
      subnet_id
         ↓
      AKS Module
```

This is both a state refactor and an interface refactor.

---

### **Moving multiple resources**

For example:

```text
Before:
azurerm_virtual_network.main
azurerm_subnet.aks
azurerm_network_security_group.aks
```

After:

```text
module.network.azurerm_virtual_network.main
module.network.azurerm_subnet.aks
module.network.azurerm_network_security_group.aks
```

I could record:

```hcl
moved {
  from = azurerm_virtual_network.main
  to   = module.network.azurerm_virtual_network.main
}

moved {
  from = azurerm_subnet.aks
  to   = module.network.azurerm_subnet.aks
}

moved {
  from = azurerm_network_security_group.aks
  to   = module.network.azurerm_network_security_group.aks
}
```

Terraform supports moves for resources, modules, module renames, and other refactoring patterns. ([HashiCorp Developer][5])

---

### **What if the resource moves to a different state file?**

This is more serious.

```text
Same state:
root resource
      ↓
child module

→ moved block is ideal
```

But:

```text
network.tfstate
       ↓
platform.tfstate
```

means changing **state ownership**, not merely a resource address.

That requires a carefully controlled state migration. HashiCorp documents `terraform state mv`, along with state pull/push procedures, for cross-state migrations, and treats direct state operations as advanced operations that require care. ([HashiCorp Developer][9])

Conceptually:

```text
Source State
    ↓
Remove/move ownership
    ↓
Destination State
    ↓
Verify both plans
```

I would ensure there is never a period where:

```text
Two states both believe they own the resource
```

because that creates conflicting Terraform ownership.

---

### **Why `moved` blocks are preferable**

For normal same-state refactoring:

```text
moved block
```

has an important advantage over manually running:

```bash
terraform state mv
```

because the migration is stored with the code.

That means:

```text
Git history
    ↓
PR review
    ↓
terraform plan
    ↓
documented migration
```

instead of an undocumented one-time state command executed from someone's terminal.

HashiCorp recommends configuration-driven moves for most module refactoring. ([HashiCorp Developer][8])

---

### **Important distinction**

```text
Moving between modules
within one state
```

is different from:

```text
Moving between separate state files
```

The first is primarily an **address refactor**.

The second changes the **ownership boundary** and requires greater operational care.

> **In an interview, I would say:**
> “When moving an existing Azure resource between Terraform modules, I preserve its state association instead of allowing Terraform to interpret the new module address as a new resource. Within the same state, I prefer `moved` blocks mapping the old resource address to the new module address, update the module inputs and outputs, and verify that `terraform plan` shows moves with no unintended recreation. If I'm moving resources between separate state files, I treat that as a state-ownership migration and use controlled state operations with backups and validation on both sides.”

**Memory line:**
**Refactoring HCL is safe only when Terraform state follows the resource to its new address.**

**Interview trap:**
Simply moving a `.tf` resource block into a module does **not** tell Terraform that the new module resource is the same Azure object.

**Keywords:**
Module refactor, `moved` block, resource address, state ownership, `terraform state mv`, outputs, no recreation

**Likely follow-ups:**

* How do you verify the refactor will not recreate resources?
* When would you use `terraform state mv` instead of a `moved` block?
* What changes when resources move between separate state files?
* Why should two Terraform states never manage the same Azure resource?
