# 9. 🔴 M IMP — Terraform on Azure

## Easy

### **T09-E01. What is Terraform?**

**Answer:**
**Terraform is an Infrastructure as Code tool from HashiCorp that lets us define, provision, and manage infrastructure using declarative configuration files.**

Instead of manually creating resources in the Azure Portal, I describe the desired infrastructure in `.tf` files and Terraform works out which Azure API operations are required.

```text
Terraform configuration
        ↓
Terraform Provider
        ↓
Azure APIs
        ↓
Azure Resources
```

For example:

```hcl
resource "azurerm_resource_group" "prod" {
  name     = "rg-prod"
  location = "Central India"
}
```

Then:

```bash
terraform init
terraform plan
terraform apply
```

Terraform can create the resource group automatically.

### **Declarative model**

Terraform is declarative.

I say:

```text
I want:
1 resource group
1 VNet
2 subnets
1 AKS cluster
1 ACR
```

rather than manually scripting every low-level API call in exact procedural order.

Terraform compares:

```text
Configuration
     ↓
Desired state

State + provider/API
     ↓
Known/current infrastructure
```

and calculates the required changes.

### **Terraform is multi-cloud**

Terraform isn't Azure-specific.

Providers exist for:

```text
Azure
AWS
GCP
Kubernetes
GitHub
Cloudflare
many SaaS platforms
```

For Azure, the most commonly used provider is:

```text
azurerm
```

### **Typical DevOps use**

A production repository might look like:

```text
terraform/
├── providers.tf
├── variables.tf
├── main.tf
├── outputs.tf
└── modules/
    ├── network/
    └── aks/
```

Then CI/CD can automatically run:

```text
Pull Request
     ↓
terraform fmt
     ↓
terraform validate
     ↓
terraform plan
     ↓
Review
     ↓
terraform apply
```

This gives repeatability and auditability compared with creating resources manually.

**Memory line:**
**Terraform = declarative Infrastructure as Code that creates and manages infrastructure through providers.**

**Interview trap:**
Don't say Terraform is only an Azure deployment tool. It is **provider-based and multi-cloud**.

**Keywords:** Terraform, declarative, IaC, provider, state, `.tf`

### **T09-E02. What is Infrastructure as Code?**

**Answer:**
**Infrastructure as Code, or IaC, means defining and managing infrastructure using version-controlled code instead of manually configuring resources through a portal or console.**

Instead of:

```text
Engineer
  ↓
Azure Portal
  ↓
Click Create VNet
  ↓
Click Create AKS
  ↓
Click Create ACR
```

we use:

```text
Git Repository
     ↓
Terraform
     ↓
Azure
```

### **Example**

Terraform:

```hcl
resource "azurerm_virtual_network" "main" {
  name                = "vnet-prod"
  address_space       = ["10.10.0.0/16"]
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name
}
```

Now the infrastructure definition is stored alongside normal source code.

### **Why IaC is important**

It gives several major benefits:

```text
Repeatability
Version control
Code review
Automation
Consistency
Audit trail
Environment recreation
Reduced manual error
```

For example, without IaC:

```text
Dev VNet
10.10.0.0/16

Prod VNet
10.10.0.0/16

Engineer accidentally creates staging as
192.168.1.0/24
```

Configurations can slowly drift.

With IaC:

```text
same module
     ↓
different approved inputs
     ↓
Dev / Staging / Prod
```

the environments are much more consistent.

### **Version control is a major benefit**

Suppose someone changes:

```text
AKS node count
3 → 5
```

With IaC:

```text
Git commit
   ↓
Pull Request
   ↓
Review
   ↓
Terraform plan
   ↓
Apply
```

we know:

* who changed it,
* what changed,
* why,
* when it changed.

### **IaC isn't the same as automation alone**

A Bash script can automate:

```bash
az group create ...
az network vnet create ...
az aks create ...
```

but IaC tools such as Terraform additionally maintain a model of infrastructure state and calculate desired changes.

Conceptually:

```text
Desired configuration
       ↓
Terraform compares
       ↓
Existing infrastructure
       ↓
Change only what's needed
```

### **Common IaC tools**

Examples include:

```text
Terraform
Bicep
ARM templates
Pulumi
CloudFormation
```

For Azure-focused DevOps, Terraform and Bicep are common choices.

**Memory line:**
**IaC = infrastructure defined, reviewed, versioned, and deployed like software.**

**Interview trap:**
IaC doesn't mean:

> “Everything is automatically secure and correct.”

Bad infrastructure code can still create bad infrastructure. IaC gives **repeatability and control**, not automatic correctness.

**Keywords:** IaC, version control, repeatability, automation, consistency, auditability

### **T09-E03. What is the AzureRM provider?**

**Answer:**
The **AzureRM provider is the Terraform provider used to manage Azure Resource Manager resources**, such as VNets, VMs, Storage Accounts, AKS clusters, Key Vaults, and many other Azure resources.

Architecture:

```text
Terraform configuration
        ↓
AzureRM Provider
        ↓
Azure Resource Manager APIs
        ↓
Azure resources
```

### **Example provider declaration**

```hcl
terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"
    }
  }
}

provider "azurerm" {
  features {}
}
```

Then resources use the `azurerm_` prefix:

```hcl
resource "azurerm_resource_group" "main" {
  name     = "rg-prod"
  location = "Central India"
}
```

Another example:

```hcl
resource "azurerm_kubernetes_cluster" "aks" {
  # AKS configuration
}
```

### **What does the provider actually do?**

Terraform itself doesn't inherently know:

```text
How to create AKS
How to create Azure VNets
How to call Azure APIs
```

The provider contains that Azure-specific implementation.

So:

```text
Terraform Core
     ↓
understands resources/state/planning

AzureRM Provider
     ↓
understands Azure Resource Manager
```

### **Provider authentication**

The AzureRM provider must authenticate to Azure.

For local development that might involve Azure CLI authentication.

For CI/CD, a stronger production pattern is:

```text
GitHub Actions / Azure DevOps
          ↓
OIDC / Workload Identity Federation
          ↓
Microsoft Entra ID
          ↓
AzureRM Provider
          ↓
Azure
```

rather than hardcoding a client secret.

### **AzureRM isn't the only Azure-related Terraform provider**

This is worth remembering.

Terraform also has providers for other Azure/Entra capabilities.

For example:

```text
azurerm
→ Azure Resource Manager resources

azuread
→ Microsoft Entra objects
```

So:

```text
azurerm_role_assignment
```

may manage Azure RBAC assignments, while Entra users/groups/app registrations are often managed with the appropriate identity-focused provider.

**Memory line:**
**AzureRM is Terraform's bridge to Azure Resource Manager resources.**

**Interview trap:**
Don't say AzureRM is Terraform itself.

```text
Terraform
→ IaC engine

AzureRM
→ Azure-specific provider/plugin
```

**Keywords:** AzureRM, provider, Azure Resource Manager, Terraform, Azure APIs

### **T09-E04. What does `terraform init` do?**

**Answer:**
`terraform init` **initializes a Terraform working directory**. It prepares the directory by downloading required providers and modules and configuring the backend used for Terraform state.

It is usually the first Terraform command I run after cloning or creating a Terraform project.

```text
Terraform files
     ↓
terraform init
     ↓
Providers downloaded
Modules initialized
Backend configured
     ↓
Ready for plan/apply
```

### **Example**

Suppose:

```hcl
terraform {
  required_providers {
    azurerm = {
      source = "hashicorp/azurerm"
    }
  }
}
```

Then:

```bash
terraform init
```

downloads the required AzureRM provider.

After that:

```bash
terraform plan
```

can actually evaluate Azure resources.

### **It also initializes the backend**

Suppose Terraform uses Azure Storage:

```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "tfstateprod123"
    container_name       = "tfstate"
    key                  = "prod.terraform.tfstate"
  }
}
```

Then:

```bash
terraform init
```

configures Terraform to use that remote backend.

Conceptually:

```text
terraform init
      ↓
Backend: Azure Storage
      ↓
prod.terraform.tfstate
```

If backend configuration changes, initialization normally needs to be run again with the appropriate migration/reconfiguration option.

### **Modules**

If configuration contains:

```hcl
module "network" {
  source = "./modules/network"
}
```

or a registry/Git module, `terraform init` also initializes/downloads those module dependencies.

### **Lock file**

Initialization also works with Terraform's provider dependency lock file:

```text
.terraform.lock.hcl
```

which records selected provider versions/checksums, improving reproducibility across machines and CI runs.

### **What `terraform init` does NOT do**

It does **not** normally create your declared Azure infrastructure.

```text
terraform init
→ prepare Terraform

terraform plan
→ preview changes

terraform apply
→ make changes
```

That distinction is extremely common in interviews.

### **Typical workflow**

```bash
terraform init
terraform fmt -check
terraform validate
terraform plan
terraform apply
```

**Memory line:**
**`terraform init` prepares the working directory: backend, providers, and modules.**

**Interview trap:**
Don't say:

> “`terraform init` deploys the infrastructure.”

It only initializes Terraform so later commands such as `plan` and `apply` can operate.

**Keywords:** `terraform init`, provider, backend, modules, `.terraform.lock.hcl`
