# 9. 🔴 M IMP — Terraform on Azure

## Easy

### **T09-E05. What does `terraform plan` do?**

**Answer:**
`terraform plan` **previews the infrastructure changes Terraform intends to make without actually applying those changes**.

Terraform compares:

```text
Terraform configuration
        ↓
Desired state

Existing state + real infrastructure
        ↓
Current state

        ↓
terraform plan
        ↓
Proposed changes
```

It answers:

> **“If I run `terraform apply` now, what will Terraform create, modify, or destroy?”**

### **Example**

Suppose Terraform currently manages:

```text
AKS node count = 3
```

and I change:

```hcl
default_node_pool {
  node_count = 5
}
```

Then:

```bash
terraform plan
```

might show something conceptually like:

```text
~ node_count = 3 -> 5

Plan:
0 to add,
1 to change,
0 to destroy.
```

No infrastructure has changed yet.

---

### **Symbols to remember**

Terraform plans commonly use:

```text
+  create

~  update in place

-  destroy

-/+ destroy then create replacement
```

For example:

```text
+ azurerm_storage_account.logs

~ azurerm_kubernetes_cluster.aks

- azurerm_public_ip.old
```

This lets me catch dangerous changes before deployment.

### **Why `plan` matters in CI/CD**

A strong Terraform PR workflow is:

```text
Pull Request
     ↓
terraform fmt -check
     ↓
terraform validate
     ↓
terraform plan
     ↓
Engineer reviews changes
     ↓
Merge / approval
     ↓
terraform apply
```

For example, a reviewer may notice:

```text
Plan:
2 to add
1 to change
27 to destroy
```

and stop the deployment before production gets damaged.

---

### **Saved plan**

For stronger automation:

```bash
terraform plan -out=tfplan
```

creates a saved execution plan.

Then:

```bash
terraform apply tfplan
```

applies that exact saved plan rather than calculating a fresh one at that moment.

Conceptually:

```text
terraform plan
      ↓
tfplan
      ↓
review/approval
      ↓
terraform apply tfplan
```

This is useful in controlled CI/CD pipelines.

### **Does `terraform plan` guarantee `apply` will succeed?**

No.

Between plan and apply:

```text
Azure resource changed
quota exhausted
permission changed
resource unavailable
```

could cause apply to fail.

A plan is a preview, not a guarantee.

**Memory line:**
**`terraform plan` = preview what Terraform intends to change before changing anything.**

**Interview trap:**
Don't say:

> “`terraform plan` creates resources.”

It only calculates and displays the proposed actions.

**Keywords:** `terraform plan`, preview, desired state, create, update, destroy, saved plan

---

### **T09-E06. What does `terraform apply` do?**

**Answer:**
`terraform apply` **executes the Terraform plan and makes the required infrastructure changes through the configured providers**, such as creating, modifying, or deleting Azure resources.

```text
Terraform configuration
        ↓
terraform plan
        ↓
Proposed changes
        ↓
terraform apply
        ↓
AzureRM Provider
        ↓
Azure APIs
        ↓
Infrastructure changed
        ↓
Terraform state updated
```

### **Example**

Configuration:

```hcl
resource "azurerm_resource_group" "app" {
  name     = "rg-app-prod"
  location = "Central India"
}
```

Then:

```bash
terraform apply
```

Terraform may show:

```text
Plan:
1 to add,
0 to change,
0 to destroy.
```

and ask:

```text
Do you want to perform these actions?
Enter a value: yes
```

After confirmation, Terraform creates the resource group.

---

### **Apply can perform three major types of action**

```text
Create
Update
Destroy
```

For example:

```text
+ Create new subnet

~ Increase AKS node count

- Remove obsolete public IP
```

It isn't limited to creating infrastructure.

---

### **Using a saved plan**

A good CI/CD pattern is:

```bash
terraform plan -out=tfplan
```

followed by:

```bash
terraform apply tfplan
```

Flow:

```text
PR / pipeline
   ↓
Generate plan
   ↓
Review plan
   ↓
Approval
   ↓
Apply exact plan
```

When applying a saved plan, Terraform doesn't need the usual interactive approval for the plan because the actions were already captured in that plan file.

---

### **`-auto-approve`**

Automation commonly uses:

```bash
terraform apply -auto-approve
```

but I wouldn't casually run that from a developer laptop against production.

A safer production pipeline is:

```text
terraform plan
       ↓
Review / policy checks
       ↓
Production approval
       ↓
terraform apply
```

The approval should happen at the CI/CD governance layer rather than blindly approving every Terraform change.

---

### **State is updated after successful operations**

Suppose Terraform creates:

```text
azurerm_virtual_network.prod
```

Terraform records the association:

```text
Terraform resource address
        ↕
Actual Azure resource
```

inside state.

That lets future runs understand that the resource already exists and is managed by Terraform.

### **What if apply partially fails?**

Terraform may successfully create some resources before another operation fails.

Example:

```text
VNet created ✅
Subnet created ✅
AKS creation ❌
```

Terraform records successful changes in state where appropriate.

Then I fix the underlying issue and run:

```bash
terraform plan
terraform apply
```

again.

Terraform should converge toward the desired configuration rather than requiring me to manually recreate everything.

**Memory line:**
**`terraform apply` = execute the planned changes and update infrastructure plus state.**

**Interview trap:**
Don't treat `terraform apply` like an all-or-nothing database transaction.

A run can **partially succeed** before encountering an error.

**Keywords:** `terraform apply`, create, update, destroy, state, `-auto-approve`, saved plan

---

### **T09-E07. What does `terraform destroy` do?**

**Answer:**
`terraform destroy` tells Terraform to **destroy the infrastructure resources managed by the current Terraform configuration and state**.

Conceptually:

```text
Terraform State
     ↓
Managed Resources
├── VNet
├── Subnets
├── AKS
├── ACR
└── Storage

     ↓
terraform destroy

Resources deleted
```

It is effectively a convenient way to create and apply a destroy plan for the managed resources.

### **Preview destruction first**

Before actually destroying anything, I can inspect the proposed destruction:

```bash
terraform plan -destroy
```

This might show:

```text
Plan:
0 to add,
0 to change,
12 to destroy.
```

Then:

```bash
terraform destroy
```

performs the deletion after confirmation.

---

### **Production caution**

This command is extremely dangerous against production.

I would never make:

```text
terraform destroy -auto-approve
```

an casually accessible production operation.

Protection should include things such as:

```text
Restricted pipeline permissions
Production approvals
Separate state
Protected branches
Least-privilege identities
prevent_destroy where appropriate
```

We'll discuss `prevent_destroy` later.

---

### **Dependencies are considered**

Suppose:

```text
Resource Group
   ↓
VNet
   ↓
Subnet
   ↓
AKS
```

Terraform understands the dependency graph and attempts destruction in a suitable order.

Conceptually:

```text
AKS
 ↓
Subnet
 ↓
VNet
 ↓
Resource Group
```

rather than blindly deleting parent resources first.

---

### **Does `destroy` delete every resource in the Azure subscription?**

No.

Terraform targets the resources represented by the Terraform configuration/state being operated on.

For example:

```text
Subscription
│
├── Terraform-managed AKS   ← destroy
├── Terraform-managed VNet  ← destroy
│
└── Manually created SQL    ← normally untouched
```

unless that SQL resource is also part of what Terraform is managing or another Azure-side cascade occurs.

### **Important state relationship**

If a resource exists in Azure but Terraform doesn't manage it in this state, `terraform destroy` doesn't simply discover every Azure resource and delete it.

Terraform relies heavily on the managed resource mappings in state.

**Memory line:**
**`terraform destroy` = remove the infrastructure managed by this Terraform state/configuration.**

**Interview trap:**
Don't describe it as:

> “Delete everything in Azure.”

It operates on the infrastructure Terraform is managing in the current context.

**Keywords:** `terraform destroy`, destroy plan, managed resources, state, dependency graph

### **T09-E08. What is Terraform state?**

**Answer:**
Terraform state is Terraform's **record of the infrastructure objects it manages and the mapping between Terraform resource addresses and the real resources created in Azure or another provider**.

By default, local state is stored in:

```text
terraform.tfstate
```

Conceptually:

```text
Terraform configuration

azurerm_virtual_network.prod
              │
              │ mapping stored in state
              ↓
Azure

/subscriptions/.../
resourceGroups/rg-prod/
providers/Microsoft.Network/
virtualNetworks/vnet-prod
```

Without that mapping, Terraform wouldn't reliably know which real Azure object corresponds to:

```hcl
azurerm_virtual_network.prod
```

---

### **Why state is needed**

Suppose configuration says:

```hcl
resource "azurerm_resource_group" "prod" {
  name = "rg-prod"
}
```

After Terraform creates it, state records information about that object.

On the next:

```bash
terraform plan
```

Terraform can determine:

```text
Configuration says resource should exist
        ↓
State says which Azure resource it manages
        ↓
Provider checks Azure
        ↓
No change?
→ do nothing
```

If you change:

```text
Central India
↓
East US
```

Terraform can calculate what action is required for that existing managed resource.

---

### **State stores more than IDs**

State can include:

```text
Resource IDs
Resource attributes
Dependencies
Metadata
Output values
Resource-instance mappings
```

Terraform uses this information when building its dependency graph and planning changes.

### **State can contain sensitive information**

This is very important.

State may contain values related to resources that are sensitive.

Therefore:

```text
terraform.tfstate
```

should **not** simply be committed to Git.

Bad:

```text
GitHub repository
└── terraform.tfstate ❌
```

For teams, I prefer a protected remote backend such as:

```text
Azure Storage Account
       ↓
Blob container
       ↓
prod.tfstate
```

with appropriate:

```text
RBAC
network controls
encryption
versioning/recovery
state locking
```

We'll cover remote Azure state in the next questions.

---

### **Local vs remote state**

Local:

```text
Developer laptop
└── terraform.tfstate
```

works for simple learning/testing.

But for a team:

```text
Engineer A ─┐
Engineer B ─┼→ Remote State Backend
CI/CD ──────┘
```

is much safer because everyone works against a shared state.

### **Configuration is not state**

This distinction matters:

```text
Terraform configuration
→ what infrastructure SHOULD look like

Terraform state
→ Terraform's recorded mapping/knowledge
   about managed infrastructure

Azure
→ actual infrastructure
```

Terraform uses all of these when planning changes.

### **Don't manually edit state casually**

State is operationally critical.

Normally I use Terraform commands such as:

```bash
terraform state list
terraform state show
terraform state mv
terraform state rm
```

rather than opening the JSON state file and manually changing values.

### **Quick architecture**

```text
             Terraform .tf
            Desired state
                 │
                 ↓
          terraform plan
            /           \
           ↓             ↓
 Terraform State      Azure API
 known resources    actual resources
           \             /
            └──── compare ┘
                  ↓
             Change plan
```

**Memory line:**
**State is Terraform's mapping between configuration addresses and real infrastructure.**

**Interview trap:**
Don't say:

> “Terraform state is just a backup of the `.tf` files.”

It is fundamentally different. `.tf` files describe the **desired configuration**; state tracks Terraform's relationship with the **managed real resources**.

**Keywords:** Terraform state, `terraform.tfstate`, resource mapping, remote backend, sensitive data, drift
