### **T09-M09. What is `count`?**

**Answer:**
`count` is a Terraform meta-argument used to create **multiple instances of a resource or module based on a number**. Each instance is identified by a numeric index such as `count.index`, so it works well when the resources are nearly identical and their individual identity does not matter much.

### **How it works**

Example:

```hcl
resource "azurerm_resource_group" "app" {
  count = 3

  name     = "rg-app-${count.index}"
  location = "centralindia"
}
```

Terraform creates:

```text
azurerm_resource_group.app[0]
azurerm_resource_group.app[1]
azurerm_resource_group.app[2]
```

Inside the block, Terraform exposes:

```hcl
count.index
```

which starts from `0`.

A more practical example is conditional creation:

```hcl
resource "azurerm_public_ip" "this" {
  count = var.create_public_ip ? 1 : 0

  name                = "pip-app-prod"
  location            = var.location
  resource_group_name = var.resource_group_name
  allocation_method   = "Static"
}
```

Here:

```text
create_public_ip = true
→ 1 resource

create_public_ip = false
→ 0 resources
```

### **Production example**

Suppose I need three identical worker VMs:

```text
Worker VM [0]
Worker VM [1]
Worker VM [2]
```

`count` can be simple and appropriate because they are essentially interchangeable.

But if I have resources with meaningful identities:

```text
frontend
backend
database
```

I would normally prefer `for_each`, because those resources are better identified by names rather than indexes.

### **Important distinction**

With `count`, Terraform identifies resources by their **position**:

```text
resource[0]
resource[1]
resource[2]
```

That can matter when the source is a list.

For example:

```hcl
names = ["dev", "staging", "prod"]
```

If I remove `"staging"`:

```text
Before:
[0] dev
[1] staging
[2] prod

After:
[0] dev
[1] prod
```

The index associated with `prod` changes.

Depending on how the configuration is written, that can lead Terraform to propose changes that would not occur with stable map keys.

> **In an interview, I would say:**
> “`count` lets Terraform create a specified number of instances of a resource or module. Each instance is addressed using a numeric index and I can reference that with `count.index`. It is useful for identical resources or simple conditional creation, but for resources with meaningful identities I usually prefer `for_each` because it uses stable keys.”

**Memory line:**
**`count` creates N instances and identifies them by numeric index.**

**Interview trap:**
Do not assume changing a list used with `count` is harmless. Index shifts can change Terraform resource addresses and cause unexpected plans.

**Keywords:**
`count`, `count.index`, numeric index, conditional creation, resource instances

* How do you conditionally create a resource using `count`?
* What is `count.index`?
* Why can removing an item from a list used with `count` be risky?

### **T09-M10. When would you use `for_each` rather than `count`?**

**Answer:**
I use `for_each` rather than `count` when each resource has a **meaningful and stable identity**, such as a subnet name, environment name, or storage account name. `for_each` addresses instances by keys instead of numeric positions, which generally makes changes easier to understand and safer when items are added or removed.

### **How it works**

With `count`:

```hcl
resource "azurerm_subnet" "this" {
  count = length(var.subnets)

  name             = var.subnets[count.index]
  address_prefixes = [var.addresses[count.index]]
}
```

Terraform addresses them as:

```text
subnet[0]
subnet[1]
subnet[2]
```

With `for_each`:

```hcl
variable "subnets" {
  default = {
    aks = "10.0.1.0/24"
    app = "10.0.2.0/24"
    db  = "10.0.3.0/24"
  }
}

resource "azurerm_subnet" "this" {
  for_each = var.subnets

  name             = "snet-${each.key}"
  address_prefixes = [each.value]
}
```

Terraform addresses them as:

```text
subnet["aks"]
subnet["app"]
subnet["db"]
```

### **Why this matters**

Imagine this collection:

```text
aks
app
db
```

If I remove `app`, with `for_each` I still have:

```text
subnet["aks"]
subnet["db"]
```

Their identities do not depend on position.

That makes Terraform plans easier to reason about.

### **When I would choose each**

```text
count
│
├── N identical instances
├── index matters
└── simple true/false creation

for_each
│
├── resources have names/IDs
├── values differ per instance
├── map/set fits naturally
└── stable identity matters
```

### **Production example**

For Azure subnets, I would strongly lean toward:

```hcl
for_each = {
  aks      = "10.0.1.0/24"
  database = "10.0.2.0/24"
  private  = "10.0.3.0/24"
}
```

because `aks`, `database`, and `private` are meaningful resource identities.

For three interchangeable worker instances, `count = 3` might be perfectly reasonable.

### **Important distinction**

`for_each` is not automatically “better” than `count`.

The right question is:

```text
Do these instances have identity?
```

If yes:

```text
for_each
```

is usually more natural.

If they are simply N interchangeable instances:

```text
count
```

may be simpler.

Also, changing an existing resource from:

```text
resource[0]
```

to:

```text
resource["prod"]
```

changes its Terraform address. In an existing environment, I would handle that carefully rather than simply changing syntax and applying.

> **In an interview, I would say:**
> “I prefer `for_each` when instances have meaningful identities, like Azure subnet or environment names, because Terraform tracks them by stable keys instead of list positions. I use `count` when I simply need N similar instances or simple conditional creation. The main consideration is resource identity, not just which syntax is shorter.”

**Memory line:**
**Named resources → `for_each`; numbered resources → `count`.**

**Interview trap:**
The main advantage of `for_each` is not merely readability. Its **key-based resource addressing** is often the more important production benefit.

**Keywords:**
`for_each`, `count`, stable keys, indexes, maps, resource addressing, identity

**Likely follow-ups:**

* What happens when an item is removed from a `count` list?
* Can you convert an existing resource from `count` to `for_each`?
* What collections can `for_each` accept?
* Can modules use `for_each` and `count`?

### **T09-M11. What is `depends_on`?**

**Answer:**
`depends_on` is a Terraform meta-argument used to create an **explicit dependency** between resources or modules when Terraform cannot infer the dependency from normal references. It tells Terraform that one object must be handled only after another dependency has been processed.

### **How Terraform normally handles dependencies**

Terraform automatically builds a dependency graph from references.

For example:

```hcl
resource "azurerm_subnet" "aks" {
  name                 = "snet-aks"
  resource_group_name  = azurerm_resource_group.main.name
  virtual_network_name = azurerm_virtual_network.main.name
}
```

Terraform sees:

```text
Resource Group
     ↓
VNet
     ↓
Subnet
```

because the subnet directly references values from other resources.

So I do **not** need:

```hcl
depends_on = [
  azurerm_virtual_network.main
]
```

in that case.

### **When `depends_on` is useful**

Sometimes a dependency exists behaviorally, but there is no attribute reference Terraform can detect.

Example:

```hcl
resource "azurerm_role_assignment" "aks_acr_pull" {
  scope                = azurerm_container_registry.main.id
  role_definition_name = "AcrPull"
  principal_id         = azurerm_kubernetes_cluster.main.kubelet_identity[0].object_id
}

resource "some_resource" "deployment" {
  # resource doesn't otherwise reference role assignment

  depends_on = [
    azurerm_role_assignment.aks_acr_pull
  ]
}
```

The intention is:

```text
Identity
   ↓
RBAC assignment
   ↓
Dependent operation
```

Terraform now understands that ordering explicitly.

### **Dependency graph**

Terraform effectively builds something like:

```text
Resource Group
      ↓
     VNet
      ↓
    Subnet
      ↓
     AKS
      ↓
Role Assignment
      ↓
Dependent Resource
```

It then uses that graph to determine what can safely run in parallel.

### **Important distinction**

I would use `depends_on` only when necessary.

This:

```hcl
resource "azurerm_subnet" "app" {
  virtual_network_name = azurerm_virtual_network.main.name
}
```

already creates an **implicit dependency**.

Adding:

```hcl
depends_on = [
  azurerm_virtual_network.main
]
```

is redundant.

Too many unnecessary explicit dependencies can make the graph more conservative and reduce Terraform's ability to perform independent operations concurrently.

### **Production example**

Suppose I deploy:

```text
Managed Identity
      ↓
Azure RBAC Role Assignment
      ↓
Resource that requires the permission
```

If the final resource doesn't directly reference the role-assignment object but operationally requires that assignment to exist first, that can be a valid place for an explicit dependency.

One caveat: `depends_on` controls Terraform's **ordering**, but it does not guarantee that an external service has completed every asynchronous propagation step. For example, Azure RBAC propagation may still take some time even after the role-assignment API operation succeeds.

> **In an interview, I would say:**
> “Terraform normally derives dependencies automatically from resource references. I use `depends_on` only when there is a real dependency Terraform cannot infer, such as an operational dependency that has no direct attribute reference. It adds an explicit edge to Terraform's dependency graph, but I avoid unnecessary use because implicit dependencies are cleaner and allow better parallelism.”

**Memory line:**
**Reference first; use `depends_on` only when Terraform cannot see the dependency itself.**

**Interview trap:**
`depends_on` does not mean “sleep until Azure is eventually consistent.” It establishes Terraform ordering, not arbitrary waiting for downstream propagation.

**Keywords:**
`depends_on`, dependency graph, implicit dependency, explicit dependency, ordering, parallelism

**Likely follow-ups:**

* How does Terraform automatically discover dependencies?
* What is an implicit dependency?
* Can `depends_on` be used with modules?
* Does `depends_on` solve Azure RBAC propagation delays?

### **T09-M12. What is the Terraform lifecycle block?**

**Answer:**
The Terraform `lifecycle` block changes how Terraform handles the creation, replacement, destruction, or change detection of a particular resource. I use it only when the normal Terraform lifecycle needs to be deliberately modified—for example to protect a critical resource from destruction or create a replacement before deleting the existing instance.

### **How it works**

A lifecycle block lives inside a resource:

```hcl
resource "azurerm_resource_group" "prod" {
  name     = "rg-prod"
  location = "centralindia"

  lifecycle {
    prevent_destroy = true
  }
}
```

Common lifecycle arguments include:

```text
lifecycle
│
├── prevent_destroy
├── create_before_destroy
├── ignore_changes
└── replace_triggered_by
```

### **1. `prevent_destroy`**

```hcl
lifecycle {
  prevent_destroy = true
}
```

Terraform rejects a plan that would destroy that resource while this lifecycle rule is present.

This can be useful for critical resources such as:

```text
production database
critical Key Vault
important Storage Account
```

but it is a guardrail, not a replacement for good RBAC, reviews, backups, or resource locks.

---

### **2. `create_before_destroy`**

Normally, if a resource must be replaced, Terraform may follow:

```text
Destroy old
    ↓
Create new
```

With:

```hcl
lifecycle {
  create_before_destroy = true
}
```

Terraform tries:

```text
Create new
    ↓
Switch dependencies
    ↓
Destroy old
```

This can help reduce downtime when the Azure resource type and naming constraints allow both versions to exist simultaneously.

---

### **3. `ignore_changes`**

Example:

```hcl
lifecycle {
  ignore_changes = [
    tags
  ]
}
```

Terraform will ignore changes to those selected attributes after creation when determining updates.

A real use case could be an attribute legitimately managed by another Azure controller or external system.

But I use this very carefully.

If I write:

```hcl
ignore_changes = all
```

too casually, Terraform can stop detecting configuration differences that I actually need to know about.

---

### **4. `replace_triggered_by`**

This can cause a resource to be replaced when another managed resource or attribute changes.

Conceptually:

```text
Dependency changes
      ↓
Replacement trigger
      ↓
Terraform replaces resource
```

It is useful where replacement must follow another infrastructure change even if Terraform would not otherwise infer that replacement from the resource's own arguments.

### **Production example**

For a critical Azure resource:

```hcl
resource "azurerm_key_vault" "prod" {
  # ...

  lifecycle {
    prevent_destroy = true
  }
}
```

That provides an additional Terraform-side guardrail.

For a replaceable application component:

```hcl
lifecycle {
  create_before_destroy = true
}
```

could help reduce interruption if Azure permits the old and new resources to coexist.

### **Important distinction**

Lifecycle rules influence **Terraform behavior**, not Azure's underlying authorization model.

```text
prevent_destroy
→ Terraform protection

Azure Resource Lock
→ Azure platform protection
```

Someone with sufficient Azure permissions may still modify or delete a resource outside Terraform unless Azure controls prevent it.

Similarly:

```text
ignore_changes
```

does not stop the external change. It only tells Terraform not to reconcile selected differences.

> **In an interview, I would say:**
> “The Terraform lifecycle block lets me alter Terraform's normal behavior for a resource. The most common examples are `prevent_destroy` to protect critical resources, `create_before_destroy` to reduce downtime during replacement, and `ignore_changes` when an attribute is intentionally managed elsewhere. I use lifecycle rules carefully because they can hide changes or alter normal replacement behavior.”

**Memory line:**
**The lifecycle block changes how Terraform treats a resource, not what the Azure resource itself is.**

**Interview trap:**
Do not use `ignore_changes` as a quick fix whenever Terraform shows drift. It can hide real configuration problems and weaken Terraform's control over infrastructure.

**Keywords:**
`lifecycle`, `prevent_destroy`, `create_before_destroy`, `ignore_changes`, `replace_triggered_by`, replacement, drift
