### **T09-M01. Why should Terraform state be stored remotely?**

**Answer:**
Terraform state should be stored remotely because in a team or CI/CD environment, multiple engineers and pipelines need a **single authoritative state file**. A remote backend also improves durability, access control, security, and—depending on the backend—provides **state locking** so two Terraform operations do not modify the same infrastructure simultaneously. HashiCorp and Microsoft both support Azure Blob Storage as a remote backend for this purpose. ([HashiCorp Developer][1])

### **How it works**

With local state:

```text
Engineer A
   ↓
terraform.tfstate on laptop A

Engineer B
   ↓
terraform.tfstate on laptop B
```

Both engineers can have different views of the infrastructure.

With remote state:

```text
Engineer A ──┐
             │
CI Pipeline ─┼──→ Azure Storage Backend
             │          ↓
Engineer B ──┘      terraform.tfstate
                       ↓
                 Azure Resources
```

Everyone operates against the same state.

The main benefits are:

1. **Collaboration** — everyone uses the same state.
2. **State locking** — helps prevent concurrent writes.
3. **Durability** — state is not lost because someone's laptop fails.
4. **Access control** — access can be controlled using Azure permissions.
5. **CI/CD support** — pipelines can access the same backend consistently.
6. **Reduced local exposure** — remote backends avoid routinely persisting state on developer machines. ([HashiCorp Developer][2])

### **Production example**

Suppose GitHub Actions manages an AKS environment:

```text
Git PR
   ↓
terraform plan
   ↓
Review / Approval
   ↓
terraform apply
   ↓
Azure Storage Backend
   ↓
AKS / VNet / ACR / Key Vault
```

I would store the state in a dedicated Azure Storage account rather than committing `terraform.tfstate` into Git.

I would also tightly restrict access because Terraform state can contain sensitive information about infrastructure and potentially sensitive values. Microsoft specifically notes that local state is unsuitable for collaboration and increases the risk of accidental loss. ([Microsoft Learn][3])

### **Important distinction**

A **remote Git repository is not a Terraform remote backend**.

```text
Git
→ stores Terraform configuration

Remote backend
→ stores Terraform state
```

I would never treat committing `.tfstate` to Git as a replacement for a proper backend.

> **In an interview, I would say:**
> “I store Terraform state remotely so the team and CI/CD pipelines have one authoritative view of the infrastructure. On Azure, I would typically use an Azure Storage backend because it gives centralized, durable state storage and supports state locking. I would secure access to that backend and never commit the state file to Git.”

**Memory line:**
**Code goes in Git; shared Terraform state goes in a remote backend.**

**Interview trap:**
Remote state is not just about backing up the file. One of its biggest production benefits is **safe collaboration and concurrency control**.

**Keywords:**
Remote backend, tfstate, Azure Storage, collaboration, locking, access control, CI/CD

**Likely follow-ups:**

* Why shouldn't `.tfstate` be committed to Git?
* Can Terraform state contain secrets?
* What happens if two pipelines run Terraform simultaneously?
* How would you secure an Azure Storage Terraform backend?

### **T09-M02. How can Azure Storage be used as a Terraform backend?**

**Answer:**
Terraform provides the `azurerm` backend, which can store Terraform state as a **blob inside an Azure Storage container**. I first create a storage account and blob container, configure the `azurerm` backend with the storage account, container, and state-file key, authenticate securely, and then run `terraform init` to initialize or migrate the state to that backend. ([HashiCorp Developer][1])

### **How it works**

The structure is:

```text
Terraform
    ↓
azurerm backend
    ↓
Azure Storage Account
    ↓
Blob Container
    ↓
prod.tfstate
```

A basic configuration might look like:

```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstateprod001"
    container_name       = "tfstate"
    key                  = "prod.terraform.tfstate"
    use_azuread_auth     = true
  }
}
```

Then:

```bash
terraform init
```

The `key` identifies the blob containing that particular state.

For example:

```text
tfstate/
├── network-prod.tfstate
├── aks-prod.tfstate
└── monitoring-prod.tfstate
```

HashiCorp's `azurerm` backend supports Azure Blob Storage and currently recommends **Microsoft Entra ID authentication** for new configurations rather than relying on long-lived storage credentials. ([HashiCorp Developer][1])

### **Production implementation**

I would normally separate the backend infrastructure from the workload Terraform.

For example:

```text
Bootstrap
   ↓
Resource Group
   ↓
Storage Account
   ↓
Blob Container

Then:

Application Terraform
   ↓
azurerm backend
   ↓
remote tfstate
```

That avoids the circular problem of Terraform needing its backend before it can initialize the configuration that creates that backend.

For CI/CD, I would prefer:

```text
GitHub Actions
      ↓
OIDC / Workload Identity Federation
      ↓
Microsoft Entra ID
      ↓
Azure Storage RBAC
      ↓
Terraform state blob
```

rather than storing a storage-account key or Azure client secret in the pipeline.

### **Important distinction**

The Terraform **AzureRM provider** and the **`azurerm` backend** are different things.

```text
AzureRM provider
→ manages Azure resources

azurerm backend
→ stores Terraform state
```

They can even authenticate separately.

> **In an interview, I would say:**
> “On Azure I normally configure Terraform's `azurerm` backend to store state as a blob in an Azure Storage container. The backend specifies the storage account, container and state key. I initialize it with `terraform init`, and in production I prefer Entra-based authentication with tightly scoped access rather than storage keys or long-lived secrets.”

**Memory line:**
**Azure Storage account → container → blob key → Terraform state.**

**Interview trap:**
Do not confuse the **`azurerm` provider** with the **`azurerm` backend**. One manages resources; the other stores state.

**Keywords:**
`azurerm` backend, Storage Account, Blob Container, state key, `terraform init`, Microsoft Entra ID

**Likely follow-ups:**

* Should the backend Storage Account be created by the same Terraform configuration?
* How would you separate state between dev and production?

### **T09-M03. How does Terraform state locking work with Azure Storage?**

**Answer:**
When Terraform uses the `azurerm` backend, it uses Azure Blob Storage's native locking capability to prevent multiple Terraform processes from writing the same state simultaneously. Before an operation that can modify state, Terraform obtains a lock; another Terraform process targeting that state must wait or fail rather than modifying it concurrently. ([HashiCorp Developer][1])

### **How it works**

Imagine two deployment pipelines start at the same time:

```text
Pipeline A
    ↓
Acquire state lock
    ↓
terraform apply
    ↓
Update state
    ↓
Release lock


Pipeline B
    ↓
Attempts state lock
    ↓
LOCKED
    ↓
Cannot safely apply yet
```

Without locking:

```text
Pipeline A ──→ modifies AKS ──┐
                              ├──→ conflicting state updates
Pipeline B ──→ modifies AKS ──┘
```

That could cause state inconsistency or corruption.

With the Azure backend, Blob Storage is automatically locked for operations that write state. Microsoft documents this behavior specifically as protection against concurrent state operations. ([Microsoft Learn][4])

### **Production example**

Suppose two pull requests are merged close together:

```text
PR #101 → Pipeline A → terraform apply
PR #102 → Pipeline B → terraform apply
```

Pipeline A acquires the backend lock.

Pipeline B might receive an error indicating that the state is locked rather than executing against the same state concurrently.

That is **good behavior**. I would not immediately remove the lock.

I would first determine:

```text
Is another Terraform job running?
          ↓
       Yes → wait
          ↓
        No
          ↓
Was the previous job terminated unexpectedly?
          ↓
       Yes
          ↓
Confirm no active operation
          ↓
Recover/remove stale lock carefully
```

### **Important operational point**

A lock can become stale if, for example, a CI runner crashes during an operation.

Before forcefully releasing such a lock, I would verify that **no Terraform process is still legitimately using it**.

Removing a valid lock while another `apply` is running can create exactly the concurrency problem the locking mechanism is designed to prevent.

### **Important distinction**

State locking protects against:

```text
Concurrent Terraform state modification
```

It does **not** prevent:

```text
Someone manually modifying Azure resources
```

Manual Azure changes are a **drift** problem, not a state-locking problem.

> **In an interview, I would say:**
> “The Azure Storage backend uses Blob Storage locking so only one Terraform operation can safely modify a given state at a time. If another pipeline tries to apply against that state, it cannot obtain the lock. If I see a lock error, I first verify whether another Terraform operation is running; I only remove a lock after confirming it is stale.”

**Memory line:**
**One state → one writer at a time.**

**Interview trap:**
Never see a lock error and immediately force-unlock it. First prove that no legitimate Terraform operation is still running.

**Keywords:**
State lock, Azure Blob Storage, concurrency, stale lock, backend, state consistency

**Likely follow-ups:**

* What would you do if a Terraform state lock became stuck?
* What happens if two CI pipelines run against the same state?
* Does state locking prevent portal changes?
* How would you prevent concurrent Terraform pipelines operationally as well?

### **T09-M04. What is a Terraform module?**

**Answer:**
A Terraform module is a **reusable collection of Terraform configuration that manages related infrastructure together**. Every Terraform configuration has a root module, and that root module can call reusable child modules—for example a standardized Azure VNet, AKS cluster, or Key Vault module. ([HashiCorp Developer][5])

### **How it works**

Instead of repeatedly writing:

```text
VNet
Subnet
NSG
Route Table
```

for every environment, I can create:

```text
modules/
└── network/
    ├── main.tf
    ├── variables.tf
    └── outputs.tf
```

and call it:

```hcl
module "network" {
  source = "./modules/network"

  vnet_name     = "vnet-prod"
  address_space = ["10.20.0.0/16"]
  location      = "Central India"
}
```

Conceptually:

```text
Root Module
│
├── module "network"
│    ├── VNet
│    ├── Subnets
│    └── NSGs
│
├── module "aks"
│    ├── AKS
│    └── Node Pools
│
└── module "keyvault"
     ├── Key Vault
     └── Private Endpoint
```

HashiCorp defines the configuration in the working directory as the **root module**. Modules called from it are **child modules**. Modules can come from local directories, registries, or version-control sources. ([HashiCorp Developer][5])

### **Why modules matter in production**

Modules give me:

* **Reuse** — avoid duplicating the same Terraform.
* **Standardization** — teams deploy infrastructure using the same patterns.
* **Abstraction** — consumers provide inputs instead of knowing every resource detail.
* **Maintainability** — changes to a common infrastructure pattern can be managed centrally.
* **Consistency** — security and naming conventions can be built into the module.

For example, an organization might publish:

```text
terraform-azure-vnet
terraform-azure-aks
terraform-azure-keyvault
terraform-azure-storage
```

Application teams then consume those modules instead of rebuilding the infrastructure pattern themselves.

### **Inputs and outputs**

A module typically accepts variables:

```text
Root Module
    │
    │ variables
    ▼
Child Module
    │
    │ outputs
    ▼
Root Module / Other Modules
```

For example:

```hcl
module "network" {
  source = "./modules/network"

  address_space = ["10.0.0.0/16"]
}

module "aks" {
  source = "./modules/aks"

  subnet_id = module.network.aks_subnet_id
}
```

Here the network module hides the implementation details and exposes only the subnet ID needed by AKS.

### **Important distinction**

A module is **not necessarily one Azure resource**.

A useful module normally represents a reusable infrastructure capability:

```text
Good abstraction:
AKS platform module
→ cluster + identity + node pools + networking configuration

Usually poor abstraction:
one module for every individual NSG rule
```

The goal is useful reuse and standardization, not creating modules merely to reduce the number of lines in `main.tf`.

> **In an interview, I would say:**
> “A Terraform module is a reusable collection of infrastructure configuration. The directory where I run Terraform is the root module, and it can call child modules. In Azure, I might create reusable modules for networking, AKS or Key Vault, expose configurable values through variables, and return things such as subnet IDs through outputs. That gives teams consistent, reusable infrastructure instead of duplicating resource definitions.”

**Memory line:**
**A module packages a reusable infrastructure pattern behind inputs and outputs.**

**Interview trap:**
A module is not automatically a separate state file. Resources called through child modules normally remain part of the **calling Terraform configuration's state**.

**Keywords:**
Root module, child module, inputs, outputs, reuse, standardization, module source
