### **T09-M13. What does `prevent_destroy` do?**

**Answer:**
`prevent_destroy` is a Terraform lifecycle rule that makes Terraform **reject a plan if that resource would be destroyed or replaced**. I use it as an additional safety guard for critical stateful resources such as production databases or storage, but I do not treat it as a replacement for Azure RBAC, resource locks, backups, and deployment approvals. ([HashiCorp Developer][1])

### **How it works**

Example:

```hcl
resource "azurerm_storage_account" "prod" {
  name                     = "stprodcritical001"
  resource_group_name      = azurerm_resource_group.prod.name
  location                 = azurerm_resource_group.prod.location
  account_tier             = "Standard"
  account_replication_type = "ZRS"

  lifecycle {
    prevent_destroy = true
  }
}
```

If a change requires destruction:

```text
Terraform configuration change
          ↓
Terraform determines:
resource must be destroyed/replaced
          ↓
prevent_destroy = true
          ↓
PLAN FAILS
          ↓
Engineer must investigate
```

This protects against commands such as:

```bash
terraform destroy
```

and against configuration changes that would require resource replacement, as long as the lifecycle rule remains in the configuration. ([HashiCorp Developer][1])

### **Production example**

Suppose a production Azure resource contains important data:

```text
Production Storage Account
Production Database
Critical Key Vault
```

I might use:

```hcl
lifecycle {
  prevent_destroy = true
}
```

so an unexpected Terraform plan cannot casually delete it.

But my actual production protection would be layered:

```text
Pull Request review
       ↓
terraform plan
       ↓
Approval
       ↓
prevent_destroy
       ↓
Azure RBAC
       ↓
Azure Resource Lock
       ↓
Backup / Recovery controls
```

### **Very important caveat**

This is a strong interview point:

`prevent_destroy` only works while that lifecycle rule exists in the configuration.

If someone removes the entire resource block from the Terraform configuration, then the `prevent_destroy` rule is also no longer present to protect that object. HashiCorp explicitly warns about this behavior. ([HashiCorp Developer][1])

So:

```text
prevent_destroy
≠ absolute Azure deletion protection
```

### **Important distinction**

```text
Terraform prevent_destroy
→ Terraform-side guardrail

Azure Resource Lock
→ Azure platform-side guardrail
```

Someone deleting a resource directly through Azure APIs is not stopped merely because Terraform contains `prevent_destroy`.

> **In an interview, I would say:**
> “`prevent_destroy` is a Terraform lifecycle rule that rejects a Terraform operation if a managed resource would be destroyed or replaced. I use it carefully for critical stateful resources, but it is only a Terraform-side guardrail. For production I would combine it with RBAC, Azure resource locks, reviews, and backups.”

**Memory line:**
**`prevent_destroy` makes Terraform say no to destruction while the rule remains configured.**

**Interview trap:**
Do not say it makes a resource impossible to delete. It does **not** protect against deletion outside Terraform, and removing its configuration also removes the lifecycle protection.

**Keywords:**
`prevent_destroy`, lifecycle, deletion protection, replacement, guardrail, Azure Resource Lock

**Likely follow-ups:**

* Is `prevent_destroy` the same as an Azure resource lock?
* What happens if the resource block is removed completely?
* Would you enable it on every production resource?
* Can `prevent_destroy` block a replacement?

### **T09-M14. What does `create_before_destroy` do?**

**Answer:**
`create_before_destroy` tells Terraform that when a resource must be replaced, Terraform should **try to create the replacement first and destroy the old resource afterward**. It can reduce downtime, but it only works when Azure allows the old and new resources to exist at the same time. ([HashiCorp Developer][1])

### **Default replacement behavior**

Some Terraform attributes cannot be updated in place.

For example:

```text
Configuration change
       ↓
Provider determines:
resource requires replacement
```

Normally the lifecycle might be:

```text
Old Resource
     ↓
Destroy
     ↓
Create Replacement
```

That can introduce downtime.

With:

```hcl
lifecycle {
  create_before_destroy = true
}
```

Terraform instead tries:

```text
Old Resource
     │
     ├── still running
     │
Create New Resource
     ↓
Redirect dependencies
     ↓
Destroy Old Resource
```

HashiCorp documents this as an opt-in lifecycle behavior for replacements. ([HashiCorp Developer][1])

### **Production example**

Suppose an application resource can be replaced while both versions coexist.

```hcl
resource "some_application_resource" "app" {
  # ...

  lifecycle {
    create_before_destroy = true
  }
}
```

The goal is:

```text
Version A serving traffic
       ↓
Create Version B
       ↓
Version B becomes usable
       ↓
Version A removed
```

This can be useful for availability-sensitive infrastructure.

### **Important limitation**

Azure resources frequently have globally or scope-unique names.

For example:

```text
Storage Account name
ACR name
Key Vault name
```

If the replacement must have exactly the same unique name, Azure may not permit:

```text
Old: myuniquename
New: myuniquename
```

to exist simultaneously.

So `create_before_destroy` does **not automatically guarantee zero downtime**.

You need an architecture and naming strategy that allows both generations to coexist. HashiCorp specifically notes unique-name constraints as an important limitation of this lifecycle option. ([HashiCorp Developer][1])

### **Important distinction**

```text
create_before_destroy
→ controls Terraform replacement ordering
```

It does not automatically provide:

```text
traffic switching
health validation
session draining
database migration
application rollback
```

Those must still be designed separately.

> **In an interview, I would say:**
> “`create_before_destroy` changes Terraform's replacement ordering so the new resource is created before the old one is deleted. It can reduce downtime, but I first verify that Azure permits both resources to coexist, especially for resources with unique-name constraints. It controls infrastructure replacement order; it is not a complete zero-downtime deployment strategy.”

**Memory line:**
**Replacement becomes create new → switch → remove old.**

**Interview trap:**
Do not claim `create_before_destroy` guarantees zero downtime. Unique naming, quotas, dependencies, and application traffic switching can still prevent that.

**Keywords:**
`create_before_destroy`, lifecycle, replacement, zero-downtime, unique names, availability

**Likely follow-ups:**

* When would `create_before_destroy` fail?
* Why can unique Azure resource names cause problems?
* Is `create_before_destroy` the same as blue-green deployment?
* How does it affect dependent resources?

### **T09-M15. What is Terraform drift?**

**Answer:**
Terraform drift occurs when the **real infrastructure changes outside the intended Terraform workflow**, so the deployed Azure resource no longer matches what Terraform configuration and state expect. A common example is someone manually changing an NSG rule, VM size, or tag in the Azure portal. ([HashiCorp Developer][2])

### **How drift happens**

Normal desired state:

```text
Terraform Configuration
        ↓
Terraform State
        ↓
Actual Azure Resource

All aligned
```

Now someone changes the Azure resource manually:

```text
Terraform Configuration
       │
       │ expects Standard_D2s_v5
       ↓
Terraform State
       │
       ↓
Azure VM
       ↑
Portal change:
Standard_D4s_v5
```

Now the actual resource differs from the Terraform-managed intent.

Common causes include:

```text
Azure Portal changes
Azure CLI / PowerShell changes
another automation system
Azure controllers or policies
emergency incident changes
```

### **How I detect it**

My first step is normally:

```bash
terraform plan
```

Terraform refreshes its understanding of managed resources and compares current infrastructure against the desired configuration when building the plan. ([HashiCorp Developer][2])

If I specifically want to inspect what has changed externally without proposing normal infrastructure reconciliation:

```bash
terraform plan -refresh-only
```

This helps show changes between Terraform's recorded state and the real infrastructure. HashiCorp recommends refresh-only operations rather than the older `terraform refresh` command, which is deprecated. ([HashiCorp Developer][3])

### **Production example**

Suppose Terraform defines:

```hcl
resource "azurerm_network_security_rule" "https" {
  destination_port_range = "443"
}
```

Someone changes it manually to:

```text
Destination port = *
```

My investigation would be:

```text
terraform plan
      ↓
Detect unexpected difference
      ↓
Determine whether change was intentional
      ↓
      ├── No
      │    ↓
      │  Apply Terraform
      │    ↓
      │  Restore desired configuration
      │
      └── Yes
           ↓
       Update Terraform code
           ↓
       Review plan
           ↓
       Reconcile configuration/state
```

### **The key production decision**

When drift exists, I do **not** automatically run `terraform apply`.

First I determine:

```text
Was the manual change wrong?
```

If yes:

```text
Terraform configuration remains source of truth
        ↓
terraform apply
        ↓
revert Azure to desired state
```

If the external change was intentional:

```text
Update Terraform configuration
        ↓
Review terraform plan
        ↓
bring code/state/infrastructure back into alignment
```

A refresh-only operation can update state to reflect the real object without changing the remote infrastructure, but that does **not by itself make your Terraform configuration represent the desired configuration**. ([HashiCorp Developer][4])

### **Important distinction**

Drift is different from a normal Terraform code change:

```text
Change .tf file
→ intentional desired-state change

Change Azure manually
→ possible Terraform drift
```

Also:

```text
State locking
→ prevents concurrent Terraform state writes

Drift detection
→ detects infrastructure changed outside Terraform
```

> **In an interview, I would say:**
> “Terraform drift is when real infrastructure no longer matches the Terraform-managed desired state, usually because something changed it outside Terraform. I would detect it with `terraform plan`, investigate whether the change was intentional, and then either reapply Terraform to restore the desired state or update the Terraform configuration to formally adopt the intended change. I would not blindly apply until I understand why the drift exists.”

**Memory line:**
**Drift = Azure changed without the Terraform source of truth changing with it.**

**Interview trap:**
Do not blindly run `terraform apply` whenever drift appears. During an incident, the manual change may have been intentional and applying immediately could undo a necessary production fix.

**Keywords:**
Drift, desired state, actual state, `terraform plan`, `-refresh-only`, reconciliation, portal changes

**Likely follow-ups:**

* How do you detect Terraform drift?
* What would you do after someone manually changes a production resource?
* What does `terraform plan -refresh-only` do?
* Should you use `ignore_changes` to solve drift?

### **T09-H01. How do you import an existing Azure resource into Terraform?**

**Answer:**
To import an existing Azure resource, I first write or generate the Terraform configuration that should represent it, identify the resource's Azure resource ID, and then associate that existing Azure object with a Terraform resource address using either an **`import` block** or `terraform import`. After importing, I run `terraform plan` and reconcile the configuration until Terraform proposes no unintended changes. Importing adds the resource to Terraform management; it does not mean the configuration is automatically perfect. ([HashiCorp Developer][5])

### **Production implementation order**

I would do it in this order:

```text
1. Inspect existing Azure resource
              ↓
2. Identify correct AzureRM resource type
              ↓
3. Write Terraform resource configuration
              ↓
4. Obtain Azure resource ID
              ↓
5. Import resource
              ↓
6. Run terraform plan
              ↓
7. Reconcile configuration
              ↓
8. Verify plan is safe
              ↓
9. Commit through normal PR workflow
```

---

### **1. Identify the existing Azure resource**

For example:

```text
Existing:
Resource Group = rg-prod
```

Its Azure resource ID would look like:

```text
/subscriptions/<subscription-id>/resourceGroups/rg-prod
```

The current AzureRM provider documentation supports importing a resource group using its full Azure resource ID. ([Terraform Registry][6])

---

### **2. Create the Terraform resource block**

```hcl
resource "azurerm_resource_group" "prod" {
  name     = "rg-prod"
  location = "centralindia"
}
```

The Terraform address is therefore:

```text
azurerm_resource_group.prod
```

---

### **3. Import it**

One option is the CLI:

```bash
terraform import \
  azurerm_resource_group.prod \
  "/subscriptions/<subscription-id>/resourceGroups/rg-prod"
```

Conceptually:

```text
Existing Azure Resource
          ↓
Azure Resource ID
          ↓
terraform import
          ↓
Terraform State

azurerm_resource_group.prod
        ↕
existing rg-prod
```

The CLI command binds that existing remote object to the specified Terraform resource address. ([HashiCorp Developer][5])

---

### **Modern configuration-driven import**

Terraform also supports `import` blocks:

```hcl
import {
  to = azurerm_resource_group.prod
  id = "/subscriptions/<subscription-id>/resourceGroups/rg-prod"
}
```

alongside:

```hcl
resource "azurerm_resource_group" "prod" {
  name     = "rg-prod"
  location = "centralindia"
}
```

Then I can run:

```bash
terraform plan
terraform apply
```

The configuration-driven approach is particularly useful because the import declaration can participate in normal reviewed Terraform workflows and CI/CD. ([HashiCorp Developer][7])

---

### **4. The most important step: run `terraform plan`**

Import is **not finished** just because the command succeeds.

I immediately run:

```bash
terraform plan
```

I want:

```text
No unexpected changes
```

not:

```text
Imported successfully
     ↓
terraform plan
     ↓
"20 attributes changed"
     ↓
terraform apply blindly
```

Suppose the real resource contains:

```text
tags:
  Environment = Production
  Owner       = Platform
```

but my configuration doesn't correctly represent them.

Terraform may propose changes after import.

I must decide whether to:

```text
Update Terraform configuration
```

or intentionally allow Terraform to change the real resource.

---

### **Generating configuration**

Terraform can also generate an initial resource configuration from an `import` block with:

```bash
terraform plan \
  -generate-config-out=generated_resources.tf
```

This can accelerate onboarding existing resources, but HashiCorp describes generated configuration as a starting point that should be reviewed and cleaned up rather than blindly accepted as production-quality HCL. ([HashiCorp Developer][8])

---

### **Import vs data source**

This distinction is frequently asked:

```text
data "azurerm_subnet" ...
        ↓
Read existing subnet
        ↓
Terraform does NOT own it
```

versus:

```text
resource "azurerm_subnet" ...
        +
terraform import
        ↓
Terraform manages it
```

So:

```text
Data source
→ consume existing infrastructure

Import
→ adopt existing infrastructure into Terraform management
```

---

### **Production safety**

For a production resource, I would never do:

```text
terraform import
      ↓
terraform apply immediately
```

My sequence would be:

```text
Import
   ↓
terraform plan
   ↓
Inspect every difference
   ↓
Fix HCL
   ↓
Plan again
   ↓
Expected/no-op plan
   ↓
PR review
   ↓
Normal Terraform management
```

I would also confirm that the object is not already owned by another Terraform state. HashiCorp expects one remote object to be bound to only one Terraform resource address; importing the same Azure object into multiple states can cause conflicting ownership and unsafe behavior. ([HashiCorp Developer][5])

> **In an interview, I would say:**
> “To import an existing Azure resource, I first model it as a Terraform resource, get its Azure resource ID, and bind it to the Terraform resource address using an import block or `terraform import`. Then I run `terraform plan` and carefully reconcile the HCL with the existing resource until there are no unintended changes. Importing establishes Terraform ownership in state; it does not automatically guarantee that my configuration exactly represents the resource.”

**Memory line:**
**Define it → identify it → import it → plan it → reconcile it.**

**Interview trap:**
The biggest mistake is assuming that a successful import means the work is finished. The critical step is the **post-import plan**.

**Keywords:**
`terraform import`, `import` block, Azure resource ID, state, existing resource, reconciliation, `terraform plan`

**Likely follow-ups:**

* Does `terraform import` automatically generate Terraform code?
* What is the difference between importing a resource and using a data source?
* What happens if the imported HCL does not match the existing Azure resource?
* Can the same Azure resource be imported into two Terraform states?
