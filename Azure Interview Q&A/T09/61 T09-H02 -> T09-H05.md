### **T09-H02. What would you do if Terraform state were accidentally deleted?**

**Answer:**
If Terraform state were accidentally deleted, my first action would be to **stop all Terraform applies and prevent anyone from creating a new empty state**. Then I would try to restore the state from the remote backend's recovery mechanisms or a known-good backup. If no trustworthy copy exists, I would reconstruct the state by importing the existing Azure resources rather than allowing Terraform to recreate them.

### **Troubleshooting / recovery flow**

```text
State missing
    ↓
STOP Terraform applies
    ↓
Confirm Azure resources still exist
    ↓
Look for recoverable state
    │
    ├── Azure Blob version / soft-deleted blob
    ├── backend backup
    └── known-good state copy
    ↓
Restore state
    ↓
terraform plan
    ↓
Validate against Azure
```

The most dangerous response would be:

```bash
terraform init
terraform apply
```

against an empty state.

Why?

Terraform could see:

```text
Configuration says:
"Create AKS"

State says:
"AKS doesn't exist"
```

even though AKS actually exists in Azure.

That could result in duplicate-name errors or, depending on the infrastructure, dangerous attempts to recreate resources.

---

### **1. Freeze Terraform changes**

I would temporarily stop:

```text
CI Terraform pipelines
manual terraform apply
terraform destroy
state manipulation
```

until the state situation is understood.

State recovery is one of those situations where I want **one controlled operator**, not multiple people experimenting simultaneously.

---

### **2. Check the remote backend**

If I use Azure Storage for Terraform state, I would check whether the state blob can be recovered through:

* Blob versioning
* Blob soft delete
* snapshots/backups if configured

Azure Blob versioning preserves previous blob versions, and Microsoft recommends using versioning together with soft delete as part of blob-data protection. ([Microsoft Learn][1])

For Terraform state, that means I may have:

```text
prod.tfstate
│
├── current version   ← accidentally deleted/corrupted
├── previous version
├── previous version
└── previous version
```

I would restore the **most recent known-good version**.

---

### **3. Validate the recovered state**

After restoration:

```bash
terraform plan
```

I would inspect the plan carefully.

The goal is ideally:

```text
No unexpected infrastructure changes
```

If Terraform suddenly proposes destroying or recreating many production resources, I would **not apply**. That tells me the recovered state may be stale or inconsistent with the real infrastructure.

---

### **4. If I have a trusted state backup**

Terraform supports manually pushing state:

```bash
terraform state push terraform.tfstate
```

but I would treat this as a recovery operation, not a normal workflow.

HashiCorp warns that `terraform state push` overwrites remote state and should be avoided unless necessary. Terraform also performs lineage and serial checks to help prevent pushing the wrong state. ([HashiCorp Developer][2])

So my flow would be:

```text
Verify backup
    ↓
Verify correct environment/backend
    ↓
Backup anything currently present
    ↓
Restore
    ↓
terraform plan
```

I would not casually use:

```bash
terraform state push -force
```

because bypassing those safety checks can overwrite the wrong state.

---

### **5. If no state backup exists**

Then I would rebuild state from the existing Azure resources.

For example:

```hcl
resource "azurerm_resource_group" "prod" {
  name     = "rg-prod"
  location = "centralindia"
}
```

Then import:

```bash
terraform import \
  azurerm_resource_group.prod \
  "/subscriptions/<sub-id>/resourceGroups/rg-prod"
```

For a large environment:

```text
Inventory Azure resources
       ↓
Match each resource
to Terraform address
       ↓
Import resources
       ↓
terraform plan
       ↓
Reconcile configuration
```

Terraform supports adopting existing infrastructure through import rather than creating it again. ([HashiCorp Developer][3])

---

### **Prevention**

For a production Azure Storage backend, I would design for recovery before this happens:

```text
Azure Storage Backend
│
├── Blob versioning
├── Blob soft delete
├── restricted RBAC
├── separate prod state
└── controlled CI/CD access
```

Microsoft recommends Blob versioning and soft delete together for stronger protection against accidental modification or deletion. ([Microsoft Learn][1])

> **In an interview, I would say:**
> “If Terraform state is deleted, I first stop all Terraform operations so nobody creates a new state or applies against an empty one. I would restore the latest known-good state from Azure Storage versioning, soft delete, or another trusted backup, then run `terraform plan` to verify it against the actual infrastructure. If no state exists, I would reconstruct it by importing the existing Azure resources. I would never blindly run `apply` against an empty state in production.”

**Memory line:**
**Lost state → freeze applies → restore if possible → import if necessary → plan before touching infrastructure.**

**Interview trap:**
The biggest mistake is assuming Terraform will rediscover all existing Azure resources automatically. It will not reconstruct ownership simply because the resources exist.

**Keywords:**
State recovery, Blob versioning, soft delete, `terraform state push`, import, remote backend, recovery

**Likely follow-ups:**

* What if the Azure resources still exist but the state is gone?
* Would `terraform refresh` rebuild a deleted state?
* How would you protect an Azure Terraform backend from state loss?
* When would you use `terraform state push`?

### **T09-H03. What would you do if two pipelines tried to run Terraform simultaneously?**

**Answer:**
If two pipelines target the **same Terraform state**, I want only one of them to be able to modify it at a time. With an Azure Storage backend, Terraform uses state locking, so one pipeline obtains the lock and the other should wait or fail rather than writing concurrently. I would keep that locking enabled and also design CI/CD so production Terraform runs are serialized.

### **How the failure should be contained**

```text
Pipeline A
    ↓
Acquire state lock
    ↓
terraform apply
    ↓
Release lock

Pipeline B
    ↓
Try state lock
    ↓
LOCKED
    ↓
Wait / fail safely
```

Terraform automatically locks state for operations that can write state when the backend supports locking. If it cannot obtain the lock, Terraform does not continue. ([HashiCorp Developer][4])

Azure Storage's Terraform backend supports this by automatically locking the state blob before write operations. ([Microsoft Learn][5])

---

### **What I would do**

#### **1. Determine whether the lock is legitimate**

First:

```text
Lock error
   ↓
Is another Terraform pipeline running?
   │
   ├── Yes → let it complete
   │
   └── No → investigate stale lock
```

I would check:

* CI/CD run history
* GitHub Actions/Azure DevOps jobs
* whether someone is running Terraform manually
* whether a previous runner crashed

---

### **2. Never bypass locking casually**

I would **not** solve this with:

```bash
terraform apply -lock=false
```

HashiCorp explicitly discourages disabling locking because concurrent writers can corrupt or conflict with state. ([HashiCorp Developer][4])

This is especially dangerous:

```text
Pipeline A ──→ modifies VNet ───┐
                                ├──→ same tfstate
Pipeline B ──→ modifies AKS ────┘
```

Even if the resources being changed look different, the pipelines are still writing to the same state object.

---

### **3. Handle a stale lock carefully**

If the previous process crashed and the lock remains, I would first prove no Terraform operation is active.

Only then would I consider:

```bash
terraform force-unlock <LOCK_ID>
```

HashiCorp specifically warns that force-unlocking a state that another process is actually using can create multiple writers. ([HashiCorp Developer][4])

So:

```text
Never:
lock exists
   ↓
force-unlock immediately
```

Instead:

```text
Lock exists
   ↓
Find lock owner/run
   ↓
Confirm operation is dead
   ↓
Force unlock if required
```

---

### **4. Prevent this at pipeline level too**

Backend locking is my last safety layer; CI/CD should also avoid unnecessary concurrency.

For example:

```text
PR #101 ──┐
          ├──→ Terraform production queue
PR #102 ──┘             ↓
                    one apply
                    at a time
```

In GitHub Actions or Azure DevOps, I would configure production deployment concurrency/environment controls so only one production Terraform apply runs against a particular state at once.

A useful pattern is:

```text
Parallel:
fmt
validate
security scan

Potentially parallel:
plans, if carefully isolated

Serialized:
apply to the same state
```

---

### **5. Better isolation with multiple states**

If two teams genuinely need independent Terraform deployments, I would consider splitting infrastructure along sensible boundaries:

```text
network.tfstate
aks.tfstate
database.tfstate
```

instead of placing an entire platform into:

```text
everything.tfstate
```

Then:

```text
Network pipeline
→ network state

AKS pipeline
→ AKS state
```

can run independently when their architectures permit it.

This also reduces blast radius.

### **Important distinction**

There are two separate controls:

```text
Backend locking
→ prevents simultaneous state writes

Pipeline concurrency control
→ prevents multiple runs from competing in the first place
```

I prefer both.

> **In an interview, I would say:**
> “If two pipelines target the same state, the backend lock should allow only one writer. With Azure Storage, Terraform locks the blob automatically for write operations, so I would let the first pipeline finish and have the second queue or fail safely. I would never disable locking to make it pass. At the CI/CD layer I would also serialize applies to the same state, and if different teams require independent deployments, I would consider splitting the state along architectural boundaries.”

**Memory line:**
**Same state = one writer at a time.**

**Interview trap:**
Do not fix concurrent pipelines using `-lock=false`. That removes the protection instead of fixing the concurrency problem.

**Keywords:**
State locking, concurrency, Azure Blob lease/locking, serialization, `force-unlock`, pipeline queue

**Likely follow-ups:**

* What would you do with a stale state lock?
* What does `terraform force-unlock` do?
* Would you allow two `terraform plan` operations simultaneously?
* How can separating state reduce pipeline contention?

### **T09-H04. How would you organize Terraform for dev, staging, and production?**

**Answer:**
For dev, staging, and production, I would reuse the same **versioned Terraform modules**, but give each environment its own root configuration, input values, credentials, and—most importantly—**separate remote state**. Production should have the strongest isolation, RBAC, approvals, and pipeline controls so a dev operation can never accidentally modify production.

HashiCorp's current style guidance recommends separate environment directories and separate state files when using Terraform outside HCP Terraform/Enterprise for this type of environment separation. ([HashiCorp Developer][6])

### **Production structure**

A clean pattern is:

```text
terraform/
│
├── modules/
│   ├── network/
│   ├── aks/
│   ├── acr/
│   └── key-vault/
│
└── environments/
    ├── dev/
    │   ├── main.tf
    │   ├── backend.tf
    │   └── terraform.tfvars
    │
    ├── staging/
    │   ├── main.tf
    │   ├── backend.tf
    │   └── terraform.tfvars
    │
    └── prod/
        ├── main.tf
        ├── backend.tf
        └── terraform.tfvars
```

Each root configuration calls reusable modules.

For example:

```hcl
module "network" {
  source = "../../modules/network"

  environment   = "prod"
  address_space = ["10.30.0.0/16"]
}
```

---

### **Separate state**

This is the most important point.

```text
DEV
 ↓
dev.tfstate

STAGING
 ↓
staging.tfstate

PROD
 ↓
prod.tfstate
```

Not:

```text
dev + staging + prod
        ↓
one giant tfstate
```

Separate state gives me:

* smaller blast radius
* separate locks
* separate RBAC
* safer pipelines
* easier recovery
* independent deployments

HashiCorp notes that separating states reduces the risk of operations unintentionally affecting another environment. ([HashiCorp Developer][7])

---

### **Azure backend example**

Conceptually:

```text
Azure Storage
│
└── tfstate container
    ├── dev/network.tfstate
    ├── staging/network.tfstate
    └── prod/network.tfstate
```

For stronger production isolation, I might go further:

```text
Non-production Storage Account
├── dev
└── staging

Production Storage Account
└── prod
```

That enables tighter Azure RBAC boundaries.

A developer might have:

```text
Dev backend       → allowed
Staging backend   → limited
Prod backend      → denied
```

---

### **Environment-specific authentication**

I would also separate deployment identity.

```text
GitHub Actions
│
├── dev federated identity
│      ↓
│   Dev subscription/RG
│
├── staging federated identity
│      ↓
│   Staging subscription/RG
│
└── prod federated identity
       ↓
    Production subscription/RG
```

The production identity should not simply be the same broad Contributor principal used everywhere.

---

### **Pipeline flow**

A strong Terraform promotion workflow would be:

```text
Git PR
   ↓
terraform fmt
   ↓
terraform validate
   ↓
security checks
   ↓
terraform plan
   ↓
Review
   ↓
DEV apply
   ↓
STAGING apply
   ↓
Production approval
   ↓
PROD plan/apply
```

Production should ideally use:

* branch protection
* required reviews
* environment approval
* workload identity federation/OIDC
* restricted Azure RBAC
* remote state locking

---

### **Environment differences**

I want **shared modules**, but I do not expect dev and prod to have identical capacity.

For example:

```text
           DEV       PROD
AKS nodes    1         3+
SKU        small     production
Zones       maybe     enabled
Backups     basic     strict
Alerts      basic     full
```

Those differences belong in inputs:

```hcl
node_count = 3
sku        = "Premium"
```

rather than copying and rewriting an entire infrastructure codebase.

---

### **Architectural boundaries**

For larger platforms, I may also separate states by layer:

```text
Production
│
├── platform-network.tfstate
├── aks.tfstate
├── database.tfstate
└── monitoring.tfstate
```

This lets infrastructure with different ownership or lifecycle be changed independently.

But I would not split state into hundreds of tiny files unnecessarily, because that increases operational complexity and dependencies between stacks.

### **Why this design**

My priorities are:

```text
Reuse code
     +
Separate state
     +
Separate identity
     +
Separate permissions
     ↓
Environment isolation
```

> **In an interview, I would say:**
> “I would keep reusable infrastructure logic in shared Terraform modules and create separate root configurations for dev, staging, and production. Each environment gets its own remote state, variables, deployment identity, and access controls. I would promote module or configuration changes through dev and staging before production, with production requiring reviewed plans and approvals. The main principle is to reuse code without sharing the blast radius.”

**Memory line:**
**Share modules, not state or production credentials.**

**Interview trap:**
Different `.tfvars` files alone do **not** give strong environment isolation if all environments still share the same state and credentials.

**Keywords:**
Environment isolation, modules, separate state, Azure Storage backend, OIDC, RBAC, promotion, blast radius

**Likely follow-ups:**

* Would you use separate Azure subscriptions for each environment?
* Would you use separate Storage Accounts or just separate state keys?
* How would one Terraform stack consume outputs from another?
* How would you promote a module change safely into production?

### **T09-H05. When should Terraform workspaces be used versus separate state files?**

**Answer:**
Terraform CLI workspaces are useful when I need **multiple instances of essentially the same configuration** and they can safely share the same backend and access model. For strongly isolated environments such as production, especially when credentials, permissions, subscriptions, or architecture differ, I prefer separate root configurations and separate state/backend boundaries.

HashiCorp specifically cautions that CLI workspaces are not a suitable isolation mechanism when deployments require different credentials or access controls because those workspaces share the same backend configuration. ([HashiCorp Developer][8])

### **First, what a CLI workspace actually does**

With the same Terraform directory:

```bash
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod
```

Terraform keeps separate state for each workspace:

```text
Same Terraform Configuration
          │
          ├── workspace: dev
          │       ↓
          │   dev state
          │
          ├── workspace: staging
          │       ↓
          │   staging state
          │
          └── workspace: prod
                  ↓
              prod state
```

HashiCorp describes CLI workspaces as separate instances of state associated with the same Terraform working directory and backend. ([HashiCorp Developer][8])

You can reference the active workspace:

```hcl
terraform.workspace
```

but I would avoid building a huge amount of conditional architecture around it.

---

### **When I would use workspaces**

CLI workspaces are reasonable when the environments are highly similar.

For example:

```text
Developer sandbox A
Developer sandbox B
Developer sandbox C
```

or short-lived test environments:

```text
Same module
Same backend
Same security model
Same topology

Only:
name / sizing / values differ
```

Example:

```text
workspace: feature-101
workspace: feature-102
workspace: feature-103
```

That can be convenient.

---

### **When I prefer separate states/configurations**

For:

```text
DEV
STAGING
PRODUCTION
```

I normally prefer:

```text
environments/
├── dev/
│      └── backend → dev state
│
├── staging/
│      └── backend → staging state
│
└── prod/
       └── backend → prod state
```

especially if they differ in:

* Azure subscriptions
* RBAC
* identities
* network design
* production approval requirements
* state access
* security controls
* architecture

HashiCorp's current guidance for Terraform outside HCP Terraform recommends modules plus per-environment directories with separate state where this stronger separation is needed. ([HashiCorp Developer][6])

---

### **The security reason**

Imagine:

```text
One backend
│
├── dev workspace
├── staging workspace
└── prod workspace
```

A principal that can access that backend may have access to more environment state than I want.

Production state can contain sensitive infrastructure information.

Instead:

```text
Developer identity
     ↓
Dev backend only

Production pipeline identity
     ↓
Prod backend only
```

provides a much cleaner security boundary.

---

### **The operational-risk reason**

With CLI workspaces, an engineer must always know which workspace is selected:

```bash
terraform workspace show
```

Imagine:

```text
Engineer thinks:
workspace = staging

Actual:
workspace = prod

terraform apply
```

That is an avoidable production risk.

For disposable environments this may be acceptable.

For critical production infrastructure, I prefer the target environment to be obvious from:

```text
working directory
backend
pipeline
identity
subscription
```

rather than relying primarily on the currently selected workspace.

---

### **Comparison**

| Requirement                   | CLI workspaces                 | Separate configurations/state |
| ----------------------------- | ------------------------------ | ----------------------------- |
| Same Terraform configuration  | Excellent                      | Excellent via modules         |
| Separate state                | Yes                            | Yes                           |
| Same backend                  | Generally yes                  | Can be completely separate    |
| Different credentials         | Awkward / poor isolation       | Strong                        |
| Different Azure subscriptions | Possible, but easier to misuse | Cleaner                       |
| Different architectures       | Can become conditional-heavy   | Better                        |
| Temporary environments        | Very useful                    | Often excessive               |
| Production isolation          | Usually weaker                 | Preferred                     |

### **One important terminology trap**

There are two different concepts:

```text
Terraform CLI workspace
```

and:

```text
HCP Terraform workspace
```

They are **not the same abstraction**.

A CLI workspace is mainly multiple state instances for one working directory/backend.

An HCP Terraform workspace has its own configuration association, state, variables, run history, and settings. HashiCorp explicitly distinguishes these two concepts. ([HashiCorp Developer][8])

---

### **Production decision**

My practical rule would be:

```text
Same infrastructure
+ same trust boundary
+ temporary/similar environments
        ↓
CLI workspace can make sense
```

But:

```text
Different subscriptions
or
different credentials
or
production isolation
or
meaningful architectural differences
        ↓
Separate configuration + backend/state
```

> **In an interview, I would say:**
> “I use CLI workspaces when I need several nearly identical instances of the same Terraform configuration and they can safely share the same backend and security boundary, such as developer or ephemeral environments. For dev, staging, and especially production where credentials, RBAC, subscriptions, or architecture may differ, I prefer separate root configurations and remote states. That gives stronger isolation and reduces the risk of accidentally applying against production.”

**Memory line:**
**Workspaces separate state; separate backends/configurations separate trust boundaries.**

**Interview trap:**
Do not say Terraform CLI workspaces provide complete security isolation between dev and production. They still share the configuration's backend context and are not designed to solve environments requiring distinct access controls. ([HashiCorp Developer][8])

**Keywords:**
CLI workspace, separate state, backend, environment isolation, trust boundary, HCP Terraform workspace

**Likely follow-ups:**

* Are Terraform CLI workspaces the same as HCP Terraform workspaces?
* Can two workspaces share one backend?
* Why might workspaces be risky for production?
* When are workspaces a good fit?
