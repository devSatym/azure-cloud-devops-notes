### **T09-H10. How would you design reusable Terraform modules for multiple Azure subscriptions?**

**Answer:**
I would make the Terraform modules **subscription-agnostic**: modules define reusable infrastructure such as VNets, AKS, ACR, or Key Vault, while the **root module owns provider configuration, authentication, subscription selection, state, and environment-specific values**. For deployments spanning multiple subscriptions, I would configure multiple AzureRM provider instances with aliases and explicitly pass the appropriate provider into each module.

### **Architecture**

```text
Root Configuration
│
├── AzureRM Provider → Platform Subscription
├── AzureRM Provider → Dev Subscription
└── AzureRM Provider → Prod Subscription
        │
        ↓
Reusable Modules
├── network/
├── aks/
├── acr/
└── key-vault/
```

The reusable module should care about:

```text
Inputs
→ resource names
→ location
→ CIDRs
→ SKUs
→ tags

Resources
→ VNet
→ subnets
→ AKS
→ etc.

Outputs
→ resource IDs
→ subnet IDs
→ endpoints
```

It should generally **not hard-code**:

```text
subscription IDs
tenant IDs
environment names
credentials
```

---

### **Provider configuration belongs at the root**

For example:

```hcl
provider "azurerm" {
  features {}

  subscription_id = var.dev_subscription_id
}

provider "azurerm" {
  alias           = "prod"
  features        = {}
  subscription_id = var.prod_subscription_id
}
```

Then:

```hcl
module "dev_network" {
  source = "./modules/network"

  providers = {
    azurerm = azurerm
  }

  name          = "vnet-dev"
  address_space = ["10.10.0.0/16"]
}
```

and:

```hcl
module "prod_network" {
  source = "./modules/network"

  providers = {
    azurerm = azurerm.prod
  }

  name          = "vnet-prod"
  address_space = ["10.20.0.0/16"]
}
```

Terraform supports multiple configurations of the same provider through **provider aliases**, and those configurations can be explicitly passed into child modules. ([HashiCorp Developer][1])

Conceptually:

```text
Same network module
       │
       ├── azurerm.dev
       │      ↓
       │   Dev Subscription
       │
       └── azurerm.prod
              ↓
          Prod Subscription
```

---

### **Why I don't configure subscriptions inside reusable modules**

Suppose my module contains:

```text
subscription_id = "123..."
```

Now that module is tied to one environment.

Instead:

```text
Root module
→ decides WHERE

Child module
→ decides WHAT to build
```

That separation makes the same module reusable across:

```text
Subscription A
Subscription B
Subscription C
```

without modifying the module itself.

Reusable child modules can inherit provider configurations from their caller, while aliases can be explicitly mapped where required. ([HashiCorp Developer][2])

---

### **State design**

I would also avoid putting hundreds of subscriptions into one Terraform state.

For example:

```text
Azure Storage Backend
│
├── platform-prod.tfstate
├── app1-prod.tfstate
├── app2-prod.tfstate
└── shared-network.tfstate
```

or:

```text
Subscription: Dev
   ↓
dev state

Subscription: Staging
   ↓
staging state

Subscription: Prod
   ↓
prod state
```

The exact split depends on ownership and lifecycle, but my goal is:

```text
smaller blast radius
+
independent locking
+
clear ownership
+
separate permissions
```

---

### **Authentication**

For CI/CD, I would also separate identities where appropriate:

```text
GitHub Actions
│
├── Dev OIDC Identity
│       ↓
│   Dev Subscription
│
└── Prod OIDC Identity
        ↓
    Prod Subscription
```

rather than giving one automation identity unrestricted access to every subscription.

---

### **Module versioning**

For centrally maintained modules, I would version them:

```hcl
module "network" {
  source = "git::https://github.com/org/tf-network.git?ref=v2.3.0"
}
```

or consume them through a private/public Terraform registry.

That gives:

```text
Module v2.3.0
     ↓
Dev testing
     ↓
Staging
     ↓
Production adoption
```

instead of every environment automatically picking up an untested module change.

---

### **Important distinction**

There are two different types of reuse:

```text
Module reuse
→ same infrastructure pattern

State sharing
→ same Terraform ownership boundary
```

Reusable modules do **not** require shared state.

In fact, a good design often has:

```text
Same module
+
many independent states
```

> **In an interview, I would say:**
> “I design reusable modules to be subscription-agnostic. The child module defines the infrastructure pattern, while root configurations handle Azure subscriptions, authentication, provider configuration, state, and environment inputs. If a deployment spans subscriptions, I use AzureRM provider aliases and pass the correct provider configuration into each module. I also keep sensible state boundaries and usually use separately scoped CI identities so reuse does not increase blast radius.”

**Memory line:**
**Root decides where to deploy; module defines what to deploy.**

**Interview trap:**
Do not hard-code subscription IDs or credentials inside reusable modules. Also, **module reuse does not mean state reuse**.

**Keywords:**
Modules, provider aliases, `providers`, root module, child module, multiple subscriptions, state isolation, module versioning

**Likely follow-ups:**

* Should provider blocks be placed inside reusable child modules?
* How would one Terraform deployment manage resources in two subscriptions?
* Would you keep all subscriptions in one Terraform state?
* How would you version internal Terraform modules?

### **T09-H11. How would you prevent secrets from leaking into Terraform state?**

**Answer:**
My first principle is to **avoid making Terraform handle secret values unless Terraform genuinely needs them**. I prefer workload identity, managed identity, and references to systems like Azure Key Vault over passing raw passwords through Terraform. If Terraform must handle a sensitive value, I use Terraform's sensitive-data controls where supported and treat the remote state itself as highly sensitive because simply marking a value `sensitive` does **not** remove it from state. ([HashiCorp Developer][3])

### **The key problem**

Suppose I write:

```hcl
variable "database_password" {
  type      = string
  sensitive = true
}
```

and use it in a resource.

Terraform may display:

```text
password = (sensitive value)
```

instead of printing the password.

But:

```text
sensitive = true
       ↓
redacts CLI output

NOT necessarily
       ↓
removes value from state
```

HashiCorp explicitly states that sensitive values can still exist in state and plan files. ([HashiCorp Developer][3])

---

### **My preferred design: don't create the secret problem**

For Azure workloads, instead of:

```text
Application
    ↓
Terraform-managed client secret
    ↓
Azure resource
```

I prefer:

```text
Application / AKS Pod
       ↓
Managed Identity /
Workload Identity
       ↓
Microsoft Entra ID
       ↓
Azure Resource
```

This completely removes many passwords and client secrets from the architecture.

For CI/CD:

```text
GitHub Actions
      ↓
OIDC
      ↓
Entra ID
```

rather than storing:

```text
ARM_CLIENT_SECRET
```

---

### **Use Key Vault without unnecessarily reading secrets into Terraform**

A good design might be:

```text
Terraform
    ↓
creates Key Vault
    ↓
creates RBAC / access relationship

Application
    ↓
Managed Identity
    ↓
reads secret directly from Key Vault
```

Terraform doesn't need to know the secret value merely because the application uses it.

I would avoid patterns where Terraform reads a secret value just so it can pass that same secret elsewhere unless there is a real requirement.

---

### **Modern Terraform options**

Current Terraform also supports mechanisms that can prevent selected runtime values from being persisted.

For example, Terraform 1.10 introduced **ephemeral values**, which can be omitted from state and plan files:

```hcl
variable "database_password" {
  type      = string
  sensitive = true
  ephemeral = true
}
```

Terraform 1.11 also introduced **write-only resource arguments**, where supported by the specific provider/resource. ([HashiCorp Developer][3])

The important caveat is:

```text
Terraform language supports it
        ≠
every AzureRM resource argument supports it
```

So I would verify provider/resource support before relying on this design.

---

### **Protect state anyway**

Some sensitive infrastructure information may still be unavoidable in state.

Therefore:

```text
Terraform
    ↓
Remote Azure Storage Backend
    ↓
Restricted access
```

and I would use:

* Azure RBAC with least privilege
* encryption at rest
* secure transport
* state versioning/recovery
* audit logging
* no `.tfstate` in Git
* separate production backend permissions

HashiCorp recommends remote state, encryption, access controls, and auditing where state contains sensitive information. ([HashiCorp Developer][3])

---

### **Production pattern**

```text
Bad
─────────────────────────────

GitHub Secret
     ↓
Database Password
     ↓
Terraform variable
     ↓
Terraform state
     ↓
Application


Better where possible
─────────────────────────────

Application
     ↓
Managed Identity
     ↓
Key Vault / Azure Service
```

The safest secret is often the one that **doesn't need to exist as a long-lived secret at all**.

---

### **What I would check for leakage**

Before production, I would review:

```text
.tf files
.tfvars files
CI logs
Terraform plan artifacts
Terraform outputs
Terraform state access
Git history
```

I would also make sure:

```text
*.tfstate
*.tfstate.*
```

are excluded from Git workflows.

---

### **Important distinction**

```text
sensitive = true
→ hides normal presentation
```

versus:

```text
ephemeral / supported write-only argument
→ can prevent supported values from being persisted
```

versus:

```text
remote encrypted state
→ protects stored state
```

These solve different problems.

> **In an interview, I would say:**
> “The best way to prevent secrets leaking into Terraform state is to avoid putting raw secrets through Terraform in the first place. On Azure I prefer managed identities, workload identity and Key Vault so workloads retrieve credentials directly. Marking a Terraform variable `sensitive` only redacts it from normal output; it can still exist in state. For values Terraform must handle, I use supported ephemeral or write-only mechanisms where available, and I always treat remote state as sensitive data protected with encryption, RBAC and auditing.”

**Memory line:**
**`sensitive` hides a secret; it does not automatically remove it from state.**

**Interview trap:**
A very common wrong answer is: **“Just mark the variable `sensitive = true`.”** That mainly addresses display, not state persistence.

**Keywords:**
Sensitive values, ephemeral, write-only arguments, Key Vault, Managed Identity, Workload Identity, remote state, RBAC

**Likely follow-ups:**

* Does `sensitive = true` encrypt a Terraform value?
* Can Terraform state contain passwords?
* How would an AKS application obtain a secret without Terraform storing it?
* How would you secure an Azure Storage state backend?

### **T09-H12. What is the AzAPI provider and when might you use it alongside AzureRM?**

**Answer:**
The **AzAPI provider** is an official Terraform provider for Azure that works close to the Azure Resource Manager REST API. I normally use **AzureRM as my primary provider**, because it offers curated Terraform resources and strong schemas, and use AzAPI when I need an Azure resource, property, API version, or preview capability that AzureRM does not yet expose. Microsoft currently recommends this AzureRM-first, AzAPI-when-needed strategy for most teams. ([Microsoft Learn][4])

### **Why two providers exist**

Conceptually:

```text
Terraform
│
├── AzureRM Provider
│       ↓
│   Curated Terraform resource model
│       ↓
│   Azure
│
└── AzAPI Provider
        ↓
    ARM REST API
        ↓
      Azure
```

AzureRM might give me something like:

```hcl
resource "azurerm_resource_group" "main" {
  name     = "rg-prod"
  location = "centralindia"
}
```

It provides a strongly modeled Terraform interface.

AzAPI operates more directly against Azure ARM resource types and API versions.

---

### **When I would use AzureRM**

My default is AzureRM when:

```text
Azure resource
     ↓
fully supported by AzureRM
     ↓
Use AzureRM
```

because it provides:

* typed resource schemas
* provider validation
* familiar Terraform resource blocks
* mature documentation/examples
* common community/module support

Microsoft describes AzureRM as the normal default for established Azure services. ([Microsoft Learn][4])

---

### **When I would add AzAPI**

Suppose Microsoft introduces:

```text
New Azure feature
      ↓
ARM API supports it
      ↓
AzureRM provider does not yet expose it
```

I don't necessarily need to wait for AzureRM support.

I can use:

```text
AzAPI
    ↓
specific Azure API version
    ↓
new capability
```

Typical reasons include:

1. **New Azure resource type not yet supported by AzureRM**
2. **New resource property not yet exposed by AzureRM**
3. **Specific ARM API version required**
4. **Preview Azure capability**
5. Advanced scenarios needing closer ARM API control

AzAPI can target Azure resource types and API versions more directly, including capabilities that have not yet reached AzureRM. ([Microsoft Learn][4])

---

### **Using them together**

A real configuration can contain both:

```text
Terraform
│
├── AzureRM
│   ├── Resource Group
│   ├── VNet
│   ├── AKS
│   └── Key Vault
│
└── AzAPI
    └── new/unsupported Azure capability
```

For example:

```hcl
terraform {
  required_providers {
    azurerm = {
      source = "hashicorp/azurerm"
    }

    azapi = {
      source = "Azure/azapi"
    }
  }
}
```

I would not replace all working AzureRM resources with AzAPI merely because AzAPI is more flexible.

---

### **Why not always use AzAPI?**

Because flexibility has a trade-off.

```text
AzureRM
→ more abstraction
→ curated schema
→ easier validation
→ easier maintenance

AzAPI
→ closer ARM access
→ broader/newer API coverage
→ potentially more Azure API knowledge required
```

Microsoft's current guidance is that **most teams should start with AzureRM and supplement it with AzAPI when needed**. ([Microsoft Learn][4])

---

### **Migration later**

Suppose:

```text
Today:
Feature supported only by AzAPI
```

Later:

```text
AzureRM adds native support
```

I would evaluate migrating that resource to AzureRM so the long-term configuration can use the standard curated provider where appropriate.

The key is to perform the migration **without accidentally recreating the production Azure resource**.

---

### **Important distinction**

AzAPI is **not a replacement for ARM itself**.

It is:

```text
Terraform provider
      ↓
exposes Azure ARM APIs
```

Also:

```text
AzureRM
≠ Azure Resource Manager
```

`AzureRM` here refers to the Terraform provider, while **Azure Resource Manager** is Azure's management platform/API layer.

> **In an interview, I would say:**
> “AzAPI is an official Terraform provider that exposes Azure Resource Manager APIs more directly. I use AzureRM as the primary provider because it gives curated, strongly modeled Terraform resources, but if Azure releases a resource, property, preview feature, or API version that AzureRM doesn't support yet, I can use AzAPI alongside it. Once stable AzureRM support becomes available, I would consider migrating back to the native AzureRM resource.”

**Memory line:**
**AzureRM for the normal path; AzAPI for Azure capabilities AzureRM hasn't caught up with yet.**

**Interview trap:**
Do not say AzAPI should replace AzureRM everywhere. Microsoft currently recommends AzureRM as the normal default for most teams. ([Microsoft Learn][4])

**Keywords:**
AzAPI, AzureRM, ARM REST API, API version, preview feature, unsupported resource, Terraform provider

**Likely follow-ups:**

* Why wouldn't you just use AzAPI for every Azure resource?
* Can AzureRM and AzAPI be used in the same Terraform configuration?
* What happens when AzureRM later supports the feature?
* What is the difference between AzureRM and Azure Resource Manager?

### **T10-E01. What is Azure Monitor?**

**Answer:**
Azure Monitor is Microsoft's **unified observability service** for collecting, analyzing, visualizing, and acting on telemetry from applications and infrastructure. It brings together signals such as **metrics, logs, traces, and events** so I can monitor health and performance, troubleshoot issues, create dashboards, and trigger alerts. ([Microsoft Learn][5])

For example:

```text
AKS / VMs / Applications / Azure Services
                 ↓
            Azure Monitor
                 ↓
        Metrics / Logs / Traces
                 ↓
      Analysis / Dashboards / Alerts
```

For logs, Azure Monitor integrates with **Log Analytics and KQL**; Application Insights provides application-level observability, while alerts can notify teams or trigger automated actions. ([Microsoft Learn][6])

**Memory line:**
**Azure Monitor collects telemetry, helps you understand it, and lets you act on it.**

**Interview trap:**
Azure Monitor is the **umbrella observability service**. Log Analytics and Application Insights are related capabilities within the broader Azure Monitor ecosystem; they are not interchangeable names for Azure Monitor itself.

**Keywords:**
Azure Monitor, metrics, logs, traces, telemetry, Log Analytics, Application Insights, alerts
