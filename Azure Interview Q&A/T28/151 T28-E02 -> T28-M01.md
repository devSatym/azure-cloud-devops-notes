# **T28-E02. What is an Automation Account?**

**Answer:**

An Automation Account is the **Azure resource that acts as the container and security boundary for Azure Automation capabilities**. It holds things such as runbooks, schedules, modules, variables, credentials or connections, job history, and Managed Identities used by automation.

For example, I might create an Automation Account called `aa-platform-prod`, assign it a system-assigned Managed Identity, give that identity only the Azure RBAC permissions required to manage selected VMs, and then run scheduled PowerShell runbooks from it.

```text
Automation Account
│
├── Managed Identity
├── Runbooks
├── Schedules
├── Modules / Packages
├── Variables / Assets
└── Jobs
       ↓
Azure Resources
```

Microsoft recommends Managed Identity for Automation runbooks because the Azure platform manages the identity and its credentials, removing the need to maintain authentication secrets manually. ([Microsoft Learn][1])

---

## **Think of it as the automation workspace**

An Automation Account is not itself the script.

Instead:

```text
Automation Account
       ↓
contains
       ↓
Runbook
       ↓
execution creates
       ↓
Job
```

So:

```text
Automation Account
≠
Runbook
```

The Automation Account is the parent Azure resource in which automation components live.

---

## **Example**

Suppose I need to stop Dev VMs every evening.

I could have:

```text
Automation Account
aa-nonprod-ops
│
├── System-assigned Managed Identity
│
├── Runbook: Stop-DevVMs
│
├── Schedule: 8 PM daily
│
└── Job history
```

RBAC:

```text
aa-nonprod-ops Managed Identity
          ↓
Required VM-management permissions
          ↓
NonProd resource group only
```

I would **not** normally give it:

```text
Owner
at subscription scope
```

when the automation only operates on a few nonproduction VMs.

---

## **Identity is important**

A secure flow is:

```text
Runbook
   ↓
Automation Account Managed Identity
   ↓
Microsoft Entra ID
   ↓
Azure RBAC
   ↓
Target Azure Resource
```

For example, PowerShell inside the runbook could authenticate using:

```powershell
Connect-AzAccount -Identity
```

rather than retrieving an Azure username/password.

Azure Automation currently supports system-assigned and user-assigned Managed Identity scenarios, and Microsoft positions Managed Identity as the recommended authentication method for runbooks. ([Microsoft Learn][1])

---

## **Automation Account vs Azure Automation**

Another useful distinction:

```text
Azure Automation
→ Azure service

Automation Account
→ resource you create inside that service
```

Similar mental model:

```text
Azure Storage
→ service

Storage Account
→ resource instance
```

---

## **Automation Account vs runbook**

```text
Automation Account
→ container / identity / automation context

Runbook
→ executable automation logic
```

For example:

```text
aa-platform
├── Stop-VMs.ps1
├── Start-VMs.ps1
└── Cleanup-Resources.py
```

Each script/workflow is a runbook inside the Automation Account.

---

**Memory line:**
**The Automation Account is the home and security context; runbooks are the automation that executes inside it.**

**Interview trap:**
An Automation Account is **not the runbook itself**—it hosts runbooks, identities, schedules, assets, and job execution information.

**Keywords:**
Automation Account, Azure Automation, Managed Identity, runbook, schedule, job, modules, Azure RBAC.

# **T28-E03. What is an Azure Automation runbook?**

**Answer:**

An Azure Automation runbook is an **executable automation workflow** hosted by Azure Automation that performs operational tasks, such as starting or stopping VMs, cleaning up resources, querying Azure, or performing recurring maintenance.

A runbook can contain PowerShell or Python automation logic, and it can execute either in the Azure Automation cloud environment or through a Hybrid Runbook Worker when the automation needs access to private or on-premises systems.

```text
Trigger / Schedule
       ↓
Runbook
       ↓
PowerShell / Python logic
       ↓
Managed Identity
       ↓
Azure API
       ↓
Operational task
```

Current Azure Automation documentation recommends PowerShell and Python for textual automation and also supports graphical and legacy PowerShell Workflow runbook types. ([Microsoft Learn][2])

---

## **Example runbook**

Suppose I want to stop Dev VMs.

Conceptually:

```powershell
Connect-AzAccount -Identity

Get-AzVM |
Where-Object {
    $_.Tags["Environment"] -eq "Dev"
} |
Stop-AzVM
```

The real production version would include:

* explicit subscription/resource scope,
* exclusion logic,
* error handling,
* logging,
* validation.

The flow is:

```text
Runbook starts
    ↓
Authenticate
    ↓
Find target resources
    ↓
Perform operation
    ↓
Validate result
    ↓
Job completes
```

---

## **A runbook execution becomes a job**

Important terminology:

```text
Runbook
→ definition/code

Job
→ one execution of that runbook
```

Example:

```text
Runbook:
Stop-DevVMs

Jobs:
2026-09-01 20:00 → Succeeded
2026-09-02 20:00 → Succeeded
2026-09-03 20:00 → Failed
```

This job history helps with troubleshooting.

---

## **How can a runbook start?**

A runbook can be launched:

```text
Manually
Schedule
Another automation/process
Operational integration
```

For example:

```text
Daily schedule
      ↓
Runbook
      ↓
Stop nonproduction VMs
```

or:

```text
Azure alert
    ↓
Automation workflow
    ↓
Remediation action
```

---

## **Cloud execution vs Hybrid Runbook Worker**

Normal cloud execution:

```text
Azure Automation
      ↓
Azure-hosted execution
      ↓
Azure APIs
```

But suppose the runbook needs to reach:

```text
10.10.20.15
```

inside an on-premises network that isn't reachable from the Azure Automation sandbox.

Then:

```text
Azure Automation
      ↓
Hybrid Runbook Worker
      ↓
Private/on-prem network
      ↓
Internal server
```

A Hybrid Runbook Worker lets Automation execute the runbook from a machine that has the required local/private connectivity. ([Microsoft Learn][3])

---

## **Security**

The runbook should not normally contain:

```powershell
$username = "admin"
$password = "Password123"
```

For Azure-resource operations, prefer:

```text
Managed Identity
      ↓
Azure RBAC
```

and grant only the required permissions.

---

**Memory line:**
**A runbook is the executable operational workflow; every time it runs, Azure Automation creates a job.**

**Interview trap:**
A runbook running successfully in Azure doesn't mean it can automatically reach private/on-premises resources; those may require a Hybrid Runbook Worker and network connectivity.

**Keywords:**
Runbook, PowerShell, Python, job, schedule, Hybrid Runbook Worker, Managed Identity, automation workflow.

# **T28-E04. What is Azure Update Manager?**

**Answer:**

Azure Update Manager is Azure's centralized service for **assessing, monitoring, scheduling, and installing operating-system updates** on Windows and Linux machines.

It supports Azure VMs as well as Azure Arc-enabled servers, so the same service can manage patch compliance across Azure, on-premises, and other clouds connected through Azure Arc.

It can show which machines are missing updates, perform one-time patching, or schedule recurring patch deployments within defined maintenance windows. ([Microsoft Learn][4])

```text
Azure Update Manager
        ↓
Update assessment
        ↓
Which patches are missing?
        ↓
Maintenance schedule
        ↓
Install updates
        ↓
Reboot if required
        ↓
Compliance result
```

---

## **What problem does it solve?**

Imagine:

```text
200 VMs
├── Windows
├── Linux
├── Azure VMs
└── Arc-enabled servers
```

Checking each machine individually would be difficult.

Update Manager gives a centralized view:

```text
All machines
     ↓
Update Manager
     ↓
Compliant / missing updates
     ↓
Scheduled remediation
```

---

## **Main capabilities**

Azure Update Manager currently supports:

```text
Update assessment
      ↓
Which patches are missing?

One-time update
      ↓
Patch now

Scheduled patching
      ↓
Patch during maintenance window

Compliance reporting
      ↓
Which machines remain out of date?
```

It supports both Windows and Linux machines. ([Microsoft Learn][4])

---

## **Scheduled patching**

For controlled production patching:

```text
Maintenance Configuration
        ↓
Approved maintenance window
        ↓
Selected VM group
        ↓
Security/Critical updates
        ↓
Install
        ↓
Reboot behavior
```

Azure Update Manager uses **Maintenance Configurations** for recurring scheduled patching. Microsoft currently recommends `Customer Managed Schedules` for Azure VMs when scheduled patching is required. ([Microsoft Learn][5])

---

## **Current architectural distinction**

This is worth remembering because older Azure material may say otherwise.

Azure Update Manager is a native Azure service and **does not depend on an Azure Automation Account and Log Analytics workspace in the way the older Automation Update Management solution did**. ([Microsoft Learn][4])

So:

```text
Current:
Azure Update Manager
      ↓
native Azure/Arc VM patch management
```

Do not describe it as:

```text
"just a runbook inside Azure Automation"
```

because that is incorrect.

---

## **How it works at a high level**

When Update Manager performs operations such as assessment or installation, Azure uses the relevant VM/Arc extension to interact with the machine and its native update mechanisms. ([Microsoft Learn][6])

Conceptually:

```text
Azure Update Manager
       ↓
VM / Arc extension
       ↓
Guest operating system
       ↓
Windows/Linux update mechanism
       ↓
Patch installation
```

Update Manager orchestrates patching; it isn't simply a giant repository that replaces the OS's normal update mechanism.

---

## **Update Manager vs Azure Automation**

```text
Azure Automation
→ general-purpose operational automation

Azure Update Manager
→ specialized VM/server patch-management service
```

For example:

```text
Stop Dev VMs nightly
→ Azure Automation

Patch 100 production Linux/Windows VMs
→ Azure Update Manager
```

---

**Memory line:**
**Azure Update Manager centrally assesses and orchestrates OS patching for Azure VMs and Arc-enabled servers.**

**Interview trap:**
Current Azure Update Manager does **not require Azure Automation and Log Analytics** like the older Automation Update Management solution did.

**Keywords:**
Azure Update Manager, patching, update assessment, Windows, Linux, Azure Arc, Maintenance Configuration, maintenance window, compliance.

# **T28-M01. What types of tasks are suitable for Azure Automation?**

**Answer:**

Azure Automation is best suited to **repeatable, deterministic operational tasks** that can be expressed as PowerShell or Python logic and that benefit from scheduling, centralized execution, job history, and workload identity.

Good examples include stopping and starting nonproduction VMs, recurring cleanup operations, resource inventory, certificate or operational housekeeping, remediation triggered by alerts, and tasks that need to run inside a private environment through a Hybrid Runbook Worker.

I would not automatically use Azure Automation for every Azure task. Infrastructure provisioning that defines persistent desired state generally belongs in Bicep or Terraform, CI/CD belongs in GitHub Actions or Azure Pipelines, and VM OS patch orchestration is better handled by Azure Update Manager.

```text
What kind of task?
      ↓
Repeated operational action?
      ↓ Yes
Azure Automation

Desired infrastructure state?
      ↓
Terraform / Bicep

Application build/deployment?
      ↓
CI/CD

OS patch management?
      ↓
Azure Update Manager
```

---

## **1. Scheduled operational tasks**

This is one of the strongest use cases.

Example:

```text
Every weekday 8 PM
       ↓
Runbook
       ↓
Find VMs:
Environment = Dev
       ↓
Stop VMs
```

Then:

```text
Every weekday 7 AM
       ↓
Runbook
       ↓
Start required Dev VMs
```

This reduces unnecessary cost without requiring someone to perform the task manually.

---

## **2. Repetitive housekeeping**

Examples:

```text
Find stale test resources
Generate resource inventory
Clean old temporary resources
Validate resource tags
Check certificate expiration
Perform recurring configuration checks
```

The key property is:

```text
Same well-defined process
      ↓
repeated many times
```

That's where automation gives strong value.

---

## **3. Alert-driven remediation**

Suppose Azure Monitor detects:

```text
Operational condition
       ↓
Alert
       ↓
Automation
       ↓
Runbook
       ↓
Safe remediation
```

For example:

```text
Known service condition
      ↓
Runbook checks current state
      ↓
performs bounded remediation
      ↓
verifies service state
```

The critical word is **safe**.

I would not build:

```text
Any alert
   ↓
blindly restart everything
```

The runbook should first confirm that the condition matches the remediation scenario.

---

## **4. Multi-resource operational actions**

Suppose I need to:

```text
Find all Dev VMs
      ↓
filter by tag
      ↓
stop eligible VMs
      ↓
verify power state
      ↓
report failures
```

That's a good automation workflow because there are multiple operational steps and decision logic.

---

## **5. Cross-subscription operations**

Automation can also be useful for inventory or maintenance across several subscriptions if the Managed Identity has the required RBAC.

For example:

```text
Automation identity
        ↓
Subscription A → Reader
Subscription B → Reader
Subscription C → Reader
        ↓
Generate inventory report
```

But I'd explicitly control which subscriptions are in scope rather than simply operating on everything the identity can see.

---

## **6. Hybrid/on-premises tasks**

Azure Automation can run workloads using a **Hybrid Runbook Worker**, allowing automation to execute from an environment with connectivity to private or on-premises systems. ([Microsoft Learn][7])

Example:

```text
Azure Automation
       ↓
Hybrid Runbook Worker
       ↓
Corporate network
       ↓
Internal Windows Server
```

This can be useful for operations that cannot be performed from Azure Automation's cloud execution environment.

---

# **What I would NOT use Azure Automation for**

Understanding the boundaries makes the interview answer much stronger.

---

## **Persistent infrastructure provisioning**

If my requirement is:

> “These 3 VNets, AKS, ACR and Key Vault resources must always be defined this way.”

I'd choose:

```text
Terraform
or
Bicep
```

because that's desired-state Infrastructure as Code.

Not:

```text
2,000-line PowerShell runbook
creating the whole platform manually
```

Azure Automation can invoke deployments, but it shouldn't replace a proper IaC model without a good reason.

---

## **Application CI/CD**

Requirement:

```text
Git commit
   ↓
Build
   ↓
Test
   ↓
Container
   ↓
Deploy
```

belongs naturally in:

```text
GitHub Actions
or
Azure Pipelines
```

not Azure Automation.

---

## **VM patch management**

I would not build my own massive patching runbook if Azure Update Manager already provides:

* assessment,
* scheduled patching,
* compliance,
* Azure/Arc support,
* maintenance-window integration. ([Microsoft Learn][4])

So:

```text
VM OS patching
→ Azure Update Manager
```

rather than reinventing patch orchestration with Automation.

---

# **Production design principles**

For a good Automation workload I would expect:

```text
Deterministic target selection
        ↓
Managed Identity
        ↓
Least-privilege RBAC
        ↓
Idempotent/safe runbook
        ↓
Logging/job history
        ↓
Validation
```

---

## **Example: safe VM shutdown**

Bad:

```text
List every VM
     ↓
Stop all
```

Better:

```text
Explicit subscription
      ↓
NonProd resource groups
      ↓
Environment=Dev tag
      ↓
AutoShutdown=true tag
      ↓
Exclude protected resources
      ↓
Stop
      ↓
Verify
```

That prevents automation from becoming a large blast-radius mechanism.

---

## **Runbook safety matters**

Automation magnifies both good and bad logic.

A manual mistake might affect:

```text
1 resource
```

A bad automation runbook might affect:

```text
500 resources
in 30 seconds
```

So I would include:

* scope checks,
* parameter validation,
* dry-run capability where practical,
* exclusion lists,
* clear logging,
* error handling,
* least privilege.

---

## **Managed Identity**

For Azure-resource automation:

```text
Automation Account
       ↓
Managed Identity
       ↓
Azure RBAC
       ↓
specific target scope
```

is preferable to embedding credentials. Microsoft recommends Managed Identities as the authentication model for Azure Automation runbooks. ([Microsoft Learn][1])

For example:

```text
Stop-DevVMs automation identity
        ↓
VM-management permission
        ↓
NonProd RG
```

instead of:

```text
Owner
at subscription
```

---

### **Interview answer condensed**

> “I use Azure Automation for repetitive operational processes that benefit from centralized execution, schedules and job history—for example starting or stopping nonproduction VMs, housekeeping, inventory, alert-driven remediation, or operations that need a Hybrid Runbook Worker to access private systems. I would authenticate runbooks using Managed Identity and scope Azure RBAC narrowly. I wouldn't use Azure Automation just because something can be scripted: persistent infrastructure belongs in Terraform or Bicep, application delivery belongs in GitHub Actions or Azure Pipelines, and VM patch orchestration should generally use Azure Update Manager.”

**Memory line:**
**Azure Automation is for repeatable operational workflows—not a replacement for IaC, CI/CD, or specialized services such as Update Manager.**

**Interview trap:**
The fact that a task can be written in PowerShell does **not mean Azure Automation is the correct service for it**.

**Keywords:**
Operational automation, runbooks, schedules, remediation, Managed Identity, Azure RBAC, Hybrid Runbook Worker, Terraform, Bicep, Update Manager.

**Likely follow-ups:**

* When would you use Azure Automation instead of an Azure DevOps pipeline?
* Why use a Hybrid Runbook Worker?
* How would you stop an automation runbook from accidentally modifying production?
* Why would you use Update Manager rather than writing your own VM-patching runbook?
