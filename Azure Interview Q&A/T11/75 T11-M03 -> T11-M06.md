### **T11-M03. What is Key Vault soft delete?**

**Answer:**
Key Vault soft delete is a recovery feature that keeps a deleted **Key Vault or Key Vault object—such as a secret, key, or certificate—in a recoverable deleted state for a retention period** instead of permanently removing it immediately. It protects against accidental deletion and is enabled by default for new vaults. The retention period is configurable from **7 to 90 days**, with 90 days as the default. ([Microsoft Learn][1])

### **How it works**

```text
Active Secret
     ↓
Delete
     ↓
Soft-deleted state
     ↓
Recover during retention period
     OR
Purge if allowed
     OR
Retention expires
```

For example:

```text
database-password
       ↓
accidentally deleted
       ↓
soft-delete
       ↓
recover database-password
```

The same basic protection applies to:

```text
Key Vault itself
Secrets
Keys
Certificates
```

### **Production example**

Suppose an engineer accidentally deletes a production certificate:

```text
App Gateway / Application
        ↓
Certificate deleted
        ↓
Key Vault soft delete
        ↓
Certificate remains recoverable
        ↓
Operations team restores it
```

Without recovery protection, an accidental deletion could become permanent data loss.

### **Important behavior**

Once soft delete is enabled on a Key Vault, it cannot be disabled. Also, the recovery retention period is set for the vault and is between **7 and 90 days**. ([Microsoft Learn][1])

There is also an important operational detail: if an entire vault is deleted and later recovered, related integrations such as some RBAC role assignments or Event Grid subscriptions might need to be recreated; recovering the vault does not necessarily recreate all external integrations. ([Microsoft Learn][1])

### **Important distinction**

Soft delete protects against:

```text
Accidental deletion
        ↓
Recoverable object
```

But unless **purge protection** is also enabled, an identity with sufficient purge permission might still permanently purge the deleted object before the normal retention period expires.

So:

```text
Soft delete
→ recover deleted object

Purge protection
→ prevent early permanent deletion
```

> **In an interview, I would say:**
> “Key Vault soft delete works like a recovery bin. If a vault, secret, key, or certificate is deleted, Azure keeps it recoverable for a configured retention period instead of deleting it immediately. I would enable it for production so accidental deletions can be recovered, and combine it with purge protection for stronger protection against malicious or premature permanent deletion.”

**Memory line:**
**Soft delete means deleted Key Vault data remains recoverable for a retention window.**

**Interview trap:**
Soft delete alone does **not** mean an authorized user can never permanently purge the object during the retention period.

**Keywords:**
Soft delete, recovery, retention period, secrets, keys, certificates, purge

**Likely follow-ups:**

* Can soft delete be disabled after enabling it?
* What is the default recovery period?
* What happens when a soft-deleted Key Vault is recovered?

### **T11-M04. What is purge protection?**

**Answer:**
Purge protection is an additional Key Vault recovery control that prevents a **soft-deleted vault, key, secret, or certificate from being permanently purged until the configured retention period expires**. Even a highly privileged administrator cannot bypass the retention period once purge protection is enabled. ([Microsoft Learn][1])

### **How it works**

Without purge protection:

```text
Object
  ↓
Delete
  ↓
Soft-deleted
  ↓
Privileged identity
  ↓
Purge
  ↓
Permanently gone
```

With purge protection:

```text
Object
  ↓
Delete
  ↓
Soft-deleted
  ↓
Attempt purge
  ↓
BLOCKED until retention expires
```

The object can still be:

```text
Recovered
```

during the retention period.

### **Production example**

Suppose a Key Vault key protects encrypted Azure data:

```text
Storage / Database
      ↓
Customer-managed key
      ↓
Key Vault
```

If that key is accidentally or maliciously permanently deleted, the encrypted data could become inaccessible.

So I would use:

```text
Soft delete
      +
Purge protection
      ↓
CMK cannot be permanently deleted early
```

Microsoft specifically recommends purge protection for encryption-key scenarios, and some Azure service integrations require it because losing the key could cause data loss. ([Microsoft Learn][1])

### **Why it matters against malicious deletion**

Soft delete handles:

```text
"Someone deleted it accidentally."
```

Purge protection also helps with:

```text
"Someone with elevated privileges deliberately tried
to permanently remove the recovery copy."
```

Microsoft describes purge protection as effectively enforcing a **time-based lock** on deleted Key Vault objects. ([Microsoft Learn][2])

### **Important behavior**

Once purge protection is enabled:

```text
Cannot disable it
Cannot bypass it
Cannot shorten the retention window afterward
```

The object must either be recovered or remain deleted until the retention period expires. ([Microsoft Learn][1])

### **Important distinction**

```text
Soft delete
→ object remains recoverable

Purge protection
→ object cannot be permanently destroyed early
```

You typically want **both** for critical production Key Vaults.

> **In an interview, I would say:**
> “Purge protection builds on soft delete. Soft delete keeps a deleted object recoverable, while purge protection prevents anyone from permanently purging it until the retention period expires. I would definitely enable it for production Key Vaults that hold customer-managed encryption keys because permanent loss of the key could make encrypted data inaccessible.”

**Memory line:**
**Soft delete gives recovery; purge protection locks that recovery window.**

**Interview trap:**
Do not say purge protection stops the initial delete. The object can still be deleted—it just cannot be **permanently purged early**.

**Keywords:**
Purge protection, soft delete, retention, CMK, recovery, irreversible deletion

**Likely follow-ups:**

* Why is purge protection important for CMKs?
* Can purge protection be disabled?
* Does purge protection prevent normal deletion?

### **T11-M05. Why should secrets not be stored in pipeline YAML?**

**Answer:**
Secrets should not be stored directly in pipeline YAML because YAML normally lives in **source control**, which creates a long-lived copy of the credential in Git history and exposes it to anyone with repository access or to tools that process the repository. Instead, I prefer **OIDC/Workload Identity Federation or Managed Identity** so there is no long-lived secret at all; when a secret is unavoidable, I store it in Key Vault or a protected secret-variable system. Microsoft explicitly advises never storing sensitive values as plaintext in Azure Pipelines YAML. ([Microsoft Learn][3])

### **The dangerous pattern**

```yaml
variables:
  CLIENT_SECRET: "super-secret-value"
```

Now the secret may exist in:

```text
Git repository
Git history
Forks / clones
Pull requests
CI logs
Backups
Developer laptops
```

Deleting it from the latest commit does not automatically erase the older copies.

### **Preferred pattern**

Best case:

```text
GitHub Actions / Azure Pipeline
        ↓
OIDC / Workload Identity Federation
        ↓
Microsoft Entra ID
        ↓
Azure RBAC
        ↓
Azure Resource
```

There is no long-lived Azure client secret to manage.

If an actual secret is required:

```text
Pipeline
   ↓
secure identity
   ↓
Azure Key Vault
   ↓
Secret at runtime
```

or use the platform's encrypted secret-variable mechanism.

Microsoft recommends Key Vault or secret variables rather than plaintext YAML and also advises against echoing secrets, passing them casually on command lines, or logging them to files. ([Microsoft Learn][3])

### **Production example**

Bad:

```text
azure-pipelines.yml
      ↓
AZURE_CLIENT_SECRET
      ↓
valid for 12 months
```

Better:

```text
Azure Pipeline / GitHub Actions
      ↓
Federated identity
      ↓
short-lived Entra token
```

Now I remove:

* secret expiry outages
* manual secret rotation
* secret leakage through YAML
* reusable stolen credentials

### **Important distinction**

A secret variable is safer than plaintext YAML, but:

```text
Secret variable
→ still a secret that must exist and be protected
```

Whereas:

```text
OIDC / Managed Identity
→ may eliminate the secret entirely
```

So my preference is:

```text
1. No secret if possible
2. Key Vault / protected secret store if required
3. Never plaintext YAML
```

> **In an interview, I would say:**
> “I never store secrets directly in pipeline YAML because YAML is normally version-controlled and the credential can leak through Git history, pull requests, logs, or developer clones. For Azure authentication I prefer OIDC federation or Managed Identity so there is no long-lived secret. If a real secret is unavoidable, I retrieve it securely from Key Vault or use protected pipeline secret variables and ensure it is never printed to logs.”

**Memory line:**
**The safest pipeline secret is the one you eliminate with identity federation.**

**Interview trap:**
Simply base64-encoding or hiding a value in YAML does **not** make it secure.

**Keywords:**
Pipeline secrets, OIDC, Workload Identity Federation, Key Vault, secret variables, Git history

**Likely follow-ups:**

* How would GitHub Actions authenticate to Azure without a secret?
* Are secret variables completely safe?
* What would you do if a secret was committed to Git?
* How would you rotate an unavoidable pipeline credential?

### **T11-M06. What is a customer-managed encryption key?**

**Answer:**
A customer-managed key, or **CMK**, is an encryption key whose lifecycle and access are controlled by the customer, typically through **Azure Key Vault or Azure Key Vault Managed HSM**, rather than having Azure completely manage the encryption key. Azure services still perform the encryption, but the organization controls important aspects such as key access, rotation, disablement, and revocation. ([Microsoft Learn][4])

### **How encryption normally works**

With platform-managed keys:

```text
Azure Service
     ↓
Microsoft-managed encryption key
     ↓
Encrypted data
```

Microsoft handles:

```text
Key generation
Storage
Rotation
Backup
Lifecycle
```

With CMK:

```text
Azure Service
     ↓
Customer-managed key
     ↓
Key Vault / Managed HSM
     ↓
Encrypted data
```

The customer controls the key lifecycle and access policies. ([Microsoft Learn][4])

### **Production example**

Suppose a regulated organization stores sensitive data in Azure Storage.

A design might be:

```text
Azure Storage
     ↓
Encryption at rest
     ↓
Customer-managed key
     ↓
Azure Key Vault
```

The Storage service uses the configured customer-managed key as part of the encryption hierarchy.

This gives the organization additional control over:

```text
Who can use the key
When the key rotates
Whether access is revoked
Key auditing
Key lifecycle
```

### **Why organizations use CMKs**

Common reasons include:

```text
Regulatory requirements
Compliance requirements
Customer control over key lifecycle
Separation of duties
Ability to revoke key access
Audit requirements
```

Azure's default **platform-managed keys** are usually sufficient for many workloads, while CMKs are an optional control when additional ownership is required. ([Microsoft Learn][4])

### **Important operational risk**

More control also means more responsibility.

If:

```text
Critical Azure data
     ↓
encrypted using CMK
     ↓
CMK permanently lost
```

then the protected data may become inaccessible.

That is why I would combine CMK scenarios with:

```text
Key Vault soft delete
+
purge protection
+
least-privilege RBAC
+
key rotation plan
+
monitoring
```

### **Important distinction**

CMK does **not** normally mean:

```text
"My application manually encrypts every byte."
```

The Azure service can still perform encryption.

The difference is who controls the key used in that encryption architecture:

```text
Platform-managed key
→ Microsoft manages key lifecycle

Customer-managed key
→ customer controls key lifecycle
```

> **In an interview, I would say:**
> “A customer-managed key is an encryption key that I control in Key Vault or Managed HSM rather than letting Azure fully manage the key lifecycle. The Azure service can still perform the encryption, but I control things such as key access, rotation, and revocation. I would use CMKs when compliance or security requirements demand that level of key ownership, while recognizing they add operational responsibility—especially protecting the key from deletion.”

**Memory line:**
**CMK means Azure encrypts the data, but I control the key lifecycle.**

**Interview trap:**
CMKs are not automatically “more secure in every situation.” They provide **more control**, but also create more operational responsibility and failure modes.

**Keywords:**
CMK, customer-managed key, platform-managed key, Key Vault, Managed HSM, encryption at rest, rotation
