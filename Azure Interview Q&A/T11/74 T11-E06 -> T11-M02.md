### **T11-E06. What is encryption at rest?**

**Answer:**
Encryption at rest means **data is encrypted while it is stored** on disks, databases, storage services, backups, or snapshots. The goal is that if the underlying storage media or stored data is accessed without authorization, the data is unreadable without the encryption key.

### **Azure example**

Examples include data stored in:

```text
Azure Managed Disks
Azure Storage
Azure SQL
Backups
Snapshots
```

Conceptually:

```text
Application Data
      ↓
Encryption
      ↓
Stored on Azure disk/storage
      ↓
Encrypted data at rest
```

Azure services commonly provide encryption at rest by default using Microsoft-managed keys, while some services also support **customer-managed keys** for organizations that require greater control over key ownership and rotation.

### **Important distinction**

```text
Encryption at rest
→ protects stored data

Encryption in transit
→ protects data moving across a network
```

**Memory line:**
**At rest = encrypted while stored.**

**Interview trap:**
Encryption at rest does not automatically protect data after an authorized application has decrypted and read it.

**Keywords:**
Encryption at rest, storage encryption, managed keys, customer-managed keys, CMK

### **T11-E07. What is encryption in transit?**

**Answer:**
Encryption in transit protects data **while it is moving between systems or across a network**, usually using protocols such as TLS. It prevents someone intercepting network traffic from easily reading or modifying sensitive data.

### **How it works**

```text
Client
   ↓
TLS-encrypted connection
   ↓
Application Gateway / API
   ↓
TLS
   ↓
Backend
```

Examples include:

```text
HTTPS
TLS to Azure SQL
TLS to Key Vault
TLS between application services
```

### **Production example**

Instead of:

```text
Client
  ↓
HTTP
  ↓
Application
```

I would use:

```text
Client
  ↓
HTTPS / TLS
  ↓
Application
```

For higher-security environments, I may also require TLS from the ingress layer to the backend rather than terminating TLS and sending plaintext internally.

### **Important distinction**

```text
At rest
→ protects stored data

In transit
→ protects data while moving
```

You normally want **both**.

**Memory line:**
**In transit = encrypted while moving.**

**Interview trap:**
Do not assume using HTTPS at the public frontend automatically means every internal hop is encrypted.

**Keywords:**
TLS, HTTPS, encryption in transit, certificates, secure transport

### **T11-M01. How can an Azure application access Key Vault securely?**

**Answer:**
I would give the application a **Microsoft Entra identity**, preferably a Managed Identity for Azure-hosted workloads or AKS Workload Identity for pods, then grant that identity only the required Key Vault **data-plane Azure RBAC role**. The application authenticates without storing Azure credentials and retrieves only the secrets, keys, or certificates it is authorized to access. Microsoft currently recommends managed identities and Azure RBAC for Key Vault access. ([Microsoft Learn][1])

### **Recommended flow**

For an Azure VM or App Service:

```text
Application
    ↓
Managed Identity
    ↓
Microsoft Entra ID
    ↓
Azure RBAC
    ↓
Azure Key Vault
    ↓
Secret / Key / Certificate
```

For AKS:

```text
AKS Pod
   ↓
AKS Workload Identity
   ↓
OIDC federation
   ↓
Microsoft Entra ID
   ↓
Key Vault RBAC
   ↓
Key Vault
```

The important part is:

```text
No client secret stored in:
GitHub
Kubernetes Secret
application config
source code
```

---

### **Production example**

Suppose an AKS workload needs to read a database password.

I could assign its workload identity:

```text
Key Vault Secrets User
```

at the appropriate Key Vault scope.

Then:

```text
Pod
 ↓
Workload Identity
 ↓
Entra authentication
 ↓
Key Vault Secrets User
 ↓
Read secret
```

The **Key Vault Secrets User** role permits reading secret contents, while roles such as **Key Vault Reader** only read metadata and not secret values. ([Microsoft Learn][2])

---

### **Network security**

Identity alone does not necessarily mean I should expose Key Vault publicly.

For a private production environment I might use:

```text
Application VNet
      ↓
Private Endpoint
      ↓
Private DNS
      ↓
Key Vault
```

and disable or tightly restrict public network access.

So secure Key Vault access has two dimensions:

```text
Identity / Authorization
→ Who can access it?

Networking
→ From where can it be reached?
```

### **Control plane vs data plane**

This is particularly important in Key Vault interviews.

```text
Control plane
→ create/delete/configure Key Vault

Data plane
→ read secret
→ decrypt with key
→ retrieve certificate
```

Azure RBAC permissions for managing the Key Vault resource do **not automatically mean** the identity can read its secrets. Key Vault's control and data planes are independently authorized. ([Microsoft Learn][3])

> **In an interview, I would say:**
> “I would give the application a Managed Identity or AKS Workload Identity, authenticate it through Microsoft Entra ID, and assign only the required Key Vault data-plane RBAC role—for example Key Vault Secrets User if it only needs to read secrets. For production I would also consider a Private Endpoint and Private DNS so Key Vault isn't unnecessarily exposed publicly. That gives me credentialless authentication, least privilege, and private network access.”

**Memory line:**
**Identity authenticates → RBAC authorizes → Private Endpoint restricts the network path.**

**Interview trap:**
Giving an application **Contributor** on the Key Vault resource does not automatically give it permission to read secret values. Control-plane and data-plane permissions are different.

**Keywords:**
Managed Identity, AKS Workload Identity, Microsoft Entra ID, Key Vault Secrets User, Azure RBAC, Private Endpoint, Private DNS

**Likely follow-ups:**

* How would an AKS pod authenticate without a client secret?
* What role would you give an application that only needs to read secrets?
* Does Contributor allow reading Key Vault secrets?
* Why might you still need a Private Endpoint?

### **T11-M02. What is Key Vault RBAC?**

**Answer:**
Key Vault RBAC means using **Azure Role-Based Access Control to authorize access to Key Vault data-plane operations**, such as reading secrets or using cryptographic keys. Microsoft currently recommends Azure RBAC instead of the legacy Key Vault access-policy model, and for new Key Vault API versions from `2026-02-01`, RBAC is also the default authorization model. ([Microsoft Learn][4])

### **How it works**

A role assignment still follows the normal Azure RBAC model:

```text
Security Principal
      +
Role
      +
Scope
      ↓
Role Assignment
```

For example:

```text
AKS Workload Identity
        ↓
Key Vault Secrets User
        ↓
kv-prod
```

Now that workload can read secret contents in that Key Vault.

---

### **Common Key Vault roles**

Some useful built-in roles include:

```text
Key Vault Reader
→ metadata only
→ cannot read secret values

Key Vault Secrets User
→ read secret contents

Key Vault Secrets Officer
→ manage secrets

Key Vault Crypto User
→ use cryptographic keys

Key Vault Administrator
→ broad data-plane access
```

Microsoft's current built-in role definitions make the distinction particularly clear: **Key Vault Reader cannot read secret contents**, while **Key Vault Secrets User can**. ([Microsoft Learn][2])

### **Control plane vs data plane**

This is the most important distinction.

```text
Control Plane
────────────────────
Create Key Vault
Delete Key Vault
Change networking
Change tags

Authorization:
Azure RBAC
```

versus:

```text
Data Plane
────────────────────
Get secret
Set secret
Decrypt using key
Read certificate

Authorization:
Key Vault Azure RBAC
or legacy access policy
```

Microsoft documents these as separate access planes with independent permissions. ([Microsoft Learn][3])

### **Example**

Suppose a developer has:

```text
Contributor
at Key Vault resource scope
```

That lets them manage many properties of the Azure resource.

It does **not necessarily mean**:

```text
GET secret value
```

For that, they need an appropriate Key Vault **data-plane role** such as:

```text
Key Vault Secrets User
```

This distinction comes up often in troubleshooting `403 Forbidden`.

---

### **RBAC vs legacy access policies**

Historically Key Vault supported its own access-policy model.

Current recommendation:

```text
New deployment
      ↓
Azure RBAC
```

rather than:

```text
Legacy Key Vault access policies
```

Microsoft specifically recommends RBAC because it gives centralized Azure access management, integrates with PIM, and provides stronger separation of access-management responsibilities. ([Microsoft Learn][4])

> **In an interview, I would say:**
> “Key Vault RBAC uses Azure RBAC to control data-plane access to secrets, keys, and certificates. For example, an application's Managed Identity might receive Key Vault Secrets User so it can read secret values without getting administrative permissions. I keep control-plane and data-plane permissions separate, and for new deployments I prefer Azure RBAC over the legacy Key Vault access-policy model.”

**Memory line:**
**Key Vault RBAC decides what an identity can do with secrets, keys, and certificates.**

**Interview trap:**
**Key Vault Reader does not mean secret reader.** It reads metadata, not secret contents. Also, Azure **Contributor** does not automatically grant Key Vault data-plane access.

**Keywords:**
Key Vault RBAC, data plane, control plane, Key Vault Secrets User, Key Vault Reader, access policies, least privilege

**Likely follow-ups:**

* What is the difference between Key Vault Reader and Key Vault Secrets User?
* Why is Contributor not enough to read a secret?
* What is the difference between Key Vault RBAC and access policies?
* At what scopes can Key Vault roles be assigned?
