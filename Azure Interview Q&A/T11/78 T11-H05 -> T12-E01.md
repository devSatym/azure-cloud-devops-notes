### **T11-H05. How would you protect an Azure environment against accidentally exposed credentials?**

**Answer:**
I would use a layered strategy: **eliminate long-lived credentials where possible, prevent new secrets from entering code, continuously scan for exposed secrets, immediately revoke anything that leaks, and limit the blast radius through least-privilege RBAC**. For Azure workloads and CI/CD, my preferred design is Managed Identity or Workload Identity Federation rather than client secrets.

### **1. Eliminate secrets first**

The strongest control is:

```text
No long-lived secret
        ↓
Nothing reusable to leak
```

For example:

```text
GitHub Actions
      ↓
OIDC
      ↓
Microsoft Entra ID
      ↓
Azure RBAC
```

instead of:

```text
GitHub Actions
      ↓
AZURE_CLIENT_SECRET
      ↓
Azure
```

Similarly:

```text
AKS Pod
   ↓
Workload Identity
   ↓
Azure service
```

and:

```text
Azure VM / App Service
       ↓
Managed Identity
       ↓
Azure service
```

---

### **2. Prevent secrets from reaching Git**

I would enable secret scanning and **push protection** in the source-control platform.

The goal is:

```text
Developer tries to push secret
           ↓
Secret scanner detects it
           ↓
Push blocked
```

For Azure DevOps, GitHub Advanced Security secret scanning can scan repository history and push protection can prevent new credentials from being introduced. Defender for Cloud can also surface exposed-secret findings from connected repositories. ([Microsoft Learn][1])

---

### **3. Scan more than just source code**

Secrets can also leak into:

```text
Terraform / ARM outputs
deployment history
VM files
container images
CI logs
configuration files
```

Current Defender for Cloud capabilities can detect exposed secrets across code repositories and certain cloud deployment/runtime contexts, so I would include secret detection as part of the broader cloud-security posture rather than scanning only `main` branch source files. ([Microsoft Learn][2])

---

### **4. If a secret is exposed, treat it as compromised**

My immediate incident order would be:

```text
Credential exposed
      ↓
REVOKE / rotate it
      ↓
Contain permissions
      ↓
Check usage/sign-in logs
      ↓
Remove secret from repository/history
      ↓
Replace architecture with OIDC/identity if possible
```

I would **not** first spend an hour cleaning Git history while leaving the credential valid.

Even if the repository is private:

```text
exposed credential
→ assume compromise
```

because it may have been cloned, cached, logged, or indexed.

---

### **5. Limit blast radius with least privilege**

A leaked identity with:

```text
Owner
at subscription scope
```

is much worse than:

```text
AcrPush
on one ACR
```

or:

```text
Contributor
on one deployment resource group
```

So:

```text
Least privilege
     +
Narrow scope
     +
Short-lived credentials
     ↓
Smaller breach impact
```

I would also avoid using one powerful identity across all environments.

```text
Dev pipeline identity
→ Dev only

Prod pipeline identity
→ Prod only
```

---

### **6. Protect real secrets in Key Vault**

For secrets that genuinely cannot be removed:

```text
Application
    ↓
Managed/Workload Identity
    ↓
Key Vault
```

I would use:

* Key Vault RBAC
* Private Endpoint where appropriate
* soft delete
* purge protection
* diagnostic logging
* rotation policies

and avoid copying the secret into multiple systems unnecessarily.

---

### **7. Monitor credential use**

I would monitor for:

```text
unexpected sign-in location/IP
unexpected resource access
new credentials added to applications
RBAC privilege escalation
credential-use spikes
```

Microsoft's compromised-application investigation guidance specifically recommends reviewing service-principal sign-ins, accessed resources, and unexpected application credentials. ([Microsoft Learn][3])

---

> **In an interview, I would say:**
> “I would first reduce the number of credentials by using Managed Identity and OIDC federation wherever possible. Then I would enable secret scanning and push protection in GitHub or Azure DevOps, scan cloud deployments and runtime environments, and keep unavoidable secrets in Key Vault. If a credential leaks, I treat it as compromised: revoke or rotate it immediately, check its sign-in and resource activity, and then clean the repository. Least-privilege RBAC and separate identities for dev and prod reduce the blast radius if something does leak.”

**Memory line:**
**Prevent secrets, detect leaks, revoke immediately, and keep every identity least-privileged.**

**Interview trap:**
Removing a secret from the latest Git commit does **not** make the credential safe. Revoke/rotate it first.

**Keywords:**
Secret scanning, push protection, OIDC, Managed Identity, Key Vault, rotation, least privilege, blast radius

**Likely follow-ups:**

* What would you do first if an Azure client secret was committed to Git?
* How does OIDC reduce credential leakage risk?
* Would you trust a leaked secret just because the repository was private?
* How would you detect whether the leaked identity was actually used?

### **T11-H06. How would you investigate a suspected compromise of an Azure service principal?**

**Answer:**
I would treat it as an identity incident and work in this order: **contain the service principal, preserve evidence, inspect service-principal sign-ins and audit logs, determine which Azure resources it accessed or changed, rotate/remove compromised credentials, then reduce permissions and eliminate long-lived credentials if possible**. Microsoft’s current incident guidance specifically recommends reviewing unusual service-principal authentication patterns, accessed resources, and unexpected credential changes. ([Microsoft Learn][3])

### **Diagnostic / incident flow**

```text
Suspected SP compromise
         ↓
Contain identity
         ↓
Preserve evidence
         ↓
Entra sign-in logs
         ↓
Azure Activity / resource logs
         ↓
Determine blast radius
         ↓
Rotate/remove credentials
         ↓
Remediate changes
         ↓
Redesign auth
```

---

### **1. Contain first**

If there is credible evidence the identity is actively compromised, I would prevent further unauthorized access.

Depending on the situation, that could mean:

```text
disable/remove compromised credential
        ↓
temporarily disable access
        ↓
remove dangerous role assignments
```

But I would be careful not to destroy investigation evidence.

I would also understand whether this identity is powering production automation before disabling it blindly:

```text
Contain attack
     +
avoid unnecessary outage
```

---

### **2. Inspect service-principal sign-ins**

I would look for anomalies such as:

```text
Unexpected source IP
Unexpected geographic location
Unusual times
Large spike in sign-ins
Repeated failures
Access to unusual resources
```

Microsoft specifically recommends reviewing these patterns in **Service Principal Sign-ins**. ([Microsoft Learn][3])

Example:

```text
Normal:
GitHub Actions runner
→ known workflow pattern

Suspicious:
new IP range
→ 03:12 UTC
→ accesses Key Vault
→ followed by Storage operations
```

That creates a timeline.

---

### **3. Determine what the identity could access**

I would enumerate:

```text
Role assignments
       ↓
Scope
       ↓
Subscription / RG / Resource
```

For example:

```text
Service Principal
      ↓
Contributor
      ↓
rg-prod
```

means the likely blast radius is very different from:

```text
Owner
at management-group scope
```

I would also inspect any custom roles.

---

### **4. Check what it actually did**

Next I move from:

```text
What could it do?
```

to:

```text
What did it do?
```

I would inspect:

```text
Azure Activity Log
Key Vault logs
Storage logs
Azure SQL logs
AKS audit/control-plane logs
other resource logs
```

depending on its permissions.

For example:

```text
Suspicious SP sign-in
      ↓
Activity Log
      ↓
Role assignment added
      ↓
Storage firewall changed
      ↓
potential persistence/exfiltration
```

---

### **5. Check application credential changes**

I would review Entra audit logs for:

```text
New client secret added
New certificate added
Federated identity credential changed
Unexpected owner added
Application permission changed
```

Microsoft's investigation guidance specifically calls out unexpected credentials on both the application and associated service principal objects. ([Microsoft Learn][3])

This matters because an attacker may add a **new credential for persistence**.

Simply rotating the original secret would not remove that backdoor.

---

### **6. Revoke and replace credentials**

For compromised credentials:

```text
Old secret/cert
    ↓
Remove
```

Then I would prefer redesigning:

```text
Service-principal secret
        ↓
OIDC / Workload Identity Federation
```

where supported.

If a secret remains necessary:

```text
new credential
+
short lifetime
+
secure storage
+
rotation
```

---

### **7. Remediate unauthorized changes**

If the compromised principal:

```text
changed NSGs
created users
added RBAC
modified Key Vault
created resources
```

I would restore the intended configuration from IaC or trusted baselines after confirming what happened.

For Terraform-managed Azure:

```text
Incident investigation
       ↓
Understand malicious drift
       ↓
Clean persistence
       ↓
terraform plan
       ↓
review
       ↓
restore intended configuration
```

I would not blindly apply before checking whether attacker-created resources or privileges need explicit removal.

---

### **8. Post-incident hardening**

I would ask:

```text
Why did this identity have a reusable credential?
Why was its scope so broad?
Why wasn't the activity alerted?
```

Then improve:

```text
OIDC / federation
least privilege
separate prod identity
PIM for human access
secret scanning
identity risk monitoring
alerting
```

> **In an interview, I would say:**
> “I would first contain the service principal so it can't continue being abused, while preserving evidence. Then I would inspect Entra service-principal sign-in logs for unusual IPs, timing and resource access, inspect audit logs for new secrets or certificates, and correlate that with Azure Activity Logs and resource logs to determine what it actually changed or accessed. I would remove all compromised or attacker-added credentials, remediate unauthorized changes, review RBAC scope, and where possible replace the long-lived secret with workload identity federation.”

**Memory line:**
**Contain → identify how it authenticated → find what it accessed → remove persistence → remediate → redesign identity.**

**Interview trap:**
Do not rotate only the known leaked secret and stop. An attacker may have added a second credential or new role assignment for persistence.

**Keywords:**
Service principal, sign-in logs, audit logs, Activity Log, credential rotation, persistence, RBAC, federation

**Likely follow-ups:**

* Which Entra log shows service-principal authentications?
* How would you find resources the identity changed?
* What persistence mechanisms would you look for?
* Why replace the secret with workload identity federation?

### **T11-H07. How would you design defense in depth for an internet-facing Azure application?**

**Answer:**
I would design multiple independent security layers so compromising one control does not directly expose the application or data. At a high level I would secure **edge ingress, origin networking, application identity, secrets, compute/workloads, data services, CI/CD, and monitoring**. For a global HTTP application, a strong Azure pattern is Front Door with WAF at the edge, private or tightly restricted origins, private PaaS connectivity, identity-based authentication, and centralized security monitoring. Microsoft currently recommends WAF for internet-facing applications and supports Front Door Premium Private Link to keep supported origins off the public internet. ([Microsoft Learn][4])

### **Architecture**

```text
Internet
   ↓
Azure Front Door
   │
   ├── TLS
   ├── WAF
   ├── Rate limiting
   └── DDoS protection
   ↓
Private / restricted origin
   ↓
Application Gateway / AKS / App Service
   ↓
Private application tier
   ↓
Private Endpoint
   ↓
Database / Storage / Key Vault
```

Alongside:

```text
Microsoft Entra ID
      ↓
Managed / Workload Identity
      ↓
Least-privilege Azure RBAC
```

---

### **1. Protect the public edge**

For global HTTP/S applications:

```text
Users
  ↓
Azure Front Door
  ↓
WAF
```

I would use WAF managed rules and tune them before enforcing production blocking.

Microsoft's current guidance recommends WAF at public web entry points, with prevention mode for production after tuning. ([Microsoft Learn][5])

Controls could include:

```text
OWASP protections
bot protection
rate limiting
IP restrictions where applicable
TLS enforcement
```

---

### **2. Do not expose backends directly**

I want:

```text
Internet
   ↓
Front Door
   ↓
Application
```

not:

```text
Internet ─────→ Application directly
      \
       → Front Door
```

Otherwise attackers bypass the WAF.

With Front Door Premium, supported origins can use Private Link:

```text
Front Door Premium
       ↓
Private Link
       ↓
Private origin
```

Microsoft specifically recommends locking down origins so traffic cannot bypass Front Door. ([Microsoft Learn][6])

---

### **3. Segment the network**

For a three-tier application:

```text
Ingress tier
     ↓
Application tier
     ↓
Data tier
```

I would separate access paths and permit only necessary flows.

For example:

```text
Ingress
→ backend HTTPS only

Backend
→ SQL 1433/private service path only

Internet
→ database: DENY
```

Use:

```text
NSGs
UDRs
Azure Firewall where needed
Private Endpoints
Private DNS
```

based on architecture.

---

### **4. Keep PaaS data services private**

For Azure SQL, Storage, and Key Vault:

```text
Application VNet
       ↓
Private Endpoint
       ↓
Private DNS
       ↓
Azure PaaS service
```

Then disable public network access where practical.

This gives:

```text
Network isolation
+
identity authorization
```

rather than relying on either alone.

---

### **5. Use identity instead of credentials**

For applications:

```text
AKS
→ Workload Identity

App Service / VM
→ Managed Identity

CI/CD
→ OIDC Federation
```

Then:

```text
Entra ID
   ↓
Azure RBAC
```

with the narrowest required scope.

I want to avoid:

```text
database password
storage access key
service-principal client secret
```

where identity-based authentication is supported.

---

### **6. Secure secrets and encryption**

For unavoidable secrets:

```text
Application
    ↓
Managed/Workload Identity
    ↓
Key Vault
```

and use:

```text
soft delete
purge protection
rotation
Private Endpoint
RBAC
```

For data:

```text
TLS in transit
+
encryption at rest
+
CMK where justified
```

---

### **7. Harden the workload**

For AKS, I might implement:

```text
Private AKS API where required
separate system/user node pools
Network Policies
Pod Security standards
non-root containers
read-only root filesystem where possible
resource limits
image vulnerability scanning
signed/trusted images
runtime threat detection
```

For VMs:

```text
no unnecessary public IPs
patching
Defender for Servers
least-open NSGs
Bastion/JIT admin access
```

---

### **8. Secure the CI/CD supply chain**

```text
Pull Request
    ↓
SAST / dependency scan
    ↓
IaC scan
    ↓
secret scan
    ↓
container scan
    ↓
build
    ↓
sign / attest
    ↓
ACR
    ↓
deployment policy
```

Authentication:

```text
GitHub Actions
      ↓
OIDC
      ↓
Azure
```

not long-lived production secrets.

---

### **9. Central monitoring and detection**

I would collect:

```text
Front Door / WAF logs
Application Insights
AKS/container logs
Azure Firewall logs
Key Vault audit logs
Activity Logs
Defender for Cloud alerts
```

into appropriate monitoring/security platforms:

```text
Azure Monitor
Log Analytics
Defender for Cloud
Microsoft Sentinel
```

Then create actionable alerts such as:

```text
WAF attack spike
5xx rate increase
suspicious identity activity
unexpected RBAC change
Key Vault access anomaly
```

---

### **10. Design for availability too**

Security controls themselves should not create a single point of failure.

I would consider:

```text
Availability Zones
autoscaling
health probes
multi-region architecture where required
backup / DR
```

Defense in depth should improve security **without making the application fragile**.

---

> **In an interview, I would say:**
> “I would use defense in depth across the whole path. At the edge I would use Front Door with TLS, WAF, rate limiting and DDoS protections. I would prevent direct origin access—using Private Link where supported—and keep application and data tiers private with segmentation and Private Endpoints. Workloads would authenticate using Managed Identity or Workload Identity with least-privilege RBAC, secrets would live in Key Vault, and CI/CD would use OIDC plus security scanning. Finally I would centralize WAF, application, platform and identity telemetry into Azure Monitor, Defender for Cloud and Sentinel. The principle is that bypassing one layer should still leave several independent controls protecting the workload.”

**Memory line:**
**Edge → network → identity → workload → data → pipeline → monitoring: protect every layer.**

**Interview trap:**
A WAF alone is **not** defense in depth. If attackers can hit the origin directly, steal broad credentials, or reach the database publicly, the architecture is still weak.

**Keywords:**
Defense in depth, Front Door, WAF, Private Link, Private Endpoint, Managed Identity, Workload Identity, Key Vault, Defender for Cloud

**Likely follow-ups:**

* How would you prevent users from bypassing Front Door?
* Front Door WAF versus Application Gateway WAF?
* How would AKS access Azure SQL privately and without a password?
* Where would Defender for Cloud and Sentinel fit?

### **T12-E01. What is high availability?**

**Answer:**
High availability means designing a system so it **continues providing service despite component failures**, with minimal downtime. In Azure, that typically means eliminating single points of failure by using multiple instances, redundancy, health probes, Availability Zones, and automatic failover where appropriate.

### **Simple example**

Bad:

```text
User
 ↓
Single VM
 ↓
Application
```

If that VM fails:

```text
Application down
```

Highly available design:

```text
             ┌── VM / Instance 1
User → LB ───┤
             └── VM / Instance 2
```

If one fails:

```text
Health probe
    ↓
Remove unhealthy instance
    ↓
Traffic continues to healthy instance
```

### **Azure example**

For a production application:

```text
Application Gateway / Load Balancer
             ↓
     Multiple instances
        across zones
             ↓
   Zone-redundant database
```

So a single VM, node, or potentially Availability Zone failure does not immediately take down the workload.

### **Important distinction**

```text
High Availability
→ keep the service running during failures
```

versus:

```text
Disaster Recovery
→ recover the service after a major disaster
```

For example:

```text
VM failure
→ HA design handles automatically

Entire Azure region lost
→ usually DR / multi-region architecture
```

**Memory line:**
**HA keeps the service running when individual components fail.**

**Interview trap:**
High availability does **not automatically mean multi-region disaster recovery**. A workload can be highly available inside one region yet still be vulnerable to complete regional failure.

**Keywords:**
High availability, redundancy, Availability Zones, health probes, failover, single point of failure
