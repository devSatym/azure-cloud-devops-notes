### **T11-H01. How would you design secret management for applications running on AKS?**

**Answer:**
For AKS, I would avoid storing Azure credentials inside Kubernetes Secrets wherever possible. I would use **AKS Workload Identity** so each workload gets its own Microsoft Entra identity, grant that identity least-privilege access to Azure Key Vault, and let the application retrieve secrets either through the **Key Vault Secrets Store CSI Driver** or directly through an Azure SDK. Microsoft supports Workload Identity, managed identity, and the CSI driver for identity-based Key Vault access from AKS. ([Microsoft Learn][1])

### **Production design**

```text
AKS Pod
  │
  │ Kubernetes ServiceAccount
  ↓
AKS Workload Identity
  │
  ↓
Microsoft Entra ID
  │
  │ Azure RBAC
  ↓
Azure Key Vault
  │
  ├── Secret
  ├── Certificate
  └── Key
```

No long-lived Azure client secret is stored inside:

```text
Deployment YAML
Git repository
GitHub Actions
Kubernetes Secret
container image
```

---

### **1. Give each workload its own identity**

I would avoid:

```text
All AKS applications
       ↓
one shared powerful identity
```

Instead:

```text
payments pod
   ↓
payments identity
   ↓
payments secrets only

orders pod
   ↓
orders identity
   ↓
orders secrets only
```

This keeps the blast radius small.

For example:

```text
payments identity
→ Key Vault Secrets User
→ payments Key Vault / required scope
```

not:

```text
AKS cluster identity
→ Key Vault Administrator
→ every Key Vault
```

---

### **2. Use AKS Workload Identity**

Conceptually:

```text
Pod
 ↓
Kubernetes ServiceAccount token
 ↓
OIDC
 ↓
Federated Identity Credential
 ↓
Microsoft Entra ID
 ↓
Azure access token
```

The workload does not need:

```text
AZURE_CLIENT_SECRET
```

This is preferable to injecting a service-principal secret into the pod.

---

### **3. Choose how the application receives the secret**

There are two common patterns.

#### **Option A — application reads Key Vault directly**

```text
Application
   ↓
Azure SDK
   ↓
DefaultAzureCredential
   ↓
Workload Identity
   ↓
Key Vault
```

This is often my preferred design if the application already supports Key Vault.

Benefits:

```text
No secret file needed
Fresh value can be fetched
Application controls caching/refresh
```

---

#### **Option B — Secrets Store CSI Driver**

```text
Key Vault
    ↓
Secrets Store CSI Driver
    ↓
Mounted volume inside pod
```

The pod sees the value as a mounted file.

Microsoft's AKS Secrets Store CSI integration supports identity-based access including Workload Identity. ([Microsoft Learn][1])

This is useful when the application expects:

```text
certificate files
config files
secret files
```

and cannot call Key Vault directly.

---

### **4. Be careful with syncing into Kubernetes Secrets**

The CSI integration can also synchronize secret material into a native Kubernetes Secret in supported patterns.

But that changes the security model:

```text
Key Vault
   ↓
Kubernetes Secret
   ↓
etcd / Kubernetes API
```

Now the secret exists inside Kubernetes as well.

If I do not need that functionality, I would prefer:

```text
direct SDK access
```

or:

```text
CSI-mounted secret
```

instead of creating another persisted copy.

---

### **5. Protect Key Vault network access**

For a private production AKS cluster:

```text
AKS VNet
   ↓
Private Endpoint
   ↓
Private DNS
   ↓
Key Vault
```

I can then disable Key Vault public network access.

So there are two independent security controls:

```text
Identity
→ Who is allowed?

Networking
→ From where is access possible?
```

---

### **6. Rotation**

The application should not require redeployment every time a secret changes.

Preferred:

```text
Key Vault secret
      ↓
new version
      ↓
application refreshes/reloads
```

For direct SDK access, the application can fetch/cache secrets appropriately.

For CSI-based mounting, I would validate the rotation behavior and how the application notices updated files.

The design is incomplete if:

```text
secret rotates
     ↓
pod continues using old value forever
```

---

### **7. Audit and recovery**

For production Key Vault:

```text
Soft delete
+
Purge protection
+
Azure RBAC
+
Diagnostic logs
+
Private Endpoint
```

I would also alert on suspicious access or unexpected administrative changes.

---

### **What I would avoid**

```text
❌ Azure credentials in YAML
❌ client secrets in Kubernetes Secrets when federation is possible
❌ shared cluster-wide identity for every workload
❌ Key Vault Administrator for applications
❌ public Key Vault unless there is a justified requirement
```

> **In an interview, I would say:**
> “For AKS I would use Workload Identity so every application authenticates to Azure through its Kubernetes service account without storing a client secret. I would grant each identity only the required Key Vault data-plane role and either let the application read Key Vault directly through the Azure SDK or use the Secrets Store CSI Driver when the application needs mounted files. In production I would also use a Key Vault Private Endpoint, Private DNS, disable public access where appropriate, and design for secret rotation so workloads don't require manual redeployment.”

**Memory line:**
**AKS ServiceAccount → Workload Identity → Key Vault RBAC → secret, with no Azure client secret in the pod.**

**Interview trap:**
Do not say **Kubernetes Secret = secure Key Vault replacement**. A Kubernetes Secret is still a Kubernetes object and has a different security and lifecycle model.

**Keywords:**
AKS Workload Identity, OIDC, Key Vault, CSI Driver, ServiceAccount, Azure RBAC, Private Endpoint

**Likely follow-ups:**

* CSI Driver versus direct SDK access—which would you choose?
* How would each microservice get a different Key Vault permission?
* Does Workload Identity require storing a client secret?
* How would secret rotation reach a running pod?

### **T11-H02. How would you rotate a database password without redeploying every application manually?**

**Answer:**
My first choice would be to **remove the database password entirely** if the database supports Microsoft Entra authentication and the workload can use Managed Identity or Workload Identity. If a password is unavoidable, I would store it in Key Vault, automate rotation, and make applications retrieve or refresh the secret at runtime rather than baking the password into deployments. Microsoft currently recommends Entra-based authentication over SQL logins where possible and documents automated SQL-password rotation using Key Vault, Event Grid, and Azure Functions. ([Microsoft Learn][2])

### **Best design**

```text
Application
    ↓
Managed Identity /
Workload Identity
    ↓
Microsoft Entra ID
    ↓
Database
```

Then:

```text
No DB password
→ no password rotation problem
```

This is the cleanest answer when supported.

---

## **If a password is required**

I would design:

```text
Database
   ↑
   │ update credential
   │
Rotation Function
   ↑
   │ Event Grid
   │
Key Vault
   ↓
new secret version
   ↓
Applications refresh secret
```

Microsoft documents a current Key Vault pattern where a near-expiry event triggers Event Grid, which invokes an Azure Function that generates a new password, creates a new Key Vault secret version, and updates the database credential. ([Microsoft Learn][2])

---

### **1. Do not inject the password at deployment time**

Bad:

```text
Pipeline
  ↓
DATABASE_PASSWORD
  ↓
Deployment
  ↓
Pod environment variable
```

Now rotation often becomes:

```text
Change password
      ↓
Update pipeline secret
      ↓
Redeploy every application
```

That is exactly the coupling I want to avoid.

---

### **2. Applications should read from Key Vault at runtime**

For AKS:

```text
Pod
 ↓
Workload Identity
 ↓
Key Vault
 ↓
Current secret version
```

or for an App Service:

```text
App Service
   ↓
Managed Identity
   ↓
Key Vault
```

The application should cache responsibly but periodically refresh the secret.

---

### **3. Rotation must update both sides**

This is critical.

A secret exists in two places conceptually:

```text
Key Vault value
      ↕
Database's accepted credential
```

Changing only Key Vault does not change the database password.

Changing only the database breaks applications.

A rotation system must coordinate:

```text
Generate credential
      ↓
Update Key Vault
      ↓
Update database
      ↓
Applications start using new version
```

Microsoft's current single-credential SQL rotation example explicitly updates both Key Vault and SQL. ([Microsoft Learn][2])

---

### **4. Account for the single-credential problem**

For a database login with only one active password:

```text
Old password
    ↓
change
    ↓
New password
```

there can be a brief coordination risk.

Microsoft's own Key Vault SQL rotation documentation notes that its sample can have a short period where the Key Vault value and SQL password aren't yet synchronized. ([Microsoft Learn][2])

For high-availability systems, a stronger design is to use:

```text
Credential A
+
Credential B
```

if the database/application architecture permits it.

Then:

```text
Apps use A
   ↓
Create/update B
   ↓
Apps refresh to B
   ↓
Verify
   ↓
Retire A
```

This is similar to a blue-green credential rotation pattern.

---

### **5. Refresh connection pools**

Another often-missed point:

Even after the application reads the new credential:

```text
Existing DB connection pool
```

may still hold connections created with the previous credential.

So the application may need to:

```text
detect secret version change
       ↓
create new DB connections
       ↓
drain old pool
```

without redeploying the entire application.

---

### **6. Monitor rotation**

I would monitor:

```text
SecretNearExpiry event
Rotation function failures
Key Vault access failures
DB authentication failures
secret age
```

and have an emergency rollback/manual rotation procedure.

Microsoft recommends monitoring rotation success/failure and validating that dependent systems handle rotated assets correctly. ([Microsoft Learn][3])

---

### **Implementation order**

```text
1. Prefer Entra auth if possible
        ↓
2. Otherwise put credential in Key Vault
        ↓
3. Applications fetch at runtime
        ↓
4. Automate rotation
        ↓
5. Update DB + Key Vault
        ↓
6. Applications refresh
        ↓
7. Refresh connection pools
        ↓
8. Verify
        ↓
9. Revoke old credential
```

> **In an interview, I would say:**
> “My first choice would be to eliminate the database password by using Entra authentication with Managed Identity or Workload Identity. If SQL authentication is required, I would store the password in Key Vault, have applications read and refresh it at runtime, and automate rotation using an event-driven function that updates both the database credential and the Key Vault secret version. For highly available systems I prefer overlapping credentials where possible so applications can switch to the new credential before the old one is revoked.”

**Memory line:**
**Best rotation is no password; otherwise rotate centrally and let applications refresh at runtime.**

**Interview trap:**
Rotating the Key Vault secret alone does **not** rotate the database password.

**Keywords:**
Secret rotation, Managed Identity, Workload Identity, Key Vault, Event Grid, Azure Functions, connection pool, secret version

**Likely follow-ups:**

* What if the database supports only one password at a time?
* How would applications know a secret has rotated?
* Why is Managed Identity better than password rotation?
* How would you prevent downtime during rotation?

### **T11-H03. How would you ensure that Key Vault is accessible only over private networking?**

**Answer:**
I would create a **Private Endpoint** for Key Vault in the application VNet, configure the appropriate **Private DNS zone** so the normal Key Vault hostname resolves to the endpoint's private IP, verify connectivity, and then disable Key Vault **public network access**. A private endpoint by itself does not disable the public endpoint, so both pieces are required. ([Microsoft Learn][4])

### **Architecture**

```text
AKS / VM / App
      │
      ↓
Private DNS
      │
vault.azure.net
      ↓
Private IP
      ↓
Private Endpoint
      ↓
Azure Private Link
      ↓
Key Vault
```

The Key Vault Private DNS zone is:

```text
privatelink.vaultcore.azure.net
```

for the standard Azure public cloud. ([Microsoft Learn][5])

---

### **Production implementation order**

#### **1. Create Private Endpoint**

```text
Key Vault
   ↓
Private Endpoint NIC
   ↓
Private IP from VNet
```

A private endpoint uses a private IP from the VNet and provides private connectivity through Azure Private Link. ([Microsoft Learn][6])

---

### **2. Configure Private DNS**

This step is crucial.

I want:

```text
myvault.vault.azure.net
        ↓
private-link DNS chain
        ↓
10.20.1.5
```

from inside the application network.

For Key Vault, the relevant private DNS zone is:

```text
privatelink.vaultcore.azure.net
```

and it must be linked to the VNets that need resolution. ([Microsoft Learn][5])

---

### **3. Verify DNS before disabling public access**

From a VM/pod inside the VNet:

```bash
nslookup myvault.vault.azure.net
```

I expect the final resolved address to be the Private Endpoint's private IP.

Conceptually:

```text
myvault.vault.azure.net
       ↓
privatelink.vaultcore.azure.net
       ↓
10.x.x.x
```

Microsoft's Key Vault Private Link guidance shows this same private-resolution pattern. ([Microsoft Learn][4])

---

### **4. Verify application connectivity**

Before closing public access:

```text
Application
   ↓
Key Vault private FQDN resolution
   ↓
Private endpoint IP
   ↓
Successful secret read
```

I want to prove:

```text
DNS works
network works
identity works
RBAC works
```

before removing the fallback public path.

---

### **5. Disable public network access**

Then I disable:

```text
Public network access
```

Microsoft specifically recommends completing the Private Endpoint configuration first and then disabling public access. ([Microsoft Learn][7])

CLI example:

```bash
az keyvault update \
  --resource-group rg-prod \
  --name kv-prod \
  --public-network-access Disabled
```

Now:

```text
Internet
   ✕
   │
Key Vault

Private Endpoint
   ✓
```

---

### **Important distinction**

Creating:

```text
Private Endpoint
```

does **not automatically mean**:

```text
public endpoint disabled
```

Microsoft's Key Vault diagnostics explicitly warns that Private Link gives a private path but does not remove existing public access unless public access/firewall configuration is also changed. ([Microsoft Learn][8])

---

### **DNS trap**

Another subtle point:

After disabling public access:

```text
myvault.vault.azure.net
```

can still have public DNS records.

That does **not** mean the vault is publicly accessible.

Microsoft explicitly notes that public DNS visibility and public data-plane access are different things. ([Microsoft Learn][4])

The important check is:

```text
From authorized private network
→ resolves private IP

From internet
→ public data-plane access rejected
```

---

### **Hub-and-spoke design**

In an enterprise architecture:

```text
Spoke AKS
    │
    ↓
Hub DNS / Private DNS Resolver
    │
    ↓
Private DNS Zone
    │
    ↓
Key Vault Private Endpoint
```

I might centralize DNS using Azure DNS Private Resolver or an existing enterprise DNS design.

---

### **Also secure identity**

Private networking alone does not provide authorization.

I still need:

```text
Private Endpoint
      +
Workload Identity
      +
Key Vault RBAC
```

because:

```text
Can reach Key Vault
≠
Can read secrets
```

> **In an interview, I would say:**
> “I would create a Key Vault Private Endpoint in the application VNet, configure the `privatelink.vaultcore.azure.net` Private DNS zone and link it to the required VNets, then verify that the normal Key Vault FQDN resolves to the private endpoint IP. After confirming application connectivity, I would disable Key Vault public network access. I would also keep identity-based authorization through Managed Identity or Workload Identity and Azure RBAC, because private networking controls reachability, not permission.”

**Memory line:**
**Private Endpoint gives the private path; Private DNS makes clients use it; disabling public access closes the public path.**

**Interview trap:**
A Private Endpoint alone does **not** automatically make Key Vault private-only.

**Keywords:**
Private Endpoint, Private Link, `privatelink.vaultcore.azure.net`, Private DNS, public network access, Azure RBAC

**Likely follow-ups:**

* Why is Private DNS required?
* What if Key Vault still resolves to a public IP?
* Does a Private Endpoint disable the public endpoint?
* Can spokes share centralized Key Vault private DNS?

### **T11-H04. How would you secure administrative access to production Azure subscriptions?**

**Answer:**
I would avoid permanent Owner access. Human administrators should normally have low-privilege standing access and use **Microsoft Entra Privileged Identity Management (PIM)** for just-in-time activation of privileged Azure RBAC roles. I would combine that with MFA/Conditional Access, narrow scopes, approvals for sensitive roles, privileged-access monitoring, separate emergency accounts, and a small number of subscription Owners. Microsoft recommends least privilege, limiting subscription Owners, and using PIM for privileged Azure access. ([Microsoft Learn][9])

### **Production privileged-access model**

```text
Administrator
    ↓
Normal account
    ↓
Reader / limited standing access
    ↓
Needs production change
    ↓
PIM activation
    ↓
MFA + justification + approval
    ↓
Time-limited RBAC role
    ↓
Production subscription/resource
    ↓
Access automatically expires
```

---

### **1. No permanent Owner access**

Bad:

```text
10 engineers
    ↓
Permanent Owner
    ↓
Production Subscription
```

Better:

```text
Platform engineers
    ↓
Eligible via PIM
    ↓
Contributor / specialized role
```

Microsoft explicitly recommends limiting the number of subscription Owners and avoiding unnecessarily broad privileged administrator assignments. ([Microsoft Learn][9])

---

### **2. Use PIM**

For example:

```text
User is eligible for:
Contributor
at production subscription
```

but not active permanently.

When needed:

```text
Activate
  ↓
MFA
  ↓
Justification
  ↓
Approval if configured
  ↓
Access for 1 hour
  ↓
Automatic expiration
```

Microsoft's identity guidance recommends **no standing privileged human access** in isolated environments and PIM-based just-in-time activation. ([Microsoft Learn][10])

---

### **3. Assign the narrowest useful role**

Instead of:

```text
Owner
```

I ask:

```text
What task actually needs to be performed?
```

Examples:

```text
VM operator
→ Virtual Machine Contributor or tailored role

Network engineer
→ Network Contributor

Security analyst
→ Security Reader

Deployment operator
→ scoped Contributor/custom deployment role
```

And preferably:

```text
Resource Group scope
```

instead of:

```text
Subscription scope
```

when possible.

---

### **4. Separate resource administration from access administration**

This is a very important distinction.

```text
Contributor
→ manages resources
→ cannot generally assign Azure RBAC roles
```

versus:

```text
Owner
→ manages resources
→ can assign roles
```

I would not give developers Owner just because they need to deploy an application.

Role-assignment administration should be tightly restricted.

Microsoft specifically recommends restricting roles with privilege to create role assignments and considering conditions when delegation is required. ([Microsoft Learn][9])

---

### **5. Use Conditional Access and strong authentication**

For privileged activation/access I would require controls such as:

```text
MFA
approved device
appropriate location/risk policies
short session duration
```

depending on the organization's security policy.

For the most sensitive environments, privileged administration should come from secured administrative devices/workstations. Microsoft recommends securing privileged operations through hardened access paths. ([Microsoft Learn][10])

---

### **6. Separate human and automation identities**

```text
Human Admin
→ PIM

Terraform / GitHub Actions
→ Workload Identity Federation

AKS workload
→ Workload Identity
```

I would never make CI/CD depend on:

```text
Satyam's personal Owner account
```

Automation should have a non-human identity with narrowly scoped RBAC.

---

### **7. Production changes through controlled workflows**

Normal infrastructure changes should go through:

```text
Git PR
  ↓
Peer review
  ↓
terraform plan
  ↓
Approval
  ↓
OIDC-authenticated pipeline
  ↓
Production
```

Humans should not normally log into the portal and make production changes manually.

Privileged manual access becomes:

```text
exception / incident path
```

not:

```text
normal deployment path
```

---

### **8. Emergency / break-glass access**

I would maintain a very small number of emergency-access identities for scenarios where normal identity controls fail.

They should be:

```text
Highly protected
Not used day-to-day
Monitored
Tested periodically
```

but deliberately designed so the organization does not lock itself out during an identity outage.

---

### **9. Audit everything**

I would monitor:

```text
PIM activations
RBAC changes
Owner/User Access Administrator assignments
failed privileged access attempts
production Activity Logs
unusual sign-ins
```

and periodically perform access reviews.

Microsoft recommends periodic reviews/attestation of privileged access and PIM reporting/alerts. ([Microsoft Learn][9])

---

### **Architecture**

```text
Humans
  │
  └── PIM → JIT RBAC
             ↓
       Production Azure

CI/CD
  │
  └── OIDC Federation
             ↓
       Narrow Azure RBAC

Applications
  │
  └── Managed / Workload Identity
             ↓
       Required Azure service
```

Each type of actor gets a different access model.

> **In an interview, I would say:**
> “I would avoid permanent Owner access in production. Engineers would have limited standing permissions and become eligible for privileged Azure RBAC roles through PIM. Activation would be time-limited and could require MFA, justification, and approval. I would use the narrowest scope and role possible, separate resource administration from RBAC administration, use dedicated workload identities for CI/CD, and route normal production changes through reviewed pipelines. I would also maintain monitored emergency-access accounts and regularly review privileged assignments.”

**Memory line:**
**Production privilege should be just-in-time, least-privilege, time-bound, and auditable.**

**Interview trap:**
Do not give permanent Owner access simply because someone occasionally needs to deploy or troubleshoot production.

**Keywords:**
PIM, JIT access, Azure RBAC, MFA, Conditional Access, least privilege, Owner, Contributor, emergency access

**Likely follow-ups:**

* What is the difference between eligible and active PIM assignments?
* Why is Contributor safer than Owner?
* What would your break-glass design look like?
* How should CI/CD get production permissions?
