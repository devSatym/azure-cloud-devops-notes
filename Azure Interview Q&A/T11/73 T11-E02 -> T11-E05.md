### **T11-E02. What can be stored inside Key Vault?**

**Answer:**
Azure Key Vault can store three main types of sensitive objects: **secrets, cryptographic keys, and certificates**. The choice depends on whether I need to store a value, perform cryptographic operations, or manage a certificate lifecycle.

### **How it works**

```text
Azure Key Vault
│
├── Secrets
│   └── passwords, connection strings, API tokens
│
├── Keys
│   └── RSA / EC cryptographic keys
│
└── Certificates
    └── TLS and application certificates
```

### **Production example**

I might use:

```text
Secret
→ third-party API token

Key
→ encryption/signing operation

Certificate
→ TLS certificate for an application
```

**Memory line:**
**Secrets store values, keys perform crypto, certificates represent identities/TLS trust.**

**Interview trap:**
Do not treat a **key** and a **secret** as the same thing. A Key Vault key is a cryptographic object with operations such as encrypt, decrypt, sign, or verify.

**Keywords:**
Secrets, keys, certificates, Key Vault

### **T11-E03. What is the difference between a secret, key, and certificate?**

**Answer:**
A **secret** is an arbitrary sensitive value such as a password or token. A **key** is a cryptographic object used for operations such as encryption or signing. A **certificate** represents an X.509 certificate and typically combines certificate metadata with an associated cryptographic key for identity or TLS scenarios.

### **Clear distinction**

```text
Secret
→ "What sensitive value do I need to store?"

Key
→ "What cryptographic operation do I need to perform?"

Certificate
→ "What certificate/identity do I need to manage?"
```

Examples:

```text
Secret
→ DB_PASSWORD=...

Key
→ customer-managed encryption key

Certificate
→ api.example.com TLS certificate
```

### **Production example**

For an internet-facing API:

```text
TLS certificate
      ↓
Key Vault Certificate
```

For application credentials:

```text
API token
      ↓
Key Vault Secret
```

For encryption:

```text
Encryption operation
      ↓
Key Vault Key
```

**Memory line:**
**Secret = value, key = crypto, certificate = identity/TLS.**

**Interview trap:**
A certificate is not just another password-like secret. It has certificate-specific lifecycle and cryptographic semantics.

**Keywords:**
Secret, key, certificate, X.509, encryption, signing, TLS

### **T11-E04. What is Microsoft Defender for Cloud?**

**Answer:**
Microsoft Defender for Cloud is Azure’s **cloud security posture management and workload protection service**. It helps identify security misconfigurations, improve security posture, and—when Defender plans are enabled—provide threat protection for workloads such as servers, containers, databases, and other supported Azure resources.

### **How it fits**

```text
Azure / Hybrid / Multicloud Resources
             ↓
   Defender for Cloud
             ↓
├── Security posture
├── Recommendations
├── Secure Score
├── Regulatory/compliance views
└── Workload threat protection
```

### **Production example**

For an AKS environment, Defender for Cloud could help surface issues such as:

```text
Security recommendations
Container-related risks
Misconfiguration
Threat detections
```

For VMs, it can contribute workload-protection capabilities when the appropriate Defender plan is enabled.

### **Important distinction**

A useful distinction is:

```text
Defender for Cloud
→ posture management + workload protection
```

versus:

```text
Microsoft Sentinel
→ SIEM / security analytics / incident investigation
```

They integrate, but they solve different problems.

**Memory line:**
**Defender for Cloud helps secure the cloud environment; Sentinel helps investigate and respond to security events across environments.**

**Interview trap:**
Do not describe Defender for Cloud as only a vulnerability scanner. Its scope is broader: posture, recommendations, compliance, and workload protection.

**Keywords:**
Defender for Cloud, CSPM, workload protection, Secure Score, recommendations, threat protection

### **T11-E05. What is the shared-responsibility model?**

**Answer:**
The shared-responsibility model means **Microsoft and the customer share security responsibilities**, and the exact split depends on whether the service is IaaS, PaaS, or SaaS. Microsoft secures the underlying cloud infrastructure, while the customer remains responsible for things such as identities, data, access control, configurations, and—in IaaS—the guest OS and applications.

### **How responsibility changes**

```text
IaaS
→ customer manages more

PaaS
→ Microsoft manages more platform layers

SaaS
→ Microsoft manages most of the application stack
```

A simplified view:

```text
Customer always cares about:
├── Data
├── Identities
├── Access control
└── Correct configuration

Microsoft always cares about:
├── Physical datacenters
├── Physical networking
└── Physical hosts
```

For an Azure VM:

```text
Microsoft
→ datacenter, host hardware, hypervisor/platform

Customer
→ OS patching, application, firewall rules,
  identities, data, configuration
```

For Azure SQL Database:

```text
Microsoft
→ OS/database platform maintenance

Customer
→ database permissions, data, identity,
  network exposure, application configuration
```

### **Important distinction**

Moving to PaaS does **not** mean:

```text
"Microsoft handles all security."
```

It means Microsoft takes responsibility for more infrastructure layers, while the customer still owns secure configuration, access, and data protection.

**Memory line:**
**The more managed the service, the more platform responsibility shifts to Microsoft—but the customer still owns data, identity, and secure configuration.**

**Interview trap:**
Do not say Azure automatically secures badly configured RBAC, public endpoints, leaked credentials, or application vulnerabilities just because the workload runs in the cloud.

**Keywords:**
Shared responsibility, IaaS, PaaS, SaaS, customer responsibility, Microsoft responsibility
