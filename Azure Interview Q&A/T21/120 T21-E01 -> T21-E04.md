# **21. 🟠 IMP — DNS, Traffic Manager, Front Door & Application Gateway**

## **T21-E01. What is Azure DNS?**

**Answer:**
Azure DNS is Microsoft's **managed authoritative DNS hosting service**. It lets you host DNS zones and records on Azure's DNS infrastructure and manage them through Azure Resource Manager, CLI, PowerShell, Terraform, or the portal.

For a public domain such as:

```text
example.com
```

the flow is roughly:

```text
User asks:
www.example.com
       ↓
Recursive DNS resolver
       ↓
DNS hierarchy
       ↓
Azure DNS authoritative
name servers
       ↓
A / AAAA / CNAME etc.
       ↓
IP / hostname returned
```

The important word is **authoritative**: Azure DNS stores the official DNS records for zones you host there.

---

### **Public Azure DNS**

Suppose I own:

```text
contoso.com
```

I create an Azure Public DNS zone:

```text
contoso.com
```

Azure assigns authoritative name servers such as:

```text
ns1-xx.azure-dns.com
ns2-xx.azure-dns.net
ns3-xx.azure-dns.org
ns4-xx.azure-dns.info
```

Then at my domain registrar I delegate:

```text
contoso.com
      ↓
those Azure name servers
```

Now records such as:

```text
www.contoso.com
api.contoso.com
mail.contoso.com
```

can be hosted in Azure DNS.

Microsoft notes that the zone's NS record set is automatically populated with Azure DNS name servers when the zone is created. ([Microsoft Learn][1])

---

### **Azure DNS does not register the domain for you**

This distinction matters.

```text
Domain registrar
→ where I buy/register contoso.com

Azure DNS
→ where I host its DNS zone/records
```

For example:

```text
Registrar:
Namecheap / GoDaddy / another registrar

DNS hosting:
Azure DNS
```

I update the registrar's NS delegation to Azure.

---

### **Azure Private DNS**

Azure also provides **Azure Private DNS** for private name resolution inside Azure virtual networks.

Example:

```text
db.internal.contoso.com
        ↓
10.20.1.15
```

That private record doesn't have to be exposed to the public internet.

Conceptually:

```text
VNet A ─┐
        ├── Private DNS Zone
VNet B ─┘
             ↓
     private service names
```

This becomes extremely important with:

```text
Private Endpoints
AKS
VMs
internal applications
hub-spoke networks
```

Azure Private DNS supports common types including A, AAAA, CNAME, MX, PTR, SOA, SRV, and TXT. ([Microsoft Learn][2])

---

### **Public DNS vs Private DNS**

```text
Azure Public DNS
→ publicly authoritative domain records

Azure Private DNS
→ private name resolution for linked VNets
```

Example:

```text
Public:
www.contoso.com
→ public application endpoint

Private:
sql.internal.contoso.com
→ 10.10.2.4
```

---

### **Common record types**

Azure DNS supports common DNS records such as:

```text
A
→ hostname → IPv4

AAAA
→ hostname → IPv6

CNAME
→ hostname → another hostname

MX
→ mail server

TXT
→ arbitrary text / verification

NS
→ authoritative name server

SRV
→ service location

PTR
→ reverse lookup
```

Microsoft's current Azure DNS documentation lists A, AAAA, CAA, CNAME, MX, NS, PTR, SOA, SRV, and TXT among supported public-zone types. ([Microsoft Learn][1])

---

### **Azure DNS vs DNS resolver**

A common confusion:

```text
Azure DNS zone
```

isn't simply a general-purpose DNS resolver.

Public Azure DNS is primarily:

```text
authoritative hosting
```

for zones you manage.

For Azure hybrid/private recursive DNS scenarios, services such as:

```text
Azure DNS Private Resolver
```

solve a different problem.

---

### **Strong interview answer**

> “Azure DNS is Microsoft's managed authoritative DNS hosting service. I can host public DNS zones such as `contoso.com` and manage A, CNAME, MX and other records using Azure Resource Manager. I still register the domain with a registrar and delegate its name servers to Azure DNS. Azure also has Private DNS zones for private name resolution inside linked VNets, which is commonly used with internal workloads and Private Endpoints.”

**Memory line:**
**Azure DNS hosts the authoritative DNS records; the registrar owns the domain registration.**

**Interview trap:**
Azure DNS is **not a domain registrar**, and an Azure DNS zone is not the same thing as Azure DNS Private Resolver.

**Keywords:**
Azure DNS, authoritative DNS, DNS zone, NS delegation, Public DNS, Private DNS

**Likely follow-ups:**

* Public DNS vs Private DNS?
* How do you move an existing domain to Azure DNS?
* What is an NS record?
* What role does DNS play with Private Endpoints?

## **T21-E02. What is an A record?**

**Answer:**
An **A record maps a DNS hostname to an IPv4 address**.

For example:

```text
www.contoso.com
       ↓
A record
       ↓
20.50.10.25
```

Microsoft describes an A record as the standard DNS record that maps a name to an IPv4 address. ([Microsoft Learn][1])

---

### **Example**

Azure DNS zone:

```text
contoso.com
```

Record:

```text
Name: www
Type: A
Value: 20.50.10.25
TTL: 300 seconds
```

The resulting FQDN is:

```text
www.contoso.com
```

and a lookup returns:

```text
20.50.10.25
```

---

### **DNS resolution**

```text
Browser
   ↓
www.contoso.com
   ↓
DNS resolver
   ↓
Azure DNS
   ↓
A = 20.50.10.25
   ↓
Browser connects to IP
```

DNS itself isn't establishing the HTTP connection.

It simply answers:

```text
Which IPv4 address
corresponds to this name?
```

---

### **A vs AAAA**

Easy interview distinction:

```text
A
→ IPv4

AAAA
→ IPv6
```

For example:

```text
A
www.contoso.com
→ 20.50.10.25

AAAA
www.contoso.com
→ 2001:db8::10
```

---

### **One name can have multiple A records**

Example:

```text
www.contoso.com
    ↓
20.1.1.10
20.1.1.11
```

Azure DNS groups records with the same name and type into a **record set**. Microsoft documents that an A record set can contain multiple records. ([Microsoft Learn][2])

This can provide DNS-level distribution, although it does not provide sophisticated application-aware load balancing by itself.

---

### **A record vs Azure alias record**

Normally:

```text
A
→ literal IPv4 address
```

Azure DNS also supports **alias record sets**, where an A record can reference an Azure resource such as a Public IP resource.

```text
A alias
      ↓
Azure Public IP resource
```

Then Azure can track the Azure resource dynamically rather than you hardcoding its current IP. ([Microsoft Learn][3])

This is especially useful for Azure-managed targets.

---

### **Troubleshooting**

Useful commands:

```bash
nslookup www.contoso.com
```

or:

```bash
dig www.contoso.com A
```

I verify:

```text
expected hostname
      ↓
expected IPv4
```

If DNS returns the wrong IP, I troubleshoot DNS before debugging HTTP/TLS.

---

### **Strong interview answer**

> “An A record maps a DNS hostname to an IPv4 address. For example, `www.contoso.com` might have an A record pointing to `20.50.10.25`. A single record set can contain multiple IPv4 addresses, and Azure DNS also supports alias A records that can point dynamically to supported Azure resources such as a Public IP.”

**Memory line:**
**A = Address = hostname to IPv4.**

**Interview trap:**
An A record points to an **IPv4 address**, not another hostname—that is normally the role of CNAME.

**Keywords:**
A record, IPv4, hostname, FQDN, record set, Azure DNS alias

**Likely follow-ups:**

* A vs AAAA?
* A vs CNAME?
* Can one A record set contain multiple IPs?
* How would you troubleshoot an incorrect A record?

## **T21-E03. What is a CNAME record?**

**Answer:**
A **CNAME, or Canonical Name, record maps one DNS hostname to another hostname rather than directly to an IP address**.

Example:

```text
www.contoso.com
       ↓
CNAME
       ↓
app.azurewebsites.net
       ↓
A/AAAA lookup
       ↓
actual IP
```

So:

```text
A record
→ name → IPv4

CNAME
→ name → another DNS name
```

---

### **Example**

Suppose App Service gives me:

```text
myapp.azurewebsites.net
```

I want users to access:

```text
www.contoso.com
```

DNS could contain:

```text
www.contoso.com
CNAME
myapp.azurewebsites.net
```

Then resolution conceptually becomes:

```text
www.contoso.com
       ↓
myapp.azurewebsites.net
       ↓
20.x.x.x
```

The actual service's IP can change while my custom hostname continues referencing its canonical DNS name.

---

### **Why CNAME is useful**

Imagine I point:

```text
www.contoso.com
```

directly to:

```text
20.1.1.10
```

and the provider later changes its IP.

I must update my A record.

With:

```text
www.contoso.com
      ↓
CNAME
      ↓
provider.example.net
```

the provider controls the underlying address resolution.

That creates useful abstraction:

```text
My hostname
→ provider hostname
→ actual infrastructure
```

---

### **Important restriction: CNAME can't coexist with other records at the same name**

DNS standards don't permit a CNAME record set and another record type with the same owner name.

So this is invalid:

```text
www.contoso.com CNAME app.example.net
www.contoso.com A     20.1.1.10
```

Azure DNS enforces this restriction. ([Microsoft Learn][1])

Also, an Azure CNAME record set contains only one CNAME record. ([Microsoft Learn][4])

---

### **CNAME at the zone apex**

Suppose your zone is:

```text
contoso.com
```

The apex is:

```text
contoso.com
```

represented as:

```text
@
```

A normal CNAME can't be placed there because the apex already needs:

```text
NS
SOA
```

records.

Microsoft explicitly notes that DNS standards prevent a CNAME at the zone apex. ([Microsoft Learn][1])

---

### **Azure solves some apex scenarios using Alias records**

Suppose I want:

```text
contoso.com
```

to point to an Azure resource.

Azure DNS supports **Alias record sets** for A/AAAA/CNAME in supported scenarios. ([Microsoft Learn][3])

So rather than breaking DNS rules with:

```text
@ CNAME ...
```

I may use:

```text
@ A Alias
   ↓
supported Azure resource
```

depending on the architecture.

---

### **CNAME does not redirect the browser**

Very common interview mistake.

CNAME:

```text
www.contoso.com
→ app.example.net
```

does **not** tell the browser:

```text
HTTP 301
Location: app.example.net
```

The browser can still display:

```text
www.contoso.com
```

DNS simply helps determine where that hostname resolves.

So:

```text
CNAME
≠ HTTP redirect
```

---

### **Strong interview answer**

> “A CNAME record maps one DNS hostname to another hostname. For example, `www.contoso.com` could be a CNAME for `myapp.azurewebsites.net`, and DNS then resolves the target hostname to its final address. Unlike an A record, a CNAME doesn't directly contain an IPv4 address. A CNAME also can't coexist with another record type at the same name, and normal DNS rules prevent using CNAME at the zone apex because the apex already contains NS and SOA records.”

**Memory line:**
**CNAME = hostname alias to another hostname.**

**Interview trap:**
A CNAME is **not an HTTP redirect** and normally cannot be used at a DNS-zone apex.

**Keywords:**
CNAME, canonical name, alias, hostname, zone apex, A record

**Likely follow-ups:**

* A vs CNAME?
* Why can't CNAME be used at the zone apex?
* What is an Azure Alias record?
* Does CNAME change the URL users see?

## **T21-E04. What is DNS TTL?**

**Answer:**
DNS TTL, or **Time To Live**, specifies **how long a DNS response may be cached before a resolver or client should query DNS again for fresh information**.

Example:

```text
www.contoso.com
A = 20.1.1.10
TTL = 300 seconds
```

A resolver can cache that answer for approximately:

```text
5 minutes
```

before it needs to refresh it.

Microsoft defines TTL as how long DNS clients/resolvers can cache a record before querying again. In Azure DNS, TTL is configured at the **record-set level**. ([Microsoft Learn][5])

---

### **Resolution example**

First request:

```text
Client
  ↓
DNS resolver
  ↓
Azure DNS
  ↓
20.1.1.10
TTL = 300
```

Resolver caches:

```text
www.contoso.com
→ 20.1.1.10

for up to 300 seconds
```

Another user asks 60 seconds later:

```text
Client
   ↓
Resolver cache
   ↓
20.1.1.10
```

No authoritative lookup may be needed.

After TTL expires:

```text
cache expires
      ↓
resolver queries again
      ↓
gets current DNS value
```

---

### **Why TTL matters during changes**

Suppose:

```text
Old region:
20.1.1.10

New region:
40.2.2.20
```

You modify DNS:

```text
A record:
20.1.1.10
      ↓
40.2.2.20
```

But some resolvers have cached the old value.

If:

```text
TTL = 1 hour
```

some users may continue using:

```text
20.1.1.10
```

until their cached record expires.

That's why DNS changes aren't necessarily instant from every client's perspective.

---

### **Low TTL vs high TTL**

#### Lower TTL

Example:

```text
60 seconds
```

Advantages:

```text
faster DNS change visibility
faster DNS-based failover
```

Trade-offs:

```text
more DNS queries
less caching
```

---

#### Higher TTL

Example:

```text
3600 seconds
```

Advantages:

```text
more cache reuse
fewer authoritative lookups
```

Trade-off:

```text
changes/failovers can take longer
to reach cached clients
```

---

### **Important for disaster recovery**

Imagine:

```text
Primary region
       ↓
DNS
       ↓
users
```

Primary fails and I update DNS to:

```text
Secondary region
```

If TTL is:

```text
24 hours
```

a resolver that recently cached the old record can potentially continue sending users toward the old endpoint for much longer than my desired RTO.

Therefore:

```text
DNS TTL
directly influences
DNS-based failover behavior
```

This becomes important later in:

**T21-M07. Why can DNS-based failover be slower than proxy-based failover?**

and:

**T21-H03. How could DNS caching affect a disaster-recovery failover?**

---

### **But TTL is not a perfect guarantee**

An important practical nuance:

TTL tells compliant resolvers how long the answer should be cached, but real-world behavior can be influenced by:

```text
recursive resolver behavior
client/OS caches
application caches
upstream DNS layers
```

Therefore:

```text
TTL = 60 seconds
```

does not mean:

```text
exactly every user switches
at second 61
```

Treat it as a cache-lifetime control, not a strict global cutover timer.

---

### **Azure DNS record-set behavior**

Azure DNS applies TTL to the entire:

```text
record set
```

not separately to every IP inside it.

Example:

```text
www
TTL = 300

A:
20.1.1.10
20.1.1.11
```

Both records share the same record-set TTL. ([Microsoft Learn][2])

Current Azure DNS documentation allows TTL values from **1 through 2,147,483,647 seconds**. ([Microsoft Learn][1])

---

### **Migration technique**

If I know tomorrow I'm migrating:

```text
20.1.1.10
→
40.2.2.20
```

and current TTL is:

```text
24 hours
```

I shouldn't reduce it five minutes before migration.

Instead:

```text
Well before migration
        ↓
reduce TTL
24h → 300s
        ↓
wait at least old TTL
        ↓
most old caches expire
        ↓
perform cutover
        ↓
observe
        ↓
increase TTL later
```

That's a very useful production DNS practice.

---

### **Strong interview answer**

> “DNS TTL defines how long a resolver can cache a DNS answer before requesting it again. For example, a TTL of 300 means the answer can normally be cached for five minutes. A lower TTL makes changes and DNS-based failover propagate more quickly but results in more DNS queries, while a higher TTL improves cache efficiency but can keep clients using stale records longer. In Azure DNS the TTL belongs to the record set, so all records in that set use the same TTL.”

**Memory line:**
**TTL controls how long old DNS information can remain cached.**

**Interview trap:**
Do not say a DNS change becomes globally effective exactly when the TTL expires; caching behavior across clients and resolvers can vary.

**Keywords:**
TTL, DNS cache, resolver, propagation, failover, record set, stale record

**Likely follow-ups:**

* Why lower TTL before a migration?
* How does TTL affect DR?
* Why not always use a TTL of one second?
* Is TTL configured per Azure DNS record or record set?
