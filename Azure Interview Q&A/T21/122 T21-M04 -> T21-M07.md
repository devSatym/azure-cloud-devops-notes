## **T21-M04. What is performance routing?**

**Answer:**
Traffic Manager **Performance routing** sends DNS queries to the **healthy endpoint expected to provide the lowest network latency** for the user's network.

The key distinction is:

```text
Performance routing
→ lowest expected network latency

NOT
→ geographically nearest region
```

Traffic Manager maintains an **Internet Latency Table** containing latency information between source IP ranges and Azure datacenters. It uses that information to select the best available endpoint. ([Microsoft Learn][1])

---

### **Example**

Suppose the application runs in:

```text
Central India
West Europe
East US
```

An Indian user performs DNS resolution:

```text
User
 ↓
Recursive DNS resolver
 ↓
Traffic Manager
 ↓
Internet Latency Table
 ↓
Lowest-latency healthy endpoint
 ↓
Central India
```

A European user might receive:

```text
West Europe
```

and a North American user:

```text
East US
```

assuming those are the lowest-latency healthy endpoints for their networks.

---

### **How does Traffic Manager know the user's location?**

This is an important interview nuance.

Traffic Manager normally does **not receive the DNS query directly from the end-user device**.

Instead:

```text
User
 ↓
Recursive DNS resolver
 ↓
Traffic Manager
```

Traffic Manager therefore generally sees the:

```text
recursive resolver's source IP
```

and uses that as a proxy for the client's network location.

Microsoft explicitly documents that Performance routing uses the recursive DNS service's IP address—not necessarily the client's actual IP—to determine the lowest-latency endpoint. ([Microsoft Learn][1])

---

### **Lowest latency ≠ shortest geographic distance**

Suppose:

```text
User in India

Region A:
Central India
Physical distance = smaller

Region B:
UAE / another region
Physical distance = larger
```

Internet routing can still make Region B lower latency due to:

```text
ISP routing
peering
congestion
backbone paths
```

So Traffic Manager makes its decision from latency data rather than simply:

```text
latitude + longitude
```

---

### **What if the nearest endpoint is unhealthy?**

Suppose:

```text
India user
    ↓
Central India
lowest latency
    ↓
UNHEALTHY
```

Traffic Manager removes the degraded endpoint from eligible responses and can choose the next-lowest-latency healthy endpoint.

Conceptually:

```text
Central India   25 ms   ✗
South India     40 ms   ✓
West Europe    130 ms   ✓

Result:
South India
```

Traffic Manager routing methods include health monitoring and automatic endpoint failover. ([Microsoft Learn][1])

---

### **Performance routing doesn't monitor application load**

This is another strong distinction.

Traffic Manager knows things such as:

```text
endpoint health
+
network-latency mapping
```

but Performance routing does **not dynamically inspect current CPU or request load on your application and choose the least-loaded endpoint**.

Microsoft explicitly notes that Performance routing doesn't account for real-time changes in endpoint load. ([Microsoft Learn][1])

So:

```text
Region A
Latency = 25 ms
CPU = 95%
```

Traffic Manager may still consider A the best Performance endpoint if its health probe remains healthy.

If workload load balancing matters, the application/platform needs additional mechanisms.

---

### **Multiple endpoints in the same Azure region**

If several available endpoints belong to the same region under Performance routing, Traffic Manager can distribute queries among those endpoints rather than deriving a different latency decision between effectively identical regional locations. ([Microsoft Learn][1])

For more complex policies I can use:

```text
Nested Traffic Manager profiles
```

Example:

```text
Parent
Performance
   │
   ├── India child profile
   │        ↓
   │     Weighted
   │     App A 80
   │     App B 20
   │
   └── Europe child profile
            ↓
         Weighted
```

---

### **Performance vs Geographic**

This distinction is frequently asked:

```text
Performance
→ "Which healthy endpoint should
   give this user the lowest latency?"

Geographic
→ "Which endpoint is assigned
   to this user's geographic area?"
```

Example:

A customer in France:

```text
Performance
→ could theoretically choose another
  region if latency is better

Geographic
→ France/EU mapping dictates
  where the query should go
```

So use **Performance** primarily for user experience; use **Geographic** when the routing location itself matters.

---

### **When would I use Performance routing?**

Typical use:

```text
Global public application
        ↓
same service in several regions
        ↓
users distributed globally
        ↓
want low network latency
```

Examples:

```text
global SaaS
public APIs
multiregion web applications
gaming/API endpoints
global customer portals
```

---

### **Strong interview answer**

> “Performance routing is a Traffic Manager DNS-routing method that returns the healthy endpoint expected to provide the lowest network latency for the client's network. Traffic Manager uses its Internet Latency Table rather than simply geographic distance. Because Traffic Manager usually sees the recursive DNS resolver rather than the end user's IP, that resolver's address is used as a proxy for the user. If the lowest-latency endpoint becomes unhealthy, Traffic Manager chooses another healthy region. I would use it for a globally distributed application where minimizing user latency is the main goal.”

**Memory line:**
**Performance routing = choose the healthy endpoint with the lowest expected network latency.**

**Interview trap:**
Do not say:

> “Performance routing always picks the geographically closest Azure region.”

It uses **latency data**, not simple distance.

**Keywords:**
Performance routing, latency, Internet Latency Table, recursive DNS, endpoint health, global application

**Likely follow-ups:**

* Performance vs Geographic routing?
* Does Traffic Manager see the user's actual IP?
* Does Performance routing consider backend CPU utilization?
* What happens if the lowest-latency region fails?

# **T21-M05. What is geographic routing?**

**Answer:**
Traffic Manager **Geographic routing directs DNS queries to specific endpoints based on the geographic origin of the query**.

Instead of asking:

```text
Which endpoint is fastest?
```

it asks:

```text
Which endpoint is assigned
to this geographic region?
```

Microsoft identifies common uses as:

```text
data sovereignty
content localization
regional user experience
geographic traffic measurement
```

([Microsoft Learn][1])

---

### **Example**

Suppose:

```text
Traffic Manager
Geographic routing

India
→ India application

European countries
→ Europe application

United States/Canada
→ North America application
```

Architecture:

```text
                 Traffic Manager
                  Geographic
                      │
          ┌───────────┼────────────┐
          ↓           ↓            ↓
        India        Europe    North America
          ↓           ↓            ↓
      India App    EU App       US App
```

An Indian DNS query is mapped to:

```text
India endpoint
```

even if another endpoint happens to have slightly lower measured latency.

---

### **How Traffic Manager determines geography**

Like Performance routing, Traffic Manager normally sees:

```text
recursive DNS resolver IP
```

rather than the end user's actual device IP.

Conceptually:

```text
User
 ↓
ISP / corporate DNS resolver
 ↓
Traffic Manager
 ↓
source resolver IP
 ↓
geographic lookup
 ↓
mapped endpoint
```

Microsoft explicitly states that Geographic routing uses the source IP of the DNS query, typically the local recursive DNS resolver, as a proxy for the user's geographic origin. ([Microsoft Learn][1])

---

### **Supported geographic granularity**

Traffic Manager currently supports mappings at levels such as:

```text
World
Regional grouping
Country/Region
State/Province
```

State/province-level mappings are currently supported for:

```text
Australia
Canada
United States
```

according to Microsoft's routing-method documentation. ([Microsoft Learn][1])

Example:

```text
Europe
    │
    ├── France
    ├── Germany
    └── Ireland
```

I can create more-specific mappings below broader ones.

---

### **Most-specific match wins**

Suppose:

```text
Endpoint A
→ Europe

Endpoint B
→ Ireland
```

A DNS query originating from Ireland matches:

```text
Ireland
```

rather than the broader:

```text
Europe
```

because Traffic Manager evaluates from the most specific geographic mapping upward. ([Microsoft Learn][1])

---

### **A geographic region maps to one endpoint**

This is a major behavior difference from Weighted routing.

For Geographic routing, a given geographic area is mapped deterministically to one endpoint within the profile.

You don't normally configure:

```text
India
→ Endpoint A
and
India
→ Endpoint B
```

as two independent geographic endpoint mappings in the same profile.

Microsoft imposes this restriction to keep geographic routing deterministic. ([Microsoft Learn][1])

---

### **Important health/failover nuance**

This is one of the most important advanced details.

Suppose:

```text
India
→ Endpoint A
```

and Endpoint A fails.

Traffic Manager cannot simply say:

```text
"India's endpoint failed,
so I'll use Europe's endpoint"
```

if India isn't mapped there.

For Geographic routing, Microsoft strongly recommends using **nested endpoints**, with multiple child endpoints inside each geographic destination, so each geography has its own redundancy. ([Microsoft Learn][1])

A better production design is:

```text
Parent Traffic Manager
Geographic
│
├── India
│     ↓
│   Nested profile
│   Priority
│   ├── Central India
│   └── South India
│
├── Europe
│     ↓
│   Nested profile
│   ├── West Europe
│   └── North Europe
│
└── World/default
      ↓
    redundant endpoints
```

That provides:

```text
geographic policy
+
regional failover
```

---

### **What if a geography has no mapping?**

Traffic Manager can return:

```text
NODATA
```

if the user's geographic region has no matching endpoint mapping.

Microsoft therefore recommends having a suitable:

```text
World
```

mapping as a fallback, typically using a nested endpoint with redundancy. ([Microsoft Learn][1])

---

### **Geographic routing and data residency**

Suppose a requirement says:

> European users must use the EU deployment.

Geographic routing can help implement:

```text
EU users
→ EU application endpoint
```

But this alone does **not prove full data residency compliance**.

You must still examine:

```text
database location
backup replication
telemetry/log destination
CDN/cache behavior
data export
support/control-plane behavior
```

Traffic routing is one architectural control, not the complete compliance solution.

---

### **Geographic vs Performance**

| Requirement                             | Use             |
| --------------------------------------- | --------------- |
| Lowest latency                          | **Performance** |
| India users must go to India            | **Geographic**  |
| EU content stays on EU endpoint         | **Geographic**  |
| Global users get fastest healthy region | **Performance** |

Mental model:

```text
Performance
→ FASTEST

Geographic
→ ASSIGNED LOCATION
```

---

### **Strong interview answer**

> “Geographic routing maps users to specific endpoints according to the geographic origin of their DNS queries. Traffic Manager determines that geography from the recursive DNS resolver's source IP and can map areas such as countries, regional groups, or supported states and provinces. I would use it for requirements such as localization or geographic routing controls rather than lowest-latency routing. For production I would usually map each geography to a nested profile containing redundant endpoints, because geographic mapping itself shouldn't leave an entire region dependent on one backend.”

**Memory line:**
**Geographic routing = location determines the endpoint; Performance routing = latency determines the endpoint.**

**Interview trap:**
Do not assume Geographic routing automatically fails an Indian user over to Europe if the Indian endpoint dies. Design redundancy within the geographic mapping.

**Keywords:**
Geographic routing, geography, data sovereignty, localization, recursive DNS, nested Traffic Manager

**Likely follow-ups:**

* Geographic vs Performance?
* What happens if a geographic endpoint fails?
* Why use nested profiles?
* Does Geographic routing guarantee data residency?

# **T21-M06. How does Traffic Manager differ from Front Door?**

**Answer:**
The fundamental difference is:

```text
Traffic Manager
→ global DNS-based traffic routing

Azure Front Door
→ global Layer-7 HTTP/HTTPS reverse proxy
  + application delivery/CDN capabilities
```

With Traffic Manager, DNS selects an endpoint and the **client then connects directly to that endpoint**.

With Front Door, the client connects to a Microsoft edge location, and **Front Door proxies the HTTP/HTTPS request to an origin**. Microsoft recommends Front Door when you need features such as WAF, TLS termination, caching, and advanced HTTP routing; Traffic Manager is appropriate for simple global DNS-based load balancing with direct client-to-endpoint connections. ([Microsoft Learn][2])

---

### **Traffic path comparison**

#### Traffic Manager

```text
Client
  ↓
DNS lookup
  ↓
Traffic Manager
  ↓
"Use Region A"
  ↓
Client ─────────────→ Region A
      direct traffic
```

Traffic Manager disappears from the application data path after DNS resolution.

---

#### Front Door

```text
Client
   ↓
Azure Front Door
nearest edge/PoP
   ↓
Microsoft global network
   ↓
selected origin
   ↓
Application
```

Front Door remains in the Layer-7 request path.

---

### **1. DNS vs Layer 7**

Traffic Manager understands:

```text
DNS queries
endpoint health
routing methods
```

It doesn't natively inspect:

```text
HTTP path
HTTP headers
cookies
TLS sessions
request body
```

Front Door works at Layer 7 for:

```text
HTTP
HTTPS
```

and supports application-delivery functionality. ([Microsoft Learn][2])

---

### **2. Protocol support**

Traffic Manager is DNS-based.

Because it only tells clients:

```text
"connect to this endpoint"
```

the selected endpoint can provide various protocols, such as:

```text
HTTP(S)
TCP services
other public application protocols
```

Traffic Manager itself doesn't proxy them.

Front Door is primarily for:

```text
HTTP / HTTPS
```

global application delivery. Microsoft's current load-balancing guidance categorizes Front Door as global HTTP(S) and Traffic Manager as global DNS-based routing that can direct clients regardless of the application protocol. ([Microsoft Learn][2])

---

### **3. WAF**

Need:

```text
SQL injection protection
XSS rules
managed WAF rule sets
bot/application security controls
```

Then:

```text
Azure Front Door Premium/Standard
+ appropriate WAF configuration
```

can provide edge application security.

Traffic Manager:

```text
does not inspect HTTP requests
```

so it cannot function as a WAF.

---

### **4. TLS termination**

Front Door can provide:

```text
Client
   ↓ HTTPS
Front Door
   ↓ HTTPS
Origin
```

and manage:

```text
TLS termination
certificates
custom domains
```

depending on configuration.

Traffic Manager never terminates the user's TLS session because:

```text
Client
   ↓
direct TLS connection
   ↓
selected endpoint
```

---

### **5. URL/path-based routing**

Suppose:

```text
/api/*
→ API origin

/images/*
→ storage/static origin

/*
→ web origin
```

Front Door can make this kind of Layer-7 routing decision.

Traffic Manager cannot, because:

```text
DNS query:
www.contoso.com
```

contains no request path such as:

```text
/api/orders
```

So Traffic Manager sees:

```text
hostname
```

not the eventual HTTP URL path.

---

### **6. Caching/CDN**

Front Door includes global edge-delivery/CDN capabilities and can cache suitable static content closer to users. ([Microsoft Learn][3])

Traffic Manager:

```text
does not cache application content
```

It only participates in DNS resolution.

---

### **7. Failover speed**

Traffic Manager:

```text
endpoint unhealthy
       ↓
new DNS answers change
       ↓
existing resolver caches
may still contain old answer
```

Front Door:

```text
origin unhealthy
       ↓
Front Door stops proxying
new requests to that origin
       ↓
selects healthy origin
```

so Front Door can generally provide **faster application-level failover**.

Microsoft's architecture guidance explicitly says Traffic Manager can't fail over as quickly because DNS caching and clients/resolvers that ignore TTL values can delay endpoint changes. ([Microsoft Learn][2])

---

### **8. Endpoint types**

Traffic Manager can route toward:

```text
Azure
on-premises
other clouds
external public endpoints
```

because it simply returns DNS information.

Front Door can also use a wide variety of HTTP(S) origins, including non-Azure origins, but those origins must behave as compatible web origins.

---

### **9. Client IP / traffic flow**

Traffic Manager:

```text
Client
→ backend directly
```

Backend naturally receives the connection from the client/network path, subject to intermediaries.

Front Door:

```text
Client
→ Front Door
→ origin
```

so the origin sees Front Door as the network peer and client information is propagated through appropriate forwarded headers.

That matters for:

```text
logging
security controls
allowlists
origin protection
```

---

### **10. Cost and complexity**

If all I need is:

```text
DNS-level regional failover
```

Traffic Manager can be simpler.

If I need:

```text
global web acceleration
WAF
TLS termination
CDN/cache
HTTP routing
fast origin failover
```

Front Door gives much more functionality—but naturally adds a proxy/application-delivery layer and corresponding cost.

Microsoft's reference architecture explicitly notes that Front Door generally costs more than Traffic Manager and recommends using its richer feature set when that additional functionality is needed. ([Microsoft Learn][4])

---

### **Comparison table**

| Feature                            | Traffic Manager                  | Azure Front Door                |
| ---------------------------------- | -------------------------------- | ------------------------------- |
| Scope                              | Global                           | Global                          |
| Primary mechanism                  | DNS                              | Layer-7 reverse proxy           |
| Traffic passes through service     | **No**                           | **Yes**                         |
| HTTP/HTTPS aware                   | No                               | Yes                             |
| WAF                                | No                               | Yes                             |
| TLS termination                    | No                               | Yes                             |
| Path routing                       | No                               | Yes                             |
| CDN/cache                          | No                               | Yes                             |
| Non-HTTP endpoint routing          | Yes, via DNS                     | Primarily HTTP/HTTPS            |
| DNS-cache-dependent failover       | Yes                              | Much less                       |
| Client connects directly to origin | Yes                              | No                              |
| Best fit                           | Simple global endpoint selection | Global web application delivery |

---

### **Current product note**

For new designs in 2026, I would refer to:

```text
Azure Front Door Standard
or
Azure Front Door Premium
```

rather than designing around Front Door classic, which Microsoft has announced will retire on **March 31, 2027**. ([Microsoft Learn][5])

---

### **Strong interview answer**

> “Traffic Manager and Front Door are both global traffic-distribution services, but they operate very differently. Traffic Manager is DNS-based: it returns a healthy endpoint and the client connects directly to it, so it works across different application protocols but has no WAF, TLS termination, caching, or URL routing. Front Door is a global Layer-7 reverse proxy for HTTP/HTTPS. Client traffic passes through Microsoft's edge network, so Front Door can provide WAF, TLS termination, CDN caching, path-based routing and faster origin failover. I use Traffic Manager when DNS-level global routing is sufficient and Front Door when I need full global web application delivery.”

**Memory line:**
**Traffic Manager tells the client where to go; Front Door receives the request and takes it there.**

**Interview trap:**
Do not say Traffic Manager and Front Door differ only by routing algorithms. Their **fundamental traffic architecture is different**.

**Keywords:**
Traffic Manager, Front Door, DNS, reverse proxy, Layer 7, WAF, CDN, TLS, global load balancing

**Likely follow-ups:**

* Why does Front Door fail over faster?
* Can Traffic Manager route non-HTTP applications?
* Front Door vs Application Gateway?
* Can Traffic Manager and Front Door be used together?

# **T21-M07. Why can DNS-based failover be slower than proxy-based failover?**

**Answer:**
DNS-based failover can be slower because **changing the authoritative DNS answer does not immediately invalidate DNS responses already cached by recursive resolvers, operating systems, applications, or other intermediaries**.

With a proxy such as Azure Front Door, clients continue connecting to the **same proxy endpoint**, and the proxy itself can stop routing new requests to an unhealthy backend without waiting for clients to perform a fresh DNS lookup.

Microsoft's current Azure load-balancing guidance explicitly says Traffic Manager can't fail over as quickly as Front Door because of **DNS caching and systems that don't honor DNS TTL values**. ([Microsoft Learn][2])

---

### **DNS-based failover**

Suppose:

```text
www.contoso.com
      ↓
Traffic Manager
      ↓
Region A
```

A recursive resolver caches:

```text
Region A
TTL remaining = 300 seconds
```

At 10:00:

```text
Region A fails
```

Traffic Manager detects it and now wants to return:

```text
Region B
```

But clients using the cached DNS response might still have:

```text
Region A
```

until their caches expire.

Flow:

```text
Region A fails
      ↓
Traffic Manager detects failure
      ↓
authoritative response changes
      ↓
BUT resolver cache still says A
      ↓
client continues trying A
      ↓
TTL expires
      ↓
new DNS lookup
      ↓
Region B
```

Thus actual user failover time is approximately affected by:

```text
failure detection
+
DNS caching
+
client/resolver behavior
```

---

### **Proxy-based failover**

Now consider Front Door:

```text
Client
   ↓
frontdoor.contoso.com
   ↓
Front Door
   ↓
Region A
```

Region A fails.

Front Door health probes determine:

```text
Region A unhealthy
```

Then:

```text
Client
   ↓
same Front Door endpoint
   ↓
Front Door
   ↓
Region B
```

The public hostname itself doesn't need to change from the client's perspective.

Therefore there is no requirement for:

```text
client DNS cache expiration
```

to select the new backend.

Front Door continuously probes origins and removes unhealthy ones from normal origin selection. ([Microsoft Learn][5])

---

### **Side-by-side**

#### DNS failover

```text
Client
   ↓
DNS resolver
   ↓
cached Region A
   ↓
Region A ✗

Wait for:
TTL / DNS refresh

Client
   ↓
new lookup
   ↓
Region B ✓
```

#### Proxy failover

```text
Client
   ↓
same proxy endpoint
   ↓
Proxy detects A ✗
   ↓
routes to B ✓
```

That is the core reason.

---

### **TTL matters**

Suppose:

```text
TTL = 60 seconds
```

then caches should normally refresh much sooner than with:

```text
TTL = 3600 seconds
```

But actual failover isn't simply:

```text
TTL = 60
therefore exactly 60-second RTO
```

because you also need to consider:

```text
Traffic Manager health-probe interval
number of failed probes required
DNS resolver behavior
OS/application caching
existing connections
systems that ignore TTL
```

Microsoft specifically notes that some systems don't honor DNS TTL values properly, making DNS failover potentially slower. ([Microsoft Learn][2])

---

### **Health detection time also matters**

Before DNS can even change:

```text
Traffic Manager
```

must first determine:

```text
endpoint unhealthy
```

So:

```text
Actual failover
≈ failure detection
 + DNS cache expiry
 + connection/retry behavior
```

A TTL of 30 seconds doesn't help if:

```text
health monitoring takes
another 60 seconds
```

to classify the endpoint as unhealthy.

---

### **Existing connections are another issue**

Suppose a client already has:

```text
TCP/TLS connection
→ Region A
```

DNS changing to Region B doesn't magically move that existing TCP connection.

The client/application may need to:

```text
detect connection failure
close/retry
perform fresh DNS lookup
```

depending on its implementation.

This is another reason DNS shouldn't be interpreted as instant connection migration.

---

### **Why not always use a 1-second TTL?**

Because very low TTLs can create:

```text
more DNS queries
more resolver activity
less caching efficiency
```

and still don't guarantee every resolver honors the value.

You choose TTL according to:

```text
required failover time
DNS query overhead
architecture
client behavior
```

rather than blindly choosing the minimum.

---

### **Example RTO comparison**

Suppose Traffic Manager:

```text
Health detection = ~30 sec
TTL             = 300 sec
```

Worst-case user experience might extend several minutes for a resolver that cached the previous answer just before the failure.

Front Door:

```text
Health detection
      ↓
origin removed
      ↓
new requests routed to healthy origin
```

doesn't depend on changing the user's DNS destination.

This is why Microsoft specifically recommends Front Door when a global web workload requires quicker failover. ([Microsoft Learn][6])

---

### **Does this mean Traffic Manager is bad?**

No.

Traffic Manager is excellent when I need:

```text
simple DNS-level global routing
non-HTTP protocols
direct client-to-endpoint connections
hybrid/multicloud DNS routing
```

and a DNS-based failover time is compatible with the application's RTO.

Front Door is preferable when I need:

```text
fast HTTP/HTTPS failover
global reverse proxying
WAF
TLS termination
CDN/cache
Layer-7 routing
```

The design depends on requirements.

---

### **Production design implication**

If the requirement is:

> “Fail over a global HTTPS application within seconds.”

I would strongly consider:

```text
Azure Front Door
```

rather than relying only on:

```text
Traffic Manager
+
DNS TTL
```

If the requirement says:

> “Route a public TCP service between regions with failover within several minutes.”

Traffic Manager may be entirely appropriate.

---

### **Strong interview answer**

> “DNS-based failover can be slower because once a DNS resolver has cached an endpoint, changing the authoritative DNS answer doesn't immediately replace that cached result. Traffic Manager may already know Region A is unhealthy and start returning Region B, but clients behind resolvers with the old record can continue attempting Region A until TTL expiry or a DNS refresh. With a reverse proxy such as Azure Front Door, clients continue connecting to the same Front Door endpoint; Front Door detects the unhealthy origin and routes new requests to another healthy origin internally. So proxy-based failover isn't dependent on every client's DNS cache updating.”

**Memory line:**
**DNS failover waits for clients to learn the new destination; proxy failover changes the destination behind the same client endpoint.**

**Interview trap:**
Do not claim:

```text
DNS TTL = 60 seconds
→ failover RTO = exactly 60 seconds
```

Health detection, caching behavior, existing connections, and resolver behavior also matter.

**Keywords:**
DNS caching, TTL, Traffic Manager, Front Door, proxy failover, health probes, RTO

* Why not always set TTL to one second?
* Does DNS failover move existing TCP connections?
* When would you still choose Traffic Manager over Front Door?
