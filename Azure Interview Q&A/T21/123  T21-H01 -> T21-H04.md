# **Hard**

## **T21-H01. How would you design global routing for users in India, Europe, and North America?**

**Answer:**
For a global **HTTP/HTTPS production application**, I would normally use **Azure Front Door Standard/Premium as the global entry point**, deploy application origins in India, Europe, and North America, configure health probes, and let Front Door route each request to the lowest-latency healthy origin.

If the requirement were instead **DNS-only routing, non-HTTP protocols, or direct client-to-region connections**, I would consider **Traffic Manager with Performance routing**.

The decision starts with:

```text
Global users
     ↓
Is this primarily HTTP/HTTPS?
     │
   Yes ─────────────→ Azure Front Door
     │                 global L7 proxy
     │
     No / direct endpoint desired
     ↓
Traffic Manager
Performance routing
```

Microsoft describes Front Door as a global HTTP/HTTPS application-delivery service whose origin selection can use latency, priority, weights, and health. Traffic Manager instead makes DNS-level endpoint selections. ([Microsoft Learn][1])

---

### **1. Regional deployment**

I would deploy the application close to the three main user populations:

```text
                   Azure Front Door
                     Global Edge
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
        India          Europe      North America
          │              │              │
       App/API         App/API         App/API
          │              │              │
       Regional       Regional       Regional
       backend        backend        backend
```

Possible regions might be selected based on:

```text
latency
service availability
capacity
data residency
DR requirements
cost
```

I would **not hardcode region selection solely from geography** without checking the business requirements.

---

### **2. For a web application, Front Door is usually my first choice**

Request flow:

```text
Indian user
    ↓
nearest Front Door edge
    ↓
Front Door origin selection
    ↓
healthy low-latency India origin

European user
    ↓
Front Door edge
    ↓
Europe origin

North American user
    ↓
Front Door edge
    ↓
North America origin
```

Front Door's default latency-routing behavior selects among healthy origins based on measured network latency, not merely physical distance. ([Microsoft Learn][1])

---

### **3. Create one origin group with regional origins**

Conceptually:

```text
Origin Group: global-app
│
├── origin-india
├── origin-europe
└── origin-na
```

Each origin:

```text
Enabled
Health probed
HTTPS
Correct Host header
Appropriate priority/weight
```

Front Door continually evaluates origin health and excludes unhealthy origins from normal routing. ([Microsoft Learn][2])

---

### **4. Health probes must test application health**

I wouldn't probe only:

```text
/
→ web server returns 200
```

if the application is unusable without its database.

A better endpoint might be:

```text
/health/ready
```

which verifies enough critical dependencies to answer:

> Can this region actually serve production traffic?

But I wouldn't make the probe extremely expensive either.

A good readiness check might verify:

```text
application process ✓
critical configuration ✓
database connectivity ✓
essential dependency ✓
```

while avoiding heavyweight transactions.

---

### **5. Regional failure**

Suppose India fails:

```text
India origin
     ↓
health probes fail
     ↓
Front Door removes India
from eligible origins
     ↓
Indian users
     ↓
next healthy low-latency origin
```

Perhaps:

```text
Europe
```

or another designated DR region, depending on routing configuration.

Front Door also supports **priority routing**, so if business policy requires a specific backup sequence I can use priorities rather than purely latency-based selection. ([Microsoft Learn][1])

---

### **6. Data architecture matters just as much as traffic routing**

Global frontend routing is easy compared with the database problem.

I need to decide:

```text
Application layer
→ active-active?

Database
→ single writer?
→ multi-region writes?
→ read replicas?
→ geo-replication?
```

For example:

```text
India App ──────┐
Europe App ─────┼──→ globally replicated data platform
NA App ─────────┘
```

or:

```text
India / EU / NA apps
       ↓
Primary database region
       ↓
regional replicas
```

The correct design depends on:

```text
RPO
RTO
consistency requirements
write locality
data sovereignty
cross-region transfer cost
```

A global load balancer cannot fix a database that isn't designed for regional failure.

---

### **7. Data residency may override latency**

Suppose European customer data must remain in Europe.

Then:

```text
EU user
→ EU application
→ EU data plane
```

may be mandatory even if another region happens to offer marginally lower latency.

In that case I could combine:

```text
routing rules
+
separate domains
+
application-level tenant routing
+
regional data boundaries
```

depending on the requirement.

So:

```text
Performance routing
≠ data-residency control by itself
```

---

### **8. Origin security**

If Front Door is the public entry point, I don't want attackers simply bypassing it:

```text
Attacker
   ↓
regional origin public address
   ↓
bypass Front Door/WAF
```

I would therefore restrict origin exposure using the supported architecture, potentially involving:

```text
Front Door Premium
Private Link to supported origins

or

origin network restrictions
service tags / header validation
where appropriate
```

depending on the backend service.

Then:

```text
Internet
   ↓
Front Door + WAF
   ↓
approved origin path
   ↓
regional application
```

---

### **9. Add WAF and TLS centrally**

A big advantage of Front Door for global web apps:

```text
Client
 ↓ HTTPS
Front Door
 ├── TLS termination
 ├── WAF
 ├── routing
 └── optional caching
 ↓ HTTPS
Origin
```

This gives one global security/application-delivery layer rather than exposing every regional deployment independently.

---

### **10. When would I choose Traffic Manager instead?**

If the application uses:

```text
non-HTTP TCP service
direct client-to-region communication
multi-cloud endpoint routing
simple DNS-level regional selection
```

I may use:

```text
Traffic Manager
Performance routing
```

Architecture:

```text
                   Traffic Manager
                      DNS
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
      India          Europe           NA
```

For each DNS lookup, Traffic Manager chooses the healthy endpoint expected to have the best network performance.

But after DNS:

```text
Client
   ↓
regional endpoint directly
```

Traffic Manager is no longer in the application traffic path.

---

### **11. Front Door vs Traffic Manager decision**

| Requirement                        | Choice              |
| ---------------------------------- | ------------------- |
| Global HTTP/HTTPS app              | **Front Door**      |
| WAF                                | **Front Door**      |
| TLS termination                    | **Front Door**      |
| CDN/caching                        | **Front Door**      |
| Fast application-level failover    | **Front Door**      |
| Non-HTTP endpoint                  | **Traffic Manager** |
| Direct client-to-region connection | **Traffic Manager** |
| DNS-only multi-cloud routing       | **Traffic Manager** |

---

### **Strong interview answer**

> “For a global HTTP/HTTPS application serving India, Europe and North America, I would normally deploy the workload in suitable regions in each geography and put Azure Front Door Standard or Premium in front. Each regional deployment becomes an origin, Front Door health-probes them and routes requests toward the lowest-latency healthy origin. If one region fails, it removes that origin and routes new requests to another healthy region. I would also design the database for regional failure, because global traffic routing alone doesn't provide data HA. If data-residency rules apply, those override pure latency routing. For a non-HTTP service or when I specifically want DNS-based direct client-to-region routing, I would use Traffic Manager Performance routing instead.”

**Memory line:**
**Global web app → Front Door edge + healthy regional origins; DNS/direct/non-HTTP → consider Traffic Manager.**

**Interview trap:**
Do not design only:

```text
global traffic routing
```

and forget:

```text
global data availability
```

A healthy secondary application region is useless if it can't reach or recover the data it needs.

**Keywords:**
Front Door, Traffic Manager, origin group, latency routing, health probe, multi-region, WAF, DR

**Likely follow-ups:**

* Why Front Door instead of Traffic Manager?
* How would you protect the regional origins from direct access?
* How would you handle data residency?
* What happens if the India region fails?

## **T21-H02. How would you migrate traffic between two Azure regions without downtime?**

**Answer:**
I would deploy and validate the new region **before sending production traffic to it**, synchronize any required state/data, then gradually shift traffic using **weighted routing**, continuously monitoring health and business metrics. If anything degrades, I immediately shift traffic back.

The high-level process is:

```text
Region A
Current production
      ↓
Build Region B
      ↓
Validate B
      ↓
Synchronize state/data
      ↓
1–5% traffic
      ↓
10%
      ↓
25%
      ↓
50%
      ↓
100%
      ↓
keep A temporarily
for rollback
```

For HTTP/HTTPS, I would generally prefer **Front Door weighted origin routing** because it makes request-level proxy decisions. Traffic Manager Weighted routing can also be used, but its distribution is DNS-based and therefore affected by caching. Front Door currently supports priority, latency, and weighted origin-routing behavior among healthy origins. ([Microsoft Learn][1])

---

### **1. Build Region B first**

Never:

```text
Turn Region A off
      ↓
start building Region B
```

Instead:

```text
              Existing Region A
                    LIVE
                      │
                      │
              Global routing layer
                      │
          ┌───────────┴────────────┐
          ↓                        ↓
Region A                       Region B
100% traffic                   0% traffic
LIVE                           READY
```

Region B should already have:

```text
infrastructure
application version
configuration
secrets/access
networking
monitoring
health checks
database connectivity
capacity
```

before receiving real users.

---

### **2. Keep infrastructure identical through IaC**

I would deploy both environments through:

```text
Terraform
Bicep
GitOps
```

rather than manually cloning portal configuration.

For example:

```text
modules/app-region

region_a:
centralindia

region_b:
southindia
```

This minimizes migration surprises such as:

```text
missing NSG rule
wrong Managed Identity
missing diagnostic settings
different SKU
incorrect application setting
```

---

### **3. Solve data migration before traffic migration**

This is where many “zero-downtime” migration plans fail.

If Region A contains:

```text
database
user sessions
files
queues
```

I need a migration strategy.

Possible patterns:

```text
database replication
geo-replication
read replicas
dual writes
change-data capture
shared managed data service
object replication
```

depending on the service.

Before shifting traffic:

```text
Region A data
       ↓
continuous replication
       ↓
Region B data
```

must satisfy the required:

```text
RPO
consistency
```

---

### **4. Make application changes backward compatible**

During migration, both versions/regions may operate simultaneously.

Therefore database changes should usually be compatible with both.

For example:

```text
Phase 1
Add new nullable column
      ↓
old + new app can run

Phase 2
migrate/backfill
      ↓
shift traffic

Phase 3
remove old schema
after Region A retired
```

Not:

```text
breaking DB migration
      ↓
Region A immediately stops working
```

because then rollback becomes impossible.

---

### **5. Start with tiny traffic**

Example:

```text
Region A = 99
Region B = 1
```

I watch:

```text
HTTP 5xx
latency
CPU/memory
dependency errors
database connections
queue backlog
business transaction success
```

If Region B looks good:

```text
99/1
 ↓
95/5
 ↓
90/10
 ↓
75/25
 ↓
50/50
 ↓
25/75
 ↓
0/100
```

There doesn't have to be this exact sequence—the important part is staged exposure.

---

### **6. Use business metrics, not only infrastructure metrics**

Suppose Region B shows:

```text
CPU = 25%
Memory = 40%
HTTP 200 = high
```

but:

```text
payment success
95% → 70%
```

Then migration is failing.

I monitor:

```text
technical:
latency
5xx
saturation
availability

business:
checkout success
login success
orders/min
payments/min
```

Rollout decisions need both.

---

### **7. Define rollback thresholds before migration**

For example:

```text
Region B:

5xx > 2%
OR
P95 latency > 800 ms
OR
payment success < 98%
      ↓
STOP migration
      ↓
route traffic back to A
```

Predefined thresholds prevent engineers from improvising during an incident.

---

### **8. Front Door approach**

For HTTP/HTTPS:

```text
Azure Front Door
      │
      ├── Origin A
      │   weight 95
      │
      └── Origin B
          weight 5
```

Then gradually adjust.

Because Front Door is in the application traffic path:

```text
Client
  ↓
Front Door
  ↓
A or B
```

you aren't waiting for client DNS caches to change every time you adjust origin weighting.

Front Door only routes normally among eligible healthy origins. ([Microsoft Learn][1])

---

### **9. Traffic Manager approach**

With Traffic Manager:

```text
TM Weighted
│
├── Region A weight 95
└── Region B weight 5
```

This can work well, but understand:

```text
weight
→ probability of DNS endpoint selection

NOT
→ exact percentage of HTTP requests
```

Recursive DNS caching can cause actual user/request distribution to differ.

Microsoft recommends lowering Traffic Manager DNS TTL while testing or performing routing changes so fresh resolutions occur more frequently. ([Microsoft Learn][3])

---

### **10. Reduce DNS TTL in advance if using DNS migration**

Suppose existing TTL:

```text
3600 seconds
```

and at migration time you suddenly change it to:

```text
30 seconds
```

Resolvers that already cached:

```text
3600
```

don't magically obey the new 30-second value.

So:

```text
well before migration
       ↓
lower TTL
       ↓
wait for old TTL caches to expire
       ↓
start weighted migration
```

This is the correct sequence.

---

### **11. Don't immediately destroy Region A**

After reaching:

```text
A = 0%
B = 100%
```

I keep A available for a defined rollback period.

```text
Region B
100%
     ↓
monitor
     ↓
24h / appropriate validation window
     ↓
declare stable
     ↓
retire Region A
```

If a delayed issue appears:

```text
B → A rollback
```

remains possible.

---

### **12. “Zero downtime” means eliminating user-visible interruption**

I wouldn't promise mathematically absolute zero downtime.

I would say:

> “I would design the migration to avoid planned user-visible downtime.”

Because real systems still face:

```text
DNS caching
long-lived connections
session state
database cutover
client retries
unexpected dependencies
```

which have to be engineered carefully.

---

### **Strong interview answer**

> “I would deploy Region B completely while Region A remains live, ensure the application and database are compatible across both regions, and replicate any required state. Then I would introduce Region B gradually using weighted traffic—preferably Front Door for an HTTP application, or Traffic Manager Weighted when DNS-level routing is appropriate. I start with perhaps 1–5%, monitor technical and business KPIs, then increase through staged percentages. Rollback thresholds are defined before the change, and Region A stays operational until Region B has been stable for the agreed validation period. If Traffic Manager is used, I lower DNS TTL well in advance because cached DNS answers can delay traffic shifts.”

**Memory line:**
**Build first, replicate state, shift traffic gradually, measure, and keep the old region ready for rollback.**

**Interview trap:**
Do not begin with:

```text
DNS → Region B 100%
```

before proving Region B works under production traffic.

**Keywords:**
weighted routing, regional migration, Front Door, Traffic Manager, canary, data replication, rollback, TTL

**Likely follow-ups:**

* Why would Front Door give more precise traffic migration?
* How would you migrate a stateful database?
* What metrics determine whether you continue?
* When would you decommission Region A?

## **T21-H03. How could DNS caching affect a disaster-recovery failover?**

**Answer:**
DNS caching can **delay how quickly users learn that traffic has moved from the failed primary region to the DR region**.

Even after Traffic Manager or another authoritative DNS service stops returning the failed endpoint, recursive DNS resolvers and client-side caches can continue using the **old cached answer until its TTL expires—or potentially longer if a resolver doesn't honor TTL correctly**.

Microsoft explicitly warns that high Traffic Manager TTL values can delay endpoint failover because clients continue using cached information. ([Microsoft Learn][4])

---

### **Example**

Normal state:

```text
www.contoso.com
       ↓
Primary region
20.10.1.10

TTL = 300 sec
```

At:

```text
10:00:00
```

a DNS resolver receives:

```text
20.10.1.10
TTL 300
```

Then at:

```text
10:00:10
```

the primary region fails.

Traffic Manager detects failure and now wants to return:

```text
40.20.2.20
DR region
```

But that resolver still has:

```text
20.10.1.10
```

cached.

So:

```text
10:00:10 → Primary fails

Traffic Manager:
"Use DR" ✓

Resolver:
"I still have cached Primary" ✗

Client
    ↓
Primary
    ↓
failure
```

until a fresh resolution occurs.

---

### **Actual failover time has several components**

Think:

```text
DR failover time
≈
failure detection
+
routing decision
+
DNS cache expiry
+
application retry/reconnect
+
backend/data readiness
```

Not simply:

```text
TTL
```

---

### **1. TTL controls the caching window**

Higher TTL:

```text
TTL = 3600
```

means an answer can be cached for:

```text
1 hour
```

Advantages:

```text
fewer DNS queries
more cache efficiency
```

Disadvantage:

```text
slower DNS-based change visibility
```

Lower TTL:

```text
TTL = 30–60 sec
```

means resolvers are expected to refresh more frequently, which generally improves DNS-based failover responsiveness. Microsoft Well-Architected guidance recommends a low Traffic Manager TTL, preferably below 60 seconds, when quicker failover is important. ([Microsoft Learn][5])

---

### **2. Traffic Manager can go as low as TTL 0**

Current Traffic Manager profiles can configure TTL from:

```text
0
to
2,147,483,647 seconds
```

A TTL of `0` asks downstream resolvers not to cache the response. ([Microsoft Learn][4])

That doesn't mean I automatically use:

```text
TTL = 0
```

for everything.

There are trade-offs:

```text
more DNS queries
higher Traffic Manager DNS-query usage/cost
resolver/client behavior
```

---

### **3. TTL is not an RTO guarantee**

Suppose:

```text
TTL = 30 sec
```

but Traffic Manager health probes require:

```text
30–60 sec
```

to declare the primary unhealthy.

Then approximate user-visible failover may still be:

```text
failure detection
+
remaining cache lifetime
```

rather than exactly 30 seconds.

Also:

```text
some resolvers
may not honor TTL perfectly
```

which Microsoft explicitly calls out. ([Microsoft Learn][4])

---

### **4. Some clients may fail over while others do not**

At the same moment:

```text
Resolver A
cached 5 sec ago
TTL remaining = 295 sec

Resolver B
cache expired
      ↓
queries Traffic Manager
      ↓
gets DR
```

Result:

```text
Users behind A
→ still primary ✗

Users behind B
→ DR ✓
```

This creates a **partial failover** period.

That's why during DNS-based DR you may see:

```text
some customers recovered
some still failing
```

even though the Traffic Manager profile is already correct.

---

### **5. Existing connections aren't moved by DNS**

Suppose a client already has:

```text
TCP/TLS connection
      ↓
Primary region
```

Changing DNS:

```text
Primary
→ DR
```

does not teleport that existing connection.

The client usually must:

```text
detect failed connection
      ↓
retry/reconnect
      ↓
possibly perform fresh DNS resolution
      ↓
connect to DR
```

So application retry behavior also affects the real RTO.

---

### **6. Long-lived application DNS caches can be especially dangerous**

Some:

```text
JVM applications
connection pools
HTTP clients
DNS caching libraries
proxies
```

may maintain resolved addresses longer than expected depending on configuration.

So for critical DR testing I test not only:

```text
nslookup
```

but the **actual application/client behavior**.

---

### **7. Lower TTL before planned failover**

For a planned regional migration or DR exercise:

Current:

```text
TTL = 3600
```

I might do:

```text
T-24h or appropriate lead time
       ↓
TTL 3600 → 60
       ↓
wait until old cached TTLs
have naturally expired
       ↓
perform migration
```

If I reduce TTL at the exact cutover moment:

```text
old cached answers
still retain old TTL
```

so the change doesn't provide immediate benefit.

---

### **8. Emergency outage is different**

During an unexpected outage, I cannot go backward in time and lower already-cached TTLs.

If:

```text
TTL was 1 hour
```

some users could remain affected substantially longer even after DNS authoritative routing switches.

This is why the TTL should be part of the **DR design before the incident**, not something considered only during the outage.

---

### **9. Proxy-based failover avoids much of this problem**

Front Door model:

```text
Client
   ↓
same Front Door hostname
   ↓
Front Door
   ├── Primary ✗
   └── DR ✓
```

Client DNS destination doesn't need to change during an origin failure.

Front Door changes:

```text
origin selection
```

inside the proxy layer.

That's one reason a global HTTP application with an aggressive RTO often benefits from Front Door rather than relying solely on DNS failover.

---

### **10. DR testing**

During DR testing I measure:

```text
T0
Primary becomes unavailable

T1
Traffic Manager sees unhealthy

T2
new DNS lookups return DR

T3
majority of client journeys recover
```

These aren't necessarily the same timestamp.

I would test from:

```text
different ISPs
different geographic locations
corporate DNS
public recursive resolvers
real application clients
```

Microsoft recommends testing Traffic Manager failover from multiple clients/locations and lowering TTL during testing. ([Microsoft Learn][3])

---

### **Strong interview answer**

> “DNS caching can extend the real RTO of a DNS-based DR design. Traffic Manager might already mark the primary region unhealthy and return the DR endpoint for new DNS queries, but resolvers or clients that cached the old primary can continue using it until the TTL expires. So actual failover is determined by health-detection time, remaining DNS cache lifetime, client DNS behavior and retry/reconnection behavior. I choose a suitably low TTL before an incident and test failover from real clients. If the HTTP workload requires failover in seconds without depending on client DNS refresh, I would consider a proxy-based service such as Front Door.”

**Memory line:**
**Traffic Manager can change the answer immediately; cached resolvers may not ask the question again immediately.**

**Interview trap:**
Do not say:

```text
TTL 60
=
guaranteed 60-second DR RTO
```

It is only one component of failover time.

**Keywords:**
DNS caching, TTL, Traffic Manager, DR, RTO, resolver, stale DNS, Front Door

**Likely follow-ups:**

* How low can Traffic Manager TTL be?
* Why lower TTL before migration rather than during it?
* Why is Front Door failover faster?
* Do existing TCP connections move when DNS changes?

## **T21-H04. How would you troubleshoot a domain that resolves correctly externally but incorrectly inside an Azure VNet?**

**Answer:**
If a domain resolves correctly from the public internet but returns a different IP, `NXDOMAIN`, or another incorrect response inside an Azure VNet, I immediately suspect **split-horizon/private DNS, a VNet-linked Private DNS zone, custom DNS servers, or incorrect DNS forwarding**.

My diagnostic order would be:

```text
Confirm exact internal result
       ↓
Identify DNS server being queried
       ↓
Compare public vs internal answer
       ↓
Check VNet DNS configuration
       ↓
Check Private DNS zones + VNet links
       ↓
Check custom DNS / forwarding
       ↓
Private Endpoint DNS?
       ↓
Cache?
```

Microsoft's current Azure troubleshooting guidance lists unlinked/misconfigured Private DNS zones, stale/missing records, and incorrect custom-DNS forwarding as common causes of private/public resolution differences. ([Microsoft Learn][6])

---

### **1. Prove the difference first**

From the affected VM/pod:

```bash
nslookup app.contoso.com
```

Record:

```text
DNS server queried
answer returned
TTL
```

Then query a known public resolver if network policy permits:

```bash
nslookup app.contoso.com 8.8.8.8
```

Example:

```text
Internal resolver:
app.contoso.com
→ 10.10.2.15

Public DNS:
app.contoso.com
→ 20.40.50.60
```

Now I know:

```text
DNS itself is split
```

rather than debugging:

```text
NSG
TLS
application
```

first.

---

### **2. Find which DNS server the VM is actually using**

Inside Azure, the VNet may use:

```text
Azure-provided DNS

or

Custom DNS
├── Active Directory DNS
├── DNS VM
├── Azure Firewall DNS proxy
├── NVA
└── other resolver
```

Check VNet:

```text
Virtual Network
   ↓
DNS servers
```

If custom servers are configured:

```text
10.10.0.4
10.10.0.5
```

then those become my first investigation target.

Microsoft specifically recommends checking the VNet's `dhcpOptions.dnsServers` when diagnosing private DNS issues. ([Microsoft Learn][6])

---

### **3. Check for split-horizon DNS**

This may actually be intentional.

Azure supports having:

```text
Public zone:
contoso.com

Private zone:
contoso.com
```

so:

```text
Internet user
→ www.contoso.com
→ PUBLIC IP

Azure VNet user
→ www.contoso.com
→ PRIVATE IP
```

This is called:

```text
split-horizon / split-brain DNS
```

and Azure Private DNS explicitly supports this scenario. ([Microsoft Learn][7])

So the first question is:

> Is the different internal result actually expected?

---

### **4. Private DNS zone can shadow the public zone**

Suppose someone created:

```text
Private DNS zone:
contoso.com
```

and linked it to:

```text
VNet A
```

but added only:

```text
db.contoso.com
```

Inside VNet A, a query for:

```text
app.contoso.com
```

can now be affected by the private-zone authority rather than simply falling through to the public zone.

This can produce:

```text
NXDOMAIN internally
```

while:

```text
app.contoso.com
```

works correctly from the internet.

Microsoft's recent troubleshooting guidance specifically describes Private DNS zones overriding public namespaces and causing internal `NXDOMAIN`. ([Microsoft Learn][8])

---

### **5. Inspect Private DNS zones and VNet links**

I check:

```text
Private DNS zones
      ↓
Is there a zone matching:
contoso.com
or
privatelink.<service-domain>?
```

Then:

```text
Virtual network links
```

Questions:

```text
Is this VNet linked?
Is the correct VNet linked?
Is the link state completed?
Is the required A record present?
Is the A record stale?
```

Microsoft identifies a missing Private DNS VNet link as one of the most common causes of private endpoint DNS failures. ([Microsoft Learn][6])

---

### **6. Private Endpoint scenario**

Suppose:

```text
storageaccount.blob.core.windows.net
```

from outside resolves through the public service path.

Inside the VNet it should ultimately resolve toward:

```text
privatelink.blob.core.windows.net
        ↓
10.x.x.x
```

for the Private Endpoint.

If instead internal resolution returns:

```text
public IP
```

I check:

```text
Private Endpoint approved?
Private DNS zone correct?
A record exists?
VNet linked?
Custom DNS forwarding configured?
```

Microsoft's current Private Link diagnostic guide specifically treats **public-IP resolution or NXDOMAIN inside the VNet** as signs of Private DNS/forwarding problems. ([Microsoft Learn][6])

---

### **7. Check custom DNS forwarding**

Very common architecture:

```text
Azure VM
   ↓
AD DNS server
10.0.0.4
   ↓
?
```

The custom DNS server needs to know how to resolve:

```text
Azure private namespaces
```

Possible architecture:

```text
VM
 ↓
Custom DNS
 ↓ conditional forwarding
Azure DNS Private Resolver
 ↓
Azure Private DNS
```

For DNS servers physically running **inside an Azure VNet**, forwarding appropriately toward Azure's resolver infrastructure can also be part of the design. But clients outside Azure should not be configured to query `168.63.129.16` directly because that virtual IP is only reachable from within Azure VNets. Microsoft specifically warns about this in hybrid DNS troubleshooting. ([Microsoft Learn][9])

---

### **8. Preferred hybrid pattern: Azure DNS Private Resolver**

For enterprise hybrid DNS:

```text
On-prem client
      ↓
On-prem DNS
      ↓
conditional forwarder
      ↓
Azure DNS Private Resolver
Inbound Endpoint
      ↓
Azure Private DNS
```

And for Azure-to-on-prem resolution:

```text
Azure workload
      ↓
Private Resolver
Outbound Endpoint
      ↓
Forwarding ruleset
      ↓
On-prem DNS
```

This is cleaner than maintaining ad-hoc DNS forwarder VMs just for hybrid resolution.

---

### **9. Compare queries against each resolver**

For example:

```bash
nslookup app.contoso.com 10.10.0.4
```

versus:

```bash
nslookup app.contoso.com 10.10.0.5
```

If:

```text
DNS1 → correct
DNS2 → wrong
```

I've isolated the problem.

Then inspect:

```text
zone data
conditional forwarders
DNS cache
forwarding rules
```

on DNS2.

---

### **10. Check stale caches**

Suppose DNS configuration was fixed five minutes ago.

The VM still gets:

```text
old IP
```

or:

```text
NXDOMAIN
```

because negative/positive responses can be cached.

Microsoft's recent Azure DNS troubleshooting guidance explicitly lists stale negative-cache entries as a cause of continued `NXDOMAIN` after the underlying DNS configuration has been corrected. ([Microsoft Learn][8])

Possible troubleshooting actions depend on OS/resolver, for example inspecting/clearing:

```text
OS DNS cache
systemd-resolved cache
Windows DNS cache
custom DNS server cache
```

rather than continuously editing correct DNS records.

---

### **11. Don't troubleshoot networking before proving DNS**

If internal:

```text
app.contoso.com
→ 10.0.0.5
```

but expected:

```text
20.40.50.60
```

then:

```text
curl app.contoso.com
```

is testing the wrong destination.

My order is:

```text
DNS answer
      ↓
correct IP?
      ↓
then TCP
      ↓
then TLS
      ↓
then HTTP
```

not:

```text
change NSGs randomly
```

---

### **12. Troubleshooting tree**

```text
External correct
Internal wrong
       ↓
Which DNS server answers internally?
       ↓
Azure default or custom?
       │
       ├── Azure default
       │      ↓
       │ Private DNS zone linked?
       │ Duplicate/split zone?
       │ Wrong/missing record?
       │ Private Endpoint DNS?
       │
       └── Custom DNS
              ↓
         Zone exists locally?
         Conditional forwarder?
         Private Resolver path?
         UDP/TCP 53 path?
         stale cache?
```

### **Example**

External:

```text
api.contoso.com
→ 20.40.50.10
```

Inside VM:

```text
api.contoso.com
→ NXDOMAIN
```

I discover:

```text
Private DNS zone:
contoso.com

linked to:
prod-vnet

records:
db.contoso.com only
```

The private zone is shadowing the public namespace.

The fix may be to:

```text
remove unnecessary private zone

or

populate the required private record

or

redesign the split-horizon namespace
```

depending on intent.

I would **not** change public Azure DNS because public resolution was already correct.

### **Strong interview answer**

> “If a name resolves correctly externally but incorrectly inside an Azure VNet, I first compare the exact answers and identify which DNS resolver the internal workload is using. Then I check the VNet DNS-server configuration, because it may be using Azure-provided DNS or custom AD/NVA resolvers. Next I inspect Private DNS zones and their VNet links for an intentional or accidental split-horizon namespace. A private zone with the same namespace as the public domain can shadow public records and even return NXDOMAIN for records it doesn't contain. For Private Endpoint names I verify the `privatelink` zone, A record and VNet link. If custom DNS is used, I validate conditional forwarding to Azure DNS Private Resolver or the appropriate Azure DNS path. Finally I check stale positive or negative caches before touching networking or the application.”

**Memory line:**
**External correct + internal wrong = investigate the internal resolver, private-zone authority, VNet link, and forwarding path first.**

**Interview trap:**
Do not assume:

```text
public DNS is correct
→ Azure VM must get the same answer
```

Azure can intentionally use **split-horizon Private DNS**, and a private zone can override the public namespace for linked VNets. ([Microsoft Learn][7])
