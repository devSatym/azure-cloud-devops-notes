## **T21-E05. What is Traffic Manager?**

**Answer:**
Azure Traffic Manager is a **DNS-based global traffic-routing service** that directs users to the most appropriate healthy application endpoint based on a configured routing method.

The most important point is:

```text
Traffic Manager
→ makes a DNS routing decision

It does NOT proxy
the user's application traffic
```

Microsoft currently describes Traffic Manager as a **DNS-based traffic load balancer** for public-facing applications, with endpoint health monitoring and automatic failover capabilities. ([Microsoft Learn][1])

---

### **How it works**

Suppose I have the same application in:

```text
Central India
West Europe
East US
```

Architecture:

```text
                  Azure Traffic Manager
                         DNS
                          │
              ┌───────────┼───────────┐
              ↓           ↓           ↓
          India App   Europe App   US App
```

A user requests:

```text
www.contoso.com
```

Conceptually:

```text
User
 ↓
DNS resolver
 ↓
Traffic Manager profile
 ↓
Traffic-routing method
+
endpoint health
 ↓
DNS response containing
selected endpoint
 ↓
Client connects DIRECTLY
to that endpoint
```

Traffic Manager is therefore primarily in the:

```text
DNS resolution path
```

not the subsequent application-data path.

Microsoft explicitly says clients connect directly to the endpoint selected through DNS. ([Microsoft Learn][2])

---

### **Example**

Suppose:

```text
India endpoint:
india.contoso.com

Europe endpoint:
europe.contoso.com
```

Traffic Manager profile:

```text
contoso.trafficmanager.net
```

Your custom DNS name might point toward the Traffic Manager profile.

For an Indian user, Traffic Manager could respond with:

```text
india.contoso.com
```

depending on the routing method.

Then:

```text
Browser
   ↓
India endpoint
```

The actual HTTP requests don't normally flow through Traffic Manager.

---

### **Traffic Manager monitors endpoint health**

Traffic Manager performs health probes against endpoints.

Example:

```text
Primary region
      ↓
health probe
      ↓
Healthy ✓
```

Traffic continues there.

If:

```text
Primary
↓
Unhealthy ✗
```

Traffic Manager can stop returning that endpoint and choose another healthy endpoint according to the profile's routing method. Microsoft documents health monitoring and automatic endpoint failover as core Traffic Manager capabilities. ([Microsoft Learn][1])

---

### **Endpoints can be inside or outside Azure**

This is a big strength.

Traffic Manager endpoints can represent internet-facing services:

```text
Azure
On-premises
Another cloud
External public services
```

For example:

```text
Traffic Manager
│
├── Azure App Service
├── AWS-hosted endpoint
└── On-premises web application
```

This makes it useful for:

```text
hybrid cloud
multi-cloud
migration
DR
cloud bursting
```

Microsoft explicitly supports external, non-Azure endpoints. ([Microsoft Learn][1])

---

### **Common uses**

```text
High availability
→ primary/secondary failover

Global performance
→ send users toward low-latency region

Traffic splitting
→ weighted migration/canary

Data locality
→ geographic routing

Hybrid applications
→ Azure + external endpoints
```

---

### **Traffic Manager vs Azure Load Balancer**

Don't confuse:

```text
Azure Load Balancer
→ Layer 4
→ regional/cross-region network traffic
→ actual network traffic passes through service
```

with:

```text
Traffic Manager
→ DNS
→ global endpoint selection
→ application traffic does not pass through it
```

---

### **Traffic Manager vs Front Door**

At a very high level:

```text
Traffic Manager
→ DNS-based

Front Door
→ global Layer 7 reverse proxy
```

This matters for:

```text
failover speed
WAF
TLS termination
HTTP routing
caching
session behavior
```

We'll cover that properly in **T21-M06**.

---

### **Important DNS consequence**

Because Traffic Manager uses DNS:

```text
Traffic Manager changes endpoint
        ↓
DNS resolver may still have
old answer cached
        ↓
some clients continue
using old endpoint temporarily
```

So failover isn't necessarily instant for every existing client.

That is one of the biggest architectural differences between Traffic Manager and proxy-based services such as Front Door. Microsoft's load-balancing guidance specifically notes that DNS caching can make Traffic Manager failover slower than Front Door. ([Microsoft Learn][3])

---

> **In an interview, I would say:**
> “Azure Traffic Manager is a DNS-based global traffic-routing service. It monitors public application endpoints and, when a client performs DNS resolution, returns an appropriate healthy endpoint according to a routing method such as priority, weighted, performance or geographic. The client then connects directly to that endpoint, so Traffic Manager isn't an HTTP reverse proxy and doesn't sit in the application data path. It's useful for global high availability, DR, performance routing, migrations and even hybrid or multi-cloud endpoints.”

**Memory line:**
**Traffic Manager chooses the endpoint through DNS; it doesn't carry the application traffic.**

**Interview trap:**
Do not call Traffic Manager a normal Layer-7 reverse proxy.

**Keywords:**
Traffic Manager, DNS-based load balancing, global routing, endpoint monitoring, failover, DNS TTL

**Likely follow-ups:**

* Traffic Manager vs Front Door?
* How does Traffic Manager detect failure?
* Can Traffic Manager use non-Azure endpoints?
* Why can Traffic Manager failover be delayed?

# **Medium**

## **T21-M01. What Traffic Manager routing methods are available?**

**Answer:**
Azure Traffic Manager currently supports **six routing methods**:

```text
1. Priority
2. Weighted
3. Performance
4. Geographic
5. MultiValue
6. Subnet
```

A Traffic Manager profile uses **one routing method at a time**, although more complex behavior can be built with **nested Traffic Manager profiles**. ([Microsoft Learn][4])

---

### **1. Priority**

Use when you want:

```text
Primary region
     ↓
all traffic

Secondary region
     ↓
only if primary fails
```

Example:

```text
Priority 1 → Central India
Priority 2 → South India
Priority 3 → West Europe
```

This is a typical:

```text
active-passive
```

DR design.

---

### **2. Weighted**

Use when you want to distribute DNS responses according to configured weights.

Example:

```text
Region A
Weight = 90

Region B
Weight = 10
```

Conceptually:

```text
~90% DNS selections
→ Region A

~10%
→ Region B
```

Useful for:

```text
gradual migration
canary release
A/B-style traffic distribution
blue/green transition
```

But because this is DNS-based, actual request percentages may not exactly equal the configured weights because recursive DNS caching can skew distribution. Microsoft explicitly documents this behavior. ([Microsoft Learn][4])

---

### **3. Performance**

Use when the goal is:

```text
lowest network latency
```

Example:

```text
Indian user
→ Central India

European user
→ West Europe

US user
→ East US
```

But Traffic Manager doesn't simply choose:

```text
geographically nearest
```

It uses Azure's Internet latency information to identify the endpoint expected to give the lowest latency for the DNS request's source network. ([Microsoft Learn][4])

---

### **4. Geographic**

Use when traffic must go to a specific endpoint according to user geography.

Example:

```text
India
→ India endpoint

EU
→ EU endpoint

USA
→ US endpoint
```

This is useful for:

```text
data sovereignty
content localization
regional user experience
regulatory routing
```

The goal is **geographic control**, not necessarily lowest latency. ([Microsoft Learn][4])

---

### **5. MultiValue**

MultiValue can return:

```text
multiple healthy endpoint IPs
```

in one DNS response.

Example:

```text
DNS response:

20.1.1.10
20.1.1.11
20.1.1.12
```

The client can potentially try another returned endpoint if one stops responding.

Microsoft says MultiValue works with endpoints represented as IPv4/IPv6 addresses and returns multiple healthy endpoints up to the configured response count. ([Microsoft Learn][4])

---

### **6. Subnet**

Subnet routing lets you map:

```text
source IP ranges
→ specific endpoint
```

Example:

```text
10.10.0.0/16
→ Endpoint A

10.20.0.0/16
→ Endpoint B
```

Use cases could include:

```text
specific office ranges
partner networks
ISP/network-specific routing
testing particular client groups
```

Microsoft describes it as mapping source IP ranges to specific Traffic Manager endpoints. ([Microsoft Learn][4])

---

### **Easy decision table**

| Requirement                     | Routing method  |
| ------------------------------- | --------------- |
| Primary + DR backup             | **Priority**    |
| 90/10 or migration split        | **Weighted**    |
| Lowest network latency          | **Performance** |
| Country/region-specific routing | **Geographic**  |
| Return multiple healthy IPs     | **MultiValue**  |
| Route particular IP ranges      | **Subnet**      |

---

### **Can routing methods be combined?**

Inside one profile:

```text
one routing method
```

But with nested profiles:

```text
Parent profile
Priority
      ↓
Child profile
Performance
```

Example:

```text
Primary geography
      ↓
Performance between
multiple endpoints

if whole geography fails
      ↓
Priority failover
to DR geography
```

Microsoft explicitly supports nested profiles for combining routing behaviors. ([Microsoft Learn][4])

---

> **In an interview, I would say:**
> “Traffic Manager supports six routing methods: Priority, Weighted, Performance, Geographic, MultiValue and Subnet. Priority is for active-passive failover; Weighted distributes traffic according to configured weights; Performance chooses the expected lowest-latency endpoint; Geographic maps user geography to a specific endpoint; MultiValue can return multiple healthy IP addresses; and Subnet maps source IP ranges to endpoints. One profile uses one method, but I can nest profiles when I need more complex routing.”

**Memory line:**
**Priority = failover, Weighted = percentage, Performance = latency, Geographic = location rule, MultiValue = many IPs, Subnet = source ranges.**

**Interview trap:**
Performance and Geographic are **not the same**:

```text
Performance
→ fastest

Geographic
→ required geographic mapping
```

**Keywords:**
Priority, Weighted, Performance, Geographic, MultiValue, Subnet, nested profile

**Likely follow-ups:**

* Priority vs Weighted?
* Performance vs Geographic?
* Can you combine routing methods?
* Which method would you use for DR?

## **T21-M02. What is priority routing?**

**Answer:**
Traffic Manager **Priority routing** is used for an **active-passive or primary-backup architecture**.

You give each endpoint a priority:

```text
Priority 1
→ primary

Priority 2
→ first backup

Priority 3
→ second backup
```

Traffic Manager normally returns the **highest-priority healthy endpoint**. If that endpoint becomes unhealthy, Traffic Manager moves to the next healthy endpoint. ([Microsoft Learn][4])

---

### **Example**

```text
Traffic Manager
      │
      ├── Priority 1
      │   Central India
      │
      ├── Priority 2
      │   South India
      │
      └── Priority 3
          West Europe
```

Normal state:

```text
Central India healthy
        ↓
all new DNS decisions
→ Central India
```

Then:

```text
Central India fails
        ↓
health probes fail
        ↓
Traffic Manager
chooses Priority 2
        ↓
South India
```

If South India is also unavailable:

```text
Priority 3
→ West Europe
```

---

### **Lower number means higher priority**

Microsoft currently supports endpoint priority values from:

```text
1–1000
```

with:

```text
1
→ highest priority
```

Endpoints in the same profile can't share the same explicit priority value. ([Microsoft Learn][4])

---

### **Typical use: Disaster Recovery**

Architecture:

```text
                   Traffic Manager
                         │
                Priority routing
                         │
             ┌───────────┴────────────┐
             ↓                        ↓
       Primary Region             DR Region
       Central India              South India
       Priority 1                 Priority 2
```

Normal:

```text
100% → Primary
```

Disaster:

```text
Primary unhealthy
      ↓
new DNS responses
      ↓
DR endpoint
```

This makes Priority routing a natural choice for:

```text
active-passive DR
```

---

### **Health monitoring drives failover**

Priority isn't simply:

```text
If endpoint exists
→ send traffic there forever
```

Traffic Manager continually monitors endpoint health.

Selection depends on:

```text
endpoint enabled?
+
endpoint healthy?
+
endpoint priority?
```

Microsoft states that Traffic Manager uses configured endpoint status and ongoing health monitoring when applying priority routing. ([Microsoft Learn][4])

---

### **DNS caching still matters**

Suppose Traffic Manager detects failure at:

```text
10:00
```

New DNS lookups may get:

```text
DR endpoint
```

but a recursive resolver may already have:

```text
Primary endpoint
TTL remaining = 120 seconds
```

So those clients may continue attempting the old endpoint until the cached response expires.

Therefore:

```text
endpoint health failover
≠ every client instantly moves
```

This is one of the limitations of DNS-level failover. Microsoft's load-balancing guidance specifically points out DNS caching as a reason Traffic Manager can fail over more slowly than Front Door. ([Microsoft Learn][3])

---

### **Priority routing vs weighted routing**

Priority:

```text
Region A  → normally 100%
Region B  → backup only
```

Weighted:

```text
Region A  → e.g. 80%
Region B  → e.g. 20%
```

So:

```text
Priority
→ active-passive

Weighted
→ active-active / migration / traffic split
```

---

### **Production scenario**

Suppose a business says:

> Central India must serve production normally, but if it becomes unavailable, fail over to South India.

I would configure:

```text
Central India
Priority 1

South India
Priority 2
```

with an endpoint monitor such as:

```text
HTTPS
/health
```

The health endpoint should validate something meaningful enough to indicate the application can actually serve users.

Bad health check:

```text
VM responds 200
but
database completely unavailable
```

could cause Traffic Manager to keep treating an unusable application as healthy.

---

### **Strong interview answer**

> “Priority routing is Traffic Manager's active-passive routing method. Each endpoint receives a unique priority, with a lower number representing a higher priority. Traffic Manager normally returns the highest-priority healthy endpoint, and if health monitoring marks it unavailable, DNS responses move to the next available priority. I would use this for a primary region plus one or more DR regions. Because it is DNS-based, I would also consider TTL and resolver caching when estimating actual failover time.”

**Memory line:**
**Priority routing = use the primary until it fails, then move down the backup list.**

**Interview trap:**
Do not promise:

```text
Primary fails
→ every user instantly moves
```

DNS caches can still contain the old endpoint.

**Keywords:**
Priority routing, active-passive, DR, health probe, failover, DNS TTL

**Likely follow-ups:**

* What happens when the primary becomes healthy again?
* Priority vs Weighted?
* How does TTL affect failover?
* What should the health endpoint check?

## **T21-M03. What is weighted routing?**

**Answer:**
Traffic Manager **Weighted routing distributes DNS selections among healthy endpoints according to relative weights that you assign**.

Example:

```text
Blue endpoint
Weight = 90

Green endpoint
Weight = 10
```

Traffic Manager makes the Green endpoint roughly:

```text
10 / (90 + 10)
= 10%
```

likely to be selected for a DNS query, while Blue is roughly 90%.

Microsoft currently supports integer endpoint weights from **1 to 1000** and chooses available endpoints probabilistically based on those relative weights. ([Microsoft Learn][4])

---

### **How it works**

```text
DNS query
   ↓
Traffic Manager
   ↓
Healthy endpoints:

Blue = 90
Green = 10
   ↓
probabilistic selection
   ↓
DNS answer
```

The client then connects directly to the chosen endpoint.

---

### **Equal weights**

If:

```text
Endpoint A = 1
Endpoint B = 1
Endpoint C = 1
```

each has approximately:

```text
1 / 3
```

of the selection probability.

Likewise:

```text
100
100
100
```

has the same relative distribution.

Weights are **relative**, not absolute percentages.

---

### **Example: 80/20 migration**

Suppose I'm moving:

```text
old application
→ new application
```

Start:

```text
Old = 100
New = 1
```

Then gradually:

```text
Old 90
New 10
```

then:

```text
Old 50
New 50
```

then:

```text
Old 0 / disabled
New 100
```

Conceptually:

```text
Old environment ──────┐
                      ├── Traffic Manager
New environment ──────┘
```

This is useful for controlled migration.

Microsoft explicitly lists gradual application upgrades and migration scenarios as Weighted-routing use cases. ([Microsoft Learn][4])

---

### **Example: canary**

New release:

```text
v1
stable
Weight = 95

v2
new
Weight = 5
```

Observe:

```text
error rate
latency
business metrics
```

If healthy:

```text
95/5
 ↓
80/20
 ↓
50/50
 ↓
0/100
```

However, Traffic Manager operates at DNS granularity, so it's not as precise as request-level traffic splitting from a Layer-7 proxy or service mesh.

---

### **Very important: weights are not exact request percentages**

Suppose:

```text
A = 50
B = 50
```

It is tempting to say:

```text
exactly 50% of HTTP requests
go to A and B
```

That's wrong.

Traffic Manager distributes:

```text
DNS query selections
```

not individual HTTP requests.

One corporate DNS resolver might resolve:

```text
A
```

and then thousands of employees behind that resolver use the cached result.

So actual application traffic could temporarily look like:

```text
A = 80%
B = 20%
```

even though:

```text
weights = 50/50
```

Microsoft explicitly warns that recursive DNS caching can significantly skew weighted distributions when the number of clients/resolvers is small. ([Microsoft Learn][4])

---

### **DNS caching example**

```text
Company has 10,000 employees
        ↓
all use one corporate DNS resolver
        ↓
resolver asks Traffic Manager once
        ↓
Traffic Manager chooses Region A
        ↓
result cached
        ↓
many employees use Region A
```

So:

```text
50/50 weights
```

don't guarantee:

```text
5,000 users each
```

at every moment.

With very large numbers of independent resolvers, the observed distribution generally approaches the configured relative weighting more closely.

---

### **Endpoint health still matters**

Suppose:

```text
A weight = 90
B weight = 10
```

but:

```text
A unhealthy
```

Traffic Manager doesn't keep returning A simply to satisfy its 90% allocation.

Instead:

```text
healthy endpoint set
→ B
```

so traffic can shift toward the available endpoint.

All Traffic Manager routing methods include endpoint health monitoring. ([Microsoft Learn][4])

---

### **Weighted vs Priority**

```text
Priority:

Primary → 100%
Backup  → 0%
unless primary fails
```

versus:

```text
Weighted:

A → 90%
B → 10%
while both healthy
```

So:

```text
Priority
→ disaster failover

Weighted
→ active-active / migration / canary
```

---

### **Weighted vs application-level canary**

If I require:

```text
exactly 5% of HTTP requests
```

or routing based on:

```text
header
cookie
URL
user identity
```

Traffic Manager isn't the ideal tool because it's DNS-based.

I would consider a Layer-7 system such as:

```text
Front Door
Application Gateway
Ingress/service mesh
```

depending on scope and requirements.

Traffic Manager Weighted is best understood as:

```text
DNS-level probabilistic distribution
```

rather than exact request-by-request splitting.

---

### **Strong interview answer**

> “Weighted routing distributes Traffic Manager DNS selections among healthy endpoints according to relative weights. For example, weights of 90 and 10 make the first endpoint roughly nine times more likely to be returned than the second. It's useful for gradual migrations, blue-green or canary-style rollouts and active-active distribution. The important limitation is that Traffic Manager distributes DNS answers, not individual HTTP requests, so resolver caching can cause actual request percentages to differ significantly from the configured weights.”

**Memory line:**
**Weighted routing controls the probability of DNS endpoint selection—not an exact percentage of HTTP requests.**

**Interview trap:**
`90/10` does **not guarantee exactly 90/10 application requests**, because DNS caching can skew real traffic.

**Keywords:**
Weighted routing, DNS distribution, relative weight, migration, canary, DNS caching, active-active

**Likely follow-ups:**

* How would you perform a gradual regional migration?
* Why might 50/50 weights produce 80/20 traffic?
* Weighted vs Priority?
* When would Front Door be better for canary routing?
