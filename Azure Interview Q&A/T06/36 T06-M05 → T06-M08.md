# 6. 🔴 M IMP — Azure Load Balancing & Application Delivery

## Medium

### **T06-M05. What is SSL/TLS termination?**

**Answer:**
TLS termination means the **load balancer or application gateway decrypts the incoming HTTPS connection instead of every backend server doing it individually**.

For Azure Application Gateway, the client establishes HTTPS with the gateway:

```text
Client
   │
   │ HTTPS
   ▼
Application Gateway
   │
   │ decrypts TLS
   ▼
Backend
```

This lets the gateway inspect the HTTP request and perform Layer-7 features such as:

* URL-based routing,
* host-based routing,
* WAF inspection,
* cookie affinity.

### **Without TLS termination**

Each backend would handle the certificate itself:

```text
Client
   ↓ HTTPS
Load balancer
   ↓ HTTPS
VM-1 / VM-2 / VM-3

Each VM handles TLS
```

That means certificate management may need to happen across many servers.

### **With TLS termination at Application Gateway**

```text
Internet
   ↓ HTTPS
Application Gateway
   ↓
TLS certificate managed here
   ↓
Backend servers
```

This centralizes certificate management and reduces TLS-processing work on the backend.

---

### **But what happens between Application Gateway and the backend?**

There are two common models.

#### **1. TLS termination / offload**

```text
Client
   ↓ HTTPS
Application Gateway
   ↓ HTTP
Backend
```

TLS ends at the gateway.

This is simple, but traffic between Application Gateway and the backend isn't encrypted at the application layer.

#### **2. End-to-end TLS**

For sensitive production workloads, I can re-encrypt traffic:

```text
Client
   ↓ HTTPS
Application Gateway
   ↓ decrypt
Layer-7 routing/WAF
   ↓ re-encrypt
HTTPS
   ↓
Backend
```

So traffic remains encrypted across both legs.

### **Example**

Suppose:

```text
https://shop.example.com
```

uses a certificate on Application Gateway.

The client establishes:

```text
Client
   ↓
TLS handshake
   ↓
Application Gateway
```

Application Gateway presents the certificate for:

```text
shop.example.com
```

Then it can route:

```text
/api/*
→ API backend

/images/*
→ Web backend
```

because after terminating TLS it can understand the HTTP request.

### **Why terminate TLS at the gateway?**

Main advantages:

```text
Central certificate management
+
Layer-7 inspection
+
WAF
+
simpler backend configuration
+
TLS offload
```

### **Where should the certificate be stored?**

In a production Azure architecture, I can integrate Application Gateway with **Azure Key Vault** for certificate management rather than manually distributing certificates across every VM.

Conceptually:

```text
Azure Key Vault
      ↓
TLS certificate
      ↓
Application Gateway
      ↓
HTTPS clients
```

### **TLS termination vs TLS passthrough**

Important distinction:

```text
TLS termination
→ Gateway decrypts the connection

TLS passthrough
→ Gateway forwards encrypted traffic
  without decrypting it
```

If the device never decrypts HTTP traffic, it generally can't perform the same HTTP-aware WAF/path-routing inspection on that encrypted connection.

**Memory line:**
**TLS termination = HTTPS ends at the gateway, allowing the gateway to inspect the HTTP request.**

**Interview trap:**
Don't assume TLS termination necessarily means:

> “Traffic from the gateway to the backend must be HTTP.”

You can use:

```text
HTTPS → Application Gateway → HTTPS
```

for **end-to-end TLS**.

**Keywords:** TLS termination, TLS offload, HTTPS, end-to-end TLS, certificate, Key Vault

**Likely follow-ups:**

* TLS termination vs end-to-end TLS?
* Where would you store certificates?
* Why terminate TLS at Application Gateway?
* Can WAF inspect traffic without decrypting TLS?

### **T06-M06. What is path-based routing?**

**Answer:**
Path-based routing is a Layer-7 routing technique where Application Gateway sends requests to different backend pools based on the **URL path**.

For example:

```text
example.com/api/*
→ API servers

example.com/images/*
→ Image servers

example.com/videos/*
→ Media servers
```

### **Architecture**

```text
                   Application Gateway
                           │
              Reads URL path
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
       /api/*          /images/*        /videos/*
          ↓                ↓                ↓
     API Pool         Image Pool        Media Pool
```

So one hostname can front multiple application components.

### **Example request**

A request arrives:

```text
GET https://shop.example.com/api/orders
```

Application Gateway sees:

```text
Path = /api/orders
```

and matches a rule:

```text
/api/*
   ↓
api-backend-pool
```

Another request:

```text
GET https://shop.example.com/images/logo.png
```

matches:

```text
/images/*
   ↓
image-backend-pool
```

### **Why is this useful?**

Imagine a microservice-style application:

```text
Frontend
API
Image service
Payment service
```

Instead of giving every service a separate public IP:

```text
api.example.com
images.example.com
payments.example.com
```

I could expose:

```text
example.com/api/*
example.com/images/*
example.com/payments/*
```

through one Application Gateway.

### **What happens when no path matches?**

I normally configure a **default backend pool**.

For example:

```text
/api/*     → API pool
/images/*  → Image pool

Everything else
→ Web pool
```

So:

```text
/
→ Web application
```

### **AKS example**

A similar concept is common with Kubernetes ingress:

```text
Application Gateway
      ↓
/frontend/*
/api/*
      ↓
AKS services
```

This is one reason Layer-7 ingress/application-routing services are valuable for microservices.

### **Path-based vs host-based routing**

```text
Path-based
example.com/api/*
example.com/images/*

Host-based
api.example.com
images.example.com
```

Path routing looks at:

```text
URL path
```

Host routing looks primarily at:

```text
HTTP Host header / hostname
```

**Memory line:**
**Path-based routing = same hostname, different URL paths, different backends.**

**Interview trap:**
Azure Load Balancer cannot perform:

```text
/api → Pool A
/images → Pool B
```

because Azure Load Balancer is Layer 4 and doesn't inspect HTTP URL paths.

**Keywords:** path-based routing, URL path, Application Gateway, backend pool, Layer 7

**Likely follow-ups:**

* Path-based vs host-based routing?
* What happens if no path matches?
* Can Azure Load Balancer do path routing?
* How would this work with AKS?

### **T06-M07. What is host-based routing?**

**Answer:**
Host-based routing sends traffic to different backend pools based on the **hostname requested by the client**.

For example:

```text
www.example.com
→ Web backend

api.example.com
→ API backend

admin.example.com
→ Admin backend
```

All three applications can potentially share the same Application Gateway frontend IP.

### **Architecture**

```text
                      Internet
                         ↓
                Application Gateway
                         │
                 Reads hostname
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
www.example.com    api.example.com   admin.example.com
        ↓                ↓                ↓
   Web Pool          API Pool         Admin Pool
```

This is also commonly called:

```text
multi-site hosting
```

in Application Gateway scenarios.

### **How does it work?**

A browser sends an HTTP request containing something like:

```text
Host: api.example.com
```

Application Gateway has a listener configured for that hostname.

It matches:

```text
api.example.com
```

and sends the request to:

```text
API backend pool
```

### **Example**

Suppose DNS contains:

```text
www.example.com   ─┐
api.example.com   ─┼──→ Application Gateway public IP
admin.example.com ─┘
```

Application Gateway then separates the traffic:

```text
Host: www.example.com
→ Frontend servers

Host: api.example.com
→ API servers

Host: admin.example.com
→ Admin servers
```

This means I don't necessarily need a separate Application Gateway for every website.

### **TLS consideration**

For HTTPS, Application Gateway also needs an appropriate certificate configuration.

For multiple hostnames, I might use:

```text
Wildcard certificate
*.example.com
```

where appropriate, or separate certificates/listeners.

For example:

```text
*.example.com

covers:
api.example.com
www.example.com
admin.example.com
```

but certificate design depends on the actual domain/security requirements.

### **Host-based vs path-based**

This is worth memorizing:

```text
HOST-BASED

api.example.com
→ API

shop.example.com
→ Shop
```

versus:

```text
PATH-BASED

example.com/api/*
→ API

example.com/shop/*
→ Shop
```

### **Can both be combined?**

Yes.

A design could conceptually route:

```text
api.example.com/v1/*
→ API-v1 pool

api.example.com/v2/*
→ API-v2 pool

shop.example.com/*
→ Shop pool
```

So the architecture can make Layer-7 decisions using both hostname and URL path.

**Memory line:**
**Host-based routing = different hostnames → different backend pools.**

**Interview trap:**
Don't confuse host-based routing with DNS routing.

DNS might send all three hostnames to the **same Application Gateway IP**.

Application Gateway then inspects the HTTP hostname and decides which backend receives the request.

**Keywords:** host-based routing, hostname, listener, multi-site hosting, Application Gateway

**Likely follow-ups:**

* Can multiple sites share one Application Gateway?
* How does HTTPS work with multiple hostnames?

### **T06-M08. What are backend pools?**

**Answer:**
A backend pool is the **group of destination resources that a load-balancing service can send traffic to**.

In simple terms:

```text
Frontend
   ↓
Load-balancing service
   ↓
Backend Pool
├── Backend 1
├── Backend 2
└── Backend 3
```

Both Azure Load Balancer and Application Gateway use the concept of backend pools, although the supported backend types and routing behavior differ.

### **Azure Load Balancer example**

For Azure Load Balancer:

```text
Public IP
   ↓
Azure Load Balancer
   ↓
Backend Pool
├── VM-1
├── VM-2
└── VM-3
```

The pool might consist of:

* VM NIC/IP configurations,
* VM Scale Set instances,
* other supported backend resources.

The Load Balancer distributes TCP/UDP flows across the healthy instances.

---

### **Application Gateway example**

Application Gateway may have:

```text
Backend Pool: api-pool
├── 10.0.2.4
├── 10.0.2.5
└── 10.0.2.6
```

and another:

```text
Backend Pool: web-pool
├── 10.0.3.4
├── 10.0.3.5
└── 10.0.3.6
```

Routing rules determine which pool receives which request.

For example:

```text
/api/*
   ↓
api-pool

/*
   ↓
web-pool
```

### **Backend pool alone isn't enough**

This is an important interview point.

Creating:

```text
Backend Pool
├── VM-1
└── VM-2
```

doesn't by itself make traffic flow.

A working load-balancing configuration also needs things such as:

```text
Frontend
+
Listener/rule
+
Backend pool
+
Health probe
+
Backend settings
```

depending on the Azure service.

For Azure Load Balancer, think:

```text
Frontend IP
      +
Backend Pool
      +
Health Probe
      +
Load-Balancing Rule
```

For Application Gateway:

```text
Frontend IP
      +
Listener
      +
Routing Rule
      +
Backend Pool
      +
Backend Settings
      +
Health Probe
```

### **Health matters**

Suppose:

```text
Backend Pool
├── VM-1 ✅
├── VM-2 ❌
└── VM-3 ✅
```

The health probe tells the load-balancing service which backend should receive traffic.

Normally:

```text
New traffic
├── VM-1 ✅
├── VM-2 ❌
└── VM-3 ✅
```

So membership in a backend pool does not automatically mean the endpoint is actively receiving requests—it also needs to be considered healthy.

### **Backend pool vs backend setting**

Especially for Application Gateway, don't confuse the two.

**Backend pool answers:**

> Where should I send traffic?

Example:

```text
10.0.2.4
10.0.2.5
```

**Backend settings answer:**

> How should I talk to those backends?

For example:

```text
Protocol: HTTPS
Port: 443
Timeout: ...
Cookie affinity: ...
```

Conceptually:

```text
Routing Rule
     ↓
Backend Pool
"where"
     +
Backend Setting
"how"
```

### **Example complete Application Gateway flow**

```text
Client
   ↓
Frontend IP
   ↓
HTTPS Listener
   ↓
Routing Rule
   ↓
/api/*
   ↓
API Backend Pool
   ↓
HTTPS Backend Setting :443
   ↓
Healthy API VM
```

**Memory line:**
**Backend pool = the set of destinations eligible to receive traffic.**

**Interview trap:**
A backend pool is not itself the load-balancing rule.

The pool defines **where** traffic can go; the listener/routing/load-balancing rule determines **when and how traffic is sent there**.

**Keywords:** backend pool, backend target, health probe, VMSS, Application Gateway, Azure Load Balancer

* What other components are required for traffic to flow?
