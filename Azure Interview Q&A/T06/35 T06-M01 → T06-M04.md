# 6. 🔴 M IMP — Azure Load Balancing & Application Delivery

## Medium

### **T06-M01. What is the difference between public and internal Azure Load Balancers?**

**Answer:**
The main difference is the **frontend IP address and who can reach it**.

A **Public Azure Load Balancer** uses a public frontend IP and is designed for internet-facing traffic.

An **Internal Azure Load Balancer** uses a private frontend IP from a VNet subnet and is used for private traffic inside Azure or from connected networks such as on-premises environments.

Microsoft's current documentation explicitly defines the type of Load Balancer by whether the frontend uses a public or private IP. ([Microsoft Learn][1])

### **Public Load Balancer**

Architecture:

```text
Internet Users
      ↓
Public IP
      ↓
Azure Load Balancer
      ↓
Backend Pool
├── VM-1
├── VM-2
└── VM-3
```

For example:

```text
Frontend:
20.10.20.30:443

Backend:
10.0.1.4:443
10.0.1.5:443
10.0.1.6:443
```

I would use this when clients on the internet need to reach the backend service.

Common examples:

* public TCP service,
* internet-facing VM application,
* public VMSS workload.

---

### **Internal Load Balancer**

An Internal Load Balancer has a **private IP**.

For example:

```text
Frontend:
10.0.2.10
```

Architecture:

```text
Application Tier
       ↓
10.0.2.10
       ↓
Internal Load Balancer
       ↓
Backend Tier
├── VM-1
├── VM-2
└── VM-3
```

It cannot accept traffic directly from the public internet. Microsoft describes Internal Load Balancer as distributing traffic to resources inside a virtual network and not exposing its frontend directly to an internet endpoint. ([Microsoft Learn][1])

### **Real-world example**

Suppose I have:

```text
Internet
   ↓
Application Gateway
   ↓
Web Tier
   ↓
Internal Load Balancer
   ↓
Application Tier
```

The web tier may be internet-facing through Application Gateway, while the application tier stays completely private behind an Internal Load Balancer.

### **Can on-premises reach an Internal Load Balancer?**

Yes, if the network is connected using something such as:

```text
Site-to-Site VPN
ExpressRoute
```

and routing/security rules allow the traffic.

So “internal” does not necessarily mean:

> Azure VMs only.

It means the frontend itself is **private rather than internet-facing**.

### **Comparison**

| Area                | Public LB          | Internal LB                |
| ------------------- | ------------------ | -------------------------- |
| Frontend            | Public IP          | Private IP                 |
| Internet accessible | Yes                | No direct internet ingress |
| VNet access         | Yes                | Yes                        |
| On-prem access      | Possible           | Possible through VPN/ER    |
| Typical use         | Public application | Internal application tiers |

**Memory line:**
**Public LB = public frontend IP.
Internal LB = private VNet frontend IP.**

**Interview trap:**
An Internal Load Balancer does not mean the backend VMs are unreachable from everywhere except their own subnet.

Other VNets or on-premises networks can potentially access it if routing and security are configured correctly.

**Keywords:** Public Load Balancer, Internal Load Balancer, frontend IP, private IP, backend pool

### **T06-M02. What is the difference between Azure Load Balancer and Application Gateway?**

**Answer:**
The biggest difference is the **OSI layer and type of traffic they understand**.

**Azure Load Balancer** primarily operates at **Layer 4** and distributes TCP/UDP traffic.

**Application Gateway** primarily operates at **Layer 7** and understands HTTP/HTTPS application traffic, so it can perform URL routing, host routing, TLS termination, cookie affinity, and WAF inspection. ([Microsoft Learn][2])

### **Comparison**

| Feature          | Azure Load Balancer               | Application Gateway           |
| ---------------- | --------------------------------- | ----------------------------- |
| Main layer       | Layer 4                           | Layer 7                       |
| Traffic          | TCP/UDP                           | HTTP/HTTPS, HTTP/2, WebSocket |
| URL routing      | ❌                                 | ✅                             |
| Hostname routing | ❌                                 | ✅                             |
| WAF              | ❌                                 | ✅ WAF_v2                      |
| TLS termination  | Not application-level TLS offload | ✅                             |
| Cookie affinity  | ❌                                 | ✅                             |
| Scope            | Regional                          | Regional                      |
| Best for         | Generic network traffic           | Web applications              |

### **Load Balancer example**

Suppose I have a custom TCP service:

```text
Client
   ↓
TCP 9000
   ↓
Azure Load Balancer
   ↓
VM-1
VM-2
VM-3
```

The Load Balancer doesn't need to understand what the application is doing inside the TCP connection.

It just needs information such as:

```text
IP
Port
Protocol
```

---

### **Application Gateway example**

Suppose I run:

```text
www.example.com/api/*
www.example.com/images/*
```

Application Gateway can route:

```text
                     Application Gateway
                            │
              ┌─────────────┴─────────────┐
              ↓                           ↓
           /api/*                     /images/*
              ↓                           ↓
        API backend                  Web backend
```

That's impossible with normal Layer-4 Azure Load Balancer because it doesn't inspect the HTTP URL.

### **Security difference**

Application Gateway can integrate **Web Application Firewall**:

```text
Internet
   ↓
Application Gateway WAF
   ↓
Inspect HTTP request
   ↓
Block SQLi/XSS/etc.
   ↓
Backend
```

Azure Load Balancer does not inspect HTTP request payloads.

### **Performance/design point**

I would not automatically choose Application Gateway just because it has more features.

If I only need:

```text
TCP/UDP distribution
```

Azure Load Balancer is usually the simpler and more appropriate service.

If I need:

```text
HTTP-aware routing
+
TLS termination
+
WAF
```

Application Gateway is the natural choice. Microsoft's current service-selection guidance reflects exactly this split. ([Microsoft Learn][3])

**Memory line:**
**Load Balancer = L4 network traffic.
Application Gateway = L7 web traffic.**

**Interview trap:**
Do not say:

> “Application Gateway is just a more advanced Load Balancer.”

They solve different problems at different layers.

**Keywords:** Layer 4, Layer 7, TCP/UDP, HTTP/HTTPS, Application Gateway, Azure Load Balancer

**Likely follow-ups:**

### **T06-M03. When should you use Application Gateway instead of Load Balancer?**

**Answer:**
I would use **Application Gateway instead of Azure Load Balancer when the routing or security decision depends on the HTTP/HTTPS application request**, rather than only on IP addresses and ports.

Typical requirements are:

```text
URL path-based routing
Hostname-based routing
TLS termination
End-to-end TLS
Web Application Firewall
Cookie-based session affinity
HTTP-specific health checks
```

Microsoft's current Azure guidance recommends Application Gateway for **regional web applications requiring Layer-7 routing, TLS termination, or WAF**. ([Microsoft Learn][3])

### **Scenario 1 — URL-based routing**

Suppose:

```text
/api/*
→ API servers

/images/*
→ Web/content servers
```

I need:

```text
Application Gateway
```

because it understands HTTP paths.

---

### **Scenario 2 — Multiple websites**

Suppose one gateway serves:

```text
shop.example.com
api.example.com
admin.example.com
```

I can use host-based routing:

```text
                   Application Gateway
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
shop.example.com   api.example.com   admin.example.com
```

Again, Azure Load Balancer cannot make routing decisions based on HTTP host headers.

---

### **Scenario 3 — WAF requirement**

Suppose the application is public and security requirements say:

> Protect the application against common web attacks such as SQL injection and XSS.

Then:

```text
Application Gateway WAF_v2
```

is appropriate.

Azure Load Balancer cannot perform this application-layer inspection. ([Microsoft Learn][4])

---

### **Scenario 4 — TLS termination**

Instead of every backend VM managing the public TLS certificate:

```text
Client
 ↓ HTTPS
Application Gateway
 ↓
TLS terminates centrally
 ↓
Backend
```

I can manage TLS at Application Gateway.

If security requires encryption all the way through:

```text
Client
 ↓ HTTPS
Application Gateway
 ↓ HTTPS
Backend
```

I can use end-to-end TLS.

---

### **When would I still choose Load Balancer?**

Suppose I'm load-balancing:

```text
TCP 5432
TCP 22
UDP 53
Custom TCP application
```

Then Layer-7 HTTP routing gives me no real advantage.

I'd prefer:

```text
Azure Load Balancer
```

for simple Layer-4 distribution.

### **Interview decision flow**

```text
Is traffic HTTP/HTTPS?
        │
        ├─ No
        │   ↓
        │ Azure Load Balancer
        │
        └─ Yes
            ↓
Need URL/host routing,
TLS termination or WAF?
        │
        ├─ Yes → Application Gateway
        │
        └─ No → either may fit,
                choose based on architecture
```

### **Application Gateway vs Front Door caveat**

If the requirement becomes:

> “I need global multi-region HTTP routing.”

then I would evaluate:

```text
Azure Front Door
```

rather than assuming Application Gateway is enough, because Application Gateway is primarily **regional** while Front Door is global. ([Microsoft Learn][3])

**Memory line:**
**Need to understand the HTTP request? Use Application Gateway.**

**Interview trap:**
Don't choose Application Gateway merely because the traffic happens to use port `443`.

Encrypted TCP traffic does not automatically mean Layer-7 routing is required.

The actual question is:

> Do I need HTTP-aware routing/security features?

**Keywords:** URL routing, host routing, WAF, TLS termination, Layer 7, Application Gateway

### **T06-M04. What is Application Gateway WAF?**

**Answer:**
Application Gateway WAF is Azure's **Web Application Firewall integrated with Application Gateway**. It inspects HTTP/HTTPS traffic and protects web applications against common application-layer attacks and vulnerabilities.

Azure WAF uses managed rule sets based on sources including the **OWASP Core Rule Set** and Microsoft's managed rule sets to detect malicious request patterns. ([Microsoft Learn][4])

### **Architecture**

```text
Internet
   ↓
Application Gateway
   ↓
WAF Policy
   ↓
Inspect HTTP request
   │
   ├── Safe ✅ → Backend
   │
   └── Malicious ❌ → Log / Block
```

Examples of threats it can help detect include:

```text
SQL injection
Cross-site scripting (XSS)
Command injection
Protocol/request anomalies
Other common web exploits
```

### **Detection mode**

In **Detection mode**:

```text
Suspicious request
       ↓
WAF detects it
       ↓
Logs event
       ↓
Request still reaches backend
```

This mode is useful while:

* initially deploying WAF,
* tuning rules,
* identifying false positives.

Microsoft documents that Detection mode evaluates and logs suspicious traffic but doesn't block it. ([Microsoft Learn][5])

### **Prevention mode**

In **Prevention mode**:

```text
Malicious request
       ↓
WAF rule matches
       ↓
Request blocked
       ↓
Backend never receives it
```

For a production internet-facing application, the eventual goal is often Prevention mode after sufficient tuning.

Microsoft states that requests identified as threats are blocked when WAF operates in Prevention mode. ([Microsoft Learn][5])

### **Managed rules**

Instead of writing thousands of attack signatures manually, I can enable managed rule sets.

Conceptually:

```text
WAF Policy
├── Managed Rules
│   ├── SQL Injection
│   ├── XSS
│   └── other attack signatures
│
└── Custom Rules
```

Custom rules can be useful for organization-specific requirements.

For example:

```text
Source country / IP
+
URL path
+
Request characteristics
        ↓
Allow / Block
```

### **Example**

Suppose an attacker sends something resembling:

```text
/login?id=' OR 1=1 --
```

WAF rules may identify the request as potential SQL injection.

In Prevention mode:

```text
Attacker
   ↓
WAF
   ↓
SQL injection detected
   ↓
BLOCK
```

The request does not reach the application server.

### **WAF does not replace secure coding**

This is important.

WAF should be one layer:

```text
Secure application code
+
Patching
+
Authentication/authorization
+
WAF
+
Monitoring
```

I would never treat WAF as an excuse to leave a SQL-injection vulnerability unfixed.

### **WAF policies**

A WAF policy can contain:

* managed rule sets,
* custom rules,
* exclusions,
* request-body inspection settings,
* mode configuration.

Azure currently allows policies to be associated with the Application Gateway and, in supported configurations, more specific listeners or path-based routing rules. ([Microsoft Learn][4])

### **Operational approach**

For a new production deployment, a sensible rollout is:

```text
Deploy WAF
   ↓
Detection mode
   ↓
Collect logs
   ↓
Identify false positives
   ↓
Tune exclusions/custom rules
   ↓
Switch to Prevention
   ↓
Continue monitoring
```

This reduces the risk of suddenly blocking legitimate application traffic.

**Memory line:**
**WAF = HTTP security filter in front of the web application.**

**Interview trap:**
Don't confuse an NSG with WAF:

```text
NSG
→ Layer 3/4
→ IP, protocol, port

WAF
→ Layer 7
→ HTTP requests and attack patterns
```

And don't say WAF makes application security unnecessary—it is an **additional defense layer**.

**Keywords:** WAF, OWASP CRS, SQL injection, XSS, Detection mode, Prevention mode, managed rules
