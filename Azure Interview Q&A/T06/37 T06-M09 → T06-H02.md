# 6. 🔴 M IMP — Azure Load Balancing & Application Delivery

## Medium

### **T06-M09. What are load-balancing rules?**

**Answer:**
A load-balancing rule tells Azure Load Balancer **how incoming traffic on a frontend IP and port should be distributed across healthy instances in a backend pool**.

The rule essentially connects:

```text
Frontend IP + Port
        ↓
Protocol
        ↓
Backend Pool + Port
        ↓
Health Probe
```

Microsoft defines a load-balancing rule as the mapping between a frontend IP/port and multiple backend IPs/ports. ([Microsoft Learn][1])

### **Example**

Suppose I have:

```text
Frontend:
20.10.10.5:80

Backend pool:
VM-1 → 10.0.1.4
VM-2 → 10.0.1.5
VM-3 → 10.0.1.6
```

I create a rule:

```text
Protocol: TCP
Frontend port: 80
Backend port: 80
Health probe: HTTP/TCP probe
```

The flow becomes:

```text
Client
   ↓
20.10.10.5:80
   ↓
Load-balancing rule
   ↓
Healthy backend
├── 10.0.1.4:80
├── 10.0.1.5:80
└── 10.0.1.6:80
```

### **What does the rule define?**

Typically:

* frontend IP configuration,
* protocol,
* frontend port,
* backend port,
* backend pool,
* health probe,
* session persistence/distribution settings where required,
* idle timeout and related TCP settings.

### **Role of the health probe**

Suppose:

```text
VM-1 ✅
VM-2 ❌
VM-3 ✅
```

The rule still references the same backend pool, but Load Balancer sends new traffic only to the backends considered healthy.

So:

```text
Load-balancing rule
        +
Health probe
        =
Traffic distribution to healthy instances
```

### **Frontend port and backend port don't have to match**

For example:

```text
Frontend:
TCP 443

Backend:
TCP 8443
```

can conceptually map:

```text
20.10.10.5:443
        ↓
Load Balancer
        ↓
VMs:8443
```

when that is how the application is designed.

### **High Availability ports**

Standard Internal Load Balancer also supports **HA Ports** rules.

Instead of defining individual ports:

```text
80
443
8080
...
```

an HA Ports rule can load-balance **all TCP and UDP ports** for scenarios such as highly available network virtual appliances. Microsoft documents HA Ports as protocol `All` with port `0`. ([Microsoft Learn][1])

### **Load-balancing rule vs inbound NAT rule**

Very important distinction:

```text
Load-balancing rule
→ one frontend endpoint
→ distribute across MULTIPLE backends

Inbound NAT rule
→ frontend port
→ reach a PARTICULAR backend instance/port
```

**Memory line:**
**Load-balancing rule = frontend traffic → healthy backend pool.**

**Interview trap:**
A backend pool alone doesn't distribute traffic. You still need the appropriate **load-balancing rule and health probe** connecting the frontend to that pool.

**Keywords:** frontend IP, backend pool, health probe, frontend port, backend port, HA Ports

**Likely follow-ups:**

* Load-balancing rule vs NAT rule?
* Can frontend and backend ports differ?
* What happens when a health probe fails?
* What are HA Ports?

### **T06-M10. What are inbound NAT rules?**

**Answer:**
An inbound NAT rule is an Azure Load Balancer **port-forwarding rule** that maps a frontend IP and port to a specific backend VM or backend-instance port.

Unlike a load-balancing rule, its main purpose isn't to distribute one connection across the whole backend pool—it's to provide **direct access to a particular backend instance**. ([Microsoft Learn][2])

### **Example**

Suppose I have three VMs behind one public Load Balancer:

```text
Load Balancer Public IP:
20.10.10.5
```

All VMs use SSH internally on:

```text
TCP 22
```

I could configure:

```text
20.10.10.5:50001 → VM-1:22
20.10.10.5:50002 → VM-2:22
20.10.10.5:50003 → VM-3:22
```

Then:

```bash
ssh -p 50002 user@20.10.10.5
```

reaches:

```text
VM-2:22
```

### **Architecture**

```text
Admin
  ↓
20.10.10.5:50002
  ↓
Azure Load Balancer
  ↓
Inbound NAT Rule
  ↓
VM-2:22
```

Typical historical uses include:

* SSH,
* RDP,
* administrative access,
* specific port forwarding.

### **Inbound NAT rule vs load-balancing rule**

Suppose three web servers exist.

A normal load-balancing rule:

```text
20.10.10.5:443
        ↓
VM-1 OR VM-2 OR VM-3
```

An inbound NAT rule:

```text
20.10.10.5:50002
        ↓
VM-2 specifically
```

So:

```text
Load balancing
→ distribute

NAT
→ target/forward
```

### **Do inbound NAT rules require health probes?**

No.

Microsoft explicitly notes that, unlike normal load-balancing rules, inbound NAT rules **don't require an attached health probe**. ([Microsoft Learn][2])

This matters because the NAT mapping can still exist even if the application on the target VM isn't healthy.

### **NAT Rule V1 vs V2**

Current Standard Load Balancer supports:

```text
Inbound NAT Rule V1
→ single VM target

Inbound NAT Rule V2
→ backend-pool based
→ supports multiple VMs / VMSS
→ frontend port range allocated
```

Microsoft recommends **V2 for Standard Load Balancer deployments targeting multiple VMs or VM Scale Sets**. ([Microsoft Learn][2])

For example:

```text
Frontend range:
50000–50100

Backend port:
22

VMSS instances
├── instance 1 ← mapped frontend port
├── instance 2 ← mapped frontend port
└── instance 3 ← mapped frontend port
```

When the backend pool scales, V2 can create port mappings for new instances automatically. ([Microsoft Learn][2])

### **Production security note**

Although inbound NAT rules can expose SSH/RDP, I would generally avoid exposing administrative ports broadly to the internet.

Instead, I would prefer:

```text
Azure Bastion
VPN
ExpressRoute
Just-in-Time access
Private connectivity
```

depending on the environment.

**Memory line:**
**Inbound NAT rule = frontend port → specific backend instance/port.**

**Interview trap:**
Don't say NAT rules load-balance SSH across all VMs.

For direct instance administration, the whole point is knowing:

```text
frontend port X
→ backend instance Y
```

**Keywords:** inbound NAT, port forwarding, SSH, RDP, frontend port, backend port, NAT V2

**Likely follow-ups:**

* NAT rule vs load-balancing rule?
* Does a NAT rule need a health probe?
* Why use NAT Rule V2?
* Would you expose SSH this way in production?

# Hard

### **T06-H01. When would you use Front Door + Application Gateway together?**

**Answer:**
I use **Azure Front Door and Application Gateway together when I need global Layer-7 traffic management at the edge plus regional Layer-7 control inside each Azure region/VNet**.

The responsibilities are different:

```text
Azure Front Door
→ global entry point
→ global health-based routing
→ edge acceleration/caching
→ global WAF

Application Gateway
→ regional ingress
→ VNet integration
→ regional path/host routing
→ regional WAF
→ backend-pool management
```

Microsoft explicitly recommends this combination for global web applications where Front Door handles global HTTP/HTTPS routing and cross-region failover while Application Gateway handles regional WAF and URL routing. ([Microsoft Learn][3])

### **Typical architecture**

```text
                    Users Worldwide
                           ↓
                    Azure Front Door
                 Global Layer-7 ingress
                   /               \
                  /                 \
                 ↓                   ↓
        Central India             East US
        App Gateway               App Gateway
             ↓                         ↓
       Regional apps              Regional apps
       ├── API                    ├── API
       └── Web                    └── Web
```

### **Why not just use Front Door?**

Front Door might already provide:

* global routing,
* TLS,
* WAF,
* path routing,
* CDN,
* health probes.

So I wouldn't add Application Gateway automatically.

I add it when the regional architecture needs something Front Door alone doesn't provide as cleanly.

---

### **Scenario 1: Regional VNet routing**

Suppose every region has multiple private application tiers:

```text
Region
│
├── /api/*       → API VMSS
├── /checkout/*  → Checkout service
└── /admin/*     → Admin backend
```

Application Gateway can perform that regional routing inside the VNet.

Microsoft specifically notes that Front Door can route globally while Application Gateway can handle routing within the VNet. ([Microsoft Learn][4])

Architecture:

```text
Front Door
    ↓
Choose healthy region
    ↓
Application Gateway
    ↓
Choose regional backend
```

That's a very clean separation of responsibilities.

---

### **Scenario 2: Multi-region failover**

Suppose:

```text
Central India = primary
East US       = secondary
```

Front Door continuously probes both origins.

Normal:

```text
Users
 ↓
Front Door
 ↓
Central India App Gateway
```

If Central India fails:

```text
Central India ❌
       ↓
Front Door detects unhealthy origin
       ↓
East US App Gateway ✅
```

Application Gateway itself is a **regional service**, so separate gateways must exist in each region for regional-outage resilience. ([Microsoft Learn][5])

---

### **Scenario 3: Private regional ingress**

One particularly strong architecture with **Front Door Premium** is:

```text
Internet
   ↓
Azure Front Door Premium
   ↓
Private Link
   ↓
Private Application Gateway
   ↓
Private backend services
```

Microsoft's networking guidance specifically notes that Front Door Premium can connect to Application Gateway using Private Link, allowing the Application Gateway to remain private. ([Microsoft Learn][6])

That reduces direct public exposure of the regional ingress.

---

### **Scenario 4: Different global and regional responsibilities**

For example:

```text
Front Door
├── Global WAF
├── Geo/performance routing
├── CDN
├── Edge TLS
└── Regional failover

Application Gateway
├── Regional listener
├── Host routing
├── Path routing
├── Backend health
├── Connection draining
└── Regional WAF
```

Microsoft also calls out capabilities such as regional backend routing, connection draining, and regional session affinity as reasons Application Gateway may sit behind Front Door. ([Microsoft Learn][4])

### **But there is a trade-off**

This design adds:

```text
Extra cost
+
Extra hops
+
Two WAF configurations
+
Certificate complexity
+
Monitoring complexity
+
More IaC
```

Microsoft's Architecture Center specifically warns that using both services increases operational complexity and cost, especially if Application Gateway is deployed in every region. ([Microsoft Learn][7])

So my design principle is:

> **Don't deploy both because both exist. Deploy both only when regional ingress requirements justify the additional layer.**

### **Production design**

For a large global application:

```text
                     Internet
                        ↓
             Azure Front Door Premium
             ├── Global WAF
             ├── TLS
             ├── health probes
             └── regional routing
                  /          \
                 ↓            ↓
           India Region      US Region
              ↓                 ↓
         App Gateway        App Gateway
         WAF_v2             WAF_v2
              ↓                 ↓
        Private AKS         Private AKS
```

I would define both regions through Terraform/Bicep to keep:

* listeners,
* certificates,
* WAF policies,
* routing rules

consistent.

**Memory line:**
**Front Door chooses the region; Application Gateway chooses the backend inside that region.**

**Interview trap:**
Don't claim Front Door + Application Gateway is automatically the “best architecture.”

For many applications:

```text
Front Door → App Service / AKS / origin
```

is enough.

Adding Application Gateway must solve an actual **regional ingress/VNet/WAF/routing requirement**.

**Keywords:** Front Door, Application Gateway, global routing, regional routing, Private Link, WAF, multi-region

**Likely follow-ups:**

* Why not use only Front Door?
* Can Front Door reach a private Application Gateway?
* Where would you place WAF?
* What happens if an entire Azure region fails?

### **T06-H02. How would you expose a globally distributed application using Azure services?**

**Answer:**
For a globally distributed HTTP/HTTPS application, I would normally use **Azure Front Door as the global entry point**, deploy the application independently in at least two Azure regions, use health probes for regional availability, and keep state/data designed for multi-region resilience.

The high-level design is:

```text
                    Global Users
                         ↓
                   Azure Front Door
              ┌──────────┴──────────┐
              ↓                     ↓
        Central India             East US
        Application              Application
              ↓                     ↓
       Regional data           Regional data
```

Front Door provides global HTTP/HTTPS routing, acceleration, health-based origin selection, and cross-region failover. ([Microsoft Learn][3])

### **1. Deploy independent regional stacks**

I don't want:

```text
Region 1 application
     ↓
depends entirely on Region 1
```

and then call the system “multi-region.”

Each region should have enough independent components to serve traffic.

For example:

```text
Central India
├── App Service / AKS / VMSS
├── regional ingress
├── cache
├── monitoring
└── resilient data path

East US
├── App Service / AKS / VMSS
├── regional ingress
├── cache
├── monitoring
└── resilient data path
```

Ideally, infrastructure is created using:

```text
Terraform / Bicep
```

so both regions stay consistent.

---

### **2. Put Azure Front Door in front**

DNS would point the public application hostname to Front Door:

```text
www.example.com
      ↓
Azure Front Door
```

Front Door then routes to an **origin group** containing the regional endpoints.

Example:

```text
Origin Group
├── India origin
└── US origin
```

Front Door performs health monitoring and chooses a healthy origin according to configured routing behavior.

### **Active-active design**

For active-active:

```text
Users in Asia
   ↓
India

Users in Americas
   ↓
US
```

Both regions actively serve production.

Advantages:

* lower user latency,
* capacity is already warm,
* no cold standby,
* better global scaling.

But data architecture becomes more challenging.

### **Active-passive design**

Alternatively:

```text
Primary
Central India ✅

Secondary
East US standby
```

Front Door sends normal traffic to primary and fails over when it becomes unhealthy.

This is operationally simpler but may waste standby capacity or create slower failover depending on how the secondary is provisioned.

---

### **3. Use regional Application Gateway only if required**

If each region needs complex VNet ingress:

```text
Front Door
      ↓
Application Gateway
      ↓
AKS / VMSS / private services
```

If not, I may simplify to:

```text
Front Door
      ↓
App Service / Container Apps / other origin
```

Microsoft explicitly supports combining Front Door with Application Gateway for global-plus-regional routing, but also warns that Application Gateway adds regional cost and complexity. ([Microsoft Learn][3])

---

### **4. Protect the origin**

I don't want users bypassing:

```text
Front Door
```

and calling the regional origin directly.

Depending on the service and Front Door SKU, I can use:

```text
Front Door Premium
        ↓
Private Link
        ↓
Private origin
```

or otherwise restrict origins to traffic that genuinely came through Front Door.

For public Application Gateway origins, Microsoft publishes patterns that combine network restrictions with validation of the Front Door identifier header (`X-Azure-FDID`) to prevent direct bypass. ([Microsoft Learn][8])

---

### **5. Design the data layer separately**

This is the part candidates often miss.

Global frontend routing does **not automatically make the application globally resilient**.

Suppose:

```text
India App ✅
US App ✅

Database only in India ❌
```

Then:

```text
India region fails
        ↓
US app exists
        ↓
but data tier unavailable
        ↓
application still fails
```

So I must design data for the application's RPO/RTO.

Depending on the workload this might involve:

```text
Cosmos DB multi-region
Azure SQL failover groups
Storage GRS/GZRS
database replication
regional caches
```

and a clear consistency/failover strategy.

### **6. Make sessions/statelessness multi-region friendly**

I avoid storing critical user session state only in:

```text
local VM memory
```

because regional failover would lose it.

Prefer:

```text
Stateless services
+
external/shared session storage where required
```

This makes traffic failover much easier.

---

### **7. Health probes must represent real application health**

Front Door should probe something like:

```text
/health
```

but the endpoint should reflect whether the region can actually serve useful traffic.

For example:

```text
Web process running ✅
Critical data dependency unavailable ❌
```

may need to report the region unhealthy if requests cannot succeed.

However, I avoid making the probe depend on every noncritical third-party service, otherwise one minor dependency can remove the entire region.

---

### **8. Monitoring and observability**

I would monitor:

```text
Front Door
├── origin health
├── WAF blocks
├── latency
├── 4xx/5xx

Regional apps
├── request rate
├── errors
├── latency
└── saturation

Data layer
├── replication
├── failover state
└── availability
```

using Azure Monitor, Log Analytics, Application Insights, and alerts as appropriate.

### **9. Test regional failover**

A design isn't complete until failover is tested.

I would test:

```text
Normal state
       ↓
Take primary origin out of rotation
       ↓
Front Door detects failure
       ↓
Secondary serves traffic
       ↓
Validate application
       ↓
Validate data
       ↓
Validate authentication
       ↓
Validate monitoring
```

Application Gateway is regional, so if it forms part of each stack, each region needs its own instance and Front Door/Traffic Manager provides the global routing layer. ([Microsoft Learn][5])

### **Strong architecture answer**

For a serious production system:

```text
                        Users
                          ↓
                         DNS
                          ↓
                Azure Front Door Premium
                 ├── Global WAF
                 ├── TLS
                 ├── Health probes
                 └── Global routing
                     /          \
                    /            \
                   ↓              ↓
             Region A          Region B
             App Gateway      App Gateway
                  ↓              ↓
                 AKS            AKS
                  \              /
                   \            /
                    ↓          ↓
                Multi-region data
```

Plus:

```text
Managed Identity
Private connectivity
IaC
Azure Monitor
Backup/DR
Regular failover tests
```

### **Interview answer condensed**

> “I'd deploy identical application stacks in at least two Azure regions and use Azure Front Door as the global HTTP entry point. Front Door performs health-based routing and cross-region failover. If I need regional Layer-7 routing or private VNet ingress, I'd put Application Gateway in each region. I'd also make the application stateless, design the database/storage for multi-region resilience, protect origins from Front Door bypass, and test failover regularly.”

**Memory line:**
**Global HA = global routing + independent regions + resilient data.**

**Interview trap:**
The weakest answer is:

> “Deploy the app in two regions and put Front Door in front.”

That's only the **traffic layer**.

A real globally resilient design also needs:

```text
Data
Identity
State
Networking
Monitoring
Capacity
RPO/RTO
Failover testing
```

**Keywords:** Azure Front Door, multi-region, active-active, active-passive, health probes, Application Gateway, Private Link, RPO/RTO

**Likely follow-ups:**

* Active-active vs active-passive?
* What happens to the database during regional failure?
* How would you stop users bypassing Front Door?
* Front Door vs Traffic Manager for this design?
