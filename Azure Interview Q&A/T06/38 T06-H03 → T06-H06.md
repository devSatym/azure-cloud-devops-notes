# 6. 🔴 M IMP — Azure Load Balancing & Application Delivery

## Hard

### **T06-H03. How would you design regional failover for a public web application?**

**Answer:**
For a public HTTP/HTTPS application, I would deploy the workload in **at least two Azure regions** and put **Azure Front Door** in front as the global entry point. Front Door would continuously health-check both regions and route traffic away from an unhealthy region.

A typical design is:

```text
                    Users
                      ↓
               Azure Front Door
             Global WAF + TLS
                /         \
               /           \
              ↓             ↓
       Central India      East US
       App Gateway        App Gateway
            ↓                 ↓
          App A             App B
```

Azure Front Door supports health-based origin selection and priority-based active/passive failover. ([Microsoft Learn][1])

### **1. Make each region independently capable**

The first mistake I avoid is creating:

```text
Region A → full stack
Region B → only application servers
              ↓
Database still only in Region A ❌
```

That is not true regional DR.

Each region should have the dependencies needed to operate:

```text
Application
Networking
Ingress
Secrets/identity
Monitoring
Data access
Required capacity
```

Infrastructure should ideally be reproducible with Terraform/Bicep.

---

### **2. Choose active-passive or active-active**

#### Active-passive

```text
Region A → Priority 1
Region B → Priority 2
```

Normal:

```text
Front Door
   ↓
Region A
```

Failure:

```text
Region A ❌
   ↓
health probe fails
   ↓
Region B ✅
```

Front Door's priority routing supports this exact active/standby pattern. ([Microsoft Learn][1])

#### Active-active

Both origins have the same priority:

```text
Region A ✅
Region B ✅
```

Traffic can be distributed based on latency and other load-balancing settings.

This can reduce latency and keeps both environments warm, but the **data architecture becomes more complicated**.

---

### **3. Configure meaningful health probes**

I would probe something like:

```text
/health
```

but that endpoint must tell me whether the region can actually serve production traffic.

For example:

```text
App process ✅
Database unavailable ❌
```

If the application cannot serve requests without the database, the region should probably report unhealthy.

Front Door uses probe responses to determine which origins remain eligible for routing. Microsoft recommends health endpoints that account for critical dependencies. ([Microsoft Learn][2])

But I would avoid testing every minor dependency:

```text
Email provider temporarily down
→ entire region unhealthy ❌
```

unless email is genuinely critical to serving requests.

---

### **4. Design the data tier around RPO/RTO**

Traffic failover is usually the easy part.

Data is harder.

For example:

```text
Region A
Application ✅
Database primary ✅

Region B
Application ✅
Database replica ✅
```

I need to define:

```text
RPO
→ How much data can we lose?

RTO
→ How long can recovery take?
```

Then choose suitable Azure database/storage replication.

Examples might include:

```text
Azure SQL failover capabilities
Cosmos DB multi-region
Storage GRS/GZRS
Database-native replication
```

depending on the workload.

### **5. Keep the application stateless**

I avoid:

```text
User session
→ stored only in VM memory
```

because when Front Door moves the user to another region:

```text
session disappears
```

Prefer:

```text
stateless app instances
+
shared/distributed session store if needed
```

This makes regional failover much cleaner.

---

### **6. Pre-provision enough capacity**

A standby region must actually be able to handle production load.

Bad design:

```text
Primary = 20 instances
Secondary = 2 instances
```

Failover:

```text
100% traffic → 2 instances
             ↓
Secondary overloads ❌
```

Either keep enough warm capacity or ensure scaling can meet the required RTO.

---

### **7. Secure each regional origin**

I don't want:

```text
Users → Front Door ✅
Users → backend directly ✅ ❌
```

because direct access can bypass:

* Front Door WAF,
* routing policy,
* TLS controls,
* rate/security rules.

We'll cover the exact controls in **T06-H06**.

---

### **8. Monitor and test failover**

I monitor:

```text
Front Door origin health
5xx rate
latency
regional application health
database replication
capacity
```

And I actually test:

```text
Disable Region A origin
       ↓
Front Door detects failure
       ↓
Region B receives traffic
       ↓
Validate login
Validate database
Validate writes
Validate monitoring
```

A DR architecture that has never been tested is only theoretical.

### **Interview answer condensed**

> “I'd deploy independent application stacks in two regions and use Azure Front Door as the global HTTP entry point. Front Door health probes determine regional health and can fail traffic from the primary to secondary origin. I'd make the app stateless, design the database according to RPO/RTO, ensure the secondary has enough capacity, secure the origins against direct access, and regularly test failover.”

**Memory line:**
**Regional failover = redundant regions + health-based routing + resilient data + tested capacity.**

**Interview trap:**
Do not answer:

> “Front Door gives regional DR.”

Front Door solves the **traffic-routing layer**. Your application, data, identity, dependencies, and capacity must also survive the regional failure.

**Keywords:** Azure Front Door, active-passive, active-active, health probe, regional DR, RPO, RTO

**Likely follow-ups:**

* Active-active vs active-passive?
* What happens to the database?
* How fast does Front Door detect failure?
* How do you prevent direct origin access?

### **T06-H04. An Application Gateway returns HTTP 502 errors; how would you troubleshoot it?**

**Answer:**
A 502 from Application Gateway usually means **the gateway received the client request but couldn't successfully communicate with a healthy backend or received an invalid backend response**.

I troubleshoot it in this order:

```text
Backend health
    ↓
Health probe
    ↓
Backend pool/settings
    ↓
Network path
    ↓
DNS
    ↓
TLS/certificate
    ↓
Application response/timeout
```

Microsoft currently lists common 502 causes including unhealthy backends, probe failures, NSG/UDR/custom DNS issues, empty backend pools, backend timeouts, and certificate mismatch. ([Microsoft Learn][3])

### **1. Start with Backend Health**

My first check is:

```text
Application Gateway
→ Backend health
```

If I see:

```text
Backend-1 → Healthy
Backend-2 → Unhealthy
```

I focus on why Backend-2 is failing.

If:

```text
All backends → Unhealthy
```

the 502 is probably caused by a common configuration or connectivity issue.

This is much faster than starting randomly with the VM.

---

### **2. Inspect the health probe**

I verify:

```text
Protocol
Host
Port
Path
Expected HTTP response
```

For example:

```text
Probe:
HTTPS
Port 443
Path /health
```

Then test the exact same path manually from a reachable environment:

```bash
curl -vk https://backend.example.internal/health
```

Common problem:

```text
Application serves:

/healthz

Probe configured:

/health

→ unhealthy backend
```

Another common issue is host-header behavior.

The backend may expect:

```text
Host: api.example.com
```

but the probe sends something else.

---

### **3. Check backend pool and backend settings**

I verify that Application Gateway is actually pointing at:

```text
Correct backend IP/FQDN
Correct backend port
Correct HTTP/HTTPS protocol
```

For example:

```text
Backend app:
HTTPS :8443

Application Gateway:
HTTP :80 ❌
```

will obviously fail.

Remember:

```text
Backend Pool
→ WHERE traffic goes

Backend Settings
→ HOW Gateway connects
```

---

### **4. Check networking**

Application Gateway must have network connectivity to the backend.

I inspect:

```text
Application Gateway subnet
        ↓
NSG
        ↓
UDR
        ↓
Firewall / NVA
        ↓
Backend subnet
```

Microsoft explicitly lists NSGs, UDRs, and network path issues as causes of Application Gateway 502 errors. ([Microsoft Learn][3])

Questions I ask:

```text
Can App Gateway reach backend port?
Is an NSG blocking traffic?
Does a UDR send traffic to an NVA?
Is return traffic symmetric?
```

---

### **5. Check DNS**

If the backend pool uses:

```text
api.internal.example.com
```

then Application Gateway must resolve that hostname correctly.

If custom DNS is configured:

```text
App Gateway VNet
      ↓
Custom DNS
      ↓
Wrong/unreachable resolver ❌
```

the backend becomes unreachable.

Microsoft's 502 troubleshooting guidance explicitly calls out custom DNS problems. ([Microsoft Learn][3])

I verify:

```text
FQDN
↓
resolves to expected backend IP
```

Especially with:

```text
Private Endpoint
Private DNS
Internal DNS zones
```

DNS is a common root cause.

---

### **6. If backend uses HTTPS, inspect certificates**

For:

```text
Application Gateway
    ↓ HTTPS
Backend
```

the gateway validates the backend TLS certificate.

I verify:

```text
Certificate valid?
Certificate expired?
Trusted CA?
Correct certificate chain?
Hostname matches CN/SAN?
Backend Host setting correct?
```

For Application Gateway v2, if the backend certificate isn't issued by a publicly trusted CA, a corresponding **trusted root certificate** may need to be configured. The backend hostname must also match the certificate identity. ([Microsoft Learn][4])

Typical failure:

```text
Backend certificate:
CN = api.example.com

Backend setting:
Host = 10.0.2.5

Hostname validation fails
      ↓
Backend unhealthy
      ↓
502
```

---

### **7. Check backend timeout**

Suppose:

```text
Application Gateway timeout = 30 sec

/backend/report
takes 90 sec
```

Then Application Gateway can return an error because the backend took too long.

Microsoft includes backend request-timeout exhaustion among common 502 causes. ([Microsoft Learn][3])

So I inspect:

* application response time,
* database latency,
* dependency latency,
* backend timeout configuration.

I wouldn't blindly increase the timeout without understanding why the application is slow.

---

### **8. Check the application directly**

If possible, test the backend without Application Gateway:

```bash
curl -v http://10.0.2.4:8080/health
```

or:

```bash
curl -vk https://api.example.internal/health
```

If that fails:

```text
Application problem
not Gateway problem
```

Then inspect:

```bash
ss -lntp
systemctl status <service>
journalctl -u <service>
```

or corresponding container/Kubernetes logs.

---

### **Fast troubleshooting map**

```text
502
 ↓
Backend health?
 │
 ├─ Unhealthy
 │     ↓
 │   Probe
 │     ↓
 │   NSG/UDR/DNS
 │     ↓
 │   TLS certificate
 │     ↓
 │   Application
 │
 └─ Healthy
       ↓
     Backend timeout
       ↓
     routing/listener rules
       ↓
     application response
```

**Memory line:**
**502 = Gateway reached, backend path failed. Start with Backend Health.**

**Interview trap:**
Don't immediately blame Application Gateway.

Very often Application Gateway is correctly reporting that:

```text
backend is unreachable/unhealthy
```

because of the application, networking, DNS, probe, or TLS configuration.

**Keywords:** HTTP 502, Backend Health, probe, NSG, UDR, DNS, certificate, timeout

**Likely follow-ups:**

* What if all backends show unhealthy?
* How can a certificate cause 502?
* How would you debug Private DNS?
* What if the probe is healthy but users still see 502?

### **T06-H05. How would you implement end-to-end TLS between clients, Application Gateway, and backend services?**

**Answer:**
I would configure HTTPS on **both legs**:

```text
Client
   ↓ HTTPS
Application Gateway
   ↓ HTTPS
Backend
```

Application Gateway terminates the client TLS connection so it can perform Layer-7 routing/WAF inspection, then establishes a **new TLS connection to the backend**.

Microsoft calls this **end-to-end TLS**, and it is enabled by configuring the backend HTTP setting to use HTTPS. ([Microsoft Learn][4])

### **1. Configure frontend HTTPS listener**

On Application Gateway I configure:

```text
Listener
Protocol: HTTPS
Port: 443
Hostname: app.example.com
```

and attach the frontend certificate:

```text
CN/SAN:
app.example.com
```

The certificate can be integrated with Azure Key Vault in a production design.

Frontend:

```text
Browser
   ↓ TLS
app.example.com
   ↓
Application Gateway
```

---

### **2. Configure backend services for HTTPS**

Each backend must serve HTTPS.

For example:

```text
Backend VM-1
api.internal.example.com:443

Backend VM-2
api.internal.example.com:443
```

Then Application Gateway's backend setting uses:

```text
Protocol = HTTPS
Port = 443
```

Flow:

```text
Client
 ↓ HTTPS
Application Gateway
 ↓ decrypt
WAF/routing
 ↓ encrypt again
Backend HTTPS
```

---

### **3. Validate backend certificate trust**

The gateway must trust the certificate presented by the backend.

If the backend uses a certificate from a **well-known trusted CA** and the hostname matches, Application Gateway v2 doesn't require an additional trusted-root upload. ([Microsoft Learn][4])

For example:

```text
Backend FQDN:
api.example.com

Certificate:
CN/SAN = api.example.com

Trusted public CA
```

→ works naturally.

---

### **4. Private CA or self-managed certificate**

If the backend certificate is issued by:

```text
Company Private CA
```

then for Application Gateway v2 I configure the appropriate:

```text
Trusted Root Certificate
```

in the backend settings.

Microsoft specifically requires the relevant trusted root for backend certificates that aren't chained to a well-known CA. ([Microsoft Learn][4])

Conceptually:

```text
Company Root CA
      ↓
Backend certificate
      ↓
Gateway trusts root CA
```

---

### **5. Hostname must match the certificate**

This is a very common failure point.

Suppose the backend certificate is:

```text
CN = api.internal.example.com
```

Then I configure the backend host appropriately:

```text
Host = api.internal.example.com
```

not:

```text
Host = 10.0.2.5 ❌
```

Application Gateway v2 validates the hostname against the backend certificate CN/SAN and uses the configured host for SNI. ([Microsoft Learn][5])

### **6. Configure HTTPS health probes**

I configure:

```text
Protocol: HTTPS
Host: api.internal.example.com
Path: /health
Port: 443
```

so health checks validate the same secure backend path used by application traffic.

If certificate validation fails:

```text
Health probe ❌
Backend unhealthy
Potential 502
```

---

### **Full architecture**

```text
             Client
               │
          HTTPS :443
               ↓
      Application Gateway
       ├── TLS termination
       ├── WAF inspection
       ├── routing
       └── frontend cert
               │
          HTTPS :443
               ↓
        Backend Service
          backend cert
```

So traffic is encrypted:

```text
Client → Gateway ✅
Gateway → Backend ✅
```

### **Certificates**

Think of them separately:

```text
Frontend certificate
→ proves Application Gateway identity to client

Backend certificate
→ proves backend identity to Application Gateway
```

They don't have to be the same certificate.

### **Production considerations**

I would also:

```text
Use modern TLS versions
Store/manage frontend certs securely
Monitor certificate expiry
Automate renewal
Use private backend IPs
Apply NSGs
Use least privilege
```

Microsoft's current v2 documentation notes backend TLS negotiates TLS 1.3 where available and falls back to TLS 1.2. ([Microsoft Learn][4])

**Memory line:**
**End-to-end TLS = HTTPS client→gateway + HTTPS gateway→backend.**

**Interview trap:**
Don't say:

> “End-to-end TLS means Application Gateway never decrypts the traffic.”

Application Gateway **does terminate/decrypt the client-side TLS connection** so it can perform Layer-7 processing, then establishes another encrypted connection to the backend.

That's different from TLS passthrough.

**Keywords:** end-to-end TLS, HTTPS, frontend certificate, backend certificate, Trusted Root Certificate, SNI

**Likely follow-ups:**

* What happens if backend CN doesn't match?
* Why do you need a trusted root certificate?
* End-to-end TLS vs TLS passthrough?
* What causes backend TLS-related 502 errors?

### **T06-H06. How would you prevent direct public access to backend services behind Front Door?**

**Answer:**
The strongest approach is to make the origin **private** and allow Front Door to reach it through **Private Link**, which is supported with Azure Front Door Premium for supported origin types.

Then users have:

```text
Internet
   ↓
Front Door
   ↓
Private Link
   ↓
Private origin
```

and cannot simply bypass Front Door by calling the backend's public endpoint. ([Microsoft Learn][6])

### **Preferred architecture**

For example:

```text
Internet
   ↓
Azure Front Door Premium
   ├── WAF
   ├── TLS
   └── global routing
          ↓
     Private Link
          ↓
 Internal Load Balancer
          ↓
        AKS
```

or:

```text
Front Door Premium
      ↓ Private Link
Private Application Gateway
      ↓
Private backend
```

Front Door Premium currently supports Private Link origins including Application Gateway, App Service, Blob Storage, internal Load Balancer-based origins such as AKS, Container Apps, and other supported services. ([Microsoft Learn][7])

### **Why this is strongest**

If the backend doesn't expose a usable public ingress path:

```text
Attacker
  ↓
backend-public-url
  ↓
No public path ❌
```

they are forced through:

```text
Front Door
```

where I enforce:

* WAF,
* TLS policy,
* routing,
* rate/security controls.

---

### **What if the origin must remain public?**

Then I restrict the origin so only genuine Front Door traffic is accepted.

A common pattern is:

```text
Allow:
AzureFrontDoor.Backend service tag

+
Validate:
X-Azure-FDID
```

Microsoft recommends combining network restrictions with validation of the `X-Azure-FDID` header for public origins such as Application Gateway. ([Microsoft Learn][6])

### **Why both controls?**

The service tag:

```text
AzureFrontDoor.Backend
```

means:

> Traffic came from Azure Front Door infrastructure.

But there are many Azure Front Door customers.

That doesn't necessarily mean:

> Traffic came from **my specific Front Door profile**.

So I also validate:

```text
X-Azure-FDID
```

against the Front Door ID for **my profile**.

Conceptually:

```text
Request arrives
      ↓
Source from AzureFrontDoor.Backend?
      │
      ├─ No → Block
      │
      └─ Yes
           ↓
X-Azure-FDID == my Front Door ID?
      │
      ├─ No → Block
      └─ Yes → Allow
```

That distinction is an excellent interview point.

---

### **Application Gateway example**

If Application Gateway remains public:

```text
Internet
   ↓
Front Door
   ↓
Application Gateway
```

I can configure the Application Gateway subnet NSG so web traffic is allowed from:

```text
AzureFrontDoor.Backend
```

and not general:

```text
Internet
```

Then on Application Gateway WAF, I can configure a custom rule that verifies:

```text
X-Azure-FDID
```

matches my Front Door profile identifier.

Microsoft documents this exact pattern for securing an Application Gateway origin behind Front Door. ([Microsoft Learn][6])

---

### **App Service example**

For App Service:

```text
Front Door
   ↓
App Service
```

I can use App Service access restrictions to:

```text
Allow Front Door service tag
+
match X-Azure-FDID
+
deny everything else
```

This gives platform-level origin protection without putting the validation logic in application code.

---

### **Why not only hide the backend URL?**

This is not security:

```text
https://very-random-name.azurewebsites.net
```

Attackers can discover DNS names, certificates, logs, source code, search indexes, and infrastructure metadata.

Security must be enforced by:

```text
network restrictions
+
identity/header validation
```

not secrecy of the hostname.

---

### **Why origin protection matters**

Without origin protection:

```text
                    ┌→ Front Door → WAF → App
User / Attacker ────┤
                    └→ Backend directly → App ❌
```

The attacker simply bypasses:

```text
WAF
rate limits
routing controls
edge protection
```

After securing the origin:

```text
Attacker → Backend directly ❌

User
 ↓
Front Door
 ↓
WAF
 ↓
Origin ✅
```

### **My preferred order**

```text
Best:
Front Door Premium
   ↓
Private Link
   ↓
Private Origin

If public origin required:
FrontDoor.Backend service tag
   +
X-Azure-FDID validation
   +
deny other public access
```

**Memory line:**
**Prevent Front Door bypass by making the origin private—or verify both Front Door network source and your specific Front Door ID.**

**Interview trap:**
Do not say:

> “I'll allow the AzureFrontDoor.Backend service tag, so only my Front Door can connect.”

That allows traffic from the **Front Door backend infrastructure**, not automatically only your specific profile.

For a public origin, additionally validate:

```text
X-Azure-FDID
```

against your Front Door profile. ([Microsoft Learn][6])

**Keywords:** Front Door Premium, Private Link, origin security, AzureFrontDoor.Backend, X-Azure-FDID, WAF, direct-access prevention

**Likely follow-ups:**

* Private Link vs service-tag restriction?
* What does `X-Azure-FDID` do?
* Why isn't the Front Door service tag alone enough?
* How would you secure an App Service origin?
