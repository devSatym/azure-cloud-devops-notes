### **T24-M05. What is the difference between `git revert` and `git reset`?**

**Answer:**
`git revert` safely undoes a commit by creating a **new inverse commit**, while `git reset` moves the current branch pointer to another commit and can also change the staging area or working tree. For shared branches like `main`, I would normally prefer `revert`; for local unpublished history, `reset` can be useful.

### **How they differ**

Suppose:

```text
A ── B ── C
```

Commit `C` is bad.

With:

```bash
git revert C
```

Git creates:

```text
A ── B ── C ── R
```

`R` reverses the effect of `C`, but the full history stays visible.

With:

```bash
git reset --hard B
```

the branch pointer moves back:

```text
A ── B
```

From the branch's perspective, `C` is no longer part of the current history.

### **Reset modes**

There are three important forms:

```bash
git reset --soft <commit>
git reset --mixed <commit>
git reset --hard <commit>
```

Conceptually:

```text
--soft
→ move HEAD
→ keep changes staged

--mixed
→ move HEAD
→ keep changes in working tree
→ unstage them

--hard
→ move HEAD
→ discard staged and working-tree changes
```

`--hard` is the dangerous one because local changes can be lost.

### **Production use**

For a bad commit already merged to `main`:

```text
Shared branch
    ↓
git revert
```

For local commits I have not pushed yet:

```text
Local feature branch
      ↓
git reset
```

may be perfectly reasonable.

### **Important distinction**

The key question is:

> **Has this history already been shared?**

If yes, rewriting it can affect other developers and CI/CD systems.

### **Interview answer condensed**

> “`git revert` preserves history by creating a new commit that reverses an older one, so it is usually safer for shared branches. `git reset` moves the branch pointer backward and can optionally modify the staging area and working tree, so I mainly use it for local unpublished history. I would be especially careful with `git reset --hard` because it can discard local changes.”

**Memory line:**
**Revert undoes history safely; reset moves history.**

**Interview trap:**
Do not use `git reset --hard` casually on a shared branch and force-push it just to undo a production change.

**Keywords:**
`git revert`, `git reset`, `--soft`, `--mixed`, `--hard`, history rewriting, shared branch.

**Likely follow-ups:**

* What does `git reset --soft` do?
* What does `git reset --hard` do?
* Can you recover a reset commit using `git reflog`?
* Why is revert safer on `main`?

### **T24-M06. What is GitFlow?**

**Answer:**
GitFlow is a branching model that uses multiple long-lived branches, typically `main` and `develop`, plus temporary feature, release, and hotfix branches. It was designed for teams with structured release cycles rather than continuous deployment.

### **Typical structure**

```text
main
│
├── hotfix/*
│
└── release tags

develop
│
├── feature/login
├── feature/payment
└── release/2.0
```

A simplified flow is:

```text
feature/*
   ↓
develop
   ↓
release/*
   ↓
main
   ↓
tagged release
```

Hotfixes usually branch from `main`:

```text
main
  ↓
hotfix/security-fix
  ↓
main + develop
```

### **Why teams used it**

GitFlow provides a very explicit separation between:

* current production code
* upcoming release development
* feature work
* release stabilization
* emergency hotfixes

That can work well for software with scheduled versions such as:

```text
v2.1
v2.2
v3.0
```

### **Main drawback in DevOps environments**

The downside is the number of long-lived branches.

For example:

```text
feature branch
      ↓
develop
      ↓
release branch
      ↓
main
```

Changes spend longer away from `main`, which increases:

* merge conflicts
* integration delay
* release complexity
* branch drift

For teams practicing frequent delivery, trunk-based development is often simpler.

### **When I might still choose GitFlow**

I would consider it when:

* releases are infrequent
* multiple supported versions exist
* release stabilization is lengthy
* the product has strict release trains

I would generally not choose it by default for a cloud-native team deploying many times per day.

### **Interview answer condensed**

> “GitFlow is a branching model with long-lived `main` and `develop` branches, plus feature, release, and hotfix branches. It gives strong release structure, which can suit versioned products with scheduled releases, but it creates more branch management and integration overhead. For modern continuous delivery, I would usually prefer a simpler trunk-based model.”

**Memory line:**
**GitFlow favors structured releases; trunk-based development favors continuous integration.**

**Interview trap:**
Do not present GitFlow as universally best practice. It can be unnecessarily heavy for fast-moving DevOps teams.

**Keywords:**
`main`, `develop`, feature branch, release branch, hotfix branch, release train.

**Likely follow-ups:**

* How is GitFlow different from trunk-based development?
* Why can long-lived branches be problematic?
* Where do hotfix branches originate?
* Would you use GitFlow for continuous deployment?

### **T24-M07. What is trunk-based development?**

**Answer:**
Trunk-based development is a branching strategy where developers integrate changes into a single main branch, or **trunk**, very frequently. Feature branches, if used, are short-lived, and the goal is to keep `main` continuously integrated and ideally always deployable.

### **How it works**

```text
main
A ── B ── C ── D ── E
     \   /
      short-lived feature
```

The normal flow is:

```text
Small change
    ↓
Short-lived branch
    ↓
Pull request
    ↓
Automated CI checks
    ↓
Merge quickly
    ↓
main
```

Branches typically live hours or a few days, not weeks.

### **Why it fits DevOps**

Frequent integration reduces:

* branch divergence
* massive merge conflicts
* late integration surprises
* release complexity

It works especially well with:

* strong automated tests
* CI/CD
* branch protection
* feature flags
* small incremental changes

### **Feature flags are important**

Suppose a feature is not ready for users but the team does not want a three-week branch.

The code can be merged behind a feature flag:

```text
main
  ↓
Feature code present
  ↓
Feature flag OFF
```

When ready:

```text
Feature flag ON
```

This separates:

```text
code deployment
from
feature release
```

which is very useful in continuous delivery.

### **Production workflow**

```text
Developer
   ↓
Small PR
   ↓
Unit / integration / security checks
   ↓
Merge to main
   ↓
Build once
   ↓
Deploy through environments
```

The important requirement is that `main` stays healthy.

### **Important distinction**

Trunk-based development does **not necessarily mean everyone directly pushes to `main`**.

A team can still use pull requests and branch protection:

```text
short-lived branch
      ↓
PR
      ↓
required checks
      ↓
merge to main
```

The defining idea is frequent integration and very short-lived branches.

### **Interview answer condensed**

> “Trunk-based development means developers integrate small changes into `main` very frequently, usually through short-lived branches and pull requests. It reduces branch drift and integration risk and works well with CI/CD, automated testing, and feature flags. I would usually prefer it for teams practicing continuous delivery.”

**Memory line:**
**Trunk-based = small changes, short branches, frequent integration into `main`.**

**Interview trap:**
Do not confuse trunk-based development with unrestricted direct pushes to `main`; branch protection and PR reviews are still commonly used.

**Keywords:**
Trunk, `main`, short-lived branches, CI, feature flags, continuous integration.

**Likely follow-ups:**

* How do feature flags support trunk-based development?
* How short should feature branches be?
* Can trunk-based development still use pull requests?
* Why does it reduce merge conflicts?

### **T24-M08. What are branch-protection rules?**

**Answer:**
Branch-protection rules are repository controls that restrict how important branches such as `main` can be changed. They are used to enforce review, testing, and security requirements before code is merged.

### **Typical protections**

For `main`, I would commonly require:

* pull requests instead of direct pushes
* one or more reviewer approvals
* required CI checks
* up-to-date branch before merge where appropriate
* code-owner review for sensitive paths
* restrictions on force pushes
* restrictions on branch deletion

A typical flow is:

```text
Developer
    ↓
Feature branch
    ↓
Pull Request
    ↓
├── Unit tests
├── Security scan
├── Terraform validation
├── Required review
└── Policy checks
    ↓
Merge permitted
    ↓
main
```

### **DevOps example**

For an infrastructure repository, I might protect:

```text
main
```

and require:

```text
terraform fmt
terraform validate
terraform plan
IaC security scan
review approval
```

before merge.

For production-sensitive Terraform:

```text
infra/prod/*
```

I might also require approval from designated platform or operations owners through CODEOWNERS-style controls.

### **Why this matters**

Without protection:

```text
Developer
   ↓
git push origin main
   ↓
Production pipeline
```

one mistake could bypass:

* review
* tests
* security scanning
* approval

With protection:

```text
Change
  ↓
PR gate
  ↓
Validated + reviewed
  ↓
Merge
```

Git becomes part of the production-control boundary.

### **Important distinction**

Branch protection controls **source-control changes**.

It does not by itself replace:

* Azure RBAC
* deployment-environment approvals
* CI/CD permissions
* production access controls

For strong defense in depth:

```text
Git branch protection
        ↓
CI checks
        ↓
Deployment approval
        ↓
Azure least privilege
        ↓
Production
```

### **Interview answer condensed**

> “Branch-protection rules prevent important branches like `main` from being changed without required controls. I would typically block direct pushes, require pull requests, successful CI checks, reviewer approvals, and restrict force pushes or deletion. For infrastructure repositories, I would also require Terraform validation and security checks before merge. Branch protection secures the source-control workflow, but I would still enforce deployment permissions separately.”

**Memory line:**
**Protected `main` means changes must pass policy before they become trusted code.**

**Interview trap:**
Do not assume protecting `main` alone secures production. A poorly permissioned CI/CD identity could still bypass other controls.

**Keywords:**
Branch protection, required checks, PR review, CODEOWNERS, force-push restriction, protected branch, policy gate.

**Likely follow-ups:**

* How would you prevent direct pushes to `main`?
* What checks would you require for Terraform repositories?
* What are CODEOWNERS?
* How is branch protection different from deployment approvals?
