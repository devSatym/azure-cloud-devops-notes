### **T24-H01. What branching strategy would you choose for a team practicing continuous delivery?**

**Answer:**

For a team practicing continuous delivery, I would normally choose **trunk-based development with short-lived feature branches**.

`main` would be the single integration branch and should always remain in a deployable state. Developers create small branches, make focused changes, raise pull requests, pass automated CI checks and code review, and merge back into `main` quickly—ideally within hours or a day or two rather than keeping branches alive for weeks.

I would avoid a heavy GitFlow model unless the product genuinely requires maintaining several release versions, because long-lived `develop`, feature, and release branches create integration delays and merge conflicts.

For incomplete features, I wouldn't keep code isolated in a branch for weeks. I would merge the code safely behind **feature flags**, so integration happens continuously while exposure to users remains controlled.

```text
Developer
   ↓
Short-lived feature branch
   ↓
Pull Request
   ↓
CI + Tests + Security checks
   ↓
Review
   ↓
main
   ↓
Always releasable artifact
   ↓
Dev / Staging
   ↓
Production approval or automatic deployment
```

The objective is simple: **reduce the distance between a developer's code and the production-ready trunk.**

### **Why trunk-based development fits continuous delivery**

Continuous delivery depends on being able to take the current version of the software and deploy it safely at almost any time.

That becomes difficult if the repository looks like:

```text
main
  |
  +-------- develop
              |
              +------ feature-A (3 weeks)
              |
              +------ feature-B (4 weeks)
              |
              +------ feature-C (2 weeks)
```

Each branch diverges from the others.

Eventually:

```text
Large branch
     +
Large branch
     +
Changed main
     ↓
Huge integration event
     ↓
Merge conflicts
     ↓
Regression testing
     ↓
Delayed release
```

That's almost the opposite of continuous integration.

With trunk-based development:

```text
main ──A──B──C──D──E──F
       ↑  ↑  ↑  ↑  ↑
     small PRs merged continuously
```

Differences remain small, so problems are easier to review, test, diagnose, revert, and deploy.

Microsoft's current Azure Repos guidance similarly recommends a simple model built around feature branches, pull requests into `main`, and keeping `main` high quality and current. ([Microsoft Learn][1])

---

### **How I would implement it in production**

I would establish several rules.

#### **1. `main` is protected**

Nobody casually pushes directly into `main`.

Changes follow:

```text
feature branch
      ↓
Pull Request
      ↓
Review + CI
      ↓
main
```

This protects the branch that represents deployable code.

---

#### **2. Branches are short-lived**

For example:

```text
feature/add-payment-timeout
bugfix/order-validation
fix/health-probe
```

I would encourage small changes rather than a branch called:

```text
feature/new-platform
```

that lives for six weeks.

Smaller PRs mean:

* easier code review,
* faster CI,
* fewer conflicts,
* easier rollback,
* lower deployment risk.

---

#### **3. CI runs before merging**

A PR should trigger checks such as:

```text
Pull Request
     ↓
Lint / formatting
     ↓
Unit tests
     ↓
Build
     ↓
Integration tests
     ↓
SAST / dependency scan
     ↓
Policy checks
     ↓
Merge allowed
```

Only validated code reaches `main`.

---

#### **4. `main` should always be releasable**

This is a major principle.

A team shouldn't say:

> "`main` is currently broken; wait until tomorrow."

If `main` breaks, fixing or reverting it becomes the priority.

---

#### **5. Use feature flags for incomplete work**

Suppose a payment redesign requires ten days of work.

A common mistake would be:

```text
feature/payment-v2

keep branch for 10 days
↓
huge PR
↓
big-bang merge
```

Instead:

```text
Day 1 → interface merged but disabled
Day 2 → backend component merged but disabled
Day 3 → API changes merged
...
Day 10 → feature flag enabled
```

Production may contain the new implementation while users still see the old behavior.

```text
Application
   |
   +-- Feature flag OFF → old payment flow
   |
   +-- Feature flag ON  → new payment flow
```

This separates:

**deploying code**

from:

**releasing functionality**.

That's extremely useful in continuous delivery.

---

### **Continuous Delivery does not mean every merge must reach production automatically**

This is an important distinction.

You could have:

```text
Merge to main
     ↓
Build artifact
     ↓
Automatic deployment to Dev
     ↓
Automatic deployment to Staging
     ↓
Production approval
     ↓
Production
```

That is **Continuous Delivery** because production remains deployable, but there is still a manual business or operational decision before production.

Continuous Deployment would typically continue automatically:

```text
main
 ↓
CI
 ↓
Staging verification
 ↓
automated production deployment
```

So the branching strategy supports both.

---

### **What about release branches?**

I would not say:

> "Release branches should never exist."

They can make sense when maintaining several supported product versions.

For example:

```text
main
 |
 +--- release/4.x
 |
 +--- release/3.x
```

Suppose a company supports:

```text
Product 3.x
Product 4.x
Product 5.x
```

Security fixes may need to be backported separately.

But for a typical SaaS platform deployed continuously to Azure:

```text
One active production version
+
frequent releases
```

I would strongly prefer one mainline and short-lived branches.

---

### **Why not GitFlow by default?**

Traditional GitFlow may have:

```text
main
develop
feature/*
release/*
hotfix/*
```

That can be appropriate for certain versioned products, but it introduces additional synchronization points.

For fast-moving DevOps environments:

```text
More branches
    ↓
More divergence
    ↓
More merging
    ↓
More integration risk
    ↓
Slower feedback
```

So I wouldn't adopt GitFlow just because it's well known.

The branching model should match the release model.

---

### **Azure DevOps / GitHub implementation**

Whether the repository is in GitHub or Azure Repos, I would enforce the workflow technically rather than relying on developers remembering the rule.

For `main`:

```text
main
 │
 ├── PR required
 ├── minimum reviewers
 ├── CI required
 ├── security checks
 ├── comments resolved
 ├── direct pushes restricted
 └── force pushes restricted
```

GitHub supports required PR reviews, status checks, merge queues, linear history and other protected-branch controls. ([GitHub Docs][2])

Azure Repos similarly supports PR policies, required reviewers, build validation, status checks and related controls. ([Microsoft Learn][1])

---

### **High-volume teams: merge queue**

There's another interesting production issue.

Suppose:

```text
PR-A → CI passed
PR-B → CI passed
PR-C → CI passed
```

All were tested against `main` at approximately the same time.

PR-A merges.

Now the code base changes.

Technically PR-B's previously successful test may no longer represent:

```text
PR-B + newest main
```

For very busy repositories, a merge queue can test changes against the current merge candidate before integrating them. GitHub specifically supports merge queues for this kind of high-throughput protected-branch workflow. ([GitHub Docs][2])

---

### **Trade-offs**

Trunk-based development requires discipline.

It works well when you have:

```text
fast CI
small PRs
strong automated tests
feature flags
good observability
easy rollback
```

If CI takes three hours and tests are unreliable, trunk-based development becomes painful.

So branching strategy and CI architecture are connected.

---

### **Interview answer condensed**

> “For continuous delivery, I'd normally use trunk-based development with short-lived feature branches. Developers make small changes, raise PRs, pass code review and required CI checks, and merge back into a protected `main` branch frequently. `main` should always remain releasable. For incomplete functionality I'd prefer feature flags rather than long-lived branches, because that allows continuous integration without exposing unfinished functionality. I would avoid heavy GitFlow unless we genuinely needed multiple supported release lines, because long-lived branches increase divergence, merge conflicts, and integration risk.”

**Memory line:**
**Continuous delivery works best when changes reach a permanently releasable trunk quickly and safely.**

**Interview trap:**
Trunk-based development **doesn't necessarily mean everyone directly pushes to `main`**; short-lived PR branches are fully compatible with trunk-based development.

**Keywords:**
Trunk-based development, short-lived branches, protected `main`, PR, CI, feature flags, small changes, continuous integration, releasable trunk, merge queue.

### **T24-H02. How would you recover from a bad commit already merged into production?**

**Answer:**

I would separate this into two problems: **restore production first**, then **repair the source-of-truth branch**.

If the bad change is actively causing a production incident, I would first assess impact and, when possible, roll the deployment back to the last known-good artifact rather than spending time debugging while users are affected.

Then I would revert the offending Git commit using `git revert`, normally through a pull request. `git revert` creates a new commit that reverses the bad change while preserving shared history, which makes it safer than rewriting `main` with `git reset`.

After CI passes, I would merge the revert, deploy it, verify application metrics and logs, and then investigate why the original change escaped testing.

```text
Bad commit
    ↓
main
    ↓
Production
    ↓
Incident
    ↓
Stabilize / rollback deployment
    ↓
git revert bad commit
    ↓
PR + CI
    ↓
main corrected
    ↓
Redeploy
    ↓
Validate
```

---

### **The first question is: how severe is the incident?**

I wouldn't immediately start typing Git commands.

First I would determine:

```text
Is production actually impacted?
        ↓
How severely?
        ↓
Can we quickly identify the release?
```

I would look at:

* 5xx rate,
* latency,
* failed transactions,
* error logs,
* affected users,
* deployment timestamp,
* health probes,
* business-critical functions.

Suppose:

```text
13:00 deployment
13:02 5xx jumps from 0.1% → 25%
```

and nothing else changed.

The deployment becomes a very strong suspect.

---

## **Step 1 — Stabilize production**

If the deployment mechanism supports fast rollback, I would restore the previously tested artifact.

For example:

```text
v1.8.3 ← known good
v1.8.4 ← bad release
```

Rollback:

```text
Production
v1.8.4
   ↓
v1.8.3
```

This is slightly different from Git revert.

### Deployment rollback

Changes **what is running**.

### Git revert

Changes **what the repository considers current code**.

This distinction matters.

You might restore production in two minutes using the previous container image, while the revert PR takes another ten minutes to pass CI.

---

## **Step 2 — Identify the offending Git change**

I'd confirm the change.

For example:

```bash
git log --oneline --decorate -20
```

I might see:

```text
f84c921 Add new payment retry logic
a918832 Update documentation
20bac01 Previous production version
```

If telemetry clearly shows the failure began with `f84c921`, that becomes the revert candidate.

I wouldn't blindly revert merely because it was the latest commit if several other infrastructure or configuration changes happened at the same time.

---

## **Step 3 — Revert rather than rewrite shared history**

For a normal commit:

```bash
git revert f84c921
```

Git creates another commit conceptually like:

```text
A -- B -- C -- BAD -- REVERT
```

History remains intact.

The resulting content undoes `BAD`.

That's preferable on a shared branch to doing something like:

```bash
git reset --hard <old-commit>
git push --force
```

because force-resetting `main` rewrites history other developers may already depend on.

---

### **Why `git revert` is safer**

Suppose the history is:

```text
A -- B -- C -- D
               ↑
             bad
```

`git reset` could move the branch pointer:

```text
A -- B -- C
```

and effectively rewrite the published history.

`git revert D` produces:

```text
A -- B -- C -- D -- R
```

where:

```text
R = inverse of D
```

That gives you:

* auditability,
* traceability,
* preserved history,
* less disruption for other clones,
* a clear record of the incident correction.

GitHub's built-in PR-revert workflow similarly creates a new PR containing a revert of the merged change rather than rewriting branch history. ([GitHub Docs][3])

---

## **What if the bad change was a merge commit?**

This is a useful interview follow-up.

If I need to revert a merge commit manually, Git may require the mainline parent:

```bash
git revert -m 1 <merge-commit-sha>
```

`-m 1` tells Git which parent represents the mainline.

I would be careful here rather than mechanically running the command because reverting a merge can affect later attempts to remerge the same changes.

---

## **Step 4 — Put the revert through CI**

Even emergency fixes should ideally be validated.

```text
revert branch
     ↓
Pull Request
     ↓
Build
     ↓
Unit tests
     ↓
Integration/smoke tests
     ↓
Merge
```

Why test a revert?

Because:

> Reversing one commit doesn't guarantee the repository is now valid.

Later commits may depend on the bad commit.

Example:

```text
Commit A → new database field
Commit B → application starts using field
Commit C → another service depends on B
```

Reverting only A might make things worse.

---

## **Step 5 — Deploy and verify recovery**

After deployment I would verify both technical and business indicators.

For example:

```text
Deployment successful
      ↓
Health checks healthy?
      ↓
5xx returned to baseline?
      ↓
Latency normalized?
      ↓
Business transactions succeeding?
      ↓
No secondary errors?
```

I would not call the incident resolved simply because:

```text
kubectl rollout status
```

says the deployment completed.

Deployment success does not mean application success.

---

### **Database changes make rollback harder**

This is one of the most important production caveats.

Imagine the bad deployment did:

```sql
DROP COLUMN customer_phone;
```

Rolling the application binary back does not recreate the data.

Or suppose the release changed schema:

```text
Application v2
     ↓
database migration
     ↓
schema v2
```

Then you deploy application v1 again:

```text
Application v1
     ↓
schema v2
```

They may be incompatible.

That's why mature teams prefer backward-compatible migrations such as **expand-and-contract**:

```text
1. Add new schema
2. Deploy app that supports old + new
3. Migrate data
4. Switch usage
5. Remove old schema later
```

This keeps rollback possible during the deployment window.

---

### **What if the bad change contains a security issue?**

Then restoring functionality isn't necessarily enough.

For example, if the commit accidentally exposed a secret:

```text
commit secret
   ↓
production deployment
```

I would:

```text
revoke/rotate credential
       ↓
remove usage
       ↓
revert/fix code
       ↓
review access/audit logs
```

Removing the secret from Git alone doesn't invalidate a credential that someone may already have copied.

---

### **What if rollback is more dangerous than fixing forward?**

Sometimes I would not revert.

Suppose:

```text
Version 3
↓
irreversible data migration
↓
minor API bug
```

A rollback could create a data compatibility incident much worse than the current issue.

Then the safer approach may be:

```text
Production issue
     ↓
feature disable / traffic mitigation
     ↓
small forward fix
     ↓
CI
     ↓
deploy
```

So the decision is:

```text
Rollback risk
      vs
Forward-fix risk
```

not an ideological rule that rollback is always better.

---

### **After recovery: prevent recurrence**

Once production is stable, I would investigate why the bad change passed.

For example:

```text
Bad commit reached production
          ↓
Why?
          ↓
Missing test?
Bad review?
CI gap?
Feature flag missing?
Canary metrics missing?
Manual deployment?
Inadequate alert?
```

Possible improvements might include:

* regression tests,
* stronger PR validation,
* canary deployment,
* automated health gates,
* feature flags,
* immutable artifacts,
* better deployment observability.

---

### **Interview answer condensed**

> “If a bad commit has already reached production, my priority is to restore service rather than debug indefinitely. If possible I'd roll the deployment back to the last known-good immutable artifact first. Then I'd revert the offending Git change using `git revert`, normally through a PR and CI, because revert preserves the shared history instead of rewriting `main` like `git reset --hard` plus force push would. After redeployment I'd verify error rate, latency, health and business transactions. I'd also check whether database migrations or other irreversible changes make rollback unsafe; in that case I might prefer a controlled forward fix.”

**Memory line:**
**Rollback restores production; `git revert` restores the repository—often you need both.**

**Interview trap:**
Do not confuse `git reset` with `git revert`: rewriting published `main` history with reset/force-push is usually the wrong recovery mechanism.

**Keywords:**
Known-good artifact, rollback, `git revert`, shared history, PR, CI, forward fix, database compatibility, expand-and-contract, validation.

**Likely follow-ups:**

* Why would you use `git revert` instead of `git reset`?
* How do you revert a merge commit?
* What if the deployment included a database migration?
* When would you fix forward rather than roll back?
* What if the bad commit exposed a credential?

### **T24-H03. How would you prevent direct pushes to `main`?**

**Answer:**

I would enforce it at the repository platform level rather than relying on a team convention.

In GitHub I would protect `main` using a **branch protection rule or ruleset**, require changes through pull requests, require appropriate reviews and CI checks, prevent force pushes and deletion, and tightly control or disable bypass permissions.

In Azure Repos I would combine **branch policies and branch permissions** so normal contributors can work through pull requests but cannot bypass the policies or force-push directly to `main`.

The intended flow is:

```text
Developer
   │
   ├── git push origin main ──────X rejected
   │
   └── push feature branch
             ↓
        Pull Request
             ↓
       Review + CI
             ↓
           main
```

Current GitHub protected-branch controls include PR reviews, required status checks, restrictions on pushes, blocking force pushes/deletion, and controls around bypassing protections. ([GitHub Docs][2])

Azure Repos similarly recommends branch permissions plus required policies and warns that broad bypass permissions defeat those protections. ([Microsoft Learn][4])

---

## **Why enforcement matters**

A policy written in a wiki saying:

> "Please don't push to main."

is not a control.

Someone can still run:

```bash
git push origin main
```

and accidentally bypass:

```text
code review
CI tests
security scanning
approval
audit workflow
```

Production controls should enforce the rule.

---

## **GitHub approach**

I would target `main` with a ruleset or branch protection configuration.

Conceptually:

```text
main protection
│
├── Require pull request
├── Require reviewers
├── Require status checks
├── Require conversation resolution
├── Block force pushes
├── Block deletion
└── Restrict bypass
```

GitHub's current protected-branch capabilities support these types of controls. ([GitHub Docs][2])

### **Normal developer flow**

```bash
git switch -c feature/add-health-check
git add .
git commit -m "Add health check"
git push -u origin feature/add-health-check
```

Then:

```text
feature/add-health-check
        ↓
      PR
        ↓
   required checks
        ↓
     review
        ↓
      main
```

---

## **Do administrators get to bypass it?**

This requires thought.

If every administrator can casually bypass protections:

```text
branch protection
      ↓
administrator bypass
      ↓
protection effectively optional
```

For production repositories, I would minimize bypass rights.

A reasonable model might be:

```text
Developers
    → no bypass

Team leads
    → normally no bypass

Repository administrators
    → tightly controlled

Emergency release group
    → bypass only under documented incident procedure
```

GitHub also provides an option to avoid allowing bypass of protected-branch requirements. ([GitHub Docs][2])

---

## **Azure Repos approach**

For Azure DevOps/Azure Repos I would configure `main` branch policies such as:

```text
main
│
├── minimum reviewers
├── build validation
├── comment resolution
├── status checks
└── other required policies
```

and then review branch permissions carefully.

The important permissions include controls around:

```text
Bypass policies when completing PRs
Bypass policies when pushing
Force push
Edit policies
Manage permissions
```

Microsoft currently recommends keeping these bypass permissions restricted to a small trusted group. ([Microsoft Learn][4])

Azure Repos documentation also states that with required branch policies, direct changes are expected to go through PRs unless the user has the relevant bypass permission. ([Microsoft Learn][5])

---

## **Why I would also block force pushes**

Even after direct pushes are controlled, force pushing is dangerous for a shared production branch.

For example:

```text
main:
A -- B -- C -- D
```

Someone does:

```bash
git reset --hard B
git push --force
```

Now the visible branch could become:

```text
A -- B
```

Potentially removing:

```text
C
D
```

from normal branch history.

So I would disable force-push capability for ordinary users.

---

## **Why I would prevent branch deletion**

Similarly:

```bash
git push origin --delete main
```

should not be part of a normal developer permission model.

Critical branches should have stronger controls than temporary feature branches.

---

## **Service accounts and CI bots matter too**

An overlooked security issue is protecting `main` from humans but giving automation unrestricted repository write permissions.

Imagine:

```text
Compromised CI workflow
        ↓
Git token with broad write
        ↓
push directly to main
```

That bypasses the human control.

So repository access should follow least privilege for:

* users,
* bots,
* GitHub Apps,
* pipeline identities,
* automation tokens.

If CI only needs to read source, give it read access.

---

## **Break-glass access**

For a high-availability production environment, some organizations retain a controlled emergency path.

For example:

```text
Normal operation
      ↓
PR required

Major incident
      ↓
authorized incident commander
      ↓
temporary emergency bypass
      ↓
audited change
      ↓
remove bypass
      ↓
post-incident review
```

That is very different from giving every senior engineer permanent bypass permission.

---

## **What I would test after configuring protection**

I would verify it from a normal developer identity.

Try:

```bash
git push origin main
```

Expected:

```text
rejected
```

Then test:

```text
feature branch
     ↓
PR
```

Expected:

```text
PR allowed
merge blocked until policies satisfied
```

Security controls should be tested, not merely assumed from the configuration page.

---

### **Interview answer condensed**

> “I would prevent direct pushes using repository-enforced branch protection rather than a team convention. For GitHub I'd protect `main` with a branch protection rule or ruleset requiring PRs and normally reviews and status checks, while disabling force pushes, branch deletion and unnecessary bypass access. In Azure Repos I'd apply required branch policies and restrict `Bypass policies when pushing` and force-push permissions. Developers would push only to short-lived branches and update `main` through reviewed PRs. I'd also apply least privilege to CI bots because an automation identity with unrestricted write access can bypass the same controls we're trying to enforce.”

**Memory line:**
**Protect `main` with permissions and policies, not promises.**

**Interview trap:**
Branch protection is weak if administrators, service accounts, or broad groups have unrestricted **bypass** permissions.

**Keywords:**
Protected branch, ruleset, branch policy, pull request, bypass permission, force push, branch deletion, least privilege, auditability.

### **T24-H04. How would you require CI checks before a pull request can be merged?**

**Answer:**

I would make CI a **blocking repository policy**, not just a pipeline that happens to run.

The PR would trigger a validation pipeline that builds and tests the exact proposed change. The pipeline could run unit tests, integration tests, linting, IaC validation and security checks. Then I would configure the target branch so selected CI results are **required status checks** in GitHub, or **required Build Validation/status-check policies** in Azure Repos.

The merge button should remain blocked unless all mandatory checks succeed.

```text
Developer pushes commit
        ↓
Pull Request
        ↓
CI starts
        ↓
Build
        ↓
Tests
        ↓
Security / Quality gates
        ↓
Pass? ───── No ──→ Merge blocked
  │
 Yes
  ↓
Review requirements
  ↓
Merge allowed
```

GitHub's current documentation confirms that required status checks on protected branches/rulesets must satisfy the configured requirements before merging. ([GitHub Docs][2])

Azure Repos provides blocking Build Validation policies for the equivalent workflow. ([Microsoft Learn][5])

---

## **Step 1 — Create a PR validation pipeline**

For example, with GitHub Actions:

```yaml
name: pr-validation

on:
  pull_request:
    branches:
      - main

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build
        run: ./scripts/build.sh

      - name: Unit tests
        run: ./scripts/test.sh
```

Conceptually:

```text
PR opened/updated
       ↓
GitHub Actions
       ↓
validate job
       ↓
check result
```

If the job fails:

```text
validate = failed
```

and repository protection should prevent merging.

---

## **Step 2 — Decide which checks are truly required**

I wouldn't necessarily make every optional pipeline job blocking.

For example:

```text
Required:
├── build
├── unit-tests
├── integration-tests
├── lint
├── SAST
└── Terraform validate/plan checks

Optional:
├── performance benchmark
└── experimental compatibility test
```

The required set should represent conditions that must be true before code can safely enter `main`.

---

## **Step 3 — Configure GitHub required status checks**

In GitHub, I would target `main` with a branch protection rule or ruleset and configure:

```text
Require a pull request
        +
Require status checks before merging
        ↓
build
unit-tests
integration-tests
security-scan
```

Then:

```text
PR
│
├── build ✅
├── tests ✅
├── security ✅
└── review ✅
       ↓
    merge
```

If:

```text
security ❌
```

then:

```text
merge blocked
```

GitHub allows required checks to be associated with an expected GitHub App as an additional protection against accepting a similarly named status from an unintended source. ([GitHub Docs][2])

That's a useful supply-chain security detail.

---

## **Strict versus loose status checks**

Suppose:

```text
main      A---B
               \
feature          C
```

CI runs for C and passes.

Before C merges, another PR changes `main`:

```text
main      A---B---D
               \
feature          C
```

Now the previous test didn't necessarily validate:

```text
D + C
```

A **strict** policy can require the PR branch to be up to date with the base branch before merging. GitHub documents both strict and loose required-status-check behavior. ([GitHub Docs][2])

Trade-off:

```text
Strict
 ↓
stronger integration confidence
 ↓
potentially more CI runs

Loose
 ↓
fewer rebuilds
 ↓
higher possibility of integration incompatibility
```

For heavily active repositories, a merge queue can address much of this problem by validating queued changes against the current target state. ([GitHub Docs][2])

## **Azure Repos implementation**

With Azure Repos, the concept is very similar but the terminology differs.

```text
Azure Repos PR
      ↓
Branch Policy
      ↓
Build Validation
      ↓
Azure Pipeline
      ↓
success / failure
      ↓
PR completion allowed / blocked
```

I would configure the `main` branch policy with:

```text
Build validation
Trigger: Automatic
Policy requirement: Required
```

Microsoft documents required build validation as a blocking condition: when the policy is required, the PR cannot complete until the validation build succeeds. ([Microsoft Learn][5])

This is an important Azure DevOps interview point.

---

### **Azure Repos PR validation vs normal CI**

A candidate should distinguish:

```text
CI build after merge
```

from:

```text
PR validation before merge
```

If my only pipeline is:

```text
merge to main
     ↓
CI runs
```

then CI detects the bad code **after it has already entered `main`**.

What I want is:

```text
PR
 ↓
validation
 ↓
only if successful
 ↓
main
```

That's prevention rather than detection.

---

## **What checks would I normally include?**

For an application going to AKS, for example:

```text
PR
│
├── code formatting/lint
├── unit tests
├── application build
├── integration tests
├── dependency vulnerability scan
├── SAST
├── Dockerfile checks
├── Helm lint
└── Terraform fmt/validate/plan where relevant
```

Not every project needs every check, but the principle is:

> Validate the properties required for safely integrating the change.

---

## **Security implication: PR pipelines execute untrusted code**

This is especially important in public repositories or organizations with many contributors.

A PR can change:

```text
source code
build scripts
tests
package scripts
sometimes workflow-related files
```

So a PR pipeline may effectively execute contributor-controlled code.

Therefore I would avoid unnecessarily giving PR-validation jobs:

```text
production credentials
Azure Contributor access
deployment secrets
ACR push rights
production Kubernetes credentials
```

A safer pattern is:

```text
PR CI
│
└── minimal/read-only credentials

main/release workflow
│
└── deployment identity via OIDC
```

This separates:

```text
Can validate code
```

from:

```text
Can deploy production
```

---

## **Do not trust a green status just because of its name**

Imagine the required check is called:

```text
security
```

but several workflows create checks with ambiguous names.

GitHub specifically warns that identical job names across workflows can produce ambiguous required-status-check results; unique job names are preferable. ([GitHub Docs][2])

So I would use clear names such as:

```text
pr-build
pr-unit-tests
pr-security-scan
```

---

## **What happens when someone pushes another commit to the PR?**

The old CI result shouldn't simply authorize the new commit.

Conceptually:

```text
PR commit A
   ↓
CI passes

Developer pushes commit B
   ↓
PR changes
   ↓
CI runs again
```

The checks should validate the current PR head / merge candidate.

Azure Repos' automatic Build Validation policy can queue validation when a PR is created or updated. ([Microsoft Learn][5])

---

## **Production-quality flow**

For an Azure/AKS application, I would want something similar to:

```text
Feature branch
      ↓
Pull Request
      ↓
PR validation
      │
      ├── build
      ├── test
      ├── security
      └── IaC validation
      ↓
Code review
      ↓
Merge into main
      ↓
Build immutable image
      ↓
Push to ACR
      ↓
Deploy Dev
      ↓
Stage
      ↓
Production
```

This gives a clear separation between:

```text
PR validation
```

and:

```text
trusted deployment pipeline
```

## **Failure-mode reasoning**

If someone tells me:

> "CI passes, but GitHub still doesn't let us merge."

I would investigate in this order:

```text
Is the required check actually complete?
           ↓
Correct check name configured?
           ↓
Check corresponds to current commit?
           ↓
Branch required to be up-to-date?
           ↓
Review requirement satisfied?
           ↓
Conversation-resolution requirement?
           ↓
Merge queue requirement?
           ↓
Ruleset/branch protection conflict?
```

If the workflow never runs, I'd then inspect:

```text
event trigger
branch filter
path filter
workflow permissions
workflow configuration
```

rather than assuming GitHub itself is broken.

### **Interview answer condensed**

> “I'd configure PR validation as a blocking repository policy. A pull request targeting `main` would automatically trigger CI for the proposed change—typically build, tests, linting and security checks. In GitHub I'd protect `main` and configure those jobs as required status checks; in Azure Repos I'd use a required automatic Build Validation branch policy. Until those checks succeed, the PR cannot merge. For busy repositories I'd consider requiring the branch to be current with `main` or using a merge queue so the actual merge candidate is validated. I'd also keep production credentials out of PR-validation jobs because PR code should be treated as less trusted than code already merged into the protected branch.”

**Memory line:**
**CI protects `main` only when passing CI is a server-enforced prerequisite for merging.**

**Interview trap:**
A pipeline that runs **after merging to `main`** is not the same as a **blocking PR validation check**.

**Keywords:**
Required status checks, Build Validation, branch protection, PR validation, blocking policy, strict checks, merge queue, least privilege, CI gates.

**Likely follow-ups:**

* What would you do if a required check never appears?
