### **T24-M01. What is the difference between merge and rebase?**

**Answer:**
Both `git merge` and `git rebase` integrate changes from different branches, but they do it differently. **Merge preserves the existing branch history**, while **rebase rewrites commits onto a new base to create a more linear history**.

### **How merge works**

Suppose:

```text
main
A ── B ── C
     \
      D ── E
      feature
```

If I merge `feature` into `main`:

```bash
git switch main
git merge feature
```

the result may be:

```text
A ── B ── C ────── M
     \             /
      D ── E ─────
```

`M` is a merge commit.

The original commits stay unchanged.

---

### **How rebase works**

If I rebase the feature branch onto the latest `main`:

```bash
git switch feature
git rebase main
```

the result becomes:

```text
A ── B ── C ── D' ── E'
```

The feature changes are replayed after `C`.

`D'` and `E'` are **new commits with new hashes**.

### **Key difference**

```text
Merge
→ preserve history
→ combine branches

Rebase
→ rewrite history
→ replay commits on a new base
```

### **When I would use each**

I would commonly use **rebase on my own local feature branch** to bring it up to date with `main` and keep history clean.

I would generally prefer **merge or the repository's configured PR strategy** when integrating reviewed work into a shared branch.

For example:

```text
Local feature branch
      ↓
rebase onto latest main
      ↓
resolve conflicts
      ↓
PR
      ↓
merge/squash according to team policy
```

### **Important distinction**

Rebase changes commit identity.

For example:

```text
Before:
D = abc123

After rebase:
D' = def456
```

So rebasing a shared branch can break other developers' history.

### **Interview answer condensed**

> “Merge integrates two histories while preserving the existing commits and may create a merge commit. Rebase takes commits from one branch and reapplies them onto a new base, creating new commit hashes and a linear history. I’m comfortable rebasing my private feature branch, but I avoid rebasing shared history because it can disrupt other developers.”

**Memory line:**
**Merge joins history; rebase rewrites history.**

**Interview trap:**
Do not say rebase simply “moves” commits unchanged. It creates new commits with new hashes.

**Keywords:**
Merge commit, rebase, linear history, history rewriting, commit hash, shared branch.

### **T24-M02. What is a merge conflict?**

**Answer:**
A merge conflict happens when Git cannot automatically decide how to combine competing changes. This usually occurs when two branches modify the same lines, or when one branch deletes something another branch modifies.

### **Example**

Suppose `main` contains:

```text
replicas: 3
```

One branch changes it to:

```text
replicas: 5
```

while another changes it to:

```text
replicas: 10
```

Git cannot know which value is correct.

During the merge, Git may show:

```text
<<<<<<< HEAD
replicas: 5
=======
replicas: 10
>>>>>>> feature
```

I have to decide what the final version should be.

For example:

```text
replicas: 5
```

Then I mark the conflict as resolved:

```bash
git add deployment.yaml
git commit
```

For a rebase, after fixing and staging the file, I would instead continue with:

```bash
git rebase --continue
```

### **How I would resolve conflicts safely**

My process would be:

```text
Identify conflicting files
        ↓
Understand both intended changes
        ↓
Edit the final correct version
        ↓
Run tests / validation
        ↓
Stage resolved files
        ↓
Continue merge or rebase
```

The important part is **understanding the intent**, not simply removing Git's conflict markers.

### **DevOps example**

A common Terraform conflict might happen when two branches both modify:

```hcl
resource "azurerm_kubernetes_cluster" "aks" {
    ...
}
```

One changes node count while another changes networking.

Even if the text conflict is easy to resolve, I would still run:

```bash
terraform fmt
terraform validate
terraform plan
```

because a syntactically resolved conflict can still produce the wrong infrastructure behavior.

### **Important distinction**

A merge conflict is not necessarily an application error.

Git is saying:

> “I cannot automatically determine the intended final content.”

A human must decide.

### **Interview answer condensed**

> “A merge conflict occurs when Git cannot automatically reconcile changes, usually because branches modified overlapping lines or one branch changed something another deleted. I resolve it by understanding both changes, editing the correct final version, staging it, and then continuing the merge or rebase. Afterward I always run the relevant tests or validation.”

**Memory line:**
**Conflict means Git cannot decide; the developer must decide the intended final state.**

**Interview trap:**
Do not resolve conflicts by blindly accepting “ours” or “theirs”; that can silently remove valid changes.

**Keywords:**
Merge conflict, conflict markers, `git add`, `git rebase --continue`, validation.

**Likely follow-ups:**

* What causes conflicts during rebase?
* How do you abort a merge?
* How do you abort a rebase?
* What is “ours” versus “theirs”?

### **T24-M03. What is `git cherry-pick`?**

**Answer:**
`git cherry-pick` applies the changes introduced by a specific commit onto the branch I am currently on. It is useful when I want **one particular change without merging the entire source branch**.

### **Example**

Suppose:

```text
main
A ── B ── C

release
A ── B ── X
```

Commit `X` contains an important production bug fix.

If I want only that fix on `main`:

```bash
git switch main
git cherry-pick <commit-hash>
```

The result becomes:

```text
main
A ── B ── C ── X'
```

`X'` contains the same logical change, but it is a **new commit with a different hash**.

### **Production example**

Imagine a developer fixes a security issue on a development branch:

```text
feature branch
      ↓
commit abc123
"Fix authentication bypass"
```

The next release is weeks away, but production needs the fix immediately.

I could:

```bash
git switch hotfix
git cherry-pick abc123
```

Then test and deploy that isolated fix.

### **When it is useful**

Typical cases include:

* backporting a bug fix
* applying a hotfix to a release branch
* recovering a useful commit from another branch
* moving one isolated change without taking unrelated commits

### **When I would avoid it**

I would not use repeated cherry-picking as the normal way to synchronize long-lived branches.

For example:

```text
branch A
   ↓
cherry-pick
   ↓
branch B
   ↓
cherry-pick back
```

can create confusing duplicate histories.

For regular branch integration, merge or rebase is usually cleaner.

### **Important distinction**

Cherry-pick copies the **change introduced by a commit**, not the original commit object itself.

Therefore:

```text
Original commit: abc123
Cherry-picked:   def456
```

Different hash, similar content.

### **Interview answer condensed**

> “`git cherry-pick` takes the change from a specific commit and applies it to my current branch as a new commit. I would use it for something like backporting a production hotfix without merging an entire feature branch. I would avoid using cherry-pick as a general branch-synchronization strategy because it can create duplicated and confusing history.”

**Memory line:**
**Cherry-pick = take one commit's change, not the whole branch.**

**Interview trap:**
Do not say cherry-pick preserves the original commit hash; it normally creates a new commit.

**Keywords:**
Cherry-pick, commit hash, backport, hotfix, isolated change.

### **T24-M04. What is `git revert`?**

**Answer:**
`git revert` safely undoes the effect of an existing commit by creating a **new commit that applies the opposite change**. It is commonly preferred for undoing changes that have already been pushed to a shared branch because it preserves history instead of rewriting it.

### **How it works**

Suppose:

```text
A ── B ── C
```

Commit `C` introduced a bug.

Running:

```bash
git revert <C-commit-hash>
```

creates:

```text
A ── B ── C ── R
```

where `R` reverses the changes introduced by `C`.

The original commit remains visible in history.

### **Production example**

Suppose a Terraform change is merged to `main`:

```text
Commit C
→ modifies production networking
```

After deployment, the change causes connectivity problems.

Rather than rewriting `main`, I might create a revert:

```bash
git revert <commit-hash>
git push
```

Then the normal CI/CD process runs again:

```text
Revert commit
     ↓
PR / CI checks
     ↓
terraform plan
     ↓
approval
     ↓
apply
```

This gives the team an auditable rollback.

### **Why revert is safer on shared branches**

Consider:

```text
main:
A ── B ── C
```

Other developers may already have based work on `C`.

If I remove `C` by rewriting history, their branches can become inconsistent.

With revert:

```text
A ── B ── C ── R
```

everyone keeps the same shared history.

### **Important distinction**

`git revert` does **not delete the original commit**.

It creates another commit that logically undoes it.

That is why it is different from commands that move branch history backward.

### **Special case: merge commits**

Reverting a merge commit requires care because Git needs to know which parent represents the mainline:

```bash
git revert -m 1 <merge-commit>
```

I would verify the history carefully before doing this in production because reverting merges can affect later merge behavior.

### **Interview answer condensed**

> “`git revert` undoes a commit by creating a new commit containing the inverse change. It preserves the original history, so it is usually the safer option for backing out a bad commit that has already been pushed to a shared branch such as `main`. I would then let the normal CI/CD pipeline validate and deploy the revert.”

**Memory line:**
**Revert adds history that undoes a change; it does not erase history.**

**Interview trap:**
Do not confuse `git revert` with `git reset`. Revert preserves shared history; reset can move the branch pointer and potentially rewrite history.

**Keywords:**
`git revert`, inverse commit, shared history, rollback, audit trail, merge revert.
