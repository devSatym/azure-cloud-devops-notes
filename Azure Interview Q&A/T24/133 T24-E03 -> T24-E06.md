### **T24-E03. What is a branch?**

**Answer:**
A Git branch is a **movable pointer to a line of commits** that lets developers work on changes independently from other work. It is commonly used for features, bug fixes, releases, or experiments without immediately changing `main`.

### **How it works**

```text
main
A ── B ── C
         \
          D ── E
          feature/login
```

The feature branch contains commits `D` and `E`, while `main` still points to `C`.

A developer can create and switch branches with:

```bash
git switch -c feature/login
```

After the work is complete, it is usually reviewed through a pull request and then merged.

### **Production example**

A common DevOps workflow is:

```text
main
  ↓
feature branch
  ↓
code / Terraform change
  ↓
pull request
  ↓
CI checks
  ↓
review
  ↓
merge
```

This keeps unfinished or unreviewed changes away from the production branch.

### **Important distinction**

A branch is lightweight in Git. Git does not copy the entire repository when you create one; it mainly creates another reference to a commit.

**Memory line:**
**A branch is an independent line of development pointing to a sequence of commits.**

**Interview trap:**
Do not describe a branch as a full duplicate copy of the repository.

**Keywords:**
Branch, `main`, feature branch, commit pointer, merge, pull request.

### **T24-E04. What is a pull request?**

**Answer:**
A pull request, or PR, is a collaboration workflow used to **propose changes from one branch into another**, usually into `main`. It allows the team to review code, run automated checks, discuss changes, and approve them before merging.

### **Typical flow**

```text
Developer branch
      ↓
Push changes
      ↓
Pull Request
      ↓
├── Code review
├── CI tests
├── Security checks
└── Approval
      ↓
Merge into main
```

### **Production example**

For a Terraform change:

```text
feature/add-private-endpoint
        ↓
Pull Request
        ↓
terraform fmt
terraform validate
terraform plan
security scan
        ↓
Reviewer approval
        ↓
Merge
```

This creates a controlled infrastructure-change process rather than letting engineers directly modify production.

### **Why PRs matter in DevOps**

Pull requests help enforce:

* peer review
* branch protection
* required CI checks
* approval policies
* auditability

They are often part of the security boundary around the production branch.

### **Important distinction**

A pull request is not itself a Git primitive like `commit` or `branch`.

It is a collaboration feature provided by platforms such as:

* GitHub
* Azure Repos
* GitLab

### **Memory line:**

**A pull request is a controlled proposal to merge one branch into another.**

**Interview trap:**
Do not say opening a PR automatically merges the code. It starts the review and validation process.

**Keywords:**
Pull request, review, merge, branch protection, CI checks, approval.

### **T24-E05. What is `git merge`?**

**Answer:**
`git merge` combines the history of another branch into the branch I am currently on. Depending on the commit history, Git may perform either a **fast-forward merge** or create a **merge commit**.

### **How it works**

Suppose:

```text
main
A ── B ── C
         \
          D ── E
          feature
```

If I switch to `main` and run:

```bash
git merge feature
```

Git can combine the feature changes into `main`.

A merge commit might produce:

```text
A ── B ── C ────── M
         \         /
          D ── E ─
```

`M` records that the two histories were joined.

### **Fast-forward case**

If `main` has not changed since the branch was created:

```text
main
A ── B
     \
      C ── D
      feature
```

Git may simply move `main` forward:

```text
A ── B ── C ── D
              ↑
             main
```

No merge commit is necessary.

### **Production example**

A reviewed feature might go through:

```text
feature branch
      ↓
Pull request
      ↓
CI passes
      ↓
git merge / platform merge
      ↓
main
```

The exact merge strategy may be controlled by repository policy.

### **Important distinction**

Merge usually **preserves the branch topology** and existing commits.

That is different from rebase, which rewrites commits onto a new base.

**Memory line:**
**Merge joins two lines of Git history together.**

**Interview trap:**
Do not assume every merge creates a merge commit; a fast-forward merge may simply move the branch pointer.

**Keywords:**
Merge, merge commit, fast-forward, branch history, conflict.

### **T24-E06. What is `git rebase`?**

**Answer:**
`git rebase` moves or reapplies a sequence of commits onto a new base commit. It is commonly used to create a cleaner, more linear history, but because it **rewrites commit history**, it should be used carefully on shared branches.

### **How it works**

Suppose:

```text
main
A ── B ── C
     \
      D ── E
      feature
```

If I rebase `feature` onto the latest `main`:

```bash
git switch feature
git rebase main
```

Git reapplies the feature commits after `C`:

```text
A ── B ── C ── D' ── E'
                  feature
```

`D'` and `E'` are new commits with new commit hashes.

### **Why teams use rebase**

It can make history easier to read:

```text
A ── B ── C ── D ── E
```

instead of having many unnecessary branch-divergence points.

It is commonly used to update a local feature branch with the latest `main` before opening or completing a pull request.

### **Important distinction**

```text
merge
→ combines histories

rebase
→ rewrites commits onto a new base
```

Because rebasing creates new commits, I generally avoid rebasing commits that other developers are already using from a shared branch.

### **Production example**

A safe common workflow is:

```text
local feature branch
      ↓
git fetch origin
      ↓
git rebase origin/main
      ↓
resolve conflicts
      ↓
push updated feature branch
```

If the rebased branch was already pushed, updating the remote may require a force update. In that case, `--force-with-lease` is safer than an unconditional `--force` because it checks that the remote branch has not unexpectedly changed.

### **Memory line:**

**Rebase replays commits on a new base and creates a cleaner linear history.**

**Interview trap:**
Do not casually rebase shared public history; rebase changes commit IDs and can disrupt other developers.

**Keywords:**
Rebase, history rewriting, linear history, new base, commit hash, `--force-with-lease`.
