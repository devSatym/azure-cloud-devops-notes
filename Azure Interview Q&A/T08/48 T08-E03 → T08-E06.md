# 8. 🔴 M IMP — Azure DevOps & GitHub Actions CI/CD

## Easy

### **T08-E03. What is Continuous Deployment?**

**Answer:**
**Continuous Deployment** is a software delivery practice where every change that successfully passes the automated CI/CD pipeline is **automatically deployed to production without requiring a manual approval step**.

The flow looks like:

```text
Developer commit
      ↓
Build
      ↓
Unit tests
      ↓
Security scans
      ↓
Integration tests
      ↓
Deploy staging
      ↓
Automated validation
      ↓
Production automatically
```

The core idea is:

> If the change passes all required automated quality gates, it can reach production automatically.

### **Continuous Delivery vs Continuous Deployment**

This is the main interview distinction:

```text
Continuous Delivery

Commit
  ↓
Build/Test
  ↓
Production-ready
  ↓
Manual approval
  ↓
Production
```

versus:

```text
Continuous Deployment

Commit
  ↓
Build/Test
  ↓
Production automatically
```

So:

```text
Delivery
→ deployment-ready automatically

Deployment
→ deployed automatically
```

### **Example with GitHub Actions**

Suppose the workflow does:

```text
Push to main
     ↓
Run tests
     ↓
Build Docker image
     ↓
Trivy security scan
     ↓
Push image to ACR
     ↓
Update AKS deployment
     ↓
Production
```

If there is **no manual production approval** after all automated checks pass, that's Continuous Deployment.

### **Is every commit deployed immediately?**

Not necessarily.

It means every change that **successfully passes the defined pipeline gates** can automatically reach production.

A failed test means:

```text
Commit
 ↓
Tests fail ❌
 ↓
Production deployment stops
```

### **Production safeguards**

Continuous Deployment usually needs strong automation around:

```text
automated tests
security scanning
progressive rollout
health checks
observability
automatic rollback
feature flags
```

For example:

```text
New version
   ↓
Canary 10%
   ↓
Metrics healthy?
   ├── Yes → 100%
   └── No  → rollback
```

This reduces the risk of automatically shipping a bad release.

**Memory line:**
**Continuous Deployment = every change that passes the pipeline automatically reaches production.**

**Interview trap:**
Don't confuse:

```text
Continuous Delivery
→ manual production decision may remain

Continuous Deployment
→ production deployment is automatic
```

**Keywords:** Continuous Deployment, automation, production, CI/CD, quality gates, rollback

### **T08-E04. What is Azure DevOps?**

**Answer:**
**Azure DevOps** is Microsoft's cloud-based DevOps platform that provides services for managing source code, CI/CD pipelines, work tracking, testing, and software artifacts.

Its major services are:

```text
Azure DevOps
│
├── Azure Repos
├── Azure Pipelines
├── Azure Boards
├── Azure Artifacts
└── Azure Test Plans
```

### **Azure Repos**

Used for source control with Git repositories.

```text
Developer
   ↓
git push
   ↓
Azure Repos
```

Typical features include:

```text
Pull Requests
branch policies
code reviews
Git repositories
```

---

### **Azure Pipelines**

Used for CI/CD.

```text
Source code
    ↓
Azure Pipeline
    ├── Build
    ├── Test
    ├── Scan
    ├── Package
    └── Deploy
```

For example:

```text
Azure Repos / GitHub
       ↓
Azure Pipelines
       ↓
Docker build
       ↓
ACR
       ↓
AKS
```

---

### **Azure Boards**

Used for project/work tracking:

```text
Epic
 ↓
Feature
 ↓
User Story
 ↓
Task / Bug
```

Teams can use it for Agile or Scrum workflows.

---

### **Azure Artifacts**

Provides package feeds for things such as:

```text
NuGet
npm
Maven
Python packages
Universal Packages
```

So internal application dependencies can be published and consumed securely.

---

### **Azure Test Plans**

Used for manual/exploratory testing management and test-case tracking.

### **DevOps example**

A complete workflow could be:

```text
Azure Boards
    ↓
Developer implements task
    ↓
Azure Repos
    ↓
Pull Request
    ↓
Azure Pipelines
    ↓
Build + Test + Security Scan
    ↓
ACR
    ↓
AKS deployment
```

### **Azure DevOps vs Azure itself**

Important distinction:

```text
Microsoft Azure
→ cloud platform

Azure DevOps
→ software-development / DevOps platform
```

I can use Azure DevOps to deploy to:

```text
Azure
AWS
GCP
on-premises
Kubernetes
```

It isn't restricted only to Azure resources.

### **Azure DevOps vs GitHub**

Both can support modern software-development workflows.

For example:

```text
Azure DevOps
→ Azure Repos + Azure Pipelines + Boards

GitHub
→ GitHub repos + GitHub Actions + Issues/Projects
```

Which one is used often depends on organizational tooling, governance, existing workflows, and integrations.

**Memory line:**
**Azure DevOps = Microsoft's integrated platform for code, CI/CD, work tracking, testing, and artifacts.**

**Interview trap:**
Don't say:

> “Azure DevOps is just Azure Pipelines.”

Azure Pipelines is only **one service inside Azure DevOps**.

**Keywords:** Azure DevOps, Repos, Pipelines, Boards, Artifacts, Test Plans

### **T08-E05. What are Azure Pipelines?**

**Answer:**
**Azure Pipelines** is the CI/CD service inside Azure DevOps that automates building, testing, packaging, and deploying applications and infrastructure.

A pipeline could look like:

```text
Git commit
    ↓
Azure Pipeline
    ├── Build
    ├── Test
    ├── Security scan
    ├── Publish artifact
    └── Deploy
```

### **Example application pipeline**

Suppose I have a Dockerized API:

```text
Developer pushes code
        ↓
Azure Pipeline triggered
        ↓
npm test
        ↓
docker build
        ↓
security scan
        ↓
push image to ACR
        ↓
deploy to AKS
```

This automates the release process.

### **Pipelines can be defined as YAML**

A simplified example:

```yaml
trigger:
  - main

pool:
  vmImage: ubuntu-latest

steps:
  - script: npm ci
  - script: npm test
  - script: docker build -t myapp .
```

Keeping pipeline configuration in YAML gives:

```text
pipeline as code
+
version control
+
code review
+
repeatability
```

### **Pipeline hierarchy**

A useful mental model is:

```text
Pipeline
│
├── Stage
│   ├── Job
│   │   ├── Step
│   │   ├── Step
│   │   └── Step
│   │
│   └── Job
│
└── Stage
```

For example:

```text
Pipeline
├── Build Stage
│   ├── Test Job
│   └── Build Job
│
├── Staging Stage
│   └── Deploy Job
│
└── Production Stage
    └── Deploy Job
```

### **What executes the jobs?**

Jobs run on a:

```text
pipeline agent
```

which can be:

```text
Microsoft-hosted
or
self-hosted
```

We'll cover agents shortly.

### **Application + Infrastructure pipelines**

Azure Pipelines isn't only for application code.

Terraform pipeline:

```text
Pull Request
   ↓
terraform fmt
   ↓
terraform validate
   ↓
terraform plan
```

Deployment:

```text
Approved main branch
   ↓
terraform apply
```

So the same CI/CD platform can automate:

```text
applications
containers
infrastructure
Kubernetes
```

**Memory line:**
**Azure Pipelines = Azure DevOps' CI/CD engine.**

**Interview trap:**
Don't define an Azure Pipeline as only a “deployment script.”

It can cover the entire lifecycle:

```text
Build → Test → Scan → Package → Deploy
```

**Keywords:** Azure Pipelines, CI/CD, YAML, stages, jobs, steps, agents

### **T08-E06. What is GitHub Actions?**

**Answer:**
**GitHub Actions** is GitHub's built-in automation and CI/CD platform. It allows workflows to run automatically in response to GitHub events such as pushes, pull requests, releases, or manual triggers.

The basic flow is:

```text
GitHub Repository
      ↓
Event
push / pull_request / manual
      ↓
GitHub Actions Workflow
      ↓
Jobs
      ↓
Steps
      ↓
Runner executes them
```

### **Example**

A workflow might trigger whenever code is pushed to `main`:

```yaml
name: CI

on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - run: npm ci

      - run: npm test
```

Conceptually:

```text
git push main
      ↓
GitHub Actions
      ↓
Ubuntu runner
      ↓
checkout
      ↓
install
      ↓
test
```

### **Important GitHub Actions hierarchy**

Remember:

```text
Workflow
   ↓
Jobs
   ↓
Steps
   ↓
Actions / shell commands
```

Example:

```text
Workflow: deploy.yml

├── Job: test
│   ├── checkout
│   ├── npm install
│   └── npm test
│
├── Job: build
│   └── docker build
│
└── Job: deploy
    └── deploy to AKS
```

### **What is an Action?**

An **action** is a reusable unit that performs a task.

For example:

```yaml
- uses: actions/checkout@v4
```

checks out repository code.

Other actions can:

```text
authenticate to Azure
configure Docker
upload artifacts
run security tooling
deploy workloads
```

### **What is a runner?**

A runner is the machine that executes the workflow job.

```text
GitHub Actions Workflow
         ↓
       Runner
         ↓
executes commands
```

It can be:

```text
GitHub-hosted runner
or
self-hosted runner
```

We'll cover this separately in **T08-E08**.

### **Azure deployment example**

A common Azure CI/CD flow is:

```text
Developer
   ↓
GitHub
   ↓
GitHub Actions
   ↓
OIDC authentication to Azure
   ↓
Build container
   ↓
Push to ACR
   ↓
Deploy/update AKS
```

For Azure authentication, a strong production pattern is using **OIDC federation** rather than storing a long-lived Azure client secret in GitHub.

Conceptually:

```text
GitHub Actions
      ↓
OIDC token
      ↓
Microsoft Entra ID
      ↓
short-lived Azure access token
```

### **GitHub Actions vs Azure Pipelines**

At interview level:

| Area                | GitHub Actions        | Azure Pipelines               |
| ------------------- | --------------------- | ----------------------------- |
| Platform            | GitHub                | Azure DevOps                  |
| Pipeline definition | YAML workflows        | YAML pipelines                |
| Execution machine   | Runner                | Agent                         |
| GitHub integration  | Native                | Supported                     |
| Azure integration   | Strong                | Strong                        |
| Main concept        | Workflow → Job → Step | Pipeline → Stage → Job → Step |

Both can implement:

```text
CI
CD
Terraform
Docker
AKS deployments
security scanning
```

**Memory line:**
**GitHub Actions = event-driven automation and CI/CD built directly into GitHub.**

**Interview trap:**
Don't say:

> “GitHub Actions is only for deploying applications.”

It can automate almost any repository workflow:

```text
testing
building
security scanning
Terraform
releases
container publishing
deployments
scheduled jobs
```

**Keywords:** GitHub Actions, workflow, job, step, runner, event, CI/CD
