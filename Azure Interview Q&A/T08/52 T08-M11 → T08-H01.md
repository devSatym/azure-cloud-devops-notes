# 8. 🔴 M IMP — Azure DevOps & GitHub Actions CI/CD

## Medium

### **T08-M11. Why is OIDC federation preferred over client secrets?**

**Answer:**
OIDC federation is preferred because it lets a CI/CD workflow obtain **short-lived cloud credentials on demand instead of storing a long-lived client secret** in GitHub or Azure DevOps.

The difference is:

```text
Client-secret model

Pipeline
   ↓
Stored client secret
   ↓
Microsoft Entra ID
   ↓
Azure access token
```

versus:

```text
OIDC federation

Pipeline
   ↓
Short-lived OIDC identity token
   ↓
Microsoft Entra ID validates trust
   ↓
Short-lived Azure access token
```

GitHub explicitly recommends OIDC because workflows can access cloud resources without maintaining long-lived cloud credentials as GitHub secrets. ([GitHub Docs][1])

### **1. No long-lived cloud credential to steal**

With a traditional service principal:

```text
AZURE_CLIENT_ID
AZURE_CLIENT_SECRET   ← sensitive
AZURE_TENANT_ID
```

The secret may remain valid for:

```text
months
or
years
```

If exposed through:

* logs,
* repository configuration,
* compromised runner,
* accidental copy/paste,
* third-party action,

an attacker may reuse it until it expires or is revoked.

With OIDC:

```text
Workflow starts
   ↓
GitHub/Azure DevOps proves workload identity
   ↓
Azure issues short-lived token
   ↓
Token expires
```

There is no reusable Azure client secret sitting in the CI/CD platform. ([GitHub Docs][2])

---

### **2. No manual secret rotation**

Client secrets require lifecycle management:

```text
Create secret
   ↓
Store in CI/CD
   ↓
Track expiry
   ↓
Rotate secret
   ↓
Update CI/CD
```

If rotation is missed:

```text
secret expires
→ production pipeline suddenly fails
```

With OIDC federation:

```text
No static client secret
→ no client-secret rotation cycle
```

Azure DevOps currently recommends Workload Identity Federation for Azure service connections instead of secret-based service-principal authentication where possible. ([Microsoft Learn][3])

---

### **3. Trust can be scoped to a specific workload**

Federation doesn't simply mean:

```text
GitHub → Azure
```

The trust can be constrained to something specific such as:

```text
repository
branch
environment
workflow identity
```

For example:

```text
repo:company/payment-api
branch: main
```

can be trusted for production deployment while:

```text
feature/random-test
```

isn't.

GitHub recommends defining trust conditions so untrusted repositories or workflows can't obtain cloud access tokens. ([GitHub Docs][1])

A production model might be:

```text
Feature branch
     ↓
No production federation

main branch
     ↓
Production GitHub Environment
     ↓
Required approval
     ↓
OIDC federation
     ↓
Production Azure identity
```

---

### **4. Short-lived credentials reduce exposure**

With OIDC:

```text
Job starts
   ↓
short-lived Azure token issued
   ↓
job executes
   ↓
token expires
```

GitHub describes these access tokens as short-lived and tied to workflow execution rather than persistent credentials. ([GitHub Docs][2])

If one were exposed, the reuse window is far smaller than a six-month client secret.

---

### **5. OIDC doesn't replace Azure RBAC**

OIDC handles:

> **How does the pipeline authenticate?**

Azure RBAC handles:

> **What can it do?**

For example:

```text
GitHub Actions
     ↓ OIDC
Production deployment identity
     ↓ RBAC
AcrPush on ACR
     +
limited AKS permissions
```

instead of:

```text
Owner on entire subscription ❌
```

So a secure setup combines:

```text
OIDC federation
+
least-privilege RBAC
```

### **Comparison**

| Area                        | Client Secret       | OIDC Federation            |
| --------------------------- | ------------------- | -------------------------- |
| Stored credential           | Yes                 | No long-lived cloud secret |
| Credential lifetime         | Usually long        | Short-lived                |
| Rotation required           | Yes                 | No static secret rotation  |
| Leakage impact              | Potentially large   | Reduced                    |
| Workload-specific trust     | Less elegant        | Strong                     |
| Recommended modern approach | Legacy where needed | ✅ Preferred                |

### **Interview answer condensed**

> “OIDC federation is preferred because the pipeline doesn't store a long-lived Azure client secret. Instead, GitHub Actions or Azure DevOps presents a federated workload identity, Entra validates its claims, and issues a short-lived Azure token. That reduces secret leakage and rotation risk, and trust can be restricted to a particular repository, branch, or environment. I still combine it with least-privilege Azure RBAC.”

**Memory line:**
**OIDC replaces stored cloud credentials with short-lived federated tokens.**

**Interview trap:**
Don't say:

> “OIDC means there are no credentials.”

There are still credentials/tokens during execution—they're simply **short-lived and dynamically issued rather than long-lived secrets stored in CI/CD**.

**Keywords:** OIDC, federation, short-lived token, client secret, Entra ID, least privilege

### **T08-M12. How would you trigger different pipelines for different branches?**

**Answer:**
I would use **branch filters in the pipeline trigger**, and normally map different branch types to different CI/CD behavior.

For example:

```text
feature/*
   ↓
CI only

develop
   ↓
CI + deploy Dev

main
   ↓
CI + deploy Staging
   ↓
approval
   ↓
Production
```

Azure Pipelines supports `include` and `exclude` branch filters for CI and related triggers. ([Microsoft Learn][4])

### **Azure Pipelines example**

A feature pipeline:

```yaml
trigger:
  branches:
    include:
      - feature/*
```

A development pipeline:

```yaml
trigger:
  branches:
    include:
      - develop
```

Production pipeline:

```yaml
trigger:
  branches:
    include:
      - main
```

Now:

```text
feature/login
→ feature pipeline

develop
→ dev pipeline

main
→ production delivery pipeline
```

### **Or one pipeline with branch-based stages**

I don't necessarily need separate YAML files.

I can have:

```text
One Pipeline
    │
    ├── feature/* → Build + Test
    │
    ├── develop   → Build + Test + Dev
    │
    └── main      → Build + Test + Staging + Prod
```

using conditions.

Conceptually:

```yaml
- stage: DeployProd
  condition: and(
    succeeded(),
    eq(variables['Build.SourceBranch'], 'refs/heads/main')
  )
```

This is often easier when most of the workflow is common.

### **Include and exclude**

For example:

```yaml
trigger:
  branches:
    include:
      - feature/*
      - main
    exclude:
      - feature/experimental/*
```

Azure Pipelines supports both branch and path filtering, including wildcards. ([Microsoft Learn][5])

So I can also say:

```text
Only run backend pipeline
when:
services/backend/**
changes
```

That becomes particularly useful in a monorepo.

---

### **Pull Request triggers**

I normally separate:

```text
PR validation
```

from:

```text
deployment after merge
```

For example:

```text
PR → main
   ↓
Build
Unit tests
Lint
Security scan
Terraform plan
   ↓
NO production deployment
```

Then:

```text
Merge → main
   ↓
Deployment pipeline
```

Azure Pipelines supports branch filters for PR triggers where supported by the repository integration. ([Microsoft Learn][6])

### **GitHub Actions equivalent**

GitHub Actions supports the same concept:

```yaml
on:
  push:
    branches:
      - main
      - 'releases/**'
```

or:

```yaml
on:
  pull_request:
    branches:
      - main
```

GitHub's current documentation supports branch and path filters for `push` and `pull_request` events. ([GitHub Docs][7])

### **Realistic strategy**

For a production project I'd commonly use:

```text
feature/*
    ↓
PR
    ↓
CI
├── unit tests
├── SAST
├── dependency scan
└── container scan

merge → develop
    ↓
Dev deployment

merge → main
    ↓
Build immutable artifact
    ↓
Staging
    ↓
approval/check
    ↓
Production
```

### **Separate pipelines vs conditions**

My rule of thumb:

```text
Very different workflows
→ separate pipelines

Mostly same workflow,
different deployment behavior
→ one multi-stage pipeline + conditions/templates
```

**Memory line:**
**Use branch filters to decide when a pipeline starts, and conditions to decide which stages run.**

**Interview trap:**
Don't make:

```text
feature/*
```

deploy directly to production just because it can trigger a pipeline.

Triggering and deployment authorization should be separate controls.

**Keywords:** branch filter, trigger, PR, `main`, `develop`, conditions, path filters

### **T08-M13. How can approvals be added before a production deployment?**

**Answer:**
In Azure DevOps, I would normally create a protected **Production Environment** and configure an **Approval and Check** on that environment. When a deployment job reaches production, Azure DevOps pauses it until an authorized approver approves it.

```text
Build
  ↓
Test
  ↓
Deploy Staging
  ↓
Smoke Tests
  ↓
Production Environment
  ↓
┌─────────────────────┐
│ Manual Approval     │
└─────────────────────┘
  ↓
Deploy Production
```

Azure DevOps specifically supports manual approval checks on environments and other protected pipeline resources. ([Microsoft Learn][8])

### **Why put approval on the Environment?**

This is important.

The approval isn't merely:

```yaml
if someone changes YAML,
approval disappears
```

Environment checks are managed **outside the YAML pipeline**.

That gives better separation:

```text
Application team
→ edits pipeline YAML

Production owners
→ control production Environment checks
```

Microsoft explicitly notes that approvals/checks aren't defined by the pipeline YAML author. ([Microsoft Learn][8])

### **Typical setup**

```text
Azure DevOps
   ↓
Pipelines
   ↓
Environments
   ↓
production
   ↓
Approvals and checks
   ↓
Approver:
Production Operations Group
```

Then when the pipeline reaches:

```text
DeployProduction
```

it waits.

### **Deployment job example**

Conceptually:

```yaml
- stage: Production
  jobs:
  - deployment: DeployProd
    environment: production

    strategy:
      runOnce:
        deploy:
          steps:
          - script: ./deploy.sh
```

Because:

```text
environment = production
```

has an approval check, the pipeline can't enter that deployment until the check succeeds.

### **Add branch control too**

Approval alone isn't the complete production security model.

I would also ensure production can only deploy from:

```text
refs/heads/main
```

using branch protection and/or Azure DevOps **Branch Control checks**.

Azure DevOps supports a branch-control check that validates whether deployment resources originated from allowed/protected branches. ([Microsoft Learn][8])

Production flow:

```text
main branch?
   ↓ yes

Branch protected?
   ↓ yes

CI passed?
   ↓ yes

Production approval?
   ↓ yes

Deploy
```

### **Other checks**

Production environments can also use controls such as:

```text
Business hours
Azure Monitor alerts
REST/Azure Function checks
Exclusive lock
Required templates
```

depending on the organization. ([Microsoft Learn][8])

Example:

```text
Production stage
     ↓
Main branch check
     ↓
No critical Azure Monitor alert
     ↓
Maintenance window
     ↓
Manual approval
     ↓
Deploy
```

### **GitHub Actions equivalent**

With GitHub Actions, the equivalent pattern is a protected:

```text
GitHub Environment:
production
```

with deployment protection rules/required reviewers where available.

Then:

```text
deploy job
   ↓
environment: production
   ↓
approval/protection rules
   ↓
Azure OIDC authentication
   ↓
production
```

This is especially useful with OIDC because the production federated trust can also be associated with the production environment. GitHub recommends environment protection when environments participate in OIDC policies. ([GitHub Docs][1])

**Memory line:**
**Put the production approval on the protected deployment environment, not merely inside a script.**

**Interview trap:**
A line like:

```bash
read -p "Deploy?"
```

inside a pipeline script is **not** proper production governance.

Use platform-level approvals/checks with auditable identities.

**Keywords:** Azure DevOps Environment, approvals, checks, branch control, production gate

**Likely follow-ups:**

* Why put approval outside YAML?
* Can you restrict production to `main`?
* What happens if approval times out?
* What other checks can run before deployment?

### **T08-H01. Design a CI/CD pipeline for an application deployed to AKS.**

**Answer:**
I would separate **CI from deployment**, build the container exactly once, produce an immutable image identified by Git SHA/digest, authenticate to Azure with OIDC federation, publish to ACR, validate security before promotion, and deploy the **same artifact** through Dev → Staging → Production with environment controls.

A production-oriented flow is:

```text
Developer
   ↓
Feature Branch
   ↓
Pull Request
   ↓
┌─────────────────────────────┐
│ CI                          │
│ ├── Lint                    │
│ ├── Unit tests              │
│ ├── SAST                    │
│ ├── Dependency scan         │
│ └── Docker build validation │
└─────────────────────────────┘
   ↓
Review + Branch Protection
   ↓
Merge main
   ↓
Build container ONCE
   ↓
Scan image
   ↓
Push ACR
   ↓
Immutable SHA / Digest
   ↓
Deploy Dev
   ↓
Smoke tests
   ↓
Deploy Staging
   ↓
Integration tests
   ↓
Approval
   ↓
Deploy Production
   ↓
Health validation
   ↓
Monitor / rollback
```

GitHub Actions can build and deploy container workloads from ACR to AKS, and Microsoft recommends pipeline/IaC automation for repeatability and controlled deployment. ([Microsoft Learn][9])

# **5. Build once, deploy many**

This is crucial.

Bad:

```text
Build dev image
Build staging image
Build prod image
```

because the binaries may differ.

Good:

```text
Build once

payment-api@sha256:abc123...
            ↓
      ┌─────┼─────┐
      ↓     ↓     ↓
     Dev  Stage  Prod
```

I promote the **same digest** through every environment.

That means:

> What I tested in staging is what I deploy to production.

# **6. Deploy to AKS**

There are two strong deployment models.

### **Model A — Pipeline directly deploys**

```text
CI/CD
 ↓
helm upgrade
 ↓
AKS
```

Example:

```bash
helm upgrade --install payment-api \
  ./helm/payment-api \
  --set image.tag=7bc23ab
```

This is simple and common.

For a **private AKS cluster**, the deployment runner/agent needs private connectivity:

```text
GitHub/Azure DevOps
       ↓
Self-hosted Runner/Agent
inside VNet
       ↓
Private AKS API
```

---

### **Model B — GitOps**

For a more GitOps-oriented architecture:

```text
CI
 ↓
Build + scan image
 ↓
Push ACR
 ↓
Update Git desired state
 ↓
Argo CD / Flux
 ↓
AKS
```

Example:

```text
GitHub Actions
     ↓
ACR:
payment-api:7bc23ab
     ↓
update Helm image tag/digest
     ↓
Git commit
     ↓
Argo CD
     ↓
AKS
```

This has an important security advantage:

```text
CI doesn't need broad direct kubectl access
```

because the GitOps controller pulls desired state from Git.

For a platform with many Kubernetes services, I generally like this model.

# **10. Use a safe Kubernetes rollout strategy**

For a normal Deployment:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

Conceptually:

```text
v1 Pods
● ● ●

Deploy v2

● ● ● + ○
          ↑ v2

v2 becomes Ready

● ● ○ ○

Eventually

○ ○ ○
```

where `○` represents new version Pods.

Availability depends on correct:

```text
readinessProbe
replicas
resource requests
PodDisruptionBudget
graceful shutdown
```

### **For higher-risk releases**

I may use:

```text
Canary
or
Blue/Green
```

Example:

```text
Production traffic
       ↓
  95% → v1
   5% → v2
       ↓
metrics healthy?
   ├── Yes → 100% v2
   └── No  → rollback
```

# **12. Rollback strategy**

Because the image is immutable:

```text
current:
payment-api:7bc23ab

previous:
payment-api:48a7c91
```

rollback is straightforward:

```text
Deploy previous known-good digest
```

For Kubernetes Deployment:

```bash
kubectl rollout undo deployment/payment-api
```

can be useful, though in a GitOps environment I prefer reverting the Git desired state so Git remains the source of truth.

```text
Bad release
   ↓
Git revert
   ↓
Argo CD
   ↓
previous image restored
```

# **14. Separate identities by responsibility**

I wouldn't use one giant identity.

For example:

```text
CI Build Identity
└── AcrPush

└── required AKS permissions

└── scoped infrastructure permissions
```

### **Interview answer condensed**

> “For AKS, I'd validate every PR with tests and security scans, protect `main`, and after merge build the container exactly once. I'd authenticate to Azure through OIDC or workload identity federation, scan and push the immutable Git-SHA/digest image to ACR, then promote that same artifact through Dev, Staging, and Production. Production would be protected by environment/branch controls and approvals. Deployment could be direct Helm or GitOps with Argo CD/Flux. I'd use rolling or canary deployment, readiness probes, multiple replicas, post-deployment health checks, Azure Monitor, and an automatic or fast rollback to the previous known-good digest.”

**Memory line:**
**PR validation → build once → scan → ACR → promote same digest → approval → AKS → verify → rollback if unhealthy.**

**Interview trap:**
Avoid designs that:

```text
Rebuild separately for production ❌
Store Azure client secrets ❌
Use latest tag only ❌
Give CI subscription Owner ❌
Deploy before PR/security gates ❌
Declare success without post-deploy health checks ❌
```
