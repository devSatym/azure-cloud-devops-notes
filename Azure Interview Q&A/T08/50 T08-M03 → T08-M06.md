# 8. 🔴 M IMP — Azure DevOps & GitHub Actions CI/CD

## Medium

### **T08-M03. What is an Azure DevOps environment?**

**Answer:**
An **Azure DevOps Environment** is a logical representation of a deployment target such as **Dev, Staging, or Production**. It is mainly used by deployment jobs to track deployments, control access, and apply approvals/checks before a pipeline can deploy.

For example:

```text
Azure Pipeline
     ↓
Build
     ↓
Deploy Dev
     ↓
Environment: dev
     ↓
Deploy Staging
     ↓
Environment: staging
     ↓
Approval
     ↓
Environment: production
```

An environment can represent an actual target such as Kubernetes or virtual machines, but it can also simply act as the controlled deployment boundary for a stage.

### **Typical environments**

```text
dev
test
staging
production
```

Pipeline:

```yaml
stages:
  - stage: DeployDev

  - stage: DeployStaging

  - stage: DeployProduction
```

Each deployment stage can target a corresponding Azure DevOps environment.

---

### **Why environments matter**

They provide several useful capabilities:

```text
Deployment history
Approvals
Checks
Security/permissions
Target resource tracking
Traceability
```

For example, for production:

```text
Pipeline
   ↓
production environment
   ↓
Approval required
   ↓
Deployment allowed
```

Azure DevOps supports approvals and checks on resources such as environments, and importantly those checks are configured **outside the pipeline YAML**. That prevents someone who can merely edit the pipeline YAML from simply removing the production approval. ([Microsoft Learn][1])

### **Example production approval**

Suppose:

```text
Environment:
production
```

has:

```text
Approver:
DevOps Team Lead
```

Then:

```text
Build ✅
Tests ✅
Security scan ✅
        ↓
Production stage
        ↓
WAITING FOR APPROVAL
        ↓
Approved
        ↓
Deploy
```

This is a common way to implement **Continuous Delivery** rather than fully automatic Continuous Deployment.

### **Checks can be more than manual approval**

Azure DevOps environment/resource checks can include things such as:

```text
Manual approvals
Branch control
Business-hours restrictions
Azure Monitor alert checks
REST API/Azure Function checks
Exclusive locks
Required templates
```

([Microsoft Learn][1])

For example:

```text
Production deployment
       ↓
Is branch = main?
       ↓
Are there active critical alerts?
       ↓
Is current time inside maintenance window?
       ↓
Manual approval
       ↓
Deploy
```

### **Environment vs pipeline stage**

These are different concepts:

```text
Stage
→ part of pipeline execution

Environment
→ deployment target/governance boundary
```

For example:

```text
Stage:
DeployProd
      ↓
Environment:
production
```

### **AKS example**

For an AKS application:

```text
Azure Pipeline
      ↓
Deployment Job
      ↓
Environment: production
      ↓
AKS cluster / namespace
      ↓
Helm deployment
```

That gives deployment history and governance around the production target.

**Memory line:**
**Environment = controlled deployment destination such as Dev, Staging, or Production.**

**Interview trap:**
Don't say:

> “An Azure DevOps environment is just a pipeline variable like `ENV=prod`.”

It's a deployment/governance resource with history, permissions, approvals, and checks.

**Keywords:** Environment, deployment target, approval, checks, production, deployment history

**Likely follow-ups:**

* Environment vs stage?
* Where do production approvals live?
* Can someone remove an approval by editing YAML?
* How would you protect production deployments?

### **T08-M04. How are secrets stored in Azure Pipelines?**

**Answer:**
Sensitive values in Azure Pipelines should be stored as **secret variables, protected variable groups, or preferably Azure Key Vault-backed secrets**, rather than directly in YAML or source control.

A secure hierarchy is roughly:

```text
Best for Azure secrets
Azure Key Vault
       ↓
Variable Group / pipeline retrieval
       ↓
Pipeline

Also supported
Secret pipeline variables
```

Microsoft specifically recommends not storing sensitive values as plaintext in `azure-pipelines.yml`, and recommends securely managing important secrets through Azure Key Vault where possible. ([Microsoft Learn][2])

### **Never do this**

```yaml
variables:
  DB_PASSWORD: "ProdPassword123!"
```

because:

```text
Git repository
      ↓
Anyone with source access
      ↓
secret exposed
```

Even deleting it later doesn't necessarily remove it from Git history.

---

### **Option 1 — Secret pipeline variable**

In Azure DevOps pipeline settings I can define:

```text
DB_PASSWORD
************
```

and mark it as secret.

Then use it within the pipeline.

For example:

```yaml
env:
  DB_PASSWORD: $(DB_PASSWORD)
```

Secret variables are encrypted and Azure Pipelines attempts to mask their values in logs. ([Microsoft Learn][3])

### **Important: secret variables aren't automatically environment variables**

Suppose I have:

```text
$(DB_PASSWORD)
```

If a shell script needs it, I should explicitly map it:

```yaml
- bash: |
    ./deploy.sh
  env:
    DB_PASSWORD: $(DB_PASSWORD)
```

Microsoft explicitly notes that secret variables aren't automatically exported as environment variables. ([Microsoft Learn][3])

---

### **Option 2 — Variable Group**

If multiple pipelines require the same secrets:

```text
Pipeline A ─┐
Pipeline B ─┼→ Variable Group
Pipeline C ─┘
```

I could create:

```text
Variable Group:
production-secrets

DB_PASSWORD = secret
API_KEY     = secret
```

Secret values inside variable groups are treated as protected resources and can have pipeline permissions, approvals, and checks. ([Microsoft Learn][4])

---

### **Option 3 — Azure Key Vault**

For production Azure workloads, I prefer:

```text
Azure Key Vault
      ↓
Azure DevOps Variable Group
      ↓
Pipeline
```

The variable group maps Key Vault secret names and retrieves current secret values at pipeline runtime. ([Microsoft Learn][5])

For example:

```text
Key Vault
├── sql-password
├── api-token
└── signing-key
```

Then:

```text
Variable Group
      ↓
Pipeline
```

rather than duplicating secrets inside Azure DevOps.

### **Security benefit**

If:

```text
sql-password
```

changes in Key Vault, pipelines linked to that mapped secret can retrieve the updated value without embedding the secret in YAML. ([Microsoft Learn][5])

---

### **Even better: eliminate secrets where possible**

For Azure authentication, I prefer:

```text
Workload Identity Federation
```

rather than storing:

```text
AZURE_CLIENT_SECRET
```

at all.

For example:

```text
Azure Pipeline
      ↓
OIDC / WIF
      ↓
Microsoft Entra ID
      ↓
short-lived Azure token
```

So good secret management follows:

```text
Can eliminate secret?
      ↓ yes
Use federation / managed identity

      ↓ no
Store in Key Vault
```

---

### **Never print secrets**

Avoid:

```bash
echo "$DB_PASSWORD"
```

and avoid passing secrets directly on command lines where process/logging behavior might expose them.

Microsoft explicitly warns against echoing secrets and recommends avoiding passing them on command lines. ([Microsoft Learn][2])

### **Secret masking is not magic**

Suppose a secret is:

```text
abc123xyz
```

Azure Pipelines attempts to mask known secret values:

```text
***
```

but I should not depend solely on masking.

A badly written script can still leak credentials through:

```text
files
debug dumps
encoded output
third-party tools
command arguments
```

So the real goal is:

```text
minimize secret exposure
+
least privilege
+
short lifetime
```

**Memory line:**
**Don't store secrets in YAML—use secret variables, variable groups, Key Vault, or eliminate them with federation.**

**Interview trap:**
Don't say:

> “Azure DevOps masking makes it safe to print secrets.”

Masking is a safety mechanism, not permission to expose credentials.

**Keywords:** secret variable, Key Vault, variable group, masking, Workload Identity Federation

**Likely follow-ups:**

* Key Vault vs secret variable?
* Are secret variables automatically environment variables?
* How would you authenticate Azure pipelines without a client secret?
* What if several pipelines share the same secrets?

### **T08-M05. What are pipeline variables?**

**Answer:**
Pipeline variables are **named values that let me parameterize and reuse configuration inside an Azure Pipeline** instead of hardcoding values repeatedly.

For example:

```yaml
variables:
  environment: production
  location: centralindia
  imageRepository: myapi
```

Then:

```yaml
- script: echo $(environment)
```

Azure Pipelines supports defining variables in YAML, pipeline settings, variable groups, templates, and dynamically from scripts. ([Microsoft Learn][3])

### **Why use variables?**

Without variables:

```yaml
docker build -t myacr.azurecr.io/payment-api:v15 .
docker push myacr.azurecr.io/payment-api:v15
```

With variables:

```yaml
variables:
  registry: myacr.azurecr.io
  image: payment-api
  tag: $(Build.BuildId)
```

Then:

```yaml
docker build -t $(registry)/$(image):$(tag) .
docker push $(registry)/$(image):$(tag)
```

This improves:

```text
reuse
consistency
maintainability
environment configuration
```

---

### **Built-in variables**

Azure DevOps provides predefined values such as:

```text
Build.BuildId
Build.SourceBranch
Build.SourceVersion
System.TeamProject
```

For example:

```yaml
variables:
  imageTag: $(Build.SourceVersion)
```

produces a Docker tag based on the Git commit.

That's much better than:

```text
latest
```

for traceability.

Example:

```text
payment-api:
7bc23ab
```

means I can map the deployed image back to the source commit.

---

### **Variable scopes**

Variables can exist at different scopes:

```text
Pipeline
  ↓
Stage
  ↓
Job
```

For example:

```yaml
stages:
- stage: Dev
  variables:
    environment: dev

- stage: Prod
  variables:
    environment: prod
```

So the same pipeline can behave differently across environments.

---

### **Variable syntax**

The most common runtime macro syntax is:

```text
$(variableName)
```

For example:

```yaml
- script: echo $(imageRepository)
```

Azure Pipelines also has template-expression and runtime-expression syntax:

```text
${{ variables.name }}
$[ variables.name ]
```

These are evaluated at different phases.

For interview level, remember:

```text
${{ }}
→ template/compile-time expression

$()
→ common runtime macro expansion

$[]
→ runtime expression
```

The distinction becomes important when conditions, templates, and output variables are involved. ([Microsoft Learn][3])

---

### **Variables can be generated dynamically**

Suppose a step determines:

```text
imageTag=1.4.27
```

It can use the Azure Pipelines logging command:

```bash
echo "##vso[task.setvariable variable=imageTag]1.4.27"
```

Then later steps can consume:

```text
$(imageTag)
```

Azure DevOps documents `task.setvariable` for making script-generated values available to subsequent pipeline tasks. ([Microsoft Learn][6])

### **Variables vs secrets**

A normal variable:

```text
environment=prod
```

is configuration.

A secret variable:

```text
DB_PASSWORD=********
```

requires protected handling.

Don't mark everything secret unnecessarily, but never leave sensitive values as normal variables.

### **Variables vs parameters**

This is a common follow-up.

At a simplified interview level:

```text
Parameters
→ primarily chosen/evaluated while pipeline/template is being constructed

Variables
→ values used and potentially changed during pipeline execution
```

For example:

```text
Parameter:
which environment should pipeline deploy?

Variable:
image tag generated by this run
```

**Memory line:**
**Pipeline variables = reusable runtime configuration values for the pipeline.**

**Interview trap:**
Don't treat every pipeline input as a variable.

Azure Pipelines also has:

```text
parameters
variables
output variables
secret variables
```

with different evaluation and security behavior.

**Keywords:** variable, `$(name)`, scope, predefined variable, output variable, runtime

**Likely follow-ups:**

* Variable vs parameter?
* What is `$(Build.BuildId)`?
* How do you set a variable from a script?
* What are variable scopes?

### **T08-M06. What are variable groups?**

**Answer:**
A **variable group** is a centrally managed collection of variables and secrets in Azure DevOps that can be reused across multiple pipelines.

Instead of duplicating:

```text
REGION
ACR_NAME
RESOURCE_GROUP
API_URL
```

inside many YAML files, I can store them once:

```text
Variable Group:
prod-config

REGION = centralindia
ACR_NAME = prodacr
RESOURCE_GROUP = rg-prod
```

Then several pipelines can consume the same values. ([Microsoft Learn][4])

### **Example**

```text
Variable Group:
shared-production
│
├── environment = prod
├── location = centralindia
├── acrName = contosoacr
└── dbPassword = ********
```

Pipeline:

```yaml
variables:
  - group: shared-production
```

Then:

```yaml
- script: echo $(location)
```

Azure DevOps uses exactly this YAML syntax for linking a variable group. ([Microsoft Learn][4])

### **Why use them?**

Imagine:

```text
frontend pipeline
backend pipeline
worker pipeline
Terraform pipeline
```

all need:

```text
AZURE_REGION=centralindia
ENVIRONMENT=prod
```

Without a variable group:

```text
4 copies
```

With one:

```text
              Variable Group
             /      |       \
            /       |        \
Frontend   Backend  Worker   Terraform
```

If the region changes:

```text
centralindia
→ southindia
```

I update the central value instead of editing several pipeline definitions.

---

### **Variable groups can contain secrets**

Example:

```text
nonsecret:
location = centralindia

secret:
db-password = ********
```

Secret variables inside groups receive additional protection as Azure DevOps protected resources, including pipeline permissions and optional approvals/checks. ([Microsoft Learn][4])

This is important because merely knowing the variable group's name should not automatically let every YAML pipeline read its secrets.

### **Pipeline authorization**

For YAML pipelines, a variable group needs to be authorized for the pipeline.

Why?

Suppose anyone who can modify YAML could simply write:

```yaml
variables:
  - group: production-secrets
```

Without authorization controls, they could potentially attempt to extract sensitive data.

Azure DevOps therefore supports explicit pipeline permissions around variable groups containing sensitive values. ([Microsoft Learn][4])

---

### **Variable Group + Key Vault**

A powerful configuration is:

```text
Azure Key Vault
      ↓
Variable Group
      ↓
Multiple pipelines
```

Example:

```text
Key Vault
├── db-password
└── api-key

       ↓

Variable Group:
prod-secrets

       ↓

Pipeline A
Pipeline B
Pipeline C
```

For mapped Key Vault secrets, Azure DevOps retrieves the current values at runtime; changes to an already-mapped secret value become available to consuming pipelines. ([Microsoft Learn][5])

### **Important Key Vault detail**

If you add a completely **new secret name** to Key Vault:

```text
old:
db-password

new:
payment-api-key
```

the variable-group mapping doesn't automatically add that new secret name.

You need to update the variable group's mapping. ([Microsoft Learn][5])

---

### **Variable vs Variable Group**

```text
Variable
→ one named value

Variable Group
→ reusable collection of variables
```

For example:

```text
Variable
imageTag=v10
```

versus:

```text
Variable Group
prod-config
├── region
├── registry
├── namespace
└── secrets
```

### **Variable Group vs Service Connection**

Another important distinction:

```text
Variable Group
→ configuration / secrets

Service Connection
→ authentication to external service
```

Example:

```text
Variable Group
RESOURCE_GROUP=rg-prod

Service Connection
sc-prod
   ↓
authenticates to Azure
```

Both might be used by the same task:

```text
Pipeline
├── config from variable group
└── Azure auth from service connection
```

### **Good production design**

I would normally keep:

```text
Non-sensitive shared configuration
→ Variable Groups / templates

Sensitive application secrets
→ Key Vault

Azure pipeline authentication
→ Workload Identity Federation
```

rather than turning a single variable group into a giant credential store.

**Memory line:**
**Variable group = centrally reusable pipeline configuration shared across pipelines.**

**Interview trap:**
Don't confuse a variable group with a service connection.

```text
Variable Group
→ values

Service Connection
→ identity/authentication
```

**Keywords:** Variable Group, shared configuration, secrets, Library, Key Vault, pipeline authorization
