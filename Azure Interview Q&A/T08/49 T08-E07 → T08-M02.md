# 8. 🔴 M IMP — Azure DevOps & GitHub Actions CI/CD

## Easy

### **T08-E07. What is a pipeline agent?**

**Answer:**
A pipeline agent is the **machine that actually executes the jobs and commands defined in an Azure Pipeline**.

Azure DevOps coordinates the pipeline, but the agent performs the real work:

```text
Azure DevOps
     ↓
Pipeline Job
     ↓
Agent
     ├── checkout code
     ├── npm test
     ├── docker build
     ├── terraform plan
     └── az / kubectl / helm commands
```

Azure Pipelines supports Microsoft-hosted agents, self-hosted agents, Managed DevOps Pools, and VM Scale Set-based agent options. ([Microsoft Learn][1])

### **Example**

Pipeline YAML:

```yaml
pool:
  vmImage: ubuntu-latest

steps:
  - checkout: self
  - script: terraform init
  - script: terraform validate
```

The pipeline definition says:

```text
Run these commands
```

but the **agent** provides:

```text
Operating system
CPU
Memory
Filesystem
Network connectivity
Installed tools
```

and actually runs them.

### **Agent → Job relationship**

A useful mental model:

```text
Pipeline
   ↓
Stage
   ↓
Job
   ↓
Agent
   ↓
Steps
```

A job is assigned to an available agent.

The steps in that job execute on that agent.

### **Microsoft-hosted agent**

Example:

```yaml
pool:
  vmImage: ubuntu-latest
```

Azure DevOps provisions a Microsoft-managed VM for the job.

For Microsoft-hosted agents, Microsoft handles maintenance and updates, and a fresh VM is normally provided for each job and discarded afterward. ([Microsoft Learn][1])

So:

```text
Job starts
   ↓
Fresh VM
   ↓
Run pipeline
   ↓
Job finishes
   ↓
VM discarded
```

### **Self-hosted agent**

I can instead install the Azure Pipelines agent software on:

```text
Azure VM
on-prem VM
physical server
container
```

Then:

```text
Azure DevOps
     ↓
my self-hosted agent
     ↓
execute pipeline
```

This is useful when the job requires private network access or specialized software.

### **AKS example**

Suppose I have a **private AKS cluster**.

A Microsoft-hosted agent may not have a route to:

```text
AKS private API
10.x.x.x
```

So I could place:

```text
Self-hosted agent
inside Azure VNet
       ↓
Private AKS API
```

and deploy with:

```bash
helm upgrade ...
kubectl apply ...
```

### **Agent vs pipeline**

Don't confuse them:

```text
Pipeline
→ instructions

Agent
→ machine executing those instructions
```

**Memory line:**
**Azure Pipeline defines the work; the agent executes the work.**

**Interview trap:**
An agent isn't the Azure DevOps server itself. It's the execution environment assigned to a pipeline job.

**Keywords:** Agent, job, Microsoft-hosted, self-hosted, execution environment

### **T08-E08. What is a GitHub Actions runner?**

**Answer:**
A GitHub Actions **runner** is the machine that executes the jobs defined in a GitHub Actions workflow.

It is essentially GitHub Actions' equivalent of an Azure Pipelines agent.

```text
GitHub Repository
      ↓
Workflow
      ↓
Job
      ↓
Runner
      ↓
Steps execute
```

GitHub defines runners as the machines that execute workflow jobs. They can be either **GitHub-hosted** or **self-hosted**. ([GitHub Docs][2])

### **Example**

```yaml
jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test
```

This line:

```yaml
runs-on: ubuntu-latest
```

requests a GitHub-hosted runner.

The execution looks like:

```text
Workflow triggered
       ↓
GitHub provisions runner
       ↓
checkout repository
       ↓
npm ci
       ↓
npm test
       ↓
job completes
```

For normal GitHub-hosted runners, a new VM is provisioned for the job and decommissioned afterward. ([GitHub Docs][2])

### **Self-hosted runner**

I can also run:

```yaml
runs-on: self-hosted
```

and install the GitHub Actions runner on infrastructure I manage.

For example:

```text
GitHub
   ↓
Self-hosted runner
inside Azure VNet
   ↓
Private AKS
```

This is useful for:

* private AKS deployments,
* private databases,
* internal services,
* specialized build hardware,
* custom tools.

GitHub notes that self-hosted runners can run on physical machines, VMs, containers, on-premises infrastructure, or cloud infrastructure. ([GitHub Docs][3])

### **Runner vs Action**

Another useful distinction:

```text
Runner
→ machine executing the job

Action
→ reusable task executed by the runner
```

Example:

```yaml
- uses: actions/checkout@v4
```

`actions/checkout` is an **Action**.

The VM executing it is the **runner**.

### **Runner vs Azure Pipeline agent**

```text
GitHub Actions
→ Runner

Azure Pipelines
→ Agent
```

Conceptually they're very similar.

**Memory line:**
**GitHub workflow defines the job; runner is the machine that executes it.**

**Interview trap:**
Don't say:

> “A runner is a GitHub Action.”

They're different:

```text
Runner = execution environment
Action = reusable automation step
```

**Keywords:** runner, GitHub-hosted, self-hosted, job, workflow, `runs-on`

## Medium

### **T08-M01. What is the difference between Microsoft-hosted and self-hosted agents?**

**Answer:**
The main difference is **who owns and manages the execution infrastructure**.

With Microsoft-hosted agents, Microsoft provisions and maintains the machines. With self-hosted agents, **I provide and operate the machine myself**, giving me more control over networking, software, hardware, caching, and security configuration. ([Microsoft Learn][1])

### **Quick comparison**

| Area                    | Microsoft-hosted       | Self-hosted            |
| ----------------------- | ---------------------- | ---------------------- |
| Infrastructure          | Microsoft manages      | You manage             |
| VM lifecycle            | Fresh VM per job       | Usually persistent     |
| Maintenance             | Microsoft              | You                    |
| Custom software         | Limited/custom per job | Full control           |
| Private VNet access     | More difficult         | Easy if placed in VNet |
| Persistent cache        | Normally no            | Yes                    |
| Specialized hardware    | Limited options        | Full control           |
| Security responsibility | Lower infra burden     | Higher                 |
| Setup effort            | Low                    | Higher                 |

### **Microsoft-hosted agents**

Example:

```yaml
pool:
  vmImage: ubuntu-latest
```

The flow:

```text
Pipeline starts
      ↓
Microsoft provides fresh VM
      ↓
Job executes
      ↓
VM discarded
```

Microsoft handles:

```text
OS patching
agent updates
VM provisioning
base tooling
machine cleanup
```

Azure DevOps documents that Microsoft-hosted agents use fresh VMs for jobs, and filesystem changes made during one job aren't retained for the next job. ([Microsoft Learn][1])

### **Advantages**

They're great when I want:

```text
minimal maintenance
fast setup
clean build environment
standard tooling
internet-accessible deployments
```

For example:

```text
GitHub/Azure Repos
      ↓
Microsoft-hosted agent
      ↓
terraform validate
      ↓
docker build
      ↓
push ACR image
```

Very little infrastructure management is required.

---

### **Self-hosted agents**

I install the Azure Pipelines agent on a machine I own/control:

```text
Azure VM
on-prem server
container
VMSS
```

Then:

```text
Azure DevOps
     ↓
Self-hosted Agent
     ↓
my network/resources
```

Microsoft notes that machine-level configuration and caches can persist between pipeline runs on self-hosted agents, which can improve build performance. ([Microsoft Learn][1])

### **Biggest DevOps use case: private networking**

Suppose I have:

```text
Private AKS API
10.10.1.5
```

A public hosted agent has no inherent route to that private address.

Instead:

```text
Azure DevOps
     ↓
Self-hosted agent
     ↓
Spoke/Hub VNet
     ↓
AKS private API
```

Now:

```bash
kubectl get pods
helm upgrade ...
```

can work through private connectivity.

The same principle applies to:

```text
private ACR
private Key Vault
private SQL
internal APIs
on-premises systems
```

---

### **Custom software and hardware**

Suppose every pipeline requires:

```text
Terraform
Helm
kubectl
Trivy
Checkov
custom enterprise CLI
specific Java SDK
```

A self-hosted agent can have these preinstalled.

With hosted agents, I generally either rely on the preinstalled image or install additional dependencies during each run.

---

### **Caching**

Suppose a huge build downloads:

```text
10 GB dependencies
```

every run.

Hosted:

```text
Job 1
↓
download
↓
VM destroyed

Job 2
↓
download again
```

unless pipeline-level caching/artifacts are explicitly configured.

Self-hosted:

```text
Persistent machine
↓
local caches remain
```

which can improve performance.

---

### **But self-hosted isn't automatically better**

You become responsible for:

```text
OS patching
security updates
capacity
disk cleanup
runner/agent security
networking
monitoring
availability
scaling
```

So for ordinary CI:

```text
Microsoft-hosted
```

is often simpler.

For private/specialized deployments:

```text
self-hosted
```

may be necessary.

### **Security consideration**

A self-hosted agent executes repository-controlled code on infrastructure you manage.

That means untrusted pipeline code can be dangerous.

The same security principle is explicitly highlighted by GitHub for self-hosted runners, especially for public-repository pull requests. ([GitHub Docs][4])

I therefore protect self-hosted execution using:

```text
trusted repositories
restricted agent pools
least-privilege identity
ephemeral agents where possible
network segmentation
no unnecessary production credentials
```

### **Current Azure option: Managed DevOps Pools**

Azure DevOps now also offers **Managed DevOps Pools**, which sits between traditional hosted and DIY self-hosted approaches: Microsoft manages the service while providing more flexibility and scalable custom agent environments. Microsoft currently recommends considering Managed DevOps Pools when teams need autoscaling/customization beyond basic hosted agents. ([Microsoft Learn][1])

For an interview, though, the core comparison remains:

```text
Hosted
→ convenience

Self-hosted
→ control
```

**Memory line:**
**Hosted agent = Microsoft manages the machine; self-hosted = you control the machine and network.**

**Interview trap:**
Don't say self-hosted is always cheaper or faster.

It can improve caching/network access, but you inherit:

```text
maintenance
security
scaling
availability
```

responsibilities.

**Keywords:** Microsoft-hosted, self-hosted, private network, caching, custom tools, maintenance

**Likely follow-ups:**

* Which would you use for private AKS?
* Why are hosted agents more ephemeral?
* What security risk exists with self-hosted agents?
* What are Managed DevOps Pools?

### **T08-M02. What is an Azure DevOps service connection?**

**Answer:**
An Azure DevOps **service connection** is a securely configured connection that lets a pipeline authenticate to and access an **external service or resource**, such as an Azure subscription, Kubernetes cluster, container registry, GitHub repository, package registry, or other external system.

Conceptually:

```text
Azure Pipeline
      ↓
Service Connection
      ↓
Authentication / identity
      ↓
External Resource
```

Azure DevOps supports service connections for Azure Resource Manager, Kubernetes, Docker registries, SSH, GitHub, Jenkins, package registries, and many other systems. ([Microsoft Learn][5])

### **Azure example**

Suppose my pipeline needs to deploy infrastructure:

```text
Azure Pipeline
      ↓
Terraform / Azure CLI
      ↓
Azure subscription
```

The pipeline needs an identity.

Instead of embedding:

```text
AZURE_CLIENT_ID
AZURE_CLIENT_SECRET
TENANT_ID
```

directly inside YAML, I configure an:

```text
Azure Resource Manager
Service Connection
```

and reference it from the pipeline.

### **Example flow**

```text
Pipeline
   ↓
Azure Service Connection
   ↓
Microsoft Entra ID
   ↓
Azure RBAC
   ↓
Resource Group
   ↓
AKS / Storage / VNet / etc.
```

The Azure identity behind the connection might receive:

```text
Contributor
```

at a specific resource group rather than the entire subscription.

### **Modern preferred authentication: Workload Identity Federation**

This is one of the most important modern Azure DevOps points.

For Azure Resource Manager service connections, Microsoft recommends **Workload Identity Federation (WIF)** instead of storing a client secret. ([Microsoft Learn][6])

The model becomes:

```text
Azure Pipeline
      ↓
Federated token
      ↓
Microsoft Entra ID
      ↓
short-lived Azure token
      ↓
Azure Resource Manager
```

instead of:

```text
Azure Pipeline
      ↓
Stored client secret ❌
      ↓
Service Principal
```

Advantages:

```text
No long-lived secret
No secret rotation
Short-lived tokens
Better credential hygiene
```

### **Service connection + Azure RBAC**

The service connection tells the pipeline:

> Which identity should I use?

Azure RBAC tells Azure:

> What is that identity allowed to do?

For example:

```text
Service Connection:
sc-prod-network

Identity:
pipeline-prod-network

RBAC:
Network Contributor

Scope:
rg-prod-network
```

Then:

```text
Can manage VNets? ✅

Can modify unrelated production database?
❌
```

if the role scope is properly limited.

Microsoft explicitly recommends scoping service connections to only the resources needed instead of granting broad subscription-level Contributor access. ([Microsoft Learn][6])

### **Example YAML**

A task might reference:

```yaml
- task: AzureCLI@2
  inputs:
    azureSubscription: sc-production
    scriptType: bash
    scriptLocation: inlineScript
    inlineScript: |
      az account show
```

Here:

```text
azureSubscription: sc-production
```

refers to the Azure Resource Manager service connection.

The task uses that connection to obtain Azure credentials.

### **Service connection vs pipeline agent**

These solve completely different things.

```text
Agent
→ WHERE the pipeline runs

Service Connection
→ WHO/HOW the pipeline authenticates externally
```

Example:

```text
Self-hosted Agent
      ↓
executes Terraform

Service Connection
      ↓
authenticates Terraform to Azure
```

You often need both.

### **Service connection vs variable group**

Also don't confuse:

```text
Service Connection
→ external authentication/integration

Variable Group
→ shared pipeline configuration/secrets
```

A service connection can encapsulate authentication without exposing credentials as ordinary pipeline variables.

### **Example production architecture**

```text
Azure DevOps Pipeline
        ↓
Self-hosted Agent
        ↓
WIF Service Connection
        ↓
Microsoft Entra ID
        ↓
Azure RBAC
        ↓
Production Resource Group
        ↓
AKS
```

This gives:

```text
Private network connectivity
+
secretless Azure authentication
+
least-privilege authorization
```

### **Current WIF note**

Azure DevOps is continuing to standardize service-connection federation around the Microsoft Entra issuer. New public-cloud WIF service connections use the Entra issuer by default, while older Azure DevOps-issued WIF configurations are being migrated ahead of their announced **July 1, 2027** retirement. ([Microsoft Learn][5])

For an interview, the important takeaway is simply:

> **Prefer workload identity federation instead of client-secret-based Azure service connections.**

**Memory line:**
**Service connection = pipeline's trusted authentication bridge to an external service.**

**Interview trap:**
Don't say:

> “A service connection automatically gives full Azure access.”

Its effective permissions are determined by the identity and **RBAC scope** behind it.

**Keywords:** service connection, Azure Resource Manager, Workload Identity Federation, Entra ID, Azure RBAC, least privilege

**Likely follow-ups:**

* Service connection vs agent?
* Why prefer WIF over a client secret?
* How would you scope a production service connection?
* Can one service connection access only one resource group?
