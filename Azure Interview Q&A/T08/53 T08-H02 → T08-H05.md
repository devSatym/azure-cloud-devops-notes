# 8. 🔴 M IMP — Azure DevOps & GitHub Actions CI/CD

## Hard

### **T08-H02. How would you deploy from GitHub Actions to Azure without storing an Azure client secret?**

**Answer:**
I would use **GitHub Actions OIDC federation with Microsoft Entra ID**. GitHub issues a short-lived OIDC token for the workflow, Entra validates that token against a configured federated identity credential, and Azure issues a short-lived access token. No `AZURE_CLIENT_SECRET` needs to be stored in GitHub.

```text
GitHub Actions
      ↓
GitHub OIDC token
      ↓
Microsoft Entra ID
      ↓
Federated Identity Credential
      ↓
Short-lived Azure token
      ↓
ACR / AKS / Azure resources
```

Microsoft currently recommends this OIDC flow for GitHub Actions authentication to Azure; the identity can be either an Entra application/service principal or a user-assigned managed identity. ([Microsoft Learn][1])

### **1. Create the Azure identity**

I first create either:

```text
Microsoft Entra application + service principal
```

or:

```text
User-assigned managed identity
```

For example:

```text
Identity:
gha-payment-prod
```

Then I grant only the required Azure permissions.

For an image-build workflow:

```text
gha-payment-build
      ↓
AcrPush
      ↓
payment ACR
```

For infrastructure:

```text
gha-terraform
      ↓
Contributor
      ↓
specific resource group
```

Not:

```text
Owner
↓
entire subscription ❌
```

OIDC handles authentication, while **Azure RBAC still controls authorization**. ([Microsoft Learn][1])

---

### **2. Configure the federated identity credential**

The Azure identity needs a trust relationship with GitHub.

Conceptually:

```text
Microsoft Entra ID trusts:

Issuer:
https://token.actions.githubusercontent.com

Subject:
specific GitHub repo/branch/environment

Audience:
api://AzureADTokenExchange
```

For example, production trust might correspond to:

```text
Repository:
company/payment-api

Environment:
production
```

instead of trusting every branch in every repository.

That creates:

```text
Trusted workflow identity
          ↓
Can exchange token

Other repository/branch
          ↓
Federation doesn't match
          ↓
No Azure token
```

Microsoft requires a federated identity credential before `azure/login` can use GitHub OIDC. ([Microsoft Learn][1])

---

### **3. Enable OIDC token issuance in the workflow**

The workflow needs:

```yaml
permissions:
  id-token: write
  contents: read
```

The important permission is:

```text
id-token: write
```

It allows the workflow to request a GitHub OIDC token.

It does **not** mean:

```text
write permission to Azure
```

Azure access still depends on the federated trust and Azure RBAC.

---

### **4. Authenticate using `azure/login`**

A typical workflow:

```yaml
name: Deploy

on:
  push:
    branches:
      - main

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - run: az account show
```

Here:

```text
Client ID
Tenant ID
Subscription ID
```

are identifiers.

There is no:

```text
AZURE_CLIENT_SECRET ❌
```

The Azure Login action uses OIDC to authenticate. ([Microsoft Learn][1])

### **Important interview nuance**

An interviewer may ask:

> “But you're still using GitHub Secrets in that example.”

Yes—but:

```text
AZURE_CLIENT_ID
AZURE_TENANT_ID
AZURE_SUBSCRIPTION_ID
```

aren't equivalent to a reusable password.

The sensitive piece we've eliminated is:

```text
AZURE_CLIENT_SECRET
```

Those IDs could alternatively be stored as variables/configuration depending on policy.

---

### **5. Deploy to Azure**

After login, the job can execute:

```bash
az acr login --name myacr
```

or:

```bash
az aks get-credentials \
  -g rg-prod \
  -n aks-prod
```

and then:

```bash
helm upgrade --install ...
```

assuming the identity has the required permissions and network connectivity.

For example:

```text
GitHub Runner
      ↓
OIDC
      ↓
Entra
      ↓
Azure identity
      ├── AcrPush
      └── required AKS access
```

---

### **6. Private AKS needs networking too**

OIDC solves identity.

It does **not** solve connectivity.

If AKS has:

```text
Private API
10.x.x.x
```

then:

```text
GitHub-hosted runner
        ↓
No VNet route
        ↓
Private AKS ❌
```

may still fail.

I'd use:

```text
GitHub
   ↓
Self-hosted runner
inside Azure VNet
   ↓
Private AKS API
```

while still using OIDC for Azure authentication.

So always separate:

```text
OIDC
→ authentication

VNet/private routing
→ connectivity
```

---

### **7. Protect the production identity**

For production, I would ideally use:

```text
GitHub Environment:
production
```

and restrict which branches/tags can deploy to it.

GitHub environments can enforce deployment branch restrictions, required reviewers, and other protection rules before the deployment job proceeds. ([GitHub Docs][2])

Architecture:

```text
main
 ↓
CI passes
 ↓
GitHub Environment: production
 ↓
Required approval
 ↓
OIDC-enabled deployment job
 ↓
Azure Production
```

This is stronger than giving every workflow execution equal production trust.

---

### **8. Why this is better than a client secret**

Old:

```text
GitHub
 ↓
Stored Azure client secret
 ↓
valid for months
 ↓
Azure
```

If stolen:

```text
attacker can reuse it
until expiry/revocation
```

OIDC:

```text
Workflow
 ↓
short-lived token
 ↓
Entra
 ↓
short-lived Azure access
 ↓
expires
```

Microsoft explicitly lists service-principal-secret authentication as **not recommended** compared with OIDC for Azure Login. ([Microsoft Learn][3])

**Interview answer condensed:**

> “I'd configure GitHub OIDC federation with an Entra application or user-assigned managed identity. The workflow gets `id-token: write`, `azure/login` exchanges GitHub's OIDC token with Entra, and Azure returns a short-lived access token. I'd assign that identity least-privilege Azure RBAC and restrict production federation to a protected branch or GitHub Environment. This removes the need to store an Azure client secret.”

**Memory line:**
**GitHub OIDC → Entra federation → short-lived Azure token → no client secret.**

**Interview trap:**
OIDC solves **authentication**, not:

```text
Azure permissions
network access
AKS authorization
```

Those still need RBAC and connectivity.

**Keywords:** OIDC, `azure/login`, federated identity credential, Entra ID, `id-token: write`, RBAC

**Likely follow-ups:**

* What does `id-token: write` mean?
* How would this work with private AKS?
* How do you restrict OIDC to production?
* Client ID vs client secret?

### **T08-H03. How would you design reusable pipelines for 30 microservices?**

**Answer:**
I would avoid maintaining 30 copied CI/CD pipelines. Instead, I would create **central, versioned pipeline templates** containing the standard build, test, security, container-publish, and deployment logic, while each microservice provides only service-specific parameters.

Conceptually:

```text
                       Central Templates
                 ┌────────────┼────────────┐
                 │            │            │
              Build         Security      Deploy
              Template      Template      Template
                 │            │            │
                 └────────────┼────────────┘
                              ↓
       ┌──────────┬───────────┼───────────┬──────────┐
       ↓          ↓           ↓           ↓          ↓
    Service A  Service B   Service C   ...       Service 30
```

Azure Pipelines templates can reuse stages, jobs, steps, variables, and parameters. `extends` templates can additionally define and enforce the allowed pipeline structure. ([Microsoft Learn][4])

### **1. Put common logic in a central repository**

For example:

```text
platform-pipelines/
│
├── templates/
│   ├── service-pipeline.yml
│   ├── build-image.yml
│   ├── unit-test.yml
│   ├── security-scan.yml
│   ├── publish-acr.yml
│   └── deploy-aks.yml
│
└── versions/
```

Each microservice does **not** recreate:

```text
docker build
Trivy
SAST
ACR push
deployment gates
```

independently.

Azure DevOps supports storing templates in another repository and referencing them from consuming pipelines. ([Microsoft Learn][4])

---

### **2. Make service pipelines tiny**

For example, `payment-api`:

```yaml
extends:
  template: templates/service-pipeline.yml@pipelines

  parameters:
    serviceName: payment-api
    dockerfile: services/payment/Dockerfile
    imageRepository: payment-api
    helmChart: helm/payment-api
```

`orders-api`:

```yaml
extends:
  template: templates/service-pipeline.yml@pipelines

  parameters:
    serviceName: orders-api
    dockerfile: services/orders/Dockerfile
    imageRepository: orders-api
    helmChart: helm/orders-api
```

The only difference is configuration.

The implementation remains centralized.

---

### **3. Template the standard pipeline**

Conceptually:

```text
service-pipeline.yml

CI
├── Checkout
├── Unit tests
├── Lint
├── SAST
├── Dependency scan
├── Build image
└── Image scan

Publish
├── OIDC/WIF login
├── Push ACR
└── Record digest

Deploy
├── Dev
├── Staging
└── Production
```

All 30 services inherit the same baseline.

### **Why parameters rather than lots of custom YAML?**

Because common differences are usually:

```text
serviceName
Dockerfile path
build context
test command
image repository
Helm chart
namespace
```

Those are inputs—not reasons to fork an entire pipeline.

---

### **4. Use `extends` for governance**

For enterprise consistency, I prefer a secure base:

```yaml
extends:
  template: secure-service-pipeline.yml@platform
```

rather than allowing every team to freely recreate the whole pipeline.

Microsoft describes `extends` templates as a way to enforce pipeline structure, compliance, and allowed behavior, not merely reuse YAML. ([Microsoft Learn][4])

For example, the central template can require:

```text
Unit test stage
SAST
container scan
immutable image tag
production approval
approved deployment task
```

and prevent teams from quietly removing these controls.

---

### **5. Version the templates**

This is extremely important for 30 services.

Bad:

```text
30 services
   ↓
always consume current template main
   ↓
central change
   ↓
30 pipelines break simultaneously
```

Better:

```text
pipeline-template repo

v1.4
v1.5
v2.0
```

Service A:

```text
template ref → v1.5
```

Service B:

```text
template ref → v1.4
```

Then teams can upgrade intentionally.

Microsoft's pipeline security guidance recommends pinning external templates to an appropriate branch/tag so central changes don't unexpectedly affect every pipeline. ([Microsoft Learn][5])

---

### **6. Separate CI logic from environment configuration**

I don't want:

```text
production URL
namespace
replica count
region
```

hard-coded into the reusable build template.

Instead:

```text
Central template
→ HOW to deploy

Environment configuration
→ WHAT values to deploy with
```

For example:

```text
config/
├── dev.yml
├── staging.yml
└── prod.yml
```

or appropriate variable groups/Helm values/GitOps configuration.

---

### **7. Build once**

Every service should produce one immutable image:

```text
payment-api:7bc23ab
```

or, ideally for promotion:

```text
payment-api@sha256:...
```

Then:

```text
Dev
 ↓
same image
Staging
 ↓
same image
Production
```

Templates should enforce that pattern.

Don't let each service pipeline rebuild per environment.

---

### **8. Use path filters in a monorepo**

If all 30 services are in one repository:

```text
repo/
├── payment/
├── orders/
├── inventory/
└── shipping/
```

I don't want a payment change building 30 images.

Use:

```text
payment/** changed
     ↓
payment pipeline
```

or dynamic changed-service detection.

For a very large monorepo:

```text
git diff
 ↓
determine affected services
 ↓
matrix / generated jobs
```

can efficiently build only impacted services.

---

### **9. Standardize identity**

Don't create:

```text
30 random service-principal secrets
```

Use:

```text
OIDC / Workload Identity Federation
```

and central patterns.

Depending on blast-radius requirements:

```text
Shared non-prod build identity
+
separate production identities
```

or:

```text
identity per service
```

for higher isolation.

Example:

```text
payment CI identity
→ AcrPush payment repository

payment prod deployment identity
→ payment production resources only
```

---

### **10. Shared security baseline**

Every service automatically receives:

```text
Unit testing
SAST
Dependency scan
Secret scan
Container vulnerability scan
SBOM if required
Image signing if required
```

Centralizing it prevents:

```text
Service A → strong pipeline
Service B → no scan
Service C → random implementation
```

### **11. Allow controlled extension**

Teams may need exceptions.

For example:

```text
Java service
→ Maven

Node service
→ npm

Go service
→ go test
```

So the template might accept typed parameters:

```text
language
testCommand
buildContext
dockerfile
```

but still retain mandatory security/deployment stages.

Think:

```text
Flexible inputs
+
fixed safety rails
```

not:

```text
copy pipeline and modify anything
```

### **Architecture**

```text
                    Platform Pipeline Repo
                           │
              ┌────────────┼────────────┐
              ↓            ↓            ↓
          CI Template   Security     AKS Deploy
              │         Template      Template
              └────────────┬────────────┘
                           ↓
                    Secure Base Template
                           │
       ┌───────────────────┼────────────────────┐
       ↓                   ↓                    ↓
 payment-api.yml       orders-api.yml      inventory.yml
       │                   │                    │
 parameters only       parameters only      parameters only
       ↓                   ↓                    ↓
      ACR                 ACR                  ACR
       ↓                   ↓                    ↓
                    Dev → Stage → Prod
```

### **Interview answer condensed:**

> “For 30 microservices, I'd create a central versioned template repository. A secure `extends` template would define mandatory CI, security, image publishing, and deployment stages, while each service pipeline would only provide parameters such as Dockerfile, service name, image repository, and Helm chart. I'd pin template versions, use path filtering for monorepos, build one immutable image per commit, and promote that image through environments. This reduces duplication while enforcing the same security and deployment standards across all services.”

**Memory line:**
**30 services ≠ 30 custom pipelines. Build one pipeline platform and parameterize the services.**

**Interview trap:**
Don't create one huge template with hundreds of service-specific `if` statements.

If the template becomes:

```text
if service=A ...
if service=B ...
if service=C ...
```

you've simply moved duplication into one giant file.

**Keywords:** templates, `extends`, parameters, central repo, versioning, microservices, path filters

**Likely follow-ups:**

* `extends` vs include templates?
* How do you roll out a template change safely?
* How would this work in a monorepo?
* One identity per microservice or shared?

### **T08-H04. How would you prevent an unreviewed pull request from reaching production?**

**Answer:**
I would enforce protection at **multiple independent layers**: protected `main`, required pull-request reviews and status checks, production environment protection, branch restrictions, and least-privilege production authentication. I don't rely on one YAML `if` statement to protect production.

Architecture:

```text
Feature Branch
      ↓
Pull Request
      ↓
Required CI checks
      ↓
Required reviewer(s)
      ↓
Protected main
      ↓
Production Environment
      ↓
Approval / branch restriction
      ↓
Production identity
      ↓
Azure
```

GitHub environments can require reviewers, restrict deployment branches/tags, and block a deployment job until those protection rules pass. ([GitHub Docs][2])

---

### **1. Protect `main`**

Developers should not be able to:

```text
git push origin main
```

directly.

Expected:

```text
feature/*
   ↓
Pull Request
   ↓
main
```

Branch protection/rulesets should require:

```text
Pull Request
Required reviews
Required CI checks
No direct force pushes
```

as appropriate.

---

### **2. Make CI checks required**

Before merge:

```text
Build             ✅
Unit tests        ✅
SAST              ✅
Dependency scan   ✅
Container scan    ✅
```

If:

```text
Tests ❌
```

then:

```text
Merge blocked
```

The key is **required** status checks.

A pipeline that runs but can be ignored provides weak protection.

---

### **3. Require independent review**

For production code:

```text
Developer creates PR
       ↓
Reviewer examines changes
       ↓
Approval
       ↓
Merge
```

For sensitive files, stronger controls may include:

```text
CODEOWNERS
```

for:

```text
.github/workflows/**
terraform/**
helm/**
security-policy/**
```

so pipeline/IaC changes require the correct owners.

---

### **4. Production should only accept a trusted branch**

The production job shouldn't say:

```yaml
on:
  push:
```

for every branch.

Instead:

```text
Production
   ↓
only trusted main/release branch
```

GitHub Environments support deployment-branch/tag rules that restrict which refs can deploy to an environment. ([GitHub Docs][2])

For Azure DevOps, a comparable protection is the Environment **Branch Control** check, which can enforce allowed fully qualified branches and require that they themselves are protected. ([Microsoft Learn][6])

---

### **5. Add a protected production environment**

Even after merge:

```text
main
 ↓
Staging deployment
 ↓
tests
 ↓
Production Environment
 ↓
required reviewer
```

GitHub states that jobs referencing an environment must satisfy its deployment protection rules before the job proceeds, and environment secrets aren't made available until those protections pass. ([GitHub Docs][2])

For example:

```yaml
jobs:
  deploy-production:
    environment: production
```

The protection exists outside the application logic itself.

---

### **6. Prevent self-approval where required**

GitHub environments support:

```text
Prevent self-review
```

so the person triggering a production deployment can't approve their own deployment when that control is enabled. ([GitHub Docs][2])

That creates:

```text
Developer
   ↓
triggers production deployment

Different authorized reviewer
   ↓
approves
```

---

### **7. Tie production OIDC to the production environment**

This is a strong design.

Don't give all branches the same Azure trust:

```text
repo:any-branch
      ↓
production Azure identity ❌
```

Instead:

```text
GitHub Environment:
production
      ↓
OIDC federated identity
      ↓
Production Azure identity
```

Then a random feature workflow cannot simply call:

```yaml
azure/login
```

and get production credentials unless its OIDC claims match the configured federation.

So even if somebody modifies workflow YAML:

```text
untrusted ref
    ↓
OIDC claims don't match
    ↓
Entra rejects token exchange
```

This is much stronger than pipeline logic alone.

---

### **8. Separate CI and production identities**

For example:

```text
PR identity
→ read/test access
→ NO production access

main build identity
→ AcrPush

production identity
→ production deployment permission
```

Then a compromised PR build doesn't automatically possess production credentials.

This is particularly important because PR workflows can execute code submitted by developers or external contributors.

---

### **9. Don't expose production secrets to PR jobs**

Avoid architecture where:

```text
PR workflow
     ↓
production secrets available
```

GitHub environment secrets are only available to jobs referencing that environment and, when approval is configured, aren't available until protection rules pass. ([GitHub Docs][2])

Better:

```text
PR
→ test credentials only

Production job
→ production identity only after gate
```

---

### **10. Use immutable artifacts**

There's another subtle protection:

```text
PR reviewed commit
      ↓
Build immutable image
      ↓
approved image digest
      ↓
Production
```

rather than letting a production stage rebuild arbitrary source.

That ensures:

> the artifact being deployed corresponds to a known, validated commit.

### **Defense-in-depth model**

```text
Developer
   ↓
Feature Branch
   ↓
PR
   ↓
┌────────────────────┐
│ Required CI checks │
└────────────────────┘
   ↓
┌────────────────────┐
│ Required reviewer  │
└────────────────────┘
   ↓
Protected main
   ↓
Immutable artifact
   ↓
Staging validation
   ↓
Production Environment
   ↓
Branch restriction
   ↓
Required deployment approval
   ↓
Environment-scoped OIDC
   ↓
Production Azure RBAC
```

An attacker would have to bypass several independent controls rather than one pipeline condition.

### **Interview answer condensed:**

> “I'd protect `main` so it only receives reviewed PRs with mandatory CI checks, then restrict production to that protected branch. Production would use a protected environment with required reviewers and preferably no self-approval. I'd also keep production credentials out of PR jobs and scope the production OIDC federation to the production environment or trusted ref. Finally, I'd deploy only the immutable artifact produced from the reviewed commit. That way changing pipeline YAML alone isn't enough to bypass production governance.”

**Memory line:**
**PR review protects the merge; environment protection and identity restrictions protect the deployment.**

**Interview trap:**
Don't rely only on:

```yaml
if: github.ref == 'refs/heads/main'
```

A condition is useful, but production security should also exist in:

```text
branch protection
environment protection
identity trust
RBAC
```

**Keywords:** protected branch, required review, required checks, environment, OIDC, branch restriction, defense in depth

**Likely follow-ups:**

* What if someone modifies the workflow YAML?
* Why use a protected Environment?
* How do you prevent PRs from reading prod secrets?
* How does OIDC strengthen deployment protection?

### **T08-H05. How would you implement build-once-deploy-many across dev, staging, and production?**

**Answer:**
I would build the application artifact **exactly once**, assign it an immutable version or container digest, and then promote that exact artifact through Dev → Staging → Production. Environment-specific configuration is injected separately; the application binary/image is never rebuilt between environments.

```text
Source commit
    ↓
Build ONCE
    ↓
Immutable artifact/image
    ↓
┌──────────┬───────────┬────────────┐
↓          ↓           ↓
Dev      Staging     Production
```

The principle is:

> **Promote the artifact, don't recreate it.**

---

### **1. Build after trusted source validation**

For example:

```text
Git commit:
7bc23ab
```

Build:

```bash
docker build \
  -t myacr.azurecr.io/payment-api:7bc23ab .
```

Push:

```text
ACR
└── payment-api:7bc23ab
```

Even better, record the registry digest:

```text
payment-api@sha256:ab32f9...
```

because tags can potentially be moved, while the digest identifies exact immutable image content.

---

### **2. Record artifact metadata**

Pipeline should capture:

```text
Git SHA
Image digest
Build ID
SBOM
Security scan result
```

Conceptually:

```text
Commit
7bc23ab
   ↓
Image
sha256:ab32...
   ↓
SBOM
   ↓
scan/signature
```

This gives traceability:

```text
Production image
      ↓
exact build
      ↓
exact Git commit
```

---

### **3. Deploy exact same image to Dev**

```text
ACR
payment-api@sha256:ab32
           ↓
Dev AKS
```

Run:

```text
Smoke tests
API tests
basic integration
```

If it fails:

```text
promotion stops
```

---

### **4. Promote to Staging—do not rebuild**

Bad:

```text
git checkout
↓
docker build staging
```

Good:

```text
Existing digest
sha256:ab32
      ↓
Staging AKS
```

Now staging validates the same application bits that were tested in Dev.

---

### **5. Production gets the same digest**

After staging passes:

```text
sha256:ab32
   ↓
Production approval
   ↓
Production AKS
```

So:

```text
Dev       = sha256:ab32
Staging   = sha256:ab32
Production= sha256:ab32
```

This gives confidence that:

> **what passed staging is exactly what went to production.**

---

### **6. Keep environment configuration outside the image**

A common mistake is rebuilding because environment settings differ.

Don't bake:

```text
DEV_DB_URL
STAGING_API_URL
PROD_DB_PASSWORD
```

into three different images.

Instead:

```text
Same image
   +
environment-specific runtime config
```

For Kubernetes:

```text
Helm values
ConfigMaps
Key Vault
Workload Identity
environment variables
```

For example:

```text
payment-api@sha256:abc
        │
        ├── Dev values
        │     replicas: 1
        │
        ├── Staging values
        │     replicas: 2
        │
        └── Prod values
              replicas: 5
```

The **configuration** changes.

The application image doesn't.

---

### **7. Secrets are environment-specific too**

For example:

```text
Same payment image
       ↓
Dev
→ dev Key Vault

Staging
→ staging Key Vault

Production
→ production Key Vault
```

using:

```text
Workload Identity
```

So production secrets never need to be baked into the container.

---

### **8. Promotion can be pipeline-based**

A pipeline might be:

```text
Build Stage
   ↓
Build image
   ↓
Push ACR
   ↓
capture digest
   ↓
Deploy Dev
   ↓
Test
   ↓
Deploy Staging
   ↓
Test
   ↓
Approval
   ↓
Deploy Production
```

The image digest becomes an output passed through the deployment stages.

---

### **9. GitOps promotion model**

With Argo CD/Flux:

```text
CI
 ↓
Build image once
 ↓
Push ACR
 ↓
sha256:abc
```

Then environment desired state contains:

```text
environments/dev/
  imageDigest: sha256:abc

environments/staging/
  imageDigest: sha256:abc

environments/prod/
  imageDigest: sha256:abc
```

Promotion means changing:

```text
desired-state reference
```

not rebuilding.

For example:

```text
Dev validated
   ↓
PR:
staging digest old → sha256:abc
   ↓
Staging validated
   ↓
PR:
prod digest old → sha256:abc
```

This gives a strong audit trail.

---

### **10. Why rebuilding per environment is dangerous**

Suppose:

```text
Dev build
→ dependency version X

Production rebuild two hours later
→ dependency repository changed
→ dependency version Y
```

Even with the same Git commit, the resulting image could differ.

Then:

```text
“What passed staging?”
```

is no longer necessarily:

```text
“What production is running.”
```

Build-once eliminates that ambiguity.

---

### **11. Signing and provenance**

For higher-security pipelines:

```text
Build once
   ↓
Generate SBOM
   ↓
Generate provenance
   ↓
Sign digest
   ↓
ACR
```

Then deployment policy can verify:

```text
Is this image signed?
Was it produced by trusted CI?
Does digest match approved artifact?
```

The security metadata follows the artifact through all environments.

---

### **12. Rollback becomes cleaner**

Suppose:

```text
Current:
sha256:new

Previous known-good:
sha256:old
```

Rollback:

```text
Production desired digest
sha256:new
     ↓
sha256:old
```

No new build required.

That gives:

```text
fast
predictable
auditable
```

rollback.

                 Git Commit

### **Interview answer condensed:**

> “I'd build the application once from the trusted commit, push it to ACR, and capture the immutable image digest. That same digest is deployed to Dev, then promoted to Staging, and finally Production after validation and approval. Environment differences such as URLs, replica counts, and secrets are injected at runtime through Helm values, ConfigMaps, Key Vault, and Workload Identity—they never require rebuilding the image. This guarantees that the artifact tested in staging is exactly the artifact running in production and also makes rollback to a previous known-good digest simple.”

**Memory line:**
**Build once, configure per environment, promote the same immutable digest.**

**Interview trap:**
This is **not** build-once-deploy-many:

```text
docker build dev
docker build staging
docker build prod
```

even when all three builds use the same Git commit.
