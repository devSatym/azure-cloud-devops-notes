# 8. 🔴 M IMP — Azure DevOps & GitHub Actions CI/CD

## Hard

### **T08-H06. How would you roll back a failed deployment automatically?**

**Answer:**
I would make rollback depend on **post-deployment health validation**, not merely whether the deployment command returned success. I deploy an immutable version, monitor rollout and application health, and if defined health checks fail, automatically restore the **previous known-good image/digest or GitOps revision**.

A good flow is:

```text
Deploy new version
      ↓
Wait for rollout
      ↓
Run health/smoke checks
      ↓
Observe error rate / latency
      ↓
Healthy?
 ┌────┴────┐
Yes       No
 ↓         ↓
Keep      Roll back
release   previous version
```

---

### **1. Keep deployments immutable**

Suppose production currently runs:

```text
payment-api@sha256:OLD
```

and the new release is:

```text
payment-api@sha256:NEW
```

I don't overwrite some ambiguous:

```text
latest
```

tag and hope I can reconstruct the previous version later.

I maintain:

```text
current digest
previous known-good digest
deployment revision
```

so rollback is deterministic.

---

### **2. Don't consider `helm upgrade` success enough**

A deployment command may succeed while the application is unhealthy.

For example:

```text
helm upgrade ✅
        ↓
Pods created
        ↓
application returns HTTP 500 ❌
```

So after deploying, I check:

```bash
kubectl rollout status deployment/payment-api
```

and then application-level health:

```text
/readiness
/health
critical API transaction
```

plus monitoring signals such as:

```text
5xx rate
latency
CrashLoopBackOff
readiness failures
Pod restarts
```

---

### **3. Kubernetes native rollback**

For a standard Kubernetes Deployment:

```bash
kubectl rollout undo deployment/payment-api
```

can restore the previous Deployment revision.

Conceptually:

```text
Revision 41
image=v1.7

Revision 42
image=v1.8 ← broken

       ↓ rollback

Revision 41
image=v1.7
```

But for mature CI/CD, I prefer explicitly knowing the previous artifact version rather than blindly assuming “previous revision” is always the correct production state.

---

### **4. Helm rollback**

With Helm:

```bash
helm history payment-api
```

might show:

```text
REVISION  STATUS
21        superseded
22        deployed
```

If revision 22 is bad:

```bash
helm rollback payment-api 21
```

A pipeline could invoke this after validation fails.

Example:

```text
helm upgrade
     ↓
kubectl rollout status
     ↓
smoke test
     ↓
failure
     ↓
helm rollback
```

---

### **5. GitOps rollback**

If I'm using Argo CD or Flux, I generally want **Git to remain the source of truth**.

Suppose:

```text
production values

imageDigest:
sha256:NEW
```

causes problems.

Then rollback should ideally be:

```text
Git revert
    ↓
imageDigest:
sha256:OLD
    ↓
Argo CD / Flux reconciles
    ↓
AKS returns to OLD
```

rather than manually changing production and leaving Git saying something else.

So:

```text
GitOps environment
→ rollback desired state

Direct pipeline environment
→ rollback Deployment/Helm release
```

---

### **6. Automated health gate**

A simple pipeline pattern could be:

```text
Deploy v2
   ↓
Wait 5–10 minutes
   ↓
Check:
- rollout complete
- health endpoint
- 5xx rate
- latency
   ↓
Threshold breached?
      ↓ yes
Rollback v1
```

For example:

```text
5xx < 1%
p95 latency < 500 ms
all required replicas Ready
```

If those conditions fail:

```text
rollback
+
mark pipeline failed
+
alert operations
```

### **7. Canary makes rollback safer**

For higher-risk releases:

```text
95% traffic → v1
5% traffic  → v2
```

Then monitor:

```text
v2 error rate
v2 latency
v2 saturation
```

If unhealthy:

```text
v2 traffic → 0%
```

This is safer than discovering the problem only after 100% of users are on the new version.

---

### **8. Database migrations need special care**

This is one of the most important real-world caveats.

Suppose:

```text
v2 deploy
↓
irreversible DB schema change
↓
application rollback to v1
```

but v1 no longer understands the schema.

Then application rollback fails.

So for production I prefer **backward-compatible database migrations**, such as expand-and-contract:

```text
1. Add new schema
2. Deploy compatible app
3. Migrate data
4. Remove old schema later
```

That lets both:

```text
old application
and
new application
```

temporarily work during the transition.

### **9. Automatic rollback shouldn't loop forever**

I don't want:

```text
Deploy v2
↓
rollback v1
↓
pipeline retries v2
↓
rollback
↓
retry...
```

After rollback:

```text
stop promotion
mark release failed
alert team
require investigation
```

### **Interview answer condensed**

> “I'd deploy an immutable image version, wait for Kubernetes rollout completion, then run smoke tests and monitor metrics such as readiness, error rate and latency. If those checks fail, I'd automatically restore the previous known-good digest using `kubectl rollout undo`, Helm rollback, or—under GitOps—a Git revert so desired state remains authoritative. I'd also design database migrations to be backward compatible, because application rollback is useless if the new schema broke the old version.”

**Memory line:**
**Deploy → validate → unhealthy → restore previous known-good artifact.**

**Interview trap:**
Don't define automatic rollback as:

> “If `kubectl apply` fails, run undo.”

Many bad deployments successfully apply but fail **after starting to serve traffic**.

**Keywords:** rollback, health gate, immutable digest, Helm rollback, GitOps revert, canary, backward-compatible migration

**Likely follow-ups:**

* Helm rollback vs GitOps rollback?
* How would you detect a bad release?
* Why can database migrations make rollback difficult?
* Canary vs rolling deployment?

### **T08-H07. How would you troubleshoot a pipeline that works with a personal account but fails using a service connection?**

**Answer:**
If the same operation works with my personal account but fails through a service connection, I immediately suspect an **identity or authorization difference**, not the application command itself.

I would compare:

```text
Personal identity
      vs
Service connection identity
```

across:

```text
Authentication
Azure RBAC
resource scope
tenant/subscription
service-specific permissions
network context
```

Microsoft's current troubleshooting guidance specifically calls out service-principal permissions and authentication state as key causes when service connections fail. ([Microsoft Learn][1])

### **1. Identify which identity the service connection uses**

First I determine:

```text
Service connection
      ↓
which Entra application /
managed identity?
```

For Azure Resource Manager connections, I inspect its:

```text
client/application ID
tenant
subscription
authentication mode
```

I don't troubleshoot using my own account permissions as evidence that the service identity is correct.

---

### **2. Reproduce the failing action**

Suppose the pipeline fails on:

```bash
az acr repository list ...
```

or:

```bash
az aks get-credentials ...
```

or:

```bash
terraform apply
```

I isolate the exact operation and error:

```text
401
→ authentication likely

403
→ authenticated but unauthorized

resource not found
→ wrong scope/subscription/resource

timeout
→ network/connectivity possibility
```

That classification immediately narrows the problem.

---

### **3. Compare Azure RBAC assignments**

This is usually the first major difference.

My personal account may be:

```text
Owner
or
Contributor
at subscription
```

while the service connection identity has:

```text
Reader
at one resource group
```

Then:

```text
Manual command works ✅
Pipeline fails ❌
```

is expected.

I inspect the service identity's role assignments at:

```text
subscription
resource group
specific resource
```

and verify required **data-plane roles**, not only control-plane roles.

---

### **4. Control plane vs data plane**

This is a common Azure interview point.

Example:

```text
Contributor on ACR resource
```

doesn't necessarily mean:

```text
push container image
```

because registry data-plane access may require an appropriate registry role such as:

```text
AcrPush
```

depending on the registry permission model.

Similarly:

```text
Contributor on Storage Account
```

isn't the same as:

```text
Storage Blob Data Contributor
```

for blob data.

So I ask:

> Does the failing command use Azure Resource Manager control-plane permissions, or service-specific data-plane permissions?

---

### **5. Verify service-connection scope**

The service connection may be scoped to:

```text
Subscription A
```

while the target resource exists in:

```text
Subscription B
```

or:

```text
RG-dev
```

while the pipeline tries to modify:

```text
RG-prod
```

So I verify:

```bash
az account show
```

inside the authenticated pipeline task where appropriate.

I compare:

```text
tenant ID
subscription ID
resource ID
```

with the intended deployment target.

---

### **6. Verify authentication itself**

For secret-based legacy connections, possibilities include:

```text
client secret expired
certificate expired
application disabled
credential rotated
```

For Workload Identity Federation:

```text
issuer mismatch
subject mismatch
audience mismatch
service connection configuration issue
```

Microsoft currently recommends WIF where feasible rather than service-principal secrets. ([Microsoft Learn][2])

---

### **7. Check service-specific permissions**

For AKS there may be several distinct requirements:

```text
Azure permission to read AKS
       ↓
permission to obtain credentials
       ↓
Kubernetes authorization
```

For example:

```text
service identity authenticates to Azure ✅
gets kubeconfig ✅
kubectl get pods → Forbidden ❌
```

That points to:

```text
AKS Kubernetes authorization
```

rather than Azure login.

This distinction is critical.

---

### **8. Check newly assigned RBAC propagation**

If someone just granted:

```text
AcrPush
```

and immediately reruns the pipeline, there may be a short propagation/cache delay.

I don't keep changing roles every few seconds and accidentally overprivilege the identity.

I verify:

```text
correct identity
correct role
correct scope
```

then allow normal propagation before escalating.

---

### **9. Check network differences**

Sometimes the identity is fine.

My laptop may have:

```text
VPN
↓
Private AKS
```

while the pipeline uses:

```text
Microsoft-hosted agent
↓
public internet
↓
Private AKS inaccessible
```

Then:

```text
my account works
pipeline fails
```

looks like permissions but is actually networking.

So I distinguish:

```text
401 / 403
→ identity/RBAC

timeout / DNS failure
→ network
```

---

### **10. Check pipeline authorization to the service connection**

There's also an Azure DevOps layer:

```text
Pipeline
   ↓
Can it use this Service Connection?
```

Even when the underlying Azure identity is valid, the pipeline must be permitted to consume that connection.

Microsoft's current service-connection guidance also recommends scoped usage and separate connections where necessary. ([Microsoft Learn][3])

### **Strong troubleshooting sequence**

```text
1. Capture exact pipeline error
2. Identify service connection identity
3. Confirm tenant/subscription/resource
4. Verify authentication
5. Check Azure RBAC scope
6. Check data-plane roles
7. Check AKS/service-specific authorization
8. Check pipeline permission to service connection
9. Compare network path with personal machine
10. Inspect Entra/Azure audit logs
```

### **Interview answer condensed**

> “If it works with my account but not through the service connection, I compare identities rather than assuming the command is broken. I identify the service principal or managed identity behind the connection, confirm the correct tenant/subscription and authentication state, and check Azure RBAC at the exact resource scope—including data-plane roles such as `AcrPush` where needed. For AKS I separately check Kubernetes authorization. I also compare network context because my laptop might reach a private resource through VPN while the hosted agent cannot.”

**Memory line:**
**Personal works, service connection fails → compare identity, scope, permissions and network context.**

**Interview trap:**
Don't “fix” it by immediately granting:

```text
Owner
at subscription
```

That hides the real missing permission and violates least privilege.

**Keywords:** service connection, service principal, managed identity, RBAC, scope, data plane, 401, 403

**Likely follow-ups:**

* Contributor vs data-plane role?
* Why could AKS still return `Forbidden`?
* What if the service connection uses WIF?
* How would you distinguish permissions from networking?

### **T08-H08. How would you secure a self-hosted Azure DevOps agent?**

**Answer:**
I treat a self-hosted agent as a **high-risk execution host**, because pipeline code can execute arbitrary commands on it and potentially reach anything the machine or its identity can access.

So I secure:

```text
Agent identity
Machine
Network
Agent pool
Pipeline permissions
Secrets
Lifecycle
```

Microsoft explicitly warns that pipeline agents execute externally supplied code and therefore must be treated as potential remote-code-execution targets. ([Microsoft Learn][4])

### **1. Run the agent as a low-privilege identity**

I would not run:

```text
agent service
→ root
```

or:

```text
highly privileged Entra admin
```

unless absolutely unavoidable.

For Linux:

```text
dedicated user:
svc_azuredevops
```

with:

```text
no sudo
no interactive admin rights
```

where possible.

Microsoft specifically recommends a dedicated non-root user without sudo for Linux/macOS self-hosted agents. ([Microsoft Learn][2])

---

### **2. Separate agent-registration identity from runtime identity**

The user who initially registers an agent may need elevated Azure DevOps permissions.

That doesn't mean the actual agent process should continuously run as that user.

Microsoft explicitly recommends separating the identity that **configures the agent** from the identity that **runs it**. ([Microsoft Learn][4])

Think:

```text
Admin
→ registers/configures agent

Low-privilege service account
→ runs agent permanently
```

---

### **3. Don't share one agent pool with everything**

Bad:

```text
One agent pool
├── PR builds
├── Development
├── Security testing
└── Production deployments
```

A compromised PR pipeline could contaminate or attack production workloads.

Better:

```text
Agent Pools
│
├── untrusted-ci
│
├── internal-build
│
└── production-deploy
```

Microsoft recommends separate pools for projects and sensitive/production workloads to reduce lateral movement. ([Microsoft Learn][5])

---

### **4. Never run untrusted fork code on sensitive self-hosted agents**

Imagine:

```text
External contributor
      ↓
Pull Request
      ↓
pipeline executes arbitrary shell script
      ↓
self-hosted agent inside corporate VNet
```

That's dangerous.

The malicious code might probe:

```text
internal APIs
metadata services
private databases
cached credentials
local filesystem
```

Microsoft specifically recommends Microsoft-hosted agents rather than corporate self-hosted agents for untrusted fork builds where possible. ([Microsoft Learn][2])

---

### **5. Restrict network access**

If the production agent only needs:

```text
Azure DevOps
ACR
AKS private API
Key Vault
```

it shouldn't have unrestricted access to:

```text
every VNet
every database
every management interface
```

I use:

```text
Dedicated subnet
NSGs
Azure Firewall
route controls
private endpoints
```

with least-required outbound/inbound connectivity.

Conceptually:

```text
Prod Agent Subnet
     ↓
Allowed:
AKS API
ACR
Azure DevOps
required Azure endpoints

Blocked:
unrelated internal systems
```

This limits lateral movement if the agent is compromised.

---

### **6. No inbound exposure unless required**

Most Azure DevOps self-hosted agents operate by initiating outbound connections to Azure DevOps.

So I generally don't expose:

```text
SSH/RDP from internet
```

to the agent.

Administrative access should go through:

```text
Bastion
VPN
private management network
JIT
```

as appropriate.

---

### **7. Keep secrets out of the machine**

Bad:

```text
/home/agent/.azure/credentials
prod-sp-password.txt
.env containing production secrets
```

persisting between jobs.

Prefer:

```text
Workload Identity Federation
Service Connection
Azure Key Vault
pipeline secret mechanisms
```

and only materialize secrets for the minimum required duration.

Microsoft recommends letting Azure Pipelines manage access to secrets rather than running the agent under highly privileged identities with direct secret access. ([Microsoft Learn][2])

---

### **8. Harden the OS**

I would:

```text
Patch OS regularly
Patch agent software
Remove unused packages/services
Enable endpoint protection
Use disk encryption
Restrict filesystem permissions
Monitor auth/system logs
Disable password SSH where possible
```

Microsoft explicitly calls out regularly updating self-hosted agents as a security best practice. ([Microsoft Learn][5])

---

### **9. Protect the agent working directory**

Agent directories can contain:

```text
repository source
generated credentials
artifacts
temporary files
pipeline secrets
```

Microsoft warns that agent-controlled folders may contain sensitive information and should be accessible to as few users as possible. ([Microsoft Learn][4])

So:

```text
agent workspace
→ service-account ownership
→ restrictive filesystem permissions
```

not a shared developer directory.

---

### **10. Prefer ephemeral agents for sensitive workloads**

Persistent agents create residue:

```text
Job 1
↓
files/cache/tokens remain

Job 2
↓
may see leftovers
```

A stronger pattern is:

```text
Job requested
   ↓
new agent/VM/container
   ↓
execute one job
   ↓
destroy
```

Microsoft recommends minimizing persistence between jobs on sensitive self-hosted agents. ([Microsoft Learn][2])

That reduces:

```text
cross-job contamination
credential residue
malware persistence
```

---

### **11. Restrict who can use the pool**

The pool itself is a protected resource.

Only trusted pipelines should be able to use:

```text
production-agent-pool
```

Otherwise someone could create:

```yaml
pool:
  name: production-agent-pool

steps:
- script: malicious-command
```

and execute inside your production network.

So I restrict:

```text
pool permissions
pipeline authorization
repository write access
YAML modification rights
```

---

### **12. Give Azure access through pipeline identity, not machine omnipotence**

Bad:

```text
Agent VM identity
→ Owner across subscription
```

Then any pipeline command executed there inherits enormous power.

Better:

```text
Agent host
→ minimal host permissions

Pipeline Service Connection
→ narrowly scoped WIF identity
→ specific Azure resources
```

This separates:

```text
machine identity
from
deployment identity
```

### **Strong architecture**

```text
Azure DevOps
      ↓
Authorized production pipeline only
      ↓
Prod Agent Pool
      ↓
Ephemeral/isolated self-hosted agent
      │
      ├── Dedicated non-root user
      ├── No stored Azure secret
      ├── Restricted subnet/NSG
      ├── Patched OS
      └── Minimal filesystem access
      ↓
WIF Service Connection
      ↓
Least-privilege Azure RBAC
      ↓
Private AKS
```

**Interview answer condensed:**

> “I treat self-hosted agents as privileged execution infrastructure. I'd run the agent as a dedicated non-root, non-admin identity, isolate sensitive workloads into separate agent pools and subnets, restrict which pipelines can use those pools, keep the OS and agent patched, and avoid storing credentials on disk. I wouldn't run untrusted PR or fork code on a production-connected agent. Azure access would come through a narrowly scoped workload-identity-federated service connection, and for high-security workloads I'd prefer ephemeral agents so each job starts clean.”

**Memory line:**
**A self-hosted agent executes arbitrary pipeline code—secure it like a production server.**

**Interview trap:**
Self-hosted is not automatically safer because:

```text
“it's inside our VNet.”
```

That can actually increase impact because a compromised pipeline may now reach internal services.

**Keywords:** self-hosted agent, least privilege, agent pools, network isolation, ephemeral agents, WIF, patching

**Likely follow-ups:**

* Why not run external PRs on self-hosted agents?
* Why use separate production agent pools?
* Persistent vs ephemeral agents?
* Should the agent run as root?

### **T08-H09. How would you avoid giving CI/CD Contributor access to an entire subscription?**

**Answer:**
I would use **least-privilege identities scoped to the smallest practical Azure resource boundary**, preferably with Workload Identity Federation. Rather than one pipeline identity with subscription-wide Contributor, I separate identities by workload and responsibility and assign only the roles each pipeline actually needs.

Microsoft explicitly recommends scoping Azure DevOps service connections to specific resources or resource groups and avoiding broad subscription-level Contributor rights. ([Microsoft Learn][2])

### **Bad design**

```text
CI/CD identity
      ↓
Contributor
      ↓
Entire Subscription
      ↓
AKS
ACR
Key Vault
SQL
Networking
Production
Everything
```

If that identity is compromised:

```text
blast radius = subscription
```

### **Better design**

```text
CI/CD identities
│
├── image-builder
│      └── AcrPush → ACR only
│
├── app-deployer
│      └── AKS deployment permissions
│
├── network-terraform
│      └── Network Contributor → rg-network
│
└── app-terraform
       └── Contributor → rg-application
```

Now compromise of:

```text
image-builder
```

doesn't automatically allow deleting:

```text
VNets
SQL
Key Vault
AKS
```

---

### **1. Scope service connection to a resource group**

Instead of:

```text
Subscription scope
Contributor
```

create:

```text
Service Connection:
sc-payment-prod

Scope:
rg-payment-prod
```

Then the Azure identity is unable to modify unrelated resource groups.

Microsoft's current Azure DevOps security guidance specifically recommends choosing a specific resource group for new Azure Resource Manager service connections where feasible. ([Microsoft Learn][6])

---

### **2. Use resource-specific roles**

Even resource-group Contributor may still be broader than necessary.

For container publishing:

```text
AcrPush
→ specific ACR
```

For blob publishing:

```text
Storage Blob Data Contributor
→ specific storage account/container
```

For networking:

```text
Network Contributor
→ network resource group
```

For reading Key Vault secrets:

```text
Key Vault Secrets User
→ required vault
```

So:

```text
Task
↓
minimum matching Azure role
```

rather than:

```text
Task
↓
Contributor everywhere
```

---

### **3. Separate build and deploy identities**

A build pipeline often needs:

```text
ACR push
```

but doesn't need:

```text
AKS admin
```

Example:

```text
CI identity
   ↓
AcrPush

CD identity
   ↓
AKS deployment permission
```

This prevents a compromised build job from automatically gaining production deployment capability.

---

### **4. Separate environments**

I don't normally use one identity for:

```text
dev
staging
production
```

A better model:

```text
sc-dev
→ dev RG

sc-staging
→ staging RG

sc-prod
→ production RG
```

Then:

```text
Feature/Dev pipeline
```

cannot accidentally use production permissions unless explicitly authorized.

Microsoft recommends segmenting environments and using narrowly scoped identities to minimize blast radius. ([Microsoft Learn][7])

---

### **5. Use Workload Identity Federation**

Instead of:

```text
Service principal
+
stored client secret
```

use:

```text
Azure DevOps
   ↓
WIF
   ↓
Microsoft Entra ID
   ↓
short-lived token
```

This solves the credential-storage problem.

Then combine it with:

```text
narrow RBAC
```

to solve the authorization problem.

Microsoft currently recommends WIF for Azure service connections whenever feasible. ([Microsoft Learn][2])

---

### **6. Terraform needs thoughtful permissions**

Terraform often needs broader access because it creates infrastructure.

But I still wouldn't automatically grant:

```text
Contributor at subscription
```

if the Terraform stack only manages:

```text
rg-payment-prod
```

I'd scope:

```text
Terraform identity
      ↓
Contributor
      ↓
rg-payment-prod
```

If it also needs role assignments, that's a separate privilege.

For example:

```text
Contributor
```

does **not** by itself provide unrestricted permission to create Azure role assignments.

So if the pipeline needs RBAC creation, I explicitly design that permission rather than just granting subscription Owner.

---

### **7. Split infrastructure by privilege boundary**

Suppose Terraform needs:

```text
App resources
VNet
RBAC
```

Rather than giving one identity enormous power:

```text
Terraform
      ↓
Owner subscription
```

I may split:

```text
Network pipeline
→ network RG

Application pipeline
→ app RG

Identity/bootstrap pipeline
→ tightly controlled higher privileges
```

This reduces everyday pipelines' privileges.

---

### **8. Use custom roles if built-ins are too broad**

Sometimes:

```text
Contributor
```

allows much more than the pipeline needs.

Then I can create an Azure custom role containing only necessary actions.

For example:

```text
Custom role:
Application Deployment Operator

Can:
- update specific application resources
- read deployment metadata

Cannot:
- modify networking
- delete Key Vault
- assign RBAC
```

Custom roles increase governance complexity, so I use them when the blast-radius reduction is worth it.

---

### **9. Scope service connection usage inside Azure DevOps**

Azure RBAC isn't the only boundary.

I also configure:

```text
Which project/pipeline
may use
which service connection?
```

Example:

```text
sc-prod
   ↓
Authorized:
production-deploy.yml

Not authorized:
PR pipeline
experimental pipeline
```

Microsoft recommends using separate connections for different projects/organizations and controlling their usage. ([Microsoft Learn][3])

---

### **10. Example production design**

```text
Azure DevOps
│
├── CI Pipeline
│      ↓
│   WIF identity-ci
│      ↓
│   AcrPush
│      ↓
│   ACR only
│
├── App CD Pipeline
│      ↓
│   WIF identity-app-prod
│      ↓
│   AKS/resource-group scoped access
│
└── Terraform Network Pipeline
       ↓
    WIF identity-network
       ↓
    Network Contributor
       ↓
    rg-network
```

Compare that with:

```text
ONE service principal
↓
Contributor subscription
↓
used by every pipeline
```

The first design gives dramatically smaller blast radius.

### **Interview answer condensed**

> “I wouldn't use one subscription-wide Contributor service connection. I'd create separate workload-identity-federated identities for different responsibilities—for example `AcrPush` on the registry for CI, a deployment identity scoped to the production application resource group or AKS permissions, and a separate Terraform identity for the infrastructure it manages. I'd scope assignments to the smallest resource or resource group possible, split dev/staging/prod identities, and restrict which pipelines can use each service connection. If built-in roles are still too broad, I'd consider a custom role.”

**Memory line:**
**Give each pipeline the smallest role, on the smallest scope, for the shortest useful lifetime.**

**Interview trap:**
Don't solve pipeline permission problems by repeatedly escalating:

```text
Reader
→ Contributor
→ Owner
```

until the pipeline works.

Instead identify the exact **action + resource + scope** that is required.

**Keywords:** least privilege, service connection, resource scope, `AcrPush`, WIF, separate identities, custom role, blast radius

**Likely follow-ups:**

* Why separate build and deployment identities?
* Contributor vs Owner?
* When would Terraform genuinely need broader access?
* Resource-group role vs resource-specific role?
