# 8. 🔴 M IMP — Azure DevOps & GitHub Actions CI/CD

## Medium

### **T08-M07. What is a multi-stage YAML pipeline?**

**Answer:**
A **multi-stage YAML pipeline** is an Azure Pipeline where the complete CI/CD workflow is divided into logical stages such as **Build, Test, Staging, and Production**, all defined as code in YAML.

```text
Pipeline
│
├── Build
│     ↓
├── Test
│     ↓
├── Deploy_Staging
│     ↓
└── Deploy_Production
```

A stage contains one or more **jobs**, and each job contains **steps**. Stages can depend on previous stages, run conditionally, and represent clear security or deployment boundaries. ([Microsoft Learn][1])

### **Hierarchy**

The structure is:

```text
Pipeline
  ↓
Stages
  ↓
Jobs
  ↓
Steps
  ↓
Tasks / Scripts
```

For example:

```yaml
stages:

- stage: Build
  jobs:
  - job: BuildApp
    steps:
    - script: npm ci
    - script: npm test

- stage: DeployStaging
  dependsOn: Build
  jobs:
  - job: Deploy
    steps:
    - script: echo "Deploying staging"

- stage: DeployProduction
  dependsOn: DeployStaging
  jobs:
  - job: Deploy
    steps:
    - script: echo "Deploying production"
```

A job is a collection of steps executed by an agent, and stages can contain multiple such jobs. ([Microsoft Learn][2])

### **Why use multiple stages?**

It gives clear separation between different parts of delivery:

```text
Build
→ create artifact

Test
→ validate artifact

Staging
→ integration/smoke tests

Production
→ controlled deployment
```

This gives better:

* visibility,
* failure isolation,
* approvals,
* conditions,
* deployment governance,
* traceability.

For example:

```text
Build succeeds ✅
      ↓
Tests fail ❌
      ↓
Production stage never runs
```

### **Dependencies and conditions**

Stages normally execute according to their dependency graph.

Example:

```yaml
- stage: Production
  dependsOn: Staging
  condition: succeeded()
```

So Production runs only if Staging succeeds.

A more complex pipeline could be:

```text
                 ┌→ Linux Tests ─┐
Build ───────────┤               ├→ Staging → Production
                 └→ Security ────┘
```

Jobs/stages can run in parallel when dependencies allow.

### **Deployment environments**

The production stage can use an Azure DevOps Environment:

```text
DeployProduction stage
       ↓
Environment: production
       ↓
Approval/checks
       ↓
Deployment
```

So the YAML defines workflow structure, while protected environment checks can provide governance outside the YAML.

### **Practical AKS example**

```text
Commit
  ↓
Stage 1 — CI
├── Unit tests
├── Docker build
└── Trivy scan
  ↓
Stage 2 — Publish
└── Push image to ACR
  ↓
Stage 3 — Staging
└── Deploy same image to AKS
  ↓
Smoke tests
  ↓
Stage 4 — Production
└── Approval → AKS production
```

This makes the full delivery process visible in one pipeline.

**Memory line:**
**Multi-stage pipeline = one YAML-defined delivery flow split into Build → Test → Deploy stages.**

**Interview trap:**
Don't confuse:

```text
Stage
→ logical pipeline boundary

Job
→ unit of work assigned to an agent

Step
→ individual task/script inside the job
```

**Keywords:** stages, jobs, steps, `dependsOn`, conditions, environments, YAML

**Likely follow-ups:**

* Stage vs job?
* Can stages run in parallel?
* Where would you add a production approval?
* How would you pass an artifact between stages?

### **T08-M08. What are pipeline templates?**

**Answer:**
Azure Pipeline templates are **reusable YAML files containing common stages, jobs, steps, variables, or pipeline structure**, allowing multiple pipelines to share the same implementation instead of copying YAML everywhere.

For example:

```text
30 application pipelines
          ↓
shared template
          ↓
Build + Test + Scan
```

Azure DevOps supports reusable template content as well as `extends` templates that define a standardized pipeline structure. ([Microsoft Learn][3])

### **Without templates**

Suppose 30 microservices each contain:

```yaml
- script: docker build ...
- script: npm test
- script: trivy image ...
- script: docker push ...
```

Then you have:

```text
same CI logic
×
30 repositories
```

If the security team wants to add:

```text
SAST scan
```

you may have to update 30 files.

### **With templates**

Instead:

```text
central template
build-and-scan.yml
       ↓
service-a
service-b
service-c
...
```

Template:

```yaml
parameters:
- name: imageName
  type: string

steps:
- script: npm test

- script: docker build -t ${{ parameters.imageName }} .

- script: trivy image ${{ parameters.imageName }}
```

Consumer:

```yaml
steps:
- template: templates/build-and-scan.yml
  parameters:
    imageName: payment-api
```

Now the common logic is defined once.

### **What can templates contain?**

Azure Pipelines supports reusable:

```text
Steps
Jobs
Stages
Variables
```

and parameterized templates. ([Microsoft Learn][3])

For example:

```text
step template
→ reusable commands

job template
→ reusable build job

stage template
→ reusable deployment stage

variable template
→ reusable configuration
```

### **Parameters make templates flexible**

Suppose the same deployment pattern applies to three environments:

```yaml
parameters:
- name: environment
  type: string

- name: namespace
  type: string
```

Then:

```text
Template
     ↓
Dev
environment=dev
namespace=dev

Template
     ↓
Prod
environment=prod
namespace=production
```

Same implementation, different inputs.

### **Include vs `extends` templates**

This distinction is useful in interviews.

**Include template:**

```text
Main pipeline
     ↓
insert these reusable steps/jobs/stages
```

Example:

```yaml
steps:
- template: templates/security-scan.yml
```

**Extends template:**

```text
Central template
      ↓
defines required pipeline structure
      ↓
application pipeline supplies parameters
```

Azure DevOps describes `extends` templates as useful for enforcing structure and security standards—not just reducing duplication. ([Microsoft Learn][3])

### **Enterprise example**

Imagine 30 microservices.

I could create:

```text
templates/
├── ci.yml
├── docker-build.yml
├── security-scan.yml
└── deploy-aks.yml
```

Each service pipeline becomes small:

```yaml
extends:
  template: templates/service-pipeline.yml

  parameters:
    serviceName: payment
    dockerfile: services/payment/Dockerfile
```

Now I can centrally enforce:

```text
Unit testing
Trivy
SAST
image tagging
ACR push
deployment rules
```

across all services.

### **Why templates matter**

They give:

```text
DRY configuration
+
consistency
+
centralized security
+
easier maintenance
```

**Memory line:**
**Pipeline template = reusable pipeline-as-code building block.**

**Interview trap:**
Don't think templates are only code deduplication.

With `extends`, they can also enforce:

```text
approved pipeline structure
allowed tasks
security controls
organizational standards
```

**Keywords:** YAML template, reusable stages, reusable jobs, parameters, `extends`, standardization

**Likely follow-ups:**

* Include vs `extends`?
* Parameters vs variables?
* How would you manage pipelines for 30 microservices?
* Can templates enforce security standards?

### **T08-M09. How do pipeline artifacts differ from container images?**

**Answer:**
A **pipeline artifact** is a generic file or directory produced by a pipeline and stored so another stage or pipeline can consume it. A **container image** is an OCI/Docker-formatted application runtime package designed to be pulled by a container runtime and executed as a container.

So:

```text
Pipeline Artifact
→ generic build output

Container Image
→ executable container filesystem/runtime package
```

Azure Pipelines allows artifacts from one stage/run to be published and later downloaded by another stage or pipeline. ([Microsoft Learn][4])

### **Pipeline artifact example**

A build stage might produce:

```text
dist/
├── app.jar
├── config/
└── scripts/
```

Then publish it:

```yaml
- publish: $(System.DefaultWorkingDirectory)/dist
  artifact: application
```

Later:

```text
Build Stage
   ↓
Pipeline Artifact
   ↓
Deployment Stage
```

downloads and uses it.

Pipeline artifacts can contain almost anything:

```text
ZIP
JAR
binary
Terraform plan
compiled frontend
Helm chart package
test output
deployment bundle
```

### **Container image example**

A Docker build creates:

```text
Container Image
├── base OS/filesystem layers
├── runtime
├── application
├── libraries
└── metadata/entrypoint
```

Example:

```bash
docker build \
  -t myacr.azurecr.io/payment-api:7bc23ab .
```

Then:

```text
Pipeline
   ↓
ACR
   ↓
payment-api:7bc23ab
   ↓
AKS
   ↓
container runtime
   ↓
running Pod
```

The image is normally stored in a **container registry**, such as Azure Container Registry.

### **Key comparison**

| Area                 | Pipeline Artifact         | Container Image               |
| -------------------- | ------------------------- | ----------------------------- |
| Purpose              | Move/store build outputs  | Run containerized application |
| Format               | Almost any files          | OCI/Docker image              |
| Stored in            | Pipeline artifact storage | Container registry            |
| Executed directly    | Usually no                | Yes, by container runtime     |
| Used by AKS directly | Usually no                | Yes                           |
| Examples             | ZIP, JAR, Helm package    | `api:v1.5.2`                  |

### **They can exist in the same pipeline**

Example:

```text
Build
 │
 ├── test-report.xml
 │      ↓
 │   Pipeline Artifact
 │
 └── Docker Image
        ↓
        ACR
        ↓
        AKS
```

They solve different problems.

### **DevOps example**

For Terraform:

```text
terraform plan
     ↓
tfplan file
     ↓
Pipeline Artifact
     ↓
approval
     ↓
terraform apply tfplan
```

A container image doesn't make sense there.

For a microservice:

```text
docker build
     ↓
Container Image
     ↓
ACR
     ↓
AKS
```

### **Build once principle**

For container workloads, I normally want:

```text
Build image once
      ↓
immutable image digest
      ↓
Dev
      ↓
Staging
      ↓
Production
```

rather than rebuilding a new container image in every environment.

A pipeline artifact can similarly transfer non-container build outputs across stages.

**Memory line:**
**Artifact = generic pipeline output; image = container runtime package stored in a registry.**

**Interview trap:**
Don't say:

> “A Docker image is just an Azure Pipeline artifact.”

Technically a pipeline could save an image tarball as a file, but operationally container images are normally **published to a registry and addressed by tag/digest**, while pipeline artifacts are generic build outputs.

**Keywords:** pipeline artifact, container image, ACR, OCI, build output, immutable image

**Likely follow-ups:**

* Where are pipeline artifacts stored?
* Why push images to ACR instead of publishing them as artifacts?
* What does build-once-deploy-many mean?
* Tag vs image digest?

### **T08-M10. How can a GitHub Actions workflow authenticate to Azure?**

**Answer:**
The preferred approach is **OpenID Connect (OIDC) workload identity federation** between GitHub Actions and Microsoft Entra ID. This lets the workflow exchange a GitHub-issued OIDC token for a **short-lived Azure access token without storing a long-lived Azure client secret**. ([Microsoft Learn][5])

The flow is:

```text
GitHub Actions Job
       ↓
GitHub OIDC token
       ↓
Microsoft Entra ID
       ↓
Federated identity validation
       ↓
Short-lived Azure access token
       ↓
Azure resources
```

### **1. Create an Azure identity**

This could be:

```text
Microsoft Entra application/service principal
```

or:

```text
User-assigned managed identity
```

Then configure a **federated identity credential** that trusts a specific GitHub identity.

For example:

```text
Repository:
devSatym/my-app

Branch:
main
```

Conceptually the trust rule says:

```text
Trust OIDC tokens from:
repo:devSatym/my-app:ref:refs/heads/main
```

So another repository shouldn't automatically be able to obtain Azure credentials.

### **2. Assign Azure RBAC**

The Azure identity gets only the permissions required.

Example:

```text
GitHub deployment identity
        ↓
AcrPush
on ACR
```

or:

```text
Terraform deployment identity
        ↓
Contributor
on specific resource group
```

not necessarily:

```text
Owner
at entire subscription ❌
```

OIDC solves authentication; **Azure RBAC still determines authorization**.

### **3. Allow the workflow to request an OIDC token**

Workflow:

```yaml
permissions:
  id-token: write
  contents: read
```

`id-token: write` allows GitHub Actions to request the OIDC token. GitHub's current Azure OIDC guidance explicitly requires this permission. ([GitHub Docs][6])

### **4. Login using `azure/login`**

A typical workflow is:

```yaml
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - run: az account show
```

Microsoft documents this OIDC flow with `azure/login` and a federated credential. ([Microsoft Learn][5])

One important nuance:

```text
AZURE_CLIENT_ID
AZURE_TENANT_ID
AZURE_SUBSCRIPTION_ID
```

are **identifiers**, not an Azure client secret.

The workflow does not need:

```text
AZURE_CLIENT_SECRET ❌
```

for OIDC authentication.

### **5. Token exchange**

Internally:

```text
GitHub
creates signed OIDC JWT
       ↓
azure/login
sends token to Entra
       ↓
Entra checks:
issuer
audience
subject/trust conditions
       ↓
access token issued
```

GitHub's documentation describes `azure/login` exchanging the GitHub OIDC JWT for an Azure access token. ([GitHub Docs][6])

### **Why is this better?**

Old approach:

```text
GitHub Secret
AZURE_CLIENT_SECRET
       ↓
valid for months
       ↓
Azure
```

Risks:

```text
secret leak
rotation burden
long credential lifetime
accidental log exposure
```

OIDC:

```text
Workflow run
    ↓
short-lived token
    ↓
Azure
    ↓
expires
```

GitHub and Microsoft both recommend OIDC over long-lived service-principal secrets for Azure authentication. ([GitHub][7])

### **Environment-specific federation**

For better production security I can tie the trust to a GitHub Environment:

```text
GitHub Environment:
production
       ↓
required reviewers
       ↓
OIDC identity associated with production
       ↓
Azure production access
```

This prevents an arbitrary branch from automatically obtaining the same production identity.

### **Other authentication methods**

`azure/login` also supports:

```text
OIDC federation          ← preferred

Service principal secret
                       ← legacy/not preferred

Managed identity
                       ← useful on suitable self-hosted
                          Azure runners
```

Microsoft explicitly lists service-principal-secret authentication as **not recommended** compared with OIDC. ([Microsoft Learn][8])

### **Interview answer condensed**

> “For GitHub Actions to Azure, I'd use OIDC workload identity federation. I create an Entra application or user-assigned managed identity, configure a federated credential that trusts the specific GitHub repository, branch, tag, or environment, grant that identity least-privilege Azure RBAC, and give the workflow `id-token: write`. `azure/login` then exchanges GitHub's short-lived OIDC token for an Azure access token, so no Azure client secret needs to be stored in GitHub.”

**Memory line:**
**GitHub OIDC → Entra federation → short-lived Azure token.**

**Interview trap:**
OIDC does **not** mean:

> “GitHub gets Azure access automatically.”

You still configure:

```text
Federated trust
+
identity
+
Azure RBAC
+
workflow OIDC permission
```

Also remember:

```text
client-id ≠ client-secret
```

The client/tenant/subscription IDs may still appear in configuration; the sensitive long-lived client secret is what's eliminated.

**Keywords:** GitHub Actions, OIDC, Workload Identity Federation, `azure/login`, `id-token: write`, Entra ID, Azure RBAC
