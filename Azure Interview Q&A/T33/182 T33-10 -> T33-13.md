# **T33-10. What metrics would determine whether a deployment should continue or roll back?**

**Answer:**

I would make the decision primarily from **user-impact and business metrics**, then use infrastructure metrics as supporting evidence.

For a web/API deployment, my main gates would normally be **availability, 5xx/error rate, p95/p99 latency, critical transaction success, and dependency failures**. For a canary, I would compare those metrics specifically for the candidate version against the stable version instead of looking only at global averages.

I would also watch saturation signals such as CPU, memory, database connections, queue depth, throttling, and Pod restarts because they can predict a failure before users notice it. But I would not roll back simply because CPU briefly reaches 80%.

Before deployment, I would define explicit thresholds and an observation window. For example:

```text
Continue if:
5xx < 1%
p95 < 500 ms
checkout success > 99.5%

Roll back if:
5xx > 5% for 5 minutes
critical transaction fails
or candidate latency is materially worse than baseline
```

The key is that the decision should be **predefined, version-specific, and based on sustained evidence**, not an engineer improvising while Production is degrading.

---

## **1. Start with user-facing signals**

My first group is:

```text
Availability
Errors
Latency
Critical business success
```

These answer:

> **Are users actually getting a healthy service?**

For example:

```text
Stable v41
Availability = 99.99%
5xx          = 0.2%
p95          = 350 ms

Candidate v42
Availability = 96%
5xx          = 8%
p95          = 1.9 sec
```

I don't need CPU to tell me v42 is bad.

The rollout should stop.

---

# **2. Error rate is one of the strongest rollback signals**

For an HTTP application:

```text
2xx/3xx
→ generally successful traffic

4xx
→ often client/auth/input issue

5xx
→ service/backend failure
```

A sudden increase:

```text
5xx:
0.2% → 12%
```

immediately after the candidate receives traffic is a strong rollback indicator.

But I would segment it by:

```text
service.version
deployment
region
endpoint
```

because global metrics can hide the problem.

---

# **3. Candidate-specific metrics are critical**

Suppose:

```text
v41 = 95% traffic
v42 = 5% traffic
```

Global error rate:

```text
0.7%
```

might look acceptable.

But:

```text
v41 error = 0.1%
v42 error = 12%
```

The candidate is clearly broken.

So for canary analysis:

```text
Candidate
vs
Stable baseline
```

is much more useful than:

```text
Whole service
```

alone.

---

# **4. Latency matters even when errors remain low**

A release might return:

```text
HTTP 200
```

for every request but increase checkout latency:

```text
p95:
350 ms → 2.5 sec
```

Users still experience degradation.

I would monitor:

```text
p50
p95
p99
```

rather than only averages.

Why?

Suppose:

```text
90% requests = 100 ms
10% requests = 8 sec
```

Average can hide serious tail latency.

---

# **5. Compare latency against both an SLO and the stable version**

Absolute gate:

```text
candidate p95 < 500 ms
```

is useful.

But consider:

```text
Stable p95    = 180 ms
Candidate p95 = 470 ms
```

Candidate technically passes 500 ms but is:

```text
>2.5× slower
```

So I might also define:

```text
Candidate p95
must not exceed stable p95
by more than 20–30%
```

depending on the application.

That catches regressions before they consume the entire SLO margin.

---

# **6. Business metrics can be more important than HTTP health**

Imagine:

```text
HTTP 200 = normal
latency  = normal
```

but new code calculates payments incorrectly.

Technical monitoring might say:

```text
Healthy
```

Business telemetry might show:

```text
Payment success:
99.8% → 88%

Checkout conversion:
72% → 43%
```

That deployment should stop immediately.

For important systems I would include metrics such as:

```text
login success
orders completed
payments authorized
messages processed
files uploaded
jobs completed
```

depending on the service.

---

# **7. Synthetic transactions are especially useful**

Instead of only asking:

```text
GET /health → 200?
```

run:

```text
login
 ↓
add item
 ↓
checkout
 ↓
payment test
 ↓
verify order
```

A controlled synthetic transaction proves the complete critical flow.

A health endpoint might remain green while:

```text
payment dependency
```

is broken.

---

# **8. Dependency metrics**

I would also monitor:

```text
Azure SQL latency
Redis/cache failures
Service Bus errors
external API latency
Key Vault failures
Storage throttling
```

Why?

A release might increase:

```text
SQL calls/request
5 → 50
```

At 5% canary traffic the application still looks okay.

But database CPU:

```text
30% → 65%
```

already indicates that 100% rollout might overload the database.

So dependency telemetry can stop a rollout **before** user-facing failure becomes severe.

---

# **9. Saturation/resource metrics are supporting indicators**

Monitor:

```text
CPU
memory
GC
thread pool
connection pools
Pod restarts
node pressure
disk
database connections
queue depth
```

But don't make simplistic policy:

```text
CPU > 80%
→ rollback
```

CPU can legitimately rise after a high-performance release.

Example:

```text
CPU:
60% → 85%

Throughput:
5k → 10k requests/sec

Latency:
unchanged

Errors:
unchanged
```

This might actually be fine.

Resource metrics need context.

---

# **10. Kubernetes-specific rollout health**

For AKS I watch:

```text
Ready replicas
Available replicas
Pod restart count
CrashLoopBackOff
OOMKilled
Pending Pods
readiness failures
```

For example:

```text
desired replicas  = 10
available replicas = 4
```

is a serious rollout failure.

But again:

```text
10/10 Ready
```

doesn't prove business correctness.

Kubernetes metrics are one layer.

---

# **11. Autoscaling behavior**

Candidate may cause:

```text
HPA:
10 Pods → 100 Pods
```

while traffic remains constant.

That can indicate:

```text
CPU regression
memory issue
bad request behavior
```

Similarly:

```text
Cluster Autoscaler
rapidly adding nodes
```

could indicate unexpectedly high resource requirements.

I'd compare:

```text
cost/capacity profile
stable vs candidate
```

as part of larger release analysis.

---

# **12. Queue-driven services need different metrics**

For a worker consuming Service Bus:

HTTP 5xx may be irrelevant.

I would monitor:

```text
queue depth
oldest message age
processing rate
failure rate
dead-letter count
processing latency
```

Example:

```text
Before release:
queue = 1,000
drain rate = 500 msg/sec

After release:
queue = 100,000 and growing
drain rate = 100 msg/sec
```

Even if workers show:

```text
CPU = 30%
```

the release is unhealthy.

Metrics must match the workload.

---

# **13. Database deployments need database signals**

If the release includes database changes, I would monitor:

```text
query latency
deadlocks
blocking
connection failures
CPU
data/log IO
timeouts
```

Suppose:

```text
API p95
400 ms → 3 sec
```

and tracing shows:

```text
SQL span
20 ms → 2.6 sec
```

I now know the release likely introduced a query/schema/indexing regression.

---

# **14. Use sustained thresholds**

Don't rollback because:

```text
one request failed
```

unless it was a catastrophic correctness/security failure.

A normal rule might require:

```text
5xx > 5%
for 5 consecutive minutes
```

or:

```text
3 out of 5 evaluation periods
```

depending on traffic.

This filters temporary noise.

---

# **15. Observation windows depend on failure type**

An immediate startup bug:

```text
30–60 seconds
```

may reveal itself quickly.

A memory leak might require:

```text
hours
```

A daily batch regression may require:

```text
one business cycle
```

Therefore:

```text
"Canary passed for 2 minutes"
```

does not prove every kind of safety.

The observation window needs to cover meaningful failure modes.

---

# **16. Minimum sample size matters**

Suppose canary gets:

```text
5 requests
```

and one fails.

Error rate:

```text
20%
```

But sample size is tiny.

Conversely:

```text
1 million requests
```

with 5% error is overwhelming evidence.

A mature rollout analysis should account for:

```text
time window
+
sample count
```

rather than only percentages.

---

# **17. Error-budget/SLO burn is useful for mature services**

Suppose service SLO is:

```text
99.95%
```

A release suddenly causes rapid error-budget consumption.

A fast-burn condition tells me:

> At this rate, this release is going to consume our reliability budget quickly.

That can become a powerful deployment gate.

I prefer this over relying exclusively on infrastructure thresholds because it ties release health to actual service reliability.

---

# **18. Security can also be a hard stop**

Suppose release passes performance gates but suddenly produces:

```text
authentication bypass
critical secret exposure
WAF anomaly
security policy violation
```

That's a valid:

```text
STOP / ROLLBACK
```

even if:

```text
5xx = 0%
```

Availability is not the only production quality requirement.

---

# **19. Example automatic rollout policy**

```text
Stable: v41
Candidate: v42
```

At 5%:

```text
Observe for 10 minutes
```

### Continue if

```text
Candidate availability >= 99.9%

Candidate 5xx < 1%

Candidate p95 < 500ms

Candidate p95 <=
stable p95 × 1.2

Payment success >= 99.5%

No critical dependency errors

No severe security signal
```

### Abort immediately if

```text
Critical transaction fails
OR
5xx > 5%
OR
availability < 98%
OR
data-integrity check fails
```

Then:

```text
Canary traffic → 0%
Stable → 100%
```

That's much more defensible than:

> “If the dashboard looks bad, rollback.”

# **T33-11. Someone manually changes an Azure resource managed by Terraform; what do you do?**

**Answer:**

I would treat that as **Terraform drift** and first determine exactly what changed before applying anything.

I would run a normal `terraform plan` or, if I specifically want to inspect out-of-band changes without proposing infrastructure corrections, `terraform plan -refresh-only`. Terraform refreshes its view of the real Azure resource and shows the difference between what Terraform previously tracked and what now exists.

Then I make a deliberate decision:

* if the manual change was unauthorized or temporary, I keep the Terraform configuration as the desired state and apply a reviewed normal plan to revert Azure;
* if the manual change was valid—for example an emergency production fix—I update the Terraform code to represent that desired change, review the resulting plan, and reconcile the state/configuration properly.

I would not immediately run `terraform apply`, manually edit the state file, or blindly run a refresh operation. The objective is to bring these three things back into agreement:

```text
Terraform configuration
        =
Terraform state
        =
actual Azure infrastructure
```

HashiCorp currently recommends `plan -refresh-only` for safely reviewing out-of-band changes; the older `terraform refresh` command is deprecated because it updates state automatically without the same review opportunity. ([HashiCorp Developer][1])

---

## **1. Understand the three states**

Terraform works with three important views:

```text
Configuration
"What we want"

State
"What Terraform thinks it manages"

Azure
"What actually exists"
```

Before drift:

```text
Code:
SKU = P1v3

State:
SKU = P1v3

Azure:
SKU = P1v3
```

Someone manually changes Azure:

```text
Azure:
SKU = P2v3
```

Now:

```text
Code ≠ Azure
```

Terraform must decide what to do during the next plan.

---

# **2. Don't immediately run apply**

Bad response:

```text
Someone changed Prod
      ↓
terraform apply -auto-approve
```

I don't yet know whether the manual change was:

```text
mistake
emergency mitigation
business-approved scaling
security remediation
```

Terraform may undo something keeping Production alive.

First gather evidence.

---

# **3. Find out who changed it and why**

Azure Activity Log can help answer:

```text
Who?
What operation?
When?
Which resource?
```

Also check:

```text
incident/change ticket
deployment logs
team communication
```

Suppose someone increased:

```text
App Service instances 4 → 20
```

during an outage.

Terraform code still says:

```text
4
```

Running apply immediately could scale back down to 4 and reintroduce the outage.

Context matters.

---

# **4. Run a refresh-only plan to inspect drift**

Useful:

```bash
terraform plan -refresh-only
```

Terraform asks providers to read real infrastructure and reports out-of-band differences but does not propose changing the Azure resources in that refresh-only plan. ([HashiCorp Developer][1])

For example:

```text
Objects have changed outside of Terraform

~ instance_count
    4 -> 20
```

What this proves:

```text
Azure actual differs
from Terraform's recorded view
```

It gives me evidence before deciding desired state.

---

# **5. Normal `terraform plan` already performs a refresh**

This is an important nuance.

I don't have to run refresh-only before every plan.

Normal:

```bash
terraform plan
```

first refreshes Terraform's in-memory view of managed resources and then calculates what changes are necessary to make Azure match the configuration. ([HashiCorp Developer][2])

So after the manual change:

```text
Code says: 4
Azure says: 20
```

normal plan may show:

```text
20 → 4
```

meaning:

> Terraform wants to restore the declared configuration.

---

# **6. Option A — Manual change was not desired**

Suppose a developer manually added:

```text
NSG:
Internet → SQL : 1433
```

That's unauthorized and unsafe.

Desired code still correctly excludes it.

Process:

```text
1. Confirm change
2. Assess security impact
3. Review Terraform plan
4. Apply desired configuration
5. Verify rule removed
6. Investigate why manual write access existed
```

Terraform becomes the remediation mechanism.

---

# **7. Option B — Manual change was legitimate**

Suppose an incident responder changed:

```text
App replicas:
4 → 20
```

and the organization decides 20 should remain for now.

Do not simply accept state and leave code saying 4.

Instead update:

```hcl
instance_count = 20
```

through the normal PR/review process.

Then run:

```bash
terraform plan
```

After Terraform reads Azure, ideally:

```text
No infrastructure changes
```

or only expected reconciliations.

Now:

```text
Code
State
Azure
```

can converge on the same intended value.

---

# **8. `apply -refresh-only` is not automatically the first answer**

You can use:

```bash
terraform apply -refresh-only
```

to record current remote changes into Terraform state without modifying infrastructure. HashiCorp supports this workflow, but applying refresh-only is a deliberate state-changing operation and should be reviewed carefully. ([HashiCorp Developer][1])

I would not use it reflexively to “fix drift.”

Why?

Because it makes:

```text
State → Azure actual
```

but does **not** automatically make:

```text
Configuration → Azure actual
```

If configuration still declares the old value, the next normal plan may try to revert it anyway.

The goal is full reconciliation, not merely state synchronization.

---

# **9. Why `terraform refresh` is not my preferred command**

Older advice often says:

```bash
terraform refresh
```

Current HashiCorp docs mark that command as deprecated and recommend refresh-only plan/apply instead. `terraform refresh` effectively updates state without giving you the safer review workflow of `plan -refresh-only`. ([HashiCorp Developer][3])

For interview purposes:

> **Use `terraform plan -refresh-only` to investigate drift, not blindly `terraform refresh`.**

---

# **10. Don't use `-refresh=false` while investigating drift**

This would be counterproductive:

```bash
terraform plan -refresh=false
```

because Terraform may ignore changes made outside its current recorded state and produce an incomplete plan. HashiCorp explicitly warns that disabling refresh can cause Terraform to ignore external changes. ([HashiCorp Developer][4])

When drift is the suspected problem:

```text
I specifically want current Azure reality.
```

---

# **11. Don't manually edit `terraform.tfstate`**

Avoid opening the state JSON and changing:

```text
"sku": "P1v3"
```

by hand.

State includes:

```text
resource addresses
provider information
dependencies
IDs
schema data
```

and a mistake can corrupt Terraform's understanding.

Prefer supported Terraform operations such as:

```text
plan/apply
import
moved blocks
state commands
```

when those operations are actually required.

---

# **12. If the resource exists in Azure but disappeared from state**

Different scenario:

```text
Azure:
VM exists

Terraform configuration:
VM exists

Terraform state:
VM missing
```

Then normal plan may propose:

```text
+ create VM
```

rather than recognize the existing object.

If it is the exact object Terraform should manage, use an **import** workflow rather than allowing Terraform to create a duplicate.

Current Terraform supports declarative `import` blocks as well as the CLI import workflow. ([HashiCorp Developer][5])

Example conceptually:

```hcl
import {
  to = azurerm_linux_virtual_machine.app
  id = "/subscriptions/.../virtualMachines/vm01"
}
```

Then review the plan.

---

# **13. If code was refactored instead of Azure manually changed**

Suppose:

Before:

```hcl
resource "azurerm_resource_group" "app" {}
```

After:

```hcl
resource "azurerm_resource_group" "production" {}
```

The actual Azure resource did not change.

But Terraform addresses changed:

```text
azurerm_resource_group.app
→
azurerm_resource_group.production
```

Without telling Terraform about the move, it may interpret that as:

```text
destroy old address
create new address
```

Use a `moved` block:

```hcl
moved {
  from = azurerm_resource_group.app
  to   = azurerm_resource_group.production
}
```

HashiCorp recommends moved blocks for these refactors because they preserve the existing object instead of destroying it. ([HashiCorp Developer][6])

This is **state-address refactoring**, not actual infrastructure drift.

# **14. Prevent recurrence**

If an unauthorized manual change was possible:

```text
Why did the developer
have Production write access?
```

Long-term model:

```text
Developers
→ Reader in Prod

Git PR
→ review

Pipeline identity
→ Production write access
```

Emergency access:

```text
PIM
→ temporary
→ audited
```

Then:

```text

```

becomes rare rather than routine.

# **15. Drift detection**

Run scheduled Terraform plans or platform drift detection.

Desired:

```text
No changes.
```

Unexpected:

```text
~ NSG rule
~ SKU
~ tag
```

creates investigation before the next deployment.

The earlier drift is discovered, the less likely it is to surprise a production apply.

## **Production example**

An operator responds to high load and manually changes:

```text
AKS node pool max:
10 → 30
```

Terraform code still:

```text
max_count = 10
```

My sequence:

```text
1. Check incident/change history
2. terraform plan -refresh-only
3. Confirm Azure is 30
4. Determine whether 30 is still required
```

If emergency condition has passed:

```text
5. Review normal plan showing 30 → 10
6. Apply during safe window
```

If 30 should remain:

```text
5. Update Terraform max_count = 30
6. PR/review
7. Run normal plan
8. Verify no unintended infrastructure change
```

Then remove unnecessary standing manual Prod permission.

# **T33-12. Terraform wants to recreate a production resource unexpectedly; what do you do before applying?**

**Answer:**

I would **stop immediately and not apply the plan** until I understand exactly why Terraform believes replacement is necessary.

I would save and inspect the plan, identify the specific attribute or resource-address change causing the `-/+` replacement, compare Terraform configuration, current state, and the actual Azure resource, and check recent module/provider/state changes.

Common causes include an immutable Azure property changing, a Terraform provider schema change, a resource/module rename without a `moved` block, changes to `count` or `for_each` keys, drift, an object missing from state, or simply running against the wrong subscription/workspace.

For production, the question isn't only:

> “Why does Terraform want replacement?”

I also need to understand:

> **What is the blast radius if this resource disappears?**

If it's a state/refactoring problem, I fix state/address mapping rather than recreate the resource. If replacement is truly required, I design the replacement deliberately—with backup, dependency analysis, HA/blue-green migration, and rollback—instead of letting an unexpected plan destroy Production.

Terraform plans represent replacement as delete/create actions when a changed attribute can't be updated in place; provider behavior determines which attributes require replacement. ([HashiCorp Developer][7])

---

## **1. `-/+` should make you stop**

Example:

```text
# azurerm_kubernetes_cluster.prod must be replaced
-/+ resource "azurerm_kubernetes_cluster" "prod" {
    ...
}
```

That is not:

```text
~ update in-place
```

It means conceptually:

```text
existing resource
    ↓
destroy/create replacement
```

For Production:

```text
DO NOT APPLY
```

until the reason is understood.

---

# **2. Save the plan**

Run:

```bash
terraform plan -out=tfplan
```

Then inspect:

```bash
terraform show tfplan
```

This gives a stable artifact for review.

If I simply rerun:

```bash
terraform plan
```

later after configuration/state changes, I may be looking at a different plan.

---

# **3. Identify the exact replacement trigger**

Look for output such as:

```text
# forces replacement
```

or inspect the structured plan when needed.

Example:

```text
~ subnet_id =
    "/subnets/old"
    ->
    "/subnets/new" # forces replacement
```

Now I know:

```text
replacement isn't random
```

Terraform/provider says that specific property cannot be changed in place.

HashiCorp describes replacement as `delete` + `create` when provider semantics indicate the changed property cannot be updated in place. ([HashiCorp Developer][7])

---

# **4. Compare configuration vs state vs Azure**

The diagnostic triangle:

```text
Terraform config
      ↓
Terraform state
      ↓
Actual Azure resource
```

Use:

```bash
terraform state show <resource-address>
```

to inspect Terraform's state representation.

Then use Azure CLI/Portal to inspect the actual resource.

Example:

```bash
az resource show --ids <resource-id>
```

I want to know:

```text
Did code change?
Did Azure change?
Did state mapping change?
```

Those lead to very different fixes.

---

# **5. Check the Git diff**

Before blaming Terraform:

```bash
git diff <last-known-good>...HEAD
```

Look for:

```text
resource rename
module path change
SKU
region
subnet ID
name
availability zone
identity model
count/for_each
provider constraints
```

A seemingly harmless refactor can produce replacement.

---

# **6. Resource rename/module move is a classic cause**

Old:

```hcl
resource "azurerm_storage_account" "app" {}
```

New:

```hcl
resource "azurerm_storage_account" "prod" {}
```

Terraform identity is based partly on resource address.

It may interpret:

```text
old address removed
+
new address added
```

as:

```text
destroy old
create new
```

even though you intended only a code rename.

---

# **7. Use a `moved` block for refactoring**

Correct:

```hcl
moved {
  from = azurerm_storage_account.app
  to   = azurerm_storage_account.prod
}
```

Terraform then changes the address association rather than destroying the Azure object.

HashiCorp specifically recommends `moved` blocks for renaming or moving resources/modules because without them Terraform commonly interprets a new address as destroy/recreate. ([HashiCorp Developer][6])

---

# **8. `count` and `for_each` changes can move identities unexpectedly**

Example:

```hcl
count = 3
```

resources:

```text
vm[0]
vm[1]
vm[2]
```

Changing list ordering can alter which logical instance Terraform associates with an index.

Similarly:

```hcl
for_each = {
  api = ...
  web = ...
}
```

If key changes:

```text
api → backend
```

Terraform may interpret:

```text
api removed
backend created
```

without a moved mapping.

This is why stable `for_each` keys matter.

---

# **9. Check provider changes**

Look at:

```text
required_providers
terraform.lock.hcl
```

and recent provider upgrades.

Maybe:

```text
azurerm 4.x.y
→ 4.x.z
```

changed:

```text
normalization
schema behavior
default handling
replacement semantics
```

I would inspect the provider changelog/documentation before approving an unexpected destructive plan.

In production I pin provider versions appropriately and upgrade them through deliberate PRs rather than letting every pipeline silently fetch a new incompatible behavior.

---

# **10. Check whether an immutable Azure property changed**

Some Azure resource properties simply cannot be modified in place.

Typical classes include things like:

```text
region/location
certain networking properties
resource names
specific creation-time options
```

depending on resource/service/provider.

If that property legitimately changed:

```text
replacement may be correct
```

The problem becomes:

> How do I perform that replacement safely?

not:

> How do I trick Terraform into avoiding it?

---

# **11. Check for drift**

Use:

```bash
terraform plan -refresh-only
```

to inspect whether Azure was changed outside Terraform. HashiCorp recommends refresh-only mode for examining drift without proposing infrastructure correction. ([HashiCorp Developer][1])

Perhaps someone manually changed a property Terraform cannot update back in place.

Then the normal plan legitimately proposes replacement to restore declared configuration.

I need to decide which side is desired.

---

# **12. Check you're targeting the correct Azure environment**

A surprisingly dangerous cause:

```text
wrong subscription
wrong tenant
wrong workspace
wrong backend state key
wrong tfvars
```

Check:

```bash
az account show
terraform workspace show
terraform state list
```

and backend/environment configuration.

Suppose code expects:

```text
prod subscription A
```

but credentials point to:

```text
subscription B
```

Terraform may conclude expected objects are missing and propose substantial changes.

Never approve destructive plans until environment identity is proven.

---

# **13. Check whether state was lost or wrong**

Suppose Azure SQL exists:

```text
sql-prod
```

but Terraform state no longer tracks it.

Configuration contains:

```text
resource "azurerm_mssql_server" "prod"
```

Terraform sees:

```text
configuration = wants resource
state = no resource
```

and may propose:

```text
+ create
```

Possibly Azure then rejects duplicate naming—or worse, Terraform creates a second resource if naming permits.

The correct action may be:

```text
import existing object
```

not recreate it.

Terraform supports import blocks/commands specifically for binding existing remote infrastructure to a Terraform resource address. ([HashiCorp Developer][5])

---

# **14. Check whether the same object is bound incorrectly**

Terraform expects one remote object to map to one resource address. Importing or manipulating state incorrectly can result in confusing behavior. ([HashiCorp Developer][5])

I would inspect:

```bash
terraform state list
terraform state show <address>
```

before changing state.

Never start randomly using:

```text
state rm
state mv
import
```

until you know the desired binding.

---

# **15. Understand blast radius**

If replacement is:

```text
diagnostic setting
```

impact may be small.

If replacement is:

```text
Production AKS
Azure SQL
VNet
Private Endpoint
Firewall
```

impact could be huge.

I ask:

```text
What depends on it?
What data lives there?
Does replacement change IP/FQDN?
Will downstream IDs change?
What other resources will Terraform replace?
```

Read the **entire plan**, not only the first scary resource.

---

# **16. Check dependent resource replacements**

One replacement can cascade.

Example:

```text
VNet replaced
 ↓
subnets replaced
 ↓
private endpoints replaced
 ↓
AKS networking impacted
```

The plan might say:

```text
1 resource must be replaced
```

at first glance, but downstream changes can create a much larger outage.

Trace dependencies.

---

# **17. If replacement is intentional, design it as migration**

Suppose new architecture genuinely needs a new production resource.

Instead of:

```text
Terraform destroys old
      ↓
creates new
```

prefer:

```text
Create replacement alongside old
      ↓
migrate/replicate
      ↓
validate
      ↓
switch traffic/dependencies
      ↓
remove old
```

when Azure service semantics allow it.

That's effectively blue-green infrastructure.

---

# **18. `create_before_destroy` can help—but isn't magic**

Terraform lifecycle can support:

```hcl
lifecycle {
  create_before_destroy = true
}
```

for resources where Terraform/provider/Azure constraints permit simultaneous old and new objects.

But it may fail if:

```text
resource name must be unique
IP conflicts
dependency can't have two instances
quota insufficient
service doesn't support parallel existence
```

So I don't blindly add `create_before_destroy` to every critical resource.

---

# **19. `prevent_destroy` is a useful guardrail**

For some critical Terraform resources:

```hcl
lifecycle {
  prevent_destroy = true
}
```

can cause Terraform to reject plans that would destroy the resource while that lifecycle rule remains configured.

Useful for:

```text
critical DB
production Key Vault
important shared resource
```

where appropriate.

But it doesn't explain **why** replacement appeared, and it shouldn't become a substitute for reviewing plans.

---

# **20. Backup before truly destructive replacement**

If a stateful resource really must be replaced:

```text
verify backup
verify restore
verify replication
define RTO/RPO
define rollback
```

before apply.

Example Azure SQL:

```text
Backup exists
```

is weaker evidence than:

```text
Restore tested successfully
```

for high-risk production operations.

---

# **21. Example scenario — module rename**

Plan:

```text
-/+ AKS cluster
```

Git diff reveals:

```text
module.aks
→
module.production_aks
```

No Azure cluster properties changed.

Cause:

```text
Terraform address changed
```

Correct fix:

```hcl
moved {
  from = module.aks
  to   = module.production_aks
}
```

Rerun plan.

Expected:

```text
No AKS destruction.
```

That's far safer than letting Terraform “recreate” a perfectly good cluster. ([HashiCorp Developer][6])

---

# **22. Example scenario — immutable property really changed**

Plan says:

```text
location:
eastus
→
centralindia
# forces replacement
```

That's not a state error.

Azure resources don't generally teleport between regions.

I would not apply this as an ordinary update.

Instead:

```text
Provision new regional environment
      ↓
replicate/migrate state
      ↓
test
      ↓
cut over
      ↓
retire old
```

That is a migration project.

---

## **Interview answer condensed**

> “If Terraform unexpectedly wants to recreate a Production resource, I stop and don't apply. I save the plan, identify the exact `forces replacement` attribute or resource-address change, and compare configuration, Terraform state and actual Azure. I also check recent Git, module and provider changes, `count`/`for_each` keys, the current subscription/workspace, and whether drift or missing state is involved. A code refactor might require a `moved` block; an existing resource missing from state might require import. If an immutable Azure property truly changed, replacement may be valid, but then I treat it as a controlled migration with backup, dependency analysis, parallel infrastructure where possible, validation and rollback—not an unexpected Terraform apply.”

**Memory line:**
**Unexpected `-/+` in Production means stop, identify why Terraform lost continuity with the existing object, and only then decide whether replacement is real.**

**Interview trap:**
A resource rename or module refactor can make Terraform propose **destroy/create even though nothing in Azure actually needs replacing**.

**Keywords:**
`forces replacement`, `-/+`, Terraform plan, state, drift, moved block, import, provider upgrade, immutable property, `create_before_destroy`, `prevent_destroy`.

**Likely follow-ups:**

* What is a `moved` block?
* When would you use import instead of a moved block?
* What would you inspect if replacement appeared after a provider upgrade?
* Would you simply use `create_before_destroy` on every production resource?
* How would you safely replace a stateful Azure resource?

# **T33-13. Terraform state becomes locked; how would you investigate it?**

**Answer:**

I would first assume the lock is protecting me from **concurrent state writers**, not that Terraform is broken.

I would read the lock information Terraform reports—especially the lock ID, operation, owner, and creation time—then check whether another pipeline or engineer is genuinely running `plan/apply` against the same backend.

If another operation is active, I wait or stop the duplicate job; I do **not** bypass the lock.

If the previous Terraform job crashed and I've positively confirmed that no process is still using the state, then I can consider `terraform force-unlock <LOCK_ID>`. HashiCorp explicitly warns that force-unlock should only be used for an abandoned lock, because unlocking an actively used state can create multiple simultaneous writers and corrupt state.

I would not solve the issue with:

```text
-lock=false
```

in Production.

The investigation is:

```text
Lock error
   ↓
Who owns lock?
   ↓
Active Terraform operation?
 /                    \
Yes                    No
 ↓                      ↓
Wait/coordinate    Confirm stale lock
                          ↓
                    force-unlock
                    correct LOCK_ID
                          ↓
                    re-run plan safely
```

Terraform automatically locks state for operations that can write it when the backend supports locking, specifically to prevent simultaneous writers and potential corruption. ([HashiCorp Developer][8])

---

## **1. Understand why state locking exists**

Imagine two pipelines.

Pipeline A reads state:

```text
VM count = 3
```

Pipeline B reads at the same time:

```text
VM count = 3
```

A changes:

```text
3 → 5
```

B changes:

```text
3 → 2
```

Both write state.

Without coordination:

```text
Which state wins?
```

You can create:

```text
lost updates
incorrect state
resource duplication
corruption
```

State locking serializes operations that could write state.

HashiCorp says Terraform automatically locks supported backends during state-writing operations and refuses to continue when it cannot obtain the lock. ([HashiCorp Developer][8])

---

# **2. A lock error is usually a safety mechanism**

Typical error contains information like:

```text
Error acquiring the state lock

Lock Info:
  ID:        abc-123...
  Path:      ...
  Operation: OperationTypeApply
  Who:       pipeline@runner
  Created:   ...
```

I capture this information.

Especially:

```text
Lock ID
Who
Created
Operation
```

These tell me whether the lock looks legitimate.

---

# **3. Check CI/CD first**

If Terraform normally runs through GitHub Actions or Azure DevOps:

```text
Pipeline
   ↓
Terraform
   ↓
same backend key
```

look for:

```text
active workflow
queued apply
previous run still executing
cancelled run
hung runner
```

A common scenario:

```text
Pipeline A still applying
Pipeline B started
```

Terraform correctly blocks Pipeline B.

Correct action:

```text
let A finish
```

not force-unlock A.

---

# **4. Check for human Terraform sessions**

Maybe an engineer is running locally:

```bash
terraform apply
```

against the same production backend.

Ask/check:

```text
Who field
deployment channel
team activity
```

If the engineer is still applying:

```text
do not unlock
```

Coordination is the fix.

---

# **5. Why simultaneous applies are dangerous**

Suppose A creates:

```text
Private Endpoint A
```

while B deletes:

```text
VNet subnet
```

Both plans were based on the same earlier state.

Even if Azure APIs reject some operations, Terraform's state may not cleanly reflect what happened.

The state lock protects the consistency of:

```text
Terraform's authoritative mapping
between configuration and remote resources.
```

---

# **6. If the process is active, wait**

Correct:

```text
Active apply
      ↓
wait
      ↓
automatic unlock
```

Terraform normally releases the lock when the operation completes.

If an operation takes a long time because Azure is still creating:

```text
AKS
Application Gateway
VPN Gateway
```

that isn't necessarily a stale lock.

These Azure resources can have long provisioning operations.

---

# **7. If the pipeline crashed, investigate whether the lock is stale**

Possible:

```text
runner terminated
network connection lost
Terraform process killed
CI job hard cancelled
```

Terraform may not have completed its normal unlock path.

Now I need to prove:

```text
No Terraform writer remains active
```

before forcing anything.

Check:

```text
CI runs
Terraform Cloud/HCP run if used
local processes/team activity
Azure resource operation status
```

The evidence threshold should be high for Production.

---

# **8. Use the exact Lock ID**

Once confirmed stale:

```bash
terraform force-unlock <LOCK_ID>
```

HashiCorp's `force-unlock` command removes the lock for the current configuration and requires the unique lock ID so you're targeting the intended lock. It does **not itself modify infrastructure**. ([HashiCorp Developer][9])

Example:

```bash
terraform force-unlock abc123...
```

Terraform asks for confirmation unless `-force` is used.

For Production, I generally want deliberate human confirmation.

---

# **9. Force-unlock is dangerous if someone still owns the lock**

Suppose:

```text
Pipeline A
still applying
```

You run:

```bash
terraform force-unlock
```

Then Pipeline B obtains lock and starts applying.

Now:

```text
A + B
```

both think they can write.

HashiCorp explicitly warns that force-unlock should only be used for **your own abandoned lock after automatic unlocking failed**, not to break a legitimate active lock. ([HashiCorp Developer][8])

---

# **10. Never casually use `-lock=false`**

Terraform supports disabling locking for some commands:

```bash
terraform apply -lock=false
```

But HashiCorp explicitly recommends against disabling locking. ([HashiCorp Developer][8])

In production, this is essentially saying:

> “I know another writer might exist, but please ignore the safety mechanism.”

That's usually the exact opposite of what I want.

---

# **11. AzureRM backend uses remote locking**

With an Azure Blob Storage backend, Terraform coordinates access to the remote state rather than relying on a local file.

Conceptually:

```text
Terraform client A ─┐
                    ├─→ Azure Blob state
Terraform client B ─┘
```

Locking allows only the appropriate operation to mutate the shared state at a time.

This is one major reason remote backends are important for teams.

---

# **12. State lock vs Azure resource lock**

Important distinction.

### Terraform state lock

```text
Protects Terraform state
from concurrent Terraform writers
```

### Azure resource lock

```text
CanNotDelete / ReadOnly
protects Azure resource operations
```

They have nothing to do with each other.

If Terraform says:

```text
Error acquiring state lock
```

checking an Azure `CanNotDelete` resource lock on the VM is irrelevant.

---

# **13. Lock contention can reveal bad pipeline architecture**

Suppose every hour:

```text
50 teams
```

fight for one lock.

Maybe the real issue is:

```text
one giant enterprise tfstate
```

containing:

```text
Network
AKS
SQL
50 teams
12 subscriptions
```

Even if Terraform locking works, all deployments are serialized.

Better state boundaries:

```text
platform-network.tfstate
team-a-prod.tfstate
team-b-prod.tfstate
...
```

aligned with independent ownership/lifecycles.

Frequent lock contention can therefore indicate poor Terraform state design.

---

# **14. Add CI concurrency controls**

State locking is the last safety boundary.

I would also prevent two production applies for the same state from being launched simultaneously.

For example conceptually:

```text
Concurrency group:
terraform-payments-prod
```

Then:

```text
Run A active
Run B waits
```

before Terraform even reaches the backend lock.

This improves developer experience and reduces accidental contention.

---

# **15. Use `-lock-timeout` for short legitimate contention**

If short overlaps are normal:

```bash
terraform plan -lock-timeout=5m
```

or apply with an appropriate lock timeout.

Instead of failing immediately:

```text
Terraform waits
for lock to become available
```

This can help when another short operation is finishing.

But don't set:

```text
infinite waiting
```

and hide genuinely stuck pipelines.

---

# **16. What if the lock appears stale but Azure is still provisioning?**

Example:

Pipeline crashed after asking Azure to create:

```text
Application Gateway
```

Terraform process is gone.

State lock is stale.

Azure operation may still continue.

After force-unlock, I would **not immediately apply again**.

First:

```text
check Azure actual state
```

Then run:

```bash
terraform plan
```

Terraform refreshes the resource view.

Maybe Azure finished successfully even though the pipeline died.

That plan tells me what Terraform believes needs reconciliation.

---

# **17. Run a normal plan after unlocking**

After stale lock removal:

```bash
terraform plan
```

before apply.

Why?

A crashed operation may have produced partial infrastructure:

```text
Resource A created
Resource B created
Resource C failed
```

A new plan can refresh Azure reality and show:

```text
what remains
```

Never assume:

```text
failed pipeline
=
nothing changed
```

---

# **18. Don't manually delete the state blob**

Terrible fix:

```text
State locked
      ↓
Delete tfstate blob
```

That destroys Terraform's tracking information and can lead to:

```text
Terraform thinks resources don't exist
→ proposes recreations
```

Potentially catastrophic.

Likewise, don't randomly manipulate the backend lease outside Terraform unless you fully understand the backend and have an exceptional recovery situation.

`terraform force-unlock` exists for the supported stale-lock workflow.

---

# **19. Troubleshooting dependency order**

I would structure it:

```text
Terraform error
   ↓
Read lock metadata
   ↓
Is same backend/state key correct?
   ↓
Is another CI/local run active?
   ↓
If active → coordinate/wait
   ↓
If inactive → confirm stale
   ↓
force-unlock exact lock ID
   ↓
terraform plan
   ↓
review partial state
   ↓
apply only if safe
```

This preserves the safety model.

---

# **20. Example production incident**

Pipeline A:

```text
22:00 terraform apply
```

creates:

```text
Private Endpoint
NSG rule
AKS node pool update
```

Runner crashes at:

```text
22:08
```

Pipeline B at:

```text
22:10
```

fails:

```text
Error acquiring the state lock
```

I would:

```text
1. Capture lock ID
2. Check Pipeline A status
3. Confirm runner/process is dead
4. Verify nobody else is using state
5. Inspect Azure operations/resources
6. terraform force-unlock <ID>
7. terraform plan
8. Review what Pipeline A already changed
9. Apply only remaining expected changes
```

I would **not**:

```text
terraform apply -lock=false
```

and hope for the best.

---

# **21. Prevent recurrence**

If crash happened because:

```text
runner unreliable
```

fix the runner.

If two workflows started simultaneously:

```text
add deployment concurrency
```

If contention happens daily:

```text
split state by lifecycle/team
```

If engineers run Prod locally:

```text
move writes to controlled CI/CD
```

The stale lock is the symptom; workflow design may be the root cause.

### **Interview answer condensed**

> “A Terraform state lock is normally protecting the state from concurrent writers, so I wouldn't bypass it immediately. I'd inspect the reported lock ID, operation, owner and timestamp and check CI pipelines and engineers to see whether another Terraform operation against the same backend is genuinely active. If it is, I wait or coordinate with that owner. If the previous job crashed and I've confirmed there is no active writer, I can use `terraform force-unlock <LOCK_ID>` for that specific stale lock. I would never casually use `-lock=false` in Production. After unlocking a crashed run, I'd run a fresh plan because Azure might contain partially applied changes even though the pipeline failed. If lock contention happens frequently, I'd also review pipeline concurrency and whether our Terraform state boundaries are too large.”

**Memory line:**
**A state lock is a safety feature: prove it is abandoned before removing it.**

**Interview trap:**
Never force-unlock a state simply because you want your deployment to run—if another Terraform process is still active, you can create **multiple state writers and corrupt your infrastructure state**.
