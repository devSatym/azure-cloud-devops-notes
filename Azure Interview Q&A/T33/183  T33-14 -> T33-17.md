# **T33-14. A pipeline accidentally destroyed a production resource; how would you prevent this from happening again?**

**Answer:**

First I would restore service and understand exactly **why the pipeline was capable of destroying that resource**. Then I would fix the failure at several layers rather than adding one safeguard.

For Production, I would separate the deployment identity from developer identities, give it only the permissions and scope it needs, require PR review plus a reviewed Terraform plan before apply, and put an explicit approval gate in front of Production.

For critical stateful resources such as databases, Storage Accounts, Key Vaults, or shared network infrastructure, I would consider Terraform `prevent_destroy` and Azure `CanNotDelete` locks. I would also separate Production Terraform state from nonproduction, validate the subscription and state backend before every apply, use Azure Policy where organization-wide delete controls make sense, and ensure backups or native recovery features exist.

The important principle is:

> **A single human mistake, pipeline bug, or bad Terraform change should have to cross multiple independent safety boundaries before it can destroy critical Production infrastructure.**

```text
Bad change
   ↓
PR review
   ↓
Terraform plan review
   ↓
Production approval
   ↓
Least-privilege pipeline identity
   ↓
Azure Policy / Resource lock
   ↓
Terraform lifecycle protection
   ↓
Critical Production resource
```

---

## **1. First investigate how the deletion happened**

Before designing prevention, I would establish the exact failure path.

For example:

```text
Developer PR
    ↓
Terraform code removed resource
    ↓
PR merged
    ↓
Pipeline auto-approved apply
    ↓
Production SQL deleted
```

Or maybe:

```text
Pipeline expected Dev state
       ↓
wrong backend/state key
       ↓
Production resources appeared unwanted
       ↓
Terraform destroyed them
```

Those need different fixes.

I would review:

* pipeline logs,
* Terraform plan,
* Azure Activity Log,
* Git commit/PR,
* deployment identity,
* Terraform backend/state key,
* subscription ID,
* approval history.

I want a precise root cause such as:

> “The Production pipeline automatically applied a plan containing a delete, and the pipeline identity had unrestricted Contributor access.”

not:

> “Terraform deleted it.”

---

# **2. Never auto-apply destructive Production changes blindly**

A strong workflow is:

```text
Pull Request
    ↓
terraform fmt
    ↓
terraform validate
    ↓
security/policy checks
    ↓
terraform plan
    ↓
Human reviews actual plan
    ↓
Production approval
    ↓
terraform apply
```

Reviewer should explicitly notice actions such as:

```text
- destroy

-/+ replace
```

For critical systems, I might make the pipeline fail automatically when the plan contains unexpected destruction unless a separate approved exception exists.

For example:

```text
Plan contains:
- production database

      ↓

BLOCK deployment
```

rather than:

```text
terraform apply -auto-approve
```

continuing automatically.

---

# **3. Apply the exact reviewed change**

A subtle problem:

```text
09:00 terraform plan
09:05 reviewer approves
09:10 another commit merges
09:15 pipeline runs a NEW plan and applies it
```

The reviewer may not have reviewed what was actually applied.

A stronger workflow ties approval to:

```text
specific Git commit
+
specific Terraform plan
```

and prevents the code from changing underneath the reviewed deployment.

---

# **4. Protect the Production branch**

Production infrastructure code should require:

```text
feature branch
      ↓
Pull Request
      ↓
Required reviewers
      ↓
Required CI checks
      ↓
Merge
```

not:

```text
developer
→ direct push to main
→ production apply
```

GitHub branch protections can require PR approval, status checks, Code Owner review, and can restrict bypass behavior. GitHub can also dismiss previous approvals when new commits change the reviewed code. ([GitHub Docs][1])

That prevents:

```text
approved safe code
      ↓
new dangerous commit
      ↓
old approval still treated as sufficient
```

when configured correctly.

---

# **5. Add an independent Production deployment approval**

Code review and deployment approval solve different problems.

```text
Code review:
"Is this Terraform change correct?"

Deployment approval:
"Is now the right time to execute it in Prod?"
```

A GitHub Production Environment can require a reviewer before the deployment job proceeds, and can prevent self-review when configured accordingly. ([GitHub Docs][2])

So:

```text
PR approved
     ↓
merged
     ↓
plan ready
     ↓
Production Environment approval
     ↓
apply
```

gives a second boundary.

---

# **6. Separate Production identity**

Avoid:

```text
same service principal
→ Dev
→ Stage
→ Prod
```

Use:

```text
tf-dev
→ Dev subscription

tf-stage
→ Stage subscription

tf-prod
→ only required Prod scope
```

Then a compromised or incorrectly configured Dev pipeline cannot simply destroy Production.

Authentication should preferably use:

```text
GitHub Actions
      ↓
OIDC federation
      ↓
Microsoft Entra
      ↓
short-lived token
```

rather than storing a long-lived Azure client secret.

---

# **7. Reduce deployment identity permissions**

Don't solve every deployment failure with:

```text
Pipeline identity
→ Owner on subscription
```

Ask what Terraform actually manages.

For example:

```text
Application RG
   ↓
Contributor
```

may be enough.

If some infrastructure requires extra permissions, either:

* use a narrowly scoped custom role,
* separate those operations into a privileged platform pipeline,
* or grant additional privilege only at the required scope.

Blast radius matters:

```text
Contributor at one RG
```

is dramatically safer than:

```text
Owner at Management Group
```

---

# **8. Use Terraform `prevent_destroy` for critical objects**

For an important resource:

```hcl
resource "azurerm_storage_account" "critical" {
  # ...

  lifecycle {
    prevent_destroy = true
  }
}
```

If Terraform produces a plan that would destroy it:

```text
Terraform
   ↓
ERROR
   ↓
apply stops
```

HashiCorp specifically recommends `prevent_destroy` as protection for resources whose accidental deletion or replacement would be costly. ([HashiCorp Developer][3])

Good candidates might include:

```text
critical database
production Key Vault
important Storage Account
central network resource
```

depending on lifecycle requirements.

---

# **9. Understand the `prevent_destroy` limitation**

This is important.

`prevent_destroy` exists inside the resource configuration.

If someone removes the **entire resource block**, that lifecycle rule disappears with it, so it isn't an absolute Azure-side deletion control. HashiCorp explicitly documents this caveat. ([HashiCorp Developer][4])

So:

```text
prevent_destroy
```

is one safety layer.

It is not the only layer.

---

# **10. Add Azure `CanNotDelete` locks for selected critical resources**

Azure supports:

```text
CanNotDelete
```

and:

```text
ReadOnly
```

management locks.

For a critical stateful resource, `CanNotDelete` is often more practical:

```text
Read
✓

Modify
✓

Delete
X
```

Microsoft states that management locks apply across authorized users/roles and can protect resources against accidental deletion. ([Microsoft Learn][5])

Example:

```bash
az lock create \
  --name protect-prod-db \
  --lock-type CanNotDelete \
  --resource-group rg-prod \
  --resource-name sql-prod \
  --resource-type Microsoft.Sql/servers
```

---

# **11. Why I wouldn't put `ReadOnly` everywhere**

`ReadOnly` means:

```text
modify
X
delete
X
```

which can also break legitimate production operations and pipelines.

Microsoft documents several cases where ReadOnly locks interfere with operations that internally use ARM `POST`, including operational actions that may not initially look like writes. ([Microsoft Learn][5])

So I'd normally use locks **surgically**, not apply ReadOnly to the whole Production subscription without understanding the consequences.

---

# **12. A resource lock also blocks the pipeline**

This is important:

```text
CanNotDelete
```

does not mean:

```text
Humans cannot delete
but Terraform can.
```

The management lock is independent of normal RBAC and applies to the relevant control-plane operation regardless of whether the caller is an engineer or the deployment identity. ([Microsoft Learn][5])

That can be desirable.

For intentional deletion:

```text
approved change
     ↓
privileged process removes lock
     ↓
delete resource
     ↓
audit
```

Now deletion requires a deliberate extra step.

---

# **13. Azure Policy can provide organization-wide protection**

Current Azure Policy has a `denyAction` effect whose supported action is currently:

```text
DELETE
```

An applicable delete request receives:

```text
403 Forbidden
```

when policy blocks it. ([Microsoft Learn][6])

This can provide a scalable guardrail for certain critical resource classes.

Example conceptually:

```text
Production resources
tagged:
DeletionProtection = true
       ↓
Policy
       ↓
DELETE denied
```

However, I would design policy exceptions and operational processes carefully.

---

# **14. Separate Terraform state**

Never:

```text
Dev + Stage + Prod
        ↓
one giant tfstate
```

if they can be independently managed.

Prefer:

```text
dev.tfstate

stage.tfstate

prod.tfstate
```

and often more granular boundaries by workload.

Then:

```text
bad Dev apply
```

cannot destroy Prod because Prod resources aren't part of that state.

---

# **15. Validate environment before every Production apply**

Before apply I would print and validate:

```text
Tenant
Subscription
Terraform workspace/root
Backend state key
Git commit
Environment
```

For example:

```bash
az account show \
  --query '{subscription:name,id:id,tenant:tenantId}' \
  -o table
```

If expected Prod subscription is:

```text
1111...
```

but command reports:

```text
2222...
```

pipeline stops.

That tiny preflight check can prevent very expensive mistakes.

---

# **16. Don't rely on `terraform destroy` availability in normal Prod pipelines**

A standard application deployment workflow usually doesn't need to run:

```bash
terraform destroy
```

at all.

Decommissioning should be a separate, deliberately controlled process.

For example:

```text
Normal Prod deployment pipeline
→ plan/apply only

Decommission workflow
→ separate approval
→ separate privileged operation
```

This reduces accidental execution paths.

---

# **17. Recovery still matters**

Prevention will never be perfect.

For critical data I also want:

```text
backups
point-in-time restore
soft delete
versioning
geo-replication where needed
```

according to service and business RPO/RTO.

A database deletion protection rule is excellent.

A **tested restore procedure** is still necessary.

---

## **Production example**

Assume a pipeline accidentally deleted a Production Storage Account because its Terraform resource block was removed.

My corrective actions could be:

```text
1. Restore/recover data if possible
2. Preserve pipeline and Activity Log evidence
3. Identify removed Terraform change
4. Require protected PRs/CODEOWNERS
5. Require reviewed Prod plan
6. Add Prod Environment approval
7. Separate Prod identity and state
8. Add prevent_destroy
9. Add CanNotDelete lock
10. Validate backups/soft delete
11. Alert on unexpected Prod DELETE operations
```

Notice that no single mechanism is trusted completely.

---

### **Interview answer condensed**

> “I would first restore service and determine exactly why the pipeline could delete the resource. Then I'd add multiple independent controls. Production infrastructure changes would require a reviewed PR, a reviewed Terraform plan, and a separate Production approval. The Prod pipeline would use its own least-privilege OIDC identity and separate Terraform state. For critical stateful resources I'd consider Terraform `prevent_destroy`, and Azure `CanNotDelete` locks or policy-based deletion protection where appropriate. I'd also validate the tenant, subscription and backend before every apply, separate decommissioning from normal deployment workflows, monitor DELETE operations, and maintain tested backups. The goal is that one bad commit or pipeline mistake cannot directly destroy a critical production dependency.”

**Memory line:**
**Prevent destructive mistakes with layers: review → approval → least privilege → state isolation → deletion protection → recoverability.**

**Interview trap:**
`prevent_destroy` is useful but **not absolute protection**—if the resource block containing it is removed, the lifecycle rule is removed too.

**Keywords:**
`prevent_destroy`, `CanNotDelete`, Azure Policy `denyAction`, Terraform plan, Production approval, least privilege, state isolation, backups.

**Likely follow-ups:**

* What's the difference between `prevent_destroy` and an Azure resource lock?
* Would `CanNotDelete` also block Terraform?
* Why wouldn't you put a ReadOnly lock on the entire Production subscription?
* How would you safely perform an intentional deletion later?
* How could the wrong Terraform state backend cause accidental deletion?

# **T33-15. How would you ensure infrastructure changes receive peer review?**

**Answer:**

I would make Git the mandatory entry point for infrastructure changes and prevent direct changes to the protected branch.

Every Terraform or Bicep change would be submitted through a pull request. Branch protection would require at least one or more independent approvals, required automated checks, and Code Owner review for sensitive areas such as networking, IAM, or production modules.

For Terraform specifically, CI would generate the plan inside the PR so reviewers see **the actual infrastructure impact**, not just the `.tf` diff. Production apply would only occur from the protected branch after the required reviews, and the deployment itself could have another environment approval.

The key distinction is:

```text
Code review:
"Is the infrastructure definition correct?"

Plan review:
"What will Terraform actually do?"

Deployment approval:
"Should this approved change run in Production now?"
```

I want all three for high-risk Production changes.

---

## **1. Block direct changes to the production branch**

Bad:

```text
Engineer
   ↓
git push main
   ↓
Terraform apply
```

Better:

```text
Feature branch
      ↓
Pull Request
      ↓
Peer review
      ↓
Required checks
      ↓
Merge
```

GitHub branch protection can require PR reviews and prevent merging until the required approvals are present. ([GitHub Docs][1])

---

# **2. Use CODEOWNERS for high-risk infrastructure**

Example:

```text
/networking/   @platform-network-team
/iam/          @security-team
/modules/aks/  @platform-team
/prod/         @prod-infra-owners
```

Then changing:

```text
prod/network.tf
```

requires someone responsible for that area to review it.

GitHub branch protection supports requiring Code Owner review before a protected branch can merge. ([GitHub Docs][7])

This gives better review than:

```text
any developer
→ approve anything
```

---

# **3. Require automated checks before human review/merge**

For Terraform:

```text
terraform fmt -check
terraform validate
terraform plan
```

plus relevant:

```text
IaC security scanning
policy-as-code
linting
unit/module tests
```

The review becomes:

```text
Human reasoning
+
automated verification
```

instead of asking reviewers to spot every syntax/security issue manually.

---

# **4. Put the Terraform plan in the PR workflow**

A `.tf` diff might look harmless:

```hcl
subnet_id = var.new_subnet
```

but the plan might show:

```text
-/+ azurerm_private_endpoint.prod
```

or even:

```text
-/+ azurerm_kubernetes_cluster.prod
```

Therefore reviewers should see:

```text
Plan:
12 to add
4 to change
1 to destroy
```

plus important resource-level changes.

Peer review should evaluate **consequences**, not merely text changes.

---

# **5. Highlight destructive operations**

For Production, pipeline can detect:

```text
- destroy
-/+ replace
```

and require:

```text
additional approval
```

or fail completely for protected resource classes.

Example:

```text
Plan:
- azurerm_mssql_server.prod
```

should be visually impossible to miss.

---

# **6. Dismiss approvals if the code changes**

Suppose reviewer approves commit:

```text
A
```

Then author adds commit:

```text
B
```

that modifies the Terraform.

The old approval should not necessarily remain sufficient.

GitHub can dismiss stale approvals when new commits are pushed and can require review of the latest change. ([GitHub Docs][7])

Otherwise:

```text
safe code reviewed
      ↓
dangerous code added
      ↓
old approval reused
```

weakens peer review.

---

# **7. Prevent self-approval**

The person who wrote the Production infrastructure change should generally not be the sole person approving it.

Conceptually:

```text
Author
  ≠
Approver
```

For deployment environments, GitHub supports preventing self-review when required-reviewer protection is enabled. ([GitHub Docs][2])

The same separation-of-duties principle should guide code review.

---

# **8. Restrict bypass capability**

Branch rules become meaningless if:

```text
20 developers
→ can bypass them
```

I would tightly control:

```text
admin bypass
force push
branch deletion
direct push
```

and make bypass exceptional and auditable.

GitHub branch protection supports restricting who can push and controlling bypass behavior. ([GitHub Docs][1])

---

# **9. Separate peer review from production approval**

Imagine:

```text
Monday:
Terraform change reviewed

Friday:
Production deployment
```

The code may still be correct, but Friday may be during:

```text
major sales event
ongoing incident
change freeze
```

So production deployment might require an additional approval:

```text
Merged main
     ↓
Production environment
     ↓
Ops/change approval
     ↓
apply
```

GitHub environments support required reviewers for jobs referencing protected environments. ([GitHub Docs][2])

---

# **10. Apply only from trusted branches**

The production identity should not be usable from:

```text
feature/*
random fork
developer laptop
```

Ideally:

```text
protected main
+
Production environment
+
OIDC federation
```

is the trusted path.

That ties cloud authorization to repository governance.

---

# **11. Review scope should match the risk**

A tag change:

```text
CostCenter=A
→ CostCenter=B
```

does not need the same process as:

```text
Replace Production SQL
```

For high-risk infrastructure I may require:

```text
2 reviewers
+
platform owner
+
security/network owner
+
change approval
```

depending on organizational requirements.

Review should be risk-based, not bureaucracy for its own sake.

---

# **12. Azure DevOps equivalent**

With Azure DevOps, I would use the same model:

```text
Azure Repos branch policies
        ↓
PR reviewers
        ↓
build validation
        ↓
protected environment/checks
        ↓
Production deployment
```

The implementation differs, but the principles remain:

```text
no direct Prod branch writes
+
independent approval
+
automated checks
+
auditable deployment
```

# **13. Emergency changes still need reconciliation**

During an incident, someone might use PIM and make a critical temporary change.

After stabilization:

```text
manual emergency change
       ↓
convert into Terraform/Bicep
       ↓
PR
       ↓
review
       ↓
reconcile state
```

Otherwise the next IaC deployment may unexpectedly undo it.

## **Example**

Developer changes:

```hcl
public_network_access_enabled = true
```

for Production SQL.

Workflow:

```text
PR
 ↓
Terraform plan
 ↓
Security policy check FAIL
```

or CODEOWNER notices:

```text

```

and rejects it.

The unsafe configuration never reaches Azure.

That's peer review providing real risk reduction.

### **Interview answer condensed**

> “I would require every infrastructure change to go through a protected Git pull request. Direct pushes to the production branch would be disabled, and sensitive paths such as networking, IAM and Prod modules would require Code Owner review. CI would run formatting, validation, security checks and, importantly, generate the Terraform plan so reviewers see what Azure resources will actually be created, changed, replaced or destroyed. **Review the IaC code, review what the plan will actually do, then separately approve execution in Production.**

# **T33-16. A service-principal secret has been committed to Git; what are your immediate actions?**

**Answer:**

I would treat the secret as **compromised immediately**, even if the repository is private and even if we think nobody has used it.

My first priority is containment: identify the service principal and its permissions, revoke the exposed credential at Microsoft Entra ID, and replace it if the dependent system still requires one. If the credential is highly privileged or compromise is suspected, I would consider disabling the service principal or temporarily removing its permissions while investigating.

Next I would update affected applications or pipelines using a secure replacement, check Microsoft Entra service-principal sign-in logs and Azure Activity/resource logs for suspicious use during the exposure window, and investigate whether the identity could have accessed additional credentials or resources.

Only after revocation would I focus on cleaning the Git repository and history. Removing the line from the latest commit is **not remediation**, because the secret can remain in previous Git history, clones, logs, caches, or forks.

Longer term, I would redesign away from the secret entirely using Managed Identity or OIDC/Workload Identity Federation and enable secret scanning/push protection.

```text
Secret discovered in Git
        ↓
Assume compromised
        ↓
Identify identity + privilege
        ↓
REVOKE credential
        ↓
Contain identity if necessary
        ↓
Replace/redeploy
        ↓
Investigate usage
        ↓
Clean Git/history
        ↓
Prevent recurrence
```

GitHub explicitly says that when a credential is exposed, the first remediation priority is to revoke or rotate it; merely removing it from the code or repository does not prevent exploitation. ([GitHub Docs][8])

---

## **1. Identify exactly what leaked**

I need:

```text
Service principal/app ID
Credential ID if available
Tenant
Credential expiry
Repository
Commit
First exposure time
Public/private repo
Branches/tags/forks
```

Most importantly:

```text
What permissions does this identity have?
```

There is a huge difference between:

```text
AcrPush
on one registry
```

and:

```text
Owner
on Production subscription
```

The latter potentially allows broad resource management and role assignment.

---

# **2. Revoke before cleaning Git**

Bad order:

```text
1. Rewrite Git history for 40 minutes
2. Revoke secret later
```

During those 40 minutes:

```text
credential remains valid
```

Correct order:

```text
Credential
      ↓
REVOKE / DISABLE
      ↓
then clean repository
```

GitHub explicitly calls revocation the most important remediation step. ([GitHub Docs][9])

---

# **3. Remove the exposed credential from Entra**

For the affected application registration:

```text
Microsoft Entra ID
  ↓
App registrations
  ↓
Application
  ↓
Certificates & secrets
  ↓
remove compromised secret
```

Microsoft's security guidance recommends removing unnecessary/compromised application credentials, because an exposed client secret allows an attacker to authenticate as that application with whatever permissions it possesses. ([Microsoft Learn][10])

Once removed:

```text
that secret
→ cannot obtain new tokens
```

---

# **4. For high-risk compromise, disable the service principal**

Suppose leaked identity has:

```text
Owner on Prod
```

and repository was publicly accessible for two hours.

I might prefer:

```text
service principal
accountEnabled = false
```

during containment.

Microsoft supports disabling service-principal sign-in by setting `accountEnabled` to `false`, which prevents future authentication attempts in that tenant. ([Microsoft Learn][11])

Then:

```text
investigate
+
replace identity/credential
+
restore only after confidence
```

rather than keeping a highly privileged identity active.

---

# **5. Existing access tokens are an important nuance**

Removing the client secret stops the attacker from using that credential to request **new** access tokens.

However, you should not assume every already-issued access token instantly disappears.

Microsoft documents that when applications are deactivated, new token issuance is blocked while existing access tokens can remain valid until their configured lifetime expires; Continuous Access Evaluation can improve revocation behavior for supported workload/resource combinations, but it should not be assumed universally. ([Microsoft Learn][12])

Therefore during a high-risk compromise I also consider:

```text
disable identity
remove/reduce role assignments
monitor resource access
contain affected resources
```

as appropriate.

---

# **6. Replace the credential carefully if the application depends on it**

If Production currently uses the compromised secret:

```text
Delete immediately
      ↓
Production authentication fails
```

Security containment may still justify that outage if exposure is severe.

But if controlled rotation is possible:

```text
Create replacement
      ↓
store securely
      ↓
deploy application
      ↓
verify new credential works
      ↓
remove compromised credential
```

Normally rotation allows overlap—but **a known-compromised credential should remain valid for the shortest possible time**.

Microsoft documents this overlapping-credential pattern for ordinary rotations. ([Microsoft Learn][13])

---

# **7. Investigate the exposure window**

Suppose secret entered Git at:

```text
10:17
```

and was revoked:

```text
12:04
```

My investigation window begins no later than:

```text
10:17
```

and possibly earlier if I cannot prove when exposure began.

Check:

```text
Microsoft Entra
→ Service principal sign-ins

Azure Activity Log
→ management operations

Resource logs
→ Storage/Key Vault/SQL etc.

GitHub audit/security events
→ repo exposure
```

I'm looking for:

```text
unknown IPs
unusual geographies
new token activity
unexpected resource reads/writes
role assignments
new credentials
resource deletion
Key Vault access
data exfiltration indicators
```

---

# **8. If the SP had Key Vault access, expand the incident**

Suppose leaked identity had:

```text
Key Vault Secrets User
```

and could retrieve:

```text
DB password
payment API key
third-party credential
```

Then rotating only the service-principal secret may be insufficient.

The attacker might already have obtained those other secrets.

I would determine what it could read during the exposure window and potentially rotate:

```text
downstream credentials
```

as well.

This is **blast-radius analysis**.

---

# **9. If the SP had privileged RBAC, look for persistence**

Suppose it had:

```text
Owner
```

An attacker could potentially create:

```text
new role assignments
new managed identity
new service principal access
new infrastructure
```

depending on accessible operations.

Therefore I would inspect:

```text
Azure Activity Log
IAM changes
new role assignments
new app credentials
policy/network changes
```

not merely look for obvious resource deletion.

A sophisticated attacker may prefer persistence over destruction.

---

# **10. Clean the repository after containment**

Then remove the secret from:

```text
current source
Git history where necessary
open PR refs
tags
cached artifacts
CI logs if leaked there
documentation
```

GitHub warns that history rewriting can be complicated because old clones/forks can reintroduce the secret, and emphasizes that rotation/revocation comes first. ([GitHub Docs][8])

Once revoked, the exposed text remaining temporarily in history is much less dangerous because it is no longer a valid credential.

---

# **11. Don't think deleting the repository solves it**

GitHub explicitly notes that:

```text
remove secret from code
push new commit
delete/recreate repository
```

does not itself make the exposed credential safe. ([GitHub Docs][9])

The credential provider—Microsoft Entra in this case—is where the credential must be revoked.

---

# **12. Replace secrets with secretless authentication**

Ask:

> Why did this pipeline/application need a service-principal secret at all?

For GitHub Actions:

```text
GitHub OIDC
     ↓
Microsoft Entra federated identity
     ↓
short-lived token
```

For Azure-hosted workloads:

```text
Managed Identity
```

For AKS:

```text
Workload Identity
```

Microsoft currently recommends moving production workloads away from client secrets toward managed identities or federated authentication where possible. ([Microsoft Learn][13])

Then there is no long-lived secret available to commit.

---

# **13. Enable secret scanning and push protection**

GitHub push protection can detect supported credential patterns and block a push before the secret enters repository history. ([GitHub Docs][14])

Layer the controls:

```text
Developer machine
→ pre-commit secret scan

Git push
→ push protection

Repository
→ secret scanning

CI
→ security scanning
```

Prevention is much cheaper than incident response.

---

## **Practical incident sequence**

```text
1. Secret discovered
2. Alert security/application owner
3. Identify service principal and permissions
4. Revoke compromised credential immediately
5. Disable SP/remove privilege if risk warrants
6. Provision secure replacement if needed
7. Redeploy dependent service
8. Verify production authentication
9. Search Entra/Azure logs for misuse
10. Rotate downstream credentials if exposure possible
11. Remove secret from Git/history/artifacts
12. Enable secret scanning/push protection
13. Migrate to OIDC/Managed Identity
14. Document incident and corrective actions
```

---

### **Interview answer condensed**

> “I would assume the committed service-principal secret is compromised. First I'd identify the service principal, its Azure scope and the exposure window, then immediately revoke the credential in Entra. If the identity is highly privileged or suspicious use is possible, I'd disable the service principal or reduce its access while investigating. I'd replace and redeploy the affected workload if it still depends on a credential, then review service-principal sign-ins, Activity Logs and relevant resource logs for unauthorized activity. If that identity could access Key Vault or assign roles, I'd expand the investigation for downstream credential theft or persistence. Only after revocation would I clean Git history. Finally I'd remove the root cause by moving CI to OIDC or Azure workloads to Managed/Workload Identity and enabling secret scanning and push protection.”

**Memory line:**
**A secret in Git is compromised: revoke first, investigate second, clean history third, eliminate the secret long-term.**

**Interview trap:**
Deleting the secret from the latest Git commit **does not revoke it**; it can still exist in history, clones, forks, caches—and remain fully usable until the credential provider invalidates it.

**Keywords:**
credential compromise, service principal, revoke, rotate, Entra sign-in logs, Activity Log, blast radius, OIDC, Managed Identity, secret scanning.

**Likely follow-ups:**

* Would you rotate first or rewrite Git history first?
* What if the leaked service principal had Owner access?
* What if it could read Key Vault secrets?
* Does deleting the client secret instantly invalidate every already-issued token?
* How would OIDC prevent this class of incident?

# **T33-17. A developer requests Owner access to production because their deployment is failing; what would you do?**

**Answer:**

I would **not grant Owner simply to make the deployment work**.

I would first identify the exact failure and determine whether it is authentication, authorization, policy, networking, quota, or an application problem. If it's an Azure RBAC failure, I would identify the specific missing action and grant the smallest appropriate role at the narrowest scope—preferably to the deployment identity rather than the developer.

For example, a pipeline pushing images may need `AcrPush`; an application reading blobs may need `Storage Blob Data Reader`; Terraform creating normal resources may need Contributor at a particular resource group. If Terraform truly needs to create Azure role assignments, Contributor is intentionally insufficient, so I would design a dedicated privileged deployment path using an appropriate RBAC-management role and conditions where possible rather than making the developer subscription Owner.

If a human needs temporary elevated access during an incident, I would use Microsoft Entra PIM with time-limited activation, MFA, justification and approval where appropriate.

The rule is:

```text
Deployment failing
      ↓
Find required permission
      ↓
Grant exact permission
at exact scope
      ↓
Fix deployment identity

NOT:

Deployment failing
      ↓
Make developer Owner
```

Owner grants full resource-management access **including Azure RBAC role assignment capability**, while Contributor can manage resources but cannot assign Azure roles. ([Microsoft Learn][15])

---

## **1. Ask for the actual error, not more privilege**

First question:

> What is the exact deployment error?

Examples:

```text
401
→ authentication

403 AuthorizationFailed
→ authorization/policy

Timeout
→ network/service connectivity

QuotaExceeded
→ capacity/quota

Policy violation
→ governance
```

Owner access only potentially addresses some authorization failures.

It does nothing for:

```text
DNS
Private Endpoint
bad Terraform
quota
application bug
```

Granting Owner before diagnosis can both increase risk and fail to solve the problem.

---

# **2. Identify which identity is actually failing**

Maybe:

```text
Developer personal account
```

works.

But:

```text
GitHub Actions service principal
```

fails.

Granting Owner to the developer would change nothing.

Deployment flow might be:

```text
Developer
   ↓
Git push
   ↓
GitHub Actions
   ↓
OIDC
   ↓
service principal / managed identity
   ↓
Azure
```

The identity Azure evaluates is:

```text
pipeline identity
```

not necessarily the developer.

---

# **3. Verify pipeline Azure context**

For example:

```bash
az account show \
  --query '{subscription:name,id:id,tenant:tenantId}' \
  -o table
```

This proves:

```text
Which tenant?
Which subscription?
```

A deployment might be failing because it authenticated successfully to:

```text
wrong subscription
```

not because it needs Owner.

---

# **4. For 403, identify the denied operation**

Azure errors commonly include something like:

```text
The client '<id>'
does not have authorization to perform action:

Microsoft.Network/virtualNetworks/write

over scope:
...
```

That is extremely valuable evidence.

I extract:

```text
Principal
Action
Scope
```

Then ask:

> Which role grants that action with the least additional privilege?

---

# **5. Inspect existing RBAC**

For the deployment identity:

```bash
az role assignment list \
  --assignee <principal-id> \
  --all \
  --output table
```

I check:

```text
Role
Scope
Inheritance
```

Maybe it has:

```text
Contributor
→ rg-dev
```

but pipeline is deploying to:

```text
rg-prod
```

Then the issue is scope.

Not role power.

---

# **6. Scope matters as much as role**

These are drastically different:

```text
Contributor
→ one resource group
```

versus:

```text
Contributor
→ subscription
```

versus:

```text
Owner
→ management group
```

Azure RBAC scope can be:

```text
Management Group
     ↓
Subscription
     ↓
Resource Group
     ↓
Resource
```

I grant at the narrowest practical level. ([Microsoft Learn][16])

---

# **7. Example: pipeline only needs to push container images**

Don't grant:

```text
Owner
```

Grant:

```text
AcrPush
→ specific ACR
```

Then compromise of the pipeline cannot automatically:

```text
delete SQL
change firewall
grant Owner
```

because its identity only has registry push capability.

---

# **8. Example: application needs Blob access**

Don't grant:

```text
Contributor
```

just because Blob operations fail.

If the workload needs:

```text
read/write blob data
```

use an appropriate **Storage data-plane role** such as:

```text
Storage Blob Data Contributor
```

at the appropriate Storage Account/container scope.

This is the key distinction:

```text
Azure management-plane role
≠
resource data-plane permission
```

---

# **9. Example: Terraform needs normal Azure resource deployment**

Terraform manages:

```text
VM
VNet
App Service
Key Vault resource
```

but not RBAC.

Then:

```text
Contributor
```

on the deployment resource group/subscription may be sufficient, depending on the exact resources/actions.

Contributor intentionally cannot assign Azure RBAC roles. ([Microsoft Learn][15])

That's often desirable.

---

# **10. Role assignments are a special case**

Terraform may contain:

```hcl
resource "azurerm_role_assignment" "app" {
  # ...
}
```

Creating that requires:

```text
Microsoft.Authorization/roleAssignments/write
```

Contributor does not provide it.

Current Microsoft guidance lists roles such as:

```text
Role Based Access Control Administrator
User Access Administrator
Owner
```

as roles that can manage role assignments, with **Role Based Access Control Administrator** specifically designed for delegated RBAC management and having fewer permissions than User Access Administrator. ([Microsoft Learn][15])

So the solution may be:

```text
Dedicated RBAC deployment identity
        ↓
RBAC Administrator
        ↓
restricted scope/conditions
```

rather than:

```text
Developer
→ Owner
```

---

# **11. Conditions can reduce delegated role-assignment privilege**

Current Azure supports conditions on delegated RBAC-management assignments.

For example, a deployment identity could potentially be allowed to assign only:

```text
AcrPull
Key Vault Secrets User
```

to approved service principals, rather than arbitrary:

```text
Owner
```

assignments.

Microsoft currently recommends **Role Based Access Control Administrator with conditions** as a least-privilege approach to delegated role management. ([Microsoft Learn][17])

That is much safer than unrestricted Owner.

---

# **12. What if the developer personally needs production visibility?**

Maybe they need to diagnose the deployment.

Give:

```text
Reader
```

plus required monitoring/log roles.

For example:

```text
Reader
+
Log Analytics Reader
```

depending on investigation requirements.

They can inspect:

```text
resource configuration
deployment status
metrics/logs
```

without being able to modify Production.

Diagnosis and modification do not require identical privileges.

---

# **13. What if they genuinely need temporary write access?**

For an incident:

```text
Developer/SRE
      ↓
PIM eligible assignment
      ↓
Activate
      ↓
MFA
      ↓
justification
      ↓
approval if configured
      ↓
temporary limited role
```

Microsoft Entra PIM supports eligible role assignments that require activation and can include MFA, justification and approval, with privilege active only for a configured period. ([Microsoft Learn][18])

For example:

```text
Contributor
→ payment-prod RG
→ 1 hour
```

is preferable to:

```text
Permanent Owner
→ Production subscription
```

---

# **14. Owner should be exceptional**

Owner grants:

```text
full resource management
+
ability to assign Azure RBAC roles
```

which means a compromised Owner could potentially:

```text
modify Production
delete infrastructure
grant additional identities access
escalate/persist through RBAC
```

That's why “deployment isn't working” is far below the bar for permanent Owner.

---

# **15. Check Azure Policy too**

Suppose error is:

```text
RequestDisallowedByPolicy
```

Giving Owner probably won't solve it.

Azure Policy `deny` is evaluated against the requested resource configuration and can block a deployment before the request reaches the resource provider. ([Microsoft Learn][19])

Example:

```text
Terraform wants:
Public network access = Enabled

Policy requires:
Public access = Disabled

Result:
DENY
```

Correct action:

```text
fix architecture
or
use formally approved policy exception
```

not:

```text
grant Owner
```

---

# **16. Check resource locks**

Similarly, a deployment might fail because:

```text
Production resource
→ CanNotDelete lock
```

and Terraform wants replacement.

Giving developer Owner does not simply bypass the lock. Azure management locks apply independently of normal RBAC permissions; an authorized principal would need the appropriate permission/process to remove the lock first. ([Microsoft Learn][5])

Again:

```text
more RBAC
≠
correct diagnosis
```

---

# **17. Check network failures separately**

Suppose deployment step:

```text
kubectl → private AKS API
```

times out.

Owner does nothing.

The issue could be:

```text
GitHub-hosted runner
       ↓
No private route
       X
Private AKS API
```

Need:

```text
self-hosted runner
private connectivity
or
GitOps deployment
```

not Azure Owner.

---

# **18. Fix the deployment identity, not the developer**

If the pipeline legitimately lacked permission:

```text
GitHub OIDC identity
```

should receive it through controlled IaC/RBAC governance.

Then:

```text
every deployment
```

works predictably.

Granting the developer temporary Owner and having them manually “make it work” creates:

```text
manual drift
unclear audit path
irreproducible deployment
```

and the next pipeline run may still fail.

---

# **19. Remove temporary permission after resolution**

If PIM or temporary assignment was needed:

```text
incident resolved
      ↓
role expires/remove assignment
      ↓
update permanent pipeline RBAC
      ↓
document reason
```

Don't let:

```text
temporary access
```

become:

```text
permanent privilege
```

because nobody cleaned it up.

---

## **Example diagnostic flow**

Developer says:

> “Terraform gets 403. Give me Owner.”

I do:

```text
1. Read exact error
```

It says:

```text
Microsoft.Authorization/roleAssignments/write
not authorized
```

Then:

```text
2. Confirm failing principal
→ GitHub Prod identity
```

```text
3. Check current role
→ Contributor on rg-prod
```

Contributor cannot assign roles.

Now options:

```text
A. Move RBAC assignment into a separate privileged platform pipeline

or

B. Give dedicated deployment identity
   RBAC Administrator
   at narrow scope
   with constraints where possible
```

Developer remains:

```text
Reader in Prod
```

Deployment succeeds without making a human Owner.

That's the outcome I want.

---

### **Interview answer condensed**

> “I would not grant Owner because a deployment is failing. First I'd inspect the exact error and determine which identity is actually failing. A 403 usually tells me the denied Azure action and scope, so I'd inspect that pipeline identity's role assignments and grant the smallest role at the narrowest scope necessary. For example, ACR pushes need AcrPush, Blob data access needs a Storage data-plane role, and normal Terraform infrastructure deployment may need Contributor. If Terraform must create Azure role assignments, Contributor is intentionally insufficient, so I'd use a dedicated privileged deployment path with something like Role Based Access Control Administrator and appropriate scope or conditions—not make the developer Owner. For exceptional human access I'd use time-limited PIM activation. Then I'd fix the pipeline identity permanently and remove any temporary privilege.”

**Memory line:**
**Never debug authorization by jumping to Owner—find the exact denied action, identity, and scope, then grant only what's required.**

**Interview trap:**
If a deployment failure is caused by **Policy, a resource lock, private networking, quota, or the wrong identity**, granting Owner may not solve the problem at all.

**Keywords:**
least privilege, Owner, Contributor, Azure RBAC, scope, `roleAssignments/write`, RBAC Administrator, PIM, OIDC, data plane.

**Likely follow-ups:**

* Why can Contributor deploy resources but not create role assignments?
* What would you grant a pipeline that only pushes to ACR?
* What if Terraform needs to create RBAC assignments?
* How would you provide emergency human write access without permanent Owner?
* How would you distinguish an RBAC 403 from an Azure Policy denial?
