# **T33-02. Your new version causes 5xx errors immediately after release; what do you do?**

**Answer:**

If 5xx errors start immediately after a release, I would treat the deployment as the leading suspect, **stop further rollout, quantify the customer impact, and compare the new version against the last known-good version**.

If the release is safely reversible and the error rate is materially affecting users, I would usually rollback quickly rather than spend a long time debugging in production. At the same time, I would check whether the errors are coming only from new instances, whether readiness probes are passing incorrectly, and whether the release changed configuration, secrets, database schema, networking, or downstream dependencies.

For AKS I would inspect the Deployment, ReplicaSets, Pods, events, logs, and application telemetry. If this is GitOps-managed, I would restore the previous image digest in Git so Argo CD reconciles Production back to the known-good state.

My order is:

```text
5xx spike after release
        ↓
Stop rollout
        ↓
Measure impact
        ↓
Confirm correlation with new version
        ↓
Rollback safe?
     /           \
   Yes            No
    ↓              ↓
Rollback       Fix forward /
known-good     dependency/schema repair
     \            /
      ↓          ↓
      Validate recovery
            ↓
            RCA
```

---

## **1. First confirm the timing**

If telemetry shows:

```text
14:02 deployment starts
14:04 new Pods receive traffic
14:05 5xx jumps from 0.2% → 18%
```

that is strong evidence that the release is involved.

I would correlate:

```text
deployment timestamp
+
image version/digest
+
error-rate graph
```

rather than beginning with unrelated infrastructure checks.

This is a classic example of using **change correlation**.

---

# **2. Stop the blast radius**

If this is a canary:

```text
5% traffic → v42
95% traffic → v41
```

and v42 is failing:

```text
stop at 5%
```

Do not continue:

```text
25% → 50% → 100%
```

If it's a rolling Deployment:

```text
pause rollout
```

before healthy old replicas are replaced.

For AKS:

```bash
kubectl rollout pause deployment/checkout
```

This prevents the Deployment controller from intentionally progressing the rollout further.

---

# **3. Determine whether failures are isolated to the new version**

This is one of the highest-value checks.

Suppose:

```text
v41:
5xx = 0.1%

v42:
5xx = 31%
```

Then I have strong evidence.

If logs/metrics include:

```text
service.version
pod name
image digest
```

I can break errors down by release.

For example conceptually:

```text
5xx
│
├── old ReplicaSet → healthy
└── new ReplicaSet → failing
```

Now rollback confidence is high.

---

# **4. Check Kubernetes rollout state**

```bash
kubectl get deployment checkout
kubectl get rs
kubectl get pods -l app=checkout -o wide
```

I'm looking for:

```text
desired replicas
updated replicas
available replicas
old vs new ReplicaSet
restart counts
Pod states
```

Then:

```bash
kubectl rollout status deployment/checkout
```

If it shows the rollout is stuck because minimum availability isn't met, I know Kubernetes itself is detecting readiness/availability problems.

---

# **5. Check why new Pods return 5xx**

Important distinction:

```text
Pod Running
≠
Application healthy
```

Run:

```bash
kubectl logs <new-pod>
kubectl describe pod <new-pod>
```

Look for:

```text
configuration errors
connection failures
timeouts
missing env vars
secret failures
dependency errors
exceptions
```

A common case:

```text
new app starts successfully
but
DB connection fails
```

so the Pod is:

```text
Running
```

while users receive:

```text
500
```

---

# **6. Check readiness probe quality**

Suppose readiness is:

```http
GET /health
```

and `/health` only checks:

```text
process is alive
```

but the application cannot reach its required database.

Then:

```text
readiness = healthy
```

and Kubernetes sends user traffic to a broken Pod.

Better readiness may check enough critical initialization to answer:

> Can this instance safely serve traffic?

Not every external dependency should necessarily be included—otherwise one optional dependency can remove every Pod from service—but the probe must represent actual serving capability.

---

# **7. Distinguish 500, 502, 503, and 504**

“5xx” is a category, not one diagnosis.

### `500 Internal Server Error`

Often:

```text
application exception
bad configuration
serialization
business logic
```

### `502 Bad Gateway`

Often:

```text
gateway/proxy
cannot get valid response
from upstream
```

### `503 Service Unavailable`

Often:

```text
no healthy backend
application unavailable
overload
readiness failure
```

### `504 Gateway Timeout`

Often:

```text
backend/dependency too slow
```

That HTTP code helps narrow the first investigation step.

---

# **8. Check deployment configuration differences**

Compare old and new:

```text
image
environment variables
ConfigMaps
Secret references
feature flags
ports
health probes
resource limits
```

Example:

```text
v41:
DB_HOST=sql-prod.internal

v42:
DB_HOST=sql.internal
```

New release starts but every DB operation fails.

Another common failure:

```text
containerPort changed
but
Service targetPort didn't
```

which could produce gateway/service errors.

---

# **9. Check secrets and identity**

New release may have introduced:

```text
Managed Identity
Workload Identity
new Key Vault secret
new ServiceAccount
```

If:

```text
network works
token acquired
but resource returns 403
```

the problem is authorization.

If token acquisition fails:

```text
workload identity/federation
```

may be wrong.

If request times out:

```text
DNS/network/private endpoint
```

is more likely.

Don't treat all dependency failures as “secret problems.”

---

# **10. Check database compatibility**

This is critical.

Suppose v42 expects:

```text
Orders.NewStatus
```

but schema migration failed.

Then:

```text
v42 → SQL error → 500
```

Alternatively the migration succeeded but old Pods still run and no longer understand the new schema.

This is why application and database rollout must be **backward-compatible during mixed-version periods**.

---

# **11. Roll back if safe**

If:

```text
old version = healthy
new version = clearly bad
DB/config changes reversible
```

I would rollback.

For Kubernetes:

```bash
kubectl rollout history deployment/checkout
kubectl rollout undo deployment/checkout
```

Then:

```bash
kubectl rollout status deployment/checkout
```

But with Argo CD:

```text
preferred durable action:
GitOps repo
v42 → v41
```

because otherwise Argo may reapply v42.

---

# **12. Don't blindly roll back after destructive schema changes**

Suppose release changed DB schema:

```sql
DROP COLUMN legacy_status;
```

and v41 needs that column.

Then:

```text
rollback app → v41
```

could make 100% of traffic fail.

In that scenario, a carefully understood **fix-forward** may be safer.

This is why good deployment engineering uses:

```text
expand
→ migrate
→ contract later
```

instead of destructive schema changes in the same release boundary.

---

# **13. Verify recovery**

After rollback:

```text
Pod healthy
```

is not enough.

Confirm:

```text
5xx returned to baseline
p95/p99 normalized
critical business transaction succeeds
dependency latency normal
DB writes correct
```

Example:

```text
Before release:
5xx 0.2%

During release:
5xx 18%

After rollback:
5xx 0.25%
```

Now I have evidence that service has recovered.

---

# **14. Preserve evidence**

Before deleting every failed Pod:

```text
logs
events
trace IDs
image digest
deployment timestamps
configuration diff
```

should be preserved where possible.

Otherwise after rollback:

```text
incident fixed
but
root cause evidence gone
```

---

# **15. Prevent recurrence**

Depending on cause:

```text
Problem:
missing environment variable
→ deployment config validation

Problem:
schema mismatch
→ backward-compatible DB migration

Problem:
new code throws under production traffic
→ canary + SLO health gate

Problem:
readiness marked broken Pods healthy
→ better readiness probe

Problem:
prod-only dependency
→ more production-like staging
```

The corrective action should match the actual failure mechanism.

---

### **Interview answer condensed**

> “If 5xx errors begin immediately after a release, I would stop further rollout and correlate the error increase with the new version. I'd compare error rate between old and new instances, inspect the Deployment, ReplicaSets, Pod logs, readiness probes, configuration, secrets, database compatibility and downstream dependencies. If the previous version is healthy and the change is safely reversible, I'd rollback quickly rather than debug for a long time while users are impacted. In a GitOps setup I'd revert the desired image digest in Git. If the release already made a backward-incompatible data/schema change, I would assess whether fix-forward is safer than rollback. After recovery I'd validate user-facing metrics and critical transactions, then perform RCA and improve canarying, health gates, readiness or schema compatibility depending on the cause.”

**Memory line:**
**Immediate post-release 5xx = stop the rollout, correlate by version, restore the last known-good state if safely reversible.**

**Interview trap:**
Do not blindly rollback the application if the release already made an **irreversible database or state change**.

**Keywords:**
5xx, rollback, rollout pause, ReplicaSet, readiness probe, change correlation, canary, database compatibility, GitOps.

**Likely follow-ups:**

* How would you distinguish a 500 from a 503 problem?
* What would make you fix forward instead of rollback?
* Why might a Pod be Running but still return 500?
* How would you make this rollback automatic?
* How would you determine whether only the new ReplicaSet is failing?

# **T33-03. A release works in staging but fails in production; how would you investigate it?**

**Answer:**

If the same release works in staging but fails in production, I would treat the **difference between the two environments as the main clue**.

First I would verify that they are actually running the same immutable artifact—not just the same tag or source commit. Then I would compare production and staging systematically across configuration, secrets, identity, networking, data/schema, dependencies, resource limits, traffic characteristics, feature flags, and infrastructure versions.

I would avoid randomly changing Production. Instead I would identify the first layer where behavior differs.

My investigation flow would be:

```text
Same artifact?
    ↓
Configuration
    ↓
Identity
    ↓
DNS/networking
    ↓
Dependencies/data
    ↓
Runtime/resources
    ↓
Traffic/load
    ↓
External integrations
```

The goal is to answer:

> **What production-specific assumption did the release depend on?**

---

## **1. First prove it really is the same artifact**

This is the first question I would ask.

Staging:

```text
myapp:v42
```

Production:

```text
myapp:v42
```

looks identical.

But if `v42` is a mutable tag, they could resolve to different images.

Check digest:

```text
Staging:
sha256:AAA

Production:
sha256:BBB
```

Then the environments aren't actually testing the same binary.

Strong deployment model:

```text
CI builds once
→ sha256:AAA
→ Stage
→ Production
```

not rebuilding per environment.

---

# **2. Compare configuration**

This is one of the most common causes.

Check:

```text
environment variables
ConfigMaps
secret references
feature flags
App Configuration
Helm values
application settings
```

Example:

```text
Staging:
PAYMENT_URL=https://sandbox.vendor.com

Prod:
PAYMENT_URL=https://api.vendor.com
```

If only the production dependency fails:

```text
staging works
prod fails
```

exactly matches the symptom.

---

# **3. Configuration presence vs value**

Don't only ask:

> Does `DB_HOST` exist?

Ask:

```text
Does it contain the correct environment-specific value?
```

For example:

```text
Stage:
DB_HOST=sql-stage.database.windows.net

Prod:
DB_HOST=sql-prod-old.database.windows.net
```

Both environments technically have the variable.

One is stale.

---

# **4. Compare identity**

Stage may use:

```text
mi-app-stage
```

Prod:

```text
mi-app-prod
```

Perhaps Stage identity has:

```text
Key Vault Secrets User
```

but Prod doesn't.

Flow:

```text
Prod app
  ↓
Managed Identity
  ↓
Key Vault
  ↓
403
```

while staging succeeds.

That gives us:

```text
same code
different authorization
```

---

# **5. Separate authentication from authorization**

Suppose Production logs show:

```text
token successfully acquired
Key Vault returns 403
```

Then:

```text
authentication works
authorization fails
```

Check:

```text
Azure RBAC / Key Vault permission
```

Don't waste time rebuilding Managed Identity.

If token acquisition itself fails:

```text
identity/federation/configuration
```

is the likely layer.

---

# **6. Compare networking**

Staging might have:

```text
public SQL access enabled
```

while Production requires:

```text
Private Endpoint
+
Private DNS
```

Now new code works in staging but fails in Prod because DNS/networking assumptions differ.

Troubleshooting order:

```text
App
 ↓
DNS
 ↓
route
 ↓
NSG/firewall
 ↓
Private Endpoint
 ↓
service
```

---

# **7. Check DNS from inside the actual production runtime**

For a private database:

```bash
nslookup mydb.database.windows.net
```

Expected in Prod:

```text
private IP
```

If:

```text
public IP
```

then the application may be trying a path blocked by:

```text
Public network access = Disabled
```

Staging may never expose this because staging DB is public.

This is a classic environment-parity problem.

---

# **8. Compare database schema**

Same application version does not guarantee same schema.

Check:

```text
Staging schema version = 42
Prod schema version = 41
```

Then v42 application may expect:

```text
column/table/procedure
```

that doesn't exist in Production.

I would verify the migration history before changing anything.

---

# **9. Data shape may differ**

Staging usually contains:

```text
small
clean
synthetic data
```

Production may contain:

```text
millions of rows
legacy values
nulls
old records
unexpected characters
```

Code:

```text
works on 1,000 staging records
```

but fails on:

```text
one legacy production record
```

This is why realistic test datasets matter.

---

# **10. Compare load**

Staging:

```text
10 requests/sec
```

Production:

```text
5,000 requests/sec
```

New release may have introduced:

```text
N+1 queries
connection leak
lock contention
thread pool starvation
memory pressure
```

that does not show under staging traffic.

If Prod fails only under load:

```text
capacity/performance regression
```

becomes more likely than configuration.

---

# **11. Compare resource limits**

AKS example:

Staging:

```yaml
limits:
  memory: 2Gi
```

Production:

```yaml
limits:
  memory: 512Mi
```

Application works in Stage but Prod Pods get:

```text
OOMKilled
```

Check:

```bash
kubectl describe pod <pod>
kubectl get pod <pod> -o yaml
```

Look for:

```text
Last State: Terminated
Reason: OOMKilled
```

Then the problem is environment-specific resource configuration.

---

# **12. Compare replica/autoscaling behavior**

Staging:

```text
replicas = 1
```

Production:

```text
replicas = 10
```

If application stores:

```text
session in local memory
```

staging may appear perfect.

Production load balancing sends requests among replicas:

```text
Request 1 → Pod A
Request 2 → Pod B
```

and user session breaks.

This is why multi-replica testing in staging matters.

---

# **13. External service differences**

Staging may connect to:

```text
payment sandbox
test SMTP
fake identity provider
```

Production connects to:

```text
real payment provider
real SMTP
real IdP
```

Potential differences:

```text
IP allow lists
TLS certificates
rate limits
credentials
API contract/version
DNS
```

The release may be valid but fail against the actual production dependency.

---

# **14. Feature flags**

Production might have:

```text
NewCheckout=true
```

while Stage accidentally has:

```text
NewCheckout=false
```

Now:

```text
"release tested in staging"
```

is misleading because the failing code path was never exercised.

I would compare feature flag state as part of release metadata.

---

# **15. Infrastructure version drift**

Examples:

```text
Stage AKS 1.x
Prod AKS different version

Stage App Service Linux
Prod Windows

Stage SQL compatibility level X
Prod Y
```

The application may rely on runtime behavior that differs.

Architecture should aim for:

```text
same pattern
different scale
```

rather than fundamentally different platforms.

---

# **16. Compare actual deployment manifests**

For AKS:

```bash
kubectl get deployment checkout -n stage -o yaml
kubectl get deployment checkout -n prod -o yaml
```

Normalize away irrelevant generated fields and compare:

```text
image
env vars
probes
resources
ServiceAccount
volume mounts
ports
```

GitOps makes this easier because desired state is already version-controlled.

---

# **17. Use distributed tracing**

Suppose:

```text
Stage:
checkout request = 220ms

Prod:
checkout request = 8s then 500
```

Trace:

```text
Checkout
  ↓
Payment dependency
  ↓
7.5 seconds
```

Now I know the failure is downstream.

Instead of investigating:

```text
AKS nodes
```

first, I investigate the production payment path.

---

# **18. Check production-only security controls**

Production may have:

```text
WAF
Azure Firewall
NSGs
Private Endpoints
Azure Policy
Conditional Access
```

that staging doesn't.

New release may call a new external host:

```text
api.newvendor.com
```

Staging has unrestricted internet.

Prod firewall:

```text
DENY
```

Result:

```text
Stage works
Prod times out
```

This is exactly why environment-specific network policy belongs in the diff.

---

# **19. Don't “fix” Production by making it more like insecure Staging**

Bad response:

```text
SQL private access causes issue
→ enable public SQL in Prod
```

Better:

```text
find why private DNS/networking is broken
```

Production controls exist for a reason.

The objective is:

```text
make application compatible with Production security
```

not:

```text
remove Production security until app works
```

---

# **20. Use a structured diff**

I would create a quick comparison:

| Layer        | Stage    | Prod             |
| ------------ | -------- | ---------------- |
| Image digest | `AAA`    | `AAA`            |
| Config       | expected | difference found |
| Identity     | stage MI | prod MI          |
| DB schema    | v42      | v42              |
| Network      | public   | private          |
| Replicas     | 2        | 12               |
| Traffic      | low      | high             |
| External API | sandbox  | live             |

Now the hypothesis space becomes manageable.

---

# **21. Fix the parity gap afterward**

If root cause was:

```text
staging public DB
production private DB
```

then longer-term action may be:

```text
make Stage use Private Endpoint too
```

If root cause was:

```text
Stage only 1 replica
```

make Stage test:

```text
multi-replica behavior
```

The lesson isn't:

> “Production is weird.”

It's:

> “Our pre-production environment failed to represent a production requirement.”

# **T33-04. How would you minimize deployment downtime?**

**Answer:**

I would minimize deployment downtime by making deployments **incremental and reversible instead of stopping the whole application while replacing it**.

For a normal stateless application, I would run multiple instances behind a load balancer, start new-version instances alongside healthy old ones, wait until the new instances pass readiness checks, gradually shift traffic, and only then remove the old version.

Depending on risk and platform, I could use **rolling, blue-green, or canary deployment**. I would also design database schema changes to remain backward compatible during the mixed-version period, externalize session state so users are not pinned to one dying server, pre-pull/build artifacts before the deployment window, and automate health checks and rollback.

For highly available systems, the real goal isn't just:

> “deploy faster.”

It's:

> **keep enough healthy capacity serving traffic throughout the deployment.**

---

## **1. Avoid stop-and-replace deployments**

Bad:

```text
Stop v41
   ↓
Deploy v42
   ↓
Start v42
   ↓
Test
```

Downtime is guaranteed between:

```text
stop
and
healthy start
```

Better:

```text
v41 serving users
      ↓
start v42 alongside v41
      ↓
v42 healthy
      ↓
shift traffic
      ↓
remove v41
```

There is always a healthy serving population.

---

# **2. Run multiple instances**

With only:

```text
1 VM
or
1 Pod
```

a restart often means an outage.

Production:

```text
Load Balancer
   ↓
App1
App2
App3
```

lets one instance update while others continue serving.

High availability and zero/low-downtime deployment are closely related.

---

# **3. Rolling deployment**

Example:

```text
Before:
v41 v41 v41 v41

Step 1:
v42 v41 v41 v41

Step 2:
v42 v42 v41 v41

Step 3:
v42 v42 v42 v41

Final:
v42 v42 v42 v42
```

If each new instance becomes Ready before the next old instance disappears, user-visible downtime can be close to zero.

---

# **4. Configure safe rollout capacity**

Kubernetes example:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

Conceptually:

```text
maxUnavailable = 0
→ don't intentionally reduce healthy replica count

maxSurge = 1
→ create one extra new Pod temporarily
```

Trade-off:

```text
extra capacity is required
```

If the cluster has no spare resources:

```text
surge Pod Pending
→ rollout stalls
```

So deployment strategy and capacity planning must agree.

---

# **5. Readiness determines when traffic moves**

New Pod lifecycle:

```text
Container starts
     ↓
Application initializes
     ↓
DB connection ready
     ↓
cache/config loaded
     ↓
readiness succeeds
     ↓
Service sends traffic
```

Without readiness:

```text
container process starts
     ↓
traffic arrives immediately
     ↓
application still starting
     ↓
5xx
```

Readiness is one of the most important low-downtime controls.

---

# **6. Use startup probes for slow startup**

Applications like Java services may need:

```text
60–120 seconds
```

to initialize.

If liveness starts too aggressively:

```text
Pod starting
 ↓
liveness fails
 ↓
restart
 ↓
starts again
 ↓
liveness fails
```

creating a loop.

A `startupProbe` can protect the initialization period before liveness begins enforcing restarts.

---

# **7. Graceful shutdown**

Traffic removal is not enough if active requests are killed.

When old instance is terminated:

```text
Stop receiving new requests
        ↓
finish existing requests
        ↓
close connections
        ↓
exit
```

For Kubernetes:

```text
SIGTERM
terminationGracePeriodSeconds
preStop where justified
```

can help.

Application should respond to SIGTERM correctly.

Bad:

```text
Pod killed
→ active payment request terminated
```

Good:

```text
Pod removed from endpoints
→ drains requests
→ exits cleanly
```

---

# **8. Externalize session state**

If sessions live in:

```text
VM memory
```

then removing that VM logs users out.

Better:

```text
App1 ─┐
App2 ─┼→ external session/cache
App3 ─┘
```

or use token-based/stateless session designs where appropriate.

Then instances are replaceable during deployments.

---

# **9. Blue-green for near-instant traffic switch**

Architecture:

```text
Blue
v41
serving production

Green
v42
fully deployed/testing
```

Then:

```text
Traffic:
Blue → Green
```

The switch can be fast.

Rollback:

```text
Green → Blue
```

is also fast if data compatibility remains intact.

Trade-off:

```text
temporarily run two environments
→ higher capacity/cost
```

---

# **10. Canary reduces risk rather than only downtime**

Canary:

```text
99% → v41
1%  → v42
```

Then:

```text
1%
5%
25%
50%
100%
```

based on health.

If the release is bad:

```text
only a small fraction of users
```

are affected.

This minimizes **deployment risk/blast radius**, which often matters more than raw downtime.

---

# **11. Database deployments are often the hardest part**

Application instances can run side-by-side.

Database schema is shared.

Bad migration:

```text
v42:
rename column Status → NewStatus
```

while old v41 Pods still query:

```text
Status
```

Mixed-version period fails.

Use backward compatibility:

```text
Add NewStatus
      ↓
v41 still works
      ↓
v42 supports old + new
      ↓
backfill data
      ↓
all traffic v42
      ↓
remove Status later
```

This is **expand-and-contract**.

---

# **12. Avoid long maintenance tasks in the critical deployment path**

Bad:

```text
deployment begins
 ↓
rebuild 500-million-row index
 ↓
40 minutes
 ↓
start app
```

Better:

```text
perform online/preparatory DB work earlier
```

where technology allows.

The deployment window should mostly contain:

```text
version activation
+
health validation
```

not expensive preparation.

---

# **13. Pre-build artifacts**

Before production deployment:

```text
container image already built
already scanned
already in ACR
```

Don't spend deployment downtime:

```text
compiling code
downloading dependencies
building image
```

Production should consume an existing immutable artifact.

---

# **14. Keep dependencies backward-compatible**

Suppose Service A v42 calls Service B with:

```text
/new-endpoint
```

but B hasn't deployed yet.

Now:

```text
A v42 → B v41 → 404
```

For independent deployment, API changes need:

```text
backward compatibility
versioning
contract testing
```

Otherwise services must deploy simultaneously, which increases downtime risk.

---

# **15. Autoscaling can help but can also hurt**

Before rollout, ensure enough capacity for:

```text
old replicas
+
surge replicas
```

If cluster runs at:

```text
99% utilization
```

and rollout needs 20% surge:

```text
new Pods Pending
```

Then the deployment stalls.

I might:

```text
pre-scale nodes
```

for major releases.

Reactive Cluster Autoscaler may be too slow for an aggressive rollout.

---

# **16. Use health gates**

After deploying initial new instances:

```text
check
├── readiness
├── 5xx
├── p95/p99
├── dependency failures
└── business transaction success
```

Only then proceed.

Deployment should be:

```text
deploy
→ observe
→ continue
```

not:

```text
deploy
→ immediately replace everything
```

---

# **17. Drain load balancer traffic before shutting down VMs**

For VMSS/VM-based apps:

```text
Backend instance
     ↓
mark unhealthy / remove from backend
     ↓
connection drain
     ↓
update/restart
     ↓
health probe passes
     ↓
return to pool
```

Same principle as Kubernetes readiness.

---

# **18. App Service deployment slots**

For supported App Service workloads:

```text
Production slot
     ↓
Staging slot
```

Deploy new version into staging slot.

Warm/test it.

Then:

```text
slot swap
```

makes it active.

This can significantly reduce downtime because the new application is initialized before receiving production traffic.

But configuration marked as slot-specific must be understood, and database compatibility remains your responsibility.

---

# **19. Feature flags can separate deployment from release**

Deploy code:

```text
NewPaymentFlow = OFF
```

Application version reaches 100% safely.

Later:

```text
enable for 1%
5%
50%
100%
```

This separates:

```text
deployment
```

from:

```text
feature exposure
```

and gives faster mitigation without redeploying.

---

# **20. Monitor throughout**

Watch:

```text
availability
5xx
p95/p99
CPU/memory
queue depth
DB connections
business transactions
```

during every rollout.

Low downtime is meaningless if the service remains technically available but:

```text
checkout correctness fails
```

---

# **21. Production example**

AKS app:

```text
replicas = 6
```

Strategy:

```text
maxUnavailable = 0
maxSurge = 2
```

Flow:

```text
6 v41 healthy
     ↓
2 v42 created
     ↓
readiness passes
     ↓
traffic starts reaching v42
     ↓
2 v41 removed
     ↓
next 2 v42
```

At all times:

```text
at least 6 Ready Pods
```

if capacity and application health cooperate.

That's the essence of minimizing downtime.

---

### **Interview answer condensed**

> “I minimize downtime by avoiding stop-and-replace deployment. I run multiple instances, start the new version alongside the old one, wait for meaningful readiness checks, gradually shift traffic, and only remove old capacity after the replacement is healthy. Depending on risk I'd use rolling, blue-green or canary deployment. For Kubernetes I'd tune `maxUnavailable`, `maxSurge`, readiness/startup probes and graceful termination, and ensure spare cluster capacity exists. I would externalize session state, pre-build immutable artifacts, and use backward-compatible database and API changes so old and new versions can coexist during rollout. Health gates should stop or rollback the deployment if user-facing error or latency metrics degrade.”

**Memory line:**
**Keep healthy old capacity serving until healthy new capacity is proven ready.**

**Interview trap:**
You cannot achieve reliable zero-downtime deployment with application replicas alone if the **database schema change is backward-incompatible**.

rolling deployment, blue-green, canary, readiness, graceful shutdown, `maxUnavailable`, `maxSurge`, expand-and-contract, deployment slots.

# **T33-05. What is a rolling deployment?**

**Answer:**

A rolling deployment is a deployment strategy where the old application instances are **gradually replaced with instances running the new version**, instead of shutting down the entire old version and replacing everything at once.

For example, with four replicas:

```text
v1 v1 v1 v1
```

Kubernetes might replace them progressively:

```text
v2 v1 v1 v1
v2 v2 v1 v1
v2 v2 v2 v1
v2 v2 v2 v2
```

If readiness checks are configured correctly, new instances receive traffic only after they are healthy, so the application can remain available throughout the deployment.

The main advantages are **low additional infrastructure cost and low/no deployment downtime**. The main trade-off is that old and new versions coexist temporarily, so APIs, configuration, and database schemas must be compatible during that period.

---

## **How it works in Kubernetes**

A Deployment manages:

```text
Deployment
   ↓
ReplicaSet old
   ↓
Pods v1
```

When image changes:

```text
image:
v1 → v2
```

Kubernetes creates:

```text
new ReplicaSet
```

and gradually adjusts replica counts.

Conceptually:

```text
Old ReplicaSet   New ReplicaSet

4                0
3                1
2                2
1                3
0                4
```

until the rollout completes.

---

# **The two key settings**

For Kubernetes RollingUpdate:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 1
```

### `maxUnavailable`

Controls how many desired replicas may be unavailable during rollout.

If:

```text
replicas = 10
maxUnavailable = 1
```

Kubernetes may allow healthy capacity to drop to roughly:

```text
9
```

during progress.

---

### `maxSurge`

Controls how many additional Pods above desired replica count may exist temporarily.

If:

```text
replicas = 10
maxSurge = 2
```

the Deployment may temporarily run:

```text
12 Pods
```

while replacing old replicas.

---

# **Safer availability-oriented example**

```yaml
strategy:
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

This aims to retain all desired healthy capacity while adding a replacement Pod.

But it requires:

```text
extra cluster capacity
```

for that surge.

If none exists:

```text
new Pod Pending
→ deployment stalls
```

So there is a cost/capacity trade-off.

---

# **Readiness controls traffic**

Suppose new Pod starts:

```text
v2 Pod
```

but application needs 30 seconds to initialize.

Until:

```text
readinessProbe = success
```

the Pod should not become a Service endpoint.

Then:

```text
old v1 Pod
```

continues serving traffic.

That's what makes rolling deployment safe.

---

# **Rolling deployment does not guarantee zero downtime**

If:

```text
replicas = 1
maxUnavailable = 1
```

then the old replica can disappear before the new replica serves traffic.

Result:

```text
temporary outage
```

Similarly, a bad readiness probe can mark a broken new instance healthy.

So:

```text
rolling strategy
+
enough replicas
+
capacity
+
correct probes
```

are all needed.

---

# **Mixed-version compatibility**

During deployment:

```text
v1 and v2
```

both serve users.

Therefore both need to understand:

```text
shared DB schema
API contracts
message formats
cache format
```

Example:

If v2 changes database column:

```text
Status
→ NewStatus only
```

while v1 still expects `Status`, the rolling period breaks.

Use backward-compatible evolution.

---

# **Rolling vs recreate**

### Recreate

```text
Stop all v1
      ↓
Start v2
```

Simple, but downtime likely.

### Rolling

```text
replace gradually
```

Better availability.

Kubernetes Deployments use RollingUpdate as the normal deployment strategy unless configured otherwise.

---

# **Rolling vs blue-green**

Rolling:

```text
replace instance by instance
```

Uses relatively little extra capacity.

Blue-green:

```text
entire Blue environment
+
entire Green environment
```

then switch traffic.

Blue-green often gives:

```text
faster full rollback
```

but uses more infrastructure.

---

# **Rolling vs canary**

Rolling deployment answers:

> How do I gradually replace instances?

Canary answers:

> How do I deliberately expose only a controlled percentage/user group to the new version and evaluate it before broad rollout?

A rolling deployment might quickly progress based mainly on readiness.

A canary typically uses richer rollout analysis:

```text
1% traffic
→ observe
→ 5%
→ observe
```

The concepts can also be combined with specialized rollout tooling.

---

# **Rollback**

If the new ReplicaSet is bad and the previous revision still exists:

```bash
kubectl rollout history deployment/myapp
kubectl rollout undo deployment/myapp
```

can restore the previous Deployment revision.

But again:

```text
application rollback
≠
database rollback
```

if state/schema was changed incompatibly.

---

# **Practical example**

Initial:

```text
replicas = 3
version = v1
```

Kubernetes:

```text
Pod1 v1
Pod2 v1
Pod3 v1
```

Deploy v2.

Step 1:

```text
Pod1 v1
Pod2 v1
Pod3 v1
Pod4 v2 starting
```

v2 readiness passes.

Step 2:

```text
Pod1 v1 removed
Pod2 v1
Pod3 v1
Pod4 v2
Pod5 v2 starting
```

Eventually:

```text
Pod4 v2
Pod5 v2
Pod6 v2
```

Users continue being routed to Ready instances through the Kubernetes Service.

### **Interview answer condensed**

> “A rolling deployment gradually replaces old application instances with the new version instead of taking the entire application down. In Kubernetes, a Deployment creates a new ReplicaSet and scales the new ReplicaSet up while scaling the old one down. `maxSurge` controls extra temporary replicas and `maxUnavailable` controls how much healthy capacity can be lost during the rollout. Readiness probes prevent new Pods from receiving traffic before they're ready. Rolling deployments are efficient and can provide near-zero downtime, but old and new versions coexist temporarily, so APIs and database schemas must remain backward compatible.”

**Memory line:**
**Rolling deployment = gradually replace old replicas while keeping enough healthy replicas serving users.**

**Interview trap:**
A rolling deployment does **not automatically mean zero downtime**—one replica, bad readiness probes, insufficient surge capacity, or incompatible DB changes can still cause an outage.

RollingUpdate, ReplicaSet, `maxSurge`, `maxUnavailable`, readiness probe, mixed versions, backward compatibility, rollback.
