# **T33-18. Your application secret expires and production goes down; how would you redesign the system to prevent recurrence?**

**Answer:**

First I would restore service by rotating the expired credential or using the documented emergency recovery path. But the permanent fix would be to ask **why the application needs a long-lived secret at all**.

If the application runs on Azure and the target supports Microsoft Entra authentication, I would replace the secret with a **Managed Identity**. For an AKS workload, I would use **Microsoft Entra Workload ID**. For GitHub Actions or another external CI system, I would use **OIDC/workload identity federation**.

That changes the model from:

```text
Application
   ↓
Client secret
   ↓
Microsoft Entra ID
   ↓
Azure service
```

to:

```text
Application
   ↓
Managed/Workload Identity
   ↓
short-lived Entra token
   ↓
Azure service
```

There is then no application secret sitting in configuration waiting to expire.

If a secret genuinely cannot be eliminated—for example a third-party API key—I would store it in **Azure Key Vault**, automate rotation where possible, monitor its expiration well in advance, support overlapping credential versions during rotation, and alert before the expiry becomes a production event.

Microsoft's current guidance recommends secretless authentication using managed identities wherever the workload and target service support Entra authentication; Key Vault remains appropriate for unavoidable secrets. ([Microsoft Learn][1])

Production is already down.

My first task is:

```text
Restore service
```

not redesign architecture while customers are affected.

I would determine:

```text
Which credential expired?
Which workload uses it?
Which service is rejecting authentication?
Is there a valid replacement credential?
```

Typical evidence might be:

```text
401 Unauthorized
invalid_client
AADSTS...
client secret expired
```

If I can safely create/activate a replacement credential:

```text
New credential
    ↓
securely update application
    ↓
restart/reload if required
    ↓
validate authentication
```

Then verify:

```text
5xx returned to baseline?
critical transactions working?
dependency authentication successful?
```

Only after stabilization do I address the architecture.

# **2. Identify whether the secret can be eliminated**

I classify the dependency.

### Azure workload → Entra-enabled Azure service

Examples:

```text
App Service → Key Vault
AKS Pod → Storage
VM → Azure SQL
Function → Service Bus
```

Prefer:

```text
Managed Identity
or
Workload Identity
```

No client secret required.

---

### GitHub Actions → Azure

Prefer:

```text
GitHub OIDC
    ↓
Entra federated identity
    ↓
short-lived token
```

No stored service-principal secret.

---

### Third-party service requiring an API key

Example:

```text
Application → Stripe/vendor API
```

Managed Identity cannot magically authenticate to a system that doesn't accept Entra tokens.

Then:

```text
Managed Identity
    ↓
Key Vault
    ↓
third-party API key
```

is appropriate.

Microsoft makes this distinction explicitly: when a target doesn't support Entra authentication and still requires a secret/key/certificate, store that credential in Key Vault and let the Azure workload access Key Vault through Managed Identity. ([Microsoft Learn][1])

# **6. If a secret must remain, Key Vault is only part of the solution**

Moving:

```text
secret from appsettings.json
```

to:

```text
Key Vault
```

is good, but it doesn't solve expiry by itself.

A Key Vault secret can still expire.

So I also need:

```text
ownership
rotation
expiration monitoring
automation
rollback
```

A secure storage location is not a lifecycle-management strategy.

# **7. Rotate before expiry with overlap**

For unavoidable credentials:

```text
Secret v1 valid
      ↓
Create Secret v2
      ↓
Update application to v2
      ↓
Validate
      ↓
Revoke v1
```

Not:

```text
Secret v1 expires
      ↓
Production breaks
      ↓
Create v2
```

Overlapping credentials allow a safe transition.

For certificates, Microsoft recommends monitoring and rotating them before expiry; Key Vault can assist with centralized certificate lifecycle management. ([Microsoft Learn][2])

```text

```

# **10. Don't solve it by creating 10-year secrets**

A weak reaction is:

```text
Secret expired after 1 year
→ create a 5-year secret
```

That reduces expiry frequency but increases exposure if the secret leaks.

Better hierarchy:

```text
1. Eliminate secret
2. If impossible, automate rotation
3. If automation impossible, monitor + documented rotation
```

A rotation procedure that has never been exercised is just documentation.

I would test:

```text
Create new credential
      ↓
Deploy it
      ↓
Old + new overlap
      ↓
Revoke old
      ↓
Application stays healthy
```

in nonproduction and periodically in Production where safe.

### **Interview answer condensed**

> “First I'd restore service by rotating the expired credential, but the permanent solution would be to eliminate the credential wherever possible. Azure-hosted applications should use Managed Identity, AKS Pods should use Workload Identity, and GitHub Actions should use OIDC federation so they receive short-lived Entra tokens instead of storing client secrets. If a third-party secret genuinely must remain, I'd put it in Key Vault, automate rotation with overlapping versions, monitor expiry well in advance, assign an owner, and test the rotation procedure. I would not solve the problem simply by creating a much longer-lived secret.”

**Memory line:**
**Don't become better at rotating Azure secrets when you can remove the secret entirely.**

**Interview trap:**
Moving a secret into Key Vault **does not prevent expiry**; you still need rotation and monitoring unless you replace the secret with identity-based authentication.

**Keywords:**
Managed Identity, Workload Identity, OIDC, Key Vault, credential rotation, expiration monitoring, short-lived tokens, secretless authentication.

* How would you alert before a Key Vault secret or certificate expires?

# **T33-19. A container scan identifies a critical CVE one hour before a scheduled deployment; what would you do?**

**Answer:**

I would **stop the deployment and assess the vulnerability before promoting that image to Production**.

A “Critical” severity alone tells me the issue deserves immediate attention, but I would also evaluate exploitability, whether the vulnerable package is actually present and reachable in our runtime path, whether a fix exists, whether the image is already running in Production, and whether this deployment is itself an emergency security/business fix.

For a normal scheduled deployment, my default would be:

```text
Critical CVE
    ↓
Deployment gate fails
    ↓
Do not promote image
    ↓
Patch base/dependency
    ↓
Rebuild from clean source
    ↓
Rescan
    ↓
Deploy only when accepted
```

I would not simply suppress the finding because the release calendar says deployment starts in an hour.

If there is a genuine business-critical emergency and no patched artifact is available, any exception should be **time-bound, risk-assessed, formally approved, and accompanied by compensating controls and a remediation deadline**.

Microsoft Defender for Containers currently provides vulnerability assessment of images in registries before deployment and recommends resolving vulnerabilities in Azure registry images to reduce supply-chain/runtime risk. ([Microsoft Learn][3])

---

## **1. Freeze the promotion, not necessarily the entire engineering process**

I would stop:

```text
Candidate image
→ Production
```

I would not necessarily stop:

```text
analysis
rebuild
testing
```

Pipeline state:

```text
Build      PASS
Tests      PASS
Scan       FAIL: Critical CVE
Deploy     BLOCKED
```

That's exactly why security scanning belongs **before** deployment.

# **2. Confirm the finding**

Before responding blindly, inspect:

```text
CVE ID
CVSS/severity
affected package
installed version
fixed version
source layer
exploitability
known exploitation
runtime exposure
```

Example:

```text
CVE-XXXX
Package: openssl
Installed: 3.x.a
Fixed:     3.x.b
```

Then determine:

```text
Which Docker layer introduced it?
```

Maybe:

```text

```

or:

```text
npm dependency

OS package
```

# **3. Severity and risk are related but not identical**

A scanner might classify:

```text
Critical
```

but operational risk also depends on:

```text
Is the vulnerable code reachable?
Is it exposed to untrusted input?
Does exploit require privilege?
Does the container run as root?
Is exploit known in the wild?
Does a patch exist?
```

For example:

```text
Critical vulnerability
in unused build-time package
```

may present different risk from:

```text
Critical unauthenticated RCE
in internet-facing runtime component
```

I still don't casually deploy either, but prioritization differs.

Defender for Cloud now incorporates contextual/risk signals into container vulnerability prioritization in supported configurations. ([Microsoft Learn][3])

# **4. Check whether the image is already running**

This dramatically changes urgency.

### Candidate only

```text
CVE image
not yet in Prod
```

Action:

```text
block promotion
patch
```

### Already in Production

Maybe existing Prod uses the same vulnerable base image.

Then this isn't only a release-gate question.

It becomes:

```text

```


Defender for Containers can also surface vulnerabilities associated with running container images, not just registry artifacts. ([Microsoft Learn][3])

# **5. Never trust tags alone**

Suppose scanner reports:

```text
myapp:v42
```

I want the exact digest:

```text
myapp@sha256:abcd...
```

because tags can move.

The deployment gate should identify the precise scanned artifact.

Otherwise:

```text
Scanner approved tag v42 at 09:00

tag v42 repointed at 09:30

Production deploys at 10:00
```

and the scanned artifact isn't necessarily what ran.

Strong supply-chain model:

```text
Build
 ↓
Digest
 ↓
Scan that digest
 ↓
Approve that digest
 ↓
Deploy that digest
```


```text

```

### **Interview answer condensed**

> “I would stop the Production promotion and inspect the exact CVE, package, image digest, exploitability and available fix. For a normal scheduled release, a newly discovered Critical vulnerability should fail the security gate. I'd patch the dependency or base image in source, rebuild an immutable image, rescan that new digest and rerun functional tests before deploying. **Memory line:**
**Critical CVE before release: block the artifact, assess the actual risk, rebuild and rescan—don't let the calendar override the gate.**

**Interview trap:**
Do not “fix” a container by patching a running Pod manually; rebuild the **immutable image from source** and deploy a newly scanned digest.

**Keywords:**

**Likely follow-ups:**

# **T33-20. You discover that an Azure Storage Account containing sensitive data is publicly accessible; what do you do?**

**Answer:**

I would treat it as a **potential security incident and immediately reduce exposure without destroying evidence**.

First I would establish what “publicly accessible” means, because Azure Storage has two different concepts:

1. **Public network access** — whether the Storage service can be reached over public networking.
2. **Anonymous blob access** — whether data can actually be read without authentication.

If sensitive data is anonymously readable, containment is urgent: I would disable anonymous blob access at the Storage Account level and validate that the affected containers are no longer anonymously readable.

If the requirement is that sensitive Storage must not be reachable from the public internet at all, I would additionally disable public network access and use **Private Endpoints**, or at minimum tightly restrict the Storage firewall while transitioning.

Then I would preserve and examine logs, determine how long exposure existed, what data was accessible, whether anonymous or suspicious reads occurred, rotate keys/SAS tokens if they may have been exposed, investigate the configuration change through Activity Log, notify the security/incident process, and add Azure Policy so the condition cannot recur.

Microsoft currently recommends disabling anonymous Blob access for sensitive Storage, and when clients can use Private Link, disabling public network access entirely so only private endpoints are accepted. ([Microsoft Learn][5])

---

## **1. First clarify what “public” means**

This distinction is extremely important.

### Public network access enabled

```text
Internet
   ↓
Storage endpoint reachable
```

does **not automatically mean**:

```text
anonymous users can read blobs
```

They may still need:

```text
Entra ID
SAS
Shared Key
```

authorization.

---

### Anonymous Blob access enabled

This means:

```text
Unauthenticated user
      ↓
Blob/container
      ↓
data returned
```

if both the account and container-level settings permit it.

That is an actual anonymous-data exposure.

Microsoft documents these as separate controls: allowing anonymous access at the account level does not itself expose a container unless that container is also configured for anonymous access. ([Microsoft Learn][6])

---

# **2. Immediate containment: disable anonymous Blob access**

If sensitive Blob data is anonymously accessible:

```bash
az storage account update \
  --resource-group <rg> \
  --name <storage-account> \
  --allow-blob-public-access false
```

This makes the account-level setting override container anonymous-access configurations.

Microsoft explicitly recommends setting `AllowBlobPublicAccess` to `false`; once disallowed at the account level, containers in that account cannot continue serving Blob data anonymously. ([Microsoft Learn][6])

Then immediately retest anonymously.

Expected:

```text
unauthenticated request
→ denied
```

---

# **3. Don't confuse anonymous access with public network access**

If I run:

```text
allowBlobPublicAccess = false
```

then:

```text
Anonymous read
→ prevented
```

But authorized users may still access the Storage Account over its public endpoint.

For sensitive workloads whose architecture is intended to be private:

```text
Public network access
= Disabled
```

plus:

```text
Private Endpoint
```

provides a much stronger network boundary.

Microsoft currently recommends exactly this where clients are entirely in Azure/private connected networks. ([Microsoft Learn][5])

---

# **4. Desired private architecture**

```text
Application
    ↓
VNet
    ↓
Private DNS
    ↓
Storage Private Endpoint
    ↓
Storage Account

Public network access
= Disabled
```

Then:

```text
Internet
   X
Storage Account
```

and application access remains private.

---

# **5. Be careful not to break Production blindly**

Suppose legitimate Production applications currently use:

```text
storageaccount.blob.core.windows.net
```

over public networking from an environment without Private Endpoint connectivity.

Immediately disabling public networking could cause:

```text
security exposure fixed
but
Production outage created
```

If the data is actively exposed anonymously, containment may still justify interruption.

But if the issue is only that the authenticated endpoint is internet-reachable, I can potentially:

```text
1. Restrict firewall immediately
2. Establish private endpoint
3. Validate private DNS/connectivity
4. Disable public network access
```

The action should balance:

```text
severity of active exposure
vs
service continuity
```

with security leading for sensitive data.

---

# **6. Preserve evidence**

Before deleting logs/resources:

```text
Activity Log
Storage logs
Defender alerts
network/access telemetry
```

should be preserved.

I need to know:

```text
When did exposure begin?
Which containers?
Which blobs?
Which IPs accessed them?
Was access anonymous?
How much data was downloaded?
Who changed the setting?
```

Containment first, but don't erase the evidence needed for breach assessment.

# **7. Determine exposure window**

Use Azure Activity Log to identify configuration changes such as:

```text

Storage firewall modified

```

If setting changed:

```text
August 29, 11:17
```

and discovered:

```text
September 6, 02:00
```

the investigation window is at least that interval.

That matters for:

```text

```

---

# **8. Determine what was actually accessible**

A Storage Account could contain:

```text
container-public
container-sensitive
container-logs
```

I would determine:

```text
Which container had public ACL?
Blob vs Container anonymous permission?
Static website enabled?
```

Microsoft also notes an important nuance: the `$web` container associated with Azure Storage static website hosting remains publicly readable while static website hosting is enabled, even when `allowBlobPublicAccess` is false. ([Microsoft Learn][7])

So if sensitive data somehow sits in `$web`, I need to address static website hosting itself.

---

# **9. Check for suspicious data access**

Look for:

```text
anonymous reads
large downloads
unusual IP addresses
unexpected geographic sources
high-volume enumeration
```

This tells me whether the situation is:

```text
misconfiguration discovered before exploitation
```

or potentially:

```text
data breach / exfiltration
```

Those have very different incident-management implications.

---

# **10. Credentials may also need rotation**

Suppose the same repository/environment exposing Storage also leaked:

```text
Storage account key
SAS token
connection string
```

or investigation shows they may have been obtained.

Then:

```text
rotate/regenerate keys
revoke SAS where possible
replace credentials
```

and ideally move applications toward:

```text
Microsoft Entra ID
+
Managed Identity
```

rather than Shared Key.

Current Azure Storage guidance also recommends Entra-based authorization over Shared Key where feasible. ([Microsoft Learn][8])

---

# **11. Disable Shared Key if the architecture allows it**

A stronger mature model:

```text
Application
   ↓
Managed Identity
   ↓
Entra ID
   ↓
Storage data-plane RBAC
```

rather than:

```text
Application
   ↓
Storage account key
```

Then compromise of an application config doesn't reveal a Storage Account master key.

But first verify every legitimate client supports the replacement authentication model.

---

# **12. Verify authorization separately from network isolation**

Private Endpoint:

```text
controls network path
```

Managed Identity:

```text
authenticates workload
```

Storage Blob Data Contributor:

```text
authorizes blob operations
```

I want all three.

```text
Network:
Can it reach Storage?

Identity:
Who is it?

Authorization:
What can it do?
```

A Private Endpoint does not mean every client on the VNet should have data access.

---

# **13. Prevent recurrence with Azure Policy**

I would apply policy at appropriate scope requiring:

```text
Anonymous Blob access disabled
```

and potentially:

```text
Public network access disabled
Private Endpoint required
```

for sensitive workload classes.

Azure provides built-in policies for disallowing anonymous public Blob access and auditing/denying Storage public network exposure. ([Microsoft Learn][9])

Then:

```text
Engineer tries to enable public access
      ↓
Policy
      ↓
DENY
```

rather than relying on review alone.

---

Terraform example conceptually:

```hcl

```

with Private Endpoint resources and Private DNS configured where required.

Do not rely on someone remembering Portal settings.

# **15. Add detection**

Alert when:

```text
Storage public-access setting enabled
anonymous access enabled
firewall default changed
Private Endpoint deleted
```

using:

```text
Azure Activity Log
Defender for Cloud
Azure Policy compliance
```

Prevention + detection is stronger than either alone.

## **Incident flow**

```text
Sensitive Storage publicly accessible
        ↓
Confirm exact exposure type
        ↓
Contain
├── disable anonymous access
└── restrict/disable public networking
        ↓
Verify inaccessible externally
        ↓
Preserve logs
        ↓
Determine exposure window
        ↓
Investigate reads/exfiltration
        ↓
Rotate compromised credentials if needed
        ↓
Security/legal process as applicable
        ↓
Private Endpoint + Entra auth
        ↓
Policy + IaC + monitoring
```

---

### **Interview answer condensed**

> “I would treat it as a security incident and first determine whether ‘public’ means the Storage endpoint is internet-reachable or the actual Blob data is anonymously readable, because those are separate Azure controls. If sensitive blobs are anonymously accessible, I'd immediately disable Blob anonymous access at the account level and verify unauthenticated requests fail. For a private-data architecture I'd then move access through Private Endpoints and disable public network access, while ensuring legitimate workloads retain connectivity. I'd preserve Storage and Activity logs, determine the exposure window and affected objects, investigate suspicious or anonymous reads, rotate keys/SAS credentials if they may be compromised, and escalate through the security process. Finally I'd enforce the secure state through Terraform and Azure Policy so anonymous/public access can't be casually re-enabled.”

**Memory line:**
**Public endpoint and anonymous data access are different—contain the actual exposure, then make sensitive Storage private by design.**

**Interview trap:**
`Allow Blob anonymous access = Disabled` **does not mean the Storage Account has no public network endpoint**; public network access is a separate setting.

**Keywords:**
Azure Storage, anonymous Blob access, public network access, Private Endpoint, Private DNS, Managed Identity, Shared Key, Azure Policy, Activity Log.

**Likely follow-ups:**

* What's the difference between public network access and anonymous Blob access?
* How would you determine whether data was actually downloaded?
* Would you immediately disable the public endpoint if Production currently uses it?
* How would you prevent the configuration from recurring?
* Why prefer Managed Identity over Storage account keys?

# **T33-21. What are your first steps when receiving a production outage alert?**

**Answer:**

My first steps are to **validate the alert, determine user impact and scope, stabilize the service, and establish incident ownership**.

I would not begin by randomly restarting resources.

I would check whether the service is actually unavailable, what users/regions/functions are affected, and whether there was a recent deployment, configuration change, infrastructure event, or Azure platform issue. I would open the relevant dashboards and logs, check Azure Service Health/Resource Health where appropriate, and identify whether the issue is at the application, dependency, network, data, capacity, or Azure platform layer.

If there's an obvious low-risk mitigation—such as rolling back a just-released bad version, failing over to a healthy region, or disabling a problematic feature—I prioritize restoring service over proving the root cause during the outage.

For a significant incident I would assign an incident commander/owner, establish a communication channel, record timestamps/actions, and keep troubleshooting controlled.

My sequence is:

```text
Alert
  ↓
Validate
  ↓
Assess impact / severity
  ↓
Declare incident if needed
  ↓
Check recent changes + platform health
  ↓
Mitigate customer impact
  ↓
Investigate systematically
  ↓
Validate recovery
  ↓
RCA later
```

Azure Service Health is specifically intended to surface service issues affecting the user's Azure resources/subscriptions, while Resource Health helps determine the health of individual resources. ([Microsoft Learn][10])

---

## **1. Validate the alert**

First ask:

```text
Is this real?
```

Check:

```text
synthetic probe
application endpoint
Azure Monitor
Application Insights
external health check
```

For example:

```bash
curl -I https://api.example.com/health
```

But I don't rely on one local laptop result.

Maybe:

```text
India affected
Europe healthy
```

or only:

```text
one Availability Zone
```

is failing.

---

# **2. Determine user impact**

I quickly answer:

```text
Who is affected?
What functionality?
How many users?
Which region?
When did it start?
Is data at risk?
```

Examples:

### Minor

```text
Internal reporting page slow
5% users
workaround available
```

### Major

```text
Public checkout unavailable
all regions
payments failing
```

These require different severity and escalation.

---

# **3. Determine scope**

Break it down by:

```text
service
region
version
endpoint
tenant/customer
dependency
```

Example:

```text
Global frontend healthy
Checkout failing
Only centralindia
Only version v42
```

That is much more actionable than:

```text
"Production down"
```

---

# **4. Establish start time**

Find the first evidence:

```text
5xx began 01:47
latency rose 01:46
deployment completed 01:45
```

Now:

```text
recent deployment
```

becomes a strong hypothesis.

Timeline is one of the most valuable incident artifacts.

---

# **5. Check recent changes early**

Ask:

```text
What changed immediately before the incident?
```

Check:

```text
application releases
Terraform applies
feature flags
database migrations
NSG/firewall changes
Key Vault/secret changes
DNS
certificates
autoscaling
```

Azure Activity Log can show recent control-plane changes, while deployment tooling provides application-change history.

A large percentage of operational failures correlate strongly with recent change.

But:

```text
recent change
≠
automatically root cause
```

It's a hypothesis to test.

---

# **6. Check Azure platform health**

Before spending 40 minutes changing the application, determine whether Azure itself has an issue.

Check:

```text
Azure Service Health
Resource Health
```

Service Health can show:

```text
regional service incidents
planned maintenance
service advisories
```

Resource Health can help identify whether a specific resource is:

```text
Available
Unavailable
Degraded
Unknown
```

Azure's current Service Health tooling provides subscription/region/resource context plus Activity Log integration for relevant alerts. ([Microsoft Learn][10])

---

# **7. Look at user-facing golden signals**

I start high in the stack:

```text
Traffic
Errors
Latency
Saturation
```

Examples:

```text
requests/sec
5xx
p95/p99
CPU/memory/connections
```

Why high-level first?

Because:

```text
CPU = 95%
```

doesn't tell me whether users are failing.

But:

```text
checkout 5xx = 70%
```

does.

Start from impact and drill downward.

---

# **8. Trace the request path**

For a three-tier service:

```text
Client
  ↓
Front Door
  ↓
Application Gateway
  ↓
Frontend/API
  ↓
Backend
  ↓
SQL
```

Find the first failing boundary.

Example:

```text
Front Door → healthy
App Gateway → 502
Backend Pods → Ready
Backend → SQL = timeout
```

Now investigation shifts to:

```text
SQL/network dependency path
```

rather than randomly restarting Front Door.

---

# **9. Use distributed traces when available**

A trace might show:

```text
Request total = 12 sec

Frontend       20 ms
Backend        70 ms
SQL dependency 11.8 sec
```

Now I have evidence:

```text
database dependency
```

is driving latency.

This is much more useful than checking every component equally.

---

# **10. Mitigation before root cause**

During active user impact:

```text
Restore service
>
complete RCA
```

Examples of fast mitigation:

```text
Rollback bad release
Disable feature flag
Fail over region
Scale capacity
Remove unhealthy backend
Restore previous configuration
```

Once customers are stable, deeper diagnosis can continue.

This distinction is important:

```text
Mitigation:
Stop the pain

Root-cause correction:
Prevent recurrence
```

They are not necessarily the same action.

---

# **11. Don't restart everything**

A weak incident response:

```text
Restart Pods
Restart database
Restart gateway
Restart VM
```

Problems:

```text
destroys evidence
can worsen outage
introduces more variables
may mask root cause
```

Every action should have a hypothesis:

```text
What do I expect this change to prove or improve?
```

---

# **12. Establish incident ownership**

For a major incident:

```text
Incident Commander / Owner
```

coordinates.

Other roles may include:

```text
Technical lead
Communications
Scribe/timeline owner
Subject matter experts
```

This prevents:

```text
five engineers
making five unrelated Prod changes
```

at the same time.

---

# **13. Start an incident timeline**

Record:

```text
01:47 alert fires
01:49 incident acknowledged
01:52 v42 release correlated
01:55 rollout paused
02:00 rollback initiated
02:04 error rate recovering
```

Also record:

```text
commands/actions
decisions
hypotheses
observations
```

This becomes invaluable during:

```text
handoff
communication
postmortem
```

---

# **14. Communicate impact, not speculation**

Initial update:

```text
"Checkout requests are failing for users in Region A.
We are investigating a deployment completed shortly before the issue
and have stopped further rollout."
```

Better than:

```text
"Database is definitely broken."
```

before evidence exists.

Communicate:

```text
Known impact
Actions underway
Mitigation status
```

and keep root-cause speculation internal until verified.

# **15. Example: AKS outage**

Alert:

```text
API availability < 90%
```

I check:

```bash
kubectl get pods -A
kubectl get nodes
kubectl get events -A --sort-by=.lastTimestamp
```

But only after determining that the request path points toward AKS.

Possible findings:

```text
Nodes Ready
Pods Running
```

yet:

```text
5xx high
```

Then infrastructure availability isn't the issue.

Check:

```text
application logs
dependency traces
recent deployment
```

# **16. Example: all Pods Pending**

If:

```text
checkout Pods
→ Pending
```

then:

```bash
kubectl describe pod <pod>
```

may reveal:

```text
0/5 nodes are available:
Insufficient cpu
```

Now dependency chain is:

```text
Deployment
 ↓
Scheduler
 ↓
Node capacity
 ↓
Cluster Autoscaler/quota
```

That gives a concrete hypothesis.

---

# **17. Example: gateway 502**

Path:

```text
User
 ↓
Application Gateway
 ↓
502
```

Check:

```text
Backend health
```

If all backends unhealthy:

```text
Application Gateway itself
may be functioning correctly
```

The failure is downstream.

Then inspect:

```text
backend health probe
DNS
port
TLS
application readiness
```

---

# **18. Example: timeout to database**

Application logs:

```text
SQL connection timeout
```

Check in dependency order:

```text
1. Database service health
2. DNS
3. Private Endpoint resolution
4. route
5. NSG/firewall
6. TCP reachability
7. authentication
8. DB saturation
```

Notice:

```text
timeout
```

usually points first toward:

```text
network/service availability
```

while:

```text
403
```

points more toward authorization.

---

# **19. Check whether there is data risk**

Outage response changes significantly if:

```text
data corruption
duplicate payments
lost writes
security breach
```

is possible.

If correctness is uncertain, I may prefer:

```text
temporarily stop writes
```

rather than continue processing potentially corrupt transactions.

Availability should not override data integrity.

---

# **20. Validate recovery independently**

After mitigation:

```text
dashboard green
```

isn't enough.

Confirm:

```text
synthetic transaction succeeds
real traffic normal
5xx baseline
latency baseline
queue catching up
database healthy
```

If a payment system:

```text
complete one safe end-to-end payment test
```

or equivalent.

Only then can I say the service is restored.

## **Practical first 10-minute flow**

```text
Minute 0–2
Acknowledge alert
Validate impact
Identify affected service/region

Minute 2–4
Declare incident/severity if needed
Open incident channel
Assign owner
Check recent changes

Minute 4–6
Check Azure Service Health/Resource Health
Review top-level metrics/traces

Minute 6–10
Identify likely failing boundary
Apply safest high-confidence mitigation
such as rollback/failover/feature disablement
```

The exact times aren't rigid—the important thing is the **ordered reasoning**.

### **Interview answer condensed**

> “When I receive a production outage alert, I first validate that the alert represents real customer impact and determine the scope—service, region, version, affected functionality and start time. I check recent deployments/configuration changes and Azure Service Health or Resource Health to separate an application problem from a platform issue. Then I use user-facing signals such as availability, 5xx and latency and trace the request path until I find the first failing dependency. If there's a safe high-confidence mitigation such as reverting a recent release, failing over, or disabling a feature, I restore service first rather than spending the outage proving root cause. For a major incident I assign an incident owner, start a timeline and communication channel, control production changes, and validate recovery with real transactions and metrics before closing the incident.”

**Memory line:**
**Validate → scope → correlate changes → mitigate → investigate → verify recovery.**

**Interview trap:**
Do not start an outage by **restarting everything**; it can destroy evidence, introduce new variables, and make the incident harder to understand.

production outage, incident response, Service Health, Resource Health, golden signals, change correlation, mitigation, incident commander, timeline, recovery validation.
