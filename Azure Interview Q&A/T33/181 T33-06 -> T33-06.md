# **T33-06. What is a blue-green deployment?**

**Answer:**

A blue-green deployment is a release strategy where I maintain **two complete application environments**: one environment, usually called **Blue**, is currently serving production traffic, while the other, **Green**, runs the new release.

I deploy and validate the new version on Green without disturbing Blue. Once Green passes health checks, smoke tests, and any required business validation, I switch production traffic from Blue to Green through the load balancer, gateway, DNS layer, or platform-specific mechanism.

The major advantage is that the traffic switch can be very fast, and if the new version fails I can usually redirect traffic back to Blue quickly. The biggest trade-offs are **extra infrastructure cost** and the fact that database or state changes can make rollback much harder than simply switching traffic.

```text
Before release

Users
  │
  ▼
BLUE — v1
  │
  ▼
Database

GREEN — v2
(no production traffic)
```

After validation:

```text
Users
  │
  ▼
GREEN — v2
  │
  ▼
Database

BLUE — v1
(kept temporarily for rollback)
```

---

## **How it works**

Assume production currently runs:

```text
Blue
Version = v41
```

I create or already maintain:

```text
Green
Version = v42
```

The deployment sequence is:

```text
1. Blue continues serving users
2. Deploy v42 to Green
3. Warm Green
4. Run health checks
5. Run smoke/integration tests
6. Confirm dependencies
7. Switch traffic Blue → Green
8. Closely monitor
9. Keep Blue available temporarily
10. Retire Blue after stabilization
```

The key difference from rolling deployment is that I don't progressively replace individual Blue instances.

I prepare the **entire Green environment first**.

---

# **1. The traffic switch is the release point**

Until traffic changes:

```text
Blue = production
Green = candidate
```

At cutover:

```text
Traffic
Blue → Green
```

That switch could be implemented through:

* Azure Front Door,
* Application Gateway/backend configuration,
* App Service deployment slot swap,
* Kubernetes Service/Ingress routing,
* another load-balancing layer.

The exact mechanism depends on the application platform.

---

# **2. Azure App Service deployment slots are a classic example**

With App Service:

```text
Production slot
→ v41

Staging slot
→ v42
```

I can deploy and warm the staging slot.

Then:

```text
slot swap
```

makes the staging version become production.

Conceptually:

```text
Before swap

Production → v41
Staging    → v42


After swap

Production → v42
Staging    → v41
```

That is very close to blue-green behavior.

It can provide a quick application-level rollback if the old slot remains usable.

---

# **3. Kubernetes blue-green**

Suppose AKS hosts checkout.

I could deploy:

```text
checkout-blue
image: checkout:v41

checkout-green
image: checkout:v42
```

Then Service initially targets:

```yaml
selector:
  version: blue
```

After validation:

```yaml
selector:
  version: green
```

Traffic switches to the Green Pods.

Conceptually:

```text
               Kubernetes Service
                       │
                version=blue
                       │
                  checkout-v41
```

Then:

```text
               Kubernetes Service
                       │
                version=green
                       │
                  checkout-v42
```

The Service selector—or a more sophisticated ingress/traffic mechanism—becomes the switch.

---

# **4. Why is rollback fast?**

Suppose Green immediately starts returning 10% errors.

If Blue has remained untouched:

```text
Traffic
Green → Blue
```

can restore the previous application version very quickly.

That is one of the strongest advantages over deployments where the old environment has already been destroyed.

But this fast rollback only applies cleanly if:

```text
data/schema/configuration
```

remain compatible with Blue.

---

# **5. Database changes are the biggest catch**

Imagine:

```text
Blue = v1
Green = v2
```

but before switching traffic v2 changes the database:

```sql
DROP COLUMN legacy_status;
```

Blue still expects:

```text
legacy_status
```

Now Green fails.

You switch traffic back:

```text
Green → Blue
```

but Blue fails too because the shared database schema changed.

Therefore:

```text
Blue-green application deployment
≠
automatic blue-green database rollback
```

For stateful systems I prefer backward-compatible schema evolution.

---

# **6. Use expand-and-contract**

Safer approach:

### Phase 1

Add new schema while preserving old:

```text
OldColumn
NewColumn
```

### Phase 2

Deploy Green that understands both.

### Phase 3

Switch traffic.

### Phase 4

Stabilize.

### Phase 5

Remove old schema later.

Now:

```text
Green fails
→ Blue can still use database
```

Rollback remains practical.

---

# **7. Configuration must also support both environments**

Blue:

```text
KEYVAULT_URI=kv-prod
DB_HOST=sql-prod
```

Green should use equivalent production dependencies unless deliberately isolated.

A dangerous pattern is validating Green against:

```text
test database
```

then switching it to:

```text
production database
```

only at cutover.

You have not really tested production dependency behavior.

---

# **8. State and sessions need attention**

Suppose Blue stores sessions locally.

At cutover:

```text
User session
exists only on Blue
```

Traffic moves to Green:

```text
session missing
→ user logged out
```

For smoother blue-green switching, prefer:

```text
external session store
token-based sessions
shared durable state
```

where appropriate.

---

# **9. Blue-green capacity cost**

If production needs:

```text
20 application instances
```

Blue-green may temporarily require:

```text
Blue = 20
Green = 20
Total = 40
```

So the trade-off is:

```text
Fast/safe traffic switching
        vs
Additional infrastructure cost
```

This matters for:

* large AKS node pools,
* expensive VMs,
* GPU workloads,
* large App Service plans.

---

# **10. Blue-green is excellent when validation needs a complete environment**

Some changes are difficult to validate with only 1% of traffic.

For example:

```text
runtime upgrade
large platform change
new base image
network redesign
```

Blue-green lets me fully construct Green first and validate:

```text
startup
DNS
identity
dependencies
configuration
capacity
```

before exposing users.

---

# **11. But don't keep Blue and Green permanently identical manually**

If environments are manually built:

```text
Blue configured one way
Green configured another way
```

the deployment strategy becomes risky.

Use:

```text
Terraform/Bicep
Helm/Kustomize
CI/CD
```

so both sides come from the same definition.

---

# **12. Validation before traffic switch**

I would check:

```text
Application health
Readiness
Database connectivity
Key Vault access
External APIs
Critical transactions
Logs/traces
Resource saturation
Configuration version
Image digest
```

Then perform the switch.

For a critical service I may also run:

```text
synthetic production-like tests
```

against Green before public traffic.

---

# **13. Monitor after the switch**

Switching traffic is not the end.

Immediately compare:

```text
Before:
Blue 5xx = 0.2%
Blue p95 = 350 ms

After:
Green 5xx?
Green p95?
checkout success?
```

If Green violates predetermined thresholds:

```text
traffic → Blue
```

while Blue remains available.

---

# **14. When do I destroy Blue?**

Not:

```text
30 seconds after successful switch
```

I'd wait through an agreed stabilization period.

For example:

```text
Traffic moved
   ↓
15 min intense validation
   ↓
several hours/one business cycle
   ↓
confidence gained
   ↓
Blue retired
```

Duration depends on workload risk and cost.

---

## **Blue-green vs rolling**

### Rolling

```text
v1 v1 v1 v1
 ↓
v2 v1 v1 v1
 ↓
v2 v2 v1 v1
 ↓
v2 v2 v2 v2
```

Low extra capacity.

But:

```text
v1 + v2 coexist
```

during rollout.

### Blue-green

```text
Entire Blue v1
+
Entire Green v2
```

Then switch traffic.

Rollback can be much faster.

But requires more capacity.

---

## **Blue-green vs canary**

Blue-green primarily controls:

```text
environment switch
```

Canary primarily controls:

```text
how much real user traffic
new version receives
```

A pure blue-green switch might be:

```text
0% Green
→
100% Green
```

A canary might be:

```text
1%
→ 5%
→ 25%
→ 50%
→ 100%
```

You can also combine the concepts.

---

### **Interview answer condensed**

> “Blue-green deployment means maintaining two production-capable environments. Blue runs the current version while Green is deployed with the new version and tested independently. Once Green is healthy, I switch production traffic to it through the routing or load-balancing layer. If the release fails, I can redirect traffic back to Blue quickly as long as the previous environment and shared data remain compatible. The advantage is fast cutover and rollback; the trade-off is that I temporarily maintain duplicate capacity, and database changes still require backward-compatible migration because switching the application doesn't automatically roll the data layer back.”

**Memory line:**
**Blue serves users while Green is prepared; release means switching traffic, not replacing instances one by one.**

**Interview trap:**
Blue-green gives a fast **application traffic rollback**, but it does not automatically undo database or irreversible state changes.

**Keywords:**
Blue-green, traffic switch, deployment slots, parallel environments, rollback, App Service slots, AKS Service selector, expand-and-contract.

* How would App Service deployment slots support this pattern?

* What is the main cost disadvantage of blue-green?
* How long would you keep Blue after switching to Green?

# **T33-07. What is a canary deployment?**

**Answer:**

A canary deployment is a release strategy where I expose the **new version to only a small percentage of production traffic first**, observe its health and business metrics, and gradually increase traffic only if it behaves correctly.

For example, I might send 5% of traffic to v2 while 95% stays on v1. If v2 has acceptable error rate, latency, dependency behavior, and business transaction success, I increase it to 25%, then 50%, and eventually 100%.

If the canary performs badly, I stop the rollout and direct that small percentage back to the known-good version.

The main benefit is **blast-radius reduction**: I'm validating the release under real production conditions without risking the whole user base immediately.

```text
             Production Traffic
                    │
             ┌──────┴──────┐
             │             │
            95%            5%
             │             │
             ▼             ▼
          v1 stable     v2 canary
                           │
                           ▼
                    Observe health
```

If healthy:

```text
5% → 25% → 50% → 100%
```

If unhealthy:

```text
5% → 0%
```

---

## **1. Why production traffic matters**

Staging cannot perfectly reproduce:

```text
real users
real production data
real traffic shape
real external dependencies
real concurrency
```

A canary gives me controlled production evidence.

For example, a release may work perfectly in staging but fail only when:

```text
10,000 concurrent users
```

trigger a connection-pool issue.

With a canary:

```text
small production subset
```

exposes the problem before the entire fleet is upgraded.

---

# **2. Canary is fundamentally risk control**

Suppose v42 has a severe bug.

### Immediate deployment

```text
100% users
→ v42

100% blast radius
```

### 5% canary

```text
5% users
→ v42

95%
→ v41
```

The error is still bad, but its initial impact is much smaller.

That's why canary deployment is attractive for high-traffic or business-critical systems.

---

# **3. A typical canary sequence**

Example:

```text
Stage 1
1% traffic
10 minutes

Stage 2
5%
15 minutes

Stage 3
25%
30 minutes

Stage 4
50%
30 minutes

Stage 5
100%
```

At every stage evaluate:

```text
5xx
p95/p99 latency
resource saturation
dependency failure rate
business transaction success
```

Only proceed when the candidate version meets acceptance criteria.

---

# **4. The important part isn't the percentage**

People sometimes think:

```text
Canary = deploy one Pod
```

Not necessarily.

Canary means:

> Deliberately limit exposure to the new version and evaluate it before broader rollout.

Traffic may be controlled by:

```text
percentage
specific users
geography
tenant
internal employees
request header
feature cohort
```

depending on routing capability.

---

# **5. Kubernetes implementation**

Suppose:

```text
checkout-v1
checkout-v2
```

both run in AKS.

A basic Service cannot inherently guarantee a precise stable percentage across two arbitrary Deployments just by wishing for it.

For controlled weighted routing I may use:

```text
ingress/service-mesh capabilities
Argo Rollouts
another traffic-management controller
```

depending on the platform.

Conceptually:

```text
Ingress
  │
  ├── 95% → checkout-v1
  └──  5% → checkout-v2
```

Then the rollout controller adjusts weights.

---

# **6. Replica-ratio canary is less precise**

One simple approach:

```text
19 old Pods
1 new Pod
```

behind one Kubernetes Service.

Roughly:

```text
~5% capacity
```

is new.

But actual traffic distribution may not equal exactly 5% because of:

```text
connection reuse
different request durations
load-balancing behavior
Pod capacity differences
```

So for controlled production experiments, explicit traffic weighting is better.

---

# **7. Canary health should compare candidate vs baseline**

Suppose global error rate is:

```text
1%
```

That sounds healthy.

But:

```text
v1 = 0.1%
v2 = 15%
```

and v2 receives only 5% traffic.

Global metrics can hide the candidate regression.

I need telemetry by:

```text
version
deployment
pod/ReplicaSet
```

Example:

```text
service.version=v41
service.version=v42
```

Then compare:

```text
Canary vs baseline
```

rather than only global service health.

---

# **8. Use business metrics too**

Technical metrics might say:

```text
HTTP 200
latency normal
```

but v42 could incorrectly calculate:

```text
discount = ₹0
```

for every order.

So canary gates may include:

```text
checkout conversion
payment success
order creation
login success
```

where relevant.

A release can be technically healthy yet functionally wrong.

---

# **9. Automated analysis**

A mature canary platform might evaluate:

```text
v42 error rate <= baseline + threshold
AND
v42 p95 <= threshold
AND
payment success >= threshold
```

If true:

```text
increase traffic
```

If false:

```text
abort
```

This is much safer than:

> “Someone looked at Grafana and it seemed fine.”

---

# **10. Canary rollback is usually exposure reduction**

If candidate fails:

```text
v2 weight:
5% → 0%
```

Then:

```text
v1 = 100%
```

Users immediately stop reaching the broken version.

Afterward I can:

```text
scale v2 down
preserve logs
investigate
```

That's faster than necessarily rebuilding anything.

---

# **11. Database compatibility still matters**

v1 and v2 run concurrently.

Therefore the database must support:

```text
v1
+
v2
```

during the canary period.

If v2 performs:

```sql
DROP COLUMN needed_by_v1;
```

then:

```text
95% of traffic
still on v1
```

could immediately fail.

Canary absolutely depends on backward-compatible state/API evolution.

---

# **12. API contracts must be compatible too**

Suppose Service A canary sends:

```json
{
  "statusV2": "paid"
}
```

to Service B v1, which doesn't understand the field/schema.

The canary may fail even though A itself is healthy.

Contract testing and backward compatibility are important for microservices.

---

# **13. Long-lived connections complicate traffic weighting**

WebSockets, streaming, or long-lived HTTP connections can mean:

```text
change weight 5% → 0%
```

doesn't immediately terminate already-established sessions.

So rollback speed depends on:

```text
connection lifetime
load-balancer behavior
session affinity
```

not only configured percentages.

---

# **14. Sticky sessions can bias the canary**

If sessions are sticky:

```text
User A always → v2
```

then the same subset may continuously experience the canary.

That can be useful if intentional:

```text
cohort-based canary
```

but it changes how I interpret:

```text
traffic percentage
```

and user impact.

---

# **15. Canary duration must be representative**

Five minutes may catch:

```text
startup failures
immediate 5xx
```

but not:

```text
memory leak after 3 hours
daily batch failure
cache expiry issue
```

The canary observation window should match likely failure modes.

For some services:

```text
10 minutes
```

is enough.

For others:

```text
a full business cycle
```

may be more meaningful.

---

# **16. Example**

Current:

```text
checkout v41
5xx = 0.2%
p95 = 400ms
payment success = 99.7%
```

Canary v42 at 5%:

```text
5xx = 0.3%
p95 = 420ms
payment success = 99.6%
```

Acceptable.

Increase:

```text
5% → 25%
```

Later:

```text
v42 5xx = 6%
payment success = 91%
```

Automatic analysis:

```text
FAIL
```

Action:

```text
v42 traffic → 0%
v41 traffic → 100%
```

That's the value of controlled exposure.

---

## **Canary vs rolling**

Rolling:

```text
replace instances gradually
```

but the percentage of traffic isn't necessarily used as an intentional validation gate.

Canary:

```text
intentionally expose limited traffic
+
measure
+
decide
```

The observation/decision loop is central.

---

## **Canary vs feature flag**

Canary:

```text
new application version
→ selected traffic
```

Feature flag:

```text
same deployed code
→ selected feature behavior
```

They can work together.

For example:

```text
canary v42 to 5%
+
inside v42
new checkout feature enabled for 10% of that cohort
```

though complexity must be justified.

---

### **Interview answer condensed**

> “A canary deployment exposes a new version to a small portion of real production traffic first—for example 5%—while the stable version serves the rest. I compare candidate and baseline metrics such as 5xx, p95/p99 latency, dependency errors and critical business success rates. If the canary remains healthy, I progressively increase traffic to 25%, 50% and eventually 100%; if health degrades, I set the candidate weight back to zero. The main benefit is reducing blast radius while validating under real production conditions. Because old and new versions coexist, database schemas and service contracts must remain backward compatible.”

**Memory line:**
**Canary means expose a little, measure, then expand only when evidence says the new version is safe.**

**Interview trap:**
Canary is not simply **“deploy one new Pod”**—the important part is controlled exposure plus objective validation before increasing it.

**Keywords:**
Canary, weighted traffic, blast radius, progressive delivery, baseline comparison, SLO health gate, Argo Rollouts, backward compatibility.

# **T33-08. When would you choose canary over blue-green?**

**Answer:**

I would choose canary over blue-green when the main risk is **unknown behavior under real production traffic** and I want to limit exposure while collecting evidence.

Canary is especially useful for high-traffic, customer-facing services where a bug affecting 5% of users is much safer than switching 100% of users to the new release at once.

I would prefer blue-green when I need to prepare and validate an entire replacement environment before a quick traffic cutover, or when rapid full-environment rollback is more important than gradual real-user validation.

The simple distinction is:

```text
Blue-green:
"Is the complete new environment ready?
Then switch."

Canary:
"Does the new version behave safely
with real users?
Then gradually increase exposure."
```

## **Decision model**

```text
                           New release
                               │
                Need real-production risk sampling?
                         /              \
                       Yes               No
                       │                 │
                    Canary        Need full parallel
                                  environment/cutover?
                                      │
                                   Blue-green
```

In practice, the choice also depends on:

```text
cost
traffic routing capability
database compatibility
release risk
application architecture
rollback requirements
```

---

# **1. Choose canary for high-risk behavior changes**

Example:

```text
new recommendation algorithm
new checkout logic
major application refactor
runtime upgrade
```

The application technically works in staging, but I'm unsure how it behaves with:

```text
real users
real concurrency
real production data
```

Canary lets me expose:

```text
1–5%
```

first.

This is particularly useful when failures may be subtle rather than immediate startup failures.

---

# **2. Choose canary for very large user bases**

Suppose the platform serves:

```text
20 million users
```

Blue-green cutover:

```text
0% new
→
100% new
```

If a bug appears:

```text
potentially everyone affected
```

Canary:

```text
1%
→
5%
→
20%
```

lets me stop much earlier.

For a highly visible internet service, reducing release blast radius can justify the extra routing/observability complexity.

---

# **3. Choose canary when production traffic is hard to reproduce**

Staging rarely reproduces:

```text
production concurrency
customer data distributions
real geographic traffic
third-party latency
request diversity
```

If those factors matter heavily, canary gives stronger evidence than an isolated Green environment.

Blue-green Green can be fully healthy under synthetic tests and still fail at production traffic scale.

---

# **4. Choose canary when I want quantitative rollout gates**

Suppose my release policy is:

```text
Proceed only if:

5xx < 1%
p95 < 500ms
payment success > 99.5%
```

Canary naturally supports:

```text
deploy 5%
measure
decide
```

then repeat.

It's excellent for automated progressive delivery.

---

# **5. Choose blue-green for whole-environment changes**

Suppose I'm changing:

```text
operating system
runtime
major networking configuration
entire application stack
```

I may want a fully constructed Green environment:

```text
build
warm
validate
```

before switching any users.

Blue-green is often cleaner for that.

---

# **6. Blue-green gives a simpler fast traffic rollback**

Blue-green:

```text
Green fails
     ↓
Traffic → Blue
```

provided shared data remains compatible.

Canary rollback:

```text
v2 weight → 0%
```

is also fast.

But blue-green keeps a complete known-good environment intact, making a total environment-level cutback especially straightforward.

---

# **7. Capacity cost comparison**

Suppose app requires:

```text
100 instances
```

### Blue-green

During migration:

```text
Blue = 100
Green = 100
Total ≈ 200
```

### Canary

Initially:

```text
Stable = 100
Canary = maybe 5–10 additional capacity
```

depending on rollout design.

Therefore if duplicate full-environment cost is high:

```text
canary
```

may be more attractive.

But eventually canary still has to replace/scale the whole release.

---

# **8. Canary requires stronger observability**

Canary only works if I can answer:

```text
How is v42 performing specifically?
```

I need telemetry segmented by:

```text
version
route
cohort
Pod
```

If all I have is:

```text
global CPU
```

I may not notice that the 5% canary is failing.

Blue-green can sometimes be operationally simpler because the environment boundary itself is obvious.

---

# **9. Canary requires traffic-management capability**

Need some way to control:

```text
95% stable
5% canary
```

Potentially:

```text
Front Door/routing layer
Ingress controller
service mesh
Argo Rollouts integrations
application-level cohort logic
```

If the platform cannot reliably split traffic:

```text
blue-green
```

may be easier.

---

# **10. Database compatibility is required for both—but especially canary**

During canary:

```text
v1 + v2
```

are definitely active simultaneously for an observation period.

The database must support both.

Blue-green can reduce the mixed-version duration, but even Blue may remain a rollback target.

So backward-compatible schema design is valuable for both.

---

# **11. Choose canary for continuous high-frequency delivery**

If teams deploy:

```text
10 times/day
```

maintaining a full Green environment and performing complete environment swaps every time may be excessive.

Canary/progressive delivery can integrate naturally into:

```text
frequent small releases
```

where automated health checks gradually increase exposure.

---

# **12. Choose blue-green when release frequency is lower but cutover is high-impact**

For example:

```text
monthly enterprise application release
```

with a complex runtime change.

Maintaining or temporarily provisioning an entire Green stack may be perfectly acceptable.

The organization values:

```text
controlled rehearsal
+
clear switch
+
quick environment rollback
```

more than gradual user sampling.

```text
Canary

```

```text
Blue-green
```

| Requirement                              |             Canary |                  Blue-green |
| ---------------------------------------- | -----------------: | --------------------------: |
| Reduce user blast radius gradually       |         **Strong** |                    Moderate |
| Validate with real traffic               |         **Strong** | Can, but often after switch |
| Full parallel environment validation     |           Possible |                  **Strong** |
| Full environment cutback                 |               Good |               **Excellent** |
| Minimize duplicate infrastructure        | **Usually better** |              More expensive |
| Requires sophisticated traffic splitting |            **Yes** |      Usually simpler switch |
| Frequent small releases                  |         **Strong** |                    Possible |
| Major platform/environment replacement   |           Possible |                  **Strong** |

---

### **Interview answer condensed**

> “I would choose canary when I need evidence from real production traffic while minimizing blast radius—for example a high-volume customer-facing service, frequent releases, or a risky behavioral change that staging can't fully reproduce. I'd expose perhaps 1–5% of traffic, compare candidate metrics against the stable version, and expand only when health gates pass. I would choose blue-green when I want to prepare and validate an entire replacement environment and then perform a fast full cutover with a complete previous environment available for rollback. Canary generally requires better traffic control and observability, while blue-green usually requires more duplicate infrastructure. They can also be combined by progressively shifting traffic from Blue to Green.”

**Memory line:**
**Choose canary to learn safely from real traffic; choose blue-green to prepare a whole replacement environment before switching.**

**Interview trap:**
Canary and blue-green are **not mutually exclusive**—a Green environment can itself receive traffic progressively as a canary.

**Keywords:**
canary, blue-green, blast radius, progressive delivery, real traffic, weighted routing, duplicate capacity, rollback.

**Likely follow-ups:**

* Can blue-green and canary be combined?
* Which requires more infrastructure capacity?
* Which requires stronger observability?
* Which would you choose for a global e-commerce checkout service?
* How does database compatibility influence this decision?

# **T33-09. How would you perform an automatic rollback?**

**Answer:**

I would implement automatic rollback as part of a **progressive deployment with predefined health gates**, not simply “rollback whenever one metric spikes.”

The pipeline or rollout controller would deploy a small amount of the new version, monitor candidate-specific signals such as availability, 5xx rate, p95/p99 latency, critical business transaction success, and dependency health over a defined observation window, and compare them against explicit thresholds or the stable baseline.

If a critical threshold is breached, the controller stops further rollout and restores traffic or desired state to the last known-good immutable version.

For Kubernetes, that could mean an advanced rollout controller such as Argo Rollouts reducing canary traffic to zero and restoring the stable ReplicaSet. In a simpler CI/CD design, the pipeline can revert the Deployment image or GitOps desired state after health validation fails.

I would only automate rollback when it is **known to be safe**. Database migrations and other irreversible state changes need separate handling; otherwise automatic application rollback could make the outage worse.

```text
New release
    ↓
Deploy 5%
    ↓
Observe health
    ↓
 ┌───────────────┐
 │ Gates passing?│
 └───────┬───────┘
       /   \
     Yes    No
      │      │
      ▼      ▼
  Increase   Stop rollout
  traffic       ↓
              Restore
             stable version
                 ↓
              Validate
```

---

## **1. First define the known-good release**

Before deployment I need an immutable identity:

```text
Stable:
checkout@sha256:AAA

Candidate:
checkout@sha256:BBB
```

Not:

```text
stable = latest
```

because `latest` can change.

Rollback must answer exactly:

> **What artifact am I restoring?**

---

# **2. Define health gates before deployment**

Example release policy:

```text
Canary duration:
10 minutes

Continue if:
5xx < 1%
AND
p95 < 600ms
AND
payment success > 99.5%

Rollback immediately if:
5xx > 5%
OR
critical transaction fails
OR
availability < 99%
```

This prevents emotional decision-making during an incident.

---

# **3. Separate warning from rollback thresholds**

A transient spike should not necessarily undo a release.

For example:

```text
Warning:
5xx > 1% for 2 minutes

Rollback:
5xx > 5% for 5 minutes
```

or more sophisticated burn-rate analysis.

This avoids:

```text
one bad request
→ automatic global rollback
```

which can itself cause instability.

---

# **4. Use an observation window**

Suppose p95 briefly spikes:

```text
400ms → 1.2s
for 10 seconds
```

during Pod warmup.

Then returns:

```text
420ms
```

An instantaneous rollback threshold could be too sensitive.

Use:

```text
evaluation duration
+
minimum sample count
```

appropriate to traffic volume.

For low-traffic services, percentage-based metrics can also be misleading when only a handful of requests exist.

---

# **5. Candidate-specific telemetry is essential**

Suppose:

```text
Stable = 95% traffic
Canary = 5%
```

Global 5xx might be:

```text
0.8%
```

which looks acceptable.

But:

```text
Stable = 0.1%
Canary = 14%
```

The candidate is clearly broken.

The rollback controller should evaluate:

```text
v42-specific signals
```

not just the blended service metric.

---

# **6. Simple Kubernetes pipeline rollback**

Suppose a normal Deployment uses:

```text
checkout:v42
```

Pipeline deploys it.

Then waits:

```bash
kubectl rollout status deployment/checkout --timeout=5m
```

If rollout itself fails:

```bash
kubectl rollout undo deployment/checkout
```

could restore the previous ReplicaSet.

This catches:

```text
readiness failures
crash loops
insufficient availability
```

but not necessarily:

```text
business logic returns incorrect result
```

Therefore infrastructure rollout status alone isn't enough.

---

# **7. Add external health verification**

After Kubernetes says:

```text
Successfully rolled out
```

pipeline should still test:

```text
synthetic checkout
API health
5xx metric
p95
business event
```

because:

```text
all Pods Ready
```

does not mean:

```text
application correct
```

---

# **8. GitOps automatic rollback**

If Argo CD is the deployment controller and Git says:

```text
sha256:BBB
```

while an external health gate decides BBB is bad, durable rollback should eventually make Git say:

```text
sha256:AAA
```

again.

Possible flow:

```text
Rollout analysis fails
      ↓
Traffic restored to stable version
      ↓
GitOps promotion marked failed
      ↓
desired version reverted
      ↓
Argo reconciles stable state
```

I don't want:

```text
Cluster = AAA
Git = BBB
```

permanently.

Otherwise Argo may reintroduce the failed release.

---

# **9. Argo CD vs Argo Rollouts**

Important distinction:

```text
Argo CD
→ GitOps synchronization/reconciliation

Argo Rollouts
→ advanced rollout strategies such as
   canary/blue-green and analysis
```

Argo CD alone is not the same thing as a canary analysis engine.

A common production architecture is:

```text
Git
 ↓
Argo CD
 ↓
Rollout resource
 ↓
Argo Rollouts
 ↓
Canary progression
```

Then analysis metrics can determine whether the rollout proceeds or aborts.

---

# **10. Example automated canary logic**

```text
Stable v41 = 95%
Canary v42 = 5%
```

Collect for 10 minutes:

```text
v41:
5xx 0.2%
p95 410ms

v42:
5xx 7.1%
p95 1.8s
```

Policy:

```text
5xx > 3%
OR
p95 > 1s
→ FAIL
```

Controller action:

```text
v42 weight → 0
v41 weight → 100
rollout state → Aborted
```

That is a real automatic rollback loop.

---

# **11. Use multiple signals**

Do not make the whole release depend on:

```text
CPU > 80%
```

High CPU may simply mean the new version uses capacity more efficiently while users are fine.

Better hierarchy:

```text
1. Availability / critical business outcome
2. Error rate
3. Latency
4. Dependency health
5. Saturation/resource metrics
```

User-facing symptoms should usually carry more weight.

---

# **12. Compare against baseline where possible**

Absolute threshold:

```text
p95 < 500ms
```

is useful.

But candidate-vs-stable comparison can be stronger.

Example:

```text
Stable p95 = 200ms
Canary p95 = 480ms
```

Both are under 500ms.

Yet candidate is:

```text
2.4× slower
```

Maybe unacceptable.

Policy could include:

```text
candidate p95
<= stable p95 × 1.2
```

depending on application requirements.

---

# **13. Business metrics matter**

Suppose candidate:

```text
HTTP 200
p95 = 300ms
```

but:

```text
payment completion
99.8% → 92%
```

Technical health looks excellent.

Business health is terrible.

Rollback signal should include:

```text
critical transaction correctness/success
```

where measurable.

---

# **14. Dependency metrics matter too**

Candidate may introduce:

```text
3× more SQL calls
```

Current users look fine at 5% traffic.

But DB CPU rises:

```text
30% → 70%
```

If rollout goes to 100%:

```text
database likely saturates
```

A good rollout gate can detect this early.

---

# **15. Database rollback is not automatically safe**

Suppose deployment:

```text
1. Database schema change
2. New application
3. Health fails
4. Auto rollback app
```

If schema is incompatible with old version:

```text
automatic rollback
→ outage becomes worse
```

Therefore either:

```text
use backward-compatible migrations
```

or mark the deployment:

```text
automatic application rollback unsafe
```

and require a controlled fix-forward/DB recovery procedure.

This is probably the most important caveat in the whole question.

---

# **16. Feature flags can be a faster rollback**

Sometimes the problematic part isn't the entire application version.

New release:

```text
v42
```

contains:

```text
NewPricingAlgorithm=true
```

If the problem is isolated to that feature:

```text
flag → false
```

may restore service in seconds without application rollback.

So mitigation hierarchy can be:

```text
Disable feature
        ↓
Reduce canary exposure
        ↓
Rollback application
```

depending on architecture.

---

# **17. Avoid rollback loops**

Danger:

```text
Deploy v42
 ↓
fails
 ↓
rollback v41
 ↓
CI sees desired v42
 ↓
deploys v42 again
 ↓
fails
```

Automation must mark the release:

```text
FAILED / BLOCKED
```

so it does not continuously retry the same broken artifact.

In GitOps, the desired state must be reconciled accordingly.

---

# **18. Rollback itself should be monitored**

After rollback:

```text
v41 restored
```

I still check:

```text
availability
5xx
latency
critical transactions
DB health
```

because rollback can also fail.

Success condition is:

```text
service restored
```

not:

```text
rollback command exited 0
```

---

# **19. Protect against flapping**

Suppose metrics alternate:

```text
Healthy
Unhealthy
Healthy
Unhealthy
```

The controller should not:

```text
promote
rollback
promote
rollback
```

repeatedly.

Use:

```text
minimum observation periods
failure thresholds
stabilization
one-way promotion states
```

and once a release is aborted, require deliberate re-evaluation.

---

# **20. Example production workflow**

```text
1. CI builds sha256:BBB
2. Stage validation passes
3. Production canary gets 5%
4. Observe for 10 minutes
5. Compare:
   - availability
   - 5xx
   - p95
   - payment success
   - SQL dependency
6. Gates pass → 25%
7. Observe again
8. 5xx rises to 6%
9. Rollout controller aborts
10. Candidate traffic → 0%
11. Stable version → 100%
12. Desired state reverted/marked failed
13. Validate service recovered
14. Alert release owner
15. Preserve telemetry for RCA
```

That's an automatic rollback I would trust much more than:

```text
if CPU > 80
then kubectl undo
```

## **Troubleshooting a failed automatic rollback**

If rollback triggers but users still see errors, I check in dependency order:

```text
Desired stable version
        ↓
Deployment controller
        ↓
ReplicaSet/Pods
        ↓
Readiness
        ↓
Traffic routing
        ↓
Configuration
        ↓
Database/state
```

### Check desired version

Is Git/pipeline actually specifying:

```text
sha256:AAA
```

?

### Check rollout

```bash
kubectl rollout status deployment/checkout
```

Did stable replicas become available?

### Check routing

Is canary weight truly:

```text
0%
```

or are long-lived/sticky sessions still reaching it?

### Check database

Did candidate change state/schema in a way that the old version cannot handle?

This is why “rollback triggered” and “rollback succeeded” are different events.

### **Interview answer condensed**

> “I would implement automatic rollback as a health-gated progressive deployment. The previous known-good image is identified by an immutable digest, then the candidate receives a small amount of traffic. During a defined observation window I compare candidate-specific availability, 5xx, p95/p99, dependency behavior and critical business metrics against explicit thresholds and preferably the stable baseline. If a rollback threshold is crossed, the rollout controller stops promotion and restores traffic to the stable version. On AKS this can be done with a rollout controller such as Argo Rollouts, or more simply through pipeline health checks plus Deployment/GitOps rollback. I would only enable automatic rollback when the application and data changes are known to be backward compatible; an irreversible database migration can make automatic app rollback unsafe.”

**Memory line:**
**Automatic rollback = known-good artifact + limited exposure + objective health gates + automatic restoration when those gates fail.**

**Interview trap:**
Do not automatically rollback an application release when an **incompatible database or state migration has already occurred**.
