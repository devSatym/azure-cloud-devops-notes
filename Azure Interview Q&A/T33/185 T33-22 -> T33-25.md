# **T33-22. How do you determine incident severity?**

**Answer:**

I determine incident severity primarily from **business and customer impact**, not from how technically complicated the failure looks.

I would look at how many users are affected, whether a critical business function is unavailable, the geographic or tenant scope, whether data integrity or security is at risk, whether there is a workaround, and how quickly the impact is growing.

For example, a CPU spike on one AKS node may look serious technically but could be low severity if users are unaffected. On the other hand, a checkout API returning 500s for all customers could be Sev-1 even if the root cause is something simple like a bad configuration value.

I normally classify severity using predefined organizational criteria so engineers aren't debating severity during an outage.

Conceptually:

```text
Severity
=
Customer impact
+
Business criticality
+
Scope
+
Data/security risk
+
Urgency
```

A typical model could be:

```text
Sev-1 / Critical
→ major business-critical outage
→ broad customer impact
→ severe data/security risk
→ immediate coordinated response

Sev-2 / High
→ significant degradation
→ partial customer impact
→ important feature unavailable

Sev-3 / Medium
→ limited impact
→ workaround exists
→ noncritical functionality affected

Sev-4 / Low
→ minimal/no customer impact
→ informational or minor issue
```

The exact labels vary by company; what's important is that the criteria are explicit and consistent.

---

## **1. Start with customer impact**

My first questions are:

```text
Are users affected?
How many?
Which functionality?
For how long?
```

Examples:

### Scenario A

```text
One internal dashboard
→ unavailable
→ 3 employees affected
→ workaround available
```

Probably:

```text
Sev-3 / Sev-4
```

depending on the company.

### Scenario B

```text
Public checkout
→ 80% failure rate
→ all regions
→ no workaround
```

That's likely:

```text
Sev-1
```

even if infrastructure itself looks healthy.

---

# **2. Consider business criticality**

Not every application has equal business importance.

Compare:

```text
Marketing image service down
```

versus:

```text
Payment authorization down
```

Both may technically be:

```text
100% unavailable
```

but the second probably has a much greater:

```text
revenue
customer
regulatory
reputation
```

impact.

Severity should reflect that.

---

# **3. Determine scope**

I classify impact dimensions such as:

```text
Single user
Single tenant
Subset of customers
Single region
Multiple regions
Global
```

For example:

```text
5% of users in Central India
```

may be Sev-2.

But:

```text
5% of global payment transactions
```

could still justify Sev-1 depending on transaction volume and financial impact.

Percentage alone isn't enough.

---

# **4. Measure availability degradation**

Suppose service SLO:

```text
99.95%
```

and current availability:

```text
99.90%
```

versus:

```text
40%
```

Those represent completely different incidents.

Signals I use:

```text
availability
5xx rate
failed transactions
latency
queue delay
```

Severity should reflect the **actual service degradation**.

---

# **5. Latency can be an outage too**

A service doesn't have to return 500s to be severely impacted.

Suppose checkout normally takes:

```text
400 ms
```

but now:

```text
30 seconds
```

Most users abandon the transaction.

Technically:

```text
HTTP 200
```

may eventually return.

Operationally:

```text
service is effectively unavailable
```

So severity must include latency/user experience.

---

# **6. Data integrity increases severity dramatically**

Suppose:

```text
API unavailable
```

versus:

```text
API successfully processes
duplicate payments
```

The second may deserve higher severity.

If there is risk of:

```text
data corruption
lost transactions
duplicate transactions
incorrect balances
```

I would escalate quickly.

Sometimes the safest response is:

```text
disable writes
```

rather than maintain availability while damaging data.

---

# **7. Security incidents may need independent escalation**

Examples:

```text
Production secret publicly exposed
Unauthorized Key Vault access
Sensitive Storage data anonymously readable
Compromised privileged identity
```

may have low immediate application downtime but very high business/security severity.

So:

```text
Availability impact = low
```

does not imply:

```text
Incident severity = low
```

Security and compliance risk are separate dimensions.

---

# **8. Consider whether there is a workaround**

Example:

```text
Primary checkout endpoint fails
but
secondary checkout path works
```

Impact may be reduced.

Compare:

```text
No workaround
```

with:

```text
users can complete transaction
through another path
```

A viable workaround can lower operational severity even before root cause is fixed.

---

# **9. Consider how quickly the problem is growing**

Current:

```text
2% failure
```

might look moderate.

But telemetry shows:

```text
2%
→ 5%
→ 15%
→ 35%
```

within ten minutes.

That's escalating rapidly.

Severity assessment should consider:

```text
current impact
+
trajectory
```

not just the current snapshot.

---

# **10. Consider duration**

A 20-second transient failure might not justify the same response as:

```text
45-minute outage
```

even if peak impact was identical.

But I don't necessarily wait for duration to increase before declaring severity.

If:

```text
all payments unavailable
```

now, that's urgent immediately.

---

# **11. Use predefined severity criteria**

A company could define:

| Severity | Example                                                                       |
| -------- | ----------------------------------------------------------------------------- |
| Sev-1    | Critical service unavailable for many/all customers, major security/data risk |
| Sev-2    | Significant degradation or partial outage                                     |
| Sev-3    | Limited customer impact, workaround available                                 |
| Sev-4    | No meaningful production impact                                               |

The benefit is:

```text
less debate
faster escalation
correct on-call response
consistent communications
```

---

# **12. Severity isn't based on number of broken resources**

Suppose:

```text
10 Kubernetes nodes fail
```

but autoscaling/redundancy absorbs it and users see no impact.

Could be:

```text
low operational severity
```

although infrastructure team should investigate.

Meanwhile:

```text
one tiny configuration change
```

causes every API request to fail.

That's Sev-1.

Infrastructure scale and business impact are not equivalent.

---

# **13. Severity may change during the incident**

Initial:

```text
one region affected
→ Sev-2
```

Then:

```text
second region begins failing
→ global impact
```

Upgrade:

```text
Sev-1
```

Or:

```text
mitigation restores most users
```

perhaps downgrade after stability is demonstrated.

Severity is a live operational classification.

---

# **14. Example incident**

Alert:

```text
checkout 5xx = 12%
```

I investigate:

```text
Affected users:
~15% globally

Critical feature:
Checkout

Revenue impact:
Yes

Workaround:
None

Data corruption:
No

Trend:
Increasing
```

I'd likely classify that very highly, potentially Sev-1 depending on company thresholds.

Why?

Because:

```text
business-critical
+
customer-facing
+
revenue impacting
+
growing
+
no workaround
```

---

### **Interview answer condensed**

> “I determine severity from business and customer impact rather than technical complexity. I look at how many users or regions are affected, which business function is failing, availability and latency degradation, whether data integrity or security is at risk, whether a workaround exists, and whether the impact is growing. A global checkout outage may be Sev-1 even if the technical root cause is simple, while several failed nodes may be lower severity if redundancy keeps users unaffected. I prefer predefined severity criteria so the team can classify and escalate incidents consistently rather than debating labels during an outage.”

**Memory line:**
**Severity measures impact and urgency—not how scary the infrastructure graph looks.**

**Interview trap:**
Do not classify severity purely by **number of failed resources**; customer, business, data, and security impact matter far more.

**Keywords:**
incident severity, Sev-1, business impact, customer impact, blast radius, data integrity, security risk, workaround, escalation.

**Likely follow-ups:**

* What would make an incident Sev-1?
* Can a security incident be Sev-1 with no downtime?
* When would you upgrade or downgrade severity?
* Would high CPU automatically justify a high-severity incident?

# **T33-23. When should you roll back versus troubleshoot forward?**

**Answer:**

I would choose between rollback and troubleshoot/fix-forward based on **customer impact, rollback safety, time to recovery, and whether the change is actually reversible**.

If a recent release clearly correlates with a major production problem, the previous version is known-good, and rollback is safe, I generally prefer rollback because restoring service quickly is more important than debugging the new version while customers are affected.

I would troubleshoot or fix forward when rollback is unsafe or slower—for example if an irreversible database migration has already run, new data has been written in a format the old application cannot understand, or the problem is well understood and a small safe correction can restore service faster.

My decision framework is:

```text
Recent change caused incident?
        ↓
Is rollback safe?
     /         \
   Yes          No
    ↓            ↓
Is rollback   Fix forward /
fast?         repair state
 /   \
Yes   No
 ↓     ↓
Rollback   Compare recovery options
```

The objective isn't:

```text
always rollback
```

or:

```text
always fix forward
```

It's:

> **Choose the lowest-risk path to restore a correct service fastest.**

---

## **1. Roll back when the change is the likely cause**

Strong evidence:

```text
14:00 v42 deployed
14:02 v42 starts receiving traffic
14:03 5xx jumps 0.2% → 20%
```

Stable v41:

```text
healthy
```

Candidate v42:

```text
failing
```

This strongly favors rollback.

I would not spend 45 minutes debugging v42 in Production if:

```text
rollback can restore service in 3 minutes
```

and is safe.

---

# **2. Roll back when the previous version is truly known-good**

Important qualification:

```text
known-good
```

means:

* it was running successfully,
* its dependencies still support it,
* its configuration is available,
* its database assumptions still hold.

If the environment changed in ways that invalidate v41, it isn't automatically known-good anymore.

---

# **3. Roll back when customer impact is severe**

Suppose:

```text
checkout error rate = 50%
```

and root cause analysis could take:

```text
30–60 minutes
```

while rollback takes:

```text
5 minutes
```

Rollback is usually the rational choice.

During an incident:

```text
restoration
>
intellectual satisfaction of finding root cause
```

Deep RCA can happen after service is stable.

---

# **4. Fix forward when rollback is unsafe**

Example:

New release executed:

```sql
DROP COLUMN old_status;
```

Old application expects:

```text
old_status
```

Now:

```text
v42 fails
```

but reverting:

```text
v42 → v41
```

may fail even worse.

In that situation I may need to:

```text
restore schema compatibility
or
patch v42
```

instead.

This is why destructive database changes are dangerous during application deployments.

---

# **5. New data can also make rollback unsafe**

Suppose v42 starts writing:

```json
{
  "schemaVersion": 2,
  "newRequiredField": "..."
}
```

and v41 only understands version 1.

During the 20 minutes v42 ran, thousands of records were created.

Rollback to v41 could result in:

```text
read failures
data corruption
incorrect processing
```

even if the database schema itself didn't change.

Rollback safety includes **data semantics**, not only schema.

---

# **6. Fix forward when the problem is trivial and known**

Example:

Deployment fails because:

```text
PAYMENT_ENDPOINT
```

contains the wrong hostname.

Diagnosis is certain.

Fix:

```text
correct one config value
```

takes 30 seconds.

Rollback:

```text
requires 15-minute redeployment
```

and might affect unrelated improvements.

A targeted fix-forward can be safer and faster.

The key word is:

```text
high confidence
```

not speculative debugging.

---

# **7. Fix forward when the incident isn't caused by the release**

Suppose:

```text
new release at 14:00
outage at 14:05
```

It looks correlated.

But evidence shows:

```text
Azure SQL unavailable
for both v41 and v42
```

Rolling back will not fix SQL.

So:

```text
recent deployment
≠
automatically rollback
```

Validate the hypothesis.

---

# **8. Roll back when the blast radius is still small**

Canary:

```text
5% → v42
95% → v41
```

v42 fails.

This is almost ideal:

```text
v42 traffic → 0%
```

because:

* stable version remains running,
* only limited users were affected,
* rollback is fast,
* database hasn't been destructively changed.

Progressive delivery makes rollback decisions easier.

---

# **9. Feature flag can be a better rollback**

Suppose:

```text
v42
```

contains two features, but only:

```text
NewPricingEngine
```

is failing.

If controlled via feature flag:

```text
NewPricingEngine = false
```

may restore service faster than:

```text
v42 → v41
```

So mitigation options can be:

```text
1. Disable failing feature
2. Remove candidate traffic
3. Roll back release
4. Fix forward
```

depending on architecture.

---

# **10. Infrastructure rollback may differ from application rollback**

Application:

```text
image v42 → v41
```

is often simple.

Terraform infrastructure change:

```text
replace subnet
move database
change region
```

may not be safely reversible with:

```text
git revert
→ terraform apply
```

because real state has changed.

Before infrastructure rollback I inspect:

```text
Terraform state
actual Azure resources
data dependencies
replacement semantics
```

Never treat infrastructure changes like stateless binaries.

---

# **11. Database rollback is especially dangerous**

Database rollback might mean:

```text
restore backup
```

which could discard legitimate transactions since the backup.

Suppose:

```text
backup at 13:55
incident at 14:10
```

Restoring 13:55 could lose:

```text
15 minutes of valid customer writes
```

So:

```text
"rollback database"
```

has an RPO implication.

It requires much more careful decision-making.

---

# **12. Compare recovery time**

I would roughly compare:

```text
Rollback:
known procedure
estimated restoration = 5 min

Fix forward:
root cause identified
patch/test/deploy = 25 min
```

Choose:

```text
rollback
```

unless rollback has material risk.

Alternatively:

```text
Rollback:
data reconciliation = 60 min

Fix:
feature flag/config change = 3 min
```

Choose:

```text
fix forward
```

This is essentially choosing the safest practical RTO path.

---

# **13. Don't debug indefinitely because rollback feels like failure**

A common bad pattern:

```text
"We're close to figuring it out."
```

for 45 minutes while users remain down.

Organizations should establish rollback triggers such as:

```text
critical SLO breach
+
no high-confidence fix within X minutes
+
rollback safe
```

Then the decision becomes less emotional.

---

# **14. Don't roll back reflexively either**

Another bad pattern:

```text
Error appears after deployment
→ instant rollback
```

when root cause is:

```text
expired Key Vault certificate
Azure regional dependency
DNS outage
```

that affects both versions.

Rollback consumes time and introduces another change without fixing the incident.

Correlation should be supported by evidence.

---

# **15. Use backward-compatible design to preserve rollback**

Strong release engineering makes rollback safe ahead of time.

Use:

```text
immutable artifacts
backward-compatible APIs
expand-and-contract DB migrations
feature flags
external session state
progressive delivery
```

Then:

```text
rollback
```

is a routine operational capability rather than a gamble.

---

# **16. Example decision**

Release v42.

Impact:

```text
5xx = 25%
```

Evidence:

```text
Only v42 fails
v41 healthy
No schema change
No new persistent data format
```

Decision:

```text
ROLL BACK
```

because:

```text
known-good stable version
+
strong release correlation
+
safe rollback
+
high customer impact
```

---

# **17. Opposite example**

Release v42 includes migration.

Migration:

```text
backfilled 40 million records
new write model active for 2 hours
```

Bug discovered.

Old v41 cannot interpret new state.

But issue is one faulty query and patch is already identified.

Decision:

```text
FIX FORWARD
```

because rollback risk is greater than repair risk.

---

### **Interview answer condensed**

> “I roll back when the recent change is strongly correlated with the incident, customer impact is significant, the previous version is known-good, and rollback is safe and faster than debugging forward. I fix forward when rollback would be risky—for example after an incompatible database or data-format migration—or when the root cause is already known and a small safe correction restores service faster. I also verify the release is actually responsible; rolling back won't help if the shared database or Azure dependency is down. The goal isn't to prefer rollback or fix-forward philosophically—it's to choose the lowest-risk path to restore correct service as quickly as possible.”

**Memory line:**
**Rollback when it is safe and faster; fix forward when rollback is unsafe or the correction is clearer and quicker.**

**Interview trap:**
Never assume the old application version is still safe after the new release has modified **shared database schema or persistent data**.

**Keywords:**
rollback, fix-forward, known-good, reversibility, RTO, database migration, data compatibility, feature flag, progressive delivery.

**Likely follow-ups:**

* What would make rollback unsafe?
* How long would you troubleshoot before deciding to rollback?
* Why does expand-and-contract make rollback easier?
* Can rolling back a database cause data loss?

# **T33-24. How would you communicate during a major production incident?**

**Answer:**

During a major production incident, I would keep communication **structured, factual, frequent enough to maintain confidence, and separate from technical troubleshooting**.

I would establish one incident channel and one source of truth, assign an incident commander and ideally a dedicated communications owner, and send updates that clearly state:

```text
what is affected
when it started
who is affected
current mitigation
what is known
what is not yet known
next update point
```

I would avoid speculation such as announcing a root cause before we have evidence.

Internal technical communication can be detailed, but customer or executive updates should focus on impact and restoration progress rather than every command engineers are running.

A useful update structure is:

```text
Impact
Current status
Mitigation
Known facts
Next update
```

For example:

```text
"Checkout requests are failing for a subset of users in West Europe.
The issue began at 14:07 UTC.
We have stopped the latest rollout and are shifting traffic to healthy capacity.
No evidence of data loss has been identified.
Investigation is ongoing; the next update will follow after the current mitigation is validated."
```

The purpose of incident communication is to reduce confusion while letting the technical responders focus on recovery.

---

## **1. Create one incident communication channel**

For a major incident:

```text
#inc-checkout-2026-09-06
```

or equivalent.

Use it for:

```text
status
decisions
actions
handoffs
links
```

Avoid:

```text
Slack DM 1
Teams chat 2
email thread
phone call
random engineering channel
```

all containing different versions of reality.

One source of truth reduces coordination failure.

---

# **2. Assign clear roles**

For a serious outage:

```text
Incident Commander
→ coordinates response

Technical Lead
→ drives investigation

Communications Owner
→ stakeholder/customer updates

Scribe
→ records timeline
```

One person can fill multiple roles in a smaller incident.

The main goal:

```text
engineers troubleshooting
should not simultaneously
manage ten stakeholder conversations
```

---

# **3. First message should communicate impact**

Bad initial message:

```text
"Kubernetes seems broken."
```

Good:

```text
"Production checkout is currently returning elevated 5xx errors.
Approximately 40% of requests are affected in Region A.
The issue began at 14:07 UTC.
Investigation is active."
```

The second tells stakeholders what matters.

---

# **4. Separate facts from hypotheses**

Suppose deployment occurred two minutes before incident.

Correct:

```text
"A deployment completed shortly before the error increase and is being investigated as a possible contributor."
```

Not:

```text
"The new deployment caused the outage."
```

unless proven.

This prevents inaccurate incident narratives from becoming accepted fact.

---

# **5. Communicate mitigation clearly**

For example:

```text
"Further deployment has been stopped."

"Traffic is being shifted to Region B."

"The feature has been disabled."

"The previous application version is being restored."
```

Stakeholders want to know:

> What are we doing to reduce impact?

They do not necessarily need every technical diagnostic command.

---

# **6. Communicate uncertainty explicitly**

It is acceptable to say:

```text
"Root cause is not yet confirmed."
```

Better than inventing certainty.

Similarly:

```text
"We have no evidence of data loss at this time, but validation is still underway."
```

is more accurate than:

```text
"No data was lost."
```

before reconciliation is complete.

---

# **7. Give predictable update cadence**

For major incidents, stakeholders should not have to repeatedly ask:

```text
"Any update?"
```

Set expectations such as:

```text
next update in 15–30 minutes
```

or according to organizational incident policy.

If nothing materially changed:

```text
"Impact remains unchanged.
Mitigation is still in progress.
No confirmed root cause yet."
```

is still useful.

Silence creates uncertainty.

---

# **8. Technical channel vs stakeholder updates**

Technical responders may discuss:

```text
DNS
ReplicaSets
SQL wait types
firewall rules
KQL traces
```

Executive/customer communication should usually say:

```text
what is broken
customer scope
business impact
mitigation
recovery status
```

Do not overload stakeholder updates with raw debugging chatter.

---

# **9. External status page communication**

For a customer-facing service, a status page might follow:

### Investigating

```text
"We are investigating elevated errors affecting checkout."
```

### Identified

```text
"We have identified an application deployment issue and are rolling back."
```

### Monitoring

```text
"Service has recovered and we are monitoring."
```

### Resolved

```text
"The issue has been resolved. We continue to review the incident."
```

Only move between states when evidence supports it.

---

# **10. Avoid exposing sensitive internals**

External updates usually should not reveal:

```text
secret names
internal IP addresses
security controls
exploit details
credentials
customer-specific data
```

especially during a security incident.

Transparency does not mean publishing information that increases risk.

---

# **11. Avoid blame**

Bad:

```text
"Developer X pushed a bad Terraform change."
```

Better:

```text
"A production infrastructure change removed a required dependency."
```

People can be accountable without turning the live incident into a blame discussion.

The postmortem can examine:

```text
review process
automation
guardrails
```

after recovery.

---

# **12. Announce important decisions**

Record major decisions such as:

```text
14:10 — Rollout paused
14:15 — Decision: rollback v42
14:20 — Region B failover initiated
14:28 — Error rate recovering
```

This is valuable both operationally and later for the postmortem.

---

# **13. Communicate recovery carefully**

Don't announce:

```text
Resolved
```

the moment one dashboard turns green.

Use:

```text
Mitigated / Monitoring
```

while validating:

```text
availability
latency
transactions
queue backlog
data correctness
```

Then declare resolved after a stable observation period.

---

# **14. Example internal update**

At 14:20:

```text
Severity: Sev-1

Impact:
Checkout failures affecting ~60% of requests in Central India.

Start:
14:07 UTC.

Known:
Failures correlate with v42 rollout.
v41 instances remain healthy.

Action:
Rollout stopped.
Traffic is being restored to v41.

Data:
No evidence of lost/duplicate orders so far; reconciliation running.

Next:
Validate error rate and checkout transaction success after rollback.
```

Short, factual, operational.

---

# **15. Example executive update**

```text
"We are experiencing a major checkout disruption affecting customers in one region. Engineering has isolated the issue to the latest application release and is restoring the previous stable version. Recovery is underway, and we currently have no evidence of data loss. We will provide another update after service restoration is validated."
```

No unnecessary technical detail.

---

# **16. Example technical update**

```text
"v42 is producing 22% 5xx; v41 remains at 0.2%.
Deployment paused at 40%.
DB migration was additive and v41-compatible.
GitOps desired digest is being reverted to sha256:AAA.
No SQL error-rate increase observed."
```

This helps responders make decisions.

Different audiences need different depth.

---

# **17. Handoffs**

If incident spans shifts/time zones, communicate:

```text
Current impact
Current hypothesis
What has been ruled out
Actions performed
Pending actions
Do-not-repeat actions
Owners
```

Without a strong handoff, the next engineer may repeat:

```text
failed diagnostic steps
```

or undo a valid mitigation.

---

# **18. Close with what happens next**

After recovery:

```text
Service restored
      ↓
monitoring period
      ↓
incident resolved
      ↓
postmortem scheduled
```

Stakeholders should know whether:

```text
root cause confirmed
```

or only:

```text
service mitigated
```

Those are different states.

---

### **Interview answer condensed**

> “During a major incident I would establish one incident channel and source of truth, assign an incident commander and ideally a communications owner, and send concise updates based on impact rather than debugging detail. Each update should state what is affected, the start time and scope, current mitigation, confirmed facts, remaining uncertainty, and the next update point. I would clearly separate facts from hypotheses and avoid announcing a root cause before evidence supports it. Technical responders can use detailed engineering communication, while executives and customers need impact and recovery status. I also wouldn't declare the incident resolved until service and critical business transactions have remained stable through a validation period.”

**Memory line:**
**Communicate impact, facts, mitigation, and next status—never speculation disguised as certainty.**

**Interview trap:**
Do not announce **“root cause identified”** merely because a recent deployment correlates with the outage.

**Keywords:**
incident communication, incident commander, status page, stakeholders, impact, mitigation, timeline, single source of truth, update cadence.

**Likely follow-ups:**

* What would your first customer-facing status message contain?
* How is an executive update different from a technical update?
* Should you give an ETA if you don't actually know one?
* When would you declare an incident resolved?

# **T33-25. What information should be captured during an incident?**

**Answer:**

During an incident, I would capture enough information to support **real-time coordination, safe handoffs, accurate recovery validation, and a useful postmortem afterward**.

At minimum I want an incident timeline; impact and severity; affected services, regions, versions, and customers; alerts and telemetry; recent deployments or infrastructure changes; hypotheses and evidence; every significant mitigation or production change; who made the decision; the result of each action; and the final recovery evidence.

For data or security incidents I would also preserve relevant logs and evidence before they expire or are overwritten.

The key is to capture:

```text
What happened?
When?
What was impacted?
What changed?
What did we observe?
What did we try?
What happened after each action?
When was service restored?
```

without turning responders into full-time note takers.

A simple incident record might look like:

```text
14:07 Alert: checkout 5xx > 20%
14:09 Sev-1 declared
14:11 v42 rollout identified as recent change
14:13 rollout paused
14:16 v42 error = 24%, v41 = 0.2%
14:18 rollback approved
14:22 v41 restored
14:25 5xx < 0.3%
14:30 transaction reconciliation healthy
14:40 incident moved to monitoring
```

That timeline later makes root-cause analysis dramatically more reliable.

## **1. Capture basic incident metadata**

At the beginning:

```text
Incident ID
Title
Start time
Detected time
Severity
Incident commander
Affected service
Environment
Region(s)
```

Example:

```text
INC-2026-091
Checkout API outage
Start: 14:07 UTC
Detected: 14:08 UTC
Severity: Sev-1
Region: Central India
```

This provides basic orientation for everyone joining the incident.

---

# **2. Capture customer/business impact**

Record:

```text
Affected functionality
Estimated users/customers
Failed request percentage
Revenue/business process impact
Data/security impact
Workaround availability
```

Example:

```text
Checkout:
~55% transactions failing

Browsing:
Unaffected

Payments already authorized:
No evidence of duplication

Regions:
Central India only
```

This helps determine both severity and later business impact.

---

# **3. Record exact start time and detection time separately**

Incident may begin:

```text
14:02
```

but alert fires:

```text
14:07
```

Then:

```text
Time to detect = 5 minutes
```

That becomes valuable later.

Similarly:

```text
Mitigation starts
Recovery achieved
Incident resolved
```

should be tracked separately.

---

# **4. Build a chronological timeline**

Example:

```text
13:58 v42 deployment begins
14:02 first error-rate increase
14:05 deployment reaches 50%
14:07 Azure Monitor alert fires
14:09 incident acknowledged
14:10 rollout paused
14:15 rollback decision
14:21 rollback complete
14:24 5xx returned to baseline
```

This timeline often reveals causality better than memory after the incident.

---

# **5. Capture recent changes**

Record things such as:

```text
application release
Terraform apply
feature flag change
database migration
NSG/firewall update
DNS change
certificate/secret rotation
autoscaling change
```

and their timestamps.

Example:

```text
v42 digest:
sha256:BBB

Deployment completed:
14:01

Errors started:
14:02
```

That's strong correlation evidence.

---

# **6. Capture immutable deployment identifiers**

Do not only record:

```text
Version = latest
```

Record:

```text
Git SHA
image digest
pipeline run ID
Helm chart version
Terraform commit
```

For example:

```text
checkout image:
myacr.azurecr.io/checkout@sha256:ab12...
```

This proves what actually ran.

---

# **7. Capture alerts and key metrics**

Useful evidence:

```text
5xx
availability
p95/p99
traffic
CPU/memory
DB latency
queue backlog
replication lag
```

and when they changed.

For example:

```text
14:00:
5xx = 0.2%

14:07:
5xx = 18%

14:25 after rollback:
5xx = 0.3%
```

That proves mitigation effectiveness.

---

# **8. Preserve logs and traces**

For the affected period:

```text
application logs
distributed traces
gateway logs
database diagnostics
firewall logs
Kubernetes events
Azure Activity Log
```

depending on incident.

Especially preserve:

```text
correlation IDs
failed transaction IDs
timestamps
```

that allow investigation after service restoration.

---

# **9. Record hypotheses**

Example:

```text
14:10 Hypothesis:
v42 caused DB connection exhaustion.

Evidence for:
DB connections increased after rollout.

Evidence against:
Old v41 Pods also show same pattern.

Status:
Not confirmed.
```

This is much better than recording:

```text
"DB caused outage."
```

when that was only an early guess.

---

# **10. Record what has been ruled out**

This helps handoff.

For example:

```text
Azure Service Health:
No relevant regional incident.

DNS:
resolving correctly.

ACR:
image pulls healthy.

Database:
service available, no failover event.
```

New responders now know not to repeat the same basic checks unless evidence changes.

---

# **11. Record every significant production action**

Examples:

```text
Paused deployment
Scaled node pool
Changed feature flag
Removed backend
Failed over database
Changed firewall rule
Rolled back image
```

Record:

```text
time
operator
reason
expected result
actual result
```

Example:

```text
14:16
Action:
Disable NewCheckout feature flag

Reason:
Hypothesis that feature causes failures

Result:
5xx unchanged

Conclusion:
Feature flag not sufficient mitigation
```

That's valuable operational evidence.

---

# **12. Record failed mitigation attempts too**

Don't only write down successful actions.

Failed action:

```text
Scaled API 10 → 30 Pods
```

Result:

```text
No latency improvement
SQL connections increased
```

This is important.

It may reveal that:

```text
database was bottleneck
```

and scaling the API actually worsened it.

Postmortems need failed attempts to understand decision quality.

---

# **13. Capture decision rationale**

For major choices:

```text
Why rollback?
Why fail over?
Why disable writes?
Why not fail over?
```

Example:

```text
Decision:
Rollback v42.

Reason:
Only v42 failing,
v41 healthy,
migration additive and backward compatible.
```

That gives future reviewers context.

Otherwise six weeks later someone may ask:

> Why didn't they just fix forward?

and have no evidence.

---

# **14. Capture ownership**

During incident:

```text
IC: Alice
DB investigation: Bob
Networking: Priya
Rollback: Chen
Communications: Sam
```

This prevents duplicated work.

It's also useful for handoffs.

The point is not blame.

It's coordination.

---

# **15. Capture security evidence carefully**

For security incidents:

```text
Entra sign-in logs
Activity Logs
Key Vault access
Storage access logs
source IPs
timestamps
affected identities
credential IDs
```

Preserve evidence before:

```text
retention expires
logs rotate
resource gets recreated
```

and follow the organization's forensic/evidence-handling procedures.

---

# **16. Capture data-integrity findings**

If transactions may be affected:

```text
Orders attempted
Orders completed
Payments authorized
Duplicate transactions
Missing writes
Queue backlog
```

Example:

```text
Failed checkout requests:
1,247

Orders requiring reconciliation:
37

Duplicate payments:
0 confirmed
```

Recovery is not complete until data correctness is understood.

---

# **17. Capture Azure control-plane changes**

Azure Activity Log may reveal:

```text
NSG updated
Private Endpoint deleted
SQL scaled
VM restarted
role assignment modified
```

Record relevant:

```text
caller
operation
scope
timestamp
result
```

This is especially valuable for Terraform/manual-change incidents.

---

# **18. Capture recovery evidence**

Don't write:

```text
14:25 — Fixed.
```

Write:

```text
14:25
5xx returned to 0.25%

14:27
p95 returned to 380 ms

14:30
synthetic checkout succeeded

14:33
payment reconciliation normal
```

Now:

```text
service restored
```

is evidence-backed.

---

# **19. Capture mitigation time vs resolution time**

Useful incident milestones:

```text
Start
Detection
Acknowledgment
Mitigation
Recovery
Resolution
```

Example:

```text
Start      14:02
Detected   14:07
Ack        14:09
Mitigated  14:21
Recovered  14:25
Resolved   15:30
```

This lets teams calculate operational metrics such as:

```text
time to detect
time to acknowledge
time to restore
```

Terminology varies between organizations, so define exactly what the metric means.

---

# **20. Don't rely on people's memory after the outage**

During a stressful incident:

```text
20 engineers
60 commands
multiple hypotheses
```

Nobody remembers the exact sequence perfectly afterward.

A real-time timeline is dramatically more accurate than:

```text
postmortem two days later
→ "I think we changed that around 3 PM"
```

---

# **21. But don't over-document during active impact**

Responders should not spend:

```text
80% of time
writing prose
```

while service is down.

Use:

```text
short timestamped entries
automation
chat export
deployment links
dashboard snapshots
```

and clean up the narrative later.

The incident record supports response; it shouldn't obstruct response.

---

## **A strong incident record structure**

```text
Incident
├── ID / title / severity
├── Start & detection
├── Incident owner
│
├── Impact
│   ├── customers
│   ├── functionality
│   └── regions
│
├── Timeline
│   ├── alerts
│   ├── deployments
│   ├── observations
│   └── mitigations
│
├── Technical evidence
│   ├── metrics
│   ├── logs
│   ├── traces
│   └── Azure changes
│
├── Decisions
│   ├── rollback
│   └── failover
│
├── Recovery validation
│
└── Follow-up / postmortem
```

### **Interview answer condensed**

> “I would capture a timestamped incident timeline plus the impact, severity, affected services and regions, owners, recent changes, deployment versions or image digests, alerts and key telemetry, hypotheses, evidence, and every significant production action with its result. I would record both successful and unsuccessful mitigation attempts and why important decisions such as rollback or failover were made. For security or data incidents I'd preserve relevant logs and reconciliation evidence before they're lost. Finally I'd capture recovery evidence—such as error rate, latency and business transaction success—rather than simply writing ‘service fixed.’ The goal is enough information for live coordination, handoff and a reliable postmortem without slowing responders down with excessive documentation.”

**Memory line:**
**Capture timestamps, impact, evidence, decisions, actions, and results—the timeline is the backbone of the incident.**

**Interview trap:**
Do not record only the final root cause and successful fix; **failed hypotheses and mitigation attempts** are often essential to understanding and improving the response.

**Keywords:**
incident timeline, impact, immutable version, telemetry, hypotheses, decisions, mitigation, recovery evidence, handoff, postmortem.
