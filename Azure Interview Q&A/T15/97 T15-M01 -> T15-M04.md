### **T15-M01. What are App Service deployment slots?**

**Answer:**
App Service deployment slots are **live, separate instances of the same App Service application**, such as `staging` and `production`, each with its own hostname and configuration. They let me deploy and validate a new version outside production, warm it up, and then **swap** it into production with minimal or no application downtime. Deployment slots are available on supported App Service Plan tiers such as Standard, Premium, and Isolated. ([Microsoft Learn][1])

### **Typical deployment flow**

```text
Production
v1
│
│ users
↓
app.contoso.com

Staging Slot
v2
│
│ validate
↓
app-staging.contoso.com
```

Then:

```text
Deploy v2 → Staging
      ↓
Smoke test
      ↓
Warm up instances
      ↓
Swap
      ↓
Production = v2
Staging    = previous v1
```

The nice part is that App Service prepares and warms the source slot before completing the swap, while the production target remains online. ([Microsoft Learn][1])

---

### **Why use slots instead of deploying directly to production?**

Without slots:

```text
Production v1
     ↓
deploy v2 directly
     ↓
startup / config / migration issue
     ↓
users affected
```

With slots:

```text
Deploy v2 to staging
        ↓
Test it
        ↓
Verify dependencies
        ↓
Swap when healthy
```

So slots support:

```text
Blue-green style deployment
Staging validation
Low-downtime releases
Fast rollback
Canary/traffic testing
```

---

### **Slot swap**

CLI example:

```bash
az webapp deployment slot swap \
  --resource-group rg-prod \
  --name payment-api \
  --slot staging \
  --target-slot production
```

Conceptually:

```text
Before
Production → v1
Staging    → v2

After swap
Production → v2
Staging    → v1
```

If v2 has a serious problem:

```text
swap again
↓
Production → v1
```

Microsoft explicitly documents reverse swapping as a fast rollback method. ([Microsoft Learn][1])

---

### **Slot-specific settings**

Not every configuration value should move during a swap.

For example:

```text
Production DB
→ prod-sql

Staging DB
→ test-sql
```

I don't want staging's database connection moving into production accidentally.

App Service therefore supports **deployment slot settings**, sometimes called sticky settings:

```text
APP_DATABASE
→ stays with slot
```

rather than being swapped with the application.

Microsoft documents app settings and connection strings as configurable to remain slot-specific. ([Microsoft Learn][1])

---

### **Important nuance**

Some settings are not swapped by default, including things such as:

```text
Managed identities
VNet Integration
Scale settings
IP restrictions
Custom domains
```

So I always review:

```text
Source slot configuration
vs
Target slot configuration
```

before production promotion. ([Microsoft Learn][1])

> **In an interview, I would say:**
> “Deployment slots are live App Service environments such as staging and production. I deploy the new release into staging, validate and warm it there, and then swap staging into production. Because production stays online while the source slot is prepared, this enables very low-downtime deployments and fast rollback. I also use slot-specific settings for environment-sensitive configuration such as database connection strings so those values don't accidentally move during a swap.”

**Memory line:**
**Deploy to staging → validate → warm up → swap → production.**

**Interview trap:**
Do not assume every setting swaps. Managed identities, VNet Integration, scale settings, and several other settings remain associated with their slots. ([Microsoft Learn][1])

**Keywords:**
Deployment slot, swap, staging, production, slot setting, blue-green, rollback

**Likely follow-ups:**

* What happens during a slot swap?
* Which settings stay with a slot?
* How would you rollback after a bad swap?
* Can you route only some users to a deployment slot?

### **T15-M02. How does App Service autoscaling work?**

**Answer:**
App Service can scale **out and in by changing the number of compute instances** running an App Service Plan. With Azure Monitor autoscale, I define rules based on metrics or schedules—for example, add instances when CPU stays above 70% and remove instances when it falls below 20%. The rules act on the **App Service Plan**, so apps sharing that plan share the scaled compute. ([Microsoft Learn][2])

### **Scale up vs scale out**

First distinction:

```text
Scale up
→ bigger VM / higher App Service Plan tier

Scale out
→ more VM instances
```

Example:

```text
Scale up
P1v3 → P2v3

Scale out
2 instances → 5 instances
```

For handling variable application load, scale-out is usually what people mean by autoscaling.

---

### **Metric-based autoscaling**

Example rule:

```text
CPU > 70%
for 10 minutes
     ↓
Add 1 instance
```

Then:

```text
CPU < 20%
for 10 minutes
     ↓
Remove 1 instance
```

Conceptually:

```text
Traffic ↑
   ↓
CPU ↑
   ↓
Autoscale rule fires
   ↓
2 instances → 3 → 4
```

Then after traffic decreases:

```text
4 → 3 → 2
```

Azure Monitor autoscale supports both metric-based and scheduled scaling. ([Microsoft Learn][2])

---

### **Minimum, maximum, and default**

A real configuration should define boundaries:

```text
Minimum = 2
Default = 2
Maximum = 10
```

So:

```text
traffic spike
→ can scale to at most 10
```

while:

```text
low traffic
→ never drops below 2
```

This protects both:

```text
availability
+
cost
```

---

### **Scheduled scaling**

Sometimes load is predictable.

Example:

```text
Weekdays 08:00
→ minimum 5 instances

Night
→ minimum 2
```

This is useful when:

```text
traffic spike is known in advance
```

because I don't have to wait for CPU to increase before capacity appears. Azure Monitor autoscale supports scheduled conditions alongside metric rules. ([Microsoft Learn][2])

---

### **Important: autoscale applies to the plan**

Suppose:

```text
App Service Plan
├── frontend
├── backend
└── admin-api
```

Azure Monitor autoscale:

```text
2 plan instances → 5
```

affects the plan compute used by all those apps.

Microsoft specifically notes that Azure Monitor autoscale settings apply to the entire App Service Plan. ([Microsoft Learn][2])

---

### **Automatic scaling vs Azure Monitor autoscale**

This is a good current interview distinction.

App Service also has **automatic scaling**, which is separate from Azure Monitor autoscale.

```text
Azure Monitor autoscale
→ metric rules + schedules
→ App Service Plan level

App Service automatic scaling
→ HTTP-traffic-driven
→ can scale individual apps
→ no custom metric rules required
```

Microsoft explicitly distinguishes these two mechanisms. ([Microsoft Learn][2])

---

### **Production example**

```text
Normal:
2 instances

Traffic surge:
Requests ↑
CPU > 70%
      ↓
Autoscale
      ↓
5 instances

Traffic falls:
CPU < 20%
      ↓
Scale in
      ↓
2 instances
```

I would also monitor:

```text
P95 latency
HTTP queue
CPU
memory
request count
5xx rate
```

because CPU alone isn't always the best signal.

> **In an interview, I would say:**
> “App Service autoscaling normally means changing the number of instances in the App Service Plan based on Azure Monitor rules or schedules. For example, I can scale from two to five instances when CPU stays above a threshold and scale back in when demand drops, while enforcing minimum and maximum limits. I also distinguish Azure Monitor autoscale from App Service automatic scaling: Monitor autoscale uses explicit metric or schedule rules at plan level, while automatic scaling can scale individual apps based on HTTP traffic.”

**Memory line:**
**Scale up = bigger instance; scale out = more instances; autoscale automates scale-out/in.**

**Interview trap:**
Do not confuse scaling an App Service **Plan** with deploying another application instance manually.

**Keywords:**
Autoscale, scale out, scale in, scale up, Azure Monitor, minimum/maximum instances, automatic scaling

**Likely follow-ups:**

* Scale up vs scale out?
* Can autoscaling use schedules?
* Does autoscale affect every app sharing the plan?
* Automatic scaling vs Azure Monitor autoscale?

### **T15-M03. How can App Service access Key Vault without credentials?**

**Answer:**
I would enable a **Managed Identity** on the App Service, grant that identity the required Key Vault data-plane permission, such as **Key Vault Secrets User**, and then either access Key Vault directly through an Entra-aware SDK or use an **App Service Key Vault reference** in the application's settings. No client secret or Key Vault password needs to be stored in the application. ([Microsoft Learn][3])

### **Architecture**

```text
App Service
     ↓
Managed Identity
     ↓
Microsoft Entra ID
     ↓
Azure Key Vault RBAC
     ↓
Secret
```

There is no:

```text
client-secret.txt
```

inside the application.

---

### **1. Enable Managed Identity**

For example:

```text
App Service
→ System-assigned Managed Identity
```

Azure creates an Entra-backed identity tied to the application.

Conceptually:

```text
payment-api
     ↓
principal ID: abc123
```

The Azure platform manages the credential lifecycle. ([Microsoft Learn][4])

---

### **2. Grant Key Vault permission**

Using modern Azure RBAC:

```text
App Service Managed Identity
          ↓
Key Vault Secrets User
          ↓
Key Vault
```

That role permits reading secret values without granting unnecessary administrative control.

Microsoft's current App Service guidance specifically recommends assigning **Key Vault Secrets User** when Key Vault uses Azure RBAC. ([Microsoft Learn][3])

---

### **3. Option A — Use Key Vault reference**

An App Service setting can contain a Key Vault reference instead of the actual secret.

Conceptually:

```text
DB_PASSWORD
=
@Microsoft.KeyVault(...)
```

App Service resolves the reference using its Managed Identity.

Then the application simply reads:

```text
DB_PASSWORD
```

as a normal environment/app setting.

The secret itself remains stored in:

```text
Azure Key Vault
```

Microsoft documents this pattern directly for App Service and Azure Functions. ([Microsoft Learn][3])

---

### **4. Option B — Access Key Vault directly from code**

The application can also use:

```text
DefaultAzureCredential
```

or an appropriate Azure Identity SDK.

Flow:

```text
App code
   ↓
Managed Identity token
   ↓
Microsoft Entra
   ↓
Key Vault SDK
   ↓
Secret
```

This is useful when the application needs:

```text
dynamic secret access
multiple secrets
explicit Key Vault API behavior
```

Managed Identity tokens represent the application, so no stored client secret is required. ([Microsoft Learn][4])

---

### **5. Network access still matters**

If Key Vault has:

```text
Public access disabled
+
Private Endpoint
```

then identity alone isn't sufficient.

The App Service also needs:

```text
VNet Integration
      ↓
Private DNS
      ↓
Key Vault Private Endpoint
```

So the two independent requirements are:

```text
Network connectivity
+
Authorization
```

Microsoft explicitly notes that network-restricted Key Vaults require the App Service to have an appropriate network path in addition to Managed Identity authorization. ([Microsoft Learn][3])

---

### **System-assigned vs user-assigned**

Usually:

```text
System-assigned identity
→ simplest
→ lifecycle tied to app
```

A user-assigned identity can be useful when:

```text
multiple apps share identity
identity must exist before app creation/configuration
identity lifecycle should be independent
```

Key Vault references use the system-assigned identity by default, but App Service can be configured to use a user-assigned identity. ([Microsoft Learn][3])

---

### **Production example**

```text
App Service
   ↓
Managed Identity
   ↓
Key Vault Secrets User
   ↓
Key Vault
   ↓
SQL password/API secret
```

No:

```text
password in Git
client secret in pipeline
secret in appsettings.json
```

> **In an interview, I would say:**
> “I would enable a Managed Identity on the App Service and grant that identity only the required Key Vault data-plane permissions, typically Key Vault Secrets User for reading secrets. The application can then either access Key Vault directly using an Entra-aware SDK such as `DefaultAzureCredential`, or I can use App Service Key Vault references so a secret appears as an app setting without storing the secret itself in App Service configuration. If the vault uses a Private Endpoint, I also need VNet Integration and correct private DNS because identity doesn't replace network connectivity.”

**Memory line:**
**App Service → Managed Identity → Key Vault RBAC → secret, with no stored credential.**

**Interview trap:**
Managed Identity solves **authentication**, not network reachability. A private Key Vault still needs a valid private network/DNS path.

**Keywords:**
Managed Identity, Key Vault Secrets User, Key Vault reference, `DefaultAzureCredential`, Azure RBAC

**Likely follow-ups:**

* System-assigned vs user-assigned Managed Identity?
* Key Vault reference vs reading secrets in code?
* What role would you grant?
* What if Key Vault uses a Private Endpoint?

### **T15-M04. What is VNet Integration for App Service?**

**Answer:**
App Service VNet Integration allows an App Service application to make **outbound connections into or through an Azure Virtual Network**. It is mainly an **outbound connectivity feature**—for example, allowing the application to reach a private Azure SQL database, a VM, a Private Endpoint, or an on-premises network reachable through the VNet. It does **not** by itself make inbound access to the App Service private. ([Microsoft Learn][5])

### **Architecture**

```text
App Service
     │
     │ outbound
     ↓
VNet Integration Subnet
     ↓
 ┌───────────────┬───────────────┐
 ↓               ↓               ↓
Azure SQL PE     VM           On-prem
```

The key word is:

```text
OUTBOUND
```

---

### **How it works**

App Service attaches virtual interfaces on its worker infrastructure using addresses from the integration subnet.

Conceptually:

```text
App Service worker
      ↓
virtual interface
      ↓
Integration subnet
10.20.2.0/24
```

This allows outbound traffic to access resources reachable through that VNet much like other VNet-connected workloads. ([Microsoft Learn][5])

---

### **Typical use case**

Suppose:

```text
Azure SQL
→ Public access disabled
→ Private Endpoint = 10.20.5.4
```

Then:

```text
App Service
      ↓
VNet Integration
      ↓
Private DNS resolution
      ↓
10.20.5.4
      ↓
Azure SQL
```

Without VNet Integration, the App Service normally doesn't have that private VNet path.

---

### **Important distinction: VNet Integration vs Private Endpoint**

This is one of the most commonly tested App Service networking distinctions.

```text
VNet Integration
→ outbound traffic FROM App Service
```

versus:

```text
Private Endpoint
→ private inbound traffic TO App Service
```

Diagram:

```text
Outbound:
App Service
    ↓
VNet Integration
    ↓
Private SQL

Inbound:
Private client
    ↓
App Service Private Endpoint
    ↓
App Service
```

They solve opposite directions.

---

### **Routing behavior**

By default/configuration, VNet Integration can route private traffic into the VNet.

App Service also supports routing **all outbound traffic** through the integration VNet when configured. ([Microsoft Learn][5])

That enables architectures such as:

```text
App Service
    ↓
VNet Integration
    ↓
0.0.0.0/0 UDR
    ↓
Azure Firewall
    ↓
Internet
```

so outbound traffic can be centrally inspected.

---

### **NSGs and UDRs**

The integration subnet can have:

```text
NSG
UDR
NAT Gateway
```

depending on the architecture.

So if App Service suddenly can't reach a backend after VNet integration:

```text
App Service
   ↓
Integration subnet
   ↓
NSG / UDR
   ↓
Firewall
   ↓
Backend
```

I troubleshoot the effective network path rather than assuming App Service itself is broken.

Microsoft notes that traffic routed through the integration subnet is subject to the subnet's configured NSGs and routes. ([Microsoft Learn][5])

---

### **Dedicated subnet requirement**

VNet Integration uses a dedicated/delegated subnet.

I would size it with enough address space for:

```text
current App Service Plan instances
+
scale-out capacity
```

because each plan instance consumes addressing from the integration subnet. ([Microsoft Learn][5])

---

### **VNet Integration does NOT make the app private**

This is the big trap.

If I configure only:

```text
VNet Integration
```

users can still potentially access:

```text
https://myapp.azurewebsites.net
```

through the public App Service endpoint.

For private inbound access, I need:

```text
Private Endpoint
+
Private DNS
+
public access restrictions/disablement as required
```

VNet Integration and Private Endpoint are complementary, not substitutes.

---

### **Production architecture**

```text
Corporate users
       ↓
Private network
       ↓
App Service Private Endpoint
       ↓
App Service
       │
       │ outbound
       ↓
VNet Integration
       ↓
Azure SQL Private Endpoint
```

So:

```text
Private Endpoint
→ inbound private access

VNet Integration
→ outbound private access
```

> **In an interview, I would say:**
> “App Service VNet Integration gives the application outbound connectivity into or through an Azure VNet. I use it when the app needs to reach resources such as Azure SQL through a Private Endpoint, internal VMs, or on-premises networks. The integration uses a dedicated subnet and traffic routed through it can be subject to NSGs, UDRs and firewalls. The key distinction is that VNet Integration is outbound; it does not make inbound App Service access private. For private inbound connectivity I would use an App Service Private Endpoint.”

**Memory line:**
**VNet Integration = App Service OUT to VNet; Private Endpoint = clients IN to App Service privately.**

**Interview trap:**
Do not say enabling VNet Integration makes the App Service's public endpoint private.

**Keywords:**
VNet Integration, outbound connectivity, integration subnet, UDR, NSG, Private Endpoint

**Likely follow-ups:**

* VNet Integration vs Private Endpoint?
* How would App Service reach private Azure SQL?
* Can VNet Integration route internet traffic through Azure Firewall?
* Why does the integration subnet need enough IP addresses?
