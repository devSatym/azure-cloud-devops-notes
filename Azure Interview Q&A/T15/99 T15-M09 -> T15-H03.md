### **T15-M09. When would you choose Container Apps instead of AKS?**

**Answer:**
I would choose **Azure Container Apps instead of AKS when I want to run containerized APIs, microservices, workers, or event-driven jobs but I do not need direct Kubernetes API access or deep control over cluster infrastructure**. Container Apps gives me built-in ingress, revisions, traffic splitting, KEDA-based autoscaling, service discovery, jobs, and scale-to-zero while Azure manages the underlying orchestration. Microsoft explicitly recommends Container Apps when teams want Kubernetes-style microservices without managing Kubernetes itself. ([Microsoft Learn][1])

### **Decision model**

```text
Need containers?
     ↓
Need full Kubernetes control?
   /                 \
 Yes                  No
 ↓                     ↓
AKS              Container Apps
```

---

### **Choose Container Apps when**

I would strongly consider Container Apps for:

```text
REST APIs
Microservices
Background workers
Queue consumers
Scheduled jobs
Event-driven workloads
Internal services
```

especially when the team wants:

```text
less operational overhead
automatic scaling
scale-to-zero
built-in ingress
revisions
traffic splitting
KEDA
Dapr
```

Microsoft's current Azure Architecture guidance says to start with Container Apps when you want microservices primitives such as service discovery, Dapr, and per-app scaling without cluster management. ([Microsoft Learn][2])

---

### **Example**

Suppose I have:

```text
Frontend API
     ↓
Orders API
     ↓
Service Bus
     ↓
Worker
```

Requirements:

```text
HTTP ingress
Service discovery
Queue-based scaling
Canary deployments
Scale-to-zero
```

I could use:

```text
Container App: frontend
Container App: orders
Container App: worker
```

with:

```text
HTTP scaling
KEDA Service Bus scaling
Revision traffic splitting
```

without administering:

```text
Node pools
Kubernetes upgrades
Ingress controller
HPA manifests
Cluster Autoscaler
CNI
Kubernetes RBAC
```

That is exactly the operational simplicity Container Apps is designed for.

---

### **Choose AKS instead when I need Kubernetes itself**

AKS is the better fit when I require:

```text
Kubernetes API access
CRDs
Operators
DaemonSets
Custom admission controllers
Custom service mesh
Advanced NetworkPolicy
Specialized node pools
GPU/node-level tuning
Custom scheduling
Persistent Kubernetes ecosystem tooling
```

Microsoft specifically says that if you require direct Kubernetes API/control-plane access, you should use AKS rather than Container Apps. ([Microsoft Learn][1])

---

### **Important 2026 nuance: AKS Automatic**

AKS now has **AKS Automatic**, which removes more node-management, scaling, security, monitoring, and upgrade work than traditional AKS Standard. So the decision is no longer simply:

```text
Container Apps = easy
AKS = difficult
```

The stronger distinction is:

```text
Container Apps
→ abstract Kubernetes away

AKS Automatic
→ still Kubernetes, but Azure manages more of it

AKS Standard
→ maximum Kubernetes/infrastructure control
```

AKS Automatic still exposes Kubernetes semantics and APIs, while Container Apps deliberately abstracts those APIs. ([Microsoft Learn][3])

---

### **Simple comparison**

| Requirement                  | Container Apps | AKS                                      |
| ---------------------------- | -------------- | ---------------------------------------- |
| Run containers               | ✓              | ✓                                        |
| Microservices                | ✓              | ✓                                        |
| Scale to zero                | Excellent fit  | Possible with additional design          |
| KEDA                         | Built in       | Install/manage                           |
| Kubernetes API               | ✗              | ✓                                        |
| CRDs/operators               | ✗              | ✓                                        |
| Node control                 | ✗              | ✓                                        |
| Infrastructure overhead      | Lower          | Higher                                   |
| Custom scheduling/networking | Limited        | Extensive                                |
| Built-in revisions           | ✓              | Build with Kubernetes deployment tooling |

---

### **Cost consideration**

For sporadic workloads:

```text
Traffic = 0
     ↓
Container Apps = 0 replicas
```

can be attractive.

But for:

```text
dozens of continuously busy services
+
predictable sustained compute
```

AKS may become economically attractive because workloads share cluster capacity.

So I would not say:

> “Container Apps is always cheaper.”

The choice depends on utilization and operational cost.

---

> **In an interview, I would say:**
> “I choose Container Apps when I need containers and microservices capabilities but don't need direct Kubernetes control. It gives me built-in ingress, revisions, traffic splitting, KEDA autoscaling and scale-to-zero without managing nodes or Kubernetes infrastructure. I would move to AKS when I need the Kubernetes API, operators or CRDs, custom service mesh, advanced networking, specialized node pools, scheduling control, or other Kubernetes ecosystem features. Even with AKS Automatic reducing operational work, Container Apps is still the simpler choice when Kubernetes itself isn't a requirement.”

**Memory line:**
**Need containers, not Kubernetes → Container Apps. Need Kubernetes control → AKS.**

**Interview trap:**
Do not choose AKS simply because the workload uses containers. Kubernetes should solve a requirement, not just add complexity.

**Keywords:**
Container Apps, AKS, KEDA, scale-to-zero, Kubernetes API, CRD, operator, revisions

**Likely follow-ups:**

* How does AKS Automatic change this decision?
* When would Container Apps become too limiting?
* Is Container Apps actually running Kubernetes underneath?
* Which is cheaper for constant workloads?

### **T15-H01. When should you use App Service versus AKS?**

**Answer:**
I would choose **App Service for straightforward web applications and HTTP APIs when I want maximum platform simplicity**, and **AKS when the application requires Kubernetes-level orchestration, multiple complex services, custom networking/scheduling, operators, sidecars, or platform-level extensibility**. Microsoft describes App Service as optimized for web applications, while AKS provides direct Kubernetes access and the broadest configurability. ([Microsoft Learn][1])

### **Decision model**

```text
Web/API workload
      ↓
Need Kubernetes features?
   /               \
 No                 Yes
 ↓                   ↓
App Service         AKS
```

---

### **Choose App Service when**

The workload is primarily:

```text
Website
REST API
Backend API
Standard web application
Single container web app
```

and I need:

```text
Managed runtime
TLS
Custom domains
Autoscaling
Deployment slots
Managed Identity
VNet Integration
Private Endpoint
Application Insights
```

without Kubernetes operations.

Example:

```text
Frontend
   ↓
Node.js API
   ↓
Azure SQL
```

This is a very natural App Service workload.

Architecture:

```text
Users
  ↓
Front Door
  ↓
App Service
  ↓
Azure SQL
```

I probably don't gain much by adding Kubernetes.

Microsoft's container-service comparison calls App Service an ideal option for web applications. ([Microsoft Learn][1])

---

### **Choose AKS when the application is a platform, not just a web app**

Suppose I have:

```text
Frontend
Payments API
Orders API
Inventory API
Async worker
Kafka consumer
Cron workload
Service mesh
Custom operator
```

and need:

```text
CRDs
operators
sidecars
DaemonSets
advanced NetworkPolicy
custom ingress
multiple node pools
GPU workloads
taints/tolerations
affinity rules
custom autoscaling
Kubernetes-native GitOps
```

Then AKS is much more appropriate.

---

### **Operational difference**

App Service:

```text
Azure manages
├── infrastructure
├── operating system
├── runtime platform
├── application hosting
└── much of scaling
```

AKS:

```text
Azure manages
└── Kubernetes control plane / managed platform pieces

You still reason about
├── pods
├── deployments
├── services
├── ingress
├── nodes/node pools
├── networking
├── upgrades
├── Kubernetes policy
└── cluster operations
```

AKS Automatic reduces much of that infrastructure work, but you're still operating a Kubernetes application model. ([Microsoft Learn][3])

---

### **Deployment differences**

App Service:

```text
Code/container
    ↓
Deployment slot
    ↓
Swap
```

AKS:

```text
Container image
    ↓
Deployment
    ↓
ReplicaSets / Pods
    ↓
Rolling / canary / blue-green
```

If deployment slots solve my release requirement cleanly, App Service can be much simpler.

---

### **Networking**

App Service gives me:

```text
Private Endpoint
→ private inbound

VNet Integration
→ private outbound
```

AKS gives much deeper networking control:

```text
Pod networking
Services
Ingress controllers
NetworkPolicy
Service mesh
CNI behavior
UDRs
LoadBalancer Services
internal load balancers
```

If I need fine-grained east-west controls or Kubernetes-specific networking, AKS is stronger.

Microsoft's architecture guidance positions AKS at the higher-control end of the Azure container options and App Service at the simpler PaaS end. ([Microsoft Learn][4])

---

### **Scaling**

App Service:

```text
Scale App Service Plan
```

Simple and effective for traditional web/API workloads.

AKS:

```text
HPA
   ↓
pods

Cluster/node autoscaling
   ↓
nodes
```

More flexible but also more moving pieces.

---

### **Team maturity matters**

Even if AKS technically supports the workload, I ask:

```text
Does the team know Kubernetes?
Do we need Kubernetes?
Can we operate it safely?
```

If the answer is no:

```text
simple REST API
+
small team
+
standard networking
```

then App Service is likely a better engineering choice.

Using AKS purely because Kubernetes looks impressive is often architectural overkill.

---

### **Example 1 — App Service**

```text
Customer portal
      ↓
.NET API
      ↓
Azure SQL
      ↓
Key Vault
```

Needs:

```text
2–6 instances
deployment slots
Managed Identity
Private SQL connectivity
```

→ **App Service**

---

### **Example 2 — AKS**

```text
40 microservices
      ↓
service mesh
      ↓
custom operators
      ↓
multiple node pools
      ↓
GPU + general compute
      ↓
GitOps
```

→ **AKS**

---

### **Strong interview answer**

> “I use App Service when the workload is fundamentally a web application or HTTP API and I want Azure to manage as much infrastructure as possible. It already gives me scaling, deployment slots, managed identity, monitoring and private networking. I choose AKS when Kubernetes features are actual requirements—for example many independently deployed microservices, operators or CRDs, custom ingress or service mesh, advanced network policies, custom scheduling, specialized node pools, or Kubernetes-native GitOps. My default is to choose the simplest platform that satisfies the requirements rather than introduce Kubernetes unnecessarily.”

**Memory line:**
**Standard web/API → App Service. Kubernetes/platform requirements → AKS.**

**Interview trap:**
Do not answer:

> “AKS is always better because it is more scalable.”

Both scale. AKS primarily buys **control and orchestration flexibility**, at higher complexity.

**Keywords:**
App Service, AKS, PaaS, Kubernetes, deployment slots, CRDs, operators, node pools

**Likely follow-ups:**

* App Service vs Container Apps?
* Would you run one container on AKS?
* How does AKS Automatic affect this decision?
* Which gives more networking control?

### **T15-H02. When should you use Azure Functions instead of Container Apps?**

**Answer:**
I would choose **Azure Functions when the workload naturally fits the Functions programming model: small event-driven units of code triggered by HTTP, timers, Service Bus, Event Grid, Event Hubs, queues, or similar sources**. I would choose Container Apps when I need a general-purpose container runtime, custom containers, sidecars, multiple processes, revision-based traffic management, or broader microservice/container control.

Microsoft describes Functions as optimized for **FaaS-style event-driven applications**, while Container Apps is optimized for general-purpose containerized microservices and jobs. ([Microsoft Learn][5])

### **Decision model**

```text
Workload triggered by events?
          ↓
Fits function programming model?
       /                 \
     Yes                  No
      ↓                    ↓
Azure Functions      Container Apps
```

---

### **Use Functions when the event is the application model**

Examples:

```text
Blob uploaded
→ resize image

Service Bus message
→ process order

Timer
→ generate report

HTTP webhook
→ validate event

Event Grid event
→ run automation
```

The architecture naturally becomes:

```text
Event
  ↓
Trigger
  ↓
Function
  ↓
Output binding / SDK
```

This is exactly what Functions is optimized for.

---

### **Functions gives developer productivity**

Functions provides:

```text
Triggers
Bindings
Function runtime
Event-driven scaling
Built-in host behavior
```

So instead of writing a long-running worker that manually:

```text
connects to queue
polls messages
handles receive loop
```

I can write:

```text
onServiceBusMessage(message)
```

and let the Functions runtime handle the invocation model.

Microsoft's architecture guidance recommends Functions for event-driven microservices with sporadic or sudden-spike traffic that benefit from trigger-based execution and scale-to-zero billing. ([Microsoft Learn][2])

---

### **Choose Container Apps when I need container control**

Container Apps becomes stronger when I need:

```text
Custom container image
Custom runtime
Sidecars
Dapr
Multiple container processes
Custom ingress behavior
Revision traffic splitting
Long-running APIs
General worker processes
Custom KEDA scalers
GPU workloads
```

For example:

```text
Python API
+
Envoy sidecar
+
custom native library
+
GPU dependency
```

is a much more natural Container Apps workload.

---

### **Interesting 2026 nuance: Functions can run on Container Apps**

This boundary is now more flexible.

Microsoft currently supports running **Azure Functions directly on Azure Container Apps**, combining:

```text
Functions programming model
+
Container Apps platform
```

That gives access to features such as:

```text
custom containers
KEDA
VNet integration
revisions
Dapr
sidecars
GPU support
```

while retaining Functions triggers and bindings. ([Microsoft Learn][6])

So the architectural decision can sometimes be:

```text
Use Functions programming model
+
host it on Container Apps
```

rather than treating Functions and Container Apps as mutually exclusive.

---

### **Example 1 — Azure Functions**

Requirement:

```text
When invoice PDF enters Storage
      ↓
extract metadata
      ↓
write DB record
```

Traffic:

```text
0 events for hours
then 5,000 events
```

Functions is an excellent fit:

```text
Blob/Event trigger
       ↓
Function
       ↓
Database
```

---

### **Example 2 — Container Apps**

Requirement:

```text
24/7 gRPC service
+
background worker
+
Dapr
+
custom container
+
sidecar
```

This isn't fundamentally a “function.”

Container Apps is more natural.

---

### **Cold start consideration**

For:

```text
low-latency synchronous API
```

I would carefully evaluate hosting and warm capacity.

Functions on a scale-to-zero plan may introduce startup latency.

Container Apps can similarly scale to zero, but I can configure:

```text
minReplicas = 1
```

And Functions Premium/Flex approaches provide always-ready options depending on the plan.

So cold start is a hosting consideration, not the sole difference between the services.

---

### **Strong interview answer**

> “I choose Azure Functions when my workload maps naturally to event-triggered units of code—such as a Service Bus consumer, timer job, webhook, Blob processor, or Event Grid handler. The trigger and binding programming model reduces a lot of integration code and gives event-driven scaling. I choose Container Apps when I need a general-purpose containerized service, custom runtime, sidecars, Dapr, revision traffic splitting, GPU support, or long-running microservices. In current Azure, Functions can also be hosted on Container Apps, so I can combine the Functions programming model with Container Apps features when required.”

**Memory line:**
**Event is the programming model → Functions. Container is the programming model → Container Apps.**

**Interview trap:**
Do not reduce the difference to:

```text
Functions = code
Container Apps = Docker
```

Functions can now also run as containers, including on Container Apps. ([Microsoft Learn][6])

**Keywords:**
Functions, FaaS, triggers, bindings, Container Apps, KEDA, event-driven, custom containers

**Likely follow-ups:**

* Can Functions run inside Container Apps?
* Functions vs Container Apps Jobs?
* Which handles Service Bus workloads better?
* Which would you choose for a long-running API?

### **T15-H03. How would you implement zero-downtime deployment with App Service slots?**

**Answer:**
I would use a **production slot and a staging slot**. The pipeline deploys the new version only to staging, validates configuration and dependencies, runs smoke/health tests, ensures the staging instances are warmed up, and then performs a **slot swap** into production. App Service prepares the source slot before switching traffic, so users continue hitting the healthy production version until the swap is ready. Microsoft explicitly recommends deployment slots for zero-downtime App Service releases. ([Microsoft Learn][7])

### **Deployment architecture**

```text
                    App Service
                         │
           ┌─────────────┴─────────────┐
           │                           │
       Production                  Staging
           │                           │
          v1                          v2
           │                           │
        Users                    CI validation
                                       │
                                  smoke tests
                                       ↓
                                      swap
                                       ↓
                                 Production = v2
```

---

### **1. Create a staging slot**

I maintain:

```text
production
staging
```

under the same App Service.

The staging slot has its own hostname, for example:

```text
myapp-staging.azurewebsites.net
```

so I can test it without sending normal production users there.

---

### **2. Never deploy the new build directly to production**

Pipeline:

```text
Git main
   ↓
CI
   ↓
Build/test
   ↓
Deploy → staging slot
```

not:

```text
Git main
   ↓
Deploy directly to production
```

Microsoft's current App Service deployment guidance specifically recommends deploying production builds into a nonproduction slot, validating them, and then swapping. ([Microsoft Learn][7])

---

### **3. Keep environment-specific settings sticky**

This is critical.

Suppose:

```text
Production
DB = prod-sql

Staging
DB = staging-sql
```

I mark environment-specific configuration as **deployment slot settings** where appropriate.

Otherwise a swap could move configuration that should remain tied to the environment.

Examples:

```text
database connection
environment name
feature flags
external endpoints
```

depending on the application.

---

### **4. Validate staging before swap**

I run:

```text
/health
/readiness
smoke tests
dependency connectivity
authentication test
synthetic transaction
```

For example:

```bash
curl -f https://myapp-staging.azurewebsites.net/health
```

Then an actual business-level synthetic test:

```text
login
  ↓
create test request
  ↓
query dependency
  ↓
verify response
```

A process being alive is not enough.

---

### **5. Make database migrations backward compatible**

This is one of the biggest production details.

During deployment there may temporarily be:

```text
old application
+
new database schema
```

or:

```text
new application
+
old-compatible schema
```

So I prefer an expand/contract migration model.

Example:

```text
Step 1
Add new DB column
but retain old column

Step 2
Deploy new application

Step 3
Migrate data

Step 4
Later remove old column
```

Bad:

```text
Drop column used by v1
      ↓
swap hasn't happened yet
      ↓
production v1 fails
```

Zero-downtime application deployment requires dependency compatibility too.

---

### **6. Warm the staging slot**

During slot swap, App Service applies target-slot settings and warms the source instances before completing the routing switch. Microsoft states that this warm-up behavior allows the swap to redirect traffic without dropping requests. ([Microsoft Learn][8])

I also make sure the application has a good health/warm-up endpoint.

The goal:

```text
v2 loaded
dependencies initialized
JIT/runtime warm
connections established
```

before production traffic reaches it.

---

### **7. Perform the swap**

Example:

```bash
az webapp deployment slot swap \
  --resource-group rg-prod \
  --name payment-api \
  --slot staging \
  --target-slot production
```

Before:

```text
Production → v1
Staging    → v2
```

After:

```text
Production → v2
Staging    → v1
```

The old production build remains available in the other slot.

---

### **8. Monitor immediately after swap**

I watch:

```text
HTTP 5xx
P95/P99 latency
request count
dependency failures
CPU/memory
Application Insights exceptions
synthetic availability
```

Example:

```text
Baseline error rate = 0.2%

After swap = 8%
```

That should trigger rollback.

---

### **9. Rollback**

Because the old version moved to staging:

```text
Production → bad v2
Staging    → known-good v1
```

I can reverse the swap:

```text
Staging v1
    ↓
swap
    ↓
Production v1
```

Current Azure Developer CLI guidance also explicitly documents reverse slot swapping as the rollback path. ([Microsoft Learn][9])

This is much faster than:

```text
rebuild old source
recreate artifact
redeploy
```

---

### **10. Optional canary validation**

Before a complete swap, App Service can route a portion of production traffic to another slot.

Conceptually:

```text
Production traffic
      │
      ├── 95% → production
      └── 5%  → staging
```

Then I compare:

```text
error rate
latency
business metrics
```

before full promotion.

This can further reduce release risk when the application supports it.

---

### **Complete release flow**

```text
Commit
  ↓
CI tests
  ↓
Build immutable artifact
  ↓
Deploy staging
  ↓
Health checks
  ↓
Smoke tests
  ↓
Backward-compatible DB check
  ↓
Warm-up
  ↓
Swap
  ↓
Production monitoring
  ↓
Healthy?
 /     \
Yes     No
 ↓       ↓
Done   Reverse swap
```

---

### **Strong interview answer**

> “I implement App Service zero-downtime deployment by keeping production and staging slots. CI deploys the new immutable build to staging, not production. I keep environment-specific configuration as slot settings, run health checks and synthetic tests, and ensure database migrations are backward compatible. App Service warms the staging workers as part of the swap process, and once validation passes I swap staging into production. I closely monitor error rate, latency and dependencies afterward. Because the previous production build moves into staging, if the release is unhealthy I immediately reverse the swap rather than rebuilding the old version.”

**Memory line:**
**Deploy staging → validate → warm → swap → observe → reverse-swap if unhealthy.**

**Interview trap:**
Deployment slots cannot make an incompatible database migration zero-downtime. The **application and its dependencies must remain backward compatible during the transition**.

**Keywords:**
Deployment slots, staging, slot swap, warm-up, smoke test, rollback, backward-compatible migration, blue-green
