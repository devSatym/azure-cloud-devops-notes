### **T15-M05. What is a private endpoint for App Service?**

**Answer:**
A private endpoint for App Service gives the application a **private IP address from an Azure VNet for inbound access** through Azure Private Link. Clients inside the VNet—or connected through peering, VPN, or ExpressRoute—can then reach the App Service privately without traversing the public internet. The private endpoint is specifically for **incoming traffic to App Service**. ([Microsoft Learn][1])

### **Core architecture**

```text
Private VM / On-prem / Private client
              ↓
         Private DNS
              ↓
       10.20.3.5
              ↓
   App Service Private Endpoint
              ↓
        Azure Private Link
              ↓
          App Service
```

Normally an App Service application has a public hostname such as:

```text
payment-api.azurewebsites.net
```

When Private Endpoint is configured correctly, clients on the private network still use the normal application hostname, but DNS ultimately resolves it through the Private Link namespace to the private endpoint IP.

---

### **Private Endpoint vs VNet Integration**

This is the most important distinction:

```text
Private Endpoint
→ inbound private connectivity TO App Service

VNet Integration
→ outbound connectivity FROM App Service
```

For example:

```text
Client
  ↓
Private Endpoint
  ↓
App Service
  ↓
VNet Integration
  ↓
Azure SQL Private Endpoint
```

Microsoft explicitly states that App Service Private Endpoint handles incoming traffic while VNet Integration handles outgoing traffic. ([Microsoft Learn][1])

---

### **Does creating a Private Endpoint automatically disable public access?**

No. A Private Endpoint and the public endpoint can coexist.

For strong isolation I would explicitly configure:

```text
Private Endpoint ✓
Private DNS ✓
Public network access = Disabled
```

Microsoft recommends disabling public network access when the intention is to expose the app only through Private Link. ([Microsoft Learn][1])

---

### **DNS is critical**

Suppose the private endpoint has:

```text
10.20.3.5
```

If the client still resolves:

```text
payment-api.azurewebsites.net
→ public App Service address
```

it can continue attempting the public path.

The desired private path is conceptually:

```text
payment-api.azurewebsites.net
            ↓
Private Link DNS
            ↓
10.20.3.5
```

So troubleshooting a Private Endpoint usually starts with:

```bash
nslookup payment-api.azurewebsites.net
```

and verifying that the client receives the expected private address.

---

### **On-premises access**

A private endpoint is also useful when:

```text
Corporate network
       ↓
VPN / ExpressRoute
       ↓
Azure VNet
       ↓
App Service Private Endpoint
```

Microsoft specifically supports private App Service access from connected on-premises networks over VPN or ExpressRoute private connectivity. ([Microsoft Learn][1])

---

### **Important slot behavior**

Deployment slots are treated separately.

For example:

```text
Production
→ Private Endpoint A

Staging
→ Private Endpoint B
```

A Private Endpoint isn't automatically shared between slots; Microsoft documents private endpoints per slot. ([Microsoft Learn][1])

> **In an interview, I would say:**
> “An App Service Private Endpoint provides private inbound connectivity to the application by creating a Private Link network interface with an IP from my VNet. Private clients resolve the App Service hostname to that private address and reach the app over Microsoft's private network. I would normally combine it with Private DNS and disable public network access. I also distinguish it from VNet Integration: Private Endpoint is inbound to App Service, while VNet Integration is outbound from App Service toward private dependencies.”

**Memory line:**
**Private Endpoint = private inbound; VNet Integration = private outbound.**

**Interview trap:**
Creating a Private Endpoint does **not automatically mean the public App Service endpoint is unavailable**. Explicitly control public network access.

**Keywords:**
Private Endpoint, Private Link, private IP, Private DNS, public network access, VNet Integration

**Likely follow-ups:**

* Private Endpoint vs VNet Integration?
* Why is DNS required?
* How would on-premises users access a private App Service?
* Can staging and production slots share the same Private Endpoint?

### **T15-M06. What are Azure Functions triggers and bindings?**

**Answer:**
A **trigger** determines **when and why an Azure Function executes**, while a **binding** declaratively connects that function to another service for input or output without requiring me to write all of the integration plumbing manually. Every function has exactly **one trigger**, while input and output bindings are optional and a function can have multiple bindings. ([Microsoft Learn][2])

### **Trigger**

A trigger answers:

> **What causes this function to run?**

Examples:

```text
HTTP request
→ HTTP trigger

Service Bus message
→ Service Bus trigger

Timer expires
→ Timer trigger

Blob event
→ Blob trigger
```

Architecture:

```text
Event
  ↓
Trigger
  ↓
Function executes
```

For example:

```text
Service Bus
     ↓
Message arrives
     ↓
Service Bus Trigger
     ↓
processOrder()
```

Microsoft defines the trigger as the mechanism that invokes the function and notes that every function must have exactly one trigger. ([Microsoft Learn][2])

---

### **Binding**

A binding connects the function to another resource.

There are two major types:

```text
Input binding
→ bring data INTO the function

Output binding
→ send data OUT of the function
```

Example:

```text
Service Bus Trigger
        ↓
Function
        ↓
Cosmos DB output binding
```

Instead of manually writing all connection/integration code, the runtime can provide or write the data through binding configuration.

---

### **Full example**

Imagine a function that processes an uploaded order:

```text
Service Bus
   ↓
Trigger
   ↓
Function
   ↓
Input Binding → Blob metadata
   ↓
Business logic
   ↓
Output Binding → Cosmos DB
```

So:

```text
Trigger
→ starts execution

Input binding
→ provides additional data

Output binding
→ sends results somewhere
```

Microsoft describes bindings as declarative connections that pass data into a function or write data out of it. ([Microsoft Learn][2])

---

### **Why bindings are useful**

Without binding:

```text
Function
  ↓
Create SDK client
  ↓
Read connection config
  ↓
Call service
  ↓
Handle integration plumbing
```

With binding:

```text
Function
  ↓
binding parameter
  ↓
Azure service
```

This can reduce boilerplate code.

However, I wouldn't force bindings into every architecture. For complicated application logic, explicit SDK clients can provide greater:

```text
control
error handling
batching
retry behavior
testing flexibility
```

So bindings are convenience and abstraction—not a mandatory design rule.

---

### **Example interview distinction**

If somebody says:

> “Can a function have two triggers?”

Normally:

```text
One function
→ exactly one trigger
```

If I need separate invocation mechanisms, I typically define separate function entry points.

But one function can have:

```text
1 trigger
+
multiple input/output bindings
```

([Microsoft Learn][2])

> **In an interview, I would say:**
> “A trigger defines what causes an Azure Function to execute, such as an HTTP request, timer, queue message, or Service Bus event. Every function has exactly one trigger. Bindings are optional declarative connections to other services: input bindings bring data into the function and output bindings send data out. For example, a Service Bus trigger could invoke a function and a Cosmos DB output binding could store the result. Bindings reduce integration boilerplate, although I may still use SDKs directly when I need finer control.”

**Memory line:**
**Trigger starts the function; bindings move data into or out of it.**

**Interview trap:**
Do not say a single Azure Function normally has multiple triggers. It has **one trigger**, but can have several bindings.

**Keywords:**
Trigger, input binding, output binding, HTTP trigger, Service Bus trigger, declarative integration

**Likely follow-ups:**

* Can a function have multiple triggers?
* Trigger vs input binding?
* When would you use an SDK instead of a binding?
* Give an example using Service Bus and Cosmos DB.

### **T15-M07. What is the difference between Consumption and Premium Azure Functions hosting?**

**Answer:**
The classic **Consumption plan** is designed for low-cost serverless execution where instances can scale to zero and billing is largely based on executions and resource consumption. The **Elastic Premium plan** still provides event-driven autoscaling, but keeps at least one instance available and supports always-ready/prewarmed capacity, stronger networking options, larger compute choices, longer execution scenarios, and more predictable performance—at a higher baseline cost. ([Microsoft Learn][3])

### **Quick comparison**

| Area             | Consumption                        | Elastic Premium                                           |
| ---------------- | ---------------------------------- | --------------------------------------------------------- |
| Scaling          | Event-driven                       | Event-driven                                              |
| Scale to zero    | Yes                                | No, minimum active capacity                               |
| Cold start       | Possible                           | Mitigated with always-ready/prewarmed instances           |
| Baseline cost    | Can be near zero when idle         | Minimum billed capacity                                   |
| VNet Integration | Classic Consumption: not supported | Supported                                                 |
| Compute choice   | More constrained                   | EP instance sizes                                         |
| Containers       | Limited/legacy scenarios           | Supported on Linux                                        |
| Best fit         | Low/irregular workloads            | Production, latency-sensitive, networking-heavy workloads |

([Microsoft Learn][3])

---

### **1. Consumption**

Classic Consumption works roughly like:

```text
No events
   ↓
0 instances
   ↓
No active execution

Event arrives
   ↓
instance created
   ↓
function executes
   ↓
scale out if required
```

This is attractive for:

```text
sporadic workloads
background automation
low traffic
cost-sensitive event processing
```

because I don't keep dedicated compute running continuously.

---

### **2. Cold starts**

The downside of scaling to zero is:

```text
Function idle
    ↓
0 instances
    ↓
HTTP request arrives
    ↓
runtime/app starts
    ↓
extra latency
```

This is a **cold start**.

Microsoft currently classifies classic Consumption as having expected cold starts because there are no always-ready instances in that plan. ([Microsoft Learn][4])

---

### **3. Premium**

Premium uses:

```text
Always-ready instance(s)
          +
Prewarmed capacity during scale
```

Conceptually:

```text
Idle
 ↓
1+ warm instances remain
 ↓
Request
 ↓
handled immediately
```

As demand rises:

```text
Always-ready
      ↓
becomes busy
      ↓
prewarmed capacity activates
      ↓
more instances provisioned
```

Microsoft states Premium keeps at least one active billed instance and uses always-ready plus prewarmed instances to effectively eliminate cold-start delays for configured capacity. ([Microsoft Learn][3])

---

### **4. Networking**

This is a major practical difference.

Premium supports:

```text
Regional VNet Integration
Private networking scenarios
```

so a function can privately access resources such as:

```text
Azure SQL Private Endpoint
Storage Private Endpoint
internal APIs
on-prem services through connected networks
```

Classic Consumption does not support VNet Integration, whereas Elastic Premium does. ([Microsoft Learn][5])

---

### **5. Cost**

Consumption:

```text
Pay mainly when functions execute
```

Premium:

```text
Pay for provisioned core/memory time
+
minimum active instance exists
```

Therefore:

```text
Very low / sporadic usage
→ Consumption may be cheaper

Steady high traffic
or latency-sensitive workload
→ Premium may make more sense
```

Premium has a baseline monthly cost even when the application is mostly idle. ([Microsoft Learn][3])

---

### **6. Important 2026 update: Flex Consumption**

For a current interview, I would add one sentence:

> **Classic Consumption is now considered the legacy dynamic plan for new serverless Function Apps; Microsoft recommends Flex Consumption for new serverless workloads where its feature set fits.**

Flex Consumption provides faster scaling, private networking, managed identity improvements, and optional always-ready capacity while preserving consumption-style billing. ([Microsoft Learn][6])

So the modern mental model is:

```text
Classic Consumption
→ legacy simple consumption model

Flex Consumption
→ current recommended serverless consumption option

Elastic Premium
→ dedicated warm capacity + advanced production capabilities
```

---

### **Production example**

Use Consumption for:

```text
Timer runs twice per day
      ↓
process report
      ↓
finish
```

Use Premium for:

```text
Customer-facing HTTP API
        ↓
strict latency requirements
        ↓
Private SQL dependency
        ↓
VNet integration required
```

> **In an interview, I would say:**
> “Consumption is the traditional pay-per-execution Functions plan. It can scale down to zero, which keeps idle cost very low, but that means cold starts are possible. Elastic Premium still dynamically scales but maintains always-ready capacity and uses prewarmed instances, so it's better for latency-sensitive workloads. Premium also provides VNet Integration, more compute control, longer execution support and container capabilities, but there is a baseline cost because at least one instance remains allocated. In 2026 I would also mention that classic Consumption is now legacy for new apps and Microsoft recommends Flex Consumption for many new serverless workloads.”

**Memory line:**
**Consumption optimizes idle cost; Premium optimizes readiness, networking, and predictable production performance.**

**Interview trap:**
Do not say Premium is just “Consumption with bigger CPU.” Its networking, warm-capacity, runtime, and billing behavior are materially different.

**Keywords:**
Consumption, Elastic Premium, cold start, always-ready, prewarmed, VNet Integration, Flex Consumption

**Likely follow-ups:**

* Why does Consumption experience cold starts?
* How does Premium avoid cold starts?
* What is Flex Consumption?
* When would you accept Premium's extra cost?

### **T15-M08. How does Container Apps scaling work?**

**Answer:**
Azure Container Apps uses **rule-based horizontal autoscaling powered largely by KEDA**. I configure a minimum and maximum number of replicas and one or more scale rules, such as **HTTP concurrency, TCP connections, CPU, memory, Azure Queue depth, Service Bus messages, or another KEDA-supported event source**. The platform then adds or removes replicas based on those signals. ([Microsoft Learn][7])

### **Basic model**

```text
Traffic / Events
       ↓
Scaling rule
       ↓
KEDA / Container Apps scaler
       ↓
Replica count
       ↓
0 → 1 → 5 → 20
```

---

### **1. Minimum and maximum replicas**

Example:

```text
minReplicas = 1
maxReplicas = 20
```

means:

```text
Never below 1
Never above 20
```

If I configure:

```text
minReplicas = 0
```

a compatible event-driven or HTTP workload can scale down to zero when idle.

Microsoft currently documents the default minimum as `0` and default maximum as `10`, with higher configurable maximums supported depending on the current platform limits. ([Microsoft Learn][7])

---

### **2. HTTP scaling**

For a web API:

```text
HTTP requests
      ↓
Concurrent requests exceed threshold
      ↓
Add replicas
```

For example:

```text
Target:
50 concurrent requests per replica

Traffic:
200 concurrent requests
      ↓
approximately more replicas required
```

The exact scale decision is made by the platform's scaling behavior rather than a simple manual division, but HTTP concurrency is the main signal.

Example CLI concept:

```bash
az containerapp update \
  --name api \
  --resource-group rg-app \
  --min-replicas 1 \
  --max-replicas 10
```

HTTP scaling is a built-in Container Apps scale-rule type. ([Microsoft Learn][7])

---

### **3. Event-driven scaling with KEDA**

This is where Container Apps becomes especially useful for workers.

Example:

```text
Azure Service Bus
Queue depth = 0
      ↓
0 worker replicas
```

Then:

```text
Queue depth = 10,000
      ↓
KEDA scaler detects backlog
      ↓
Container Apps
      ↓
1 → 5 → 20 workers
```

As the backlog drains:

```text
20 → 10 → 2 → 0
```

This gives:

```text
cost proportional to work
+
automatic burst handling
```

KEDA-based custom scalers are a core part of Container Apps autoscaling. ([Microsoft Learn][7])

---

### **4. CPU and memory scaling**

Container Apps also supports scaling based on CPU or memory utilization.

For example:

```text
Average memory > 70%
      ↓
Scale out
```

But there is an important nuance:

**CPU and memory scaling alone do not support scaling all the way to zero**, because there must be a running replica from which resource utilization can be measured. Microsoft explicitly documents this limitation. ([Microsoft Learn][8])

So:

```text
HTTP / event scaler
→ can support scale-to-zero

CPU-only / memory-only rule
→ keep minReplicas >= 1
```

is a useful interview distinction.

---

### **5. Multiple scaling signals**

A containerized worker could use:

```text
Service Bus backlog
```

while the frontend uses:

```text
HTTP concurrency
```

Example:

```text
Frontend Container App
       ↓
HTTP scaler

Worker Container App
       ↓
Service Bus/KEDA scaler
```

Each workload scales according to the signal that actually represents demand.

---

### **6. Scale-to-zero**

This is a key Container Apps capability.

```text
No traffic/events
       ↓
0 replicas
       ↓
No active replica usage
```

Then:

```text
New event/request
       ↓
platform activates workload
```

The tradeoff is potential startup latency.

For latency-sensitive production APIs I might configure:

```text
minReplicas = 1
```

instead of zero.

---

### **7. Scaling is revision-specific**

Container Apps revisions are immutable snapshots.

Scale settings apply to revisions, and changing scaling configuration can create a new revision. Microsoft documents scaling limits and rules at the revision level. ([Microsoft Learn][7])

Conceptually:

```text
Revision v1
→ 3 replicas

Revision v2
→ 7 replicas
```

if both are active and receiving traffic.

---

### **Container Apps vs AKS scaling**

Conceptually:

```text
AKS
→ HPA/KEDA scales pods
→ Cluster Autoscaler / node autoscaling handles nodes
→ you manage Kubernetes concerns

Container Apps
→ configure application replica rules
→ Azure manages underlying orchestration capacity
```

That's a major reason Container Apps reduces operational complexity.

> **In an interview, I would say:**
> “Container Apps uses rule-based horizontal scaling, largely powered by KEDA. I configure minimum and maximum replica counts and scale rules based on signals such as HTTP concurrency, TCP connections, CPU, memory, queue depth or other KEDA-supported event sources. For example, a Service Bus worker can scale from zero when there are no messages to many replicas when a backlog appears, then scale back down after the queue drains. For latency-sensitive services I normally keep at least one replica warm. I also remember that CPU- or memory-only scaling can't independently scale from zero because there has to be a running replica to measure utilization.”

**Memory line:**
**Container Apps scaling = demand signal → KEDA/rule → replica count.**

**Interview trap:**
Do not say every Container Apps scaling rule can scale to zero. CPU/memory-only rules need running capacity.

**Keywords:**
KEDA, replicas, HTTP concurrency, queue depth, scale-to-zero, min replicas, max replicas

**Likely follow-ups:**

* How does KEDA work with Container Apps?
* Why can't CPU-only scaling go from zero?
* When would you keep `minReplicas = 1`?
* Container Apps scaling vs AKS HPA?
