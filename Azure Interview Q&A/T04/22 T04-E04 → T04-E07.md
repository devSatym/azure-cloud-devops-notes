# 4. 🔴 M IMP — Azure Virtual Machines, VMSS & Compute

## Easy

### **T04-E04. What are OS disks and data disks?**

**Answer:**
An **OS disk** contains the virtual machine’s operating system, boot files, and system volume.

A **data disk** is an additional persistent managed disk attached to the VM for application data, databases, logs, or other workload files.

So:

```text
OS disk   → operating system
Data disk → application/workload data
```

### **Example**

A Linux VM could have:

```text
OS Disk
└── /
    └── Ubuntu operating system

Data Disk 1
└── /data
    └── Application files

Data Disk 2
└── /var/lib/database
    └── Database data
```

Keeping important application data on separate data disks can make storage management, resizing, backup, and recovery easier.

### **Important point**

Both OS and data disks can use Azure Managed Disks and can be persistent.

A VM may also have a **temporary/local disk**, but that is different: temporary disk data can be lost during events such as host movement or redeployment, so I would not store critical data there.

**Memory line:**
**OS disk boots the VM; data disks store workload data.**

**Interview trap:**
Do not confuse a **data disk** with a **temporary disk**.

Data disks are persistent managed storage. Temporary disks are host-local and should only hold disposable data.

**Keywords:** OS disk, data disk, managed disk, persistent storage, temporary disk

### **T04-E05. What is an Azure Availability Set?**

**Answer:**
An Azure Availability Set is a logical grouping of VMs that helps improve availability by distributing them across different **fault domains and update domains** within an Azure datacenter infrastructure.

Its purpose is to reduce the chance that all application VMs become unavailable because of a single hardware failure or planned maintenance event.

### **How it works**

Conceptually:

```text
Availability Set
│
├── VM-1
│   ├── Fault Domain 1
│   └── Update Domain 1
│
└── VM-2
    ├── Fault Domain 2
    └── Update Domain 2
```

* **Fault domains** separate VMs across different underlying hardware groups.
* **Update domains** help ensure planned platform maintenance does not update all instances at the same time.

### **Example**

If I run two web servers:

```text
web-vm-01
web-vm-02
```

placing them in an Availability Set can reduce the risk that both go down simultaneously because of a rack-level hardware issue or planned Azure maintenance.

### **Availability Set vs Availability Zone**

An Availability Set protects against failures **within a datacenter environment**.

Availability Zones provide stronger physical separation because they use separate datacenter groups within the same Azure region.

For new highly available designs in a region that supports zones, I would generally prefer **Availability Zones** where the workload and VM SKU support them. ([learn.microsoft.com](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview?utm_source=chatgpt.com))

**Memory line:**
**Availability Set = spread VMs across fault and update domains.**

**Interview trap:**
An Availability Set does **not protect against an entire Azure region failure**, and it does not provide the same datacenter-level separation as Availability Zones.

**Keywords:** Availability Set, fault domain, update domain, high availability, planned maintenance

### **T04-E06. What is an Availability Zone?**

**Answer:**
An Availability Zone is a **physically separate group of datacenters within an Azure region**, with independent power, cooling, and networking.

By distributing VM instances across multiple zones, I can protect an application from a failure affecting one datacenter or zone.

### **Example**

Suppose I deploy:

```text
web-vm-01 → Zone 1
web-vm-02 → Zone 2
web-vm-03 → Zone 3
```

and place them behind a zone-resilient load-balancing service.

If Zone 1 fails:

```text
Zone 1 ❌

Zone 2 ✅
Zone 3 ✅
```

the remaining instances can continue serving traffic.

### **Why zones are stronger than Availability Sets**

Availability Sets distribute VMs across hardware failure boundaries within a datacenter environment.

Availability Zones provide **physical datacenter-level isolation** inside the region.

So for high availability:

```text
Availability Set
→ hardware/maintenance isolation

Availability Zones
→ datacenter/zone isolation
```

Azure recommends zone-aware or zone-redundant designs where available for workloads that require higher resiliency. ([learn.microsoft.com](https://learn.microsoft.com/en-us/azure/availability-zones/az-overview?utm_source=chatgpt.com))

**Memory line:**
**Availability Zone = separate datacenter failure domain inside one region.**

**Interview trap:**
Availability Zones protect against a **zone failure**, not a complete regional outage.

For regional disaster recovery, I still need a multi-region architecture.

**Keywords:** Availability Zone, zonal VM, zone-redundant, datacenter isolation, high availability

### **T04-E07. What is a Virtual Machine Scale Set?**

**Answer:**
Azure Virtual Machine Scale Sets, or **VMSS**, let me deploy and manage a group of similar virtual machines as a single scalable compute resource.

VMSS is designed for workloads that need:

* multiple VM instances,
* automatic scaling,
* load balancing,
* consistent configuration,
* rolling upgrades,
* high availability.

### **Example**

Suppose a web application normally needs:

```text
2 VMs
```

but during peak traffic needs:

```text
10 VMs
```

With VMSS:

```text
Low traffic
VM VM

      ↓ Autoscale

High traffic
VM VM VM VM VM VM VM VM VM VM
```

Azure Monitor autoscale rules can increase or decrease the number of VM instances based on metrics such as CPU usage or other supported signals.

### **Typical architecture**

```text
Users
   ↓
Azure Load Balancer / Application Gateway
   ↓
VM Scale Set
├── VM instance 1
├── VM instance 2
├── VM instance 3
└── ...
```

The VM instances are created from a common model so I can manage them consistently. VMSS also supports spreading instances across Availability Zones for resilient architectures. ([learn.microsoft.com](https://learn.microsoft.com/en-us/azure/virtual-machine-scale-sets/overview?utm_source=chatgpt.com))

### **When I would use it**

VMSS is suitable when I need VM-level control but also want cloud-native scaling and fleet management.

For example:

* stateless web servers,
* application servers,
* build agents,
* batch processing workers.

If I do not need OS-level VM control, I would also evaluate services such as App Service, Container Apps, or AKS.

**Memory line:**
**VMSS = a scalable, consistently managed fleet of Azure VMs.**

**Interview trap:**
VMSS is not just “multiple VMs.”

The important value is **centralized instance management, scaling, availability, and upgrade orchestration**.

**Keywords:** VMSS, autoscaling, instance model, load balancing, rolling upgrade, Availability Zones
