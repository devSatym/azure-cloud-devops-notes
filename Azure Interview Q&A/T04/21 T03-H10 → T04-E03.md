# 3. 🔴 M IMP — Azure Virtual Networking

## Hard

### **T03-H10. How would you troubleshoot intermittent SNAT port exhaustion?**

**Answer:**
SNAT port exhaustion happens when a workload creates more outbound connections than the available source NAT ports can support.

The typical symptom is **intermittent outbound connection failure**, especially under high concurrency, while inbound traffic and some existing connections may continue working.

My troubleshooting flow would be:

```text
Confirm outbound failures
      ↓
Identify outbound mechanism
      ↓
Check SNAT connection metrics
      ↓
Inspect connection behavior
      ↓
Fix application connection reuse
      ↓
Increase/replace SNAT capacity
```

### **1. Confirm that the problem is outbound and intermittent**

I would first verify:

* which destinations are failing,
* whether only outbound connections are affected,
* whether failures increase with traffic,
* whether existing connections continue working while new connections fail.

Typical symptoms include:

* connection timeouts,
* intermittent TCP failures,
* API calls failing only during traffic spikes,
* database or external API connection failures.

---

### **2. Identify the outbound connectivity method**

I would check whether the workload is using:

* NAT Gateway,
* Standard Load Balancer outbound rules,
* Azure Firewall,
* public IP,
* or another SNAT mechanism.

The available SNAT capacity and troubleshooting method depend on that architecture.

---

### **3. Check Azure Monitor metrics**

For NAT Gateway, I would inspect metrics such as:

```text
SNAT Connection Count
Total SNAT Connection Count
Datapath Availability
```

A rise in **failed SNAT connections** can indicate port exhaustion. Microsoft specifically recommends monitoring failed SNAT connection counts when diagnosing this problem. ([Microsoft Learn][1])

---

### **4. Check application connection behavior**

SNAT exhaustion is often caused not just by high traffic, but by inefficient connection management.

I would check whether the application:

* creates a new TCP connection for every request,
* fails to reuse HTTP connections,
* creates excessive database connections,
* leaves connections idle for long periods,
* lacks proper connection pooling.

For example:

```text
Bad:
Request
 ↓
Open connection
 ↓
Call API
 ↓
Close
 ↓
Repeat thousands of times
```

A better approach is:

```text
Connection pool / keep-alive
        ↓
Reuse existing connections
        ↓
Fewer SNAT allocations
```

### **5. Check idle timeout settings**

Long idle timeouts can keep SNAT ports allocated longer than necessary.

Microsoft notes that increasing NAT Gateway's idle timeout significantly can cause ports to remain unavailable longer and contribute to exhaustion. ([Microsoft Learn][1])

So I would not increase idle timeout blindly.

---

### **6. Scale the outbound architecture**

If connection behavior is legitimate and additional capacity is required, I would consider:

```text
Add NAT Gateway public IPs
          ↓
Increase available SNAT inventory
```

or attach a public IP prefix where appropriate.

For architectures currently relying on Load Balancer SNAT, I would strongly consider moving outbound connectivity to **Azure NAT Gateway**, because it uses dynamic SNAT allocation and is specifically designed to reduce SNAT exhaustion risk. ([Microsoft Learn][2])

### **Example**

Suppose 20 application VMs call an external payment API.

During peak traffic:

```text
Thousands of new outbound TCP connections/sec
                    ↓
Available SNAT ports exhausted
                    ↓
New API requests timeout
```

I would:

```text
1. Check NAT/SNAT metrics
2. Check application connection pooling
3. Reduce unnecessary short-lived connections
4. Check idle timeout
5. Scale NAT Gateway public IP capacity if required
```

**Memory line:**
**SNAT exhaustion = too many outbound connections competing for finite translated source ports.**

**Interview trap:**
Do not solve SNAT exhaustion only by adding more public IPs.

That may increase capacity, but if the application creates excessive short-lived connections, I would also fix **connection pooling and reuse**.

**Keywords:** SNAT exhaustion, NAT Gateway, connection pooling, keep-alive, outbound connectivity, SNAT ports, Azure Monitor

**Likely follow-ups:**

* How does NAT Gateway reduce SNAT exhaustion?
* What application behavior commonly causes SNAT exhaustion?
* Which NAT Gateway metric would you inspect?
* Why can increasing idle timeout make exhaustion worse?

# 4. 🔴 M IMP — Azure Virtual Machines, VMSS & Compute

## Easy

### **T04-E01. What is an Azure Virtual Machine?**

**Answer:**
An Azure Virtual Machine is an **IaaS compute service that provides a virtualized Windows or Linux server running on Microsoft Azure infrastructure**.

With a VM, Azure manages the physical datacenter, servers, storage infrastructure, and virtualization layer, while I am responsible for much of the guest operating system and software running inside the VM.

That typically includes:

* OS configuration,
* patching,
* installed applications,
* host-level security configuration,
* application runtime.

Azure VMs are useful when I need **more control over the operating system or compute environment** than a managed PaaS service provides. ([Microsoft Learn][3])

### **Example**

I might choose an Azure VM for:

```text
Legacy application
     ↓
Requires specific Linux packages
     ↓
Needs OS-level configuration
     ↓
Azure VM
```

The VM could then have:

```text
VM
├── CPU / Memory
├── OS Disk
├── Data Disks
├── NIC
├── VNet/Subnet
└── NSG
```

### **When I would choose a VM**

Good use cases include:

* legacy applications,
* custom software requiring OS access,
* development/test servers,
* self-managed databases,
* network appliances,
* workloads that cannot easily run on PaaS.

If I do not need OS-level control, I would also consider managed services such as App Service, Container Apps, or AKS depending on the workload.

**Memory line:**
**Azure VM = cloud server where Azure manages the hardware, but I manage the guest OS and application.**

**Interview trap:**
A VM is **IaaS, not fully managed PaaS**.

Microsoft manages the physical infrastructure, but I still have operational responsibilities such as OS configuration and patching. ([Microsoft Learn][3])

**Keywords:** Azure VM, IaaS, virtualization, Windows, Linux, guest OS, compute

---

### **T04-E02. What is an Azure VM size?**

**Answer:**
An Azure VM size defines the **compute capacity and hardware characteristics allocated to a virtual machine**.

The selected size determines things such as:

* number of vCPUs,
* memory,
* maximum disk throughput and IOPS,
* network bandwidth,
* number of data disks,
* temporary/local storage,
* GPU availability for supported families.

Azure provides different VM families optimized for different workload types. ([Microsoft Learn][3])

### **Common categories**

For example:

```text
General purpose
→ balanced CPU and memory

Compute optimized
→ higher CPU-to-memory ratio

Memory optimized
→ large memory capacity

Storage optimized
→ high local/disk throughput

GPU
→ AI, graphics, rendering, compute
```

### **Example**

For a small web server:

```text
General-purpose VM
```

may be appropriate.

For an in-memory database:

```text
Memory-optimized VM
```

may be more suitable.

For heavy computation:

```text
Compute-optimized VM
```

could be better.

### **Why VM size matters**

The VM size also affects:

* cost,
* performance,
* scaling limits,
* available disk configuration,
* network performance.

So I select the VM size based on actual workload CPU, memory, storage, and networking requirements rather than choosing only by vCPU count.

**Memory line:**
**VM size = CPU + memory + storage/network limits + cost profile.**

**Interview trap:**
Two Azure VM sizes with the same number of vCPUs may still have different:

* RAM,
* disk throughput,
* network bandwidth,
* local storage,
* supported features.

So sizing is not just about CPU count.

**Keywords:** VM size, vCPU, memory, IOPS, throughput, bandwidth, VM family

### **T04-E03. What is an Azure managed disk?**

**Answer:**
An Azure managed disk is a **persistent block-storage volume managed by Azure and designed primarily for Azure Virtual Machines**.

Instead of manually managing the underlying Azure Storage account, I specify things such as:

* disk type,
* disk size,
* performance characteristics,

and Azure handles the underlying storage placement and management. ([Microsoft Learn][4])

A managed disk behaves conceptually like a physical disk attached to a server:

```text
Azure VM
   │
   ├── OS Managed Disk
   └── Data Managed Disk
```

### **Main managed disk types**

Azure currently provides disk options including:

* Standard HDD,
* Standard SSD,
* Premium SSD,
* Premium SSD v2,
* Ultra Disk.

They are designed for different combinations of:

* cost,
* latency,
* IOPS,
* throughput,
* workload criticality. ([Microsoft Learn][5])

### **Example**

For a normal development VM:

```text
Standard SSD
```

may be sufficient.

For a production application requiring consistent high performance:

```text
Premium SSD
```

may be more suitable.

For very high-I/O database workloads:

```text
Premium SSD v2
or
Ultra Disk
```

may be considered depending on requirements and support.

### **Why managed disks are useful**

Azure manages:

* underlying storage accounts,
* replication,
* availability,
* disk lifecycle integration,
* scalability.

This means I focus on selecting the required **capacity and performance**, rather than manually managing storage-account placement.

**Memory line:**
**Managed disk = Azure-managed persistent block storage for VMs.**

**Interview trap:**
Do not confuse a managed disk with the VM's **temporary/local disk**.

Managed disks are persistent Azure storage.

Temporary disks are physically associated with the VM host and should only contain data that can be lost.

**Keywords:** managed disk, block storage, persistent storage, OS disk, data disk, Premium SSD, Ultra Disk
