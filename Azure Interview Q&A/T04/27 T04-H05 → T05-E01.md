# 4. 🔴 M IMP — Azure Virtual Machines, VMSS & Compute

## Hard

### **T04-H05. How would you perform rolling upgrades on a VM Scale Set?**

**Answer:**
For a production VM Scale Set, I would use the **Rolling upgrade policy** so Azure updates instances in controlled batches instead of updating every VM at once.

The goal is:

> **Upgrade part of the fleet → verify health → continue to the next batch → maintain enough healthy capacity throughout.**

Azure currently supports **Manual, Automatic, and Rolling** VMSS upgrade-policy modes. Rolling mode is specifically intended for workloads where availability must be maintained during model updates. ([Microsoft Learn][1])

### **Typical flow**

Suppose I have:

```text
VMSS
├── VM-1
├── VM-2
├── VM-3
├── VM-4
├── VM-5
└── VM-6
```

I update the scale-set model to a new image:

```text
v1 → v2
```

With rolling upgrades:

```text
Batch 1
VM-1, VM-2
   ↓
Upgrade
   ↓
Health check
   ↓
Healthy ✅

Batch 2
VM-3, VM-4
   ↓
Upgrade
   ↓
Health check
   ↓
Healthy ✅

Batch 3
VM-5, VM-6
```

So I don't take all six instances down simultaneously.

### **1. Configure health monitoring first**

This is essential.

Azure needs to know whether an upgraded instance is actually healthy before continuing.

Depending on the VMSS orchestration mode, rolling upgrades require application health monitoring using a **load-balancer health probe or Application Health Extension**. For Flexible orchestration, Microsoft specifically requires the Application Health Extension for rolling upgrades. ([Microsoft Learn][1])

For example:

```text
VM starts
   ↓
Application starts
   ↓
/health returns 200
   ↓
Instance considered healthy
```

I would make the health probe represent actual application readiness rather than merely checking whether the OS is running.

---

### **2. Update the VMSS model**

Changes might include:

* new image version,
* OS update,
* VM configuration,
* extension changes.

For image-based deployments, I prefer a tested image in something like **Azure Compute Gallery**.

Conceptually:

```text
Image v1
   ↓
Build/test
   ↓
Image v2
   ↓
Update VMSS model
```

---

### **3. Configure rolling parameters**

I control things such as:

* maximum batch size,
* minimum healthy percentage,
* unhealthy-instance handling,
* cross-zone upgrade behavior,
* MaxSurge where appropriate.

The objective is to maintain enough healthy instances to serve production traffic while each batch upgrades. ([Microsoft Learn][1])

For example:

```text
10 VM instances

20% batch
→ upgrade ~2 at a time
```

rather than:

```text
10/10 unavailable simultaneously ❌
```

---

### **4. Keep spare capacity**

If the application requires:

```text
minimum 6 instances
```

to handle production traffic, I should not run exactly six instances and then take a large percentage offline for upgrades.

I may temporarily maintain extra capacity:

```text
Required capacity = 6
Running during upgrade = 8
```

This reduces the chance of overload during deployment.

---

### **5. Monitor the rollout**

During each batch I watch:

* application health,
* VM provisioning status,
* HTTP error rate,
* latency,
* CPU/memory,
* load-balancer health,
* Azure Monitor alerts.

If upgraded instances become unhealthy, I want the rollout to stop rather than blindly upgrade the remaining fleet.

### **Production deployment pattern**

A good process is:

```text
Build image
   ↓
Security + functional testing
   ↓
Deploy to staging
   ↓
Validate
   ↓
Update VMSS model
   ↓
Rolling upgrade
   ↓
Health validation per batch
   ↓
Complete rollout
```

For more critical systems, I might also use:

```text
Canary deployment
```

or maintain separate scale sets for **blue/green deployment**, depending on release requirements.

**Memory line:**
**Rolling VMSS upgrade = update in batches, validate health, keep enough instances serving traffic.**

**Interview trap:**
Do not say:

> “Rolling upgrade just updates every VM one after another.”

The important production concepts are **batch size, application health, healthy-capacity thresholds, and controlled progression**.

**Keywords:** VMSS, rolling upgrade, upgrade policy, health probe, Application Health Extension, batch, MaxSurge

**Likely follow-ups:**

* Automatic vs Manual vs Rolling upgrade?
* What happens when an upgraded VM becomes unhealthy?
* Why is a health probe important?
* How would you achieve near-zero-downtime VMSS deployment?

### **T04-H06. How do you choose between VMs, VMSS, App Service, Container Apps, and AKS?**

**Answer:**
I choose based on **how much infrastructure control the application actually needs**.

My general principle is:

> **Use the highest-level managed service that satisfies the application's requirements. Don't operate Kubernetes or VMs unless the workload actually needs that control.**

Azure's current compute guidance makes the same distinction: VMs give maximum infrastructure control, App Service provides managed application hosting, Container Apps provides managed/serverless container hosting without direct Kubernetes API access, and AKS provides managed Kubernetes with access to the Kubernetes control plane/API. ([Microsoft Learn][2])

### **Quick decision table**

| Service            | I choose it when...                                   | Main trade-off                        |
| ------------------ | ----------------------------------------------------- | ------------------------------------- |
| **VM**             | I need full OS control                                | Highest management burden             |
| **VMSS**           | I need many scalable VMs                              | Still manage VM/OS layer              |
| **App Service**    | Standard web/API app                                  | Less infrastructure control           |
| **Container Apps** | Containerized app without Kubernetes-management needs | Less Kubernetes-level control         |
| **AKS**            | I actually need Kubernetes                            | Highest container-platform complexity |

---

### **1. Azure VM**

I choose a VM when the application needs:

* OS-level access,
* custom kernel/software,
* legacy installation,
* unsupported runtime,
* network appliance,
* lift-and-shift deployment.

Example:

```text
Legacy Java application
+
custom OS packages
+
specific filesystem configuration
        ↓
Azure VM
```

The trade-off is that I manage:

```text
OS
patching
agents
scaling
configuration
availability design
```

---

### **2. VM Scale Sets**

I choose VMSS when I need **VM-level control plus horizontal scale and fleet management**.

Example:

```text
Custom application server
must run directly on Linux VMs
+
needs 2–50 instances
+
autoscaling required
        ↓
VMSS
```

VMSS gives me:

* autoscaling,
* rolling upgrades,
* consistent VM configuration,
* load-balancer integration,
* zone distribution.

So:

```text
Need one/few individually managed servers
→ VM

Need scalable fleet of similar servers
→ VMSS
```

---

### **3. Azure App Service**

For a conventional:

```text
Web app
REST API
Backend service
```

where I don't need OS-level control, App Service is often my first choice.

Example:

```text
.NET / Java / Node.js web API
        ↓
App Service
```

Azure manages much more of:

* infrastructure,
* operating-system platform,
* load balancing,
* scaling integration,
* TLS/web hosting.

Microsoft describes App Service as a managed service for web applications, APIs, and related application workloads. ([Microsoft Learn][3])

---

### **4. Azure Container Apps**

I choose Container Apps when the workload is containerized but I **don't need direct Kubernetes administration**.

For example:

```text
Frontend container
API container
Background worker
      ↓
Container Apps
```

It works well for:

* microservices,
* APIs,
* event-driven workloads,
* background workers,
* containerized apps needing autoscaling.

The important distinction is:

```text
Want containers
but don't want to operate Kubernetes
→ Container Apps
```

Microsoft explicitly notes that Container Apps is Kubernetes-based underneath but doesn't expose the underlying Kubernetes APIs/control plane to the customer. ([Microsoft Learn][3])

---

### **5. AKS**

I choose AKS when the requirements genuinely need Kubernetes features such as:

* Kubernetes APIs,
* custom controllers/operators,
* complex scheduling,
* advanced networking,
* Helm ecosystem,
* service mesh,
* Kubernetes-native GitOps,
* portability of Kubernetes workloads,
* sophisticated multi-service orchestration.

Example:

```text
20 microservices
+
Helm
+
Argo CD
+
custom controllers
+
complex networking/policies
        ↓
AKS
```

AKS manages much of the Kubernetes control-plane infrastructure, but I still take responsibility for substantial areas including:

* cluster design,
* node pools,
* upgrades,
* workload security,
* networking,
* resource management,
* observability.

### **My interview decision flow**

```text
Need full OS control?
│
├─ Yes
│   ├─ Single/small number → VM
│   └─ Scalable fleet     → VMSS
│
└─ No
    ↓
Is it primarily a web/API app?
│
├─ Yes → App Service
│
└─ Containerized?
    │
    ├─ Don't need Kubernetes API
    │       → Container Apps
    │
    └─ Need Kubernetes capabilities
            → AKS
```

### **A practical example**

Suppose someone gives me a simple containerized REST API.

I would **not automatically choose AKS** just because Kubernetes is powerful.

If requirements are:

```text
1 API
autoscaling
HTTPS
managed deployment
no Kubernetes-specific requirements
```

I would strongly consider:

```text
Container Apps
```

because AKS introduces unnecessary operational complexity.

**Memory line:**
**VM = OS control.
VMSS = scalable VM fleet.
App Service = managed web app.
Container Apps = managed containers.
AKS = Kubernetes control.**

**Interview trap:**
Do not answer:

> “AKS is best because it can run everything.”

Technically it can run many workloads, but architecture is about choosing the **simplest service that meets the requirements**.

**Keywords:** IaaS, PaaS, VMSS, App Service, Container Apps, AKS, operational complexity

**Likely follow-ups:**

* Container Apps vs AKS?
* App Service vs Container Apps?
* VMSS vs AKS?
* When is Kubernetes overkill?

### **T04-H07. How would you reduce VM costs without sacrificing production availability?**

**Answer:**
I would optimize cost in layers: **remove waste first, right-size capacity, autoscale safely, then apply pricing discounts**. I would not reduce cost by simply shutting down redundant production instances or removing availability protection.

Azure Advisor specifically recommends resizing or shutting down underutilized VMs/VMSS based on observed CPU, memory, and network utilization. Microsoft also recommends performing rightsizing before buying reservations or savings plans. ([Microsoft Learn][4])

My sequence would be:

```text
Measure utilization
      ↓
Right-size
      ↓
Autoscale
      ↓
Eliminate idle resources
      ↓
Reservations / Savings Plan
      ↓
Hybrid Benefit
      ↓
Spot only for interruptible capacity
```

### **1. Right-size based on metrics**

First I inspect:

* CPU,
* memory,
* disk IOPS/throughput,
* networking,
* peak usage,
* historical usage.

Suppose:

```text
Standard_D8s
8 vCPU
32 GB RAM

Observed:
CPU 8–15%
Memory 25%
```

If sustained measurements prove it safe, I might resize to a smaller SKU.

Azure Advisor can recommend less expensive VM sizes based on utilization data. ([Microsoft Learn][4])

But I would preserve enough headroom for:

* traffic spikes,
* zone failure,
* deployment operations.

---

### **2. Use VMSS autoscaling**

Instead of permanently running:

```text
10 VMs × 24/7
```

I could maintain:

```text
Minimum = 3
Normal = 4
Peak = 10
```

with autoscaling.

That gives me:

```text
Low traffic → fewer VMs
High traffic → more VMs
```

without eliminating baseline HA.

Microsoft recommends autoscaling as a VM cost-optimization technique specifically to reduce idle capacity. ([Microsoft Learn][5])

### **Important distinction**

I would not set:

```text
Minimum = 1
```

for a production HA workload just because it is cheaper.

Instead:

```text
Minimum capacity
=
enough instances to survive expected failure scenarios
```

---

### **3. Preserve zone redundancy**

If I currently have:

```text
Zone 1 → VM
Zone 2 → VM
Zone 3 → VM
```

I would not save money by moving everything into:

```text
Zone 1 only
```

unless the business explicitly accepts reduced availability.

Cost optimization should preserve the required **SLA/SLO and failure tolerance**.

---

### **4. Use Reservations for stable baseline workloads**

For workloads that will run continuously and predictably, I would consider **Azure Reservations**.

Microsoft currently recommends reservations for stable workloads where instance family, service, and region are predictable; reservations generally provide stronger discounts in exchange for less flexibility. ([Microsoft Learn][6])

For example:

```text
Production baseline:
4 VMs always required
        ↓
Reservation may fit well

Variable capacity:
0–10 extra VMs
        ↓
PAYG / other flexible pricing
```

Important interview point:

> A VM reservation is primarily a **billing discount**, not automatically a guarantee that physical compute capacity will be available.

Microsoft explicitly distinguishes reservations from capacity reservations. ([Microsoft Learn][7])

---

### **5. Consider Azure Savings Plan for Compute**

If compute usage is predictable in total spend but moves between:

* VM families,
* regions,
* supported compute services,

a **Savings Plan for Compute** can provide more flexibility than a VM-specific reservation.

Microsoft's current guidance is roughly:

```text
Stable, predictable workload
→ Reservation

Changing compute mix
→ Savings Plan
```

([Microsoft Learn][6])

---

### **6. Use Spot VMs only for fault-tolerant capacity**

I can introduce Spot instances for:

* batch processing,
* build agents,
* asynchronous workers,
* interruptible scale-out capacity.

For example:

```text
VMSS
├── 4 regular VMs → guaranteed baseline
├── Spot VM
├── Spot VM
└── Spot VM       → cheap burst capacity
```

Azure's cost-optimization guidance explicitly supports combining regular and Spot VM capacity where workloads tolerate eviction. ([Microsoft Learn][8])

I would **not replace the entire production HA baseline with Spot VMs**.

---

### **7. Use Azure Hybrid Benefit where eligible**

If the organization has eligible existing licenses, Azure Hybrid Benefit can reduce licensing costs for workloads such as Windows Server and eligible Linux distributions.

This can reduce cost **without reducing compute capacity at all**. ([Microsoft Learn][8])

---

### **8. Optimize non-compute VM costs**

I would also inspect:

```text
Managed disks
Snapshots
Public IPs
Backup retention
Log ingestion
Unused NICs/disks
```

because deleting or deallocating a VM doesn't necessarily eliminate these charges.

---

### **9. Use Azure Advisor + Cost Management continuously**

I would monitor:

```text
Azure Advisor
+
Cost Management
+
Azure Monitor
```

so rightsizing decisions are based on real workload behavior rather than guesses.

### **A strong production approach**

Suppose production currently uses:

```text
6 × oversized VMs
running constantly
```

Rather than:

```text
6 → 2 VMs ❌
```

I might redesign as:

```text
Right-size SKU
      +
VMSS
      +
Min 3 across zones
      +
Autoscale to 10
      +
Reservation for baseline 3
      +
PAYG/Spot for suitable burst capacity
```

That reduces cost while preserving resilience.

**Memory line:**
**Right-size first → autoscale → commit stable baseline → Spot only interruptible capacity.**

**Interview trap:**
Cost optimization is **not simply minimizing VM count**.

The real goal is:

> **Minimum cost while still meeting availability, performance, recovery, and business requirements.**

**Keywords:** right-sizing, Azure Advisor, autoscale, Reservations, Savings Plan, Hybrid Benefit, Spot VM, Availability Zones

**Likely follow-ups:**

* Reservation vs Savings Plan?
* Do Reserved VM Instances guarantee capacity?
* Where would you use Spot VMs in production?
* How would you know whether a VM is oversized?

# 5. 🔴 M IMP — Azure Storage

## Easy

### **T05-E01. What is an Azure Storage Account?**

**Answer:**
An Azure Storage Account is the **top-level Azure resource that provides a unique namespace and configuration boundary for Azure Storage services**.

A general-purpose v2 storage account can contain data for services such as:

```text
Storage Account
├── Blob Storage
├── Azure Files
├── Queue Storage
└── Table Storage
```

Microsoft currently recommends **general-purpose v2 (GPv2)** for most standard Azure Storage scenarios. ([Microsoft Learn][9])

### **What does the storage account define?**

At the account level I configure important properties such as:

* region,
* redundancy,
* networking,
* security configuration,
* access methods,
* performance/account type.

The storage account also creates a unique namespace for its services.

For example:

```text
mystorageaccount
```

can expose service endpoints conceptually like:

```text
Blob:
mystorageaccount.blob.core.windows.net

Files:
mystorageaccount.file.core.windows.net

Queue:
mystorageaccount.queue.core.windows.net

Table:
mystorageaccount.table.core.windows.net
```

Azure Storage is designed to provide durable, highly available, scalable storage behind these service endpoints. ([Microsoft Learn][9])

### **Example**

Suppose an application needs:

```text
User images
→ Blob Storage

Shared configuration files
→ Azure Files

Asynchronous messages
→ Queue Storage
```

These can potentially live under the same appropriate storage account:

```text
stprodapp01
├── blobs
├── file shares
└── queues
```

depending on security, scale, lifecycle, and architecture requirements.

### **Security**

In production I generally prefer:

```text
Microsoft Entra ID / Managed Identity
+
RBAC
```

over embedding storage-account access keys in applications.

For private workloads, I may additionally use:

```text
Private Endpoint
+
Disable/restrict public network access
```

depending on requirements.

**Memory line:**
**Storage Account = namespace and management/security boundary containing Azure Storage services.**

**Interview trap:**
A storage account is **not itself Blob Storage**.

Blob Storage is one service that can exist inside an appropriate storage account, alongside Files, Queues, and Tables.

**Keywords:** Storage Account, GPv2, Blob, Files, Queue, Table, namespace, redundancy
