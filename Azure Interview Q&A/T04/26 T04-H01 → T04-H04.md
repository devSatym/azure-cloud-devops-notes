# 4. 🔴 M IMP — Azure Virtual Machines, VMSS & Compute

## Hard

### **T04-H01. A VM is running but cannot be accessed over SSH; how would you troubleshoot it?**

**Answer:**
I would troubleshoot SSH **from the network layer toward the guest OS**, instead of immediately resetting the VM.

My sequence would be:

```text
VM state / IP
     ↓
Port 22 reachability
     ↓
NSG
     ↓
Route
     ↓
Public/private connectivity path
     ↓
sshd service
     ↓
SSH key / user / config
```

### **1. Confirm the basics**

First I check:

* VM is actually `Running`
* correct private/public IP
* correct username
* TCP port 22 is the expected SSH port
* DNS name resolves correctly if using a hostname

From my machine:

```bash
ssh -vvv azureuser@<vm-ip>
```

I can also test the port:

```bash
nc -zv <vm-ip> 22
```

The failure type gives me a clue:

```text
Timeout
→ usually network/routing/NSG path

Connection refused
→ VM reachable, but SSH service may not be listening

Permission denied
→ authentication/key/user issue
```

---

### **2. Check the NSG**

I inspect both:

```text
Subnet NSG
+
NIC NSG
```

and confirm an inbound rule allows:

```text
Source: my trusted IP/range
Destination port: 22
Protocol: TCP
Action: Allow
```

I would preferably use **Network Watcher IP Flow Verify** to determine whether an NSG is blocking the flow and which rule is responsible. ([Microsoft Learn][1])

I avoid opening:

```text
0.0.0.0/0 → TCP 22
```

unless it is only a very temporary troubleshooting measure, because SSH should normally be restricted.

---

### **3. Check routing**

Next I inspect:

* effective routes,
* UDRs,
* VNet peering if applicable,
* Azure Firewall/NVA rules,
* return path.

Network Watcher **Next Hop** can help verify that an incorrect route isn't sending the SSH traffic somewhere unexpected. ([Microsoft Learn][1])

---

### **4. Verify how the VM is supposed to be reached**

If the VM has no public IP, direct SSH from the internet will not work.

The intended path may instead be:

```text
Laptop
  ↓
VPN / ExpressRoute
  ↓
Private IP
```

or:

```text
Laptop
  ↓
Azure Bastion
  ↓
VM private IP
```

So I verify that I am troubleshooting the **actual intended access path**.

---

### **5. Check SSH inside the VM**

If Azure networking is correct, I investigate the guest OS.

I check:

```bash
systemctl status sshd
```

or on some distributions:

```bash
systemctl status ssh
```

Then:

```bash
ss -lntp | grep :22
```

I want to see that SSH is listening on the expected interface.

Potential problems include:

* `sshd` stopped,
* bad `/etc/ssh/sshd_config`,
* OS firewall blocking port 22,
* disk full,
* incorrect permissions,
* broken SSH keys.

---

### **6. Use Azure recovery tools**

If I cannot SSH but the VM still runs, I can use Azure's recovery options.

For example, the Azure portal can:

* reset the SSH configuration,
* replace/reset an SSH public key,
* reset credentials.

Microsoft specifically recommends these options after network checks. ([Microsoft Learn][1])

I can also use **Azure Serial Console** for deeper OS-level recovery if normal SSH access is unavailable.

### **Interview-ready troubleshooting flow**

```text
1. VM/IP correct?
2. TCP 22 reachable?
3. Effective NSG rules?
4. Effective route / Next Hop?
5. Firewall/Bastion/VPN path?
6. sshd listening?
7. OS firewall?
8. Key/user/config correct?
9. Serial Console / reset SSH if needed
```

**Memory line:**
**SSH failure: Network first, SSH service second, credentials last.**

**Interview trap:**
Do not immediately regenerate keys or recreate the VM.

If the error is a **timeout**, changing the SSH key will not fix an NSG, route, firewall, or connectivity problem.

**Keywords:** SSH, NSG, IP Flow Verify, effective routes, Next Hop, sshd, Serial Console, Bastion

**Likely follow-ups:**

* What does `connection refused` vs `timeout` tell you?
* How would you access a VM without a public IP?
* How can Azure reset an SSH key?
* What if SSH broke after editing `sshd_config`?

### **T04-H02. How would you recover a Linux VM after an incorrect `/etc/fstab` configuration prevents booting?**

**Answer:**
A bad `/etc/fstab` entry can cause Linux to wait for or fail to mount a filesystem during boot.

I would first try **Azure Serial Console and single-user/emergency mode**. If that is not possible, I would perform an offline repair using Azure's VM repair process or by attaching the OS disk to a rescue VM. Microsoft documents both online and offline recovery paths for `fstab` failures. ([Microsoft Learn][2])

### **1. Recognize the symptom**

Typical causes include:

* wrong UUID,
* wrong device name,
* missing disk,
* invalid filesystem type,
* bad mount options,
* filesystem unavailable during boot.

For example:

```text
UUID=wrong-uuid /data ext4 defaults 0 2
```

Linux tries to mount `/data`, cannot find the device, and the VM may enter emergency mode.

---

### **2. Try Azure Serial Console**

If Serial Console is available:

```text
Azure Portal
    ↓
VM
    ↓
Serial Console
```

I enter single-user/emergency mode and inspect:

```bash
cat /etc/fstab
```

Then verify actual block devices:

```bash
lsblk
```

and UUIDs:

```bash
blkid
```

Microsoft's documented recovery procedure specifically recommends editing `/etc/fstab` from single-user mode when possible. ([Microsoft Learn][2])

### **3. Correct the faulty entry**

For example, I might comment it temporarily:

```text
# UUID=bad-value /data ext4 defaults 0 2
```

or replace it with the correct UUID.

Then test:

```bash
mount -a
```

This is extremely useful.

If:

```bash
mount -a
```

returns no relevant errors, the corrected `fstab` syntax/mount configuration is much safer to reboot with.

---

### **4. Consider `nofail` for noncritical data disks**

For a nonessential data disk, I may use:

```text
nofail
```

where appropriate so that the entire VM does not fail boot simply because that optional disk cannot mount.

For example:

```text
UUID=<uuid> /data ext4 defaults,nofail 0 2
```

I would use this only when the workload can safely start without that mount.

---

### **5. If Serial Console doesn't work: offline repair**

The recovery architecture is:

```text
Broken VM
    ↓
Stop/deallocate where required
    ↓
Access/repair OS disk
    ↓
Attach/mount via repair VM
    ↓
Edit /etc/fstab
    ↓
Restore disk to original VM
    ↓
Boot
```

Azure also provides Linux repair tooling that can automate parts of this process. ([Microsoft Learn][2])

If repairing manually, I make sure I edit the **broken VM's mounted OS filesystem**, not the rescue VM's own `/etc/fstab`.

---

### **6. Validate after recovery**

Once the VM boots:

```bash
lsblk
df -h
mount
```

and:

```bash
systemctl --failed
```

Then I verify that all expected disks are mounted.

### **Interview answer condensed**

> “I would use Serial Console first, enter emergency or single-user mode, compare `/etc/fstab` against `lsblk` and `blkid`, correct or comment the invalid entry, run `mount -a`, and reboot. If I can't repair online, I would use Azure's Linux VM repair workflow or attach the OS disk to a rescue VM and edit the file offline.”

**Memory line:**
**Bad `fstab`: Serial Console → `lsblk/blkid` → fix → `mount -a` → reboot.**

**Interview trap:**
Do not reboot repeatedly without fixing the configuration.

And before rebooting after editing `fstab`, use:

```bash
mount -a
```

to catch many configuration errors immediately.

**Keywords:** `/etc/fstab`, Serial Console, emergency mode, `blkid`, `lsblk`, `mount -a`, rescue VM

**Likely follow-ups:**

* Why can a bad `fstab` prevent boot?
* Why use UUID instead of `/dev/sdX`?
* What does `nofail` do?
* How would you repair the VM if Serial Console is unavailable?

### **T04-H03. How would you design a highly available web application using VM Scale Sets?**

**Answer:**
For a highly available VMSS-based web application, I would make the web tier **stateless**, deploy multiple VM instances across **Availability Zones**, place them behind a health-aware load-balancing layer, enable autoscaling and health monitoring, and keep application state in external managed services.

A production design could look like:

```text
                   Internet
                      │
                      ↓
          Application Gateway / Front Door
               + WAF if required
                      │
                      ↓
          ┌─────────────────────┐
          │     VM Scale Set    │
          │                     │
          │ Zone 1 → VM-1       │
          │ Zone 2 → VM-2       │
          │ Zone 3 → VM-3       │
          └──────────┬──────────┘
                     │
          ┌──────────┴───────────┐
          ↓                      ↓
     Azure SQL / DB        Storage / Cache
   external state          external state
```

VMSS supports spreading instances across Availability Zones and automatically scaling instance count. ([Microsoft Learn][3])

### **1. Make the instances stateless**

I do not want critical state tied to one VM.

Instead:

```text
Sessions → Redis / external session store
Files    → Blob Storage / Azure Files
Database → Azure SQL / managed database
Secrets  → Key Vault
```

Then if a VM disappears:

```text
VM fails
   ↓
Load balancer stops sending traffic
   ↓
Other instances continue serving users
   ↓
VMSS replaces/adds capacity
```

---

### **2. Spread instances across Availability Zones**

For production, where supported, I would deploy the scale set across multiple zones:

```text
Zone 1 → instances
Zone 2 → instances
Zone 3 → instances
```

Azure documents multi-zone VMSS as the recommended approach for protection from datacenter-level failures. ([Microsoft Learn][4])

I would also maintain enough baseline capacity so one zone failure does not leave the application underpowered.

---

### **3. Put a load-balancing service in front**

For simple Layer-4 TCP/UDP:

```text
Azure Load Balancer
```

For HTTP/HTTPS features such as:

* TLS termination,
* path-based routing,
* WAF,
* host-based routing,

I would typically consider:

```text
Application Gateway
```

For global multi-region HTTP routing, Front Door may sit even further in front.

VMSS supports integration with both Azure Load Balancer and Application Gateway. ([Microsoft Learn][3])

---

### **4. Configure health probes**

The load balancer should send traffic only to healthy application instances.

For example:

```text
GET /health
```

should validate enough of the application to determine whether the instance can serve traffic.

```text
Healthy VM
→ receives traffic

Unhealthy VM
→ removed from traffic rotation
```

I would avoid a useless probe that returns `200` even when the app is broken.

---

### **5. Configure autoscaling**

For example:

```text
Minimum: 3
Default: 3
Maximum: 15
```

Then:

```text
CPU > 70% for 5 minutes
→ Scale out

CPU < 30% for sustained period
→ Scale in
```

For web workloads, request count, queue depth, or application metrics may be more meaningful than CPU alone.

Azure Monitor Autoscale supports metric-based and scheduled rules. ([Microsoft Learn][5])

---

### **6. Use immutable/repeatable configuration**

All instances should come from a controlled configuration:

```text
Golden image / Azure Compute Gallery
+
cloud-init / extensions where appropriate
+
IaC
```

Every new instance should become ready automatically.

I should not have to SSH into a newly scaled-out VM and configure it manually.

---

### **7. Handle upgrades safely**

For application/OS changes:

```text
New image/config
      ↓
Rolling upgrade
      ↓
Update a subset
      ↓
Health validation
      ↓
Continue
```

That limits blast radius and maintains capacity during deployment.

---

### **8. Monitor everything**

I would monitor:

* VM health,
* CPU/memory,
* request rate,
* latency,
* 5xx errors,
* load-balancer health,
* autoscale operations,
* disk/network pressure.

And configure alerts through Azure Monitor.

### **Failure scenario**

If Zone 1 fails:

```text
Zone 1 ❌
VM-1 unavailable

Zone 2 ✅
VM-2 serving traffic

Zone 3 ✅
VM-3 serving traffic

Autoscale
   ↓
Add capacity in available zones if required
```

Microsoft notes that autoscale can help restore capacity in unaffected zones during a zone outage. ([Microsoft Learn][4])

**Memory line:**
**HA VMSS = multiple zones + stateless instances + load balancing + health probes + autoscale + external state.**

**Interview trap:**
Simply putting three VMs into a VMSS does **not automatically make the application highly available**.

If all instances:

* live in one failure domain,
* depend on one local stateful VM,
* or have no health-aware traffic routing,

the application can still have major single points of failure.

**Keywords:** VMSS, Availability Zones, Application Gateway, Load Balancer, health probe, autoscale, stateless

**Likely follow-ups:**

* Where would you store user sessions?
* Application Gateway vs Load Balancer?
* How many instances would you keep minimum?
* How would you deploy updates without downtime?

### **T04-H04. How does VMSS autoscaling work?**

**Answer:**
VMSS autoscaling uses **Azure Monitor Autoscale** to automatically increase or decrease the number of VM instances based on metrics, schedules, or configured rules.

This is **horizontal scaling**:

```text
Scale out
→ add VMs

Scale in
→ remove VMs
```

It does not automatically resize the existing VMs to a larger SKU—that would be vertical scaling. Azure Monitor Autoscale is designed around horizontal scale-out and scale-in. ([Microsoft Learn][6])

### **Core configuration**

An autoscale profile defines:

```text
Minimum instances
Default instances
Maximum instances
+
Scale rules
```

For example:

```text
Minimum: 2
Default: 3
Maximum: 10
```

These limits prevent the scale set from:

* dropping below required capacity,
* or scaling indefinitely and creating unexpected cost.

Microsoft's current VMSS autoscale guidance uses this exact min/default/max model. ([Microsoft Learn][5])

---

### **Example metric-based rules**

```text
Average CPU > 70%
for 5 minutes
        ↓
Add 2 VMs
```

Then:

```text
Average CPU < 30%
for 10 minutes
        ↓
Remove 1 VM
```

The idea is to require the condition to remain true long enough that a short spike does not constantly create and remove instances.

### **Scaling flow**

```text
Traffic increases
       ↓
Metric crosses threshold
       ↓
Azure Monitor evaluates rule
       ↓
Scale-out action triggered
       ↓
VMSS creates new instance(s)
       ↓
Application/config initializes
       ↓
Health probe becomes healthy
       ↓
Load balancer sends traffic
```

When demand falls, the opposite process occurs.

---

### **Cooldown period**

After a scaling operation, autoscale normally uses a **cooldown period** before responding to another scale event.

This gives newly added capacity time to affect the monitored metric.

Without this protection, you could get:

```text
CPU high
→ add VMs
→ CPU still briefly high
→ immediately add more
→ unnecessary over-scaling
```

---

### **What can autoscale use?**

Examples include:

* percentage CPU,
* queue length,
* memory where the appropriate metric is available,
* application/custom metrics,
* schedules.

Azure Monitor currently supports both **metric-based** and **time/schedule-based** autoscale profiles. ([Microsoft Learn][6])

### **Scheduled example**

If traffic always rises at 9 AM:

```text
08:45
→ Scale to 8 instances

18:00
→ Scale down
```

This avoids waiting for CPU to rise before capacity is created.

---

### **Important scale-out vs scale-in rule behavior**

A useful Azure-specific interview detail:

When multiple rules exist in one autoscale profile:

* **scale-out occurs if any scale-out rule is satisfied**
* **scale-in occurs only when all relevant scale-in conditions are satisfied**

Microsoft describes this as effectively:

```text
Scale out → OR

Scale in → AND
```

This conservative scale-in behavior helps reduce aggressive removal of capacity. ([Microsoft Learn][6])

### **Example**

Suppose I have:

```text
Scale out if:
CPU > 70%
OR
Queue length > 1000
```

Either condition can justify adding capacity.

For scale-in I want stronger evidence that demand is actually low before removing instances.

---

### **Predictive autoscale**

For cyclical workloads, Azure Monitor also supports **predictive autoscale**, which uses historical CPU patterns to forecast demand and scale out ahead of expected load. ([Microsoft Learn][6])

I would consider it for workloads with predictable daily or weekly patterns.

### **What I monitor after enabling autoscale**

I would verify:

* instance count,
* scale actions,
* provisioning time,
* application startup time,
* health probes,
* whether thresholds cause oscillation,
* min/max limits,
* cost impact.

**Memory line:**
**Metric/schedule → rule → scale action → VMSS changes instance count.**

**Interview trap:**
Autoscale is not instantaneous capacity.

A newly created VM still needs time to:

```text
Provision
→ boot
→ configure
→ start application
→ pass health probe
```

So for sudden traffic spikes, I design thresholds, baseline capacity, and scheduled/predictive scaling accordingly.

**Keywords:** Azure Monitor Autoscale, scale out, scale in, min/max/default, cooldown, metric rule, predictive autoscale
