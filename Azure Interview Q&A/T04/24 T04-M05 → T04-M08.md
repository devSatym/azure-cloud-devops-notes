# 4. 🔴 M IMP — Azure Virtual Machines, VMSS & Compute

## Medium

### **T04-M05. What is a VM extension?**

**Answer:**
An Azure VM extension is a **small software component used to perform post-deployment configuration, automation, monitoring, security, or management tasks inside an Azure VM**.

Instead of manually SSHing or RDPing into every VM, I can install an extension through Azure Resource Manager, CLI, PowerShell, Terraform, or the portal.

Common use cases include:

* installing monitoring agents,
* running configuration scripts,
* enabling security agents,
* resetting VM access,
* configuring backup,
* installing additional software.

Microsoft describes VM extensions as small applications used for post-deployment configuration and automation of Azure VMs. ([Microsoft Learn][1])

### **Example**

Suppose I provision a Linux VM and need to install Nginx automatically.

I could use the **Custom Script Extension**:

```text
Terraform / ARM / CLI
        ↓
VM Custom Script Extension
        ↓
Run Bash script inside VM
        ↓
Install + configure Nginx
```

Another common example is deploying the **Azure Monitor Agent** through an extension for monitoring.

### **How it works**

The Azure VM Agent running inside the guest OS works with the Azure platform to install and manage extensions.

Conceptually:

```text
Azure control plane
      ↓
VM Extension
      ↓
Azure VM Agent
      ↓
Guest OS
      ↓
Configuration / software
```

### **Important operational point**

Extensions run **inside the VM**, so they can fail because of:

* broken VM Agent,
* unsupported OS,
* blocked outbound connectivity,
* bad script,
* missing package repository,
* invalid extension configuration.

When troubleshooting, I check:

```text
Extension provisioning state
        ↓
VM Agent health
        ↓
Extension logs
        ↓
Network/dependency access
```

**Memory line:**
**VM extension = Azure-managed post-deployment automation inside a VM.**

**Interview trap:**
A VM extension is not the same thing as **cloud-init**.

Cloud-init is primarily used during Linux VM provisioning, while extensions can be installed and managed **after the VM already exists**.

**Keywords:** VM extension, Azure VM Agent, Custom Script Extension, post-deployment configuration, automation

### **T04-M06. What is cloud-init?**

**Answer:**
Cloud-init is an industry-standard mechanism for **automatically configuring Linux virtual machines during their initial provisioning and first boot**.

I can pass cloud-init configuration as custom data when creating a Linux VM and use it to perform tasks such as:

* creating users,
* installing packages,
* writing configuration files,
* running commands,
* configuring services.

Azure supports cloud-init on supported Linux images. ([Microsoft Learn][2])

### **Example**

When creating a VM, I could provide cloud-init like:

```yaml
#cloud-config

packages:
  - nginx

runcmd:
  - systemctl enable nginx
  - systemctl start nginx
```

The flow is:

```text
VM creation
   ↓
cloud-init configuration supplied
   ↓
Linux VM boots
   ↓
cloud-init processes configuration
   ↓
Nginx installed and started
```

This is especially useful when creating VMs automatically through:

* Terraform,
* Bicep,
* Azure CLI,
* VM Scale Sets.

### **cloud-init vs VM Extension**

I think of them as:

```text
cloud-init
→ initial Linux provisioning

VM Extension
→ Azure-managed configuration before or after deployment
```

Cloud-init is portable across many cloud providers, whereas Azure VM extensions are Azure-specific.

Microsoft also notes that Azure Linux Agent, or WALA, is still used for Azure-specific functions such as extension handling even when cloud-init performs provisioning. ([Microsoft Learn][2])

### **When I would use it**

I would use cloud-init for simple Linux bootstrap configuration such as:

```text
Create user
Install package
Write config
Start service
```

For complex long-term configuration management, I would prefer a dedicated configuration-management or immutable-image approach rather than putting hundreds of lines into cloud-init.

**Memory line:**
**cloud-init = bootstrap a Linux VM automatically on first boot.**

**Interview trap:**
Cloud-init is **not Azure-specific**.

It is widely supported across cloud platforms, whereas Azure VM extensions are Azure platform features.

**Keywords:** cloud-init, Linux provisioning, custom data, bootstrap, first boot, automation

### **T04-M07. How do you resize an Azure VM?**

**Answer:**
To resize an Azure VM, I change its **VM size or SKU**, which changes resources such as CPU, memory, disk limits, and networking capacity.

Before resizing, I check:

* whether the target size is available in the region,
* whether it is supported on the VM's current cluster,
* disk and NIC limits,
* feature compatibility,
* expected downtime.

### **Basic process**

In the portal:

```text
Virtual Machine
    ↓
Size
    ↓
Select new VM SKU
    ↓
Resize
```

Or through CLI, PowerShell, Terraform, or other IaC tools.

### **Will resizing restart the VM?**

Normally, I assume **resizing can cause a restart**, so I schedule it during an appropriate maintenance window.

If the requested size is available on the current cluster, Azure may resize the running VM but still restarts it during the operation.

If the required VM size is **not available on the current cluster**, I may have to:

```text
Stop (Deallocate)
      ↓
Resize
      ↓
Start
```

Deallocation allows Azure to place the VM on another compatible compute cluster. ([Microsoft Learn][3])

### **Example**

Suppose:

```text
Current:
Standard_D2s_v5
2 vCPU
8 GB RAM
```

and monitoring shows sustained memory pressure.

I might resize to:

```text
Standard_D4s_v5
4 vCPU
16 GB RAM
```

after confirming:

* workload requirement,
* target SKU availability,
* cost increase,
* disk/network limits.

### **Important consequence of deallocation**

If resizing requires deallocation:

* compute capacity is released,
* temporary disk contents can be lost,
* dynamic public IP behavior must be considered,
* capacity must be allocated again when the VM starts.

Microsoft notes that resizing/deallocation can expose capacity-allocation issues if the requested VM SKU is unavailable in the target cluster or zone. ([Microsoft Learn][4])

**Memory line:**
**Resize = change VM SKU; assume restart, and deallocate if the target size isn't available on the current cluster.**

**Interview trap:**
Do not say resizing is always zero-downtime.

A VM resize can restart the VM, and some resize operations require full deallocation.

**Keywords:** VM resize, SKU, deallocate, restart, allocation, vCPU, memory

### **T04-M08. What happens when an Azure VM is stopped versus deallocated?**

**Answer:**
The important difference is whether Azure still **reserves the underlying compute resources** for the VM.

### **Stopped**

If the guest OS is shut down from inside the VM, for example:

```bash
sudo shutdown -h now
```

the VM may enter:

```text
Stopped
```

The operating system is no longer running, but Azure can still keep the compute allocation reserved.

As a result, **compute billing can continue**.

### **Stopped (Deallocated)**

When the VM is stopped and deallocated through Azure:

```bash
az vm deallocate ...
```

Azure releases the underlying compute resources.

The state becomes:

```text
Stopped (Deallocated)
```

and compute charges for the VM instance stop. Microsoft explicitly documents that deallocation releases compute allocation and stops compute charges. ([Microsoft Learn][5])

### **Comparison**

| State                     | OS running? | Compute reserved? | VM compute charge? |
| ------------------------- | ----------: | ----------------: | -----------------: |
| **Stopped**               |          No |     Generally yes |                Yes |
| **Stopped (Deallocated)** |          No |                No |                 No |

### **What still costs money after deallocation?**

Deallocating does **not mean the entire VM becomes free**.

You can still be charged for associated resources such as:

* managed disks,
* snapshots,
* certain public IP configurations,
* backup,
* other attached Azure services.

### **Important implications of deallocation**

Because the physical compute allocation is released:

* local/temporary disk data can be lost,
* Azure has to allocate compute capacity again when the VM starts,
* a start operation can theoretically fail if the requested SKU lacks available capacity.

Microsoft documents allocation failures occurring when starting a stopped-deallocated VM because Azure must allocate capacity again. ([Microsoft Learn][4])

### **Example**

For a development VM that is only needed during working hours:

```text
9 AM
Start VM

6 PM
Stop (Deallocate)
```

This reduces compute cost while preserving persistent managed disks.

**Memory line:**
**Stopped = OS off, compute may still be reserved and billed.
Deallocated = compute released, compute billing stops.**

**Interview trap:**
Do not simply run:

```bash
shutdown
```

inside the VM and assume Azure compute billing has stopped.

For cost saving, I verify the portal/API state is:

```text
Stopped (Deallocated)
```

**Keywords:** stopped, deallocated, compute billing, capacity release, temporary disk, managed disk
