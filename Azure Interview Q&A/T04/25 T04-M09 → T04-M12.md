# 4. 🔴 M IMP — Azure Virtual Machines, VMSS & Compute

## Medium

### **T04-M09. Are you charged for a stopped Azure VM?**

**Answer:**
It depends on **how the VM was stopped**.

If the VM is only in the:

```text
Stopped
```

state, Azure may still reserve the underlying compute resources, so **compute charges can continue**.

If the VM is:

```text
Stopped (Deallocated)
```

Azure releases the compute allocation, so **VM compute charges stop**.

### **But deallocated does not mean zero cost**

You can still be charged for resources attached to the VM, such as:

* managed disks,
* snapshots,
* backup,
* reserved public IP resources where applicable,
* monitoring/log ingestion,
* other dependent Azure services.

### **Example**

For a non-production VM:

```text
During work hours
→ Running
→ Compute + storage charges

After work
→ Stop (Deallocate)
→ No VM compute charge
→ Disk/storage charges continue
```

This is why scheduled deallocation is a common cost-optimization technique for development and test environments.

### **How I verify it**

I check the Azure power state and make sure it says:

```text
Stopped (Deallocated)
```

rather than just:

```text
Stopped
```

**Memory line:**
**Stopped may still cost compute; deallocated stops compute billing, but attached resources still cost money.**

**Interview trap:**
Running `shutdown` inside Linux or Windows does **not necessarily stop Azure compute billing**.

For cost optimization, I want the Azure resource state to be **deallocated**.

**Keywords:** stopped, deallocated, compute billing, managed disks, cost optimization

**Likely follow-ups:**

* Are managed disks charged after deallocation?
* What happens to temporary disk data?
* Can you automate VM shutdown?
* Can a deallocated VM fail to start later?

### **T04-M10. What is Accelerated Networking?**

**Answer:**
Accelerated Networking is an Azure VM networking feature that improves **network throughput, latency, and CPU efficiency** by using hardware-based network virtualization.

Normally, packets pass through more of the host's virtual networking stack.

With Accelerated Networking, Azure uses technologies such as **SR-IOV** to allow much of the networking traffic to bypass the software virtual switch and reach the VM more directly.

Conceptually:

```text
Without Accelerated Networking

NIC
 ↓
Host virtual networking stack
 ↓
VM


With Accelerated Networking

NIC
 ↓
Hardware-assisted virtual function
 ↓
VM
```

### **Benefits**

It can provide:

* lower network latency,
* reduced jitter,
* higher packet-processing performance,
* lower CPU overhead inside the VM.

This is useful for network-intensive workloads such as:

* high-throughput application servers,
* distributed systems,
* database tiers,
* network appliances,
* performance-sensitive microservices.

### **Example**

Suppose an application VM spends significant CPU time processing high packet rates.

With Accelerated Networking:

```text
Less host networking overhead
        ↓
More CPU available to application
        ↓
Lower latency and higher throughput
```

### **Requirements**

Not every VM size or operating-system image supports it, so I verify:

* VM SKU support,
* OS/driver support,
* deployment configuration.

### **Memory line:**

**Accelerated Networking = hardware-assisted networking that reduces virtualization overhead.**

**Interview trap:**
Accelerated Networking does **not increase your application's bandwidth beyond the VM size's networking limits**.

It reduces networking overhead and improves packet-processing efficiency, but the VM SKU still defines maximum network performance.

**Keywords:** Accelerated Networking, SR-IOV, latency, throughput, CPU overhead, VM NIC

**Likely follow-ups:**

* What is SR-IOV?
* Does Accelerated Networking bypass NSGs?
* Does it increase the VM's maximum bandwidth?
* Which workloads benefit most from it?

### **T04-M11. What are Spot VMs?**

**Answer:**
Azure Spot VMs let me use **unused Azure compute capacity at a significant discount**, but Azure can evict the VM when that capacity is needed elsewhere or when configured pricing conditions are no longer met.

The trade-off is:

```text
Much lower cost
        ↕
No guaranteed continuous availability
```

So Spot VMs are appropriate for **interruptible and fault-tolerant workloads**.

### **Good use cases**

I would consider Spot VMs for:

* batch processing,
* CI/CD agents,
* development/test,
* rendering,
* distributed compute,
* stateless worker nodes,
* jobs that can checkpoint and resume.

### **Bad use cases**

I would normally avoid relying exclusively on Spot VMs for:

* critical databases,
* single-instance production applications,
* stateful systems that cannot tolerate interruption,
* workloads requiring guaranteed capacity.

### **Eviction**

Azure may evict a Spot VM when:

* Azure needs the capacity back,
* or the VM exceeds the configured maximum-price behavior where applicable.

The eviction policy can typically be configured as:

```text
Deallocate
```

or:

```text
Delete
```

depending on the workload design.

### **Example**

For a batch-processing architecture:

```text
Job Queue
   ↓
VMSS
├── Regular VMs
├── Spot VM
├── Spot VM
└── Spot VM
```

If Azure evicts one Spot VM:

```text
Worker disappears
      ↓
Job returned/retried
      ↓
Another worker processes it
```

The application remains reliable because the workload was designed to tolerate node loss.

### **Production strategy**

For some workloads, I might combine:

```text
Baseline capacity → Regular VMs
Burst capacity    → Spot VMs
```

That provides predictable baseline availability while reducing the cost of additional capacity.

**Memory line:**
**Spot VM = cheap spare Azure capacity that can be taken back.**

**Interview trap:**
Spot VMs are **not simply cheaper normal VMs**.

The discount exists because Azure provides **no continuous-capacity guarantee** and the VM can be evicted.

**Keywords:** Spot VM, eviction, unused capacity, fault tolerant, batch workload, cost optimization

**Likely follow-ups:**

* What happens when a Spot VM is evicted?
* Would you run a production database on Spot VMs?
* How would you use Spot instances with VMSS?
* Spot VM vs Reserved Instance?

### **T04-M12. What are Azure Dedicated Hosts?**

**Answer:**
Azure Dedicated Hosts provide a **physical Azure server dedicated to a single customer**, on which that customer can place supported Azure VMs.

Normally, Azure VMs from different customers can share the same physical host while remaining isolated through virtualization.

With a Dedicated Host:

```text
Physical Server
└── Dedicated to one customer
    ├── VM-1
    ├── VM-2
    └── VM-3
```

No other Azure customer's VMs are placed on that host.

### **Why would I use one?**

The main reasons are:

* regulatory or compliance requirements,
* physical server isolation,
* software licensing requirements,
* control over VM placement,
* greater visibility into host-level maintenance.

### **Example**

Suppose a financial organization has a compliance requirement stating:

> Production workloads must not share the physical server with another cloud customer.

Instead of regular multi-tenant VM hosting, I could use:

```text
Dedicated Host
   ↓
Production VM-1
Production VM-2
Production VM-3
```

That satisfies the physical-host isolation requirement while still using Azure.

### **Important trade-off**

Dedicated Hosts provide stronger isolation, but they are generally **more expensive and less flexible** than normal Azure VM placement.

I am paying for dedicated host capacity, so utilization matters.

For normal workloads that do not require physical-host isolation, I would generally prefer standard Azure VMs or VMSS.

### **Dedicated Host vs Dedicated Instance**

The important architectural point is that Dedicated Host gives me visibility and control at the **physical host level**, not merely a VM that happens to be isolated logically.

### **Memory line:**

**Dedicated Host = Azure physical server reserved for my organization's VMs.**

**Interview trap:**
Do not confuse:

```text
Dedicated Host
```

with:

```text
Dedicated VM
```

Azure already provides strong VM isolation in normal multi-tenant environments. Dedicated Hosts are mainly for cases where I specifically need **physical host isolation or licensing/compliance control**.

**Keywords:** Dedicated Host, physical isolation, compliance, licensing, host placement, single tenant

* When would you choose Dedicated Host?
* Dedicated Host vs normal Azure VM?
* What is the cost trade-off?
* Does Dedicated Host protect against an Availability Zone failure?
