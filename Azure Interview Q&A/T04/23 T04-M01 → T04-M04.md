# 4. 🔴 M IMP — Azure Virtual Machines, VMSS & Compute

## Medium

### **T04-M01. What is the difference between Availability Sets and Availability Zones?**

**Answer:**
Both improve VM availability, but they protect against **different levels of failure**.

**Availability Set** distributes VMs across **fault domains and update domains within a datacenter infrastructure**.

**Availability Zones** distribute VMs across **physically separate datacenter groups within the same Azure region**, with independent power, cooling, and networking.

So the key distinction is:

```text
Availability Set
→ protects mainly against host/rack/maintenance failures

Availability Zones
→ protects against an entire zone/datacenter-level failure
```

### **Comparison**

| Area                 | Availability Set            | Availability Zone                  |
| -------------------- | --------------------------- | ---------------------------------- |
| Isolation            | Fault/update domains        | Physically separate zones          |
| Failure protection   | Hardware/rack + maintenance | Datacenter/zone failure            |
| Placement            | Azure distributes VMs       | You choose/distribute across zones |
| Resilience           | Lower                       | Stronger                           |
| Modern HA preference | Legacy/specific scenarios   | Preferred where supported          |

Microsoft recommends Availability Zones when the workload requires higher reliability than Availability Sets provide. ([Microsoft Learn][1])

### **Example**

With an Availability Set:

```text
Availability Set
├── VM-1 → Fault Domain 0
├── VM-2 → Fault Domain 1
└── VM-3 → Fault Domain 2
```

With Availability Zones:

```text
Azure Region
├── Zone 1 → VM-1
├── Zone 2 → VM-2
└── Zone 3 → VM-3
```

If a hardware rack fails, an Availability Set can help.

If an entire zone loses power or networking, a multi-zone deployment provides stronger protection.

### **Which would I choose?**

For a new production application, if the region and VM SKU support it, I would normally prefer **Availability Zones**.

Availability Sets are still useful where zones aren't available or for workloads designed around that deployment model.

**Rule of thumb:**
**Availability Set = hardware/maintenance isolation.
Availability Zone = datacenter-level isolation.**

**Interview trap:**
Neither automatically protects against a **complete Azure region outage**.

For regional disaster recovery, I need a **multi-region architecture**.

**Keywords:** Availability Set, Availability Zone, fault domain, update domain, datacenter isolation, high availability

### **T04-M02. What are fault domains and update domains?**

**Answer:**
Fault domains and update domains are the two isolation concepts used by **Azure Availability Sets**.

### **Fault domain**

A fault domain represents a group of VMs that share underlying physical infrastructure such as:

* power,
* networking,
* and hardware failure boundaries.

Azure spreads VMs across fault domains so one hardware failure is less likely to affect all instances.

Conceptually:

```text
Fault Domain 0
├── VM-1
└── shared hardware boundary

Fault Domain 1
├── VM-2
└── different hardware boundary
```

### **Update domain**

An update domain is a logical group of VMs that Azure may restart together during **planned platform maintenance**.

Azure processes update domains sequentially so all application instances are not intentionally restarted at once.

```text
Update Domain 0 → VM-1, VM-6
Update Domain 1 → VM-2, VM-7
Update Domain 2 → VM-3, VM-8
...
```

Azure Availability Sets support up to **3 fault domains and 20 update domains**, depending on configuration and region. ([Microsoft Learn][1])

### **Example**

Suppose I run three web servers behind a load balancer.

```text
VM-1 → Fault Domain 0
VM-2 → Fault Domain 1
VM-3 → Fault Domain 2
```

If hardware associated with Fault Domain 0 fails, VM-2 and VM-3 can continue operating.

Likewise, planned maintenance is spread across update domains rather than intentionally rebooting every VM simultaneously.

**Memory line:**
**Fault domain = unplanned hardware failure.
Update domain = planned platform maintenance.**

**Interview trap:**
Fault domains and update domains are **not Availability Zones**.

Availability Zones provide physically separate datacenter-level isolation, which is stronger.

**Keywords:** fault domain, update domain, Availability Set, hardware failure, planned maintenance

### **T04-M03. What is the difference between Standard HDD, Standard SSD, Premium SSD, and Ultra Disk?**

**Answer:**
The main differences are **performance, latency, workload suitability, and cost**.

I choose the disk based primarily on required:

* IOPS,
* throughput,
* latency,
* workload criticality,
* and cost.

### **Comparison**

| Disk             | Best suited for                                        | Performance | Cost    |
| ---------------- | ------------------------------------------------------ | ----------- | ------- |
| **Standard HDD** | Backup, infrequently accessed/noncritical workloads    | Lowest      | Lowest  |
| **Standard SSD** | Dev/test, web servers, light enterprise apps           | Moderate    | Low     |
| **Premium SSD**  | Production and performance-sensitive workloads         | High        | Higher  |
| **Ultra Disk**   | Very I/O-intensive databases and transaction workloads | Very high   | Highest |

Microsoft currently offers five managed-disk families: Standard HDD, Standard SSD, Premium SSD, **Premium SSD v2**, and Ultra Disk. ([Microsoft Learn][2])

### **Standard HDD**

Uses traditional HDD-backed storage.

I would use it for workloads where:

```text
Cost matters more than latency/performance
```

such as backup or infrequently accessed noncritical data.

---

### **Standard SSD**

Provides SSD-based storage at a lower cost than premium tiers.

Good for:

* development/test,
* web servers,
* lightly used applications.

It gives more consistent latency than Standard HDD.

---

### **Premium SSD**

Designed for production workloads requiring:

* low latency,
* predictable performance,
* higher IOPS,
* higher throughput.

For a normal production database or application server requiring strong disk performance, Premium SSD is a common choice.

---

### **Ultra Disk**

Designed for extremely I/O-intensive workloads such as:

* high-end SQL Server,
* Oracle,
* SAP HANA,
* transaction-heavy databases.

Current Ultra Disk capabilities can reach significantly higher IOPS and throughput than the lower tiers, and performance can be configured independently within supported limits. ([Microsoft Learn][2])

### **Example decision**

```text
Backup archive
→ Standard HDD

Dev web server
→ Standard SSD

Production application/database
→ Premium SSD

Extremely high-I/O database
→ Ultra Disk
```

### **Important point**

Disk performance is also limited by the **VM size**.

Even if the disk supports very high IOPS, the VM itself may have a lower storage throughput or IOPS limit.

So actual performance is effectively constrained by:

```text
Disk limit
+
VM storage limit
→ whichever bottleneck is reached first
```

**Memory line:**
**HDD = cheapest.
Standard SSD = general/light.
Premium SSD = production.
Ultra = extreme I/O.**

**Interview trap:**
Do not choose a disk only based on capacity.

A `1-TB` Standard HDD and a `1-TB` Premium SSD may have completely different latency, IOPS, and throughput characteristics.

Also, Azure now has **Premium SSD v2**, so saying Azure has only these four disk types is outdated. ([Microsoft Learn][2])

**Keywords:** Standard HDD, Standard SSD, Premium SSD, Ultra Disk, IOPS, throughput, latency

**Likely follow-ups:**

* What is IOPS?
* Premium SSD vs Premium SSD v2?
* Can Ultra Disk be used as an OS disk?
* Why might a fast disk still give poor performance?

### **T04-M04. What is an ephemeral OS disk?**

**Answer:**
An Ephemeral OS Disk stores the VM's operating-system disk on **local storage attached to the VM host instead of persisting the OS disk in remote Azure Storage**.

It is designed mainly for **stateless workloads** where individual VM instances can be destroyed and recreated rather than recovered.

The main benefits are:

* lower OS-disk latency,
* faster VM provisioning/reimaging,
* good performance for disposable instances.

Microsoft specifically recommends Ephemeral OS Disks for stateless workloads that can tolerate individual VM replacement. ([Microsoft Learn][3])

### **Example**

A VM Scale Set running stateless web servers might look like:

```text
Load Balancer
     ↓
VMSS
├── VM-1 → Ephemeral OS Disk
├── VM-2 → Ephemeral OS Disk
└── VM-3 → Ephemeral OS Disk
```

Application state is stored externally in services such as:

```text
Azure SQL
Blob Storage
Redis
other persistent stores
```

If VM-2 fails:

```text
Don't recover VM-2's OS state
        ↓
Reimage/recreate VM-2
        ↓
Application rejoins service
```

That is a good ephemeral workload pattern.

### **Persistent vs Ephemeral OS disk**

```text
Persistent OS Disk
→ OS data stored persistently in Azure Storage
→ survives normal VM lifecycle operations

Ephemeral OS Disk
→ OS writes reside on local VM storage
→ designed to be recreated
```

Operations such as redeploying or resizing to another VM size can cause an Ephemeral OS Disk VM to be reprovisioned and its OS-disk changes to be lost. ([Microsoft Learn][3])

### **What should never live there?**

I would not store important application state only on an Ephemeral OS Disk.

Persistent data should go to:

* Azure Managed Disks,
* Azure Files,
* Blob Storage,
* databases,
* or another durable service.

### **Ephemeral OS Disk vs temporary disk**

They are different concepts.

```text
Ephemeral OS Disk
→ the operating system itself uses local ephemeral storage

Temporary disk
→ separate local scratch disk for temporary data
```

Microsoft explicitly distinguishes local temporary storage from Ephemeral OS Disks. ([Microsoft Learn][4])

**Memory line:**
**Ephemeral OS Disk = fast, local, disposable OS disk for stateless VMs.**

**Interview trap:**
Do not use Ephemeral OS Disks for workloads where you expect to preserve changes made to the operating-system disk after VM replacement.

Think:

> **Cattle, not pets.**

If the VM disappears, automation should be able to recreate it.

**Keywords:** Ephemeral OS Disk, stateless workload, local storage, VMSS, fast reimage, non-persistent OS state
