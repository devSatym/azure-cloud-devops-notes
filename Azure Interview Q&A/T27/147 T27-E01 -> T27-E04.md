### **T27-E01. What is an ARM template?**

**Answer:**

An ARM template is a **declarative JSON file used to define and deploy Azure infrastructure through Azure Resource Manager**. Instead of manually creating resources in the portal, I describe the desired resources—such as VNets, Storage Accounts, VMs, AKS, or Key Vault—and Azure Resource Manager creates or updates them.

A template can contain parameters, variables, resource definitions, dependencies, and outputs, which makes infrastructure deployments repeatable and suitable for CI/CD.

```text
ARM Template
    ↓
JSON describing desired resources
    ↓
Azure Resource Manager
    ↓
Resource Providers
    ↓
Azure Resources
```

### **Basic structure**

An ARM template conceptually contains:

```text
ARM Template
│
├── parameters
├── variables
├── resources
└── outputs
```

For example:

```json
{
  "resources": [
    {
      "type": "Microsoft.Storage/storageAccounts",
      "apiVersion": "...",
      "name": "mystorageaccount",
      "location": "centralindia"
    }
  ]
}
```

The important idea isn't memorizing the JSON structure. It's understanding that I declare:

> “I want this Azure resource to exist with these properties.”

ARM then talks to the relevant Azure resource provider.

For Storage:

```text
ARM
 ↓
Microsoft.Storage
 ↓
Storage Account
```

For AKS:

```text
ARM
 ↓
Microsoft.ContainerService
 ↓
AKS
```

---

### **Why ARM templates matter**

Without Infrastructure as Code:

```text
Engineer
   ↓
Azure Portal
   ↓
click
click
click
   ↓
Environment A
```

Then someone has to remember those steps for Environment B.

With an ARM template:

```text
Git
 ↓
ARM Template
 ↓
Dev
Stage
Prod
```

the deployment process is reproducible and reviewable.

This helps with:

* repeatability,
* source control,
* automation,
* environment consistency,
* peer review.

---

### **ARM template vs Azure Resource Manager**

Don't confuse these.

```text
Azure Resource Manager
→ Azure's management/control-plane deployment service

ARM template
→ JSON document submitted to Resource Manager
```

ARM itself is much broader than templates.

For example:

```text
Azure Portal
Azure CLI
PowerShell
Bicep
ARM template
```

can all ultimately interact with the Azure Resource Manager control plane.

---

### **ARM template vs Terraform**

Another useful distinction:

```text
ARM Template
→ Azure-native declarative IaC
→ JSON
→ deployed through ARM
→ no Terraform-style external state file

Terraform
→ multi-cloud declarative IaC
→ HCL
→ provider + Terraform state
```

Both can provision Azure infrastructure, but their execution and state models are different.

---

### **Practical DevOps example**

A CI pipeline might contain:

```text
Git Repository
      ↓
ARM Template
      ↓
Pull Request
      ↓
Validation
      ↓
Azure deployment
      ↓
Resource Group
      ├── VNet
      ├── Storage
      └── Key Vault
```

That is much more reproducible than configuring each environment manually.

---

**Memory line:**
**An ARM template is JSON that declaratively describes Azure resources for Azure Resource Manager to deploy.**

**Interview trap:**
An **ARM template is not Azure Resource Manager itself**; it is one declarative format that ARM can deploy.

**Keywords:**
ARM template, JSON, declarative IaC, Azure Resource Manager, parameters, variables, resources, outputs, resource providers.

### **T27-E02. What is Bicep?**

**Answer:**

Bicep is Microsoft's **declarative Infrastructure as Code language specifically designed for Azure**. It provides a much cleaner and more concise syntax than writing ARM-template JSON directly.

I write a `.bicep` file, and Bicep translates it into the ARM-template representation that Azure Resource Manager understands. So Bicep doesn't replace ARM—it gives me a better authoring experience on top of the ARM deployment platform.

```text
main.bicep
    ↓
Bicep
    ↓
ARM representation
    ↓
Azure Resource Manager
    ↓
Azure Resources
```

### **Simple example**

Instead of writing a large JSON ARM template, Bicep might look conceptually like:

```bicep
resource rgStorage 'Microsoft.Storage/storageAccounts@<api-version>' = {
  name: storageName
  location: location
  sku: {
    name: 'Standard_LRS'
  }
  kind: 'StorageV2'
}
```

The syntax is considerably less verbose than raw ARM JSON.

---

### **What Bicep gives me**

Bicep supports concepts such as:

```text
Parameters
Variables
Resources
Modules
Outputs
Loops
Conditions
Resource references
```

That means I can create reusable Azure infrastructure such as:

```text
main.bicep
│
├── network.bicep
├── aks.bicep
├── acr.bicep
└── monitoring.bicep
```

This is much easier to maintain than one enormous JSON ARM template.

---

### **How Bicep relates to ARM**

This is the key interview point:

```text
Bicep
    ↓
authoring language

Azure Resource Manager
    ↓
deployment engine
```

So don't say:

> “Bicep replaced Azure Resource Manager.”

It didn't.

A useful mental model is:

```text
Bicep
→ human-friendly Azure IaC language

ARM
→ Azure deployment/control-plane platform
```

---

### **Bicep vs Terraform at a high level**

```text
Bicep
→ Azure-specific
→ tightly integrated with ARM
→ no separate Terraform-style state

Terraform
→ multi-cloud
→ provider architecture
→ uses Terraform state
```

Both are declarative and suitable for production IaC.

The choice depends on architecture, tooling standards, and whether Azure-only integration or multi-cloud/provider portability matters.

---

### **Practical example**

For an Azure-only platform:

```text
Git
 ↓
main.bicep
 ↓
Modules
 ├── Networking
 ├── AKS
 ├── ACR
 └── Key Vault
 ↓
CI/CD
 ↓
Azure Resource Manager
 ↓
Azure
```

This gives me version-controlled infrastructure without maintaining raw ARM JSON manually.

---

**Memory line:**
**Bicep is the cleaner Azure-native language used to author declarative ARM deployments.**

**Interview trap:**
Bicep does **not bypass or replace ARM**; Bicep deployments still use Azure Resource Manager underneath.

**Keywords:**
Bicep, `.bicep`, Azure-native IaC, ARM, declarative, modules, parameters, resource references.

### **T27-E03. Why was Bicep introduced?**

**Answer:**

Bicep was introduced mainly because **raw ARM-template JSON is powerful but very verbose and difficult to author and maintain**.

Microsoft wanted to preserve the benefits of Azure Resource Manager—such as native Azure resource support and declarative deployment—while giving engineers a simpler language with better readability, reusable modules, type-aware tooling, IntelliSense, and easier resource references.

So Bicep improves the **authoring experience**, while Azure Resource Manager remains the underlying deployment engine.

```text
ARM JSON
   ↓
Powerful
but verbose
   ↓
Bicep
   ↓
Cleaner authoring experience
   ↓
Same ARM deployment platform
```

---

### **Why raw ARM JSON becomes difficult**

Imagine defining:

```text
VNet
├── Subnets
├── NSGs
├── Route Tables
│
AKS
ACR
Key Vault
Private Endpoints
Monitoring
```

in raw JSON.

JSON requires lots of structural syntax:

```text
{
  ...
  [
    ...
  ]
}
```

plus ARM expressions and explicit references.

Large templates can become difficult to:

* read,
* review,
* modify,
* reuse,
* troubleshoot.

The actual infrastructure logic may be relatively simple, but it can be hidden inside lots of JSON boilerplate.

---

### **Bicep makes the intent clearer**

Conceptually, raw ARM might require a lot of structure to represent:

```text
Storage Account
name = appstorage
location = centralindia
SKU = Standard_LRS
```

Bicep lets the code look much closer to that actual intent.

That improves:

```text
Readability
     ↓
Code review
     ↓
Maintainability
     ↓
Lower authoring error rate
```

---

### **Better resource references**

Bicep lets resources reference one another using symbolic resource names.

Conceptually:

```bicep
resource vnet '...' = {
  ...
}

resource subnet '...' = {
  parent: vnet
}
```

Instead of manually constructing complicated resource IDs everywhere, Bicep can understand dependencies from references.

This helps Azure Resource Manager build the deployment dependency graph.

---

### **Modules improve reuse**

Instead of:

```text
10,000-line ARM JSON
```

you can structure:

```text
main.bicep
│
├── modules/network.bicep
├── modules/aks.bicep
├── modules/acr.bicep
└── modules/keyvault.bicep
```

Then reuse those modules across environments.

This makes infrastructure easier to reason about.

---

### **Better development tooling**

Bicep was also designed for a better developer experience, including features such as:

* syntax validation,
* type information,
* IntelliSense,
* compile-time feedback,
* easier navigation/reference handling.

So many mistakes can be discovered while authoring rather than after staring at a large JSON deployment error.

---

### **Important point: Bicep did not create a new Azure infrastructure engine**

The architecture remains:

```text
Bicep source
    ↓
ARM-compatible deployment
    ↓
Azure Resource Manager
    ↓
Azure Resource Providers
```

Therefore Bicep gets the benefit of Azure-native ARM capabilities while presenting them in a much more manageable language.

---

### **Why not just improve ARM JSON?**

JSON itself is a general data format, not a purpose-built Azure IaC language.

Bicep can provide infrastructure-specific syntax such as:

```text
resource
module
param
var
output
```

which is much more natural for infrastructure authors.

So instead of treating infrastructure code as a giant JSON document, Bicep lets it look like an actual IaC language.

---

**Memory line:**
**Bicep was introduced to keep ARM's Azure-native power while removing much of ARM JSON's authoring pain.**

**Interview trap:**
Bicep was introduced primarily as a **better authoring language**, not as a completely separate deployment engine from ARM.

**Keywords:**
ARM JSON verbosity, Bicep, readability, modules, IntelliSense, type safety, symbolic references, Azure-native IaC.

### **T27-E04. Is Bicep declarative or imperative?**

**Answer:**

Bicep is **declarative**.

I describe the Azure resources and properties I want, and Azure Resource Manager determines how to create or update those resources to reach that configuration.

I don't normally write procedural instructions such as “create the VNet, wait five seconds, then create this subnet.” Instead, I declare the VNet, subnet, and references between them, and ARM determines the required dependency order.

```text
Bicep
 ↓
"What infrastructure should exist?"
 ↓
Azure Resource Manager
 ↓
Dependency graph
 ↓
Azure Resources
```

That is fundamentally different from an imperative Azure CLI or PowerShell script.

---

### **Declarative example**

Bicep conceptually says:

```text
I want:

Resource Group
   ↓
VNet
   ↓
Subnet
```

and defines the resources and relationships.

It does **not primarily say**:

```text
Step 1: run create-group
Step 2: run create-vnet
Step 3: wait
Step 4: run create-subnet
```

The second model is imperative.

---

### **Declarative vs imperative**

```text
Bicep / ARM / Terraform
        ↓
Declarative

"Describe desired infrastructure"


Azure CLI / scripting
        ↓
Usually imperative

"Execute these operations"
```

For example:

#### Bicep

```bicep
resource vnet 'Microsoft.Network/virtualNetworks@<api-version>' = {
  name: 'vnet-prod'
  location: location
}
```

You're declaring:

> `vnet-prod` should exist with this configuration.

#### CLI

```bash
az network vnet create ...
```

You're telling Azure:

> Perform this create operation now.

---

### **Dependencies can be inferred**

Suppose:

```text
Private Endpoint
       ↓
references subnet
```

Bicep/ARM can infer that the subnet must exist before that dependent operation can complete.

Conceptually:

```text
Subnet
  ↑
reference
  │
Private Endpoint
```

becomes:

```text
Create/configure subnet
        ↓
Create/configure private endpoint
```

without requiring the engineer to manually orchestrate every API call.

Explicit dependency declarations are available when genuine implicit references do not express the dependency, but unnecessary manual dependency declarations should be avoided.

---

### **But Bicep has loops and conditions—is that imperative?**

No.

Bicep supports constructs such as:

```text
conditions
loops
```

but they are used to **generate or conditionally describe desired resources**.

For example:

```text
For every application name
→ declare one Storage Account
```

is still declarative.

The presence of loops doesn't automatically make a language imperative.

The important question is whether I'm describing:

```text
desired end state
```

or manually orchestrating:

```text
step-by-step execution
```

Bicep is primarily the former.

---

### **Why the distinction matters operationally**

With an imperative script, I may need to manage:

```text
Does resource exist?
What step ran before?
Should I retry?
Should I update?
What happens on rerun?
```

With declarative infrastructure:

```text
Desired configuration
        ↓
Deployment engine evaluates current Azure state
        ↓
Create/update resources as necessary
```

This reduces the amount of orchestration logic I need to write myself.

It doesn't mean every deployment is risk-free or magically idempotent under every possible resource behavior, but the programming model is fundamentally desired-state oriented.

---

**Memory line:**
**Bicep says what Azure should look like, not the sequence of commands required to build it.**

**Interview trap:**
Bicep having loops, conditions, or dependencies does **not make it imperative**; those constructs still describe the desired infrastructure deployment.

**Keywords:**
Declarative, desired state, Bicep, Azure Resource Manager, dependency graph, imperative, Azure CLI.
