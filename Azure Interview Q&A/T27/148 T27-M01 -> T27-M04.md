# **T27-M01. What are Bicep parameters?**

**Answer:**

Bicep parameters are **input values supplied to a Bicep deployment** so the same infrastructure code can be reused for different environments or deployments without hardcoding every value.

For example, instead of hardcoding:

```text
location = centralindia
environment = prod
sku = Standard_LRS
```

inside the template, I can define parameters and provide different values for Dev, Staging, and Production.

```text
Same Bicep code
      ↓
Parameters
      ├── Dev values
      ├── Stage values
      └── Prod values
      ↓
Different deployments
```

Parameters are especially useful for values that are expected to vary **from deployment to deployment**, such as region, environment name, SKU, instance count, or resource-name prefix.

---

## **Basic example**

A Bicep parameter can look like:

```bicep
param location string
param environment string
param skuName string = 'Standard_LRS'
```

Here:

```text
location
→ required unless supplied another way

environment
→ required

skuName
→ has default value Standard_LRS
```

Then a resource can use them:

```bicep
resource storage 'Microsoft.Storage/storageAccounts@<api-version>' = {
  name: 'st${environment}app'
  location: location
  sku: {
    name: skuName
  }
  kind: 'StorageV2'
}
```

---

# **Why parameters matter**

Without parameters, you might end up with separate copies:

```text
main-dev.bicep
main-stage.bicep
main-prod.bicep
```

that gradually drift apart.

A better model is:

```text
main.bicep
   ↓
deployment inputs
   ├── Dev
   ├── Stage
   └── Prod
```

That gives:

* one infrastructure definition,
* fewer duplicated files,
* easier review,
* less environment drift.

---

# **Parameters vs hardcoded values**

Suppose I write:

```bicep
location: 'eastus'
```

Now every deployment goes to East US unless I edit the source.

Instead:

```bicep
param location string
```

lets the deployment caller decide.

This is useful because:

```text
Infrastructure structure
        ↓
belongs in Bicep

Environment-specific values
        ↓
often belong in parameters
```

---

# **Default values**

Parameters can have defaults:

```bicep
param location string = resourceGroup().location
```

or:

```bicep
param replicaCount int = 2
```

This makes common deployments easier while still allowing overrides.

But I would avoid defaults for values where choosing the wrong value could be dangerous.

For example, for:

```text
production subscription
critical network range
environment
```

I may prefer explicit values rather than silently defaulting.

---

# **Allowed values**

Bicep can constrain parameters.

Conceptually:

```bicep
@allowed([
  'dev'
  'stage'
  'prod'
])
param environment string
```

This prevents values such as:

```text
productionnn
```

from accidentally entering the deployment.

This is useful for guardrails.

---

# **Secure parameters**

For secret-like values, Bicep supports secure parameter declarations.

Conceptually:

```bicep
@secure()
param adminPassword string
```

This helps avoid exposing the value in deployment history/output where secure handling is supported.

However, the stronger design is often:

```text
Don't pass secrets at all
       ↓
Use Managed Identity / Key Vault
```

when the architecture supports it.

So `@secure()` is a protection mechanism, not an excuse to build secret-heavy templates.

---

# **Parameters should represent external variability**

A good rule:

```text
If caller should decide it
→ parameter

If template derives it internally
→ variable
```

Example:

```text
Parameter:
environment = prod

Variable:
resourcePrefix = '${environment}-payments'
```

The caller should not need to calculate every internal naming detail.

---

# **Parameter files**

For environment-specific deployments, I can separate values from template logic.

Conceptually:

```text
main.bicep
│
├── dev parameters
├── stage parameters
└── prod parameters
```

This makes the Bicep code reusable while keeping environment configuration distinct.

For example:

```text
Dev:
replicas = 1
SKU = lower

Prod:
replicas = 5
SKU = higher
```

while the infrastructure architecture remains the same.

---

# **Production example**

Suppose I have one AKS deployment module.

Inputs might be:

```text
environment
location
nodeCount
nodeVmSize
privateClusterEnabled
```

Then:

```text
Dev
 ↓
nodeCount = 1

Prod
 ↓
nodeCount = 3
privateClusterEnabled = true
```

Same module, different deployment intent.

---

# **Parameters vs secrets from Key Vault**

If a deployment needs a database password, I would avoid:

```text
Hardcode password in .bicep
```

and avoid committing it in a parameter file.

Better choices include:

```text
Key Vault reference
Managed Identity
deployment-time secure input
```

depending on the service and architecture.

---

# **Important distinction: parameters vs variables**

```text
Parameters
→ values provided from outside the template

Variables
→ values calculated inside the template
```

Example:

```bicep
param environment string

var storageName = 'st${environment}app'
```

`environment` is input.

`storageName` is derived.

---

### **Interview answer condensed**

> “Bicep parameters are deployment-time inputs that let me reuse the same infrastructure code for different environments. I use them for values that vary externally, such as region, environment, SKU, or replica count. Parameters can have defaults, allowed values, and secure handling where appropriate. I try to keep the architecture in the Bicep code and put environment-specific values in parameters, rather than maintaining separate Dev, Stage, and Prod templates.”

**Memory line:**
**Parameters are values the deployment caller provides to the Bicep template.**

**Interview trap:**
Do not use parameters for every internal derived value; values computed from other inputs usually belong in variables.

**Keywords:**
Bicep parameters, deployment inputs, defaults, allowed values, secure parameters, environment configuration, reuse.

# **T27-M02. What are Bicep variables?**

**Answer:**

Bicep variables are **values calculated or defined inside the Bicep file** for reuse within the deployment.

Unlike parameters, variables are not normally supplied by the deployment caller. I use them to derive repeated values, simplify expressions, build naming conventions, or calculate configuration from parameters.

For example:

```bicep
param environment string

var resourcePrefix = '${environment}-payments'
```

Now multiple resources can use:

```text
resourcePrefix
```

instead of repeating the same expression everywhere.

```text
External input
   ↓
Parameter
   ↓
Internal calculation
   ↓
Variable
   ↓
Resources
```

---

## **Why variables are useful**

Without variables:

```bicep
name: '${environment}-${application}-network'
```

might be repeated many times.

That creates:

* duplication,
* more typo risk,
* harder refactoring.

Instead:

```bicep
var prefix = '${environment}-${application}'
```

Then:

```bicep
name: '${prefix}-network'
```

and:

```bicep
name: '${prefix}-aks'
```

This makes the code clearer.

---

# **Parameters vs variables**

The simplest mental model is:

```text
Parameter
→ supplied from outside

Variable
→ calculated inside
```

For example:

```bicep
param environment string
param location string

var resourcePrefix = '${environment}-${location}'
```

The caller chooses:

```text
prod
centralindia
```

Bicep calculates:

```text
prod-centralindia
```

---

# **Variables are not mutable program variables**

This is an important distinction.

In an imperative programming language:

```text
x = 1
x = 2
x = x + 1
```

you might repeatedly change state.

Bicep is declarative.

A variable is more like:

```text
named expression
```

than a mutable memory location.

So:

```text
Bicep variable
≠
imperative mutable variable
```

This reinforces the declarative model.

---

# **Example: naming convention**

Suppose parameters are:

```bicep
param environment string
param application string
```

Then:

```bicep
var prefix = '${application}-${environment}'
```

Resources:

```text
${prefix}-vnet
${prefix}-aks
${prefix}-kv
```

Now if the naming scheme changes, I modify one expression rather than dozens of resources.

---

# **Example: environment-specific configuration**

A variable can derive configuration conditionally.

Conceptually:

```bicep
var nodeCount = environment == 'prod' ? 3 : 1
```

Then:

```text
Prod
→ 3 nodes

Dev
→ 1 node
```

The caller only chooses the environment; the module owns the internal rule.

This is often cleaner than requiring callers to understand every internal setting.

---

# **Variables reduce API surface of a module**

Imagine a module accepts 40 parameters.

That means every caller must understand 40 implementation details.

Instead:

```text
Caller provides:
environment
region
workloadName

Module derives:
resource names
tags
SKU defaults
internal resource IDs
configuration
```

This produces a cleaner reusable module.

---

# **Variables vs outputs**

Another distinction:

```text
Variable
→ internal value used during deployment

Output
→ value exposed after deployment
```

For example:

```bicep
var prefix = '${environment}-app'
```

is internal.

But:

```bicep
output storageId string = storage.id
```

exposes something for another consumer.

---

# **Variables vs resource properties**

You don't need a variable for every value.

This is unnecessary:

```bicep
var storageKind = 'StorageV2'
```

if it's used exactly once and never changes.

Variables are helpful when they improve:

* readability,
* reuse,
* consistency,
* complex expression management.

Not when they simply add indirection.

---

# **Production example**

Suppose I define centralized tags:

```bicep
param environment string
param owner string

var commonTags = {
  Environment: environment
  Owner: owner
  ManagedBy: 'Bicep'
}
```

Then multiple resources use:

```bicep
tags: commonTags
```

Now tagging is consistent across:

```text
VNet
AKS
ACR
Key Vault
Storage
```

This is a strong practical use.

---

# **Dependency implication**

Variables can reference resource properties, but you should understand that resource references can create dependencies.

For example:

```text
Variable uses resource A property
        ↓
Resource B uses variable
        ↓
ARM may infer dependency
```

So variables are not just text substitution; their expressions participate in the declarative dependency graph where resource references are involved.

---

### **Interview answer condensed**

> “Bicep variables are internal named expressions used to derive or reuse values inside the template. Parameters come from the caller, while variables are calculated within the Bicep code. I use variables for things like naming conventions, common tags, environment-derived settings, or complex expressions so I don't repeat logic across resources. They're declarative values, not mutable variables like in an imperative programming language.”

**Memory line:**
**Parameters come in; variables are calculated inside.**

**Interview trap:**
Bicep variables are not mutable stateful programming variables—they are declarative expressions.

**Keywords:**
Bicep variables, internal value, derived configuration, naming convention, tags, expressions, declarative.

**Likely follow-ups:**

* What's the difference between variables and parameters?
* When should you derive a value rather than expose another parameter?
* Can a Bicep variable reference a resource?
* When is creating a variable unnecessary?

# **T27-M03. What are Bicep outputs?**

**Answer:**

Bicep outputs are **values that a deployment exposes after evaluation**, so other deployments, modules, pipelines, or operators can consume important results such as a resource ID, endpoint, hostname, or managed identity ID.

For example, after deploying an ACR module, I may output:

```text
ACR resource ID
ACR login server
```

Then a parent module or later pipeline step can use those values rather than reconstructing them manually.

```text
Bicep deployment
      ↓
Creates resources
      ↓
Outputs
      ├── Resource ID
      ├── Endpoint
      └── Identity ID
      ↓
Consumer
```

Outputs are especially useful for connecting reusable modules together.

---

## **Basic example**

Conceptually:

```bicep
resource storage 'Microsoft.Storage/storageAccounts@<api-version>' = {
  name: storageName
  ...
}

output storageId string = storage.id
```

After deployment:

```text
storageId
→ /subscriptions/.../storageAccounts/...
```

That value can be consumed externally.

---

# **Why outputs matter**

Without outputs, another script might try to reconstruct a resource ID:

```text
/subscriptions/${sub}/resourceGroups/${rg}/providers/...
```

That's:

* repetitive,
* error-prone,
* tightly coupled to naming assumptions.

Instead, the deployment already knows:

```text
storage.id
```

so expose it directly.

---

# **Outputs between modules**

Suppose:

```text
main.bicep
│
├── network module
└── aks module
```

The network module can output:

```text
subnetResourceId
```

Then the AKS module consumes that output.

Flow:

```text
network.bicep
     ↓
creates subnet
     ↓
output subnetId
     ↓
main.bicep
     ↓
passes subnetId
     ↓
aks.bicep
```

This creates clean module interfaces.

---

# **Module input/output contract**

A well-designed Bicep module should behave like a function:

```text
Inputs
 ↓
Module
 ↓
Outputs
```

For example:

```text
Network module

Inputs:
- VNet CIDR
- subnet CIDR
- location

Outputs:
- VNet ID
- subnet ID
```

Consumers don't need to know all internal implementation details.

That improves encapsulation.

---

# **Outputs for CI/CD**

Suppose Bicep creates:

```text
App Service
```

and outputs:

```text
hostname
```

The pipeline could retrieve the deployment output and run a smoke test:

```text
Deploy infrastructure
       ↓
Output application hostname
       ↓
curl https://hostname/health
```

That is a practical DevOps use.

---

# **Outputs should not expose secrets casually**

This is very important.

Bad:

```bicep
output databasePassword string = adminPassword
```

because deployment outputs can be visible in deployment history or pipeline logs depending on how they are handled.

Prefer:

```text
Output:
Key Vault URI
Managed Identity ID
Secret resource reference

Not:
actual secret value
```

If a sensitive output is absolutely required, use the platform's secure-output capabilities where supported and ensure the consuming pipeline also handles it securely.

But the best approach is often not to output secrets at all.

---

# **Output resource IDs, not reconstructed names**

Good:

```bicep
output subnetId string = subnet.id
```

because the ID comes from the actual resource object.

Less robust:

```text
manually concatenate subscription + RG + VNet + subnet
```

Using resource properties keeps the module tied to actual deployment results.

---

# **Outputs vs variables**

```text
Variable
→ internal

Output
→ externally exposed
```

Example:

```bicep
var prefix = '${environment}-app'
```

Only the Bicep file needs it.

But:

```bicep
output acrLoginServer string = acr.properties.loginServer
```

may be useful to downstream deployment automation.

---

# **Outputs vs parameters**

These form an intuitive flow:

```text
Parameters
   ↓
Bicep deployment
   ↓
Variables/resources
   ↓
Outputs
```

So:

```text
Parameter
→ input

Output
→ result
```

---

# **Production example**

Suppose a platform module creates:

```text
AKS
ACR
Key Vault
```

Useful outputs might be:

```text
aksResourceId
acrLoginServer
keyVaultUri
kubeletIdentityObjectId
```

A downstream deployment stage can then consume these values for:

* RBAC setup,
* workload configuration,
* smoke tests,
* integration with another module.

---

# **Don't overexpose module internals**

A module shouldn't output every property just because it can.

If a network module exposes:

```text
50 internal properties
```

consumers become tightly coupled to its implementation.

Better:

```text
only expose values consumers genuinely need
```

This makes refactoring easier.

---

### **Interview answer condensed**

> “Bicep outputs expose selected values after a deployment so another module, pipeline, or operator can consume them. Typical outputs are resource IDs, endpoints, hostnames, or managed identity IDs. They are especially useful for connecting modules—for example, a network module can output a subnet ID that the AKS module receives as input. I avoid outputting secrets because deployment outputs can surface in logs or deployment history; instead I'd usually output references such as a Key Vault URI or resource ID.”

**Memory line:**
**Parameters are deployment inputs; outputs are the deployment results I intentionally expose.**

**Interview trap:**
Do not casually output secrets—an output is an integration interface, not a safe secret store.

**Keywords:**
Bicep outputs, resource ID, endpoint, module interface, pipeline integration, deployment result, secure output.

**Likely follow-ups:**

* How do outputs help connect Bicep modules?
* What's the difference between an output and a variable?
* Why shouldn't you output a database password?
* What kinds of values make good outputs?

# **T27-M04. What are Bicep modules?**

**Answer:**

Bicep modules are **reusable Bicep files that encapsulate a group of Azure resources behind a defined set of parameters and outputs**.

Instead of putting an entire platform into one huge `main.bicep`, I would split it into logical modules such as networking, AKS, ACR, Key Vault, and monitoring.

```text
main.bicep
│
├── network.bicep
├── acr.bicep
├── aks.bicep
├── keyvault.bicep
└── monitoring.bicep
```

The parent Bicep file passes parameters into each module and consumes its outputs.

This improves reuse, readability, testing, and separation of concerns.

---

## **Basic architecture**

```text
main.bicep
   ↓
network module
   ↓
outputs subnet ID
   ↓
AKS module
```

Conceptually:

```bicep
module network './modules/network.bicep' = {
  name: 'networkDeployment'
  params: {
    ...
  }
}

module aks './modules/aks.bicep' = {
  name: 'aksDeployment'
  params: {
    subnetId: network.outputs.subnetId
  }
}
```

This creates a clear dependency:

```text
Network module
     ↓
Subnet output
     ↓
AKS module
```

---

# **Why modules matter**

Without modules:

```text
main.bicep
├── 2,000 lines networking
├── 2,000 lines AKS
├── 1,000 lines monitoring
└── 1,500 lines security
```

That becomes hard to:

* review,
* reuse,
* test,
* maintain.

With modules:

```text
Network
AKS
Monitoring
Security
```

can evolve independently behind stable interfaces.

---

# **Modules behave like infrastructure functions**

Think:

```text
Inputs
 ↓
Module
 ↓
Resources
 ↓
Outputs
```

Example:

### Network module input

```text
addressSpace
subnetCIDR
location
```

### Network module output

```text
subnetId
vnetId
```

The caller doesn't need to know the exact resource implementation.

That's encapsulation.

---

# **Reusable across environments**

Same module:

```text
modules/aks.bicep
```

can be used by:

```text
Dev
Stage
Prod
```

with different parameters.

Example:

```text
Dev
→ nodeCount = 1

Prod
→ nodeCount = 3
→ privateCluster = true
```

This reduces duplicated infrastructure code.

---

# **Reusable across workloads**

A platform team might maintain:

```text
modules/private-aks
modules/private-keyvault
modules/standard-vnet
modules/log-analytics
```

Then application teams consume them rather than redesigning every Azure resource from scratch.

That supports organizational standardization.

---

# **Module dependencies**

If one module output is used by another:

```text
network.outputs.subnetId
```

ARM/Bicep can infer the dependency.

```text
network
   ↓
aks
```

You usually don't need to manually add `dependsOn` merely because you want a certain visual ordering.

This is similar to good dependency modeling in Terraform:

```text
Reference
→ dependency inferred
```

Explicit dependency should be used only when the relationship cannot be expressed naturally through references.

---

# **Module scope**

Modules can deploy at different Azure scopes depending on design.

For example, infrastructure may target:

```text
subscription
resource group
management group
tenant
```

This is useful for separating concerns such as:

```text
Subscription-level:
Resource groups / policy

Resource-group-level:
AKS / VNet / Key Vault
```

The module should have a clear intended scope.

---

# **Module registries and reuse**

For larger organizations, modules can be centralized rather than copied manually between repositories.

Conceptually:

```text
Platform Team
     ↓
Approved Bicep modules
     ↓
Internal registry
     ↓
Application teams consume versioned modules
```

That allows:

* versioning,
* central maintenance,
* standardized architecture,
* controlled upgrades.

Instead of:

```text
copy-paste network.bicep
into 50 repositories
```

which causes drift.

---

# **Version modules deliberately**

Suppose Platform Team publishes:

```text
network module v1
```

Application A consumes v1.

Later v2 changes:

```text
NSG rules
DNS behavior
subnet design
```

I don't want every workload silently receiving breaking infrastructure changes.

So treat module versions like application dependencies:

```text
publish
 ↓
version
 ↓
consumer upgrades intentionally
 ↓
review / test
```

---

# **Avoid giant “god modules”**

A bad module:

```text
enterprise-everything.bicep
```

with:

```text
97 parameters
40 optional features
network
AKS
SQL
App Service
VMs
Functions
monitoring
```

becomes difficult to reason about.

Better modules map to coherent responsibilities:

```text
network
aks
acr
keyvault
monitoring
```

Then `main.bicep` composes them.

---

# **Don't make modules too tiny either**

The opposite extreme is also bad:

```text
one module per NSG rule
one module per subnet
one module per tag
```

That creates excessive indirection.

A good module represents a **meaningful reusable infrastructure capability**.

Examples:

```text
private-aks-cluster
hub-network
application-vnet
monitoring-stack
private-keyvault
```

---

# **Production architecture example**

```text
main.bicep
│
├── network module
│     ├── VNet
│     ├── Subnets
│     ├── NSGs
│     └── Route Tables
│
├── identity module
│     └── Managed Identities
│
├── acr module
│     └── ACR
│
├── aks module
│     ├── AKS
│     └── Node Pools
│
└── monitoring module
      ├── Log Analytics
      └── Diagnostic settings
```

Dependencies:

```text
Network
   ↓
AKS

Identity
   ↓
AKS

ACR
   ↓
AKS integration

Monitoring
   ↓
AKS diagnostics
```

This is much easier to explain and maintain than a monolithic file.

---

# **Modules vs copying files**

Copying:

```text
network-dev.bicep
network-prod.bicep
network-project2.bicep
```

creates multiple independent codebases.

Modules give:

```text
one implementation
+
different parameter values
```

That is much more maintainable.

---

> “Bicep modules are reusable Bicep files that package related Azure resources behind parameters and outputs.
