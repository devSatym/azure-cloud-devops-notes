# **T27-M05. What is incremental deployment?**

**Answer:**

Incremental deployment is the default and recommended Azure Resource Manager deployment mode for ARM templates and Bicep. In incremental mode, Azure creates resources that are declared in the deployment and updates matching existing resources when their declared properties change, but it **does not delete unrelated resources just because they are absent from the Bicep file**.

So if my resource group contains:

```text
Resource Group
├── VNet        ← declared in Bicep
├── AKS         ← declared in Bicep
└── Storage     ← NOT declared in Bicep
```

and I redeploy the Bicep file, incremental mode manages the VNet and AKS but normally leaves the Storage Account alone.

However, there's an important nuance: for a resource that **is** redeployed, ARM applies the declared resource configuration. You should not interpret “incremental” as “only append the specific property I changed.” Microsoft currently recommends incremental deployment and recommends **deployment stacks** when you need managed deletion behavior; complete mode is being gradually deprecated. ([Microsoft Learn][1])

---

## **How incremental deployment works**

Think of the deployment as:

```text
Bicep desired resources
        ↓
Azure Resource Manager
        ↓
Compare with Azure resources
        ↓

Resource absent?
→ create

Resource exists and properties changed?
→ update

Resource exists but not mentioned in deployment?
→ normally leave it alone
```

For example:

### Current Azure

```text
rg-app-prod
│
├── vnet-prod
├── aks-prod
└── storage-legacy
```

### Bicep

```text
vnet-prod
aks-prod
```

After incremental deployment:

```text
rg-app-prod
│
├── vnet-prod       ← managed/update if needed
├── aks-prod        ← managed/update if needed
└── storage-legacy  ← remains
```

That last behavior is the key difference from the older concept of a complete deployment.

---

# **Incremental does NOT mean property-level patching**

This is the biggest interview trap.

Suppose the existing resource has:

```text
Property A = value1
Property B = value2
Property C = value3
```

and you redeploy that same resource with:

```text
Property A = value4
Property B = value2
```

You should **not automatically assume**:

```text
Property C stays untouched
because I omitted it
```

Microsoft explicitly warns that during redeployment of an existing resource, the resource's properties are reapplied according to the resource provider/API behavior. Incremental mode protects **resources omitted from the deployment**, not necessarily every omitted property on a resource that you are redeploying. ([Microsoft Learn][1])

So:

```text
Incremental mode
≠
"patch only the exact property I changed"
```

---

# **Incremental vs complete mode**

Historically ARM supported:

```text
Incremental
vs
Complete
```

### Incremental

```text
Resource not in template
→ leave it
```

### Complete

```text
Resource not in template
→ may delete it
```

But current Microsoft guidance is important here:

> **Use incremental mode for normal ARM/Bicep deployments, and use deployment stacks when you need lifecycle-managed deletion.**

Microsoft states that complete mode is being gradually deprecated. ([Microsoft Learn][1])

So in a current interview, I would **not** recommend complete mode as the normal way to reconcile deletions.

---

# **Why incremental is safer for normal deployments**

Imagine a resource group contains:

```text
Application resources
+
resources owned by another team
+
manually maintained resource
```

If a deployment automatically deleted everything not present in one Bicep file, the blast radius could be huge.

Incremental behavior reduces that risk:

```text
Deployment owns resources it describes
       ↓
Unrelated resources remain
```

This is useful when multiple deployments coexist in one scope.

---

# **But this introduces an ownership challenge**

Suppose yesterday Bicep contained:

```text
VNet
AKS
Storage Account
```

Today you delete the Storage Account resource block:

```text
VNet
AKS
```

Incremental deployment doesn't necessarily mean:

```text
Storage deleted
```

Instead:

```text
Storage can remain in Azure
```

Now the Bicep source and actual environment can diverge in terms of resource existence.

That's one reason Microsoft now recommends **deployment stacks** when you need ARM/Bicep to manage resource deletion as part of lifecycle management. ([Microsoft Learn][1])

---

# **Deployment stacks mental model**

Conceptually:

```text
Bicep
  ↓
Deployment Stack
  ↓
Tracks managed resources
  ↓
Resource removed from stack definition
  ↓
Apply configured deletion/detach behavior
```

This is closer to a managed ownership model.

You don't need to explain every deployment-stack feature unless asked, but knowing why they matter is useful.

---

# **How I would preview changes**

Before significant infrastructure deployment, I would use ARM/Bicep **what-if**.

For example:

```bash
az deployment group what-if \
  --resource-group rg-app-prod \
  --template-file main.bicep
```

Conceptually:

```text
Current Azure
      +
Bicep
      ↓
What-if
      ↓
Create / Modify / Delete / Ignore
```

Then deploy only after reviewing expected changes.

This is especially important for production.

---

# **Bicep deployment example**

For a resource-group deployment:

```bash
az deployment group create \
  --resource-group rg-app-prod \
  --template-file main.bicep
```

Incremental is the normal deployment model.

A safe workflow is:

```text
Bicep PR
   ↓
Lint / validation
   ↓
What-if
   ↓
Review
   ↓
Deployment
   ↓
Post-deployment validation
```

---

# **Incremental deployment vs Terraform state**

This is another useful distinction.

Bicep does not maintain an external Terraform-style state file. Microsoft describes Bicep as declarative and goal-seeking but notes that it relies on ARM/incremental deployment rather than a stored Terraform state file. ([Microsoft Learn][2])

Terraform:

```text
Configuration
      +
Terraform State
      +
Actual Azure
      ↓
terraform plan
```

Bicep:

```text
Bicep definition
      ↓
Azure Resource Manager
      ↓
Current Azure resource state
      ↓
Deployment
```

This difference becomes especially important for deletion and resource ownership.

---

## **Production example**

Suppose I have:

```text
main.bicep
│
├── VNet
├── NSG
├── Key Vault
└── Storage
```

An engineer removes Key Vault from the Bicep code.

A dangerous assumption is:

```text
Removed from Bicep
      ↓
Azure automatically deletes Key Vault
```

With normal incremental deployment, that is not the mental model I should use.

Instead I should determine:

```text
Do we intentionally want lifecycle-managed deletion?
      ↓
Yes
      ↓
Use appropriate controlled mechanism
such as deployment stacks
```

and review the deletion explicitly.

---

### **Interview answer condensed**

> “Incremental deployment is ARM and Bicep's default and recommended deployment behavior. Resources declared in the deployment are created or updated, while existing resources that aren't included are normally left in place. A key nuance is that incremental doesn't mean individual resource properties are simply patched—when an existing resource is redeployed, its declared configuration is reapplied according to the resource provider. Also, removing a resource from a Bicep file doesn't necessarily delete it in incremental mode. For managed deletion, Microsoft's current recommendation is deployment stacks rather than relying on complete deployment mode, which is being gradually deprecated.”

**Memory line:**
**Incremental deployment manages what you declare without treating everything omitted from the deployment as something to delete.**

**Interview trap:**
Incremental mode means omitted **resources** remain; it does **not guarantee omitted properties on a redeployed resource remain unchanged**.

**Keywords:**
Incremental deployment, ARM, Bicep, create, update, omitted resources, what-if, deployment stacks, complete mode.

**Likely follow-ups:**

* What happens if you remove a resource from a Bicep file?
* What's the difference between incremental and complete deployment?
* Why are deployment stacks relevant now?
* Does incremental mode only modify the one property you changed?

# **T27-M06. What is a deployment scope?**

**Answer:**

A deployment scope is the **Azure hierarchy level at which an ARM/Bicep deployment executes and where the declared resources are targeted**.

Bicep supports deployments at:

```text
Tenant
  ↓
Management Group
  ↓
Subscription
  ↓
Resource Group
```

The default Bicep target scope is:

```text
resourceGroup
```

but I can explicitly set:

```bicep
targetScope = 'subscription'
```

or:

```bicep
targetScope = 'managementGroup'
```

or:

```bicep
targetScope = 'tenant'
```

The scope matters because it determines what types of resources can be created and what permissions the deployment identity requires. Modules can also deploy into other scopes when a single solution needs resources across multiple hierarchy levels. Microsoft currently documents Bicep deployment at resource-group, subscription, management-group, and tenant scopes. ([Microsoft Learn][3])

---

# **Azure hierarchy and scope**

Think:

```text
Microsoft Entra Tenant
        ↓
Management Groups
        ↓
Subscriptions
        ↓
Resource Groups
        ↓
Resources
```

Different resources belong naturally at different levels.

For example:

```text
Resource Group scope
→ VNet
→ AKS
→ Storage
→ Key Vault

Subscription scope
→ Resource Groups
→ some Policy assignments
→ RBAC assignments

Management Group scope
→ enterprise Policy
→ enterprise RBAC

Tenant scope
→ management-group-related resources
→ selected tenant-wide resources
```

So the deployment scope should match what you're trying to manage.

---

# **1. Resource-group scope**

This is the default for Bicep.

Conceptually:

```bicep
targetScope = 'resourceGroup'
```

or simply omit `targetScope`, since resource group is the default.

Then:

```text
Deployment
    ↓
rg-app-prod
    ↓
├── VNet
├── AKS
├── ACR
└── Key Vault
```

Typical command:

```bash
az deployment group create \
  --resource-group rg-app-prod \
  --template-file main.bicep
```

This is the most common workload deployment scope.

---

# **2. Subscription scope**

Use:

```bicep
targetScope = 'subscription'
```

when managing subscription-level resources.

For example:

```text
Subscription
│
├── Resource Group A
├── Resource Group B
├── Policy Assignment
└── RBAC Assignment
```

A subscription-scoped deployment can create resource groups and other supported subscription-level resources. Microsoft documents:

```bash
az deployment sub create
```

for subscription-level Bicep deployments. ([Microsoft Learn][4])

Example:

```bash
az deployment sub create \
  --location centralindia \
  --template-file main.bicep
```

Notice the deployment needs a location because the deployment metadata itself must be stored somewhere even though the scope is the subscription.

---

# **3. Management-group scope**

Use:

```bicep
targetScope = 'managementGroup'
```

for governance that should apply across multiple subscriptions.

For example:

```text
corp-management-group
│
├── Policy: approved regions
├── Policy: required security config
└── RBAC assignment
        ↓
Subscriptions inherit governance
```

This is useful in enterprise landing zones.

Microsoft currently documents management-group-level Bicep for things such as policy and RBAC across subscriptions. ([Microsoft Learn][5])

---

# **4. Tenant scope**

Use:

```bicep
targetScope = 'tenant'
```

for supported tenant-level deployments.

Examples can include:

```text
Management Group creation
selected tenant-level RBAC
selected tenant resources
```

The deploying principal must have the required tenant-level permissions. ([Microsoft Learn][3])

This is obviously more privileged than deploying one resource group.

---

# **Deployment scope affects authorization**

Suppose a user has:

```text
Contributor
on:
rg-app-prod
```

They may be able to deploy resource-group-level workload resources there.

But if the Bicep file has:

```bicep
targetScope = 'subscription'
```

and tries to create:

```text
another Resource Group
subscription-level policy
```

their resource-group Contributor assignment isn't sufficient.

So:

```text
Deployment scope
      ↓
Required Azure RBAC scope
```

must line up.

---

# **Deployment scope does not mean everything must stay there**

This is where modules matter.

Microsoft's Bicep documentation explains that resources declared directly with `resource` normally align with the deployment scope, while modules allow nested deployments targeting other scopes. ([Microsoft Learn][3])

Example:

```text
Subscription-level main.bicep
      ↓
Create Resource Groups
      ↓
Module A → rg-network
      ↓
Module B → rg-aks
```

Conceptually:

```bicep
targetScope = 'subscription'

module network './network.bicep' = {
  name: 'networkDeploy'
  scope: resourceGroup('rg-network')
  params: {
    ...
  }
}
```

Now the parent runs at subscription scope while the module deploys resources into the resource group.

---

# **Multi-subscription deployment**

Suppose a platform deployment needs:

```text
Shared Networking Subscription
        +
Application Subscription
```

A subscription-scoped Bicep file can invoke a module targeting another subscription, assuming the deploying principal has authorization there. Microsoft explicitly supports modules targeting other subscriptions. ([Microsoft Learn][4])

Conceptually:

```text
Parent deployment
    ↓
Subscription A
    │
    ├── networking
    │
    └── module
          ↓
      Subscription B
          ↓
       workload
```

This is useful, but cross-subscription permissions increase complexity and blast radius.

---

# **`existing` resources are another distinction**

Suppose my Bicep deployment targets:

```text
Application Subscription
```

but needs to reference:

```text
Shared VNet
in Networking Subscription
```

I don't necessarily need to redeploy the shared VNet.

I can reference it as an `existing` resource when supported:

```text
Application deployment
       ↓
Reference shared existing resource
       ↓
Use its ID/property
```

Microsoft's scope documentation distinguishes referencing existing resources from deploying new resources at another scope. ([Microsoft Learn][3])

---

# **Why scope matters in architecture**

For enterprise Bicep I might organize:

```text
Tenant
  ↓
Management Group deployment
  ├── enterprise policy
  └── governance

Subscription deployment
  ├── Resource Groups
  └── subscription RBAC

Resource Group modules
  ├── Network
  ├── AKS
  ├── ACR
  └── Key Vault
```

This mirrors Azure's natural resource hierarchy.

---

# **Common mistake**

A developer writes:

```bicep
targetScope = 'resourceGroup'
```

then tries to create a resource group as though it were a normal resource inside that same target resource group.

That is conceptually wrong.

To create resource groups, move up to:

```text
subscription scope
```

because:

```text
Subscription
   ↓
contains Resource Groups
```

not:

```text
Resource Group
   ↓
contains another Resource Group
```

---

### **Interview answer condensed**

> “A Bicep deployment scope is the Azure hierarchy level where the deployment runs. The supported main scopes are resource group, subscription, management group, and tenant, with resource group being the default. I would use resource-group scope for normal workload resources like AKS or VNets, subscription scope for things like creating resource groups or subscription-level policy/RBAC, and management-group or tenant scope for broader governance. Scope also determines the permissions the deployment principal needs. If one solution has to deploy across multiple scopes, I can use Bicep modules with explicit target scopes.”

**Memory line:**
**Deployment scope answers: at what level of the Azure hierarchy is this Bicep deployment operating?**

**Interview trap:**
A deployment identity having Contributor on one resource group does **not** automatically let a subscription-scoped Bicep deployment create or govern resources across the subscription.

**Keywords:**
Deployment scope, `targetScope`, resource group, subscription, management group, tenant, modules, Azure RBAC, nested deployment.

**Likely follow-ups:**

* What is Bicep's default deployment scope?
* How would you create a resource group using Bicep?
* How can one Bicep solution deploy resources to multiple resource groups?
* How does deployment scope affect RBAC?

# **T27-M07. How does Bicep differ from Terraform?**

**Answer:**

Both Bicep and Terraform are declarative Infrastructure as Code tools, but their architecture and intended scope are different.

**Bicep is Azure-native**. It is designed specifically for Azure and deploys through Azure Resource Manager. It doesn't maintain a separate Terraform-style state file; ARM evaluates the deployment against Azure.

Terraform is **provider-based and multi-platform**. It can manage Azure as well as many other clouds and services, and it maintains Terraform state to map configuration resources to real infrastructure.

So my high-level mental model is:

```text
Bicep
→ Azure-native
→ ARM deployment engine
→ no Terraform state file

Terraform
→ provider-based
→ multi-cloud/multi-service
→ Terraform state
```

Both are declarative, modular, version-controllable, and suitable for CI/CD. The choice is usually about Azure-native integration versus ecosystem consistency and Terraform's state/provider model. Microsoft's own comparison emphasizes these differences in state, target platforms, processing, and Azure integration. ([Microsoft Learn][2])

---

## **Architecture**

### Bicep

```text
Bicep code
    ↓
Azure Resource Manager
    ↓
Azure Resource Providers
    ↓
Azure Infrastructure
```

### Terraform

```text
Terraform HCL
     ↓
Terraform engine
     ↓
State
     ↓
AzureRM / AzAPI provider
     ↓
Azure APIs
     ↓
Azure Infrastructure
```

That architectural difference explains many operational differences.

---

# **1. Azure-specific vs provider ecosystem**

Bicep:

```text
Azure
only
```

Terraform:

```text
Azure
AWS
GCP
Kubernetes
GitHub
Cloudflare
Datadog
many other APIs
```

through providers.

So if an organization needs:

```text
Azure infrastructure
+
GitHub configuration
+
Cloudflare
+
Kubernetes resources
```

Terraform can potentially provide one IaC ecosystem across those systems.

Bicep is intentionally Azure-focused.

---

# **2. State model**

This is probably the most important distinction.

### Terraform

Terraform maintains:

```text
terraform.tfstate
```

which maps configuration addresses such as:

```text
azurerm_resource_group.prod
```

to actual Azure objects.

Production model:

```text
Terraform Configuration
       ↓
Remote State
       ↓
Actual Azure
       ↓
terraform plan
```

State needs:

* secure storage,
* locking,
* access control,
* backup/protection.

---

### Bicep

Bicep does not maintain an external Terraform-style state file.

Microsoft's comparison states that Bicep relies on ARM/incremental deployment rather than Terraform's stored state model. ([Microsoft Learn][2])

Conceptually:

```text
Bicep
 ↓
ARM deployment request
 ↓
Azure's current resource state
```

So there is:

```text
No tfstate backend to manage
```

but also a different ownership/deletion model.

---

# **3. Deletion behavior**

Terraform knows from its state/configuration that:

```text
Resource used to be managed
+
now removed from configuration
```

and `terraform plan` can propose:

```text
- destroy
```

Bicep incremental deployment doesn't use that same stateful ownership model.

If a resource disappears from normal Bicep input:

```text
Removed from Bicep
       ↓
Incremental deployment
       ↓
Resource can remain
```

For Bicep lifecycle-managed deletions, current Microsoft guidance points toward **deployment stacks**. ([Microsoft Learn][1])

---

# **4. Plan vs what-if**

Terraform:

```bash
terraform plan
```

Bicep/ARM:

```bash
az deployment group what-if ...
```

Both help preview proposed changes, but they come from different engines.

Terraform uses:

```text
Configuration
+
State
+
Provider/API refresh
```

Bicep What-If uses the ARM deployment model against Azure.

Neither preview is an absolute guarantee that execution will succeed because state/permissions/policy/capacity can change afterward.

---

# **5. Provider support versus immediate Azure API support**

Terraform Azure deployments typically rely on:

```text
AzureRM provider
```

and sometimes:

```text
AzAPI provider
```

for newer or less directly supported Azure API capabilities.

Bicep maps directly to Azure resource-provider API types.

This can give Bicep an advantage for very Azure-specific features because it operates naturally in Azure's ARM resource model.

That doesn't mean Bicep always has zero lag or that every preview resource is automatically easy to use, but it is tightly aligned to Azure's resource providers.

---

# **6. Authentication model**

Both can authenticate using modern Azure workload identities.

For example:

```text
GitHub Actions
      ↓
OIDC
      ↓
Microsoft Entra ID
```

then either tool can deploy.

But their client architecture differs.

Bicep is submitted through an authenticated ARM deployment request.

Terraform providers authenticate to Azure APIs as Terraform runs.

Microsoft's comparison highlights that Bicep deployment authorization is handled through ARM while Terraform authenticates through its providers. ([Microsoft Learn][2])

---

# **7. Resource dependency handling**

Both infer many dependencies automatically.

Bicep:

```text
resource reference
      ↓
ARM dependency graph
```

Terraform:

```text
resource attribute reference
       ↓
Terraform dependency graph
```

And both provide explicit dependency mechanisms for cases where natural references don't express the dependency.

So this is more similar than different.

---

# **8. Modules**

Both support reusable infrastructure components.

### Bicep

```text
main.bicep
 ↓
module network
module aks
module monitoring
```

### Terraform

```text
root module
 ↓
network module
aks module
monitoring module
```

The module concepts are similar even though language/ecosystem details differ.

---

# **9. Language**

Bicep:

```text
Bicep DSL
```

Terraform:

```text
HCL
```

Both are much more readable than raw ARM JSON for most engineers.

Syntax preference alone shouldn't determine enterprise tooling.

---

# **10. Multi-cloud portability**

This is often overstated.

Terraform gives you:

```text
one IaC tool
```

across multiple clouds.

It does **not** mean:

```text
same Terraform code
runs unchanged on Azure and AWS
```

An Azure VNet resource:

```text
azurerm_virtual_network
```

doesn't magically become an AWS VPC.

So the portability is primarily:

```text
workflow
language
module practices
state model
tooling
```

not resource-level portability.

That's a useful interview distinction.

---

# **11. Out-of-band/manual changes**

Terraform:

```text
Terraform config
        +
state
        +
refresh actual Azure
        ↓
plan can detect relevant drift
```

Bicep:

```text
Bicep redeployment
      ↓
ARM applies declared configuration
```

Bicep doesn't have Terraform's persistent state mapping, so operational drift handling is conceptually different. Microsoft explicitly identifies out-of-band changes/state behavior as a major comparison area between the two. ([Microsoft Learn][2])

---

# **12. Operational complexity**

### Terraform introduces backend responsibilities

Production:

```text
Azure Storage backend
      ↓
tfstate Blob
      +
locking
      +
RBAC
      +
state protection
```

You need to secure that state.

Bicep avoids this separate Terraform-state infrastructure.

That can reduce tooling overhead for Azure-only organizations.

---

# **13. Existing enterprise standards matter**

Suppose an organization already has:

```text
Terraform modules
Terraform Cloud
policy framework
CI pipelines
team expertise
```

Switching to Bicep simply because the workload is Azure-native may create unnecessary fragmentation.

Likewise, if an organization is:

```text
Azure-only
+
deep Microsoft platform investment
+
no need for Terraform ecosystem
```

Bicep can be simpler.

Tool selection is architectural and organizational, not just syntactic.

### **Interview answer condensed**

> “Both Bicep and Terraform are declarative IaC tools, but Bicep is Azure-native and deploys directly through Azure Resource Manager, while Terraform is provider-based and can manage Azure plus many other platforms. The biggest architectural difference is state: Terraform keeps a state file that maps configuration to real resources, whereas Bicep doesn't maintain a separate Terraform-style state and instead relies on ARM's deployment model. Terraform therefore has explicit state/backend and drift-management workflows, while Bicep has tighter native Azure integration and less backend-state operational overhead. I'd choose based on the organization and target estate rather than saying one is universally better.”

**Memory line:**
**Bicep is Azure-native ARM IaC without Terraform-style state; Terraform is provider-based IaC with explicit state and a broader ecosystem.**

**Interview trap:**
Terraform being “multi-cloud” does **not** mean the same Azure resource code is portable unchanged to AWS or GCP.

# **T27-H01. When would you choose Bicep instead of Terraform?**

**Answer:**

I would choose Bicep when the environment is **primarily or exclusively Azure**, the team wants the closest integration with Azure Resource Manager, and there isn't a strong requirement for Terraform's multi-provider ecosystem or external state model.

For example, for an Azure-only landing zone or application platform where I'm deploying management-group policy, subscriptions, resource groups, VNets, AKS, Key Vault, Azure Monitor, and other Azure-native services, Bicep can be attractive because it maps directly to Azure resource-provider APIs, supports Azure hierarchy scopes naturally, and doesn't require maintaining a Terraform backend and state-locking architecture.

I would choose Terraform instead if the organization already standardizes on Terraform, needs to manage multiple clouds or non-Azure providers through one workflow, or depends heavily on Terraform's state-based lifecycle and module ecosystem.

So I would make the decision based on **platform scope, operational model, existing team standards, and lifecycle requirements**, not simply on which syntax I prefer. Microsoft similarly positions Bicep as Azure-specific and Terraform as the broader provider/multi-cloud choice. ([Microsoft Learn][2])

```text
Terraform     Bicep remains strong candidate
 ↓
Need native Azure-first governance/scopes
with minimal state-backend overhead?
                 ↓
               Bicep
```

But this isn't a rigid algorithm; organization standards often outweigh individual technical advantages.

---

# **Scenario 1 — Azure-only organization**

Suppose the company runs:

```text
Microsoft Entra ID
Azure subscriptions
Azure networking
AKS
ACR
Key Vault
Azure SQL
Azure Monitor
Azure Policy
```

and has no:

```text
AWS
GCP
Cloudflare IaC
other provider requirements
```

Then Bicep fits naturally.

Architecture:

```text
Git
 ↓
Bicep
 ↓
Azure DevOps / GitHub Actions
 ↓
ARM
 ↓
Azure
```

No additional Terraform state backend has to be maintained.

---

# **Scenario 2 — Deep Azure governance deployments**

Suppose I'm building an Azure landing zone:

```text
Tenant
  ↓
Management Groups
  ↓
Policy
  ↓
Subscriptions
  ↓
Resource Groups
```

Bicep's direct support for:

```text
tenant
managementGroup
subscription
resourceGroup
```

scope makes it natural for Azure governance architecture. Microsoft documents Bicep deployments across all of these scopes. ([Microsoft Learn][3])

Example:

```text
Management Group Bicep
       ↓
Policies

Subscription Bicep
       ↓
Resource Groups / RBAC

Resource Group Modules
       ↓
Workloads
```

---

# **Scenario 3 — I want Azure-native feature alignment**

Suppose a newly released Azure feature exposes an ARM API quickly.

Bicep works against Azure resource-provider types directly:

```text
Microsoft.X/resourceType@apiVersion
```

That can be attractive for teams that need close alignment with ARM.

Terraform may require:

```text
AzureRM provider support
```

or:

```text
AzAPI
```

before the experience is equally direct.

This doesn't mean Terraform is unsuitable—the AzAPI provider exists specifically to close many of these gaps—but Bicep can be very natural for Azure-first capabilities.

---

# **Scenario 4 — I don't want Terraform state operations**

Terraform production architecture includes:

```text
Terraform
  ↓
Remote Backend
  ↓
Azure Storage
  ↓
tfstate
  +
locking
```

That is a powerful model, but it introduces operational responsibilities:

* protect state,
* control backend access,
* handle locks,
* manage state movement/import/refactoring,
* recover state if damaged.

Bicep avoids maintaining a separate Terraform-style state file. ([Microsoft Learn][2])

For a team that doesn't need Terraform's broader capabilities, fewer moving parts can be valuable.

---

# **But “no Terraform state” is not automatically better**

Terraform state also gives useful capabilities.

For example:

```text
Configuration
+
State
+
Azure
 ↓
Plan
```

supports a strong managed-resource lifecycle.

Bicep has a different model.

If I remove:

```text
resource storage ...
```

from normal incremental Bicep deployment, I shouldn't expect Terraform-like automatic destruction.

Current Microsoft guidance is to use deployment stacks for ARM/Bicep-managed resource deletion. ([Microsoft Learn][1])

So I would understand the lifecycle trade-off before saying:

> “No state means Bicep is simpler and therefore always better.”

---

# **Scenario 5 — Strong Microsoft/Azure skill set**

If the platform team already understands:

```text
ARM
Azure Policy
resource-provider APIs
Azure hierarchy
Azure CLI
Azure DevOps
```

Bicep can have a very low conceptual gap.

For example:

```bicep
resource kv 'Microsoft.KeyVault/vaults@...' = {
  ...
}
```

maps quite directly onto the Azure resource model engineers already know.

# **When I would NOT choose Bicep**

## **1. Multi-cloud platform**

Suppose:

```text
Azure
+
AWS
+
Cloudflare
+
GitHub
```

must all be managed through one IaC ecosystem.

Terraform's provider model is stronger.

```text
Terraform
├── azurerm
├── aws
├── cloudflare
└── github
```

Bicep cannot become a universal IaC language for those providers.

---

## **2. Organization already standardized on Terraform**

Suppose the company has:

```text
Terraform module registry
Terraform policies
remote-state conventions
trained teams
Terraform CI templates
```

Then introducing:

```text
Bicep
```

creates:

```text
second language
second module ecosystem
second deployment model
second operational knowledge requirement
```

Even if Bicep is technically excellent for Azure, standardization may be more valuable.

---

## **3. Cross-platform resource relationships**

Suppose one infrastructure deployment needs:

```text
Azure AKS
+
GitHub repository configuration
+
Cloudflare DNS
+
Datadog monitoring
```

Terraform can potentially model the dependency graph through multiple providers.

With Bicep, the Azure infrastructure could be managed well, but other systems require different tooling.

---

# **Production example: when I'd choose Bicep**

Requirement:

> Build an Azure-only private application platform for one enterprise.

```text
Management Group
      ↓
Azure Policy
      ↓
Production Subscription
      ↓
Resource Groups
      ↓
Hub VNet
      ↓
Private AKS
      ↓
ACR
Key Vault
Azure Monitor
Private Endpoints
```

Team:

```text
Azure specialists
No AWS/GCP
No Terraform existing standard
```

I'd seriously consider Bicep.

Possible structure:

```text
main.bicep
│
├── governance.bicep
├── networking.bicep
├── aks.bicep
├── acr.bicep
├── keyvault.bicep
└── monitoring.bicep
```

Pipeline:

```text
GitHub / Azure DevOps
        ↓
Bicep lint/build
        ↓
ARM What-If
        ↓
Approval
        ↓
Deployment
        ↓
Azure
```

That's clean and highly Azure-native.

---

# **Production example: when I'd choose Terraform instead**

Requirement:

```text
Azure infrastructure
+
GitHub organization configuration
+
Cloudflare
+
future AWS workloads
```

Organization already has:

```text
Terraform remote backend
shared modules
Terraform expertise
```

Then:

```text
Terraform
```

would probably be the better organizational decision.

---

# **Security differences don't fundamentally choose the winner**

Both can use:

```text
GitHub Actions
     ↓
OIDC
     ↓
Microsoft Entra ID
     ↓
least-privilege Azure RBAC
```

Both can be:

```text
version controlled
reviewed
validated
deployed through CI/CD
```

So I wouldn't say:

```text
Bicep is secure
Terraform is insecure
```

or vice versa.

Security depends heavily on:

* identity,
* RBAC,
* pipeline permissions,
* code review,
* backend/state protection,
* policy enforcement.

---

# **Cost consideration**

Neither tool normally determines the cost of Azure resources by itself.

The infrastructure architecture matters.

But operational complexity has a cost:

```text
Bicep
→ Azure-only tooling simplicity

Terraform
→ backend/state/provider ecosystem management
```

versus:

```text
Terraform
→ one standardized tool across many platforms
```

which may reduce organization-wide tooling complexity.

So “simpler” depends on context.

# **Decision framework I'd say in an architecture interview**

I'd evaluate:

```text
1. Azure-only or multi-cloud?
2. Existing company IaC standard?
3. Need to manage non-Azure providers?
4. How important is Terraform's state model?
5. How Azure-native are governance/deployment requirements?
6. Team expertise?
7. Module ecosystem already available?
8. Long-term operational ownership?
```

Then make the decision.

---

### **Interview answer condensed**

> “I'd choose Bicep when the estate is primarily Azure and I want very tight Azure Resource Manager integration without operating a Terraform state backend. It's particularly attractive for Azure-native governance and landing-zone work because it understands resource-group, subscription, management-group and tenant deployment scopes directly and maps closely to ARM resource-provider APIs. I'd choose Terraform instead if the organization already standardizes on it, needs multiple clouds or non-Azure providers, or specifically benefits from Terraform's explicit state-based lifecycle. I wouldn't pick between them based only on syntax—the right choice depends on the target platforms, existing engineering ecosystem and lifecycle model.”

**Memory line:**
**Choose Bicep when Azure itself is the platform boundary; choose Terraform when your IaC boundary extends beyond Azure or your organization already standardizes on Terraform.**

**Interview trap:**
“Bicep has no Terraform-style state” is **not automatically an advantage in every scenario**—Terraform's state model also provides powerful lifecycle and drift-management capabilities.
