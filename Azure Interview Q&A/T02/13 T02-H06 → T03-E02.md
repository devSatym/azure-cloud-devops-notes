# 2. 🔴 M IMP — Microsoft Entra ID, Authentication, Authorization & RBAC

## Hard

### **T02-H06. How would you design privileged administration using PIM instead of permanent Owner assignments?**

**Answer:**
I would remove permanent high-privilege access wherever possible and make administrators **eligible for privileged roles through Microsoft Entra PIM**.

Instead of:

```text
Admin
→ Permanent Owner
→ Production Subscription
```

I would design:

```text
Admin
→ Eligible Owner / Contributor
→ PIM activation
      ↓
MFA
      ↓
Justification
      ↓
Approval if required
      ↓
Time-limited access
      ↓
Automatic expiration
```

The idea is to minimize **standing privilege**. Administrators get powerful permissions only when they actually need them, and only for a limited period. Eligible Azure role assignments provide just-in-time role access through PIM. ([Microsoft Learn][1])

### **My production design**

I would normally separate roles based on actual responsibility rather than making everyone eligible for Owner.

For example:

```text
Platform Engineer
→ Eligible Contributor
→ Production platform RG

Network Engineer
→ Eligible Network Contributor
→ Connectivity subscription

Security Engineer
→ Eligible Security-specific role

Small set of senior administrators
→ Eligible Owner / User Access Administrator
→ Subscription
```

This follows least privilege because even during activation, the engineer receives only the role required for that task.

### **Activation controls**

For sensitive roles, I would configure:

* MFA
* justification
* approval for highly privileged roles
* limited activation duration
* notifications
* audit logging
* periodic access reviews

For example:

```text
Production Owner activation

MFA required
+ Ticket/change number required
+ Manager/security approval
+ Maximum duration: 1 hour
```

### **Separate resource management from access management**

I would also avoid using Owner when the person only needs to manage infrastructure.

For normal operations:

```text
Contributor
```

may be sufficient.

If someone specifically needs to manage RBAC:

```text
User Access Administrator
```

or an appropriate narrower role may be better than giving broad Owner access.

### **Emergency access**

I would still maintain carefully protected **emergency-access or break-glass accounts** for scenarios where the normal identity or PIM process is unavailable.

Those accounts should:

* be heavily monitored,
* not be used for normal administration,
* have strong credentials,
* trigger alerts when used,
* and be periodically tested.

### **Important limitation**

PIM eligibility is primarily suitable for **human administrators** who can perform an activation step.

Applications, service principals, and managed identities cannot perform normal interactive PIM activation in the same way, so workload identities should instead use fixed least-privilege permissions with narrow scopes and short-lived authentication mechanisms where possible. ([Microsoft Learn][2])

**Memory line:**
**No standing Owner → eligible privilege → activate when needed → expire automatically.**

**Interview trap:**
PIM does not replace RBAC.

**RBAC defines what the role can do.
PIM controls when and for how long the privileged role becomes active.**

**Keywords:** PIM, eligible assignment, JIT access, standing privilege, MFA, approval, time-bound access, break-glass

**Likely follow-ups:**

* Would you make every administrator eligible for Owner?
* What is the difference between PIM and RBAC?
* How would you handle emergency access if PIM is unavailable?
* Can service principals use PIM eligibility like human users?

### **T02-H07. How would you give developers access to Kubernetes resources without making them Azure subscription Contributors?**

**Answer:**
I would separate **access to the AKS Azure resource** from **authorization inside the Kubernetes cluster**.

Developers usually do not need Azure subscription Contributor just to work with Kubernetes objects.

I would integrate AKS with **Microsoft Entra ID** for authentication and then authorize developers either through:

1. **Kubernetes RBAC**, or
2. **Azure RBAC for Kubernetes authorization**

at the required cluster or namespace scope. AKS supports both approaches. ([Microsoft Learn][3])

### **Preferred model**

Suppose the developers only need access to the `orders` namespace.

I would create an Entra group:

```text
aks-orders-developers
```

and add the developers to it.

Then I could grant namespace-scoped permissions such as:

```text
Namespace: orders

Allowed:
- get/list/watch pods
- view logs
- manage deployments
- manage services

Not allowed:
- cluster-wide administration
- kube-system changes
- Azure subscription resource changes
```

### **Option 1 — Microsoft Entra authentication + Kubernetes RBAC**

The flow would be:

```text
Developer
    ↓
Microsoft Entra ID authentication
    ↓
AKS Kubernetes API
    ↓
Kubernetes Role / RoleBinding
    ↓
orders namespace
```

For example:

```text
Role: orders-developer
RoleBinding:
  Entra Developers Group
      ↓
  orders namespace
```

AKS supports using Entra identities with native Kubernetes RBAC for namespace and cluster permissions. ([Microsoft Learn][4])

### **Option 2 — Azure RBAC for Kubernetes authorization**

AKS can also authorize Kubernetes API requests using Azure role assignments.

Microsoft provides AKS-specific roles such as:

```text
Azure Kubernetes Service RBAC Reader
Azure Kubernetes Service RBAC Writer
Azure Kubernetes Service RBAC Admin
Azure Kubernetes Service RBAC Cluster Admin
```

For example, I could grant:

```text
aks-orders-developers
→ Azure Kubernetes Service RBAC Writer
→ /namespaces/orders
```

so developers can manage permitted Kubernetes resources in that namespace without becoming Azure subscription Contributors. Azure RBAC for Kubernetes supports role assignments at cluster or namespace scope for standard Kubernetes resources. ([Microsoft Learn][3])

### **What I would avoid**

I would not solve this by giving developers:

```text
Contributor
→ Production Subscription
```

because that grants Azure infrastructure permissions far beyond Kubernetes application access.

They may then be able to modify:

* VNets,
* VMs,
* storage,
* AKS infrastructure,
* or other Azure resources,

depending on scope.

### **Production model**

A clean design is:

```text
Azure infrastructure
    ↓
Platform/DevOps team
    ↓
Azure RBAC

Kubernetes workloads
    ↓
Application developers
    ↓
Namespace-scoped Kubernetes/Azure RBAC
```

That separates **platform administration from application administration**.

**Memory line:**
**Azure RBAC controls the AKS Azure resource; Kubernetes authorization controls what developers do inside the cluster.**

**Interview trap:**
Having access to the AKS Azure resource and having permission inside Kubernetes are **not automatically the same thing**.

Authentication to AKS and authorization to Kubernetes resources are separate decisions.

**Keywords:** AKS, Microsoft Entra ID, Kubernetes RBAC, Azure RBAC for Kubernetes, namespace scope, least privilege

**Likely follow-ups:**

* What is the difference between Kubernetes RBAC and Azure RBAC for Kubernetes?
* Would you give developers cluster-admin?
* How would you restrict developers to one namespace?
* How does `kubectl` authenticate against an Entra-integrated AKS cluster?

# 3. 🔴 M IMP — Azure Virtual Networking

## Easy

### **T03-E01. What is an Azure Virtual Network?**

**Answer:**
An Azure Virtual Network, or **VNet**, is the fundamental service used to create an **isolated private network in Azure**.

It provides the network address space in which Azure resources can communicate privately with:

* each other,
* other connected VNets,
* on-premises networks,
* and, when configured, the internet.

Microsoft describes VNet as the fundamental building block for private networking in Azure. ([Microsoft Learn][5])

### **Example**

I might create:

```text
VNet: vnet-prod
Address space: 10.10.0.0/16
```

and divide it into:

```text
10.10.1.0/24 → web subnet
10.10.2.0/24 → application subnet
10.10.3.0/24 → database/private-endpoint subnet
```

I can then use network controls such as:

* NSGs for traffic filtering,
* route tables for routing,
* VNet peering for connecting VNets,
* VPN or ExpressRoute for hybrid connectivity,
* Private Endpoints for accessing Azure PaaS services privately.

### **Default connectivity concept**

Resources in the same VNet can generally communicate using private IP addresses, subject to controls such as NSGs, routes, firewalls, and operating-system firewalls.

Resources in separate VNets require explicit connectivity such as VNet peering or another network connection. ([Microsoft Learn][6])

**Memory line:**
**VNet = your private network boundary in Azure.**

**Interview trap:**
A **VNet and subnet are not the same thing**.

The VNet defines the larger private network address space; subnets divide that address space into smaller network segments.

**Keywords:** VNet, private network, address space, subnet, routing, NSG, peering

---

### **T03-E02. What is a subnet?**

**Answer:**
A subnet is a **smaller IP address range carved out of a VNet's address space**.

Subnets are used to segment resources by function, security requirement, or routing requirement.

For example:

```text
VNet: 10.0.0.0/16

├── Web subnet  → 10.0.1.0/24
├── App subnet  → 10.0.2.0/24
└── Data subnet → 10.0.3.0/24
```

Azure uses subnets as important scopes for things such as:

* Network Security Groups,
* route-table associations,
* service-specific subnet integrations,
* network segmentation.

Microsoft defines a subnet as a range of IP addresses inside a VNet and recommends using subnets to organize workload components and apply security and routing controls. ([Microsoft Learn][6])

### **Example**

For a three-tier application:

```text
Internet
   ↓
Application Gateway
   ↓
Web Subnet
   ↓
App Subnet
   ↓
Database / Private Endpoint
```

I can apply different NSG rules to each subnet so, for example:

```text
Internet → Web        Allow HTTPS
Web → App             Allow app port
App → Database        Allow database port
Internet → Database   Deny
```

### **Important Azure detail**

Azure reserves **five IP addresses in every subnet**:

* the first four addresses,
* and the last address.

So in a `/24` network:

```text
256 total addresses
251 usable addresses
```

Azure's current networking guidance explicitly documents those five reserved addresses. ([Microsoft Learn][6])

**Memory line:**
**VNet defines the network; subnet divides the network.**

**Interview trap:**
Subnet sizing matters.

For services such as AKS, Application Gateway, Azure Firewall, or large VM deployments, choosing a subnet that is too small can cause future scaling problems.

**Keywords:** subnet, CIDR, segmentation, NSG, route table, address space, IP planning
