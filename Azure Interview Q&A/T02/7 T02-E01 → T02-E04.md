# 2. 🔴 M IMP — Microsoft Entra ID, Authentication, Authorization & RBAC

## Easy

### **T02-E01. What is Microsoft Entra ID?**

**Answer:**
Microsoft Entra ID is Microsoft’s **cloud-based identity and access management service**.

It is used to manage and authenticate identities such as:

* users,
* groups,
* applications,
* service principals,
* and managed identities.

It also provides capabilities such as:

* Single Sign-On,
* Multi-Factor Authentication,
* Conditional Access,
* identity governance,
* application authentication,
* and integration with Azure RBAC.

From an Azure perspective, Entra ID answers:

> **“Who is this identity?”**

Azure RBAC then usually answers:

> **“What is this identity allowed to do on Azure resources?”**

**Example:**
Suppose a DevOps engineer signs in to Azure.

```text
User
  ↓
Microsoft Entra ID
  ↓ Authentication
Azure
  ↓
Azure RBAC
  ↓ Authorization
AKS / VM / Storage / Other Resource
```

Entra ID authenticates the engineer. Azure RBAC then determines whether that engineer can view, modify, or deploy Azure resources.

The same concept applies to workloads. A GitHub Actions workflow, VM, or AKS workload can also authenticate using an identity rather than a human username and password.

**Memory line:**
**Entra ID = identity and authentication platform.**

**Interview trap:**
Microsoft Entra ID is **not the same thing as traditional Windows Server Active Directory**.

Traditional Active Directory is primarily designed around concepts such as:

* domains,
* domain controllers,
* LDAP,
* Kerberos,
* Group Policy.

Entra ID is a cloud-native identity platform primarily based around modern authentication protocols and cloud identity management.

**Keywords:** identity provider, authentication, SSO, MFA, Conditional Access, tenant, service principal, managed identity

### **T02-E02. What was Azure Active Directory renamed to?**

**Answer:**
**Azure Active Directory, or Azure AD, was renamed to Microsoft Entra ID.**

The rename was part of Microsoft’s broader Microsoft Entra identity product family.

The important interview point is that this was mainly a **product-name change**, not a migration to a completely different identity service.

So if older documentation or an interviewer says:

> Azure AD

they are generally referring to what is now called:

> **Microsoft Entra ID**

You may also still encounter older terminology in:

* scripts,
* Terraform resources,
* APIs,
* documentation,
* CLI output,
* existing company architecture diagrams.

**Example:**

Older terminology:

```text
Azure AD Tenant
Azure AD Application
Azure AD Service Principal
```

Current terminology:

```text
Microsoft Entra Tenant
Microsoft Entra Application
Microsoft Entra Service Principal
```

**Memory line:**
**Azure AD → Microsoft Entra ID.**

**Interview trap:**
Do not say:

> “Azure AD became Azure RBAC.”

They are completely different concepts.

**Entra ID** handles identities and authentication.

**Azure RBAC** handles authorization to Azure resources.

**Keywords:** Azure AD, Microsoft Entra ID, identity, rename, authentication

### **T02-E03. What is an Entra tenant?**

**Answer:**
A Microsoft Entra tenant is a **dedicated instance of Microsoft Entra ID that represents an organization and acts as an identity boundary**.

It contains identity objects such as:

* users,
* groups,
* application registrations,
* service principals,
* managed identities,
* devices,
* and directory roles.

When an organization creates or uses Microsoft cloud services, it typically has an Entra tenant that acts as its identity directory.

**Example:**

Imagine a company called Contoso.

It may have:

```text
Contoso Entra Tenant
│
├── Users
│   ├── Alice
│   └── Bob
│
├── Groups
│   ├── DevOps
│   └── Security
│
├── Applications
│
├── Service Principals
│
└── Managed Identities
```

That tenant may then be associated with several Azure subscriptions:

```text
Contoso Entra Tenant
│
├── Development Subscription
├── Production Subscription
└── Platform Subscription
```

The identities come from the tenant, while Azure RBAC controls what those identities can do inside the subscriptions.

**Memory line:**
**Tenant = organization's identity directory and identity boundary.**

**Important distinction:**
A tenant can be associated with **multiple Azure subscriptions**.

The tenant contains the identities.

The subscriptions contain the Azure resources.

**Interview trap:**
Do not treat **tenant** and **subscription** as interchangeable.

A useful distinction is:

```text
Tenant       → Identity boundary
Subscription → Resource, governance and billing boundary
```

**Keywords:** tenant, identity boundary, users, groups, applications, service principals, subscriptions

### **T02-E04. What is the difference between authentication and authorization?**

**Answer:**
The simplest way to remember it is:

**Authentication = Who are you?**
**Authorization = What are you allowed to do?**

Authentication verifies the identity of a user or workload.

Authorization happens after authentication and determines what that identity is permitted to access or modify.

### **Authentication examples**

In Azure, authentication might use:

* username and password,
* MFA,
* certificate,
* managed identity,
* service principal,
* workload identity federation.

Microsoft Entra ID commonly handles this step.

### **Authorization examples**

Once the identity is authenticated, authorization may be controlled through:

* Azure RBAC,
* Microsoft Entra directory roles,
* application-specific permissions,
* data-plane permissions.

**Example:**

Suppose I log into Azure.

```text
Step 1
Username + MFA
      ↓
Microsoft Entra ID
      ↓
Authentication successful
```

Azure now knows **who I am**.

Then I try to delete a VM:

```text
Authenticated User
      ↓
Azure RBAC
      ↓
Do I have Microsoft.Compute/.../delete?
      ↓
Allow / Deny
```

That second step is **authorization**.

### **DevOps example**

The same concept applies to GitHub Actions.

```text
GitHub Actions
      ↓
OIDC federation
      ↓
Entra ID authenticates workload
      ↓
Azure RBAC
      ↓
Contributor on rg-app-prod
```

OIDC establishes the workload's identity.

RBAC determines which Azure resources that workload is allowed to modify.

**Memory line:**
**Authentication proves identity.
Authorization grants permission.**

**Interview trap:**
Successfully logging into Azure does **not** mean you automatically have access to Azure resources.

A user can authenticate successfully and still receive:

```text
AuthorizationFailed
```

because the identity lacks the required Azure RBAC permission.

**Keywords:** authentication, authorization, identity, Entra ID, Azure RBAC, permissions, OIDC, MFA
