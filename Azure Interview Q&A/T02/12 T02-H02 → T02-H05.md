# 2. 🔴 M IMP — Microsoft Entra ID, Authentication, Authorization & RBAC

## Hard

### **T02-H02. How would you implement least-privilege access for a DevOps team?**

**Answer:**
I would implement least privilege by controlling both **what permissions the team receives** and **where those permissions apply**.

My approach would be:

1. Identify the actual tasks the DevOps team performs.
2. Prefer specific built-in roles over broad roles like Owner.
3. Assign roles to **Entra groups rather than individual users**.
4. Apply them at the **smallest practical scope**.
5. Separate production and non-production access.
6. Use **PIM** for privileged human access.
7. Use separate managed identities or federated workload identities for automation.
8. Regularly review and remove unused permissions.

Microsoft recommends granting only the permissions required and avoiding broad roles at broad scopes because reducing both role privilege and scope reduces the impact of credential compromise. ([Microsoft Learn][1])

### **Example design**

Suppose the DevOps team manages an AKS application.

I might configure:

```text
DevOps Developers
├── Contributor → development application RG
└── Reader → production application RG

Senior Operations
└── Eligible Contributor → production RG through PIM

GitHub Actions Identity
└── Contributor → production application RG only

Application Workload Identity
└── Key Vault Secrets User → one required Key Vault
```

I would **not** give everyone:

```text
Owner → entire subscription
```

just because it is easier.

### **Separate humans from automation**

This is especially important.

A CI/CD pipeline should have its **own identity**, with only the permissions required for deployment.

For example:

```text
Human engineer
    ≠
GitHub deployment identity
    ≠
AKS workload identity
```

This makes auditing clearer and limits the blast radius if one identity is compromised.

### **Use narrow roles where possible**

If a team only manages VMs, I would consider a role such as:

```text
Virtual Machine Contributor
```

instead of:

```text
Contributor
```

If no built-in role fits, I could use a custom role containing only the required operations.

### **Production access**

For production, I would normally avoid permanent privileged access.

Instead:

```text
Eligible role
    ↓
PIM activation
    ↓
MFA
    ↓
Justification / approval
    ↓
Time-limited production access
```

**Rule of thumb:**
**Least privilege = minimum permission + minimum scope + minimum duration.**

**Interview trap:**
Least privilege is not just:

> “Don't give Owner.”

Giving Contributor at an entire management group or subscription can still be far too broad.

Both the **role** and the **scope** matter.

**Keywords:** least privilege, RBAC, narrow scope, Entra groups, PIM, workload identity, separation of duties, blast radius

**Likely follow-ups:**

* Would you give a CI/CD pipeline Contributor?
* Why assign roles to groups instead of users?
* When would you create a custom role?
* How would you handle emergency production access?

### **T02-H03. How would you grant a CI/CD pipeline permission to deploy only into one resource group?**

**Answer:**
I would create a **dedicated workload identity for the pipeline** and assign it only the required Azure RBAC role at the **resource-group scope**.

For GitHub Actions, I would prefer **OIDC workload identity federation** rather than storing a long-lived client secret.

Conceptually:

```text
GitHub Actions
      ↓ OIDC
Microsoft Entra ID
      ↓
Deployment Identity
      ↓
Contributor
      ↓
rg-orders-prod only
```

The key part is the scope.

Instead of:

```text
Contributor
→ Subscription
```

I would assign:

```text
Contributor
→ /subscriptions/<id>/resourceGroups/rg-orders-prod
```

Azure recommends assigning roles at the smallest scope required by the workload. ([Microsoft Learn][2])

### **Practical implementation**

For example:

```bash
az role assignment create \
  --assignee-object-id <pipeline-object-id> \
  --assignee-principal-type ServicePrincipal \
  --role Contributor \
  --scope /subscriptions/<subscription-id>/resourceGroups/rg-orders-prod
```

Now the pipeline can deploy resources inside `rg-orders-prod`, but it does not automatically have Contributor rights over:

```text
rg-network-prod
rg-security
rg-database-prod
```

### **Would I always use Contributor?**

No.

If the pipeline only needs a smaller set of actions, I would prefer:

* a narrower built-in role,
* or a custom role.

For example, a pipeline that only pushes images to ACR may need an ACR-specific data role instead of general Contributor access.

### **For GitHub Actions authentication**

I would configure a federated identity relationship between:

```text
GitHub repository/environment
        ↓
OIDC token
        ↓
Microsoft Entra application/service principal
```

This removes the need to store an Azure client secret in GitHub.

### **Production hardening**

For production I would also restrict the federation to the correct:

* repository,
* branch or environment,
* deployment workflow context,

and use GitHub environment protections or deployment approvals where appropriate.

**Memory line:**
**Dedicated identity + narrow role + resource-group scope + short-lived authentication.**

**Interview trap:**
Do not give the CI/CD pipeline:

```text
Owner at Subscription
```

just because Terraform or deployment automation needs to create resources.

If the pipeline only deploys into one resource group, scope it there unless there is a specific requirement for broader permissions.

**Keywords:** CI/CD identity, workload identity federation, OIDC, resource-group scope, Contributor, least privilege

**Likely follow-ups:**

* Why is OIDC preferable to a client secret?
* What if Terraform needs to create role assignments?
* What if the pipeline needs resources in two resource groups?
* Would you use the same deployment identity for dev and prod?

### **T02-H04. How would you troubleshoot a user receiving `AuthorizationFailed` despite having an RBAC role?**

**Answer:**
I would troubleshoot `AuthorizationFailed` systematically by checking:

**Identity → Role → Scope → Required Action → Propagation → Conditions/Deny → Resource context**

rather than simply assigning a broader role.

### **1. Confirm the actual identity**

First, I verify which identity is making the request.

This is especially important with:

* multiple Azure accounts,
* service principals,
* managed identities,
* multiple Entra tenants,
* CI/CD pipelines.

The object ID shown in the error is very useful.

I would confirm:

```bash
az account show
```

and compare the tenant, subscription, and identity with what I expect.

---

### **2. Read the exact denied action and scope**

An Azure error typically contains something like:

```text
AuthorizationFailed

does not have authorization to perform action
'Microsoft.Network/virtualNetworks/write'

over scope
'/subscriptions/.../resourceGroups/rg-network/...'
```

That tells me two critical things:

```text
Required permission
+
Required scope
```

I then check whether the assigned role actually contains that action.

---

### **3. Verify the role-assignment scope**

A common problem is correct role, wrong scope.

For example:

```text
Contributor
→ rg-app
```

does not allow modifying a VNet located in:

```text
rg-network
```

I inspect the effective role assignments at the target resource and its parents.

Azure authorization is based on applicable role assignments and their scopes. ([Microsoft Learn][3])

---

### **4. Check whether the role really contains the required permission**

A role name can be misleading.

For example, a specialized role may manage a VM but not:

* networking resources,
* role assignments,
* Key Vault data,
* storage data.

So I compare the denied operation against the role's `Actions` or `DataActions`.

---

### **5. Check control plane versus data plane**

This is a frequent issue.

For example, someone may have:

```text
Contributor
on Storage Account
```

but receive a 403 while trying to read blobs.

The problem may be that they have management-plane permission but lack a data-plane role such as:

```text
Storage Blob Data Reader
```

---

### **6. Consider RBAC propagation**

If the role was just assigned, Azure RBAC changes may take several minutes to propagate.

Microsoft notes that role-assignment changes can take up to around 10 minutes in normal cases, and refreshing the access token or signing in again can help pick up the new authorization state. ([Microsoft Learn][4])

So I would refresh credentials before concluding the assignment is wrong.

---

### **7. Check deny assignments and conditions**

Azure's authorization evaluation checks applicable **deny assignments before allowing access**. Even when an RBAC allow exists, a relevant deny can block the operation. ([Microsoft Learn][3])

I would also check whether the role assignment has an **ABAC condition** that prevents this particular operation.

---

### **8. Check Azure Policy and resource locks separately**

If RBAC succeeds but the operation still fails, I check:

* Azure Policy,
* resource locks,
* service-specific restrictions.

These are not all technically `AuthorizationFailed` causes, but they often appear during the same troubleshooting workflow.

### **My troubleshooting flow**

```text
Correct identity?
      ↓
Correct tenant/subscription?
      ↓
Correct role?
      ↓
Correct scope?
      ↓
Required Action/DataAction included?
      ↓
Role propagated/token refreshed?
      ↓
Conditions or deny assignment?
      ↓
Policy / lock / service restriction?
```

**Memory line:**
**Don't fix `AuthorizationFailed` by blindly adding Owner—read the denied action and scope first.**

**Interview trap:**
A visible role assignment does not automatically prove effective authorization.

It could be:

* assigned at the wrong scope,
* missing the required action,
* newly assigned and not propagated,
* restricted by a condition,
* or overridden by a deny assignment.

**Keywords:** AuthorizationFailed, object ID, action, scope, effective permissions, propagation, DataActions, deny assignments

**Likely follow-ups:**

* How long can Azure RBAC propagation take?
* How do you distinguish data-plane and management-plane permission failures?
* How would you inspect effective role assignments?
* What if assigning Owner still doesn't fix the problem?

### **T02-H05. How do deny assignments differ from Azure RBAC role assignments?**

**Answer:**
An Azure RBAC role assignment **grants permissions**, while a deny assignment explicitly **blocks specific actions**, even when an RBAC role assignment would otherwise allow them.

Conceptually:

```text
Role Assignment
→ ALLOW

Deny Assignment
→ BLOCK
```

During Azure authorization evaluation, applicable deny assignments are checked before allowed role assignments. If a deny applies to the requested operation, access is blocked. ([Microsoft Learn][3])

### **Example**

Suppose a user has:

```text
Owner
→ Resource Group
```

Normally, Owner can delete resources.

But if a deny assignment applies that blocks:

```text
*/delete
```

then the user can still be prevented from performing the affected delete operations, even though Owner normally grants them.

So:

```text
Owner ALLOW
+
Applicable DENY
=
Operation denied
```

### **How this differs from `NotActions`**

This is an important interview distinction.

In a custom role:

```text
Actions:
  *

NotActions:
  Microsoft.Compute/virtualMachines/delete
```

`NotActions` simply subtracts that permission from **that role definition**.

It is **not an explicit deny**.

If the user receives VM delete permission from another role assignment, the operation may still be allowed.

A deny assignment is different because it actively blocks the operation during authorization evaluation.

### **Where deny assignments appear**

Deny assignments are commonly associated with Azure-managed scenarios and protected resources. Azure also exposes mechanisms for viewing and, in supported contexts, managing deny assignments. Microsoft's Azure CLI documentation describes them as blocking specific resource actions even when role assignments grant access. ([Microsoft Learn][5])

### **Troubleshooting implication**

If somebody says:

> “I'm Owner, but Azure still won't let me perform this operation.”

one of the things I would investigate is:

```text
Deny assignment
```

rather than assuming the RBAC role is missing.

**Memory line:**
**RBAC grants; deny assignment overrides the grant for the denied action.**

**Interview trap:**
`NotActions` and deny assignments are **not equivalent**.

```text
NotActions
= permission excluded from one role

Deny assignment
= explicit authorization block
```

**Keywords:** deny assignment, RBAC allow, explicit deny, authorization evaluation, NotActions, effective permissions

**Likely follow-ups:**

* Does deny override Owner?
* What is the difference between `NotActions` and deny assignments?
* How do you list deny assignments?
* Can Azure Policy also block an operation?
