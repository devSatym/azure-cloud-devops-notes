# 2. 🔴 M IMP — Microsoft Entra ID, Authentication, Authorization & RBAC

## Easy

### **T02-E05. What is Azure RBAC?**

**Answer:**
Azure RBAC, or **Azure Role-Based Access Control**, is Azure’s authorization system for controlling **who can do what on which Azure resources**.

An RBAC assignment combines three core things:

```text
Security Principal + Role + Scope
```

For example:

```text
DevOps-Team
    +
Contributor
    +
rg-app-prod
```

This means the DevOps team can perform the permissions defined by the Contributor role within that resource group and its child resources.

RBAC can be assigned at different scopes:

```text
Management Group
    ↓
Subscription
    ↓
Resource Group
    ↓
Resource
```

Permissions assigned at a higher scope are generally inherited by the lower scopes.

**Example:**
If I give a user:

```text
Reader
at Subscription scope
```

they can view resources across that subscription.

If I instead assign:

```text
Contributor
at one Resource Group
```

their modification permissions are limited to that resource group.

This is why Azure RBAC is one of the main tools for implementing **least privilege**.

**Memory line:**
**RBAC = Who + What permissions + Where.**

**Interview trap:**
Azure RBAC does **not authenticate users**.

Microsoft Entra ID normally handles authentication.

Azure RBAC handles **authorization after authentication**.

Also, Azure RBAC roles are different from Entra directory roles such as Global Administrator.

**Keywords:** Azure RBAC, authorization, role assignment, security principal, role definition, scope, least privilege

---

### **T02-E06. What is an Azure role assignment?**

**Answer:**
An Azure role assignment is the mechanism that gives an identity a specific Azure RBAC role at a specific scope.

The three main components are:

```text
Who?
Security Principal

What can they do?
Role Definition

Where?
Scope
```

So conceptually:

```text
Role Assignment =
Principal + Role + Scope
```

### **1. Principal**

The principal can be:

* user,
* group,
* service principal,
* managed identity.

### **2. Role**

The role defines allowed operations.

Examples:

* Reader
* Contributor
* Owner
* Virtual Machine Contributor
* Storage Blob Data Reader

### **3. Scope**

The scope determines where those permissions apply.

For example:

```text
Management Group
Subscription
Resource Group
Individual Resource
```

**Example:**
Suppose I assign:

```text
Principal: GitHub deployment identity
Role: Contributor
Scope: /subscriptions/.../resourceGroups/rg-orders-prod
```

The pipeline can manage resources inside `rg-orders-prod`, but it does not automatically receive Contributor access to other resource groups in the subscription.

That is much safer than assigning Contributor at subscription level when the pipeline only needs one resource group.

**Memory line:**
**Role assignment = Who gets which role at what scope.**

**Interview trap:**
A **role definition** and a **role assignment** are different.

A role definition says:

> “What permissions exist?”

A role assignment says:

> “Give those permissions to this identity at this scope.”

**Keywords:** role assignment, principal, role definition, scope, inheritance, least privilege

### **T02-E07. What are Owner, Contributor, and Reader roles?**

**Answer:**
Owner, Contributor, and Reader are common built-in Azure RBAC roles with increasing levels of privilege.

### **Reader**

Reader can **view Azure resources and their configuration**, but cannot modify them.

Typical use:

```text
Auditors
Support engineers
Developers who only need visibility
```

---

### **Contributor**

Contributor can generally:

* create resources,
* modify resources,
* delete resources,
* manage resource configuration.

However, Contributor **cannot normally manage Azure RBAC role assignments**.

So a Contributor can manage infrastructure but cannot simply grant another user Owner access.

---

### **Owner**

Owner has the resource-management permissions of Contributor and can also **manage access**, including Azure RBAC role assignments.

That makes Owner a highly privileged role.

### **Simple comparison**

| Role        | View | Modify resources | Delete resources | Manage RBAC access |
| ----------- | ---: | ---------------: | ---------------: | -----------------: |
| Reader      |  Yes |               No |               No |                 No |
| Contributor |  Yes |              Yes |              Yes |                 No |
| Owner       |  Yes |              Yes |              Yes |                Yes |

**Example:**
For an application team:

```text
Developers → Reader in Production
CI/CD identity → Contributor on application RG
Platform admins → Owner only where required
```

In a mature environment, I would avoid giving permanent Owner access broadly and instead use least privilege and PIM for privileged roles.

**Memory line:**
**Reader = see.
Contributor = manage resources.
Owner = manage resources + access.**

**Interview trap:**
Contributor is still a **very powerful role**. It may not manage RBAC, but it can create, change, or delete many Azure resources.

So “Contributor” should not automatically be treated as a low-risk role.

**Keywords:** Reader, Contributor, Owner, built-in roles, RBAC, manage access, least privilege

### **T02-E08. What is the difference between an Azure subscription and an Entra tenant?**

**Answer:**
The easiest distinction is:

**Microsoft Entra tenant = identity boundary.**
**Azure subscription = resource, management, quota, and billing boundary.**

An Entra tenant contains identities such as:

* users,
* groups,
* service principals,
* application registrations,
* managed identities.

An Azure subscription contains:

* resource groups,
* VMs,
* VNets,
* AKS clusters,
* storage accounts,
* databases,
* and other Azure resources.

The subscription trusts a Microsoft Entra tenant for identity and authentication.

### **Relationship**

A common enterprise setup looks like:

```text
Microsoft Entra Tenant
│
├── Production Subscription
│   ├── Resource Groups
│   └── Azure Resources
│
├── Non-Production Subscription
│   ├── Resource Groups
│   └── Azure Resources
│
└── Platform Subscription
    ├── Resource Groups
    └── Azure Resources
```

The users and workload identities come from the **tenant**, while Azure RBAC determines what those identities can do in each **subscription**.

**Example:**
A company may have one corporate Entra tenant but separate subscriptions for:

```text
Production
Development
Security
Connectivity
```

The same employee identity can potentially access multiple subscriptions, but only if Azure RBAC grants the required permissions.

**Memory line:**
**Tenant = identities.
Subscription = Azure resources + billing/governance boundary.**

**Interview trap:**
A tenant and subscription are **not one-to-one**.

A single Entra tenant can be associated with multiple Azure subscriptions.

Also, changing subscription access does not mean creating a new tenant; these are separate architectural concepts.

**Keywords:** Entra tenant, subscription, identity boundary, billing boundary, resources, RBAC, governance
