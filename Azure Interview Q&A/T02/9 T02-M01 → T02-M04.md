# 2. 🔴 M IMP — Microsoft Entra ID, Authentication, Authorization & RBAC

## Medium

### **T02-M01. What are the components of an Azure RBAC role assignment?**

**Answer:**
The three core components of an Azure RBAC role assignment are:

```text
Security Principal + Role Definition + Scope
```

### **1. Security principal — who gets access**

This can be:

* a user,
* a group,
* a service principal,
* or a managed identity.

### **2. Role definition — what they can do**

The role contains the allowed permissions.

Examples:

* Reader
* Contributor
* Owner
* Virtual Machine Contributor
* Storage Blob Data Reader

### **3. Scope — where those permissions apply**

The role can be assigned at:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Resource
```

Microsoft defines these three elements—security principal, role definition, and scope—as the core of an Azure RBAC role assignment. ([Microsoft Learn][1])

**Example:**
Suppose my GitHub Actions pipeline only needs to deploy an application into one resource group.

I could assign:

```text
Principal: GitHub deployment service principal
Role: Contributor
Scope: rg-orders-prod
```

Now that identity can manage resources in `rg-orders-prod`, but it does not automatically get Contributor access across the entire subscription.

That follows the principle of least privilege.

**Memory line:**
**RBAC role assignment = Who + What + Where.**

**Interview trap:**
Do not confuse a **role definition** with a **role assignment**.

```text
Role definition
= what permissions the role contains

Role assignment
= give that role to a principal at a scope
```

**Keywords:** security principal, role definition, scope, role assignment, least privilege

**Likely follow-ups:**

* What types of security principals can receive Azure roles?
* What is the difference between a role definition and role assignment?
* Can a role assignment have conditions?

### **T02-M02. What is an Azure RBAC scope?**

**Answer:**
Azure RBAC scope defines the **resource or set of resources where a role assignment applies**.

There are four main Azure RBAC scope levels:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Individual Resource
```

The lower I assign the role, the smaller the blast radius of that permission.

For example:

```text
Contributor at Subscription
```

can affect resources throughout that subscription.

Whereas:

```text
Contributor at rg-app-prod
```

is limited to that resource group and its child resources.

Microsoft recommends assigning permissions at the **smallest scope necessary** to meet the requirement. ([Microsoft Learn][2])

**Example:**
If an application only needs to read one storage account, I would prefer:

```text
Storage Blob Data Reader
at that storage account
```

instead of assigning the same role at subscription scope.

Even though both may technically work, the second option exposes far more resources if that identity is compromised.

**Memory line:**
**Role = what you can do.
Scope = where you can do it.**

**Interview trap:**
A more specific scope does not mean the role becomes more powerful.

For example:

```text
Owner at one VM
```

has a smaller reach than:

```text
Reader at an entire management group
```

The role determines the allowed actions; the scope determines where they apply.

**Keywords:** scope, management group, subscription, resource group, resource, least privilege, blast radius

**Likely follow-ups:**

* Which scope should you normally prefer?
* Can permissions be inherited?
* Can a user have different roles at different scopes?
* What happens if a user receives roles at multiple scopes?

### **T02-M03. At which scopes can RBAC roles be assigned?**

**Answer:**
Azure RBAC roles can be assigned at four primary scopes:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Resource
```

The scope controls how widely the permission applies, and permissions assigned at parent scopes are inherited by child scopes. ([Microsoft Learn][3])

### **Management-group scope**

Used when I want permissions across multiple subscriptions.

Example:

```text
Security Team
→ Security Reader
→ Production Management Group
```

The team can inherit that access across subscriptions under that management group.

### **Subscription scope**

Used when an identity needs access across most or all resources in one subscription.

Example:

```text
Platform Team
→ Reader
→ Production Subscription
```

### **Resource-group scope**

Useful when a team manages one application or environment.

Example:

```text
Orders DevOps Team
→ Contributor
→ rg-orders-prod
```

### **Resource scope**

Most restrictive option.

Example:

```text
Application Identity
→ Storage Blob Data Reader
→ one Storage Account
```

**Practical rule:**
I choose the **lowest scope that satisfies the operational requirement**, because that reduces accidental access and the impact of credential compromise.

**Memory line:**
**MG → Subscription → RG → Resource**

**Interview trap:**
Do not automatically assign everything at subscription scope because it is easier.

For workload identities and CI/CD pipelines especially, I try to use resource-group or individual-resource scope whenever practical.

**Keywords:** management group, subscription, resource group, resource, inheritance, least privilege

**Likely follow-ups:**

* Which scope would you use for a CI/CD pipeline?
* Can a role at management-group level affect multiple subscriptions?
* Can I assign Owner to a single resource?
* What happens to inherited permissions at child scopes?

### **T02-M04. How is RBAC inheritance applied?**

**Answer:**
Azure RBAC permissions assigned at a **parent scope are inherited by child scopes**.

The hierarchy is:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Resource
```

So if I assign a user:

```text
Reader
at Subscription scope
```

that user automatically receives Reader access to the resource groups and resources beneath that subscription.

Microsoft explicitly documents that lower scopes inherit role permissions from higher scopes. ([Microsoft Learn][3])

### **Permissions are generally cumulative**

Suppose a user has:

```text
Reader
at Subscription
```

and:

```text
Contributor
at rg-orders-prod
```

Then the effective result is:

```text
Rest of subscription
→ Reader

rg-orders-prod
→ Contributor
```

The more privileged Contributor role at that specific resource group is added to the inherited Reader access.

### **Another example**

```text
Management Group
│
│ Reader → Security Team
│
└── Subscription
    │
    └── Resource Group
        │
        └── VM
```

The Security Team can read the VM even though no Reader assignment was created directly on the VM, because the permission was inherited from the management group.

### **Important caveat**

Azure RBAC is generally **additive**.

If a user receives multiple role assignments, Azure normally combines the allowed permissions.

You cannot simply assign a lower role at a child scope to cancel a higher inherited role.

For example:

```text
Contributor at Subscription
+
Reader at one Resource Group
```

does **not** turn the user into Reader-only in that resource group. The inherited Contributor permission still applies.

Controls such as **deny assignments** can override allowed RBAC actions in specific scenarios.

**Memory line:**
**Permissions flow downward; multiple allows generally add together.**

**Interview trap:**
This is a very common mistake:

> “I'll give Contributor at subscription and Reader at production RG so they can't modify production.”

That does **not work**.

The Contributor assignment inherited from the subscription remains effective.

Instead, I would redesign the scope of the Contributor assignment so production is never included in the first place.

**Keywords:** inheritance, parent scope, child scope, additive permissions, effective access, deny assignment

**Likely follow-ups:**

* Can a child role assignment remove inherited permissions?
* What if a user has Reader and Contributor simultaneously?
* How do deny assignments affect RBAC?
