# 2. 🔴 M IMP — Microsoft Entra ID, Authentication, Authorization & RBAC

## Medium

### **T02-M05. What is the difference between an Azure RBAC role and a Microsoft Entra directory role?**

**Answer:**
The main difference is **what they control**.

**Azure RBAC roles control access to Azure resources.**
**Microsoft Entra directory roles control administration of the identity directory.**

For example:

| Azure RBAC               | Microsoft Entra directory roles |
| ------------------------ | ------------------------------- |
| Reader                   | Global Reader                   |
| Contributor              | User Administrator              |
| Owner                    | Global Administrator            |
| Storage Blob Data Reader | Application Administrator       |

An Azure RBAC role might answer:

> “Can this user create a VM or modify an AKS cluster?”

An Entra directory role might answer:

> “Can this user create accounts, manage application registrations, or administer Entra ID?”

### **Example**

Suppose a user has:

```text
Global Administrator
in Microsoft Entra ID
```

That makes them highly privileged in the identity directory, but it does **not automatically make them Owner of every Azure subscription**.

Likewise, someone with:

```text
Owner
on an Azure subscription
```

can manage Azure resources and RBAC at that scope, but that does not automatically make them a Global Administrator in Entra ID.

So these are two separate authorization systems with different scopes.

**Memory line:**
**Entra role = manage identities.
Azure RBAC role = manage Azure resources.**

**Interview trap:**
A **Global Administrator is not automatically an Azure subscription Owner**.

There are specific mechanisms through which a Global Administrator can elevate access to Azure resources, but the roles are not equivalent by default.

**Keywords:** Azure RBAC, Entra directory roles, resource authorization, identity administration, Global Administrator, Owner

**Likely follow-ups:**

* Does Global Administrator automatically have access to all subscriptions?
* What is the difference between Owner and Global Administrator?
* Where would User Administrator be used?
* Can PIM manage both Azure and Entra roles?

### **T02-M06. What is the difference between Contributor and Owner?**

**Answer:**
Both **Contributor and Owner can manage Azure resources**, including creating, modifying, and deleting them.

The major difference is:

**Owner can also manage Azure RBAC access.**
**Contributor normally cannot assign Azure roles to other identities.**

So:

```text
Contributor
= manage resources

Owner
= manage resources + manage access
```

### **Example**

Suppose I give a DevOps engineer:

```text
Contributor
on rg-orders-prod
```

They can typically:

* create resources,
* modify resources,
* delete resources,
* deploy infrastructure.

But they cannot normally do:

```text
Give another user Owner access
```

If I instead assign **Owner**, that user can also create and remove role assignments within that scope.

### **Why this matters**

Owner is significantly more sensitive because it can be used for **privilege delegation**.

If an Owner credential is compromised, an attacker may not only modify infrastructure but also grant persistent access to additional identities.

For that reason, I prefer:

* Contributor or narrower roles for normal operations,
* Owner only when genuinely required,
* and PIM for privileged access where possible.

**Memory line:**
**Contributor = infrastructure control.
Owner = infrastructure control + access control.**

**Interview trap:**
Contributor is still a very powerful role.

Not being able to manage RBAC does **not** make Contributor harmless—it can still delete or alter many production resources.

**Keywords:** Contributor, Owner, role assignments, manage access, least privilege, privilege escalation

**Likely follow-ups:**

* Which role would you give a deployment pipeline?
* What is User Access Administrator?
* Why should Owner access be limited?
* Can Contributor manage Key Vault secrets?

### **T02-M07. What is a custom Azure RBAC role?**

**Answer:**
A custom Azure RBAC role is a **role definition that I create myself when Azure's built-in roles do not match the exact permissions required**.

The goal is usually to implement **least privilege** by granting only the operations a user or workload actually needs.

A custom role can define:

* allowed management-plane actions,
* excluded management-plane actions,
* allowed data-plane actions where supported,
* excluded data-plane actions,
* and the scopes where the role can be assigned.

Conceptually:

```text
Custom Role
├── Actions
├── NotActions
├── DataActions
├── NotDataActions
└── AssignableScopes
```

### **Example**

Suppose an operations team should be able to:

* view VMs,
* start VMs,
* restart VMs,

but must **not delete or create VMs**.

Instead of giving them broad `Virtual Machine Contributor` access, I could create a custom role containing only the required VM read/start/restart operations.

That provides a smaller blast radius.

### **When I would use one**

I would first check whether a suitable **built-in role** already exists.

If it does, I prefer the built-in role because it is easier to understand and maintain.

I create a custom role only when built-in roles are either:

* too broad,
* or missing required permissions.

**Memory line:**
**Built-in role first; custom role when least privilege requires a more precise permission set.**

**Interview trap:**
`NotActions` is not a deny rule.

It subtracts permissions from that particular role definition. If the identity receives the same permission through another role assignment, that operation may still be allowed.

That is different from a **deny assignment**.

**Keywords:** custom role, Actions, NotActions, DataActions, AssignableScopes, least privilege

**Likely follow-ups:**

* What is the difference between `Actions` and `DataActions`?
* Is `NotActions` the same as deny?
* When should you avoid custom roles?
* How would you create a custom role?

### **T02-M08. What is Conditional Access?**

**Answer:**
Microsoft Entra Conditional Access is a **policy engine that evaluates signals during authentication and decides what access controls should be applied**.

A useful way to think about it is:

```text
IF these conditions are true
THEN enforce these access controls
```

Conditional Access can evaluate signals such as:

* user or group,
* target application,
* device state,
* location,
* platform,
* sign-in risk,
* user risk,
* authentication context.

It can then apply controls such as:

* require MFA,
* require a compliant device,
* require stronger authentication,
* block access,
* require an approved authentication method.

### **Example**

For Azure administrators, I might create a policy like:

```text
IF:
  User = privileged administrator
  AND
  Accessing = Azure management

THEN:
  Require MFA
```

I could make it stricter:

```text
Privileged admin
      +
Untrusted location
      ↓
Require MFA
      +
Require compliant device
```

This means authentication decisions can change depending on the context rather than relying only on a username and password.

### **How it fits into authentication**

A simplified flow is:

```text
User signs in
     ↓
Entra authenticates identity
     ↓
Conditional Access evaluates signals
     ↓
Policy decision
     ↓
Allow / Require controls / Block
```

### **Important design point**

Conditional Access policies should normally be introduced carefully using testing or report-only approaches where appropriate, because a badly configured policy can lock administrators out.

Emergency or **break-glass accounts** also need to be considered in the design.

**Memory line:**
**Conditional Access = if these conditions are true, enforce these access controls.**

**Interview trap:**
Conditional Access and MFA are **not the same thing**.

MFA is an authentication control.

Conditional Access is the policy engine that can decide **when MFA—or another access control—must be required**.

**Keywords:** Conditional Access, policy engine, MFA, signals, device compliance, risk, location, access control

**Likely follow-ups:**

* What signals can Conditional Access evaluate?
* What is report-only mode?
* What are break-glass accounts?
* What is the difference between Conditional Access and MFA?
