# 2. 🔴 M IMP — Microsoft Entra ID, Authentication, Authorization & RBAC

## Medium

### **T02-M09. What is MFA?**

**Answer:**
MFA, or **Multi-Factor Authentication**, means requiring a user to prove their identity using **two or more different authentication factors**.

The three common factor categories are:

* **Something you know** → password or PIN
* **Something you have** → phone, hardware key, authenticator app
* **Something you are** → fingerprint or facial recognition

The purpose is to reduce the risk of account compromise. If an attacker steals only the password, they still need the second factor to authenticate. Microsoft Entra MFA supports several methods, including Microsoft Authenticator, passkeys/FIDO2, certificate-based authentication, OATH tokens, SMS, and others. ([Microsoft Learn][1])

**Example:**
For an Azure administrator:

```text
Username + Password
        ↓
Microsoft Entra ID
        ↓
MFA challenge
        ↓
Microsoft Authenticator
        ↓
Authentication succeeds
```

In an enterprise environment, I would normally enforce MFA using **Conditional Access**, particularly for privileged accounts and sensitive applications. ([Microsoft Learn][2])

**Memory line:**
**MFA = prove identity using multiple independent factors.**

**Interview trap:**
Entering a password and then answering another password-like question is not strong MFA if both are effectively the same factor category.

Also:

**MFA ≠ Conditional Access**

MFA is an authentication control. Conditional Access is the policy engine that can decide **when MFA must be required**.

**Keywords:** MFA, authentication factors, password, Authenticator, FIDO2, Conditional Access

**Likely follow-ups:**

* What are the three authentication-factor categories?
* What is the difference between MFA and Conditional Access?
* Which MFA methods are stronger than SMS?
* How would you enforce MFA for Azure administrators?

### **T02-M10. What is Privileged Identity Management?**

**Answer:**
Microsoft Entra Privileged Identity Management, or **PIM**, is a service used to reduce permanent privileged access by providing **just-in-time and controlled activation of privileged roles**.

Instead of giving an administrator permanent Owner or Global Administrator access, I can make that user **eligible** for the role and require them to activate it only when they need to perform privileged work.

Activation can require controls such as:

* MFA,
* justification,
* approval,
* limited activation duration,
* notifications,
* access reviews.

Microsoft describes PIM as a way to limit standing administrator access and manage privileged role assignments for Microsoft Entra roles and Azure resource roles. ([Microsoft Learn][3])

**Example:**

Instead of:

```text
Engineer
→ Permanent Owner
→ Production Subscription
```

I would prefer:

```text
Engineer
→ Eligible Owner
→ Production Subscription
        ↓
Needs production access
        ↓
Activate through PIM
        ↓
MFA + justification + approval
        ↓
Owner for 1 hour
        ↓
Privilege expires
```

This significantly reduces the amount of **standing privilege** in the environment.

**Memory line:**
**PIM = privileged access only when needed, for only as long as needed.**

**Interview trap:**
PIM does not create completely new Azure permissions.

It controls **how and when existing privileged roles are assigned or activated**.

**Keywords:** PIM, just-in-time access, eligible role, active role, MFA, approval, least privilege, standing access

**Likely follow-ups:**

* What is eligible versus active in PIM?
* Can PIM manage Azure RBAC roles?
* Can PIM manage Entra directory roles?
* Why is PIM better than permanent Owner access?

### **T02-M11. What is the difference between eligible and active PIM assignments?**

**Answer:**
The key difference is whether the user has the privileged permissions **immediately** or must **activate them first**.

### **Eligible assignment**

An eligible user does **not continuously have the privileged role active**.

They are allowed to activate it when needed.

Activation can require:

* MFA,
* business justification,
* approval,
* activation duration,
* other configured controls.

### **Active assignment**

An active user has the role's permissions **ready to use without performing an activation first**.

Microsoft PIM explicitly defines eligible assignments as requiring activation and active assignments as being immediately usable. ([Microsoft Learn][3])

### **Example**

Suppose I need occasional production access.

With an **active** assignment:

```text
Satyam
→ Owner
→ Production
→ Privileges available continuously
```

With an **eligible** assignment:

```text
Satyam
→ Eligible Owner
→ Production
        ↓
Activate role
        ↓
MFA + justification
        ↓
Owner for 1 hour
```

For privileged human access, I would generally prefer **eligible assignments**, because they reduce standing privilege.

### **Important distinction**

Eligible does not mean the role provides fewer permissions.

Once activated, an eligible Owner has the same Owner permissions as an active Owner at the same scope.

The difference is **when those permissions become available**. ([Microsoft Learn][3])

**Memory line:**
**Eligible = can activate privilege.
Active = privilege is already available.**

**Interview trap:**
Do not say:

> “Eligible users have limited permissions.”

They do not.

Before activation, they do not have the role's active privileges. After valid activation, they receive the role permissions for the activation period.

**Keywords:** eligible, active, activation, PIM, JIT, standing privilege, MFA, approval

**Likely follow-ups:**

* Can an eligible assignment be permanent?
* Can an active assignment be time-limited?
* What controls can PIM require during activation?
* Would you assign Owner as eligible or active for administrators?

# Hard

### **T02-H01. A user has Reader at subscription level and Contributor at resource-group level; what can the user do?**

**Answer:**
Azure RBAC permissions are generally **additive**, and permissions assigned at a higher scope are inherited by lower scopes.

So if the user has:

```text
Reader
at Subscription
```

and:

```text
Contributor
at rg-app-prod
```

the effective permissions are:

```text
Subscription
│
├── rg-app-prod
│      → Contributor
│
├── rg-network
│      → Reader
│
└── rg-database
       → Reader
```

In other words:

**Across the subscription → Reader**

**Inside that specific resource group → Contributor**

Azure documents that overlapping role assignments are additive, so the effective permissions are the sum of the applicable assignments. ([Microsoft Learn][4])

### **Why?**

The Reader permission is inherited from the subscription.

When the user enters `rg-app-prod`, another role assignment applies:

```text
Inherited Reader
+
Contributor at RG
=
Effective Contributor capabilities there
```

Contributor already includes broad resource-management capabilities, so the extra Reader permission does not meaningfully increase access within that resource group.

### **What can they do inside that resource group?**

They can generally:

* view resources,
* create resources,
* modify resources,
* delete resources,
* manage supported resource configurations.

But Contributor normally **cannot manage Azure RBAC role assignments**. ([Microsoft Learn][5])

### **What about the rest of the subscription?**

Outside that resource group, the user remains Reader, so they can inspect resources but cannot normally modify them.

### **Important caveat**

Effective authorization can still be restricted by other controls such as:

* deny assignments,
* Azure Policy,
* resource locks,
* resource-specific data-plane authorization.

So RBAC says what the user is allowed to attempt, but other Azure controls may still prevent a particular action.

**Memory line:**
**Reader everywhere + Contributor on one RG = Reader everywhere, Contributor on that RG.**

**Interview trap:**
Azure RBAC is **not “most restrictive role wins.”**

If someone has:

```text
Contributor at Subscription
+
Reader at Resource Group
```

they do **not become Reader-only** at the resource group.

The inherited Contributor permission still applies because Azure RBAC allow assignments are generally additive. ([Microsoft Learn][4])

**Keywords:** RBAC inheritance, additive permissions, Reader, Contributor, effective permissions, scope

**Likely follow-ups:**

* What if Contributor is assigned at subscription and Reader at resource group?
* Can a lower-level role remove inherited permissions?
* How would you prevent the user from modifying one specific resource group?
