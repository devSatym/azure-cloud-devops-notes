# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Hard

### **T07-H07. How would you upgrade a production AKS cluster with minimal downtime?**

**Answer:**
I would treat an AKS upgrade as an **application-availability exercise**, not just a Kubernetes-version change. My plan is: validate compatibility, maintain spare capacity, use rolling/surge node upgrades, protect workloads with replicas and PDBs, and monitor every stage before proceeding.

AKS upgrades node pools using a rolling process: it adds surge capacity, cordons and drains old nodes, reschedules workloads, upgrades/replaces the node, and then removes temporary capacity. ([Microsoft Learn][1])

### **1. Check the upgrade path first**

Before production:

```bash
az aks get-upgrades \
  -g rg-prod \
  -n aks-prod
```

I check:

* current → target Kubernetes version,
* deprecated/removed APIs,
* ingress-controller compatibility,
* CSI drivers,
* Helm charts/operators,
* admission policies,
* service meshes or KEDA if used.

I would upgrade:

```text
Dev
 ↓
Staging
 ↓
Production
```

not jump directly into production.

---

### **2. Ensure workloads are actually highly available**

For an important API:

```text
replicas = 3+
readiness probe
startup/liveness probes
PDB
topology spread / anti-affinity
```

Example:

```text
Node-1 → API Pod A
Node-2 → API Pod B
Node-3 → API Pod C
```

If one node drains:

```text
A evicted
B + C still serve traffic
replacement A scheduled elsewhere
```

If I have:

```text
replicas = 1
```

no AKS upgrade setting can magically guarantee zero downtime.

---

### **3. Configure a sensible PodDisruptionBudget**

For three replicas:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: api
```

This permits:

```text
3 running
↓
1 voluntary eviction allowed
↓
at least 2 remain available
```

Before maintenance, I check:

```bash
kubectl get pdb -A
```

A PDB showing:

```text
ALLOWED DISRUPTIONS = 0
```

can block node drains and therefore block an upgrade. Microsoft specifically recommends ensuring PDBs permit at least some eviction while still protecting availability. ([Microsoft Learn][2])

---

### **4. Use `maxSurge`**

Instead of reducing existing capacity before replacement capacity exists, AKS can temporarily create extra nodes.

Example:

```text
Production pool:
9 nodes

maxSurge = 33%
```

Conceptually:

```text
9 old nodes
   +
3 temporary new nodes
```

Then:

```text
new capacity ready
     ↓
drain old nodes gradually
     ↓
reschedule Pods
     ↓
upgrade completes
```

Microsoft currently cites around **33% as a general recommendation for disruption-sensitive Standard AKS workloads**, though the right setting depends on quota, subnet/IP capacity, cost, and application behavior. ([Microsoft Learn][3])

---

### **5. Verify surge capacity can actually be created**

Before the upgrade I check:

```text
Azure VM quota
Regional VM SKU capacity
Subnet IP space
Pod IP space
Disk limits
```

Otherwise:

```text
AKS requests surge node
        ↓
Azure cannot allocate it
        ↓
upgrade stalls/fails
```

This is especially important with flat Azure CNI where new nodes/Pods can consume additional VNet IPs.

---

### **6. Use maintenance windows**

I schedule upgrades during:

```text
lower traffic
+
engineering coverage
+
monitoring active
```

not at a random platform-selected period if the workload is critical.

Conceptually:

```text
Maintenance window
02:00–05:00

Upgrade starts
   ↓
engineers monitoring
   ↓
rollback/mitigation available
```

---

### **7. Drain nodes gracefully**

During upgrade:

```text
Node-1
 ↓
cordon
 ↓
no new scheduling
 ↓
drain
 ↓
Pods evicted gracefully
 ↓
replacement Pods become Ready
 ↓
continue
```

I verify applications have appropriate:

```text
terminationGracePeriodSeconds
preStop hook if needed
readiness probes
```

so connections can finish before termination.

AKS allows tuning drain timeout; Microsoft documents a default drain timeout of 30 minutes and recommends increasing it when workloads legitimately need longer to reschedule or terminate. ([Microsoft Learn][4])

---

### **8. Don't bypass PDBs casually**

AKS now supports a force-upgrade option that can bypass PDB protections, but Microsoft explicitly warns that this can cause service disruption.

So:

```text
PDB blocks upgrade
     ↓
Fix replicas/PDB first ✅

Force bypass PDB
     ↓
last-resort emergency option ⚠️
```

([Microsoft Learn][4])

---

### **9. Monitor throughout**

During upgrade:

```bash
kubectl get nodes -w
kubectl get pods -A -o wide
kubectl get events -A --sort-by=.lastTimestamp
```

I also monitor:

```text
5xx
latency
Pod restarts
Pending Pods
PDB violations
node readiness
application health
```

I don't just wait for:

```text
az aks upgrade → Succeeded
```

because the infrastructure upgrade can succeed while the application is unhealthy.

### **Production sequence**

```text
1. Check supported target version
2. Check removed/deprecated APIs
3. Upgrade staging
4. Validate replicas + readiness
5. Validate PDBs
6. Check quota/IP headroom
7. Configure maxSurge
8. Schedule maintenance window
9. Upgrade control plane/node pools
10. Monitor application during each drain
11. Run smoke tests
12. Validate observability and SLOs
```

**Memory line:**
**Minimal-downtime AKS upgrade = replicas + PDB + surge capacity + graceful drain + monitoring.**

**Interview trap:**
Don't say:

> “AKS is managed, so upgrades are zero downtime.”

AKS handles the rolling infrastructure mechanics; **your workload architecture determines application availability**.

**Keywords:** AKS upgrade, `maxSurge`, PDB, rolling upgrade, drain, readiness, maintenance window

**Likely follow-ups:**

* What if a PDB blocks the upgrade?
* Why is `maxSurge` useful?
* What causes surge-node creation to fail?
* Would you ever use force upgrade?

### **T07-H08. How would you protect application availability while draining AKS nodes?**

**Answer:**
I protect availability by ensuring **multiple healthy replicas exist before the drain, controlling voluntary disruption with a PodDisruptionBudget, spreading replicas across nodes/zones, and using readiness plus graceful termination so traffic leaves a Pod before the Pod is killed**.

The desired behavior is:

```text
3 replicas
    ↓
Drain Node-1
    ↓
Pod A stops receiving traffic
    ↓
Pod A terminates gracefully
    ↓
Pods B + C keep serving
    ↓
replacement Pod becomes Ready
```

### **1. Run multiple replicas**

For a production web/API workload:

```yaml
replicas: 3
```

is fundamentally safer than:

```yaml
replicas: 1
```

With one replica:

```text
Drain node
   ↓
only Pod evicted
   ↓
temporary outage
```

With multiple replicas:

```text
drain one
↓
others continue serving
```

---

### **2. Use a PodDisruptionBudget**

For example:

```yaml
spec:
  minAvailable: 2
```

for three replicas.

Then Kubernetes tries to prevent a voluntary operation such as drain from reducing availability below two Pods.

Microsoft notes that PDBs directly control eviction during maintenance and that `ALLOWED DISRUPTIONS=0` can block a drain. ([Microsoft Learn][2])

A good PDB protects availability while still permitting maintenance.

Bad:

```text
replicas = 1
minAvailable = 1

Drain allowed?
NO
```

Too strict.

Better:

```text
replicas = 3
minAvailable = 2

One controlled eviction?
YES
```

---

### **3. Spread replicas across nodes**

Three replicas are not useful if:

```text
Node-1
├── Pod A
├── Pod B
└── Pod C
```

Then draining Node-1 removes all three.

I use:

```text
podAntiAffinity
or
topologySpreadConstraints
```

so they are distributed:

```text
Node-1 → Pod A
Node-2 → Pod B
Node-3 → Pod C
```

For zonal clusters:

```text
Zone 1 → Pod A
Zone 2 → Pod B
Zone 3 → Pod C
```

where architecture and capacity allow it.

---

### **4. Readiness probe removes terminating Pods from traffic**

Suppose a Pod begins shutdown.

I don't want:

```text
Load Balancer
   ↓
Pod that is already shutting down
```

Readiness controls whether the Pod should receive Service traffic.

Conceptually:

```text
Pod Ready ✅
→ traffic

termination begins
→ becomes/not treated as ready
→ removed from endpoints
→ no new traffic
```

---

### **5. Allow graceful shutdown**

For applications with live requests:

```yaml
terminationGracePeriodSeconds: 60
```

can give the process time to:

```text
stop accepting new requests
finish current requests
flush buffers
close DB connections
exit
```

A `preStop` hook can also be used when the application needs an explicit shutdown action.

Bad behavior:

```text
SIGTERM
↓
application killed immediately
↓
active requests fail
```

Desired:

```text
SIGTERM
↓
stop accepting work
↓
finish work
↓
clean exit
```

---

### **6. Ensure spare cluster capacity exists**

A PDB does not create CPU or memory.

Suppose:

```text
All remaining nodes = 100% allocated
```

Then draining one node causes:

```text
Pod evicted
   ↓
scheduler tries replacement
   ↓
no capacity
   ↓
Pending
```

So before maintenance I ensure:

```text
spare node capacity
or
Cluster Autoscaler headroom
or
surge nodes
```

exists.

---

### **7. Be careful with stateful workloads**

Stateful workloads may require:

```text
PVC attachment
zone compatibility
application quorum
leader election
graceful replication
```

For example:

```text
3 database replicas
```

might need a quorum of two.

A careless drain could remove multiple quorum members if topology isn't designed correctly.

So I verify:

```text
PDB
topology
storage zones
application-specific maintenance requirements
```

before evictions.

---

### **8. Check PDB before drain**

Before maintenance:

```bash
kubectl get pdb -A
```

I look at:

```text
DESIRED HEALTHY
CURRENT HEALTHY
ALLOWED DISRUPTIONS
```

If:

```text
ALLOWED DISRUPTIONS = 0
```

I determine why before draining.

Microsoft explicitly recommends verifying PDB eviction headroom before cluster maintenance. ([Microsoft Learn][2])

### **Strong availability model**

```text
Deployment
├── replicas: 3
├── readiness probe
├── graceful shutdown
├── PDB minAvailable: 2
└── topology spread
          ↓
Nodes in multiple failure domains
          ↓
Node drain
          ↓
only controlled disruption
```

**Memory line:**
**Drain safely = redundancy + spread + PDB + readiness + graceful termination + spare capacity.**

**Interview trap:**
A PDB by itself does not guarantee HA.

If all replicas run on one node, or no replacement capacity exists, availability can still suffer.

**Keywords:** PDB, drain, replicas, readiness, topology spread, graceful shutdown, eviction

**Likely follow-ups:**

* Can PDB protect against a node suddenly crashing?
* Why can PDB block upgrades?
* `minAvailable` vs `maxUnavailable`?
* What if replacement Pods remain Pending?

### **T07-H09. How would you separate system workloads and application workloads?**

**Answer:**
In AKS I would use a **dedicated System node pool for Kubernetes/AKS critical add-ons and one or more User node pools for business applications**, then enforce the separation with **taints, tolerations, labels, and scheduling rules**.

Architecture:

```text
AKS
│
├── systempool
│   ├── CoreDNS
│   ├── networking/system agents
│   └── critical add-ons
│
├── webpool
│   └── web/API workloads
│
└── batchpool
    └── batch/Spot workloads
```

Microsoft recommends dedicating system pools to critical system Pods and scheduling applications onto user pools. ([Microsoft Learn][5])

### **1. Create a dedicated System pool**

For example:

```text
systempool
mode = System
Linux
3 nodes
```

AKS automatically labels system-pool nodes:

```text
kubernetes.azure.com/mode=system
```

which causes AKS to prefer those nodes for system workloads. ([Microsoft Learn][5])

But that label alone doesn't prevent application Pods from landing there.

---

### **2. Apply `CriticalAddonsOnly` taint**

For strict separation:

```text
CriticalAddonsOnly=true:NoSchedule
```

on the System pool.

Then:

```text
Application Pod
     ↓
systempool
     ↓
no matching toleration
     ↓
rejected by scheduler
```

while critical add-ons that tolerate it can still run there.

Microsoft specifically recommends this taint for dedicated system pools. ([Microsoft Learn][5])

---

### **3. Put applications on User pools**

Example:

```text
userpool
mode = User
min = 3
max = 20
autoscaling enabled
```

Then application workloads run there.

For workload-specific placement I might label:

```text
workload=web
```

and:

```text
workload=batch
```

Then Deployment:

```yaml
nodeSelector:
  workload: web
```

Conceptually:

```text
frontend/API
    ↓
webpool

batch jobs
    ↓
batchpool
```

---

### **4. Use taints for specialized pools**

Suppose a GPU pool should only run ML workloads:

```text
sku=gpu:NoSchedule
```

Only GPU Pods get:

```yaml
tolerations:
  - key: sku
    value: gpu
    effect: NoSchedule
```

Similarly:

```text
spot=true:NoSchedule
```

can keep critical applications off Spot capacity.

---

### **5. Scale pools independently**

Example:

```text
systempool
3–5 nodes

webpool
3–30 nodes

batchpool
0–50 nodes
```

This prevents web traffic spikes from unnecessarily scaling system capacity.

Microsoft notes that user pools can scale independently and can even scale to zero where supported, while System pools have stricter availability requirements. ([Microsoft Learn][6])

---

### **6. Protect system components from noisy neighbors**

Without separation:

```text
Bad application
   ↓
Consumes CPU/memory
   ↓
CoreDNS starved
   ↓
DNS failures cluster-wide
```

With dedicated system capacity:

```text
Application overload
     ↓
User pool affected
     ↓
CoreDNS/system capacity protected
```

That's the real operational reason behind the design.

### **Production example**

```text
AKS
│
├── sysnp
│   ├── Mode: System
│   ├── 3 regular nodes
│   └── CriticalAddonsOnly=true:NoSchedule
│
├── appnp
│   ├── Mode: User
│   ├── autoscale 3–20
│   └── app workloads
│
└── batchnp
    ├── Mode: User
    ├── Spot
    ├── autoscale 0–30
    └── interruptible jobs
```

Current AKS requirements also specify that System pools use Linux, contain at least two nodes with three recommended, and cannot use Spot; Spot requires a User node pool. ([Microsoft Learn][6])

**Memory line:**
**System pool protects Kubernetes; User pools provide application compute.**

**Interview trap:**
Don't say:

> “Setting `mode=System` automatically prevents application Pods from running there.”

It doesn't.

Use the dedicated-system-pool taint:

```text
CriticalAddonsOnly=true:NoSchedule
```

when strict isolation is required.

**Keywords:** System pool, User pool, taints, tolerations, node labels, `CriticalAddonsOnly`, workload isolation

**Likely follow-ups:**

* Can application Pods technically run on System pools?
* Why use taints instead of only labels?
* Can Spot nodes be System nodes?
* How would you isolate GPU workloads?

### **T07-H10. How would you troubleshoot an AKS service that works internally but is inaccessible externally?**

**Answer:**
If the Service works **inside the cluster**, that already proves a lot: the application is likely running, Service selectors are probably correct, and basic Pod-to-Service communication works.

So I move outward through the traffic path:

```text
Pod
 ↓
Kubernetes Service ✅
 ↓
Node / AKS dataplane
 ↓
Azure Load Balancer / Ingress
 ↓
NSG / route / firewall
 ↓
Public client ❌
```

Microsoft's current AKS troubleshooting guidance recommends exactly this approach: first verify internal Kubernetes connectivity, then isolate the external-to-Kubernetes networking layer. ([Microsoft Learn][7])

### **1. Check Service type and external IP**

```bash
kubectl get svc -n <namespace>
```

For external Layer-4 access I expect something like:

```text
NAME    TYPE           CLUSTER-IP      EXTERNAL-IP
web     LoadBalancer   10.0.100.20     20.50.10.30
```

If:

```text
EXTERNAL-IP = <pending>
```

I investigate Azure provisioning:

```text
AKS identity permissions
public IP availability
Load Balancer configuration
Azure quota
service annotations
events
```

Then:

```bash
kubectl describe svc web
```

and inspect Events.

---

### **2. Confirm it isn't intentionally internal**

If the Service has an annotation requesting an **internal Azure Load Balancer**, then the “external” IP may actually be:

```text
10.x.x.x
```

and internet clients should not be able to reach it.

An internal Load Balancer is only reachable from networks with private connectivity to that VNet. ([Microsoft Learn][8])

So:

```text
10.x LoadBalancer frontend
+
internet client
=
expected failure
```

not necessarily a fault.

---

### **3. Test the external IP directly**

From an external client:

```bash
curl -v -m 5 http://<external-ip>:<service-port>
```

Microsoft recommends testing the LoadBalancer IP directly to determine whether the failure exists between Azure networking and the Kubernetes service. ([Microsoft Learn][7])

If TCP cannot establish:

```text
timeout
```

I focus on:

```text
Azure Load Balancer
NSG
health probe
UDR/firewall
```

rather than the application.

---

### **4. Check Azure Load Balancer health probes**

A very common cause is:

```text
Pods work internally ✅
but Azure LB marks nodes unhealthy ❌
```

Then:

```text
External request
      ↓
Load Balancer
      ↓
No healthy backend
      ↓
timeout/failure
```

I inspect:

```text
health probe port
health probe path
externalTrafficPolicy
node health
```

Health-probe failures cause Azure Load Balancer to remove backends from rotation. ([Microsoft Learn][9])

---

### **5. Check `externalTrafficPolicy`**

A Service may use:

```yaml
externalTrafficPolicy: Local
```

This preserves client source IP and only sends external traffic to nodes that have local Service endpoints.

That changes probe/routing behavior.

For example:

```text
LB
 ↓
Node-1 → Pod exists ✅
Node-2 → no local Pod
```

If health probing is incorrectly configured, the Load Balancer may consider valid paths unhealthy.

This is especially relevant with custom probe settings or specialized Private Link/proxy configurations. ([Microsoft Learn][10])

---

### **6. Check NSGs**

Microsoft explicitly calls out custom NSGs as a frequent cause of AKS applications timing out externally even when Pods are running correctly. ([Microsoft Learn][7])

I inspect inbound rules on:

```text
AKS subnet
node NIC/subnet path
```

and verify required traffic from the Azure Load Balancer/client is allowed.

Think:

```text
Load Balancer frontend ✅
Service ✅
Pod ✅

NSG deny ❌
```

→ still inaccessible.

---

### **7. Check UDR / Azure Firewall for asymmetric routing**

This is an excellent interview-level diagnosis.

Suppose inbound flow is:

```text
Internet
  ↓
Azure Load Balancer
  ↓
AKS node
```

but the node's default route is:

```text
0.0.0.0/0
→ Azure Firewall
```

Then the reply might go:

```text
AKS node
  ↓
Azure Firewall
  ↓
Internet
```

instead of returning through the expected Load Balancer path.

Result:

```text
asymmetric routing
→ connection resets/timeouts
```

Microsoft specifically documents forced tunneling/UDR return-path asymmetry as a cause of external AKS connectivity failure. ([Microsoft Learn][7])

So I inspect:

```text
effective routes
0.0.0.0/0
firewall/NVA path
return-path symmetry
```

---

### **8. If using ingress, troubleshoot one layer higher**

If architecture is:

```text
Internet
 ↓
Application Gateway / ingress controller
 ↓
ClusterIP Service
 ↓
Pods
```

then I inspect:

```bash
kubectl get ingress -A
kubectl describe ingress <name>
kubectl get svc
kubectl get endpoints
```

and verify:

```text
DNS
listener
certificate
host/path rule
ingress controller health
backend health
NSG/firewall
```

Internal Service success doesn't automatically prove the ingress configuration is correct.

---

### **9. Verify Service endpoints anyway**

Even though internal access works, I quickly verify:

```bash
kubectl get endpoints <service>
```

or modern EndpointSlices:

```bash
kubectl get endpointslice
```

Microsoft's AKS networking guidance recommends validating Service selectors/endpoints when isolating application connectivity problems. ([Microsoft Learn][11])

Expected:

```text
web-service
→ 10.x.x.5:8080
→ 10.x.x.6:8080
```

If empty:

```text
Service selector mismatch
```

although that would normally break internal access too.

---

### **10. Use the symptom to narrow the layer**

```text
ClusterIP works
LoadBalancer IP fails
→ Azure LB / NSG / health probe / route

LoadBalancer IP works
DNS name fails
→ DNS

Public IP connects but HTTP 404
→ ingress host/path routing

Timeout
→ network/probe/routing

502
→ ingress/gateway unable to reach healthy backend

Works intermittently
→ unhealthy subset of nodes / probes / asymmetric routing
```

### **Strong troubleshooting sequence**

```text
1. kubectl get svc
2. Confirm public vs internal frontend
3. kubectl describe svc → Events
4. Test External-IP directly
5. Check Azure LB health probe
6. Check externalTrafficPolicy
7. Check NSGs
8. Check UDR / Azure Firewall / return path
9. If ingress, inspect listener/routing/backend health
10. Verify endpoints and controller logs
```

**Interview answer condensed:**

> “Since the Service works internally, I'd focus on the external path. I'd verify it's actually a public `LoadBalancer` service, inspect its external IP and Service events, test that IP directly, then check Azure Load Balancer health probes, `externalTrafficPolicy`, NSGs, and UDR/firewall return routing. If there's an ingress layer, I'd additionally check its listener, host/path rules, certificates, and backend health. A forced-tunneling UDR causing asymmetric return traffic is an important Azure-specific possibility.”

**Memory line:**
**Internal works, external fails → move outward: Service → Load Balancer/Ingress → probe → NSG → route.**

**Interview trap:**
Don't start by redeploying the application when:

```text
ClusterIP access works perfectly.
```

That evidence strongly suggests the failure is more likely in the **external exposure/networking layer**.

**Keywords:** LoadBalancer Service, External IP, health probe, NSG, UDR, `externalTrafficPolicy`, asymmetric routing, ingress

**Likely follow-ups:**

* What if `EXTERNAL-IP` stays Pending?
* How can a UDR break inbound traffic?
* What does `externalTrafficPolicy: Local` change?
* What if LoadBalancer IP works but the DNS hostname doesn't?
