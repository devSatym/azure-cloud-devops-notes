# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Easy

### **T07-E01. What is Azure Kubernetes Service?**

**Answer:**
Azure Kubernetes Service, or **AKS**, is Microsoft's managed Kubernetes service for deploying, scaling, and operating containerized applications.

The key idea is that Microsoft manages much of the Kubernetes platform—especially the **control plane**—while I focus primarily on my workloads, node configuration, networking, security, and application operations.

```text
                    AKS Cluster
                        │
          ┌─────────────┴─────────────┐
          ↓                           ↓
   Control Plane                 Worker Nodes
   Azure managed                Run workloads
          │                           │
   API Server                     kubelet
   Scheduler                      container runtime
   Controllers                    application Pods
   etcd
```

AKS currently offers **Standard** and **Automatic** operating modes. Standard provides more direct infrastructure/node-pool control, while Automatic manages more node management, scaling, security, monitoring, and upgrade decisions for you. ([Microsoft Learn][1])

### **Why use AKS instead of self-managing Kubernetes?**

Without AKS, I might need to operate:

```text
Control-plane VMs
API server
etcd
Controller Manager
Scheduler
HA configuration
Control-plane patching
```

With AKS, Microsoft manages the control-plane infrastructure.

I still use normal Kubernetes concepts such as:

```text
Deployment
Service
Pod
ConfigMap
Secret
Ingress
Namespace
HPA
PersistentVolume
```

So AKS is still Kubernetes—it just reduces the infrastructure-management burden.

### **Example**

Suppose I have:

```text
Frontend
Product service
Cart service
Payment service
```

I could deploy them as containers:

```text
Azure Container Registry
        ↓
       AKS
        │
        ├── frontend Deployment
        ├── product Deployment
        ├── cart Deployment
        └── payment Deployment
```

Kubernetes then handles:

* scheduling,
* service discovery,
* self-healing,
* rolling deployments,
* scaling.

Azure adds integration with services such as:

```text
ACR
Microsoft Entra ID
Managed Identity / Workload Identity
Azure Monitor
Azure Load Balancer
Application Gateway
Azure networking
```

### **What AKS does NOT mean**

Managed Kubernetes does **not** mean:

> Microsoft runs my entire application for me.

In AKS Standard, I still have significant responsibility for areas such as:

```text
Workloads
resource requests/limits
node pools
cluster upgrades/configuration
network design
RBAC
NetworkPolicies
secrets
application security
monitoring
```

Microsoft manages the Kubernetes control plane, while responsibility for workloads and substantial cluster configuration remains with the customer. ([Microsoft Learn][1])

**Memory line:**
**AKS = Kubernetes where Azure manages the control plane and integrates it with Azure services.**

**Interview trap:**
Don't say:

> “AKS is serverless Kubernetes.”

AKS still normally has worker compute underneath. The level of node-management responsibility depends on whether you're using **AKS Standard or AKS Automatic**.

**Keywords:** AKS, managed Kubernetes, control plane, worker nodes, containers, orchestration

---

### **T07-E02. Which Kubernetes components are managed by Microsoft in AKS?**

**Answer:**
The most important interview answer is that **Microsoft manages the AKS control plane**.

That includes core Kubernetes control-plane functionality such as:

```text
API Server
Scheduler
Controller Manager
etcd / control-plane data store
```

The control plane decides **what should run and where**, while worker nodes actually execute the Pods.

Microsoft's current AKS support policy describes the control plane and AKS-managed system components as Microsoft-operated, while node and workload operations remain a shared/customer responsibility depending on the AKS mode. ([Microsoft Learn][2])

### **Architecture**

```text
                 Microsoft-managed
              ┌─────────────────────┐
              │     Control Plane   │
              │                     │
kubectl ─────→│ API Server          │
              │ Scheduler           │
              │ Controller Manager  │
              │ etcd                │
              └──────────┬──────────┘
                         │
                         ↓
             Customer workload layer
              ┌─────────────────────┐
              │ Worker Nodes        │
              │                     │
              │ kubelet             │
              │ container runtime   │
              │ Pods                │
              └─────────────────────┘
```

### **What each component does**

**API Server**

The entry point for the Kubernetes API.

```bash
kubectl get pods
```

communicates with the API server.

---

**etcd**

Stores Kubernetes cluster state such as:

```text
Deployments
Services
ConfigMaps
cluster metadata
desired state
```

AKS manages this control-plane data store rather than making me operate an etcd cluster myself.

---

**Scheduler**

Determines which node should run a new Pod.

For example:

```text
New Pod
   ↓
Scheduler
   ↓
Check:
CPU/memory
taints/tolerations
affinity
node selectors
   ↓
Choose Node-2
```

---

**Controller Manager**

Runs controllers that continuously reconcile:

```text
Desired state
vs
Actual state
```

For example:

```text
Deployment says replicas = 3

Actual Pods = 2

Controller
   ↓
Create another Pod
```

### **What do I still manage?**

Especially in **AKS Standard**, I remain responsible for important parts of:

* workload manifests,
* node-pool design,
* scaling configuration,
* node OS/update strategy,
* Kubernetes RBAC,
* network policies,
* application security,
* application monitoring.

AKS Automatic shifts more node-management responsibility to Azure than Standard does. ([Microsoft Learn][1])

**Memory line:**
**Azure manages the Kubernetes brain; worker nodes run your workloads.**

**Interview trap:**
Avoid saying:

> “Microsoft manages everything in AKS.”

AKS is a **shared-responsibility managed Kubernetes service**, especially in Standard mode.

**Keywords:** API Server, etcd, Scheduler, Controller Manager, control plane, managed Kubernetes

### **T07-E03. What is an AKS node pool?**

**Answer:**
An AKS node pool is a **group of worker nodes with the same basic configuration**, such as VM size, operating system, scaling configuration, and Kubernetes role.

The nodes in the pool provide compute capacity for Pods.

```text
AKS Cluster
│
├── Node Pool: system
│   ├── Node-1
│   ├── Node-2
│   └── Node-3
│
└── Node Pool: apps
    ├── Node-4
    ├── Node-5
    └── Node-6
```

Each node underneath is essentially Azure VM-based compute managed as part of AKS.

### **Why have multiple node pools?**

Because different workloads may need different compute characteristics.

For example:

```text
systempool
Standard_D4s_v5
        ↓
Kubernetes system workloads

webpool
Standard_D4s_v5
        ↓
Web/API applications

gpupool
GPU VM SKU
        ↓
ML workloads
```

This lets me separate workloads based on:

* VM size,
* OS,
* CPU/memory requirements,
* GPU requirements,
* scaling requirements,
* workload criticality,
* Spot vs regular capacity.

### **Scheduling workloads onto specific pools**

AKS node pools create labels that Kubernetes can use for scheduling.

I can also apply my own labels/taints.

For example:

```text
GPU Pool
label:
workload=gpu
```

Then:

```yaml
nodeSelector:
  workload: gpu
```

helps ensure the Pod runs on the appropriate nodes.

Similarly, taints and tolerations can prevent ordinary workloads from accidentally landing on specialized pools.

### **Autoscaling**

Different node pools can scale independently.

For example:

```text
System Pool
Min 3
Max 5

Application Pool
Min 2
Max 20

Batch Spot Pool
Min 0
Max 50
```

This is useful because the application pool can grow with traffic without unnecessarily increasing expensive specialized nodes.

### **Windows and Linux**

AKS can have different OS node pools where supported:

```text
Linux system pool
        +
Linux user pool
        +
Windows user pool
```

However, the cluster requires a Linux system node pool; Windows nodes are added as user pools. ([Microsoft Learn][3])

**Memory line:**
**Node pool = a group of similar AKS worker nodes used to run particular workloads.**

**Interview trap:**
A node pool is **not a Kubernetes namespace**.

```text
Node pool
→ compute separation

Namespace
→ logical Kubernetes resource separation
```

**Keywords:** node pool, worker node, VM size, autoscaling, labels, taints, Linux, Windows

### **T07-E04. What is the difference between system and user node pools?**

**Answer:**
A **system node pool** is intended primarily for critical Kubernetes and AKS system Pods, while a **user node pool** is intended primarily for my application workloads.

The clean production architecture is:

```text
AKS
│
├── System Node Pool
│   ├── CoreDNS
│   ├── metrics/system agents
│   └── critical AKS/Kubernetes components
│
└── User Node Pool
    ├── frontend
    ├── API
    ├── worker
    └── application Pods
```

Microsoft recommends separating critical system workloads from application workloads using dedicated system and user node pools. ([Microsoft Learn][4])

### **System node pool**

A system pool has:

```text
mode = System
```

AKS labels those nodes:

```text
kubernetes.azure.com/mode=system
```

which causes AKS to prefer them for system Pods. ([Microsoft Learn][5])

Important current requirements include:

```text
OS = Linux

Minimum nodes = 2
Recommended = 3

Minimum supported VM capability:
at least 4 vCPU and 4 GB memory

B-series VM = not supported
```

for Standard AKS system pools. ([Microsoft Learn][4])

### **User node pool**

A user pool has:

```text
mode = User
```

and is where I normally schedule:

```text
frontend
backend APIs
workers
batch jobs
business applications
```

User pools can have:

```text
0 or more nodes
```

which is useful for workloads that can scale down completely. ([Microsoft Learn][3])

They can also use:

* different VM sizes,
* Linux or Windows,
* autoscaling,
* Spot instances,
* workload-specific labels/taints.

### **Very important scheduling detail**

The `System` mode does **not automatically guarantee** application Pods can never run there.

If I want a dedicated system pool, Microsoft recommends adding:

```text
CriticalAddonsOnly=true:NoSchedule
```

as a taint.

Then:

```text
Application Pod
      ↓
System Pool
      ↓
No matching toleration
      ↓
Not scheduled ❌
```

while system components with the appropriate toleration can run there. ([Microsoft Learn][5])

### **Production example**

I might design:

```text
AKS
│
├── systempool
│   ├── 3 × D-series VMs
│   ├── mode=System
│   └── CriticalAddonsOnly taint
│
├── apppool
│   ├── 3–20 × D-series
│   ├── mode=User
│   └── regular application workloads
│
└── spotpool
    ├── 0–20 nodes
    ├── mode=User
    └── interruptible batch workloads
```

This separates critical Kubernetes components from unpredictable application workloads.

### **Why separation matters**

Imagine a badly configured application suddenly consumes:

```text
100% CPU
100% memory
```

If application workloads share the same capacity as:

```text
CoreDNS
critical system agents
```

they can potentially create cluster instability.

Separating pools protects important system capacity.

### **Quick comparison**

| Area                              | System pool          | User pool        |
| --------------------------------- | -------------------- | ---------------- |
| Main purpose                      | Critical system Pods | Application Pods |
| Mode                              | `System`             | `User`           |
| OS                                | Linux                | Linux or Windows |
| Minimum node count                | 2                    | Can be 0         |
| Spot supported                    | No                   | Yes              |
| Recommended application placement | Avoid when dedicated | Yes              |
| Can use autoscaling               | Yes                  | Yes              |

### **Current AKS Automatic caveat**

With **AKS Automatic**, Microsoft manages the system nodes and much more of node provisioning automatically, so you don't manage system pools in the same way as traditional AKS Standard clusters. ([Microsoft Learn][6])

**Memory line:**
**System pool runs the cluster; user pools run the business workloads.**

**Interview trap:**
Don't say:

> “Application Pods technically cannot run on a system node pool.”

The `System` label makes AKS **prefer** that pool for system Pods. If strict isolation is required, use the appropriate taint such as:

```text
CriticalAddonsOnly=true:NoSchedule
```

**Keywords:** System pool, User pool, `CriticalAddonsOnly`, taints, CoreDNS, workload isolation, AKS node pools
