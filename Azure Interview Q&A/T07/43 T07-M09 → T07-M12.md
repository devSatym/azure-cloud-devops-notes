# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Medium

### **T07-M09. How does Entra ID integrate with AKS authentication?**

**Answer:**
Microsoft Entra ID can be integrated with AKS so that **users, groups, and service principals authenticate to the Kubernetes API using their Entra identities instead of separate Kubernetes usernames/passwords or long-lived client certificates**.

The flow is:

```text
Engineer
   ↓
Microsoft Entra ID login
   ↓
Entra access token
   ↓
AKS API Server
   ↓
Authentication succeeds
   ↓
Authorization check
```

Microsoft recommends Entra ID for Kubernetes API authentication in AKS. After authentication, authorization can be handled either by native Kubernetes RBAC or by Azure RBAC for Kubernetes authorization. ([Microsoft Learn][1])

### **Example**

Suppose I run:

```bash
az aks get-credentials \
  --resource-group rg-prod \
  --name aks-prod
```

and then:

```bash
kubectl get pods
```

For an Entra-integrated cluster, `kubectl` can use an Entra authentication flow, commonly through `kubelogin`.

Conceptually:

```text
kubectl
  ↓
kubelogin
  ↓
Microsoft Entra ID
  ↓
Token
  ↓
AKS API Server
```

So access is tied to my corporate identity.

### **Why is this better?**

Instead of manually maintaining:

```text
user certificates
static credentials
shared kubeconfigs
```

I can use:

```text
Microsoft Entra users
Microsoft Entra groups
Conditional Access / identity governance
central user lifecycle
```

For example:

```text
Entra Group:
aks-prod-readers
```

can be mapped to read permissions in the cluster.

When an employee leaves the company:

```text
Disable/remove Entra account
        ↓
Cluster authentication removed
```

rather than hunting down manually issued Kubernetes credentials.

---

### **Authentication is NOT authorization**

This is one of the most important AKS identity distinctions.

Entra answers:

> **Who are you?**

Then another mechanism answers:

> **What are you allowed to do?**

For example:

```text
Satyam authenticates with Entra ✅
             ↓
Authorization check
             ↓
Can list Pods? ✅
Can delete Namespace? ❌
```

AKS supports two major authorization approaches after Entra authentication:

```text
Option 1
Microsoft Entra authentication
        +
Kubernetes RBAC

Option 2
Microsoft Entra authentication
        +
Azure RBAC for Kubernetes authorization
```

([Microsoft Learn][1])

### **Entra + Kubernetes RBAC**

For example:

```yaml
kind: RoleBinding
subjects:
  - kind: Group
    name: <Entra-group-object-id>
roleRef:
  kind: Role
  name: namespace-reader
```

Then:

```text
Entra Group
   ↓
Kubernetes RoleBinding
   ↓
Role / ClusterRole
   ↓
Kubernetes permissions
```

Permissions live inside Kubernetes.

### **Entra + Azure RBAC**

Alternatively:

```text
Entra User / Group
        ↓
Azure role assignment
        ↓
Azure Kubernetes Service RBAC Reader
        ↓
Kubernetes API authorization
```

Permissions can then be centrally managed through Azure RBAC instead of managing all `RoleBindings` manually.

We'll cover that in **T07-M10**.

### **Production hardening**

For a production AKS cluster, I would normally:

```text
Enable Microsoft Entra integration
        +
use groups rather than individual assignments
        +
least-privilege RBAC
        +
disable local AKS accounts where appropriate
```

Microsoft currently recommends disabling local accounts in production where your operating model supports it. ([Microsoft Learn][1])

**Memory line:**
**Entra authenticates the human/service; RBAC decides what that identity can do in Kubernetes.**

**Interview trap:**
Don't say:

> “If someone can authenticate with Entra, they automatically have cluster access.”

Authentication only establishes identity.

They still need:

```text
Kubernetes RBAC
or
Azure RBAC for Kubernetes
```

to perform operations.

**Keywords:** Microsoft Entra ID, authentication, `kubelogin`, Kubernetes API, RBAC, identity

**Likely follow-ups:**

* Authentication vs authorization?
* Kubernetes RBAC vs Azure RBAC?
* Why disable local AKS accounts?
* How would you give an Entra group read-only namespace access?

### **T07-M10. How can Azure RBAC be integrated with AKS authorization?**

**Answer:**
AKS can use **Azure RBAC to authorize Kubernetes API operations**, allowing me to assign Kubernetes permissions to Microsoft Entra users, groups, and service principals through normal Azure role assignments.

The flow becomes:

```text
User
 ↓
Microsoft Entra authentication
 ↓
AKS API Server
 ↓
Azure RBAC authorization
 ↓
Allow / Deny Kubernetes operation
```

Microsoft's current AKS implementation uses Entra identities plus Azure role assignments to authorize access to standard Kubernetes API resources. ([Microsoft Learn][2])

### **Built-in AKS RBAC roles**

Common roles include:

```text
Azure Kubernetes Service RBAC Reader
Azure Kubernetes Service RBAC Writer
Azure Kubernetes Service RBAC Admin
Azure Kubernetes Service RBAC Cluster Admin
```

Conceptually:

```text
Developer Group
      ↓
AKS RBAC Writer
      ↓
Namespace: dev
```

while:

```text
Operations Group
      ↓
AKS RBAC Admin
      ↓
Namespace: production
```

This lets me manage Kubernetes access using familiar Azure IAM tooling.

### **Example**

Suppose developers should inspect but not modify production resources.

I could assign:

```text
Group:
aks-prod-readers

Role:
Azure Kubernetes Service RBAC Reader

Scope:
production namespace
```

Then:

```bash
kubectl get pods -n production
```

might succeed:

```text
✅
```

but:

```bash
kubectl delete deployment api -n production
```

would fail:

```text
Forbidden ❌
```

### **Azure RBAC vs Kubernetes RBAC**

This comparison is important.

#### Kubernetes RBAC

Permissions live as Kubernetes objects:

```text
Role
ClusterRole
RoleBinding
ClusterRoleBinding
```

Example:

```text
Entra Group
   ↓
RoleBinding
   ↓
Kubernetes Role
```

#### Azure RBAC for Kubernetes

Permissions live as Azure role assignments:

```text
Entra Group
   ↓
Azure RBAC role assignment
   ↓
AKS Kubernetes API permission
```

This is useful when an organization wants centralized Azure IAM governance across multiple clusters.

Microsoft currently describes Azure RBAC for Kubernetes as delegating Kubernetes API authorization through Azure role assignments. ([Microsoft Learn][1])

### **Don't confuse two different Azure RBAC layers**

This is a very common interview trap.

There is:

```text
Azure RBAC on the AKS RESOURCE
```

and:

```text
Azure RBAC for KUBERNETES authorization
```

They are not the same.

For example:

```text
Contributor on AKS resource
```

may allow someone to manage the Azure AKS resource itself.

That does **not automatically mean** they can:

```bash
kubectl delete pods
```

inside Kubernetes.

Likewise:

```text
AKS RBAC Reader
```

for Kubernetes API access doesn't necessarily give someone broad permission to modify the Azure AKS resource.

Think:

```text
Azure control plane
vs
Kubernetes data/API plane
```

### **AKS Automatic current behavior**

AKS Automatic clusters currently come preconfigured with **Azure RBAC for Kubernetes authorization** as part of their default security posture. ([Microsoft Learn][2])

**Memory line:**
**Azure RBAC for AKS = Entra identity + Azure role assignment → Kubernetes API permissions.**

**Interview trap:**
Don't confuse:

> `Contributor` on the AKS Azure resource

with:

> `Azure Kubernetes Service RBAC Writer/Admin`

for Kubernetes resources.

They're different authorization planes.

**Keywords:** Azure RBAC, AKS RBAC Reader, Writer, Admin, Entra ID, Kubernetes authorization

**Likely follow-ups:**

* Azure RBAC vs Kubernetes RBAC?
* Can you scope permissions to a namespace?
* Does Azure Contributor give `kubectl` admin access?
* Authentication vs authorization?

### **T07-M11. How do you pull private images from ACR into AKS?**

**Answer:**
For AKS, the preferred approach is to give the **AKS kubelet managed identity permission to pull images from Azure Container Registry**, rather than storing an ACR username/password as an `imagePullSecret`.

For a normal RBAC-based ACR:

```text
AKS kubelet identity
        ↓
AcrPull role
        ↓
Azure Container Registry
        ↓
Pull image
```

Microsoft's AKS-to-ACR integration assigns the required pull role to the managed identity associated with the AKS agent pool. ([Microsoft Learn][3])

### **Simple integration**

For an existing cluster:

```bash
az aks update \
  --resource-group rg-prod \
  --name aks-prod \
  --attach-acr myregistry
```

For a traditional RBAC-mode ACR, this typically assigns:

```text
AcrPull
```

to the AKS kubelet identity. ([Microsoft Learn][3])

Then my Deployment can simply reference:

```yaml
containers:
  - name: api
    image: myregistry.azurecr.io/api:v1
```

I don't need:

```yaml
imagePullSecrets:
  - name: acr-password
```

for the normal same-tenant managed-identity integration.

### **Who actually pulls the image?**

This is the important identity distinction.

The image is pulled by the **node's kubelet/container runtime**, so the relevant identity is normally:

```text
kubelet identity
```

not:

```text
cluster control-plane identity
```

and not:

```text
application Workload Identity
```

Conceptually:

```text
Pod scheduled
     ↓
Node kubelet sees image
     ↓
Kubelet managed identity
     ↓
Entra token
     ↓
ACR
     ↓
Pull image layers
```

### **ACR role: important 2026 nuance**

For a registry using normal:

```text
RBAC Registry Permissions
```

use:

```text
AcrPull
```

But if the registry uses:

```text
RBAC Registry + ABAC Repository Permissions
```

then the classic `AcrPull` role is **not honored** for repository data access.

Instead, use:

```text
Container Registry Repository Reader
```

and optionally:

```text
Container Registry Repository Catalog Lister
```

only if repository listing is also needed. Also, `az aks --attach-acr` does not support the ABAC-enabled configuration—you assign the appropriate repository role manually. ([Microsoft Learn][3])

That's a very useful current interview point.

### **If the Pod shows `ImagePullBackOff`**

I troubleshoot:

```text
1. Image name/tag correct?
2. ACR DNS resolves?
3. Node can reach ACR?
4. Correct kubelet identity?
5. AcrPull / Repository Reader assigned?
6. ACR firewall/private endpoint okay?
7. Repository/image actually exists?
```

Useful commands:

```bash
kubectl describe pod <pod>
```

Look for:

```text
ErrImagePull
ImagePullBackOff
401 Unauthorized
403 Forbidden
manifest unknown
```

Then inspect kubelet identity:

```bash
az aks show \
  -g rg-prod \
  -n aks-prod \
  --query identityProfile.kubeletidentity
```

Microsoft's current AKS diagnostics explicitly recommend checking the kubelet identity's ACR role assignment when image pulls fail. ([Microsoft Learn][4])

### **What about `imagePullSecret`?**

Kubernetes supports:

```text
imagePullSecrets
```

and they may be needed for:

* non-Azure registries,
* unusual cross-tenant scenarios,
* registries where managed-identity integration isn't available.

But for standard AKS → ACR integration:

```text
Managed Identity + Azure RBAC
```

is cleaner because it removes static registry credentials.

**Memory line:**
**AKS pulls ACR images using the kubelet identity—not the application's Workload Identity.**

**Interview trap:**
Don't say:

> “Give `AcrPull` to the AKS cluster identity.”

The standard AKS-ACR integration uses the **kubelet managed identity**.

And for an **ABAC-enabled ACR**, remember that `AcrPull` is replaced by the repository-reader role model.

**Keywords:** ACR, kubelet identity, `AcrPull`, `Container Registry Repository Reader`, `--attach-acr`, `ImagePullBackOff`

**Likely follow-ups:**

* Cluster identity vs kubelet identity?
* How would you troubleshoot `ImagePullBackOff`?
* When would `imagePullSecret` be required?
* What changes with an ABAC-enabled ACR?

### **T07-M12. How do you store secrets securely for AKS workloads?**

**Answer:**
For important application secrets, I prefer to keep the **authoritative secret outside Kubernetes in Azure Key Vault**, let the Pod authenticate using **AKS Workload Identity**, and retrieve or mount the secret using either the Azure SDK or the **Azure Key Vault Secrets Store CSI Driver**.

A strong architecture is:

```text
AKS Pod
   ↓
Kubernetes ServiceAccount
   ↓
Workload Identity / OIDC
   ↓
Microsoft Entra ID
   ↓
Azure Key Vault
   ↓
Secret
```

This avoids putting long-lived Azure credentials into Kubernetes manifests or Git repositories. ([Microsoft Learn][5])

### **Bad approach**

Never commit:

```yaml
env:
  - name: DB_PASSWORD
    value: "ProdPassword123!"
```

to:

```text
Git
Helm values
Terraform variables
Deployment YAML
```

That's an obvious secret leak.

Encoding it as:

```text
base64
```

inside a Kubernetes Secret doesn't make it encrypted by itself.

Base64 is encoding, not encryption.

---

### **Option 1 — Azure Key Vault + Workload Identity**

This is my preferred Azure-native pattern.

```text
Application Pod
      ↓
ServiceAccount
      ↓
OIDC federation
      ↓
Workload Identity
      ↓
Key Vault Secrets User
      ↓
Azure Key Vault
```

No:

```text
client secret
storage key
password for Key Vault authentication
```

needs to exist inside the Pod.

The workload receives short-lived Entra tokens instead.

### **Option 2 — Key Vault CSI Driver**

The Secrets Store CSI Driver allows Key Vault content to appear as files mounted into a Pod.

Conceptually:

```text
Azure Key Vault
      ↓
CSI Provider
      ↓
Pod volume
      ↓
/mnt/secrets-store/db-password
```

Microsoft's AKS Key Vault provider supports Workload Identity and uses a Kubernetes service-account token that is exchanged for an Entra token before retrieving Key Vault objects. ([Microsoft Learn][5])

The workload doesn't need to contain a Key Vault client secret.

### **Example**

Suppose Key Vault contains:

```text
secret:
prod-db-password
```

My Pod gets:

```text
/mnt/secrets-store/prod-db-password
```

and reads it as a mounted file.

This avoids putting the plaintext secret directly into the Deployment manifest.

### **Can CSI sync into a Kubernetes Secret?**

Yes, the Secrets Store CSI Driver can also be configured to synchronize mounted content into Kubernetes Secret objects when that integration is needed.

But from a security perspective, I prefer:

```text
Mount directly from Key Vault
```

when possible because copying it into a native Kubernetes Secret creates another location where the plaintext secret must be protected.

### **What about normal Kubernetes Secrets?**

Kubernetes Secrets are still valid for many use cases.

If I use them, I would ensure:

```text
Encryption at rest
RBAC restrictions
namespace isolation
no secrets in Git
no unnecessary read access
secret rotation
```

and potentially use GitOps-safe tooling such as an external secret-management workflow rather than committing plaintext secrets.

But for Azure-native sensitive credentials:

```text
Key Vault
+
Workload Identity
```

is generally the stronger pattern.

### **Key Vault permissions**

The workload should receive the smallest necessary role.

For reading Key Vault secrets with Azure RBAC:

```text
Key Vault Secrets User
```

may be appropriate.

For certificates or keys, permissions differ.

Microsoft's current CSI guidance explicitly distinguishes roles for secrets, keys, and certificates. ([Microsoft Learn][5])

### **Networking**

Just like Storage, identity and networking are separate.

A hardened architecture might be:

```text
AKS
 ↓
Private DNS
 ↓
Key Vault Private Endpoint
 ↓
Key Vault

Authentication:
Workload Identity
```

So:

```text
Private Endpoint
→ controls network path

Workload Identity + RBAC
→ controls who can retrieve the secret
```

### **Production model**

```text
Git
└── contains NO secret

Azure Key Vault
└── DB password

AKS Pod
├── ServiceAccount
├── Workload Identity
└── CSI mounted secret

Azure RBAC
└── Key Vault Secrets User
```

This gives:

```text
central secret storage
+
secretless Azure authentication
+
least privilege
+
rotation capability
```

**Memory line:**
**Keep the secret in Key Vault; give the Pod an identity, not another secret.**

**Interview trap:**
Don't say:

> “Kubernetes Secrets are secure because they're Base64 encoded.”

Base64 provides **no confidentiality**.

Also avoid solving secret management by putting a **Key Vault client secret inside Kubernetes** when Workload Identity can eliminate that credential entirely.

**Keywords:** Azure Key Vault, Workload Identity, Secrets Store CSI Driver, Kubernetes Secret, OIDC, least privilege

**Likely follow-ups:**

* Kubernetes Secret vs Key Vault?
* How does the CSI driver work?
* How do you rotate secrets?
* How would a private AKS cluster reach Key Vault?
