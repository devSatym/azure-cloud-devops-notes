# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Medium

### **T07-M01. How does AKS networking work?**

**Answer:**
AKS networking connects four main things:

```text
Pods ↔ Pods
Pods ↔ Kubernetes Services
Pods ↔ Azure/VNet resources
Pods ↔ Internet/external clients
```

AKS uses a **CNI networking model** to assign Pod IPs and route traffic, Kubernetes Services to provide stable access to dynamic Pods, CoreDNS for service discovery, and Azure networking components such as VNets, Load Balancers, NSGs, NAT Gateway, and firewalls for connectivity outside the cluster. ([Microsoft Learn][1])

### **1. Nodes are connected to an Azure VNet**

AKS worker nodes live in an Azure VNet subnet:

```text
Azure VNet
└── AKS Node Subnet
    ├── Node-1
    ├── Node-2
    └── Node-3
```

Pods run on those nodes.

How Pod addresses relate to the VNet depends on the networking model.

---

### **2. Pod networking can be Overlay or Flat**

Current AKS networking is mainly divided into:

```text
Azure CNI Overlay
        or
Azure CNI Flat networking
```

#### Overlay

```text
VNet:
10.0.0.0/16

Nodes:
10.0.1.x

Separate Pod CIDR:
192.168.0.0/16
```

Pods don't consume normal VNet addresses.

Traffic leaving the cluster is normally SNATed to the **node IP**. ([Microsoft Learn][1])

#### Flat networking

Pods receive addresses integrated with the Azure VNet.

```text
VNet
├── Nodes
└── Pods
```

This makes direct Pod connectivity from connected networks easier, but requires considerably more VNet IP planning. ([Microsoft Learn][1])

---

### **3. Pod-to-Pod communication**

Within Kubernetes:

```text
Frontend Pod
      ↓
Backend Pod
```

Pods communicate using their Pod networking.

Kubernetes expects Pods to be able to communicate without applications manually performing NAT between every Pod.

The CNI implementation handles the necessary networking.

---

### **4. Kubernetes Services provide stable endpoints**

Pods are temporary.

Today:

```text
api-pod-1 = 192.168.1.7
```

Tomorrow it might be:

```text
api-pod-2 = 192.168.2.14
```

Applications shouldn't depend on individual Pod IPs.

Instead:

```text
Frontend Pod
      ↓
api-service
      ↓
┌──────────────┐
│ API Pod 1    │
│ API Pod 2    │
│ API Pod 3    │
└──────────────┘
```

The Service gives a stable virtual IP/DNS name while the endpoints behind it can change.

---

### **5. DNS uses CoreDNS**

Suppose the frontend needs the backend:

```text
http://orders.default.svc.cluster.local
```

The flow is roughly:

```text
Frontend Pod
     ↓
CoreDNS
     ↓
orders Service IP
     ↓
orders Pods
```

AKS uses CoreDNS for Kubernetes service discovery. ([Microsoft Learn][2])

---

### **6. Inbound traffic**

For external traffic, I might expose workloads using:

```text
Service type LoadBalancer
```

for Layer-4 traffic:

```text
Internet
   ↓
Azure Load Balancer
   ↓
Kubernetes Service
   ↓
Pods
```

For HTTP/HTTPS workloads, I generally use an ingress/application-routing layer:

```text
Internet
   ↓
Application Gateway / ingress
   ↓
Host/path routing
   ↓
Kubernetes Services
   ↓
Pods
```

---

### **7. Outbound traffic**

Pods may need to reach:

```text
Azure APIs
Container registries
Databases
Internet APIs
```

Outbound architecture might use:

```text
AKS Pod
   ↓
Node/VNet
   ↓
Standard Load Balancer
or NAT Gateway
or Azure Firewall
   ↓
Destination
```

For Overlay specifically, traffic leaving the cluster is SNATed from the Pod address to the node IP before entering normal Azure networking. ([Microsoft Learn][3])

---

### **8. Security exists at different layers**

For nodes/subnets:

```text
NSG
```

For Pod-level east-west control:

```text
Kubernetes NetworkPolicy
```

For example:

```text
Frontend Pods
     ↓ allow 8080
Backend Pods

Other Pods
     ↓
DENY
```

Microsoft specifically distinguishes Azure NSGs for VNet/node-level control from Kubernetes network policies for Pod-level traffic filtering. ([Microsoft Learn][2])

### **Interview answer condensed**

> “AKS nodes connect to an Azure VNet, while the CNI plugin manages Pod addressing and routing. Pods communicate through the Kubernetes network, Services provide stable virtual endpoints, and CoreDNS provides service discovery. External traffic comes through services such as Azure Load Balancer or an ingress layer. For egress, traffic follows the configured Azure outbound path such as Load Balancer, NAT Gateway, or Firewall. The exact Pod-to-VNet behavior depends on whether I use Azure CNI Overlay or a flat Azure CNI model.”

**Memory line:**
**AKS networking = Pod IPs + Services + DNS + VNet ingress/egress.**

**Interview trap:**
Don't describe AKS networking as only:

> “Pods get IP addresses.”

Interviewers usually expect you to understand the full traffic path:

```text
Pod
Service
DNS
Node/VNet
Ingress
Egress
Network security
```

**Keywords:** Azure CNI, VNet, Pod IP, CoreDNS, Service, ingress, egress, NetworkPolicy

**Likely follow-ups:**

* Overlay vs flat Azure CNI?
* How does Pod-to-Pod traffic work?
* How does AKS access the internet?
* NSG vs NetworkPolicy?

### **T07-M02. What is Azure CNI Overlay?**

**Answer:**
Azure CNI Overlay is an AKS networking mode where **nodes receive normal Azure VNet IP addresses, but Pods receive IP addresses from a separate overlay Pod CIDR instead of consuming addresses from the VNet subnet**.

That makes it especially useful when VNet IP space is limited or the cluster needs to scale to many Pods. ([Microsoft Learn][1])

### **Example**

Suppose:

```text
Azure VNet
10.0.0.0/16

Node subnet
10.0.1.0/24
```

Nodes receive:

```text
Node-1 = 10.0.1.4
Node-2 = 10.0.1.5
```

But Pods can use:

```text
Pod CIDR
192.168.0.0/16

Pod-A = 192.168.1.5
Pod-B = 192.168.2.8
```

So:

```text
VNet IP space
→ primarily consumed by nodes

Overlay CIDR
→ consumed by Pods
```

### **Why is this useful?**

Imagine:

```text
100 nodes
×
100 Pods
=
10,000 Pods
```

With a flat model, potentially thousands of VNet addresses need to be planned.

Overlay lets those Pod addresses come from an independent address space.

Microsoft currently describes Azure CNI Overlay as the preferred option for many scenarios where **IP conservation and large cluster scale** matter. ([Microsoft Learn][1])

---

### **Pod-to-Pod traffic**

Pods can communicate directly across nodes through the Azure CNI Overlay data plane:

```text
Node-1
└── Pod-A
      │
      │ overlay networking
      ↓
Node-2
└── Pod-B
```

Applications don't need to know that the Pod addresses are overlay addresses. ([Microsoft Learn][3])

---

### **Traffic leaving the cluster**

This is one of the most important interview points.

Suppose:

```text
Pod:
192.168.1.5

Node:
10.0.1.4
```

The Pod calls:

```text
10.20.0.10
Azure database
```

With Overlay:

```text
Pod 192.168.1.5
      ↓
SNAT
      ↓
Node IP 10.0.1.4
      ↓
Azure network
      ↓
Destination
```

Microsoft states that traffic from an Overlay Pod to destinations outside the cluster is translated to the node's primary IP. ([Microsoft Learn][3])

### **Can an external VM directly connect to the Pod IP?**

Generally, no.

```text
External VM
   ↓
192.168.1.5 Pod IP
   ↓
Direct access ❌
```

The Pod overlay address isn't directly routable from ordinary networks outside the cluster.

To expose a workload, I use:

```text
Kubernetes Service
Ingress
Load Balancer
```

([Microsoft Learn][3])

---

### **Overlay vs flat CNI**

| Area                             | Azure CNI Overlay        | Flat Azure CNI            |
| -------------------------------- | ------------------------ | ------------------------- |
| Node IP                          | VNet                     | VNet                      |
| Pod IP                           | Separate Pod CIDR        | VNet-integrated address   |
| VNet IP consumption              | Lower                    | Higher                    |
| Direct external Pod reachability | No                       | Possible                  |
| Large-scale IP planning          | Easier                   | Requires more VNet space  |
| Outside-cluster source           | Usually node IP via SNAT | Pod IP can remain visible |

### **Current AKS default note**

As of current AKS behavior, when `--network-plugin` isn't explicitly specified, **Azure CNI Overlay is the default networking configuration for new clusters**. ([Microsoft Learn][4])

And legacy:

```text
kubenet
```

is scheduled for retirement on **March 31, 2028**, with Microsoft directing customers toward Azure CNI alternatives such as Overlay. ([Microsoft Learn][5])

**Memory line:**
**Overlay = VNet IPs for nodes, separate CIDR for Pods.**

**Interview trap:**
Do not say:

> “Overlay Pods have no Azure network connectivity.”

They absolutely can communicate externally. The key is that outside-cluster traffic is generally **SNATed to the node IP**, rather than exposing the Overlay Pod IP directly.

**Keywords:** Azure CNI Overlay, Pod CIDR, VNet IP conservation, SNAT, node IP, overlay network

**Likely follow-ups:**

* Azure CNI Overlay vs flat CNI?
* Can an on-prem VM directly reach an Overlay Pod?
* What source IP does an Azure resource see?
* Why is Overlay good for large clusters?

### **T07-M03. How do pods communicate with Azure resources?**

**Answer:**
Pods communicate with Azure resources through the AKS networking path, and then authenticate separately using an identity mechanism such as **AKS Workload Identity**.

I separate the problem into:

```text
1. Network connectivity
2. DNS
3. Authentication
4. Authorization
```

That separation is very useful both architecturally and while troubleshooting.

### **Example**

Suppose a Pod needs to access Azure Key Vault:

```text
AKS Pod
   ↓
Network path
   ↓
Key Vault endpoint
   ↓
Microsoft Entra token
   ↓
RBAC permission
   ↓
Secret returned
```

The fact that the Pod can reach Key Vault's IP doesn't automatically mean it has permission to retrieve a secret.

---

### **1. Network path depends on CNI model**

With Azure CNI Overlay:

```text
Pod IP
192.168.1.5
   ↓
SNAT
   ↓
Node IP
10.0.1.4
   ↓
Azure VNet
   ↓
Azure resource
```

So destinations outside the cluster normally see traffic originating from the node-side Azure networking path rather than the Pod overlay IP. ([Microsoft Learn][3])

With flat networking:

```text
Pod
10.0.2.10
   ↓
VNet routing
   ↓
Azure resource
```

the Pod IP itself is integrated with VNet networking and can be directly visible/routable where the network architecture allows. ([Microsoft Learn][1])

---

### **2. Public endpoint example**

Suppose a Pod accesses:

```text
Azure Storage public endpoint
```

Traffic might follow:

```text
Pod
 ↓
Node/VNet
 ↓
Configured egress
 ↓
Azure Storage public endpoint
```

The cluster might use:

```text
Standard Load Balancer
NAT Gateway
Azure Firewall
```

for outbound connectivity.

---

### **3. Private Endpoint example**

For production workloads, I may instead use:

```text
AKS Pod
   ↓
CoreDNS
   ↓
Private DNS
   ↓
10.20.5.4
Private Endpoint
   ↓
Storage / Key Vault
```

Then the service remains reachable privately through the VNet.

This requires three pieces to be correct:

```text
DNS
+
Routing/connectivity
+
Service firewall/private endpoint configuration
```

---

### **4. Authentication: use Workload Identity**

Networking gets the packet there.

Identity decides whether Azure accepts the request.

For example:

```text
Payment Pod
    ↓
Kubernetes ServiceAccount
    ↓
AKS Workload Identity
    ↓
Microsoft Entra ID
    ↓
OAuth token
    ↓
Key Vault
```

I would then grant that workload the minimum Azure role required.

For Blob Storage:

```text
Storage Blob Data Reader
```

For Key Vault:

```text
Key Vault Secrets User
```

depending on the workload requirement.

### **Avoid this**

```text
AKS Secret
   ↓
Storage Account Key
Client Secret
Password
```

where a secretless federated identity option is available.

### **5. DNS is critical**

Azure SDKs usually connect using hostnames such as:

```text
mystorage.blob.core.windows.net
```

or:

```text
myvault.vault.azure.net
```

For private endpoints, that DNS must resolve to the correct private endpoint address.

So if a Pod cannot reach an Azure resource, I might test:

```bash
kubectl exec -it <pod> -- nslookup myvault.vault.azure.net
```

then:

```bash
kubectl exec -it <pod> -- curl -v https://myvault.vault.azure.net
```

as appropriate.

### **Troubleshooting model**

If an AKS Pod can't access Blob Storage:

```text
Can DNS resolve it?
       ↓
Can network connect?
       ↓
Storage firewall/private endpoint okay?
       ↓
Can Pod get Entra token?
       ↓
Does identity have Storage RBAC?
```

This quickly separates:

```text
network error
```

from:

```text
identity error
```

### **Interview answer condensed**

> “Pods reach Azure resources through the configured AKS/VNet networking model. With CNI Overlay, traffic leaving the cluster is generally SNATed to the node IP; with flat CNI, Pod IPs are VNet integrated. For private services I usually use Private Endpoints and Private DNS. Connectivity and authorization are separate—I use AKS Workload Identity with Entra ID and Azure RBAC instead of storing long-lived credentials in Pods.”

**Memory line:**
**Pod → network path → Azure endpoint; Workload Identity → authorization.**

**Interview trap:**
Don't confuse:

```text
Private Endpoint
```

with:

```text
Managed Identity
```

Private Endpoint answers:

> **How does traffic reach the resource?**

Workload Identity answers:

> **Who is the Pod?**

You generally need both networking and identity configured correctly.

**Keywords:** AKS Pod, VNet, Azure CNI, SNAT, Private Endpoint, Workload Identity, Entra ID

**Likely follow-ups:**

* How would a Pod access Key Vault without a secret?
* What changes with Azure CNI Overlay?
* How do Private Endpoints work from AKS?
* How would you troubleshoot `403` vs connection timeout?

### **T07-M04. How does a Kubernetes LoadBalancer Service integrate with Azure?**

**Answer:**
When I create a Kubernetes Service with:

```yaml
type: LoadBalancer
```

AKS translates that Kubernetes intent into **Azure Load Balancer configuration**.

Conceptually:

```text
Kubernetes manifest
       ↓
Service type LoadBalancer
       ↓
AKS/Azure cloud integration
       ↓
Azure Load Balancer
       ↓
Frontend IP + rules + probes
       ↓
AKS nodes/services
       ↓
Pods
```

Microsoft's AKS networking documentation explicitly states that creating a Kubernetes load balancer causes Azure to configure the corresponding Azure Load Balancer resources. ([Microsoft Learn][2])

### **Example manifest**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
```

Kubernetes understands:

```text
Expose web externally on port 80
```

AKS then handles the Azure integration.

---

### **What Azure creates/configures**

Conceptually, Azure configures pieces such as:

```text
Frontend IP
       +
Backend association
       +
Load-balancing rule
       +
Health probe
```

Then:

```text
Internet
   ↓
Public IP
   ↓
Azure Load Balancer
   ↓
AKS traffic path
   ↓
web Service
   ↓
web Pods
```

The Kubernetes Service itself remains the abstraction developers interact with.

---

### **Service selects Pods**

The Service uses labels:

```yaml
selector:
  app: web
```

Suppose:

```text
Pod-1 → app=web
Pod-2 → app=web
Pod-3 → app=payments
```

Then the web Service targets:

```text
Pod-1
Pod-2
```

not the payments Pod.

So there are two layers:

```text
Azure Load Balancer
      ↓
Kubernetes Service
      ↓
Matching Pods
```

---

### **Public LoadBalancer**

Typical default design:

```text
Internet
   ↓
Public Azure Load Balancer
   ↓
AKS
```

Useful for:

```text
TCP/UDP service
Simple public endpoint
```

---

### **Internal LoadBalancer**

For private applications:

```text
Internal client
     ↓
Private IP
     ↓
Internal Azure Load Balancer
     ↓
AKS Service
     ↓
Pods
```

This keeps the frontend private within the VNet/connected network.

For example, a service annotation/configuration can request an internal Azure Load Balancer rather than a public one.

---

### **Why not create one LoadBalancer Service per HTTP microservice?**

Suppose I have:

```text
frontend
catalog
orders
payment
shipping
```

Creating:

```text
5 × Service type LoadBalancer
```

can result in unnecessary external load-balancing exposure and IP/resource complexity.

For HTTP/HTTPS microservices, I would usually prefer:

```text
One ingress/application-routing layer
           ↓
      /catalog
      /orders
      /payment
           ↓
Multiple ClusterIP Services
```

So:

```text
Layer 4 TCP/UDP
→ LoadBalancer Service

Multiple HTTP applications
→ Ingress/Gateway-style Layer 7 routing
```

---

### **Health matters**

Azure needs health information to know whether backend paths are valid.

The overall concept is:

```text
Azure LB probe
      ↓
AKS node/service traffic path
      ↓
Healthy workload
```

If the required backend path becomes unhealthy, new load-balanced traffic should stop being sent through that unhealthy path.

### **Traffic flow at interview level**

You don't need to drown the interviewer in iptables/eBPF details unless asked.

A strong answer is:

```text
Client
   ↓
Azure Load Balancer frontend
   ↓
AKS Service
   ↓
eligible Pod endpoint
```

The exact internal implementation can vary with the Kubernetes networking/data-plane configuration.

### **Interview answer condensed**

> “When I create a Kubernetes Service of type LoadBalancer, AKS's Azure integration configures an Azure Load Balancer frontend, load-balancing rules, health probing, and the backend traffic path. The Kubernetes Service still selects Pods using labels. I can expose it publicly or create an internal Load Balancer for private traffic. For multiple HTTP services, I normally prefer an ingress or Gateway solution rather than creating a separate Layer-4 load balancer for every service.”

**Memory line:**
**Kubernetes says `type: LoadBalancer`; AKS turns that intent into Azure Load Balancer resources.**

**Interview trap:**
Do not say:

> “The Azure Load Balancer directly tracks every Pod IP in all AKS networking modes.”

The exact backend/data-plane path depends on the AKS networking configuration. The safer interview-level model is:

```text
Azure Load Balancer
→ AKS Service traffic path
→ Pods
```

**Keywords:** Service `LoadBalancer`, Azure Load Balancer, public IP, internal LB, health probe, Kubernetes Service

**Likely follow-ups:**

* Internal vs public LoadBalancer Service?
* LoadBalancer Service vs ingress?
* What happens when Pods scale?
* How does Azure know which backend is healthy?
