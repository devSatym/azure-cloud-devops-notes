# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Easy

### **T07-E05. What is an AKS cluster identity?**

**Answer:**
An **AKS cluster identity** is a Microsoft Entra managed identity that the **AKS control plane uses to interact with Azure resources on behalf of the cluster**.

Think of it as:

```text
AKS Control Plane
       ↓
Cluster Managed Identity
       ↓
Azure RBAC
       ↓
Azure resources
```

For example, the AKS control plane may need permissions to manage:

* Azure Load Balancer resources,
* AKS-managed public IPs,
* cluster autoscaling infrastructure,
* Azure Disk/File/Blob CSI operations,
* networking resources.

Microsoft currently creates a **system-assigned managed identity by default** for new AKS clusters, although you can also supply a user-assigned identity. ([Microsoft Learn][1])

### **Example**

Suppose AKS creates a Kubernetes service:

```yaml
type: LoadBalancer
```

AKS may need to create/configure Azure networking resources:

```text
Kubernetes Service
       ↓
AKS control plane
       ↓
Cluster identity
       ↓
Azure Resource Manager
       ↓
Azure Load Balancer / Public IP
```

The identity must have the Azure permissions required for that action.

### **Cluster identity vs kubelet identity**

This distinction is very interview-important.

```text
Cluster / control-plane identity
→ AKS control plane → Azure

Kubelet identity
→ AKS nodes/kubelet → Azure
```

A common kubelet use case is pulling container images from:

```text
Azure Container Registry
```

Microsoft explicitly distinguishes the control-plane identity from the kubelet identity. ([Microsoft Learn][1])

### **Cluster identity vs Workload Identity**

They're also different:

```text
Cluster Identity
AKS platform → Azure resources

Workload Identity
Pod/application → Azure resources
```

So if my application Pod needs Key Vault access, I shouldn't simply grant that permission to the whole AKS cluster identity.

I should normally use:

```text
AKS Workload Identity
+
least-privilege RBAC
```

**Memory line:**
**Cluster identity = AKS itself authenticating to Azure.**

**Interview trap:**
Don't confuse:

```text
Cluster identity
Kubelet identity
Workload identity
```

They solve three different identity problems.

**Keywords:** Managed Identity, AKS control plane, Azure RBAC, kubelet identity, cluster identity

### **T07-E06. What is Azure CNI?**

**Answer:**
Azure CNI is Azure's **Container Network Interface implementation for Kubernetes networking**. It handles things such as assigning Pod IP addresses and enabling communication between Pods, nodes, services, and external networks.

At a high level:

```text
Pod
 ↓
Azure CNI networking
 ↓
Node / VNet / other Pods / Azure services
```

CNI plugins in AKS handle Pod IP assignment, traffic routing, and Kubernetes service networking. ([Microsoft Learn][2])

### **Why does AKS need CNI?**

Kubernetes needs networking where Pods can communicate with each other.

For example:

```text
Frontend Pod
    ↓
API Pod
    ↓
Database / Azure service
```

Azure CNI integrates that Kubernetes networking with Azure's networking infrastructure.

### **Current Azure CNI models**

An important modern AKS distinction is between:

```text
Flat networking
```

and:

```text
Overlay networking
```

#### Flat model

In Azure CNI flat networking, Pods receive addresses integrated directly with Azure VNet networking.

Conceptually:

```text
VNet: 10.0.0.0/16

Nodes:
10.0.1.x

Pods:
10.0.2.x / VNet-related address space
```

This gives strong VNet integration, but Pod IP planning can consume a significant amount of VNet address space. ([Microsoft Learn][2])

#### Azure CNI Overlay

With Azure CNI Overlay:

```text
Nodes
→ VNet IPs

Pods
→ separate Pod CIDR
```

For example:

```text
VNet
10.0.0.0/16

Nodes
10.0.1.x

Pod CIDR
192.168.0.0/16
```

That conserves VNet IP addresses and simplifies large-cluster address planning. Microsoft currently recommends Azure CNI Overlay when VNet IP conservation is important. ([Microsoft Learn][3])

### **Very current AKS point**

`kubenet` is now considered a **legacy networking option** and is scheduled to retire on **March 31, 2028**. Microsoft recommends migrating toward Azure CNI options such as Azure CNI Overlay. ([Microsoft Learn][2])

**Memory line:**
**Azure CNI = networking that connects AKS Pods into Azure networking.**

**Interview trap:**
Don't define Azure CNI as simply:

> “Every Pod gets a VNet IP.”

That describes some **flat Azure CNI models**, but Azure CNI also supports **Overlay**, where Pods use a separate Pod CIDR.

**Keywords:** Azure CNI, Pod IP, VNet, Overlay, flat networking, IPAM

### **T07-E07. What is a Kubernetes Service of type `LoadBalancer` in AKS?**

**Answer:**
A Kubernetes Service of type `LoadBalancer` exposes an AKS workload through an **Azure Layer-4 Load Balancer**.

When I create:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
```

AKS integrates with Azure and provisions/configures an Azure Load Balancer so external traffic can reach the selected Pods. ([Microsoft Learn][4])

### **Traffic flow**

Conceptually:

```text
Internet
   ↓
Public IP
   ↓
Azure Load Balancer
   ↓
Kubernetes Service
   ↓
Pods
├── web-pod-1
├── web-pod-2
└── web-pod-3
```

The Azure Load Balancer works at:

```text
Layer 4
→ TCP / UDP
```

so it doesn't understand HTTP URL paths such as:

```text
/api/*
/images/*
```

([Microsoft Learn][4])

### **Public vs internal LoadBalancer Service**

By default, a `LoadBalancer` Service commonly exposes a public frontend.

But I can also configure an **internal Load Balancer**:

```text
VNet client
    ↓
Private IP
    ↓
Internal Azure Load Balancer
    ↓
AKS Pods
```

which is useful for internal applications. ([Microsoft Learn][5])

### **When would I use it?**

Good use cases include:

```text
TCP application
UDP application
Simple externally exposed service
```

For example:

```text
TCP 5432
custom TCP service
UDP service
```

For HTTP/HTTPS applications requiring:

```text
/api routing
TLS termination
WAF
multiple applications sharing one IP
```

I would usually consider a Layer-7 ingress solution instead. Microsoft's current AKS guidance recommends `LoadBalancer` Services for non-HTTP Layer-4 traffic and ingress mechanisms for HTTP-like workloads. ([Microsoft Learn][6])

**Memory line:**
**`Service type: LoadBalancer` = expose an AKS Service using Azure Layer-4 load balancing.**

**Interview trap:**
Do not confuse:

```text
Service type LoadBalancer
```

with:

```text
Ingress
```

`LoadBalancer` is primarily **Layer 4**.

Ingress provides **Layer-7 HTTP routing**.

**Keywords:** Kubernetes Service, LoadBalancer, Azure Load Balancer, public IP, internal LB, Layer 4

### **T07-E08. What is AKS Workload Identity?**

**Answer:**
AKS Workload Identity lets **Pods authenticate securely to Microsoft Entra-protected Azure resources without storing long-lived client secrets or storage keys inside Kubernetes**.

For example:

```text
AKS Pod
   ↓
Kubernetes ServiceAccount
   ↓
OIDC federation
   ↓
Microsoft Entra ID
   ↓
Azure Managed Identity
   ↓
Key Vault / Storage / Cosmos DB
```

Microsoft Entra Workload ID uses Kubernetes-native service-account tokens and federated identity to obtain Azure credentials for the workload. ([Microsoft Learn][7])

### **Example**

Suppose my payment application needs a secret from Key Vault.

Bad approach:

```yaml
env:
  - name: AZURE_CLIENT_SECRET
    value: "super-secret"
```

because now I have a long-lived credential stored somewhere in Kubernetes.

Instead:

```text
Payment Pod
     ↓
Kubernetes Service Account
     ↓
Workload Identity
     ↓
Microsoft Entra ID
     ↓
Key Vault Secrets User
     ↓
Azure Key Vault
```

No Azure client secret needs to be stored in the Pod.

### **How does it work?**

There are several pieces:

```text
AKS OIDC Issuer
      +
Kubernetes ServiceAccount
      +
Federated Identity Credential
      +
Microsoft Entra identity
```

The federated credential establishes trust between:

```text
AKS service account identity
        ↕
Microsoft Entra managed identity/app
```

Microsoft's current AKS setup explicitly enables the **OIDC issuer and Workload Identity**, then configures federation between a Kubernetes ServiceAccount and the Azure identity. ([Microsoft Learn][8])

### **Example identity mapping**

Suppose:

```text
Namespace:
payments

ServiceAccount:
payment-api
```

The federated subject looks conceptually like:

```text
system:serviceaccount:payments:payment-api
```

That specific Kubernetes identity can be trusted by the corresponding Entra identity.

So:

```text
payment-api Pod ✅
→ Key Vault

other Pod ❌
→ not automatically allowed
```

This gives much better workload-level isolation than giving broad Azure permissions to every AKS node.

### **Workload Identity vs cluster identity**

Remember this:

```text
Cluster Identity
AKS control plane → Azure

Kubelet Identity
Node/kubelet → Azure

Workload Identity
Application Pod → Azure
```

This distinction is one of the most valuable AKS identity concepts to know for interviews. ([Microsoft Learn][1])

### **Example with Blob Storage**

```text
AKS Pod
   ↓
Workload Identity
   ↓
Entra token
   ↓
Storage Blob Data Contributor
   ↓
Blob Storage
```

Instead of:

```text
Kubernetes Secret
   ↓
Storage Account Key ❌
```

### **Current AKS note**

In **AKS Automatic**, the OIDC issuer and Workload Identity capabilities are enabled as part of the preconfigured defaults. In AKS Standard, they're capabilities the operator configures as needed. ([Microsoft Learn][9])

**Memory line:**
**Workload Identity = Pod → Entra ID → Azure resource, without stored Azure secrets.**

**Interview trap:**
Do not say:

> “Workload Identity gives the Pod the node's managed identity.”

That's not the model.

It uses:

```text
Kubernetes ServiceAccount token
+
OIDC federation
+
Microsoft Entra identity
```

to give the **specific workload** an Azure identity.

**Keywords:** Workload Identity, OIDC, federation, ServiceAccount, Managed Identity, secretless authentication
