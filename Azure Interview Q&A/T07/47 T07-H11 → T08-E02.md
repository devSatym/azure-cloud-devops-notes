# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Hard

### **T07-H11. How would you troubleshoot an AKS DNS-resolution failure?**

**Answer:**
I would troubleshoot AKS DNS by first determining **where the failure occurs**—a single Pod, all Pods, one node, or the whole cluster—and whether the problem affects Kubernetes service names, external domains, or private Azure endpoints.

My troubleshooting flow is:

```text
Application Pod
      ↓
/etc/resolv.conf
      ↓
CoreDNS Service
      ↓
CoreDNS Pods
      ↓
Node/VNet DNS
      ↓
Azure DNS / Custom DNS
      ↓
Target DNS zone
```

Microsoft's current AKS guidance recommends isolating failures across the same layers: Pod, CoreDNS Service/Pods, nodes, and VNet/upstream DNS. ([Microsoft Learn][1])

### **1. Reproduce the failure from a Pod**

I start with:

```bash
kubectl exec -it <pod> -- nslookup kubernetes.default.svc.cluster.local
```

Then test an external name:

```bash
kubectl exec -it <pod> -- nslookup microsoft.com
```

And if the problem involves a private Azure resource:

```bash
kubectl exec -it <pod> -- nslookup mydb.database.windows.net
```

This gives me three useful categories:

```text
Internal Kubernetes name fails
→ CoreDNS/Kubernetes DNS problem

External name fails
→ upstream DNS/egress problem

Only private Azure name fails
→ Private DNS/link/forwarding problem
```

---

### **2. Inspect the Pod's DNS configuration**

Inside the Pod:

```bash
kubectl exec -it <pod> -- cat /etc/resolv.conf
```

Typically I expect the nameserver to point to the cluster DNS service.

I also inspect:

```text
search domains
nameserver
options such as ndots
```

because incorrect custom Pod DNS settings can cause unexpected resolution behavior.

For example, a workload using:

```yaml
dnsPolicy: None
```

with bad custom nameservers may completely bypass normal cluster DNS.

---

### **3. Check CoreDNS Pods**

```bash
kubectl get pods \
  -n kube-system \
  -l k8s-app=kube-dns
```

They should be:

```text
Running
Ready
```

Then:

```bash
kubectl top pods \
  -n kube-system \
  -l k8s-app=kube-dns
```

and:

```bash
kubectl logs \
  -n kube-system \
  -l k8s-app=kube-dns
```

Microsoft specifically recommends checking CoreDNS health, CPU/memory utilization, hosting nodes, and logs because overloaded CoreDNS instances can cause latency and intermittent timeouts. ([Microsoft Learn][1])

### **4. Check the CoreDNS Service**

CoreDNS Pods can be healthy while the Kubernetes Service path is broken.

I check:

```bash
kubectl get svc kube-dns -n kube-system
```

and:

```bash
kubectl get endpoints kube-dns -n kube-system
```

or:

```bash
kubectl get endpointslice -n kube-system
```

Conceptually:

```text
Client Pod
   ↓
kube-dns ClusterIP :53
   ↓
CoreDNS endpoints
```

If endpoints are missing or traffic can't reach them, Pods won't resolve names even though CoreDNS containers themselves may be running.

---

### **5. Compare direct CoreDNS and upstream resolution**

If necessary, I test progressively:

```text
Pod
 ↓
CoreDNS
 ↓
Upstream DNS
```

Suppose:

```text
Query through CoreDNS → fails
Query directly to upstream DNS → works
```

then:

```text
CoreDNS configuration/path
```

is the likely problem.

If both fail:

```text
upstream DNS/networking
```

becomes more likely.

Microsoft's AKS troubleshooting guidance specifically recommends testing each DNS layer rather than treating DNS as one black box. ([Microsoft Learn][1])

---

### **6. Check custom VNet DNS**

This is especially important in enterprise AKS environments.

Architecture may be:

```text
AKS
 ↓
CoreDNS
 ↓
Custom DNS Server
 ↓
Azure DNS / on-prem DNS
```

For example:

```text
10.0.0.4
10.0.0.5
```

might be domain controllers or Azure DNS Private Resolver endpoints.

I check whether the VNet actually has the expected DNS servers configured and whether those servers can resolve the requested domain.

A broken custom resolver can produce:

```text
All Pods experience external DNS failure
```

even when CoreDNS itself is healthy.

---

### **7. Private Endpoint DNS**

Suppose AKS needs:

```text
myvault.vault.azure.net
```

and Key Vault uses Private Endpoint.

Expected:

```text
myvault.vault.azure.net
        ↓
privatelink.vaultcore.azure.net
        ↓
10.x.x.x
```

If AKS instead gets a public IP:

```text
20.x.x.x
```

while public access is disabled, the application fails.

I check:

```text
Private DNS zone
A record
VNet link
hub-spoke DNS forwarding
Private DNS Resolver rules
```

Microsoft specifically lists missing Private DNS VNet links and incorrect custom DNS configuration among common AKS DNS causes. ([Microsoft Learn][1])

---

### **8. Check NetworkPolicy, NSG, firewall, and routing**

DNS needs network connectivity too.

The required path might be:

```text
Pod
 ↓ UDP/TCP 53
CoreDNS
 ↓ UDP/TCP 53
Upstream DNS
```

A Kubernetes NetworkPolicy could block:

```text
Pod → CoreDNS :53
```

while an NSG, firewall, or route could block:

```text
CoreDNS/node → upstream resolver
```

Microsoft's real-time AKS DNS troubleshooting documentation explicitly identifies NetworkPolicy, firewall, NSG, routing, and packet loss as possible causes of DNS timeouts. ([Microsoft Learn][1])

---

### **9. Distinguish `NXDOMAIN` from timeout**

This gives a useful clue.

```text
NXDOMAIN
→ DNS server replied:
   "name doesn't exist"

Timeout
→ query or response probably
   isn't making it through
```

So:

```text
NXDOMAIN
→ record/name/zone/forwarding configuration

timeout
→ connectivity/performance/firewall/CoreDNS
```

Not absolute, but an excellent initial diagnostic distinction.

---

### **10. Check for CoreDNS overload**

If DNS failures are intermittent:

```text
works
works
timeout
works
timeout
```

I investigate capacity:

```bash
kubectl top pods -n kube-system -l k8s-app=kube-dns
kubectl top nodes
```

Possible causes include:

```text
CoreDNS CPU starvation
node CPU pressure
node I/O throttling
very high DNS query volume
```

Microsoft specifically notes CoreDNS/node resource exhaustion as a source of DNS latency and intermittent failures. ([Microsoft Learn][1])

AKS also now supports **LocalDNS** configurations; AKS Automatic includes LocalDNS by default, while it is optional on AKS Standard. It can improve resilience and reduce pressure on CoreDNS/conntrack for high-DNS-volume workloads. ([Microsoft Learn][2])

---

### **Strong troubleshooting flow**

```text
1. nslookup from affected Pod
2. Test internal + external + private name
3. Check /etc/resolv.conf
4. Check CoreDNS Pods
5. Check kube-dns Service/endpoints
6. Check CoreDNS logs/resources
7. Test upstream resolver
8. Check VNet/custom DNS
9. Check Private DNS zones/VNet links
10. Check NetworkPolicy/NSG/firewall/routes
```

**Interview answer condensed:**

> “I first identify whether DNS fails for one Pod or cluster-wide and whether it affects Kubernetes, external, or private names. Then I test from the Pod, inspect `/etc/resolv.conf`, verify CoreDNS Pods and the kube-dns Service/endpoints, and test the upstream DNS resolver. If private endpoints are involved, I check Private DNS zones and VNet links. Finally, I check NetworkPolicies, NSGs, firewalls, routes, and CoreDNS resource pressure. `NXDOMAIN` usually points me toward DNS data/configuration, while timeouts make me investigate connectivity or performance.”

**Memory line:**
**AKS DNS: Pod → CoreDNS → upstream DNS → authoritative/private zone.**

**Interview trap:**
Don't immediately restart CoreDNS.

A healthy CoreDNS deployment cannot fix:

```text
missing Private DNS VNet link
broken custom DNS server
NetworkPolicy blocking UDP 53
bad upstream forwarding
```

**Keywords:** CoreDNS, kube-dns, `/etc/resolv.conf`, Private DNS, custom DNS, UDP/TCP 53, `NXDOMAIN`

**Likely follow-ups:**

* What if internal names work but external names don't?
* What if only Private Endpoint names fail?
* `NXDOMAIN` vs timeout?
* How can NetworkPolicy break DNS?

### **T07-H12. How would you handle a sudden traffic spike that requires both pod and node scaling?**

**Answer:**
I would use **HPA for workload scaling and Cluster Autoscaler for infrastructure scaling**, with enough baseline headroom so the cluster doesn't have to wait for brand-new nodes before it can absorb the initial spike.

The normal sequence is:

```text
Traffic spike
     ↓
CPU/RPS/queue metric rises
     ↓
HPA increases Pods
     ↓
Existing nodes fill
     ↓
New Pods become Pending
     ↓
Cluster Autoscaler adds nodes
     ↓
Scheduler places Pending Pods
```

### **1. HPA reacts at the application layer**

Suppose:

```text
API
replicas = 4
target CPU = 65%
```

Traffic spikes:

```text
CPU = 90%
```

HPA decides:

```text
4 Pods
 ↓
10 Pods
```

The important point is that HPA can make the scaling decision quickly, but Kubernetes still needs somewhere to schedule those Pods.

---

### **2. Existing capacity absorbs the first wave**

A good production cluster should ideally maintain some spare capacity:

```text
Node-1 → 70% allocated
Node-2 → 65%
Node-3 → 70%
```

rather than:

```text
Node-1 → 99%
Node-2 → 99%
Node-3 → 99%
```

Then when HPA creates new replicas:

```text
4 → 7 Pods
```

some can start immediately.

This is important because provisioning a new Azure VM/node takes longer than starting a Pod on an existing node.

---

### **3. Pending Pods trigger Cluster Autoscaler**

Once remaining capacity is exhausted:

```text
Pod-8 → Pending
Pod-9 → Pending
Pod-10 → Pending
```

with events like:

```text
FailedScheduling:
Insufficient cpu
```

Cluster Autoscaler evaluates whether adding a node would allow them to schedule.

Then:

```text
nodepool
3 nodes
 ↓
5 nodes
```

and the scheduler places the waiting Pods.

### **4. Configure sensible scaling boundaries**

Example:

```text
HPA
minReplicas = 4
maxReplicas = 40

Node pool
minNodes = 3
maxNodes = 15
```

I make sure both limits make sense together.

Bad design:

```text
HPA max = 100 Pods

Node pool max = 4 nodes
```

If four nodes can only run 20 Pods:

```text
remaining 80 → Pending
```

So application and infrastructure scaling limits need capacity planning.

---

### **5. Resource requests must be accurate**

Cluster Autoscaler and Kubernetes scheduling depend heavily on:

```yaml
resources:
  requests:
    cpu:
    memory:
```

If requests are unrealistically high:

```text
Pod requests 4 CPU
actually uses 500m
```

the scheduler may think the cluster is full far earlier than it really is.

If requests are far too low:

```text
Pod requests 100m
actually consumes 2 CPU
```

too many Pods may get packed onto a node, causing CPU starvation.

So good autoscaling starts with realistic requests.

---

### **6. Use better metrics where CPU isn't enough**

For web APIs:

```text
CPU
requests/sec
latency
```

may be useful.

For workers:

```text
queue depth
```

is often more meaningful.

Example:

```text
Azure Service Bus
10,000 queued messages
       ↓
KEDA/HPA
       ↓
2 workers → 30 workers
```

Then Cluster Autoscaler supplies nodes if those Pods cannot fit.

For event-driven workloads, KEDA can provide a more natural scaling signal than CPU.

---

### **7. Avoid putting every workload in one node pool**

For example:

```text
AKS
├── systempool
│
├── webpool
│   autoscale 3–15
│
└── batchpool
    autoscale 0–20
```

If the spike is in web traffic:

```text
webpool scales
```

without unnecessary growth of:

```text
system nodes
batch nodes
```

This also lets me use different VM sizes per workload.

---

### **8. Watch Azure-side constraints**

Cluster Autoscaler may request nodes but Azure may fail to supply them because of:

```text
Regional VM SKU shortage
subscription vCPU quota
subnet IP exhaustion
VMSS limits
Availability Zone capacity
```

So during an incident I would inspect:

```bash
kubectl describe pod <pending-pod>
kubectl get events -A --sort-by=.lastTimestamp
```

and AKS/node-pool scaling events.

If the node pool has reached:

```text
maxNodes
```

I may need to increase it if architecture and quotas permit.

---

### **9. Pre-scale for predictable spikes**

Autoscaling is reactive.

If I know a campaign starts at:

```text
20:00
```

and usually causes 10× traffic, I'd consider increasing baseline capacity before the event.

Conceptually:

```text
Normal
4 Pods / 3 nodes

Before event
10 Pods / 6 nodes

Traffic spike
↓
HPA + CA handle additional burst
```

This reduces cold-scale latency.

For predictable workloads:

```text
scheduled/pre-scaling
+
reactive autoscaling
```

is often better than purely reactive scaling.

---

### **10. Protect downstream dependencies**

Scaling:

```text
5 Pods → 50 Pods
```

can suddenly produce:

```text
10× DB connections
10× Redis requests
10× downstream API calls
```

If the database can only handle the original capacity:

```text
front end scales successfully
       ↓
database collapses
```

So I also monitor:

```text
DB connection pools
Storage throttling
API quotas
cache capacity
rate limits
```

### **11. Observe the full chain**

During the spike:

```text
Azure Monitor / Prometheus
      ↓
Pod CPU/RPS/latency
      ↓
HPA desired/current replicas
      ↓
Pending Pods
      ↓
node count
      ↓
Cluster Autoscaler
      ↓
application SLO
```

Useful:

```bash
kubectl get hpa -w
kubectl get pods -w
kubectl get nodes -w
```

### **Interview answer condensed:**

> “I'd use HPA to scale Pods based on demand and Cluster Autoscaler to add nodes when those new Pods become unschedulable. I'd keep some baseline node headroom because Pods can start much faster than Azure can provision new nodes. I'd make sure resource requests are accurate, HPA and node-pool maximums are aligned, and Azure quota/subnet capacity can support scale-out. For predictable spikes I'd pre-scale, and I'd also verify downstream services such as the database can handle the increased concurrency.”

**Memory line:**
**HPA handles demand; Cluster Autoscaler supplies capacity. Headroom handles the delay between them.**

**Interview trap:**
Don't assume HPA + Cluster Autoscaler means instant scaling.

```text
Pod creation
→ seconds

New Azure VM/node
→ significantly slower
```

For extreme spikes, baseline headroom or pre-scaling matters.

**Keywords:** HPA, Cluster Autoscaler, Pending Pods, headroom, requests, KEDA, capacity planning

**Likely follow-ups:**

* Why maintain spare capacity?
* What if Cluster Autoscaler reaches `maxNodes`?
* How would you scale based on queue depth?
* Can application autoscaling overload a database?

# 8. 🔴 M IMP — Azure DevOps & GitHub Actions CI/CD

## Easy

### **T08-E01. What is CI?**

**Answer:**
**Continuous Integration (CI)** is the practice of frequently integrating developers' code changes into a shared repository and automatically validating those changes through steps such as building, testing, linting, and security scanning.

Conceptually:

```text
Developer
   ↓
git push / Pull Request
   ↓
CI Pipeline
   ├── Build
   ├── Unit tests
   ├── Lint
   ├── Security scan
   └── Package/artifact
```

The main goal is to detect integration problems **early**, rather than waiting until many developers' changes have accumulated.

### **DevOps example**

Suppose I push an application change:

```text
GitHub
  ↓
GitHub Actions
  ↓
npm test
  ↓
docker build
  ↓
Trivy scan
  ↓
push image to ACR
```

That pipeline is performing CI.

### **Infrastructure example**

CI isn't only for application code.

For Terraform:

```text
Pull Request
   ↓
terraform fmt -check
   ↓
terraform validate
   ↓
tflint
   ↓
security scanning
   ↓
terraform plan
```

is also a CI workflow.

### **CI does not necessarily deploy to production**

That's an important distinction.

```text
CI
→ integrate and validate change

CD
→ deliver/deploy validated change
```

A CI pipeline might end after producing:

```text
Docker image
ZIP artifact
Helm chart
Terraform plan
```

**Memory line:**
**CI = every change is integrated and automatically validated early.**

**Interview trap:**
Don't define CI as:

> “Automatically deploying code to production.”

That's deployment, not the defining purpose of Continuous Integration.

**Keywords:** Continuous Integration, build, test, validation, pull request, artifact

### **T08-E02. What is Continuous Delivery?**

**Answer:**
**Continuous Delivery** means software changes are automatically built, tested, and prepared so that they are **always in a releasable state**, but production deployment can still require a manual approval or business decision.

The flow might be:

```text
Code commit
    ↓
Build
    ↓
Tests
    ↓
Security scans
    ↓
Package artifact
    ↓
Deploy staging
    ↓
Validation
    ↓
Manual approval
    ↓
Production
```

The key idea is:

> **Production is ready to deploy at any time, but the final release doesn't have to be automatic.**

### **Example**

Using GitHub Actions:

```text
Commit
 ↓
Build image
 ↓
Unit tests
 ↓
Trivy scan
 ↓
Push image to ACR
 ↓
Deploy to staging
 ↓
Smoke tests
 ↓
Production approval
 ↓
Deploy production
```

Everything up to the production decision can be automated.

### **Continuous Delivery vs Continuous Deployment**

This is the most important distinction:

```text
Continuous Delivery
→ production-ready automatically
→ production release may require approval

Continuous Deployment
→ every qualified change automatically
  goes to production
```

Example:

```text
DELIVERY

Tests pass
   ↓
Staging
   ↓
[Manual approval]
   ↓
Production
```

versus:

```text
DEPLOYMENT

Tests pass
   ↓
Production automatically
```

### **Why companies use Continuous Delivery**

It gives a balance between:

```text
automation
+
release control
```

which is useful when production releases require:

* change approval,
* maintenance windows,
* compliance checks,
* business coordination.

**Memory line:**
**Continuous Delivery = always production-ready, but production release can still be a conscious decision.**

**Interview trap:**
Don't say Continuous Delivery and Continuous Deployment are identical.

The usual interview distinction is:

```text
Delivery → manual production gate allowed
Deployment → production automatically
```

**Keywords:** Continuous Delivery, releasable state, automation, approval gate, staging, production
