# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Medium

### **T07-M13. How does the Key Vault CSI driver work with AKS?**

**Answer:**
The **Azure Key Vault Secrets Store CSI Driver** lets AKS Pods consume secrets, keys, and certificates from **Azure Key Vault as mounted files**, instead of storing the source secret directly in the Kubernetes manifest.

A strong modern design is:

```text
Azure Key Vault
      ↓
Azure Key Vault Provider
      ↓
Secrets Store CSI Driver
      ↓
CSI volume
      ↓
AKS Pod
/mnt/secrets-store/*
```

For authentication, I would normally combine it with **AKS Workload Identity** so the Pod can access Key Vault without a client secret. ([Microsoft Learn][1])

### **How the flow works**

Suppose my application needs:

```text
DB_PASSWORD
```

which is stored in Key Vault.

The Kubernetes side contains a:

```text
SecretProviderClass
```

that describes:

* which Key Vault to access,
* which objects to retrieve,
* which Azure identity to use,
* whether the object is a secret, key, or certificate.

Then the Pod references that `SecretProviderClass` through a CSI volume.

Conceptually:

```text
Pod starts
   ↓
CSI volume requested
   ↓
Secrets Store CSI Driver
   ↓
Azure Key Vault Provider
   ↓
Authenticate to Entra ID
   ↓
Read authorized Key Vault objects
   ↓
Mount them into Pod filesystem
```

With Workload Identity, the CSI flow uses the Pod's Kubernetes ServiceAccount token, exchanges it through the configured OIDC federation for a Microsoft Entra token, and uses that token to access Key Vault. ([Microsoft Learn][1])

### **Example structure**

A simplified `SecretProviderClass` looks conceptually like:

```yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass

metadata:
  name: app-kv
spec:
  provider: azure
  parameters:
    clientID: "<workload-identity-client-id>"
    keyvaultName: "kv-prod"
    objects: |
      array:
        - |
          objectName: db-password
          objectType: secret
```

Then the Pod mounts it:

```yaml
volumes:
  - name: secrets
    csi:
      driver: secrets-store.csi.k8s.io
      readOnly: true
      volumeAttributes:
        secretProviderClass: app-kv
```

Inside the container:

```text
/mnt/secrets-store/db-password
```

becomes available.

### **Important identity flow**

With Workload Identity:

```text
Pod
 ↓
Kubernetes ServiceAccount token
 ↓
AKS OIDC issuer
 ↓
Federated Identity Credential
 ↓
Microsoft Entra token
 ↓
Azure Key Vault
```

This is much better than:

```text
Pod
 ↓
client_id + client_secret stored in Kubernetes ❌
 ↓
Key Vault
```

because the workload doesn't need a long-lived Azure credential.

### **Key Vault RBAC still matters**

Workload Identity proves:

> Who is this workload?

Azure RBAC decides:

> What may it retrieve?

For example, if the Pod only needs secrets:

```text
Key Vault Secrets User
```

can be assigned at the appropriate scope.

For keys/certificates, the required roles differ. Microsoft's current CSI guidance specifically distinguishes the data-plane roles required for secrets versus keys/certificates. ([Microsoft Learn][1])

### **Can it sync into a Kubernetes Secret?**

Yes.

CSI-mounted content can optionally be synchronized into a normal Kubernetes Secret when an application requires the Kubernetes Secret API/environment-variable pattern.

Conceptually:

```text
Key Vault
   ↓
CSI Driver
   ├── Mounted file
   │
   └── Optional Kubernetes Secret
```

But from a security perspective, direct file mounting is attractive because copying the value into a Kubernetes Secret creates another persisted copy that must be protected.

### **Secret rotation**

Another benefit is secret rotation.

If:

```text
Key Vault secret version changes
```

the CSI provider can periodically refresh mounted content when automatic rotation is enabled.

However, there's an important application-design point:

```text
File updated
   ↓
Application must actually reload it
```

An application that reads the secret only once at startup might still require a Pod restart or application-specific reload mechanism.

### **Private AKS production architecture**

For a hardened environment:

```text
AKS Pod
   ↓
Workload Identity
   ↓
Private DNS
   ↓
Key Vault Private Endpoint
   ↓
Azure Key Vault
```

This gives two separate controls:

```text
Private Endpoint
→ network security

Workload Identity + RBAC
→ identity/authorization
```

Microsoft recommends Private Endpoint access to Key Vault for network-isolated AKS designs. ([Microsoft Learn][2])

### **Troubleshooting CSI failures**

If the Pod fails to mount:

```text
MountVolume.SetUp failed
```

I check:

```text
1. SecretProviderClass exists in correct namespace
2. Key Vault object name/type correct
3. ServiceAccount correct
4. Workload Identity label/config correct
5. Federated credential subject correct
6. Managed identity client ID correct
7. Key Vault RBAC correct
8. DNS/private endpoint connectivity works
9. CSI provider Pods are healthy
```

**Memory line:**
**Key Vault CSI = Key Vault secret → identity-authorized CSI mount → Pod filesystem.**

**Interview trap:**
Don't say:

> “CSI automatically puts all Key Vault secrets into Kubernetes.”

It only retrieves the specifically configured objects, using an identity that must have Key Vault permission.

**Keywords:** Key Vault, CSI Driver, `SecretProviderClass`, Workload Identity, OIDC, mounted secrets, rotation

**Likely follow-ups:**

* CSI driver vs native Kubernetes Secret?
* How does Workload Identity authenticate it?
* How does secret rotation work?
* What would cause `MountVolume.SetUp failed`?

### **T07-M14. How do AKS upgrades work?**

**Answer:**
An AKS upgrade usually involves upgrading the **managed Kubernetes control plane first and then upgrading/replacing worker nodes in each node pool**, while AKS drains workloads from old nodes and reschedules them onto upgraded capacity.

For production, the key concepts are:

```text
Control plane upgrade
        ↓
Node pool upgrade
        ↓
Surge node created
        ↓
Old node cordoned/drained
        ↓
Pods rescheduled
        ↓
Old node replaced
```

AKS provides controls such as `maxSurge`, Pod Disruption Budgets, maintenance windows, drain timeout, and node soak time to reduce workload disruption. ([Microsoft Learn][3])

### **1. Check available versions**

I first check:

```bash
az aks get-upgrades \
  --resource-group rg-prod \
  --name aks-prod
```

I don't blindly choose the newest possible version.

I check:

* supported upgrade path,
* deprecated Kubernetes APIs,
* ingress/controller compatibility,
* CSI drivers,
* Helm charts/operators,
* admission policies,
* application compatibility.

A cluster upgrade that succeeds technically can still break an application using a removed Kubernetes API.

### **2. Test in non-production first**

My upgrade path would normally be:

```text
Dev
 ↓
Staging
 ↓
Production
```

using the same:

* Kubernetes version,
* workloads,
* add-ons,
* policies,
* ingress,
* storage drivers

as closely as possible.

### **3. Control plane upgrade**

The managed AKS control plane is upgraded by Azure.

Conceptually:

```text
API Server
Scheduler
Controller Manager
etc.
   ↓
New supported Kubernetes version
```

Because the control plane is Microsoft-managed, I don't manually patch its VMs.

### **4. Node pool upgrade**

Worker nodes then need to move to a compatible version/image.

For a surge-based upgrade:

```text
Existing pool:
Node-1
Node-2
Node-3

       ↓

Temporary surge:
Node-1
Node-2
Node-3
Node-4-new

       ↓

Drain Node-1
       ↓
Pods → other/new nodes
       ↓
Replace/remove Node-1
```

Then AKS continues through the pool.

### **`maxSurge`**

`maxSurge` controls how many extra nodes may be temporarily created during the node-pool upgrade.

Example:

```text
10-node pool
maxSurge = 30%
```

allows roughly:

```text
3 additional upgrade nodes
```

to speed the rollout and preserve capacity.

Current Microsoft guidance for AKS Standard suggests tuning `maxSurge` in production and notes **33% as a general production recommendation**, though actual values should be chosen based on quota, subnet space, workload availability, and cost. ([Microsoft Learn][3])

### **5. Node draining**

Before replacing a node:

```text
Node
 ↓
cordon
 ↓
stop new Pods
 ↓
drain
 ↓
evict Pods
 ↓
scheduler places replacements elsewhere
```

This is why workload design matters enormously.

If the application has:

```text
1 replica
```

then draining its node can cause downtime.

If it has:

```text
3 replicas
+
anti-affinity/topology spreading
+
readiness probes
+
PDB
```

maintenance can be much safer.

### **6. Pod Disruption Budgets**

A PDB limits voluntary disruption.

For example:

```yaml
minAvailable: 2
```

for a three-replica Deployment means Kubernetes should preserve at least two available Pods while voluntarily draining nodes.

But a PDB can also **block an AKS upgrade** if configured too strictly.

For example:

```text
replicas = 1
minAvailable = 1
```

means:

```text
Drain Pod?
→ would violate PDB
→ node cannot drain
→ upgrade may stall
```

Microsoft specifically identifies restrictive PDBs as a major cause of AKS node-drain upgrade failures. ([Microsoft Learn][3])

### **7. Capacity and IP planning**

Surge nodes require real infrastructure capacity.

I check:

```text
VM quota
Regional SKU capacity
Subnet IP availability
Pod IP capacity
Disk constraints
```

before production upgrades.

For flat Azure CNI designs in particular, surge capacity can require significant extra subnet IP space. Microsoft explicitly notes subnet exhaustion as a common upgrade failure scenario. ([Microsoft Learn][3])

### **8. Maintenance windows / auto-upgrade**

AKS also supports managed upgrade channels and planned maintenance.

A production design might use:

```text
Maintenance window
→ Sunday 02:00–06:00

Auto-upgrade channel
→ selected according to risk policy
```

The goal is not merely automatic upgrades—the goal is **controlled, observable, tested upgrades**.

### **Strong production sequence**

```text
1. Review release notes / breaking APIs
2. Check supported upgrade path
3. Test in staging
4. Validate PDBs + replicas
5. Validate quota + subnet headroom
6. Configure maxSurge
7. Use maintenance window
8. Upgrade control plane/node pools
9. Monitor Pods and application
10. Run post-upgrade smoke tests
```

**Memory line:**
**AKS upgrade = upgrade platform, surge new nodes, drain old nodes, reschedule Pods safely.**

**Interview trap:**
Don't answer:

> “Azure upgrades AKS with no downtime automatically.”

Azure manages much of the mechanism, but **application availability depends on workload design**—replicas, PDBs, readiness, topology, capacity, and correct drain behavior.

**Keywords:** AKS upgrade, control plane, node pools, `maxSurge`, drain, PDB, maintenance window

**Likely follow-ups:**

* What is `maxSurge`?
* How can a PDB block an upgrade?
* How would you achieve zero/minimal downtime?
* Why can subnet exhaustion break upgrades?

# Hard

### **T07-H01. An AKS pod remains in `Pending`; how would you troubleshoot it?**

**Answer:**
For a `Pending` Pod, I start with the Kubernetes scheduler because `Pending` usually means **the Pod exists, but Kubernetes hasn't been able to schedule it onto a suitable node yet**, although storage and other setup conditions can also contribute.

My first command is:

```bash
kubectl describe pod <pod> -n <namespace>
```

and I read the **Events** section before changing anything.

My troubleshooting order is:

```text
Pending Pod
    ↓
FailedScheduling event
    ↓
Resources?
    ↓
Taints / selectors / affinity?
    ↓
Storage?
    ↓
Node health/capacity?
    ↓
Cluster Autoscaler?
```

Microsoft's current AKS troubleshooting guidance specifically recommends using `kubectl describe pod` and looking for scheduling events such as insufficient resources or impossible placement constraints. ([Microsoft Learn][4])

### **1. Check status and Events**

```bash
kubectl get pod <pod> -n <namespace> -o wide

kubectl describe pod <pod> -n <namespace>
```

I look for messages such as:

```text
FailedScheduling

0/3 nodes are available:
3 Insufficient cpu
```

or:

```text
Insufficient memory
```

or:

```text
node(s) had untolerated taint
```

or:

```text
node(s) didn't match Pod's node affinity/selector
```

The event often tells me the root-cause category immediately.

---

### **2. CPU / memory requests**

The scheduler uses **resource requests**, not actual current CPU usage, to decide Pod placement.

Suppose:

```yaml
requests:
  cpu: "8"
  memory: "32Gi"
```

but the largest node has only:

```text
4 CPU
16 GiB allocatable
```

Then even adding ten identical nodes won't help.

```text
Pod request
8 CPU
   ↓
Largest node
4 CPU
   ↓
Never schedulable ❌
```

Microsoft specifically documents this as a reason Cluster Autoscaler may refuse to scale: the Pod wouldn't fit even on a new node. ([Microsoft Learn][4])

I compare:

```bash
kubectl describe pod <pod>
kubectl describe node <node>
```

and:

```bash
kubectl top nodes
```

where useful.

---

### **3. Taints and tolerations**

Suppose the available node pool has:

```text
workload=gpu:NoSchedule
```

but the Pod doesn't have a matching toleration.

Then:

```text
Pod
 ↓
GPU node
 ↓
untolerated taint
 ↓
Pending
```

Check:

```bash
kubectl describe node <node> | grep -i taint
```

and inspect the Pod's:

```yaml
tolerations:
```

---

### **4. Node selectors and affinity**

Suppose:

```yaml
nodeSelector:
  workload: payment
```

but no node has:

```text
workload=payment
```

The scheduler has nowhere to place it.

Likewise, overly strict:

```text
nodeAffinity
podAffinity
podAntiAffinity
topologySpreadConstraints
```

can make placement impossible.

Microsoft explicitly identifies affinity/topology constraints as causes of AKS Pods staying Pending. ([Microsoft Learn][4])

---

### **5. PVC / storage**

A Pod can also remain Pending because storage isn't ready.

I check:

```bash
kubectl get pvc -n <namespace>
```

If:

```text
PVC = Pending
```

then inspect:

```bash
kubectl describe pvc <pvc> -n <namespace>
```

Possible causes:

```text
StorageClass missing
CSI provisioner problem
Azure Disk quota
zone conflict
invalid access mode
storage capacity
```

A zone-bound Azure Disk is particularly important in multi-zone clusters.

---

### **6. Node state**

Check:

```bash
kubectl get nodes
```

If nodes show:

```text
NotReady
SchedulingDisabled
```

I inspect:

```bash
kubectl describe node <node>
```

for:

```text
MemoryPressure
DiskPressure
PIDPressure
NetworkUnavailable
```

A cluster may have “three nodes” on paper while only one is actually schedulable.

---

### **7. Check Cluster Autoscaler**

If the Pod really just needs more capacity:

```text
Pending Pod
   ↓
Cluster Autoscaler
   ↓
new node
```

should occur when configured.

If it doesn't, I check:

```text
Node pool at max?
Azure VM quota?
Regional VM SKU unavailable?
Subnet/IP exhaustion?
Pod wouldn't fit on new node anyway?
Affinity/taint prevents placement?
```

A very useful event is:

```text
pod didn't trigger scale-up:
it wouldn't fit if a new node is added
```

Microsoft's AKS guidance calls this out directly. ([Microsoft Learn][4])

---

### **8. Image pull is a different symptom**

If the Pod is already scheduled but the container image can't be pulled, I usually see:

```text
ErrImagePull
ImagePullBackOff
```

rather than a pure scheduling problem.

So I don't start debugging ACR credentials when Events clearly say:

```text
FailedScheduling: Insufficient cpu
```

### **Fast diagnostic tree**

```text
Pod Pending
   ↓
kubectl describe pod
   ↓
Events
   │
   ├── Insufficient CPU/RAM
   │      → requests / node capacity / autoscaler
   │
   ├── Untolerated taint
   │      → toleration / correct node pool
   │
   ├── Affinity/selector mismatch
   │      → scheduling constraints
   │
   ├── PVC Pending
   │      → StorageClass / CSI / zone
   │
   └── No available nodes
          → node health / scaling / quota
```

### **Interview answer condensed**

> “I start with `kubectl describe pod` and inspect the scheduler Events. If I see `FailedScheduling`, I check CPU/memory requests versus node allocatable capacity, then taints/tolerations, node selectors and affinity, PVC/storage constraints, and node health. If Cluster Autoscaler should help but doesn't, I check the node-pool max, VM quota/capacity, subnet IP space, and whether the Pod would actually fit on a newly added node.”

**Memory line:**
**Pending → ask the scheduler why before touching the application.**

**Interview trap:**
Don't immediately increase the node count.

If the Pod requests:

```text
16 CPU
```

while every node SKU only provides:

```text
8 CPU
```

adding more nodes of that same SKU changes nothing.

**Keywords:** Pending, `FailedScheduling`, requests, taints, affinity, PVC, Cluster Autoscaler

**Likely follow-ups:**

* Why wouldn't Cluster Autoscaler scale?
* How do requests affect scheduling?
* How can a PVC make a Pod Pending?
* What does `0/5 nodes are available` mean?

### **T07-H02. A pod is in `CrashLoopBackOff`; what would you investigate?**

**Answer:**
`CrashLoopBackOff` means the container **starts, exits or is killed repeatedly, and Kubernetes progressively backs off before restarting it again**.

So unlike `Pending`, the Pod has generally been scheduled—the problem is now usually at the **container/application/runtime level**.

My troubleshooting order is:

```text
CrashLoopBackOff
      ↓
Describe Pod
      ↓
Previous container logs
      ↓
Exit reason / exit code
      ↓
Config + secrets
      ↓
Command/entrypoint
      ↓
Probes
      ↓
Memory/OOM
      ↓
Dependencies/network
```

Microsoft's current AKS troubleshooting guidance recommends checking Pod events plus current and `--previous` container logs, with common causes including application startup failures, probe failures, OOM kills, bad commands, dependencies, and networking. ([Microsoft Learn][5])

### **1. Describe the Pod**

First:

```bash
kubectl describe pod <pod> -n <namespace>
```

I inspect:

```text
State
Last State
Reason
Exit Code
Restart Count
Events
```

For example:

```text
Last State:
  Terminated
Reason: OOMKilled
Exit Code: 137
```

already gives a strong direction.

Or:

```text
Reason: Error
Exit Code: 1
```

means I need application logs.

---

### **2. Get the previous container logs**

This is one of the most valuable commands:

```bash
kubectl logs <pod> \
  -n <namespace> \
  --previous
```

Why `--previous`?

Because:

```text
Container starts
 ↓
crashes
 ↓
new container starts
```

and normal logs might show only the current instance.

`--previous` retrieves logs from the instance that just failed. Microsoft explicitly recommends it when AKS containers repeatedly restart. ([Microsoft Learn][6])

For multi-container Pods:

```bash
kubectl logs <pod> \
  -n <namespace> \
  -c <container> \
  --previous
```

---

### **3. Check application startup errors**

Typical logs might reveal:

```text
Cannot connect to database
Missing environment variable
Invalid configuration file
Permission denied
Migration failed
Port already in use
Certificate missing
```

Example:

```text
FATAL:
DATABASE_URL is not defined
```

Then I'd inspect:

```bash
kubectl get deployment <deployment> -o yaml
kubectl get configmap
kubectl get secret
```

and the external secret source if using Key Vault CSI.

---

### **4. Check command / entrypoint**

Suppose the image expects:

```text
/usr/local/bin/server
```

but the Deployment overrides it with:

```yaml
command:
  - /app/start-prod.sh
```

and that script doesn't exist.

Result:

```text
Container starts
   ↓
command fails
   ↓
exit
   ↓
restart
   ↓
CrashLoopBackOff
```

So I inspect:

```yaml
command:
args:
```

and compare them to the image's real `ENTRYPOINT`/`CMD`.

---

### **5. Check OOMKilled**

A common AKS cause is:

```text
memory limit = 256 MiB
application needs = 600 MiB
```

Then:

```text
Container exceeds memory limit
        ↓
Linux OOM killer
        ↓
Container terminated
        ↓
Kubernetes restarts it
        ↓
CrashLoopBackOff
```

Check:

```bash
kubectl describe pod <pod>
```

for:

```text
Reason: OOMKilled
Exit Code: 137
```

and:

```bash
kubectl top pod <pod>
```

Microsoft confirms that container-level `OOMKilled` commonly appears with exit code `137`; the fix is to investigate memory consumption and right-size requests/limits rather than blindly restarting the Pod. ([Microsoft Learn][6])

---

### **6. Check liveness/startup probes**

This one comes up often in interviews.

Suppose the application takes:

```text
90 seconds
```

to start.

But liveness probe begins after:

```text
10 seconds
```

Kubernetes sees:

```text
Probe failed
Probe failed
Probe failed
```

then restarts the container.

The application never gets enough time to finish starting:

```text
start
 ↓
probe kills it
 ↓
restart
 ↓
start
 ↓
probe kills it
```

For slow-starting applications I use a:

```text
startupProbe
```

so liveness checks don't kill the container during initialization.

Microsoft's current AKS guidance recommends startup probes for slow initialization and warns that overly aggressive liveness settings can cause repeated restarts. ([Microsoft Learn][5])

### **Readiness vs liveness**

Remember:

```text
Readiness failure
→ stop sending traffic

Liveness failure
→ restart container
```

So a bad **liveness** probe can directly create CrashLoop behavior.

---

### **7. Check dependencies**

The application may terminate intentionally if a required dependency isn't reachable:

```text
Pod
 ↓
Database ❌
 ↓
App exits
 ↓
CrashLoopBackOff
```

I check:

```text
DNS
Service endpoint
NetworkPolicy
Private Endpoint
NSG/firewall
credentials
database availability
```

For example:

```bash
kubectl exec <working-debug-pod> -- \
  nslookup db.internal.example.com
```

and connectivity tests as appropriate.

### **8. Check Secret/ConfigMap mounts**

Typical failures:

```text
Secret doesn't exist
wrong key name
ConfigMap missing
Key Vault CSI mount error
bad file permissions
wrong configuration value
```

Useful:

```bash
kubectl describe pod <pod>
```

because the Events section can reveal mount failures.

If the failure happens before the main app starts, also inspect:

```text
Init Containers
Volumes
Mounts
```

---

### **9. Check init containers**

A failing init container can prevent the application from reaching a normal running state.

Use:

```bash
kubectl get pod <pod> -o jsonpath='{.status.initContainerStatuses}'
```

and:

```bash
kubectl logs <pod> \
  -c <init-container>
```

Typical problem:

```text
Init container:
run database migration
       ↓
DB unreachable
       ↓
init fails
       ↓
application never starts
```

---

### **Exit codes help**

Some useful clues:

```text
Exit 0
→ app exited normally but shouldn't have

Exit 1
→ generic application failure

Exit 126
→ command found but cannot execute

Exit 127
→ command not found

Exit 137
→ commonly SIGKILL / OOMKilled

Exit 143
→ SIGTERM, often graceful termination
```

But I always correlate the exit code with:

```text
Last State
Reason
Events
Logs
```

instead of diagnosing from the number alone.

### **Strong troubleshooting flow**

```text
1. kubectl get pod
2. kubectl describe pod
3. Check Last State + Exit Code
4. kubectl logs --previous
5. Check application config/secrets
6. Check command/args
7. Check startup/liveness probes
8. Check OOM/resource limits
9. Check dependencies/DNS/network
10. Check init containers and volume mounts
```

### **Interview answer condensed**

> “For CrashLoopBackOff I first use `kubectl describe pod` to inspect the last termination reason, exit code, restart count, and events. Then I immediately check `kubectl logs --previous`. From there I investigate application startup errors, missing ConfigMaps or secrets, bad commands, failing init containers, liveness/startup probes, OOMKilled conditions, and dependencies such as databases or private endpoints. I fix the underlying crash rather than repeatedly restarting the Pod.”

**Memory line:**
**CrashLoopBackOff → the container ran and died; find out why the previous instance died.**

**Interview trap:**
Don't treat:

```text
CrashLoopBackOff
```

as the actual root cause.

It's a **restart/backoff state**.

The real root cause is usually underneath it:

```text
OOMKilled
bad config
application exception
probe failure
missing dependency
bad command
```

**Keywords:** CrashLoopBackOff, `--previous`, exit code, OOMKilled, liveness, startup probe, ConfigMap, Secret
