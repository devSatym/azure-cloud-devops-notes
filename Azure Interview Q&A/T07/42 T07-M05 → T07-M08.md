# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Medium

### **T07-M05. What is the AKS cluster autoscaler?**

**Answer:**
The AKS **Cluster Autoscaler** automatically changes the **number of worker nodes in a node pool** based on Kubernetes scheduling demand.

The most important trigger is not simply “CPU is high.” It watches for **Pods that remain Pending because the scheduler cannot place them due to insufficient node capacity**. It then adds nodes, within the node pool's configured minimum and maximum. It can also remove underutilized nodes when their workloads can be safely moved elsewhere. ([Microsoft Learn][1])

### **Scale-out example**

Suppose:

```text
Node Pool
├── Node-1  nearly full
├── Node-2  nearly full
└── Node-3  nearly full
```

A Deployment creates three additional Pods:

```text
pod-8  → Pending
pod-9  → Pending
pod-10 → Pending
```

Kubernetes scheduler says:

```text
0/3 nodes are available:
Insufficient cpu
```

The Cluster Autoscaler detects that the Pods are schedulable **if additional node capacity exists**:

```text
Pending Pods
     ↓
Cluster Autoscaler
     ↓
Increase node-pool size
     ↓
New Node-4
     ↓
Scheduler places Pods
```

### **Min and max nodes**

For example:

```text
minCount = 3
maxCount = 10
```

The autoscaler can operate between those boundaries:

```text
3 ←→ 4 ←→ 5 ... ←→ 10
```

It won't scale beyond the configured maximum just because demand continues increasing. ([Microsoft Learn][1])

### **Scale-down**

When demand falls:

```text
Node-4
├── little/no workload
└── workloads can move elsewhere
```

the autoscaler can:

```text
cordon/drain candidate
      ↓
reschedule movable Pods
      ↓
remove node
```

Scale-down isn't just:

> “CPU below 50%, delete VM.”

Kubernetes scheduling constraints matter.

A node might not be removable because of:

* restrictive `PodDisruptionBudget`,
* node affinity,
* taints/tolerations,
* Pods that can't safely move,
* certain local-storage or system-Pod conditions.

Microsoft specifically calls these out as common reasons scale-down can be blocked. ([Microsoft Learn][1])

### **Important troubleshooting case**

Suppose Pods remain:

```text
Pending
```

but the node pool does **not** scale.

I would check:

```bash
kubectl describe pod <pod>
```

for `FailedScheduling`, then:

```bash
kubectl get events \
  --field-selector source=cluster-autoscaler,reason=NotTriggerScaleUp
```

Possible causes include:

```text
Node pool already at max
Wrong taints/tolerations
Node affinity impossible
PV zone conflict
Azure VM quota/capacity problem
Pod requests too large for available VM SKU
```

AKS exposes autoscaler events specifically for these cases. ([Microsoft Learn][2])

### **Don't combine it with VMSS autoscale**

AKS worker nodes may use VM Scale Sets underneath, but I should **not independently configure VMSS autoscaling** on a node pool that is controlled by the Kubernetes Cluster Autoscaler.

Kubernetes needs to make scaling decisions based on **Pod scheduling**, not only Azure VM metrics. Microsoft explicitly advises against combining another node autoscaling mechanism with Cluster Autoscaler. ([Microsoft Learn][1])

**Memory line:**
**Cluster Autoscaler scales nodes when Kubernetes doesn't have enough schedulable capacity.**

**Interview trap:**
Don't say:

> “Cluster Autoscaler adds nodes when CPU reaches 80%.”

That's closer to metric-based infrastructure autoscaling.

The Kubernetes Cluster Autoscaler's key signal is:

```text
Pods can't be scheduled
because suitable node capacity is unavailable.
```

**Keywords:** Cluster Autoscaler, nodes, Pending Pods, scheduler, min/max nodes, scale-down

**Likely follow-ups:**

* What can prevent scale-down?
* Why might Pending Pods not trigger scale-up?
* HPA vs Cluster Autoscaler?
* Should you configure VMSS autoscale too?

### **T07-M06. What is Horizontal Pod Autoscaler?**

**Answer:**
The Kubernetes **Horizontal Pod Autoscaler (HPA)** automatically changes the **number of Pod replicas** based on workload demand.

Unlike Cluster Autoscaler, which changes nodes:

```text
HPA
→ scales Pods

Cluster Autoscaler
→ scales Nodes
```

HPA can scale using CPU, memory, application/custom metrics, or external metrics depending on the metrics provider. ([Microsoft Learn][3])

### **Example**

Suppose:

```text
orders-api

replicas = 3
target CPU = 70%
```

Normal state:

```text
Pod-1  45%
Pod-2  55%
Pod-3  50%
```

No scaling required.

Traffic increases:

```text
Pod-1  92%
Pod-2  87%
Pod-3  90%
```

HPA calculates more replicas are required:

```text
3 Pods
   ↓
HPA
   ↓
desiredReplicas = 6
   ↓
Deployment replicas = 6
```

Kubernetes then creates the additional Pods.

When demand falls, HPA can reduce replicas while respecting its configured minimum and scaling behavior.

### **Typical HPA configuration**

Conceptually:

```yaml
minReplicas: 2
maxReplicas: 10

metric:
  CPU utilization: 70%
```

The workload might move:

```text
2 Pods
  ↓ traffic
4 Pods
  ↓ more traffic
8 Pods
  ↓ demand falls
3 Pods
```

### **Metrics Server**

For normal CPU/memory-based HPA, Kubernetes uses resource metrics exposed through the **Metrics API**, typically backed by Metrics Server in AKS. ([Microsoft Learn][4])

Useful commands:

```bash
kubectl top pods
kubectl get hpa
kubectl describe hpa
```

For example:

```text
NAME         REFERENCE              TARGETS    MIN   MAX   REPLICAS
orders-hpa   Deployment/orders      82%/70%    2     10    6
```

### **CPU requests matter**

This is a common interview trap.

For CPU utilization-based HPA, the percentage is based on the Pod's configured **resource request**.

Suppose:

```yaml
resources:
  requests:
    cpu: 500m
```

and the Pod is using:

```text
350m CPU
```

then utilization is approximately:

```text
350 / 500 = 70%
```

So badly configured or missing resource requests can make CPU-based HPA ineffective or misleading. ([Microsoft Learn][5])

### **Can HPA scale using non-CPU metrics?**

Yes.

For example:

```text
HTTP requests/sec
queue depth
latency
custom Prometheus metric
external metric
```

With the appropriate custom/external metrics provider.

For event-driven workloads such as:

```text
Azure Service Bus queue length
```

AKS commonly uses **KEDA**, especially if scale-to-zero behavior is required. ([Microsoft Learn][3])

### **Good workload for HPA**

HPA works particularly well for stateless workloads:

```text
API
Frontend
Worker fleet
```

where:

```text
1 replica
```

can easily become:

```text
10 identical replicas
```

**Memory line:**
**HPA scales the number of Pods based on workload metrics.**

**Interview trap:**
HPA doesn't create new Azure VMs itself.

It may create more Pods:

```text
HPA
3 → 10 Pods
```

but if the cluster has no room:

```text
new Pods → Pending
```

Then the **Cluster Autoscaler** needs to provide additional node capacity.

**Keywords:** HPA, replicas, Metrics Server, CPU, memory, custom metrics, scaling

**Likely follow-ups:**

* Why are resource requests important?
* Can HPA scale on custom metrics?
* Can HPA scale nodes?
* HPA vs KEDA?

### **T07-M07. What is the difference between HPA and cluster autoscaler?**

**Answer:**
The simplest distinction is:

> **HPA scales application replicas; Cluster Autoscaler scales infrastructure nodes.**

They solve different layers of the same capacity problem and are commonly used together. ([Microsoft Learn][3])

### **Comparison**

| Area                  | HPA                                | Cluster Autoscaler         |
| --------------------- | ---------------------------------- | -------------------------- |
| Scales                | Pods                               | Worker nodes               |
| Kubernetes layer      | Workload                           | Cluster infrastructure     |
| Typical trigger       | CPU/memory/custom metrics          | Unschedulable Pending Pods |
| Example               | 3 → 10 replicas                    | 3 → 6 nodes                |
| Main object affected  | Deployment/other scalable workload | Node pool                  |
| Handles app demand    | ✅                                  | Indirectly                 |
| Creates node capacity | ❌                                  | ✅                          |

### **How they work together**

Suppose I have:

```text
3 nodes
3 API Pods
```

Traffic suddenly increases.

#### Step 1 — HPA reacts

CPU rises:

```text
CPU = 90%
target = 70%
```

HPA changes:

```text
3 Pods
  ↓
8 Pods
```

#### Step 2 — Scheduler tries to place them

The existing nodes only have capacity for:

```text
5 Pods
```

So:

```text
Pod-6 → Pending
Pod-7 → Pending
Pod-8 → Pending
```

#### Step 3 — Cluster Autoscaler reacts

It detects:

```text
Pending Pods
caused by insufficient resources
```

and scales:

```text
3 Nodes
   ↓
5 Nodes
```

#### Step 4 — Scheduler places Pods

```text
New nodes ready
     ↓
Pending Pods scheduled
     ↓
8 running Pods
```

Full chain:

```text
Traffic increases
       ↓
CPU/RPS increases
       ↓
HPA adds Pods
       ↓
Not enough node capacity
       ↓
Pods become Pending
       ↓
Cluster Autoscaler adds nodes
       ↓
Scheduler places Pods
```

Microsoft describes HPA and Cluster Autoscaler as complementary mechanisms: HPA adjusts replicas according to workload demand, while Cluster Autoscaler adjusts node capacity based on scheduling requirements. ([Microsoft Learn][3])

### **Scale-down works in reverse**

Demand decreases:

```text
HPA:
8 Pods → 3 Pods
```

Now several nodes become underutilized.

Then:

```text
Cluster Autoscaler:
5 Nodes → 3 Nodes
```

assuming workloads can be safely rescheduled.

So:

```text
HPA removes workload demand first
        ↓
Cluster Autoscaler can remove excess capacity
```

### **Important ordering concept**

HPA doesn't need to explicitly call Cluster Autoscaler.

They communicate indirectly through Kubernetes state:

```text
HPA creates Pods
      ↓
Scheduler cannot place Pods
      ↓
Pending Pods
      ↓
Cluster Autoscaler sees scheduling pressure
```

That's the key mental model.

### **Production example**

```text
Deployment
min Pods = 3
max Pods = 30

Node pool
min Nodes = 3
max Nodes = 10
```

At night:

```text
3 Pods
3 Nodes
```

Peak traffic:

```text
24 Pods
8 Nodes
```

Then traffic falls:

```text
4 Pods
3 Nodes
```

This gives both:

```text
application elasticity
+
infrastructure elasticity
```

**Memory line:**
**HPA asks for more Pods; Cluster Autoscaler provides more places to run them.**

**Interview trap:**
Don't say:

> “HPA triggers the Cluster Autoscaler directly.”

Usually the relationship is indirect:

```text
HPA → more replicas → Pending Pods → Cluster Autoscaler.
```

**Keywords:** HPA, Cluster Autoscaler, Pods, nodes, Pending, scheduling, elasticity

**Likely follow-ups:**

* Which one reacts first during traffic growth?
* What if HPA reaches `maxReplicas`?
* What if Cluster Autoscaler reaches max nodes?
* Can the Cluster Autoscaler scale even without HPA?

### **T07-M08. What is a private AKS cluster?**

**Answer:**
A **private AKS cluster** is an AKS cluster where communication with the Kubernetes **API server uses a private endpoint/private IP inside the Azure network**, rather than exposing the Kubernetes API server through a public network endpoint.

So cluster administration requires private network connectivity. ([Microsoft Learn][6])

### **Normal public API architecture**

A conventional cluster can expose the API server through a publicly reachable endpoint:

```text
Administrator
     ↓ Internet
AKS API Server
     ↓
Cluster
```

Authentication and authorization still protect it, but the API endpoint is network-reachable publicly.

### **Private AKS**

With private cluster mode:

```text
Administrator
      ↓
VPN / ExpressRoute / connected VNet
      ↓
Private Endpoint
10.x.x.x
      ↓
AKS API Server
```

The Kubernetes API traffic stays on private connectivity.

Microsoft states that enabling private cluster mode deploys the API server through a private endpoint in the VNet. ([Microsoft Learn][6])

### **Important distinction: API server vs applications**

A private AKS cluster means:

```text
Kubernetes API server
→ private
```

It does **not automatically mean every application running inside AKS is private**.

You could still have:

```text
Private AKS API
       +
Public ingress
       ↓
Internet users → application
```

For example:

```text
Internet
   ↓
Front Door / App Gateway
   ↓
AKS application

Admin
   ↓
VPN
   ↓
Private AKS API
```

So control-plane exposure and application exposure are separate design decisions.

### **How do administrators use `kubectl`?**

If my laptop is directly on the public internet:

```bash
kubectl get pods
```

may fail because the API endpoint isn't publicly reachable.

I need a network path such as:

```text
Corporate network
      ↓
Site-to-Site VPN
      ↓
Azure VNet
      ↓
Private AKS API
```

or:

```text
Jump/Bastion VM
inside connected network
```

or ExpressRoute/VNet peering depending on the architecture.

### **What about CI/CD?**

This is important for DevOps interviews.

Suppose GitHub Actions or Azure DevOps must execute:

```bash
kubectl apply
helm upgrade
```

against the private API server.

A completely internet-hosted runner may not have a route to it.

So I may use:

```text
Self-hosted runner/agent
       ↓
inside or connected to Azure VNet
       ↓
Private AKS API
```

Microsoft specifically recommends connected/self-hosted agents for DevOps pipelines that need private-cluster API access. ([Microsoft Learn][6])

### **Private DNS**

DNS is a key component.

Conceptually:

```text
kubectl
   ↓
AKS API hostname
   ↓
Private DNS
   ↓
10.x.x.x
   ↓
Private Endpoint
```

If the client has network connectivity but can't resolve the AKS private API hostname, cluster management still fails.

So private AKS troubleshooting often becomes:

```text
DNS
↓
routing
↓
NSG/firewall
↓
authentication
```

### **Public FQDN nuance**

This is a useful current-AKS detail.

A private AKS cluster can still have a **publicly resolvable FQDN** by default, even though the actual API communication occurs through the private endpoint.

If I want the DNS name itself not publicly resolvable, I can disable the public FQDN with:

```text
--disable-public-fqdn
```

That doesn't turn a public API endpoint into a private one—the cluster is already using the private endpoint. It changes public DNS-name exposure. ([Microsoft Learn][6])

### **Why use a private AKS cluster?**

Common reasons:

```text
Security/compliance
Enterprise hub-spoke architecture
No public Kubernetes API exposure
Regulated workloads
Private management plane requirements
```

### **Production architecture**

```text
Developers
    ↓
Corporate VPN
    ↓
Hub VNet
    ↓
Spoke VNet
    ↓
Private AKS API

CI Runner
    ↓
Same/peered private network
    ↓
Private AKS API
```

Applications can separately use:

```text
Front Door
Application Gateway
Internal Load Balancer
Private ingress
```

depending on whether they should be public or internal.

**Memory line:**
**Private AKS = Kubernetes API server reachable through private networking.**

**Interview trap:**
Don't say:

> “Private AKS means nothing in the cluster can access the internet and no public application can run.”

That's incorrect.

Private cluster primarily describes **API-server/control-plane network access**.

Application ingress and egress are separate choices.

**Keywords:** Private AKS, API server, private endpoint, Private DNS, VPN, ExpressRoute, self-hosted CI runner

**Likely follow-ups:**

* How would GitHub Actions deploy to private AKS?
* Does private AKS mean the applications are private?
* Why is Private DNS important?
* How would your laptop access the API server?
