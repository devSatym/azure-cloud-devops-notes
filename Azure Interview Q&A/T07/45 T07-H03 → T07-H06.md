# 7. 🔴 M IMP — Azure Kubernetes Service (AKS)

## Hard

### **T07-H03. AKS pods cannot reach the internet; how would you troubleshoot the issue?**

**Answer:**
I would troubleshoot AKS internet egress in layers: **Pod → DNS → node → route → outbound mechanism → firewall/proxy → destination**.

My first step is to identify the cluster's **outbound type**, because AKS egress can use Azure Load Balancer, NAT Gateway, user-defined routing, or isolated/custom egress designs. ([Microsoft Learn][1])

```text
Pod
 ↓
Node / VNet
 ↓
Route table
 ↓
Load Balancer / NAT Gateway / Firewall
 ↓
Internet
```

### **1. Test from inside the Pod**

First determine whether this is:

```text
DNS failure
or
network connectivity failure
```

For example:

```bash
kubectl exec -it <pod> -- nslookup microsoft.com
```

Then:

```bash
kubectl exec -it <pod> -- curl -I https://www.microsoft.com
```

If DNS fails, I focus on:

```text
CoreDNS
upstream DNS
custom DNS
network path to DNS
```

If DNS resolves but `curl` times out, I move to routing/egress.

---

### **2. Determine the AKS outbound type**

I check the AKS network profile:

```bash
az aks show \
  -g rg-prod \
  -n aks-prod \
  --query networkProfile.outboundType
```

Possible values include:

```text
loadBalancer
managedNATGateway
userAssignedNATGateway
userDefinedRouting
none
```

and newer isolated-cluster options depending on the configuration. ([Microsoft Learn][1])

This is critical because troubleshooting differs for each model.

---

### **3. If outbound type is Load Balancer**

The default AKS Standard architecture commonly uses a **Standard Load Balancer with a public IP for egress**. ([Microsoft Learn][1])

I verify:

```text
AKS nodes
   ↓
Load Balancer backend pool
   ↓
Outbound rule/public IP
   ↓
Internet
```

Check that:

* outbound public IP exists,
* Load Balancer configuration is intact,
* nodes are in the expected backend pool,
* NSGs aren't blocking egress,
* public IP resources haven't been accidentally modified.

I avoid manually editing AKS-managed infrastructure resources because AKS manages their lifecycle. ([Microsoft Learn][2])

---

### **4. If using NAT Gateway**

For NAT Gateway:

```text
AKS subnet
    ↓
NAT Gateway
    ↓
Public IP / prefix
    ↓
Internet
```

I confirm the AKS subnet is actually associated with the NAT Gateway.

Conceptually:

```bash
az network nat gateway show ...
```

and inspect associated subnets/public IPs.

Microsoft specifically recommends verifying NAT Gateway subnet association when debugging AKS external connectivity. ([Microsoft Learn][3])

Also check for:

```text
SNAT port pressure
public IP configuration
routing conflicts
```

especially under heavy outbound connection loads.

---

### **5. If using `userDefinedRouting`**

This is a very common enterprise design:

```text
AKS
 ↓
UDR 0.0.0.0/0
 ↓
Azure Firewall / NVA
 ↓
Internet
```

With:

```text
outboundType = userDefinedRouting
```

AKS does **not automatically create the egress path**. I am responsible for creating a valid route, usually:

```text
0.0.0.0/0
→ Azure Firewall/NVA
```

and ensuring that device provides outbound connectivity. ([Microsoft Learn][1])

So I inspect:

```bash
az network route-table route list ...
```

and verify the effective route from the node NIC/subnet.

---

### **6. Check Azure Firewall / proxy rules**

If egress is centralized:

```text
Pod
 ↓
Azure Firewall
 ↓
Internet
```

I verify that the firewall permits the required:

```text
FQDNs
ports
protocols
service tags
```

AKS itself has mandatory outbound dependencies. If egress filtering blocks those endpoints, cluster operations and workloads can fail. Microsoft explicitly calls out restricted egress configurations that don't allow required AKS FQDNs as a common cause of failures. ([Microsoft Learn][4])

A useful current command is:

```bash
az aks egress-endpoints list \
  --resource-group rg-prod \
  --name aks-prod
```

to inspect required cluster egress destinations. ([Microsoft Learn][3])

---

### **7. Check NSGs**

I verify outbound NSG rules on:

```text
AKS subnet
and
relevant NIC/subnet path
```

A deny rule could block:

```text
TCP 443
DNS
required Azure endpoints
```

Remember:

```text
UDR decides WHERE traffic goes
NSG decides WHETHER traffic is allowed
```

Both must be correct.

---

### **8. Check DNS separately**

If:

```bash
curl https://1.1.1.1
```

works but:

```bash
curl https://example.com
```

doesn't, the issue is probably DNS rather than internet routing.

I check:

```bash
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system <coredns-pod>
```

and:

```bash
kubectl exec <pod> -- cat /etc/resolv.conf
```

If using custom DNS in the VNet, I verify the resolver can forward queries correctly.

---

### **9. Check NetworkPolicy**

A Kubernetes NetworkPolicy can block Pod egress even when Azure networking is perfect.

For example:

```yaml
policyTypes:
  - Egress
```

with no allow rules could result in:

```text
Pod → Internet ❌
```

So:

```bash
kubectl get networkpolicy -A
```

is part of my investigation.

---

### **10. Compare Pod and node connectivity**

If the Pod fails but the node succeeds:

```text
Node → Internet ✅
Pod  → Internet ❌
```

then I investigate:

```text
CNI
NetworkPolicy
iptables/eBPF dataplane
Pod SNAT
DNS
```

If both fail:

```text
Node → Internet ❌
Pod  → Internet ❌
```

the problem is more likely:

```text
UDR
NAT
Load Balancer
Firewall
NSG
```

### **Strong troubleshooting flow**

```text
1. Test DNS from Pod
2. Test HTTPS from Pod
3. Determine outboundType
4. Inspect effective routes
5. Validate LB/NAT/Firewall
6. Validate NSGs
7. Check required AKS FQDNs
8. Check NetworkPolicies
9. Compare Pod vs node connectivity
10. Packet capture if still unclear
```

Microsoft's AKS troubleshooting guidance recommends first identifying the egress architecture, then validating each hop and using packet capture when normal checks don't reveal the problem. ([Microsoft Learn][5])

**Memory line:**
**No AKS internet = determine outbound type first, then trace the egress path hop by hop.**

**Interview trap:**
Don't immediately say:

> “Add a public IP to the nodes.”

AKS egress should be solved through the cluster's supported outbound architecture—not ad hoc changes to managed node NICs.

**Keywords:** AKS egress, outbound type, NAT Gateway, Load Balancer, UDR, Azure Firewall, NSG, DNS

**Likely follow-ups:**

* What changes with `userDefinedRouting`?
* How would Azure Firewall affect AKS egress?
* What if DNS fails but IP connectivity works?
* Why shouldn't you edit AKS-managed NICs manually?

### **T07-H04. AKS pods cannot access an Azure database through a private endpoint; what would you check?**

**Answer:**
I would troubleshoot this in four separate layers:

```text
1. DNS
2. Network path
3. Private Endpoint configuration
4. Authentication / authorization
```

For AKS-to-PaaS access through Private Link, **DNS is often the first thing I check**, because the public database hostname must resolve to the private endpoint IP from the AKS network. Microsoft specifically documents Azure Private DNS as the standard resolution mechanism for AKS-to-private-PaaS connectivity. ([Microsoft Learn][6])

### **1. Check DNS from the Pod**

Suppose this is Azure SQL.

The application uses:

```text
mydb.database.windows.net
```

From the Pod:

```bash
kubectl exec -it <pod> -- \
  nslookup mydb.database.windows.net
```

I expect resolution toward the appropriate private endpoint path, ultimately returning a **private IP**.

For example:

```text
mydb.database.windows.net
        ↓
privatelink.database.windows.net
        ↓
10.20.5.8
```

If it resolves to a public address while public access is disabled:

```text
connection fails
```

### **2. Validate Private DNS zone**

I verify:

```text
Correct Private DNS zone exists
        +
correct A record exists
        +
zone is linked to AKS VNet
```

For Azure services, the exact Private DNS zone depends on the service.

For example:

```text
Azure SQL
→ privatelink.database.windows.net
```

A classic error is:

```text
Private Endpoint exists ✅
Private DNS zone exists ✅
VNet link missing ❌
```

Then Pods cannot resolve the endpoint privately.

Microsoft notes that Private DNS zones must be visible to the AKS network or the central DNS infrastructure resolving names for that network. ([Microsoft Learn][6])

---

### **3. If using custom DNS, check forwarding**

In hub-spoke environments:

```text
AKS VNet
  ↓
Custom DNS
  ↓
Hub resolver
  ↓
Azure Private DNS
```

I verify that the custom DNS server knows how to resolve Azure Private Link zones.

If the custom resolver doesn't forward correctly:

```text
network path may be perfect
but application still fails
```

This is extremely common.

---

### **4. Test TCP connectivity**

Once DNS gives a private IP, test the database port.

For example, Azure SQL:

```bash
kubectl exec -it <debug-pod> -- \
  nc -zv mydb.database.windows.net 1433
```

For PostgreSQL:

```text
5432
```

For MySQL:

```text
3306
```

If DNS works but TCP fails, I shift to:

```text
NSG
UDR
Azure Firewall
route
Private Endpoint network policy
database firewall/configuration
```

---

### **5. Inspect effective routing**

Expected path:

```text
AKS Pod
   ↓
AKS node/VNet
   ↓
Private Endpoint IP
   ↓
Azure database
```

In many normal designs, Private Endpoint traffic is routed directly within the VNet rather than through the central internet egress path. Microsoft notes that Private Endpoint routes can take precedence over hub-firewall egress paths unless routing is intentionally designed otherwise. ([Microsoft Learn][6])

So I inspect:

```text
effective routes
peering
NVA/Firewall
asymmetric routing
```

---

### **6. Check NSGs**

I verify:

```text
AKS subnet outbound
        ↓
DB private endpoint port
```

is allowed.

For example:

```text
TCP 1433
```

for Azure SQL.

If an NSG denies that flow:

```text
DNS ✅
Private Endpoint ✅
Authentication irrelevant yet
Network timeout ❌
```

### **7. Verify Private Endpoint state**

I check that the Private Endpoint connection is:

```text
Approved
```

not:

```text
Pending
Rejected
Disconnected
```

Also verify that it targets the correct:

```text
database/server resource
subresource/group ID
```

A private endpoint pointed at the wrong PaaS subresource won't solve the intended path.

---

### **8. Check public-network setting**

If the database has:

```text
Public network access = Disabled
```

that's fine—but then the AKS path must resolve and connect through Private Link successfully.

If troubleshooting shows the Pod still trying to use a public IP, that strongly indicates:

```text
DNS misconfiguration
```

rather than an authentication failure.

---

### **9. Separate networking from identity**

Suppose:

```text
nc -zv DB 1433
```

works, but the application gets:

```text
Login failed
403
authentication error
```

Now networking is probably okay.

I investigate:

```text
Microsoft Entra authentication
Managed Identity / Workload Identity
DB user mapping
database role
password/secret
```

depending on the database authentication model.

This distinction matters:

```text
Timeout
→ usually network/DNS

401/403/login failure
→ usually identity/authorization
```

---

### **10. AKS Workload Identity if supported**

If the application uses Microsoft Entra authentication:

```text
Pod
 ↓
Workload Identity
 ↓
Entra token
 ↓
Azure database
```

I check:

```text
ServiceAccount annotation
OIDC issuer
federated credential
managed identity
database permissions
```

### **Interview answer condensed**

> “I first run DNS resolution inside the Pod because the database FQDN must resolve to the private endpoint IP. Then I verify the correct Private DNS zone and VNet link or DNS forwarding. Once DNS is right, I test the database port and inspect NSGs, UDRs, peering and Private Endpoint approval. If TCP works but authentication fails, I move to Workload Identity or database credentials and RBAC/database permissions.”

**Memory line:**
**Private Endpoint troubleshooting: DNS first, network second, identity third.**

**Interview trap:**
Don't say:

> “Private Endpoint is approved, so connectivity must work.”

A Private Endpoint without correct:

```text
DNS
routing
NSG
```

can still be unusable.

**Keywords:** Private Endpoint, Private DNS, AKS, Azure SQL, NSG, UDR, Workload Identity

**Likely follow-ups:**

* Why is DNS so important for Private Link?
* What should the database FQDN resolve to?
* What if TCP works but login fails?
* How does hub-spoke DNS affect AKS?

### **T07-H05. How would you design a production-grade private AKS cluster?**

**Answer:**
For a production-grade private AKS cluster, I would design around **private control-plane access, controlled ingress/egress, strong identity, workload isolation, secure secrets, HA node pools, observability, and repeatable IaC**.

At a high level:

```text
Users / CI
   ↓
VPN / ExpressRoute / VNet
   ↓
Private AKS API

Internet users
   ↓
Front Door / WAF
   ↓
Private regional ingress
   ↓
AKS

AKS egress
   ↓
Azure Firewall / NAT
   ↓
approved destinations

AKS workloads
   ↓
Private Endpoints
   ↓
Key Vault / ACR / DB / Storage
```

Microsoft's current AKS Well-Architected guidance recommends private control-plane access where appropriate, Entra ID, managed identities, Workload Identity, network segmentation, egress controls, Key Vault, and security monitoring. ([Microsoft Learn][7])

### **1. Private Kubernetes API**

Create AKS with:

```text
private cluster / private API endpoint
```

Then cluster administration occurs through:

```text
VPN
ExpressRoute
VNet peering
Bastion/jump host
self-hosted CI runner
```

rather than exposing the API server publicly.

Microsoft's current private-cluster design uses a private API-server path and supports removing the public FQDN as well if desired. ([Microsoft Learn][8])

---

### **2. Separate system and user node pools**

Example:

```text
AKS
├── systempool
│   ├── 3 nodes
│   ├── dedicated system workloads
│   └── CriticalAddonsOnly taint
│
├── apppool
│   ├── autoscaling
│   └── production apps
│
└── batchpool
    └── optional Spot workloads
```

This prevents noisy application workloads from competing with:

```text
CoreDNS
network agents
critical Kubernetes components
```

I would spread production node pools across Availability Zones where supported.

---

### **3. Autoscaling**

For workload elasticity:

```text
HPA
→ scales Pods

Cluster Autoscaler
→ scales Nodes
```

Example:

```text
app replicas:
3 → 20

node pool:
3 → 10
```

I set minimum capacity high enough to preserve availability and avoid using autoscaling as a substitute for baseline HA.

---

### **4. Private application ingress**

For internal-only workloads:

```text
Internal Load Balancer
or
private ingress
```

For public applications:

```text
Internet
   ↓
Azure Front Door WAF
   ↓
private regional ingress
   ↓
AKS
```

or Application Gateway depending on requirements.

I don't expose every microservice with a separate public `LoadBalancer`.

Microsoft recommends starting with the least-exposed Service type and only exposing endpoints publicly when required. ([Microsoft Learn][9])

---

### **5. Controlled outbound traffic**

In a stricter enterprise design:

```text
AKS
 ↓
UDR
 ↓
Azure Firewall
 ↓
Internet
```

This gives:

```text
central egress logging
FQDN filtering
data-exfiltration controls
predictable outbound IPs
```

Microsoft explicitly recommends routing outbound traffic through a firewall or proxy when organizations need centralized security controls. ([Microsoft Learn][7])

Alternatively, for simpler controlled egress:

```text
AKS
 ↓
NAT Gateway
```

may be enough.

---

### **6. Private access to Azure PaaS**

For:

```text
ACR
Key Vault
Storage
Azure SQL
Cosmos DB
```

I would consider:

```text
Private Endpoint
+
Private DNS
```

where the threat model and cost justify it.

Example:

```text
AKS
 ↓
Private DNS
 ↓
Key Vault Private Endpoint
```

Microsoft's AKS reference designs commonly use private endpoints plus Private DNS for backend PaaS connectivity. ([Microsoft Learn][10])

---

### **7. Identity**

For human access:

```text
Microsoft Entra ID
+
Azure/Kubernetes RBAC
```

For cluster operations:

```text
AKS managed identities
```

For application Pods:

```text
Microsoft Entra Workload Identity
```

Microsoft recommends Workload Identity for Pod-to-Azure authentication so applications don't manage Azure credentials directly. ([Microsoft Learn][7])

I would also disable local AKS accounts where operationally appropriate.

---

### **8. Secrets**

Use:

```text
Azure Key Vault
+
Workload Identity
+
Secrets Store CSI Driver
```

rather than putting credentials into:

```text
Git
Helm values
plain Kubernetes manifests
```

Microsoft's AKS Well-Architected guidance explicitly recommends Key Vault plus Workload Identity/CSI for secret protection and rotation. ([Microsoft Learn][7])

---

### **9. NetworkPolicy**

Use Pod-level segmentation:

```text
frontend
   ↓ allowed
api
   ↓ allowed
database connector

other namespaces
   ↓ denied
```

Default-deny plus explicit allows where feasible.

This limits east-west movement after a Pod compromise. Microsoft recommends network policies for controlling Pod-to-Pod traffic. ([Microsoft Learn][7])

---

### **10. Pod security**

I enforce controls such as:

```text
non-root containers
read-only filesystem where practical
drop Linux capabilities
seccomp
resource requests/limits
restricted hostPath/privileged usage
```

and use policy controls such as Azure Policy/Kubernetes admission policy where appropriate.

---

### **11. High availability**

For critical Deployments:

```text
replicas >= 2/3
+
topology spread
+
PodDisruptionBudget
+
readiness/liveness/startup probes
```

Example:

```text
Zone 1 → Pod A
Zone 2 → Pod B
Zone 3 → Pod C
```

So node or zone maintenance doesn't remove the whole workload.

---

### **12. Observability**

Enable:

```text
Azure Monitor
Container Insights
Log Analytics
Managed Prometheus/Grafana where needed
diagnostic logs
alerts
```

and monitor:

```text
node pressure
Pod restarts
Pending Pods
5xx
latency
API server audit/activity
autoscaling
network failures
```

For security-sensitive workloads, Microsoft also recommends Defender for Containers and SIEM integration. ([Microsoft Learn][7])

---

### **13. CI/CD and GitOps**

A private API means CI needs private connectivity.

A clean model is:

```text
GitHub Actions
     ↓
self-hosted runner in VNet
     ↓
AKS private API
```

or use a GitOps controller running inside the cluster:

```text
Git
 ↓
Flux / Argo CD
 ↓
AKS
```

depending on architecture.

---

### **14. Infrastructure as Code**

I would manage:

```text
VNet
subnets
Private DNS
AKS
node pools
identities
role assignments
firewall
private endpoints
monitoring
```

through Terraform/Bicep rather than manual Portal configuration.

### **Production architecture**

```text
                         Internet
                            ↓
                    Azure Front Door
                         + WAF
                            ↓
                     Private ingress
                            ↓
        ┌──────────────── AKS ────────────────┐
        │                                      │
        │ System Pool     User Pool            │
        │ 3 nodes         autoscaling           │
        │                                      │
        │ Workload Identity                    │
        │ NetworkPolicy                        │
        └───────────────┬──────────────────────┘
                        │
           ┌────────────┴────────────┐
           ↓                         ↓
     Private Endpoints         Controlled egress
     KV / ACR / DB             Firewall / NAT
```

**Interview answer condensed:**

> “I'd use a private AKS API, zone-aware system and user node pools, Entra authentication, least-privilege RBAC, Workload Identity, Key Vault CSI, NetworkPolicies, private endpoints for sensitive PaaS services, and controlled egress through NAT Gateway or Azure Firewall. For availability I'd use multiple replicas, PDBs, topology spreading, HPA and Cluster Autoscaler. CI would reach the private API through a connected self-hosted runner or GitOps, and everything would be deployed through IaC with Azure Monitor and security logging enabled.”

**Memory line:**
**Production AKS = private control plane + controlled network + strong identity + HA workloads + observability.**

**Interview trap:**
Don't make the answer only about:

```text
Private AKS API ✅
```

A production-grade cluster also needs:

```text
identity
egress
ingress
secrets
HA
scaling
monitoring
policies
upgrades
CI/CD
```

**Keywords:** private AKS, Entra ID, Workload Identity, Key Vault, Private Endpoint, Firewall, NetworkPolicy, HA

**Likely follow-ups:**

* How would GitHub Actions access it?
* Azure Firewall vs NAT Gateway?
* How would you expose public applications?
* How would you secure Pod-to-Pod traffic?

### **T07-H06. How would you implement zero-secret Azure authentication for Kubernetes workloads?**

**Answer:**
I would use **Microsoft Entra Workload Identity with AKS OIDC federation**.

The Pod authenticates using a Kubernetes ServiceAccount token, which Microsoft Entra ID trusts through a **federated identity credential**. The workload then receives short-lived Azure tokens without storing a client secret, certificate, storage key, or service-principal password in Kubernetes. ([Microsoft Learn][11])

Architecture:

```text
AKS Pod
   ↓
Kubernetes ServiceAccount token
   ↓
AKS OIDC issuer
   ↓
Federated Identity Credential
   ↓
Microsoft Entra ID
   ↓
Short-lived access token
   ↓
Key Vault / Storage / Azure SQL / other Azure service
```

### **1. Enable OIDC issuer + Workload Identity**

For AKS Standard, enable:

```bash
az aks update \
  --resource-group rg-prod \
  --name aks-prod \
  --enable-oidc-issuer \
  --enable-workload-identity
```

For a new cluster, enable those options during creation.

Microsoft's current setup requires both the AKS **OIDC issuer** and **Microsoft Entra Workload ID** capability. ([Microsoft Learn][11])

---

### **2. Create a managed identity**

For example:

```text
uami-payment-api
```

This represents the Azure identity of the payment workload.

Then assign only the Azure permissions it actually needs.

For example:

```text
Key Vault Secrets User
```

or:

```text
Storage Blob Data Reader
```

at the narrowest useful scope.

---

### **3. Create a Kubernetes ServiceAccount**

Example:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-api
  namespace: payments
  annotations:
    azure.workload.identity/client-id: "<managed-identity-client-id>"
```

The identity is now associated with:

```text
namespace = payments
service account = payment-api
```

Microsoft's current Workload Identity setup uses exactly this ServiceAccount annotation model. ([Microsoft Learn][11])

---

### **4. Create a federated identity credential**

Now create the trust relationship:

```text
AKS OIDC issuer
      +
subject:
system:serviceaccount:payments:payment-api
      +
managed identity
```

Conceptually:

```text
Managed Identity says:

"I trust tokens issued by this AKS OIDC issuer
when subject =
system:serviceaccount:payments:payment-api"
```

Microsoft currently recommends the audience:

```text
api://AzureADTokenExchange
```

for this federation. ([Microsoft Learn][11])

### **5. Deploy the workload using that ServiceAccount**

Example:

```yaml
spec:
  serviceAccountName: payment-api
```

The Pod should also carry the expected Workload Identity label/configuration required by the current AKS integration.

Now:

```text
Payment Pod
    ↓
payment-api ServiceAccount
    ↓
federated identity
    ↓
Azure identity
```

No secret required.

---

### **6. Application obtains Azure credential dynamically**

Using Azure SDK:

```text
DefaultAzureCredential
```

can detect the Workload Identity environment.

Conceptually:

```text
Application
    ↓
DefaultAzureCredential
    ↓
Projected ServiceAccount token
    ↓
Microsoft Entra token exchange
    ↓
access token
```

The application does not contain:

```text
AZURE_CLIENT_SECRET ❌
storage account key ❌
password ❌
certificate file ❌
```

### **7. Azure RBAC controls what it can do**

Authentication doesn't grant unlimited access.

For example:

```text
payment-api identity
      ↓
Storage Blob Data Reader
      ↓
container: invoices
```

while:

```text
orders-api identity
      ↓
no role assignment
      ↓
access denied
```

That creates strong workload-level separation.

---

### **8. Why this is better than a Kubernetes Secret**

Old model:

```text
Kubernetes Secret
├── client ID
└── client secret
       ↓
Azure
```

Problems:

```text
secret rotation
secret leakage
GitOps exposure
secret-copy sprawl
long-lived credential risk
```

Workload Identity:

```text
ServiceAccount token
      ↓
OIDC federation
      ↓
short-lived Azure token
```

No static Azure credential to rotate.

Microsoft's AKS security guidance recommends Workload Identity specifically to avoid directly managing Azure credentials in workload code. ([Microsoft Learn][7])

---

### **9. Workload Identity + Key Vault**

For application secrets that still fundamentally exist, such as a third-party database password:

```text
Pod
 ↓
Workload Identity
 ↓
Key Vault
 ↓
retrieve password
```

So there are still application secrets, but **the Azure authentication itself is secretless**.

Combine with:

```text
Key Vault CSI Driver
```

if the app prefers mounted files.

---

### **10. Troubleshooting**

If Workload Identity fails:

```text
403 / authentication failure
```

I check:

```text
1. OIDC issuer enabled?
2. Workload Identity enabled?
3. ServiceAccount annotation correct?
4. Pod uses correct ServiceAccount?
5. Federated identity subject exact?
6. Issuer URL exact?
7. Audience correct?
8. Managed identity client ID correct?
9. Azure RBAC role assigned?
10. Token/RBAC propagation completed?
```

The federated subject must match exactly:

```text
system:serviceaccount:<namespace>:<serviceaccount>
```

Microsoft notes that federated credential propagation can take a short time after creation. ([Microsoft Learn][11])

### **Identity comparison**

```text
Cluster identity
→ AKS control plane → Azure

Kubelet identity
→ nodes/kubelet → ACR etc.

Workload Identity
→ individual Pod/application → Azure
```

### **Interview answer condensed**

> “For zero-secret Azure authentication in AKS, I'd enable the AKS OIDC issuer and Microsoft Entra Workload Identity. I'd create a managed identity for the application, associate a Kubernetes ServiceAccount with that identity, and create a federated credential trusting the exact ServiceAccount subject. The Pod then exchanges its projected ServiceAccount token for a short-lived Entra access token and uses Azure RBAC to access Key Vault, Storage, or other services. No client secret or storage key needs to be stored in Kubernetes.”

**Memory line:**
**Pod ServiceAccount → OIDC federation → Entra token → Azure resource. No client secret.**

**Interview trap:**
Don't call this:

> “The Pod uses the node's managed identity.”

That's the older/wrong mental model.

With Workload Identity, access is scoped to the **specific Kubernetes ServiceAccount/workload identity relationship**, not to every Pod on the node.
