# **T29-H03. How would you onboard a new subscription into an enterprise Azure environment?**

**Answer:**

I would onboard the subscription through an **automated landing-zone or subscription-vending process**, rather than manually configuring it through the portal.

My sequence would be:

1. collect workload metadata such as owner, environment, cost center, compliance level, connectivity needs, and region;
2. create or receive the subscription;
3. move it under the correct management group;
4. establish workload-team RBAC groups and deployment identities;
5. inherit or assign the appropriate Azure Policy baseline;
6. configure security and Defender requirements;
7. configure networking, such as a spoke VNet, hub connectivity, DNS, and routes if needed;
8. enable logging, budgets, tagging, and operational integrations;
9. validate the finished configuration;
10. hand the subscription to the application team.

The application team should then have enough control to deploy its workload, but it should **not** be able to modify the higher-level management-group policies or shared platform resources.

Microsoft's current subscription-vending guidance explicitly includes RBAC, policies, Defender configuration, networking, budgets, external-system updates, and final handoff as part of a subscription onboarding workflow. ([Microsoft Learn][1])

```text
Application team requests subscription
              ↓
       Workload metadata
              ↓
      Subscription vending
              ↓
      Subscription created
              ↓
   Correct Management Group
              ↓
 ┌────────────┼─────────────┐
 ↓            ↓             ↓
Policy       RBAC        Networking
 ↓            ↓             ↓
Security    CI identity    Hub/DNS
 └────────────┼─────────────┘
              ↓
      Logging + Budget
              ↓
         Validation
              ↓
   Handoff to workload team
```

---

## **1. Start with workload requirements**

Before touching Azure, I would determine:

```text
Application owner
Environment
Business criticality
Compliance requirements
Data classification
Region
Expected cost
Internet-facing or internal
On-prem connectivity required?
Private DNS requirements?
```

This matters because I can't correctly choose:

```text
Management group
Policy set
Network product
RBAC model
```

until I understand the workload.

For example:

```text
Internet-facing customer application
→ Online landing-zone archetype

Internal ERP requiring ExpressRoute
→ Corp-connected landing zone
```

The onboarding process should therefore begin with a **subscription product**, not just:

> “Give me an empty subscription.”

---

# **2. Create or acquire the subscription**

Ideally:

```text
Self-service request
       ↓
automated subscription creation
```

where the organization's commercial agreement/API capabilities support it.

Microsoft notes that programmatic subscription creation depends on the organization's commercial agreement; even where creation itself must remain manual, the subsequent configuration can still be automated. ([Microsoft Learn][1])

So I separate:

```text
Subscription creation
```

from:

```text
Subscription configuration
```

because the second part should still be automated.

---

# **3. Place it in the correct management group**

This is one of the most important steps.

Example:

```text
Enterprise
│
├── Platform
│
├── Landing Zones
│   ├── Online
│   └── Corp
│
└── Sandbox
```

If the workload is corporate-connected:

```text
new subscription
      ↓
Corp management group
```

Now it automatically inherits controls assigned above it.

This is better than manually copying 30 policies into every new subscription.

Conceptually:

```text
Management Group
      ↓
Azure Policy
      ↓
new subscription inherits
```

---

# **4. Establish RBAC ownership**

I would create or use Microsoft Entra groups such as:

```text
app-payments-admins
app-payments-contributors
app-payments-readers
```

Then assign roles at the application subscription or required resource scope.

For example:

```text
Payments team
      ↓
Contributor
      ↓
Payments subscription
```

while:

```text
Platform networking team
      ↓
Network permissions
      ↓
Connectivity subscription
```

The application team should normally **not** receive:

```text
Management Group Contributor
Policy Contributor
Owner on platform subscriptions
```

just because it owns its application.

---

# **5. Configure the CI/CD deployment identity**

I would also onboard the workload pipeline.

For example:

```text
GitHub Actions
      ↓
OIDC
      ↓
Microsoft Entra workload identity
      ↓
App subscription RBAC
```

or the equivalent Azure DevOps workload-identity-federated service connection.

I would avoid:

```text
one enterprise service principal
→ Contributor across every workload
```

because compromising one pipeline could compromise the whole estate.

Instead:

```text
App A pipeline identity
→ App A

App B pipeline identity
→ App B
```

This is an important supply-chain blast-radius control.

---

# **6. Apply/inherit Azure Policy**

Typical baseline policies could cover:

```text
Allowed locations
Required tags
Diagnostic settings
Security configuration
Public network restrictions
Allowed resource types/SKUs
```

The preferred model is inheritance:

```text
Management Group
      ↓
Policy initiative
      ↓
Subscription
```

rather than creating unique hand-built policy assignments for every workload unless a real exception is needed.

---

# **7. Enable security baseline**

Depending on enterprise standards:

```text
Microsoft Defender for Cloud plans
Security contact/integration
Activity logs
Policy compliance
central SIEM integration
```

may be established automatically.

Current Microsoft subscription-vending guidance explicitly includes Defender/security configuration as a subscription onboarding concern. ([Microsoft Learn][1])

---

# **8. Configure networking**

This depends on the subscription product.

### Corporate-connected workload

The onboarding automation may create:

```text
Spoke VNet
      ↓
Hub connectivity
      ↓
Azure Firewall routing
      ↓
Private DNS
      ↓
ExpressRoute/VPN path
```

### Isolated online workload

It may instead have:

```text
Spoke VNet
      ↓
controlled internet ingress/egress
```

without corporate routing.

Microsoft's vending guidance explicitly includes deploying VNets and establishing peering/connectivity to regional platform hubs. ([Microsoft Learn][1])

---

# **9. IPAM / CIDR allocation**

In a large enterprise, I would not simply pick:

```text
10.0.0.0/16
```

because it looks convenient.

The process should obtain an approved range from:

```text
IPAM
      ↓
Reserve CIDR
      ↓
Create VNet
      ↓
Commit reservation
```

Otherwise at 100+ subscriptions you eventually get:

```text
overlapping CIDRs
       ↓
hub/on-prem routing problems
```

The subscription-vending process can integrate with external systems such as IPAM. ([Microsoft Learn][1])

---

# **10. Configure logging and operational baseline**

I would establish appropriate:

```text
Activity Log export
Diagnostic baseline
Azure Monitor integration
Defender/security telemetry
operational ownership
```

The workload team may own application telemetry, while the platform/security team owns enterprise-level visibility.

So:

```text
Platform
→ governance/security/estate visibility

Application team
→ service logs, SLOs, application alerts
```

---

# **11. Add FinOps metadata and budget**

Every subscription should have clear ownership.

For example:

```text
Application = Payments
Owner = Payments-Team
Environment = Prod
CostCenter = CC-421
```

Then:

```text
Subscription budget
      ↓
80% threshold
100% threshold
      ↓
notification
```

Microsoft's subscription-vending guidance includes budget creation based on the workload data gathered during onboarding. ([Microsoft Learn][1])

---

# **12. Validate before handoff**

I would run automated checks such as:

```text
Correct management group?
      ↓
Expected policies inherited?
      ↓
RBAC groups present?
      ↓
CI identity correctly scoped?
      ↓
Defender/security baseline?
      ↓
Network reachable?
      ↓
DNS working?
      ↓
Budget configured?
      ↓
Activity logs flowing?
```

For connected subscriptions, I might validate:

```text
Spoke → Hub connectivity
DNS → expected resolver
Private endpoint name resolution
Required on-prem route
Firewall path
```

A provisioning pipeline returning `Succeeded` doesn't prove the **landing zone is operational**.

---

# **13. Hand off to the application team**

The result should be:

```text
Ready subscription
      ↓
Platform controls already present
      ↓
App team has deployment access
      ↓
Team can self-service workload resources
```

The platform team should not then become responsible for creating every:

```text
Storage Account
AKS cluster
database
application subnet
```

for the team.

The goal is to vend a **ready-to-use governed environment**.

---

# **14. Make onboarding idempotent**

If onboarding runs twice:

```text
First execution
→ configure subscription

Second execution
→ verify/converge
```

not:

```text
duplicate RBAC groups
duplicate peerings
duplicate policy assignments
```

This is another reason I would implement the vending workflow with version-controlled IaC.

---

# **15. What if the subscription already contains resources?**

This is a harder case.

Before moving an existing subscription under a heavily governed management group:

```text
Inventory resources
      ↓
Run Policy compliance assessment
      ↓
Check policies that would Deny/Modify
      ↓
Check networking
      ↓
Check RBAC
      ↓
Remediate incompatibilities
      ↓
Move subscription
```

I would **not** blindly move a production subscription and discover afterward that inherited governance blocks critical deployments.

---

# **16. Failure and rollback thinking**

Suppose networking setup fails after the subscription was created.

I wouldn't necessarily delete the subscription.

I'd leave its onboarding status as:

```text
ProvisioningFailed
```

prevent workload handoff, remediate the failed stage, and rerun idempotently.

For management-group moves or policy rollout:

```text
pre-check
→ move
→ compliance validation
```

is safer than relying on emergency rollback.

> “I would onboard subscriptions through automated subscription vending. First I'd collect workload metadata such as ownership, environment, compliance and networking requirements. Then I'd create or receive the subscription, place it under the correct management group, establish Entra groups and workload-specific CI identities, inherit the Azure Policy baseline, enable the security and monitoring baseline, configure networking and DNS, establish budgets and tags, and run validation before handoff. Application teams would then own their workload subscription but wouldn't have permission to modify higher-level policy or shared platform resources. # **T29-H04. How would you manage both Azure and on-premises resources using a common governance model?**

**Answer:**

I would use **Azure Resource Manager as the common management plane and Azure Arc to project supported on-premises resources into it**.

For servers, I would onboard Windows and Linux machines as Azure Arc-enabled servers using the Azure Connected Machine agent. For external Kubernetes, I would use Azure Arc-enabled Kubernetes. Once connected, those resources appear in Azure Resource Manager and can be organized into subscriptions and resource groups, tagged, queried with Resource Graph, governed with Azure Policy, and integrated with services such as Azure Monitor, Defender for Cloud, and Update Manager where supported.

I would then apply governance at management-group or subscription scope so the same policies can cover both:

```text
Azure VMs
+
Arc-enabled servers
```

or:

```text
AKS
+
Arc-enabled Kubernetes
```

where the policy supports both resource types.

The critical caveat is that Azure Arc creates a **common control plane**, not identical runtime behavior. The on-premises machine still depends on its local network, hypervisor, OS, storage, and update repositories, so I would keep the governance model common while respecting the differences in execution environments.

Azure Arc's current model explicitly projects non-Azure resources into Azure Resource Manager and supports unified inventory, governance, policy, security, patching, and Kubernetes management scenarios. ([Microsoft Learn][2])

```text
                         Azure Resource Manager
                                 │
                ┌────────────────┼────────────────┐
                │                │                │
                ▼                ▼                ▼
           Azure VMs      Arc-enabled       Arc-enabled
                          Servers           Kubernetes
                │                │                │
                └────────────────┼────────────────┘
                                 ↓
                      Common governance layer
                                 │
             ┌───────────────────┼──────────────────┐
             ↓                   ↓                  ↓
        Azure Policy          Azure RBAC       Resource Graph
             ↓                                      ↓
        Compliance                             Inventory
             │
       ┌─────┼─────────┐
       ↓     ↓         ↓
   Monitor Defender Update Manager
```

I would define:

```text
Management Groups
      ↓

      ↓
```

for hybrid assets just as I do for Azure-native assets.

For example:

```text

│
├── Platform
│
└── Managed Estates
    ├── Production

```

Then an Azure VM and an Arc-enabled machine can both exist under a common governance hierarchy.

The physical server can remain in:

```text

```

while its Azure resource representation belongs to:

```text

```

# **2. Onboard on-premises servers using Azure Arc-enabled servers**

Architecture:

```text
On-prem Windows/Linux server
            ↓
Azure Connected Machine agent
            ↓
secure outbound connectivity
            ↓
Azure Arc
            ↓
Azure Resource Manager resource
```

```text

      ↓
```

```text
      ↓
├── Azure VMs
```

With Arc:


# **6. Common access model using Azure RBAC**

Azure Arc resources have Azure Resource IDs.

That means Azure RBAC can protect operations against the Azure Arc resource/control plane.

For example:

```text
Hybrid Operations Team
      ↓
Reader / appropriate Arc role
      ↓
Hybrid subscription
```

Current Arc-enabled Kubernetes also supports Azure RBAC integration for connected-cluster access scenarios. ([Microsoft Learn][4])

But distinguish:

```text
Azure RBAC on Arc resource
```

from:

```text
local OS administrator/root
```

These are not automatically the same thing.

For servers:

```text
Arc-enabled server
```

This can give one operational view for:

* Linux updates,

```text
      ↓

```

# **10. Security architecture**

I would think in layers:

```text
Azure management identity
       ↓
Azure RBAC
       ↓
Azure Arc control plane
       ↓
Arc agent/extension permissions
       ↓
Local OS/Kubernetes authorization
```

A user being:

```text
Reader on Arc server resource
```

does not mean:

```text
root on Linux
```

and being local admin doesn't necessarily mean permission to modify Azure Policy assignments.

Keep Azure control-plane security and local runtime security distinct.

# **11. Network flow**

Arc typically works through outbound connectivity from the connected environment.

Conceptually:

```text
On-prem server
      ↓
Outbound HTTPS
      ↓
Azure Arc endpoints
```

This is operationally useful because you don't generally need to expose inbound administrative ports from Azure to every server just to connect it to Arc.

For Arc-enabled Kubernetes, Microsoft states the Arc agents establish a secure outbound connection to Azure. ([Microsoft Learn][4])

I would still review:

* proxy,
* firewall,
* DNS,
* TLS inspection,
* required endpoints

during onboarding.

# **14. Availability and disconnected scenarios**

Arc is a management plane dependency, not necessarily the application's data path.

If Azure Arc connectivity is temporarily lost:

```text
on-prem application
```

may continue running locally, but:

```text
governance updates
remote management
telemetry
extension operations
```

may be delayed/unavailable.

That is an important architectural distinction.

Also, current Azure Arc documentation notes that some older connectivity modes/capabilities evolve over time; for example, the Arc overview notes that indirectly connected mode for the relevant Arc service was retired in September 2025. ([Microsoft Learn][2])

So I would verify connectivity-mode requirements for any Arc design rather than relying on old documentation.

Arc does not replace:

```text

hardware management
SAN/storage administration
local backup systems
physical networking
```

Those systems still exist.

```text

```

on top.

So architecture becomes:

```text
Azure control plane
      ↓
Arc
      ↓
existing infrastructure
      ↓
local operational platform
```

not:

```text

```

# **T30-E01. What is the Azure Well-Architected Framework?**

**Answer:**

The Azure Well-Architected Framework is Microsoft's **design and review framework for building and operating high-quality Azure workloads**.

It helps architects and engineers evaluate workload decisions across five areas:

* Reliability
* Security
* Cost Optimization
* Operational Excellence
* Performance Efficiency

The important idea is not to maximize one pillar independently. Architecture is about balancing them according to the workload's actual business requirements.

For example, deploying an application active-active across multiple Azure regions may improve reliability, but it also increases cost and operational complexity. The Well-Architected Framework helps make those trade-offs deliberately rather than accidentally.

Microsoft's current framework continues to use these five pillars and emphasizes evaluating workload decisions and trade-offs across them. ([Microsoft Learn][6])

```text
             Azure Workload
                  │
     ┌────────────┼─────────────┐
     │            │             │
 Reliability   Security    Cost Optimization
     │            │             │
     └──────┬─────┴─────┬───────┘
            │           │
 Operational Excellence
            │
 Performance Efficiency
```

### **How I use it**

Suppose I'm designing an API.

I ask:

```text
Reliability
→ What happens when a zone fails?

Security
→ How are identities, secrets, and network access protected?

Cost Optimization
→ Are we paying for unused capacity?

Operational Excellence
→ Can we deploy, monitor, troubleshoot, and recover safely?

Performance Efficiency
→ Can the system meet latency and scale requirements?
```

The framework therefore acts as a **review lens**, not a specific Azure product.

---

### **CAF vs Well-Architected Framework**

A useful distinction:

```text
Cloud Adoption Framework
→ organization/cloud-estate adoption

Well-Architected Framework
→ individual workload quality
```

Microsoft explicitly notes that WAF is centered on workload-level design; portfolio-wide centralized controls are more in Cloud Adoption Framework territory. ([Microsoft Learn][7])

**Memory line:**
**The Well-Architected Framework is the checklist of architectural lenses I use to ask whether an Azure workload is reliable, secure, cost-effective, operable, and performant.**

**Interview trap:**
The Well-Architected Framework is **not an Azure service you deploy**; it is architectural guidance and a review methodology.

**Keywords:**
Well-Architected Framework, workload, Reliability, Security, Cost Optimization, Operational Excellence, Performance Efficiency, trade-offs.

# **T30-E02. What are the five pillars of the Azure Well-Architected Framework?**

**Answer:**

The five pillars are:

1. **Reliability** — keeping the workload resilient, available, and recoverable when failures occur.
2. **Security** — protecting confidentiality, integrity, availability, identities, and data.
3. **Cost Optimization** — delivering the required business value without unnecessary spend.
4. **Operational Excellence** — operating, monitoring, deploying, and improving the system safely and consistently.
5. **Performance Efficiency** — using resources effectively so the workload can meet performance and scaling requirements.

Microsoft's current Well-Architected Framework uses exactly these five pillars. ([Microsoft Learn][6])

A simple memory model is:

```text
Can it survive?
→ Reliability

Can it be trusted?
→ Security

Is the spend justified?
→ Cost Optimization

Can we operate it well?
→ Operational Excellence

Can it perform and scale?
→ Performance Efficiency
```

```text
budgets
removing waste
appropriate pricing models
```

Example:

```text
autoscaling instead of permanent overprovisioning
reserved capacity where predictable
shutting down unused nonprod resources
```

The goal is not:

```text
cheapest possible architecture
```

but:

```text
appropriate business value for cost
```

---

### **4. Operational Excellence**

Focuses on:

```text
Observability
automation
IaC
CI/CD
safe deployments
incident management
continuous improvement
```

Example:

```text
Git
 ↓
CI/CD
 ↓
Terraform/Bicep
 ↓
automated validation
 ↓
monitoring
```

Microsoft's current WAF guidance associates Operational Excellence with standards, comprehensive monitoring, DevOps practices, and safe deployment processes. ([Microsoft Learn][8])

---

### **5. Performance Efficiency**

Focuses on:

```text
Capacity
scaling
latency
throughput
load testing
resource efficiency
```

Example:

```text
Traffic increases
      ↓
scale out
      ↓
maintain latency target
```

Microsoft defines Performance Efficiency around adapting capacity to changing demand and sustaining performance while avoiding unnecessary resource usage. ([Microsoft Learn][9])

---

### **The pillars create trade-offs**

An important point:

```text
More reliability
→ more replicas / regions
→ more cost

More security controls
→ sometimes more complexity/latency

More performance capacity
→ potentially more cost
```

Good architecture isn't:

```text
maximize all five infinitely
```

It is:

```text
balance all five
against business requirements
```

**Memory line:**
**Reliability, Security, Cost Optimization, Operational Excellence, Performance Efficiency — survive, protect, spend wisely, operate well, perform well.**

**Interview trap:**
The pillars are **not independent checkboxes**; improving one can create trade-offs in another, especially reliability versus cost and security versus complexity/performance.

**Keywords:**
Reliability, Security, Cost Optimization, Operational Excellence, Performance Efficiency.
