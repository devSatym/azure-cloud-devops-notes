# **T29-E01. What is an Azure landing zone?**

**Answer:**

An Azure landing zone is a **standardized, scalable Azure environment designed so workloads can be deployed with the required governance, security, identity, networking, and operational controls already in place**.

I think of it as preparing the Azure foundation before application teams start deploying workloads. Instead of every team independently deciding subscription structure, RBAC, networking, policies, logging, and security, the landing-zone architecture provides those guardrails consistently.

Microsoft's current Azure landing-zone model has two major components: the **platform landing zone**, which provides centralized foundation and shared capabilities, and **application landing zones**, where workload teams deploy and operate their applications. ([Microsoft Learn][1])

```text
Microsoft Entra tenant
        │
        ▼
Management Groups
        │
        ├── Platform Landing Zone
        │      ├── Identity / access foundations
        │      ├── Connectivity
        │      ├── Management / monitoring
        │      └── Governance
        │
        └── Application Landing Zones
               ├── Workload A
               │    ├── Dev
               │    └── Prod
               │
               └── Workload B
                    ├── Dev
                    └── Prod
```

### **What problem does it solve?**

Without a landing-zone approach:

```text
Team A
→ creates subscriptions one way
→ different network
→ different RBAC
→ different logging

Team B
→ completely different design

Team C
→ another design
```

Eventually you get:

```text
inconsistent governance
+
security gaps
+
networking complexity
+
difficult operations
```

With landing zones:

```text
Central Azure foundation
        ↓
Common guardrails
        ↓
Application teams
        ↓
Deploy workloads consistently
```

---

### **It is more than a resource group**

A landing zone is an **architecture and operating model**, not simply:

```text
Resource Group + VNet
```

It can involve:

```text
Microsoft Entra ID
        ↓
Management Groups
        ↓
Subscriptions
        ↓
Azure Policy
        ↓
Azure RBAC
        ↓
Networking
        ↓
Monitoring / management
        ↓
Application workloads
```

Microsoft specifically describes Azure landing zones as an architecture for governing, securing, and scaling a **multi-subscription Azure environment**. ([Microsoft Learn][1])

---

### **Example**

Suppose a company has 50 application teams.

Instead of giving all of them access to one large subscription:

```text
One Subscription
├── App A
├── App B
├── App C
├── App D
└── ...
```

a landing-zone architecture might establish:

```text
Management Group Hierarchy
│
├── Platform
│    ├── Connectivity Subscription
│    └── Management Subscription
│
└── Landing Zones
     ├── App-A Subscription
     ├── App-B Subscription
     └── App-C Subscription
```

Policies can then be inherited from management groups.

For example:

```text
Landing Zones MG
       ↓
Azure Policy:
Approved regions only
Mandatory diagnostics
Security baseline
       ↓
Application subscriptions inherit policy
```

That gives teams autonomy **inside guardrails**.

---

### **Important distinction**

```text
Azure Landing Zone
≠
a single Azure service
```

There is no service where you simply create:

```text
az landing-zone create
```

and magically solve governance.

It is an architectural approach implemented using Azure capabilities such as:

```text
Management Groups
Subscriptions
Azure Policy
Azure RBAC
Networking
Monitoring
IaC
```

Microsoft also provides landing-zone accelerators, but organizations can implement customized designs where needed. ([Microsoft Learn][1])

**Memory line:**
**An Azure landing zone is the governed Azure foundation into which workloads can safely and consistently land.**

**Interview trap:**
An Azure landing zone is **not just a subscription, VNet, or resource group**; it is the broader governance, identity, connectivity, management, and subscription architecture.

**Keywords:**
Azure landing zone, management groups, subscriptions, Azure Policy, Azure RBAC, governance, platform landing zone, application landing zone.

# **T29-E02. What is the Azure Cloud Adoption Framework?**

**Answer:**

The Azure Cloud Adoption Framework, or CAF, is Microsoft's **structured guidance for planning, building, governing, securing, and operating Azure adoption**.

It is broader than technical architecture. It helps organizations connect business goals with cloud strategy, prepare people and processes, establish an Azure landing zone, migrate or modernize workloads, and then govern, secure, and manage the environment over time.

The current framework organizes Azure adoption around **Strategy, Plan, Ready, Adopt, Govern, Secure, and Manage**. ([Microsoft Learn][2])

```text
Strategy
   ↓
Plan
   ↓
Ready
   ↓
Adopt
   ↓
Govern
Secure
Manage
```

The last three aren't simply “final steps”; they become ongoing operational disciplines as the Azure estate grows.

---

### **What each stage means**

A useful interview mental model is:

```text
Strategy
→ Why are we moving to Azure?

Plan
→ What people, skills, workloads, cost, and operating model do we need?

Ready
→ Is the Azure environment prepared?
   Build landing zones.

Adopt
→ Migrate, modernize, or build workloads.

Govern
→ How do we maintain organizational controls?

Secure
→ How do we protect the Azure estate?

Manage
→ How do we operate and optimize it?
```

Microsoft's 2026 CAF guidance describes Ready as the phase where the Azure environment and landing zones are prepared, while Govern, Secure, and Manage define continuing operational standards. ([Microsoft Learn][3])

---

### **CAF vs landing zone**

This distinction is important:

```text
Cloud Adoption Framework
        ↓
Broad cloud-adoption methodology
        ↓
Strategy
Planning
Organization
Governance
Security
Operations
Architecture
        ↓
Azure Landing Zone
        ↓
one major technical foundation
within the Ready methodology
```

So:

> **CAF tells you how to approach Azure adoption overall; a landing zone provides the Azure environment into which workloads are deployed.**

---

### **Practical example**

Imagine an enterprise wants to move 100 applications to Azure.

CAF would encourage questions such as:

```text
Business objectives?
       ↓
Which applications migrate first?
       ↓
Who owns the cloud platform?
       ↓
What skills are missing?
       ↓
What subscription/governance model?
       ↓
Build landing zone
       ↓
Migrate / modernize applications
       ↓
Govern + secure + operate continuously
```

Without this, companies sometimes jump straight to:

```text
Create VMs
Create VNets
Start migrating
```

and only later discover that they haven't designed:

```text
RBAC
cost ownership
governance
network architecture
logging
subscription structure
security controls
```

CAF tries to prevent that kind of unstructured adoption.

---

### **CAF vs Well-Architected Framework**

Another interview distinction:

```text
Cloud Adoption Framework
→ organization-wide Azure adoption

Well-Architected Framework
→ quality of individual workload architecture
```

CAF asks:

> How should our organization adopt and operate Azure?

Well-Architected asks:

> Is this particular workload designed well?

They complement each other.

**Memory line:**
**CAF is Microsoft's end-to-end methodology for adopting Azure—from business strategy through landing zones, workload adoption, governance, security, and operations.**

**Interview trap:**
CAF is **not just a migration framework**; it covers the organization, platform foundation, workload adoption, governance, security, and ongoing management.

**Keywords:**
Cloud Adoption Framework, CAF, Strategy, Plan, Ready, Adopt, Govern, Secure, Manage, landing zone.

# **T29-E03. What is Azure Arc?**

**Answer:**

Azure Arc extends **Azure's management and governance control plane to resources that are running outside Azure**, such as on-premises servers, Kubernetes clusters, and supported resources in other clouds.

The resource continues running where it already exists, but after onboarding it to Azure Arc, it can be represented and managed through Azure Resource Manager and use Azure capabilities such as Azure RBAC, Azure Policy, tagging, Resource Graph, monitoring, security, and update-management integrations where supported.

So the key idea is:

```text
Workload stays outside Azure
        +
Azure management extends to it
```

Azure Arc does **not require moving the workload itself into Azure**. ([Microsoft Learn][4])

---

### **How it works conceptually**

Suppose I have:

```text
On-prem Linux Server
```

Normally:

```text
On-premises tools
      ↓
Linux Server
```

After Azure Arc onboarding:

```text
On-prem Linux Server
        │
        │ Arc connectivity/agent
        ▼
Azure Resource Manager
        │
        ├── Resource Group
        ├── Tags
        ├── Azure RBAC
        ├── Azure Policy
        ├── Resource Graph
        ├── Monitor
        └── Security / operations integrations
```

The machine is still:

```text
On-premises
```

but it now has an Azure management representation.

Microsoft describes Arc as projecting non-Azure resources into Azure Resource Manager so organizations can apply a more consistent management and governance model across Azure, datacenters, other clouds, and edge environments. ([Microsoft Learn][4])

---

### **What types of environments can Arc help manage?**

Important examples include:

```text
Physical / virtual servers
        ↓
Azure Arc-enabled servers

Kubernetes outside Azure
        ↓
Azure Arc-enabled Kubernetes

SQL Server outside Azure
        ↓
SQL Server enabled by Azure Arc
```

Azure Arc also supports additional hybrid capabilities depending on the resource type. ([Microsoft Learn][4])

---

### **Example: on-premises servers**

Suppose a company has:

```text
Azure VMs:        500
On-prem servers:  300
```

Without Arc:

```text
Azure VMs
→ Azure governance

On-prem servers
→ separate governance model
```

With Arc:

```text
Azure Resource Manager
          ↓
     common view
      /       \
Azure VMs   Arc-enabled servers
```

Now the organization can apply more consistent:

```text
Inventory
Tags
Azure RBAC
Azure Policy
Monitoring
Defender integrations
Update management
```

where supported.

---

### **Example: Kubernetes**

Suppose the organization has:

```text
AKS
+
on-prem Kubernetes
+
Kubernetes in another cloud
```

Arc-enabled Kubernetes can connect external Kubernetes clusters into Azure's management plane.

Conceptually:

```text
Azure
     \
On-prem K8s ──→ Azure Arc
     /
Other-cloud K8s
```

Azure Arc can then help with centralized governance and management, including capabilities such as Policy and GitOps integrations. ([Microsoft Learn][4])

---

### **Azure Arc is not migration**

This is the most important distinction.

```text
Azure Migrate
→ helps move workloads toward Azure

Azure Arc
→ helps manage resources wherever they run
```

Connecting a server with Azure Arc does **not** convert it into an Azure VM.

It remains:

```text
physical / VMware / another-cloud VM / on-prem VM
```

but becomes manageable through Azure capabilities.

---

### **Control plane vs workload location**

Remember:

```text
Management plane
→ Azure

Actual compute
→ may remain on-prem / edge / another cloud
```

That is the heart of Azure Arc.

**Memory line:**
**Azure Arc brings non-Azure resources into the Azure management plane without requiring the workloads themselves to move to Azure.**

**Interview trap:**
Azure Arc does **not migrate an on-premises server into Azure**; it extends Azure governance and management to the server where it already runs.

**Keywords:**
Azure Arc, hybrid cloud, multicloud, Azure Resource Manager, Arc-enabled servers, Arc-enabled Kubernetes, Azure Policy, Azure RBAC.

# **T29-E04. What is a platform landing zone?**

**Answer:**

A platform landing zone is the **central Azure foundation owned primarily by the platform team that provides governance and shared capabilities for application landing zones**.

It normally establishes the management-group hierarchy and centralized capabilities needed across workloads—for example governance, connectivity, identity integration, security, and management services.

Application teams then deploy their workloads into separate application landing zones while inheriting the guardrails established by the platform landing zone.

Microsoft's current guidance says most organizations should have **one platform landing zone per Microsoft Entra tenant**, consisting of a management-group hierarchy and centralized resources as required. ([Microsoft Learn][1])

```text
Microsoft Entra Tenant
        ↓
Platform Landing Zone
        │
        ├── Management Groups
        ├── Governance
        ├── Shared Connectivity
        ├── Security
        └── Management capabilities
                ↓
      Application Landing Zones
        ├── Application A
        ├── Application B
        └── Application C
```

---

### **What typically belongs in the platform layer?**

Conceptually, capabilities shared by many workloads:

```text
Platform Landing Zone
│
├── Management-group structure
│
├── Azure Policy
│
├── Central RBAC patterns
│
├── Connectivity
│     ├── Hub network / Virtual WAN
│     ├── Azure Firewall
│     └── shared DNS
│
├── Management / operations
│     └── centralized monitoring as required
│
└── Security foundation
```

The exact implementation depends on organizational requirements; Microsoft explicitly describes centralized resources as being provided **as needed**, rather than requiring every organization to deploy exactly the same components. ([Microsoft Learn][1])

---

### **Platform team vs application team**

A useful ownership model:

```text
Platform Team
      ↓
Platform Landing Zone
      ↓
provides guardrails + shared capabilities
      ↓
Application Landing Zones
      ↓
Workload Teams
      ↓
Application resources
```

For example:

### Platform team may own

```text
management groups
enterprise policies
shared connectivity
central DNS
security baseline
subscription vending/onboarding
```

### Application team may own

```text
AKS workload resources
App Service
Storage
databases
application-specific networking
application monitoring
```

within the platform guardrails.

---

### **Why centralize these capabilities?**

Imagine 100 teams independently building:

```text
100 firewalls
100 DNS architectures
100 monitoring strategies
100 governance approaches
```

You get duplication and inconsistency.

Instead:

```text
Platform capability
        ↓
reused by
        ↓
many application landing zones
```

gives standardization.

But the platform team should avoid becoming a ticket-based bottleneck.

A mature model often provides:

```text
IaC templates
subscription vending
policy guardrails
self-service platform capabilities
```

so application teams can move independently.

---

### **Platform landing zone vs application landing zone**

This distinction is fundamental:

```text
Platform Landing Zone
→ shared organizational foundation

Application Landing Zone
→ environment for a specific workload
```

Microsoft's current landing-zone model says each workload has one application landing zone containing its required environments, while the platform landing zone establishes the centralized foundation used across workloads. ([Microsoft Learn][1])

Example:

```text
Platform Landing Zone
│
├── Connectivity
├── Governance
└── Management
        │
        ├──────────────┐
        ▼              ▼
Application A      Application B
Landing Zone       Landing Zone
│                  │
├── Dev            ├── Dev
├── Test           └── Prod
└── Prod
```

---

### **Important distinction**

A platform landing zone is not:

```text
"the subscription where all applications run"
```

In fact, one major purpose is to separate:

```text
shared platform concerns
```

from:

```text
individual workload concerns
```

and apply governance consistently through the Azure hierarchy.

**Memory line:**
**The platform landing zone provides the shared Azure foundation; application landing zones consume that foundation to run workloads safely.**

**Interview trap:**
A platform landing zone should **not become one giant subscription containing every platform and application resource**; separation of responsibilities and subscriptions is part of scalable landing-zone design.

**Keywords:**
Platform landing zone, management groups, shared services, governance, connectivity, platform team, Azure Policy, application landing zone.
