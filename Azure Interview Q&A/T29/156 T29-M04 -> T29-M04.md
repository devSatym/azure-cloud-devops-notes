# **T29-M04. What is a hub-and-spoke landing-zone network?**

**Answer:**

A hub-and-spoke landing-zone network is an Azure network topology where **shared connectivity and security services are centralized in one or more hub networks**, while individual application landing zones use separate spoke VNets.

The hub is normally owned by the platform/network team and can contain services such as Azure Firewall, VPN or ExpressRoute gateways, Azure DNS components, and shared routing services. Each workload gets its own spoke VNet, often in its own application subscription, and connects to the hub using VNet peering or an equivalent managed topology.

The main benefit is that application teams keep network isolation and ownership of their workload while the organization centralizes expensive or security-sensitive services.

Microsoft's Azure landing-zone guidance supports both traditional hub-and-spoke and Azure Virtual WAN-based topologies; the traditional model gives the organization greater direct control of routing and network-security components. ([Microsoft Learn][1])

```text
                         On-premises
                             │
                   ExpressRoute / VPN
                             │
                             ▼
                 ┌─────────────────────┐
                 │      HUB VNET       │
                 │                     │
                 │ Azure Firewall      │
                 │ VPN/ER Gateway      │
                 │ Shared DNS          │
                 │ Routing services    │
                 └──────┬──────┬───────┘
                        │      │
                 Peering│      │Peering
                        │      │
              ┌─────────▼─┐  ┌─▼──────────┐
              │ Spoke A   │  │ Spoke B    │
              │ App Team A│  │ App Team B │
              │ AKS/API   │  │ App/DB     │
              └───────────┘  └────────────┘
```

---

## **1. What belongs in the hub?**

The hub contains services that are shared across many workloads.

Typical examples are:

```text
Hub / Connectivity Subscription
│
├── Hub VNet
├── Azure Firewall
├── VPN Gateway
├── ExpressRoute Gateway
├── Azure Bastion, if centralized
├── DNS resolver/forwarding components
└── routing components
```

In the Azure landing-zone reference architecture, these shared connectivity resources normally belong in a dedicated **Connectivity subscription**, while application VNets live in workload subscriptions. ([Microsoft Learn][1])

That separation matters because the application team should normally not be able to:

```text
modify corporate firewall policy
delete ExpressRoute
change enterprise DNS
modify central routing
```

just because it needs connectivity.

---

# **2. What belongs in a spoke?**

Each spoke normally represents a workload or a coherent application environment.

For example:

```text
App-A Production Subscription
        ↓
Spoke VNet
│
├── frontend subnet
├── AKS subnet
├── private endpoint subnet
└── application resources
```

Another application gets:

```text
App-B Subscription
        ↓
Different Spoke VNet
```

The spokes don't have to share administrative ownership.

This creates:

```text
Shared network services
+
Workload isolation
```

at the same time.

---

# **3. Why not put every application in the hub?**

Because then the hub becomes:

```text
shared routing
+
shared security
+
every workload
+
every team
```

which creates a huge blast radius.

A network-platform change could affect application resources directly, and application-team permissions become difficult to isolate.

The hub should generally provide **transit/shared connectivity**, not become the place where every application is hosted.

---

# **4. How does traffic flow?**

Suppose App A needs internet egress through the corporate firewall.

```text
App A VM / AKS
      ↓
Spoke subnet
      ↓
User Defined Route
0.0.0.0/0
      ↓
Azure Firewall in Hub
      ↓
Internet
```

For on-premises:

```text
Application Spoke
       ↓
Hub
       ↓
ExpressRoute / VPN Gateway
       ↓
On-premises
```

Microsoft's current landing-zone networking guidance discusses using route tables in spokes to steer traffic through centralized firewalls when inspection is required. ([Microsoft Learn][2])

---

# **5. Important: VNet peering is not naturally transitive**

This is a classic Azure interview point.

Suppose:

```text
Spoke A
   ↕
Hub
   ↕
Spoke B
```

Do not assume:

```text
Spoke A
→ Hub
→ Spoke B
```

works automatically just because both spokes are peered to the hub.

Traditional Azure VNet peering is not a general-purpose automatic transit router.

For controlled spoke-to-spoke traffic, you typically use:

```text
UDRs
+
Azure Firewall / NVA
```

or use a networking platform that provides the required transit behavior, such as Azure Virtual WAN or relevant Virtual Network Manager designs.

Microsoft's current guidance specifically describes additional routing configuration for inter-spoke communication in traditional landing-zone environments. ([Microsoft Learn][2])

# **6. Example inter-spoke flow**

If App A needs App B:

```text
App A Spoke
     ↓
UDR
     ↓
Azure Firewall
     ↓
security policy inspection
     ↓
App B Spoke
```

This gives the platform team a centralized point for:

* inspection,
* logging,
* segmentation,
* routing control.

But it introduces:

* firewall cost,
* routing complexity,
* dependency on shared hub availability.

# **7. Hub ownership vs spoke ownership**

A mature responsibility split might be:

```text
Platform / Network team
├── hub
├── firewall
├── ExpressRoute/VPN
├── shared DNS
└── peering framework

Application team
├── spoke workload subnets
├── workload NSGs
├── private endpoints
└── application resources
```

Exactly where responsibility is split depends on the organization's platform model.

But application teams should generally not require full control of the connectivity subscription.

---

# **8. DNS is part of the architecture**

Hub-and-spoke doesn't solve DNS automatically.

Suppose App A accesses:

```text
myvault.vault.azure.net
```

through a Private Endpoint.

The client needs:

```text
FQDN
   ↓
Private DNS
   ↓
private IP
```

A landing-zone network often centralizes private DNS or DNS-resolution services.

Traffic can be perfectly routed but still fail if DNS resolves the public endpoint.

So for private networking:

```text
DNS
+
routing
+
firewall
```

all matter.

# **9. Traditional hub-and-spoke vs Azure Virtual WAN**

There are two common landing-zone networking approaches.

### Traditional hub-and-spoke

```text
You manage:
routing
VNet hub
firewall
gateways
peerings
```

Good when you need granular/custom control.

### Azure Virtual WAN

```text
Microsoft-managed virtual hubs
        ↓
VNet connections
VPN
ExpressRoute
branch connectivity
hub-to-hub transit
```

Microsoft currently recommends evaluating Virtual WAN where organizations need large-scale, multi-region, branch, or transitive connectivity, while traditional hub-and-spoke is suitable where more direct routing control is needed. ([Microsoft Learn][3])

---

# **10. Azure Virtual Network Manager can help at scale**

Imagine:

```text
5 spokes
```

Manual peering is manageable.

At:

```text
500 VNets
```

manual topology management gets difficult.

Azure Virtual Network Manager can centrally organize VNets into network groups and apply connectivity configurations, including hub-and-spoke patterns across subscriptions. ([Microsoft Learn][4])

So the network architecture can evolve from:

```text
hand-managed peerings
```

toward:

```text
centralized topology management
```

as scale increases.

---

# **11. High availability**

A hub is shared infrastructure.

Therefore a hub failure can potentially affect:

```text
many application spokes
```

I would consider:

* Azure Firewall availability,
* gateway resiliency,
* ExpressRoute redundancy,
* zone-redundant components where supported,
* multiple regional hubs for multi-region workloads,
* redundant DNS resolution.

For multi-region landing zones, Microsoft's guidance recommends expanding connectivity with additional regional hubs rather than stretching one regional network everywhere. ([Microsoft Learn][5])

---

# **12. Security advantage**

A hub gives you a choke point:

```text
Workload
   ↓
Hub firewall
   ↓
Internet / On-prem / another spoke
```

That allows central:

* egress filtering,
* threat intelligence,
* logging,
* segmentation.

But I still use NSGs and workload-level controls.

```text
Azure Firewall
≠
replacement for every NSG
```

Defense should remain layered.

---

### **Interview answer condensed**

> “A hub-and-spoke landing-zone network centralizes shared connectivity services in a hub, usually in a dedicated Connectivity subscription, while individual workload subscriptions get separate spoke VNets. The hub can contain Azure Firewall, VPN or ExpressRoute gateways, DNS and routing services, and spokes connect using peering. This lets application teams own their workload networks without owning enterprise connectivity. For inspected internet, on-prem or spoke-to-spoke traffic, I would use explicit routing through the hub firewall because VNet peering isn't automatically transitive. At larger scale I would also evaluate Azure Virtual WAN or Virtual Network Manager rather than manually managing hundreds of peerings.”

**Memory line:**
**The hub provides shared transit and security; spokes isolate individual workloads.**

**Interview trap:**
Two spokes peered to the same hub do **not automatically gain transitive spoke-to-spoke connectivity**.

**Keywords:**
Hub-and-spoke, Connectivity subscription, spoke VNet, VNet peering, Azure Firewall, UDR, ExpressRoute, VPN, Private DNS, Virtual WAN.

# **T29-M05. What problems does Azure Arc solve?**

**Answer:**

Azure Arc solves the problem of **operating a distributed estate where servers, Kubernetes clusters, and data platforms exist across Azure, on-premises datacenters, edge locations, and other clouds but each environment otherwise needs a separate management model**.

Arc projects supported non-Azure resources into Azure Resource Manager, so they can participate in familiar Azure governance and operational capabilities such as inventory, Azure Policy, Azure RBAC, tagging, Resource Graph, monitoring, security integrations, update management, extensions, and GitOps where applicable.

The important point is that Arc doesn't move the workload to Azure. It extends Azure's management plane to wherever the workload already runs. Microsoft currently describes Arc as a unified multicloud and on-premises management platform for servers, Kubernetes, SQL and other supported hybrid resources. ([Microsoft Learn][6])

---

## **Problem 1 — Fragmented inventory**

Without Arc:

```text
Azure
→ Azure Portal

VMware
→ vCenter

AWS
→ AWS console

On-prem Linux
→ internal CMDB

Kubernetes
→ separate tooling
```

An organization can struggle to answer:

> How many servers do we actually operate?

Arc-enabled resources appear as Azure resources.

```text
Azure Resource Graph
        ↓
Azure VMs
+
Arc-enabled servers
+
supported Arc resources
```

This gives a more unified inventory.

Imagine the company requires:

```text

```

Azure resources can use Azure Policy.

But non-Azure servers traditionally need a separate governance mechanism.

Arc allows supported non-Azure resources to participate in Azure governance.

For example:

```text
Azure Policy
    ↓
Arc-enabled servers
```

or:

```text
Azure Policy
    ↓
Arc-enabled Kubernetes
```

Microsoft explicitly lists consistent governance and compliance across hybrid estates as a key Arc scenario. ([Microsoft Learn][6])

Suppose an operations team manages:

Without Arc, the operating model may be:

```text

+
```

Arc can expose applicable Azure services to non-Azure machines.

For Arc-enabled servers this can include capabilities around:

* extensions,

Microsoft describes Arc-enabled servers as representing Windows and Linux machines hosted outside Azure as Azure resources. ([Microsoft Learn][7])

For Kubernetes:

# **Problem 7 — Hybrid security posture**

Security teams often struggle with:

```text

+

```

Conceptually:

```text

      ↓
```

The phrase **“where supported”** matters.

# **Problem 8 — Data-residency/edge workloads**

Some workloads cannot move to Azure because of:

* latency,
* local hardware dependency,
* sovereignty,
* regulatory constraints,
* disconnected/edge requirements.

Arc allows:

```text
Workload stays local
       ↓

```

So hybrid architecture does not have to mean completely separate management models.

# **What Arc does NOT solve**

This is interview-important.

### Arc does not migrate the workload

```text
Arc
≠
Azure Migrate
```

### Arc does not make an on-prem VM an Azure VM

It becomes:

```text
Arc-enabled server resource
```

not a normal Azure VM.

### Arc does not eliminate networking

The connected agent/resource still needs the supported connectivity needed to communicate with Azure services.

### Arc does not automatically solve application HA

It manages/governs resources; it doesn't redesign the application.

### **Interview answer condensed**

> “Azure Arc solves the management fragmentation that appears when an organization runs resources across Azure, on-premises, edge locations, and other clouds. It projects supported external resources into Azure Resource Manager, which lets teams use common capabilities such as inventory, Policy, RBAC, monitoring, security, Update Manager and, for Kubernetes, GitOps. The workload still runs where it originally lived—Arc isn't a migration service. I see its main value as giving a hybrid estate a more consistent Azure-based governance and operations plane without requiring every workload to move into Azure.”

**Memory line:**
**Arc solves hybrid management fragmentation by bringing external resources into Azure's management plane, not by moving them into Azure.**

**Interview trap:**
Azure Arc does **not** turn an on-premises VM into an Azure VM or remove the need for network connectivity.

**Keywords:**

# **T29-H01. How would you design an Azure foundation for 100 application teams?**

**Answer:**

For 100 application teams, I would not design Azure around individual resource groups or manually provision infrastructure team by team. I would build a **landing-zone platform that scales through management groups, automated subscription vending, policy-driven governance, shared platform subscriptions, and self-service application landing zones**.

At the top I would establish a simple management-group hierarchy based on governance requirements. Shared connectivity, management/security services, and other platform capabilities would live in dedicated platform subscriptions. Application teams would receive workload subscriptions through an automated vending process, placed under the appropriate management group and automatically configured with Azure Policy, RBAC groups, budgets, network connectivity, logging, and other baseline controls.

The application teams would then own their workload resources inside those subscriptions. Production and nonproduction would be isolated where the risk model requires it, but I would avoid creating unnecessary management-group layers for every team or environment.

The operating principle would be:

> **centralize governance and shared capabilities, automate the platform, and decentralize workload delivery.**

Microsoft's current landing-zone principles explicitly emphasize **subscription democratization**, **policy-driven governance**, and automated subscription vending so application teams can move independently while remaining inside platform guardrails. ([Microsoft Learn][9])

---

```text
                         Microsoft Entra Tenant
                                  │
                                  ▼
                      Intermediate Root MG
                                  │
             ┌────────────────────┼────────────────────┐
             │                    │                    │
             ▼                    ▼                    ▼
         Platform MG         Landing Zones MG       Sandbox MG
             │                    │
      ┌──────┼───────┐      ┌─────┴─────┐
      │      │       │      │           │
      ▼      ▼       ▼      ▼           ▼
 Connectivity Management Security    Corp          Online
 Subscription Subscription Sub.       MG             MG
      │                             │              │
 Hub/VWAN                           │              │
 Firewall                          ▼              ▼
 DNS                        App subscriptions  App subscriptions
 VPN/ER                     Team A...Team N    Team A...Team N

                                  ▲
                                  │
                          Subscription Vending
                                  │
                         Self-service request
```

This lets me support 100 teams without manually designing 100 independent Azure estates.

# **1. Start with the tenant and management-group hierarchy**

I would keep the hierarchy **shallow and governance-driven**.

For example:

```text
Tenant Root
   ↓
Organization
│
├── Platform
│   ├── Connectivity
│   ├── Management
│   └── Security
│
├── Landing Zones
│   ├── Corp
│   └── Online
│
└── Sandbox
```

Why `Corp` vs `Online`?

Not because those names are mandatory, but because workloads may have materially different connectivity/security requirements.

For example:

```text
Corp
→ corporate/private connectivity required

Online
→ internet-oriented workload
→ potentially no traditional corporate L3 connectivity
```

Microsoft recommends organizing management groups around common security, compliance, connectivity and feature requirements rather than creating one branch per team. ([Microsoft Learn][10])

---

# **2. Do NOT create 100 management groups just because there are 100 teams**

Bad:

```text
Landing Zones
├── Team001
├── Team002
├── Team003
...
└── Team100
```

unless each team genuinely needs different inherited governance.

That architecture becomes difficult to maintain.

Instead:

```text
management groups
→ governance archetypes

subscriptions
→ workload/team boundaries
```

This is a crucial enterprise pattern.

# **3. Make subscriptions the workload boundary**

For example:

```text
Payments Team
├── Payments-NonProd subscription
└── Payments-Prod subscription

Orders Team
├── Orders-NonProd subscription
└── Orders-Prod subscription
```

The exact number depends on:

* compliance,
* team ownership,
* quota/limits,
* isolation needs,
* environment strategy.

I would not force exactly two subscriptions on every application if that creates needless complexity.

Microsoft's current landing-zone guidance treats subscriptions as key units of management and encourages workload teams to manage subscriptions independently within platform guardrails. ([Microsoft Learn][9])

With 100 teams, manual subscription creation is not acceptable.

I would build something like:

```text

       ↓

       ↓

       ↓
Validate:

├── cost center
├── workload type
├── environment

       ↓

       ↓
Apply baseline
       ↓

```

Microsoft's current subscription-vending guidance describes exactly this model: standardize subscription creation/configuration, apply governance, and hand the resulting subscription to the application team. ([Microsoft Learn][11])

# **17. Blast-radius model**

If Team A's application pipeline is compromised:

```text
Team A pipeline
      ↓
Team A identity
      ↓
Team A subscription
```

The attacker should **not** automatically gain:

```text
Connectivity Subscription
Security Subscription
Team B Prod
Team C Prod
Management Group Policy
```

This is why:

* subscription boundaries,
* separate workload identities,
* platform RBAC,
* Policy

all matter.

# **18. Platform availability matters**

A shared hub failure might affect dozens of teams.

So platform SLOs need to cover:

```text
Connectivity
DNS
Firewall
Subscription-vending service
Identity dependencies
central monitoring
```

At this scale, the platform team is effectively operating an internal cloud product.

## **Interview answer condensed**

> “For 100 application teams I would build an Azure landing-zone platform rather than manually provision resources team by team. I would keep a shallow governance-driven management-group hierarchy, separate platform subscriptions for connectivity, security and management, and give workload teams application subscriptions through automated subscription vending. Vending would place the subscription in the correct management group and establish Policy, RBAC groups, budgets, networking and logging automatically. I'd offer several subscription products such as corporate-connected, online and sandbox rather than one design for everyone. Governance would be enforced centrally with Azure Policy, while teams deploy their own workload resources using app-specific federated CI identities. The key is centralized guardrails and shared services with decentralized workload ownership.”

**Memory line:**
**At 100 teams, build a self-service Azure platform—not 100 manually managed cloud environments.**

**Interview trap:**
Do **not** create one management group per application team unless those teams genuinely require different inherited governance.

Azure landing zones, management groups, subscription vending, subscription democratization, platform subscriptions, Azure Policy, workload identity, self-service, Virtual WAN, platform engineering.

# **T29-H02. How would you enforce centralized governance while allowing development teams autonomy?**

**Answer:**

I would use a **guardrails-not-gates** model.

The platform team would define non-negotiable controls at management-group scope using Azure Policy and carefully scoped Azure RBAC, while development teams would receive ownership of their workload subscriptions through an automated subscription-vending process.

The developer should be able to create an AKS cluster, Storage Account, Key Vault, database, or application network without waiting for the platform team—as long as the deployment complies with the organization's policies.

For example, developers might have broad deployment permissions inside their subscription, while inherited Policy prevents prohibited regions, enforces required diagnostics, or restricts insecure configurations. They cannot modify those policies because the policy assignment lives at a higher management-group scope.

This is exactly the model Microsoft's current landing-zone guidance describes as **subscription democratization plus policy-driven governance**: give workload teams independent control of their subscriptions while Azure Policy maintains organization-wide guardrails. ([Microsoft Learn][9])

```text
                    Platform Team
                         │
                  Management Group
                         │
           ┌─────────────┼──────────────┐
           │             │              │
       Azure Policy     RBAC        Shared Platform
           │             │              │
           └─────────────┼──────────────┘
                         ↓
               Application Subscription
                         │
                   Dev Team owns
                         │
            ┌────────────┼─────────────┐
            ↓            ↓             ↓
           AKS         Storage       Database
            │
     must satisfy Policy
```

# **1. Define what is non-negotiable**

First I would classify organizational controls.

Examples:

### Central security/compliance guardrails

```text
Approved Azure regions
No prohibited public exposure
Required diagnostics/security configuration
Required data residency
Allowed resource types/SKUs where necessary
```

### Workload decisions

```text
AKS vs App Service
SQL vs Cosmos DB
number of microservices
application autoscaling
application dashboards
deployment strategy
```

The platform should govern the first category.

The application team should usually own the second.

---

# **2. Put governance above the workload subscription**

Architecture:

```text
Landing Zones MG
       ↓
Policy Initiative
       ↓
Online MG
       ↓
Application subscription
       ↓
workload resources
```

The application team receives rights at:

```text
Application subscription
```

but not:

```text
parent management group
```

Therefore they can manage their resources without being able to remove the inherited control.

Microsoft recommends using management-group policy inheritance for workloads that share security, compliance and connectivity requirements. ([Microsoft Learn][10])

---

# **3. Understand RBAC vs Policy**

This distinction is critical.

### Azure RBAC asks:

```text
WHO is allowed to perform an action?
```

Example:

```text
Developer group
→ Contributor
→ App-A subscription
```

### Azure Policy asks:

```text
WHAT configurations are allowed?
```

Example:

```text
Contributor tries:
Create Storage Account
public access enabled
```

RBAC:

```text
User is authorized to create Storage Accounts.
```

Policy:

```text
Configuration violates policy.
DENY.
```

So:

```text
RBAC
+
Policy
```

provides both delegated access and central governance.

Microsoft explicitly describes Azure Policy as complementing Azure RBAC rather than replacing it. ([Microsoft Learn][15])

---

# **4. Example developer workflow**

Developer wants an Azure Storage Account.

```text
Developer
    ↓
Terraform / Bicep
    ↓
Workload CI identity
    ↓
ARM
    ↓
RBAC
"Can this identity create Storage?"
    ↓ YES
Azure Policy
"Is this configuration compliant?"
    ↓
 YES ─────────→ Create

 NO ──────────→ Deny / modify / audit
```

The platform team is not manually approving every Storage Account.

The control is automated.

---

# **5. Use Policy effects deliberately**

I would use different effects depending on risk.

### Audit

```text
Detect condition
but don't block
```

Useful while introducing a new control.

### Deny

```text
Unsafe request
→ reject
```

For non-negotiable controls.

### Modify

```text
request
→ automatically add/adjust supported configuration
```

Useful for certain metadata or supported configuration.

### DeployIfNotExists

```text
resource exists
but required companion configuration missing
→ deploy it
```

Useful for cases such as required diagnostics where appropriate.

This reduces how many platform details developers need to remember.

---

# **6. Roll policy out safely**

I would not necessarily deploy:

```text
brand-new Deny policy
→ production management group
```

immediately.

A safer path:

```text
Policy definition
     ↓
Sandbox / test scope
     ↓
Audit
     ↓
Measure noncompliance
     ↓
Fix applications / exemptions
     ↓
Deny
```

Why?

A poorly tested policy at management-group scope can block deployments for 100 teams at once.

Centralization increases both consistency **and blast radius**.

---

# **7. Policy exemptions must be governed**

Sometimes a workload has a valid exception.

For example:

```text
Policy:
public IP prohibited

Requirement:
approved internet ingress appliance
needs public IP
```

The solution is not:

```text
Disable Policy for whole subscription.
```

Instead:

```text
Documented exemption
      ↓
smallest required scope
      ↓
business/security justification
      ↓
owner
      ↓
expiration/review date
```

This keeps exceptions visible and intentional.

# **8. Give teams subscriptions through self-service vending**

Developer experience should be:

```text
Request:
"Production corporate-connected subscription"
        ↓
Automated vending
        ↓
subscription created/configured
        ↓
team gets access
```

not:

```text
Email platform team
      ↓

      ↓
ticket routed
      ↓
manual configuration
```

Microsoft's current guidance treats automated subscription vending as a key mechanism for enabling developer autonomy while preserving central governance. ([Microsoft Learn][11])

# **9. Use predefined subscription products**

Developers could choose:

Each product automatically gets the right:

* management-group placement,

This gives developers choices without allowing unconstrained infrastructure.

# **10. Let teams own IaC**

Application team:

```text
app-repo
│

      ├── AKS
```

The platform team does not need to become an approver for every normal application change.

Azure Policy remains the non-negotiable guardrail.

# **11. Use workload-specific identities**

For application deployments:

```text
App A GitHub Actions
      ↓
OIDC
      ↓
App A deployment identity
      ↓
App A subscription
```

App B:

```text
different identity
```

This gives autonomy while preserving isolation.

I would avoid:

```text
central-prod-deployer
→ Owner on all 100 subscriptions
```

because compromise blast radius becomes enormous.

# **12. Separate platform control from application control**

Example:

```text
Platform team owns:
├── management groups
├── policy
├── shared networking
├── subscription vending
└── platform modules

Application team owns:
├── application resources
├── workload IaC
├── deployments
├── runtime configuration
├── application SLOs
└── app-specific monitoring
```

This prevents central governance from becoming centralized delivery.

# **13. Offer golden paths, not only restrictions**

If platform engineering gives developers only:

```text
DENY
DENY
DENY
DENY
```

they will see governance as friction.

Instead provide:

```text

       ↓

       ↓
Key Vault pattern
       ↓
monitoring defaults
       ↓
networking integration
```

so compliant infrastructure is the easiest infrastructure to deploy.

This is where platform engineering and landing zones complement each other.

# **14. Sandbox environment**

Teams sometimes need to experiment with a new Azure service before the enterprise baseline supports it.

I would provide:

```text
Sandbox

├── spending limit/budget
├── no sensitive data
├── restricted enterprise connectivity
├── reduced privileges
└── lifecycle/expiry
```

Microsoft's current landing-zone application-environment guidance recommends sandbox resources specifically so teams can experiment while the main estate remains controlled. ([Microsoft Learn][14])

# **15. Central networking without ticket-driven subnet creation**

This can be tricky.

Platform team might own:

```text
Hub
Firewall
DNS
```

while application team owns:

```text
Spoke
subnets
NSGs
private endpoints
```

within policy.

For example, Policy can require:

```text
approved NSG configuration
```

without requiring the network team to manually create every subnet. Microsoft's subscription-vending guidance explicitly discusses using higher-scope Policy to enforce network behavior while allowing application teams to manage their own application network design. ([Microsoft Learn][12])

# **16. Visibility without ownership**

Security/operations teams often need:

```text
read access
security posture
logs
policy compliance
```

across every workload.

They don't necessarily need:

```text
Owner
```

on every application subscription.

Assign appropriate centralized read/security roles from higher scopes where justified.

This preserves separation of duties.

---

# **17. Prevent governance bypass**

Controls should apply regardless of how the developer deploys:

```text
Portal
Azure CLI
Bicep
Terraform
Azure DevOps
GitHub Actions
```

That's why control-plane Policy is stronger than saying:

```text
"Please use our approved Terraform module."
```

A developer can bypass a Terraform module.

They cannot bypass an inherited `Deny` policy simply by using another client—assuming they do not have permission to modify/exempt the policy itself.

Microsoft specifically calls out Azure Policy as tooling-agnostic governance across provisioning channels. ([Microsoft Learn][9])

# **18. Monitor governance itself**

I would monitor:

```text
Policy compliance
Policy exemptions
management-group changes
policy-assignment changes
RBAC changes
subscription moves
new subscriptions
```

Why?

An attacker with enough privilege might not violate the policy.

They might:

```text
remove the policy first.
```

The governance plane itself is high-value infrastructure.

# **19. Break-glass / privileged operations**

A normal app developer does not need:

```text
Management Group Contributor
Policy Contributor
User Access Administrator
```

For rare platform operations, use controlled elevated access:

```text
Microsoft Entra PIM
       ↓
approval/MFA
       ↓
time-bound role
```

where appropriate.

This minimizes persistent privilege.

# **20. Practical example**

Requirement:

> Teams can create Key Vault, but production Key Vaults must not be publicly exposed.

Flow:

```text
Developer
   ↓
Bicep
   ↓
Key Vault
publicNetworkAccess=Enabled
   ↓
Azure RBAC
   ↓
Authorized to create Key Vault
   ↓
Azure Policy
   ↓
Production rule violated
   ↓
DENY
```

Developer changes:

```text
public access off
+
Private Endpoint
+
appropriate DNS
```

Then:

```text
Policy passes
      ↓
deployment succeeds
```

The platform team never had to manually approve the Key Vault.

That's autonomy with guardrails.

## **Interview answer condensed**

> “I would enforce centralized governance using management-group-level Azure Policy while delegating application subscriptions to development teams. RBAC determines what a team is authorized to manage, while Policy constrains which configurations are acceptable. That means a developer can have enough permission to create AKS, Key Vault or Storage in their subscription, but an inherited policy can still deny an insecure configuration. I'd automate subscription vending so teams get the correct policy, networking, RBAC and budget baseline without tickets, use app-specific federated CI identities, provide reusable golden-path modules, and maintain a governed sandbox for experimentation. I would roll new deny policies out through test and audit first because a bad centralized policy can impact every team at once.”

**Memory line:**
**Give teams control of their subscriptions; keep organization-wide rules above them as automated guardrails.**

**Interview trap:**
Azure RBAC alone cannot enforce that a developer chooses a **secure configuration**—RBAC controls who can act, while Azure Policy controls what configurations are allowed.
