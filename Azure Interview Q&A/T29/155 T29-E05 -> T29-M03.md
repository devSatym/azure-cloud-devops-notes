# **T29-E05. What is an application landing zone?**

**Answer:**

An application landing zone is the **Azure environment allocated to a specific workload or application team**, where that team deploys and operates its resources while inheriting governance and security guardrails from the broader platform landing zone.

For example, an application landing zone might contain the Dev, Test, and Production subscriptions for one application, along with workload-owned resources such as AKS, App Service, databases, Storage Accounts, Key Vault, and application-specific networking.

The platform team provides the foundation and guardrails; the workload team operates inside those boundaries.

```text
Platform Landing Zone
        ↓
Management Groups
Azure Policy
Shared Connectivity
Identity / Governance
        ↓
Application Landing Zone
        │
        ├── Dev Subscription
        ├── Test Subscription
        └── Prod Subscription
               ↓
           Workload resources
```

Microsoft's current landing-zone guidance describes each workload as having one application landing zone containing the environments required by that workload; each environment can consist of one or more subscriptions depending on ownership, workload requirements, or subscription limits. ([Microsoft Learn][1])

---

## **Platform landing zone vs application landing zone**

This distinction is the most important part.

```text
Platform Landing Zone
→ shared foundation for the organization

Application Landing Zone
→ environment for one workload
```

For example:

```text
Platform
├── Management Groups
├── Azure Policy
├── Shared DNS
├── Hub / Virtual WAN
├── Monitoring baseline
└── Security controls

Application A Landing Zone
├── Dev
├── Test
└── Prod

Application B Landing Zone
├── Dev
└── Prod
```

The workload teams shouldn't need to redesign the Azure foundation themselves.

---

## **What might an application team own?**

Typical workload-owned resources:

```text
Application Landing Zone
│
├── AKS / App Service / VMs
├── Application Gateway
├── Storage
├── Azure SQL / Cosmos DB
├── Key Vault
├── workload subnets
├── managed identities
└── application monitoring
```

The exact responsibility split depends on the organization's operating model.

Microsoft currently describes three broad management approaches:

* central-team managed,
* application-team managed,
* shared management. ([Microsoft Learn][2])

So application landing zone does **not necessarily mean**:

> “The application team has unrestricted control over everything.”

---

## **Inheritance of governance**

Suppose the subscription is placed under:

```text
Landing Zones
      ↓
Online
      ↓
App-A-Prod Subscription
```

Azure Policies assigned higher in the management-group hierarchy are inherited by the subscription.

For example:

```text
Management Group Policy
│
├── allowed regions
├── mandatory diagnostics
├── public access restrictions
└── security baseline
        ↓
App subscription inherits them
```

The application team can therefore have meaningful autonomy without being able to bypass organizational controls. Microsoft explicitly describes application landing zones inheriting governance and security policies based on where their subscriptions are placed in the hierarchy. ([Microsoft Learn][1])

---

## **Why subscriptions are useful boundaries**

An application landing zone commonly uses subscriptions because a subscription provides useful boundaries for:

```text
RBAC
Policy
Quotas
Billing
Resource organization
Blast radius
```

For example:

```text
App A
├── app-a-nonprod-sub
└── app-a-prod-sub
```

is much stronger isolation than:

```text
one huge subscription
├── App A
├── App B
├── App C
└── Shared resources
```

especially when teams have different permissions and compliance requirements.

---

## **Example**

For an e-commerce workload:

```text
E-Commerce Application Landing Zone
│
├── NonProd Subscription
│    ├── Dev AKS
│    ├── Test SQL
│    └── Test Storage
│
└── Prod Subscription
     ├── AKS
     ├── ACR
     ├── Key Vault
     ├── Azure SQL
     └── Application Gateway
```

Above it:

```text
Landing Zones Management Group
       ↓
Azure Policy
       ↓
E-Commerce subscriptions
```

The application team operates the workload while centralized governance remains enforced.

**Memory line:**
**A platform landing zone builds the road; an application landing zone is where a specific workload drives on that road.**

**Interview trap:**
An application landing zone is **not necessarily one subscription**. It represents the workload's Azure environment and can contain multiple subscriptions across Dev, Test, and Production.

**Keywords:**
Application landing zone, workload, subscriptions, platform landing zone, Azure Policy, RBAC, Dev, Test, Prod, workload team.

# **T29-M01. Why are management groups important in enterprise landing zones?**

**Answer:**

Management groups are important because they give an enterprise a **hierarchical governance layer above Azure subscriptions**.

Instead of assigning Azure Policy and RBAC separately to hundreds of subscriptions, I can organize subscriptions according to platform or workload requirements and apply governance at a management-group level. Those controls are then inherited by subscriptions underneath.

That makes management groups one of the key scaling mechanisms in Azure landing zones.

For example:

```text
Tenant Root
    ↓
Contoso
├── Platform
│   ├── Connectivity
│   ├── Management
│   └── Security
│
├── Landing Zones
│   ├── Online
│   └── Corp
│
└── Sandbox
```

I could enforce common policies at `Landing Zones`, more specific policies at `Online` or `Corp`, and keep sandbox subscriptions under a different governance model.

Microsoft's current Cloud Adoption Framework describes management groups as a critical structure for organizing and governing subscriptions as an Azure estate scales. ([Microsoft Learn][3])

---

## **Why subscriptions alone don't scale**

Imagine 200 subscriptions.

Without management groups:

```text
Subscription 001
→ assign policy A
→ assign policy B
→ assign RBAC

Subscription 002
→ repeat

...

Subscription 200
→ repeat
```

Problems:

```text
duplication
configuration drift
policy inconsistency
operational overhead
```

With management groups:

```text
Management Group
      ↓
Policy A
Policy B
RBAC baseline
      ↓
200 subscriptions inherit
```

That's dramatically easier to govern.

---

# **1. Policy inheritance**

Suppose the organization requires:

```text
Allowed locations:
Central India
West Europe
East US
```

Instead of assigning that policy to every workload subscription:

```text
Landing Zones MG
      ↓
Allowed Locations Policy
      ↓
├── Subscription A
├── Subscription B
├── Subscription C
└── Subscription D
```

All children inherit the rule.

Azure's hierarchy gives:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Resource
```

and policy/RBAC assigned at higher scopes can flow downward.

---

# **2. Different workload classes can receive different guardrails**

Not every application has the same connectivity or compliance profile.

For example:

```text
Landing Zones
│
├── Online
│     ↓
│   Internet-facing workloads
│
└── Corp
      ↓
    Internal/private workloads
```

Then policies can differ.

### Online

Maybe requires:

```text
WAF
DDoS considerations
public-facing controls
internet exposure policies
```

### Corp

Maybe requires:

```text
private connectivity
central DNS
hub connectivity
restricted public access
```

Microsoft specifically recommends organizing workload subscriptions according to shared security, compliance, connectivity, or feature requirements rather than mirroring a complicated organizational chart. ([Microsoft Learn][3])

---

# **3. Separate platform from workloads**

A strong hierarchy keeps shared platform subscriptions separate from application subscriptions.

```text
Enterprise
│
├── Platform
│   ├── Connectivity subscription
│   ├── Management subscription
│   └── Security subscription
│
└── Landing Zones
    ├── App A
    ├── App B
    └── App C
```

Microsoft's reference hierarchy includes a `Platform` management group specifically to contain foundational platform areas such as connectivity, management, identity/security. ([Microsoft Learn][4])

Why?

Because:

```text
shared platform resources
```

have very different:

```text
owners
permissions
change cadence
risk
```

from application resources.

---

# **4. Central governance without removing workload autonomy**

This is a major landing-zone benefit.

Suppose the platform team assigns:

```text
Azure Policy
at management-group scope
```

but gives the application team:

```text
Owner/Contributor-like workload administration
at its subscription/resource scope
```

Conceptually:

```text
Platform Team
   ↓
MG-level Policy
   ↓
Cannot be modified by app team

App Team
   ↓
Subscription-level permissions
   ↓
Can deploy its workload
```

Microsoft's current landing-zone identity guidance recommends role assignments for application teams at subscription/resource-group scope while governance policy remains higher in the hierarchy. ([Microsoft Learn][5])

That gives:

> **autonomy inside guardrails.**

---

# **5. RBAC can also inherit**

Management groups can also be used for Azure RBAC.

For example:

```text
Security Readers group
        ↓
Security Reader role
@ Landing Zones MG
        ↓
all application subscriptions
```

Now the security team doesn't need hundreds of individual assignments.

However, I would use high-level RBAC carefully.

For example:

```text
Owner
@ tenant-root-level management group
```

creates enormous blast radius.

Broad inherited permissions should be exceptional and strongly protected, ideally with controls such as PIM where appropriate.

---

# **6. Management groups should not mirror every business department**

A common mistake is building:

```text
Company
├── Finance
│   ├── Team A
│   │   └── App 1
│   └── Team B
├── HR
├── Sales
├── Europe
├── India
...
```

just because that is the organizational chart.

Then a reorganization forces the Azure governance hierarchy to change.

Microsoft recommends structuring management groups primarily around **governance requirements**, and using tags for horizontal organization/querying when appropriate. ([Microsoft Learn][3])

A better question is:

> “Which subscriptions need the same governance?”

not:

> “Which manager owns this application?”

---

# **7. Avoid excessive depth**

Another bad design:

```text
Root
 ↓
Region
 ↓
Business Unit
 ↓
Department
 ↓
Team
 ↓
Environment
 ↓
Application
 ↓
Subscription
```

This makes inheritance hard to understand.

A policy assigned five levels above a subscription can become difficult to troubleshoot.

Keep the hierarchy intentional and relatively simple.

Microsoft explicitly advises limiting unnecessary hierarchy complexity and limiting broad root-level policy assignments because inherited policy becomes harder to debug lower down. ([Microsoft Learn][3])

---

# **8. Production example**

Suppose I support 100 product teams.

I might design:

```text
Tenant Root
    ↓
Contoso
│
├── Platform
│   ├── Connectivity
│   ├── Management
│   └── Security
│
├── Landing Zones
│   ├── Online
│   │    ├── App subscriptions
│   │    └── ...
│   │
│   └── Corp
│        ├── App subscriptions
│        └── ...
│
└── Sandbox
```

Policy flow:

```text
Contoso
→ universal baseline

Landing Zones
→ workload baseline

Online
→ internet-facing controls

Corp
→ internal/private connectivity controls

Sandbox
→ relaxed experimentation controls
```

This scales much better than manually governing individual subscriptions.

---

## **Interview answer condensed**

> “Management groups are important because they let me govern Azure subscriptions hierarchically. Instead of assigning the same Policy and RBAC separately to hundreds of subscriptions, I can group subscriptions according to shared governance requirements and let controls inherit downward. In a landing zone I would normally separate platform subscriptions from workload subscriptions, and potentially separate workload archetypes such as internet-facing and internal workloads when they require different policies. I avoid modeling every business unit or environment as another management-group level because the hierarchy should represent governance requirements, not simply the company org chart.”

**Memory line:**
**Management groups let governance scale from dozens to hundreds of subscriptions through inheritance.**

**Interview trap:**
Management groups should primarily model **governance boundaries**, not blindly reproduce the organization's reporting hierarchy.

**Keywords:**
Management groups, subscriptions, hierarchy, Azure Policy, Azure RBAC, inheritance, platform, landing zones, governance.

**Likely follow-ups:**

* Why not assign policies directly to every subscription?
* Should Dev and Prod always have separate management groups?
* What risks come from RBAC assignments at management-group scope?
* Why shouldn't management groups mirror the company's org chart?

# **T29-M02. What responsibilities should a platform team centralize?**

**Answer:**

A platform team should centralize capabilities that are **shared across workloads, create enterprise-wide risk if implemented inconsistently, or benefit strongly from standardization**, while leaving application-specific decisions to workload teams.

Typical centralized responsibilities include the management-group and subscription architecture, Azure Policy baseline, identity and privileged-access patterns, shared connectivity and DNS, security and monitoring baselines, subscription vending, platform IaC, and common cost/governance controls.

I would not centralize every workload decision. Application teams should still own things such as their application architecture, workload-specific resources, deployment pipelines, SLOs, and runtime configuration within the platform guardrails.

```text
                Platform Team
                     │
      ┌──────────────┼──────────────┐
      ↓              ↓              ↓
  Governance      Shared          Platform
                  Services        Automation
      │              │              │
   Policy          DNS            IaC
   RBAC           Network         Subscription vending
   standards      Security        Golden paths
      │              │              │
      └──────────────┼──────────────┘
                     ↓
             Application Teams
                     ↓
              Workload autonomy
```

Microsoft's landing-zone design areas identify identity, resource organization, security, management, governance, connectivity, and platform automation/DevOps as foundational design concerns. ([Microsoft Learn][6])

---

# **1. Resource organization and subscription vending**

The platform team should normally define:

```text
Management-group hierarchy
Subscription placement
Naming/tagging requirements
Subscription creation process
Baseline policy assignments
```

Application teams shouldn't have to raise a manual infrastructure ticket that takes three weeks every time they need a subscription.

A mature platform might offer:

```text
Developer requests landing zone
       ↓
Automated workflow
       ↓
Create subscription
       ↓
Place in correct MG
       ↓
Apply baseline
       ↓
Create workload RBAC groups
       ↓
Configure connectivity/logging
       ↓
Hand to team
```

This is often called **subscription vending**.

The platform is centralized; consumption becomes self-service.

---

# **2. Enterprise governance**

The platform team should centralize guardrails such as:

```text
Azure Policy
├── allowed regions
├── resource restrictions
├── diagnostic baselines
├── security configuration
└── required metadata
```

Why centralize?

Because if every team independently decides:

```text
whether public Storage is acceptable
whether diagnostics are required
which regions are compliant
```

the company doesn't really have governance.

---

# **3. Identity and access patterns**

The platform team should establish:

```text
Entra groups
RBAC role-assignment model
PIM for privileged roles
Managed Identity standards
workload identity/federation patterns
break-glass process
```

But they shouldn't personally approve every developer's routine deployment.

For example:

```text
Platform Team
→ defines access model

Application Team
→ gets subscription-scoped groups
→ manages workload within boundary
```

Microsoft's current landing-zone identity guidance recommends provisioning workload-specific groups and role assignments for each application landing zone while preserving higher-level governance. ([Microsoft Learn][5])

---

# **4. Shared networking**

Typical centralized capabilities include:

```text
Hub network / Virtual WAN
Azure Firewall
ExpressRoute / VPN
Central DNS
Private DNS patterns
DDoS strategy
egress controls
```

Why?

Because networking is inherently shared.

If 100 teams independently build:

```text
100 different DNS designs
100 VPNs
100 egress patterns
```

you create:

* overlapping CIDRs,
* inconsistent security,
* routing complexity,
* difficult troubleshooting.

The platform team should provide the shared network foundation while allowing teams to manage their workload-specific network components where appropriate.

---

# **5. Security baseline**

Centralize things such as:

```text
Defender for Cloud baseline
Azure Policy security initiative
central logging/SIEM integration
security monitoring standards
vulnerability-management integration
```

But workload-specific threat modeling remains a workload responsibility.

For example:

```text
Platform:
require diagnostics

Application:
decide what application security events mean
```

The central team cannot understand every business application's threat model better than the owning team.

---

# **6. Management and observability baseline**

A platform team may centralize:

```text
resource inventory
activity-log strategy
central security logs
monitoring agent/policy baseline
common alert-routing patterns
backup governance
```

Microsoft describes the landing-zone management design area as providing a baseline for visibility, operations compliance, and protection/recovery capabilities. ([Microsoft Learn][7])

But:

```text
application-specific metrics
application dashboards
SLOs
business alerts
```

should generally remain with the application team.

---

# **7. Platform automation and golden paths**

The platform team should provide reusable automation such as:

```text
Bicep / Terraform modules
CI/CD templates
standard AKS module
standard Key Vault module
standard private networking module
```

Conceptually:

```text
Platform Team
      ↓
Versioned golden modules
      ↓
Application Team
      ↓
self-service deployment
```

This creates consistency without forcing everyone to become an expert in every Azure service.

---

# **8. Cost and FinOps guardrails**

Platform teams often centralize:

```text
budgets
cost-allocation tag policy
shared cost reporting
reserved-capacity guidance
subscription ownership mapping
```

But workload teams should be accountable for the cost of architecture decisions they make.

So:

```text
Platform
→ provides visibility and guardrails

Workload team
→ owns workload economics
```

---

# **What should NOT be centralized?**

This is just as important.

I would avoid the platform team becoming responsible for every:

```text
application deployment
database schema
application config
microservice scaling value
application SLO
release decision
```

Otherwise:

```text
Developer
 ↓
ticket
 ↓
Platform team
 ↓
ticket queue
 ↓
deployment
```

The platform team becomes a bottleneck.

A better model is:

```text
Centralized standards
        +
Decentralized execution
```

---

# **Decision rule**

I ask:

### Centralize when:

```text
Used by many teams
OR
creates organization-wide risk
OR
requires enterprise integration
OR
benefits heavily from standardization
```

### Delegate when:

```text
workload-specific
+
low enterprise blast radius
+
application team has best context
```

---

## **Interview answer condensed**

> “I would centralize capabilities that are shared across workloads or create enterprise risk if they're inconsistent: management groups and subscription vending, Azure Policy, identity and RBAC patterns, shared connectivity and DNS, security and monitoring baselines, and reusable platform IaC. The goal isn't for the platform team to own every resource. Application teams should still own their workload architecture, application deployment, SLOs, application monitoring and service-specific configuration within those guardrails. A good platform team provides paved roads and self-service rather than becoming a ticket queue.”

**Memory line:**
**Centralize the guardrails and shared capabilities; decentralize workload ownership.**

**Interview trap:**
A centralized platform team should **not become the team that deploys every application resource for everyone**—that destroys team autonomy and creates a bottleneck.

**Keywords:**
Platform team, subscription vending, Azure Policy, RBAC, shared networking, DNS, security baseline, monitoring, IaC, golden path, self-service.

**Likely follow-ups:**

* What should the application team still own?
* What is subscription vending?
* Why should DNS and connectivity often be centralized?
* How do you stop the platform team becoming a bottleneck?

# **T29-M03. How would you separate platform resources from workload resources?**

**Answer:**

I would separate platform and workload resources primarily using **management groups, subscriptions, RBAC ownership boundaries, and separate IaC lifecycles**.

Shared resources such as central connectivity, security/SIEM, management services, and enterprise DNS would live in dedicated platform subscriptions under a `Platform` management group. Application resources would live in separate application landing-zone subscriptions under workload management groups.

That prevents workload teams from accidentally modifying shared infrastructure and prevents platform changes from becoming tightly coupled to application deployments.

```text
Microsoft Entra Tenant
        ↓
Intermediate Root
│
├── Platform
│   │
│   ├── Connectivity Subscription
│   │    ├── Hub / Virtual WAN
│   │    ├── Azure Firewall
│   │    └── DNS
│   │
│   ├── Management Subscription
│   │    └── Central management resources
│   │
│   └── Security Subscription
│        └── Sentinel / security tooling
│
└── Landing Zones
    │
    ├── App-A Subscription
    │    ├── AKS
    │    ├── Key Vault
    │    └── Database
    │
    └── App-B Subscription
         └── workload resources
```

Microsoft's current landing-zone reference guidance specifically separates platform resources from workload resources in the management-group hierarchy and places shared platform capabilities under dedicated platform areas. ([Microsoft Learn][4])

---

# **1. Separate by responsibility first**

I start by asking:

> Who owns and operates this resource?

For example:

### Platform-owned

```text
Hub / Virtual WAN
Azure Firewall
ExpressRoute
VPN Gateway
central DNS
central monitoring/security infrastructure
landing-zone automation
```

### Workload-owned

```text
AKS
App Service
application Storage
application Key Vault
Azure SQL
Application Gateway
workload subnets
application alerts
```

Ownership drives the boundary.

---

# **2. Put platform services in dedicated subscriptions**

For example:

```text
Platform MG
│
├── Connectivity Subscription
├── Management Subscription
└── Security Subscription
```

Why not one giant shared subscription?

Because different shared functions often have different:

```text
owners
RBAC
budgets
change cadence
blast radius
```

For example, the networking team may need strong access to:

```text
Hub
Firewall
ExpressRoute
DNS
```

without needing administrative access to:

```text
Sentinel
security automation
management tooling
```

Subscription separation makes that cleaner.

---

# **3. Workload resources get application subscriptions**

For App A:

```text
App A Application Landing Zone
│
├── NonProd Subscription
└── Prod Subscription
```

For App B:

```text
App B Application Landing Zone
│
├── NonProd Subscription
└── Prod Subscription
```

This makes application ownership and blast radius much clearer.

---

# **4. Apply different RBAC boundaries**

Platform resources:

```text
Connectivity Team
      ↓
Network platform subscription
```

Application resources:

```text
App A Team
      ↓
App A subscription
```

Crucially:

```text
App A Team
    X
No Contributor on shared hub
```

They may be allowed to:

```text
create workload resources
manage workload subnets
deploy AKS
manage workload identities
```

but cannot:

```text
change corporate firewall policy
modify ExpressRoute
delete central DNS
```

---

# **5. Governance should flow downward**

The platform team doesn't need administrative access to every application resource just to enforce governance.

Instead:

```text
Management Group
      ↓
Azure Policy
      ↓
Application subscription
```

For example:

```text
Landing Zones MG
├── required diagnostic policy
├── allowed region policy
└── security restrictions
      ↓
App A
App B
App C
```

Application teams retain resource ownership while Policy enforces centralized standards. This is exactly the autonomy-with-guardrails model Microsoft describes for application landing zones. ([Microsoft Learn][5])

---

# **6. Connect workloads to platform services without merging ownership**

Suppose:

```text
Connectivity Subscription
      ↓
Hub VNet
```

and:

```text
App A Subscription
      ↓
Spoke VNet
```

They can connect:

```text
Hub VNet
   ↕ peering
App A Spoke
```

without moving everything into one subscription.

Likewise:

```text
Central Private DNS Zone
       ↕
Spoke VNet links
```

can be platform-owned while applications consume it.

So:

```text
Shared capability
≠
shared administrative ownership
```

---

# **7. Use separate IaC repositories or deployment boundaries**

I would also separate deployment lifecycles.

For example:

```text
platform-infra repo
│
├── management-groups
├── policy
├── hub-network
├── firewall
└── dns
```

and:

```text
app-a-infra repo
│
├── aks
├── database
├── storage
└── app-network
```

Why?

Because otherwise an application deployment may accidentally contain:

```text
change AKS version
+
modify central firewall
```

in one pull request.

Those changes have very different:

```text
owners
approvers
risk
maintenance windows
```

---

# **8. Use separate deployment identities**

Platform pipeline:

```text
platform-infra pipeline
       ↓
platform workload identity
       ↓
Platform subscriptions
```

Application pipeline:

```text
App A pipeline
       ↓
App A workload identity
       ↓
App A subscription
```

Not:

```text
one CI identity
      ↓
everything in Azure
```

This limits supply-chain blast radius.

If App A's GitHub Actions pipeline is compromised:

```text
Compromised App A pipeline
        ↓
App A subscription permissions
        X
cannot modify central firewall
```

That's a very strong security benefit.

---

# **9. Avoid putting shared platform resources in application resource groups**

Bad:

```text
rg-app-a-prod
├── App A VM
├── App A SQL
├── corporate DNS zone
└── ExpressRoute Gateway
```

Now deleting:

```text
rg-app-a-prod
```

could destroy shared infrastructure.

Shared lifecycle means shared failure domain.

Platform resources should normally have an independent lifecycle.

---

# **10. Separate cost ownership**

Subscriptions make cost allocation easier.

```text
Connectivity Subscription
→ platform shared cost

App A Prod Subscription
→ App A workload cost

App B Prod Subscription
→ App B workload cost
```

Shared connectivity costs may later be allocated internally according to organizational FinOps policy.

Without separation, chargeback/showback becomes much harder.

---

# **11. Don't over-separate every resource**

Separation has a cost.

Creating:

```text
one subscription per Storage Account
```

would be absurd.

Each boundary adds:

* RBAC management,
* billing/accounting overhead,
* policy complexity,
* networking complexity,
* subscription lifecycle overhead.

The boundary should correspond to a meaningful:

```text
ownership
governance
billing
security
or scale
```

requirement.

```text
│   │   └── Private DNS
│   │
│   ├── Management Subscription
│   │   └── shared operations resources
│   │
│   └── Security Subscription
│       └── Sentinel / SIEM
│
└── Landing Zones MG
    │
    ├── Online
    │   ├── App-A-Prod
    │   └── App-B-Prod
    │
    └── Corp
        ├── ERP-Prod
        └── HR-Prod
```

Traffic can still flow:

```text
App-A Spoke
     ↓
Hub / Firewall
     ↓
On-prem / Internet / Shared services
```

while administrative ownership remains separated.

---

# **Failure/blast-radius reasoning**

Suppose App A has:

```text
Contributor
on App-A subscription
```

A developer accidentally runs:

```text
delete resource group
```

Worst-case impact should remain approximately:

```text
App A
```

not:

```text
Hub
Firewall
DNS
App B
Corporate connectivity
```

That is why subscription and RBAC boundaries matter.

---

## **Interview answer condensed**

> “I would separate platform and workload resources using Azure's hierarchy and ownership boundaries. Shared connectivity, management and security services would sit in dedicated platform subscriptions under a Platform management group, while each workload would use application landing-zone subscriptions under the Landing Zones hierarchy. Application teams would get RBAC only in their workload scope, while platform teams manage shared services and enforce common Policy from higher scopes. I would also use separate IaC repositories or deployment boundaries and separate workload identities so an application pipeline cannot modify shared networking or security infrastructure. The goal is independent ownership, lifecycle and blast radius while still allowing workloads to consume shared platform capabilities.”

**Memory line:**
**Separate by ownership and blast radius; connect through services and networking, not shared admin permissions.**

**Interview trap:**
“Shared service” does **not mean it should live in the same subscription or be writable by every team that consumes it**.

**Keywords:**
Platform subscriptions, workload subscriptions, management groups, RBAC, Azure Policy, connectivity subscription, security subscription, IaC boundary, blast radius.

**Likely follow-ups:**

* Why put connectivity in a separate subscription?
* Should application teams have access to the hub network?
* How would workload VNets consume centrally managed DNS?
* Why separate platform and application CI identities?
